> **Title**: Compose strip on by default — first-render notice, focus on fresh navigation, one name
>
> **Premise (decided)**: terminal input via xterm is the wrong default for the dominant use (prompting an agent); the compose strip is the keyboard and the terminal is the control surface (y/n, arrows, Ctrl-C, vim, passwords). The strip is already non-modal (Escape blurs to the terminal, ⌘I re-focuses, drafts lossless), and change 1 gave it an in-place collapsed tongue. This change flips the default and fixes the two things default-on exposes: where focus lands, and what the thing is called.
>
> **What changes**: (1) `readComposeStrip()` — absent/unreadable key ⇒ `true`; explicit `"false"` stays off. (2) One-time first-render notice toast `Compose is on by default — ⌘I hides it` with the platform-resolved `compose-toggle` chord, shown once per browser behind a persisted sentinel, never to users with a stored preference. (3) On a **fresh navigation** to a terminal route (a never-visited `{server, windowId}` — not a remount, not a dock/layout flip, not a board↔terminal round-trip to a window already in focus memory) with the strip expanded and a target present, the textarea takes focus only if nothing else has focus — never stealing from xterm, the palette, a dialog, or an iframe; the remount no-steal rule stays byte-for-byte; integrate with the restore router's first-visit default (verify it runs on fresh navigation first). (4) One name — `View: Text Input` → `Compose: Toggle`; the chips' "Compose text" → "Compose"; action id / chord / behavior unchanged; update every assertion. (5) Fine-pointer placeholder gains `· Esc → terminal`; coarse unchanged. (6) Unchanged: Enter semantics (re-examine after a week), the status-bar `a▏` chip (redundancy noted), coarse tongue + bottom-bar chip duplication (deferred pending device screenshots), the tongue, drafts, uploads, send path.
>
> **Blast radius**: e2e specs that `goto` a terminal route and then type/press without clicking the terminal will type into the textarea; non-punch-through chords are suppressed while the textarea has focus. Unit tests assuming default-off must seed `"false"`. Test Integrity: tests follow the spec.
>
> **Rejected**: per-pane-kind defaults; Enter = submit on agent panes; a modal onboarding step; focusing the textarea on every mount.

## Why

**The pain point.** The dominant use of a run-kit terminal is prompting an agent: multi-line text, pasted blocks, dictation, edits before sending. xterm is a `<canvas>` with a hidden helper textarea — no IME, no autocorrect surface, character-by-character over the relay, and no local editing of a half-written prompt. The compose strip solves all of that and already exists, but it is **opt-in**: `readComposeStrip()` returns `false` for an absent key (`chrome-context.tsx` L71–77), so every new browser lands on the collapsed tongue and the user has to discover the toggle before the good input surface appears. The terminal stays the *control* surface — y/n answers, arrows, Ctrl-C, vim, passwords all belong in xterm — and the strip's existing hand-off (Escape blurs to the pane, ⌘I refocuses the strip) already makes the two coexist without modality. The default is simply wrong for what people do first.

**The consequence of not fixing it.** Change 1's tongue teaches how to re-open the strip, but only to users who already found it once. Default-off means the first-run experience is the worse input surface, and the tongue's value (in-place education for a dismissed default) is mostly wasted.

**What default-on exposes — the two things this change must fix at the same time.**

1. *Focus.* Verified at intake (not merely assumed): on the desktop terminal route the restore router in `app.tsx` (`useEffect` keyed `[server, windowParam, isMobile, restoreFocus]`, L1738–1754) **does** run on a fresh navigation, including the initial page load, and resolves `recallFocus(key) ?? "tty"` — so today a first visit focuses **xterm** (`focus-restore.spec.ts` test (a) proves it: "the first visit to a window focuses the terminal on its own"). The strip itself focuses only on the off→on toggle transition ("focus on open, and only on open"). With the strip expanded by default, the user would therefore see a text box and have their first keystroke land in the pane. The fix is to make the router's **first-visit default** resolve to `compose` when the strip is expanded with a target — not to add a second focus mechanism. The remount/return path (a recorded kind, or a return to a window already in memory) is untouched: the strip never steals on remount.
2. *Naming.* The same preference is called `View: Text Input` in the palette, "Compose text" on both `a▏` chips and in the keybinding registry label, and `Compose` on the tongue (change 1 made "Compose" the visible in-place name). Default-on makes the toggle a thing everyone meets in their first minute, so it needs one name: **Compose**.

**Why this approach over the alternatives.**
- *Per-pane-kind defaults* (agent panes on, shells off) — a second policy path for one preference; the "global default + agent-aware focus" variant was considered and rejected for v1 as overcomplicating. Revisit only with evidence that shells suffer.
- *Enter = submit on agent panes* — contradicts the recorded terminal-faithful classifier decision ([compose-and-bottom-bar](/run-kit/ui/compose-and-bottom-bar.md) § Design Decisions → "Enter stages a line in the strip…"). Kept as-is; re-examine after a week of living with default-on.
- *A modal onboarding step* — the tongue already teaches the toggle in place; one info toast naming the chord is enough.
- *Focusing the textarea on every mount* — steals focus on terminal↔board remounts and dock flips; the recorded no-steal rule exists precisely against this.

## What Changes

### 1. Default flips to on (`contexts/chrome-context.tsx`)

Today:

```ts
function readComposeStrip(): boolean {
  try {
    return localStorage.getItem(COMPOSE_STRIP_STORAGE_KEY) === "true";
  } catch {
    return false;
  }
}
```

After — **absent, unreadable, or non-`"false"` ⇒ on; an explicit `"false"` ⇒ off**:

```ts
function readComposeStrip(): boolean {
  try {
    return localStorage.getItem(COMPOSE_STRIP_STORAGE_KEY) !== "false";
  } catch {
    return true;
  }
}
```

- Users who chose off keep it: `toggleComposeStrip()` already writes `String(next)` — an explicit `"false"` — on the on→off transition (L271), so every existing opt-out is preserved without migration. A stored `"true"` reads on, as today. A corrupt value (e.g. `"banana"`) reads as the default (on) — the inverse of the scroll-lock rule, because the default is now on.
- **Expose whether the value was defaulted.** The first-render notice (§ 2) must fire only when the strip is on *because of the default*. `ChromeProvider` records at mount whether the key was absent/unreadable (`getItem === null` or threw) and exposes it on `ChromeState` as a read-only boolean — `composeStripDefaulted` (name is apply's) — beside `composeStripEnabled`. It is computed once (`useState(() => …)` / a ref), never updated: the first explicit toggle writes the key, and the notice's own sentinel prevents a second showing regardless.
- The operator page's `forceExpanded` and the tongue forms are unchanged — the wrapper's decision table in `compose-strip.tsx` L269–272 needs no edit; it simply sees `composeStripEnabled === true` more often.
- `toggleComposeStrip` is unchanged (still marks the focus-on-open flag on off→on, still persists `"true"`/`"false"`).

### 2. One-time first-render notice (toast)

- **Copy**: `Compose is on by default — {chord} hides it`, where `{chord}` is `chordHintFor("compose-toggle", bindings, host.platform)` from `useKeybindings()` (`lib/keybindings.ts` L1030 — the same seam the tongue and both chips use). Expected faces: `⌘I` on mac, `⇧Ctrl+E` on win/linux (Playwright's Desktop Chrome pins a Windows UA, so the e2e asserts the win/linux face — the `tooltips.spec.ts` precedent). When the binding is unbound/disabled the chord clause is **omitted**: `Compose is on by default` (a hint advertising a dead chord would lie).
- **Seam**: `useToast().addToast(message, "info")` — the strip already imports `useToast` (`compose-strip.tsx` L20); the variant MUST be `"info"` (the default is `"error"`). No action button, no `onDismiss`. `TOAST_DURATION` is 4000 ms (the existing toast timing; not changed).
- **Where it fires**: from `ComposeStripExpanded`'s mount effect (a `useEffect` with `[]` deps, beside the focus-on-open consume at L975), gated on ALL of: (a) `!forceExpanded` — the operator page forces the strip on regardless of the default, and "⌘I hides it" would be false there (the toggle flips the preference, the forced strip stays); (b) `composeStripDefaulted === true` from `ChromeState`; (c) the sentinel is absent. It then writes the sentinel **before** calling `addToast`, so StrictMode's double-invoked effect (e2e/dev run under `<StrictMode>`) cannot show it twice. It fires on whichever route first renders the expanded body — the desktop terminal route's in-tile dock, the board footer, the coarse footer dock — exactly once per browser.
- **Sentinel**: a persisted localStorage key — `runkit-compose-default-notice` (name is apply's; the `runkit-` prefix is the chrome-preference convention), value `"1"`. Read/written inside `try/catch` like every other `runkit-*` key. Never shown to a user with a stored preference either way (gate (b)), never shown twice (gate (c)).
- Not shown on the no-target tongue or the collapsed tongue (neither is "the strip rendered enabled").

### 3. Focus on fresh navigation — the restore router's first-visit default

**Seam (verified at intake — recorded as Assumption 6).** `app.tsx`'s restore router is the right place, and no separate `app.tsx` first-visit effect is needed:

- The effect at L1738–1754 is keyed `[server, windowParam, isMobile, restoreFocus]`, runs on mount (the `page.goto` case) and on every window switch, is **desktop-only** (`if (!windowParam || isMobile) return;` — auto-focus pops the mobile keyboard), arms the steal guard, calls `restoreFocus(key)`, and installs capture-phase `pointerdown`/`keydown` listeners that cancel a pending restore on the first genuine interaction.
- `restoreFocus` (L1705–1735) resolves `const recalled = recallFocus(key) ?? "tty"`, then: `code` → no-op; `compose` → `focusComposeStrip()` with a tty fallback when the focuser declines; else the tty rAF retry loop bounded by `FOCUS_RESTORE_RETRY_MS` (5000).
- `revertProgrammaticFocus` (L1776–1783, the code-tile steal-guard revert) repeats `recallFocus(key) ?? "tty"`.

**New rule.** The `?? "tty"` first-visit default becomes a resolver — `firstVisitKind()` (name is apply's) — returning `"compose"` when the strip is **expanded with a target**, `"tty"` otherwise. Both call sites (`restoreFocus`, `revertProgrammaticFocus`) use it so the steal-guard revert lands on the same surface the fresh navigation did. Concretely:

- "Expanded with a target" is decided by the strip, not guessed by the router: `focusComposeStrip()` already returns `false` when the body is unmounted (collapsed tongue, no-target tongue) or disabled. The router's compose-first-visit arm therefore **tries the registered focuser and falls back to tty when it declines** — the same decline→tty rule the existing `compose` arm has. The router only needs to know whether to *prefer* compose: read `composeStripEnabled` (already in `app.tsx` scope) through a ref, since `restoreFocus` is a stable callback that reads refs + module state only. When the preference is off the resolver is `"tty"` immediately (no attempt).
- **Retry until ready.** On a fresh navigation the expanded body mounts *after* the terminal registers into `FocusedTerminalContext` (the body renders only once `focused !== null`), so a one-shot `focusComposeStrip()` at effect time would decline and fall to tty every time. The compose-first-visit arm rides the **same rAF retry loop and deadline** the tty arm uses: each frame, if `focusComposeStrip()` succeeds → done; else keep retrying until `FOCUS_RESTORE_RETRY_MS` elapses, then fall back to the tty arm (which has its own retry-until-ref semantics). The recorded-`compose` arm (a return to a window whose memory says `compose`) may keep its one-shot decline→tty behavior, or share the loop — apply's call; the acceptance pins the outcomes, not the loop shape.
- **Only if nothing else has focus.** Immediately before the compose arm calls the focuser it checks `document.activeElement`: it proceeds when the active element is `null`, `document.body`, or a non-editable chrome control (a sidebar row button, a top-bar control — the element that *initiated* the navigation); it **abandons** (falls through to today's behavior, i.e. the tty arm) when the active element is inside `.xterm`, inside `[role="dialog"]`/`[aria-modal="true"]`, inside the command palette (its input is a `<input>`, so the editable check covers it), any `<input>`/`<textarea>`/contentEditable, or an `<iframe>` (the code/web tiles). Reuse `shouldSuppressChord`'s editable checks (`lib/keybindings.ts` L1012) rather than a second list. The sidebar-row case is deliberate (Assumption 8): today's tty first-visit already takes focus from the row button (`focus-restore.spec.ts` switches through sidebar rows and asserts `.xterm` ends up active), and a sidebar click into a never-visited window is the most common fresh navigation — leaving focus on the row would defeat "the strip is the keyboard".
- **The no-steal rules already in place stay byte-for-byte**: the effect's capture-phase `pointerdown`/`keydown` cancel a pending retry (a user who clicks the pane or starts typing before the strip mounts has chosen); the strip's own mount effect still focuses **only** on the focus-on-open flag (a plain remount with the preference on never sets it); a window with a recorded kind (`tty` because the user clicked the pane, `code` from an in-editor interaction) recalls that kind — the resolver is consulted only when `recallFocus(key)` is `undefined`.
- **Recording side effect (Assumption 9).** The first-visit compose focus fires the textarea's `onFocus`, which records `compose` for the window (the existing recorder in `compose-strip.tsx` L1101–1111, gated on `focusMemoryWindow` matching the route window). This is accepted: the recorded value equals what the resolver would have produced, a later pane click overwrites it with `tty`, and the existing `compose` restore arm and the ⌘I chord already record through the same programmatic path. The focus-ownership memory's "programmatic grabs never write it" sentence is about `code` (the recording asymmetry that defeats the workbench grab) and is amended to say so explicitly.
- **Mobile**: no change — the router is desktop-only, and the strip on coarse pointers keeps the ⌨ chip / tap-to-focus model.
- **What is NOT a fresh navigation** (and so never lands focus in the strip by this rule): a remount of the same `{server, windowId}` (layout change, dock flip broadcast on/off, `SurfaceLayout` re-key) — the effect does not re-run; a board→terminal return to a window already in memory — the recorded kind wins; a window whose memory says `tty` — lands on tty.

## Impact

- **Frontend only.** No backend, API, tmux, or route changes. One new persisted key (`runkit-compose-default-notice`, the notice sentinel); the `runkit-compose-strip` key keeps its name and `"true"`/`"false"` values — only the absent-key reading flips.
- Files: `app/frontend/src/contexts/chrome-context.tsx` (`readComposeStrip`, `composeStripDefaulted`), `app/frontend/src/components/compose-strip.tsx` (notice effect, placeholder clause), `app/frontend/src/app.tsx` (first-visit resolver in `restoreFocus` + `revertProgrammaticFocus`, `composeStripEnabled` ref, palette label), `app/frontend/src/components/status-bar.tsx`, `app/frontend/src/components/bottom-bar.tsx`, `app/frontend/src/lib/keybindings.ts` (label), possibly `app/frontend/src/lib/focus-memory.ts` (if the resolver is extracted), `tests/e2e/_ready.ts` (seed helper); tests: `chrome-context.test.tsx`, `compose-strip.test.tsx`, `keybindings.test.ts`, `status-bar.test.tsx`, `bottom-bar.test.tsx`, `tests/e2e/compose-strip.spec.ts`, `focus-restore.spec.ts`, `status-bar.spec.ts`, plus the § 7 audit list (seeds only).
- **Unchanged by contract**: `compose-strip-events.ts` (`runComposeToggleChord`, the focus-on-open flag, the focuser registry), `terminal-client.tsx`, `surface-layout.tsx`, `compose-draft-store.ts`, `quake-launcher.tsx`, `board-page.tsx`, the wrapper's decision table.
- **User-visible on upgrade**: every browser without a stored preference gets the expanded strip on next load, one info toast, and focus in the textarea on desktop fresh navigations. Users who stored `"false"` see nothing new. Users who stored `"true"` see only the renames and the placeholder clause.
- **Layout budget**: unchanged from change 1 in kind (the surface always mounted); in degree, the expanded strip (compact row ~34px fine) replaces the tongue (~27px) as the common case on the desktop terminal route — the terminal body shrinks by the difference and refits (existing mechanic).
- **e2e runtime risk**: the § 7 audit is the bulk of apply. `shortcut-registry.spec.ts` alone has 61 key presses after `gotoWindowOne` with no terminal click; its session/window-jump chords are not in the punch-through set and WILL be suppressed until the spec seeds the preference off. Run each audited spec with `just test-e2e <name>.spec` before the full lane; on CI, a shard failure whose error-context shows "Server not found" is the rig dying, not this change.

## Open Questions

- **Sidebar-row navigation into a never-visited window**: the design's "only if `document.activeElement` is `body`/null" wording, read literally, would leave focus on the row button and fall to tty for the most common fresh navigation. Recorded as Confident (Assumption 8) that the guard excludes *typing surfaces* (xterm, palette, dialog, inputs, iframes) and not nav controls — today's tty first-visit already takes focus from the row. `/fab-clarify` if the literal reading was intended.
- **Should the first-visit compose focus write `compose` into focus memory?** Accepted as-is (Assumption 9); the alternative (a suppress flag around the router-driven focus) is a few lines if the recording asymmetry is felt to matter for `compose` too.
- **Enter semantics** (plain Enter inserts) and the **status-bar `a▏` chip's redundancy** with the tongue — explicitly deferred by the design; not decided here.

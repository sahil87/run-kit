# run-kit UI — Top Bar

## Chrome (Top Bar)

The full-width top bar is the app's primary chrome and doubles as the navbar. **It mounts ONCE at the persistent root layout, above the router `<Outlet>` — not once per page** (see § Persistent root mount below). `TopBar` (`app/frontend/src/components/top-bar.tsx`) accepts a `mode: "terminal" | "board" | "server" | "host"` prop (default `"terminal"`) selecting the left-nav content; the left nav is a breadcrumb bar. Everything below (per-mode breadcrumbs, center heading, right-cluster pyramid, connection dot) describes `TopBar`'s internal rendering. (`260702-6m46`, `260707-4vq2`, `260715-zs1y`)

### Persistent root mount (`RootTopBar` / `AppLayout`)

`TopBar` mounts once at the persistent root layout and re-renders in place across route changes (§ Design Decisions → TopBar mounts once at the root layout).

**Where it mounts.** A **pathless layout route** (`id: "app-layout"`, `router.tsx`) uniformly parents every page route (index, server, terminal, board), so every navigation keeps the match chain `[root, app-layout, <leaf>]`. Its component `AppLayout` (`app.tsx`) sits at a **stable match depth with a stable route id and is never remounted** across navigation; it renders a flex column — `<div className="app-root flex flex-col" style={{ height: "var(--app-height, 100vh)" }}>` — with `RootTopBar` in a `shrink-0` wrapper above a `flex-1 min-h-0` content region. The bar keeps a stable React identity and re-renders (props change, no unmount) as the URL flips. The pathless layout normalizes tree depth (§ Design Decisions → TopBar mounts once at the root layout). The `AppLayout` wrapper is a plain `div`, NOT `<header>` — `TopBar` already renders its own `<header>` banner landmark, so a second would nest two `role="banner"` landmarks.

**Suspense blast radius.** The `<Suspense fallback={null}>` boundary wraps ONLY the `<Outlet>` content region (inside `AppLayout`), not the header. So when the lazy board chunk loads, only the page body blanks — the bar stays painted.

**Prop delivery — two channels.** `TopBar`'s inputs split by how synchronously they must resolve:

- **Route-derived (synchronous, at root)**: `RootTopBar` (`app.tsx`) derives `mode` + `boardName` from `useMatches()` — a deepest-first walk over route params (`window` ⇒ `terminal`, `name` ⇒ `board` + `boardName`, `server` ⇒ `server`, none ⇒ `host`; param names are unique across the tree, the same walk `SessionContext` uses for `currentServer`). This flips the instant the URL changes, so the heading never waits on the incoming page's mount — critical for the lazy board (`Board: <name>` renders from the URL param while the chunk still loads). `mode`/`boardName` are deliberately NOT in the slot.
- **Page-registered (a slot context, `contexts/top-bar-slot-context.tsx`)**: pages publish their data/handler props — `sessions`, `currentSession`, `currentWindow`, `sessionName`, `windowName`, `sidebarOpen`, `server`, `onNavigate`, `onToggleSidebar`, `onCreateWindow`, plus board extras (`paneCount`, `serverCount`, `waitingPaneCount`, `boards`, `focusedPane` — the focused-tile split target — `onRequestKill` — the board Kill row's kill-dialog opener — and `autofit`/`onToggleAutofit` for the board autofit toggle, § Board Autofit Toggle) — via `useRegisterTopBarSlot(...)` (an effect: publish on mount/update, **clear to `null` on unmount**, last-writer-wins). This follows the `FocusedTerminalProvider` precedent (referentially-stable dispatcher held in a `useRef`, `useMemo`'d context value) and keeps the heavy handlers where they live — `AppShell`'s `navigateToWindow` (View-Transitions gate) is published by reference; **no logic lives at root**. (`260708-738w`, `260715-6jwn`, `260718-co9z`, `260813-kvk7`)

**Tolerant-empty defaults.** When no page has registered yet (first frame after navigation, or a lazy chunk still loading), the slot value is `null` and `RootTopBar` renders the route-derived mode with the tolerant-empty prop shape every `TopBar` mode already supports (`sessions=[]`, `currentSession=null`, `currentWindow=null`, `sessionName/windowName/server=""`, `sidebarOpen=false`, no-op callbacks). No crash, no stale props from the prior page (the clear-on-unmount guarantees this).

**Not-found is a dedicated boolean channel.** `TopBarSlotContext` carries a `notFound` flag SEPARATE from the page-data `slot`. `NotFoundPage` (`router.tsx`) — the `app-layout` route's `notFoundComponent`, rendered inside the `<Outlet>` below the persistent bar — calls `useSignalTopBarNotFound()` (sets `true` on mount / `false` on unmount); `RootTopBar` reads `useTopBarNotFound()` and forces `mode="host"` (nulling `boardName`) BEFORE the route-param walk. This is required because TanStack Router's fuzzy not-found handling RETAINS the partially-matched params in `useMatches()` (e.g. `/board/x/y` keeps `name=x`), so the param walk alone would derive `board` mode ("Board: x") over the not-found body. A separate boolean keeps `NotFoundPage` — which owns no TopBar data — from publishing the full slot shape, and avoids coupling to a router-internal field + hardcoded route-id string. Because `RootTopBar` sits ABOVE the `<Outlet>`, the in-Outlet signal is inherently one render behind: a ~1-frame "Board: x" flash before the effect lands is unavoidable without reading router internals — not user-perceptible, and the settled state is unaffected. (The `/a/b/c` shape is a DIFFERENT arm: it renders `AppShell`'s `ServerNotFound` early-return, not `NotFoundPage`, so `notFound` stays false there and the `server`/`terminal` mode derivation is kept.)

**Per-page registration.** No page mounts `<TopBar>`; pages that own TopBar data register into the slot context instead: `AppShell` registers its terminal/server data (the `terminal` vs `server` distinction is derived at root); `BoardPage` registers the board extras (`boardName`, counts, `boards`, `focusedPane`, `onRequestKill: requestKillFocused` — the kill-dialog opener; it keeps the `HELP_URL` import for its palette action). `HostOverviewPage` registers **nothing** (wrapper `flex flex-col h-full`) — the connection state that was its only payload now reaches the Sidebar as a prop, and `/` has no sidebar (§ Design Decisions → App-global actions live in the top bar). Edge pages (`NotFoundPage`, `ServerNotFound`, `ServerWaiting`) center with `h-full` so they fit the content region below the persistent bar without overflow. (`260718-co9z`)

**Achievable-invariant note (e2e).** No component in the persistent chain (`RootWrapper`/`AppLayout`/`RootTopBar`/`TopBar`) remounts across navigation, so the bar stays continuously present with a per-route heading — this is what `tests/e2e/top-bar-persistence.spec.ts` asserts (mount-effect stability + per-route heading), NOT strict DOM-node identity. TanStack Router 1.168's per-match Suspense re-commit recreates the header host node on the `→ /` (index-route) transition; that is a router-internal reconciliation artifact that does NOT remount the component and does NOT blank the bar (the heading renders synchronously from route state), so it is not a user-visible flicker. The spec's brand-crumb hop is a RELOAD BOUNDARY — the brand is a raw `<a href="/">` TanStack Router does not intercept, a full document navigation — so only the client-side hops carry the no-remount claim.

**Non-goals.** Sidebar/BottomBar/Shell stay per-page (they still remount on `/$server` ↔ `/board/$name`); `TopBar`'s internal rendering across all four modes is unchanged; frontend-only (no backend/API/tmux change).

`app.tsx`, `board-page.tsx`, and `host-overview-page.tsx` (Host page `/`) register into the slot context rather than rendering `<TopBar>` directly (see § Persistent root mount above). The right-section control cluster is a **strict 3-level cumulative pyramid**: a stable always-block pinned right renders in every mode, with terminal+board extras and terminal-only extras growing leftward — so no shared button ever changes screen position between pages. Only which levels appear gates on mode; see § Right cluster below. (`260704-9o7k`)

**Layout** (`border-b-[3px] border-border` — a 3px structural seam, see § Border-Width System): a single line, a **3-column CSS grid `grid grid-cols-[1fr_auto_1fr] items-center gap-2 py-2`**. `1fr auto 1fr` makes the CENTER cell truly centered regardless of asymmetric left/right widths. LEFT cell = a flex wrapper holding the hamburger (first, outside the nav) + `<nav aria-label="Breadcrumb">` (the nav ends at the parent — see per-mode below); CENTER cell = the **universal `PageType: name` page heading, FILLED IN EVERY MODE** (terminal `WindowHeading` + ▾ window switcher / board display heading + ▾ board switcher / server display heading / solo `Host`; § Chrome (Top Bar) center cell); RIGHT cell = the control cluster (`justify-self-end`). No Line 2. The header itself carries `px-3` plus — outside the desktop shell — the `pt-[env(safe-area-inset-top)]` safe-area guard (§ Safe-Area Insets — 0 in browsers, non-zero only in standalone PWA mode where `viewport-fit=cover` exposes the status-bar strip; in-shell the class is `isShell()`-gated off, because the `ShellTitlebarStrip` already reserves the titlebar band and macOS hidden-titlebar windows can report it as `safe-area-inset-top` — padding on top would reserve the band twice); the center cell is `flex items-center justify-center min-w-0`, no flex `gap` — the boot sweep owns the prefix→name spacing via its own space cell. (`260703-5ilm`, `260704-pr0p`, `260724-2bmy`, `260805-9hn1`)

**Left cluster** — the `1fr` left grid cell is a flex wrapper (`flex items-center gap-1.5 min-w-0`) holding, in order, the **hamburger**, the **history ◀ ▶ arrows** (`HistoryNav`), then the **breadcrumb nav** — the macOS convention (sidebar toggle → back → forward → brand crumb). Both the hamburger and the arrow pair are siblings BEFORE the nav (outside the `nav[aria-label="Breadcrumb"]` landmark — neither a drawer toggle nor global history is a breadcrumb item); `min-w-0` lets the nav shrink below its content inside the `1fr` column. The center heading's true centering is untouched by the wrapper. (`260720-ap63`, `260731-oiho`)

**Hamburger** — the sidebar toggle (`aria-label="Toggle navigation"`, a Notion-style rounded-rect pictogram whose left column fills when `sidebarOpen`), the FIRST element of the left cluster (standard drawer-toggle position — VS Code / Slack), rendered before and outside the breadcrumb nav. Present on every mode that has a sidebar; `hasSidebar` is DERIVED as `mode !== "host"` (no separate prop) — the host mode is the only sidebar-less mode, so it gets no hamburger (the brand shifts left ~30px there; no ghost slot is reserved). It joins the top-bar button-control size vocabulary via the shared fixed-size token `TOP_BAR_BUTTON_BASE` (28px fine / 30px coarse, `shrink-0` included — the same token the HistoryNav arrows and the whole right-side cluster use, NOT the bottom-bar's 36px; § Right cluster → shared button-size token), composed with its own `text-text-primary` (the toggle carries page-level chrome weight). It is a **bordered chip** in the sibling vocabulary (`rounded border border-border hover:border-text-secondary` — the same treatment the HistoryNav arrows and `LINK_CRUMB_CLASS` crumbs carry), so hover is the full `rk-glint` treatment: green icon + sweep + border flip. Its `HamburgerIcon` renders at **16px** (a `18`-unit viewBox scaled down) — the ~13–14px optical scale of the icons inside neighboring chips; the same icon renders mirrored at the bar's far right as the rail toggle's glyph via its `side="right"` prop (§ Right cluster → rail toggle chip). (`260720-ap63`, `260724-2bmy`, `260812-nm4p`)

**Brand root crumb** (all modes, the nav's FIRST child): the logo icon (`/icon.svg`, always visible) + `hidden sm:inline` "RunKit" wordmark wrapped in a single `<a href="/">` (`aria-label="RunKit home"`). It is the breadcrumb's root crumb, so the `›` separator starts after it. This IS the home affordance — there is no separate "Host" crumb and no right-side "RunKit" anchor. The brand carries the `LINK_CRUMB_CLASS` bordered-chip treatment (see § Crumb Affordance Vocabulary) and `rk-brand-glitch` hover, plus `min-h-[28px] coarse:min-h-[30px]` on the anchor itself — the shared control height axis, so the brand, the hamburger, and the HistoryNav arrows all sit on ONE horizontal axis (same `y`, same height) instead of the brand riding 4px shorter on coarse pointers. The `min-h` lands on the brand anchor only, NOT inside `LINK_CRUMB_CLASS`: the server crumb — the class's other consumer — is an inline truncating link where `min-h` is inert without a flex display. Below `sm` it collapses to the bare icon so long crumbs still fit the single-line 375px topbar. (`260702-6m46`, `260720-ap63`, `260724-2bmy`)

**Separator** — `›` (U+203A, `aria-hidden`, `BreadcrumbSeparator`), the palette-label convention (`<session> › <name>`) between every crumb level. No `/` separator. (`260702-6m46`)

**Host** (`/`, `mode="host"`): brand crumb ONLY — no hamburger, no crumbs, no terminal-font control, no split/close buttons, and **no fixed-width button** (terminal-only; the 900px effect never applied to the Host page — `host-overview-page.tsx` never reads `fixedWidth`). Renders only the L3 always-block (UpdateChip when qualifying + Refresh + the Settings gear) plus the exempt overflow chevron. It is the one route with **no sidebar-footer status row** (no sidebar to hold one), so it shows no connection dot or resting version readout — but the app-global actions are all present on host mode like every other mode: the Settings gear in-bar and Help / Keyboard shortcuts / Theme… as the chevron menu's App-section rows (§ Right cluster → Settings gear; § Design Decisions → App-global actions live in the top bar). It registers nothing into the slot context — it owns no TopBar data. Session/server-dependent props are passed empty (`sessions=[]`, `currentSession=null`, `currentWindow=null`, `sessionName=""`, `server=""`, no-op callbacks) — the same tolerant-empty shape board mode uses. The Host page's page identity is the **solo `Host` heading in the top-bar center cell** (a `PageHeadingDisplay` with `prefix=""` + `name="Host"` + `solo` — primary-medium, visible at all breakpoints; § center cell), plus the in-page `Host Overview` SectionHeading (§ Page Overview Headings). A "RunKit Host" doubled word is avoided — it would duplicate the adjacent brand crumb. (`260704-9o7k`, `260704-pr0p`, `260715-zs1y`)

**tmux Server** (`/$server`, no `$window`, `mode="server"`): the left cluster is **hamburger + brand** — nothing more (the breadcrumb nav holds just the brand crumb). The server name is the **`tmux Server: <server>` heading in the CENTER cell** (a display-only `PageHeadingDisplay`, no rename), NOT a left-nav leaf (move-don't-copy: the current-page leaf is the centered heading; a name never appears twice in the bar). "Dashboard" appears nowhere. (`260702-6m46`, `260704-pr0p`)

**Terminal** (`/$server/$window`, `mode="terminal"`): the left cluster is hamburger + brand + `›` + server link + `›` + **session crumb — and the breadcrumb ENDS THERE** (the hamburger precedes the brand, outside the nav) (the window identity lives in the centered `WindowHeading`, not the breadcrumb chain). The server crumb here is a plain `<a href="/$server">` (a link back to the tmux Server page, `LINK_CRUMB_CLASS` chip, `truncate max-w-[16ch]`) — NOT a dropdown (server switching stays in the command palette, `Server: Switch to …`). The session crumb is a **static, non-interactive chip** — a plain span carrying the shared `CRUMB_BOX_CLASS` box + `max-w-[16ch] truncate` with no hover treatment, no pointer cursor, and no ▾ (a session has no route of its own; session switching lives in the sidebar rows + palette `Window: Switch to …`, creation in the palette `Session: Create` / `Session: Create at Folder` and the sidebar server-header `+`; the session name is snapshot-derived from the active `@N`, not a URL segment). **The window switcher lives in the center cell** — a label-less bare-`▾` `BreadcrumbDropdown` (`title="Window"`, `windowItems` + `+ New Window` action) sitting beside the `WindowHeading` (name-click = edit, `▾`-click = switch), so the window name is never duplicated in one bar. The centered `WindowHeading` carries a static prefix sibling span (§ Window Heading) — the two-tone `PageType: name` identity, `Window:` in every lens. See § Chrome (Top Bar) center cell / § Breadcrumb Dropdowns → Window switcher. No type-prefix words ("SERVER"/"tmux Server"/"session") — crumbs are instance names only; position conveys the level. The level IS named on hover via native `title` tooltips in the canonical vocabulary: brand `title="Host"`, server crumb `title="tmux Server"` (both link and leaf variants), and the window switcher `title="Window"` (via BreadcrumbDropdown's optional `title` prop). (`260529-jad6`, `260703-5ilm`, `260704-pr0p`, `260714-uco1`, `260813-kvk7`)

**Center cell — the universal `PageType: name` page heading** (filled on every mode). The outer center `<div className="flex items-center justify-center min-w-0">` (no flex `gap` — the boot sweep's own `sp` space cell separates prefix from name) stays centered in the grid; it wraps an **inner anchor `<div className="flex items-center justify-start min-w-0 sm:min-w-[28ch]">`** — a `sm:`-gated min-width with LEFT-aligned content so the heading's left edge stops drifting as the instance name length changes (below `sm` the min-width is absent — space is scarce at 375px). The box carries **no history-arrow furniture** — `HistoryNav` is left-cluster chrome (§ Left cluster), so the box needs no width-compensation offset between its prefix and a neighbouring control. The heading is **single-caret**: the prefix (`Window:`/`Board:`/`tmux Server:`) renders contiguous with its colon and carries NO dropdown — the only `▾` is the name-side window/board switcher; ancestor navigation lives in the palette's `Go:` entries (§ Center-heading stable anchor + nav affordances) + browser back. It renders per mode: (`260703-5ilm`, `260704-pr0p`, `260714-uco1`, `260731-oiho`, `260813-kvk7`)

- **terminal** (`mode === "terminal" && currentWindow`): `<WindowHeading>` (static `Window: <window>` prefix, editable name — see § Window Heading) + the relocated bare-`▾` window switcher.
- **board** (`mode === "board" && boardName`): a `<PageHeadingDisplay prefix="Board:" name={boardName}>` (display-only — boards have no rename API) + the `<BoardSwitcher>` ▾ (moved here from the left `BoardModeBreadcrumb`).
- **server** (`mode === "server" && server`): `<PageHeadingDisplay prefix="tmux Server:" name={server}>` (display-only).
- **host**: `<PageHeadingDisplay prefix="" name="Host" solo>` — a solo type word, no instance name, primary-medium, visible at all breakpoints.

The type-prefix constants live once in `top-bar.tsx`: `WINDOW_PREFIX = "Window:"`, `BOARD_PREFIX = "Board:"`, `TMUX_SERVER_PREFIX = "tmux Server:"`, `HOST_SOLO = "Host"` (title case). Because the cell lives in the `auto` middle grid column, it stays centered under the topbar regardless of the breadcrumb / control-cluster widths. The `WindowHeading` (and the display headings) are deliberately NOT keyed on the route identity (no remount `key`) so they persist across window/page switches — that is what lets the boot sweep replay on navigation and keeps an in-progress inline edit alive (an external windowId/server switch mid-edit CANCELS the stale edit instead, since committing the typed name onto the newly-navigated window would rename the wrong one). (`260714-uco1`, `260715-zs1y`)

### Center-heading stable anchor + nav affordances

Three navigation affordances around the top-bar page heading — the anchor, the history ◀ ▶ pair (left-cluster chrome, § Left cluster), and the `Go:` palette parity, which is also the ancestor-navigation coverage (`Go: tmux Server` / `Go: Host`, plus browser back below `md` where the server crumb hides) — no new routes and no backend surface: (`260714-uco1`, `260731-oiho`, `260813-kvk7`)

- **Stable left anchor.** The outer center cell stays `justify-center` in the grid; an INNER container `flex items-center justify-start min-w-0 sm:min-w-[28ch]` reserves a `sm:`-gated min-width with LEFT-aligned content, so the heading's left edge stops drifting as the instance name length changes (min-width over fixed-width+truncate — long names grow rightward, accepted). Applies uniformly across all four modes; below `sm` the min-width is absent (375px). The `28ch` value is monospace-exact, visually tuned. The inline-rename `<input>` is `text-left` so the name does not jump on edit entry (§ Window Heading → edit).
- **Browser-history ◀ ▶ arrows** (`HistoryNav`). Bordered `rk-glint` icon buttons on the shared fixed-size token (`TOP_BAR_BUTTON`, § Right cluster → shared button-size token), rendered in the **LEFT cluster** immediately right of the hamburger (before the brand crumb on Host, which has no hamburger) on ALL FOUR modes (history is global) — the macOS ordering, and the reason the center box needs no width-compensation furniture (§ Left cluster). The pair sits in its own `shrink-0` group so the arrows never collapse under breadcrumb pressure. **`hidden lg:flex`** — the pair is a rung of the left cluster's degradation ladder (§ Mid-width overlap degradation): below `lg` the rigid left cluster (toggle + arrows + the nav's `sm:min-w-[150px]` floor) exceeds its equal-`1fr` side track against a 28ch-capped long-name heading (worst case needs ~832px) and the overflowing nav would paint over the centered prefix — the exact overlap class the `260715-q8ey` invariant forbids (`top-bar-overlap.spec.ts`); browser back gestures plus the palette's `Go: Back` / `Go: Forward` carry coverage at narrow widths. They call TanStack Router's `useRouter().history.back()` / `.forward()` — BROWSER HISTORY, explicitly NOT sibling-window cycling. Forward is always-active (browser-chrome style — `canGoForward` is not reliably exposed, so a dim/disabled state is omitted; a no-forward click is a harmless no-op). **Within-server window hops retrace**: user-initiated window switches **push** history entries (`navigateToWindow` — see § URL as Resumable Bookmark → optimistic navigate), so Back/Forward step through every within-server hop, not only server boundaries. No dedup — `w1→w5→w1` yields three entries. History Back/Forward bypasses `navigateToWindow` (raw `router.history.back()/forward()`), so no slide transition plays on arrow navigation; the landed window's tmux is realigned for free by the deep-link intent effect (§ URL as Resumable Bookmark, contract 1 — its `hasAlignedToUrlRef` guard re-arms on every `windowParam` change). (`260715-m4xy`)
- **`Go:` palette parity** (Constitution V) via the pure `lib/palette-nav.ts` builder `buildNavActions(mode, server, handlers)` (+ colocated `palette-nav.test.ts`), mirroring `palette-move.ts`/`palette-view.ts`. Returns the two history actions (`Go: Back`/`Go: Forward`, ALWAYS) followed by the route-appropriate ancestor entries: `Go: tmux Server` when `mode === "terminal" && server`, then `Go: Host` **unconditionally** (the Host root is an ancestor of every palette-bearing mode — only the `terminal` extra differs). `NavMode` is `"terminal" | "board" | "server"` — the **palette-bearing subset of `TopBarMode`**: the root Host route carries no route params and resolves to the `"server"` arm, so there is no `host` mode (`TopBarMode` keeps its `"host"` member; only `NavMode` narrows). **Wired once at the layout level** (§ Single palette mount + palette-actions slot): `use-global-palette-actions.ts` derives the mode from the same deepest-first route-param walk `RootTopBar` does (a `name` param → `"board"`, a `window` param → `"terminal"`, anything else → `"server"`) and passes `router.history.back/forward` + `navigate(...)` bodies. No new app-level keybindings (browser-native Alt+←/→ already cover history). (`260714-uco1`, `260719-i996-nav-actions-board-wiring`)

**Board** (`/board/$name`, `mode="board"`): the left cluster is hamburger + brand + a **counts/hint span ONLY** (`BoardModeInfo` — `{N} pane[s] · {M} server[s] · ⌘[⌘] cycle`, no leading `›` because the hint is not a crumb). The board name + ▾ switcher live in the center heading (`Board: <board>` display + `<BoardSwitcher>`; § center cell); there is no left `Board ▸` home button (the brand crumb is the home affordance, and a left `Board` word would duplicate the centered type word — move-don't-copy). Right cluster: the L1 **merged split control** (wired to the focused tile's window via `focusedPane`) + the board-only **autofit toggle** (the one in-bar L2 survivor) + the L3 always-block. **Kill lives in the chevron menu** (`menuOnly` — § Right cluster): the menu's Kill row is a **confirm-gated window-kill** of the focused tile's window, opening the kill dialog with a default-focused `Unpin instead` escape (§ Board Kill Confirm Dialog); unpin lives on the tile-header pin-glyph + palette (§ Close pane / Kill / § Board Tile Header / § Board Autofit Toggle). The L3 block carries the connection dot, which shows an **AND over the board's attached servers** (green iff ≥1 entry AND every distinct attached server's `isConnectedByServer` slice is connected; `board-page.tsx` derives `boardConnected` and passes it). (`260702-6m46`, `260704-pr0p`, `260704-9o7k`, `260715-6jwn`, `260718-co9z`)

**Mobile (`< sm`)** — the brand collapses to the bare icon and intermediate crumbs (server link + session, plus their `›` separators, wrapped in `hidden sm:flex` spans) are hidden, leaving brand icon + the centered heading. The leaf is the **center-cell heading in EVERY mode**: Terminal → `WindowHeading` (the mobile leaf AND primary rename affordance, `coarse:min-h-[30px]` touch target), tmux Server → the `tmux Server: <server>` display heading, Board → the `Board: <board>` display heading, Host → the solo `Host`. **The two-tone `PageType:` prefix is hidden below `sm`** (`hidden sm:inline`) so mobile keeps just the name — EXCEPT the solo `Host` word (a name-equivalent, not a prefix), which stays visible at all breakpoints. The `▾` window/board switcher stays visible on mobile with its `+ New Window` / board-switch action. Long names truncate in the center cell (`max-w-[16ch]` on mobile, `sm:max-w-[28ch]`) — never wrap or squeeze neighbors. The topbar stays a single line at 375px (the documented invariant in `fab/project/context.md`). (`260704-pr0p`)

**Mid-width overlap degradation.** Between the `sm` breakpoint (640px) and ~900px (the common sidebars-open / half-screen browser-pane case), a deterministic **degradation ladder** (class-only in `top-bar.tsx`, no API/routing/backend change) keeps the left breadcrumb from painting over the centered heading: (`260715-q8ey`)

0. **History arrows hide below `lg`.** `HistoryNav` is `hidden lg:flex` — the ladder's widest rung, and the only one above the 640–900px band. The pair is rigid (`shrink-0` fixed-size buttons), so below `lg` the left cluster's floor (toggle + arrows + the nav's `sm:min-w-[150px]`) exceeds its equal-`1fr` side track against a 28ch-capped long-name heading — worst case needs ~832px — and the overflowing nav would paint over the centered prefix, the exact overlap this ladder exists to prevent. Coverage survives via browser back gestures and the palette's `Go: Back` / `Go: Forward`. (`260731-oiho`)
1. **Crumbs truncate first.** The two left-nav crumb wrapper spans (server-link crumb + session crumb) each gained `min-w-0` so the `truncate max-w-[16ch]` already present on their inner anchor / static chip span finally engages. **`min-w-0`-chain rule**: a nested flex item defaults to `min-width: auto`, which blocks `truncate` from shrinking the item until an explicit `min-w-0` is added at that level — the crumb text had been overflowing the nav box because the intervening wrapper span, not the anchor, was the blocked link in the chain. `BreadcrumbSeparator` and the brand chip stay `shrink-0` — the protected identity floor inside the nav; the hamburger sits outside the nav and carries its own `shrink-0`.
2. **Server crumb hides below `md`.** The server-link crumb wrapper is `hidden md:flex … min-w-0` — the first element to give way; below `md` the ancestor path it offered is covered by the palette's `Go: tmux Server` / `Go: Host` entries and browser back. The **session crumb stays at `sm+`** (a static chip — § Crumb Affordance Vocabulary). (`260714-uco1`, `260813-kvk7`)
3. **Nav clips at its explicit floor.** The `<nav aria-label="Breadcrumb">` carries an explicit breakpoint-aware floor `min-w-[46px] sm:min-w-[150px]` plus `overflow-hidden`. The floor budgets only nav content — the hamburger sits outside the nav and carries its own `shrink-0` + min sizes: below `sm` the floor guarantees just the bare brand icon; at `sm+` also a session-crumb sliver. The left cell's TOTAL floor (hamburger + gap + nav floor) is what holds the left budget. **Clip-backstop rule**: `overflow-hidden` converts any residual overflow past the shrunk floor into a clean clip at the nav's right edge instead of paint-over overlap — overlap becomes structurally impossible, not merely unlikely. The `min-w-[46px] sm:min-w-[150px]` values hold across the full Playwright sweep (375 / 640 / 700 / 768 / 1024px) with the 30px coarse hamburger, no clip or wrap regression — the top-bar-overlap spec is the harness. (A clipped child keeps a layout box wider than its clipping parent, which is expected; the meaningful proofs are the no-intersection assertion + computed `overflow:hidden`, not a layout-box comparison.)

**Center protection.** The center `auto` grid column is protected by holding its bounded **content floor**, NOT by a magic pixel min-width. The center cell's OUTER wrapper (`flex items-center justify-center`) carries no `min-w-0`, so the `auto` column can not be squeezed below the heading's content. That floor is *bounded* because the heading name spans carry `max-w-[16ch] sm:max-w-[28ch] truncate` (WindowHeading button + PageHeadingDisplay) and the history ◀ ▶ / window & board ▾ controls are fixed-width `shrink-0`. The inner box's **`sm:min-w-[28ch]` stable anchor stays at `sm:` (NOT `md:`)** — the right cluster absorbs squeeze instead. Net effect: squeeze lands on the left (and right) `1fr` columns; the center heading is never compressed into overlap across the 640–900px band. (`260715-q8ey`)

**Right-cluster degradation.** The right cluster is registry-driven and its `1fr` grid track is squeezable via `min-w-0` on the cell, so under width pressure controls collapse into a chevron menu instead of clipping (full mechanics in § Right cluster → overflow chevron menu below). It uses an explicit fit computation + move-to-menu, NOT `overflow-hidden` — a partial `overflow-hidden` on the right cluster would clip the *wrong* end (flex overflow spills toward inline-end, dropping the L3 always-block / the chevron first). The cell carries `min-w-0` but deliberately NO `overflow-hidden` (the only content that can exceed a very-narrow track is the always-present exempt chevron, which must stay visible/clickable per R6). Regression coverage lives in `tests/e2e/top-bar-overlap.spec.ts` (+ `.spec.md`): at ~700×800 with long window + session names, nav-box ∩ heading-box is empty and crumbs are ellipsised; server crumb toggles across `md`; 375px stays single-line; 1024px+ keeps the anchor intact. The width-sweep spec `tests/e2e/top-bar-overflow.spec.ts` (+ `.spec.md`) is the right-cluster's regression proof (see § Right cluster). (`260715-q8ey`, `260715-h1ck`)

- **Ordered registry drives the cluster.** The right cluster is built from an ordered `RegistryEntry[]` (`{ id, tier — implicit in position, modes: TopBarMode[], hidden?, menuOnly?, menuGroup: MenuGroup, barRender: () => ReactNode, menuRender: () => ReactNode }`), one entry per control — the pyramid in drop order: L1 open · split (dynamic `menuOnly: mode === "terminal"` — menu-rows-only on terminal, in-bar on board; `260813-w1lf`) · **layout** (terminal-only, `menuGroup: "view"` — the ▦ layout chip, § Surface Layout); `fixed-width` · `terminal-font` (both `menuOnly`) · autofit; `close-pane` (`menuOnly`); L3 update-chip · refresh · settings; then the `menuOnly` app rows `help` · `keyboard` · `theme`. The `open` entry is the **first L1 fit candidate** (the head of the list, so first to drop) — earliest-drop placement keeps it out of the L1/L2/L3 pyramid-drop invariants the overflow e2e asserts (§ Open split-button). One ordered source drives BOTH the bar (first-that-fit render `barRender` as icon buttons) and the menu (overflowed + `menuOnly` entries render `menuRender` as labeled rows), so bar↔menu can never drift. Optional gate fields filter each render: (a) **`hidden`** (an entry with `hidden` true renders NOWHERE — not bar, not menu, not the measurement probe) — `open` `hidden` when not terminal mode, no `currentWindow`, or zero available open targets (a control with an empty menu is a dead control — § Open split-button); `split` `hidden: mode === "board" ? !focusedPane : !currentWindow` (one expression covering both wirings); `layout` `hidden: !(mode === "terminal" && currentWindow && layout && onApplyLayout)` (hidden until AppShell registers the layout slot); `fixed-width` `hidden: !currentWindow`; autofit `hidden: !(mode==="board" && onToggleAutofit)`; `close-pane` `hidden: mode === "terminal" && !currentWindow` (the board row stays, disabled, on an empty board); `update-chip` `hidden: !showChip` (kept out of the candidate set entirely so it never reserves an empty slot); (b) **`menuOnly`** (below) — the entry NEVER renders in-bar and its `menuRender()` rows ALWAYS render in the menu (subject to `hidden`). `hidden` keeps its "renders nowhere" priority over `menuOnly`. A third field, **`menuGroup`**, names the menu section the entry's rows render under (§ Menu density + section labels) — it is pure row-placement data and does not gate anything. Gating is 100% registry data — no per-item `hidden sm:flex` empty-flex-item gap hack. (`260717-6anu`, `260722-n2n4`, `260722-6d0f`, `260731-oiho`, `260812-d1at`, `260812-ab5v`)

- **`menuOnly` — never-in-bar placement (`260722-n2n4`).** An optional `menuOnly?: boolean` on `RegistryEntry`: a `menuOnly: true` entry is excluded from the visible in-bar row, the hidden measurement probe, AND the width-fit computation (it contributes ZERO pixels to the fit budget), while its `menuRender()` rows ALWAYS render in the chevron menu (when the entry passes its `modes`/`hidden` gates), in registry (pyramid) order alongside the overflowed fit candidates. It is a generic registry capability, not a one-control special case — any control can opt in (§ Design Decisions → `menuOnly` is a registry capability). **Six entries set it statically**: `fixed-width`, `terminal-font`, and `close-pane` (§ Right cluster → `menuOnly` demotions), plus the app-global `help` / `keyboard` / `theme` entries — those three exist ONLY as App-section menu rows by design (their chrome home is the menu; the settings gear beside them is a regular fit candidate whose menu row is the overflow fallback). A seventh — **`split`** — sets it DYNAMICALLY (`menuOnly: mode === "terminal"`, `260813-w1lf`): on terminal routes it contributes zero fit/probe width and its rows are always-present; on board it is a normal fit candidate. Each demoted control's in-bar component stays intact but unreachable, so reverting any one of them is removing its flag. (`260722-n2n4`, `260731-oiho`)

- **Drop order = fit candidates consumed from the LEFT; surviving buttons never shift.** The fit candidates are the registry entries minus the `menuOnly` ones (`fitCandidates = candidates.filter((e) => !e.menuOnly)`). Overflow eats them leftmost first — **L1 (`open` first to yield when present, then `layout` on terminal — the terminal split is `menuOnly` and never a fit candidate — or `split` on board), then the L2 survivor (`autofit`, board only), then L3** — so the surviving in-bar set is a SUFFIX of the fit-candidate order and every survivor keeps its exact screen position (the pyramid invariant). Implementation: the fit function reverses the measured widths (L3-end first), `computeVisibleCount` greedily fits from the tail, and the returned N trailing fit candidates stay in-bar while the leading `fitCandidates.length − N` overflow into the menu. `visibleItems = fitCandidates.slice(splitAt)`; **`overflowItems = candidates.filter((e) => !visibleIds.has(e.id))`** — candidates-minus-visible, so the `menuOnly` entries (never in `visibleItems`) interleave at their registry positions, all in one expression that preserves registry order for free and cannot double-count (§ Design Decisions → Overflow list is candidates-minus-visible). (`260717-6anu`, `260722-n2n4`)

- **Exempt items never overflow**: the exempt set lives in the **trailing block** (`trailingRef`), distinct from the `menuOnly` entries, which are not exempt but simply out of the fit entirely (always in the menu, never fit candidates). The block holds the **overflow chevron** — present in every mode — plus, when AppShell registers `onToggleRail` (every desktop terminal route), the **rail-toggle chip** as the bar's outermost right element. The block's measured width is the only thing RESERVED before fit candidates are placed. So `reserved = trailing + RIGHT_GAP_PX` (the trailing block plus one `gap-3` joining it to the last fit candidate). No `menuOnly` entry contributes probe width, so the fit budget is unaffected by which lenses the window offers or by the demoted controls' bar forms. (`260717-6anu`, `260722-n2n4`, `260724-6j1v`, `260731-oiho`, `260812-nm4p`)

### Shared top-bar control glyphs (`top-bar-icons.tsx`)

**One glyph definition per mirrored top-bar control, consumed by BOTH the in-bar button form and its chevron-menu / SplitControl-popover rows** — so bar↔menu visual parity is structural rather than copy-paste. The module exports eight components: `SplitVerticalGlyph`, `SplitHorizontalGlyph`, `ClosePaneGlyph`, `ClosePaneBoxedGlyph`, `RefreshGlyph`, `FixedWidthGlyph({expanded?})`, `AutofitGlyph({filled?})`, and `TerminalFontGlyph`. It is the sibling of `open-app-icons.tsx` (§ Open split-button → Row icons) and follows that precedent's conventions: **~14px rendered size, `currentColor` stroke/fill** (so the glyph rides the row hover treatments and `rk-glint` accent-green flips for free), **`aria-hidden="true"` decoration** (the row/button's accessible name stays its text label or `aria-label`), **`shrink-0`**, and a kebab-case **`data-icon` attribute as the test seam** (`split-vertical`, `split-horizontal`, `close-pane`, `close-pane-boxed`, `refresh`, `fixed-width`, `autofit`, `terminal-font`) — monochrome paths are otherwise indistinguishable to queries. (`260801-3q1z`)

**`ClosePaneBoxedGlyph`** (`data-icon="close-pane-boxed"`, the 24-viewBox strokeWidth-2 `ControlGlyph` defaults) is a rounded rect + inner cross (the lucide `square-x` shape) — the tty tile header's Close Pane glyph, deliberately distinct from the bare-✕ `ClosePaneGlyph` so the two destructive closes never share a shape (§ Surface Layout → Tile renderer → close-distinction contract; `260813-w1lf`).

**A viewBox/strokeWidth/join-parameterized local wrapper, not `open-app-icons.tsx`'s fixed `Glyph`.** `ControlGlyph({name, viewBox, strokeWidth, join, children})` defaults to the 24-viewBox / strokeWidth-2 / round-caps-and-joins shape the split, close, and refresh originals carry, and each stateful-toggle glyph overrides it: fixed-width is 14-viewBox strokeWidth 1.5 with **round caps only** (`join={false}` omits `strokeLinejoin` entirely), autofit is 14-viewBox strokeWidth 1.5 with caps *and* joins. Preserving each original's exact attributes is what makes the in-bar refactor zero-visual-change (§ Design Decisions → A dedicated `top-bar-icons.tsx`, and per-glyph exact SVG attributes).

**Stateful toggles expose a variant prop so one definition serves both forms.** `FixedWidthGlyph` takes `expanded` (outward/expand arrows when true, inward/contract when false) and `AutofitGlyph` takes `filled` (three 0.35-opacity `currentColor` pane rects over the frame when true). **Both default to `false` — the static identity variant.** The in-bar buttons pass live state (`expanded={fixedWidth}` / `filled={autofit}`, preserving their pre-existing state-driven flip); the menu rows render the bare default, so the leading icon never flips and the trailing ✓ stays the sole state marker (§ Right cluster → leading-glyph parity).

**`TerminalFontGlyph` is a text span, not an SVG** — an `aria-hidden` `<span data-icon="terminal-font">Aa</span>` in a fixed `w-[14px] shrink-0 inline-flex items-center justify-center font-semibold leading-none` box, matching the in-bar `TerminalFontControl` trigger where "Aa" reads as "text size". Font size inherits from the host (`text-xs` on both the trigger and the menu rows), so the glyph matches whichever surface renders it. The fixed 14px box is a sub-pixel (~0.4px) squeeze on the natural monospace width of "Aa" at `text-xs` — centered and unclipped, the one place the refactor is not byte-identical to the original markup.

**In-bar consumers**: `SplitControl`'s primary segment, `ClosePaneButton`, `RefreshButton`, `FixedWidthToggle`, `BoardAutofitToggle`, and the `TerminalFontControl` trigger — all render the shared components with their inline SVGs deleted. **Menu/popover consumers**: the two `SplitControl` popover rows plus `SplitMenuRow` ×2, `ClosePaneMenuRow`, `RefreshMenuRow`, `FixedWidthMenuRow`, `AutofitMenuRow`, `TerminalFontMenuRow`. The tty tile header's pane segment (§ Surface Layout → Tile renderer) consumes `SplitHorizontalGlyph`, `SplitVerticalGlyph`, and `ClosePaneBoxedGlyph` (`260813-w1lf`). Two inline rotate-cw copies remain outside the module's reach and are **deletion candidates** for a follow-up: `top-bar-overflow-menu.tsx`'s "Check for updates" button (byte-identical to `RefreshGlyph`, and it lives in this very menu) and `sidebar/status-panel.tsx`'s pane-header refresh (a sidebar control outside the top-bar vocabulary — a shared home would need a module neither `top-bar-icons.tsx` nor `sidebar/icons.tsx` owns today).

**Tests.** `top-bar.test.tsx` asserts, via the `data-icon` seam: every terminal-mode menu row leads with its glyph while row accessible names stay unchanged; both SplitControl popover rows lead with direction glyphs and the primary segment shares the `split-horizontal` definition; the in-bar Refresh renders the shared refresh glyph; `FixedWidthMenuRow` keeps a **static** identity glyph across ON/OFF with the trailing ✓ as the sole state marker; and on board mode `Autofit panes` leads with the UNFILLED identity glyph even when autofit is ON while `Kill` leads with the close glyph. ### Open split-button (`open-button.tsx`)

**A Conductor-style "Open ▾" split-button in the top-bar right cluster that opens the active pane's folder in an editor/app** — the FIRST L1 registry candidate (§ Right cluster), **Terminal mode only in v1** (the folder is the active pane's cwd, already derived server-side; server/board routes have no unambiguous folder). `OpenButton` is a two-segment control: a **primary segment** re-runs the last-used target, and a **chevron** opens the full menu. `OpenMenuRows` is the overflow representation (one `Open: {label}` row per target; § Right cluster overflow menu-row representations). (`260722-6d0f-navbar-open-in-app`)

**Two mechanisms, chosen by local/remote branch** (pure `buildOpenTargets({hostname, sshHost, sshUser, hostApps, path})` in `lib/open-in-app.ts`, which derives `local` and the effective deeplink host internally):

- **Deeplink targets** — from the static `DEEPLINK_APPS` const (`lib/open-in-app.ts`): VS Code · Cursor · Windsurf, each a `(host, path) => "{scheme}://vscode-remote/ssh-remote+${host}${path}"` template (vscode/cursor/windsurf schemes over the shared `ssh-remote` grammar). No API, no detection — a plain frontend const (the templates live in run-kit's frontend only; architecture.md § Design Decisions → Open-in-app). Shown on **any remote** client (all three unconditionally — client installs are unknowable, a dead scheme no-ops on click); the section's visibility is not gated on `RK_SSH_HOST`. Activation is a plain user-gesture `window.location.href = url` navigation — the browser shows its own "Open <app>?" confirm.
- **Host targets** — from `GET /api/open-apps` (the `wt` registry). Shown as the sole section on a **local** client, and as an explicitly labeled **"on host"** escape hatch on a remote client. Activation calls `openInApp(server, path, app)` (`POST /api/open`) with an error toast on failure. Hidden when the registry is empty.

**Deeplink host resolution** (pure `resolveDeeplinkHost({sshHost, sshUser, hostname})`): (1) `RK_SSH_HOST` set → use it **verbatim, never `user@`-prefixed** (an alias carries user/port/key from the client's `~/.ssh/config`); (2) unset AND remote → derive `${sshUser}@${location.hostname}` (the name the browser reached the host by — SSH-reachable on a tailnet — plus the server-derived username from `GET /api/health`; the `user@` prefix is **omitted when `sshUser` is empty**, leaving the bare hostname, and the hostname is used as-given with no reachability guessing); (3) local → empty.

**Local/remote branch** keys on `isLocalHostname(location.hostname)` (∈ `localhost`/`127.0.0.1`/`[::1]`). **Section visibility composes to zero-target hiding**: the deeplink section shows for **any remote client** (no `sshHost` gate), the host section is hidden when the registry is empty — when no targets remain the whole control renders nothing (registry `hidden`; a control with an empty menu is a dead control). A local client with an empty registry still renders nothing.

**Split-button behavior + last-used preference.** The primary segment re-runs the **last-used target**, persisted to `localStorage["runkit-open-last-used"]` (`LAST_USED_OPEN_TARGET_KEY`, the `runkit-*` preference convention — same shape as `runkit-terminal-font-size` / `runkit-last-pinned-board`, best-effort try/catch-noop so private mode / quota never throw). With **no stored preference** (or a stored target that is no longer available), the primary click **opens the menu instead**. Clicking a menu target runs it AND persists its id as last-used, then closes the menu. Target ids are **kind-qualified** (`deeplink:vscode` / `host:vscode`) so deeplink and host entries for the same editor never collide.

**Primary segment last-used glyph.** When `lastUsed` resolves non-null (`resolveLastUsedTarget(targets, readLastUsedOpenTarget())`), the primary segment renders `<OpenTargetIcon target={lastUsed} />` (`open-app-icons.tsx`, § Row icons) before the kept "Open" text, so the segment shows WHICH app a primary click launches. The glyph is `aria-hidden` `currentColor` decoration — it rides the segment's `text-text-secondary hover:text-text-primary` flip for free (a small `gap` spaces it from the text) and stays out of the accessible name. **No glyph when `lastUsed` is null** (nothing stored, or the stored id no longer resolves against live targets — e.g. a cleared SSH host removed the deeplink section); the segment then looks text-only, exactly as the chevron-opens-instead case above. The accessible name is unchanged either way (`Open in {label}` when resolved, `Open in app` otherwise). Scope is the primary segment ONLY — the dropdown/overflow rows already carry their glyphs (§ Row icons). (`260723-l317`)

**Data ownership — an invalidatable external store, TopBar props untouched.** A `useOpenTargets(enabled)` hook (`hooks/use-open-targets.ts`) reads `OpenContext` `{sshHost, sshUser, hostApps}` from a small **module-level external store** consumed via React's `useSyncExternalStore` (a listener `Set` + `getSnapshot`), shared by every consumer. The bundle — `getHealth()` (`sshHost` + `sshUser`) + `getOpenApps()` — is fetched **once** and held; the context is then **static BETWEEN settings commits** (no client polling, no per-render refetch — the registry does not change on its own). The one runtime seam that changes it is the Settings dialog's successful SSH-host commit, which calls the exported **`invalidateOpenContext()`**: it bumps an epoch, drops the cache, and — when consumers are mounted — eagerly refetches the bundle and notifies subscribers so they re-render with the fresh `sshHost` **without a page reload**; with zero mounted subscribers it plain-drops the cache so the next `useOpenTargets(true)` mount fetches fresh (§ Design Decisions → Open control owns its data via an invalidatable external store; § Settings-commit invalidation seam). `enabled` gates the fetch; data still returns when another consumer already populated the store; both halves stay individually **fail-silent** (a failing health read ⇒ `sshHost`/`sshUser: ""`, deeplink section hidden, never a thrown error). `resetOpenTargetsCacheForTest()` resets the store cold between tests. The store feeds BOTH the TopBar registry entry (TopBar calls the hook itself) and the palette builder; no new TopBar props or slot-context fields are threaded through, keeping the e2e-asserted chrome surface stable. (`260723-l317`)

**Row icons** (`open-app-icons.tsx`, `OpenTargetIcon({target})`). Each Open menu row leads with a **monochrome `currentColor` inline SVG glyph** (~14px, `aria-hidden`, no image fetches, no icon dependency) — full-color brand marks would clash with the terminal aesthetic, and `currentColor` lets the existing row hover treatments (accent-green flips) apply to the glyph for free. Resolution: a `BRAND_ICONS` id map first (BOTH `vscode` — the deeplink id — and `code` — the wt host registry id — key to the VS Code glyph; plus `cursor`, `windsurf`), then a `KIND_ICONS` generic fallback by `kind` (editor → code-brackets, terminal → `>_` prompt, file-manager → folder — covers `ghostty_macos`/`terminal_app`/`finder` and any future entry), then a neutral open-in-app glyph for anything kindless. Deeplink targets resolve with implicit kind `editor`; host targets carry `appKind` from the wt registry `kind`. Each glyph carries a `data-icon` attribute naming the resolution (`vscode`/`cursor`/`windsurf`/`editor`/`terminal`/`file-manager`/`app`) — the test seam, since monochrome paths are otherwise indistinguishable to queries. Icons render on **both** row renderings (`OpenTargetRow` in the split-button dropdown AND `OpenMenuRows` in the overflow chevron menu); **command-palette rows stay text-only** (no icon affordance today).

**Keyboard parity (Constitution V).** Every available open target is a command-palette entry via the pure `buildOpenActions(targets, run)` (`lib/palette-open.ts`, the `lib/palette-*.ts` pattern), composed into `paletteActions` in `app.tsx`: `Open: <label>`, with host targets suffixed ` (on host)` ONLY on a remote client (disambiguating deeplink/host label collisions — a local view has no collision). The **per-target** entries carry no chord — the target set is data-driven and varies per deployment, so no static chord can name one; palette reachability satisfies §V, documented in the module's registration comment per the code-review rule.

**The last-used behavior does get a chord: ⇧⌘O / Shift+Ctrl+O (`open-last-used`).** Naming the *behavior* ("re-run the last-used target") rather than an app sidesteps the data-driven objection, giving the split-button's primary segment its keyboard twin. The builtin binding is `scope: "terminal"` and its handler is registered in `app.tsx` only when `windowParam` is set (the Open control is terminal-route-only; the board twin mounts no handler and the chord falls through). The handler resolves `resolveLastUsedTarget(openTargets, readLastUsedOpenTarget())` over the same live target set the palette uses and runs it through the shared `useRunOpenTarget().runTarget`, so chord, palette entry, and primary segment share one execution path and one last-used write. With nothing stored (or a stale id) the chord surfaces the info toast **"No last-used app yet — pick one from Open ▾ or the palette"** rather than trying to pop a mouse menu. The pure `buildOpenLastUsedAction(lastUsed, onRun)` adds the matching palette entry `Open: Last used (<label>)`, **hidden when no target resolves** (the dynamic suffix needs a target to name — the boundary-hidden convention of Move up/down); its id `open-last-used` doubles as the registry actionId, so `withShortcutHints` decorates it automatically. ### Window Heading (`WindowHeading` in `top-bar.tsx`)

The centered, highlighted, editable window heading — the single most important identity on the Terminal route (the tmux window name, e.g. `riff-gallant-jackal`). It gives the window name the prominence of a document title (mental model: browser-tab / editor title bar) and makes rename lowest-friction direct manipulation. Lives in the top bar's center grid cell (§ Chrome (Top Bar) center cell); renders only when `mode === "terminal" && currentWindow`. It is the terminal instance of the universal `PageType: name` heading — a static prefix span sits OUTSIDE the rename button, and the name is driven by the shared boot-sweep primitive (`useBootSweep`/`SweepCells`, § Hover-Animation Vocabulary → boot sweep). **The prefix is a static `Window:` in every lens** (§ Heading is a static `Window:`): `WindowHeading` takes a `prefix` prop, but the sole call site passes the CONSTANT `WINDOW_PREFIX` — the heading does not vary by lens (lens identity rides the tile content and the rail's lit toggles). (`260704-pr0p`, `260714-uco1`, `260717-6anu`, `260722-n2n4`)

**Two-tone prefix**: the `Window:` prefix (static in every lens) renders `text-text-secondary` as a **static sibling span outside the rename button/input** (`hidden sm:inline` — mobile keeps just the name) — clicking it never starts an edit, and the button's `aria-label` stays clean. The name keeps `font-semibold text-text-primary`. The prefix's frame states (dim ahead of cursor / typed behind) come from the boot sweep's `prefix` half. (`260704-pr0p`, `260714-uco1`)

**Three states** (one component):

- **display** — a `<button aria-label="Rename window {name}">` wrapped in `Tip label="Click to rename"` (the Tier-1 form — § Tier-1 `Tip`; the visible hover cue naming the rename action for sighted users, since the boot sweep signals interactivity without naming it and the `aria-label` covers screen readers) rendering the name (via `<SweepCells>` at rest → plain text) at `text-sm font-semibold text-text-primary` (weight-600 + primary color IS the "highlighted" rest state; the surrounding crumbs are secondary, so weight+color alone read as highlighted — no background). `max-w-[16ch] sm:max-w-[28ch] inline-flex items-center coarse:min-h-[30px]` (mobile-leaf touch target), with the name inside an inner `min-w-0 truncate` span — truncation MUST live on the span, not the button: `text-overflow` is inert on a flex container, and flex centering clipped long names on BOTH ends with no ellipsis (`riff-blustery-whale` → `iff-blustery-whal`). Left-anchored, so long names keep their head and cut at the tail; the button itself stays centered in the grid cell. Click enters edit.
- **boot sweep** — the JS sweep from `useBootSweep` (§ Hover-Animation Vocabulary → boot sweep). One inverse-video accent-green cursor at `DECODE_FRAME_MS = 28`ms/cell sweeps `Window:` + space + name; over the prefix it types (TypedLabel states), over the name it churns `DECODE_GLYPHS`. The heading container does NOT flip `text-accent-green` for the whole scramble — green lives ONLY on the per-cell churn/cursor spans inside `SweepCells`; each resolved cell settles to its own REST color (`restCellClass`: prefix → `text-secondary`, name → semibold `text-primary`), so the left-to-right two-tone reveal is visible instead of a uniform green flash. **Guards**: (a) a `DECODE_HOVER_INTENT_MS = 140`ms hover-intent delay before the sweep starts (cursor transit toward the right buttons doesn't replay it); (b) edit-start stops the sweep and the input binds to the real `name`/`draft` state, never the scrambled DOM text; (c) the sweep replays once whenever the **DISPLAYED name changes** — a `prevNameRef` **seeded `null`** effect keyed on the incoming `name` prop. The null seed plays the sweep ONCE on mount (first name resolution flips `prevNameRef` from `null`), so route navigation between page types animates — AND a committed rename, an SSE external rename, and window navigation all replay through the same name-change mechanism. This is why the instance is NOT remounted per window — a fresh mount would re-seed `prevNameRef` to `null` and replay every time / double-play. Skipped entirely under `prefers-reduced-motion` (`prefersReducedMotion()` reads `window.matchMedia`, guarded for jsdom — the rest state IS the reduced-motion state). (`260704-pr0p`)
- **edit** — an identically-styled inline `<input aria-label="Window name">` (monospace, `text-left font-semibold text-text-primary`, `border-b border-accent`; `text-left` so the name does not jump horizontally on edit entry given the left-anchored heading), width sized in `ch` and growing with content (`Math.max(draft.length + 1, 3)ch`), `autoFocus` + select-on-focus. **Enter commits, Escape cancels, blur commits**; empty/whitespace-only trim on commit = cancel (matches the sidebar/dialog trim guard); an unchanged name is also a no-op. Commit calls the shared `useWindowRename()` hook (§ Shared window rename below) — optimistic store rename + toast on error — then optimistically sets the display; the name-change effect replays the sweep when the store-driven `name` prop settles. (`260714-uco1`)

**Keyboard path (Constitution V)**: the command-palette `Window: Rename` action dispatches a `window-heading:rename` `CustomEvent` (mirroring `theme-selector:open`); a document-level listener in `WindowHeading` enters inline edit. There is no rename modal dialog — the inline edit (heading + sidebar) is the only window-rename surface; see § Keyboard Shortcuts (the palette rename action) and § Component Conventions (the shared `Dialog`). Only the SESSION rename dialog lives in `app.tsx`.

**External-switch cancel**: a `prevIdentityRef` effect keyed on `${server}:${windowId}` cancels an in-progress edit when the window identity changes out from under it (another client / tmux switching the route) — committing the typed name onto the newly-navigated window would rename the wrong window.

**Open menu escapes any `overflow:hidden` ancestor via `position: fixed`.** The open `role="menu"` element renders **`position: fixed` anchored to the trigger's viewport rect** — it measures `buttonRef.getBoundingClientRect()` on open and positions its top-left at `rect.bottom + gap` / `rect.left`, recomputing (or closing) on `scroll`/`resize` (capture-phase, so a scrolling ancestor container is heard) so it never detaches from the moving trigger. **The reusable invariant — clip-backstop vs. contained popover**: when you add `overflow-hidden` (or `overflow-clip`) to a container that also *holds* a popover, a plain `absolute` popover inside it gets **both clipped AND focus-scroll-displaced** — `overflow:hidden` turns the container into a scroll box, and the menu's focus-on-open `scrollIntoView` then scrolls the whole container's content out of its own clip box. This is exactly the bug the `q8ey` nav clip-backstop (§ Center-heading … → degradation ladder step 3) introduced on the session-switcher menu (empirically: post-clip the menu landed off-viewport at y≈-75 with an empty hit-test; pre-clip it rendered visible at y≈37). The nav clip is a user-approved requirement, so the resolution is to let the menu **escape the clip context**, not weaken the clip — and `position: fixed` is viewport-relative, so no `overflow:hidden` ancestor can clip it. `overflow-clip` on the container would have fixed only the focus-scroll (a clip box is not a scroll container), not the clipping itself. Because the escape lives in the shared `BreadcrumbDropdown` component, it applies identically to **both call sites** (window switcher, board switcher); it keeps `z-50`, the `min-w-[160px] max-w-[240px]` sizing, and the existing click-outside / Escape / Arrow-key focus behavior. **Rule for future clips**: adding `overflow-hidden` to any container that contains a popover requires that popover to escape via fixed/portal positioning, or the popover breaks. (`260715-q8ey`)

### Crumb Affordance Vocabulary

Breadcrumb crumbs advertise their interactivity WITHOUT hover — an affordance vocabulary where the current-page LEAF lives in the centered heading, not the left nav (§ Chrome (Top Bar)), so the "you are here" signal is the centered heading itself. The cases: (`260704-pr0p`, `260813-kvk7`)

- **Link crumbs** (brand, server link) — carry the shared `LINK_CRUMB_CLASS` constant (`top-bar.tsx`): the **bordered chip** box (`CRUMB_BOX_CLASS` — `rounded border border-border px-1.5 py-0.5 text-text-secondary`) PLUS the hover treatment (`hover:border-text-secondary hover:text-text-primary transition-colors`), reusing the right cluster's "bordered = clickable" language. The user compared three candidates live (chip / accent color / dotted underline) and picked the chip; the unused variant definitions were removed at lock-in. *(Accent color was rejected — hue is reserved by the StatusDot phases; dotted underline was rejected — it left the mobile icon-only brand with no affordance, and text-decoration doesn't propagate into an anchor's flex children, so the wordmark needed a `[text-decoration:inherit]` patch that the chip doesn't.)*
- **Static chip** (session crumb) — the same `CRUMB_BOX_CLASS` box with NO hover classes, no pointer cursor, and no caret: a session has no route of its own, so the box is pure crumb styling (visual consistency across the trail), and interactivity cues are reserved for crumbs that do something. Session switching/creation live in the sidebar and palette (§ Chrome (Top Bar) → Terminal).
- **Dropdown triggers** (the window/board switchers) — bare-`▾` `BreadcrumbDropdown`s in the top bar's center cell beside their headings (§ Chrome (Top Bar) center cell). Signals "opens a switcher", distinct from "navigates". (`260703-5ilm`, `260704-pr0p`)
- **Current-page leaf** — there is NO leaf crumb in the left nav; the current page's identity is the **centered `PageType: name` heading** (the tmux Server page's identity is the centered `tmux Server: <server>`). The heading carries the "you are here" role. (`260704-pr0p`)

*Why not hover-only cues*: a `hover:text-text-primary` cue is invisible to first-time users and absent entirely on touch. (`260702-6m46`)

### Desktop-Shell Titlebar Strip (`components/shell-titlebar-strip.tsx` + `lib/shell-strip.ts`)

The instance accent's **third consumer surface**, and the only one that exists outside a browser: inside the Electron viewer shell the native titlebar is hidden, so the SPA draws the window's titlebar itself as a 28px full-width band above the top bar. The accent chain is therefore PWA titlebar meta → top-bar wash/stripe → **shell titlebar strip**, all three fed by the same `useInstanceAccent()` instance.

**Background is `titlebarHex`, read not re-derived.** The strip paints `titlebarHex ?? theme.palette.background` — the identical ~35% accent-into-background blend the installed-PWA titlebar carries, which is the point: the same window chrome should be the same color whether run-kit is installed as a PWA or as the desktop app. It consumes the context's exposed field rather than calling `deriveAccentHexes` again, so one derivation cannot drift into two (§ Design Decisions → `titlebarHex` is exposed, not re-derived). With no accent resolved the band falls back to the plain theme background and is still a drag surface.

**Drag region via a CSS utility class, with exactly one no-drag island.** The band carries `.rk-shell-drag` (`globals.css`: `-webkit-app-region: drag`); the host-switcher trigger and its open menu carry the sibling `.rk-shell-no-drag` (`-webkit-app-region: no-drag`) and are the band's **only** interactive island — everything else in the band drags the window. Both are classes because `WebkitAppRegion` is absent from React's `CSSProperties` and an inline style would need an `as` cast the code-quality rules forbid; `rk-*` is also where the utility vocabulary already lives. The classes are inert in browsers, so they cost nothing outside the shell (§ Design Decisions → Drag regions are a CSS utility class; → The strip's switcher trigger is the band's only no-drag island).

**The label names the window's host, and is the switcher trigger.** A centered, truncated `location.hostname`-fallback label showing the shell-registered **active** host's display name, fetched on mount via `listShellServers()` and reduced by the pure `activeShellHostName(servers)`. Text color is `stripLabelColor(bg)` — a `contrastRatio` pick between the two standard text hexes, the same WCAG helper the border guard uses. Horizontal insets keep it clear of the OS controls compositing over the band: a fixed symmetric 80px on darwin (traffic lights sit left; symmetry keeps the label visually centered) and `titlebar-area-*` env expressions elsewhere, which degrade to no inset where window-controls-overlay is absent. `stripLabelColor`, `stripInsets`, `activeShellHostName`, and the shared `SHELL_STRIP_HEIGHT_PX` / `SHELL_STRIP_MARKER_CLASS` constants live in `lib/shell-strip.ts` with a colocated vitest suite.

**Host-switcher dropdown — the mouse-secondary switch path.** When the bridge answers a **non-empty** host list (`stripSwitcherEnabled(servers)`, a type guard) the label renders as a trigger button — `<active-host-name> ▾`, `aria-haspopup="menu"` / `aria-expanded`, `aria-label="Switch host"`, with a subtle currentColor-tinted hover pill (`hover:bg-current/15`, which reads on any accent-blended strip background since the label color is already contrast-derived against it) — reusing the top bar's `▾` switcher vocabulary (§ Crumb Affordance Vocabulary). It is the mouse-secondary companion to the ⌥⌘1–9 / ⇧Ctrl+1–9 accelerators and the palette's `Server: Switch to` block, which stay the primary paths (Constitution V). Below the gate — an older shell exposing only `version`/`platform`, a denial, or an empty store — the label is a plain static span with no chevron, no pill, and no click behavior; the band still mounts, because its gate is `isShell()` alone (§ Design Decisions → Shell chrome mounts on `isShell()`).

**Row anatomy** (`shellHostMenuRows(servers, platform)` in `lib/shell-strip.ts`, list order preserved because that IS the native menu's binding order): a fixed-width ✓ marker column so names align, the active row in `text-accent`; the display name; the **dimmed origin** (`new URL(url).origin`, falling back to the raw string on a parse failure) — host display names are not unique because the shell's store never dedupes, so the origin disambiguates; and a trailing accelerator hint `⌥⌘{n}` on darwin / `⇧Ctrl+{n}` elsewhere, `null` past `MAX_SHELL_SWITCHER_HINTS = 9` (mirroring the native menu's `MAX_SWITCHER_ACCELERATORS` — a host with no binding gets no hint). Platform comes from the bridge's `shellInfo()?.platform`. The row model also carries two additive, independently optional fields from the `servers:list` projection ([desktop-shell](/run-kit/desktop-shell.md) § Bridge): `accentColor: string | null` — the host's persisted instance accent (the full-strength `stripeHex` each host's SPA reports over `accent:set` via `ShellAccentReporter`; a host last captured by the older theme-color fallback carries a 35% titlebar blend instead and its bar renders muted until the raw report overwrites it — [desktop-shell](/run-kit/desktop-shell.md) § Bridge), passed through only when it hex-validates against a strict `#RGB`/`#RRGGBB`/`#RRGGBBAA` pattern (the shell-side `fallbackStripCss` precedent — an unvalidated value never reaches style interpolation); and `waiting: number | null` — the view-registry-joined waiting-agent count, kept only when positive and the row is NOT active (the active host's attention surface is the dock badge). An older shell's plain `{id, name, url, active}` projection parses fine with both fields absent (`isShellServer` validates optionals strict-when-present) and derives `null`/`null`.

**Three capability-gated row features render off that model.** A non-null `accentColor` paints a ~3px left-edge bar (`absolute bottom-1 left-0 top-1 w-[3px] rounded-full`, `aria-hidden`) overlaid on the row's edge, so a colorless row keeps identical text alignment. A non-null `waiting` renders an amber `● {N}` chip (`text-amber-600`) in the trailing `ml-auto` cluster before the accelerator hint — waiting-only semantics, `0`/absent renders nothing, matching the dock badge's "non-zero means act now" rule. **Manual reorder** rides the optional `reorder` invoker (`canReorderShellHosts()` / `reorderShellHosts(id, toIndex)` in `lib/shell.ts`, following the optional-invoker pattern exactly — separate structural narrowing of the additive bridge member, `false` outside the shell or on rejection, never throws): a hover-revealed drag grip (`⋮⋮`, trailing edge, width reserved by `pr-6` only when the capability is present) starts an HTML5 drag keyed on a custom MIME (`application/x-shell-host-reorder`, so it never collides with the sidebar/board drag payloads); the local order reorders optimistically during the drag (derive-over-store presentation state — the open-time refetch reconciles), and exactly ONE `reorderShellHosts(id, toIndex)` commits at drop, with a failure surfacing the error-toast precedent plus a refetch. With the menu open, ⌥↑/⌥↓ (Alt+ArrowUp/Down on ALL platforms — arrows compose no characters, so the macOS Option-composition issue does not apply) moves the focused row one step per keypress with the same optimistic reorder so the accelerator hints re-number live; focus follows the moved row, there is no wrap at the list edges (an edge move swallows the key without invoking the shell), and the Add-Host footer is not movable. Each committed move lands in the shell's store and rebuilds its native menu ([desktop-shell](/run-kit/desktop-shell.md) § `window.runkitShell` Bridge). Without the capability (older shell) no grips render and Alt+arrows fall through to the plain roving-focus cycle; all three features degrade independently, so an older shell renders exactly the marker/name/origin/hint rows.

**Refetch on open, guarded by a monotonic sequence.** Every open issues a fresh `listShellServers()` — the native `Hosts → Remove "<name>"…` menu mutates the store without a page reload, so a mount-time-only list goes stale. One `listSeqRef` counter guards *both* fetches: a resolution whose sequence is not the latest issued is dropped, so out-of-order resolutions can never leave a stale list rendered, and the mount effect's cleanup bump doubles as cancellation (the open-time fetch has no effect cleanup to cancel it). A `null` resolution — the never-throw wrapper's denial signal — keeps the last known list rather than blanking an open menu.

**Menu semantics copy `BreadcrumbDropdown`'s contract** (§ Breadcrumb Dropdowns): `role="menu"` with `role="menuitem"` rows, capture-phase keydown for Escape (close + refocus trigger) and ArrowDown/ArrowUp (wrapping roving tabindex — Alt-modified arrows are intercepted for row moves instead when the reorder capability is present; Enter needs no handler because each row is a native `<button>`), outside-`mousedown` close, and focus landing on the active row on open. The menu is a plain `absolute left-1/2 top-full` anchor — the strip has no `overflow: hidden` ancestor clipping below it, so no fixed-position machinery is needed — and it paints in theme surface colors (`bg-bg-primary`/`border-border`) rather than the strip's accent blend, because it overlays SPA content below the band. Three guards make an open-time refetch that changes the row count safe: the seed effect keys on the **open transition only** (re-running on a refetched set would yank focus mid-arrowing); a separate clamp effect keyed on `[open, rows.length]` re-seats the roving tabindex when a refetch *shrinks* the set below the current seat (an in-bounds seat is left alone, so an unchanged or growing list never moves focus); and the arrow branch's emptied-list guard reads the live committed row count from `hostCountRef` — a ref a `useLayoutEffect` keyed on `rows.length` writes at commit time — returning before `preventDefault` when it is 0, so even a stale capture-phase subscription still attached in the commit→passive-effect-flush window observes the zero and releases the key instead of swallowing arrows app-wide (a passive-effect ref write would flush in the same phase it is meant to beat); the wraparound modulus derives from the same live read, so a shrunk-but-non-empty refetched list also cycles over the committed count (§ Design Decisions → The emptied-list arrow guard reads the live row count from a commit-synced ref). A close-on-empty effect then releases `open` so the menu's effects tear down with it.

**Selection hands off to the shell, no optimistic UI.** Picking a row closes the menu and calls `switchShellServer(id)`; the shell's single `switchToHost` seam swaps the displayed host, so there is nothing to update optimistically and no SPA-side path handling exists. The swap is a detach/attach flip between per-host renderer views ([desktop-shell](/run-kit/desktop-shell.md) § Host Views), so this component instance simply stops being displayed — it keeps running, with its state intact, and is shown again unchanged when the user switches back. A `false` resolution surfaces an error toast (the palette's precedent), and selecting the already-active row is a harmless no-op — the same behavior the palette action and the native menu radios have, so all three switch paths behave identically.

**Marker class + mount gating.** While mounted the component sets `rk-shell-strip` on `<html>` (a `useLayoutEffect`, removed on unmount) — the shell's version-skew fallback CSS is keyed on `html:not(.rk-shell-strip)` and self-disables against it ([desktop-shell](/run-kit/desktop-shell.md) § Hidden Titlebar & Accent Strip). `AppLayout` mounts the strip gated on `isShell()`, as a **sibling above** the top-bar wrapper — the top bar itself is untouched, which is the explicit contrast with a titlebar merge. `isShell()` is false in every browser and in Playwright, so **no e2e sees the strip or its dropdown**: the whole surface is covered by two colocated vitest suites — `lib/shell-strip.test.ts` for the pure helpers and `shell-titlebar-strip.test.tsx` for the component (rendered inside `ToastProvider`, asserting the gate branch, the open-time refetch call count, row anatomy including the accent bar / waiting chip / drag grip, ⌥↑/⌥↓ moves with live hint re-numbering and edge no-ops, drop-commits-one-invoke, the older-shell degradation, shrunk/emptied-list focus behavior, out-of-order resolutions, selection, and Escape/Arrow keys) — plus manual verification in the real shell. The band persists in macOS fullscreen (traffic lights auto-hide over it; no fullscreen bridge flag exists).

### Desktop-Shell Waiting Badge Reporter (`components/shell-badge-reporter.tsx`)

A null-rendering subscriber, mounted in `AppLayout` beside the strip and gated on `isShell()`, that mirrors the waiting-agent count to the OS dock/taskbar badge — the attention tier escaping the page (§ Attention Surfacing). It is the fifth `lib/waiting.ts` consumer and the only one whose output leaves the browser.

The count is `countWaitingAcrossServers(sessionsByServer)` — a new helper composing the existing `countWaitingInSessions` over every entry in the streamed map, so the badge counts identically to the sidebar and tile badges. It derives from SSE state already in the client: no polling, no new endpoint (Constitution II). **Scope caveat**, inherited from `sessionsByServer` itself: only **attached** servers stream windows, so an unattached server contributes 0 — the same accepted constraint the Host-page and sidebar server tiles carry.

Reporting is change-only: the derived count is the effect dependency and a ref guards re-mount duplicates, so a 2 → 2 SSE tick makes no bridge call while 2 → 0 reports `0` explicitly (clears must propagate). The call goes through `setShellBadge(count)`, which never throws — a plain browser or an older shell without the `badge` bridge group simply resolves `false`.

## Design Decisions

### `menuOnly` is a registry capability, not a one-control hack
**Decision**: never-in-bar placement is a generic optional `menuOnly?: boolean` on `RegistryEntry`, honored by the candidate pipeline for ANY entry (excluded from bar + probe + fit; its `menuRender()` rows always in the menu; `hidden` keeps priority). Six entries set it — `fixed-width`, `terminal-font`, `close-pane`, `help`, `keyboard`, `theme` — each costing nothing but the flag (§ Right cluster → `menuOnly` demotions).
**Why**: rides the existing overflow machinery (`ViewSwitcherMenuRows` already existed and was wired), so reverting when the chat lens is ready is deleting one flag, and any future control can opt in. The chat lens is not fully functional, and an inline `[tty|chat]` pill advertised a half-finished lens in the most prominent chrome position.
**Rejected**: a one-off "skip the view-switcher" special case in the fit wiring (same diff, not reusable, harder to revert cleanly); removing the `ViewSwitcher` component or feature-flagging `hasChat()` (breaks the web lens / hides chat capability the user wants reachable); splitting the switcher so web stays inline while chat is menu-only (violates spec R4's one-switcher contract). The `[tty|web]` pill on iframe-URL windows moves too — accepted over splitting the unified switcher.
*Introduced by*: 260722-n2n4-view-switcher-menu-only

### Overflow list is candidates-minus-visible, not a menuOnly+overflowed concat
**Decision**: `overflowItems` is computed as `candidates.filter((e) => !visibleIds.has(e.id))` — the full candidate list minus the in-bar (visible) set — rather than concatenating the `menuOnly` entries with the non-fitting fit-candidate prefix.
**Why**: one expression preserves registry (pyramid) order for free — `menuOnly` entries interleave at their registry positions — and cannot double-count.
**Rejected**: an explicit concat of `menuOnly` + overflowed-fit-candidate lists (requires a re-sort by registry index to preserve order).
*Introduced by*: 260722-n2n4-view-switcher-menu-only

### Close distinction is glyph + grouping + distance
**Decision**: Close Pane is the boxed ⊠ inside the bordered pane segment; the tile-close ✕ is the bare glyph isolated far right behind a hairline. Both keep `text-signal-red` hover.
**Why**: Two destructive closes in one header need structural distinction, not just labels; the misclick-trap mitigation is shape + grouping + ~5-button spatial separation.
**Rejected**: A confirm dialog (terminal close-pane is deliberately immediate); identical glyphs with different tooltips (invisible at rest).
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### Terminal split demotion rides the dynamic `menuOnly` flag
**Decision**: `menuOnly: mode === "terminal"` on the single existing `split` registry entry, mirroring the dynamic `hidden` predicates.
**Why**: The registry rebuilds per render with `mode` in scope; a dynamic flag is the minimal diff and keeps one entry driving both modes' bar and menu forms (no drift).
**Rejected**: Splitting into separate terminal/board registry entries — duplicates menuRender and risks the bar↔menu drift the single-source registry exists to prevent.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### TopBar mounts once at the root layout
**Decision**: `TopBar` mounts a single persistent instance at the pathless `app-layout` route, above the router `<Outlet>`, and re-renders in place across route changes; a `<Suspense fallback={null}>` boundary wraps ONLY the `<Outlet>` content region, not the header.
**Why**: mounting `TopBar` per-page unmounts one instance and mounts a fresh one on cross-page navigation — a visible navbar "reload"/flicker (a component-identity problem, not an MPA→SPA gap; the app is already an SPA). A single persistent mount keeps the bar continuously present with a per-route heading; scoping Suspense to the Outlet keeps the bar painted while a lazy page chunk loads.
**Rejected**: per-page `TopBar` mounts (three instances — AppShell, HostOverviewPage, BoardPage — caused the flicker); wrapping the header in the Suspense boundary (blanked the bar on lazy load); hosting the bar directly in `RootWrapper` (the index route `/` is a direct child of the root at the same pathname, so root→index is structurally shorter than root→serverLayout→…, and React remounted the root subtree on the index transition — the pathless layout normalizes tree depth).
*Introduced by*: 260707-4vq2-lift-topbar-root-layout

### Refresh is a full page reload
**Decision**: the top-bar RefreshButton does a full page reload (`window.location.reload()`; Shift+click force-reloads), not a targeted relay reconnect.
**Why**: the reload is non-destructive by design (all client state re-derives on load; tmux sessions are unaffected) and needs no spinner because the page unloads synchronously.
**Rejected**: a `TerminalClient` `key`-bump remount to reconnect just the relay (deferred as a possible follow-up); tmux `respawn-pane` (destructive — kills the running process).
*Introduced by*: 260703-p29w-topbar-refresh-button

### Drag regions are a CSS utility class, not an inline-style cast
**Decision**: `globals.css` defines `.rk-shell-drag { -webkit-app-region: drag; }` and `.rk-shell-no-drag { -webkit-app-region: no-drag; }`; the shell titlebar strip applies them as classes. No component writes `-webkit-app-region` inline.
**Why**: `WebkitAppRegion` is not in React's `CSSProperties`, so an inline style needs an `as CSSProperties` assertion — exactly the type-assertion-over-narrowing pattern the project's code-quality rules forbid. A class sidesteps the type system entirely, is inert in browsers, and lands in the `rk-*` utility vocabulary the codebase already uses for non-Tailwind primitives (`rk-scanlines`, `rk-hazard`, `rk-waiting-seam`). The `no-drag` sibling exists for the same reason as the `drag` one and serves the strip's single interactive island (→ The strip's switcher trigger is the band's only no-drag island).
**Rejected**: `style={{ WebkitAppRegion: "drag" } as CSSProperties}` (the banned assertion); a `<DragRegion>` wrapper component (a component to carry one declaration); augmenting React's `CSSProperties` type globally (a global type change to serve one property in one component).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The strip's switcher trigger is the band's only no-drag island
**Decision**: The titlebar strip band holds exactly ONE interactive element — the host-switcher trigger and its open menu, carrying `.rk-shell-no-drag`. Everything else in the band is a pure drag surface, and no other chrome is admitted into it. The one-island scope IS the rule: the band's job is drag + host identity, and the switcher is admitted only because it IS that identity ([desktop-shell](/run-kit/desktop-shell.md) § Design Decisions → The titlebar is colored by a page-drawn strip).
**Why**: The strip's centered label *names* the switchable identity, so an inert label is a discoverability dead end for the shell's most identity-defining action — otherwise reachable only through the native menu, the ⌥⌘1–9 accelerators, and the palette, all keyboard-or-menu paths where Constitution V asks for a mouse-secondary one. A single carve-out costs nothing the whole-band drag rule protects: the cost that rules out a titlebar merge is `no-drag` exceptions threaded through *every* control of live chrome, whereas one pill on an otherwise unchanged band leaves the drag surface the whole band minus that pill and the SPA top bar below untouched. It also needs zero new IPC — `servers.list()` and `servers.switch` already serve the palette block.
**Rejected**: Leaving the band inert so switching stays keyboard/menu-only (the discoverability dead end above); merging the top bar into the titlebar so its controls become the chrome (the option the strip decision rejects, at the same cost, over a much larger surface); putting the switcher in the top bar below the strip (the strip's label is where the eye already rests for host identity, and duplicating the host name in two bars breaks the move-don't-copy rule); admitting further chrome into the band on this precedent (the island is scoped to identity, not opened to chrome generally).
*Introduced by*: 260731-4bqi-shell-strip-host-switcher-dropdown

### Host-switcher accelerator knowledge lives in three shapes, not one helper
**Decision**: The mac-vs-other host-switcher accelerator knowledge is intentionally triplicated: `app/desktop/src/menu.ts` holds `MAX_SWITCHER_ACCELERATORS` plus Electron's `Alt+Cmd+{n}` / `Shift+Ctrl+{n}` binding syntax; `components/shortcuts-overlay.tsx` holds the `switcherCaps` segmented keycap array keyed on `"mac"`; and `lib/shell-strip.ts`'s `hostAcceleratorHint` holds the `⌥⌘{n}` / `⇧Ctrl+{n}` display string keyed on `"darwin"`. No shared constant spans them.
**Why**: The three consumers span the Electron main/renderer process boundary — `menu.ts` runs in main and cannot import from the SPA bundle — and each needs a genuinely different *shape*: Electron accelerator syntax, an array of keycap segments for the overlay's rendering vocabulary, and a single glyph string for a menu row. Their platform vocabularies also differ (`"mac"` vs `"darwin"`), following each side's own convention. Extracting a shared source would mean a cross-process package plus a shape-conversion layer for three call sites.
**Rejected**: A shared accelerator module imported by all three (crosses the main/renderer boundary the shell's electron-free-module discipline maintains); deriving the display strings from the Electron syntax at runtime (a parser for three literals); collapsing the overlay's segmented array to a plain string so two of the three could share (loses the keycap rendering the overlay is built on). A future change to the binding tier must update all three deliberately — this entry is the pointer that names them.
*Introduced by*: 260731-4bqi-shell-strip-host-switcher-dropdown

### The host-switcher waiting chip surfaces background hosts only
**Decision**: The dropdown's amber `● N` waiting chip derives from the `servers:list` projection's `waiting` field but is nulled on the ACTIVE row in `shellHostMenuRows` — only background hosts ever show a count.
**Why**: The menu's job here is to make a background host's waiting agents visible BEFORE the user switches; the active host already has its attention surface — the dock/taskbar badge, which stays deliberately active-host-only ([desktop-shell](/run-kit/desktop-shell.md) § Dock/Taskbar Waiting Badge). Showing the count on the active row too would duplicate that signal inside the menu that already serves it.
**Rejected**: Showing the count on every row including the active one (duplicates the dock badge on the one host whose count the user can already see); aggregating all hosts' counts into the dock badge instead (contradicts the badge's per-window identity claim — a recorded non-goal).
*Introduced by*: 260813-1i7j-host-switcher-color-reorder-waiting

### Shell chrome mounts on `isShell()`; switch affordances gate on list emptiness
**Decision**: The titlebar strip and the badge reporter are *mounted* from `AppLayout` behind `isShell()`. Every affordance that actually *switches* hosts — the shell server-switch palette block and the strip's own switcher trigger inside the mounted band — gates instead on `listShellServers()` resolving a non-empty list (`stripSwitcherEnabled`). The two gates nest: the band mounts on `isShell()`, its trigger appears on the list.
**Why**: The gates answer different questions and both answers are right for their surface. A switch affordance asks "does the `servers` bridge group actually answer?" — an older shell exposes `version`/`platform` without the group, and offering a switch that cannot switch is worse than offering none. Window chrome asks "is this a shell window at all?" — the strip must exist whenever the native titlebar is hidden, even if `servers.list()` fails (the label falls back to `location.hostname`), and the reporter is harmless when the `badge` group is absent (`setShellBadge` resolves `false`). Splitting the strip's mount gate from its trigger gate is what lets both answers hold on one surface: a denied list degrades the band to a static label instead of removing the window's drag surface.
**Rejected**: Gating the strip's *mount* on the `servers` list (a failed or denied list call would remove the window's only drag surface — a bridge hiccup becomes an unusable window); gating the strip's trigger on `isShell()` alone (an older shell would render a chevron whose click can never switch); gating the palette on `isShell()` (the less accurate signal for that surface); a single shared gate for all of it (the surfaces have genuinely different failure semantics).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### The emptied-list arrow guard reads the live row count from a commit-synced ref
**Decision**: The shell titlebar strip's capture-phase keydown handler reads the host-row count from `hostCountRef.current` inside `handleKey` — both the emptied-list guard (`if (hostCount === 0) return`) and the wraparound modulus key on that live read — and a `useLayoutEffect` keyed on `rows.length` keeps the ref current at commit time.
**Why**: A capture-phase handler stays attached from a commit until the passive-effect flush swaps the subscription, so a closure-captured count reads stale exactly in that window — after an open-time refetch empties the list, the stale handler would `preventDefault` ArrowDown/ArrowUp app-wide until the flush. The ref read makes the guard subscription-staleness-proof: it reflects the committed count regardless of which render subscribed the handler. The layout-effect write satisfies the no-later-than-commit contract without mutating a ref during render (unsafe under discarded concurrent renders); a passive `useEffect` write would flush in the same phase it is meant to beat. This also retired a CI-only flake in the colocated suite, whose synchronous `fireEvent.keyDown` could land inside that window.
**Rejected**: A closure-captured count (the stale-subscription window itself); a passive-effect ref write (same-phase flush); forcing synchronous effect teardown (fights React's effect model); wrapping the test's timing in `act` (fixes the test while leaving the production arrow-swallow window in place).
*Introduced by*: 260811-fgzi-shell-titlebar-arrow-release-flake

### Open split-button: last-used primary via localStorage, menu when no preference
**Decision**: the Open control's primary segment re-runs the last-used target (persisted kind-qualified to `localStorage["runkit-open-last-used"]`, the `runkit-*` preference convention); with no stored (or no-longer-available) preference the primary click opens the menu instead, and the chevron always opens the menu.
**Why**: mirrors Conductor's split-button UX and the existing `runkit-terminal-font-size` / `runkit-last-pinned-board` preference pattern — a one-click repeat of the common action with the full list one chevron away; a menu-on-first-use avoids firing an arbitrary default. Kind-qualifying the id (`deeplink:vscode` / `host:vscode`) stops a deeplink and host entry for the same editor from colliding on the shared key.
**Rejected**: a fixed default editor (arbitrary, wrong for most); primary always opens the menu (loses the one-click repeat); an un-qualified last-used id (deeplink/host collision for the same editor).
*Introduced by*: 260722-6d0f-navbar-open-in-app

### Open control owns its data via an invalidatable external store; TopBar props untouched
**Decision**: a `useOpenTargets` hook backed by a module-level external store (health + open-apps fetched once, then static between settings commits) feeds both the TopBar registry entry and the palette builder; no new TopBar props or slot-context fields are added. Freshness comes from an exported `invalidateOpenContext()` invoked at the ONE seam the data changes — the Settings dialog's successful SSH-host commit (§ Settings-commit invalidation seam) — NOT from client polling or per-render refetch.
**Why**: keeps the TopBar prop/slot surface stable (the e2e suite asserts chrome details) and avoids client polling (a code-quality anti-pattern). The open context genuinely only changes at the SSH-host commit, so invalidating exactly there is precise and cheap; everywhere else the once-per-load fetch is correct.
**Rejected**: threading `openTargets` through the slot context (prop churn across app.tsx/TopBar/tests); a per-menu-open or per-render refetch (needless requests, popup latency, and it re-fetches even when nothing changed); client polling for freshness (a code-quality anti-pattern — the SSE stream / event seam is the sanctioned path).
*Introduced by*: 260722-6d0f-navbar-open-in-app; invalidatable store 260723-l317-open-button-ssh-refresh-icon

### Settings-commit invalidation seam refreshes the open context, over polling or per-render refetch
**Decision**: the open context is refreshed by an exported `invalidateOpenContext()` called from the Settings dialog's SSH-host `commit` handler after `await setSSHHost(...)` **succeeds** (success only — a rejected commit leaves the server value unchanged, so it must not invalidate). The store is React's `useSyncExternalStore` over a module-level listener `Set` + `getSnapshot`. Invalidation drops the cache and, when subscribers are mounted, eagerly refetches and notifies (mounted consumers re-render fresh, no reload); with zero subscribers it plain-drops the cache for the next mount.
**Why**: the SSH host is runtime-mutable via the Settings dialog (`POST /api/settings/ssh-host`) and the backend serves the fresh value per `GET /api/health` request, but the frontend cached it once per load — so a saved host only reached editor deeplinks after a full page reload, embedding the stale derived `${sshUser}@${location.hostname}` fallback until then. Invalidating at the single commit seam is the precise fix. `useSyncExternalStore` is React 19's canonical external-store primitive — tear-free snapshots, automatic unsubscription on unmount, no `alive`-flag bookkeeping.
**Rejected**: refetching health on every Open-button render (wasteful — the once-per-load cache is correct everywhere except this one seam); client polling (a code-quality anti-pattern — use the event seam); a hand-rolled subscriber array driving per-consumer `useState` (more code for the same behavior, re-implements what the hook provides); invalidating on a failed `setSSHHost` (the commit failed; the server value is unchanged).
*Introduced by*: 260723-l317-open-button-ssh-refresh-icon

### Epoch guard discards in-flight open-context fetches that predate an invalidation
**Decision**: a module-level `epoch` counter is bumped on every `invalidateOpenContext()` (and `resetOpenTargetsCacheForTest()`); a fetch records the epoch at start and writes `cached` / notifies subscribers / clears `pending` **only** when the epoch still matches at resolve time.
**Why**: two rapid SSH-host commits would otherwise let the first (now-stale) refetch resolve after the second invalidation and resurrect exactly the pre-commit data this change exists to kill.
**Rejected**: ignoring the race (small window, but silently serves the stale value the invalidation dropped); aborting via `AbortController` (heavier — the fetch helpers take no signal).
*Introduced by*: 260723-l317-open-button-ssh-refresh-icon

### Remote client shows deeplinks; the derived `user@hostname` replaces the `RK_SSH_HOST` gate
**Decision**: the deeplink section shows for any remote client (no `RK_SSH_HOST` gate). The effective SSH host resolves as `RK_SSH_HOST` verbatim (alias — no `user@` prefix), else a derived `${sshUser}@${location.hostname}` on remote clients (prefix omitted when `sshUser` is empty), else empty for local.
**Why**: on a tailnet `location.hostname` (the name the browser reached the host by) is itself SSH-reachable, and the one missing ingredient — the SSH username — is derivable server-side (`os/user.Current()`, per constitution X, no new config). Gating on `RK_SSH_HOST` left the entire remote story permanently invisible for zero-config Tailscale users. The accepted trade is "shown ⇒ works on tailnets, errors on tunnels": behind an HTTP-only tunnel the derived host is not SSH-reachable and the editor shows its own connect error rather than the section staying hidden. `RK_SSH_HOST` remains the override for aliases, non-standard users, ports, and keys.
**Rejected**: keeping the `RK_SSH_HOST` gate (permanently-dark feature for the common case); probing reachability of the derived host before showing (guessing; the connect-error trade is accepted); an explicit-disable sentinel (`RK_SSH_HOST=none`) in v1 (deferred — most env loaders can't distinguish empty from unset, and the gate change makes disable rarely needed).
*Introduced by*: 260722-fc3b-ssh-host-fallback-open-logos

### Open-row icons are monochrome `currentColor` inline SVGs, resolved id-then-kind
**Decision**: Open menu rows lead with monochrome `currentColor` inline SVG glyphs (~14px, `aria-hidden`, `data-icon` test seam), resolved by an id map (`vscode`+`code` → VS Code glyph, `cursor`, `windsurf`) then a kind-based generic fallback (editor/terminal/file-manager), then a neutral glyph. Palette rows stay text-only.
**Why**: full-color brand marks would clash with the terminal aesthetic, and `currentColor` lets the existing accent-green hover treatments apply to the glyph for free with no new dependency and no image fetches. The kind fallback keeps unknown/future registry entries rendering; both `vscode` (deeplink id) and `code` (wt's VS Code host id) must map to the same glyph because wt's registry id for VS Code is `code`, not `vscode`.
**Rejected**: full-color brand assets (aesthetic clash, licensing/asset pipeline); asserting raw SVG path data (brittle) or per-glyph `aria-label` (icons are decorative — `aria-hidden` keeps row accessible names clean); adding icons to the command palette (no icon affordance today, separate change).
*Introduced by*: 260722-fc3b-ssh-host-fallback-open-logos

### Mirrored menu rows lead with the in-bar glyph; toggle state stays on the trailing ✓
**Decision**: Every chevron-menu / SplitControl-popover row that mirrors an in-bar icon control leads with that control's glyph as its first child, and the glyph is extracted into a shared component so bar and menu render ONE definition each (`top-bar-icons.tsx`). On the two stateful toggle rows the leading icon is a **static identity variant** that never flips with state; the trailing ✓ remains the sole state marker. The command palette stays text-only.
**Why**: the registry already guaranteed bar↔menu *behavior* can never drift (one ordered source drives both renderings), but the menu mixed icon-bearing Open rows with text-only rows — so users matched rows by reading, never learned the icon↔action mapping, and each new `menuOnly` demotion widened the gap. Sharing one component makes visual parity structural rather than copy-paste, and dedupes the direction-glyph SVGs that `SplitControl` alone inlined twice. Leading-icon-as-identity plus trailing-✓-as-state is the macOS menu convention; a leading icon that flipped with state would make the row carry two competing state signals and defeat the identity read.
**Rejected**: icons on action rows only, toggles left text-only (the mixed look the change exists to remove — rejected in favor of the mock-approved "toggles too" variant); a state-flipping leading icon on toggle rows (duplicates the ✓ and breaks the identity read); iconifying the View-switcher rows (nothing to mirror); inventing new glyphs for menu rows instead of mirroring (the bar↔menu mapping is the entire point).
*Introduced by*: 260801-3q1z-top-bar-menu-leading-icons

### A dedicated `top-bar-icons.tsx`, and per-glyph exact SVG attributes over one uniform wrapper
**Decision**: Host the shared control glyphs in a new sibling module `top-bar-icons.tsx` (not in `open-app-icons.tsx`, not in `top-bar-overflow-menu.tsx`), and give it a local `ControlGlyph` wrapper parameterized by `viewBox`/`strokeWidth`/`join` so each glyph byte-preserves its in-bar original's SVG attributes. Stateful toggles take a variant prop defaulting to the static identity form. The terminal-font glyph is an `aria-hidden` text span, not an SVG.
**Why**: `open-app-icons.tsx` is Open-target-specific (its API takes an `OpenTarget`) and `top-bar-overflow-menu.tsx` hosts row classes and sizing tokens, not glyph definitions — a dedicated module mirrors the `open-app-icons.tsx` shape and imports into `top-bar.tsx` with no cycle. The originals genuinely differ (24-viewBox/strokeWidth-2 for split/close/refresh; 14-viewBox/strokeWidth-1.5 round-caps-only for fixed-width; 14-viewBox/strokeWidth-1.5 caps+joins for autofit), so normalizing them onto one wrapper would visibly change stroke weight in the bar — the refactor's whole premise is zero visual change there. A defaulted variant prop is the minimal seam that lets one definition serve both the state-driven bar form and the static menu form. "Aa" is a text glyph in the bar, so a span is the direct match and keeps `currentColor` behavior.
**Rejected**: extending `open-app-icons.tsx` (couples control glyphs to the OpenTarget resolution API); inlining into `top-bar-overflow-menu.tsx` (mixes glyph definitions into the menu-shell component); reusing that module's fixed 24-viewBox/1.8-stroke `Glyph` (changes every glyph's weight); two separate components per stateful toggle (duplicates the definition the change exists to unify); rendering "Aa" as an SVG (needlessly diverges from the in-bar trigger's text styling).
*Introduced by*: 260801-3q1z-top-bar-menu-leading-icons

### `Open: PR #{n}` is a client-side palette action, not an Open target
**Decision**: The PR palette entry is a standalone `openActions` member built by `buildOpenPrAction` — `window.open` in the viewer's own browser, gated on `currentWindow.prUrl`, terminal route only. It is NOT an `OpenTarget`, so it never reaches `buildOpenTargets`, the top-bar Open split-button, or `OpenMenuRows`, and it registers no keyboard chord.
**Why**: `prUrl` is a public GitHub URL already on the client (derived server-side per constitution X), so a client-side open behaves identically for local and remote viewers with no backend surface at all. Keeping it out of `OpenTarget` preserves the documented palette↔menu mirror, which is a mirror of Open *targets* (folder-in-an-app), a different thing from "open this window's PR". The palette entry alone satisfies §V — the sidebar `PrLinkRow` anchor is pointer-only and stays as the mouse path.
**Rejected**: a host-side open via `POST /api/open`/exec (opens a browser on the host where nobody may be looking, fails headless, adds an exec surface for zero benefit); an `OpenTarget` entry plus a top-bar menu row (breaks the target mirror and puts a per-window action in server-wide chrome); a dedicated keyboard chord (the `Open:` family registers none — palette reachability is the §V path); board/tmux-Server-page variants (no unambiguous current window there).
*Introduced by*: 260727-w2d8-palette-open-pr

### Shared chrome definitions live in `global-chrome.tsx`
**Decision**: `HELP_URL`, `NOTIFICATIONS_HELP_URL`, `HelpIcon`, and `ThemeModeIcon` live in `components/global-chrome.tsx`; `top-bar.tsx` exports none of them, and the overflow-menu App-section rows, the settings dialog, `app.tsx`, and `board-page.tsx` all import from that one module.
**Why**: single definitions are the no-drift requirement, and `top-bar.tsx` uses none of these symbols itself — re-exporting from it would be an orphan seam pointing at a file with no stake in them.
**Rejected**: re-exporting from `top-bar.tsx` (dead indirection); duplicating the SVGs in the menu rows (guaranteed drift, which is the whole thing the move prevents).
*Introduced by*: 260724-6j1v-sidebar-footer-chrome-settings

### Shell safe-area gate ships without pinning the native paint mechanism
**Decision**: The top bar's `pt-[env(safe-area-inset-top)]` is gated off with `isShell()` inside the desktop shell without first pinning the exact Electron-native mechanism behind the v3.12.12 band-over-toolbar symptom (regression boundary: PR #487, the accent titlebar strip).
**Why**: Whichever agent paints the band, the SPA reserving the titlebar band twice — `ShellTitlebarStrip` plus safe-area padding — is a defect on its own, so removing the second reservation is correct and sufficient regardless of the rendering internals. Coverage is the unit test driving `isShell()` through its real seam (`window.runkitShell` injection/deletion) plus a manual in-shell check post-release — Playwright cannot cover the shell (`isShell()` is false in e2e); if the band survives a release build, the native-paint investigation reopens as a separate change.
**Rejected**: blocking the fix on a DevTools probe from the affected shell window (the double reservation is a defect independent of the probe's result); `vi.mock("@/lib/shell")` in the test (the bridge-injection pattern exercises the real narrowing seam).

### Shared top-bar button token is hosted beside `MENU_ROW_*`
**Decision**: The `TOP_BAR_BUTTON*` / `TOP_BAR_BUTTON_H` / `TOP_BAR_SEGMENT_H` constants live in `top-bar-overflow-menu.tsx` next to `MENU_ROW_*`, and the square token is a FIXED size (`w-[28px] h-[28px] coarse:w-[30px] coarse:h-[30px]`), not a `min-*` floor.
**Why**: Every consumer — `top-bar.tsx`, `open-button.tsx`, the menu itself — already imports that file, so the same no-cycle host precedent `MENU_ROW_*` established applies with no new module. The fixed size addresses the root cause of visible size inconsistency in the cluster: a `min-*` floor lets each box stretch to its own content, so a bare-glyph control renders smaller than a padded sibling and the class string drifts further with every copy-paste. Fixing the size once, in a shared constant, makes that class of defect unrepresentable.
**Rejected**: A new `top-bar-button.ts` module (an extra file for a handful of string constants when an established host exists); keeping `min-*` floors and normalizing per callsite (treats the symptom — the drift returns with the next copy-paste).
*Introduced by*: 260731-oiho-navbar-consolidation-menu-density

### The split ▾ lists both directions; the primary stays a fixed direction
**Decision**: The merged `SplitControl`'s ▾ dropdown lists BOTH `Split horizontal` and `Split vertical`; the primary segment always performs one fixed direction, never last-used.
**Why**: Split-button convention (and the in-bar `OpenButton` precedent) puts the complete option set in the dropdown, so a one-row menu would hide half the control's capability behind the assumption that the user knows the primary's direction. A fixed primary keeps the primary click deterministic — the same guarantee the two per-direction buttons gave.
**Rejected**: A single-row dropdown carrying only the non-default direction (hides the complete option set); a last-used-tracking primary (makes the most-used affordance in the cluster non-deterministic).
*Introduced by*: 260731-oiho-navbar-consolidation-menu-density

### Horizontal is the default split direction, and one direction vocabulary spans every surface
**Decision**: The primary segment's fixed direction is HORIZONTAL (side-by-side, tmux `-h`), and horizontal leads wherever both directions appear — the ▾ menu, the overflow `SplitMenuRow` pair, and the command palette. Every surface names directions after tmux's own flags: horizontal = `horizontal: true` = `split-window -h` = beside; vertical = `horizontal: false` = `split-window -v` = stacked. The terminal route's split entries (`app.tsx`), the board's split entries (`board-page.tsx`), and the `/api/keybindings` whitelist labels are aligned to that vocabulary; the backend `horizontal` boolean contract is untouched.
**Why**: Side-by-side is the dominant working layout, and a split-button's default and its first menu row must agree — so the ordering rides with the default rather than moving on its own. The vocabulary is settled in the same decision because two naming schemes for one action let the same word mean opposite things: a chip labeled "Split horizontal" running `-h` beside a palette entry labeled `Split Horizontal` running `-v` means a user who learns the word from one surface gets the opposite split from the other. The chip's mapping is the internally consistent one — its glyph, its label, and tmux's flag name all agree — which makes it the convention to standardize on rather than the one to relabel.
**Rejected**: Reordering the menus while leaving the primary vertical (the default and the first row would disagree, breaking the split-button convention the control rests on); relabeling the chip to match the palettes (puts the label at odds with both its glyph and `split-window -h`); leaving the palette booleans inverted and documenting the divergence (a same-name-opposite-action bug is not documentable away); persisting a last-used direction (the primary is deliberately deterministic — § above).
*Introduced by*: 260806-2x2h-split-default-horizontal-first

### Menu sections are named on the registry entry, not derived in the menu
**Decision**: Each `RegistryEntry` carries `menuGroup: "view" | "window" | "app"` (surfaced as `group` on `OverflowMenuRow`); `TopBarOverflowMenu` partitions rows by group and renders non-empty sections in the fixed View → Window → App order.
**Why**: The partition preserves registry (pyramid) order *within* each section for free with zero re-sorting, and a new control declares its section at the one place it is already declaring `modes`/`hidden`/`menuOnly`.
**Rejected**: Grouping inside the menu component by hardcoded id lists (silently drifts the moment the registry gains or renames an entry); sorting rows into groups by tier (tier encodes drop priority, not conceptual grouping — the two answer different questions).
*Introduced by*: 260731-oiho-navbar-consolidation-menu-density

### Demoted in-bar components stay intact rather than being deleted
**Decision**: `ClosePaneButton`, `FixedWidthToggle`, and `TerminalFontControl` remain in the codebase — reachable only through their registry entries' `barRender`, which `menuOnly` never calls — instead of being removed with their demotions.
**Why**: The revert contract is what makes a demotion cheap to try: reverting is deleting one flag, and that only holds while the bar form still compiles and renders. The components are tracked as deletion candidates for a later change that confirms the demotions stick, so the cleanup is a deliberate follow-up rather than an omission.
**Rejected**: Deleting each component with its demotion (turns a one-flag revert into a re-implementation, and would lose the `TerminalFontControl` popover's `Reset terminal font` stepper — the menu row has `−`/`+` only — before its replacement is agreed).
*Introduced by*: 260731-oiho-navbar-consolidation-menu-density

### Content-sized split direction menu (`w-max` + `min-w-[170px]` floor)
**Decision**: The SplitControl direction popover sizes to its content (`w-max`) with the `min-w-[170px]` floor kept only as a guard for the unbound (no-keycap) case.
**Why**: The menu is absolutely positioned inside the tiny chip container, so without help it shrink-wraps and wraps rows; with trailing keycaps the rows' content width varies per platform (short ⇧⌘D on mac, long Shift+Ctrl+\ elsewhere), and content-sizing fits every tier without a per-platform fixed bump.

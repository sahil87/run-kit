# run-kit UI — Keyboard & Palette

## Keyboard Shortcuts

Every app chord is **data in one declarative registry** — `app/frontend/src/lib/keybindings.ts` (pure, DOM-light, colocated `keybindings.test.ts`, the `window-view.ts`/`palette-*.ts` convention). The module owns the tier definitions, `DEFAULT_BINDINGS` with its per-platform default refinements, the tier-stamped claimed-key map, the per-device override layer, chord matching (incl. scope precedence and the terminal-seam refusal predicate), conflict detection, capture, per-platform formatting, the shared suppression predicate, and the palette-hint decorator. React integration is two hooks: `hooks/use-keybindings.ts` (the reactive effective map) and `hooks/use-keybinding-dispatch.ts` (ONE window-level `keydown` listener per route shell). (`260730-g40a`)

### Tiers and the `e.code` rule

Three tiers, each a modifier predicate in `matchesCombo` — **Alt is excluded from every tier** (macOS composes characters with it):

| Tier | Chord | Used by |
|------|-------|---------|
| `shifted` | `Shift + (Meta or Ctrl)` — ⇧⌘ on macOS, ⇧Ctrl on Windows/Linux | the Windows/Linux action tier in full, and the mac actions that cannot demote (H/L/A) |
| `cmd` | `(Meta or Ctrl)` without Shift | the legacy punctuation chords ⌘K ⌘., the board ⌘[/⌘] pair, and the macOS-demoted action defaults (§ Per-platform default tiers) |
| `ctrl` | plain `Ctrl` without Meta/Shift | `focus-hop` is the first shipped default — mac-only ⌃` via `macTier` (plain Ctrl belongs to the pane on Win/Linux, so its base tier is shifted); a mac chord capture reading plain Ctrl otherwise lands in this tier, kept distinct from ⌘ (macOS window/system territory the page must not claim) |

Matching is on **`KeyboardEvent.code`, never `e.key`** — layout-independent (`"KeyN"`, `"BracketLeft"`), and it sidesteps the shifted-accelerator character-resolution flakiness the shell docs flag ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam). **The letters are constant across platforms; only the modifier varies.** The shifted tier is what makes N/T/W/H/L coexist on Windows/Linux at all: **plain Ctrl must always reach the pane** there (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+N/P history), and legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so claiming the shifted tier costs terminal apps nothing (the same tier every cross-platform terminal — Windows Terminal, GNOME Terminal, Konsole, kitty — uses for app actions). That pane-ownership constraint is **Windows/Linux-only**, and browser key reservation is **host-specific** — so macOS defaults demote to the unshifted ⌘ tier wherever nothing immovable blocks them (§ Per-platform default tiers).

Seventeen starter actions on the letter/punctuation tier — `actionId` doubles as the palette action id wherever one exists. The letter is invariant — with one deliberate exception, the split pair's mac `macCode` refinement (§ Per-platform default tiers) — and the modifier is per platform and per host. All are `scope: "global"` except `open-last-used`, the two split actions, `code-toggle`, and `focus-hop`, which are `terminal`:

**B and J demote on macOS in both hosts** (`260816-sm66`) — the VS Code primary-sidebar and panel keycaps. Both are `preventDefault`-interceptable in a mac browser (the same accelerator class as the shipped ⌘D/⌘[/⌘]/⌘/ interceptions, not reserved like N/T/W), so neither carries `macShellOnly` nor a claimed-keys entry, and both carry a rendered `mapLabel` (`sidebar` / `code`) — `KeyB` and `KeyJ` have keycap cells in the overlay's tier-map grids. On Win/Linux the pair sits on the shifted tier: plain Ctrl+B stays with the pane (readline back-char / nested-tmux prefix), and ⇧Ctrl+J shadows Chrome's DevTools-console accelerator there — interceptable, not reserved (DevTools stays on F12/⇧Ctrl+I). **mac-Chrome ⌘J Downloads suppression is a pre-ship manual verification gate** (not automatable on the Linux e2e rig): if `preventDefault` fails to suppress the Downloads panel, the recorded fallback is `macShellOnly: true` on `code-toggle` plus a `browser`-owner claimed-keys row on cmd-tier `KeyJ` (the mac browser then reverts to ⇧⌘J).

**`focus-hop` is the first shipped `ctrl`-tier default** (`260816-sm66`) — ⌃` on macOS in both hosts (`macTier: "ctrl"`), ⇧Ctrl+` on Win/Linux (plain Ctrl belongs to the pane there, so the base tier is shifted and `macTier` does the demotion). It hops focus between the tty and code tiles ([focus-ownership](/run-kit/ui/focus-ownership.md) § Recording Seams), and the terminal seam's third refusal rule is what lets ⌃` fire under terminal focus on mac (§ Dispatch seams). `Backquote` has no keycap cell in the overlay's tier-map grids (the `Period`/`Comma` no-cell precedent), so the row ships no `mapLabel`; `formatCombo` renders the ctrl tier with the `` Ctrl+` `` spelling.

**⇧⌘P is deliberately unbound on every tier** — `KeyP` is reserved for a future create/open-PR action (the Conductor convention), recorded as a `DEFAULT_BINDINGS`-adjacent comment so a later change does not spend the keycap. `compose-toggle` (⇧⌘E) is likewise a do-not-move constraint.

**`settings-open` is the one comma chord** (`260801-mqim`): a chrome-level *opener*, not a toggle — a re-fire while the dialog is open is a React state bailout, matching the macOS ⌘, convention where Preferences never closes itself. It is the third `macShellOnly` demotion alongside N/T/W, but for a different reason: ⌘, is the **browser's own Preferences accelerator** on macOS (claimed data, § Claimed keys), so the browser default stays shifted while the shell — which binds no ⌘, accelerator — promotes it to the OS-conventional ⌘,. `ignoreInputs: true` mirrors `shortcuts-overlay`/`compose-toggle`, the other chrome-level chords. `mapLabel: "settings"` is carried for parity but unrendered: `Comma` has no keycap cell in the overlay's tier-map grids, the `Period`/`Backquote` precedent.

**E and O stay shifted on every platform** — no `macTier` demotion. ⌘E is macOS browser "use selection for find" territory, and the letter choice for the compose toggle is what the surrounding tier left free: C is the win/linux terminal copy/paste claim, T is `create-window`, I is win/linux DevTools. `compose-toggle` carries `ignoreInputs: true` so the chord also fires from *inside* the strip's own textarea (the one place the strip is most likely to be closed from) — the same field ⌘K and the overlay toggle use. `open-last-used` names the **behavior**, not an app, which is why it can carry a static chord at all while the per-target `Open:` palette entries cannot (§ Open-in-App palette actions). (`260801-sm6g`)

**The split pair is the one per-platform-CODE default** (`260807-rbx5`): `split-horizontal`/`split-vertical` bind the existing `Window: Split Horizontal` / `Window: Split Vertical` palette bodies, direction semantics inherited from the top-bar chip (horizontal = side-by-side = tmux `-h`; § Horizontal is the default split direction). Both are `scope: "terminal"` — the `view-cycle`/`open-last-used` precedent, since the palette bodies exist only on window routes, so `fromPalette` yields no handler elsewhere and the chord falls through untouched. The base (Win/Linux) codes are keycap-as-divider mnemonics: ⇧Ctrl+\ side-by-side (shift+\ types `|`, the divider the split creates — the VS Code split-editor keycap) and ⇧Ctrl+- stacked. macOS refines both to the D keycap (`macCode: "KeyD"`) for the iTerm2/Warp/Ghostty pair: `macTier: "cmd"` also demotes horizontal to ⌘D in **both** mac hosts (⌘D is the mac-browser bookmark accelerator, page-interceptable like ⌘[/⌘]/⌘/ — no `macShellOnly`, and no `browser`-owner claim entry), while vertical keeps the shifted tier as ⇧⌘D — tier-disjoint on the one code, so the mac pair is conflict-free. The mac pair cannot ship with constant codes: plain Ctrl+D is EOF and belongs to the pane on Win/Linux, and two rows cannot share ⇧Ctrl+D because equal-scope same-combo defaults would break the conflict-free invariant (§ Per-platform default tiers). Horizontal takes the plain ⌘D because it is the primary/default split. `mapLabel`s `split h` / `split v` annotate whichever keycap each is bound to on its map layer.

Both split rows also carry **`ttyOnly: true`** (`260812-wfic`) — an optional `KeyBinding` data flag meaning "this chord targets the tmux pane; only meaningful when the tty tile owns focus", set on exactly these two rows and consulted by gate sites rather than hardcoded actionId lists: `app.tsx`'s handler map drops a `ttyOnly` handler when the focused tile kind is not `tty` (§ Dispatch seams), and the code-surface reclaim predicate refuses to reclaim a keydown whose only matches are `ttyOnly` (§ Code Surface → Chord reclaim).

Five further bindings cover the remaining punctuation chords — same registry, so they are per-device rebindable like everything else: `command-palette` ⌘K (`cmd`, global, `ignoreInputs`), `view-cycle` ⌘. (`cmd`, terminal), `layout-cycle` ⌘; (`cmd`, terminal — the next same-arity layout preset, order kept; § Surface Layout), and the board pane-cycle pair `board-cycle-prev`/`board-cycle-next` ⌘[/⌘] (`cmd`, board). `scope` (`global | terminal | board | sidebar`) is descriptive — it drives overlay grouping and conflict scoping; actual applicability is handler presence at each dispatcher mount. `sidebar` is schema-reserved with no binding. `kind` is `"builtin" | "macro"` — the builtins are the shipped registry actions above; `macro` bindings are user-defined and enter resolution from the macro store (see § Macro bindings). (`260730-hbyh`)

`Cmd+C`/`Ctrl+C` in a focused terminal is **not** a registry binding — it is a special case at the head of `attachCustomKeyEventHandler` (copy selection when one exists, else fall through to xterm's SIGINT), using `navigator.clipboard.writeText()` with a `document.execCommand('copy')` fallback for non-secure contexts and clearing the selection via `.finally()`.

No single-key shortcuts (`j`/`k`/`c`/`r`) or `Esc Esc` — these conflicted with xterm.js terminal input. Every action is also reachable via `Cmd+K` or top-bar buttons.

### Per-platform default tiers (`macTier` / `macCode` / `macShellOnly` / `defaultComboFor`)

The per-key table above is **data on the binding**, not a resolver branch. `KeyBinding` carries the base (Windows/Linux) `tier` plus three optional refinements — all of which touch the SHIPPED DEFAULT only, never the stored override:

- **`macTier?: BindingTier`** — the tier this binding's default combo uses on mac hosts. Shipped on `go-back`/`go-forward`/`shortcuts-overlay`/`split-horizontal`/`sidebar-toggle`/`code-toggle` (all demoting to the `cmd` tier) and `focus-hop` (the one `ctrl`-tier demotion — ⌃`).
- **`macCode?: string`** — the KEY CODE the default combo uses on mac hosts, replacing `code`. The one deliberate exception to 260730-n789's letters-constant rule, for chords whose mac convention has no legal cross-platform letter. Shipped on both split rows (`macCode: "KeyD"`): mac gets the iTerm2/Warp/Ghostty ⌘D/⇧⌘D pair while Win/Linux keeps the divider-mnemonic `\`/`−` base codes. Composes with `macTier` under one host gate. (`260807-rbx5`)
- **`macShellOnly?: boolean`** — restricts the mac refinements (`macTier`/`macCode`) to `isShell()` hosts. Shipped alongside `macTier: "cmd"` on `create-session`/`create-window`/`kill-window`/`settings-open`.

Every other binding (including the legacy chords and macro projections) carries none of the three and resolves identically everywhere.

`defaultComboFor(def, host)` is the **single seam** where platform and shell are consulted for defaults — it returns `{ code: macCode ?? code, tier: macTier ?? tier }` when `host.platform === "mac"` and either mac refinement is set and (`!macShellOnly || host.shell`), else `{ code, tier }`. Both `resolveBindings` (the no-override fallback *and* the `isDefault` comparison) and `applyCapture` (own-default detection, which therefore takes a required `host`) read defaults through it, so an effective map is always host-coherent: on a mac shell host ⌘[ *is* `go-back`'s default and shows no modified dot (and ⇧⌘D *is* `split-vertical`'s default, so re-capturing it is a diff-dropping no-op), while the same combos on Win/Linux are user overrides.

The **stored override shape is untouched** — `{ [actionId]: { code, tier } | null }`, byte-identical. Overrides are per-device by construction (localStorage), so per-platform storage is inherent and no migration exists. Win/Linux resolution is byte-identical to the pre-demotion map.

Which keys demote is constrained by what the environment refuses to give up:

- **⌘[ / ⌘] / ⌘/ demote on macOS in both hosts** — all three are interceptable in a mac browser (the board pane-cycle already ran on the cmd tier), and ⌘[/⌘] match native browser back/forward convention.
- **⌘B / ⌘J demote on macOS in both hosts** — the VS Code primary-sidebar and panel keycaps, page-interceptable in a mac browser like the set above (no `macShellOnly`, no `browser` claim rows on `KeyB`/`KeyJ`). The ⌘J interception of mac Chrome's Downloads accelerator is **verified-pending** — a pre-ship manual gate, with `macShellOnly: true` plus a `browser`-owner claimed-keys row on cmd-tier `KeyJ` as the recorded fallback (§ The default binding set).
- **⌃` demotes to the `ctrl` tier on macOS in both hosts** — `focus-hop`'s `macTier: "ctrl"`, the registry's first shipped ctrl-tier default; no mac claim exists on `Backquote` in any tier. Win/Linux keeps ⇧Ctrl+`: plain Ctrl is the pane's there, so the base tier is shifted.
- **The split pair refines to the D keycap on macOS in both hosts (`macCode`)** — `split-horizontal` also demotes to ⌘D (mac-browser ⌘D is the bookmark accelerator, `preventDefault`-interceptable like the ⌘[/⌘]/⌘/ set rather than reserved like N/T/W, so no `macShellOnly` and no `browser` claim row) while `split-vertical` keeps the shifted tier as ⇧⌘D — tier-disjoint on the one code, so the mac pair is conflict-free. Win/Linux never sees the D codes: the pair lives there on its divider-mnemonic base codes ⇧Ctrl+\ and ⇧Ctrl+- (§ The default binding set), because plain Ctrl+D is the pane's EOF and two rows cannot share ⇧Ctrl+D (equal scope → `findConflicts`).
- **⌘N / ⌘T / ⌘W demote in the macOS shell only** — a browser reserves them unshifted *and* shifted (incognito / reopen-tab / close-window), so a mac browser keeps the shifted default and resolves it `reserved` (palette-only). The shell deliberately leaves the whole unshifted tier unbound, which is exactly what these spend ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam; ⌘W is unbound-by-design there for this).
- **⌘, demotes in the macOS shell only, for a narrower reason** — the browser claims only the **unshifted** ⌘, (Preferences), not the shifted tier, so `settings-open`'s ⇧⌘, browser default is live rather than `reserved` (unlike N/T/W, which are palette-only in a mac browser). The demotion is therefore about reaching the OS-conventional ⌘, where the accelerator is free, not about escaping a shifted-tier reservation.
- **H / L / A / E / O stay shifted on every platform** — ⌘H is macOS Hide (OS/app-menu level, dead in both hosts; the shell's App menu binds `role: hide`) and ⌘A is browser select-all plus the shell's Edit-menu `selectAll` role. H and L stay shifted **as a pair**: demoting L alone would split the H/L navigation pair across two tiers. ⌘E is mac-browser "use selection for find" territory.

### Claimed keys

Claimed keys are registry data (`claimedKeys(platform, shell)`), each carrying a **`tier`** (a claim occupies one chord tier — the mac ⌘ page tier has its own claimed set alongside the shifted tier) and an `owner` that drives presentation and effect:

- **`shell`** — menu accelerators. Shifted tier: ⇧CmdOrCtrl+R (force reload, everywhere), plus ⇧Ctrl+1–9 (server switcher) and ⇧Ctrl+I (DevTools) on **win/linux only** — `SHELL_SWITCHER_DIGITS` carries `platform: "other"`. The mac switcher sits on ⌥⌘1–9, which no tier can express (Alt is excluded from every tier), so on mac the shell owns no shifted digits at all; that unrepresentability is the point of the mac accelerator choice, not a gap in the mirror ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam). Mac `cmd` tier, present only inside the shell (`MAC_SHELL_CMD_CLAIMS`, mirroring the exhaustive mac bound set in `app/desktop/src/menu.ts`): ⌘Q quit, ⌘H hide, ⌘M minimize, ⌘R reload, the Edit roles ⌘Z/X/C/V/A, and zoom ⌘0/⌘+/⌘− (`Digit0`/`Equal`/`Minus`). Display + capture-warning data; the menu accelerator consumes the key before the page sees it anyway.
- **`system`** — shifted ⇧⌘Q (macOS logout), the mac ⇧⌘3/4/5 screenshot trio (`MAC_SCREENSHOT_CLAIMS`), and ⇧Ctrl+C/V (the win/linux terminal copy/paste convention), plus mac-browser `cmd`-tier ⌘Q/⌘H/⌘M (OS-level). Display-only. The mac rows carry `platform: "mac"` with no `shell` restriction — like logout, screenshots are system-wide, so they claim in both hosts. Mac ⇧⌘1/2/6–9 carry **no** claim: unclaimed page real estate.
- **`browser`** — the one owner that changes resolution. Shifted N/T/W (incognito / reopen-tab / close-window) outside the shell on every platform; on a mac browser also the `cmd` tier's ⌘N/⌘T/⌘W (new window / new tab / close tab), ⌘L (address bar), ⌘, (Preferences — the reason `settings-open`'s browser default stays shifted, `260801-mqim`), and tab digits ⌘1–9. Reservation is **tier-aware** — `resolveBindings` keys its reserved set on `` `${tier}:${code}` `` — so a combo resolves `enabled: false` with `disabledReason: "reserved"` only when a browser claim matches *both* its tier and its code. In a plain browser `create-session`/`create-window`/`kill-window` are therefore inert chords that stay palette-reachable, and an override onto ⌘L or ⌘, is dead on a mac browser but live in the mac shell (⌘, being the mac shell's shipped `settings-open` default there). Inside the shell every action is live.

Win/Linux claim sets are unchanged: the unshifted Ctrl tier there belongs to the pane, so it carries no claims data.

### Override layer

`localStorage["runkit-keybindings"]` stores **diffs only** — `{ [actionId]: { code, tier } | null }`, `null` meaning unbound/disabled (the same persistence shape as `runkit-terminal-font-size`; no backend, no config file, Constitution II). `resolveBindings(defaults, overrides, host)` merges them into the effective map — defaults resolved host-aware through `defaultComboFor` (§ Per-platform default tiers) — marking each binding `enabled` / `isDefault` / `disabledReason`. `parseOverrides` is tolerant — malformed JSON, a non-object root, or garbage entries degrade to "no override" — and both storage wrappers are try/catch, so an unavailable localStorage falls back to defaults without throwing.

This is also the **only** combo store: a macro's key lives here as an ordinary diff entry keyed by its actionId, never inside the macro definition. Macros therefore enter resolution as **keyless defaults** — `resolveBindings` resolves an effective combo whose `code` is `""` to `enabled: false, isDefault: false, disabledReason: "user"`, the same state a steal victim lands in, so the overlay's `unbound` affordance covers both. Builtins always carry a code and are unaffected. (`260730-hbyh`)

Rebinding is **steal-with-warning** in a single capture press: `applyCapture(bindings, overrides, actionId, combo, host, defaults?)` gives the combo to the new owner, sets the previous owner's override to `null`, and reports it as `stolenFrom` so the overlay flags it until it is rebound or reset. Re-capturing an action's own **host** default (`defaultComboFor(def, host)` — so ⌘[ counts for `go-back` on a mac) is a **no-op that short-circuits before the victim search**: it deletes the diff entry, keeping the blob diffs-only, and steals from nobody. The ordering is load-bearing — the mac defaults ship global↔board shadow pairs on ⌘[/⌘], so a victim search running first would let a no-op re-capture of either partner unbind the other. The optional `defaults` parameter is what the own-default check reads, so callers holding a **macro-extended** default set (`use-keybindings.ts`, which also passes its `host`) get the same detection as the `DEFAULT_BINDINGS` fallback. Stealing is kind-blind: a builtin capture can unbind a macro and a macro capture can unbind a builtin, one mechanism in both directions. Reactivity is an in-module pub/sub in `use-keybindings.ts` (the `use-local-storage-enum.ts` pattern — the native `storage` event fires only across tabs, which covers cross-tab for free); every write funnels through one `persist()`, and `setBinding` recomputes against freshly-read storage — **both** stores, so a macro-owned combo is steal-detected — meaning rapid successive captures compose.

`useKeybindings` composes `useMacros` and resolves over `DEFAULT_BINDINGS ∪ macros.map(macroToBinding)`. Because macros ride that one effective map, the dispatcher, the terminal seam (`attachCustomKeyEventHandler`), palette hints (`withShortcutHints`), and the overlay key map (`custom` keycap state) pick them up with **zero** consumer changes. A macro-store change also re-reads override storage, since `removeMacro` drops the deleted macro's diff without a keybinding-store notification and the two stores must not drift in-memory. `reset all` writes `{}`, which unbinds every macro combo while leaving the definitions intact — rows return to `unbound`. (`260730-hbyh`)

### Macro bindings

A **macro** is a user-named keyboard route to an action that already exists — never a shell string. `app/frontend/src/lib/macros.ts` (pure, DOM-light, colocated `macros.test.ts`) owns the model; `hooks/use-macros.ts` is its React integration. (`260730-hbyh`)

```ts
type MacroTarget =
  | { type: "riff"; preset: string }              // → POST /api/riff
  | { type: "palette"; paletteActionId: string }; // → the palette action body
type MacroAction = { actionId: string; kind: "macro"; label: string; target: MacroTarget };
```

- **Two target kinds only.** A riff target carries the preset **NAME** alone; the pane commands and arguments live in the preset definition inside `fab/project/config.yaml` — the committed-config trust boundary ([rk-riff](/run-kit/rk-riff.md) § Security / Trust Boundary). Riff targets carry **no `args` passthrough**: `POST /api/riff` has no args field and its `task` REPLACES preset panes (`composePanes`), so per-macro dynamic args would need a backend extension. `isMacroTarget` narrows structurally, so a `{type:"shell",cmd}` blob planted in localStorage is dropped on parse.
- **Definitions in `localStorage["runkit-macros"]`** — a JSON array with the tolerant-parse posture of `parseOverrides` (malformed JSON, a non-array root, and invalid entries degrade to dropped/empty; valid entries are re-projected so unknown keys are stripped and `kind` is pinned) and try/catch storage wrappers. An empty list removes the key. The combo lives in `runkit-keybindings` (§ Override layer).
- **`actionId` is `"macro:<label-slug>"`** — lowercase, non-alphanumeric runs collapse to `-`, `-2`/`-3`… suffixes on collision (the riff `resolveWindowName` convention), empty slug falls back to `macro`. It doubles as the palette action id, so the `withShortcutHints` join is free. `isMacroActionId` is the guard that keeps macros out of target lists and out of palette-target resolution — no macro→macro recursion.
- **`macroToBinding(macro)`** projects a macro into a `KeyBinding`: `kind: "macro"`, `scope: "global"`, `tier: "shifted"`, `code: ""` (keyless — the unbound resolution in § Override layer), `description`/`mapLabel` from `macroCommandPreview(target)`, which renders `rk riff --preset discuss` / `palette: {actionId}`.
- **`useMacros()`** returns `{ macros, addMacro(label, target) → actionId, removeMacro(actionId) }` with the same in-module pub/sub + native `storage` reactivity as `use-keybindings.ts`; `addMacro` uniquifies against freshly-read storage so rapid adds compose. `removeMacro` also drops the actionId's `runkit-keybindings` entry, so a later same-slug macro can never inherit a ghost combo.

**Execution** is `executeMacro` in `app.tsx`, mounted on AppShell only. A `palette` target resolves its action body by id through the stable `getAllActions()` API channel **at call time** (the merged route + layout-globals list — the § Design Decisions "Chord handlers are the palette action bodies" convention; § Single palette mount + palette-actions slot) and invokes it in place; an absent action means no handler, so the chord falls through untouched. A `riff` target is **session-gated** (the `Agent: Spawn` precedent) and calls the existing `spawnRiff(server, session, { preset })` client: success surfaces an info toast and navigates via `navigateToWindow` when `windowId` is truthy (the spawn dialog's falsy-id guard preserved); failure — including a 400 for a preset gone from fabconfig — surfaces the error text as a toast. No new endpoint, no new exec surface, no fire-and-forget. `keybindingHandlers` spreads the macro handlers **first** so a theoretical id collision resolves builtin-first. The board route mounts no macro handlers, so macro chords fall through there.

Macros are also palette-reachable without their key: one `Macro: {label}` entry per macro (id = the macro's actionId) folded into `paletteActions`, riff macros filtered out with no session. `withShortcutHints` decorates them automatically; an unbound macro renders no hint.

`findConflicts` is a pure function over the effective map — two **enabled** bindings conflict when their codes match, their tiers collide (`tiersCollide`: equal, or the overlapping `cmd`/`ctrl` pair), and their scopes are **EQUAL**. A same-combo global↔scoped pair is a **shadow, not a conflict** (§ Scope precedence). It is the **test-only invariant guard** asserting the shipped defaults are conflict-free in every host — including the mac hosts, whose defaults ship exactly one such shadow shape; the capture UI takes its steal warning from `applyCapture`'s `stolenFrom` instead, and that search stays `scopesOverlap`-wide (`global` overlaps everything, equal scopes overlap, `terminal`/`board` are disjoint since those routes never co-mount).

### Dispatch seams

- **`useKeybindingDispatch(handlers)`** — one window-level bubble-phase `keydown` per route shell, keyed by `actionId`. Rules in order: skip `defaultPrevented` events (the overlay's capture-phase rebind listener claims its own); walk the **enabled** matches in `findMatches` order (§ Scope precedence) and fire the **first one that has a handler at this mount**; when **no** match has a handler the chord falls through untouched (no `preventDefault`), so a route without context for an action leaves browser/pane behavior alone; then `shouldSuppressChord` gates real text inputs unless the binding sets `ignoreInputs`. Bindings and handlers live in refs so the listener registers once per mount and SSE ticks never churn it.
- **`shouldSuppressChord(target)`** — the single shared input-gating predicate (`lib/keybindings.ts`): suppress only when a real text input owns focus, with two carve-outs — anything inside `.xterm` (the hidden helper textarea is the terminal's normal focus state) and `.rk-chat-input` (the chat lens's analog). jsdom-safe (`contentEditable` attribute fallback for the missing `isContentEditable` getter). ⌘K and the overlay toggle carry `ignoreInputs` and skip it entirely.
- **AppShell (`app.tsx`)** mounts the dispatcher with handlers derived from the **palette action bodies** — `fromPalette(id)` looks each up by id over the **merged route+globals list** (`[...paletteActions, ...paletteGlobals]`, both this-render fresh — the globals-only channel keeps the memo loop-safe, § Single palette mount + palette-actions slot), so chords bound to layout-global ids resolve the same way as route-scoped ones: `create-session`, `create-window`, `kill-window`, `agent-next-waiting`, `go-back`, `go-forward`, `settings-open` (the `Settings: Open` global entry's body), `code-toggle` (the code surface's tile toggle — desktop window route with the code surface available, via `togglePanel("code")` → `addSurface`/`closeSurface` — § Surface Layout) and `focus-hop` (the tty↔code focus hop, same gate — open-then-focus on a closed code tile; [focus-ownership](/run-kit/ui/focus-ownership.md)) — plus `layout-cycle` (reuses the `Layout: Cycle Shape` palette body — the next same-arity preset, order kept; § Surface Layout), `window-prev`/`window-next` (a modulo cycle over the current session's windows in sidebar order, wrapping, through the rich `navigateToWindow` path; gated by `canCycle`, so the chord no-ops off a window route), the `shortcuts-overlay` toggle (the global entry's layout-owned `onSelect`), `compose-toggle` (chrome-context's `toggleComposeStrip`, the same body the `a▏` chip and `View: Text Input` run), `open-last-used` (registered only when `windowParam` is set — § Open-in-App palette actions), `split-horizontal`/`split-vertical` (the two `Window: Split …` palette bodies, whose block is gated on a current session + window, so off a window route `fromPalette` yields `undefined` and the chord falls through — and which additionally carry the registry's `ttyOnly: true` flag, so `app.tsx` treats their handlers as ABSENT unless the focused tile kind is `tty`: with a non-tty tile focused the split chord falls through untouched, no `preventDefault`, while the palette's `Window: Split …` rows stay invocable regardless of focus — the gate wraps only the chord handler map, § Surface Layout → Focused tile; `260812-wfic`), and one handler per stored macro (§ Macro bindings).
- **BoardPage (`board-page.tsx`)** mounts its own dispatcher with `board-cycle-next`/`board-cycle-prev` (both handlers are absent when the board has no panes, so the chords fall through untouched), `go-back`/`go-forward`, `shortcuts-overlay` (resolved from the layout global list via `usePaletteGlobals` — the overlay state is layout-owned, § Single palette mount + palette-actions slot), `compose-toggle` (the same chrome-context body — the compose strip has a board footer mount too), and `settings-open` (`useSettingsDialog().openSettings` lifted above the handler memo for the dep). `open-last-used` and the `split-horizontal`/`split-vertical` pair are deliberately unhandled here: the Open control and the split palette bodies are terminal-route-only, so those chords fall through. The two route shells never co-mount.
- **Three chords keep their own component-local listeners** rather than joining the dispatcher, because their enablement is local state: ⌘K in `command-palette.tsx` (palette open-state), the `sidebar-toggle` chord (⌘B/⇧Ctrl+B) in `shell.tsx`'s `useSidebarKeyboardToggle`, and ⌘. in `app.tsx`'s view-cycle effect (lens availability). Each reads its binding through `byAction` and matches with `matchesCombo` + `shouldSuppressChord` — definition and suppression are the registry's, enablement is the seam's.
- **Terminal seam** — `terminal-client.tsx`'s `attachCustomKeyEventHandler` keeps the ⌘C copy case first, then delegates the refusal decision to the pure predicate `shouldRefuseTerminalChord(e, bindings, platform)`, reading both the bindings and the host platform through render-updated refs (the handler attaches once at terminal init, but overrides can change any time). Returning `false` means xterm neither handles nor transmits the key, and xterm does not `preventDefault` a refused key, so the event bubbles to the window dispatcher and the action fires while the terminal owns focus. Three refusal rules:
  - **Any enabled shifted-tier match, on every platform** — legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so xterm would emit the Ctrl-char; refusing costs the pane nothing.
  - **On macOS only, an enabled `cmd`-tier match pressed with `metaKey`** — ⌘ chords never reach the pane as control bytes, so refusal is loss-free and the demoted ⌘[/⌘]/⌘/⌘B/⌘J (plus shell-host ⌘N/T/W) fire under terminal focus. The `metaKey` gate is load-bearing: `matchesCombo`'s cmd tier also accepts plain Ctrl, and mac Ctrl+[ is ESC.
  - **On macOS only, an enabled `ctrl`-tier match pressed with `ctrlKey` and WITHOUT `metaKey`** — lets ⌃` (`focus-hop`) bubble to the dispatcher under terminal focus, at the cost of stealing NUL (the byte Ctrl+` encodes to) from the pane: near-zero cost, the same trade VS Code makes for its own ⌃`. The `!metaKey` gate is rule 2's inverse — a ⌘+Ctrl combined press must not double-match.
  **Plain-Ctrl chords matching no enabled ctrl-tier binding are never refused on any platform** (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+[ ESC). On Win/Linux the cmd and ctrl rules never apply at all — cmd-tier combos *are* plain-Ctrl chords there, and no ctrl-tier default resolves there (`focus-hop`'s base tier is shifted) — so the seam is byte-identical to its pre-demotion behavior.

The chords are SPA-renderer bindings, **not Electron menu accelerators** — the shell's documented seam is accelerator *avoidance*, so the letters work identically in shell and browser hosts; only which modifier is bound varies (§ Per-platform default tiers).

### Scope precedence — scoped beats global

`findMatches(e, bindings)` returns **every** enabled matching binding, ordered non-`global` scopes first (registry order within each class). This exists because the mac demotion makes two shipped defaults share a combo by design: the board pane-cycle pair `board-cycle-prev`/`board-cycle-next` (`scope: "board"`) and the global `go-back`/`go-forward` both sit on ⌘[/⌘] on mac hosts.

Resolution is **precedence, not conflict**: the board route keeps pane-cycle on ⌘[/⌘] (back/forward stays palette-reachable there), every other route gets history navigation, and a *paneless* board — where the cycle handlers are absent — falls through to the global back/forward at the same mount, because the dispatcher's walk skips matches with no handler. `findConflicts` therefore flags only **equal**-scope pairs, while `applyCapture`'s steal search deliberately stays `scopesOverlap`-wide (§ Override layer, § Design Decisions).

### Shortcuts overlay (`components/shortcuts-overlay.tsx`)

The cheatsheet is **THE single shortcuts surface** — app chords, user macros, and tmux keybindings in one sheet. It is a focus-trapped **dialog, not a route** (Constitution IV fixes the route set), opened by three affordances that all TOGGLE it: the `shortcuts-overlay` chord (⌘/ on mac hosts, ⇧Ctrl+/ on Win/Linux), the `Help: Keyboard Shortcuts` palette action, and the chevron menu's "Keyboard shortcuts" App-section row (via the `shortcuts-overlay:open` document CustomEvent — § Right cluster → overflow chevron menu). It mounts **once in `AppLayout`** (`LayoutShortcutsOverlay`) with layout-owned open state — the chord and the palette entry both resolve the layout-global `Help: Keyboard Shortcuts` entry's `onSelect` through the merged palette list (§ Single palette mount + palette-actions slot). It uses `useFocusTrap`, the bracket-heading vocabulary, `rk-glint` buttons, accent-green states, and theme tokens; `data-testid="shortcuts-overlay"`. Rows, keycap states, and capture all read the **host-effective** map, so the per-platform tiers surface without per-consumer branching.

**No tabs — one scroll, one filter.** The core query is "what's the key for X?", and the user should not have to know which system owns X before asking. So a single filter input spans app rows + macro rows + tmux rows, and everything lives in one scroll container. Navigation is a **sticky jump-nav chip row** under the header instead (`<nav aria-label="Shortcut sections">`, `data-testid="shortcuts-jump-nav"`): `key map · global · terminal · board · custom · tmux`, each chip a `scrollIntoView` anchor onto a section ref. While a filter is active each chip additionally renders its **live match count** and dims (`opacity-40`) at zero hits, so matches below the fold stay discoverable. The `custom` chip renders only when that section does; the `key map` chip carries no count and dims while filtering (the map hides then). Contents in document order:

- **ONE keycap grid with a modifier picker**, **foldable** via a `▾ collapse map` / `▸ expand map` toggle and **auto-hidden entirely while a filter is active** (a keycap grid cannot answer a text query, and the reclaimed vertical space keeps row hits above the fold on short viewports). The **tables are the authority** for effective chords; the map is a **discovery + rebind tool** — which is why one grid answers "what does my keyboard do while I hold these modifiers" rather than two grids re-answering per-action chords the rows already carry. The grid is three rows of keycaps where a key renders `bound` (accent-green, host default combo), `custom` (accent, overridden), `claimed` (amber, dimmed — claimed wins over bound so a browser-reserved N reads claimed) or `free`, annotated with the binding's `mapLabel`, all via one shared `keyCell(states, code, idx)` over a per-layer state map. The map stays **app-layers-only**: tmux prefix chords are sequences, not combos, and do not fit the model. The digit run collapses into a **decorative `…` ellipsis cell** standing for Digit3–Digit8, which takes its claimed styling from **`Digit3`** — the one digit carrying a claim on *both* displays (switcher-claimed on win/linux, screenshot-claimed on mac). Keying it off the run's first member is what keeps mid-run claims visible on the mac display, where `Digit1`/`Digit2`/`Digit9` have their own unclaimed cells.
  - **The picker IS the map label**: the header's left slot reads **"Holding"** followed by a segmented control (`role="group"`, `aria-label="Keyboard map modifier"`, `aria-pressed` per segment, the platform-toggle visual idiom) whose selected segment supplies the modifier caps — `⇧ ⌘` | `⌘`. Selecting a segment swaps which layer the single grid renders, feeding `tierKeyStates(activeMapTier)`.
  - **The `⌘` option is a macOS-display affordance only** — the Win/Linux unshifted layer is plain Ctrl and belongs to the pane, so that display renders a static **"Holding Shift Ctrl"** label instead (a one-option segmented control is dead chrome). Default selection is `⇧⌘`. The active layer is **derived** (`displayPlatform === "mac" ? mapTier : "shifted"`), so switching the display away from macOS falls back to the shifted layer while the `⌘` selection survives and reapplies on return.
  - **Session-scoped view state**, like the fold: `mapTier` and `mapFolded` are both deliberately excluded from the on-close reset effect — a chosen layer and a folded map are reading preferences, unlike the transient filter/capture state the close effect clears.
  - The map header also carries the **"plain Ctrl always reaches the pane"** note (it explains why there is no Ctrl layer to pick) and the fold toggle, all on one row.
  - **Legend** (four states): `bound` · `custom` · `claimed — taken by the OS / browser / app menu (the desktop app frees the browser ones)` · `free`. The claimed entry is where the browser-vs-desktop story lives in the map — one line, no per-map captions.
- **Platform display toggle** (macOS ↔ Win·Linux) — a **view** control initialized from the detected host: it restyles keycaps and gates the `⌘` picker option, never what this host must actually press. Capture and the header chord always read the physical `host.platform`; claim lookups combine the *display* platform with the *physical* host's `shell` flag.
- **Header chord hint** — `{chord} toggles this sheet` derives from the effective map (`byAction.get("shortcuts-overlay")`) formatted for the physical host, so it reads ⌘/ on a mac and reflects overrides; it is **hidden entirely** when that binding is unbound or disabled rather than advertising a dead chord.
- **Filter input** over label + description, and a per-scope **grouped row list** (GLOBAL / TERMINAL / BOARD) with `ScopeBadge` pills on non-global rows.
- **Shell-owned locked rows are a subgroup at the END of GLOBAL** (a `SubHead` reading "Shell-owned — accelerators live in the desktop shell menu"), not a top-level section — three flavors of locked top-level section was one too many once tmux arrived. Same 🔒 non-interactive idiom (accelerators are edited in the shell menu; the DevTools row is win/linux only), and the rows still count toward the `global` jump chip. Locked rows are **free-form caps arrays**, not tier-constrained, which is what lets the `Switch to server 1–9` row render `⌥ ⌘ 1…9` on the mac display — diverging from the shared `tierCaps` helper that still gives `Force reload` ⇧⌘R — while win/linux keeps `Shift Ctrl 1…9` on both rows. No registry or tier change backs the divergence, because the mac switcher accelerator lives outside every tier.
- **Click-to-rebind capture** — arming a row installs a capture-phase window listener that `preventDefault`+`stopPropagation`s (keeping the chord away from the focus trap, the dispatcher, and the legacy listeners); Esc cancels without persisting; a modifier-only or tier-less press keeps capturing. After a successful capture the row shows a steal warning naming the victim, or a claimed-key warning when the combo is spoken for — the claim lookup is **tier-aware** (`c.tier === combo.tier && c.code === combo.code`), so capturing ⌘R inside the mac shell warns that the shell owns it while ⇧⌘R warns separately.
- **Host-divergent rows carry the fact themselves** — a `desktop` pill (ScopeBadge/reserved-pill idiom) plus the OTHER host's chord as secondary text: `in browser: ⇧⌘T` inside the shell, `in desktop app: ⌘T` in a mac browser (there alongside the amber `browser` reserved pill). The gate is `host.platform === "mac" && b.isDefault && b.macTier != null && b.macShellOnly === true`, so exactly the `create-session`/`create-window`/`kill-window` trio qualifies — the only `macTier`+`macShellOnly` set in `DEFAULT_BINDINGS`. It is a **physical-host** fact, never the display toggle, and only at the host default: an override applies verbatim on both hosts and an unbound row has no chord, so either collapses the divergence and drops the badge. Host-invariant rows and win/linux hosts never render it. Most of the ⌘ layer (⌘K, ⌘., ⌘[/⌘], ⌘/) works in a browser tab too, so the layer as a whole is **not** labelled desktop-only. Derivation reuses existing seams: `macTier`/`macShellOnly` ride onto `EffectiveBinding` through `resolveBindings`'s spread, and the other-host chord is `defaultComboFor(def, { platform: "mac", shell: !host.shell })` over the base def read from `DEFAULT_BINDINGS` (the effective row's `tier` is overwritten by resolution, so the base def is the correct input). No registry schema change.
- **Per-row modified dot + ↺ reset**, an `unbound` button on user-disabled rows, a `browser` badge on reserved rows, and a footer with the localStorage note + **reset all**.
- **`[ CUSTOM ]` section** (`data-testid="macro-section"`) — the editable macro tier (§ Macro bindings). One row per macro: the label, a monospace `macroCommandPreview` chip, the same click-to-rebind combo button as a builtin row (an unbound macro shows the amber `unbound` button; a browser-reserved combo shows the `browser` badge), and a `✕` delete that drops the definition **and** its combo diff. A riff macro whose preset is absent from the fetched preset list renders a red `missing preset` badge — no silent fallback. The grouped GLOBAL/TERMINAL/BOARD lists filter macros out (`b.kind !== "macro"`), so each macro renders exactly once; the filter input searches macro labels and previews too.
- **`+ bind a key to a palette action or riff preset…`** — an inline add flow: a searchable target list (riff presets + the mount's palette actions, macros excluded), a name input pre-filled from the picked target's label, and `add + capture key`, which creates the macro and immediately arms capture on the fresh row — naming and binding in one gesture. Target data arrives via optional props `paletteTargets` / `riffPresetNames`, fed by the single layout mount (`LayoutShortcutsOverlay`): `paletteTargets` is the merged palette list minus the macro entries themselves (no macro→macro chains), and **`paletteTargets == null` gates the whole add flow off** — the layout mount passes none unless the route has a server + session, so on board/host routes the CUSTOM rows render read/rebind/delete-only. `riffPresetNames == null` means "preset list unknown" — no badges, no riff targets offered.

- **`[ TMUX ]` section** (last, `data-testid="tmux-section"`) — the pane's own keybindings, **read-only**. tmux keys are pressed inside the pane and configured in `configs/tmux/default.conf`; run-kit only documents them, so every row is the same 🔒 locked, non-interactive idiom as the shell-owned subgroup (no capture, no reset, no rebind). Data is the existing curated `getKeybindings(currentServer)` client API (`app/backend/api/keybindings.go`'s whitelist — a read-only dependency, unchanged). Two `SubHead` groups: **Direct** for root-table rows (F2/F3/F4 new/prev/next window, Shift+F3/F4 prev/next pane, Shift+F7 copy mode) and **Prefix — Ctrl+S, then key** for prefix-table rows, rendered as a keycap **sequence** (`Ctrl` `S` *then* `\`) rather than a simultaneous combo. Both subheads hide while filtering (the group labels are navigation, not matches). Key-name formatting is `S-` → `Shift+`, `C-` → `Ctrl+`.

  The server comes from `useSessionContext().currentServer` read **inside** the overlay, and the fetch runs only while the overlay is open, cancel-flagged on close/server change. `null` bindings means loading; `[]` means no current server (board/host routes), an empty response, or a failed fetch — all three collapse to the one-line **"No tmux server running"** empty state, so there is no spinner deadlock and no crash path.

`riffPresetNames` comes from a best-effort `getRiffPresets(server, session)` fetch inside `LayoutShortcutsOverlay` (`app.tsx`) that runs only **while the overlay is open on a route with a session**, mapped to names; a failed fetch leaves it `null`. Detection is therefore advisory — `POST /api/riff` validates authoritatively at execution time either way (§ Macro bindings), so a macro is never silently inert.

Export/import of overrides is not offered.

### Palette hints

`withShortcutHints(actions, byAction, platform)` (pure, in `lib/keybindings.ts`) decorates a palette action array with each action's **effective** combo as its `shortcut` hint — `actionId` doubles as the palette id, so the join is free. Each route applies it to the list it registers into the slot (AppShell's `paletteActions`, the board's `boardRouteActions`), and the layout applies it to the global groups inside `use-global-palette-actions.ts` (§ Single palette mount + palette-actions slot). Formatting is per platform via `formatCombo`/`comboParts`: mac symbol tiers join bare (`⇧⌘N`, `⌘.`), other platforms join with `+` (`Shift+Ctrl+N`), and the `ctrl` tier keeps the `` Ctrl+` `` spelling on both. Hints reflect overrides. A **disabled** binding (user-disabled or browser-reserved) contributes NO hint — advertising a dead chord would lie — while the palette entry itself stays reachable. Actions with no registered binding pass through untouched, so hand-set hints survive; `buildViewActions` (`lib/palette-view.ts`) takes the effective cycle hint string as a parameter rather than hardcoding it.

The **page tier** — the unshifted `⌘<key>` tier on macOS, unshifted `Ctrl+<key>` on Windows/Linux — is left entirely unbound by the Electron desktop shell on every platform it packages for ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam). The SPA spends part of that budget on **macOS**: ⌘[/⌘]/⌘/ and ⌘B/⌘J in both mac hosts and ⌘N/⌘T/⌘W inside the mac shell (§ Per-platform default tiers), alongside the legacy ⌘K/⌘. chords that always lived there. Host-conditional demotion is the `isShell()` gate in `defaultComboFor` (`lib/shell.ts`, the `window.runkitShell` detection seam). Whatever the SPA does not take stays the browser's or the OS's: mac-browser ⌘N/T/W/L and ⌘1–9 are claimed data, and on **Windows/Linux the page tier remains untouched by the SPA** — plain Ctrl is the pane's.

### Education micro-copy (placeholders, empty states, in-situ hints)

Discoverability copy lives **at the point of use**, never in a dedicated surface — placeholders, empty states, and existing Tips teach the hidden feature they sit on, each string computed where the mode is known so it cannot lie about it (§ Design Decisions → Placeholder over inline legend; → Hints render from current state alone). No new routes, dialogs, or persistent state — the whole apparatus is copy plus existing Tip `kbd` slots and menu-row keycap chips. (`260811-ke2s`)

- **Mode-aware placeholders.** The compose strip's textarea is the exemplar (§ Docked Compose Strip): terminal target `Compose text — Enter inserts · {submitKeycap} sends · ↑ history` (the sole surfacing of ↑ sent-history recall anywhere in the UI), selection broadcast `Compose prompt — {submitKeycap} sends to all selected`, no target `No focused terminal — click a pane to target it`. The chat send box reads `Message the agent — Enter for newline · {submitKeycap} sends` — chat's plain Enter deliberately diverges from the strip (newline, not insert-line), and the placeholder is where the divergence stops surprising ([chat](/run-kit/chat.md) § Send-form input box). The command-palette input reads `Type a command — try Board: Pin: View: Window:` and its no-results row `No results — try a prefix: Board:, Pin:, View:, Window:` — typed-namespace education, not a chord, so neither branches on pointer type (the confirming step's `Confirm action...` is untouched).
- **Empty states name their fill action.** No bare labels: the board page and host BOARDS zone name the sidebar row 📌 + `Pin:` palette route; SERVICES reads `No services — listening TCP ports appear here automatically`; HOST HEALTH `No metrics — waiting for the host's first report`; a session-less server group reads `(no sessions — + new, or {chord})`; every `{chord}` here is fine-pointer-only (see the coarse-pointer bullet below); the shortcuts overlay's no-match line scopes its own filter (`… · the filter spans app, custom & tmux keys`).
- **Platform-aware keycaps, never hardcoded lies.** Fixed Enter-policy chords (owned by `classifyComposeEnter`, not the registry) use the `composeSubmitKeycap()` seam. Chords for **rebindable** actions (`create-session`, `command-palette`, `open-last-used`) are read from `useKeybindings().byAction` + `formatCombo(…, host.platform)` and the clause is **omitted when the binding is unbound/disabled** — the `sheetChord`/palette-hints rule (§ Palette hints, § Tier-1 `Tip`) extended to prose copy. The derivation stays inline at each call site (no shared helper — readability over cleverness).
- **Menu-row keycaps.** A menu row whose action has a registry binding carries a trailing right-aligned `kbd` chip (the shared `MENU_ROW_KBD_CLASS`, palette-row visual weight, `ml-auto`, `aria-hidden` so the chord stays out of the accessible name), derived inline by the same `byAction` + `formatCombo` enabled-else-`undefined` rule — the SplitControl direction popover rows, the overflow chevron menu's split rows (§ Split control), and the App-section Settings / Keyboard shortcuts rows. A menu is itself a discovery surface, so every open doubles as a shortcut lesson; rows without a matching binding stay keycap-free. (`260811-0f3d`)
- **Coarse pointers keep the short copy.** Keyboard-chord hints never render on touch — the Tip suppression rule (§ Design Decisions → Suppress-by-early-return on coarse pointers) applied to strings via `useCoarsePointer()`. It binds **every** chord clause, not just the placeholders: placeholders fall back to their short forms (`Compose prompt…` / `Message the agent…`; the compose strip's terminal-target coarse placeholder instead folds the target name in — `→ {name}…`, § Docked Compose Strip → Coarse header fold); the SelectionIndicator drops both its `⇧click extends` clause and its `{chord} → Selection:` clause; and the empty states drop their chord tail, leaving the pointer path alone (`(no sessions — + new)`, `… click its 📌` on the board page and the host BOARDS zone). Each site folds the pointer test into the same expression that derives the chord (`!coarse && binding?.enabled ? formatCombo(…) : undefined`), so an unbound binding and a touch pointer collapse to one `undefined` and the copy has a single fallback branch.
- **Stateless.** Every hint renders from current state alone (selection active, binding bound, pointer type) — no first-run tours, dismissal flags, or rotating tip carousels.

### Single palette mount + palette-actions slot

Exactly one (lazy) `CommandPalette` mounts in `AppLayout` (`LayoutCommandPalette` in `app.tsx`) and renders the merged list `[...routeActions, ...globalActions]` — the active route's registered actions first, then the layout-level global groups, both already shortcut-decorated. **Command Palette Move up/down (server / session / window)**: a keyboard/touch reorder path parallel to the two drag surfaces, giving all THREE hierarchy levels a keyboard-reachable reorder (Constitution V). Six `PaletteAction`s, each acting on the **current** route-context entity (the `Session: Move` / `Window: Move` current-entity semantics), grouped with their existing families in `app.tsx`, all with boundary = **hidden** (the entry is filtered out at the top/bottom of its list — no wraparound, no disabled state): (`260705-bpnr`)

- **`Server: Move up` / `Server: Move down`** (`server-move-up`/`-down`, `serverActions`) — move the current server one position within the REGULAR class (infra excluded). The new full regular-class order is computed and POSTed via `setServerOrder` (server-global `event: server-order` echo re-sorts every client). Hidden when the current server is infra (`currentRegularIdx === -1`) or at a class boundary.
- **`Session: Move up` / `Session: Move down`** (`session-move-up`/`-down`, `sessionActions`) — move the current session one position in the **effective** session order (`deriveEffectiveSessionOrder(liveNames, sseOrder)` — persisted `@rk_session_order` filtered to live names, un-ordered live sessions appended in natural order; the sidebar's transient drag override is component-local and NOT visible to the palette). Persisted via the EXISTING `setSessionOrder(server, order)` — the same primitive the sidebar session drag uses; no new backend.
- **`Window: Move up` / `Window: Move down`** (`window-move-up`/`-down`, `windowActions`) — move the current window ±1 index via `moveWindow(server, windowId, targetIndex)`, then navigate to the same stable window ID with `search: (prev) => prev` (view-preserving). The sole window-move pair. See § Window move actions above.

**`Board: Move up` / `Board: Move down`** (`board-move-up`/`-down`) — the same boundary-hidden / no-wraparound keyboard+touch path for the board list, registered in `board-page.tsx`'s `boardRouteActions` (NOT `app.tsx`), because "current board" only has meaning on a `/board/$name` route (the board registers its own route-scoped list — § Single palette mount + palette-actions slot). Each acts on the CURRENT board (the `/board/$name` param), computes the full new order via `computeMoveOrder(boardNames, currentBoardIdx, delta)` over the backend-sorted `boards`, and POSTs it via `setBoardOrder` (server-global `event: board-order` echo re-sorts every client — see § Board-list drag reorder). Hidden when the current board is first (`currentBoardIdx === 0` → only Move down) or last (only Move up); a `null` from `computeMoveOrder` is a defensive no-op. `onError` surfaces `useToast().addToast`. (`260708-a2qd`)

**Pure order-computation helpers** — the boundary gating, effective-order derivation, and swap arithmetic are extracted into `app/frontend/src/lib/palette-move.ts` (Vitest-covered `palette-move.test.ts`) so they are testable without mounting the shell; the palette action bodies are thin wrappers that call these then invoke the client mutation. Exports: `deriveEffectiveSessionOrder(liveNames, sseOrder)` (SSE-order-∪-natural), `computeMoveOrder(order, currentIdx, delta)` (insert-before splice, `null` on boundary/out-of-range — shared by Server, Session, AND Board Move), and `computeWindowMoveTarget(index, delta, minIndex, maxIndex)` (target index, `null` on boundary — used by the Window up/down pair). `MoveDelta = -1 | 1`.

**Selection palette commands (`Selection:` prefix)** — the action surface for the sidebar's window-row multi-select (§ Window-Row Multi-Select). Composed by the pure builders in `lib/palette-selection.ts` (+ colocated `palette-selection.test.ts`, the `palette-pin.ts`/`palette-move.ts` convention) with thin `onSelectAll(keys)` / `onClose(keys)` / `onCompose(keys)` / `onMove(targetSession)` bodies wired in `app.tsx`'s `selectionActions` memo. Four entry kinds, every one **omitted rather than disabled** when ineligible (the family's convention) — close and send need only a non-empty selection, so they are the two that stay eligible across a **cross-server** one (§ Design Decisions → Close and send are cross-server): (`260807-nf9f`, `260808-ebgs`)

- **`Selection: Select all merged (N)`** (id `selection-select-all-merged`) — replaces the selection with exactly the current server's merged-PR windows via `selectOnly`. Merged comes from the PR knowledge the frontend already has: `win.prState === "merged"` read directly (`mergedWindowKeys`), the same field `prGlyphColor` reads for its merged branch (§ Shared PR vocabulary). Scoped to the current server — a cross-server selection would dead-end the single-server bulk move below. Omitted with no current-server context or no merged windows. **It also carries the feature's discovery surface**: `SELECTION_GESTURE_HINT` (`x · ⌘-click · ⇧-click`) rides its `shortcut` badge, which the palette renders as a `<kbd>`. That is deliberate — `x` is a bare key handled inside the tree's own keydown and is NOT in `DEFAULT_BINDINGS` (§ Design Decisions → The `x` toggle is documented at the palette registration), so it appears on no chord map and in no shortcuts overlay.
- **`Selection: Close N window(s)`** (id `selection-close`, `buildSelectionCloseAction`) — the destructive one, and the only palette entry in the app that **confirms in the palette itself**. It carries a `confirmLabel` (`Close N window(s) — Enter to confirm`), an optional field on `PaletteAction` that `CommandPalette` interprets as a **one-row confirmation sub-step**: selecting the entry does NOT run `onSelect` — it stashes the action in `confirming` state, replaces the whole result list with the single derived `${id}-confirm` row, resets query + index, and makes the search input `readOnly` with a `Confirm action…` placeholder (so typing cannot escape the step). Enter on that row runs the action once and closes; Escape (the shared `useFocusTrap` document handler), a backdrop click, and the ⌘K toggle all cancel through the same `closePalette` / `setConfirming(null)` seam, leaving the windows live and the selection intact. The mechanism is generic — any action can opt in by setting `confirmLabel`; the confirmed row itself carries `confirmLabel: undefined`, so a step can never recurse.
- **`Selection: Send prompt to N agent(s)`** (id `selection-send-prompt`, `buildSelectionSendPromptAction`) — hands a **snapshot** of the selected keys to `app.tsx`, which stores it as `selectionBroadcastKeys` and routes text entry to the docked compose strip in its selection-broadcast target mode (§ Docked Compose Strip → Selection-broadcast target). The action does not send: it opens the strip if the `composeStripEnabled` preference is off (`toggleComposeStrip()`, whose off→on focus-on-open flag then focuses the textarea) or, when it is already mounted, focuses it via `queueMicrotask(() => focusComposeStrip())` — one microtask later, so React has swapped the disabled focused-terminal target for the selection target first. Toggling the strip off cancels the target (an effect clearing `selectionBroadcastKeys`); per-window drafts in the module store are untouched.
- **`Selection: Move N window(s) to <session>`** (ids `selection-move-to-<session>`) — one entry per eligible existing session, with the live count and correct singular/plural. **The palette's fuzzy filter IS the session picker**: no dialog, no create-if-missing, no new backend surface. A target that would be a COMPLETE no-op (every selected window already lives in it) is excluded; a selection with unresolved keys excludes nothing, since the move is still meaningful.

**The move family's server is the SELECTION's, never the route's.** With sessions scope `all` the sidebar paints every server's groups, so a user can select rows on server A while routed to server B — and tmux `@N` ids are unique per server only, so feeding the route server's sessions would list the wrong targets AND move the wrong windows. `app.tsx` derives `selectionServer = singleSelectedServer(selectedWindows)` and passes THAT server's sessions (the merged `useMergedSessions` list when it is the route server — it carries the ghost/rename overlays the sidebar paints — else the raw `ctx.sessionsByServer.get(srv)`), omitting the entries entirely when that server's sessions are `undefined` (not loaded yet, which is not the same answer as "no eligible targets"). `buildSelectionMoveActions` additionally takes an explicit `sessionsServer` first parameter and returns `[]` on a mismatch, so the contract is enforceable at the builder seam rather than trusted at the call site. `singleSelectedServer` returning `null` for an empty or cross-server selection omits the whole family (§ Design Decisions → The move builder owns the server-match guard).

The entries are folded into `paletteActions` in AppShell only. The **board route registers board-scoped actions only** (§ Design Decisions → One palette mount in AppLayout, routes register via the slot) and does not include them, while `BoardPage` mounts the sidebar with `currentServer={null}`. So a board-route user can still build a selection, but the indicator **suppresses its `→ Selection:` hint** there — `SelectionIndicator` takes `hasSelectionActions={currentServer !== null}`, keyed on the same non-null-server condition the `Selection:` family itself is scoped to — rather than advertising a palette route to entries that route cannot reach.

**Cross-session move actions**: Dynamically generated "Window: Move to {sessionName}" actions (id `move-window-to-session-{sessionName}`) — one per session other than the current one. Only shown when `currentWindow` exists AND there are at least 2 sessions. On select, calls `moveWindowToSession(server, currentWindow.windowId, targetSession)` then navigates to `/$server` (server dashboard) because tmux auto-assigns the window index in the destination session and no `/$server/$session` route exists. Flat action list (not a sub-picker) — works well for typical session counts (2-5) and requires zero changes to the command palette component.

### Keyboard-Navigable List Scroll Pattern

Both `CommandPalette` and `ThemeSelector` use the same scroll-into-view pattern for arrow key navigation: a `listRef` on the listbox container plus a `useEffect` on `[selectedIndex, open]` that queries `[aria-selected="true"]` and calls `scrollIntoView({ block: "nearest" })`. This ensures the selected item stays visible when navigating past the `max-h-64` scroll boundary. New keyboard-navigable list components SHOULD follow this pattern.

The sidebar session/window tree is a **third consumer** (see § Sidebar → Keyboard Navigation & Tree ARIA): a `treeRef` on the `role="tree"` container plus a `useEffect` on `[rovingKey]` that resolves the roving row (`[data-window-id]`/`[data-session-row]`) and calls `scrollIntoView({ block: "nearest" })` + `focus()`. It reuses the scroll-into-view half but deliberately diverges from the `selectedIndex` numeric-state model — the roving cursor is a row-key STRING (robust to the variable-length tree's expand/collapse and SSE row churn, where a numeric index can desync); the focus call is gated by `focusMovedRef` so passive SSE re-renders never scroll/steal focus.

## Design Decisions

### Delete the zoom binding row outright
**Decision**: the `layout-zoom` entry is removed from `DEFAULT_BINDINGS` rather than shipped as a default-unbound row; the zoom action survives through the palette's `Layout: Zoom`/`Unzoom` entries and the tile ⛶ verb.
**Why**: `KeyBinding.code` is a required field; default-unbound needs a type change rippling through combo matching for one action, and the action stays reachable via palette + verb.
**Rejected**: optional-`code` support — disproportionate to removing one chord; users lose overlay rebind for zoom, accepted.
*Introduced by*: 260813-j3jb-compose-tile-dock-drop-zoom-chord

### Shell servers reach the palette by empty-list gating, not an `isShell()` branch
**Decision**: `useShellServers()` resolves `[]` outside the desktop shell (the bridge wrappers swallow every absent/malformed/denied case), so `buildShellServerActions` yields no entries and `app.tsx` registers the group unconditionally — no `isShell()` conditional at the registration site. The list is a mount-time snapshot with no refresh seam, quoted labels distinguish shell servers from tmux servers, and v1 is switch-only.
**Why**: One code path for both environments — an `isShell()` branch would gate on a *second* signal that can disagree with whether the `servers` group actually answers (an older shell has `version`/`platform` but no bridge group), so the list's own emptiness is the more truthful gate. A snapshot suffices because every list mutation the shell offers (switch, add) loads a different server URL, which remounts the SPA anyway; only removing a non-active server leaves a stale entry until reload.
**Rejected**: An explicit `isShell()` conditional around the registration (a second, less accurate signal); a live refresh subscription or poll (a new seam for a list that changes only via flows that already remount the SPA); unquoted labels matching the tmux entries (two different kinds of "server" reading identically in one palette); including Add/Remove Server (Constitution IV — the native menu + welcome flow already own those, and Remove needs a confirm dialog the palette has no home for).
*Introduced by*: 260730-9lez-shell-keyboard-tier-symmetry

### One palette mount in AppLayout, routes register via the slot
**Decision**: The single (lazy) `CommandPalette` mounts in `AppLayout` and renders `[...routeActions, ...globalActions]` — routes publish route-scoped, shortcut-decorated lists through `useRegisterPaletteActions` (`palette-actions-context`, the `top-bar-slot-context` pattern), and the global groups (nav, font, refresh, help, shortcuts, settings, update/check/maintenance/version) build once at the layout in `use-global-palette-actions.ts`. The server create/kill dialogs and the shortcuts overlay follow the same shape: one mount in `AppLayout` (`server-dialogs-context` + `components/server-dialogs.tsx`, the `settings-dialog-context` pattern; layout-owned overlay state), triggered from any route.
**Why**: The board route does not render AppShell, so per-route mounts forced every globally-meaningful action and the server dialogs to be re-implemented inside `BoardPage` — and the twins had drifted in user-visible ways (the board's kill confirm lacked the daemon warning; its create input skipped the safe-name sanitization). A layout mount plus a register channel makes a global unreachable-by-omission impossible and gives every route the same dialog behavior.
**Rejected**: Per-route palette/dialog mounts with duplicated global groups (drift is inevitable — each global tweak must be written twice); rendering AppShell on the board route (AppShell is deliberately server-scoped); shared JSX with per-route state (removes JSX drift but keeps the state twins).
*Introduced by*: 260811-239r-board-twin-dialogs-palette

### The palette slot splits state from a stable API channel
**Decision**: `palette-actions-context` exposes three channels — a reactive state channel (`usePaletteActions`, the merged list, for the layout-level leaves that render it), a referentially-stable API channel (`setRouteActions` / `getAllActions`, identity never changes), and a globals-only channel (`usePaletteGlobals`) that routes may safely subscribe to. Routes resolve ids over `[...localRouteActions, ...globalActions]` at memo-build time, or imperatively via `getAllActions()` at chord/macro-invocation time.
**Why**: A route that both publishes its actions and subscribes to the merged state closes a render loop (publish → state change → re-render → fresh action identities → re-publish → "Maximum update depth exceeded"); and resolving through the slot state would lag one commit (the registration effect lands after the route's memo builds) with no way to trigger a rebuild, so a chord could stay dead. The globals-only prop identity never changes in response to a route registration, so subscribing to it is loop-safe.
**Rejected**: One reactive context for everything (render loop); routing all id resolution through the slot state (one-commit lag, unreachable rebuild).
*Introduced by*: 260811-239r-board-twin-dialogs-palette

### The action tier's LETTERS are uniform; its modifier is per platform and per host
**Decision**: The canonical letters (N/T/W/H/L/A + [/]//) are the same on every platform, but the modifier is not: Windows/Linux uses `Shift+Ctrl` throughout, while macOS demotes to the unshifted ⌘ tier wherever nothing immovable blocks it — [/]// in both mac hosts, N/T/W inside the desktop shell only, with H/L/A staying shifted everywhere. The refinement is declarative data on each binding (`macTier`/`macShellOnly`) resolved once in `defaultComboFor`.
**Why**: Letter consistency is what must not fragment; chord weight is negotiable per environment, and the constraints that force Shift were never symmetric. Plain Ctrl must stay with the pane on Windows/Linux (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+N/P history) — a macOS-only constraint-free tier gets taxed for nothing by uniformity, and the desktop shell exists precisely to hand the SPA the unshifted ⌘ tier, so a uniformly-shifted tier left that premise unspent. What blocks a demotion is genuinely immovable, not aesthetic: ⌘H is macOS Hide and ⌘A is select-all / the shell's Edit role, and demoting L alone would split the H/L pair across two tiers — the same fragmentation the letter rule exists to prevent. Because the resolver already funnels every consumer through one effective map, expressing the tier as per-key data costs no architecture.
**Rejected**: A uniform shifted tier on every platform (taxes mac users a three-key chord the environment would give them in two, and leaves the shell's whole reason for existing unused); demoting H/L/A too (⌘H/⌘A are dead in both mac hosts — the chord would silently do nothing); demoting N/T/W on mac *browsers* as well (browser-reserved unshifted AND shifted, so they stay palette-only there); per-platform `DEFAULT_BINDINGS` arrays or a resolver-level actionId→tier table (duplicates every binding, or splits the per-key truth across two structures).
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts

### The tables are the chord authority; the key map is a discovery and rebind tool
**Decision**: The overlay renders ONE keycap grid with a "Holding ⇧⌘ | ⌘" modifier picker, and the browser-vs-desktop divergence lives on the affected table ROWS (a `desktop` badge + the other host's chord) rather than in a second grid or a per-map caption.
**Why**: Two stacked grids named the registry's internal tier taxonomy in user-facing chrome and re-answered per-action chords the rows already carry, at double the vertical mass — which pushed the authoritative tables and the TMUX section below the fold on short viewports. Giving each surface one job removes the duplication instead of restyling it: the map answers the physical question ("hold this — here's what my keyboard does", the model Karabiner-style keyboard viewers use), and the rows carry the per-action truth including where it differs by host. The divergence is genuinely per-binding — exactly the `macTier`+`macShellOnly` trio — so a row is where the fact belongs.
**Rejected**: Keeping both grids with de-jargonized headers (still double the vertical mass, still duplicates the tables); labelling the whole ⌘ layer desktop-only (factually wrong — ⌘K/⌘./⌘[/⌘]//⌘/ all work in a browser tab; only the trio differs); a registry change to carry the new presentation (unnecessary — `macTier`/`macShellOnly` already ride onto `EffectiveBinding`, and `defaultComboFor` already computes the other-host chord).
*Introduced by*: 260801-r8j2-shortcuts-map-modifier-picker

### The picker IS the map label, and the inactive layer falls back by derivation
**Decision**: The map header's left slot is "Holding" plus the segmented control itself (the selected segment supplies the modifier caps), with a static "Holding **Shift Ctrl**" on the Win·Linux display; the rendered layer is derived (`displayPlatform === "mac" ? mapTier : "shifted"`) rather than reset when the display toggles.
**Why**: The picker and the layer label are the same header element — rendering them separately would duplicate the modifier caps and widen the header row, and a one-option segmented control on Win·Linux is dead chrome. Deriving the fallback matches "the option disappears" rather than "the selection is destroyed": a user flipping the display to Win·Linux and back gets their ⌘ selection returned, consistent with the session-scoped view state the fold already establishes.
**Rejected**: A separate "Holding ⇧⌘" title plus a detached picker (duplicates the caps); resetting `mapTier` on display change (loses the selection on a round-trip for no benefit); persisting the selection to localStorage (a reading preference within one sheet, not a device setting).
*Introduced by*: 260801-r8j2-shortcuts-map-modifier-picker

### Chord handlers are the palette action bodies, looked up by id
**Decision**: The AppShell dispatcher resolves `create-session`, `create-window`, `kill-window`, `agent-next-waiting`, `go-back`, `go-forward`, and `settings-open` by finding the palette action with the matching id — over the MERGED route+globals list (`fromPalette` over `[...routeActions, ...usePaletteGlobals()]`, § The palette slot splits state from a stable API channel) — and reusing its `onSelect`.
**Why**: `actionId` doubles as the palette id by design, so the lookup is free — and reuse makes chord/palette drift impossible, including gating: a palette entry that does not exist (e.g. `kill-window` with no active session) yields no handler, and the dispatcher's no-handler fall-through is exactly the desired no-op. Resolving over the merged list keeps chords working when an id's ownership moves between a route group and the layout-level globals.
**Rejected**: A parallel handler implementation per chord — duplicates every gate and drifts from the palette behavior it must mirror.
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### Enablement-bearing chords keep their own listeners; the registry owns definition and suppression
**Decision**: `command-palette`, `sidebar-toggle`, and `view-cycle` dispatch from component/hook-local listeners that read their combo from the effective map and gate on the shared suppression predicate; the other chords (including the board pane-cycle) run through `useKeybindingDispatch`.
**Why**: Centralizing *definition* and *suppression* is the registry's charter; centralizing *enablement* is not — palette open-state and lens availability are local state, and routing them through one dispatcher would need context plumbing for zero user-visible gain.
**Rejected**: One dispatcher for every chord (high regression risk, new context plumbing); leaving these chords out of the registry entirely (they would be unrebindable and invisible to the overlay).
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### The terminal seam refuses shifted chords everywhere, cmd chords only on mac (metaKey-gated), and ctrl-tier chords only on mac (ctrlKey-gated)
**Decision**: `shouldRefuseTerminalChord` returns `true` for an enabled shifted-tier match on any platform, an enabled cmd-tier match on macOS **only when `event.metaKey` is set**, and an enabled ctrl-tier match on macOS **only when `event.ctrlKey` is set without `metaKey`**; everything else returns `true` from the handler (reaches the pane), after the ⌘C copy case.
**Why**: Refusal must be exactly as wide as the set of chords the pane cannot use. Legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so the shifted tier costs the pane nothing anywhere; ⌘ chords never reach a pane as control bytes, so refusing them on mac is loss-free and is what lets the demoted ⌘[/⌘]/⌘/⌘B/⌘J fire under terminal focus. The `metaKey` gate is the load-bearing half: `matchesCombo`'s cmd tier accepts Meta **or** Ctrl, so an ungated refusal would steal Ctrl+[ (ESC) from mac panes — the same hazard that forbids cmd refusal on Windows/Linux, where CmdOrCtrl *is* the pane's own Ctrl. The ctrl-tier rule is what lets ⌃` (`focus-hop`) fire under terminal focus on mac; it steals NUL (the byte Ctrl+` encodes to) from the pane — near-zero cost, the same trade VS Code makes for its own ⌃` — and its `!metaKey` gate is rule 2's inverse, so a ⌘+Ctrl combined press cannot double-match. Gating both mac rules on platform + modifier therefore keeps the Win/Linux seam byte-identical rather than making it a special case (no ctrl-tier default resolves there — `focus-hop`'s base tier is shifted).
**Rejected**: Refusing every registry match (breaks plain-Ctrl pane chords everywhere); refusing all cmd-tier matches on mac ungated (breaks Ctrl+[ = ESC); refusing every plain-Ctrl chord on mac to keep the predicate simple (steals the pane's whole control-byte vocabulary for one shipped ctrl-tier chord); narrowing `matchesCombo`'s cmd tier to Meta-only on mac (would change the legacy ⌘K/⌘. predicates project-wide); adding a `preventDefault` in the handler (xterm's non-preventing refusal is what lets the event bubble to the window dispatcher). Residual: on Windows/Linux an action deliberately rebound *into* the cmd/ctrl tier is not refused and reaches the pane while the terminal has focus.
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts; ctrl-tier rule: 260816-sm66-vscode-shortcut-realignment

### Overrides are localStorage diffs with single-press steal-and-warn
**Decision**: Only differences from the defaults are persisted (`{ [actionId]: {code,tier} | null }`), and one capture press hands the combo over, unbinding the previous owner and flagging it.
**Why**: A diff blob keeps the shipped defaults authoritative — adding or renaming a default binding needs no migration, and re-capturing an action's own **host** default drops its entry rather than freezing a redundant one. Single-press steal keeps rebinding to one gesture and is honest about the consequence, since the victim's `unbound` state is visible in the overlay until it is rebound or reset. Storing only diffs also makes the per-platform tiers free: overrides are per-device by construction, so a device's platform is implicit and no per-platform storage key or migration exists. localStorage matches Constitution II (no database) and the `runkit-terminal-font-size` precedent.
**Rejected**: Persisting the full effective map (defaults freeze into user storage, and the per-platform default would be baked in); a press-again-to-confirm steal (two gestures for one intent, and the warning already carries the information); a backend-stored per-user map (a new persistence surface for a per-device preference); a per-platform override shape (per-device storage already makes per-platform inherent).
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### A same-combo global↔scoped pair is precedence for conflicts but still a steal target for capture
**Decision**: `findMatches` orders matches non-global-first and the dispatcher fires the first one with a handler; `findConflicts` flags only **equal**-scope pairs; `applyCapture`'s victim search stays `scopesOverlap`-wide, and its own-host-default check short-circuits **before** that search.
**Why**: Once dispatch is scoped-beats-global, a global↔scoped shadow leaves both bindings fully functional (the scoped one wins on its route, the global one everywhere else), so reporting it as a defaults-integrity conflict would make the shipped mac map permanently "dirty" — the board ⌘[/⌘] pair shadowing back/forward is intended, not a defect. Capture stealing cannot be narrowed the same way: four chords dispatch through component-local listeners that never see `findMatches` precedence, so a cross-scope rebind onto their combos would genuinely double-fire, and steal-with-warning is the visible, reversible guard. The short-circuit ordering follows from the same shape — the mac defaults ship shadow pairs, so a victim search running first would let a *no-op* re-capture of one partner unbind the other.
**Rejected**: Treating the shadow as a conflict (would flag the shipped mac defaults); narrowing `applyCapture` to equal scopes too (silently allows double-fire on the locally-listened chords); a schema flag marking locally-listened bindings (scope creep for one edge); resolving the shared combo by moving the board pane-cycle off ⌘[/⌘] (breaks an established board chord to accommodate a global default).
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts

### Macro targets are riff presets and palette action ids, never shell strings
**Decision**: `MacroTarget` is a two-arm union — a riff **preset name** or a **palette action id**. Execution reaches process spawn only through the existing `POST /api/riff`, which resolves the name as a map-key lookup against `fab/project/config.yaml`-defined presets; an unknown name is a `ValidationErr` → 400.
**Why**: A shortcut executing user-typed shell text would make a web-reachable endpoint run arbitrary commands — precisely what Constitution I exists to prevent. Both motivating flows ("spawn a worktree with a fab-discuss agent", "spawn a codex loop") are already expressible as riff presets, so the macro tier adds **zero** new process-execution surface: it is a keyboard route to an already-validated spawn, and a localStorage-planted preset name can never reach argv. Arguments belong in the preset definition, inside the committed-config trust boundary.
**Rejected**: An arbitrary command string on the macro (Constitution I); an `args?: string[]` passthrough on the riff target (`POST /api/riff` has no args seam and its `task` replaces preset panes, so it needs a backend extension the "no new exec surface" premise rules out — additive to the union later if that seam appears); a preset-authoring UI in the web app (Constitution IV — presets already have a home and an authoring path in fabconfig).
*Introduced by*: 260730-hbyh-shortcut-macro-riff-bindings

### Macro combos live in the keybindings diff map, not the macro definition
**Decision**: A macro definition carries no combo; its binding is an ordinary `runkit-keybindings` override entry keyed by the macro's actionId, and a macro without an entry resolves unbound (`disabledReason: "user"`).
**Why**: One binding store and one resolution path means steal-with-warning, per-row reset, reset-all, browser-reserved disabling, palette hints, the overlay key map, and the terminal seam all work on macros with the existing machinery — no parallel plumbing, and reusing the steal-victim state gives the overlay's `unbound` affordance for free.
**Rejected**: Storing the combo inside the MacroAction — a second combo store that `applyCapture`/steal/reset could not see without duplicated wiring.
*Introduced by*: 260730-hbyh-shortcut-macro-riff-bindings

### Keyless defaults (`code: ""`) instead of a macro-specific resolver
**Decision**: `resolveBindings` carries one extra rule — an effective combo with an empty `code` resolves unbound — and macros enter resolution as ordinary defaults via `macroToBinding`.
**Why**: One resolver keeps every consumer (dispatch, hints, overlay, terminal seam, capture) macro-agnostic; builtins always carry a code, so they are untouched by the rule.
**Rejected**: A parallel `resolveMacroBindings` merged after the fact — duplicates the override/reserved/steal logic and forks the effective-map contract.
*Introduced by*: 260730-hbyh-shortcut-macro-riff-bindings

### The mac split pair rides a `macCode` default refinement rather than a platform-gated unbound vertical
**Decision**: `macCode?: string` refines a binding's SHIPPED DEFAULT key code on mac hosts, composing with `macTier` inside the one existing mac branch of `defaultComboFor` (`{ code: macCode ?? code, tier: macTier ?? tier }`, under the same `macShellOnly` gate). The split rows ship divider-mnemonic base codes — ⇧Ctrl+\ side-by-side (shift+\ types `|`, the divider the split creates), ⇧Ctrl+- stacked — with `macCode: "KeyD"` refining both to the iTerm2/Warp/Ghostty ⌘D/⇧⌘D pair on mac. Both actions are bound-by-default on every host.
**Why**: The mac pair is unrepresentable with constant codes — both rows on `KeyD` collide on the Win/Linux shifted tier (the test-enforced conflict-free invariant) and plain Ctrl+D is the pane's EOF — so each platform gets its own coherent pair instead of one platform getting half of one. `defaultComboFor` is already the single seam both `resolveBindings` (fallback + `isDefault`) and `applyCapture` (own-default detection) read defaults through, so conflict detection, overlay keycaps, and own-default re-capture handle the refined code with no new branch. The cost is one deliberate, documented exception to 260730-n789's letters-constant rule.
**Rejected**: Shipping `split-vertical` mac-only via a `platform` default gate that resolves keyless off-platform (the first-cut design this replaced in-PR: it left a Win/Linux action unbound-by-default behind an unexplained amber `unbound` row, and forced capture-suite tests off ⇧Ctrl+D); a second constant letter for vertical (breaks the mac ⌘D/⇧⌘D muscle-memory pair the chords exist for); leaving vertical on a colliding ⇧Ctrl+D (the conflict invariant forbids it); claiming plain Ctrl+D (takes EOF from the pane).
*Introduced by*: 260807-rbx5-split-keyboard-shortcuts

### An unrepresentable shell claim is recorded as absence plus the system claim that replaces it
**Decision**: The mac Hosts-switcher claim is expressed by *narrowing* `SHELL_SWITCHER_DIGITS` to `platform: "other"` and adding mac `owner: "system"` ⇧⌘3/4/5 "screenshot" rows — no Option tier is added to `BindingTier`, and the freed mac ⇧⌘1/2/6–9 carry no rows at all. The overlay's decorative digit-run ellipsis cell keys its claimed styling off `Digit3`.
**Why**: The mac accelerator lives on ⌥⌘, which the registry cannot express because Alt is excluded from every tier — and that exclusion is precisely why ⌥⌘ was chosen ([desktop-shell](/run-kit/desktop-shell.md) § Design Decisions → The mac shell tier is ⌥⌘). Adding a tier to represent the claim would undo the property that makes the key safe. What the key map still owes the user is honesty about what a mac ⇧⌘ digit press actually does, which the system screenshot rows supply: shell and system claims never disable a binding (only `browser` claims reserve), so this is pure display data and `resolveBindings` behavior is untouched — a capture onto mac ⇧⌘3/4/5 now warns "claimed by system (screenshot)" instead of "claimed by shell". `Digit3` is the ellipsis key because it is the only digit in the run claimed on **both** displays, so mid-run claims stay visible where `Digit1` would render the mac trio invisible.
**Rejected**: A fourth `BindingTier` for Option-carrying chords (destroys the un-claimable property the accelerator choice rests on, and `captureFromEvent` rejects Alt chords by design); leaving the mac shifted digits claim-free (the key map would show nine free keys where three take screenshots); claiming the freed ⇧⌘1/2/6–9 defensively (they genuinely are page real estate — a claim there would lock keys nothing owns).
*Introduced by*: 260731-nv5r-mac-host-switcher-alt-cmd

### One shortcuts surface with one filter, not two dialogs or tabs
**Decision**: The registry overlay is the only shortcuts dialog. tmux keybindings are a read-only section inside it, and there are no tabs — a single filter and a single scroll span app rows, macros, and tmux rows, with a sticky jump-nav chip row (live per-section match counts while filtering) standing in for tab navigation.
**Why**: The user's query is "what's the key for X?", and answering it should not require first knowing whether X belongs to the app or to tmux. Two dialogs made the answer depend on that knowledge, and the second dialog's hardcoded App rows drifted stale the moment the registry gained tiers and per-device overrides — the registry surface is self-updating by construction. Tabs would have re-imposed the same "pick the right pane first" cost inside one dialog; the tmux set is small enough that one scroll stays readable, and the chip counts keep hits below the fold discoverable.
**Rejected**: Keeping both dialogs (the staleness and the which-one-do-I-open question are structural, not a copy problem); tabs inside the merged overlay (reintroduces the pre-selection cost the merge exists to remove); making tmux rows rebindable (tmux keys are pressed inside the pane and configured in `configs/tmux/default.conf` — run-kit only documents them).
*Introduced by*: 260801-sm6g-keyboard-shortcuts-consolidation

### A chord may name a behavior even when it cannot name a target
**Decision**: `open-last-used` (⇧⌘O) is a builtin binding, while the per-target `Open: <label>` palette entries stay chord-less.
**Why**: The objection to chording Open was that targets are data-driven — the set varies per deployment, so no static chord can name one. "Re-run the last-used target" is a behavior, not an app, so it is nameable and stable across deployments; it also gives the split-button's primary segment the keyboard twin Constitution V wants. The empty case degrades to a toast rather than a popped menu, because a chord has no anchor to pop a mouse menu from.
**Rejected**: Per-target chords (unnameable, and they would collide differently on every deployment); leaving the primary segment keyboard-unreachable (the most-used Open path had no chord at all).
*Introduced by*: 260801-sm6g-keyboard-shortcuts-consolidation

### A tooltip keycap chip is resolved from the registry, never hard-coded
**Decision**: A `Tip`'s `kbd` slot for a registry-bound action is derived at the call site from the effective map (`useKeybindings()` → `byAction.get(id)` → `formatCombo(…, host.platform)` when `enabled`, else `undefined`), and the chip is **omitted** when the binding is unbound, disabled, or browser-reserved. Non-registry `kbd` strings survive only for chords the registry does not own (the compose/chat submit plus the per-surface Insert keys, `Enter` on the strip and `Alt+Enter` in chat — the submit chip still resolves per-platform through the shared `composeSubmitKeycap()` rather than a literal). The ⌘K chip's button FACE keeps its brand glyph regardless.
**Why**: A hard-coded chip is wrong the moment the platform or the user's override differs from the author's machine — a literal `"⌘K"` reads wrong on every Windows and Linux host and survives a rebind unchanged. Deriving it makes hover-discovery teach the chord that actually works (Constitution V), and omitting rather than dimming a dead chord follows the same rule the palette hints and the overlay's header chord apply: advertising a chord that does nothing is worse than advertising none. The derivation stays a 4-line snippet per site rather than a hook because `withShortcutHints` already covers the palette-array shape and a second abstraction for four scalar call sites would be the heavier option.
**Rejected**: A static string per call site for a registry-bound action (lies under rebinds and off-platform); rendering a dimmed/struck chip for a disabled binding (still advertises the chord, and the tip is one line with no room to explain why it is dead); a shared `useActionChord(id)` hook (four call sites and one shared derivation shape do not yet justify a hook — revisit if the count grows).
*Introduced by*: 260801-mqim-tooltip-shortcut-chips-settings-binding

### `settings-open` takes the shifted tier in browsers and ⌘, only in the shell
**Decision**: `settings-open` ships `code: "Comma"`, base `tier: "shifted"`, with `macTier: "cmd"` + `macShellOnly: true`, and ⌘, is added to `MAC_BROWSER_CMD_CLAIMS` as a browser-owned Preferences claim.
**Why**: ⌘, is the macOS convention for preferences, and the desktop shell binds no accelerator on it — so inside the shell the conventional chord is simply available. A mac *browser* owns ⌘, for its own Preferences, so the browser default has to sit one tier up; recording that as claims data (rather than only as a comment) is what makes a user override onto ⌘, resolve `reserved` in a browser instead of silently advertising a dead chord, while the identical combo stays the enabled default in the shell. Open-only semantics (not toggle) match every macOS app: ⌘, never closes preferences, and `openSettings` being `setIsOpen(true)` makes a re-fire a React state bailout for free.
**Rejected**: A single ⇧⌘, default everywhere (gives up the OS convention in the one host where it is free); an unshifted ⌘, default in browsers too (dead chord — the browser consumes it first); toggle semantics on re-fire (contradicts the macOS convention and the action's own `settings-open` / `Settings: Open` open-vocabulary naming); a `Comma` cell in the overlay's tier-map grids (the `Period`/`Backquote` precedent leaves punctuation off the fixed grid).
*Introduced by*: 260801-mqim-tooltip-shortcut-chips-settings-binding

**Why**: The change's stated constraint excludes persistent state; stateless hints cannot drift out of sync with a dismissal flag and cost no storage.

### The chrome chords mirror VS Code's keycaps: B for sidebar, J for the code panel, ⌃` for the focus hop
**Decision**: `sidebar-toggle` ships on `KeyB`, `code-toggle` on `KeyJ`, and `focus-hop` on `Backquote` — mac demotes B/J to the ⌘ tier in both hosts and the hop to the `ctrl` tier (⌃`); Win/Linux keeps all three on the shifted tier. **Why**: the target audience lives in VS Code (the code-server surface embeds it), so borrowing its exact keycaps removes the mis-fire tax — ⌘\ is *split editor* in VS Code, while VS Code's most-pressed chrome chord (⌘B) sat unbound.

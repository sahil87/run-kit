# run-kit UI — Visual Design

## Visual Design

Three theme modes: **system** (follows OS), **light**, **dark**. Default: system. Linear/Raycast aesthetic.

Theme is applied via `data-theme` attribute on `<html>` (`"dark"` or `"light"`). CSS custom properties in `globals.css` switch values per `html[data-theme="dark"]` and `html[data-theme="light"]` selectors. The `@theme` block registers token names for Tailwind CSS 4 with dark palette as initial values.

### Border-Width System

A three-tier border-width vocabulary, all in `--color-border`: (`260702-6m46`)

- **1px hairlines** (`border` / `border-t` / `border-b`) — the default: card borders, tile borders, in-panel dividers, dropdown separators, the `SectionHeading` rule.
- **3px structural seams** (`border-t-[3px]` / `border-b-[3px]` / `w-[3px]` / `border-[3px]`) — the major chrome boundaries that partition the app frame: the topbar's bottom edge (`top-bar.tsx`), both bottombars (`app.tsx` + `board-page.tsx`), the sidebar's inter-panel separators + Sessions-section top (`collapsible-panel.tsx` + `sidebar/index.tsx`), and the **waiting board-pane seam** (`border-[3px]` + `rk-waiting-seam`; a pulsing yellow attention border, static under reduced-motion — see § Attention Surfacing). The intent: seams read as deliberate structure, hairlines as content detail. (`260706-y1ar`)
- **8px selection accent** (`borderLeft: 8px solid`) — the contrast-guardrailed colored-row accent border (`computeRowBorders`; see § Contrast-guardrailed borders). The thickest tier — a selection/identity signal, not a structural seam. The **sidebar window row does not use it** (selection = 40% tint depth, active-board pin = accent glyph; § Row Anatomy); it is used on **server tiles** (stripe/edge).

### Theme Switching

Preference persisted to backend API (`PUT /api/settings/theme` → `~/.rk/settings.yaml`) with localStorage key `runkit-theme` as synchronous cache (values: any theme ID or `"system"`). On init, ThemeProvider calls `getThemePreference()` from API; falls back to localStorage / `"system"` if API fails. `setTheme` writes localStorage immediately and calls `setThemePreference(id)` fire-and-forget. Three switching surfaces: (1) command palette (`Cmd+K` → "Theme: System/Light/Dark", current indicated with "(current)" suffix), (2) the settings dialog's theme-pair row (§ Settings Dialog), and (3) the Theme Selector modal (opened by the chevron menu's "Theme…" App-section row dispatching `theme-selector:open`, or command palette "Theme: Select Theme" — the selector modal mounts in AppShell, so the event has a listener wherever the Shell renders).

### No-Flicker Initialization

A blocking inline `<script>` in `index.html` `<head>` reads `localStorage("runkit-theme")`, resolves system preference via `matchMedia`, and sets `data-theme` on `<html>` before first paint. Static fallback: `data-theme="dark"` on the `<html>` tag. The same script also seeds the `theme-color` meta from the echoed instance-accent hex (§ PWA Meta Tags & Theme Color / § Instance Accent).

### PWA Meta Tags & Theme Color

`app/frontend/index.html` includes PWA-related tags in `<head>`:
- `<meta name="theme-color" content="#0f1117" />` — initial value matching dark theme background
- `<meta name="apple-mobile-web-app-capable" content="yes" />` — enables standalone mode on iOS
- `<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />` — content renders behind the status bar
- `<link rel="apple-touch-icon" href="/generated-icons/icon-192.png" />` — homescreen icon for iOS
- `<link rel="manifest" href="/manifest.json" />` — a static link to the manifest route (the Go backend serves `/manifest.json` dynamically, accent-tinting the icon `src`s per instance — see § Instance Accent → PWA install identity and architecture.md § PWA Identity Assets)
- `<link rel="icon" type="image/svg+xml" href="/generated-icons/favicon.svg" />` — the tab favicon, likewise served dynamically and accent-tinted per request

**Theme-color synchronization**: The `theme-color` meta tag value is kept in sync via a **single shared writer** (`src/instance-accent.ts`, § Instance Accent) that resolves the content to the instance-accent hex when an accent is resolved, else the active theme background:
1. **Initial load** — the blocking inline script in `index.html` sets `theme-color` alongside `data-theme` before first paint; it first tries the echoed instance-accent hex from `runkit-instance-color` (validated `#rrggbb`), falling back to the per-mode default (`#0f1117` dark / `#f8f9fb` light) so an installed PWA window opens already tinted with no flash
2. **Runtime switch** — `applyThemeToDOM` in `ThemeProvider` calls `applyThemeColorMeta(theme.palette.background)` (NOT a direct `setAttribute`), and the `InstanceAccentProvider` calls `setAccentThemeColor(hex)`; both funnel through the one writer's module state so a theme switch cannot clobber the accent tint (§ Instance Accent → PWA titlebar bridge)

Theme color is per-theme (derived from `palette.background`) when no accent is set, else the accent's `titlebarHex` (the ~35% accent-into-background titlebar blend, § Instance Accent → Theme-derived hexes) — not a fixed dark/light pair.

**Icon set**: Canonical mark at `app/frontend/public/icon.svg` (grayscale hexagonal cube, transparent — its five gray fills are what the instance-accent tint replaces). Generated variants in `app/frontend/public/generated-icons/`:
- `favicon.svg` — copy of `icon.svg` (transparent, used as browser favicon)
- `icon-192.png` — 192x192, solid `#0f1117` background, ~20% padding (homescreen icon)
- `icon-512.png` — 512x512, solid `#0f1117` background, ~20% padding (splash screen)
- `icon-512-maskable.png` — 512x512, solid `#0f1117` background, ~40% padding (maskable, safe zone for adaptive icon shapes)

Generated by `scripts/generate-icons.sh` (Node + sharp). Run via `just icons`.

**Standalone display mode**: When installed via "Add to Home Screen" (Android or iOS), the app runs without browser chrome (no address bar, no toolbar). The `display: "standalone"` manifest property and `apple-mobile-web-app-capable` meta tag enable this on their respective platforms.

### ThemeProvider Context

`app/frontend/src/contexts/theme-context.tsx` — split context (ThemeStateContext + ThemeActionsContext) following ChromeContext pattern. Provides `useTheme()` (preference + resolved + theme object) and `useThemeActions()` (setTheme, previewTheme, cancelPreview). Listens to `matchMedia("(prefers-color-scheme: dark)")` change events when preference is "system" for real-time OS theme tracking. On init: calls `getThemePreference()` from API, falls back to localStorage / `"system"` if API fails (§ Theme Switching for the write path). `applyThemeToDOM` computes CSS values via `deriveUIColors(theme.palette, theme.category)` and writes the `theme-color` meta tag through the shared `applyThemeColorMeta(theme.palette.background)` writer (§ Instance Accent → PWA titlebar bridge — the instance accent wins over the bare background when resolved).

Provider order: `ThemeProvider > ToastProvider > InstanceAccentProvider > ChromeProvider > SessionProvider > AppShell` (`InstanceAccentProvider` inside the theme so it can read `useTheme()`; § Instance Accent).

### xterm Terminal Theme

`terminal-client.tsx` uses `useTheme()` to get the active `Theme` object. Initial theme set at Terminal construction via `deriveXtermTheme(activeTheme.palette)` — all 22 colors (background, foreground, cursor, cursorAccent, selectionBackground, selectionForeground, and 16 named ANSI colors). Live updates via `xtermRef.current.options.theme = deriveXtermTheme(theme.palette)` in a `useEffect` — no terminal recreation needed. There is no `XTERM_THEMES` constant.

### Hover-Animation Vocabulary

A site-wide motion map where each treatment encodes **exactly one** category of element, so motion carries meaning instead of noise. The shared color cue: **the animated element turns `--color-accent-green` while it animates** (the brand chip on glitch-hover, the boot-sweep cursor + name-churn cells, both caret variants, the stepping brackets — user-requested — including the glint: the sweep strip is accent-green-tinted and the hovered chip's border + glyph flip green for the hover duration, the "green line"). **Scope note**: the boot-sweep green is PER-CELL — only the single cursor cell and the unresolved name-churn glyphs are green; the heading container does NOT tint green wholesale, so resolved cells settle to their own rest color and the two-tone reveal reads left-to-right (`260704-pr0p`). All CSS utilities live in `globals.css` (beside the `logo-chase` keyframes / `coarse` variant; Tailwind CSS 4). Under `@media (prefers-reduced-motion: reduce)` the contract is **animations zeroed, not styling removed**: the CSS gate zeroes every keyframe animation (classes stay in the DOM — that is the test seam), the JS treatments (decode, typed sweep, brand logo sweep) skip themselves by reading the same media query — a JS treatment therefore has NO reduced-motion line in the CSS gate, and its rest state IS its reduced-motion state — and static hover styling (e.g. the glint's green border/glyph flip) remains — a color change is not motion. No pixel assertions in tests — treatments are asserted via class-presence + reduced-motion emulation, plus one behavioral guard for the caret (below).

### Logo Ring — `LogoSpinner` (`components/logo-spinner.tsx`)

The shared brand mark, used both as the app-wide loading spinner (~9 call sites: dialogs, pending split/close buttons, the UpdateChip, the sidebar SERVER-panel refresh slot, the window-switch mask, `ServerWaiting`) and — at rest — as the top-bar brand crumb's inline logo. Its geometry is two static arrays: six `BORDER_SEGMENTS` (the ring, indexed 0–5 clockwise) and three `INNER_FACES` (the cube, never animated). Each border segment carries a `staticFill` — the lit trio `{5, 0, 1}` is `#b4b4b4` (`LIT_FILL`), the dark trio `{2, 3, 4}` is `#2a2a2a` (`DARK_FILL`) — and those static fills are the **single source of truth for the rest pattern**: the hover sweep derives lit-trio membership from them (`staticFill === LIT_FILL`) rather than restating the index set. Segments are tagged `data-ring-segment={i}` so JS can select the ring without touching the sibling `INNER_FACES` polygons. Props: `size`, `loading` (default `true`), and `svgRef` (the seam that lets JS reach the segments — used only by the brand crumb).

**Loading chase — negative stagger, steady state from frame one.** Under `loading` every segment runs `logo-chase 1.2s ease-in-out ${i * 0.2 - 1.2}s infinite`. The delays are **negative** (−1.2s … −0.2s), which starts each segment mid-cycle so the established six-phase chase is on screen at the first rendered frame (§ Design Decisions → Chase stagger is negative). At rest (`loading={false}`) segments take their `staticFill` with an inline `transition: opacity 0.5s ease-out, fill 0.5s ease-out`.

### Brand Logo Hover Sweep (`sweepSegmentFill` + `useBrandLogoSweep`)

The brand crumb's ring treatment: a white glow blob **detaches** from the lit half, **orbits** the ring three laps decelerating over 900ms while the lit half dims, and **lands** centered on segment 0 — the lit trio's center — where it crossfades into the rest pattern. Motion is segment *illumination*, the same language as the loading chase, so the logo has one motion vocabulary across loading and hover; no geometry moves and there is no CSS rule for it (§ Design Decisions → Brand logo motion is state-based).

**Pure math — `sweepSegmentFill(i, p)`** (exported for unit tests) returns segment `i`'s fill at progress `p ∈ [0,1]`:

- Head position: ease-out cubic `ease = 1 − (1−p)³`, then `h = (ease · SWEEP_LAPS · 6) mod 6` — continuous/fractional, `SWEEP_LAPS = 3`.
- Settle envelope: `s = max(1 − smoothstep(p / 0.1), smoothstep((p − 0.78) / 0.22))` — `1` at both ends (rest pattern), `0` mid-flight (glow). `smoothstep(t) = clamp(t,0,1)² · (3 − 2·clamp(t,0,1))`; the constants are named `SWEEP_DETACH_END` / `SWEEP_LAND_START` / `SWEEP_LAND_SPAN`.
- Brightness: circular distance `d = min(|h − i|, 6 − |h − i|)`, `gauss = exp(−d² / (2·0.85²))` (`SWEEP_SIGMA = 0.85`), `rest_i = 1` for the lit trio else `0`, `B = gauss·(1−s) + rest_i·s`.
- Color: `bright = mix(WHITE, #b4b4b4, s)`, fill = `rgb(mix(#2a2a2a, bright, B))` — linear per-channel RGB interpolation, rounded. So the blob is **white** in flight and crossfades to the lit gray as it settles.

**Seamless at both ends.** The integer lap count parks `h` at exactly 0 when `p = 1`, and `s = 1` at both `p = 0` and `p = 1`, so those two frames compute to the literal rest fills — the landing and the rest state are the same event, with no restore snap. (`rest` at both ends is what makes an integer lap count a requirement, not a stylistic choice.)

**rAF driver — `useBrandLogoSweep()`** returns `{ svgRef, onMouseEnter }`; `top-bar.tsx` puts `svgRef` on the crumb's `<LogoSpinner size={20} loading={false}>` and `onMouseEnter` on the whole `.rk-brand-glitch` anchor (so the wordmark triggers it too, matching the glitch's scope — floating-ui's `getReferenceProps` composes the handler with `Tip`'s own rather than overwriting it). Per frame it walks `polygon[data-ring-segment]` and applies `sweepSegmentFill` via `setAttribute("fill", …)` — an attribute, matching how React renders the `fill` prop, so the completion restore leaves the DOM and React's recorded props consistent. Three behaviors the driver owns:

- **Re-trigger guard** — a `runningRef` flag; a mouseenter while a sweep is in flight is ignored outright (no restart, no queue).
- **Transition suspension** — the rest state's inline `transition: fill 0.5s` would smear the per-frame fills into crossfades and destroy the timing, so the driver captures each polygon's `style.transition`, sets it to `none` for the flight, and restores the captured values on landing.
- **Reduced motion** — `prefersReducedMotion()` (from `@/lib/motion`, the same helper `TypedLabel` reads) short-circuits `onMouseEnter` before any frame is scheduled; fills never change. The rest state IS the reduced-motion state, so there is nothing to gate in CSS.

On landing the driver parks the literal `staticFill` hex values and restores the transitions — a numerical safety net over an already-exact `p = 1` frame, not a corrective snap. Coverage is unit-level in `logo-spinner.test.tsx` (exact rest fills at `p = 0`/`p = 1`, mid-flight white glow near the head + dimmed lit trio, the negative per-segment delays, the guard, the reduced-motion skip, the completion restore) — animation frames are not asserted in e2e. (`260803-ufqr`)

### Theme System

> Full spec: [`docs/specs/themes.md`](../../specs/themes.md) — architecture, ANSI palette structure, tmux colour mapping, import script usage, persistence model.

Palette-based theme model: each theme defines a `ThemePalette` with 22 canonical terminal colors — `foreground`, `background`, `cursorColor`, `cursorText`, `selectionBackground`, `selectionForeground`, plus 16 ANSI colors (indices 0-15) as a fixed-length readonly tuple. The `Theme` type has shape `{ id, name, category, palette }` — no `colors` or `themeColor` properties; both are derived from the palette.

20 built-in themes (14 dark + 6 light) defined in `app/frontend/src/themes.ts` with canonical ANSI palettes sourced from iTerm2-Color-Schemes / official theme repos. Three consumers derive from the same palette:

1. **Web UI CSS** — `deriveUIColors(palette, category)` produces 8 `UIColors` keys (`bgPrimary`, `bgCard`, `bgInset`, `textPrimary`, `textSecondary`, `border`, `accent`, `accentGreen`). Derivation: `bgPrimary` = background, `bgCard` = lighten/darken background, `bgInset` = darken background, `textPrimary` = foreground, `textSecondary` = ansi[8] (bright black), `border` = blend(fg, bg, 0.25), `accent` = ansi[4] (blue), `accentGreen` = ansi[2] (green). Color utility helpers (`hexToRgb`, `rgbToHex`, `lightenHex`, `darkenHex`, `blendHex`) are module-private. CSS custom properties (`--color-bg-primary`, etc.) applied via inline styles on `document.documentElement.style` overriding `globals.css` fallbacks.
2. **xterm.js canvas** — `deriveXtermTheme(palette)` produces an xterm.js `ITheme` with all 22 colors mapped (background, foreground, cursor, cursorAccent, selectionBackground, selectionForeground, and 16 named ANSI colors black through brightWhite). Terminal content (syntax highlighting, colored prompts, git diff output) matches the selected theme.
3. **tmux chrome** — `configs/tmux/default.conf` uses ANSI `colour{N}` indices (colour0-colour15) instead of hardcoded hex. Because tmux renders its chrome as escape sequences that xterm.js interprets, changing the xterm.js ANSI palette automatically themes tmux status bar, pane borders, and pane-border-format. No runtime `tmux set -g` calls needed — the tmux.conf is static.

`data-theme` attribute set to theme's `category` ("dark" or "light") for CSS branching. Theme preferences persisted to both backend API (`GET/PUT /api/settings/theme` writing `~/.rk/settings.yaml`) and localStorage as synchronous cache. Three settings: `theme` (mode: `"system"` or specific ID), `theme_dark` (preferred dark theme, default `"default-dark"`), `theme_light` (preferred light theme, default `"default-light"`). localStorage keys: `runkit-theme`, `runkit-theme-dark`, `runkit-theme-light`. On init, API is canonical source; localStorage is the fast fallback if API fails. Unrecognized `theme` values fall back to `"system"`, while unrecognized `theme_dark`/`theme_light` values fall back to `"default-dark"`/`"default-light"`. PUT accepts partial updates (load-then-merge).

**Theme menu row** (chevron menu App section, § Right cluster → overflow chevron menu): the "Theme…" row dispatches the `"theme-selector:open"` CustomEvent to open the theme selector; its leading `ThemeModeIcon` (monitor / sun / moon) and trailing slot reflect the effective mode (`preference === "system" ? "system" : resolved`). There is no click-to-cycle surface — the selector, the palette's quick-switch actions, and the settings dialog's theme-pair row (§ Settings Dialog) are the theme-switch surfaces.

**Theme Selector** (`app/frontend/src/components/theme-selector.tsx`): Modal overlay matching CommandPalette structure (fixed z-50, backdrop, max-w-lg at 20vh). Search input filters by name (case-insensitive). Themes grouped under "Dark" / "Light" category headers. Arrow key navigation wraps and skips headers. Mouse hover and arrow navigation trigger live preview via `previewTheme()` — CSS custom properties update in real-time. Enter confirms (persists to API + localStorage), Escape/outside-click reverts to original theme via `cancelPreview()`. Opens via `"theme-selector:open"` custom event (same pattern as `"palette:open"`). Theme rows display multi-color palette swatches showing background plus representative ANSI colors (red, green, yellow, blue, magenta, cyan).

**Command palette**: "Theme: Select Theme" action dispatches `"theme-selector:open"`. Individual "Theme: System", "Theme: Light", "Theme: Dark" quick-switch actions are registered alongside it.

**ThemeProvider** (`app/frontend/src/contexts/theme-context.tsx`): `useTheme()` returns `{ preference, resolved, theme, themeDark, themeLight }`. `useThemeActions()` returns `{ setTheme, previewTheme, cancelPreview }`. Preview applies colors to DOM without persistence. Cancel reverts to the last persisted theme. Uses stable `actionsRef` pattern for callback identity. On init: calls `getThemePreference()` from API (returns `{ theme, themeDark, themeLight }`), falls back to localStorage / defaults if API fails. Per-mode theme resolution: in `"system"` mode, resolves to the user's preferred dark or light theme based on OS `prefers-color-scheme`, falling back to `DEFAULT_DARK_THEME` / `DEFAULT_LIGHT_THEME` if the stored ID is invalid. `setTheme` with a specific theme ID saves it to the matching per-mode slot (by `category`), keeps preference as `"system"` (preserving OS auto-toggle), and persists all three values to API and localStorage. `setTheme("system")` resets to system mode without changing per-mode prefs. Backend is canonical source of truth; localStorage is the fast fallback.

### Section Heading (`section-heading.tsx`)

### Color Tinting — Owned Palette + Axis Split

Session rows, window rows, and server tiles support an optional color assignment that applies a full-width background tint. The palette is an **owned set of 10 fixed OKLCH hue families adapted to the active theme**: each family has a stable hue angle, and hue identity survives theme switches (a window labeled "orange" reads orange on every theme). The row's visual channels are split so labeling and selection never collide: **hue = label**, **tint depth = selection**, **left-edge marker = an independent label axis** (§ Left-Edge Label Zone). On window rows both label axes (color + marker) are set from the single left-edge Label picker; session rows and server tiles keep a right-side color affordance and have no marker.

**Owned hue families** (`themes.ts` `HUE_FAMILIES`): 10 families in stable display order, each `{ name, hue, legacy, neutral? }`. Hue angles are placed non-uniformly — tight through the discriminable red→amber region, the large gap parked in teal→blue where human hue discrimination is weakest: red 25°, orange 55°, amber 90°, olive 120°, green 150°, teal 185°, blue 250°, purple 290°, magenta 330°, slate 250° (`neutral`). `FAMILY_BY_NAME` / `FAMILY_BY_LEGACY` are the two lookup maps.

**Two-shade axis (normal + dark), 20 picker values**: each of the 10 families spans a **normal** and a **dark** shade — a second color axis that doubles the label space for organizing many parallel windows. The shade is a **render-time lightness offset carried on `PickerColor` (`{ family, shade }`), not a parallel vocabulary of pseudo-families** — hue identity, legacy mapping, and theme adaptation stay properties of the 10 families, so dark variants derive for free with zero new palette data. `PICKER_COLOR_VALUES` is the 20 display values in **paired order** (`red, red-dark, orange, orange-dark, … slate, slate-dark`). `parseColorValue` / `formatColorValue` / `resolveFamily` / `colorValueToHex` accept the `-dark`-suffixed names; `formatColorValue` emits `"{family}-dark"` for dark shades.

**Theme adaptation (full adoption) + dark derivation**: `themeColorStats(palette) → { L, C }` computes the mean OKLab lightness and mean chroma over `palette.ansi[1..6]`, with a chroma floor `THEME_CHROMA_FLOOR = 0.05` (near-monochrome themes stay distinguishable). A family's **normal** source hex = `oklchToHexInGamut(L_theme, C_theme, family.hue)` (slate uses a near-neutral chroma `min(C_theme × 0.2, 0.025)`); its **dark** source hex renders at `L_dark = L_theme − 0.14` with the **same hue and same chroma** (slate keeps its near-neutral chroma rule — an intentional gray ramp), gamut-reduced via the same `oklchToHexInGamut`. The normal shade IS the mean-L rendering, so **every stored value without a `-dark` suffix resolves to the normal shade**. `colorValueToHex(value, palette)` resolves any stored value (family name, `-dark` suffix, OR legacy alias) to its adopted hex, returning `null` when it maps to no family.

**OKLCH → in-gamut hex, chroma-reduction not channel-clamp**: `oklchToHex(L, C, hueDeg)` converts polar chroma/hue to OKLab (`a = C·cos h`, `b = C·sin h`) then reuses `oklabToHex`. `oklchInGamut(L, C, hueDeg)` reports whether the triple maps inside sRGB without any channel being clamped, reusing the shared `oklabToLinearRgb(c)` matrix helper (extracted so its 18 coefficients stay in lockstep with `oklabToHex` — both consume it). `oklchToHexInGamut(L, C, hueDeg)` brings an out-of-gamut triple in by **reducing chroma stepwise** (`GAMUT_REDUCE_FACTOR = 0.92`, `GAMUT_REDUCE_MAX_STEPS = 20`) — L and hue are preserved; sRGB channel-clamping is never used because it shifts hue and would defeat the stable-hue goal.

**Storage vocabulary — three coexisting forms, zero migration**: a color value is stored as one of (a) a **legacy numeric/blend descriptor** (`"4"` / `"1+3"`) — the form pre-existing colored rows carry, valid forever on read and write; (b) a plain **family name** (`"blue"`); or (c) a **`-dark` family-name value** (`"blue-dark"`) — the only form for dark shades, which have no legacy equivalent. The normal-shade 1:1 legacy map: red←`1`, orange←`1+3`, amber←`3`, olive←`1+2`, green←`2`, teal←`6`, blue←`4`, purple←`1+4`, magenta←`5`, slate←`3+4`. `resolveFamily(value)` accepts a family name, a `-dark` suffix, OR a legacy descriptor (legacy normalized via the file-private `normalizeLegacy`, mirroring the backend `NormalizeColorValue` rule) and returns the same family for all shades/forms. **Write seam** — `familyToLegacy(name)` maps a **normal**-shade pick to its legacy descriptor (zero migration — stored values are never rewritten), while **dark** picks have no legacy form and pass through unchanged, written verbatim as `"{family}-dark"`; the helper is idempotent — an already-legacy, `-dark`, or unrecognized input passes through unchanged.

**Pre-blended row tints, multi-keyed for all 20 values**: `computeRowTints(palette) → Map<string, RowTint>` pre-computes the three blended state hexes for every shade of every family, keyed under **every stored vocabulary form** — a normal shade under BOTH its family name AND its legacy descriptor (both point at the *same* entry), a dark shade under its `"{family}-dark"` key (no legacy form exists) — plus the `"8"` uncolored-selected sentinel (10×2 normal keys + 10 dark keys + sentinel = 31 entries). All forms are keyed because consumers (`window-row`/`session-row`/`server-panel`) look up the RAW stored value and the backend emits legacy forms for pre-existing rows, so a family-name-only map would miss every legacy-stored row. Each shade's adopted source hex (`colorValueToHex`, dark included) is saturated ×1.5 (`TINT_SATURATE_FACTOR`) before blending into the theme background at three ratios:

| State | Constant | Saturated-source ratio |
|-------|----------|------------------------|
| Base | `TINT_BASE_RATIO` | 14% |
| Hover | `TINT_HOVER_RATIO` | 22% |
| Selected | `TINT_SELECTED_RATIO` | 40% |

Selection is carried by tint **depth** alone (no left border — § Row Anatomy), so the selected ratio is 40%. The uncolored-selected gray sentinel (`"8"`, `UNCOLORED_SELECTED_ANSI`/`UNCOLORED_SELECTED_KEY`) is NOT saturated (gray is near-zero chroma) and uses the deeper `UNCOLORED_SELECTED_RATIO = 0.5` so it beats the `bg-card/50` hover. Each state gets its own concrete hex — no stacked transparent layers. The `RowTint` type (`{ base, hover, selected }`) is exported. Hover is applied imperatively via `onMouseEnter`/`onMouseLeave` style mutations to avoid CSS-specificity issues with dynamic backgrounds.

**Contrast-guardrailed borders** (`computeRowBorders(palette, category) → Map<string, string>`): each shade's adopted source hex passed through a WCAG contrast guardrail, multi-keyed (family name + legacy descriptor for normal shades, `"{family}-dark"` for dark shades, + `"8"` sentinel — 31 entries) exactly like `computeRowTints`. `adjustBorderForContrast(border, bg, isDark, BORDER_MIN_CONTRAST)` nudges **only the OKLab lightness L** (lighten on dark themes, darken on light) in `0.03` steps until the border clears `BORDER_MIN_CONTRAST = 3.0` against the background or hits a 24-step cap; **hue and chroma are preserved** so the color keeps its identity. Window rows do not use these for a selection border; **server tiles** use them for their stripe/edge, **the left-edge marker stripe uses them as its guarded family color** (`markerColor`, § Left-Edge Label Zone), and **the Label picker's marker preview cells use them as the guarded stripe color of the live row preview** (§ Variant-C paired-grid Label picker). `sidebar/index.tsx` computes `rowTints` + `rowBorders` once per theme via `useMemo` and threads them to `WindowRow`/`ServerPanel`.

**OKLab + WCAG color-math helpers** (`themes.ts`): `hexToOklab` / `oklabToHex` (Björn Ottosson 2020 coefficients; `oklabToHex` and `oklchInGamut` share the `oklabToLinearRgb` matrix helper), the sRGB↔linear `srgbToLinear` gamma step, `relativeLuminance` (WCAG 2.x) and `contrastRatio(hex1, hex2)` (1..21), and `adjustBorderForContrast`. OKLab is the chosen lightness/distinctness space; WCAG is the separate legibility standard.

**SwatchPopover** (`app/frontend/src/components/swatch-popover.tsx`): one shared component, **one universal square style** — no rounded variant, no `square` prop. The color section renders the **20 paired values** from `PICKER_COLOR_VALUES` laid out 4-wide (5 color rows, `normal | dark` adjacent) plus the removal row: `Clear` (cols 1–3) beside the ✕ close cell (col 4). Props are STRINGS: `selectedColor?: string`, `onSelect(color | null)`, `onClose()`, plus the marker extension `selectedMarker?`, `onSelectMarker?(marker)`. **Color write seam** — every color emit funnels through `familyToLegacy` (the file-private `emit` callback: `onSelect(familyToLegacy(value))`): a **normal**-shade pick is stored as its legacy descriptor (`"orange"` → `"1+3"`, zero migration), a **dark** pick passes through verbatim as `"{family}-dark"` (no legacy form exists), and `null` (Clear) passes through untouched — the backend accepts all three vocabularies (see architecture.md § validate closed sets), so no write 400s. **Uniform solid swatches**: each swatch is a single 18×18px solid fill = the value's `computeRowTints` `selected` tint (falling back to `colorValueToHex` then `theme.palette.foreground`), with a ✓ glyph + bright ring on the selected swatch so the selection is unambiguous between the two adjacent same-family shades. Selection is `-dark`-aware — matched by the picked value's `{family, shade}` (via `parseColorValue`), so a legacy-stored value highlights the right family's normal shade. The listbox **autofocuses on mount** (`containerRef.current?.focus()` in a mount effect, mirroring pin-popover) so arrow-key nav works immediately after the `Window: Label` palette action — the sole keyboard path to the marker section. **Dismissal contract**: selection NEVER dismisses (live combo toggling); the popover closes only via its ✕ cell, an outside click, or Escape — callers pass pure write handlers and close only from `onClose`.

**Universal square style**: every caller gets the same vocabulary — zero border radius on the container and all cells (no `rounded-md`/`rounded-sm`), a hard offset block shadow `3px 3px 0 rgba(0,0,0,.35)` (not `shadow-lg`), 3px gaps (`gap-[3px]`), 18px cells (`w-[18px] h-[18px]`), and 1px selection/focus outlines (`ring-1 ring-text-secondary`). There is a single style literal per axis — no dual class-string branches, no `SQUARE_GRID_COLS`/`DEFAULT_GRID_COLS` split. Session/server rows and the palette color actions render square like the window-row picker.

**Variant-C paired-grid Label picker**: when `onSelectMarker` is supplied (`showMarkers`), the popover renders two side-by-side sections divided by a **vertical hairline** (`w-px bg-border mx-1.5 self-stretch`) — markers LEFT (a 1-column `flex flex-col gap-[3px]` of 6 cells), colors RIGHT (the 20-swatch 4-wide paired grid). The layout pairs the two axes row-for-row:

```
∅   │  [   Clear   ]  ✕          ← row 0: removal row + close cell
∷   │  red  red-dk  or  or-dk    ← row 1: dotted  + colors 1–4
┆   │  am   am-dk   ol  ol-dk    ← row 2: dashed  + colors 5–8
▐   │  gr   gr-dk   te  te-dk    ← row 3: solid   + colors 9–12
▐▓  │  bl   bl-dk   pu  pu-dk    ← row 4: double  + colors 13–16
▐█  │  ma   ma-dk   sl  sl-dk    ← row 5: thick   + colors 17–20
```

- **Row 0 is the removal row**: the `∅` no-marker cell (marker column) beside a `Clear` button spanning color columns 1–3 (`col-span-3`) and the **✕ close cell** in column 4 (`aria-label="Close picker"`, an 18px `role=option` cell that is never `aria-selected` — an option-as-command matching Clear's pattern, keeping the `role=listbox` container's children ARIA-valid per Copilot's #452 review).
- **Dismissal contract — selection never closes**: picking a color, a marker, or Clear leaves the popover OPEN so color + marker combos can be toggled and compared live against the row; it dismisses only via the ✕ cell, an outside click, or Escape. Closing on select is the component's contract, not the callers' — every call site (window-row Label picker, session/server rows, HOST panel, settings dialog, the palette Set Color overlay) passes a pure write handler and closes only from `onClose`.
- **Rows 1–5** pair the dotted / dashed / solid / double / thick marker cells with the 5 color rows (each `normal | dark` adjacent — row 1: red, red-dark, orange, orange-dark; …).
- **Marker cells are live row previews of the selected color** — each non-∅ cell renders as a miniature window row for the currently selected color: background = that value's `tint.base` (gray sentinel when uncolored), the stripe via the shared `markerStripeStyle` helper in the **guarded border color** with a **2px left inset** (so the marker doesn't kiss the cell edge and the cell reads as a mini row), plus the paired row texture — the static `.rk-hazard` wedge on the thick cell and the static `.rk-scanlines` wash on the double cell (with per-cell `--rk-marker-color`), reusing the row classes so the texture vocabulary lives in one place. Picking a different swatch **repaints the marker column immediately**. The empty ∅ cell shows a glyph; the current state carries `aria-selected` + a selection ring. Selecting a cell calls `onSelectMarker` **directly with the exact state** (no cycling — any state is one click; `""` clears).
- **Preview cells NEVER animate** — an explicit user decision that motion belongs to real rows only: no scanline crawl even when the double cell is selected, the hazard wedge is static as always, and the dashed preview never carries the data-rain overlay. No cell ever carries `rk-scanlines-crawl` or `rk-dash-rain`.
- Marker cell order mirrors `MARKER_STATES` (`["", "dotted", "dashed", "solid", "double", "thick"]`) via `MARKER_CELLS` — `∅` in row 0, the five non-empty states beside the five color rows.
- **One-period stripe tiles make the previews correct**: the marker cells are 18px tall, so the fixed one-period `markerStripeStyle` tiles (§ Left-Edge Label Zone) are what let the dotted/dashed rhythm render correctly inside them — an element-height-dependent tile does not survive at that size.
- **Documented 1:1 invariant**: the marker-cell ↔ grid-row pairing is a deliberate `GRID_ROWS === MARKER_CELLS.length` invariant (6 marker cells ↔ 6 grid rows: 5 color rows of 20 swatches 4-wide + the Clear row), documented as such in a code comment. The 20-swatch grid and the 6-cell marker set are sized to pair exactly — the two extensions fix each other's layout, leaving no dead cells.

**Color-only callers get the same paired grid, marker-less**: with the marker props absent (`onSelectMarker` undefined) the left marker column and vertical hairline are simply not rendered — the color section stands alone with its `Clear` + ✕ removal row over the 20 paired swatches (5 rows of 4). Same square style; no separate layout branch.

**Keyboard navigation — conceptual 5-column × 6-row grid, no dead cells**: focus is a `{row, col}` `GridPos` pair (not a linear item index). `col` 0 = the marker column (valid only when `showMarkers`), cols 1–4 = the color columns; `row` 0 = the removal row, rows 1–5 = the five color rows. The 20 colors fill the 5×4 color region exactly, so there are **no dead cells** to clamp around. ArrowLeft/ArrowRight cross the hairline (col 1 ↔ col 0) and step within the color columns; ArrowUp/ArrowDown move within a column. The `Clear color` button is a **single spanning focus target** occupying cols 1–4 of row 0 (canonicalized to col 1; `focusOnClear = row === 0 && col >= 1`). Off-grid moves clamp to the nearest valid cell; focus stays valid, no crash. Enter/Space activates the focused cell (`activate`): col 0 → `onSelectMarker(MARKER_CELLS[row])`, row 0 → `emit(null)` (Clear), else → `emit(PICKER_COLOR_VALUES[colorIndexAt])`. **Initial focus FOLLOWS SELECTION**: the selected color swatch, or the `Clear color` cell (row 0 — already `aria-selected` in that state) when uncolored, never an arbitrary swatch; the marker column is reached via ArrowLeft. **Focus-visible semantics**: the focus ring (`ring-text-secondary`, visually quieter than the `ring-text-primary` selection ring) renders only after the first arrow key (`keyboardActive` flag) — the listbox autofocuses on mount, so an always-on ring showed mouse users a phantom highlight. The selected item is marked with the brighter `ring-text-primary` (colors additionally show a ✓; the uncolored state rings `Clear color`). Color-only mode is the same grid minus column 0.

**Window-row left-edge trigger**: the combined Label picker opens from the window row's left-edge label zone (§ Left-Edge Label Zone) or the `Window: Label` palette action — it is not a right-edge hover indicator. Session rows and server tiles still surface their color picker via a right-edge hover palette icon (visible on hover on desktop, always on touch via `coarse:opacity-100`).

**Command palette actions**: "Session: Set Color" opens the color-only SwatchPopover. The window **label** action is `window-label` / `Window: Label`, which dispatches an imperative `label-popover:open` CustomEvent (`{ detail: { server, windowId } }`) for the current window — the matching `WindowRow` listens and opens its combined picker (mirroring the `pin-popover:open` pattern used by "Board: Pin Current Window") to set both color and marker in one picker. The color-only `window-set-color` / `Window: Set Color` action (which opens the color-only SwatchPopover via `setShowColorPicker("window")`) is a separate registered action. Every color write path flows through the `familyToLegacy` write seam (normal picks → legacy descriptor, dark picks → `"{family}-dark"` verbatim); "Clear color" sends `null`, and clearing the marker sends `null` through `setWindowMarker`.

**Storage**: a stored color value is a **legacy descriptor** (`"4"` / `"1+3"`, the form pre-existing rows keep), a plain **family name** (`"blue"`), or a **`-dark` family-name value** (`"blue-dark"`, the only dark-shade form) — all three valid on read and write. ### Instance Accent ("host color")

A per-instance accent color makes multiple run-kit instances (laptop, Mac mini, GCP server) viewed as visually-identical installed Chrome PWA windows tell each other apart at a glance. It is an **axis orthogonal to the owned-palette color tinting above**: server/window/session colors saturate the sidebar and mean "which tmux server"; the instance accent means "which run-kit instance" and owns surfaces the sidebar colors never touch (the top bar and the HOST panel). The accent is a property of the **instance**, not the viewer — stored authoritatively on the instance's host (`~/.rk/settings.yaml` `instance_color`, see architecture.md § `internal/settings` and § `/api/settings/instance-color`), so every device viewing that instance sees the same accent. (`260721-1etw-instance-accent-host-color`)

**Resolution chain** (frontend, in the `InstanceAccentProvider`): (1) the explicit `instance_color` setting from `getInstanceColor()` — authoritative; (2) the localStorage echo (`runkit-instance-color`) — a **paint cache only, never authoritative**, used as the first-frame seed before the fetch lands; (3) **none** — there is **no derived default**: a fresh instance renders no accent until the user picks one (§ Design Decisions → No derived default accent). An `authoritative` flag (the explicit fetch resolved) gates clearing the echo/meta on a null accent, so the paint seed is never wiped before the real resolution replaces it.

**Provider + consumers** — `InstanceAccentProvider` / `useInstanceAccent()` (`contexts/instance-accent-context.tsx`) mounts once in `RootWrapper` inside `ThemeProvider` > `ToastProvider` and above `ChromeProvider`, so it can read `useTheme()` for the theme-derived hexes and `useToast()` for the write-failure toast. It fetches `getInstanceColor()` + `getHealth()` once on mount (StrictMode-guarded via a `didFetchRef`), seeds the first paint from the echo, resolves per the chain, derives `{stripeHex, washHex, titlebarHex}` from the active theme, keeps the echo + theme-color meta in sync on every accent/theme change, and exposes all three on the context value (`{color, isExplicit, stripeHex, washHex, titlebarHex, setColor}`). `titlebarHex` is nullable like its siblings and has two consumers: the theme-color meta bridge effect, and the desktop shell's titlebar strip, which renders from it directly rather than re-deriving the same blend (§ Desktop-Shell Titlebar Strip). `setColor(descriptor | null)` updates state optimistically then POSTs via `setInstanceColor`, toasting on failure. Every rendering surface reads from this ONE instance — one fetch, one state, so a pick in the HOST panel repaints the top-bar stripe without a reload. A test seam `InstanceAccentValueProvider` injects a fixed value (mirroring the session-context value-injection pattern).

**Theme-derived hexes** (`deriveAccentHexes(value, theme)` in `src/instance-accent.ts`, never hardcoded) — a three-hex split, each a distinct accent surface: `stripeHex` is the **contrast-guarded** family hex — `colorValueToHex(value, palette)` then `adjustBorderForContrast(src, bg, isDark, BORDER_MIN_CONTRAST)` (the same guarded-hex derivation server tiles/stripes use, § Color Tinting) — used for the 2px top-bar stripe and the HOST hostname tint, and, in-shell, reported over `accent:set` by the render-nothing `ShellAccentReporter` (`components/shell-accent-reporter.tsx`, mounted beside the badge reporter behind `isShell()`, ref-guarded change-only reporting, null never reported) so the shell persists the full-strength value for the host-switcher's edge bars rather than the meta's 35% blend. `washHex` is a subtle `blendHex(src, bg, INSTANCE_WASH_RATIO = 0.065)` (~6.5%) accent-into-background blend for the top-bar background wash. `titlebarHex` is the strongest of the three — `blendHex(src, bg, INSTANCE_TITLEBAR_RATIO = 0.35)` (~35%) accent-into-background — and paints **every titlebar-class surface**: the theme-color meta content (the installed-PWA titlebar tint) and the desktop shell's page-drawn titlebar strip, in both cases a tinted band with the full-brightness `stripeHex` 2px stripe visible directly below it. `INSTANCE_TITLEBAR_RATIO` sits beside `INSTANCE_WASH_RATIO` (a taste constant). Blend descriptors (`"1+3"`) render through the same `resolveFamily`-based owned-family mapping as single indices — no new blend scheme. All three recompute on a theme switch (light themes get a light-background blend by construction); nothing hardcoded survives. An unrecognized descriptor yields `null` (no partial object).

**Top-bar stripe + wash** (`AppLayout`, `app.tsx`) — the persistent top bar's `shrink-0` wrapper (above `RootTopBar`) carries a 2px accent stripe (an `aria-hidden` `<div style={{height:"2px", backgroundColor: stripeHex}}>`) plus the `washHex` as its `backgroundColor` (the `TopBar` header has no background of its own, so the wash on the wrapper shows through). Both render only when their hex is non-null (no accent resolved ⇒ neither renders). This is the "which instance" channel living where the sidebar colors do not.

**HOST panel — accent hostname tint + swatch picker** (`components/sidebar/host-panel.tsx`) — the hostname in the panel's `headerRight` slot renders in `stripeHex` (the contrast-guarded accent) when resolved, else the default `text-text-primary`. A palette swatch button rides the `CollapsiblePanel` **`titleAction` slot** (immediately right of the HOST title — a sibling of the toggle button, since a nested button would be invalid markup; with `titleAction` set the header splits into `[toggle: chevron+title][titleAction][toggle click-region: headerRight]`, the trailing region keeping mouse click-to-toggle while keyboard toggling stays on the title button), hover-revealed with the touch/keyboard fallbacks `opacity-0 group-hover/panel:opacity-100 coarse:opacity-100 focus-visible:opacity-100` (`CollapsiblePanel`'s header gained a `group/panel` class to drive it) and an `aria-label="Set instance color"`. Clicking it opens a **color-only** `SwatchPopover` (no `onSelectMarker`) portalled to `document.body` at fixed coordinates anchored at the button — left-aligned (the button sits beside the title at the sidebar's left edge), with a **flip-above** `useLayoutEffect` heuristic (the HOST panel sits at the sidebar bottom, so flip-above is the norm) — escaping the panel's overflow clip. This is the x4sf ServerGroup-header picker precedent (§ Server-group header action cluster). A pick calls `useInstanceAccent().setColor` (which POSTs and repaints every surface); `Clear color` sends `null`, removing the accent entirely (the no-color default). The HOST header carries **no connection dot**: the top-bar dot already reflects the same current-server subscription health (`setChromeConnected(slice.isConnected)` in session-context).

**PWA titlebar bridge — single theme-color meta writer** (`src/instance-accent.ts`) — the `<meta name="theme-color">` tag is accent-aware through ONE shared writer holding module-level state (`currentAccentHex` + `lastBackground`, content = accent hex when set, else the theme background): (a) the blocking pre-paint script in `index.html` (§ PWA Meta Tags & Theme Color) reads the echoed `hex` from `runkit-instance-color`, validates the `#rrggbb` shape, and applies it **verbatim** as the initial theme-color (falling back to the per-mode defaults) so an installed PWA window opens already tinted with no flash; (b) at runtime the provider calls `setAccentThemeColor(titlebarHex)` (the ~35% titlebar blend, NOT `stripeHex`) on accent/theme change, and writes the same `titlebarHex` into the echo's `hex` field — so cold start and runtime both paint the subtle tinted titlebar, and the full-brightness `stripeHex` 2px stripe stays visible directly below it; (c) `theme-context.tsx`'s `applyThemeToDOM` calls `applyThemeColorMeta(theme.palette.background)` instead of writing the meta directly, so a theme switch cannot clobber the accent tint. Desktop Chrome retints installed-PWA titlebars live on meta changes, and the **Electron shell listens to the same meta** — `did-change-theme-color` is what repaints its Windows/Linux window-controls overlay, so the one writer serves both hosts with no shell-specific color API ([desktop-shell](/run-kit/desktop-shell.md) § Hidden Titlebar & Accent Strip). The pre-paint script applies the echoed `hex` verbatim, so swapping the echoed value retints cold start for free; a stale echoed hex self-corrects when the runtime resolution rewrites both meta and echo — the same accepted self-correcting transient class as cross-mode loads.

**PWA install identity — Dock/Cmd-Tab icon + tab favicon** — the instance accent also tints the installed PWA's OS-level identity, so multiple instances are distinguishable in the Dock and Cmd-Tab, not only inside the window (`260722-eo8e-accent-dock-icon`). This is a **backend** concern: the Go server serves `/manifest.json`, the three `/generated-icons/icon-*.png`, and `/generated-icons/favicon.svg` dynamically, tinting the grayscale logo per the instance's `instance_color` (see architecture.md § PWA Identity Assets). No frontend component changes — `index.html`'s static `<link rel="manifest">` / `rel=icon` / `apple-touch-icon` hrefs are unchanged; the tint enters through the responses. Two behaviors matter to the UI surface:
- **Cache-bust contract**: the dynamic manifest appends `?c=<descriptor>` to each icon `src` (`+` encoded `%2B`) when an accent is owned; the icon PNG routes tint only on that owned `?c=`, serving stock bytes otherwise. The favicon route carries no `?c=` (its href is static) and resolves the tint from settings per request with `Cache-Control: no-cache`, so open browser tabs re-tint on their next load.
- **Chrome icon-refresh limitation** (accepted, documented — not engineered around): Chrome snapshots PWA icons at install and re-checks the manifest only on app launch with ~daily throttling, so an accent picked **before** install is immediate while a change **after** install updates the Dock icon eventually (reinstall forces it). The top-bar stripe/wash and PWA titlebar theme-color stay live regardless.

### Easter Egg — Double-Marker Scanlines (`globals.css` `.rk-scanlines`)

**Static scanlines**: `.rk-scanlines::before` paints a `repeating-linear-gradient(to bottom, {marker color}@24% 0 1px, transparent 1px 3px)` reading the family color from the `--rk-marker-color` custom property (set on the row when `double`). The overlay sits above the tint/button background (`z-5`), below the `z-10` icon cluster and `z-20` gutter. Pure static CSS — it does not touch the status pyramid's animation channel (the waiting halo stays unambiguous).

**Selected + double retro animation**: when a double-marker row is ALSO selected, the class `rk-scanlines-crawl` is added, animating a slow downward crawl of the gradient period (`@keyframes rk-scanline-crawl`, `background-position-y` 0 → 3px, 2.4s linear infinite) plus an occasional CRT refresh band — a soft ~12px gradient band in the marker color rolling top→bottom via `::after` (`@keyframes rk-scanline-band`, 7s cycle with a rest phase then a ~2.8s sweep, `pointer-events: none`). Static again when deselected. **Both animations move `background-position-y`, never `transform`** — an animated translateY range grows the compositor layer beyond the row box (ancestor clips ignored), and the HTML5 drag-ghost snapshot of a selected+double row then carries a sliver of the neighboring row along with it; a background sweep cannot paint outside the element's own box. The band is a `no-repeat` `background-size: 100% 12px` gradient on an `inset-0` `::after`, parked at `background-position-y: -12px` (outside the box paints nothing) and swept to `calc(100% + 12px)` (band top at box bottom — fully exited).

**Reduced motion**: inside the existing `@media (prefers-reduced-motion: reduce)` block, `.rk-scanlines-crawl::before { animation: none }` and `.rk-scanlines-crawl::after { animation: none; display: none }` — the crawl and band are fully zeroed (static scanlines only, band hidden). The base rules PRECEDE the reduced-motion block so its equal-specificity overrides win by source order, mirroring the `rk-waiting-halo`/`rk-waiting-seam` discipline.

### Character Flair Overlays (`globals.css` `.rk-flair-nyan` / `.rk-flair-naruto` / `.rk-flair-onepiece`)

A row carrying a **flair** (the per-row opt-in decorative channel — `""`/`nyan`/`naruto`/`onepiece`, `FLAIR_STATES` in `themes.ts`; see [sidebar](/run-kit/ui/sidebar.md) § Row Flair) gets an always-on ambient character animation across its full width, on window rows and session rows (server group headers carry none — they mirror the flair-free SERVER-pane tiles). Flair is decoration only — no wiring to `@rk_agent_state` or the status pyramid. (`260814-2esh`)

**The three treatments** (all sprites are original stylized art embedded as inline SVG data URIs — no external requests, no copyrighted assets):

The treatments are FRAME-ANIMATED sprite sheets, not static sprites: each character is a vertical SVG sheet of 22px-tall frames (frame n at y = −22n) on a fixed 22px strip pseudo (static top/margin centering, so the px frame offsets hold at every row height — 24px rows, 36px coarse rows, 18px picker preview cells). The two `background-position` LONGHANDS animate independently and compose: `-x` carries the slow linear traversal, `-y` steps the sheet with `step-end` keyframes at classic low-fps sprite cadence. WebGL was considered and rejected — browsers cap live WebGL contexts per page (~8–16), and every flaired row would need one.

- **`.rk-flair-nyan`** — the pop-tart cat: a 36×88 4-frame sheet (leg-shuffle A/B, tail wag up/down, 1px body bob, ~6.7fps) plus a 140px rainbow comet-trail layer (6 full-saturation stripes, left edge faded through an SVG mask) glued to the cat and jiggled ±1px at frame cadence on the same pseudo; `::before` is a parallax starfield (80px 2-frame twinkling tile drifting the OPPOSITE way, one tile per loop). ~9s traversal (`rk-flair-nyan-x`/`-y`, `-stars-x`/`-stars-y`).
- **`.rk-flair-naruto`** — an orange-clad runner in the arms-back naruto-run lean: a 32×88 4-frame sheet (stride/tuck/mid-stride leg cycle, fluttering headband ribbon, 1px bob, ~8fps) plus a 120×44 2-frame trail (drifting leaves, dust puffs, speed lines) on the same pseudo; `::before` is a faint 48px speed-streak tile racing the opposite way. ~6s traversal (`rk-flair-naruto-x`/`-y`, `-streaks`).
- **`.rk-flair-onepiece`** — a pirate ship under sail: a 34×88 4-frame sheet (sail billow A/B, fluttering black flag with the straw-hat-over-skull emblem, ±1.4° hull roll via per-frame SVG rotate, 1px bob, stern wake dashes, ~2.5fps) on a bottom-anchored strip; `::before` is TWO scallop-wave tiles (16px and 24px periods) drifting the opposite way at different speeds — parallax swell, displaced by exact tile multiples per loop. ~14s traversal (`rk-flair-onepiece-x`/`-y`, `-waves`).

**CSS discipline — the `.rk-dash-rain` rules applied**: each treatment animates `background-position` only (never layout-affecting properties, never transform) on `::before`/`::after` pseudos of the dedicated overlay element (overlay-owns-clip, `pointer-events-none` — never `overflow-hidden` on the row root, the `.rk-scanlines` rule). Sprite and trail live as two `no-repeat` background layers on ONE pseudo; the traversal keyframes balance each layer's from/to constants (start offset − image width + end offset equal across layers) so both displace by identical px and never separate; traversal runs from a negative offset to a `calc(100% + Npx)` off-right position, so the loop boundary happens fully off-screen. Trails and ambience carry low alphas; the sprites are near-opaque but small, and row text paints above the z-5 overlay, so rows stay readable. **Picker flair section**: the Label/color picker's flair cells (∅ / nyan / naruto / onepiece) are LIVE previews — each non-∅ cell is a miniature row carrying its always-on animated `.rk-flair-*` overlay (the dashed marker cell's live-rain precedent), unlike the marker preview cells, which never animate.

**Reduced motion**: flair is motion-only decoration carrying no semantic meaning, so under `prefers-reduced-motion` all three overlays are hidden ENTIRELY (`animation: none; display: none` on every flair pseudo in the existing gate block) — no static fallback, unlike the marker stripes which remain. Source-order rule: the base rules PRECEDE the reduced-motion block so its equal-specificity overrides win by source order (the `.rk-dash-rain` discipline).

## Mobile Responsive

### Breakpoints & Container Width

All zones use `px-3 sm:px-6` — reduced horizontal padding on screens < 640px. No `max-w-4xl` constraint — terminal, top bar, and bottom bar all span full width. The mobile/desktop breakpoint for the `<Shell>` topology is **640px** (matches the existing `sm:` Tailwind breakpoint and `useIsMobile()` hook): `>= 640px` uses the 2-column grid with sidebar full-height; `< 640px` uses the single-column grid with sidebar overlay. Sidebar is drag-resizable on desktop (default 220px, min 160, max 400); terminal fills remaining space via the right grid column. Terminal container has `py-0.5 px-1` padding for breathing room against border lines. The bottom-bar toolbar row uses `pt-1.5` with a `--bottom-bar-floor`-driven bottom arm — 6px, raised to 1rem on coarse pointers while the keyboard is collapsed (§ Safe-Area Insets).

### Touch Targets

A custom Tailwind variant `coarse:` is defined in `globals.css` via `@custom-variant coarse (@media (pointer: coarse))`. On touch devices, interactive elements are upsized per surface — `coarse:` is the mechanism, not a universal size (there is no single 44px minimum; each surface documents its own target). Upsized elements include:
- Top-bar icon controls — the shared fixed-size token's `coarse:w-[30px] coarse:h-[30px]` arm (`TOP_BAR_BUTTON*`, § Right cluster → shared button-size token); content-width chips/segments share the height axis via `TOP_BAR_BUTTON_H` / `TOP_BAR_SEGMENT_H`
- Sidebar session/window row action buttons — `coarse:min-w-[32px] coarse:min-h-[36px]`, both axes (§ Sidebar Row Icon System explains why 32 and not 36 on the width axis)
- Breadcrumb name dropdown triggers
- `⋯` command palette trigger
- Hamburger icon (sidebar toggle — single state covers desktop column collapse and mobile overlay) (`260509-17m3`)

**Both axes or neither.** An icon-only control needs `coarse:min-w-*` as well as `coarse:min-h-*`: a bare glyph has no horizontal padding to grow into, so a `min-h`-only rule yields a tall-but-thin target that measures ~17px wide on touch. Wider padded chips (text buttons) can get away with `min-h` alone.

Bottom bar buttons use the full `coarse:min-h-[36px] coarse:min-w-[36px]` touch target on touch devices, `min-h-[33px] min-w-[35px]` on fine pointers (with a 6px fine / 4px coarse row gap). The row's own bottom padding also lifts on coarse pointers — via the `--bottom-bar-floor` custom property rather than a `coarse:` utility class, because the lift is additionally gated on the keyboard being collapsed (§ Safe-Area Insets).

### Viewport Zoom Prevention

The viewport meta tag in `app/frontend/index.html` includes `maximum-scale=1.0` and `user-scalable=no` to prevent iOS Safari from auto-zooming when text inputs (command palette, docked compose strip) receive focus. Without these directives, iOS zooms in on inputs with `font-size < 16px`, displacing the entire interface. Pinch-to-zoom is also disabled — acceptable tradeoff for a keyboard-first tool dashboard where zoom doesn't improve terminal readability. The `interactive-widget=resizes-content` directive (keyboard layout resizing) and `viewport-fit=cover` (§ Safe-Area Insets) ride the same meta tag and are unrelated to zoom.

### Safe-Area Insets

**The app is `viewport-fit=cover` and every edge-docked pad is a `max(<floor>, env(safe-area-inset-<edge>))` expression — but on this app `env()` is 0 in in-browser Safari, so the floor is what actually ships the clearance.** The viewport meta in `app/frontend/index.html` carries `viewport-fit=cover`, which is the precondition for `env(safe-area-inset-*)` resolving to anything but 0 on iOS. In practice it resolves to **0 in in-browser iOS Safari** for this app on **both** edges: the page is `position: fixed` and non-scrollable (`html.fullbleed .app-root` pinned to `--app-height`, § iOS Keyboard Support), so Safari never enters the chrome states where it reports insets. Non-zero values appear only in standalone PWA mode. Device-confirmed on the bottom edge 2026-08-05 (photo evidence: the bottom-bar chips clipped by the corner arc). The `max()` shape is retained everywhere so genuine inset reporting — standalone PWA, future Safari behavior — still wins where it exists. Two consumers: (`260724-2bmy`, `260805-fi9m`)

- **Bottom bar toolbar row** (`bottom-bar.tsx`): `pt-1.5 pb-[max(var(--bottom-bar-floor,0.375rem),env(safe-area-inset-bottom))]` — asymmetric padding whose bottom arm reads a floor custom property. `--bottom-bar-floor` is owned by `globals.css` beside the `html.fullbleed` block: `0.375rem` (6px) at `:root`, raised to **`1rem` (16px)** under `@media (pointer: coarse)` on `html:not(.kb-open)`. That raised coarse floor is what clears the corner-arc/home-indicator zone for the extreme chips (`⇥` left, `⌨` right) on iPhone-class devices — `env()` contributes nothing in-browser. Fine-pointer and desktop-shell layouts stay byte-identical at 6px (the `@media (pointer: coarse)` scope is the gate; the raised floor must not leak into contexts that don't need it — the same rule as the shell's `isShell()` top gate below). Accepted cost: flat-screen touch devices spend ~10px of terminal height they didn't need.
- **Top-bar `<header>`** (`top-bar.tsx`): `pt-[env(safe-area-inset-top)]` — a guard, because `viewport-fit=cover` in standalone PWA mode also extends the page under the status bar, which would tuck the bar beneath the clock. The class is `isShell()`-gated OFF inside the desktop shell (a conditional template literal — browser/PWA output stays byte-identical): the `ShellTitlebarStrip` already reserves the titlebar band in the SPA layout (§ Desktop-Shell Titlebar Strip), and macOS hidden-titlebar windows can report that band as `safe-area-inset-top`, so keeping the padding would reserve the band twice. `isShell()` is read once per render — the preload injects `window.runkitShell` before any SPA script runs, so the value is stable for the page's lifetime. (`260805-9hn1`)

**The raised bottom floor is gated by an explicit JS keyboard signal.** A static raised floor would waste vertical space on an already-short viewport when the on-screen keyboard is up and the bar rides above it on flat screen area. `useVisualViewport` therefore toggles **`kb-open` on `<html>`** (§ iOS Keyboard Support), and `html:not(.kb-open)` is what admits the 1rem floor — with the keyboard open, coarse pointers fall back to the same 6px floor fine pointers always use. **Do NOT rely on `env()` collapsing, or on any layout-viewport side effect of `interactive-widget=resizes-content`, to produce this behavior**: iOS support for that directive is unreliable, and on this app `env()` is already 0 in both keyboard states, so it carries no signal at all. JS toggles the class; the padding math stays entirely in CSS.

**Playwright/Chromium reports every `env()` as 0**, so e2e can honestly assert only the floor values and the class flip (`bottom-bar-safe-floor.spec.ts`: 16px coarse-emulated via `hasTouch: true`, 6px after adding `kb-open`, 6px on fine pointers). The `max()` arm itself is verifiable only from the compiled class, never from a computed style — no test may pretend to exercise a real inset.

**New chrome docked to a screen edge SHOULD use this convention** rather than a hardcoded pad: `max(<the pad you wanted>, env(safe-area-inset-<edge>))`. Treat `env()` as a bonus that fires only in standalone PWA mode — pick the floor as if it will never fire, and scope any coarse-pointer-only lift with `@media (pointer: coarse)`.

**Interaction rule: edge-docked safe-area padding and shell-reserved chrome must not stack.** Where the desktop shell already reserves an edge with its own chrome (today: the titlebar strip at the top edge), the safe-area pad for that edge is gated off with `isShell()` rather than layered on top — the OS-reported inset covers the same band the shell chrome occupies, and applying both reserves it twice. (`260805-9hn1`)

## Design Decisions

### Shade carried on PickerColor, not a parallel vocabulary
**Decision**: Extend `PickerColor` to `{ family, shade }` with `formatColorValue` emitting `"{family}-dark"`, rather than minting 10 new pseudo-families for the dark shade.
**Why**: Hue identity, legacy mapping, and theme adaptation stay properties of the 10 `HUE_FAMILIES`; the shade is a render-time L offset (mean-L − 0.14), so there is zero new palette data and every family-keyed code path (tints, borders, accent) derives dark variants for free.
**Rejected**: 20 `HueFamily` entries — duplicates hue/legacy data and breaks the 1:1 legacy map (dark variants have no legacy form). Also rejected a light shade variant — normal+dark is what keeps every stored value without a `-dark` suffix mapping to the normal shade.
*Introduced by*: 260723-wwoi-label-picker-markers-shades

### Marker preview color held as picker-local state
**Decision**: The Label picker's marker-preview color derives from `selectedColor`, but a swatch pick also updates picker-local preview state before emitting.
**Why**: The requirement is "picking a different swatch repaints the marker column immediately"; the window-row caller closes the popover on pick, so prop-driven repaint alone would make the requirement vacuously untestable — local state makes it true for any caller.
**Rejected**: Prop-only derivation — repaint would depend on the caller keeping the popover open and re-rendering.
*Introduced by*: 260723-wwoi-label-picker-markers-shades

### Marker preview cells and the hazard wedge are never animated; rest-state motion is rationed to the data rain and opt-in flair
**Decision**: The `thick` hazard wedge is static in every state (rest, hover, selected), and the Label picker's MARKER preview cells never animate — no scanline crawl even when the double cell is selected, no data rain on the dashed preview. On real rows, rest-state motion is the dashed data rain (§ Dashed data rain, always-on) plus any per-row opt-in flair overlay (§ Character Flair Overlays — ambient in every state; flair PICKER cells are live previews and DO animate, the dashed cell's live-rain precedent). The dashed gutter STRIPE itself stays static in every state — the motion is the row rain, in its thinned two-lane form, which is quiet enough to run always-on.
**Why**: Motion on real rows is rationed to treatments that are either inherently live ("working" rain) or explicitly opted into per row (flair); marker preview cells stay still so the picker reads as a menu, not a wall of motion. The other animated variants tried during the design session (scrolling the dashed stripe, progress seam, barber-pole thick, animated hazard weave, phosphor bleed) stayed rejected as distracting or reading like a loading state. Double's scanline crawl + CRT band remains selection-gated.
**Rejected**: Scrolling the dashed stripe itself; animating the hazard weave; the progress seam; a phosphor bleed paired with solid; animating MARKER preview cells to mirror real rows.
*Introduced by*: 260723-wwoi-label-picker-markers-shades (wedge/previews); data rain added in the picker-dismissal follow-up (260723), always-on since 260724; flair motion scope 260814-2esh

### Hazard wedge is a left-edge mask, not full-row wallpaper
**Decision**: `.rk-hazard`'s 45° weave is confined by `mask-image: linear-gradient(to right, #000 22%, transparent 55%)` (with its `-webkit-` twin) — full strength for the first ~22% of the row, faded out by ~55%.
**Why**: The wedge is the "taped-off corner" cue for a completed row, so it has to read as a corner marking rather than as a second row background competing with the selected row's tint; the 22%/55% stops are the tuning that keeps it legible at row width without becoming loud.
**Rejected**: A full-width weave (louder than the selected row); a 13% fade-from-zero-to-38% mask (tapers so aggressively the wedge is hard to make out).
*Introduced by*: 260723-wwoi-label-picker-markers-shades

### One media-query substrate, thin policy wrappers over it
**Decision**: `useMediaQuery(query)` / `evaluateMediaQuery(query)` (`hooks/use-media-query.ts`) own the entire matchMedia mechanism — the non-browser guard, the `typeof`-checked modern-`addEventListener`-with-legacy-`addListener` fallback, the `mql.matches` re-read, the post-subscribe sync, and the `[query]`-keyed resubscribe. Every policy hook is a thin wrapper that contributes only its query string: `useIsMobile` ORs two subscriptions, `useCoarsePointer` is a single one, and `evaluateIsMobile` is the one-shot twin for non-hook readers. Components carry no local media-query hook and no width literal — `MOBILE_BREAKPOINT_PX` in `use-is-mobile.ts` is the single source of the 640px breakpoint, so `max-width: 639px` is always derived (`MOBILE_BREAKPOINT_PX - 1`), never typed.
**Why**: the fallback dance has several plausible-looking variants that differ in robustness — truthiness-checked vs `typeof`-checked listener attachment, trusting the `change` event object vs re-reading `mql.matches` — so any hand-written copy is a drift risk. A hardcoded `639` in a component is worse: it silently splits the app's mobile breakpoint the moment `MOBILE_BREAKPOINT_PX` moves, with nothing to fail. Concentrating the mechanism in one primitive makes the defensive variant the only variant and leaves each wrapper stating just its policy.
**Rejected**: keeping per-consumer copies of the subscription (the drift source); one combined `"(pointer: coarse), (max-width: 639px)"` query string inside `useIsMobile` (a single MQL is cheaper but re-introduces a literal breakpoint inside a string, where `MOBILE_BREAKPOINT_PX` cannot reach it, and loses the two-query shape existing test stubs key on); a CSS-only `coarse:` / `sm:` variant for the sidebar panels (their consumers need the boolean in JS to pick heights and grid-flow objects, not just classes).
*Introduced by*: 260731-tfr1-use-media-query-hook

### Two pointer policies stay unmerged
**Decision**: `useCoarsePointer()` keys on pointer TYPE alone; `useIsMobile()` keys on narrow width OR coarse pointer. Both wrap the same `useMediaQuery` substrate, and the shared substrate is explicitly not a licence to collapse them into one hook — a consumer picks the policy that matches what it is deciding.
**Why**: the two answer different questions. Tooltip suppression and the chat form's autofocus skip are about input capability — a narrow desktop window still has a hardware keyboard and a mouse — while layout topology (sidebar overlay, panel heights, terminal font default) is about available width, where a coarse pointer is a useful additional signal. Merging them would make a narrowed desktop window lose hover tooltips, or a wide touch device render the desktop sidebar.
**Rejected**: one `useIsTouch`/`useIsMobile` hook serving both (couples input policy to viewport width in both directions); routing an input-capability consumer through `useIsMobile` for consistency with the sidebar (the earlier explicit split decision, `260719-mxvw`, exists precisely to prevent this).
*Introduced by*: 260731-tfr1-use-media-query-hook

### No derived default accent
**Decision**: The instance-accent resolution chain ends at **none** — a fresh instance renders no accent until the user explicitly picks one. There is no hostname-hash or otherwise-derived default anywhere in the chain.
**Why**: A derived default's color can coincide with a just-cleared explicit pick, which makes "Clear color" look like a no-op — the user clears the accent and the surface repaints in a near-identical hue.
**Rejected**: A hostname-hash default accent (the coincidence above); treating the localStorage echo as authoritative rather than as a paint cache (an `authoritative` flag gates clearing the echo/meta on a null accent, so the paint seed is never wiped before the real resolution lands).
*Introduced by*: 260721-1etw-instance-accent-host-color

### Single theme-color meta writer module
**Decision**: All `meta[name="theme-color"]` writes funnel through one module (`src/instance-accent.ts`) holding module-level `currentAccentHex` + `lastBackground` state; `theme-context.tsx` (`applyThemeColorMeta`) and the instance-accent provider (`setAccentThemeColor`) both write through it, and the content resolves to the accent hex when set, else the theme background.
**Why**: React passive effects run child-first, so `ThemeProvider`'s `applyThemeToDOM` effect fires AFTER any child accent effect on a theme switch and would clobber an accent-tinted meta tag with the bare background. One writer with shared state removes the ordering race at its root rather than papering over it.
**Rejected**: having the accent provider re-write the meta in its own effect after theme changes — loses deterministically to the parent effect's ordering (fixes the symptom, not the cause).
*Introduced by*: 260721-1etw-instance-accent-host-color

### Instance-accent echo carries the precomputed meta hex, not just the descriptor
**Decision**: `runkit-instance-color` stores `{"value","hex"}` where `hex` is the final computed theme-color meta content; the `index.html` blocking pre-paint script applies `hex` verbatim. The echo is a paint cache only — never authoritative (the runtime resolution overwrites it every load).
**Why**: deriving a hex from a descriptor needs the OKLCH/palette machinery (`colorValueToHex` + contrast guard), far too heavy to inline in a blocking script; precomputing at echo time keeps the script a validate-and-apply read. A cross-theme-mode load shows a transient mismatch that self-corrects post-fetch (accepted).
**Rejected**: inlining the derivation in `index.html` (duplicates themes.ts logic in unlintable inline JS); echoing only the descriptor (leaves the script unable to tint).
*Introduced by*: 260721-1etw-instance-accent-host-color

### PWA titlebar carries a subtle blend, not the full accent hue
**Decision**: The theme-color meta content (and the echo's `hex`) is `titlebarHex` — a `blendHex(src, background, INSTANCE_TITLEBAR_RATIO = 0.35)` accent-into-background blend — not the contrast-guarded `stripeHex`. `stripeHex` stays the 2px top-bar stripe and the HOST hostname tint; `washHex` (~6.5%) stays the top-bar background wash. Three distinct derived hexes, one per surface class.
**Why**: mock parity. The design mock tinted the installed-PWA titlebar with a subtle dark blend of the accent into the theme background and relied on the full-brightness 2px stripe sitting directly below it as the vivid accent line. Painting the meta with the full-hue `stripeHex` made the whole titlebar a loud color band and rendered the stripe invisible — it abutted a titlebar painted the identical hex. The blend restores the tinted-titlebar + bright-line pairing the mock designed. Reuses the existing `blendHex` machinery (theme-aware by construction, no hardcoded hexes); `index.html` needs no change because the pre-paint script applies the echoed `hex` verbatim, so swapping the echoed value retints cold start for free.
**Rejected**: keeping the saturated titlebar and instead removing/relocating the stripe (the mock's whole point is the tinted-titlebar + bright-line pairing); a dynamic manifest / tinted dock icons / Badging API (separate follow-up `260722-eo8e-accent-dock-icon`).
*Introduced by*: 260722-y5c3-instance-accent-titlebar-wash

### `titlebarHex` is exposed from the accent context, not re-derived in the strip
**Decision**: `InstanceAccent` carries a nullable `titlebarHex` alongside `stripeHex`/`washHex`, and the shell titlebar strip reads it from the context. It does not call `deriveAccentHexes(color, theme)` itself, and it does not read the rendered `theme-color` meta.
**Why**: The provider already computes all three hexes for the meta bridge, so a second derivation in the strip would be one formula in two places — and the failure mode of drift is silent (a strip and a PWA titlebar that are subtly different colors for the same accent, on surfaces users rarely see side by side). Exposing the field costs a line in the context value and a mechanical fixture update; the field was nullable-by-construction already.
**Rejected**: A strip-local `deriveAccentHexes` call (duplicate derivation, silent drift); reading `document.querySelector('meta[name=theme-color]').content` (a DOM round-trip for state React already holds, and it inverts the dependency — the meta is an *output* of the accent state); passing the hex down as a prop from `AppLayout` (threads accent state through a layout that otherwise does not care).
*Introduced by*: 260731-ofws-shell-accent-titlebar-dock-badge

### Brand logo motion is state-based (segment illumination), not a transform spin
**Decision**: The brand crumb's logo hover is a JS-driven white glow "detach, orbit, land" sweep over the six border segments' fills — no geometry moves, no CSS keyframes, and no `prefers-reduced-motion` gate line (the JS skips itself). The glow is **white**, not the accent green the rest of the hover vocabulary animates in.
**Why**: The loading chase already speaks segment illumination, so a hover treatment in the same language gives the logo ONE motion vocabulary across both states instead of two unrelated grammars (illumination while loading, rotation on hover). White is the only color that reads: the glow rides over the lit half's own `#b4b4b4`, and a gray-toned glow is invisible there — accent green was prototyped and rejected outright ("green is not the answer"), which also keeps the Brand row's green cue on the wordmark's glitch where it already lives. Driving fills from JS is the established treatment class here (`typed-label.tsx`, the top-bar boot sweep), and it is what a continuous fractional head position and a per-frame gaussian falloff require — CSS keyframes can only step whole segments.
**Rejected**: The `rk-brand-spin` transform spin it replaces (`.rk-logo-ring` `<g>` + `transform-box: fill-box` — rotating geometry, a second vocabulary for one element); a stepped chase head scheduled as `floor(ease(t)·N)` (whole-segment jitter, and the last step lands only on the exact final frame so the ring parks then snaps); an accent-green or segment-gray glow (invisible over the lit half / off-vocabulary); a CSS-only illumination sweep (no fractional head, no gaussian).
*Introduced by*: 260803-ufqr-logo-animation-polish

### Landing IS the rest state — an integer lap count, not a restore
**Decision**: The sweep runs a whole number of laps (3) with a settle envelope that reaches `1` at both `p = 0` and `p = 1`, so those two frames compute to exactly the literal rest fills. The post-landing write of the static hex values is a numerical safety net, not the mechanism.
**Why**: The seam between "the animation stopped" and "the lit segments reset" is the whole design goal — the eye must not be able to tell them apart. An integer lap count parks the head on segment 0, which is the lit trio's own center, so the blob's landing spot IS the rest pattern's position and the crossfade has nowhere to jump; a fractional lap count would land the glow off-center and make the restore a visible snap no easing could hide. Deriving the lit trio from `BORDER_SEGMENTS[i].staticFill` rather than a duplicated `{5,0,1}` set keeps that alignment true by construction — the rest pattern cannot drift from the math that lands on it.
**Rejected**: A fractional/duration-tuned lap count with a crossfade or eased restore at the end (the snap the mock exhibited); a separate `{5,0,1}` constant beside the static fills (two sources for one pattern, silently divergent); leaving the inline `fill 0.5s` transition live during flight (smears every per-frame fill into a 0.5s crossfade and destroys the timing — hence the capture/suspend/restore).
*Introduced by*: 260803-ufqr-logo-animation-polish

### Chase stagger is negative so the spinner opens in steady state
**Decision**: `LogoSpinner`'s per-segment loading delay is `${i * 0.2 - 1.2}s` — negative across the board — leaving the `logo-chase` keyframes, the 1.2s duration, and the 0.2s stagger interval untouched.
**Why**: A positive stagger holds each segment at its unanimated opacity until its own delay elapses, so the ring mounts as one bright side that expands over the first full lap before the chase establishes. Every spinner mount in the app paid that transient, so it is a bug in the shared loading affordance rather than a per-call-site nicety. Negating the delays starts each segment mid-cycle instead, which is the whole fix — one sign change, no keyframe or timing edit, and every call site inherits it.
**Rejected**: Rewriting the keyframes so frame 0 already reads as mid-chase (encodes the phase offset twice and couples the fix to the six-segment count); a mount-time fade-in over the transient (hides the artifact instead of removing it); per-call-site delay overrides (the transient is shared, so the fix belongs in the component).
*Introduced by*: 260803-ufqr-logo-animation-polish

### Signal hues are per-theme tokens; only the semantic is constant
**Decision**: The four signal hues are theme tokens — `--color-signal-{yellow,purple,blue,red}` defined in the `@theme` block and both `html[data-theme]` blocks of `globals.css` exactly like `--color-accent-green`, consumed through the Tailwind-generated `text-signal-*` / `bg-signal-*` / `border-signal-*` utilities (opacity modifiers via color-mix). Dark values are the legacy Tailwind `-400` hexes (`#facc15` / `#c084fc` / `#60a5fa` / `#f87171`), so dark renders pixel-identical; light values darken to `#b07d02` (custom gold) / `#9333ea` / `#2563eb` / `#dc2626`, each meeting the WCAG 1.4.11 ≥3:1 graphics bar on the light backgrounds. The **semantic** is constant — yellow = "an agent needs you now" in every theme — while the **value** re-themes. `pr-status-model.ts` remains the single edit point for the shared PR/phase color vocabulary; every consuming surface (sidebar rows, session tiles, row flyout card, pane panel, waiting badge/halo/seam, chat warning banner, error foregrounds, kill affordances) inherits from it or references the tokens directly. The chat warning body text collapses into the single `signal-yellow` token; the `border-red-500/50` / `bg-red-500/10` washes stay raw classes (not contrast-critical foregrounds).
**Why**: The fixed `-400` utilities measured 1.3:1–2.8:1 on the light backgrounds — below the ≥3:1 bar for UI graphics — so the highest-priority signals (waiting halos, pending checks, failing PRs, error text) were effectively dark-theme-only. The three-block token pattern was already proven by `--color-accent-green`, and one token per hue keeps the vocabulary centralized.
**Rejected**: `yellow-700` `#a16207` for the light yellow — passes 4.5:1 but reads brown, killing the yellow chroma that carries the attention semantic; the accepted single-token trade-off leaves text surfaces reusing the gold (waiting badge, chat warning body) below the 4.5:1 AA text threshold. A two-tone yellow split (brighter gold for glyphs, darker shade for text-only surfaces) — set aside for single-token simplicity. Moving the red washes to `signal-red` derivatives — deferred as an aesthetic call.
*Introduced by*: 260811-m3f3-light-theme-signal-color-tokens

### Two-family chrome vocabulary
**Decision**: Every chrome surface is either **attached frame** (top bar + status bar ONLY — flush, square, full-width, never rounded, never inset by stage padding; the status bar is a direct outer-grid child so the stage's 6px padding never reaches it) or a **floating card** (tiles, board panes, the server route's 900px `fixedWidth` column, the sidebar — `rounded-md`, the 55% dimmed `rk-card-border`, `bg-bg-primary`, floating with 6px gaps on the shared `bg-bg-inset` ground). All four routes share one inset floor: Shell routes (terminal, `/$server`, `/board/$name`) get it from Shell's universal stage; the host page `/` mounts no Shell and sets `bg-bg-inset` on its own root (`host-overview-page.tsx:240`). The sidebar card floats 6px above the status bar; its drag-resize handle carries the `.rk-divider` gap-seam chrome straddling the 6px gap rather than a seam bar.
**Why**: One organizing rule keeps every seam decidable; a half-card sidebar corner, a stage-scoped status bar, or per-route grounds each break it. One continuous inset floor gives all four routes the same visual ground, and carding the sidebar keeps the frame family down to host-global chrome — the sidebar is content navigation and reads as a card.
**Rejected**: An attached square sidebar with a `border-r` seam welded to the status bar (the sidebar sits on no ground, and the junction reads as a square T); a sidebar bottom gap + rounded bottom-right corner on an attached sidebar (a half-card); the status bar starting right of the sidebar (a stage-scoped strip carrying host-global segments, and two competing bottom edges); scrollable status-bar overflow (a scrolling bar hides what it exists to show — overflow degrades by ladder instead).
*Introduced by*: 260815-19me-composed-frame-unification

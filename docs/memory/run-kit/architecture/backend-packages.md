| `internal/codeserver` | **The rk-owned code-server install engine** (260813-oid2-own-code-server-install) — release resolution, digest-verified download, extraction, and the versioned layout under `~/.rk/code-server-bin/`, shared by the daemon (the resolution ladder + install job) and the CLI (`rk code-server` + the `rk update` leg) with **zero tmux coupling** (the `internal/desktop` install-engine-as-library precedent). Layout (path helpers `BinDir`/`VersionDir`/`CurrentPath`/`BinaryPath`): one extracted release per `~/.rk/code-server-bin/<version>/` dir (the tarball's top-level directory stripped, so the binary is `<version>/bin/code-server`) with a `current` symlink beside them naming the active version; activation is an **atomic symlink flip** (temp symlink + `os.Rename` over `current` — never a remove+recreate, so no observer sees a missing `current`). `InstalledVersion(home)` reads the `current` symlink's target basename (absent ⇒ `("", nil)` — absence is a state, not an error; Constitution II derive-from-filesystem, no registry); `ManagedBinary(home)` is the daemon's rung-1 resolution (the `current`-symlink binary path, verified regular+executable, else `""`). `resolveLatest` queries `https://api.github.com/repos/coder/code-server/releases/latest` **unauthenticated** (10s bound; acquisition is rare enough that rate limits are irrelevant) and selects the `code-server-<ver>-<os>-<arch>.tar.gz` asset for the host (`darwin`→`macos`, `amd64`/`arm64` pass through; an unsupported platform or missing asset is a clear error), capturing the asset's `sha256:` digest. `Install(ctx, home)` is **idempotent** (installed == latest ⇒ an `AlreadyCurrent` skip, nothing downloaded), streams the tarball to a staging dir under `code-server-bin/` computing SHA256 inline (15m `downloadTimeout` — a generous bound on failure for the ~100MB asset, not an expected duration), and **fails closed on verification**: a missing digest or a mismatch aborts before any promotion — no flip, `current` untouched, staging cleaned up (unlike the desktop package there is no codesign second gate, so the digest is the only verification — Constitution I). Extraction is **in-process** `gzip`+`archive/tar` (no curl/tar subprocesses), preserving mode bits (the `bin/code-server` entry script and bundled `node` stay executable), recreating symlink entries, and refusing dest-escaping entries; the tree is promoted staging→`<version>/` by `os.Rename`, then `current` flips — both single-syscall renames on one filesystem, so a crash leaves the old world intact or a garbage staging dir, never a torn active install. The `Installer` struct holds the seams (`Client`, `GOOS`/`GOARCH`, `APIBase` for httptest, `Progress` wired to the caller's chatter channel) as **struct fields, not package vars** (the `internal/desktop` idiom — parallel tests never race). `extension.go` adds the bridge-extension half: `ExtensionsDir(home)` — the one resolution of code-server's default extensions dir (`$XDG_DATA_HOME/code-server/extensions`, else `~/.local/share/code-server/extensions`), shared by the daemon's spawn flags, the bridge install step, and the doctor row — plus `InstalledBridgeVersion` (filesystem scan of `run-kit.rk-code-bridge-*/package.json`, no subprocess) and `InstallBridgeExtension` (skip-when-equal, else a private-temp VSIX staged and installed via the managed binary's `--install-extension … --force` under a 2-minute `exec.CommandContext`; see [code-bridge](/run-kit/code-bridge.md) § Distribution) |
| `internal/codeworkspace` | **The derived per-tab `.code-workspace` file library** (260909-kji8-tab-keyed-code-workspace-actions) — carries the run-kit tab identity into the code-server extension host; full contract in [code-bridge](/run-kit/code-bridge.md) § Tab identity. `StateDir()` resolves `$XDG_STATE_HOME/run-kit/code` (default `~/.local/state/run-kit/code`) by exactly the `codebridge.StateDir()`/`snapshot.DefaultDir()` rule, mirrored rather than imported (no import edge between sibling libraries); `Path(stateDir, server, windowID, root)` composes `<stateDir>/<server>/<windowID>-<hash6>.code-workspace` with `hash6` the first 6 lowercase hex of sha256(absolute root) (the `present.RootHash` rule, truncated — the windowID segment already keys the tab); `Content(root, windowID, server)` renders exactly `{"folders":[{"path":<root>}],"settings":{"rk.tab":<windowID>,"rk.server":<server>}}` (`json.MarshalIndent` + trailing newline, no other keys); `Ensure` validates `validate.ValidateServerName`/`ValidateWindowID` before any path composition, byte-compares the existing file, and writes only when absent or different (temp + rename, file `0600`, server dir `0700`). | `internal/daemon` | Daemon lifecycle management — `IsRunning()`, `Start()`, `Stop()`, `StartWithBinary(binPath)`, and the single options-driven restart sequencer `Restart(opts RestartOptions{Force, Full, Binary})` (`restart.go` — owns the `--full` inside-server guard → stop → kill-server → force-reclaim → start ordering for every restart composition; consumed by `cmd/rk/daemon_restart.go`'s thin RunE and by `cmd/rk/upgrade.go` after `brew upgrade` via `RestartOptions{Binary: path}`, for when the running process's `os.Executable()` path is stale) — both Start paths begin with the fail-fast `checkTmuxPresent()` tmux-presence precheck (seam `daemonTmuxLookPath`, remediation hint via `tmux.InstallHint` — § Daemon Lifecycle → Tmux-presence precheck) and end with the best-effort managed-code-server spawn (`ensureCodeServer` in `codeserver.go`, the `rk-code-server` sibling session — § Daemon Lifecycle) followed by the gated `ensureGUI()` boot hook (`gui.go`, the `rk-gui` sibling session — a silent skip when `gui.enabled` is off; § Daemon Lifecycle and [gui](/run-kit/gui.md)). The kill primitives are **release-synchronous** w.r.t. the code-server port: `KillServer()` probes `rk-code-server` existence pre-kill and waits (bounded by the `codeServerPortFreeTimeout`/`codeServerPortFreePoll` vars, expiry non-fatal) for the port to free only when the sibling pre-existed; `KillCodeServerSession()` runs the same wait after a successful kill (`killed == true` only) — § Daemon Lifecycle → Release-synchronous kill primitives — plus `InnerServePID() (int, error)` returning the inner serve's PID via tmux `pane_pid` (a single `list-panes -F '#{pane_pid}'` query through the `runTmuxOutput` helper, delegating to the session-parameterized `innerServePIDFor(session)` that `Stop()`'s signal-first delivery also uses — seams `innerServePIDForFn` and `signalPID`) and the `OwnerIsDaemon(owner *ports.PortOwner) bool` predicate built on it (seam `innerServePIDFn`) — consumed by the sequencer's force leg, by `cmd/rk/daemon*.go` for `--force` self-recognition, and by `rk daemon status` for port-owner classification. Manages `rk serve` in a dedicated tmux server (socket `rk-daemon`, session `rk-daemon`, legacy session `rk` consulted by `Stop`/`Restart` for transparent upgrade, window `serve`). All tmux calls go through `runTmux`/`runTmuxOutput` which use `exec.CommandContext` with a 5s `cmdTimeout` per command (each probe/delivery command/kill gets its own fresh context) and prepend `-L rk-daemon`. `Stop()`'s overall wait for graceful shutdown is NOT bounded by that per-command 5s — it uses a separate, independent `stopGracePeriod` (12s, a package `var` test seam) grace-deadline `time.NewTimer`, sized to exceed the inner serve's ~10s worst-case shutdown (supervisor stop 5s + `server.Shutdown` 5s, sequential in `cmd/rk/serve.go`); each liveness poll within that wait runs under its own fresh `cmdTimeout` context via the `sessionExists` helper, so no probe inherits a near-expired deadline. A session that has already vanished by kill-time (graceful delivery worked, exit just took longer than the poll budget) is treated as a successful stop (`Stop()` returns nil after a fresh-context re-probe, and re-confirms after a `kill-session` error) — only a session still alive after a failed kill surfaces an error. `Stop()`'s graceful delivery is **signal-first** — SIGINT to the inner serve PID (`innerServePIDFor(session)` + the `signalPID` seam), because signaling bypasses tmux key dispatch entirely: a pane in a mode swallows `C-c` into the mode key table, and tmux ≥3.7 rejects `send-keys` outright (`client is read-only`) whenever the recency-resolved target client is read-only (a user-attached `-r` client can still be that client; run-kit's own `-CC` bridge attaches writable — [daemon-lifecycle](/run-kit/daemon-lifecycle.md) § Design Decisions → Writable bridge, read-only enforced in Go) — with the best-effort tmux fallback behind it (`copy-mode -q` mode pre-cancel, then `send-keys … C-c`), and never early-returns on a delivery failure (`slog.Warn` fall-through, so the grace/kill fallback is reachable regardless) — see § Daemon Lifecycle for the full sequence. Port-based liveness probe via `net.DialTimeout` (400ms, with loopback substitution for wildcard hosts) and stale-session reaping via exact-match `runTmux(ctx, "kill-session", "-t", "="+session)` per daemon session name (current + legacy — never `kill-server`; the socket is multi-tenant, § Daemon Lifecycle → Stale-session reaping) before session creation; supports daemon startup logging tee via `RK_DAEMON_LOG` env var (exported as `daemon.LogEnvVar`). Also owns the managed job-window primitive `RunJob(ctx, window, argv) (JobTarget, started bool, error)` (`jobs.go`, `JobsSessionName = "rk-jobs"`): gate on the daemon running (never births a tmux server) → session-absent fast path creating `rk-jobs` WITH the job window as its first window (`new-session -d -n <window> <argv…>` — no idle default window, probe skipped; a lost `duplicate session` race falls through) → otherwise dedup on the exact-match `=rk-jobs:=<window>` target via a `list-panes` probe (hard-fails on a missing window, unlike `display-message`'s active-window fallback — the released 3.15.10 bug; live pane ⇒ in-flight, returns `started=false` with the existing target; dead remained pane ⇒ `respawn-window -k` in place; absent ⇒ `new-window -d -t =rk-jobs: -n <window> -P -F '#{window_id}' <argv…>`) → best-effort post-spawn `remain-on-exit on` + `pipe-pane` tee to `~/.rk/<window>.log` (§ Daemon Lifecycle → the `rk-jobs` sibling session, and § API Server version/checker wiring → the spawn seam). Used by `cmd/rk/daemon*.go` (CLI surface, incl. `daemon run` wrapping `RunJob`), `cmd/rk/serve.go` (`LogEnvVar` consumption in `setupSlog`), `cmd/rk/upgrade.go` (auto-restart after update), and `api/update.go`/`api/restart.go` (`RunJob` via the `runJobFn` seam) |
| `internal/desktop` | **Desktop-app installer library** (260730-pl4v-rk-desktop-install) — resolves, downloads, verifies, and installs the Electron shell's release DMG (see [desktop-shell](/run-kit/desktop-shell.md) § Installation & Updates for the quarantine rationale). Electron-free and **fully seam-parameterized**: an `*http.Client` (GitHub API + asset download) and a `Runner func(ctx, name, args...) ([]byte, error)` for every subprocess (`hdiutil`, `ditto`, `codesign`, `plutil`, `pgrep`), both **struct fields** rather than package vars so parallel tests do not race — the `internal/updatecheck.checkFn` idiom. `New()` supplies production defaults (`Repo` `sahil87/run-kit`, `Arch` `runtime.GOARCH`, `InstallDir` `/Applications` = `DefaultInstallDir`, `Token` from `GITHUB_TOKEN`, `Progress` `io.Discard`). `ResolveRelease(ctx, tag)` GETs `{APIBase}/repos/{Repo}/releases/latest` (or `/releases/tags/{tag}`, with a bare-semver `--version` normalized to the repo's `v`-prefixed convention) and matches the DMG by **prefix `run-kit-desktop-` + suffix `-{arch}.dmg`** (`arm64`→`arm64`, `amd64`→`x64` via `archLabel`, which errors before any HTTP request on an unsupported GOARCH) rather than an exactly-constructed filename; `net/http` + `encoding/json` only, **no GitHub client library**. HTTP 403/429 yields an explicit unauthenticated-rate-limit error naming `GITHUB_TOKEN`; 404 distinguishes tag-not-found from no-releases. `InstalledVersion(ctx)` reads `<InstallDir>/Run Kit.app/Contents/Info.plist`'s `CFBundleShortVersionString` via `plutil -extract … raw` (missing plist → `("", nil)`, i.e. not installed) — never assumed equal to the `rk` CLI version (Constitution II). `AppRunning(ctx)` is a best-effort `pgrep -f <bundle>/Contents/MacOS` probe (any error, incl. pgrep's exit 1, reads as not-running). `Install(ctx, rel)` streams the asset to a temp file computing SHA256 inline, **hard-gates** on digest match (when the API supplied one; absent → a chatter note, codesign stays the gate) then `hdiutil attach -nobrowse -readonly -mountpoint`, validates the mounted bundle's basename against the `AppBundleName` constant, `codesign --verify --deep --strict`, then `ditto` to a deterministic dot-prefixed **staging** name inside `InstallDir` followed by remove-old + `os.Rename` (same-volume atomic replace — a mid-copy failure never destroys a working install), and `hdiutil detach` in a `defer` on `context.Background()` so a canceled parent ctx still releases the mount; every failure branch removes the staged copy and the temp DMG. **The whole stage phase runs while the app may be live** — `AppRunning` is probed once, at the swap boundary (the TOCTOU probe), and when it hits, `restart.go` orchestrates the swap gap: `quitApp` (`osascript -e 'tell application "Run Kit" to quit'`, target name derived from `AppBundleName` so it cannot drift), `waitAppExit` (poll `AppRunning` at `ins.QuitPoll` until the deadline `ins.QuitWait` — the osascript call returns when the app *accepts* the Apple event, so process exit lags it), the rename, then `relaunchApp` (`open -a <dest>`). A wait-bound expiry returns a manual-quit error **before** the destructive step, leaving both the existing install and the staged copy intact (the next run's staging `RemoveAll` reclaims it); a `relaunchApp` failure is swallowed into a `Progress` warning so a completed swap is not misreported. `InstallResult.Restarted` is true only when the app was running and quit→swap→relaunch all completed — the CLI layer keys its restart announcement on it. `QuitWait`/`QuitPoll` are `Installer` **struct fields** defaulted in `New()` (30s/1s), so a test shrinks the timeout path to milliseconds without a package var; `quitTimeout` (15s) and `relaunchTimeout` (30s) stay consts. Bounds are per-call `context.WithTimeout` on the single `runCommand` exec site: API 30s, download 15m, attach 2m, codesign 5m, ditto 5m, detach 1m, probes 10s, quit 15s, relaunch 30s — generous rather than tight (the DMG is ~110MB; `codesign --deep` reads every file of a ~200MB Electron bundle), which the intake sizes at "the build-op tier or above". The whole flow unit-tests on Linux with an `httptest` server + a recorded runner; only the real end-to-end run needs a Mac |
| `internal/fsatomic` | **Crash-safe file writes** — one exported `WriteFile(path, data, perm)`: temp file in the same directory, write, atomic rename, temp removed on any failure, so readers see either the old contents or the complete new contents. `perm` applies at file **creation** (`O_CREATE\|O_EXCL`, with a bounded same-pid collision retry) so the process umask is respected exactly like `os.WriteFile` — an explicit `Chmod` would silently widen permissions on hardened-umask hosts. Three consumers: `internal/push` (VAPID keypair + subscriptions, 0600), `internal/remote` (`remotes.yaml`), `internal/snapshot` (latest/history/tombstones). Constitution §II keeps state in plain files rather than a database, which makes torn writes a real corruption vector — this is the one implementation of the guarantee |

## Design Decisions

### The readiness state reader is injected into `internal/inject`
**Decision**: `inject.AwaitReady` takes its agent-state reader as a caller-supplied `ReadyOpts.State` func; `internal/inject` never imports the tmux state layer.
**Why**: inject stays the dependency-light delivery core shared by daemon and CLI; every caller already knows its state source (`tmux.PaneAgentState`) and its per-read bounds — the CLI wires a 5s-bounded reader, riff wires `tmux.PaneAgentState` directly.
**Rejected**: inject importing `internal/tmux` for `PaneAgentState` (dependency inversion for one func; complicates the daemon's mocked seams).
*Introduced by*: 260903-4czh-boot-ready-spawn-inject

### The layout verb port lives in the existing `internal/layoutspec`
**Decision**: `internal/layoutspec` holds the pure mutations (`Default`, `Promote`, `SwapWithNext`, `Close`, `Add`, `Cycle`, `SetShape` with named sentinel errors) as a case-for-case port of the frontend's `surface-layout.ts` table, beside the grammar (`Parse`/`String`/`Has`) the `/options` validator uses.
**Why**: one Go table for shapes/surfaces/arity serves both the API validator and the `rk tab layout` verbs; a sibling package would duplicate the grammar and could drift — agent and human go through one growth/collapse table.
**Rejected**: a new `internal/layoutverbs` package.
*Introduced by*: 260829-c143-rk-tab-cli-present-sugar

### Shared tmux install-hint helper in `internal/tmux` with injected lookPath
**Decision**: one pure `InstallHint(goos, lookPath)` helper in `internal/tmux` produces every tmux-missing remediation hint, consumed by both the doctor tmux row (`cmd/rk/doctor.go`) and the daemon-start precheck (`internal/daemon`).
**Why**: all tmux concerns route through `internal/tmux`; both consumers already import it; a single source keeps the two user-facing hints from drifting; the injected `lookPath` (the `codeServerCheck(home, lookPath, dial)` idiom) makes every platform/package-manager branch unit-testable without host PATH dependence.
**Rejected**: duplicating the darwin/generic branch in the daemon package (drift risk); a standalone `internal/hints` package (needless surface for one function).
*Introduced by*: 260817-ho1o-tmux-missing-remediation-hints

### The managed code-server is curated through launch flags, backed by an rk-owned seeded profile for settings-only behavior
**Decision**: the `ensureCodeServer` argv carries five curation flags after `--auth none` — `--disable-telemetry --disable-update-check --disable-workspace-trust --disable-getting-started-override --app-name run-kit` (verified against installed code-server 4.112.0 / Code 1.112.0) — and behavior with **no CLI flag** (the "Build with Agent" chat panel, the welcome tab) is curated through the rk-owned profile's write-once settings seed instead (see the profile decision below).
**Why**: flags are the smallest legible lever — an argv-only change at the single spawn site rk owns, covered by the existing exact-argv test seam; `--disable-workspace-trust` is code-server's only trust mechanism (no auto-accept flag), correct because the `/code` lens only opens rk-managed worktrees; `--idle-timeout-seconds` is deliberately absent — server-side terminals and hot-exit state live in the editor process, whose persistence is the sibling-session design's point.
**Rejected**: mutating the user's default-profile settings.json from rk (clobbers the personal code-server profile).
*Introduced by*: 260812-6rxw-code-server-launch-flags, 260812-71bv-code-server-seeded-profile

### The rk-owned profile lives in `~/.rk/code-server-profile`, seeded write-once, with extensions pinned to the default location
**Decision**: `--user-data-dir {home}/.rk/code-server-profile` (resolved via the `codeServerUserHomeDir` seam), `User/settings.json` seeded with `{"chat.disableAIFeatures": true, "workbench.startupEditor": "none"}` only when the file is absent, and `--extensions-dir` pinned to `$XDG_DATA_HOME/code-server/extensions` (else `~/.local/share/...`) — code-server's own default. A one-shot `os.Rename` migration (`migrateCodeServerProfile`, run before the seed) moves a legacy `~/.rk/code-server` profile dir across when the old exists and the new does not (both-exist ⇒ the new wins, both untouched; fresh host ⇒ no-op), preserving settings and hot-exit state.
**Why**: the two settings have no CLI flags, so a profile rk owns is the only reproducible-baseline mechanism that never touches the user's personal profile; write-once means user edits win forever (a baseline, not enforcement); `~/.rk/` is rk's user-config namespace and the seeded settings.json is the user-editable artifact; the extensions pin exists because code-server derives its default extensions dir from the user-data-dir, so the override alone would hide installed extensions. Degrade rungs are asymmetric by design: seed failure keeps the flags (code-server creates its own dir), home-resolution failure drops them (no valid absolute path to pass — a relative/empty value is worse than the curation-flags-only status quo).
**Rejected**: `$XDG_DATA_HOME/rk/code-server` (mirrors code-server's placement but hides the editable settings.json in a data dir); `$XDG_STATE_HOME/run-kit/code-server` (those carve-outs are rk-written state — this dir is code-server-owned and user-edited); aborting the spawn on profile failures (an editor must never block the dashboard).
*Introduced by*: 260812-71bv-code-server-seeded-profile, 260813-oid2-own-code-server-install

### The layout grammar lives in `internal/layoutspec`
**Decision**: a pure package ports the frontend's `parseLayout`/`serializeLayout` and owns the shape/arity/surface validation.
**Why**: the `/options` API validation and the `rk tab layout` CLI verbs share one table; a regex validator inside `api` would be thrown away.
**Rejected**: regex validation in `api/windows.go`.
*Introduced by*: 260828-fykg-ui-state-backend-tmux-options

### One validator table, two writers
**Decision**: the `rk tab` signal setter verbs validate through the same `internal/validate` functions the `/options` handler uses; the note rule lives once as `validate.ValidateNoteText` / `validate.NoteTextMaxLength`, consumed by both writers, so neither carries a private copy.
**Why**: the `layoutspec` precedent — a sibling copy of a closed set drifts; the API's private note bound would have become exactly that copy.
**Rejected**: importing the `api` package's constant from `cmd/rk` (wrong dependency direction); re-declaring the bound in the CLI.
*Introduced by*: 260910-hzih-tab-setter-verbs-owner-option

### procfs direct reading over external monitoring tools
**Decision**: `internal/metrics` reads `/proc/stat`, `/proc/meminfo`, `/proc/loadavg`, `/proc/uptime` directly; `syscall.Statfs` for disk. All readers return zero values on non-Linux (macOS dev graceful degradation). No new Go dependencies.
**Rejected**: a dependency on `top`, `htop`, or monitoring agents.
*Introduced by*: 260411-z63r-sidebar-host-window-panels

### Toolkit update-notify + one-click upgrade: delegated `shll check-updates` detection + scoped `shll update`, no new deps/routes/DB
**Decision**: the daemon execs `shll check-updates --json` once per ~6h (`internal/updatecheck`), consumes the per-tool verdicts it returns, and broadcasts the notable-tool set + composite key over the server-global `event: update-available`; the running version rides a set-once `event: version` slot; a `POST /api/update` runs the scoped `shll update <matched…>` in the managed `update` job window of the `rk-jobs` sibling session (fallback `rk update` self when shll is absent); a `POST /api/updates/check` runs the same pass on demand and returns the fresh verdict synchronously. run-kit is the only toolkit tool with a daemon + UI, so it is the only place a passive reminder for the WHOLE toolkit (shll, wt, idea, tu, hop, fab-kit) can live. Cross-repo: `shll check-updates` is owned by shll — that repo owns the check logic + policy values; the JSON contract is vendored in rk as `testdata/check-updates.json` (260720-puxw-check-updates-command). Frontend: `useUpdateNotification()` hook + top-bar L3 UpdateChip (single/multi form) + palette parity (two check commands, `Update Now` as the single update action) — see [ui/updates-and-notifications](/run-kit/ui/updates-and-notifications.md) § Update Notification.
**Why**: *Delegate the check to `shll check-updates`* — an in-rk reimplementation of shll's canonical check logic (a manifest HTTP fetch of `https://shll.ai/versions.json`, a `brew list --versions` join, and a hand-rolled sibling threshold evaluation) is two places for the notify policy, roster, and manifest schema to drift as the toolkit evolves. One exec of `shll check-updates --json` replaces those three code paths with a single subprocess under rk's standard discipline (`exec.CommandContext`, argv slice, 30s bound — §I), so the check is defined ONCE, on the shll side (§III Wrap, Don't Reinvent). *Two backends, not one filtered verdict* — the ambient loop and the default `run-kit: Check for Updates` command use shll's `released` manifest source (flag-free — its default, keeping the invocation valid across shll's `--released`→`--source` consolidation); the `incl. patches` command uses the FRESH `--source github` release-tags source because the shll.ai manifest refreshes ~daily and can lag a just-cut release. A github check runs as a SIDE-CHANNEL query — `CheckNow(ctx, SourceGithub)`, no cache write, no `OnQualify` — so the chip, dismissal key, and scoped `shll update` argv stay bound to the notify-policy-bearing released source (the github contract carries no `notify`/`notable`; every row lands `notable=false`, so caching it would wipe a legit released chip and starve the scoped-update argv). The two commands are therefore not "same data, two filters" but TWO BACKENDS: the default can report all-up-to-date while incl.-patches lists updates, purely from manifest lag — deliberate. *The run-kit row is re-compared locally* — shll can only see the brew-VISIBLE version, but run-kit's restart-relevant truth is the RUNNING ldflags version (brew's on-disk version can legitimately be ahead between upgrade and daemon restart), so rk consumes shll's `latest`+`notify` for that one row but does the comparison locally (producing BOTH `update_available` and `notable`), and keeps its `selfBrew` gate (a go-install/dev rk can't self-update through brew, so its own row is omitted). Sibling verdicts are trusted VERBATIM. *The retained semver helpers* — `crossesThreshold`/`anyIncrease`/`parseMajorMinor` exist ONLY as the machinery for that one local run-kit comparison and `New`'s suppression parse — the sibling-wide evaluation lives behind `shll check-updates`. *Dual failure posture (ambient fail-silent, manual fail-loud)* — the ambient 6h loop skips a failed pass silently and retains the previous verdict (stale-while-revalidate) — a background reminder must never crash or nag on a transient shll hiccup; but a MANUAL `POST /api/updates/check` deserves an honest answer, so `CheckNow` surfaces the failure as a `502`/`409` the client turns into an error toast. *An on-demand check endpoint at all* — with only the ambient chip and a blind force-update a user could not ask "is anything updatable right now?"; the endpoint runs the SAME code path as the loop and converges on the SAME cached verdict (so a manual notable finding lights the chip immediately). *Scoped `shll update` not `rk update`* — updating run-kit alone can skew cross-repo contracts (run-kit ↔ fab-kit share `@rk_agent_state`); `shll update <matched…>` keeps the matched tools moving together and delegates to `rk update --skip-brew-update` for run-kit's daemon-restart side effect (§III). It CANNOT run in-process (the restart kills the serving process mid-request), so the job runs in a managed window of the `rk-jobs` sibling session via `daemon.RunJob` (260812-z1ya-update-daemon-tmux-window) — the window survives the daemon restart it triggers by placement (Constitution VI), every tmux call stays `exec.CommandContext`-bound (§I — no detached-child carve-out), the response carries the `watch` target so the UI can jump to the live job, and output tees to `~/.rk/update.log` via `pipe-pane`. *The post-remediation re-check (R17)* — a siblings-only `shll update` never restarts the daemon, so nothing would naturally clear the consumed match: the chip would stick on `updating…`, the cached SSE slot would replay a stale match to every new tab, and a later click would 409. Firing `OnQualify` on ANY key change (incl. →empty), broadcasting the cleared verdict into the slot, clearing frontend state on key change, and a ~2min post-spawn `RecheckAfter` close the loop end to end. *SSE cached slots not a `GET /api/version`* — the two events reuse the exact `server-order`/`board-order` fan-out + cached-on-connect machinery (all clients incl. `?metrics=1`), and the connect IS the moment the client needs the version (§IV). *Extract `internal/selfpath`* — the brew marker + self-path resolver would otherwise be duplicated byte-for-byte in `upgrade.go` and `update.go`; the shared package means brew-install detection cannot drift between the CLI and web entry points. Accepted: until a shll release carries `check-updates` the not-on-PATH path keeps the checker silent (fail-silent-retain leaves the verdict empty → the chip stays hidden); a failed brew upgrade leaves the chip on `updating…` until the verdict changes (escape hatches: the palette force path + a page reload; the `remain-on-exit on` job window + teed log carry the evidence).
**Rejected**: reimplementing the check in rk (drift risk — §III); a github check that WRITES the shared cached verdict (would wipe the released chip + 409 the scoped update — the side-channel posture is load-bearing); silently treating an unknown `source` as released (masks a client bug — 400 instead); an invented client-side boolean instead of echoing `report.Source` (the echo doubles as a defensive check); a shll-side change (the github contract already omits `notify`/`notable` and self-identifies `"source":"github"`); in-process upgrade (restart kills the server); `GET /api/version` (needless surface); a semver DEPENDENCY (the ~20-line hand-rolled compare backs only the one local run-kit row); a frontend-only `updating` timeout (leaves the stale verdict up to 6h); tracking the job's exit from the handler process (the job must outlive the daemon it restarts — the window state + teed log are the observation surface); Web Push for update notices (reserved for waiting agents — update notices must not buzz phones, user-decided).

### A dedicated `internal/codeserver` package owns the code-server install + layout
**Decision**: release resolution, download/verify/extract, layout paths, and installed-version reads live in `internal/codeserver`; `internal/daemon` (the resolution ladder + install-job spawn) and `cmd/rk` (the `rk code-server` family + the `rk update` leg) both consume it.
**Why**: the engine has two consumers and zero tmux coupling; `internal/daemon` is tmux-lifecycle code and `cmd/rk` must stay thin. Mirrors the desktop-installer precedent (install engine as a library, CLI as the caller).
**Rejected**: growing `internal/daemon/codeserver.go` (couples pure install logic to the daemon package's tmux seams); implementing in `cmd/rk` (unreachable from the daemon's job-spawn decision and untestable per the internal-package convention).
*Introduced by*: 260813-oid2-own-code-server-install

### Long-lived spawns carry the version-stable rk path
**Decision**: every process the daemon spawns to outlive its own binary version — the `rk-code-server` session's `RK_BIN` env element, the `code-server-install` job's shell chain, the `rk-gui` supervisor argv — names `selfpath.Stable()`: on a Homebrew install the brew-prefix `<prefix>/bin/run-kit` symlink, elsewhere the resolved binary. `StableFor` is a pure string derivation (Cellar path → prefix symlink) that never stats the result; `cmd/rk/upgrade.go`'s daemon-restart path uses the same function.
**Why**: `brew upgrade` deletes the old keg while those tmux sessions keep running, and `rk update` respawns the code-server session from the *old* CLI process (Go's `os.Executable` trims the ` (deleted)` suffix, `EvalSymlinks` fails on the gone file, and the raw Cellar path survives looking valid) — a Cellar-pinned path therefore dangles after every release. The symlink dangles only for a moment mid-upgrade, so a stat-then-fallback at spawn time would re-pin exactly the path that breaks; `Resolve` stays for brew detection (needs the Cellar marker) and the daemon's own respawn (the daemon session should name the binary actually running).
**Rejected**: teaching the code-bridge extension to fall through to `rk` on PATH when `$RK_BIN` is set but missing (symptom treatment; leaves the install chain and gui spawn broken); a single resolver with a mode flag (two named functions read better at the call site); self-healing an already-running session with a dangling `RK_BIN` (the next respawn carries the fix).
*Introduced by*: 260910-4t9b-stable-rk-path-daemon-spawns

### The install job runs the literal shell chain, exe path quoted
**Decision**: the `code-server-install` job's argv is the shell chain `<quoted-rk-exe> code-server install && <quoted-rk-exe> code-server start`, with the version-stable `selfpath.Stable` exe path quoted via the daemon package's existing `shellQuote`.
**Why**: the chain is the agreed install→start sequencing (daemon start is one-shot; no supervisor loop, Constitution VI), visible verbatim in the job window — a user watching the dashboard sees exactly what runs; `&&` gives success-gated start for free; quoting closes the space-in-path edge `RunJob`'s unquoted argv join documents.
**Rejected**: an `--and-start` flag on install (hides the sequencing inside one process; diverges from the agreed command shape); relying on unquoted paths (breaks on any exe path with a space).
*Introduced by*: 260813-oid2-own-code-server-install

### Staged extract + rename promotion, temp-symlink flip
**Decision**: download and extract into a staging dir under `code-server-bin/`, promote with `os.Rename` to `<version>/`, then flip `current` via temp symlink + `os.Rename`.
**Why**: both promotions are single-syscall renames on the same filesystem — a crash at any point leaves either the old world intact or a garbage staging dir, never a torn active install.
**Rejected**: extracting directly into `<version>/` (a crash leaves a plausible-looking broken install that the ladder would happily spawn); `Symlink`+`Remove` flips (an observable missing-`current` window).
*Introduced by*: 260813-oid2-own-code-server-install

### Install is the migration verb; foreign-session detection is a path-string match, not a spawn-argv version marker
**Decision**: `rk code-server install` respawns a running session whose live `#{pane_start_command}` lacks the managed `current` binary path, behind the daemon gate; the ownership gate on `update` stays.
**Why**: an explicit install is unambiguous intent to move the editor onto the managed binary — it closes the brew-era gap (a PATH binary satisfies rung 2, the update leg gates on the managed dir, the session survives restarts by design, and a fresh install reads already-current to update: nothing else ever migrates) with zero new state and a state-free re-run convergence.
**Rejected**: embedding `RK_CODE_SERVER_VERSION=<ver>` in the spawn argv to also detect a flipped-underneath managed session (grows the spawn contract for a rare corner — update normally runs right after `rk update` restarted the daemon — that honest daemon-down messaging already covers); auto-respawning from the daemon's own start path (Constitution VI — an implicit editor teardown on daemon start is exactly what the sibling design forbids).
*Introduced by*: 260813-2s4u-respawn-aware-code-server-install

### No HTTP probe on enumerated ports
**Decision**: `internal/ports` is a purely observational enumerator — it connects to no port; there is no `probe.go` and no verdict machinery (`probeTTL`/`probeEntry`/`probeCache`/`probePort`/`probeVerdicts`), and `Service` carries no `http:` boolean.
**Why**: a `GET /` to every newly-seen port *consumes* one-shot local servers on first contact — `gcloud`/`gh`/`aws` OAuth callback listeners handle exactly one request, so probing breaks routine CLI auth; there is no safe cadence, because the FIRST probe is the killer. Probing also spams dev-server access logs and can defeat idle-shutdown timers. Constitution §II: state is derived, never interacted with.
**Rejected**: any probing cadence, however slow (the first contact is the damage); an HTTP verdict field on `Service` (nothing can produce it without probing).
*Introduced by*: 260715-vfcz-passive-ports-process-attribution

### `sanitizeEnv` restores the pre-direnv PATH; `cleanPATH` is a last-resort guard only
**Decision**: `CleanEnvForServer()` reverse-applies `DIRENV_DIFF` to recover the operator's true pre-direnv environment INCLUDING PATH, and injects the POSIX-default `cleanPATH` iff no `PATH=` entry survives the reversal — never over a PATH that is already present.
**Why**: the target semantics are "as if the operator had started tmux from `$HOME`", and the reversal already yields the operator's real PATH; unconditionally resetting it to the POSIX default would strip brew, asdf, and every user toolchain from every rk-born tmux server, which is strictly worse than the direnv pollution the sanitization exists to remove.
**Rejected**: an unconditional POSIX-PATH reset (destroys the operator's toolchain PATH); dropping `cleanPATH` entirely (a reversal that leaves no PATH at all would give the server none).
*Introduced by*: 260706-6mpm-direnv-diff-reversal-server-env

### `layoutspec` surface kinds are exactly the frontend `ViewName` registry
**Decision**: the Go validator's surface registry contains exactly
`tty`/`web`/`code`/`gui` — the frontend `ViewName` union — with no backend-only kinds;
`rk tab layout set/--add/--promote` rejects anything else as unknown-surface.
**Why**: a kind the frontend cannot render (it parse-rejects and heals to
`single:tty`) must not validate at the CLI — accepting one writes stored layouts
that silently self-heal into a different layout, a user-reachable inconsistency.
Keeping the two registries identical makes the port-of-`surface-layout.ts` claim
hold in both directions, and stored layouts carrying a retired kind heal to
`Default()` exactly as any invalid layout does.
**Rejected**: accepting extra kinds backend-side and relying on frontend healing
(validates input that can never render as stored).
*Introduced by*: 260904-0mrk-chat-lens-residual-code-trim

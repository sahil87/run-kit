# run-kit UI — Lenses & Surface Layout

## Iframe Window (the `web` lens renderer)

`app/frontend/src/components/iframe-window.tsx` — the renderer for the **`web` surface/lens** (§ Window Views (Lens Model)), mounted as a tile by `SurfaceLayout` whenever the layout's order includes `web` (§ Surface Layout). The `web` surface is ALWAYS available (§ Window Views (Lens Model)) — the tile renders the window's **web-tab family**: `SurfaceLayout` feeds `tabs={webTabs ?? []}` and `active={webActive}` (overlaid by the store's optimistic web override while select/remove/move is in flight — § Optimistic select/remove/move below), and the component derives the active address itself (`webTabs[(webActive || 1) - 1] ?? ""`, clamped — the same value `activeWebUrl(win)` yields). Stored `@rk_win_web_<n>` values may be site-relative paths beyond `/present/` and `/proxy/`; `/tutorial/ch*.html` companion pages are the first shipped consumer, and each viewer resolves them against its own run-kit origin. A family with declared tabs mounts one iframe PER TAB; the strip ALWAYS renders with the tile — at 0 tabs/0 drafts it is just the trailing `+`, keeping the draft entry points reachable from the empty state; an empty family selects the tile's ONBOARDING content state below the strip (§ Onboarding state below); and an out-of-range active pointer clamps to the family, never to onboarding. Bottom bar is NOT rendered for a web tile (no terminal to send keys to). The component takes `tabs`/`active`, an optional `onWriteUrl: (url: string) => Promise<unknown>` address-bar write seam (the caller owns the slot index — `SurfaceLayout` binds it to the active `@rk_win_web_<n>` option write, n = `webActive` or 1 while the pointer is unset), optional strip verb callbacks (`onSelectTab(n)` / `onCloseTab(n)` / `onAddTab(target) → {index, existed}` / `onMoveTab(n, to)` — the caller owns the POSTs; the component re-renders declared state from the next `tabs`/`active` props and never renumbers it locally), and three optional interaction seams — an `onInteract: () => void` tile-focus seam, a `shouldReclaimChord` chord-reclaim predicate, and an `onPageMeta: (meta: { title: string | null }) => void` page-meta seam (all below). It owns ephemeral draft and per-frame chrome state but no persisted view/URL/localStorage state; it mutates no `@rk_win_lens` (§ Window Views → decoupling). View switching is owned by the top-bar surface toggles / mobile switch group and the palette — the tile itself carries no switch-to-terminal affordance. (260714-t97o, 260812-ab5v, 260819-v6y4, 260821-zqlq, iip5, 9kip, s36e, 6uu0)

**Layout**: Outer wrapper `flex flex-col flex-1 min-h-0` with up to six children: the web tab strip (`shrink-0`, always rendered — § Web tab strip below), the URL bar (`shrink-0`), the find bar (`shrink-0`, rendered only while open — § Find bar below), the load progress line (rendered only while the ACTIVE frame loads — § Load progress line below), an in-tile error state (rendered in place of the ACTIVE iframe's VISIBLE area while active — § Error states below), and the content-zoom wrapper (`flex-1 min-h-0 overflow-hidden`) holding one `<iframe>` PER DECLARED TAB — each `key`ed by its URL, every non-active frame `hidden` but never unmounted (P3; § Web tab strip below). In the ONBOARDING state (empty family) the wrapper holds the strip (bare `+` plus any open drafts), the reduced URL bar, and the onboarding panel — the frames, find bar, progress line, and error/probe machinery do not mount (§ Onboarding state below).

**Web tab strip**: a `role="tablist"` strip (`data-testid="web-tab-strip"`, `shrink-0`, horizontally scrollable, 11px monospace, the tile-header `bg-bg-card border-b border-border` idiom) always renders above the URL bar — at 0 tabs/0 drafts it holds only the trailing `+` (a tablist with zero `role="tab"` children is the accepted resting shape), so the empty family keeps its draft entry points. Each declared tab (`role="tab"`, `aria-selected`, `data-testid="web-tab"`, `data-index={n}`, `title={displayForm(url)}`) labels itself with its URL-keyed tracked document title and falls back to `webTabTitle(url)`/`#n`. Its icon slot shows a per-frame loading spinner, static under `prefers-reduced-motion`; after load it shows the same-origin document's icon link or frame-origin `/favicon.ico`, an external host's `https://{host}/favicon.ico`, or the `classifyAddress` kind dot (green present / amber proxy / blue external) when no icon applies or an image errors. A cross-origin navigation clears the tracked title, location and icon derived from the prior readable document so the stored URL drives the fallbacks. The close `×` is always rendered on the active tab and on coarse pointers, hover/focus-within-revealed otherwise; `auxclick` button 1 closes through the same `onCloseTab` path. The strip is a ROVING-FOCUS tablist: only the selected entry is in the tab order; ←/→/Home/End move focus without writing; Enter/Space select; Delete/Backspace close; component-local ⌥⇧←/⌥⇧→ moves the active declared tab one slot through `onMoveTab`, with boundary presses as silent no-ops. Pointer drag crosses a 6px threshold before becoming reorder, paints a green drop-side indicator on the hovered tab edge, and commits one `onMoveTab(from, to)` on release; drafts are neither drag sources nor targets. The trailing `+`, a double-click on empty strip space, and the palette's `Web: New tab` event append a dashed viewer-local draft after every declared tab and focus the address bar. Multiple drafts may coexist. Enter materializes the selected draft through `onAddTab`, selects the returned server-assigned slot through `onSelectTab(index)`, and removes the draft after add resolves; add idempotence may return an existing slot. Escape or the draft's `×` discards only that draft without a POST. Drafts live for one mounted window tile and disappear on window switch/unmount. The `+` disables at the declared-family cap (`tabs.length >= 8`) with a `web tabs full (8)` Tip; add errors surface inline in the address bar's `role="alert"` submit-error slot. **Frames**: the zoom wrapper mounts one `<iframe key={url}>` per declared tab — every non-active frame `hidden` (`display:none`), never unmounted by selection or reorder and never re-`src`d, so in-page state survives tab switches; URL keys keep close and move renumbering from remounting frames. Frame-scoped state (ref, loading, cross-origin, tracked location, title, favicon, probe/error) lives in the extracted per-tab `WebFrame` and reports into the parent's URL-keyed chrome-state map; the URL bar, back/forward, refresh, find bar, progress line, error surface, `onPageMeta`, and zoom bind to the ACTIVE frame, while every same-origin frame contributes its title/icon to its own tab. All frames mount EAGERLY (the family cap of 8 bounds the count; no lazy mount, no LRU) and inactive frames run no dead-port probe timer — a frame probes on first mount and on activation. The document CustomEvents (`web-find:open`, `web-address:focus`, `web-tab:open-draft`, `web-open-external`, `web-zoom`) keep their single listeners on the ONE `IframeWindow` per layout. e2e: `web-tabs.spec.ts` seeds real tmux families and covers the one-tab strip, drafts and materialization/discard, drag/keyboard/palette reorder, middle-click close, shared-state convergence, and URL-keyed mounted frames. (9kip, s36e)

**Optimistic select/remove/move**: the strip verbs are wired in `SurfaceLayout` (`components/surface-layout.tsx`) through `useOptimisticAction` over the window store's per-entry `webOverride { webTabs?, webActive? }` (display only). Select sets `{ webActive: n }`; remove derives the local family with `webFamilyAfterRemove(tabs, active, n)`; move derives it with `webFamilyAfterMove(tabs, active, n, to)`, including the active-pointer repoint. Synchronous override refs make consecutive gestures compound on the family already displayed instead of stale SSE payload. Move POSTs are serialized in gesture order. A rejected move rolls back to the SSE-confirmed family, cancels every queued dependent move whose indices came from the rejected optimistic family, fires no dependent POST, and emits one error toast; dependents are dropped rather than reinterpreted against different indices. Successful verb POSTs wake the SSE hub, and a reconcile effect clears the override once the payload matches; a window switch (the parent's `${server}:${windowId}` key) drops any in-flight override. Add is not optimistic because the slot index is server-assigned; `addWebTab` receives `toWebAddTarget(target)` so a root-relative `/proxy/…` draft reaches the backend's `rk present`-shaped target resolver. The component types verbs as promise-returning; optimistic executors are fire-and-forget, so the `SurfaceLayout` wrappers resolve at once. (9kip, s36e)

**URL Bar**: Thin toolbar above the iframe (`border-b border-border bg-bg-primary`), one warm-tip `TipGroup` cluster, button order per the approved design study (`fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html`):
- **Back / Forward buttons** (`WebBackGlyph`/`WebForwardGlyph` — `data-icon="web-back"`/`"web-forward"`, register arrow SVGs) — drive `contentWindow.history.back()/forward()` on same-origin frames; both are HIDDEN when the frame is cross-origin (cross-origin history is unreachable to a parent by design). The navigation is per-viewer view state and never touches the stored web tab (spec window-views R7). The buttons render enabled whenever same-origin — a parent has no reliable canGoBack signal, and a boundary click is a harmless no-op. (260819-v6y4)
- **Refresh button** (`RefreshGlyph` — `data-icon="refresh"`, the same register export the top-bar RefreshButton renders) — a REAL reload on same-origin frames: `contentWindow.location.reload()` preserves the frame's CURRENT location and in-page state (no reset to the stored tab address); the `about:blank` bounce (clear `src`, re-set via `setTimeout(0)`) remains ONLY as the cross-origin fallback. Styled: `w-7 h-7 rounded hover:bg-bg-card text-text-secondary hover:text-text-primary` — every URL-bar button carries the tile-verb hover brighten. (260819-v6y4, 76uz)
- **Address input (display/edit split)** — at rest it SHOWS the kind-specific DISPLAY form (`displayForm(rawAddress)`, § Address model below — a proxied `/proxy/3000/…` reads `localhost:3000/…`, a presented file reads its basename with the `server`/`v` plumbing params hidden, an external URL reads host+path with the scheme omitted). Focusing it reveals the RAW editable value (the tracked frame location when known, else the active tab's address) with select-all. On Enter the input is normalized (`normalizeAddressInput` — bare `localhost:{port}`/`127.0.0.1:{port}` → `/proxy/{port}/…`, bare domain → `https://…`, already-valid values pass through) and scheme-checked (`isAllowedUrl`, the frontend mirror of the backend web-tab scheme allowlist — an invalid scheme surfaces an inline `role="alert"` error and fires NO POST). With a selected draft, Enter calls `onAddTab(normalized)`, selects the returned index, and removes that draft after success; otherwise it calls `onWriteUrl(normalized)` and a same-URL submit is a no-op. `SurfaceLayout` binds the write seam to `setWindowOptions(server, windowId, { "@rk_win_web_<n>": url })` → `POST /api/windows/{windowId}/options` (partial-merge — n = `webActive`, or slot 1 while the pointer is unset). Escape reverts a declared tab's edit without a POST or discards the selected draft; an ordinary blur restores the rest display. The address bar REPLACES the active declared slot; the strip `+`, empty-space double-click, and palette `Web: New tab` open drafts that materialize through add — § Design Decisions → Address bar replaces, `+` adds. On a replace failure the input reverts to the SSE-confirmed address; on a draft-add failure the draft remains selected with its submitted value and inline error for retry. Styled: `bg-bg-card text-text-primary text-sm px-2 py-1 rounded border border-border`. Editing a declared content address is *substrate* state (shared, POSTed, every viewer sees it); editing an unmaterialized draft is viewer-local and never POSTed. (260529-jad6, 260819-v6y4, iip5, 9kip, s36e)
- **Find button** (`FindGlyph` — `data-icon="find"`, the same register export as the tty tile's find toggle: one find identity across surfaces; `aria-label="Find in page"`, `aria-pressed` while open — lit `text-accent-green` when the bar is open) — the pointer/touch entry point to the find bar; toggles it locally (the chord and palette entries share one open seam instead, § Find bar)
- **Open-in-browser button** (`OpenExternalGlyph` — `data-icon="open-external"`, register arrow-up-right; `aria-label="Open in browser"`, rightmost) — opens the CURRENT address (the tracked frame location when known, else the stored tab address) in a new tab via `window.open(…, "_blank", "noopener")`; relative addresses resolve naturally against the viewer's origin (the stored address stays relative per the display contract `docs/site/skill/display.md`). The universal escape hatch for anything the tile can't render; the `Web: Open in browser` palette action mirrors it (§ Address model below — the document-CustomEvent seams). (260819-v6y4)

**SSE Sync**: a `useEffect` on the derived active address syncs the URL bar text (`setInputUrl(url)`) and clears the submit error on every active-address change — an SSE push, a tab select, or a same-slot replace. The iframe side needs NO sync effect: a changed tab URL re-keys (remounts) exactly that frame, and a selection change only flips `hidden` — no frame's `src` is ever rewritten by the parent, so identical SSE ticks and tab switches reload nothing. When the active web tab changes externally (an agent or another viewer runs `tmux set-option -w @rk_win_web_<n>` or a web verb), the next payload repaint flips the visible frame and the URL bar follows automatically. (9kip)

**Interaction + reclaim seam (`onInteract`, `shouldReclaimChord`)**: in-frame clicks and keydowns stay in the frame's own document, and focus entering a frame fires NO focusin in the parent — parent-document listeners are blind to them. The component attaches capture-phase `pointerdown`/`keydown` listeners to the same-origin `contentDocument` after every iframe `load` (each navigation replaces the document; cross-origin access throws and is skipped silently — the `CodeSurface` attach pattern) plus a parent-window `blur` fallback that reports when `document.activeElement` is the iframe, covering cross-origin embeds. Every in-frame keydown reports `onInteract` FIRST, then — when a `shouldReclaimChord` predicate prop is injected — a keydown matching it is `preventDefault` + `stopImmediatePropagation`ed inside the frame and re-dispatched as a synthetic bubbling `KeyboardEvent` on the parent **document** (the CodeSurface `onKey` mechanism, byte-for-byte — § Code Surface → Chord reclaim): run-kit's registry chords (⌘K, ⌘;, ⌘F, …) keep working with focus inside the frame while every non-claimed key reaches the framed page untouched (typing into an in-frame form is unchanged). `SurfaceLayout` injects the predicate bound to the `web` kind (`shouldReclaimChord("web")`, the kind-aware factory in `app.tsx` — § Surface Layout → Tile renderer), so `ttyOnly` chords pass through to the framed page and `webOnly` chords (⌘F, ⌘L) reclaim only here (§ Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags). Cross-origin frames get no reclaim — the `blur` fallback stays the only interaction signal, and once a cross-origin frame holds focus, later in-frame clicks report nothing — accepted, the tile is already focused by then. `SurfaceLayout` wires the seam to tile focus (§ Surface Layout → Focused tile); both props are optional and other mount contexts omit them unchanged. (260815-41t9, 260819-ie2i)

**Find bar (⌘F find-in-page)**: the web tile ships in-frame page search for same-origin content — a `shrink-0` row rendered between the URL bar and the iframe while open (`data-testid="web-find-bar"`, the URL bar's border/background vocabulary; layout per the approved design study `fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html` state 03). The row is the shared presentational **`FindBar`** component (`components/find-bar.tsx`, colocated `find-bar.test.tsx`) — props-driven (`query`/`matchIndex`/`matchCount`/`onQueryChange`/`onNext`/`onPrev`/`onClose`, plus optional `toggles`, `disabled`, `statusText` (replaces the counter), and `scopeNote`), the consumer owning the search mechanism — also mounted by the tty tile (§ Tile renderer → tty find bar); `IframeWindow` owns the in-frame engine and passes no toggles. Row contents in order: an autofocused text input, the `n/N` match counter with the active ordinal in accent green (`0/0` when the query matches nothing), ∧/∨ previous/next buttons, a ✕ close button, and a right-aligned key hint `Enter next · ⇧Enter prev · Esc close` suppressed on coarse pointers (`useCoarsePointer()` — keyboard-chord copy never renders on touch). Enter advances to the next match, Shift+Enter to the previous (both wrap), Escape closes the bar and clears all highlights. Three entry points share ONE open seam: the ⌘F/Ctrl+F `web-find` chord (reclaimed inside the frame or handled at tile level while the web tile owns focus — § Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags) and the `Web: Find in page` palette action both dispatch the `web-find:open` document CustomEvent (`WEB_FIND_OPEN_EVENT`), which the mounted web tile listens for (the `window-heading:rename` / `theme-selector:open` precedent — one `IframeWindow` per layout hosting N frames, so the receiver is unambiguous; the listener acts on the ACTIVE frame); the ⌕ URL-bar button (the pointer/touch entry) toggles the bar locally. A cross-origin frame renders the bar DISABLED — input and navigation buttons disabled, the inline hint `page is cross-origin — find unavailable` in place of the counter — and no search is attempted (⌘F pressed while a cross-origin frame holds focus never reaches the parent at all, so the ⌕ button and the palette are the bar's entry points there). Every ACTIVE frame `load` resets the find state — matches, highlights, and the query die with the document they were collected from (no term persistence across navigations); the bar's open/closed state itself survives navigation. (260819-ie2i, 260819-zqf9)

**Find engine (`lib/find-in-page.ts`)**: a pure module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract), parent-driven over the same-origin `contentDocument` — no script injected into the framed page. `collectMatches` walks the frame document's text nodes with a case-insensitive TreeWalker into DOM `Range`s (skipping non-rendered containers like `script`/`style`); `stepMatch` is the wrap-around active-index transition; `applyHighlights` registers two CSS Custom Highlights (`rk-find` all matches, `rk-find-active` the active match with its accent-green outline) on the FRAME window's `CSS.highlights` and installs one `<style>` element of `::highlight()` rules into the frame's `<head>` (inert DOM — `clearHighlights` removes both on reset); the active match scrolls into view (`block: "nearest"`). Where the Highlight API is unavailable, `contentWindow.find()` is the best-effort fallback — navigation works, the counter may read the zero form. All frame-DOM access carries the attach seam's try/catch posture (pre-load and cross-origin frames no-op silently). Unit-provable in jsdom without the Highlight API. e2e: `web-tile-find.spec.ts` on the real-tmux port-3020 rig (the `web-view-lens.spec.ts` `_tmux.ts` pattern) proves ⌘K opening the palette with focus inside a same-origin web-tile frame, the ⌘F open → match count → Enter navigation → Escape close flow on a presented HTML file, and the cross-origin disabled bar + hint via the ⌕ button. (260819-ie2i)

**Address model (`lib/web-url.ts`)**: a pure, DOM-free module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract) owning every derivation over a stored `@rk_win_web_<n>` address or an address-bar keystroke. `classifyAddress(url)` returns one of four kinds — `present` (any root-relative `/present/…`, covering both `/present/{server}/{roothash}/{path}` and the legacy `/present/{windowId}/{n}/{path}?server=` arm), `proxy` (root-relative `/proxy/{port}/…` OR an absolute loopback `http(s)://localhost|127.0.0.1|[::1]:{port}…`), `external` (any other absolute http(s) URL), `relative` (any other root-relative path) — driving the header badge and error posture; unrecognized input degrades to `relative`, never throws. `displayForm(url)` is the kind-specific resting form: a presented file shows its basename, with content-keyed `server`/`roothash` path segments and the legacy `server` plus shared `v` query plumbing excluded; a presented directory or degraded shape retains the raw-address fallback; proxy shows `localhost:{port}{path}`; external shows `host{path}{?query}` with the scheme omitted; relative stays raw. `normalizeAddressInput(input)` maps bare loopback `host:port[{path}]` to `/proxy/{port}{path or /}`, maps a bare domain to `https://…`, and otherwise passes through for `isAllowedUrl` to validate. `isAllowedUrl(input)` mirrors the backend allowlist (absolute http/https with a host or root-relative). `proxyPortOf(url)` returns the proxy-kind port; `toProxySrc(url)` owns iframe-src mapping. `webTabTitle(url)` is the shorter tab label: presented files show the basename with both address shapes' plumbing excluded, proxy shows `localhost:{port}{path}`, external shows the host, and relative stays raw; directory/degraded present shapes retain the raw-address fallback, and empty input returns `""` for the caller's `#n` fallback. `toWebAddTarget(url)` passes both present shapes through unchanged and re-expresses only a root-relative `/proxy/{port}…` address as `http://localhost:{port}…` for the backend's `rk present`-shaped add parser. The module exports `WEB_ADDRESS_FOCUS_EVENT` (`web-address:focus`, the plain ⌘L/palette focus seam), `WEB_TAB_DRAFT_EVENT` (`web-tab:open-draft`, the palette's draft-opening seam), and `WEB_OPEN_EXTERNAL_EVENT` (`web-open-external`, the palette seam). Each follows the `WEB_FIND_OPEN_EVENT` single-receiver pattern: one `IframeWindow` per layout hosts N frames, so one listener can act on the active frame or tile-local draft state. Display derivation never rewrites the stored relative address. (260819-v6y4, 9kip, 260901-ei4t-present-url-server-root-hash, s36e)

**Current-path tracking + page meta**: every `WebFrame` handles its own `load` events through the attach seam's try/catch posture. A same-origin frame stores its location root-relative (viewer origin stripped), document title, and favicon link or frame-origin `/favicon.ico` in the parent's URL-keyed chrome map; every tab can therefore show metadata from its own frame. An unreadable cross-origin load clears that frame's tracked location/title/favicon so stored-URL fallbacks apply. The address bar, navigation controls and optional `onPageMeta` header seam bind only to the ACTIVE map entry; `SurfaceLayout` holds the active title for the tile header. All metadata and in-frame navigation are display-only and never POSTed; only explicit Enter on a declared tab's address writes its slot. (260819-v6y4, 9kip, s36e)

**Onboarding state (empty web-tab family)**: with no tab to render (`tabs.length === 0`), the tile mounts the ONBOARDING state in place of the frames and their probe machinery — the branch is `onboarding = tabs.length === 0`, and NO frame-check/dead-port probing runs (the probes key off an address; § Error states below). With ≥1 tab every frame mounts regardless of the active pointer's value (an out-of-range pointer clamps, never shows onboarding). The **reduced URL bar** keeps only the REFRESH button and the ADDRESS INPUT — back/forward, the find ⌕ button, and the ↗ open-in-browser button are hidden (nothing to navigate, search, or open) — and the input is FULLY LIVE with placeholder `localhost:3000 · /present/… · https://…`: typing an address + Enter runs the existing submit pipeline (`normalizeAddressInput` → `isAllowedUrl` → `onWriteUrl` → the slot-1 `@rk_win_web_1` POST, § URL Bar above) and boots the tile for real — the bar is itself an init path. The **body panel** (replacing the frames; centered, monospace, on `bg-bg-primary`) carries a large dimmed `://` glyph, the heading **"Nothing to show yet"**, the subhead *"this tile follows the window's active web tab (@rk_win_web_N) — three ways to fill it:"*, three instruction rows (accent-green lead glyph, bold lead-in, `bg-bg-inset` bordered code chips): `❯` **Ask your agent to show something** — "Present this as a page" — the agent runs `rk present ./report.html` and it appears here (HTML files, diagrams, mocks, directories); `⇄` **Preview a dev server** — type `localhost:3000` in the address bar above (proxied through run-kit, works from any device), or have the agent run `rk present :3000`; `↗` **Open any URL** — external sites embed when they allow it, and find-in-page (⌘F) + back/forward work on same-origin pages. A dimmed footer reads *"the tile goes live automatically when an address lands ● no reload needed"*. The tile header renders the plain `://  Web` label — no kind badge, no page title, no meta chip (§ Surface Layout → Tile chrome). The flip is automatic in BOTH directions — `onboarding` derives from the tab family's emptiness (§ SSE Sync), so an empty→non-empty transition swaps the panel for the live frames with no user action, and non-empty→empty returns to onboarding; `present-auto-expand` is untouched — an already-open onboarding tile flips in place via the `withAutoWeb` identity arm (§ Surface Layout → Present auto-expand). The find entry points no-op here: the `Web: Find in page` palette entry is content-gated on `hasWebUrl` and the tile's own `web-find:open` listener double-guards ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § `web-find`). (260821-zqlq, 9kip)

**Error states (fail loudly)**: a silent blank iframe is not a reachable state for a probed-blocked external URL or a dead proxied port — the tile renders an explicit error surface (`data-testid="web-tile-error"`) IN PLACE of the ACTIVE iframe's visible area, copy per the design study (states 05/06). Three kinds: **frame refusal** — for `external`-kind addresses the frontend calls `GET /api/frame-check` (`checkFrame`, [architecture](/run-kit/architecture.md) § API Layer) on address change; `embeddable: false` renders "`{host}` refuses embedding" + the reason line + an Open in browser ↗ button; **unreachable external** — `reachable: false` renders "`{host}` can't be reached" + the probe reason + the same hatch; **dead proxied port** — for `proxy`-kind addresses a same-origin `fetch` of the proxied path reads the reverse proxy's 502 (nothing listening) and renders "nothing listening on :{port}" + "connection refused — the dev server may have stopped" + a ↻ Retry button that re-runs detection and reloads (a nonce re-fires the probe effect). Present/relative kinds never probe; a same-origin fetch FAILURE (the app server itself down) is not a dead upstream and leaves the iframe alone. The probes live in the per-tab `WebFrame` and run on first mount and on ACTIVATION only — an inactive frame runs no probe timer and renders no error surface; only the active frame's entry feeds the tile's error render. The error state clears on the next address change/retry. The errored iframe stays MOUNTED but `hidden` beneath the error surface (§ Design Decisions → Error states render over a hidden, still-mounted iframe). (260819-v6y4, 9kip)

**Load progress line**: a 2px indeterminate accent-green sweep (`.rk-web-progress` in `globals.css`, `data-testid="web-load-progress"`) rendered at the content's top edge while the ACTIVE frame loads — set on the active frame's src change/reload/history navigation, cleared on that frame's `load` event (the element's presence IS the state; inactive frames carry no progress line). Under `prefers-reduced-motion` the sweep zeroes to a static dim line — load feedback is never motion-only. (260819-v6y4, 9kip)

**Content zoom**: the web tile magnifies its guest content by a per-viewer zoom level `s` applied as a SCALE WRAPPER on the ACTIVE frame — that iframe renders inside the `overflow-hidden` wrapper (`data-testid="web-zoom-frame-wrapper"`) at `width/height: 100%/s` with `transform: scale(s); transform-origin: 0 0`, so zooming in shrinks the frame's CSS viewport and responsive guest layouts adapt exactly as under real browser zoom; at `s = 1` no transform is applied and the layout is identical to an unzoomed tile. The mechanism never reaches into the guest document, so it covers all four address kinds including cross-origin `external` (§ Design Decisions → Scale wrapper over guest-document CSS zoom). Zoom has TWO trigger families with different quantization (the Chrome/macOS convention): CLICK/SHORTCUT zoom steps the discrete ladder; GESTURES are CONTINUOUS — the factor tracks the fingers through arbitrary values, clamped to `[WEB_ZOOM_MIN, WEB_ZOOM_MAX]` (0.5–3, the ladder's ends). The pure, DOM-free `lib/web-zoom.ts` (colocated tests, the `web-url.ts` module contract) owns the derivations: the browser-standard ladder `WEB_ZOOM_LEVELS` (50%–300%, default/reset 1) + `stepWebZoom` (clamps at the ends, snaps an off-ladder value to the nearest level FIRST — the load-bearing bridge from a gesture-set float to the button/palette ladder: a `+` click from 137% snaps to 125% and lands on 150%); `webZoomKeyFor(url)` — the persistence bucket derived via `classifyAddress`: `external` → the URL's origin, `proxy`/loopback → `proxy:{port}`, `present`/`relative` → the single viewer-origin bucket `self` (presented files rotate paths, so per-path buckets would fragment state); and try/catch-noop `readWebZoom`/`writeWebZoom` over ONE localStorage key `runkit-web-zoom` holding a `{[bucket]: level}` map — `readWebZoom` returns the stored FLOAT clamped to the bounds, never snapped (a gesture-set 1.37 reloads as 1.37; the ladder snap lives solely in `stepWebZoom`), `writeWebZoom` rounds to 2 decimals and a round-to-1 value removes the entry (100% is the absent state, robust to gesture float noise), per-viewer state only, never POSTed (Constitution IV; spec window-views R7). `IframeWindow` seeds its zoom state from the ACTIVE address's bucket and re-seeds when the bucket changes — an active-tab change switches buckets (per-viewer, per-bucket — not per tab). Persistence timing differs by family: click-path writes are immediate; gesture writes ride a trailing debounce (`ZOOM_PERSIST_DEBOUNCE_MS = 250` — a pinch emits dozens of events) whose pending write FLUSHES, never drops, on unmount and on bucket change (the flush targets the OLD bucket before re-seeding). **Triggers**: (1) a compact control in the URL-bar cluster between the find ⌕ and open-external ↗ buttons (`data-testid="web-zoom-control"`; text-glyph `−`/`+` steppers with the percent readout between them doubling as the reset affordance — disabled at 100% — in the `w-7 h-7 rounded hover:bg-bg-card` + `Tip` URL-bar button vocabulary) — the universal floor trigger, and the only one that works over an `external` frame; NOT rendered in the onboarding state (the reduced URL bar keeps only refresh + address input). (2) The palette's `Web: Zoom in`/`Web: Zoom out`/`Web: Reset zoom` actions ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) dispatch the `web-zoom` document CustomEvent (`WEB_ZOOM_EVENT` in `lib/web-zoom.ts`, `detail.direction: "in" | "out" | "reset"` — the `web-find:open` precedent: the mounted tile is the single receiver, double-guarded to no-op on a contentless tile). (3) Ctrl/Cmd+wheel and touchpad-pinch gestures — CONTINUOUS, applied per event: each ctrl/meta wheel event maps `s → clamp(s * exp(-deltaY * WHEEL_ZOOM_SENSITIVITY))` (`applyWheelZoom` in the shared `lib/zoom-gesture.ts` — exponential, so equal deltas multiply equally and a reversed gesture returns to its start), and Safari's `gesturechange` sets `clamp(base * scale)` from a base captured at `gesturestart` (its scale is cumulative — no accumulator state); the stepped accumulator family in the same module remains the TERMINAL's ([terminal](/run-kit/ui/terminal.md) § Terminal Font Size → Gesture triggers — integer font steps are inherently discrete). Both families arrive through TWO non-passive capture arms — one on the tile's own wrapper (covering the URL bar, find bar, and error surface, all parent-document DOM) and one attached to each same-origin frame's document on every `load` (the chord-reclaim attach posture: try/catch, cross-origin/pre-load skips silently, re-attaches per navigation) — a wheel event over an iframe never reaches the parent document, so both arms are needed. Over a cross-origin (`external`) frame gestures are unreachable — accepted platform limit, no fallback attach; the chrome control and palette remain the triggers. Only ctrl/meta-modified wheel and Safari `gesture*` events are intercepted (`preventDefault` — the gesture never becomes browser page zoom); everything else passes through untouched. e2e: `web-tile-zoom.spec.ts` on the real-tmux rig (the `web-view-lens` pattern) proves control stepping, reset to 100%, persistence across reload, onboarding absence, palette stepping, and the continuous gesture semantics (an in-frame ctrl-wheel lands on the off-ladder `182%`, a small tick compounds with no threshold, and a `+` click snaps back onto the ladder) on a same-origin page. (260823-cwvv, 260824-iafo, 9kip)

**Proxy URL conversion**: `toProxySrc(url)` (`lib/web-url.ts`, § Address model above) maps an absolute loopback URL to its same-origin proxy path: `http://localhost:8080/docs` → `/proxy/8080/docs`. Portless loopback and every other address pass through unchanged (relative addresses are already same-origin).

**Iframe attributes**: `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"` (without `allow-downloads`, VS Code file downloads break — the same sandbox `CodeSurface` reuses, § Code Surface), `title="Proxied content"`, `border-0`.

**Window creation**: "Tab: New Iframe Tab" command palette action (id `create-iframe-window`) opens a `Dialog` with two inputs: window name (autofocused, Enter focuses URL input) and URL (Enter creates window). Create button disabled until both fields non-empty. Calls `createWindow(server, session, name, undefined, url)` — the API client maps a given URL onto the `{ rkType: "iframe", rkUrl: <url> }` POST body (the backend keeps those body field names this release — Change 1 R10 — and stamps `@rk_win_layout=single:web` + `@rk_win_web_1` + `@rk_win_web_active=1`). Backend uses `CreateWindowWithOptions` for atomic `\;`-chained tmux command. Only shown when a session is active. Synthetic iframe windows are created this way. (260714-t97o, 260820-lfla, iip5)

## Code Surface (the `code` lens renderer)

`app/frontend/src/components/code-surface.tsx` — the renderer for the **`code` surface/lens** (§ Window Views (Lens Model)) — mounted as a tile by `SurfaceLayout` whenever the layout includes `code` (§ Surface Layout): via the top-bar surface toggles, the `Tile: Show Code` palette entry, or the switcher's `View: Code` row (which applies `single:code` through `switchView`). It embeds **code-server** at the window's code root — a full editor (tabs, syntax highlighting, SCM view, side-by-side diffs) beside the live agent terminal with no editor functionality built in run-kit. It is a lean component, NOT an `IframeWindow` reuse: the code-server URL is fully DERIVED, so the URL bar (`@rk_win_web_<n>` substrate chrome) is meaningless here — the component is exactly an iframe plus the not-running empty state (§ Design Decisions → The code surface is a lean `CodeSurface`). (260811-k3vp)

- **src** — `codeServerSrc(folder)` returns the RELATIVE path `/code/?folder=<folder>` (folder value `encodeURIComponent`d), never a composed absolute origin and never a port — the same relative-path discipline `toProxySrc` follows, so the embed rides the same origin through any reverse proxy. The path is STABLE: code-server keys browser-side workspace state by the proxy pathname, and `/code/` is fixed by the backend route (the port behind it is a private implementation detail, resolved server-side). code-server restores per-folder state from the `?folder=` param. The folder is the window's code root (`codeRootFor(win)` = the shared `@rk_win_code_root` when set, else the live `gitRoot` derivation — § The code root), and the computed `src` is held in a **ref keyed to the iframe's MOUNT GENERATION** (the `reachable` gate): a code-root update never rewrites a live frame's `src`, while a genuine remount (a reachability `false→true` flip, a window switch) boots the CURRENT code root.
- **Availability vs reachability** (spec right-panel.md § Surface Registry): AVAILABILITY = `codeRootFor(win)` is non-empty — the shared `@rk_win_code_root` OR a `gitRoot` derives non-empty — the STABLE capability signal (`hasCode`, computed over the payload), so the surface toggle / switcher segment never strobe when the active pane leaves the repo (the port is always resolvable by convention, so the "configured" leg is always true). REACHABILITY (the host's TTL-cached probe, the state socket's `code-server` event) selects the surface's CONTENT only: reachable renders the iframe; unreachable renders the terse monospace empty state `code-server not running — check rk doctor` (`data-testid="code-surface-empty"`) instead of a dead iframe.
- **Sandbox** — the same token set as `IframeWindow`, including `allow-downloads` (without it VS Code file downloads break).
- **Chord reclaim** — focus inside the iframe swallows run-kit's chords (`⌘K` collides with VS Code's own), and same-origin makes an escape hatch possible: a capture-phase `keydown` listener attached to the iframe's `contentDocument` after every load intercepts events matching the INJECTED `shouldReclaimChord` predicate (built in `app.tsx` from the keybinding registry's pure, kind-aware `hasReclaimableMatch(e, bindings, kind)` — `findMatches(...).some(...)` over the surface-restriction flags, here bound to the `"code"` kind), `preventDefault` + `stopImmediatePropagation`s them before the embedded app's keybinding service, and re-dispatches a synthetic bubbling `KeyboardEvent` on the parent **document** (reaching both document-level listeners — the palette chord — and window-level ones — the dispatcher). The reclaim carve-outs: a keydown whose ONLY registry matches are `ttyOnly` bindings (the tmux split pair — a keydown arriving inside the iframe means the code tile owns focus) is NOT reclaimed, so ⌘D reaches code-server's own keybinding service, and a `webOnly` match (⌘F web find) is NOT reclaimed in the code iframe either — code-server keeps its own find — while unrestricted registry chords (⌘K, ⌘;, ⌘2, ⌃`, …) are reclaimed — ⌃` deliberately preempts code-server's own integrated-terminal toggle, the hop back to tty winning over the embedded app's binding (260812-wfic, 260819-ie2i). The effect is keyed on `reachable` (the iframe only mounts when reachable, so a reachability flip re-runs it against the fresh iframe), re-attaches on `load` (each navigation replaces the document), guards `contentDocument` access in try/catch (a cross-origin or pre-load frame silently skips the attach — click-out remains the escape), and removes the listener from the attached document on cleanup. Proven by the `code-surface.spec.ts` e2e "keyboard spike: a registry chord pressed INSIDE the iframe reaches the parent" (§ Design Decisions → Chord-reclaim via a capture-phase iframe listener).
- **Load-time focus grab — guarded** — the code-server workbench grabs DOM focus once per iframe load (a script `focus()` at editor-restore time that no VS Code / code-server setting suppresses), which would otherwise win every window switch and flip `focusedTileKind` to `code`, killing all `ttyOnly` keybindings. Per-window focus memory plus a steal guard answer it: `CodeSurface` reports the grab through the `onProgrammaticFocus?: () => boolean` prop, fed by a capture-phase `focusin` listener on the frame's contentDocument attached by the same load/attach effect as chord reclaim (the ONLY observable — a script `focus()` re-points the focus chain but fires no parent-side iframe event); `app.tsx` reverts an armed grab whose remembered kind is not `code`. The tile wrapper's `onFocus` consults the guard before `focusSlot`, so a grab never settles the focused kind on `code` (§ Surface Layout → Tile renderer). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (260815-ltz7)

### The code root — `@rk_win_code_root` seed + follow

The folder the editor opens is the shared, per-window tmux option **`@rk_win_code_root`** (surfaced on the payload as `codeRoot`), never the live SSE derivation. `gitRoot` is re-derived per tick from the ACTIVE pane's cwd (backend `deriveGitRoot`), so a pane switch or a `cd` would otherwise retarget the embedded editor to another workspace — or null the tile entirely when the pane leaves every repo — taking in-flight editor state with it (open tabs, dirty buffers, undo stacks). Derivation's only job is to SEED. Because the state is a window option, every viewer of the tab renders the same folder and a snapshot restore carries it with the window. (260813-if5d, iip5)

- **Module** — `lib/code-folder-latch.ts` is pure and DOM-free with colocated tests (the `window-view.ts` / `right-panel.ts` module contract): `codeRootFor(win)` = `win?.codeRoot || win?.gitRoot || ""` — the folder the code surface opens and the availability predicate's input — and `codeRootSeed(win, layout)` = `layout.order.includes("code") && !win?.codeRoot && win?.gitRoot ? win.gitRoot : null` — the seed decision.
- **Seed rule — derivation runs exactly once** — the seed POSTs `setWindowOptions({ "@rk_win_code_root": gitRoot })` the first time the code surface actually RENDERS for a window whose `codeRoot` is empty, keyed on `layout.order.includes("code")`, the choke point every entry path resolves through (the surface toggles, `View: Code`, the mobile switch group). Availability alone seeds nothing: an offered-but-never-opened code lens is not an open editor. An empty derivation seeds nothing either, so a window that has never been inside a repo simply offers no code surface. A per-window in-flight ref suppresses a second POST while the payload still reads empty (the SSE tick arrives after the POST); after seeding, derivation never moves the editor — not on a pane switch, not on tile close/reopen, not on reload.
- **Follow rule — the editor's own navigation and the shell move it** — `CodeSurface`'s `load`-event seam (the same one the chord reclaim re-attaches on) also reads the same-origin `contentWindow.location`, parses `folder`, and reports it via `onFolderNavigated` when present, non-empty, and different (decoded comparison) from the current folder; `SurfaceLayout` passes it through as `onCodeFolderNavigated` and `app.tsx` POSTs `setWindowOptions({ "@rk_win_code_root": folder })`. So File > Open Folder inside code-server moves the shared code root and a later remount renders where the editor actually is, while the terminal never moves the editor. The shell twin is `rk tab code set <folder>` — the same option write (`SetWindowOptions`), so a CLI-set root repaints every viewer on the next option tick. The location read carries the attach's try/catch posture — a cross-origin or pre-load frame skips silently.
- **The render feed** — the payload record carries `codeRoot` directly, so `hasCode`, `availableTiles`, `degradeLayout`, the tile render guard, `tileMeta`, and `codeServerSrc` all read it with no substitution layer: `CodeSurface` receives `codeRootFor(win)` as its folder prop from the tile renderer. A tab whose active pane left the repo keeps offering `code` (`hasCode` reads `codeRoot` as availability) and the editor stays on the shared root.
- **Stale roots are accepted** — a code root pointing at a deleted worktree renders code-server's own "folder does not exist" state; the escape is File > Open Folder, which moves the option via the follow write. No liveness probe, no reset verb, no palette entry.
- **One-shot latch migration (one release)** — the route-entry translation effect (§ Surface Layout → `app.tsx` integration) migrates a surviving per-browser `runkit-code-folder:{server}:{@N}` localStorage key: when `win.codeRoot` is empty and the key holds a non-empty path, one POST seeds `@rk_win_code_root` from it; the key is deleted either way. (iip5)
- **e2e — `code-folder-latch.spec.ts`** — real tmux on the port-3020 rig with the `code-surface.spec.ts` code-server stub: a window with one pane inside a repo and one outside proves the first code-tile render seeds `@rk_win_code_root` (asserted via `_tmux.ts` `windowOption`), that the code tile survives the active pane leaving the repo and reopens at the seeded root across a reload (persistence is tmux's), and that the option is substrate state shared across viewers. Live File > Open Folder navigation is unit-tested only (no live code-server in the harness).

## Window Views (Lens Model)

The model (`docs/specs/window-views.md`, rules R1–R7; arrangement generalized by `docs/specs/surface-layout.md`): **a window ROW is a substrate** (a supervised tmux pane); **a VIEW is a lens** over one derivable output of that pane (the tty is a lens; an iframe of the pane's HTTP service is a lens; the parsed agent transcript is a lens; later: desktop). **Which lenses a window offers is a derived capability set; which surfaces the tab shows is shared tab state** — the surface layout (§ Surface Layout) carried in the `@rk_win_layout` window option, never part of the window's identity; only a viewer's zoom/single-tile choice is per-viewer client state. A single-tile layout IS the exclusive-lens view: `single:chat` is "the chat lens", `single:tty` the default terminal. The frontend is a renderer of the payload — the `@rk_win_layout`/`@rk_win_web_<n>`/`@rk_win_code_root` options and `POST /options` carry the layout and content addresses; the SSE payload carries `layout`/`webTabs`/`webActive`/`codeRoot`/`chatProvider`. (260714-t97o, 260714-r7rq, iip5)

Four lenses are implemented: `tty` (always available, `TerminalClient`), `web` (ALWAYS available, like `tty` — `hasWebUrl` selects its CONTENT: the onboarding state when the web-tab family is empty, the live iframe when the active tab carries an address; `IframeWindow`, § Iframe Window → Onboarding state), `code` (available when `codeRootFor(win)` is non-empty — the shared `@rk_win_code_root` or a derived `gitRoot`; the stable capability signal; `CodeSurface`, § Code Surface), and `chat` (available when `chatProvider` is non-empty, `ChatView` — the read-only transcript renderer, § Chat View). Capabilities are orthogonal and STACK (spec R5): one window can offer `tty`+`web`+`code`+`chat` at once, and the layout can tile up to three of them at once (§ Surface Layout). The lens set IS the layout's tileable surface set (`SurfaceKind = ViewName`). The registry is open-ended — `desktop` adds a `ViewName` member, an availability clause, and surfaces on the existing affordances (the top-bar toggle group, the palette `View:` action), NOT a new component/route/window-type. There is no default-view hint: a web-first window carries an explicit `single:web` `@rk_win_layout` value (stamped at creation by the `rkType:"iframe"` arm, or by the retired-`@rk_win_lens` migration/dual-read). (iip5)

### Pure view-model helper — `lib/window-view.ts`

The single source of lens CAPABILITY logic — pure, DOM-free, colocated `window-view.test.ts` (the same pattern as `window-transition.ts`/`navigation.ts`). `surface-layout.ts` builds its availability set on these predicates, so the toggles, the layout, and the palette share one capability source (no drift). Helpers take a minimal structural `{ layout?, webTabs?, webActive?, codeRoot?, chatProvider?, gitRoot? }` shape (`ViewWindow`, assignable from `WindowInfo`):

- **`ViewName = "tty" | "web" | "chat" | "code"`** — the lens union; aliased as the layout's `SurfaceKind`.
- **`hasWebUrl(win)` / `hasChat(win)` / `hasCode(win)`** — the capability predicates (`hasChat`/`hasCode`) plus web's CONTENT selector: `hasWebUrl` is `(win?.webTabs?.length ?? 0) > 0` and gates NOTHING about availability — web is always available (below); it selects the web tile's content (onboarding vs live iframe — an empty web-tab family renders onboarding, never a blank-src iframe) and drives the web toggle's corner dot (§ Surface Toggles); `chatProvider` non-empty (mirrors the backend `resolveWindowChat` gate); for `code`, `(win?.codeRoot || win?.gitRoot)` non-empty — the shared `@rk_win_code_root` OR the live derivation, so a window whose code root is seeded keeps offering `code` after its active pane leaves the repo (the port is always resolvable by convention, so there is no configured-port leg); code-server REACHABILITY is deliberately NOT in this gate (it fluctuates and would strobe the toggles/palette; it selects the surface's content instead, § Code Surface).
- **`activeWebUrl(win): string`** — `webTabs[(webActive >= 1 ? webActive : 1) - 1] ?? ""`: the address the single web tile shows as its ACTIVE tab (empty family or out-of-range pointer → slot 1 / `""`). The tile header's display form reads it; `IframeWindow` derives the same value internally from its `tabs`/`active` props. (iip5, 9kip)
- **`availableViews(win): ViewName[]`** (spec R1/R3) — `["tty"]`, plus `"web"` UNCONDITIONALLY (always available; `hasWebUrl` selects content, never availability), plus `"code"` when `hasCode`, plus `"chat"` when `hasChat`. **Availability is decoupled from `@rk_win_lens`**: an iframe-created window with no URL offers `tty` + `web` (the web tile renders its onboarding state). Returned in the registry's fixed order via a `HINT_ORDER` (`[chat, code, web, tty]`) filter — so a fully-stacked window yields `["chat","code","web","tty"]` (`HINT_ORDER` is purely the capability ordering; there is no default-view hint). The layout module's `availableTiles` re-derives the same set tty-first (§ Surface Layout).
- Input gating for the lens chord is **not** a `window-view.ts` concern: the shared `shouldSuppressChord` predicate in `lib/keybindings.ts` gates every app chord (§ Keyboard Shortcuts → Dispatch seams).
- **localStorage helpers** — **value-bearing** key `runkit-window-view:{server}:{windowId}` storing the view NAME, including `"chat"` (absent = default). `windowViewStorageKey`/`readStoredView` (READ-only — nothing writes this key), try/catch-noop per `chrome-context.tsx`. The key is a LEGACY input to the one-shot route-entry translation (§ Surface Layout → `app.tsx` integration) and survives only for that one consumer; the follow-up cleanup change removes it. (260814-6b0j, iip5)

### Legacy layout search params — `lib/router-url.ts`

The terminal route is the BARE route: nothing in the frontend writes search params anymore, and every history entry is `/{server}/{N}` alone. The legacy `layout`/`view`/`panel` params remain ACCEPTED inbound for one release so old deep links never break — they are translation-only inputs to the route-entry one-shot effect (§ Surface Layout → `app.tsx` integration), which folds them into `@rk_win_layout` (rendered at once through the `pendingLayout` optimistic overlay — a carried deep link never waits for the option tick; a rejected write reverts) and replaces the URL with the bare route. The exported pure `validateTerminalSearch(search): { view?: "web" | "chat" | "code"; panel?: "web" | "code"; layout?: string }` passes `view` ∈ {`web`, `chat`, `code`} and `panel` ∈ {`web`, `code`} through, forwards any non-empty string `layout` (shape/arity validation happens in `parseLayout`, § Surface Layout), and **drops any other/unknown/non-string value** (treated as absent, NEVER errored). It is wired as the route's `validateSearch` and unit-tested directly in `router-url.test.ts`. The `declare module "@tanstack/react-router"` `Register` block types the params, so `useSearch({ strict: false })` in `app.tsx` reads them **with no `as` cast** (code-quality type-narrowing — `tsc --noEmit` clean). `translateLegacyParams(view, panel)` maps `?view=X` → `single:X` and `?view=X&panel=Y` → `split-h:X,Y` (X in slot A) as the pure param→layout-string mapper the one-shot effect consumes. (iip5)

### `app.tsx` integration — derivation, `switchView`, the layout render

`app.tsx` (terminal route) owns ONE layout-state block (§ Surface Layout → `app.tsx` integration for the full derivation/optimistic/translation machinery): `layout = effectiveLayout(effectiveWindow)` — the payload's `@rk_win_layout` parsed and degraded — overlaid by the optimistic `pendingLayout` while a verb's POST is in flight. The lens model's consumers key off **slot A** — `resolvedView: ViewName = layout.order[0]` (spec R12's shim: a multi-tile layout reads as its slot-A surface to the palette `View:` actions). One stable `switchView(view)` callback collapses to a single-tile layout: `applyLayout({ shape: "single", order: [view] })` — `applyLayout` POSTs `@rk_win_layout` through the unified `/options` seam, so a lens pick is a shared tab-state mutation every viewer of the window renders (never an `@rk_win_lens` mutation, spec R7). The **render** is `<SurfaceLayout layout={layout} …/>` keyed `` `${server}:${windowId}` `` (a window switch remounts it) — one tile per surface in the rendered order (§ Surface Layout → tile renderer). There is no `@rk_win_lens`-mutating "switch" path anywhere: switching lenses/surfaces is the surface toggles' and the palette's job, neither of which mutates `@rk_win_lens` (spec R7).

### Lens-switch surfaces — palette, top-bar toggles

There is no lens-switcher component: the lens-switch surfaces are the command palette's `View: …` actions (§ Palette parity below — DESKTOP-only; on mobile the top-bar switch group and its `Tile: Switch to <Surface>` palette twin take their place, § Surface Layout → Mobile slot-A + the top-bar switch group) and the top bar's open-tile toggles for non-hidden surfaces (§ Surface Toggles — switch mode on mobile). The top-bar chevron menu carries no lens rows — its VIEW section holds the ▦ layout chip's shape rows plus the `menuOnly` Fixed width and Terminal font rows (§ Chrome (Top Bar) → Right cluster). (260812-0c6o, 260816-ox16)

### Palette parity + keyboard shortcuts (Constitution V)

- **`View: Terminal` / `View: Web` / `View: Code` / `View: Chat` palette actions** (AppShell `viewActions` in `app.tsx` — DESKTOP-only; on mobile the `Tile: Switch to <Surface>` entries take their place, § Surface Layout → Mobile slot-A + the top-bar switch group), each visible only when its view is **available AND not the current** (slot-A) view — each applies `single:<view>` through `applyLayout` via `switchView` (§ app.tsx integration). The gating + label composition live in a pure builder `buildViewActions(available, resolved, onSwitch)` in `lib/palette/view.ts` (mirrors `lib/palette/move.ts`/`palette/update.ts`, unit-tested in `palette/view.test.ts`). Every entry's `shortcut` is `""` — no chord reaches a single-tile lens switch, so no hint is advertised (§ Design Decisions → No chord reaches a lens switch). One `buildViewActions` call feeds them; there is no `@rk_win_lens`-mutating `toggle-iframe-terminal` action. The multi-tile affordances (add/close/promote/swap/zoom/shape) carry their own `Layout:` palette entries (§ Surface Layout → palette + chords).

### Heading is a static `Tab:` in every lens

The top-bar center `PageType: name` heading on the terminal route reads a **static `Tab: <name>` in every lens** (tty / web / code / chat) — it does NOT follow the active view (§ Window Heading). A single `WINDOW_PREFIX = "Tab:"` constant (`top-bar.tsx`) is passed as a constant `prefix` into `WindowHeading` at the terminal-mode center cell. The heading identifies the WINDOW (the substrate); which lens you look through is carried by the view content itself (chat bubbles vs. terminal) and the top bar's lit tile toggles, not the heading (§ Design Decisions → Heading identifies the window, not the lens). The name's anchor does not jump on a lens switch, since the prefix width does not change with the lens (§ Center-heading stable anchor + nav affordances). The click-to-rename affordance and boot-sweep treatment apply. (260714-uco1, 260717-6anu, 260820-lfla)

### Internal navigation targets the bare route (spec R6 / surface-layout L4)

Navigating to a DIFFERENT window carries NO layout/view/panel param — each destination window renders its own shared `@rk_win_layout` (§ Surface Layout → `app.tsx` integration). Client-side navigations (sidebar/palette/breadcrumb via `navigateToWindow`, plus the window-death redirect and SSE-writeback switch) omit/clear `search`, and TanStack Router's `final` search middleware returns `{}` when `dest.search` is absent, so a carried legacy param does not leak onto the target. (The web-view-lens e2e persistence case exercises this through a real sidebar-click navigation to guard against a future `retainSearchParams`/router-upgrade regression.) History entries are bare routes — layout mutations never create or rewrite entries, so back/forward always lands on `/{server}/{N}` and each window renders its current shared layout. The one exception is the `Agent: Next waiting` / WaitingBadge deep-link, which INTENTIONALLY sets `?view=chat` for a chat-capable target — the one-shot translation folds it into `single:chat` on `@rk_win_layout` and cleans the URL (§ Chat View → WaitingBadge).

### Window-switch transition classification (one rule)

## Surface Layout (the center is a layout of tiles)

The terminal route's center is a **layout manager** (`docs/specs/surface-layout.md`): a resolved **layout** `(shape, order, ratios)` renders as 1–3 **tiles**, each mounting an existing surface renderer unchanged. `docs/specs/right-panel.md`'s P6 slot mechanics do not apply to the layout manager; its availability derivation and P4 attention do (§ Surface Toggles). A **surface** is a (substrate, lens) pair of the ROUTE window; the tileable set is `tty | web | chat | code` (`SurfaceKind = ViewName` — § Window Views (Lens Model)); `tty` is `(current window, tty)`, always available, listed first. (260812-ab5v) Tiles are content-area state; the toggles that open and close them live in the top bar (§ Surface Toggles).

### The model — preset shapes × ordered surfaces × ratios

- **Shapes** (`SHAPE_ARITY`): `single` (1), `split-h` / `split-v` (2), `row` / `col` / `main-left` / `main-right` / `main-top` (3). Slot A (first in `order`) is the main slot in `main-*` shapes. A layout carries exactly its shape's arity. Max 3 tiles (Constitution IV); presets, never free split trees.
- **Order** — 1–3 surface kinds; kinds MUST NOT repeat within a layout **except `tty`** (the muxed `/ws/terminals` relay supports N clients per pane, so duplicate tty tiles of one window are legal; only the FIRST tty tile receives the shared `wsRef`/`focusRef`).
- **Ratios** — divider positions, per-viewer localStorage ONLY, keyed `rk-layout-ratios:{server}:{windowId}:{shape}` (a ratio is meaningless across shapes), written on drag RELEASE; never in the URL. Clamped by `clampRatio` (`lib/right-panel.ts`, the `MIN_PANEL_WIDTH_PX` 280px floor bounding both sides).
- **Zoom** — the one zoomed tile, per-viewer localStorage ONLY, keyed `rk-layout-zoom:{server}:{windowId}` storing a surface KIND (`readStoredZoom`/`writeStoredZoom`, try/catch-noop like ratios; a stored kind the layout no longer hosts reads/clears as unset). Desktop zoom resolves the kind to its first slot in the layout; the mobile single-tile switch reads the same key (§ Mobile slot-A + the top-bar switch group). Zen-initiated zoom rides the same seam (zen is a viewer posture). (iip5)

### Pure layout model — `lib/surface-layout.ts`

Pure, DOM-free module with colocated tests (the `window-view.ts` pattern — § Design Decisions → Layout helpers live in a pure module). Untrusted URL/localStorage strings are validated by guards on the parse path (no `as` casts):

- **`parseLayout` / `serializeLayout`** — `<shape>:<a>,<b>[,<c>]` round-trips byte-identically; rejects unknown shape/kind, arity mismatch, repeated non-tty kind (returns `null`). `ALL_SHAPES`, `shapesForArity(arity)` (the same-arity ring), `SURFACE_LABEL` / `SHAPE_LABEL` / `SURFACE_GLYPH` — shared copy for tile headers, the surface toggles' tooltips/aria, palette `Tile:`/`Layout:` entries, and the mobile switch group so none drift.
- **`effectiveLayout(win)`** — THE resolution: `degradeLayout(parseLayout(win?.layout), win) ?? { shape: "single", order: ["tty"] }`. The payload's raw `@rk_win_layout` string is the single source; an unset, malformed, or fully-unavailable value renders `single:tty`, and the option itself is NEVER rewritten by degradation (the author sees their mistake with `show-options`). (iip5)
- **Availability degradation (`degradeLayout`)** — an unavailable surface drops out TILE-BY-TILE: the remaining order renders in the matching smaller-arity shape (3→2 `split-h`, 2→1 `single`, slot A kept). No broken iframe ever mounts. `tty` and `web` never degrade — both are always available, so a `…web…` layout on a URL-less window keeps its web tile (rendering the onboarding state, § Iframe Window → Onboarding state).
- **`SURFACE_RAIL_HIDDEN: ReadonlySet<SurfaceKind>`** — a per-surface demotion flag (currently `chat` only): a surface in the set renders NO button in the top-bar `surface-toggles` group in either mode (the desktop toggle group and its overflow Tiles rows; the mobile switch group) and no `Tile: Switch to Chat` palette entry — the consumers filter by the flag AT RENDER, never at availability, so `availableTiles` is untouched and the palette's `Tile: Show Chat` / `Tile: Hide Chat` entries keep working as chat's entry points (§ Surface Toggles). An already-open chat tile still renders and closes normally (the tile's ✕, `Tile: Hide Chat`, layout verbs) — the flag hides the toggle, never the tile. Un-hiding when chat ships is deleting the entry from the set. (260812-0c6o, 260816-ox16)
- **The inbound translation mapper** — `translateLegacyParams(view, panel)`: `?view=X` → `single:X`; `?view=X&panel=Y` → `split-h:X,Y`; bare `?panel=Y` → `split-h:tty,Y`. A pure param→layout-string mapper whose only consumer is the one-shot route-entry translation (§ `app.tsx` integration) — inbound-only for one release, removed by the follow-up cleanup change. Beside it, the pure `legacyTranslationDecision({carried, storedLayout, storedLegacy, winLayout})` folds the four candidate sources into `{ write?: string; dropParams: boolean }` — the translation's decision table, unit-tested without React. (iip5)
- **Mutations** (all pure): `promote` (surface → slot A; order permutes, shape unchanged), `swapWithNext`, `closeSurface` (arity collapse, slot A kept; `null` when closing the last tile — disallowed), `addSurface` (1→2 `split-h`, 2→3 `main-left`; `null` at 3), `cycleShape` (next same-arity preset, order kept — tmux `next-layout` muscle memory), `setShape`. The `rk tab layout` CLI verbs are the shell twins of these mutations: `internal/layoutspec` ports them case-for-case to Go (named sentinel errors where the TS returns `null`), so the frontend's `applyLayout` POST path and the shell verbs share one growth/collapse table (260829-c143).
- **Storage** — per-viewer only: the ratios key above + `rk-layout-zoom:{server}:{windowId}` (the zoomed surface KIND — `zoomStorageKey`/`readStoredZoom`/`writeStoredZoom`, kind-validated reads, `null` clears; § The model → Zoom). All reads/writes try/catch-noop. There is NO layout persistence in localStorage — the layout itself is `@rk_win_layout`. (iip5)

### `app.tsx` integration — derivation, optimistic write, one-shot translation

One layout-state block (§ Window Views → app.tsx integration): `baseLayout = useMemo(() => effectiveLayout(effectiveWindow), [effectiveWindow])` — the layout is DERIVED from the payload, never a `useState` copy and never a localStorage/URL read. **`applyLayout(next)` is the ONE mutation path** — `setWindowOptions(server, windowParam, { "@rk_win_layout": serializeLayout(next) })` through the unified `/options` seam, with no navigation and no localStorage write; tile verbs, the surface toggles, the ▦ chip, and the palette `View:` actions all funnel through it. The render is OPTIMISTIC: a `pendingLayout { key, value }` state (key = `` `${server}:${windowId}` ``) is set before the POST, and the rendered layout is `effectiveLayout({ ...effectiveWindow, layout: pendingLayout.value })` while the key matches — cleared when the SSE payload's `layout` equals the pending value, on POST rejection (revert to the payload value; the mutation-feedback path surfaces the failure), or on a route change. Degradation still applies to the pending value, so the tiles reorder immediately and never flicker back when the tick confirms. Internal navigation (sidebar, ▾ switcher, palette) targets the bare route (§ Window Views → Internal navigation targets the bare route); layout consumers read the derived layout, never parse `location.search`. `togglePanel(surface)` is the toggle behind the top-bar group, the overflow Tiles rows, and the palette `Tile: Show/Hide` entries: open surface → `closeSurface`, closed → `addSurface`, then `applyLayout` (a `null` mutation — closing the last tile — is a no-op).

**One-shot legacy translation (one release)** — a single effect per `(server, windowParam)` arrival, gated on `effectiveWindow !== null`, folds every retired layout carrier into the option: compute `carried = search.layout ?? translateLegacyParams(search.view, search.panel)`, the retired `rk-layout:{server}:{@N}` localStorage value, and `translateLegacyParams(readStoredView(…), readStoredPanel(…))`; when `win.layout` is empty, `legacyTranslationDecision` picks the winner (URL params > `rk-layout:` key > legacy view/panel keys) and exactly one POST writes it (a per-key in-flight ref suppresses a second fire while the payload still reads empty); when `win.layout` is set, nothing is written — the shared layout wins over any carried param. Both arms then navigate `replace: true` to the bare route when the URL carried any of the three params and delete exactly the four matching keys (`rk-layout:`, `runkit-window-view:`, `runkit-window-panel:`, `runkit-code-folder:` for this window only — never a prefix sweep); the code-folder arm POSTs `@rk_win_code_root` from a surviving `runkit-code-folder:` value when `win.codeRoot` is empty (§ Code Surface → The code root). Nothing in the frontend writes `?layout=` anymore; history entries are bare routes. (iip5)

### Present expansion — the layout write is the expand

There is NO client-side present reaction: `rk present` is sugar over `rk tab web add <target> --show` — the CLI writes the web-tab slot AND the shared layout itself (the `webAddShow` helper: `WebAdd`, then `@rk_win_layout` gaining `web` when absent — grown through the ordinary table, a full 3-tile layout yielding its last slot — then `WebSelect(n)`). An agent or any external writer can equally expand by hand — `tmux set-option -w @rk_win_layout …`, `rk tab layout --add web`, or `rk tab web select <n>`. Every mounted viewer of the window repaints on the next option tick with no client-side state machine — the frontend renders `@rk_win_layout`, so any writer's expansion IS the render. Closing the revealed web tile POSTs the layout without it, which every viewer renders too. (iip5, 260829-c143)

- **e2e — `present-auto-expand.spec.ts`** — real tmux on the port-3020 rig (the `_tmux.ts` `windowOption` pattern), gated on the status bar's Connected readiness signal: a `tmux set-option -w @rk_win_layout split-h:tty,web` issued while a viewer is mounted repaints the web tile within the option tick (and a second external write repaints again); an invalid hand-written option value degrades to `single:tty` at render with the option itself left untouched.

- **Hide-never-unmount (P3)** — a surface opened earlier this route visit stays mounted (`hidden` class) when closed or zoomed away, so iframe/terminal/chat state survives; bookkeeping is keyed by surface kind and resets per window.

## Design Decisions

### Draft tabs are viewer-local, not a stored sentinel
**Decision**: The empty-tab flow is client-side draft state that materializes into a real slot on first Enter; nothing lands in tmux until an address exists.
**Why**: A stored blank fights three spec decisions at once — identity-is-the-URL (two blanks collide with idempotent add), "absent and empty read alike as unset" (an empty option value cannot exist), and "declared only". The One Rule classes drafts as viewer preferences (the compose-draft class).
**Rejected**: An `about:blank`/`/newtab` sentinel URL — needs an idempotence exemption and makes blanks shared state with no shared content.
*Introduced by*: 260901-s36e-web-tab-strip-drafts-reorder

### Progress line is an absolute overlay, not an in-flow strip
**Decision**: The tty tile's 2px progress line renders inside a zero-height `relative` wrapper with an `absolute`, `pointer-events: none` 2px bar overlaying the content's top edge.
**Why**: The tile layout must not shift when progress appears, and — stronger — an in-flow strip would change the terminal container's height, firing `ResizeObserver → fit → PTY resize` churn on every task start/stop, which the window-switch machinery treats as a hard constraint (transform-only, no layout change).
**Rejected**: The web tile's in-flow `.rk-web-progress` form (fine over an iframe whose element's presence IS the loading state, resize-churn over xterm); reserving a permanent 2px row (burns 2px on every idle tile).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### One shared progress slot per window, wired on every tty mount
**Decision**: Progress is a single `SurfaceLayout` state slot (the `webPageTitle` precedent) fed by `onProgressChange` on every tty `TerminalClient` mount, primary and duplicates alike.
**Why**: All tty tiles show the same window, so per-tile state would duplicate identical values; wiring every mount keeps the signal alive when the primary tile is hidden (hide-never-unmount keeps its stream open), and duplicate firings fold idempotently under the rAF coalescing.
**Rejected**: Primary-tty-only wiring (loses updates in hidden-primary arrangements for no savings); per-tile state (duplication with no benefit).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### Heading identifies the window, not the lens
**Decision**: the terminal-route center heading is a static `Tab: <name>` in every lens (tty/web/code/chat); lens identity is carried by the tile content and the top bar's lit tile toggles, not the heading.
**Why**: the heading identifies the WINDOW (the substrate), per window-views.md "rows are substrates, views are lenses". Keeping the prefix constant also stops the name's anchor from jumping on a lens switch (the prefix width does not change with the lens).
**Rejected**: a lens-following heading ("the center page heading follows the lens") — the prefix would flip on every lens switch and misidentify what the heading names.
*Introduced by*: 260714-uco1-topbar-heading-anchor-nav; static `Tab:` in every lens: 260820-lfla

### Two verb families on tile headers
**Decision**: Tile-header verbs split into layout verbs (generic, arity-gated) and content verbs (per-kind, any-arity, zoom-visible) — the tty tile carries a bordered pane segment holding Split H / Split V / Close Pane.
**Why**: Pane operations act on the tmux pane inside the tty tile; proximity is the disambiguation. The tile header is already per-kind on its left side (StatusDot, meta chips), so per-kind verbs on the right are an evolution, not a break.
**Rejected**: Keeping pane verbs in the top bar (target invisible on multi-tile layouts); moving only the splits; a confirm-on-close variant — the glyph+grouping distinction below was chosen.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### Page title crosses the component seam via a callback, kind stays derived
**Decision**: `IframeWindow` reports `{ title }` through an optional `onPageMeta` prop on the ACTIVE frame's `load`; `SurfaceLayout` holds it as state for the header. The kind badge is derived purely from the active web tab's address via `lib/web-url.ts` with no seam.
**Why**: the header is SurfaceLayout's render but only the mounted iframe can read `contentDocument.title`; a narrow optional callback matches the existing `onInteract`/`onFolderNavigated` seam shapes, and deriving the badge purely keeps it testable and SSE-consistent.
**Rejected**: rendering a second header inside `IframeWindow` (duplicates the tile-header contract) or lifting the whole iframe ref up (breaks the presentational-component boundary).
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Dead-port detection is a frontend same-origin fetch, not a proxy ErrorHandler
**Decision**: a dead proxied port is detected by `fetch`ing the proxied path from the frontend and reading the reverse proxy's 502, rendering the error state client-side.
**Why**: the proxy already answers 502 on connect failure (the default `ReverseProxy` error path); a same-origin fetch reads it with zero backend change and keeps `frame-check` scoped to absolute external URLs only.
**Rejected**: a custom `ErrorHandler` serving a styled error page from `proxy.go` — touches the proxy layer and couples error UI to the Go layer.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Error states render over a hidden, still-mounted iframe
**Decision**: the tile's error surfaces render in place of the iframe's VISIBLE area while the iframe stays mounted under the `hidden` class.
**Why**: unmounting would strand the attach seam's mount-once listeners, forcing a remount dance on Retry; `hidden` satisfies "replace the iframe render" visually with zero seam churn.
**Rejected**: conditional unmount of the iframe — breaks the mount-once attach effect and complicates Retry.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### `SurfaceLayout` owns zoom/drag/mount-once; `app.tsx` owns layout state
**Decision**: the tile renderer receives the derived layout as a prop and owns only per-viewer interaction state (zoom — persisted via the `rk-layout-zoom:` key, the in-flight ratio drag, the ever-opened mount bookkeeping); layout derivation from the payload, the optimistic `pendingLayout` overlay, and the `@rk_win_layout` write live in `app.tsx` behind the single `applyLayout` mutation path.
**Why**: layout state is route-integrated (the payload feed, the one-shot translation effect, navigation seams) and belongs beside the lens machinery; zoom and drag are self-contained viewer postures with no tmux footprint. Prop-in/callback-out composition keeps the renderer free of the router/storage import graph — tile chrome, verbs, and hide-never-unmount are unit-testable in jsdom — and new surface kinds slot in without touching the shell.
**Rejected**: the renderer importing storage/router helpers and owning layout derivation — two sources of truth for the layout (component + route) and untestable without mocking the router.
*Introduced by*: 260811-2r1w-right-panel-shell-web-surface (as the panel shell's contract); generalized to the tile renderer: 260812-ab5v-surface-layout-core; option-driven derivation: 260828-iip5-ui-state-frontend-layout-code-root

### Zoom key stores a surface kind
**Decision**: `rk-layout-zoom:{server}:{@N}` holds a `SurfaceKind`; desktop zoom resolves it to the first slot of that kind, and the mobile single-tile switch reads the same key as its visible-tile choice.
**Why**: one key serves desktop zoom and the kind-addressed mobile switch group; the spec phrases the clear rule as "the zoomed *surface* leaves the layout", which is kind-shaped. A phone's tile choice and a desktop's zoom are the same viewer posture at different widths.
**Rejected**: slot index — breaks the mobile switch group's kind addressing and survives a reorder pointing at the wrong tile. Duplicate-tty zoom independence (hand-written layouts only) is not persisted.
*Introduced by*: 260828-iip5-ui-state-frontend-layout-code-root

### Mobile switch to a not-open surface grows the shared layout
**Decision**: `switchToTile(kind)` for a kind not in the layout runs `addSurface` through `applyLayout` (one `@rk_win_layout` POST) and sets the local zoom key; `null` growth (arity 3 without the kind) is a disabled no-op. Switching to an already-open surface writes only the zoom key.
**Why**: the spec names the shared `--add` mutation for this case, and the one-rule demands a phone posture never destroy shared tab state — a not-open switch must grow the arrangement, not collapse it.
**Rejected**: the `single:<kind>` collapse — it rewrote every desktop viewer's arrangement from a phone; a transient swap for the not-open arm — it breaks code-root seeding (keyed on `layout.order.includes("code")`) and drops the persistence an explicit pick implies.
*Introduced by*: 260828-iip5-ui-state-frontend-layout-code-root

### Code-surface availability gates on stable signals; reachability gates content
**Decision**: `hasCode` — the availability gate for the `code` lens/tile — is stable signals only: `(win?.codeRoot || win?.gitRoot)` non-empty — the shared `@rk_win_code_root` OR a derived git root (the code-server port is always resolvable by convention — preset `RK_CODE_SERVER_PORT` else `RK_PORT+2` — so a configured-port leg would be vacuous). The TTL-cached reachability probe never gates availability; it selects the surface's CONTENT (live iframe when up, the `code-server not running — check rk doctor` empty state when down).
**Why**: reachability fluctuates with code-server restarts — gating the surface toggle / switcher segment on it would strobe the affordances, and the not-running state could never render (the affordance would vanish exactly when its message is needed). The live derivation fluctuates too, with the ACTIVE PANE's cwd: a window whose editor is open would lose its surface toggle, switcher segment, and deep-link validity the moment an agent `cd`s out of the repo. The seeded `@rk_win_code_root` is what makes the signal genuinely stable per window; content states may fluctuate.
**Rejected**: availability = configured ∧ reachable (internally contradictory with the not-running state); availability = gitRoot ∧ port-configured (vacuous once the port resolves by convention); derivation-only availability (strobes with the terminal's cwd).
*Introduced by*: 260811-k3vp-right-panel-code-lens; gitRoot-only gate: 260811-a2bo-daemon-code-server-stable-route; seeded code root: 260828-iip5-ui-state-frontend-layout-code-root

### Web availability is unconditional; `hasWebUrl` selects the content
**Decision**: the `web` lens/tile is ALWAYS available (like `tty`) on every window; `hasWebUrl` selects the tile's CONTENT — an empty web-tab family renders the onboarding state (reduced live URL bar + the fill-path panel), a non-empty active tab renders the live iframe — exactly as code splits availability from reachability.
**Why**: a single `hasWebUrl` availability predicate gated six consumer surfaces (the ⌘3 chord, the top-bar toggle, palette `View:`/`Tile:` entries, the mobile switch group, deep-link degradation), making the tile undiscoverable before initialization; the availability-vs-content split is the codebase's named model for "the lens exists but has nothing to show", and the onboarding state doubles as the discoverability surface (its live address bar is itself an init path).
**Rejected**: a ⌘3-only carve-out (a chord opening a tile the availability model says doesn't exist — the layout resolver would drop the tile anyway, so the resolver, toggles, and palette would each need contradictory special-cases); a modal/tooltip explainer (no live address bar, no automatic flip).
*Introduced by*: 260821-zqlq-web-tile-always-tileable-onboarding

### The web toggle dot means "has content"
**Decision**: the web toggle button always renders (the surface is always available); its corner dot is driven by a per-surface `showDot` predicate (`app.tsx`: `surface !== "web" || hasWebUrl(win)`) — web's dot means "has content"; every other surface's dot stays always-on; the overflow Tiles rows carry no dot.
**Why**: the button's constant presence is the discoverability affordance; the dot carries the at-a-glance "something to see" signal that a conditionally-present button would otherwise convey.
**Rejected**: a dotless always-on web button (loses the content signal); hiding the button until content exists (recreates the discoverability hole).
*Introduced by*: 260821-zqlq-web-tile-always-tileable-onboarding

### The code surface is a lean `CodeSurface`, not an `IframeWindow` reuse
**Decision**: the `code` lens/surface renders a minimal component — an iframe of `/code/?folder=<gitRoot>` plus the not-running empty state — while `web` uses `IframeWindow` with its URL bar and refresh chrome.
**Why**: the code-server URL is fully derived (the stable `/code/` path plus the code root — no port, no editable address), so the URL bar (the web tab's substrate state — a shared, POSTed content address) is meaningless; reusing `IframeWindow` would drag inapplicable chrome and substrate semantics into a surface whose content address nobody edits. The relative-path discipline (`toProxySrc`'s convention — never compose an absolute origin) is the one piece reused.
**Rejected**: `IframeWindow` with a hidden URL bar (dead chrome, plus web-tab-address semantics that do not apply to a derived URL).
*Introduced by*: 260811-k3vp-right-panel-code-lens; stable `/code/` src: 260811-a2bo-daemon-code-server-stable-route

### Chord-reclaim via a capture-phase iframe `contentDocument` listener
**Decision**: Both iframe renderers (`CodeSurface`, `IframeWindow`) attach a capture-phase `keydown` listener to the same-origin iframe's `contentDocument` after every load (re-attached on each navigation, removed on cleanup, `contentDocument` access try/catch-guarded), reclaim exactly the events matching an injected `shouldReclaimChord` predicate — one curried factory in `app.tsx` (`reclaimChordForKind`) binds the registry's pure, kind-aware `hasReclaimableMatch` per surface kind; it carves out keydowns whose only matches are `ttyOnly` bindings and gates `webOnly` matches to the web kind — and re-dispatch a synthetic bubbling `KeyboardEvent` on the parent DOCUMENT.
**Why**: the `/proxy/` embed is same-origin by design, so a focused iframe's key events are reachable before the embedded app's keybinding service sees them; dispatching on the parent document reaches both document-level listeners (the palette's chord) and window-level ones (the keybinding dispatcher) in one event. Injecting the predicate keeps both components free of the registry import graph, one factory keeps the two kinds reading one registry, and reclaiming only REGISTRY chords leaves the embedded/framed app's own Ctrl/⌘ bindings working.
**Rejected**: dispatching on `window` (misses document-level listeners); reclaiming every chord (breaks VS Code's own bindings); shipping without reclaim (click-out-only escape leaves ⌘K dead whenever the editor has focus).
*Introduced by*: 260811-k3vp-right-panel-code-lens; shared with the web tile + kind-aware predicate: 260819-ie2i-web-tile-keyboard-find

### The find-bar open seam is a document CustomEvent
**Decision**: each find consumer's chord handler and palette body dispatch ONE document CustomEvent — `web-find:open` (`WEB_FIND_OPEN_EVENT`), received by the mounted `IframeWindow`, and `terminal-find:open` (`TERMINAL_FIND_OPEN_EVENT`, `lib/terminal-find.ts`), received by the mounted `SurfaceLayout` (the `window-heading:rename` / `theme-selector:open` precedent). The ⌕ buttons toggle locally.
**Why**: `IframeWindow` is presentational and the web find bar's state belongs inside it, and the tty bar's state belongs to the tile layer — a CustomEvent avoids threading an imperative ref through `SurfaceLayout` (or deeper) for one action; only one web tile exists per layout (kinds don't repeat except tty) and at most one terminal route's `SurfaceLayout` is mounted, so neither receiver is ambiguous — the ONE `IframeWindow` stays the single receiver however many tab frames it hosts, acting on the ACTIVE frame.
**Rejected**: a `findBarRef`/`openFindRef` threaded app.tsx → SurfaceLayout → consumer (touched signatures for one opener); lifting find state into app.tsx (drags search state into the shell for no consumer).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find; tty seam: 260819-zqf9-terminal-tile-find

### Highlight styling enters the frame as a `<style>` element, not injected script
**Decision**: the engine registers Highlight objects on the frame window's `CSS.highlights` and appends one `<style>` with `::highlight(rk-find)` / `::highlight(rk-find-active)` rules to the frame's head, removed/replaced on reset.
**Why**: `::highlight()` pseudo-elements must be styled in the document that owns the ranges; a style element is inert DOM (no execution), which honors the no-script-injection constraint while keeping the search fully parent-driven.
**Rejected**: `window.find()` as the primary (no match count, engine-inconsistent); wrapping matches in `<mark>` elements (mutates the framed page's DOM structure — breaks pages that read their own DOM, and unwinding on reset is error-prone).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find

### Stateful digit chords toggle the surface tiles; `` ⌃` `` hops tty↔code focus
**Decision**: the tile chords are stateful three-state handlers (show+focus / focus / hide+restore) keyed on the CURRENT render layout and focused kind — one positional digit per surface kind (⌘1 tty / ⌘2 code / ⌘3 web, ⇧Ctrl+digit on Win/Linux) riding `togglePanel`, the per-kind landing flag, the `focusTileRef` seam, and the restore router, with the hide arm a no-op at arity 1; the code surface's `Tile: Show/Hide Code` palette entry carries the chord's hint (the `toggleTarget: "code"` / `toggleShortcut` seam) so it stays discoverable. The sibling `focus-hop` chord hops focus between the tty and code tiles through the `Tile: Focus <Surface>` focus-by-kind seam, opening a closed-but-available code tile first (open-then-focus — VS Code's ⌃`-opens-the-hidden-panel analog).
**Why**: the JetBrains tool-window model gives every surface both verbs on ONE chord — a pure toggle cannot express "put my cursor there", and a kind-fixed positional digit gives each surface a stable identity (toggling needs a stable target). Statefulness lives in the chord handlers only — the palette entries keep explicit single-verb semantics ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Design Decisions → Statefulness lives in chord handlers, not palette bodies).
**Rejected**: a generic first-non-tty toggle (a surface picker with no stable target across capability sets, and no chord for the hop); separate toggle and focus chord layers (double the keycap spend); making `togglePanel` itself stateful (it backs the top-bar toggles and menu checkboxes, whose semantics must stay pure toggle); no-op when the code tile is closed (deads the hop in the shipped `single:tty` default layout — VS Code's ⌃` opens the hidden panel, so the borrowed gesture includes the open half).
*Introduced by*: 260811-k3vp-right-panel-code-lens; retargeted to tiles: 260812-ab5v-surface-layout-core; stateful digit family: 260819-qwr7-surface-focus-chords

### Surface toggles are one ordered-registry group in the top bar
**Decision**: The open-tile toggles live in the top bar's right cluster as the single `surface-toggles` ordered-registry entry (`menuGroup: "tiles"`, terminal-route only) — a bordered sub-group with a divider, left of the remaining terminal chips, registered at the head so it is the first fit candidate to drop into the overflow menu; the menu's Tiles section mirrors the group as one `menuitemcheckbox` row per shown surface. Click routing runs through the caller's `togglePanel` semantics unchanged.
**Why**: A dedicated side column forks the stage grid template for one route's worth of four small buttons; as a registry entry the toggles inherit the top bar's probe/fit/overflow machinery for free, and the Tiles section keeps every toggle reachable at narrow widths. Grouping them as ONE entry (not four independent chips) preserves their internal order and divider treatment through the fit pipeline.
**Rejected**: A dedicated collapsible rail column in the stage grid (a whole grid track, a persisted collapse pref, and a top-bar toggle chip to serve four small buttons); `menuOnly` toggles (the primary add/close affordance hidden behind the overflow menu at every width).
*Introduced by*: 260815-19me-composed-frame-unification

**Why**: mirrors the shipped `window-view.ts` pure-helper pattern (unit-testable, drift-free single source) and minimizes churn in shipped, tested code; one registry (`SurfaceName = SurfaceKind`) keeps the toggles, the layout, and the palette availability from drifting.

### Layout verbs are palette-reachable; zoom and the shape cycle carry the direct chords

Further per-verb direct bindings remain open to a later phase if palette latency proves irritating.
**Why**: a small chord set plus palette rows covers keyboard-first (Constitution V — every action is keyboard-reachable) with far less chord-surface to defend against collisions and to learn; the cycle chord earns its binding because it is the tmux `next-layout` muscle memory, and zen earns its own because ⇧⌘⏎ is the iTerm2 maximize-pane habit ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Design Decisions → Zen is a transient render-time override, bound as a shifted-tier Enter chord). `` Ctrl+` `` stays the `focus-hop` keycap (and collides with code-server's own integrated-terminal toggle inside the code tile), so it was never a zoom candidate.

### Focused slot owned by SurfaceLayout, kind mirrored to app.tsx
**Decision**: The focused **slot** index is `SurfaceLayout` component state; `app.tsx` receives only the focused **kind** via `onFocusedKindChange` and triggers focus via a registered ref (`focusTileRef`, the `zoomToggleRef` pattern).
**Why**: Per-window reset comes free from the existing `${server}:${windowId}` key (the same reason zoom lives there); the `ttyOnly` gate and the palette only need the kind; duplicate-tty highlight needs the slot, which only the component knows.
**Rejected**: Lifting the slot into `app.tsx` — it would need manual reset on window switches and layout mutations, re-deriving what the component key already guarantees.
*Introduced by*: 260812-wfic-surface-titlebar-redesign-shortcut-scoping

### Chord scope gates at handler presence, not inside the dispatcher
**Decision**: The `ttyOnly` shortcut gate works by making the handler `undefined` in the `app.tsx` handler map when the tty tile is unfocused, keyed off the registry's `ttyOnly` data flag.
**Why**: "Scope is descriptive; handler presence gates" is the established dispatcher contract — a match with no handler falls through without `preventDefault` for free, so the chord reaches the focused surface (e.g. code-server's own ⌘D).
**Rejected**: Teaching `useKeybindingDispatch` about tile focus — the dispatcher is deliberately generic and route-agnostic.
*Introduced by*: 260812-wfic-surface-titlebar-redesign-shortcut-scoping

### No terminal-route tile-focus cycling on ⌘[/⌘]
**Decision**: Boards cycle pane focus on `board-cycle-prev`/`board-cycle-next` (⌘[/⌘], scope `board`); the terminal route has NO tile-focus cycling chord — it is a backlog item, not shipped behavior.
**Why**: a terminal-scoped ⌘[/⌘] pair shadows macOS history navigation and the usage need is unproven. The focused-slot state and the `Tile: Focus <Surface>` palette entries exist, so the chord is cheap to add on that focus seam once tile focus proves its usage.

*Introduced by*: 260812-0c6o-retire-view-rows-demote-chat

### Derivation seeds the code root once; only the editor moves it
**Decision**: The code surface's folder is the shared per-window tmux option `@rk_win_code_root`. The backend's live `gitRoot` derivation seeds it exactly once — at the code surface's first actual render for that window — and the only writer afterward is the editor's own navigation, reported back from the iframe's `load` event. The terminal never moves the editor.
**Why**: `gitRoot` follows the ACTIVE pane's cwd and agents `cd` constantly, so a live folder makes the terminal's movement move the editor: a pane leaving every repo unmounts the tile, and two panes in two repos swap the workbench between them — either way the editor's in-flight state (open tabs, dirty buffers, undo stacks) is expensive or impossible to recover. That defeats hide-never-unmount (P3), which exists precisely so the iframes keep their in-memory state. A window option makes the folder the tab's choice rather than the terminal's — and every viewer of the tab sees the same folder, a snapshot restore carries it, and no viewer-local store needs migrating (the one-shot route-entry effect folds any surviving per-browser latch into the option once).
**Rejected**: Stabilizing the backend derivation (first-pane-with-a-root wins) — still moves the editor whenever panes `cd`, so it is a mitigation, not a guarantee; re-deriving on tile close/reopen (seed only while open) — reopening after a `cd` is exactly when the editor must come back where it was; liveness probing a stale root — code-server's own "folder does not exist" state plus File > Open Folder is the escape.
*Introduced by*: 260813-if5d-latch-code-surface-folder; shared `@rk_win_code_root`: 260828-iip5-ui-state-frontend-layout-code-root

### Iframe src fixed per mount generation
**Decision**: `CodeSurface` computes its iframe `src` once per iframe mount generation — a ref keyed to the `reachable` gate that mounts the iframe — not reactively from the folder prop.
**Why**: P3 (hide, never unmount): React re-rendering a changed `src` attribute re-navigates a live frame, even to a URL the frame is already at, which would reload the editor on the very code-root follow write the editor just caused. Keying the computation to mount generation means a reachability `false→true` flip or a window-switch remount picks up the CURRENT code root (fresh workbench, correct folder) while a mounted frame is never parent-navigated. A ref rather than `useMemo` because a memo cache is a documented performance hint React may discard, and a dropped cache here would re-navigate the live frame — the exact hazard the decision prevents.
**Rejected**: A `src` state set only at first render — goes stale across reachability flips (a remounting iframe would boot into the seed-time folder instead of where the editor last was).
*Introduced by*: 260813-if5d-latch-code-surface-folder

### The waiting-badge click advances, never restarts
**Decision**: `handleWaitingBadgeClick` resolves its destination through `nextWaitingTarget(ordered, server, windowParam)` (`lib/palette/agent-nav.ts`) — the same helper the `Agent: Next waiting` palette action uses — rather than scanning the session's windows itself.
**Why**: the badge means "the next waiting window", relative to where the viewer already is. Picking the session's FIRST waiting window makes the badge a silent no-op whenever the viewer is already on that window, instead of advancing to the next one.
**Rejected**: a local `windows.find(isWaiting)` scan — re-implements the palette's ordering (drift risk) and dead-ends on the first waiting window.
*Introduced by*: 260717-vhvz

### Scale wrapper over guest-document CSS zoom
**Decision**: web-tile content zoom is a transform-scale wrapper on the iframe with compensated width/height (rendered at `100%/s`, scaled back by `s`, origin 0 0).
**Why**: works for all four address kinds including cross-origin `external`; reproduces browser-zoom semantics (zooming in shrinks the frame's CSS viewport, so responsive guest layouts adapt); zero reach into guest documents.
**Rejected**: injecting CSS `zoom` into the guest document — same-origin only, and touching proxied content re-opens the proxy-rewrite class of bugs (the stale Content-Length scar).
*Introduced by*: 260823-cwvv-tile-content-zoom-gestures

### Content zoom owns "Zoom"; the tile-maximize verb is Expand/Restore
**Decision**: "Zoom" names content magnification everywhere (the web tile's URL-bar control, the `Web: Zoom *` palette actions); the tile-maximize verb's user-facing strings are Expand/Restore (`Layout: Expand`/`Layout: Restore`, the tile-header Tip/aria-labels, the `zen-toggle` binding description) while its ids (`layout-zoom`/`layout-unzoom`), the `ZoomGlyph`/`data-icon="zoom"` seam, and the `zoomed`/`zoomToggleRef` internals keep the zoom vocabulary.
**Why**: two different "Zoom"s in one tile header/palette is a vocabulary collision, and the browser muscle-memory meaning of zoom is content magnification; ids persist in user macros/overrides, so only labels may move.
**Rejected**: per-surface content-zoom names with the tile-maximize verb keeping "Zoom" — leaves "zoom" meaning maximize, fighting every browser's meaning of the word.
*Introduced by*: 260823-cwvv-tile-content-zoom-gestures

### Gestures zoom continuously; only click/shortcut zoom steps the ladder
**Decision**: web-tile gesture zoom is continuous — `s *= exp(-deltaY * 0.01)` per ctrl/meta wheel event (`applyWheelZoom`), `s = base * e.scale` per Safari `gesturechange` — while buttons and palette actions keep the discrete ladder.
**Why**: a pinch that clicks between ladder stops reads as broken next to Chrome/macOS, where pinch tracks the fingers and only Cmd+± steps; the exponential mapping multiplies equal deltas equally, so in/out feel symmetric and a reversed gesture returns to its start.
**Rejected**: shrinking the step ladder (finer quantization) — still visibly clicks; linear `s += k*deltaY` — asymmetric feel, zoom-out crawls near the low bound.
*Introduced by*: 260824-iafo-web-tile-continuous-gesture-zoom

### Read returns the float; only stepping snaps
**Decision**: `readWebZoom` returns the stored float clamped to the continuous bounds; the ladder snap lives solely in `stepWebZoom`, the click/shortcut path.
**Why**: a reload must restore a gesture-set value exactly; snapping belongs to the one path that needs a ladder index.
**Rejected**: read-time snapping — a 137% pinch would reload as 125%, silently moving the user's zoom.
*Introduced by*: 260824-iafo-web-tile-continuous-gesture-zoom

### One `IframeWindow` chrome, N URL-keyed frames
**Decision**: the web tile stays a single `IframeWindow` component that mounts one `<iframe key={url}>` per tab — hidden when inactive, never unmounted by a selection change — with per-frame state held in the extracted `WebFrame` child and the chrome bound to the ACTIVE frame's entry.
**Why**: P3 (hide, never unmount): dev-server pages, HMR sessions, and half-filled forms keep their in-page state across tab switches, which a single re-`src`d iframe loses on every switch. One component keeps exactly one receiver for the `web-find:open` / `web-address:focus` / `web-open-external` / `web-zoom` document CustomEvents, one URL bar / find bar / zoom control DOM set, and one `sandbox` attribute set. Keying by URL means a middle close's slot renumber remounts nothing (identity is the URL); index keys would remount every surviving frame on a `WebRemove` shift, and stable client-side ids would be a second identity the spec deliberately avoids.
**Rejected**: N stacked `IframeWindow` instances (duplicated chrome, N receivers for every document CustomEvent — each would need listener gating — and zoom buckets re-seeding per instance); index keys (remount storm on a middle close); lazy frame mount or LRU eviction (P3 defers eviction; the family cap of 8 bounds the eager-mount cost).
*Introduced by*: 260828-9kip-web-tab-strip

### Client selects after add
**Decision**: after a selected draft's Enter resolves `onAddTab` to the server's `{index}`, the component calls `onSelectTab(index)`.
**Why**: the backend's add verb sets `@rk_win_web_active` only when the family is empty ("add" is not "show" — idempotent adds must not yank an existing view); materializing a selected UI draft carries user intent to look at the resolved tab.
**Rejected**: a server-side `?show=1` flag on the add route (a backend change, out of scope for a frontend change; the verb routes' select-only-on-empty contract is already shipped).
*Introduced by*: 260828-9kip-web-tab-strip

### Address bar replaces; drafts materialize through add
**Decision**: Enter on the address bar writes `@rk_win_web_<active>` when a declared tab is selected; the strip's `+`, an empty-space double-click, and the palette's `Web: New tab` open a draft, whose Enter POSTs the add verb.
**Why**: browser semantics — typing a URL never silently grows a tab strip — and the ui-state spec's Web Tabs wording; it also preserves the pre-strip write path unchanged for single-tab windows.
**Rejected**: routing every address-bar submit through the add verb (typing a URL would grow the family on every submit — surprising, and idempotent adds of the same URL would make repeats indistinguishable from edits).
*Introduced by*: 260828-9kip-web-tab-strip

### Detected-port `+ :port` chip is deferred (declared-only)
**Decision**: the web tab strip ships with NO detected-port add chip; every add goes through a declared address (the address-bar draft, the `rk present`-shaped target forms).
**Why**: the chip assumed a per-window `ports` field on the Window payload, which does not exist — the host-global services list has no window attribution (backend pane-pid → process-tree → port join, tracked in `fab/backlog.md`). Declared-only keeps the add path honest instead of guessing at ports.
**Rejected**: consuming the host-global `useHostServices()` list un-attributed (wrong-window chips); shipping a per-window join inside this frontend-only change.

### No chord reaches a lens switch
**Decision**: On desktop the palette `View: Terminal/Web/Code/Chat` actions are the only single-tile lens-switch surface; no keyboard chord cycles or selects a lens, and the `View:` entries carry no shortcut hint (`buildViewActions(available, resolved, onSwitch)` emits `shortcut: ""`). `Period` (⌘./Ctrl+.) is deliberately unbound ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Design Decisions → `Period` is deliberately unbound).
**Why**: a lens cycle bound to a reflex-hit chord repeatedly dropped users into the Chat lens — a full-tile surface with no top-bar toggle back — defeating chat's deliberate demotion; the tile toggles (⌘1/⌘2/⌘3) and `View:` entries already cover every lens, so the cycle added only the footgun.
**Rejected**: keeping the cycle but skipping `chat` (redundant chord, misleading registry description); hinting the tile-toggle digits on `View:` entries (toggle semantics ≠ lens switch).
*Introduced by*: 260826-sfsv-remove-cmd-dot-view-cycle

### `--show` on a full 3-tile layout replaces the last slot
**Decision**: when `web` is absent and the layout already holds 3 tiles, `rk tab web add --show` (and `rk present`, its sugar) writes `web` into `Order[2]` instead of failing.
**Why**: the show path must succeed on every layout — `rk present` never fails to open the tile — and the last slot is the least valuable tile in every 3-tile shape while slot A stays dominant.
**Rejected**: exit 1 (regresses `present` on full layouts); replacing slot A (steals the user's main tile).
*Introduced by*: 260829-c143-rk-tab-cli-present-sugar

Component System Direction Studies

Three candidate component-system directions for run-kit's next design language, rendered on the same two screens with the same live data so they compare on real content, not abstractions. Mobile (375px true size) is the primary lens — run-kit's founding motivation — with desktop treated as the easier direction to scale toward. The current CRT-terminal system's weakness on touch frames the whole study: every signature treatment (glitch, boot-sweep, typed-sweep, CRT glint) is hover-triggered, a channel that does not exist on phones. Each direction below therefore declares what replaces hover as its personality channel.

Shared scenario

One tmux server (fabKit1) with three sessions: run-kit (main checkout — windows serve, claude busy, logs), racing-saola (worktree — claude waiting on input, dev; PR #842 open, CI green), and swift-mink (worktree, idle, collapsed). Screen A is the sessions sidebar as a full mobile page; Screen B is the racing-saola:claude terminal window, where the agent has finished a test run and is asking a question.

1 · The three systems

B — IDE Refined (JetBrains New UI / Fleet lineage)

ground #1a1b1e island #26282c accent #3574f0 waiting #e8a34a text #dfe1e5 muted #9da0a8

Shape: rounded islands (10–12px) floating on a flat ground, gaps instead of borders · Type: sans UI at 13px, monospace only inside the terminal island · Controls: pills and filled rounded rows · Hover replacement: fill states — pressed/selected rows get a tinted fill, which reads identically on touch.

C — SaaS Dev-Tool (Linear / Graphite lineage)

ground #0e0f12 hairline 7% white accent #5e6ad2 attention #e5734f ok #4cb782 muted #8a8f98

Shape: full-bleed rows and hairline separators, no cards — hierarchy carried by type and spacing · Type: strong sans hierarchy (weight + tracking do the work), 8px status dots · Touch vocabulary: 48px rows, bottom sheets for row actions, segmented controls · Hover replacement: state-change motion — a dot flipping busy→waiting animates once; selection is an inset accent bar.

D — Agent Console (Warp / Devin lineage)

ground #15171c glass card 5% white busy #e8c66f waiting #f07178 ok / accent #7ee2a8 muted #9aa0ab

Shape: translucent glass cards (12–14px radius) and a block stream — Warp's blocks model applied to agent turns · Type: sans chrome, monospace confined to command/output content inside blocks · Status: labeled chips (dot + word) are the primary signal channel, not bare dots · Hover replacement: live status motion — busy chips pulse, a completing block flashes its edge green. Keeps run-kit's accent-green as the "ok/act" color.

4 · Verdict scaffolding

B — IDE RefinedC — SaaS Dev-ToolD — Agent Console
Density at 375px Medium — island margins tax width Best — full-bleed rows, full tree fits Low by design — cards spend space on status
Touch vocabulary Adapted (pills scale up well) Native — sheets, 48px rows, segmented controls Native — feed + composer is a phone idiom
Terminal identity kept Framed, polite Most terminal-forward chrome Deliberately demoted to escape hatch
Distance from today's UI Re-layout + re-token Mostly re-token; anatomy survives New surfaces + new backend derivations
Fit to agent orchestration Neutral Neutral-good (status dots + chips) Strongest — the domain is the design
Distinctiveness Reads "JetBrains" Reads "every 2025 dev SaaS" unless flavored Ownable
Main risk Card metaphor fights tree depth Genericism Engineering cost; tty demotion backlash

Working hypothesis (to be argued with): C is the base system — it wins density, touch vocabulary, and cheapest migration, and its terminal screen is essentially today's anatomy re-tokened. D is the content vocabulary layered on top where the domain earns it: the sidebar's waiting-first agent cards and the block stream's tappable question actions are the two genuinely mobile-native wins in this study, and both can ship incrementally inside C's chrome (the D sidebar is a view mode; the block stream is a lens beside the raw tty, per the window-views two-species taxonomy). B contributes its fill-state selection language and dies as a whole system. run-kit's identity survives as flavor: monospace content, accent-green as the act/ok color, and the CRT animation vocabulary retained as a desktop-only, prefers-reduced-motion-respecting garnish.

Open questions

1. Does the board surface adopt the same system, and if so is it C-rows or D-cards? · 2. Which accent survives — C's indigo chrome accent alongside green-as-status, or green-everywhere as today? · 3. Is D's block stream a lens (per window-views.md, sitting beside tty/web/code) or a replacement — the lens answer keeps the raw tty first-class and makes D shippable incrementally? · 4. Do the existing hover treatments stay as desktop garnish or retire fully? · 5. Where does the bottom-bar key row live in D — quick-keys above the composer (shown) or inside the raw-tty lens only?

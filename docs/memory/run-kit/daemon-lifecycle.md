# Daemon Lifecycle & tmux Control Mode

**Domain**: run-kit

## Daemon Lifecycle

The Go binary manages its own daemon lifecycle via the top-level `rk daemon` subcommand tree (sibling of `rk serve`, not nested under it). The daemon runs in a dedicated tmux server (socket `rk-daemon`, session `rk-daemon`, window `serve`) — separate from the `runkit` server used for agent sessions. The session name matches the socket name so the combined exact-match target (`=rk-daemon:=serve`) cannot collide with user-facing sessions via tmux prefix matching. `LegacySessionName = "rk"` is consulted only by `Stop`/`Restart` (via `runningSessionCtx`, which checks `SessionName` first then falls back to the legacy name) so a daemon started by a pre-rename binary can still be stopped cleanly during the first upgrade. Daemon helpers live in `internal/daemon/`; the CLI surface lives in `app/backend/cmd/rk/daemon*.go` (one file per subcommand: `daemon.go` parent, `daemon_start.go`, `daemon_stop.go`, `daemon_restart.go`, `daemon_status.go`, `daemon_run.go`); the shared port-owner helpers live in `internal/ports` (§ Port-owner lookup below).

- `rk daemon start [--force]` — start daemon (errors if already running)
- `rk daemon stop [--force]` — graceful shutdown via C-c to the tmux pane, with a mode pre-cancel and a force-kill fallback (see `Stop()` sequence below); prints `rk daemon not running` and exits 0 when no session exists
- `rk daemon restart [--force] [--full]` — idempotent: stop existing daemon (the full `Stop()` sequence below — mode pre-cancel → C-c → wait up to `stopGracePeriod` 12s for graceful exit, an independent grace-deadline timer sized to cover the inner serve's ~10s worst-case shutdown — see `internal/daemon` row; a session that vanished on its own counts as a clean stop, and a C-c that fails to deliver degrades to `kill-session` rather than wedging) then start new one; starts fresh if no daemon running. All sequencing is owned by the single `daemon.Restart(opts RestartOptions{Force, Full, Binary})` sequencer in `internal/daemon/restart.go` (§ One restart sequencer below); the RunE is a thin wrapper — parse flags, capture the up-tunnel set (`--full` only, before anything dies), call `daemon.Restart` behind the single `daemonRestartFn` seam, print the start outcome, run the reconnect sweep
- `rk daemon status [--json]` — read-only report of daemon state (running / not running, socket, session, window, target) AND port owner (free / held by the daemon / held by another process). `--json` emits a structured machine-readable form (`daemon.{running,socket,session,window,target,pid}` + `port.{host,port,state,holder_pid,holder_command}`)
- `rk daemon run --window <name> -- <cmd> [args…]` — run an argv in a managed job window of the `rk-jobs` sibling session (wraps `daemon.RunJob`, see the `rk-jobs` paragraph below) (260812-z1ya-update-daemon-tmux-window). `--window` is required and validated (the `validate.ValidateToolName` class — empty, leading `-`, whitespace/control chars rejected) before it becomes a tmux target; a missing `--` command is a usage error; a down daemon is an operational error naming the fix (`rk serve -d`). Success prints ONE bounded line (Principle 9): `spawned rk-daemon:rk-jobs:<name> (@N)` on a fresh spawn, `already running: rk-daemon:rk-jobs:<name> (@N)` (exit 0) when a live job window exists. This is the standardized surface behind `POST /api/update` + `POST /api/restart` (those handlers call `RunJob` in-process — no self-exec), exposed for scripts, other toolkit tools, and debugging
- `rk update` — auto-restarts daemon after successful `brew upgrade` using `daemon.Restart(RestartOptions{Binary: brewBinPath})` (behind the `restartDaemonFn` seam, which keeps its `func(string) error` shape) where `brewBinPath` is `<brewPrefix>/bin/run-kit` derived from the resolved `/Cellar/run-kit/` path (resolves to the new Cellar version post-upgrade, avoiding stale `os.Executable()` path from the running process; the bin/Cellar identity is `run-kit`). Operates at the Go API layer, not the CLI surface (260709-gidk-swap-canonical-cli-name-run-kit)

`rk serve` is foreground-only: it accepts no `-d`/`--restart`/`--stop` flags (daemon lifecycle lives entirely under `rk daemon`), so invoking those surfaces cobra's standard `unknown flag` error. (260528-5zvv-rk-daemon-cli-restructure)

**Naming collision note**: `rk daemon status` is distinct from `rk status` (the top-level tmux session summary in `cmd/rk/status.go`). The collision is sibling-namespaced — cobra disambiguates cleanly — but `rk daemon status --help` includes a one-line note pointing this out so users typing `rk status` expecting daemon info land at the right command.

**`--force` semantics** — consistently "override the safety check that prevents claiming the port from a non-rk-daemon owner":

- `rk daemon start --force` — lazy / on-error. The happy path is identical to the non-forced path (`daemon.Start()` → port-probe). Only when `Start()` returns the port-in-use error does the command look up the port owner, refuse to kill if the holder identifies as the rk daemon (`daemon.InnerServePID()` match), otherwise SIGTERM the owner with graceful-then-forceful escalation, and retry `Start()`.
- `rk daemon stop --force` — stop the daemon first (if running), then regardless of step 1's outcome probe the port. If still held by a non-daemon process, SIGTERM it. If the port is free at probe time, exit 0 silently (no `Killed port owner` line). If the holder identifies as the rk daemon itself, exit non-zero with a "manual investigation needed" message.
- `rk daemon restart --force` — the `Force` leg of `daemon.Restart`: after the daemon stops, proactively probe the port BEFORE the start step. Any non-daemon holder is SIGTERMed (with graceful-then-forceful escalation, via `ports.FindPortOwner`/`ports.TerminateOwner` behind the sequencer's `restartFindPortOwnerFn`/`restartTerminateOwnerFn` seams) before `daemon.Start()` is called; lookup errors are surfaced (not swallowed), and a holder identified as the daemon itself (`daemon.OwnerIsDaemon`) is never signaled.

`rk daemon status` is read-only and does NOT accept `--force` — passing it produces cobra's `unknown flag` error.

**`--full` semantics (`rk daemon restart --full`)** — the explicit opt-in for a genuinely fresh rk-daemon tmux SERVER, not just a fresh session. The rk-daemon server is otherwise effectively immortal (sibling sessions + the `_rk-ctl` anchor + `exit-empty off` hold it up — see `internal/tmuxctl`), so stale server-scoped state has no other supported escape. Sequence: (1) **guard** — inside `daemon.Restart` itself (`insideDaemonServer` lives in `internal/daemon/restart.go` and parses `tmux.OriginalTMUX`, the pre-strip `$TMUX`, socket-path basename == `daemon.ServerSocket`; the env var itself is stripped by `internal/tmux.init()`, so the package's `restartOriginalTMUXFn` seam reads the captured value — the command-prefixed `$TMUX`-seam idiom of `muxOriginalTMUXFn`/`presentOriginalTMUXFn`), refusing a `--full` restart invoked from a pane on the rk-daemon server, which structurally prevents an rk-jobs-hosted invocation from killing itself mid-run — guard-in-primitive, so no future caller can bypass it; (2) **tunnel capture** (CLI-side) — derives the up-set of registered remote tunnels (`remote.Load` ∩ `remote.ListTunnels`) BEFORE anything dies, degrading store/derivation problems to a warning + empty set; (3) graceful `Stop()` when running; (4) **`daemon.KillServer()`** — a wrapper over `tmux.KillServer(serverSocket)` (which emits the `killAudit` teardown WARN with a caller chain) that widens dead-server tolerance via `tmux.IsServerGone` ⇒ nil, taking down the daemon remnants and every sibling (`rk-jobs`, `rk-code-server`, `rk-remotes`, `_rk-ctl`) — and is **release-synchronous** w.r.t. the code-server port (§ Release-synchronous kill primitives below), so the fresh `Start()` cannot observe the dying sibling's still-bound port; (5) the `--force` port-owner step when combined (the flags compose); (6) normal `daemon.Start()` (fresh server birth, CWD pin, `ensureCodeServer` on boot); (7) **reconnect sweep** (CLI-side — it stays in the wrapper because `internal/remote` imports `internal/daemon`, so the daemon package cannot own it without an import cycle) — re-runs the idempotent `remote.Connect` for exactly the captured up-set of remotes, printing installed/updated notices; per-remote failures warn with the `rk remote connect <name>` recovery pointer and never fail the command. Manual verb only — nothing in the auto-update chain passes `--full`. Seam vars: the CLI carries the single `daemonRestartFn = daemon.Restart` plus `listTunnelsFn`/`remoteConnectFn`; the sequencer's own steps sit behind package-var seams in `internal/daemon` (`restartIsRunningFn`/`restartStopFn`/`restartKillServerFn`/`restartStartFn`/`restartStartWithBinaryFn`/`restartFindPortOwnerFn`/`restartTerminateOwnerFn`/`restartOriginalTMUXFn`), making the ordering testable without tmux or ssh. (260818-lqcf-daemon-restart-full-flag) (260818-gs6y-unify-daemon-restart-sequencing)

**Release-synchronous kill primitives** — the port-release invariant lives in the kill primitives, not at any call site, so every kill+ensure composition is safe by construction. tmux `kill-session`/`kill-server` only SIGHUPs the pane process, and the node-based code-server takes up to a few seconds to exit and unbind its port; without the wait, a start/ensure composed right after a kill probes the still-bound port and misclassifies the *dying* instance as externally managed (the ensure path's externally-managed carve-out is correct for genuinely foreign instances and is unaffected by the wait). Both primitives wait on the same bounded port-free loop in `internal/daemon/codeserver.go` — `codeServerPortFreeTimeout` (5s) / `codeServerPortFreePoll` (200ms) package vars (the `stopGracePeriod`/`stopPollInterval` test-seam idiom) driving the `codeServerPortBusy` seam (an unresolvable port, 0, probes as free and skips the wait); expiry is **non-fatal** — the caller's externally-managed classification then fires exactly as without the wait, so the wait closes the race window and adds no failure mode. `KillCodeServerSession` waits only after a successful kill (`killed == true`); `KillServer` probes `rk-code-server` session existence BEFORE the kill and waits only when the sibling pre-existed — when it never did, a busy code-server port belongs to a genuinely externally managed instance that will not release it, and an unconditional wait would burn the full 5s on every `--full` restart for those users (the dead-server `IsServerGone` ⇒ nil path performs no wait). The `rk code-server update` respawn relies on the synchronous kill directly (no explicit wait between `codeServerKillFn` and the gated start).

**One restart sequencer (`daemon.Restart(opts RestartOptions)`)** (`internal/daemon/restart.go`) — the single options-driven state machine every restart composition routes through; `RestartOptions{Force bool, Full bool, Binary string}` selects the optional legs. Sequencing, in order: (1) the `--full` inside-daemon-server guard; (2) `Stop()` when `IsRunning()`; (3) `KillServer()` when `Full`; (4) the port-owner reclaim when `Force`; (5) `Start()`, or `StartWithBinary(opts.Binary)` when `Binary` is non-empty (the upgrade path — `StartWithBinary` remains the explicit-binary start primitive). Each step sits behind a package-var seam (`restartIsRunningFn`/`restartStopFn`/`restartKillServerFn`/`restartStartFn`/`restartStartWithBinaryFn`/`restartFindPortOwnerFn`/`restartTerminateOwnerFn`/`restartOriginalTMUXFn`), so ordering, guard refusal, and force self-recognition are unit-tested without tmux. Callers stay thin: the `rk daemon restart` RunE (flags → tunnel capture → `daemon.Restart` → outcome line → reconnect) and `rk update`'s `restartDaemonFn` seam (`daemon.Restart(RestartOptions{Binary: path})`). `POST /api/restart` spawns `rk daemon restart` in an rk-jobs window and funnels into the CLI path.

**`Stop()` sequence** (`internal/daemon/daemon.go`, resolved-session target `targetFor(session)` throughout so the legacy `rk` name is handled): (1) **mode pre-cancel** — `copy-mode -q` runs FIRST, before the C-c send, best-effort (a failure is `slog.Debug`-logged and never aborts `Stop()`). This defends against a root-cause wedge: a pane left in tmux copy-mode does NOT receive C-c as a literal key — tmux looks the key up in the mode key table (`copy-mode` binds `C-c` → `send-keys -X cancel`, a non-read-only command) and dispatches that binding through the session's only attached client, run-kit's own read-only `-CC` control bridge (attached with `-r` — see the `internal/tmuxctl` production dial), which tmux rejects with `client is read-only`, so the interrupt never reaches the serve process. `copy-mode -q` returns the pane to normal mode so the subsequent send injects C-c literally; it is idempotent (exit 0 when the pane is not in a mode — `-q` since tmux ≥3.2), so it runs unconditionally on every `Stop()`. (2) **C-c send** — `send-keys ... C-c` triggers graceful shutdown; on failure it MUST NOT early-return (an `slog.Warn` fall-through) so the grace-timer → `kill-session` fallback below stays reachable on any graceful-delivery failure. Returning the wrapped send error instead would wedge `Stop()` and everything layered on it (`rk daemon restart`, `rk update`'s `Restart(RestartOptions{Binary: …})` leg, `POST /api/restart`) even though the force-kill would have stopped the daemon. (3) **grace-timer → kill-session** — the independent `stopGracePeriod` (12s) timer + `stopPollInterval` (200ms) polls (each under a fresh `cmdTimeout` context, per the per-command-context discipline documented in the `internal/daemon` row); the full grace is still waited before the kill even when the C-c send failed (no shortened-grace special case). A session that vanished on its own by kill-time — or after a `kill-session` that errored — is the success outcome (returns nil); only a session still alive after a failed kill surfaces an error.

Binary resolution: `Start()` uses `os.Executable()` + `filepath.EvalSymlinks()` (works for the standard `rk daemon start` / `restart` paths where the running binary is valid). `StartWithBinary(path)` accepts an explicit binary path and resolves its symlinks (used by `update` after `brew upgrade` deletes the old Cellar directory). Both delegate to shared `startSession(exe)` for tmux session creation.

**Tmux-presence precheck**: `Start()`/`StartWithBinary()` both begin with `checkTmuxPresent()` — a lookPath probe through the package-var seam `daemonTmuxLookPath` (= `exec.LookPath`) that runs BEFORE `IsRunning()`, `guardPortAvailable()`, and the stale-socket reap, all of which shell out to tmux. On a tmux-less host it fails fast with a remediation-carrying error — `tmux not found on PATH — the run-kit daemon runs inside a tmux session; {hint} (or run rk doctor for a full dependency check)` — instead of the raw exec wrap `startSession` would surface mid-operation (the fresh-VM first-run failure). `{hint}` is `tmux.InstallHint(runtime.GOOS, daemonTmuxLookPath)`, the same shared helper behind the doctor tmux row (§ CLI Subcommands), so the two remediation surfaces cannot drift; passing the same seam to both the tmux probe and the helper's package-manager probe makes a stubbed host yield a deterministic hint in tests. (260817-ho1o) A present tmux additionally passes through the **version-floor check** (`warnTmuxBelowFloor`): the PATH tmux's version is probed via the `daemonTmuxVersion` seam (= `tmux.CurrentVersion`), and a parsed version below the floor (tmux ≥ 3.4, `>=` comparison — exactly 3.4 passes silently) prints the shared `tmux.UpgradeHint` message exactly once at start to the `daemonWarnWriter` seam (stderr in production, a buffer in tests) and start continues — warn-don't-block, since only remote tunnels hard-require the floor ([remote-hosts](/run-kit/remote-hosts.md) § Design Decisions); unknown (unparseable) versions neither warn nor block. `rk serve` repeats the same check at startup via `slog.Warn` (after `slog.SetDefault`, so it rides the `RK_DAEMON_LOG` tee), covering the paths where daemon-start stderr is invisible (the desktop app's Start & connect, `rk update`'s restart). (260819-vtd1-tmux-version-floor)

**Server-birth CWD pin — the highest-leverage seam** (260720-ji0k-pin-server-birth-cwd-home): `startSession`'s `new-session` BIRTHS the rk-daemon tmux server, so it runs via `runTmuxInDir(ctx, tmux.ServerBirthDir(), args...)` — a dir-carrying variant of the shared `runTmux` helper (which delegates with an empty dir). Both are thin `-L rk-daemon` argv-prefix wrappers that keep the file's `cmdTimeout` discipline and delegate the exec itself to `tmux.Run(ctx, fullArgs, tmux.RunOpts{Dir: dir})` (§ tmux Runner Core), which lands `cmd.Dir` on the actual `exec.CommandContext` and owns the stderr-in-error capture. This pins the daemon server's CWD to `$HOME` (fallback `/`) regardless of where `rk daemon start` ran. It is the highest-leverage of the four birth seams because `rk serve` runs inside this session and **every later server birth inherits `rk serve`'s CWD** — without this pin, an `rk daemon start` from a git worktree that is later deleted parks the daemon server (and thus every downstream server) on a dead inode, silently breaking new-pane `-c` chdir on tmux 3.7. The daemon session's env is unchanged (only CWD is pinned — `config.Load` needs the `RK_*` env; see the `internal/tmux` module row). Full failure-mode analysis and the shared `tmux.ServerBirthDir()` helper: `tmux-sessions.md` § Server-Birth CWD Pin.

**The `rk-remotes` sibling session shares the socket, not the lifecycle.** The `rk-daemon` socket carries a second session, `rk-remotes`, holding one window per SSH-only remote host running that remote's `ssh -N -L` tunnel (`internal/remote`, see [remote-hosts](/run-kit/remote-hosts.md)). It is a **sibling** of the `rk-daemon` session, never nested under it: the daemon's `Stop()` targets `=rk-daemon` exactly, so stopping the daemon never touches a tunnel, and a user with no local daemon at all can still tunnel (`openTunnel` births the socket's tmux server itself, pinning CWD via `tmux.ServerBirthDir()` on the same server-birth seam rule). Living on the infrastructure socket also keeps tunnel windows out of the dashboard's user-session enumeration entirely. The one shared fate is a whole-server kill — a manual `tmux -L rk-daemon kill-server`, or the explicit `rk daemon restart --full` opt-in (which captures the up-tunnel set first and reconnects it after the fresh start — see **`--full` semantics** above); no rk startup path issues one: `reapStaleDaemonSocket` kills only the exact-match daemon session(s) (see **Stale-session reaping** below).

**The `rk-code-server` sibling session runs the daemon-managed editor** (260811-a2bo-daemon-code-server-stable-route) (260813-oid2-own-code-server-install). Every `daemon start` / `restart` (both `Start` and `StartWithBinary` funnel through `startSession`) ends with a best-effort `ensureCodeServer()` (`internal/daemon/codeserver.go` — a thin wrapper over the shared `ensureCodeServerCore(cli bool)`, whose `EnsureOutcome` enum classifies the ending so the CLI sibling can print outcome lines while the daemon ignores it) that spawns code-server as its own session `rk-code-server` (single window `code-server`) on the SAME `rk-daemon` socket — the `rk-remotes` sibling-session precedent: it shares the socket, not the `rk-daemon` session's lifecycle, so it survives `rk serve` exits and `daemon stop` (`Stop()`'s exact-match `=rk-daemon` target and kill-session fallback never touch it — server-side terminals and hot-exit state live in the editor process; killing it is a manual tmux action, no `--all` flag). The binary resolves via a **two-rung ladder** (`resolveCodeServerBinary`): (1) the managed install's `~/.rk/code-server-bin/current/bin/code-server` — verified regular+executable via `codeserver.ManagedBinary`, spawned as the absolute `current`-symlink path (the tmux window's PATH is not rk's, and spawning through `current` means a version flip + respawn needs no argv change), then (2) `exec.LookPath("code-server")` — a user-managed PATH install stays respected (same spirit as the externally-managed-port carve-out). Launch argv: `new-session -d -s rk-code-server -n code-server env -u VSCODE_IPC_HOOK_CLI <resolved-binary> --bind-addr 127.0.0.1:{port} --auth none --disable-telemetry --disable-update-check --disable-workspace-trust --disable-getting-started-override --app-name run-kit --user-data-dir {home}/.rk/code-server-profile --extensions-dir {XDG_DATA_HOME|~/.local/share}/code-server/extensions` via the shared `runTmux` wrapper — the `env -u` strips the VS Code integrated-terminal var that flips code-server into `code`-CLI mode ("open in existing instance" → exits with *Please specify at least one file or folder*; the dev.sh lesson); loopback-only + `--auth none` because the rk origin is the trust boundary. The five curation flags curate the embedded `/code` lens (260812-6rxw-code-server-launch-flags): telemetry and the update notifier off (updates arrive via rk — `rk code-server update`, also run as `rk update`'s third leg — so the built-in GitHub check could only nag wrongly), workspace trust disabled (the lens only opens rk-managed worktrees; code-server has no auto-accept flag — disabling the feature is the only mechanism, and every workspace runs implicitly trusted), the Coder getting-started promo removed from the Welcome tab, and the app name set to `run-kit`. The two trailing profile flags carry the **rk-owned seeded profile** (260812-71bv-code-server-seeded-profile): `--user-data-dir ~/.rk/code-server-profile` (absolute, via the `codeServerUserHomeDir` seam — tmux execs the argv via `env`, not a shell, so no tilde expansion) reaches the settings that have **no CLI flags** (verified code-server 4.112.0 / Code 1.112.0), and `--extensions-dir` is pinned back to code-server's **default** extensions location ($XDG_DATA_HOME else `~/.local/share`, + `code-server/extensions`) because code-server derives its default extensions dir from the user-data-dir (`<user-data-dir>/extensions`) — the pin keeps the user's installed extensions visible. Before the spawn, a **one-shot profile migration** (`migrateCodeServerProfile`) renames the legacy `~/.rk/code-server` profile dir to `~/.rk/code-server-profile` when the old exists and the new does not (both-exist ⇒ the new wins, both untouched; fresh host ⇒ no-op), preserving settings and hot-exit state across the path change, and `seedCodeServerSettings` writes `{profile}/User/settings.json` **only when absent** (write-once: user edits persist byte-for-byte) with the baseline `{"chat.disableAIFeatures": true, "workbench.startupEditor": "none"}` — the first hides the "Build with Agent" chat panel, the second suppresses the welcome tab. Degradation is two distinct rungs: a failed migration or seed warns and keeps the profile flags (code-server creates its own dir; only the baseline is lost), an unresolvable home warns and drops both profile flags (spawning with the curation-flags-only argv — a relative/empty path would be worse; with no home there is also no managed rung, so PATH alone decides the binary). Flags and seed apply only to instances rk spawns — an externally managed instance keeps its own configuration and is never seeded, and an already-running `rk-code-server` session keeps its old argv until it next spawns fresh. **Idempotency ladder** (re-entrant on every start, in check order): (1) the `rk-code-server` session already exists ⇒ skip silently; (2) no resolvable port (degenerate `RK_PORT`) ⇒ warn and skip; (3) the resolved port already accepts connections ⇒ skip with an `slog` note (an externally managed instance is respected — the mirror of dev.sh's preset-port carve-out); (4) the binary absent on BOTH ladder rungs ⇒ spawn the **`code-server-install` job window** in `rk-jobs` (`spawnCodeServerInstallJob`, via `daemon.RunJob`) running the shell chain `<rk-exe> code-server install && <rk-exe> code-server start` — `<rk-exe>` is the daemon's own `selfpath.Resolve`d binary, single-quoted with the package's `shellQuote` because tmux joins the argv words into its own `sh -c` (the space-in-path edge `RunJob`'s unquoted join documents) — and return immediately: the daemon NEVER blocks on the ~100MB download; the chain's `&&` IS the install→start sequencing (daemon start is one-shot, no supervisor loop, Constitution VI); `RunJob`'s live-window dedup is the duplicate-job guard (a second daemon start mid-download spawns nothing), and a dead window from a failed prior run respawns naturally on the next start. The job's progress is visible as a tmux window on the dashboard; meanwhile the lens degrades to the not-running state and `rk doctor` reports the absence with the `rk code-server install` hint. Acquisition fires ONLY when the binary is missing — never a per-start latest check (no surprise upgrades, no spurious GitHub API calls; upgrades are the explicit `rk code-server update` / `rk update` paths). Any spawn failure is `slog`-logged, never propagated — `rk serve` comes up on every branch. The exported `StartCodeServer()` / `KillCodeServerSession()` / `CodeServerSessionCommand()` are the CLI surface over the same machinery (§ CLI Subcommands, `code-server` row). `KillCodeServerSession()` returns `(killed bool, err error)` — `(false, nil)` when no session existed (and never waits), `(true, nil)` after a successful exact-match kill — and on that successful kill it blocks, bounded, until the dying process's port stops accepting connections (§ Daemon Lifecycle → Release-synchronous kill primitives; the kill's tmux command runs through the `codeServerKillRun` seam). `CodeServerSessionCommand()` (260813-2s4u-respawn-aware-code-server-install) reads the running session's spawn command live from `#{pane_start_command}` — via `list-panes -t =rk-code-server:=code-server`, NOT `display-message` (whose unresolvable-window target silently falls back to the active window — see the `rk-jobs` probe note below); first line wins, tolerating a manual split — returning `(cmd, exists, err)` where an absent session is `("", false, nil)` and an existing-but-uninspectable session is `("", true, err)`, uncertain evidence the CLI never kills on. It is how `rk code-server install` classifies a session as managed (start command contains the `codeserver.ManagedBinary` path — managed-rung spawns embed the `current`-symlink path in argv) vs foreign (brew/PATH-era). Test seams are the package vars `codeServerSessionExists` / `codeServerSpawn` / `codeServerLookPath` / `codeServerUserHomeDir` / `codeServerRunJob` / `codeServerSelfPath` / `codeServerPaneCommand` / `codeServerKillRun` (the file's seam style; the home seam is stubbed to a temp dir in every test so no test writes the real `~/.rk`).

**The `rk-jobs` sibling session hosts managed job windows** (`internal/daemon/jobs.go`). `RunJob(ctx, window, argv)` runs an argv in a window of the `rk-jobs` session on the `rk-daemon` socket (260812-z1ya-update-daemon-tmux-window) — the third instance of the sibling-session shape (`rk-remotes`, `rk-code-server`): it shares the socket, not the `rk-daemon` session's lifecycle, so a job window survives the daemon restart the job itself triggers (`daemon.Stop()`'s exact-match `=rk-daemon` kill never touches it). Semantics, in order: (1) **daemon gate** — a down daemon errors instead of birthing a tmux server as a side effect; (2) **session-absent fast path** — `rk-jobs` is created WITH the job window as its first window (`new-session -d -s rk-jobs -n <window> -P -F '#{window_id}' <argv…>`, the `internal/remote` tunnel pattern), so no idle default shell window ever exists and the dedup probe is skipped (no session ⇒ no in-flight job); a lost concurrent-create `duplicate session` race falls through to the session-exists path; (3) **window dedup** on the exact-match `=rk-jobs:=<window>` target, one `list-panes -t <target> -F '#{window_id} #{pane_dead}'` probe (an error — `can't find window` — ⇒ absent; first line parsed, job windows are single-pane by construction). `list-panes`, NOT `display-message`: display-message with an unresolvable window part silently falls back to the session's ACTIVE window and exits 0 (verified on tmux 3.6a), so it cannot distinguish an absent job window from the session's active one (§ Design Decisions → Job-window probe reads `list-panes`, never `display-message`) (260812-anac-fix-job-window-probe-fallback). Live pane ⇒ return the existing target with `started=false` (in-flight — no second spawn); dead pane (a completed prior run, any exit status) ⇒ `respawn-window -k` relaunches argv IN the dead window (reap-on-rerun in place — no timer/reaper, window id stable; `kill-window` + respawn is wrong here because the job window is usually the session's ONLY window and killing a session's last window kills the session); absent ⇒ spawn; (4) **spawn (session-exists path)** `new-window -d -t =rk-jobs: -n <window> -P -F '#{window_id}' <argv…>` (tmux joins the trailing argv into its own `sh -c` — the shipped codeserver spawn's same boundary. argv is caller-supplied and shell-sensitive: the primitive validates only the WINDOW name; the web handlers pass rk-controlled binaries plus `ValidateToolName`-validated tool names, while `rk daemon run` passes the CLI user's own command verbatim — their own shell authority. Multi-word arguments do NOT survive the unquoted join, so effective argv are single-word tokens); (5) **best-effort post-spawn options** (warn-only, never fail the spawn): `set-option -w remain-on-exit on` (the pane persists after any exit — the completed run's output stays on screen until the next run respawns the window in place) and `pipe-pane -o 'cat >> ~/.rk/<window>.log'` (durable log continuity at the `~/.rk/update.log` / `~/.rk/restart.log` paths). The window name is validated at the primitive (`ValidateToolName` class) before it becomes a tmux target or a pipe-pane shell-string component (§I). Job windows are **watchable in the dashboard for free** — `ListServers` surfaces every live tmux server, so `rk-jobs:update` appears on the existing terminal route (`/rk-daemon/{N}`, window id `@{N}`) with zero new UI plumbing. Consumers: the `/api/update` + `/api/restart` handlers (in-process via the api `runJobFn` seam), `rk daemon run` (CLI wrapper), and the daemon's missing-binary code-server acquisition (the `code-server-install` window running the quoted install-then-start shell chain — see the `rk-code-server` sibling session above). Test seams mirror the codeserver style: `jobDaemonRunning` / `jobSessionExists` / `jobWindowState` / `jobRunTmux` / `jobRunTmuxOutput` / `jobUserHomeDir`.

Detection: `tmux -L rk-daemon has-session -t =rk-daemon` (anchored `=` prefix forces exact-match — see PR #196). `runningSessionCtx` consults `=rk-daemon` first, then falls back to `=rk` for transparent stop/restart of pre-rename daemons. No polling loop, no signal files, no supervisor script.

**Port-based liveness probe**: Before `Start()`/`StartWithBinary()` create the tmux session — and AFTER the `IsRunning()` check passes — they call `guardPortAvailable()`, which loads `config.Load()` and runs `net.DialTimeout("tcp", host:port, 400ms)` against `RK_HOST:RK_PORT`. Wildcard/empty hosts (`""`, `"0.0.0.0"`, `"::"`, `"[::]"`, `"[::1]"`) substitute `127.0.0.1` via `probeHost()` — dialing `0.0.0.0` itself is platform-inconsistent and not a reliable liveness signal. If the dial succeeds (something is listening), `Start` returns an error containing the substrings `already serving on`, `not under the rk-daemon`, and `RK_PORT` so scripts can pattern-match. Cobra `RunE` propagates the non-zero exit. This closes the split-brain detection gap where a foreground `rk serve` was invisible to the tmux-only `IsRunning()` check.

**Stale-session reaping**: When `IsRunning()` is false AND the port probe passes, `Start`/`StartWithBinary` call `reapStaleDaemonSocket(ctx)`, which issues an exact-match `runTmux(ctx, "kill-session", "-t", "="+session)` for each daemon session name — `SessionName` then `LegacySessionName` — scoped strictly to `serverSocket = "rk-daemon"` (never the agent-session `runkit` server) and never `kill-server`: the socket is multi-tenant, and the sibling sessions (`rk-jobs`, `rk-code-server`, `rk-remotes`) deliberately outlive the daemon (§ Design Decisions → Session-scoped daemon startup reap). Each attempt is preceded by a `tmux teardown` audit WARN (`op=kill-session`, `target=<session>`, `callers=daemon.reapStaleDaemonSocket`). It is a race-window safety net — a leftover daemon session appearing between the `IsRunning()` probe and `startSession` — and idempotent: "can't find session" / "no server running" on cold start is the common case, suppressed to `slog.Debug` and never blocking startup; if anything is genuinely broken, the subsequent `startSession` surfaces it. (260813-b41g-scope-daemon-socket-reap)

**Startup logging via `RK_DAEMON_LOG`**: `startSession` resolves `os.UserCacheDir()/rk/daemon.log` (e.g. `~/.cache/rk/daemon.log` on Linux, `~/Library/Caches/rk/daemon.log` on macOS) via `resolveDaemonLogPath()` and passes it to the inner `tmux new-session` via `-e RK_DAEMON_LOG=<path>`. The serve startup's `setupSlog(level)` reads the env var, `os.MkdirAll(filepath.Dir(p), 0o755)`, opens the file with `O_APPEND|O_CREATE|O_WRONLY` (mode 0o644), and wraps `io.MultiWriter(os.Stderr, file)` so slog output is teed to both the tmux pane (preserves `tmux attach` debugging) and a durable log file. Open failures fall back to stderr-only with one `slog.Warn("daemon log unavailable", ...)`; `UserCacheDir()` failure in `startSession` spawns the inner serve without the env var (single `slog.Warn` upstream). Logging is best-effort — never blocks daemon creation. Constitution §VI compliance: the log is a passive append-only artifact, no supervisor, no signal file, no liveness derivation from contents.

The exported constant `daemon.LogEnvVar = "RK_DAEMON_LOG"` is the single source of truth (consumed by both `internal/daemon/startSession` and `cmd/rk/serve.go/setupSlog`).

**`rk doctor` `agent hooks` row** (`agentHooksCheck(home, readFile, stat)` in `cmd/rk/doctor.go`, registered in `runDoctorChecks` — `failLabel: "agent hooks"`): a **pure function over the `(home, readFile, stat)` seam triple** (the `tmuxGuardShimCheck` style, so fixtures never touch the real home) that reports the installed agent-hook generation per `agentRegistry(home)` agent (v1: Claude Code, `~/.claude/settings.json`). For each agent it reads the settings file, walks the rk-owned hook commands (the same hooks-array walk the installer uses — one shared walk, no duplicated traversal), and classifies each entry via `classifyHookGeneration` reusing `isRkEntry`'s three markers ([agent-state](/run-kit/agent-state.md) § `rk agent setup`): gen-1 = inlines `@rk_agent_state` (`tmux.LegacyAgentStateOption`), gen-2 = contains ` agent-hook `, gen-3 = contains ` agent hook `. Outcomes: an absent settings file or one carrying no rk entries → OK, Note `not installed (optional — install with \`rk agent setup\`)`; any gen-1 or gen-2 entry → FAIL, Hint `N stale hook entr(y|ies) in <path> (generation <g>) — they write legacy option names; re-run \`rk agent setup\` to replace them`; a gen-3 entry whose embedded rk path (the first double-quoted token after `; `, matching `agentStateHookCommand`'s template) is not an existing regular executable → FAIL, Hint naming the path and `re-run \`rk agent setup\``; an unreadable-but-present settings file → FAIL (never misreported as "not installed"); otherwise OK, Note `installed (generation 3, <agent>); writes @rk_pane_agent_state + @rk_agent_state`. The row exists because gen-3 hook text names no option — the write lives in the binary — so only gen-1 inline one-liners can still write the retired unscoped pane names. Its removal-window counterpart lives in [tmux-sessions](/run-kit/tmux-sessions.md) § Deprecation Ledger (the row itself stays; its gen-1/gen-2 FAIL branches can go once nothing reports them).

**Port-owner lookup (`internal/ports/portowner.go`)**: shared helpers used by all four `rk daemon` subcommands and by the sequencer's force leg. `ports.FindPortOwner(ctx, host, port) (*ports.PortOwner, error)` queries who is listening on the configured TCP port via `lsof -ti:<port>` (primary), falling back to `ss -tlnp '( sport = :<port> )'` when `lsof` is unavailable or errors. Both queries are port-only — the `host` argument is pass-through for display (both tools correctly cover loopback and wildcard binds). Holder command is resolved via `ports.ResolveCommand` (`/proc/<pid>/comm` on Linux, `ps -p <pid> -o comm=` on macOS). Returns `(nil, nil)` when nothing is listening; `(nil, error)` only when both tools fail. The companion `ports.TerminateOwner(ctx, owner)` mirrors `daemon.Stop`'s graceful escalation: `syscall.Kill(pid, syscall.SIGTERM)` → 200ms polling for exit via `syscall.Kill(pid, 0)` up to a 5s grace period → `syscall.Kill(pid, syscall.SIGKILL)` on timeout. Signal delivery uses `syscall.Kill` directly — never a shell `kill` invocation. All subprocess calls (`lsof`, `ss`, `ps`) use `exec.CommandContext` with a 5s `context.WithTimeout` per Constitution §I. The CLI call sites (`daemon_start.go`, `daemon_stop.go`, `daemon_status.go`) reach the helpers through cmd-level seam vars (`findPortOwnerFn`/`terminateOwnerFn`/`ownerIsDaemonFn`) so CLI tests drive `--force` paths without spawning the real tools; the sequencer stubs its own `restartFindPortOwnerFn`/`restartTerminateOwnerFn` seams in `internal/daemon`.

**Holder-identity check (`daemon.InnerServePID()`)**: small helper in `internal/daemon` that returns the PID of the `rk serve` process running inside the daemon tmux pane, derived from tmux's `pane_pid` format spec via `tmux -L rk-daemon list-panes -t =rk-daemon:=serve -F '#{pane_pid}'` (a new `runTmuxOutput` internal captures stdout where `runTmux` would have discarded it). Returns `(0, error)` when the daemon session is absent or the tmux query fails. Used by every `--force` code path and by `rk daemon status` to recognize the daemon as the port owner — when `owner.PID == innerServePID`, the port is classified as held by us (no signal sent in `--force`; `held-by-daemon` state in `status`). The shared predicate is `daemon.OwnerIsDaemon(owner *ports.PortOwner) bool` in `internal/daemon` (behind its own `innerServePIDFn` package seam, so the sequencer's force leg and cmd tests drive the self-recognition branch); `daemon status` additionally wires a cmd-level `var innerServePIDFn = daemon.InnerServePID` in `daemon_status.go` because its report needs the raw PID, not just the predicate.


## tmux Control-Mode Subscription (`internal/tmuxctl`)

Package `app/backend/internal/tmuxctl/` owns the long-running `tmux -CC` control-mode subscriptions that drive sub-500ms SSE freshness. It is the **only sanctioned bypass** of the `internal/tmux/` boundary — every other tmux interaction goes through the request-response helpers in `internal/tmux/tmux.go` with their 10s `context.WithTimeout`. The bypass exists because a single long-lived subscription is structurally incompatible with the `exec.CommandContext`-plus-timeout shape of `internal/tmux/`. The package's `doc.go` documents the boundary explicitly.

### Core types

- **`Client`** (`client.go`) — one PTY-backed `tmux -CC` subscription per tmux server (identified by socket name). Runs `tmux [-L <socket>] -CC attach-session -t =<bootstrap> -r` via `creack/pty.Start` (the `-r` flag puts the connection in read-only mode — see Design Decision below). The `=`-anchored target prevents prefix-match collisions, matching the convention established in PR #196. A single goroutine reads lines via `bufio.Scanner` and dispatches them through `ParseLine`. Public surface:
  - `Open(ctx, socket, sink) (*Client, error)` — non-blocking; errors only on initial PTY allocation or process start failure.
  - `Close() error` — idempotent; cancels the Client's context, kills the subprocess, terminates the reconnect loop.
  - `Generation() int64` — atomic per-server counter incremented on every handled notification.
  - `Wait(after int64) <-chan struct{}` — returns a channel closed once generation > after. Single-use; callers re-call after each consumed event.
- **`Supervisor`** (`supervisor.go`) — owns `map[socket]*Client` guarded by `sync.Mutex`, plus an `fsnotify.Watcher` on the watch directory. Resolves the watch dir from `TMUX_TMPDIR` if set, else `/tmp/tmux-<euid>/`; missing directories are created via `os.MkdirAll(dir, 0o700)` and watched as sockets appear. `Start(ctx)` enumerates existing sockets synchronously (so the SSE hub never races an empty Client map for sockets that already exist on disk) and then runs an fsnotify event loop. Re-creating a socket of the same name closes the prior Client before opening a new one. `Stop(ctx)` closes every Client and the watcher; bounded 5s in production. `Get(socket) *Client` is the lookup used by the SSE bridge. Three observation seams serve the layout snapshotter (all nil-safe/no-op when unwired, so an unwired Supervisor behaves identically): `Sockets() []string` (the covered-server set — `rk-test-*`/`.lock` candidates never open a Client, so a consumer inherits this scope filter with no enumeration of its own), `Generation(name) int64` (convenience over `Get` for callers that only need the counter), and the `OnSocketRemoved func(name string)` callback field invoked from `closeSocket` **outside** the mutex on the event-loop goroutine after a dead server's Client is closed — set it before `Start`.
- **`EventSink`** (`event_sink.go`) — consumer interface with 8 callbacks (`OnSessionWindowChanged`, `OnWindowAdd`, `OnWindowClose`, `OnWindowRenamed`, `OnSessionsChanged`, `OnLayoutChange`, `OnConnectionLost`, `OnConnectionEstablished`). All callbacks dispatch from a single goroutine — the Client's read loop. Sink implementations MUST NOT block. The production sink in `api/tmuxctl_bridge.go` (`hubSink`) records per-group active-window state into a per-Client `ActiveWindowTracker` (see § SSE Hub Bridge) (260530-v6hm-active-window-event-derivation). The SSE hub observes *change* via the per-server generation counter; the sink's tracking is a side effect that supplies the Tier-1 active-window signal to the fetch path. `NoOpSink` is exported for tests, PTY-unavailable scenarios, and as the degraded sink a `nil` SinkFactory produces.
- **`ParseLine(line string) Event`** (`parser.go`) — pure function (no I/O, no time dependence). Recognises the six relevant tmux 3.6a notifications (`%session-window-changed`, `%window-add`, `%window-close`, `%window-renamed`, `%sessions-changed`, `%layout-change`) and framing markers (`%begin`/`%end`/`%error`). `%output` and `%unlinked-window-*` are silently dropped. Unknown notification names return `UnknownEvent{Raw}` and log `slog.Debug` exactly once per unique name (surfaces protocol additions without log noise). Malformed input returns `MalformedEvent{Raw}` — never panics.

### Reconnect FSM

When the PTY read loop encounters EOF or any error other than a Close-driven context cancellation, the Client calls `sink.OnConnectionLost()` exactly once, tears down the subprocess (`cmd.Process.Kill()` if still running, `cmd.Wait()` to reap), waits a backoff, then retries `pty.Start`. The backoff sequence is `initialBackoff = 250ms` → `500ms` → `1s` → `2s` → `5s` → `5s` … capped at `maxBackoff = 5 * time.Second`. The backoff resets to `initialBackoff` on the first non-`%begin` event after a successful reconnect (see `client.go` `handleEvent`). Reconnect retries continue indefinitely until `Close()` is called. Test injection points: `dialFn` and `sleepFn` are swappable so the FSM can be exercised with stubbed I/O and a fake clock.

### Anchor session (`_rk-ctl`)

`tmux -CC` requires an attached session to emit notifications. `resolveBootstrap` (in `client.go`) **always** creates a hidden anchor session named `_rk-ctl` via `tmux [-L <socket>] new-session -d -s _rk-ctl` — unconditionally on every observed server, not only when the server is empty (260602-a1wo-prevent-exit-empty-server-death) — the anchor is a permanent **session floor** that keeps the server's session count above zero so tmux's `exit-empty` cannot reap it — see § Constitution Alignment §VI below and `tmux-sessions.md` § `_rk-ctl` Anchor). A "duplicate session" error from `new-session` (concurrent `rk serve` created the anchor first) is treated as benign by `isDuplicateSessionError` and the Client proceeds to attach. The anchor's `new-session` is built by the extracted `anchorCommand(ctx, socket)`, which pins `cmd.Dir = tmux.ServerBirthDir()` (the server-birth CWD pin — the anchor's `new-session` is birth-capable) and `cmd.Env = tmux.CleanEnvForServer()` (the same env sanitization `CreateSession` uses) while preserving the stderr-capture-into-error `isDuplicateSessionError` relies on (260720-ji0k-pin-server-birth-cwd-home); see `tmux-sessions.md` § `_rk-ctl` Anchor. **Floor vs. attach target are decoupled**: the anchor is always created (the floor), but the control-mode attach target still prefers the first existing real session (`firstSessionName`, which skips `_rk-ctl` so the always-present anchor is not picked), falling back to `_rk-ctl` only when no real session exists. The anchor is hidden from user-facing surfaces via `tmux.ControlAnchorSessionName` — see `tmux-sessions.md` § `_rk-ctl` Anchor for the filtering chokepoints, the `exit-empty off` backstop, and the explicit-kill-only lifetime contract.

### Origin stamp (`@rk_srv_origin`)

`productionDial` also stamps the covering deployment's origin onto the dialed server's `@rk_srv_origin` user option, immediately beside the `SetExitEmptyOff` backstop and under the same contract: it runs on **every dial AND every reconnect**, is **non-fatal** on error (`slog.Debug`, the dial proceeds), and writes unconditionally (no read-compare — dials are rare: startup, socket birth, reconnect). `cmd/rk/serve.go` injects the origin once before `supervisor.Start` via `tmuxctl.SetStampOrigin(fmt.Sprintf("http://%s:%d", cfg.Host, cfg.Port))`, derived from the same `config.Load()` the server binds with. The stamp is skipped when the injected origin is empty (non-serve tmuxctl consumers are unaffected) or when `tmux.ServerAllowed(socket)` is false (an allowlisted deployment must never overwrite a host server's origin). This seam placement is what covers and heals: fsnotify socket-create → `openSocket` → dial stamps every server at birth, the synchronous `Start` enumeration stamps every pre-existing server at daemon startup (healing a port change across restarts), and reconnects re-stamp for free — independent of whether any client is viewing the server. The pane-side reader is the `cmd/rk` origin resolver (see the `url` row and `tmux-sessions.md` § Server-Scoped User Options).

### SSE Hub Bridge (`api/tmuxctl_bridge.go`)

The `api` package owns the bridge between `tmuxctl.Supervisor` and the SSE hub. Three artefacts:

- **`WindowChangeSubscriber`** (interface defined in `api/sse.go`) — the interface the hub uses to receive per-server change notifications. Methods: `Generation(server string) int64` and `Wait(server string, after int64) <-chan struct{}`. Generation semantics mirror `tmuxctl.Client`: every observed notification increments the counter; `Wait(after)` returns a channel closed once `generation > after`.
- **`supervisorSubscriber`** — the production adapter. Forwards `Generation` and `Wait` calls to `Supervisor.Get(server).Generation()` / `.Wait(after)`. When no Client exists for a server (PTY-unavailable host, socket not yet allocated), `Wait` returns a **never-closing** channel via `neverChan()` so `selectFirst` falls through to the safety-net timer rather than busy-looping `FetchSessions`. Exported via `NewSupervisorSubscriber(sup)`.
- **`hubSink`** — the production EventSink, one per Client, built by the `SinkFactory` returned from `NewHubSinkFactory()` (the `Supervisor` calls the factory per socket, passing that socket's own `ActiveWindowTracker` — see § Active-Window Event Derivation below). Beyond the generation-counter path (which the Client bumps itself, before invoking the sink, so the hub observes *change* via `Wait`), `hubSink` records active-window state into its tracker: `OnSessionWindowChanged(sid, wid)` resolves `sid`→group via the tracker's cached map (O(1), no subprocess) and records `wid` as that group's active window (latest-event-wins; an unresolved `sid` is dropped for tracking, never errors/blocks); `OnSessionsChanged` refreshes the `$sid`→group map; `OnConnectionEstablished` re-seeds the tracker (refresh map + seed Tier 1 from current `#{window_active}` per group). The two re-seed callbacks issue read-only tmux queries that could block, so they are **offloaded to a goroutine** (the read loop returns immediately — honoring the EventSink "MUST NOT block" contract); the tracker's concurrency-safety makes a slightly-delayed refresh racing an event harmless. The read-only query seams (`listSessionGroups`/`listActiveByGroup`) are injectable struct fields so tests stub them without spawning tmux. The remaining callbacks (`OnWindowAdd`/`Close`/`Renamed`/`OnLayoutChange`/`OnConnectionLost`) stay no-ops.

`Server.SetWindowChangeSubscriber(sub)` materialises the lazy SSE hub (`initSSEHub`) and stores the subscriber. Safe to call before any SSE client connects. `Server.SetActiveWindowProvider(provider)` (260530-v6hm) injects the Tier-1 `ActiveWindowProvider` (the Supervisor) into the production `prodSessionFetcher` so the REST + SSE fetch paths derive `isActiveWindow` from control-mode events; it is a no-op when the fetcher is a test-injected fake, keeping the seam optional.

### Active-Window Event Derivation

The active-window highlight is **event-derived per session group** rather than read from the base session's `#{window_active}` pointer alone. The base pointer goes stale whenever an attachment moves the active window while another group member keeps an independent active-window pointer — `rk riff` or an external `new-window`; reading the base pointer alone produces a wrong highlight. This derivation subsystem (`internal/tmuxctl/*`) is **not deletable**: it is driven by the `_rk-ctl` anchor and serves the SESSIONS highlight independently of boards (260602-qn62-move-based-board-pin-sessions). The relay is NOT among its stale-pointer sources — there is no `rk-relay-*` ephemeral (the subsystem's internal comments reference relays; they are not a live source). The derivation corrects the *read signal* only; it changes no window creator. (260530-v6hm-active-window-event-derivation)

**Tracker** (`internal/tmuxctl/active_window.go`) — `ActiveWindowTracker` is a concurrency-safe, in-memory (Constitution §II) store for ONE server, owned by one `Client` (the read-loop goroutine is the sole writer; the fetch path reads). Two `sync.RWMutex`-guarded maps: `byGroup` (group name → active `@wid`, latest-event-wins via `Set`, bulk re-seeded via `SeedGroups`) and `sidGroup` (`$sid` → group, resolved via `ResolveGroup`, refreshed wholesale via `ReplaceSidGroups`). `Get`/`Snapshot` are the read accessors.

**Ownership/wiring** — `NewSupervisor(factory SinkFactory)` takes a `SinkFactory` (a `nil` factory degrades every Client to `NoOpSink` — control-mode observed only via the generation counter, no tracking). `Supervisor.openSocket` allocates a fresh tracker per socket and binds the sink to it (a close-then-reopen gets a new tracker so stale state never leaks across the gap — `OnConnectionEstablished` re-seeds it). `Supervisor.ActiveWindow(server, group) (wid, ok)` is the server-keyed read accessor — a server with no Client, or a group with no tracked entry, returns `("", false)` so the caller falls back to Tier 2. The Supervisor satisfies `sessions.ActiveWindowProvider` directly. Wired in `cmd/rk/serve.go`: `tmuxctl.NewSupervisor(api.NewHubSinkFactory())`, then after `Start` both `SetWindowChangeSubscriber(NewSupervisorSubscriber(supervisor))` and `SetActiveWindowProvider(supervisor)`.

**Two-tier derivation** (`internal/sessions/sessions.go`) — `FetchSessions(ctx, server, provider)` threads an `ActiveWindowProvider` (nil ⇒ Tier-2-only). Per session it queries `provider.ActiveWindow(server, sessionName)` — the user-facing session name IS the group key after `parseSessions` filtering. **Tier 1 (authoritative):** when a tracked `@wid` exists, the pure helper `applyActiveWindow(windows, trackedWid)` marks exactly the matching window active and clears the rest, overriding the parsed `#{window_active}` flag. **Tier 2 (fallback):** no tracked entry ⇒ the base-pointer flag from `parseWindows` stands. Tier 1, once set, is authoritative — the base pointer never overrides it; external clients (iTerm/Ghostty) also emit `%session-window-changed`, so "latest event wins" subsumes them with no override path. `applyActiveWindow` also enforces the single-highlight-per-session invariant and falls back to Tier 2 for a session when the tracked `@wid` matches no live window (e.g. closed between event and fetch) rather than highlighting nothing. The fetcher reaches `FetchSessions` via `prodSessionFetcher` (holding the provider) in `api/router.go`. Frontend auto-follow: the `app.tsx` URL-writeback effect navigates once the corrected `isActiveWindow` arrives via SSE; board panes pin explicit window IDs and never read it.

### Event-Driven SSE Loop

`app/backend/api/sse.go`'s per-server snapshot loop is an event-driven `select` with a 12s safety-net backstop. Five constants govern the cadence:

| Constant | Value | Role |
|----------|-------|------|
| `safetyPollInterval` | `12 * time.Second` | Backstop when a `WindowChangeSubscriber` is wired (production). Heals missed events across reconnect gaps; primary freshness driver is the Client's `Wait` channel. |
| `sseEventDebounce` | `300 * time.Millisecond` | Trailing-edge coalescing window for **subscriber generation bumps**: after a bump-only win, `waitForNext` absorbs further bumps for this window so a control-mode event burst (e.g. `%window-renamed` churn from `cd`-tracking `automatic-rename-format`) costs ONE derive, flooring the event-driven derive rate. Fixed, never extended by further bumps. Explicit `wake()` signals bypass it entirely (a wake ends a pending window immediately); timer wins never enter it; the safety timers and `sseCacheTTL` are independent of it. Per-hub `eventDebounce` field override (zero ⇒ the constant), the `safetyInterval` idiom. (rtwx) |
| `legacyPollInterval` | `2500 * time.Millisecond` | Used when no subscriber is wired (PTY-unavailable startup, unit tests). The snapshot-rebuild cadence is then the only freshness guarantee. |
| `metricsPollInterval` | `2500 * time.Millisecond` | Cadence for `metrics.Collector` host CPU/memory polling. Deliberately decoupled from the SSE intervals so metrics sampling frequency is not coupled to the SSE event/safety cadences. |
| `prStatusPollInterval` | `90 * time.Second` | Cadence for `prstatus.Collector`'s single batched `gh` call (260610-596o-pr-status-sidebar). Deliberately slow (~40 calls/hr vs. the 5000/hr authenticated limit) — the SSE hot path reads the cached snapshot, never `gh`, so PR-status freshness is decoupled from the SSE cadence; on-demand `POST /api/status/refresh` covers the "I want it now" case (260715-jykd). |

`sseHub.safetyIntervalEffective()` picks `safetyPollInterval` when `subscriber != nil`, else `legacyPollInterval` — preserves correctness for the PTY-unavailable case and for tests exercising the hub without a control-mode driver.

The loop body (`poll` + `waitForNext` + `selectFirst`) blocks on a `select` over (a) one `subscriber.Wait(server, perServerGen[server])` channel per active server (only when a subscriber is wired), (b) one **wake** channel per polled server (always — see below), and (c) `time.NewTimer(safetyIntervalEffective())`. Once `selectFirst` unblocks, a non-blocking peek over all cases routes every fired case: each fired server's prior generation is refreshed and the server is marked event-driven so the next iteration invalidates its 500ms `cache` entry and observes the post-mutation tmux state. A **bump-only** win (at least one subscriber case fired, no wake consumed in the same peek) then waits out the `sseEventDebounce` window before returning — blocking on the wake cases plus a fresh window timer, so a wake landing mid-window ends the wait immediately while further bumps are absorbed into the same pass by a final peek (its `Generation()` re-read folds them into `perServerGen`; a bump landing after that peek closes the NEXT `Wait` channel, so nothing is lost). Wake-only and timer wins never enter the window. `selectFirst` reads `timer.C` in the outer select to avoid the goroutine leak that would otherwise occur if a subscriber wins the race and the timer goroutine blocked on `timer.C` forever (`Stop` does not deliver on `C`). Heartbeat is wall-clock-based (`sseHeartbeatPeriod = 15 * time.Second`) — wall-clock cadence prevents the slower safety interval from starving heartbeats.

**Per-server wake seam** (`sseHub.wake(server)`) — a second freshness driver alongside the control-mode subscriber, for mutations tmux control mode never announces. User-option writes (`@rk_win_color`, `@rk_ses_color`, `@rk_win_url`, `@rk_win_lens`, `@rk_win_marker`, `@rk_win_role`, `@rk_win_flair`, `@rk_win_note`, `@rk_protected` — `set-option`) emit **no** `tmux -CC` notification (the tmuxctl parser handles only session/window add/close/rename/active-window/layout events), so without the wake seam these mutations would repaint only on the 12s safety tick (0–12s, mean ~6s — the color-apply lag this exists to remove). `wake(server)` closes the server's entry in a `wakes map[string]chan struct{}` guarded by a **dedicated `wakeMu`** (separate from `h.mu` so a mutation handler never contends on the poll lock): a closed channel means a wake is pending. It is non-blocking, safe from any goroutine, and coalescing — a double `wake` before consumption is a no-op via `select { case <-ch: default: close(ch) }` (never a double-close panic); N wakes before consumption trigger 1..N passes (redundant passes suppressed by the `previousJSON` dedup). Two `wakeMu`-guarded helpers serve `waitForNext`: `wakeChannel(server)` returns the current (lazily-created) channel to add as a wait case, and `consumeWake(server)` retires a *closed* channel by replacing it with a fresh open one and reporting `true` — the replace happens BEFORE the next fetch, so a wake landing between observation and fetch closes the fresh channel and triggers one more pass (**at-least-once**, never a busy-loop). `waitForNext` builds a wake case for **every** polled server **independent of `h.subscriber`** (tagged `waitCase.isWake`), so wakes work even when `subscriber == nil` (unit-test hubs, PTY-unavailable hosts) — there is no timer-only early return for the nil-subscriber path. After `selectFirst` unblocks, a non-blocking peek over all cases (run again after the `sseEventDebounce` window when a bump-only win entered it — re-peeking a closed channel is idempotent) routes each fired case by `isWake`: a wake win calls `consumeWake` and, only when it retires a pending wake, sets `eventDrivenServers[server] = true`; a wake consumed in the initial peek — or firing mid-window — skips or ends the debounce, keeping the seam's sub-second repaint (so `poll()` invalidates the 500ms fetch cache and the woken pass observes post-mutation state, not a stale cached fetch) — it never touches `perServerGen`/`Generation()` (every `h.subscriber` deref is guarded, so a wake-only path with `subscriber == nil` never nil-panics); a subscriber win keeps its existing bookkeeping unchanged. The seam lives entirely within `sseHub`/`waitForNext`/`selectFirst`; the tmuxctl bridge, `supervisorSubscriber.Wait`'s `neverChan()` contract, and the timer/coverage machinery are outside it. Effect: user-option mutations repaint every consumer (sidebar rows, session tiles, boards, all tabs) within one poll pass — sub-second, since the tmux write has already landed when the wake fires. Call sites: `handleWindowOptions` (`windows.go`, `POST /api/windows/{windowId}/options`), `handleSessionColor` (`sessions.go`, `POST /api/sessions/{session}/color`), and `handleServerProtect` (`servers.go`, `POST /api/servers/protect`) each run `s.initSSEHub(); s.sseHub.wake(server)` after a successful tmux write and before the `{"ok": true}` response — no wake on validation failure or tmux error (the handlers return early), no API-contract change. Mirrors the established `handleSessionOrderPost` wake-after-write pattern. **Known limitation**: the dead-server reap block deletes `perServerGen`/`eventDrivenServers`/`h.cache`/`h.clients` for a gone server but NOT `h.wakes[server]`, so the `wakes` map can slowly grow with churning ephemeral server names (a per-server closed/open `chan struct{}` — small; not yet reaped). (260718-xpur-hub-wake-option-mutations)

**Operator-request queue tracker seam** (`sseHub.operatorQueue *operatorQueueTracker`, `api/operator_queue.go`) — the third tracker riding the per-server assembly seam, beside waiting-push and auto-name: `newSSEHub` constructs it unconditionally (always-on — no settings key, unlike the auto-name tracker), `initSSEHub` wires its deliver closure (`Server.operatorQueueDeliver()`, `api/router.go` — the closure fetches sessions fresh inside the detached worker and takes no tick snapshot), the tick advances it right after the auto-name block, and the post-loop retain sweep reaps per-server state with `retain(polledServers, reapableServers)` — keyed off the polled-server set, so a confirmed-dead server drops its queue/in-flight/min-gap state while a transiently-unpolled server keeps it. Full contract in [operator-actuation](operator-actuation.md) § Operator-request queue — drain on idle.

**Settings-driven tracker apply seam** (`sseHub.setAutoName`/`getAutoName` behind a dedicated `autoNameMu`, `api/sse.go`) — the hub's auto-name tracker is the one hub structure an HTTP mutation swaps at runtime. `setAutoName(enabled, deliver)` is the single apply seam, shared by `initSSEHub` (the startup seed from `Server.autoNameEnabled`) and `handlePostSettings` (a successful body containing `auto_name`, set or null-unset): disabled publishes nil (the feature-absent state both tick sites — advance, retain — already check), enabled publishes a freshly-built tracker with the deliver closure wired; a re-enable builds a NEW tracker, dropping prior in-memory cooldowns (process-memory semantics, Constitution II). The deliver closure is built once by `Server.autoNameDeliver()` (`api/router.go` — closing over the shared operator-request delivery core, always the `fix-tab-name` template) so both call sites share identical wiring. The pointer is guarded by a dedicated `autoNameMu` (the poll loop reads while the POST handler swaps from an HTTP goroutine): both tick sites read via `getAutoName()` and use the snapshot lock-free, the tracker being self-contained once published (own mutex; deliver wired by the publisher). The seam is a local apply, not a broadcast — no SSE event is emitted. See [operator-actuation](operator-actuation.md) § Auto-name on idle for the tracker's transition/rate-limit contract. (260823-5r41-settings-pane-live-apply)

### Board Membership Needs No Kill-Cleanup Diff

The SSE hub does NOT detect killed windows to clean up board membership: there is no killed-window diff, no per-server `previousWindowIDs` tracking, no per-tick window-kill cleanup loop, and no `RemoveAllByWindowID` on `BoardEntriesFetcher`. ### PR-Status SSE Join

The SSE hub attaches live PR status to **any window with a derived `PrURL`** on each poll via a PURE in-memory read — the 2.5s hot path makes ZERO network/`gh` calls (the `gh` cost lives entirely on the collector's 90s background tick, the branch→PR refresher's 30s tick plus its coalescing registration/seed wake, and the on-demand `POST /api/status/refresh` — which kicks BOTH) (260715-jykd). The startup seed cache's file IO is off the hot path for the same reason: one read at process start before either poller runs, and writes only at the tail of those same background passes. There is no change-bound gate: `PrURL` is derived from the pane's branch (§ Branch→PR Derivation), so PR status appears for any pane on a branch with an open PR, not only fab-change-bound windows. (260705-dmex-generic-agent-state-tier) (260610-596o-pr-status-sidebar)

**Seam + wiring**: `PRStatusSnapshotter` (one method, `Snapshot() map[string]prstatus.PRStatus` — URL-keyed, since PR numbers are only unique per repo, in `api/sse.go`) is implemented by `*prstatus.Collector` and held on the hub (`sseHub.prStatus`). `newSSEHub(fetcher, mc, svc, pc)` takes it as the fourth arg; `NewRouterAndServer` constructs `pc := prstatus.NewCollector(prStatusPollInterval); pc.Start(ctx)` next to the metrics collector, stores it on `Server.prStatus`, and `Server.initSSEHub` passes it through — but as a true nil interface when `s.prStatus` is nil (the explicit `var pc PRStatusSnapshotter; if s.prStatus != nil { pc = s.prStatus }` wrap avoids the typed-nil-interface trap so the hub's `h.prStatus == nil` check actually fires). A nil `prStatus` degrades gracefully (no PR fields attached) — used by tests and unwired routers.

**`attachPRStatus(sess []sessions.ProjectSession)`**: called in `poll()` AFTER the 500ms session-cache write (so the cached snapshot slice stays free of mutable PR fields conceptually, though it operates on the same slice by reference). For every window it FIRST resets the **collector-only** fields (`PrChecks/PrReview/PrIsDraft` → zero, `PrFetchedAt` → nil) so a window that lost its PR (merged/closed → dropped from the snapshot) clears cleanly even on a cached result slice (260715-nwla-status-refresh-feedback); **`PrState` is deliberately NOT reset here** — it is dual-sourced (the branch-derived `MapBranchState` fallback seeded upstream by `enrichWindowPR`), so it survives a collector miss and is overridden below only on a collector hit. THEN, gating only on a **non-empty `PrURL`** (`w.PrURL == nil || *w.PrURL == ""` → skip; there is no `FabChange` gate), it looks `*w.PrURL` up in the URL-keyed `Snapshot()` and copies `State/Checks/ReviewDecision/IsDraft` onto the window, plus `PrFetchedAt = &fetchedAt` where `fetchedAt := st.FetchedAt` — a per-hit copy of the snapshot value scoped to the loop body, so taking its address yields a stable pointer independent of the range variable. `PrFetchedAt` (`prstatus.PRStatus.FetchedAt`, stamped `now` on each collector rebuild, or carried through verbatim from the startup seed so the line reports honest staleness across a restart rather than claiming just-fetched data) is thus collector-join-owned exactly like the `PrChecks`/`PrReview`/`PrIsDraft` siblings — set on a URL hit, nil on a miss (a URL-miss/empty/nil-`PrURL` window carries no stale freshness timestamp) — and is surfaced as the row flyout card's ambient "checked Xs ago" line (ui/status-signals.md § Row-hover register flyout card). The join key is the **canonical PR URL, never a bare number** — numbers are unique only per repo, so a number join can pick up an unrelated repo's PR state. No-op when `h.prStatus == nil`. `PrURL`/`PrNumber` are NOT touched here — they come from the branch→PR enrichment in `internal/sessions` (260705-dmex) (`enrichWindowPR` → register + snapshot-join against the `prstatus` branch refresher), upstream of the hub.

### Branch→PR Derivation

`PrURL`/`PrNumber` are **derived server-side from the pane's git branch**, never joined from `fab pane map` (Constitution §X — PR links are derivable, not pushed). This surfaces PR status for **any** pane on a branch with an open PR, in any repo under any workflow — not only fab-change-bound windows. (260705-dmex-generic-agent-state-tier)

**Two layers, both network-isolated from the SSE hot path:**

1. **Background `BranchRefresher`** (`internal/prstatus/prstatus_branch.go`): resolves each registered `(repoDir, branch)` → PR on a 30s tick (`branchPRRefreshInterval`, mirroring `Collector.Start`'s immediate-warm-then-tick lifecycle) **plus a coalescing registration/seed wake** (§ Cold Start below). Per pair it tries three resolvers IN ORDER:

   1. **Default-branch exclusion** (§ Default-Branch Exclusion below) — a pair whose branch equals the repo's default branch resolves to an authoritative negative with no gh call, and it outranks an index hit. It is deliberately NOT gated on gh availability (a local `git symbolic-ref` is all it needs), so a stale positive still clears while gh is down.
   2. **Viewer head-index join** — the pair's `repoDir` is resolved to its host-qualified `host/owner/name` origin identity (TTL-cached `git remote get-url origin`) and looked up in the index the viewer-wide collector's ONE batched GraphQL call seeded (`StoreViewerIndex`). A hit resolves the pair with **zero subprocesses**. A **miss is never an authoritative negative** — the batch covers only viewer-authored PRs inside its top-100 recently-updated window, so it cannot tell "no PR" from "not covered" — and falls through.
   3. **Per-pair `gh pr list --head <branch> --state all --json number,url,state,updatedAt,isDraft`** (run in the repo via `cmd.Dir`, `exec.CommandContext` + `ghTimeout` + explicit argv — §I) — the fallback for index misses only, and (with the exclusion) the only path that may write a negative. It is also the only resolver that yields `IsDraft`, which is what lets a draft opened by someone OTHER than the viewer reach `WindowInfo.PrIsDraft` (n927) — the index covers viewer-authored PRs only, and those get their authoritative draft flag from the collector's URL join regardless.

   Both derivation paths rank candidates through the SAME `pickBranchCandidate` helper — **precedence open > merged > closed** (`branchStateRank`, case-insensitive), most-recently-updated within a class, URL-less nodes skipped, empty/all-skipped ⇒ `nil` (a valid negative). The gh path keeps the last-good entry on a transient exec/network error OR malformed JSON (true stale-while-revalidate — never fail-to-negative) and records a **successfully parsed empty/no-PR result as a valid negative** (`nil pr`; no grace/negative-stamp retention). Unobserved pairs ride a two-window age-out: past `branchPRObservedTTL = 5m` a pair stops being resolved (no gh/git cost) but its entry is RETAINED and served by `Snapshot` — the presence hold that keeps a reopened dashboard's glyphs from blanking — and past `branchPRRetainTTL = 30m` the entry is deleted (bounded map, Constitution §II); retention holds entries only, never overriding an authoritative negative. The per-repo default-branch and origin-identity caches are pruned against the resolution-eligible (observed ≤ 5m) set. The gh-availability probe is resolved **lazily and memoized per pass**, so a pass resolved entirely by exclusions and index hits issues no gh subprocess at all. A whole pass is **single-flighted** by `refreshMu` (distinct from the map-guarding `mu`, mirroring the collector), so the tick/wake pass and an on-demand `RefreshNow` serialize instead of interleaving — a pass blocked in a slow `gh pr list` cannot come back with a stale parsed-empty result and clear an entry a concurrent pass just resolved positively. Started in `router.go` via `prstatus.DefaultBranchRefresher.Start(ctx)` next to the viewer-wide collector, whose seed sink is wired first (`pc.SetViewerPRSink(prstatus.DefaultBranchRefresher.StoreViewerIndex)`) and whose disk seed is applied before either `Start` (§ Startup Disk Seed below).

2. **Hot-path register + snapshot-join** (`internal/sessions.enrichWindowPR`): the FetchSessions loop does ZERO network work — it `prstatus.Register(repoDir, branch)`s the observed pair (a cheap lock-guarded set touch) and `prstatus.SnapshotBranchPR(repoDir, branch)`s the last-good derived PR from the in-memory snapshot, assigning `WindowInfo.PrURL`/`PrNumber`. The window's `(repoDir, branch)` is `windowPRKey`'s: `windowBranchRepo` picks the pane (active pane with a branch, else the first pane with one) and supplies the branch, and that pane's cwd is mapped to its GIT ROOT via `config.FindGitRoot` (pure stat-walk, hot-path safe; raw-cwd fallback outside a repo) — so `cd`-churn inside a worktree and same-worktree active-pane flips keep hitting one stable entry instead of minting blank first-sight pairs. Upstream, the per-cwd branch cache (`resolveGitBranches`) bridges a DETACHED HEAD (rebase/bisect — `.git/HEAD` readable but not `ref:`-prefixed, or `rev-parse` printing `HEAD`) by serving the cwd's last-known branch for `gitBranchDetachedGraceTTL = 5m` from its last genuine positive (`gitBranchCacheEntry.lastGood`/`lastGoodAt`, never re-stamped by a grace serve), cached on the 15s negative cadence so the live ref is re-read promptly once HEAD re-attaches; grace expiry and non-repo cwds keep plain negative behavior. Together the two keep the PR fields — and every surface gated on them — from flickering through rebases and pane movement.

**Cold Start — registration wake + seeded index** (260807-2ept-pr-status-cold-start): on an unseeded start `Start`'s immediate first refresh is a no-op — no pair is registered until the SSE enrichment loop has observed panes — so the tick alone would leave every sidebar/window PR glyph and status dot blank after each `rk serve` start or restart until a full 30s pass had run its one sequential `gh pr list` per pair, minutes across dozens of windows. Two mechanisms make the first useful pass land seconds after start instead, with both steady-state cadences intact:

- **Registration wake** — `Register` signals a cap-1 `wake` channel on **first-sight** pairs only (a re-observation never signals; the SSE pass re-registers everything every 2.5s), and `Start`'s loop drains further wakes for a fixed `branchPRWakeDebounce = 1s` settle window before running exactly ONE `refresh`. One SSE pass's burst of dozens of registrations therefore costs one pass, seconds after start.
- **Seeded head-index** — the collector's immediate batched fetch stores the `(host/owner/name, headRef) → candidates` index, so that first wake-driven pass mostly *joins* instead of spawning subprocesses. `StoreViewerIndex` signals the same wake channel after a non-empty store, so cold start does not depend on wiring order: the collector's first fetch and the first SSE registrations race (on the restart path the registrations win), and whichever lands second triggers the pass.

Steady-state cost: every non-empty collector store wakes the refresher, so there is ~1 extra branch pass per 90s collector tick — near-zero-subprocess, because that pass is index-served. Subprocess volume is one `gh pr list` per index miss, not one per pair per 30s pass.

**Startup Disk Seed — stale-while-revalidate across the process boundary** (260809-r4vk-pr-status-disk-seed): the cold-start machinery above is network-gated, so a restart while `gh` is slow, offline, or rate-limited has nothing to seed from and every glyph stays blank until the first successful fetch — which a rate-limit window puts minutes away and an offline host puts indefinitely away. Restarts are routine (`rk serve` restarts on self-update). `prstatus_disk.go` closes that window with one droppable cache file, read once before either poller starts.

- **Store** — `Store`/`NewStore(path)` over ONE JSON document at `DefaultCachePath()` (`$XDG_STATE_HOME/run-kit/prstatus.json`, else `~/.local/state/run-kit/prstatus.json` — the layout snapshots' state root minus the per-server fan-out; one viewer-wide file, no history, no tombstones). The shape is explicit private DTOs with an integer `schema` (any other value is treated as absent, so a future shape change ships without a migration), carrying `login`, `savedAt`, the collector map, the viewer-PR list, and branch entries as discrete `repoDir`/`branch` fields — never the refresher's internal NUL-joined key. Writes go through `internal/fsatomic.WriteFile` at `0600` into a `0700` directory — tighter than the snapshots' 0644/0755 because PR metadata is private-repo data, and both are umask-reduced, never widened. `Load` is total: absent, unreadable, malformed, truncated, or version-mismatched all yield an empty seed with no error (one `slog.Debug` line at most); a failed write is likewise debug-only.
- **Write coalescing** — `Save` skips the write when the candidate equals the last document this process wrote with every freshness-only stamp zeroed (`dedupKey`: the document `savedAt` plus each collector entry's `fetchedAt`, which `Collector.refresh` re-stamps on every successful pass — the same rule `snapshot.ContentEqual` applies to `TakenAt`), so the 30s/90s ticks write nothing at idle. Branch entries serialize sorted by `(repoDir, branch)` so equal state assembled from a Go map serializes equally. The written document keeps its real `fetchedAt` values, so a coalesced file describes the last pass that actually changed content — conservatively older, self-correcting at the next real change.
- **Seeding** — `SeedCache.Seed()` loads once and pre-fills both pollers: the collector's `byURL` AND its last-good viewer list (`Collector.Seed`, each half only while still empty), then the head-index (`SeedViewerIndex`, flagged seed-originated) before the positive branch entries (`SeedEntries`). `FetchedAt` is preserved and `observedAt` is stamped at load time, because the two timestamps mean different things: `observedAt` is liveness driving the 5-minute age-out, and a preserved pre-restart value would let the first pass evict every seeded entry before the ~2.5s SSE re-registration bumps the live ones; `FetchedAt` is freshness, surfaced as the flyout's "checked Xs ago". Negatives are not persisted — a seed fills blanks, and a negative re-derives cheaply.
- **Never authoritative** — the seed neither suppresses nor delays a fetch. A successful collector fetch rebuilds `byURL`, the viewer list, and the index wholesale, authoritative negatives included (a PR absent from the new batch is gone); a successful branch pass overwrites a seeded entry with its index/gh result, and a parsed-empty result or the default-branch exclusion clears it. A FAILED fetch leaves the seeded value serving — the package's existing stale-while-revalidate rule, extended across the process boundary.
- **Login keying** — the cache records the login of the last successful fetch (`viewer { login }`). The startup seed applies UNCONDITIONALLY, since verifying it would need exactly the network call the seed exists to survive; the comparison happens at the NEXT successful fetch (`SeedCache.collectorRefreshed`). A different login discards every still-seed-originated branch entry, once — the only state the wholesale rebuilds do not touch — and rewrites the file under the new login. An empty login on either side is "unknown", never a mismatch.
- **Effect on the wake** — a seeded process's immediate first pass has the seeded pairs to re-resolve rather than nothing, and those pairs never fire the first-sight wake: they are in `entries` before their first `Register`. The wake still covers every pair the seed did not carry.
- **Wiring** — `AttachSeedCache(pc, prstatus.DefaultBranchRefresher)` in `NewRouterAndServer`, after `SetViewerPRSink` and before `pc.Start(ctx)` / `DefaultBranchRefresher.Start(ctx)`; a path-resolution failure degrades to a debug line and an unseeded start. Every `NewTestRouter*` stays unwired so unit tests never touch the real state directory (store tests run against `t.TempDir()`), and the store type lives in `internal/prstatus`, so package `api` gains no import edge.
- **Two daemons, one file** — the cache is viewer-wide, not per-server, so concurrent `rk serve` processes on one host share it and the last writer wins. Correctness-neutral (nothing on disk is authoritative and every value is re-derived). The e2e harness is not among the writers: `scripts/test-e2e.sh` exports a per-run temp `XDG_STATE_HOME` into the dev-server launch, so an e2e backend's cache writes land in a throwaway dir the EXIT trap removes.

**Known index-miss classes** — these permanently fall back to the per-pair gh path (fail-open, correct but unoptimized): PRs not authored by the viewer, PRs aged out of the top-100 recently-updated window, fork heads (head repository ≠ the pane repo's origin), host aliases whose origin authority differs from the PR URL's host (`ssh.github.com:443`), userless scp-like remotes (`host:owner/name` with no `user@`), and origins whose path is not exactly `owner/name` — GitLab subgroups, Bitbucket `/scm/` prefixes, proxy prefixes such as `github.com/proxy/acme/tool` — all of which yield no joinable identity at all.

**D2 merged durability — state-all + precedence, stateless/restart-proof** (260706-4h26-durable-merged-pr-register-keys; the D2 of status-pyramid.md § Open Decisions): durability comes **from `gh` directly, statelessly**. The branch query is `--state all` (§ prstatus package row + layer 1 above), so a merged PR keeps resolving to a positive result on **every** refresh pass — `pickBranchPR` ranks it by precedence (open > merged > closed) and serves it as the last-good entry. There is **no grace clock** to expire or to wipe on restart, and no `wentNegativeAt` retention: a cold `BranchRefresher` (fresh process, no prior positive) serves the merged PR on its first pass, so the done-square is durable **statelessly and restart-proof end-to-end**. `refresh` clears the entry directly on a successfully parsed empty/no-PR result (a true negative) and keeps last-good only on a transient exec error or malformed JSON (stale-while-revalidate). The viewer-wide collector (which queries OPEN/MERGED/CLOSED) supplies the merged `prState` via the URL join, so the dot shows the done-square; a **closed-unmerged** PR (still derived for the register/tip) has its fall-back to the live fab tier handled **frontend-side** (`statusDotState`'s `prOwnsDot` drops PR ownership for `prState === "closed"` — see [ui/status-signals](/run-kit/ui/status-signals.md) § Status Dot D2). The **branch-reuse edge**: an open PR always outranks an older merged PR on the same branch (state precedence beats recency across classes), so a reopened branch's live PR wins.

**Default-Branch Exclusion — no branch-PR derived for a default-branch pane** (260718-0vuz-skip-branch-pr-default-branch): a pane parked on its repo's **default branch** never gets a branch-PR derived — `Snapshot`/`SnapshotBranchPR` returns `(nil, false)`, so `enrichWindowPR` leaves `PrURL`/`PrNumber`/`PrState` unset and the pane panel renders no `pr` row (the StatusDot falls through to the lower fab/agent/tmux tiers). The branch→PR feature links *feature* branches to *their* PRs; a default branch never "has its own PR" in that sense — every `gh pr list --head <default>` match for it is degenerate (a fork PR whose head ref is named `main`/`master`, or an old same-repo PR whose head happened to be the default branch). Because the derivation is stateless and durable (`--state all`, open > merged > closed precedence, no grace clock — D2 above), such a degenerate match would otherwise re-resolve positive every 30s pass forever, restart-proof. Excluding the default branch removes the whole degenerate class in one move — no per-PR heuristics (§ Design Decisions → Default-branch exclusion over per-PR cross-repo filtering).

- **Refresher-only, hot path unchanged**: the exclusion lives in `BranchRefresher.refresh()`, applied per pending pair **first** — ahead of the viewer-index join and the gh call alike. `Register`/`Snapshot` stay dumb zero-subprocess set-touches (default-branch pairs still register); recognition happens on the background tick, honoring the documented zero-subprocess SSE hot-path invariant (Constitution §II/§X). An excluded pair makes **no `gh pr list` call** (saves a subprocess/network round-trip per pass).
- **Authoritative negative, not skip** — clears a stale positive: an excluded pair sets its entry's `pr = nil` directly (exactly like a genuinely-empty parsed result), overwriting any cached PR. This is what makes a live stale line disappear within one refresh tick — e.g. a fork-PR match cached for `main` before `origin/HEAD` resolved is cleared on the next pass, never stale-kept by the stale-while-revalidate rule. Treating the exclusion as a transient skip would keep serving the wrong PR indefinitely, defeating the exclusion.
- **Branch-scoped, not repo-scoped**: only the pair whose branch matches the default is excluded; a feature-branch pair in the same repo resolves normally via `gh pr list`.
- **Local, network-free default-branch detection** (`branchDefaultExec` seam + `parseDefaultBranch`): `git symbolic-ref refs/remotes/origin/HEAD` run in `repoDir` (`exec.CommandContext` + `ghTimeout` + explicit argv, `cmd.Dir = repoDir` — no user input in argv, §I; a local ref read, never the network). `parseDefaultBranch` strips the `refs/remotes/origin/` prefix + surrounding whitespace (`refs/remotes/origin/main` → `main`); missing-prefix or empty output is a parse failure. `branchDefaultExec` is a package-var seam mirroring `branchPRExec`, defaulted onto the per-instance `defaultExec` field in `NewBranchRefresher` so tests stub it — the third injectable seam alongside `exec`/`available`.
- **Per-repo, TTL-cached, fail-open** (`defaultBranch(ctx, now, repoDir)` + `defaultBranchEntry` + `branchDefaultBranchTTL = 5m`): the lookup runs on the refresher goroutine only and is cached per `repoDir` (the `defaultBranches` map, `mu`-guarded), so each repo costs at most one `git symbolic-ref` per TTL window regardless of pair count — never one per pair per pass (mirrors the `availValid`/`availAt` gh-availability cache). BOTH outcomes are cached with a taken-at timestamp: a resolved name (`ok=true`) and a **fail-open failure** (`ok=false` — `origin/HEAD` unset/never-initialized, no `origin` remote, git absent/error, unparseable output). On `ok=false` the pair falls through to the normal `gh pr list` path (current behavior), so a missing local ref does not silently disable the feature repo-wide; caching the failure verdict avoids a per-pass `git symbolic-ref` retry storm. The default-branch resolution runs **outside** the `mu` critical section (like `r.exec`), so a hung `git symbolic-ref` never blocks `Register`/`Snapshot`; the entry write takes the lock. No persistent state (Constitution §II). `sessions.go` (`enrichWindowPR`) is untouched — an excluded pair simply misses the snapshot join, indistinguishable from "no PR exists".

Resolution runs off-tick and the hot path only registers + joins a snapshot, because resolving `gh` inline in the enrichment loop would break `api/sse.go`'s zero-network-call hot-path invariant and code-review.md's 5s cap (260705-dmex). The `prstatus` viewer-wide collector (URL-keyed live state/checks/review) composes with it: derive `PrURL` here → `attachPRStatus` joins live status by that URL.

`attachPRStatus` applies **no `FabChange` gate** — see § PR-Status SSE Join. The cross-repo contract for the fab-kit divestment this enables is in [`docs/specs/agent-state.md`](../../specs/agent-state.md); the run-kit-side agent-state tier is [agent-state](agent-state.md).

### Web Push on Sustained Waiting

The SSE poll seam fires exactly **ONE Web Push per sustained-`waiting` episode** — an agent blocked on a HUMAN (the most notification-worthy state) that stays `waiting` for ≥ `waitingPushSustain` (15s). `idle`/`active` never push. It rides the per-server poll tick where the rolled-up window `AgentState` already exists — **no new goroutine, no new poller** (Constitution II applies to *durable* state; the episode map is in-memory only, mirroring the metrics/prstatus collectors). Logic lives in `api/waiting_push.go`; the seam wiring is in `api/sse.go`'s `poll()`. (260706-y1ar-status-pyramid-ui-surfacing)

**Episode model + tracker** (`waitingPushTracker`, own mutex — independent of the hub lock): a waiting EPISODE is a maximal run of consecutive `waiting` ticks for one window, keyed `waitingKey(server, windowID)` (`server\x00windowID` — window ids are unique only within a server). `waitingEpisode{since, pushed}` stamps when the current run began and whether it has pushed. The **pure `decide(wins []pushWindow) []waitingPush`** advances the tracker for one server's windows at `now` and returns the pushes to send: waiting + no run → start the run; waiting + run < sustain → wait; waiting + run ≥ sustain + `!pushed` → PUSH once + mark pushed; not-waiting → **delete the key** (re-arm — the next `waiting` run is a fresh episode that can push again). It is pure w.r.t. its inputs + the tracker map (the only side effect is mutating that map, which IS the episode memory). `decide` is the extracted testable helper (drives enter/sustain/push/continue/leave/re-enter — A-022/A-023).

**Sync decision, detached send** (the load-bearing invariant): `notifyWaiting(server, sess)` runs `decide` **synchronously** (in-memory map mutation, no I/O — the caller observes the tracker advance in-tick) but fans the actual `push.Notify` sends out in a **detached `context.Background()` goroutine** — a slow/hung Web Push endpoint can NEVER stall the SSE poll loop's documented zero-network hot path. Push errors are logged (`slog.Warn`), never surfaced (matches the `/api/notify` posture). Body: window name + `"waiting for input"`. The `notify` send fn is a seam (defaults to `push.Notify`, stubbed in tests).

**Scoped reap** (`retain(live, polled)`): the poll loop accumulates `liveWaitingKeys` across all polled servers, then reaps episodes for windows that vanished (so a re-created window id can't inherit a stale `pushed` flag). The sweep is **SCOPED to servers actually observed this tick** — the ones successfully polled (`polledServers`) PLUS the ones confirmed gone (`deadServers`). A server whose fetch failed TRANSIENTLY (non-`IsServerGone`) is in neither set and contributes zero live keys, so scoping the sweep leaves its still-waiting episodes untouched — otherwise its `since`/`pushed` would reset every failing tick, re-arming and firing a DUPLICATE push the moment the server recovered. `retain` recovers the server from a key by splitting on the NUL separator and reaps only `polled[server] && !live[key]`.

**Wiring**: `sseHub` holds a `waitingPush *waitingPushTracker` field (`newWaitingPushTracker()` in `newSSEHub`); in `poll()`, after `attachPRStatus(result)` for each successfully-fetched server, `h.waitingPush.notifyWaiting(server, result)` runs and its returned live keys accumulate into `liveWaitingKeys`; after the server loop, `h.waitingPush.retain(liveWaitingKeys, polledServers∪deadServers)` sweeps. Uses the existing `internal/push` subsystem (§ Web Push Notifications) — no new endpoint. `@rk_agent_msg` question text in the body is a **future tenant** (out of scope; the body is the fixed `"waiting for input"`).

**Deep-link URL** (260714-r7rq-chat-read-frontend): each `waitingPush` carries a `url` — the notification's click target, built by the pure `waitingPushURL(server, windowID, hasChat)`: `/{server}/{N}` where `N` is the window id's numeric part (tmux `@N` sans `@`, matching `windowIdToUrlSegment`), with `?view=chat` appended **iff the window is chat-capable** (`hasChat`), else the plain window URL (which resolves the window's own view pref on load). `server` and the numeric segment are `url.PathEscape`-d so a reserved-character name stays a valid same-origin relative URL. `hasChat` is read off the rolled-up window's `ChatProvider != ""` in `pushWindowsForServer`. The URL threads through `decide` → `waitingPush.url` → the detached-goroutine `t.notify(ctx, title, body, url)` → `push.Notify`. Go units (`waiting_push_test.go`) cover the chat-vs-plain URL construction.

### Session-Tile Previews — `event: preview` + preview-scope

The `SessionTiles` density view (`ui/routes-and-shell.md` § Session Tiles) shows a periodic **text snapshot** of each expanded window's active pane. Snapshots ride the existing SSE hub as a **dedicated `event: preview`** — deliberately NOT extending the `sessions` payload and NOT a live xterm/relay per tile (that would re-trigger the documented HTTP/1.1 6-per-origin pool starvation — the load-bearing constraint). This decoupling keeps the `sessions` dedup/order machinery lean (growing preview text never bloats the sessions dedup cache) and lets preview cadence stay independent of structural updates. `WindowInfo` carries **no `preview` field**. (260701-70a0-session-window-tile-grid)

**Per-connection expanded-set scope**: each `sseClient` carries `connID` (from the `?conn=` stream query param) and `expanded map[string]bool` (the session names that connection currently has expanded). Both are in-memory only (Constitution II) and drop with the client on disconnect (`removeClient` deletes the whole `*sseClient` — no leaked hub state, no separate cleanup path). `setPreviewScope(server, connID, expanded)` finds the client whose `connID` matches (under the hub lock) and replaces its `expanded` set; a `connID` miss is a silent no-op. It also immediately emits the cached preview subset for the just-changed set via `sendCachedPreviewLocked` (a no-op when the set is empty or nothing is cached).

**Capture in `poll()` (rides the existing tick — no new goroutine/loop)**: after the `sessions` broadcast for a server, the poll computes `expandedUnionLocked(clients)` — the union of every client's expanded session names on that server. When the union is empty (capture-nothing default — previews are opt-in per expansion), nothing is captured. Otherwise `capturePreviews(result, union, server, h.captureFn)` captures each window in a union session **once per tick, deduped by window ID** (`h.captureFn` defaults to `capturePreviewForWindow`; tests inject a stub so the broadcast path runs without a live tmux server). The full `{windowId → text}` union map is cached in `previousPreviewJSON[server]` (seeds cached-on-connect), then each client is sent a **per-connection-filtered subset** (`previewSubsetFor`, keyed off its own `expanded` set via `windowsBySession(result)`) over `event: preview`. The tmux captures run OUTSIDE the hub lock (each is an exec with its own timeout); only the cache write + per-client emit take the lock.

**Capture primitive (reused, no new tmux helper)**: `capturePreviewForWindow(w, server)` in `api/preview.go` picks the window's active pane via `activePaneID(w)` — the `PaneInfo` in `WindowInfo.Panes` whose `IsActive` is true, falling back to the first pane, `("", false)` when the window has no panes — then calls the existing `tmux.CapturePane(paneID, previewCaptureLines, server)` (Constitution I — `exec.CommandContext` + timeout, arg slices). `previewCaptureLines = 18` (named constant, within the ~15–20 range). Best-effort: a no-pane window or a capture error yields no entry (skipped, never a hard failure). The active pane ID rides `WindowInfo.Panes` from `ListWindows`'s `list-panes` enrichment, so no tmux resolution helper is needed.

**Cached-on-connect**: `addClient` calls `sendCachedPreviewLocked` after the metrics cached-on-connect send, mirroring the `sessions`/`session-order`/`metrics` pattern — filtered to the new client's current expanded set (a no-op for a fresh connection, since scope is declared by a POST that arrives after connect).

**Frontend seam** (`app/frontend/src/contexts/session-context.tsx`): the transport is the single `StateSocket` (260716-qf3j-state-socket) — one `hello` conn id per tab, not a per-server `connId`, and no `&conn=<id>` stream-URL append. The provider routes the `preview` event through the socket's `onEvent` demux (merging the `{windowId → text}` map into that server's slice so a preview for one window doesn't clobber the others), exposes `previewsByServer: Map<string, Record<string,string>>` + a `setPreviewScope(server, expanded[])` context method, and that method sends the scope **in-band** via `socketRef.current.sendPreviewScope(server, expanded)` (addressed by the socket's own conn id — decision D4; no POST-races-the-stream window). The `api/client.ts` `setPreviewScope(server, conn, expanded)` HTTP helper has no importer; the server-side `POST /api/preview-scope` endpoint remains available (D4). The `SessionTiles` view calls the context method whenever its expanded set changes.

### `rk serve` Wiring

**Managed tmux.conf refresh + reload sweep** — `rk serve` begins with `tmux.EnsureConfig()`, the three-state managed-conf refresh at the default path (missing → write the hash-stamped header + embed; managed & stale → force-write; managed & current or hand-edited → untouched; a no-op when `tmux_conf`/`RK_TMUX_CONF` makes the path user-owned — full contract in [configuration](/run-kit/configuration.md) § Managed tmux.conf). Daemon start is the only trigger — no timer, no watcher. Only when it reports a stale→force-write transition does `serve.go` run `tmux.RefreshSweep` under a 30s context: enumerate via `ListServers` (live-socket-probed — a tmux command on a dead socket resurrects a server) and `ReloadConfig` each live server, per-server failures logging and continuing, the sweep never failing startup. `history-limit`-class options apply only to panes created after the reload — existing panes keep their old values. The sweep also runs the legacy-option migration per managed server (`MigrateLegacyOptionsOnce`, seam `sweepMigrateLegacy` — one attempt per daemon lifetime; see [tmux-sessions](/run-kit/tmux-sessions.md) § Legacy Option Migration).

`cmd/rk/serve.go` instantiates the Supervisor after `tmux.EnsureConfig()` but BEFORE the `server.ListenAndServe()` goroutine, so the SSE hub never races an empty Client map for sockets that already exist on disk. Startup ordering is `EnsureConfig → Supervisor.Start → ListenAndServe` — there is no orphaned-relay sweep step, because there are no relay ephemerals and pin-sessions are persistent (260602-qn62-move-based-board-pin-sessions). The Supervisor is constructed with `api.NewHubSinkFactory()` — the per-socket tracker-bound sink factory (260530-v6hm) — and started synchronously; per-socket `Open` failures (PTY unavailable, etc.) are logged inside the Supervisor and never block startup. Once `Start` returns, `apiServer.SetWindowChangeSubscriber(api.NewSupervisorSubscriber(supervisor))` wires the change-notification bridge and `apiServer.SetActiveWindowProvider(supervisor)` wires the Tier-1 active-window read path (see § Active-Window Event Derivation) — if `Start` itself fails (rare; usually fsnotify allocation), a single `slog.Warn` falls back to safety-net-only mode without aborting the server.

**Layout snapshotter** — between constructing the Supervisor and `supervisor.Start(ctx)`, `serve.go` resolves `snapshot.DefaultDir()`, builds `snapshot.NewSnapshotter(supervisor, snapshot.NewStore(dir))`, assigns `supervisor.OnSocketRemoved = snapshotter.OnServerRemoved` (the seam must be set before `Start`), wires `apiServer.SetServerKillNotifier(snapshotter.NoteAuditedKill)`, wires `apiServer.SetSnapshotStore(snapStore)` (the nil-safe `/api/recovery` read seam over the same store the snapshotter writes — unwired degrades recovery to empty offers), and starts the snapshotter on the serve context. An unresolvable state dir is a single `slog.Warn` ("layout snapshots disabled") — the same graceful-degradation stance as the Supervisor's own start failure. The Supervisor is the snapshotter's `ServerSource`, so its scope is exactly the covered set. See [layout-snapshots](/run-kit/layout-snapshots.md).

On SIGINT/SIGTERM, the shutdown handler runs `supervisor.Stop(ctx5s)` BEFORE `server.Shutdown(ctx)`. Stop errors are logged at `slog.Warn` and never block shutdown — matches PR #197's daemon-log graceful-degradation pattern. The 5s bounded teardown matches the existing `tmux.TmuxTimeout = 10s` shape (control-mode subprocesses are expected to close cleanly within half that bound).

### API Server version/checker wiring

The version-exposure + update-checker wiring lives in `cmd/rk/serve.go` (NOT `NewRouterAndServer`) because it needs the ldflags-injected `main.version`, which is known only in `cmd/rk`. Immediately after `router, apiServer := api.NewRouterAndServer(ctx, logger)`: (260713-4zap-update-notify-one-click-upgrade)

```go
selfBrew := resolveBrewInstalled()                                 // computed ONCE, shared by SetVersion + New
apiServer.SetVersion(version, newBootID(), selfBrew, started, cfg.Port) // seed SSE event: version (version+boot+brew+started+port) + hold version on Server
updateChecker := updatecheck.New(version, selfBrew)                // construct with the running version + its brew-install status
updateChecker.OnQualify = apiServer.WireUpdateAvailableBroadcast() // bind BEFORE Start
updateChecker.Start(ctx)                                           // background poll, bound to serve ctx
apiServer.SetUpdateChecker(updateChecker)                          // inject so /api/update reads its snapshot
```

`newBootID()` / `resolveBrewInstalled()` are `cmd/rk/serve.go` helpers (260714-3law-force-update-restart-palette): `newBootID` returns `hex.EncodeToString` of `bootIDBytes = 8` random bytes (⇒ 16 hex chars) from `crypto/rand`, or `""` on a rand failure (degrades to version-only reload); `resolveBrewInstalled` resolves the self path once and tests the Cellar marker (`selfpath.Resolve` → `selfpath.IsBrewInstalled`), reporting `false` on a resolve error. `selfBrew` is computed ONCE per `rk serve` start and passed to BOTH `SetVersion` (the `event: version` `brew` field) and `updatecheck.New` (the run-kit-row self-match brew gate — a go-install/dev rk never self-matches).

The three `*api.Server` seams (all in `api/tmuxctl_bridge.go`, co-located with `SetWindowChangeSubscriber`/`SetActiveWindowProvider`):

- **`SetVersion(version, boot string, brew bool, started int64, port int)`** (260714-3law-force-update-restart-palette) (260824-j2k6-daemon-system-presentation) — stores `s.version = version` (a held copy) AND calls `s.initSSEHub()` + `s.sseHub.setVersion(version, boot, brew, started, port)` to seed the cached `event: version` slot with all five additive fields. The `started` value is captured in `serve.go` BEFORE `NewRouterAndServer` (`started := time.Now().Unix()`) so the whole boot sequence counts toward the client's uptime readout. Safe to call before any SSE client connects. **`s.version` has a live reader**: `handleRestart`'s dev guard reads `s.version == devVersion` to `409` a restart on a dev build (see `/api/restart` in the API Layer table) — so the struct field is read.
- **`SetUpdateChecker(c *updatecheck.Checker)`** — stores `s.updateChecker = c` so `handleUpdate` reads its `Snapshot().Matched` (the scoped-update argv + the non-force empty-set 409 gate) and calls `RecheckAfter` post-remediation. A nil checker makes `/api/update` report `409 no update available` on the non-force paths (the test/unwired-router degradation).
- **`WireUpdateAvailableBroadcast() func(updatecheck.Result)`** — `initSSEHub()`s then returns a closure `func(verdict) { s.sseHub.broadcastUpdateAvailable(verdict) }`, assigned to `checker.OnQualify`. The end-to-end chain: `updatecheck.checkOnce` → `OnQualify(verdict)` → this closure → `broadcastUpdateAvailable` → `buildUpdateAvailablePayload` (the shared builder, `{tools[…updateAvailable,notable], key, current, latest}`) → caches `cachedUpdateAvailableJSON`, fans `event: update-available` to all clients (a cleared verdict broadcasts + replaces the slot too). The SAME closure fires whether the pass is the ambient tick or a manual `POST /api/updates/check` → `CheckNow`, so both paths converge on the one cached slot.

The whole block sits before the tmuxctl Supervisor start and the HTTP listen. The checker suppresses itself for the `"dev"` sentinel / unparseable versions (so a local `go build` never fetches or notifies), and its goroutine exits on `ctx.Done()`.

#### Managed job-window spawn seam (`runJobFn` → `daemon.RunJob`)

Both self-restarting handlers run their job in a managed tmux window through **ONE shared api-package seam** in `api/update.go` (260812-z1ya-update-daemon-tmux-window):

```go
var runJobFn = daemon.RunJob  // RunJob(ctx, window, argv) (JobTarget, started bool, error)
```

- `handleUpdate` runs its argv in window `update`; `handleRestart` runs `[selfPath, "daemon", "restart"]` in window `restart` — two call sites, one primitive, no per-verb duplication. Log continuity lives in the primitive: its `pipe-pane` tee appends to `~/.rk/<window>.log` (the `~/.rk/update.log` / `~/.rk/restart.log` paths).
- **The window outlives the server by placement, not detachment** — job windows live in the `rk-jobs` sibling session on the `rk-daemon` socket (§ Daemon Lifecycle), which `daemon.Stop()`'s exact-match `=rk-daemon` kill never touches, so the job survives the daemon restart the job itself triggers (Constitution VI). No `Setsid` dance: every tmux call stays `exec.CommandContext`-bound under the daemon package's per-command `cmdTimeout`, so §I holds throughout with no detached-child carve-out.
- **Spawn-before-respond** — the shared `runJobAndRespond(w, r, status, window, argv)` helper runs `runJobFn` BEFORE writing the response, so a spawn failure is a reportable `502 {"error":…}` (a "could not start the `<window>` job" prefix + the wrapped error) instead of a committed-202-with-logged-failure. Outcomes: fresh spawn → `202 {"status":"updating"|"restarting","watch":{server,session,window,window_id}}`; a live in-flight window (`started=false`) → `200 {"status":"already-running","watch":{…}}` — window existence is the derived in-flight answer (Constitution II) and the second click becomes navigation (see the `/api/update` / `/api/restart` rows and [ui/updates-and-notifications](/run-kit/ui/updates-and-notifications.md) § Update Notification).
- **Daemon gate** — both handlers `409` when the rk-daemon tmux server is down (`daemonRunningFn` seam, default `daemon.IsRunning`; update's copy is `daemonRequiredError`): the managed window is the ONLY spawn mechanism, no detached-spawn fallback.
- **Test seams**: the package vars `runJobFn` + `daemonRunningFn` let handler tests record `(window, argv)` and drive the daemon-down 409 without a live tmux server — the same seam style `internal/daemon/codeserver.go` established. The `resolveSelfPathFn` seam (default `selfpath.Resolve`) is shared by both handlers too.

### Constitution Alignment

- **§I (Security First)** — all subprocess calls in `tmuxctl/` use `exec.CommandContext` with explicit argument slices; no shell strings. The Client's `tmux -CC` invocation has no overall timeout because the connection is long-lived (per-call timeouts are not appropriate); the context is cancelled by `Close()` and propagates through the goroutine.
- **§II (No Database)** — the package itself writes no file. The Supervisor's `map[socket]*Client` mirrors the kernel-observable filesystem view of tmux sockets; nothing persists across `rk serve` lifetimes. Two persistent artefacts sit in this neighbourhood, both artefacts about the past rather than databases about the present: `~/.cache/rk/daemon.log`, and the layout snapshots the `internal/snapshot` writer persists off the Supervisor's `Sockets()`/`Generation()`/`OnSocketRemoved` seams — read only through the sanctioned recovery readers (`/api/recovery` and the `rk mux snapshot` CLI), never to answer a live-state query ([layout-snapshots](/run-kit/layout-snapshots.md) § Snapshot read boundary).
- **§VI (Tmux Sessions Survive Server Restarts)** — `tmuxctl` observes tmux state changes and pushes them to SSE clients; it never mutates *user* sessions (it creates/reads only the `_rk-ctl` anchor and sets the server-scoped `exit-empty off` and `@rk_srv_origin` options — never touching any window, pane, or user session). The `_rk-ctl` anchor is created **on every observed server** (including the user's `default` with live sessions), as a permanent session floor — NOT only on servers with zero pre-existing sessions (260602-a1wo-prevent-exit-empty-server-death). This is itself the deliberate Constitution VI *prevention*, not a violation: the floor + the server-global `set-option -g exit-empty off` (set imperatively in `productionDial` before the anchor on every dial/reconnect, plus baked into the embedded conf) together stop tmux's default `exit-empty on` from reaping a server when its session count momentarily hits zero — the recurring failure (`runWork`/`utils`/`kit`, ≥3x) that killed live agent sessions. (The same backstop keeps an *empty home session* alive after its only window is pinned away into a `_rk-pin-*` session — pin-session persistence relies on `exit-empty off`.) The anchor is harmless on a server with real sessions: it is filtered from every user-facing list (`tmux.ControlAnchorSessionName` chokepoint in `parseSessions`), ungrouped, and the control-mode connection attaches read-only (`-r`). Managed servers die only via explicit `kill-server` / `rk mux reap`; empty anchor-only servers persist by design (no auto-reaping, no cross-process state per §II).
- **No new network surface** — the Client is a local subprocess attached via PTY. `ss -tlnp` still shows only the existing HTTP listener.


## Design Decisions

### Kill primitives own the port-release invariant
**Decision**: The bounded port-free wait lives inside `KillCodeServerSession` and `KillServer` (`internal/daemon`), not at any call site.
**Why**: The hazard is created by the kill (tmux kill only SIGHUPs; node takes seconds to unbind) and suffered by the ensure path's port probe. Owning it at the source makes every present and future kill+ensure composition safe by construction — the call-site wait era recreated the same race precisely because the invariant lived in one caller.
**Rejected**: Ensure-side wait (taxes genuinely externally-managed setups ~5s on every daemon start); per-call-site waits (the recurrence pattern this decision exists to end).
*Introduced by*: 260818-gs6y-unify-daemon-restart-sequencing

### One options-driven restart sequencer
**Decision**: `daemon.Restart(RestartOptions{Force, Full, Binary})` owns stop → kill-server → force-reclaim → start ordering and the `--full` inside-server guard; the CLI RunE and the upgrade seam are thin wrappers.
**Why**: Three sequencers each held a different subset of the invariants; the CLI re-implemented orchestration inline. A single state machine makes a forgotten invariant structurally impossible for new callers, and guard-in-primitive means no future caller can bypass it.
**Rejected**: Keeping niladic `Restart`/`RestartWithBinary` as deprecation wrappers (only module-internal callers exist — upgrade.go and tests); moving remote reconnect into the sequencer (import cycle: `internal/remote` imports `internal/daemon`).
*Introduced by*: 260818-gs6y-unify-daemon-restart-sequencing

### Port-owner helpers as an untagged internal/ports file
**Decision**: The port-owner helpers live in `internal/ports/portowner.go` without build tags, preserving the no-tag posture.
**Why**: `internal/daemon.Restart`'s force step (untagged) must reference these symbols on every platform the daemon package builds for; the release matrix is linux/darwin only and `cmd/rk` already uses `syscall.Kill` untagged, so no supported build regresses.
**Rejected**: `//go:build linux || darwin` + an `_other` stub (new surface — the move is a relocation, not a redesign; the collector's platform split exists for genuinely divergent implementations, not for this self-contained unix helper).
*Introduced by*: 260818-gs6y-unify-daemon-restart-sequencing

### The origin stamp rides `productionDial`, not the SSE hub poll
**Decision**: `@rk_srv_origin` is stamped in `tmuxctl.productionDial` beside `SetExitEmptyOff`, with the origin injected once from serve startup via `tmuxctl.SetStampOrigin`.
**Why**: the supervisor covers EVERY server the deployment touches (fsnotify socket-create → dial at birth; synchronous start enumeration → heals staleness across daemon restarts; reconnect → re-stamp), independent of whether any client is viewing — and `SetExitEmptyOff` already established the exact every-dial, idempotent, non-fatal contract at that spot. The SSE hub's safety poll was the alternative seam, but its poll set is client-derived (`h.clients`), so panes in never-viewed servers would never get stamped — the dial seam strictly dominates it on coverage and staleness.
**Rejected**: SSE hub poll stamp (client-scoped coverage, misses unviewed servers, adds hot-path work); birth-seam-only stamp (stale across daemon restarts, misses foreign/pre-existing servers).
*Introduced by*: 260814-qb8z-server-url-tmux-option

### Unconditional set on dial (no read-compare)
**Decision**: the origin stamp writes the option on every dial without reading it first.
**Why**: dials are rare events (startup, socket birth, reconnect), and `SetExitEmptyOff` already pays an identical unconditional round-trip at the same spot; a read-compare would double the tmux calls to save nothing.
**Rejected**: write-if-different (an extra `show-option` per dial for zero benefit); an in-memory once-per-server memo (extra state, and a manually cleared option would never heal until restart).
*Introduced by*: 260814-qb8z-server-url-tmux-option

### The pane-side origin resolver lives in `cmd/rk` (package main)
**Decision**: `resolveOrigin()` sits in `cmd/rk/origin.go` beside its two consumers (`rk url`, `rk notify`), reusing the local `tmuxSocketArgs` helper and the `role.go` seam-var test idiom (`originRunOutputFn`/`originOriginalTMUXFn`).
**Why**: both consumers are `cmd/rk` commands, and the `$TMUX`-socket targeting helper and the `tmux.OriginalTMUX` capture pattern already live there (`role.go`, `present.go`, `agent_hook.go`).
**Rejected**: a new `internal/origin` package (premature — extract later if a non-CLI consumer appears); extending `internal/config` (config is a leaf package that must not import `internal/tmux`).
*Introduced by*: 260814-qb8z-server-url-tmux-option

### One-click update / restart run in managed `rk-jobs` sibling-session windows, not detached children
**Decision**: `POST /api/update` and `POST /api/restart` run their job via `daemon.RunJob` — a window in the `rk-jobs` sibling session on the `rk-daemon` socket — gated on the daemon running (`409` when down, no fallback path), with spawn-before-respond (`202` fresh + `watch` target / `200 already-running` / `502` spawn error); `rk daemon run` is the same primitive's CLI wrapper.
**Why**: a tmux window converts an opaque fire-and-forget spawn into the product's own core competency — the job is watchable on the existing terminal route (`ListServers` surfaces every live server), in-flight state is derivable from window existence at request time (Constitution II), and the window survives the daemon restart it triggers because `daemon.Stop()`'s exact-match `=rk-daemon` kill never touches a sibling session (Constitution VI) — which also deletes the entire `Setsid` detachment carve-out from §I's `exec.CommandContext` discipline. `remain-on-exit on` keeps the completed run's output in the pane (the next run of the same job relaunches in place via `respawn-window -k` — no timer/reaper); `pipe-pane` tees to the durable `~/.rk/<window>.log`.
**Rejected**: a detached `Setsid` child (opaque — no exit observation, no in-flight answer, log-file-only diagnostics); a window inside the `=rk-daemon` session (the job would kill itself on the restart it triggers); a generic any-server/any-pane exec subcommand (reimplements tmux addressing where the target-hijack footguns live); a `409` for a second click while in-flight (a truthful derived answer, not an error — the UI navigates instead).
*Introduced by*: 260812-z1ya-update-daemon-tmux-window

### Job windows persist after every exit
**Decision**: `RunJob`'s post-spawn option is `remain-on-exit on` — a job window (update, restart, `rk daemon run`) survives its command's exit as a dead pane, success and failure alike, until the next run of the same job respawns it in place.
**Why**: with the earlier `failed` value a successful update's output vanished the moment it completed — the watchable-job story was asymmetric (failures left evidence, successes disappeared); the completed run's scrollback staying on screen until the next run replaces it is the feature, including the permanent `rk-jobs:<window>` dead-pane row on the dashboard between runs. The respawn/dedup machinery needs no change: `jobWindowState` probes `#{pane_dead}` and `respawn-window -k` relaunches in place.
**Rejected**: keeping `remain-on-exit failed` (success evidence lost); per-job configurability of the persistence (a flat flip covers every job window).
*Introduced by*: 260813-4n9h-persistent-job-windows

### Session-scoped daemon startup reap
**Decision**: `reapStaleDaemonSocket` kills only the exact-match daemon sessions (`=rk-daemon`, legacy `=rk`) — never `kill-server` — on the multi-tenant `rk-daemon` socket.
**Why**: the socket's sibling sessions (`rk-jobs`, `rk-code-server`, `rk-remotes`) deliberately outlive the daemon (Constitution VI); a server-wide kill at `Start()` had exactly one live-fire case — a server alive with siblings but no daemon session, i.e. the restart-via-job path — where it SIGHUPed the `rk-jobs` update window mid-`shll update` (the job that triggered the restart), left code-server absent after every auto-update (`ensureCodeServer` ran later in the dying updater process and lost the SIGHUP race), and tore down SSH tunnels on every restart.
**Rejected**: probing `list-sessions` and issuing `kill-server` only at zero sessions (more machinery for the same coverage — a zero-session tmux server exits on its own); deleting the reap entirely (kept as a race-window safety net between the `IsRunning()` probe and `startSession`).
*Introduced by*: 260813-b41g-scope-daemon-socket-reap

### Full server restart is a flag on `restart`, and its tunnel-reconnect failures degrade to warnings
**Decision**: the whole-server kill lives behind `rk daemon restart --full` (not a new verb), guarded against invocation from inside the rk-daemon server via `tmux.OriginalTMUX` (the env var is stripped by `internal/tmux.init()`, so reading the env directly would never fire); per-remote reconnect failures after the fresh start print warnings with the `rk remote connect <name>` recovery pointer and the command still exits 0.
**Why**: Constitution IV minimal surface — the destructive variant sits behind an explicit opt-in on the verb users already reach for; the restart's contract (a fresh daemon server) succeeded even when a remote box is unreachable, and that condition has its own idempotent recovery, so a non-zero exit would misreport the restart. The guard structurally prevents the rk-jobs self-kill class (§ Session-scoped daemon startup reap) without needing the update chain to know about the flag.
**Rejected**: a new `nuke`/`full-restart` verb (surface growth + help-dump churn); non-zero exit on any reconnect failure (conflates two independent outcomes, breaks scripted use); reading `$TMUX` from the environment for the guard (always empty post-init).
*Introduced by*: 260818-lqcf-daemon-restart-full-flag

### The daemon-managed code-server is a sibling session on the rk-daemon socket
**Decision**: code-server runs as its own tmux session `rk-code-server` (one window `code-server`) on the `rk-daemon` socket — the `rk-remotes` precedent — spawned best-effort at the end of every daemon start behind the idempotency ladder session-exists ⇒ silent skip / port-listening ⇒ respect the externally managed instance / binary-absent-on-both-ladder-rungs ⇒ spawn the `code-server-install` job window in `rk-jobs` (the install-then-start shell chain) and continue.
**Why**: stop-leaves-running and serve-restart survival are impossible for a window inside the `rk-daemon` session — that session dies with the serve process and `Stop()`'s kill-session fallback would take the editor with it; and an editor must never block the dashboard, so every failure branch degrades to a log line and the missing-binary case self-heals through the job (whose progress is a visible tmux window).
**Rejected**: a window inside the `rk-daemon` session (coupled lifecycle); hard-failing daemon start over a missing binary (the lens degrades to the not-running state plus a doctor row while the install job runs); blocking daemon start on the ~100MB download (availability-first — the job window IS the progress surface).
*Introduced by*: 260811-a2bo-daemon-code-server-stable-route, 260813-oid2-own-code-server-install

### The respawn's daemon gate fires before any tmux command, in one shared helper
**Decision**: `respawnCodeServerSession` checks daemon liveness FIRST and both callers (update's version-changed respawn, install's migration) route through it; daemon down ⇒ nothing is killed and nothing is probed.
**Why**: the #582 review should-fix — the ungated kill tore the editor down when the daemon was off (siblings outliving the daemon is a designed state) and its has-session probe could birth a stray tmux server on a dead socket; the callers keep distinct recovery copy because the truthful guidance differs (install: re-run converges; update: post-flip the survivor is undetectable by string match, so the exact-match manual chain is named).
**Rejected**: one shared skip message (wrong for one caller or the other); gating inside `KillCodeServerSession` alone (the start half and the notes belong to the same transaction — one helper keeps exactly one kill+start sequence in the CLI).
*Introduced by*: 260813-2s4u-respawn-aware-code-server-install

### The kill primitives own the port-release wait, gated on the kill's own evidence
**Decision**: the port-free wait (5s budget, 200ms cadence, non-fatal expiry) lives inside `KillCodeServerSession` (gated on `killed == true`) and `KillServer` (gated on the `rk-code-server` sibling existing pre-kill) — `respawnCodeServerSession` and the `--full` restart both rely on the synchronous kill, with no wait at any call site; the ensure path stays byte-identical for all callers.
**Why**: `kill-session` only SIGHUPs the pane and the node process unbinds seconds later, so the ensure path's `portInUse` probe found rk's own dying instance and took the externally-managed carve-out — reproducibly leaving no editor running after every version-changed update and every `--full` restart; the carve-out itself is correct for genuinely foreign instances and must survive, and a wait that lives at one call site is forgotten by the next composition.
**Rejected**: loosening the ensure path's externally-managed check (breaks the legitimate carve-out); keeping the wait in the respawn helper (the recurrence pattern); an unconditional `KillServer` wait (burns the full timeout on every `--full` for externally-managed users); treating budget expiry as an error (the fall-through keeps the truthful degradation — the wait closes the race window without adding a failure mode).
*Introduced by*: 260818-gs6y-unify-daemon-restart-sequencing, 260818-nzho-code-server-respawn-port-race

### tmux ≥ 3.4 floor: one constant, warn everywhere, gate only the tunnels
**Decision**: the floor is one constant (`FloorMajor`/`FloorMinor`/`FloorString` = 3.4) in `internal/tmux/version.go` with `>=` comparison; every surface (daemon-start precheck, `rk serve` startup, doctor note, remote Connect) probes through the shared `CurrentVersion` helper and renders the one `UpgradeHint` message; all but the tunnels warn-and-continue, and an unparseable version is **unknown** — no warning, no block, no error.
**Why**: a runtime check is the only mechanism that covers every install path, every point in time, and PATH shadowing (Homebrew cannot express version constraints on dependencies; the install script stays a thin bootstrap); blocking daemon start would brick working setups when only the tunnels' no-shell argv exec genuinely requires the floor (Constitution §I — see [remote-hosts](/run-kit/remote-hosts.md)); never blocking on a parse keeps vendor builds and `next-*` snapshots safe.
**Rejected**: per-consumer floor constants (drift across four call sites is guaranteed eventually); blocking daemon start below the floor (bricks working setups for a tunnels-only requirement); treating unknown as below-floor (cosmetic parse gaps become hard tunnel refusals).
*Introduced by*: 260819-vtd1-tmux-version-floor

### Job-window probe reads `list-panes`, never `display-message`
**Decision**: `RunJob`'s window-dedup probe is one `list-panes -t =rk-jobs:=<window> -F '#{window_id} #{pane_dead}'` call; an error (`can't find window`) means absent.
**Why**: `display-message` with an unresolvable window part silently falls back to the session's ACTIVE window and exits 0 (verified on tmux 3.6a), so on a session whose idle default window is the active one it read as a live in-flight job and the update command never spawned — the released 3.15.10 first-click bug. The same fallback class is why `CodeServerSessionCommand()` reads `#{pane_start_command}` through `list-panes`.
**Rejected**: `display-message -t <target>` (cannot distinguish an absent window from the active one).
*Introduced by*: 260812-anac-fix-job-window-probe-fallback

### Default-branch exclusion over per-PR cross-repo filtering
**Decision**: a pane on its repo's default branch never gets a branch-PR derived — the exclusion is applied per pair in `BranchRefresher.refresh()` ahead of every other resolver.
**Why**: every `gh pr list --head <default>` match is degenerate (a fork PR whose head ref is named `main`/`master`, or an old same-repo PR whose head happened to be the default branch), and the stateless `--state all` derivation would re-resolve it positive every pass, restart-proof; excluding the default branch removes the whole class in one move with no per-PR heuristics.
**Rejected**: `isCrossRepository` cross-repo/fork filtering (removes only the fork variant and leaves the same-repo-historical variant in place).
*Introduced by*: 260718-0vuz-skip-branch-pr-default-branch

### Doctor row instead of a hook-generation bump
**Decision**: `rk doctor` carries an `agent hooks` check classifying installed hook generations (gen-1 inline one-liners and gen-2 `agent-hook` entries FAIL; gen-3 entries validate their embedded rk path); the installed hook text is untouched.
**Why**: gen-3 hook text names no option — the pane-option write lives in the binary — so a text bump would force every user through `rk agent setup` for no behavioural change; only gen-1 inline one-liners still write the legacy unscoped option names.
**Rejected**: bump the hook text plus a doctor row (pure churn — a no-op rewrite of every installed settings.json); skip the doctor row (stale-generation stragglers stay invisible through the deprecation window).
*Introduced by*: 260828-5jlp-tmux-option-dual-read-external-keys

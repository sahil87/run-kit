> How to support Linux for run-kit's Electron app. Decisions: AppImage is the only Linux format (drop the deb target and the `*.deb` upload glob; keep x64 + arm64). The recommended install path is `curl -fsSL https://hexokit.com/install | sh -s -- run-kit` (installs the CLI via Homebrew; lives in the shll repo, out of scope) followed by `rk desktop install`, mirroring macOS — the CLI is the only updater on every platform. Shell: `app.setDesktopName("run-kit-desktop.desktop")` and the Restart-to-Update item on Linux. Docs: README and docs/site/install.md desktop sections go cross-platform.

- Everything around the package is macOS-only: `cmd/rk/desktop.go`'s `PersistentPreRunE` returns `rk desktop is macOS-only (the shell is packaged as a macOS .app)` when `desktopGOOS != "darwin"`; `runUpdateDesktopLeg` in `cmd/rk/upgrade.go` returns nil (silent skip) on non-darwin; `refreshUpdateMenu()` in `app/desktop/src/main.ts` returns at `process.platform !== "darwin"`; **and** `buildMenu` in `app/desktop/src/menu.ts` passes `update` only to `macAppMenu` — `fileMenu(callbacks)` (win/linux) has no slot for the item, so the item is "mac-only by structure" (memory § Restart-to-Update Menu Item). ## Why

**The problem.** run-kit ships Linux desktop packages on every release but gives a Linux user no way to install, find, or update them through the toolkit. The `rk desktop` command group — the *primary* install path on macOS, and the shell's only updater on any platform — refuses outright on Linux. So a Linux user must know the Releases page exists, pick the right AppImage, `chmod +x` it, launch it from wherever it landed, and never hears about updates: the Restart-to-Update menu item never renders (`refreshUpdateMenu` exits on non-darwin and `fileMenu` has no slot for it), the umbrella `rk update` skips the app silently, and there is no launcher entry, no icon, no PATH entry. The dock badge — the shell's OS-level "an agent is waiting" signal — most likely never associates on Linux because the app never declares its desktop-file name.

**If we do nothing.** Linux stays shipped-but-unusable: the six AppImage downloads per release cycle are people who found the asset by themselves and are now on a stale version with no upgrade path except repeating the manual dance. The macOS story ("`rk desktop install`, then one **Start & connect** click") is exactly the story the toolkit tells, and it is false on the platform the daemon side actually runs on most.

**Why this shape.** The user decided the format question in the study: **AppImage only**. The deb (root-only install, no update path without hosting an apt repo, un-drivable from the CLI, and download-count-equal to the AppImage) and rpm (same reasoning; every native format multiplies manual, un-updatable paths) are dropped or not added. Snap is rejected because strict confinement blocks exec of the host `rk`/`ssh` — the welcome page's "This Machine" and SSH rungs die — classic confinement is rarely granted to Electron apps, snapd auto-refresh contradicts the shell's "never updates anything on its own" contract and the CLI-owned updater, and it is not universal (Mint/Debian/Fedora lack snapd). Flatpak has the same sandbox problem via `flatpak-spawn --host`. Hosting apt/dnf repos means signing keys, metadata, and hosting — revisit only if demand appears. Fedora/openSUSE/Arch are served by the AppImage + CLI path.

The CLI-driven AppImage path reuses two precedents already in the tree: the **macOS installer's contract** (resolve → download while hashing → verify → stage while the app runs → quit gracefully at the swap boundary → atomic swap → relaunch → data lines) and **`internal/codeserver`'s layout** (`~/.rk/<tool>/<version>/` + a `current` symlink flipped atomically; installed version derived from the symlink target; missing digest is a hard refusal). Extracting the AppImage once at install time (rather than running it as a FUSE mount) removes the libfuse2 runtime dependency, gives the running-state probe a real binary path, and yields a `.desktop` + icon to integrate. The shell's part is small: declare the desktop name so the badge associates, and let the existing Restart-to-Update flow render on Linux — the `rk desktop status` probe and the detached `rk desktop update` spawn are already platform-neutral.

## What Changes

### 1. Platform gate and Linux arch labels (`app/backend/cmd/rk/desktop.go`, `app/backend/internal/desktop/release.go`)

- `desktopCmd.PersistentPreRunE` accepts `desktopGOOS` ∈ {`darwin`, `linux`}; everything else returns the operational (exit 1) error `rk desktop supports macOS and Linux (the shell is packaged as a macOS .app and a Linux AppImage)`. The `desktopGOOS` seam var stays (tests pin `darwin`, `linux`, `windows`). Commands remain **registered on every platform** — `rk help-dump`'s command tree is a contract surface.
- `desktopCmd.Short` becomes `Install and update the Run Kit desktop app (macOS, Linux)`; every `Long:` block (parent, `install`, `update`, `status`) gains the Linux facts (install root, AppImage, digest-only verification, desktop integration) alongside the mac ones. The `Long` text must stay platform-neutral: help-dump's `text` is the byte-for-byte `-h` output and is pulled on a schedule from one machine.
- `Installer` gains a `GOOS` field (default `runtime.GOOS` in `New()`) that selects the per-platform strategy inside `internal/desktop` (mac: the DMG flow exactly as today; linux: the AppImage flow below). Existing mac tests pin `GOOS: "darwin"`.
- `archLabel(goos, goarch)`: darwin keeps `arm64 → arm64`, `amd64 → x64` (DMG names); linux maps `amd64 → x86_64`, `arm64 → arm64` (the real AppImage filenames, per electron-builder's per-target arch naming). Unsupported GOARCH errors before any HTTP request, as today.

### 2. Linux install root and layout (`app/backend/internal/desktop`)

Mirror `internal/codeserver` (`BinDir`/`VersionDir`/`CurrentPath`/`InstalledVersion`):

```
~/.rk/desktop/<version>/        one extracted AppImage per version (the squashfs-root contents:
                                AppRun, run-kit-desktop, run-kit-desktop.desktop, resources/app.asar, usr/…)
~/.rk/desktop/current           symlink → <version>; activation = temp symlink + os.Rename (atomic flip)
~/.rk/desktop/.staging-*        MkdirTemp staging dirs; deterministic prefix so leftovers are reclaimed
```

- `DefaultInstallDir` becomes per-platform: `/Applications` on darwin, `~/.rk/desktop` on linux (home from an `os.UserHomeDir` seam var, the `codeServerUserHomeFn` idiom; no env key — Constitution IV restricts env to deployment-bootstrap keys). The `--path` flag on `install`/`update`/`status` (and `uninstall`) overrides the root on either platform.
- Because the flag default differs per platform, the cobra default is `""` and the usage string states both (`install directory (default: /Applications on macOS, ~/.rk/desktop on Linux)`); the command resolves the default at runtime when `Flags().Changed("path")` is false, and an explicitly-empty `--path ""` remains a usage error (exit 2). Rationale: a per-platform literal default would make the published help-dump reference depend on the puller's platform.
- `AppPath()` (used in messages and the not-installed error): darwin `<InstallDir>/Run Kit.app` as today; linux `<InstallDir>/current`.
- `InstalledVersion(ctx)` on linux reads the `current` symlink's target basename; a missing symlink yields `("", nil)` (not installed); any other read error is returned. No state file (Constitution II). It is never assumed equal to the CLI version.

### 3. Release resolution (`release.go`)

Same GitHub API call (`/releases/latest` or `/releases/tags/<tag>` with `normalizeReleaseTag`), same token handling and 403/429/404 error shapes. On linux the asset match is prefix `run-kit-desktop-` + suffix `-<label>.AppImage` (`x86_64` / `arm64`); the not-found error names the AppImage (`release vX has no x86_64 AppImage asset (looked for run-kit-desktop-*-x86_64.AppImage)`). `Release.Digest` parsing is unchanged (`sha256:<hex>` → hex; anything else → `""`).

### 4. The Linux install flow (`install.go` linux strategy — the ten-step contract)

1. **Download** the AppImage to a temp file under the staging dir (`os.MkdirTemp(root, ".staging-")`), SHA256 computed while streaming, `downloadTimeout` (15 min) bound, the existing `progressPrinter` on `Progress`.
2. **Verify — the only hard gate on Linux.** Compare to `rel.Digest`. A **missing digest REFUSES** (`release vX supplied no sha256 digest for <asset> — refusing to install an unverified binary`), matching `internal/codeserver` and diverging deliberately from the mac path's note-and-continue (there codesign is the second gate; here there is none). A mismatch discards the download with the existing message shape. No flag (`--force`, `--quiet`, `--path`) reaches or skips this gate.
3. **Extract once.** Only after the digest passes, `chmod 0700` the downloaded file and run it with `--appimage-extract` (`exec.CommandContext`, argv slice, `extractTimeout` = 5 min — the build-op tier or above; the AppImage is ~127 MB) with the **working directory set to the staging dir**, because the AppImage runtime writes `./squashfs-root` into the CWD and has no target-directory flag. The `Runner` seam gains a working-directory-aware variant for this call (existing recorded-runner tests keep working). Extraction does not need FUSE, so libfuse2 is not a runtime dependency of the installed app.
4. **Validate the extracted tree** (the Linux analogue of the "bundle is named Run Kit.app" check), refusing otherwise with the install target untouched: `AppRun`, `run-kit-desktop` (regular, executable), `resources/app.asar`, `run-kit-desktop.desktop`, and the icon at `usr/share/icons/hicolor/<size>/apps/run-kit-desktop.png` must exist; the `.desktop`'s `X-AppImage-Version=` value must equal `rel.Version` (`mounted AppImage reports version %q, expected %q — refusing to install an unexpected build`); and no symlink inside the tree may resolve outside it (reuse the `within`/`EvalSymlinks` containment idiom from `internal/codeserver/install.go`; `.DirIcon -> usr/share/icons/...` is inside and passes). The downloaded AppImage file is removed after extraction (the staging dir holds only the tree).
5. **Version dir.** The version dir name is `rel.Version` (no leading `v`); the installed version is later derived from the `current` symlink, never stored elsewhere.
6. **Running-state probe.** `AppRunning(ctx)` on linux = `pgrep -f <root>/<installed-version>/run-kit-desktop` where `<installed-version>` is the `current` symlink's target **before** the flip (the running app lives in the old version dir; `AppRun` `exec`s that absolute ELF path, and Electron's zygote/renderer/GPU helpers carry it in their cmdline too — any hit means live). `probeTimeout` 10 s; pgrep exit 1 reads as not running, as on mac. Nothing installed → not running.
7. **Swap.** Everything above runs while the app may be live. At the swap boundary: probe; when running, quit and wait (step 8); then `os.Rename(<staging>/squashfs-root, <root>/<version>)` (a leftover `<root>/<version>` from a prior interrupted run is `RemoveAll`'d first — its existence proves that run never flipped), flip `current` via `current.tmp` symlink + `os.Rename`, and only after the flip succeeds remove every other version dir under the root (so the root holds exactly `current` + one version). A failed rename or flip removes the staged copy and leaves the existing install untouched; the staging dir is `RemoveAll`'d on every path (`defer`).
8. **Quit and relaunch when it was running.** Graceful quit = `SIGTERM` to the **main** process — the oldest PID matching the probe pattern (`pgrep -o -f <path>`), delivered via a Go signal seam (`syscall.Kill`, no subprocess; a struct-field seam so the recorded tests assert it). Electron's SIGTERM handler runs the `before-quit` and window `close` handlers, so the shell captures `lastPath` exactly as the AppleScript quit does on mac. Poll `AppRunning` at `QuitPoll` until `QuitWait` (existing 1 s / 30 s struct fields); on expiry abort **before** the swap with the existing manual-quit error, leaving the install and the staged copy intact. After the flip, relaunch `<root>/current/AppRun` detached — `Setsid`, stdio on `/dev/null`, `cmd.Start()` + async `Wait` (the `internal/gui.StartDetached` idiom); the start is bounded, the child is not waited on. A relaunch failure is a non-fatal `Progress` warning, exactly as on mac; `InstallResult.Restarted` is true only when quit → swap → relaunch all completed.
   **Sandbox flag — decided once, here:** the installer passes **no** `--no-sandbox` and launches via `AppRun`, not the raw ELF. `AppRun` already applies `--no-sandbox` only when unprivileged user namespaces are unavailable (Ubuntu 24's default), keeps Chromium's sandbox where they work, and supplies the bundled `usr/lib` libraries via `LD_LIBRARY_PATH` — launching the ELF directly would lose both. The desktop entry (step 9), the PATH symlink, and the relaunch all target `AppRun`, so they agree by construction. This diverges from the shipped AppImage entry's hardcoded `--no-sandbox` and from the study's initial proposal; see Assumptions.
9. **Desktop integration** (all under the user's home; every write is a plain file write, best-effort ordering after the flip):
   - `~/.local/share/applications/run-kit-desktop.desktop`:

     ```ini
     [Desktop Entry]
     Name=Run Kit
     Comment=run-kit desktop viewer shell — loads an existing rk serve URL (client only, never spawns or supervises the daemon)
     Exec="<root>/current/AppRun" %U
     Terminal=false
     Type=Application
     Icon=run-kit-desktop
     StartupWMClass=Run Kit
     Categories=Development;
     ```

     `Exec` is quoted (the root may contain spaces); the filename `run-kit-desktop.desktop` is what `app.setDesktopName` (§ 10) and the LauncherEntry badge key on.
   - Icon: copy `<root>/current/usr/share/icons/hicolor/<size>/apps/run-kit-desktop.png` to `~/.local/share/icons/hicolor/<size>/apps/run-kit-desktop.png`, mirroring the size directory found in the tree (the shipped AppImage carries only `1024x1024`; the study's `512x512` would mislabel it).
   - `update-desktop-database ~/.local/share/applications` when `exec.LookPath` finds it (30 s bound); a failure or absence is a chatter note, never an error. No `gtk-update-icon-cache` (hicolor user icons need no cache).
   - `~/.local/bin/run-kit-desktop` → `<root>/current/AppRun` (symlink replaced atomically via temp + rename; `~/.local/bin` created if missing). `~/.local/bin` being off `PATH` is the user's shell's concern — no PATH editing.
   - Integration failures after a successful flip are `Progress` warnings, not install failures (the app is installed and launchable via `current/AppRun`).
10. **Report.** Same data lines as the mac path via the shared `cmd/rk` layer: `Installed Run Kit v<ver> to <root>/<ver>` / `Updated Run Kit v<old> -> v<new> (<root>/<new>)` / `Run Kit v<ver> is already installed (<root>/current). Use --force to reinstall.` / `Already up to date (v<ver>).` and the restart announcement `Run Kit was running — restarted on the new version.` — all stdout, surviving `--quiet` (Toolkit Principle 9). Progress/decoration (download %, "Extracting…", "Quitting…", integration notes) stays on `Progress` = chatter.

### 5. `rk desktop update`, `status`, and the umbrella `rk update` desktop leg on Linux

- `runDesktopUpdate` and `runDesktopStatus` work unchanged through the platform-seamed installer (`InstalledVersion` from the symlink; `updatecheck.AnyIncrease` compare; `desktopUpdateToLatest` shared with the umbrella so data lines cannot drift). `update` with nothing installed still errors `Run Kit is not installed at <root>/current — run 'rk desktop install' first`.
- `runUpdateDesktopLeg` (`cmd/rk/upgrade.go`): the gate becomes `desktopGOOS` ∈ {darwin, linux}; the leg constructs the installer with no `InstallDir` override, so it sees only the **default root for the platform** (`/Applications` or `~/.rk/desktop`); an empty `InstalledVersion` is a silent exit-0 skip; a custom `--path` install stays invisible (Constitution II — no state store). `updateCmd.Long`'s "Desktop leg (macOS) … /Applications" paragraph and its closing "/Applications only" note are reworded to "the default install root for the platform (`/Applications` on macOS, `~/.rk/desktop` on Linux)".

### 6. New `rk desktop uninstall` (Linux)

- Registered everywhere (help-dump stability); on darwin it returns an operational error `rk desktop uninstall is Linux-only — on macOS drag "Run Kit.app" to the Trash` (whether a mac implementation should exist is the deferred question below). Flags: `--path` (same default resolution as the siblings). `Args: cobra.NoArgs` wrapped in `usageArgs`.
- Behaviour: refuse when nothing is installed (`Run Kit is not installed at <root>/current`), refuse when the app is running (`AppRunning` probe → `Run Kit is running — quit it, then re-run this command`), otherwise remove: every version dir under the root and the `current` symlink (then the root itself when empty), `~/.local/bin/run-kit-desktop` (only when it points into the root), `~/.local/share/applications/run-kit-desktop.desktop`, `~/.local/share/icons/hicolor/*/apps/run-kit-desktop.png`, then best-effort `update-desktop-database`. Data line: `Uninstalled Run Kit v<ver> from <root>`. `hosts.json` and other Electron user data under `~/.config/run-kit-desktop` are **not** touched (user data, not the install).

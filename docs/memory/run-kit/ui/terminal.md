# run-kit UI — Terminal Frontend

### Terminal Relay (frontend) — `RelayMux` singleton + `TerminalClient` stream handles

The browser opens no `/relay/{windowId}` WebSocket per pane. A **`RelayMux` singleton** (`src/lib/relay-mux.ts`, mirroring `state-socket.ts`) owns the ONE `/ws/terminals` socket per tab; each `TerminalClient` consumes a per-stream handle. This mirrors the state-socket transport — same URL-builder shape (`terminalsSocketURL()` vs `stateSocketURL()`), same backoff-reconnect + re-open-live-streams lifecycle, same singleton-per-tab ownership — but carries bulk binary terminal I/O on a SEPARATE socket (see `architecture.md` § Terminal Relay). (260716-qf3j) (260717-803u)

- **`openStream({server, windowId, cols, rows}) → { send, resize, close, onData, onOpened, onClosed, setWindowId }`** — allocates a fresh client-side u32 stream id and issues an `open` control op (once the socket is open, else re-issued in `ws.onopen`). `send` emits a binary `[u32 BE streamId][payload]` data frame (strings UTF-8-encoded); `resize`/`close` emit control ops; `onData` fires on inbound binary frames for that id; `onOpened` on the `opened` control event; `onClosed` on `closed` (carrying 4004/4001/1000). `onOpened` is the re-open signal seams 2/4 (below) need.
- **Backoff reconnect + re-open of live streams** — on a SOCKET-level drop the mux reconnects with exponential backoff (`RECONNECT_BASE_MS = 1000` → `RECONNECT_CAP_MS = 30000`) and, in `ws.onopen`, **re-issues `open` for every still-live stream** — the server re-attaches (fresh PTY) and each pane's deferred reset (below) repaints on the incoming first data frame, so a reconnect is flicker-free with NO per-pane reconnect loop. An idle tab with zero live streams lets the socket stay closed. Each live stream **REUSES its SAME stream id on the new connection** (ids are unique per-connection, so reusing them across a reconnect is valid); a closed stream's id is retired.
- **`setWindowId(windowId)` — the fresh-target seam** — a same-session windowId ride updates the stream's `opts.windowId` WITHOUT a wire op (the live PTY already tracks the new active window). This keeps the stream's re-open target CURRENT: without it, a transient socket drop would re-`open` the STALE open-time window and `SelectWindowInSession` would yank the pane back. `cols`/`rows` stay fresh the same way via `resize()`, so `s.opts` is the single current source the mux re-issues `open` from.
- **A stream-level `closed` retires the stream client-side** (does NOT re-open — unlike a socket drop): `onClosed` fires and the stream is deleted from the mux map.

**Hidden-page stream suspension** — a page the user is not looking at holds NO tmux attach client. (260903-xj0w)

- On `visibilitychange` → `hidden` the mux arms ONE mux-level grace timer (`HIDDEN_RELEASE_GRACE_MS` = 60 000); still hidden at expiry ⇒ every live stream **suspends**: its `close` op is sent (the server tears down the attach client + PTY) but the stream is KEPT in the mux map with its current `opts`, marked suspended. A `visible` transition inside the grace window just cancels the timer (quick app-switches cost nothing). `pagehide` and `freeze` suspend **immediately, no grace** (a frozen page's timers stop; a navigated-away page must not hold clients). A stream opened while hidden opens normally and starts the timer if none is running.
- **Only the `visible` transition resumes** — the mux re-issues `open` with each suspended stream's current `opts` (`resize`/`setWindowId` keep them fresh even while suspended, so a pre-suspension same-session ride resumes on the ridden-to window). Resume runs BEFORE the wake-probe logic in the shared `visibilitychange` handler, so a dead socket is judged against the resumed live set. The repaint rides the existing machinery — `onOpened` re-arms the deferred reset, first data frame repaints — with no `TerminalClient` change; resume wipes local xterm scrollback (accepted: rare under the grace period, tmux history remains reachable).
- **Suspended streams are not "live"**: the `ws.onopen` re-open loop skips them, and every stream-count gate (`scheduleReconnect`'s zero-check, `syncHeartbeat`/`heartbeatTick`, `handleWake`) keys on `liveCount()` (non-suspended only) — a fully suspended tab lets a dropped socket stay closed and stops the heartbeat.
- **`closed` handling while suspended**: the server echoes `closed` 1000 for every client `close` op (`terminals_ws.go` `closeStream` → `emitClosed`), so a suspended stream swallows EVERY inbound `closed` (retiring it would fire `onClosed` → the non-4004 probe re-open, defeating suspension); a per-stream `closeEchoPending` mark — armed only when the suspension close actually went out on an OPEN socket — extends the shield across a **fast resume** for exactly one post-resume `closed` 1000, and any `opened` clears it (an echo lost to a socket death must not swallow a later genuine PTY-EOF 1000). A 4004 after resume always retires — a window that died while hidden surfaces at resume through the existing recovery path.
- Scope: `/ws/terminals` only — `/ws/state` deliberately stays connected (background desktop-shell views keep reporting dock-badge waiting counts, [desktop-shell](/run-kit/desktop-shell.md) § Bridge). The IntersectionObserver board-pane suspension (seam 3 below) is untouched: same stream verbs at element granularity; the page-visibility layer is additive above it. Only on-screen pages hold sized attach clients, so tmux's `window-size latest` resolves to a client the user actually sees ([tmux-sessions](/run-kit/tmux-sessions.md) § Terminal Relay). Unit coverage: the "RelayMux hidden-page suspension" block in `relay-mux.test.ts`.

**`TerminalClient` — the four delicate seams.** The stream handle is surfaced through the `wsRef` seam via a **WebSocket-shaped adapter** (`{ readyState, send, close }`) so the shell consumers (`BottomBar`, the docked compose strip, touch-scroll, `fitAndSync`) drive the stream through the plain `wsRef.current.{send,readyState,close}` surface (a `{type:"resize"}` JSON `send` routes to the stream's `resize` op, everything else to a binary data frame; the `adapter as unknown as WebSocket` double-cast is the documented tradeoff — a structural `wsRef` type would remove it). The four seams:

1. **Confirmation-gated window-switch receipt = the stream's first DATA frame** — `notifyFirstWrite()` fires at the top of the stream's `onData` handler (`handleInbound`), before the write/coalesce decision. The gate state machine is pure. See § Window-Switch Slide Transition. (260715-38kg)
2. **Connect-select alignment epoch anchors on `open`→`opened`** — the deferred reset is armed and the grid re-fit/re-synced in `stream.onOpened` (which fires on the initial open AND every transparent re-open). Because the server enqueues `opened` on the stream's own queue ahead of any data (`architecture.md` § Terminal Relay, M2), the epoch is soundly ordered in-band, closing the `onmessage`-races-the-select-POST hazard (memory `relay-connect-select-alignment`).
3. **IntersectionObserver pane suspension = stream `close`/`open`** (no socket churn) — see § Desktop Relay-Connection Suspension.
4. **Deferred per-stream reset** — the deferred reset (below) is per-stream, re-armed in `stream.onOpened`.

**Non-4004 `closed` self-heal.** RelayMux re-opens only on a SOCKET drop, not a stream-level `closed`, so the client owns per-stream recovery: a `closed` with code 4004 prints `[session not found]` and fires `onSessionNotFound` (redirect); a non-4004 close (4001 attach-failed, 1000 PTY-EOF/graceful) prints `[reconnecting…]` and **probes exactly ONE fresh re-open of the current window** (bounded by a `probedReopen` flag). A genuinely gone window then 4004s the probe → redirect; a transient one re-attaches. A second non-4004 close prints `[disconnected]` and stops (no spin on a hard-failing window). This is a per-pane self-heal without a per-pane reconnect loop.

**Tab budget.** The tab holds a fixed **2 WebSockets** (state + terminals) and zero SSE — the e2e connection guard (`connection-budget.spec.ts`) asserts exactly this. See `architecture.md` § Terminal Relay for the backend/protocol. (260716-qf3j)

### Terminal Write Batching (Adaptive Flush + Deferred Reset)

Inbound terminal data in `terminal-client.tsx` — a `RelayMux` stream's inbound binary frames — flows through an **adaptive flush**: (260327-cnav) (260717-803u)

- **Immediate path** — a chunk that is small (≤ `IMMEDIATE_WRITE_MAX_BYTES` = 64 **UTF-8 bytes**), arrives while **idle** (nothing buffered, no flush pending), and is the **first immediate write this frame** is written synchronously so a keystroke echo paints on the same tick (latency attribution showed the rAF tail dominated perceived input latency ~3:1 over the network hop; keystroke→echo went 40→10ms). The threshold is measured in UTF-8 bytes via `textByteLength` — `String.length` UTF-16 units would under-count multibyte input and weaken the flood guard; the helper only pays for a `TextEncoder` encode in the ambiguous middle band, keeping the tiny-ASCII hot path allocation-free. The one-immediate-write-per-frame guard is `wroteImmediatelyThisFrame`, set by `markImmediateWrite()` and cleared by a one-shot rAF — a program emitting one byte at a time still coalesces after its first byte of the frame.
- **Coalesced path** — everything else (large chunk, already buffering, or a second small chunk in the same frame) accumulates in buffers (string concatenation for text, `Uint8Array[]` for binary) and flushes once per `requestAnimationFrame` (`flushToTerminal`), batching floods (builds, log tailing, `cat largefile`) into one xterm render pass per frame.
- **Ordering guarantee** — terminal bytes are order-sensitive: the moment anything is buffered, every subsequent chunk buffers until the buffer drains; an immediate write only happens when the buffer is empty AND no flush is pending, so a synchronous write can never jump ahead of buffered bytes.
- **Close-time drain** — the stream's `onClosed` handler cancels pending rAFs and calls `flushToTerminal()` (try/catch for a disposed terminal) **before** the `cancelled` check, so a transient-drop reconnect never loses tail data; `cancelAnimationFrame()` also runs on effect cleanup. Under the mux, a socket-level drop is transparent — RelayMux re-opens and the pane repaints on the first data frame — so `onClosed` fires only for stream-level closes; the close-time drain runs before the non-4004 probe re-open (above).

**Deferred per-stream reset**: each (re)open arms an effect-scoped `pendingReset` flag — armed in the stream's `onOpened`; `consumePendingReset()` (check + clear + `terminal.reset()`) runs **exactly once per stream open, immediately before that open's FIRST chunk write** — in the same tick on the immediate path, at the top of the same rAF callback (same frame) on the coalesced path — so clear + repaint land in **one presented frame**, with no black-frame flicker (the old content persists until the new redraw paints). This holds on every re-open path (sidebar click, tmux status-bar click, palette, board pane churn, transient socket-drop re-open, non-4004 probe re-open). **Ordering dependency**: arming on `onOpened` is only sound because the server enqueues `opened` ahead of the first data frame (`architecture.md` § Terminal Relay, M2) — a data-before-`opened` frame would fire the reset AFTER the first repaint and wipe it. (260610-qf25) (260717-803u)

**`onOpened` also wipes the carried-over flush state.** Alongside arming `pendingReset`, the `onOpened` handler clears `binaryBuffers` and cancels/nulls any pending `flushRafId` — the adaptive-flush state belongs to the connection that just died, and it must never replay into the fresh one. **Why it is load-bearing**: on a backgrounded tab rAF never fires, so inbound bytes pile up unflushed; RelayMux then re-opens on wake and the server re-attaches. Writing that stale backlog into the new stream repaints dead-connection content, and any terminal query sitting in it would be answered by xterm.js into the CURRENT tmux client — which already got its answer, so the extra reply is typed into the active pane as junk. The relay strips tmux's DA identification queries before they ever reach the browser (`tmux-sessions.md` § Terminal Relay), so this wipe is defense-in-depth against that specific symptom while independently closing the whole replay-dead-connection-bytes class. Discarding the backlog costs nothing — the deferred reset wipes the repaint anyway. Safe w.r.t. the handoff below — an empty flush neither consumes nor executes the freshly armed `pendingReset`. The per-frame immediate-write pacing state (`wroteImmediatelyThisFrame`/`frameResetRafId`) is deliberately left untouched: it holds no bytes and self-resets on the next rAF tick. (260801-f715-relay-device-attributes-responder)

**Handoff semantics**: an **empty flush neither consumes nor executes a pending reset** — `flushToTerminal` early-returns when both buffers are empty, so a zero-data stream's close-time drain is a no-op (resetting with nothing to repaint would recreate the flicker); the next open simply re-arms in `onOpened`, idempotently. The **effect cleanup additionally neutralizes the closure's pending write state** (`pendingReset = false; binaryBuffers = []`): a late-delivered `onClosed`/`onData` — which can arrive AFTER cleanup, and whose drain runs before the `cancelled` check so same-effect transient-drop tail drains keep working — can therefore neither reset the shared terminal nor write stale old-window content after a successor effect (e.g. a `windowId` change forcing a fresh stream) has taken over. Reset-ordering unit tests live in `terminal-client.test.tsx` (no receipt-time reset; exactly once per stream open; string + binary first chunks; re-armed on re-open; zero-data close; post-consumption tail drain; connection A's buffered-but-unflushed bytes never written after connection B's `onOpened` — asserting against the mocked `RelayMux`/stream handle).

**Relay connection identity is (server, owning session), NOT windowId**: the stream-open effect's deps are `[terminalReady, server, wsRef, connectionEpoch]` — `sessionName` and `windowId` are deliberately excluded (the `eslint-disable react-hooks/exhaustive-deps` comment explains why). A same-session windowId switch (sidebar click, palette, URL writeback after a tmux-status-bar click) **rides the existing stream**: tmux has already switched the active window in place (or will, via the REST `selectWindow` already fired by `navigateToWindow` and mount-time alignment in app.tsx) and the directly-attached PTY redraws by itself — no stream close/open, no `terminal.reset()`, and **xterm scrollback is preserved** across same-session switches (native `tmux attach` behavior). A dedicated `windowId`-keyed effect calls **`streamRef.current.setWindowId(windowId)`** on every ride so the mux's re-open target stays current. Any GENUINE reconnect — session change, server change, transient socket drop — attaches to the latest window: the epoch-bumping paths re-open a fresh stream reading `windowIdRef.current`, and a socket drop's re-`open` reads the stream's `setWindowId`-kept-fresh `opts.windowId`. (260602-qn62) (260610-9umy) (260717-803u)

Identity is tracked by `connectedSessionRef` (session the live connection serves; `""` = resolved server-side only) + `connectedServerRef` + a `connectionEpoch` state bumped by a **session-identity watcher** effect on `[sessionName, server]`. The watcher is declared BEFORE the connect effect — ordering is load-bearing: on a same-commit server+session change it must read the PRE-change server from `connectedServerRef` (the connect effect overwrites it) to skip its bump, since the connect effect already re-runs via its own `server` dep — bumping too would tear down and reconnect twice. Watcher direction semantics:

- **`""` → resolved: absorption only** (record, never bump). On a cold deep-link the SSE-derived `sessionName` prop is `""` until the first snapshot; the client connects immediately by windowId and the relay resolves the owning session server-side (`ResolveWindowSession`) — by construction the live connection is already attached to that window's owning session, so the resolution transition costs no reconnect.
- **resolved → resolved: bump** — cross-session navigation, or a window moved to another session. A session RENAME also lands here and reconnects — accepted tradeoff: the SSE snapshot carries no stable session id to tell a rename from a genuine session change, renames are rare, and the deferred reset keeps any reconnect flicker-free.
- **resolved → `""`: LOSS-OF-IDENTITY signal** — record `""` AND bump for a probe reconnect. `sessionName` is derived by locating the URL's `@N` in the SSE snapshot, so it goes `""` and STAYS `""` when the viewed window left the snapshot: killed externally, pinned to a filtered `_rk-pin-*` session (pin transitions present as resolved → `""`, never resolved → resolved), or a dead deep link. The probe (by `windowIdRef.current`) either re-resolves the owning session server-side (an X → `""` → X ghost gap during navigation costs one flicker-free reconnect) or the relay closes 4004 → the `onSessionNotFound` redirect fires. This is the ONLY reachable recovery path in that state — `computeKillRedirect` and the URL writeback are both gated on a non-empty `sessionName` — so the bump is load-bearing.
- **`""` → `""`: no-op** (cold mount, still unresolved).

Deferred-reset and adaptive-flush semantics apply on every stream open that IS established (cross-session switch, server change, transient drop re-open, non-4004 probe re-open). Connection-lifecycle unit tests live in the "TerminalClient connection identity" block of `terminal-client.test.tsx` (same-session switch keeps the stream + pushes `setWindowId`; cross-session switch closes old + opens exactly one new with the deferred reset before its first write; `""` → resolved no-reconnect with later genuine change reconnecting; server change reconnects exactly once — no watcher double-bump; resolved → `""` probe; 4004 recovery after an external kill; the non-4004 feedback + one-probe path). The **transient-drop-latest-windowId** assertion is split across the seam: `terminal-client.test.tsx` pins the same-session ride pushing `setWindowId("@5")` into the live stream, and `relay-mux.test.ts` pins the socket-drop reconnect re-issuing `open` with the ridden-to windowId (`relay-mux.test.ts` also unit-tests framing, id-demuxed data in/out, and `opened`/`closed` dispatch against a stubbed WebSocket).

### Window-Switch Slide Transition

A same-server window switch animates as a **vertical slide** of the terminal surface via the browser's [View Transitions API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transitions_API), keyed off the two windows' positions in the flattened sidebar order (macOS-Spaces-like, but vertical because the sidebar arranges windows vertically). It is **fire-and-forget** (a play-on-switch animation), NOT a gesture-scrubbed interactive drag. It is pure UX polish and layers ON TOP of the deferred-reset / relay-identity machinery above — a same-session switch still rides the existing socket with no reconnect; the slide just animates the in-place repaint. Progressive enhancement: any gate failure falls through to the instant switch. (260703-l4nf)

> **The slide is an EARNED signal.** The mechanics below (the one seam, the gate, direction, CSS, the first-paint gate) are the foundation; the slide plays ONLY on confirmed-fast arrival, with a pending spinner mask + a failure bounce-back layered on (§ Confirmation-gated motion below). `waitForFirstWrite()` resolves a `GateSettleReason` (three values — see the settle-reason contract under § Confirmation-gated motion), and the wrapper `skipTransition()`s on every non-`"first-write"` settle. (260715-38kg)

**The one seam — `navigateToWindow`.** The wrapper lives on `navigateToWindow` (`app.tsx`) alone — the single same-server switch seam shared by sidebar clicks, command-palette `Window: Switch to …` entries (keyboard path, constitution V), TopBar breadcrumb navigation, and SessionTiles clicks — so the animation applies identically to keyboard- and mouse-driven switches. The instant-switch body is factored into a `runSwitch()` closure (optimistic `navigate` + `selectWindow` POST + mobile sidebar close); the wrapper either calls it directly (fallback) or runs it inside `document.startViewTransition`'s async callback (see the timing caveat in § URL as Resumable Bookmark — on the animated path `runSwitch` runs ≥1 frame after the click). `runSwitch` **returns the `selectWindow` POST** so the gate can wait until tmux has been told to switch. **Direct `startViewTransition`, NOT TanStack Router's `viewTransition: true` option** — the polished first-paint gate (below) needs the async-callback seam to await a custom signal, which the router option does not expose.

**Gate (`shouldAnimateWindowSwitch`).** The switch animates only when ALL hold: View Transitions supported (`viewTransitionSupported()` — a plain-`boolean` `typeof document.startViewTransition === "function"` check, NOT a type predicate; the TS 5.7+ `dom` lib already declares the API, so no ambient augmentation and no `as` cast — code-quality type-narrowing), `prefers-reduced-motion: reduce` NOT set (checked via a **guarded** `matchMedia` — `typeof window.matchMedia === "function"`, for jsdom/older-WebView envs), an outgoing terminal window is in view (`windowParam`/`currentWindowId` non-empty — a first switch from SessionTiles with no outgoing surface skips), and the slide direction is non-null. Any failure → `runSwitch()` directly (instant switch). Cross-server navigation takes the separate `navigate` branch in `handleSidebarSelectWindow`, never `navigateToWindow`, so it falls out with no transition; board routes and the Host page have none either.

**Direction — flattened SSE sidebar order → root data attribute.** `windowSwitchDirection(order, currentId, targetId)` (pure, exported, in `src/lib/window-transition.ts`, colocated `.test.ts` — the same pure-helper pattern as `resolveServerView`/`computeKillRedirect`) returns `"up"` when the target sits BELOW current (new content enters from the bottom), `"down"` when ABOVE, and `null` when either id is missing from the order or the ids are equal (→ skip). `order` is `flatWindows.map((fw) => fw.window.windowId)` read from a render-synced `switchTransitionRef` (so the click handler reads current order without re-creating the callback). The resolved direction is written to `document.documentElement.dataset.windowSwitchDirection = "up" | "down"` immediately before `startViewTransition` (the `data-theme` root-attribute pattern); the CSS pseudo-elements key off `:root[data-window-switch-direction=…]`. **Accepted divergence:** `flatWindows` is raw SSE order, while the sidebar's drag-reorder override (`orderOverrideRef`) is component-local, so during a transient drag-reorder window the slide direction may briefly disagree with the visual sidebar order until SSE confirms — rare and self-healing.

**Direction-attribute latest-wins guard.** The attribute is cleared in `transition.finished.finally()`. But `finished` **FULFILLS on skip** (a rapid second switch displaces this transition) — it does not reject — so a displaced transition's `finally()` would otherwise delete the attribute its successor already set, dropping the successor's direction CSS. Guard: each switch mints a monotonic token via `nextDirectionToken()` and clears the attribute only when `isLatestDirectionToken(token)` — only the LATEST switch's cleanup may clear it (mirrors the gate's still-points-at-itself pattern; pure module state, no DOM).

**CSS (`globals.css`) — pure transform + containment + full UA-animation neutralization.** `view-transition-name: terminal-surface` is on the terminal content container `<div>` (the shared wrapper around the `TerminalClient`/`IframeWindow` branch, merged with the fixed-width style) so **only the terminal region slides** — sidebar, top bar, bottom bar stay static. `::view-transition-old/new(terminal-surface)` animate via pure `translateY` keyframes, **180ms ease-out**, up/down variants keyed off the root attribute. Transform-only means **no layout change** — the container's `ResizeObserver`/`fitAndSync` path never fires, so tmux sees NO resize churn during the slide (hard constraint). Two non-obvious rules, both probe-verified:
- **Containment:** `::view-transition-image-pair(terminal-surface) { overflow: clip; }` — without it the translating snapshots escape the terminal group and paint over the top bar / bottom bar / sidebar (the UA does no clipping on the pseudo-tree by default).
- **Full UA-default neutralization for LIFETIME, not just visuals:** `::view-transition-old/new(root)` AND `::view-transition-old/new(terminal-surface)` AND `::view-transition-group(root), ::view-transition-group(terminal-surface)` ALL get `animation: none`. The group rule is the load-bearing one: `animation: none` on old/new alone does NOT shorten the transition — the UA's default **~250ms `::view-transition-group(*)` animations** hold the whole pseudo-tree (and thus the pointer-dead window and `transition.finished`) alive ~250–290ms past the 180ms slide. Neutralizing the group animations makes the 180ms slide govern the transition's whole lifetime.

**First-paint gate (`SwitchGate` in `window-transition.ts`).** The new-state snapshot is gated on the incoming window's first inbound bytes so the surface slides in painted, not blank, with a **~300ms budget measured from callback entry**. Mechanics, in one module:
- `beginWindowSwitchGate()` opens a per-transition gate (a distinct token) and **FIRES any prior still-pending gate on supersession** — so rapid switches never serialize: the VT spec queues a second `startViewTransition` callback behind the first's returned promise, and the first callback holds that promise open while awaiting its gate, so firing the prior gate lets the queued second callback run at once. This call is load-bearing on BOTH the terminal AND iframe paths (a terminal→iframe switch must fire an in-flight terminal gate), so it runs before branching on iframe-vs-terminal.
- The callback does NOT `await` the `selectWindow` POST — it **chains `openForNotify()` off it** (`void posted.then(() => gate.openForNotify()).catch(() => {})`) and awaits only `gate.waitForFirstWrite()`, whose timeout clock starts at callback entry. This hard-caps the callback (and thus document-wide render suppression) at ~300ms **regardless of the POST's fate** — a stalled `selectWindow` (no client fetch timeout) cannot freeze the document up to Chromium's ~4s VT deadline, and a rapid second switch never queues behind a stalled POST. `openForNotify` is the identity filter: only writes arriving AFTER the POST resolves count, so a busy OUTGOING window's still-streaming bytes (a same-session switch rides the existing socket) can't release the gate before tmux has run `select-window`.
- `settleGate` resolves the pending promise, clears the timer, and relinquishes the module slot **only when it still points at that gate** (still-points-at-itself) — a late timeout from a displaced gate can neither resolve nor null a newer gate.
- **Release is at message-RECEIPT time — `notifyFirstWrite()` at the TOP of the stream's `onData` handler (`handleInbound`) in `terminal-client.tsx`, before the write/coalesce decision — NOT at write time.** The receipt source is the stream's first DATA frame (inbound frames are always binary under the mux, so there is one `onData` handler). This is the load-bearing subtlety: `startViewTransition` suppresses rendering while its callback runs, and **rAF callbacks do not fire during suppression**. The coalesced flush (`flushToTerminal`) is reachable only via `scheduleFlush`'s `requestAnimationFrame`, and a tmux redraw's first chunk (~4KB) always exceeds `IMMEDIATE_WRITE_MAX_BYTES` (64) — so a write-time signal is structurally unreleasable on the common path, and every animated switch would degenerate into the full 300ms freeze. `onData` is a macrotask and DOES run during suppression; releasing there is safe for capture correctness because the pending rAF flush runs at the first rendering opportunity after the callback resolves — the same rendering update in which the new state is captured, so the received bytes are painted into the captured frame. **Distinguish this receipt-time NOTIFY (the transition first-paint gate) from the deferred per-stream RESET (`consumePendingReset`, above)** — different mechanisms at different seams: the reset fires once per stream open before its first chunk write, the notify fires at receipt time. (260717-803u)
- **iframe targets** (`switchTransitionRef.iframeIds`) have no terminal receipt seam, so they use the **ungated capture** (skip the wait entirely). The predicate is the **effective resolved layout** (surface-layout spec L2), not raw `rkType && rkUrl`: a target is an iframe target iff slot A of `resolveLayout(readStoredLayout(server, id) ?? translateLegacyParams(readStoredView(…), readStoredPanel(…)), undefined, win)` is non-`tty` (the URL `?layout=` param is unknown for a not-yet-navigated target, so it resolves from localStorage — the `rk-layout:` key AND its legacy predecessors via the shim — plus the window's default hint only). This keeps a non-tty-led target on the ungated path AND — critically — keeps an **iframe-typed window whose stored layout is tty-led** (or one with no `rkUrl`) on the **gated terminal path**, exactly where it renders a `TerminalClient`. Getting this wrong reintroduces the blank-pane/stuck-transition class of bugs this section documents — e2e switch coverage guards it. Because both the render branch and this classification call the same `resolveLayout`, the two can't drift. (260714-t97o)

**Accepted trade-offs.** (1) During the ~180ms slide the VT snapshot pseudo-element hit-tests to `<html>`, so a click landing on the terminal region mid-transition is lost — a brief **whole-document pointer-input dead window**. Keyboard input is unaffected (it targets the focused element, not a hit-tested point), so keyboard-first flows (constitution V) never lose input. (2) The direction-vs-sidebar-drag divergence noted above.

#### Confirmation-gated motion — the slide is an EARNED signal

Each visual state is an **honest, distinct signal** — the slide plays only on confirmed-fast arrival, so it never animates unconfirmed content (which would show the OLD window's bytes on a slow/failed switch), and a silent `selectWindow` failure cannot park the URL/heading in an indefinite limbo with keystrokes routed to the OLD window: (260715-38kg)

| Signal | Meaning |
|--------|---------|
| slide | confirmed arrival (bytes within the 300ms budget) |
| spinner mask | in transit — don't type |
| spinner → content cut | arrived late |
| spinner → bounce + toast | switch failed |

Navigation is optimistic (heading/URL flip at click = acknowledged intent; sidebar highlight stays SSE-derived = confirmation) — see § Design Decisions → Window-switch feedback stays optimistic. Frontend-only — the `notifyFirstWrite()` call is the ONE arrival signal. The gate machine is pure; the receipt SOURCE is the RelayMux stream's first `onData` frame (see the first-paint-gate release bullet above). (260715-38kg) (260717-803u)

**Gate settle reasons (`window-transition.ts`).** `waitForFirstWrite()` resolves a `GateSettleReason = "first-write" | "timeout" | "superseded"`. `settleGate(gate, reason)` carries the reason from its three callers: `notifyFirstWrite` → `"first-write"`, the gate timer → `"timeout"`, supersession by a newer `beginWindowSwitchGate`/`armGraceMask` → `"superseded"`. `FIRST_WRITE_TIMEOUT_MS = 300` is forced by VT render suppression — must not be extended. Three concurrency guarantees hold: supersession fires the prior pending gate immediately; only the INCOMING window's post-POST bytes release the gate; the still-points-at-itself guard means a stale timer never clobbers a newer gate or touches its mask. (260715-38kg)

**`skipTransition()` on EVERY non-`first-write` settle.** In `navigateToWindow`'s VT callback the wrapper awaits the reason and calls `transition.skipTransition()` whenever `reason !== "first-write"` (`app.tsx`). This covers `"timeout"` (cut to the masked new state — no motion into unconfirmed content) AND `"superseded"`, which has TWO cases: a rapid successor VT (the VT spec already skips this transition, so the explicit call is a harmless no-op) AND an **abandoned/bounced** switch — `abandonSwitchFeedback()` settles a still-pending gate with the displaced reason and NO successor VT, so WITHOUT the explicit skip the failed switch would animate alongside its own failure feedback (slide = confirmed arrival, so a failed switch must never slide). Note SSE-confirm deliberately settles `"first-write"` (via `confirmSwitchArrived`, below): an authoritative arrival IS a confirmed arrival, so its slide is correct.

**The LogoSpinner pending mask — pure module state machine + a `useSyncExternalStore` seam.** The mask is expressed as pure, DOM-free, unit-testable module logic in `window-transition.ts` (NOT React `useState` in the wrapper — that would duplicate arm/lift/teardown and reintroduce gate↔mask drift): a `MaskState = "idle" | "masked"` with `getMaskState()` + `subscribeMaskState(listener)` (the `useSyncExternalStore` contract — snapshot stable while unchanged, listeners fire only on an actual transition). `app.tsx` reads it via `useSyncExternalStore(subscribeMaskState, getMaskState)` and, when `"masked"`, renders an absolutely-positioned full-cover `<div className="rk-window-switch-mask" role="status">` with a centered `<LogoSpinner size={48}>` over the `terminal-surface` container (which gained `position: relative`). It FULLY hides the stale bytes (a full mask, never a dimmed overlay) and sits at `z-index: 40` (below the `z-50` toast container).
- **Armed ONLY at the 300ms gate-timeout decision — NEVER at click time.** The mask arms as a side effect of `settleGate` when `reason === "timeout"` AND the gate was created `gated` (tty). Arming there, not in the wrapper after the await, makes the "never at click time" invariant structural (during the VT callback the screen is frozen on the old snapshot anyway, so early masking gains nothing). `beginWindowSwitchGate({ gated })` carries the tty flag; the wrapper passes `{ gated: !targetUngated }` (the `ungatedIds` classification, § Window Views → Window-switch transition classification — non-tty-led targets never mask and never reach a timeout settle).
- **POST-filtered lift via epoch + `liftAccepting`.** The SAME `notifyFirstWrite` receipt that releases the gate ALSO lifts the mask on late arrival ("one signal drives everything") — but the lift is FILTERED exactly like the gate release: a byte counts only once the switch's `selectWindow` POST has resolved. A module-level `liftAccepting` flag is `false` from switch start until the switch opens it (`openForNotify()` on the gate path chains off the POST; `openForLift()` on the grace path — see below), guarded by a monotonic `switchEpoch` minted per switch so a STALE switch's late POST resolution can never enable lifts for a NEWER switch's mask. Without the filter, a busy OUTGOING window's still-streaming bytes (a same-session switch rides the same socket) would un-mask stale content before tmux ever ran `select-window` — the exact hazard the filter closes.
- **Input block while masked.** The overlay's `pointer-events: auto` swallows clicks on the old window; keyboard is blocked by a capture-phase `onKeyDownCapture` on the `terminal-surface` container that `preventDefault()`+`stopPropagation()`s keystrokes (dropped, NOT buffered/replayed — replay into the new window would be its own surprise). **Global chords are EXEMPT** via the pure `isMaskExemptKey(e)` predicate (constitution V — Cmd+K is the primary discovery mechanism, and the swallow could otherwise kill it for up to the 5s confirmation window): `Escape`; meta (Cmd) chords EXCEPT `Cmd+V` (xterm doesn't forward meta-modified keys to the pty, but the browser's default paste DOES land in xterm's focused textarea → the old pty, so paste stays swallowed); and the specific Ctrl-bound globals `Ctrl+K` and `Shift+Ctrl+B` (the sidebar chord on Win/Linux — shift REQUIRED, plain Ctrl+B is pty input: readline back-char) with `!altKey` required (AltGr reports `ctrlKey:true` and AltGr+char is typed INPUT, not a chord). `Ctrl+\` and `` Ctrl+` `` are NOT exempt (the predicate gained a `shiftKey` field to make the B chord shift-aware). Plain typing and terminal control bytes (Ctrl+C) stay dropped.
- **Lift is a CUT (a fast fade-in only), never a second slide.** `.rk-window-switch-mask` has a 120ms `rk-window-switch-mask-in` fade-IN; the lift is a plain unmount. Under `prefers-reduced-motion: reduce` the mask STILL shows (input safety is never motion-only) but the fade is dropped (`animation: none`). **Ordering matters:** the base rule + keyframes sit BEFORE the reduced-motion block, so the equal-specificity `animation: none` override wins by later source order (the same discipline as `.rk-waiting-halo`).
- **`abandonSwitchFeedback()` teardown — settles the gate, not just the mask.** The failure/bounce and route-leave/unmount paths call `abandonSwitchFeedback()` (NOT a bare `tearDownMask()`): it settles a still-pending gate with the displaced reason AND tears the mask down. A bare unmask would leave the pending gate armed — a `selectWindow` POST that rejects INSIDE the 300ms budget bounces first, then the gate's timer fires `settleGate(gate, "timeout")` and re-arms a mask over the bounced-back window with NO lift path (`liftAccepting` stays false after a rejected POST), a permanently stuck input-blocking mask. `confirmSwitchArrived()` is the sibling authority-confirmed teardown: it settles a still-pending gate `"first-write"` (so its slide is correct) and tears down any mask — closing the real gap where a same-session tmux redraw completes BEFORE `openForNotify` (those bytes filtered as outgoing), leaving no later write to lift and letting the gate arm a mask over a switch that DID land. The bare `tearDownMask()` primitive has ONE sanctioned direct production caller — `beginPendingSwitch`'s fresh-switch teardown (§ below) — which clears a leftover mask WITHOUT settling a gate; the abandonment (`abandonSwitchFeedback`) and arrival (`confirmSwitchArrived`) wrappers cover every other intent and both delegate here.

**Failure bounce-back — un-sticking the silent-failure limbo.** `CONFIRMATION_WINDOW_MS = 5000` (named tunable) arms a SINGLE `setTimeout` per pending switch (NOT a poll — SSE stays the confirmation source that clears the intent). The resolved `selectWindow` POST is a parallel confirmation source (260823-ke9i): the pure settlement classifier `resolvePendingSwitchPost({ outcome, targetWindowId, isCurrent, intentMatches })` in `window-transition.ts` maps a current, intent-matching 200 whose `activeWindow` equals the target (or is absent — older daemon) to `"confirm"`, which cancels ONLY that switch's bounce timer (flagged `bounceDisarmed` on the tracked entry, so a straggler pre-resolution timer fire is a silent no-op) — `pendingClickRef` stays set until SSE confirms (the intent IS the writeback suppression) and the gate/mask machinery is untouched (paint feedback stays byte-driven; § Design Decisions → POST-200 cancels only the bounce timer). A mismatched `activeWindow` (an external switch won the race) or an explicit rejection classifies `"contradiction"` — fresh post-click evidence recorded as `postContradiction` on the tracked entry; a rejection additionally enters the bounce path immediately (the verdict below decides bounce vs re-arm). On timer expiry the verdict is freshness-gated through the pure `resolvePendingSwitchVerdict({ isConnected, tickAtClick, currentTick, postContradiction, activeWindowId, targetWindowId })` → `"confirm" | "bounce" | "rearm"` — a failure is NEVER rendered from evidence older than the click: with the socket disconnected or no post-click receipt (`currentTick <= tickAtClick`, the per-server receipt tick `getServerReceiptTick` — see `architecture.md` § `session-context.tsx` transport) the timer re-arms for another window (extend-until-evidence, unbounded, no toast/navigation; the re-armed timer replaces the tracked entry's, so every existing clear path cancels it), post-click evidence showing the TARGET active takes the existing silent-clear rescue, and ONLY fresh post-click evidence showing a DIFFERENT window active bounces — **NEVER** merely because SSE still reports the old window mid-switch. The bounce itself: `bouncePendingSwitch(target)` clears `pendingClickRef`, calls `abandonSwitchFeedback()`, explicitly `navigate`s (replace) to tmux's actual active window (a stale `activeWindow` won't retrigger the writeback effect), and `addToast("Tab switch didn't confirm — back to the active tab", "error")`.
- **Server-scoped identity at all FOUR seams.** `pendingClickRef` is a `PendingSwitchTarget = { server, windowId }` compared via the pure `isSamePendingTarget(pending, server, windowId)` at: (1) the mount-alignment skip, (2) the writeback's `urlMatchesPending`, (3) the writeback's `sseConfirmed`, and (4) `bouncePendingSwitch`'s guard. tmux `@N` ids are only unique per server and `AppShell` persists across `$server` changes, so a window-id-alone match false-positives on a cross-server collision (serverA `@5` vs serverB `@5`) — see § Click-intent and URL-match above. `bouncePendingSwitch` additionally clears SILENTLY (no toast, no navigation) when the recorded server does not match the live route (`serverRef.current !== target.server`), and its navigate uses `target.server` only after verifying it equals the live route server — a stale-server navigation is structurally inexpressible.
- **Three teardown effects, each a distinct route topology.** (a) **Server-change** (`$server` param change) — declared BEFORE the alignment effect (effects run in declaration order within a commit) so the skip sees a cleared intent and serverB's alignment fires; prev-ref keyed so it no-ops on mount. (b) **Route-leave** (`!windowParam` — windowless `/$server` SessionTiles, where the writeback can early-return) so a straggler timer can't navigate the user back with a spurious toast. (c) **Unmount** (Host `/` or a board route unmounts AppShell, but the setTimeout closure + module mask state outlive the instance). All three call `abandonSwitchFeedback()`. These are NOT subsumed by one another.
- **`beginPendingSwitch(target, { posted, graceMask })`** is the one entry point that records the intent, replaces prior tracking, **proactively tears down a leftover mask/grace timer** (a fresh switch owns ALL feedback), arms the confirmation timer, and (instant path only) arms the grace mask + wires `openForLift` off the POST. The proactive teardown is a **bare `tearDownMask()`** at the top of the callback (right after `clearPendingSwitchTracking()`): `clearPendingSwitchTracking` cancels only the tracked entry's own timer/handle, NOT the module mask, so without it a prior TIMED-OUT switch's armed mask survives into the new route until SSE confirmation. It is deliberately the BARE primitive, NOT `abandonSwitchFeedback` — on the animated path `beginPendingSwitch` runs (via `beginWindowSwitchGate → startViewTransition → runSwitch`) while the switch's OWN just-opened gate is current, and settling it would skip the earned slide — R8 (260715-38kg); it is idempotent on the gated paths (which already tore down via `armGraceMask`/`beginWindowSwitchGate`). The two gateless call sites — the deep-link mount-alignment effect (no grace mask — a cold deep-link mounts a fresh connecting pane, not stale bytes) and `navigateToWaitingTarget`'s same-server branch (no grace mask) — rely on this teardown; without it a stale input-blocking mask would carry into a window the user just navigated to. Its explicit-rejection handler is keyed on the **tracked object identity** (`pendingSwitchRef.current === tracked`, the still-points-at-itself pattern), NOT the windowId — so a displaced POST's late rejection can't bounce a newer healthy switch. It is also called from the click path (`runSwitch`). The mount-alignment effect SKIPS re-tracking when `isSamePendingTarget(pendingClickRef.current, server, windowParam)` — a click already recorded the intent, and re-tracking would fire a DUPLICATE `selectWindow` POST and (via `beginPendingSwitch`'s supersession) cancel the click's just-armed grace mask, making the instant-path mask dead in the live app.
- **Accepted non-goal — a prior switch's still-PENDING gate re-masking after a gateless switch begins.** The bare teardown clears an already-*armed* leftover mask, not a still-pending prior gate: an animated switch to A followed within ~300ms by a gateless nav to B lets A's gate timer fire and re-arm the mask over B. Discriminating that needs gate supersession `beginPendingSwitch` cannot safely perform (own-gate ambiguity — it runs with the animated path's own gate current), so it stays a rare self-healing corner, settled on the next SSE confirm or by the ungated instant path's own `abandonSwitchFeedback()`.

**Non-VT / reduced-motion grace-timer parity (`armGraceMask`).** Browsers without View Transitions support or with `prefers-reduced-motion: reduce` take the instant-switch path (no render-freeze phase, so no gate to time out). `armGraceMask(timeoutMs = 300)` returns a `GraceMaskHandle { openForLift(), cancel() }` and arms `maskState → "masked"` after the same 300ms threshold UNLESS an early first write cancels it or a late one lifts it — same threshold as the gate, different mechanism, same POST-filtered lift (`openForLift` mirrors the gate's `openForNotify`; epoch-guarded) and same `abandonSwitchFeedback` teardown. It replaces any prior grace timer AND any still-pending gate (a rapid animated→instant sequence must not let a stale gate's timeout mask the newer switch) and clears any leftover mask — one feedback machinery at a time. On the instant path `runSwitch(graceMask)` receives `!ungatedIds.has(windowId)` (a gated tty target masks; non-tty-led targets stay mask-less, matching the gated path); the animated path passes `false` (its gate's timeout arms the mask instead).

**Tests.** `window-transition.test.ts` (colocated Vitest) covers the three settle reasons, the mask state machine (arm-at-timeout gated-only, lift-on-late-write via `notifyFirstWrite`, teardown on supersession / via `abandonSwitchFeedback` / via `confirmSwitchArrived`, gated-`false` does NOT arm), the `subscribeMaskState` seam (notify-on-change, unsubscribe stops), grace-timer parity (arm-after-threshold / cancel-on-early / lift-on-late), the post-POST lift filter, the stale-rejection identity guard, `isMaskExemptKey` (Cmd+V NOT exempt, AltGr NOT exempt), `isRedundantSwitch`, `isSamePendingTarget` INCLUDING the cross-server `@N` collision, the POST-settlement classifier (`resolvePendingSwitchPost` — confirm / contradiction / none, incl. the displaced-late-settlement no-op), and the freshness-gated expiry verdict (`resolvePendingSwitchVerdict` — rearm on no-fresh-evidence or disconnected, bounce on a fresh contradiction, confirm when post-click evidence shows the target) — plus the gate/direction-token assertions. The e2e spec keeps the fast-path animated-completion guard and adds a deterministic **mask-not-stuck** poll (`toHaveCount(0)` within budget); a strict "never-flashes-on-fast-path" assert and the >300ms/failure paths are documented in the spec's intent comments as unit-covered (a >300ms first write can't be deterministically forced on localhost).

### Terminal Addons

Addons loaded in `init()` from **static top-of-file imports**, after `terminal.open()`, before `ResizeObserver` setup. Order: FitAddon → fit() → ClipboardAddon → WebLinksAddon → UnicodeGraphemesAddon → SearchAddon → SerializeAddon → ProgressAddon → WebglAddon. The Unicode addon MUST precede WebGL so the renderer measures cell widths against the active Unicode 15 table on first paint; WebGL stays last so its runtime try/catch guard wraps only WebGL construction.

**Static import bundling**: all nine xterm-family value imports (`@xterm/xterm` `Terminal`, `addon-fit`, `addon-clipboard`, `addon-web-links`, `addon-unicode-graphemes`, `addon-search`, `addon-serialize`, `addon-progress`, `addon-webgl`) are static top-of-file `import` statements in `terminal-client.tsx`, NOT runtime `await import()`. This keeps the chunk fetches out of the browser's per-origin connection budget at terminal-init time, and the board-route E2E depends on it: on the plaintext dev/test origin (no HTTP/2 — only negotiated over TLS), the browser caps ~6 persistent connections per origin, and long-lived streams (Vite HMR socket, pooled SSE `EventSource`, the `/ws/terminals` socket) already saturate the slots, so a runtime xterm chunk fetch hangs pending forever → `setTerminalReady(true)` never runs → blank pane → E2E poll timeout. Production over Tailscale HTTPS masks it (h2 multiplexes). The CSS side-effect import (`@xterm/xterm/css/xterm.css`) and type-only `import("@xterm/...")` annotations are static too.

#### Terminal Export

The tty tile's ⇩ menu ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Tile chrome) and the palette's four `Terminal: …` entries ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) run the same four export actions against the PRIMARY tty tile — `ExportAction = "snapshot" | "transcript" | "copy-visible" | "history"`; palette → tile via ONE `terminal-export` document CustomEvent carrying `detail.action` (`EXPORT_EVENT` in `lib/terminal-export.ts`, the `web-find:open` precedent), answered by the export cluster in `SurfaceLayout`. The pure mechanics live in **`lib/terminal-export.ts`** (the `window-view.ts` module contract — structural buffer shapes so tests need no real xterm, colocated vitest, one DOM edge): `buildExportFilename` (`{session}-{window}-{YYMMDD-HHmmss}.{html|txt}` from the route context + client clock, safe-name sanitized with the windowId/name fallbacks, `-full` suffix for the server arm), `transcriptFromBuffer` / `visibleScreenText` (buffer walks over `translateToString(true)` rows — trailing whitespace trimmed, a row whose successor `isWrapped` joins without a newline; never `serialize()`, which emits escape sequences — the wrong artifact for .txt), `wrapHtmlSnapshot` (`serializeAsHTML({ includeGlobalBackground: true })` output wrapped in a standalone document — doctype, charset, monospace stack, terminal background — so the .html opens self-contained), and `downloadTextFile` (Blob + temporary `<a download>` anchor — the two client-arm downloads make no server round-trip). Copy-visible copies exactly the viewport rows (`buffer.active.viewportY`, `terminal.rows` rows) via the shared `copyToClipboard` ([dialogs-and-state](/run-kit/ui/dialogs-and-state.md)). The **history** row is the server arm — the client buffer holds only what streamed since attach, so full history is a tmux capture: `fetchWindowHistory(server, windowId)` (GET `/api/windows/{windowId}/history?server=`, [architecture](/run-kit/architecture.md) § REST API) fed to the same Blob download with the `-full.txt` suffix; a fetch failure surfaces as a toast, never a crash. The server arm is honest only for NORMAL-screen panes: an application on tmux's alternate screen (pane `alternate_on 1`, `history_size 0`) holds no scrollback — the alt screen is discarded when the TUI exits, so `capture-pane -S -` returns only the viewport plus any stale pre-TUI normal-screen lines, never the session transcript — and for agent-TUI panes the xterm client buffer (scrollback-sized, § Terminal Scrollback) is the only transcript that exists. The window's SSE `altScreen` flag (the active pane's `alternate_on` rollup — [architecture](/run-kit/architecture.md) § `internal/sessions`) therefore gates the server arm at the UI: the menu row renders disabled with the hint `agent TUI on alternate screen — tmux holds no scrollback` ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Tile chrome) and the palette omits the action ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions); the endpoint itself is unchanged — correct for normal-screen panes, and a gated client never calls it for alt-screen ones. (260820-4le0)

The tile layer drives the buffer through TWO seams `SurfaceLayout` passes to the PRIMARY tty `TerminalClient` only (the `wsRef`/`focusRef` primary-tty rule): `serializeAddonRef` (the snapshot row) and **`terminalRef?: React.MutableRefObject<Terminal | null>`** — the live `Terminal` instance, same fill-at-init/null-on-cleanup lifecycle as the addon refs. The transcript/copy rows need `terminal.buffer`, which no addon seam exposes (SerializeAddon's public API is serialize-only). (260819-shqo)

#### WebLinksAddon Explicit Handler

`WebLinksAddon` is constructed with an explicit activation handler that calls `window.open(uri, "_blank", "noopener,noreferrer")` — the codebase's universal external-open idiom (`app.tsx`, `board-page.tsx`, `buildOpenPrAction`). **The handler is load-bearing for the desktop shell, not a stylistic preference.**

The addon's default handler opens a window with **no URL** (to get a blank window whose `.opener` it can clear), then assigns `location.href = uri` on it. In a browser that works — `window.open()` succeeds on the click gesture. In the Electron shell it cannot: the main process's `setWindowOpenHandler` sees `url: "about:blank"`, which is not http(s), so the intent is denied (see [desktop-shell](/run-kit/desktop-shell.md) § Security Wiring); `window.open()` returns `null` and the addon bails with a console warning ("Opening link blocked as opener could not be cleared"). The failure mode is a dead link with nothing but that console warning as evidence, and the shell cannot fix it from its side: `about:blank` carries no URL by the time main sees it.

Passing the URI through `window.open` directly makes the two environments agree: identical browser behavior (new tab, opener severed by `noopener,noreferrer` rather than the addon's manual `.opener = null` dance), and the shell's window-open policy receives the real URL and routes it to the system browser. Covered by a unit test in `terminal-client.test.tsx` asserting the addon is constructed *with* a function and that invoking it calls `window.open` with the three-arg idiom; there is no e2e — xterm renders links on a canvas, so link-region clicks are not reliably automatable. (260730-e9lz)

#### Find-in-terminal (the tty find bar's addon-search consumption)

The tty tile's find bar ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Tile renderer → tty find bar) searches the xterm CLIENT BUFFER — what streamed since attach — never tmux history, and the bar says so: a muted `client buffer only (since attach)` scope note (`TERMINAL_FIND_SCOPE_NOTE`) appears in the hint area once a search has run. The mechanics live in the pure `lib/terminal-find.ts` module (the colocated-test convention, `terminal-find.test.ts`):

- **`buildSearchOptions(toggles, palette)`** maps the bar's terminal-native toggles onto `ISearchOptions` — `Aa → caseSensitive`, `.* → regex` — always with `decorations` populated: amber matches (`palette.ansi[3]`) and an accent-green active match (`palette.ansi[2]`), derived from the active theme at search time. The addon accepts only opaque `#RRGGBB` (no alpha channel), so the in-buffer fills are blended toward the terminal background (`blendHex` — fill ratios 0.35 match / 0.5 active) to keep the matched glyphs legible; the overview-ruler ticks stay full-strength (they sit outside the text grid).
- **`runFind(addon, query, direction, options)`** wraps `findNext`/`findPrevious` and never throws — an invalid pattern while the regex toggle is on behaves exactly like a no-match (`false`); an absent addon or empty query is a no-op.
- The `Terminal` constructor carries `overviewRuler: { width: 14 }` — the addon's ruler ticks render only when the ruler has a width, so without the option no ruler ever appears.
- The consumer side (`surface-layout.tsx`, primary tty tile only) subscribes the addon's `onDidChangeResults` for the `n/N` counter (no polling), re-runs the active query on query/toggle changes (the addon re-indexes incrementally as new pane output streams in), and calls `clearDecorations()` on close/Escape and on query clear. Match state and decorations survive scrolling; the query does not persist across window switches (the tile layer remounts per window).

### Keyboard: Option as Meta

The xterm `Terminal` in `terminal-client.tsx` is constructed with `macOptionIsMeta: true`. xterm.js's own default for this option is `false`, under which macOS treats Option as a third-level shift: the browser composes an Option+letter keydown into an OS glyph (e.g. Option+P → `π`) before xterm's keyboard handler ever sees it, and that composed character is what gets written to the pty. A CLI's Meta-bound keybinding (e.g. Claude Code's Option+P → `/model`) needs the `ESC`-prefixed sequence instead, so under the default it never fires — the keypress silently does nothing, or inserts a stray glyph into whatever has focus. With `macOptionIsMeta: true`, xterm encodes every Option/Alt + key chord as `ESC` + key uniformly, the same Meta convention standard readline/shell bindings and other CLIs already expect.

This option governs the raw terminal pane's physical-keyboard path only, and shares no code path with two other Alt/Option-adjacent surfaces in the app: the docked compose textarea's `lib/readline-keys.ts`, which intercepts Alt+B/F/D by `event.code` on its own DOM element for word motion, and the bottom bar's Fn-menu `sendSpecial`, which already synthesizes an `ESC`-prefixed Alt for keyboardless coarse-pointer devices with no physical Option key to encode. Neither reads nor is affected by the Terminal constructor's `macOptionIsMeta` setting.

### Terminal Font Size (user-controllable global preference)

Terminal font size is a **global** user preference owned by `ChromeContext`, not a per-pane or per-window value (260613-oo89). The context exposes the **effective** size as `terminalFontSize: number` (what `TerminalClient` reads and the top-bar control displays); the internal preference is stored as `number | null` (null = unset) and persisted to `localStorage["runkit-terminal-font-size"]`. Effective = preference ?? device default — 11px mobile / 13px desktop via the shared `isMobileViewport()` rule (narrow-width OR coarse-pointer, NOT a CSS media query). Bounds 8–24px, step 1, exported as `TERMINAL_FONT_BOUNDS` (`{ min: 8, max: 24, step: 1 }`); all stored values clamped into `[8, 24]` on read. Helpers `clampTerminalFont`/`deviceDefaultFontSize`/`readTerminalFontSize` mirror the `fixedWidth`/`SIDEBAR_WIDTH_BOUNDS` shape.

**Mutators** (`ChromeDispatch`): `increaseTerminalFont` / `decreaseTerminalFont` step `effective ± step`, clamp, persist (try/catch noop); `resetTerminalFont` = **forget preference** (`localStorage.removeItem` → preference back to `null` → effective reverts to the device default), NOT a fixed value. First step from the unset (null) state operates on the device default and persists a concrete adjacent value (desktop 13 → 14).

**Applied to xterm** (`terminal-client.tsx`): `terminalFontSize` is passed as the `fontSize` option on construction (and to the `document.fonts.load` preloads); an effect keyed on it sets `term.options.fontSize = N` + calls `fitAddonRef.current?.fit()` on change (guarded against an uninitialized terminal). `fit()` recomputes rows×cols and **resizes the PTY** (the correct xterm resize path — reflows running TUIs, not a bitmap-scaled canvas). Because the value is global, **every** live `TerminalClient` reacts on change — including all mounted board-route panes. The mobile touch-scroll `LINE_HEIGHT` fallback reads `options.fontSize` live, so it tracks runtime changes.

**Control surfaces**: (1) the top-bar chevron menu's `−`/`+` stepper row plus the settings dialog's `[−] {size} [+]` + reset combo (see § Terminal font (Aa)), and (2) three command-palette actions — `terminal-font-increase` ("Increase terminal font"), `terminal-font-decrease` ("Decrease terminal font"), `terminal-font-reset` ("Reset terminal font"), no `shortcut`, wired to the dispatch fns. The palette actions are **layout-level globals** (`use-global-palette-actions.ts`, § Single palette mount + palette-actions slot) — the setting is global (the board's panes are live terminals too) and Constitution V requires the palette reachable on every route.

**Gesture triggers (Ctrl/Cmd+wheel, touchpad pinch)**: non-passive capture-phase `wheel` plus Safari `gesturestart`/`gesturechange` listeners on the terminal container step the global preference through the same `increaseTerminalFont`/`decreaseTerminalFont` dispatch fns the palette actions ride (bounds/step unchanged; every mounted terminal reacts, the font-change effect owning the xterm refit). Pinch arrives cross-browser as `wheel` with `ctrlKey: true` (Safari's `gesture*` carry a cumulative `scale` ratio instead); the modified deltas feed the shared pure `lib/zoom-gesture.ts` accumulator (colocated tests, the `window-view.ts` module contract — `WHEEL_STEP_THRESHOLD = 50` accumulated |deltaY| per step with the remainder carried and the accumulator reset on a direction flip, so one pinch or wheel tick never over-steps; the Safari arm steps once per ~1.1× of scale ratio, re-based on `gesturestart`). The capture phase runs before xterm's own wheel handling, so `preventDefault` blocks browser page zoom; ONLY ctrl/meta-modified wheel and `gesture*` events are intercepted — an unmodified wheel passes through to xterm untouched, and the touch-scroll-to-tmux handler (below) is unaffected (it reads single-touch moves, not wheel). The module is shared with the web tile's content zoom ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Iframe Window → Content zoom). (260823-cwvv)

**Deliberate non-decision**: `Cmd +/-` is **NOT** intercepted — browser-native whole-page zoom is retained (no global keybinding registered), avoiding the brittleness of hijacking `Cmd +/-` / `Cmd 0`.

### Terminal Scrollback (mount-time device-split buffer)

The xterm buffer's scrollback length follows the font size's mount-time device rule, not a user preference: `terminal-client.tsx` exports `SCROLLBACK_DESKTOP = 25_000` / `SCROLLBACK_MOBILE = 10_000` and accepts an optional `scrollback?: number` prop — absent → the device default via the shared `isMobileViewport()` rule (narrow-width OR coarse-pointer), resolved once at Terminal construction; an explicit value wins. Sizing is measured: the heaviest agent sessions render ~19k–31k terminal lines, so 25k covers all but the most extreme desktop runs; xterm allocates buffer lines lazily (worst case ≈1–2.5KB/line at wide cols → ~25–60MB for a FILLED desktop buffer — acceptable for the single terminal-route tile) and 10k bounds mobile memory. Board pane cards pass `scrollback={1000}` explicitly (`board/board-pane.tsx`) — boards mount many live TerminalClients as preview surfaces (the full view is one click away), so N large buffers is the one real memory hazard. Duplicate tty tiles on the terminal route share the default — full views of one window. Like `fontPx`, the split is not reactive to viewport flips (self-heals on remount). Scrollback is also what bounds the client-side transcript for alt-screen panes, where it is the only transcript that exists (§ Terminal Export). (260820-4le0)

### Terminal Font Bundling

The frontend bundles JetBrainsMono Nerd Font (patched single-file variant) as a webfont so terminal rendering is deterministic across all viewers, independent of which monospace fonts the browser happens to have installed. Without bundling, per-glyph font fallback for Nerd Font private-use-area codepoints produces visible baseline wobble within a single terminal row.

**Asset layout**: Three `.woff2` weights served from `/fonts/` — `JetBrainsMonoNerdFont-Regular.woff2` (400 normal), `-Bold.woff2` (700 normal), `-Italic.woff2` (400 italic). All three `@font-face` rules in `app/frontend/src/globals.css` expose the same `font-family: "JetBrainsMono Nerd Font"` name and MUST declare `font-display: block`. `swap` or `fallback` would let xterm measure cells against system-font metrics that persist as misalignment — xterm measures the character cell grid exactly once at `terminal.open()` and does not re-measure when a deferred font arrives. `index.html` includes a `<link rel="preload" as="font" type="font/woff2" crossorigin href="/fonts/JetBrainsMonoNerdFont-Regular.woff2" />` to overlap the Regular download with JS parsing (only Regular is preloaded — Bold/Italic are a smaller fraction of the initial paint and don't justify the extra critical-path bytes).

**Load convention before `terminal.open()`**: The init routine in `app/frontend/src/components/terminal-client.tsx` awaits a concurrent `Promise.all([document.fonts.load(...), document.fonts.load(...), document.fonts.load(...)])` for all three weights at the exact `fontPx` (`isMobile ? 11 : 13`) the Terminal will use, BEFORE `new Terminal(...)` / `terminal.open()` / `fitAddon.fit()`. Three explicit `document.fonts.load(size, family)` calls (not `document.fonts.ready`) scope the await to exactly the weights xterm will request. A fresh `if (cancelled || !terminalRef.current) return;` guard MUST follow the await. With all xterm imports static, this font-load `await Promise.all([...])` is the **only** async boundary in `init()`, so it is the sole place a post-await unmount guard is required before `new Terminal(...)`; one post-construction dispose guard sits before `setTerminalReady(true)`. (260531-m3pl)

**Primary `fontFamily`**: `'"JetBrainsMono Nerd Font", ui-monospace, monospace'` — bundled webfont first, `ui-monospace` as the system-default monospace, generic `monospace` as final guard against total load failure. The older long tail (`JetBrains Mono`, `Fira Code`, `SF Mono`, `Menlo`, `Monaco`, `Consolas`) is dead code once `font-display: block` plus a successful load makes the webfont always win; do not reintroduce it. Non-terminal monospace surfaces pick up the same font automatically via Tailwind's `--font-mono` custom property (webfont-first). (260417-hyrl)

**Test caveat**: jsdom does not implement the FontFaceSet API. `src/test-setup.ts` stubs a minimal `document.fonts.load()` / `document.fonts.ready` surface (same pattern as the existing `ResizeObserver` stub) so unit tests that mount `TerminalClient` do not hang on the await.

### Terminal Unicode Width Handling

xterm.js defaults to Unicode 6 width tables, which classify many modern glyphs (most emojis, several Misc Symbols codepoints) as 1 cell. Modern tmux lays out its buffer using wcwidth with a newer Unicode table (typically 14/15), treating the same glyphs as 2 cells. Without alignment, subsequent characters in a row drift between tmux's intended column and xterm's rendered column, producing visible ghost/overlap artifacts — especially with the WebGL renderer.

**Resolution** (`app/frontend/src/components/terminal-client.tsx`):
1. Construct the Terminal with `allowProposedApi: true` — required to access `terminal.unicode` (a proposed-API surface in xterm v6).
2. After `terminal.open()`, `loadAddon(new UnicodeGraphemesAddon())` (statically imported) and set `terminal.unicode.activeVersion = "15-graphemes"`.
3. Load order MUST precede the WebGL addon so the renderer initialises against the Unicode 15 table on first measure.

The `addon-unicode-graphemes` package (v6-era) covers Unicode 15 and grapheme clusters (ZWJ sequences, flag emoji, skin-tone modifiers). The `unicodeVersion` Terminal constructor option is a no-op past `"6"` without the addon — the addon is what registers the newer width table. (260418-xgl2)

### Terminal Touch Scroll

The terminal container div has `coarse:touch-none` (CSS `touch-action: none` on coarse pointers) so iOS delivers every `touchmove` to JS instead of panning the page. A capture-phase `touchstart`/`touchmove` pair on the container (coarse pointers only, no overlay) translates vertical swipe gestures into SGR mouse-wheel escape sequences sent to tmux over the terminal stream — `\x1b[<{64|65};{col};{row}M` per accumulated line (button 65 = swipe up = newer content, 64 = swipe down = older; col/row are mid-screen terminal coordinates because tmux ignores `1;1`). The line height divides the accumulated delta by the LIVE `options.fontSize` (the terminal-font control can change it at runtime and the effect is mount-stable). The xterm.js `.xterm-viewport` keeps `overscroll-behavior: none` (in `globals.css`) so any residual scroll never chains to the page. In the single-view model, fullbleed is always active — `overflow: hidden` and `overscroll-behavior: none` are applied to both `html` and `body` (via `globals.css`), preventing iOS Safari elastic bounce scrolling. The docked compose strip and bottom bar are siblings of the terminal container, not children, so their touch behavior is preserved.

#### Coarse-pointer focus suppression

Two effects in `terminal-client.tsx` register capture-phase listeners on the terminal container that keep xterm's hidden helper textarea from gaining focus except through a deliberate tap — coarse pointers only, each listener checking `evaluateMediaQuery(COARSE_POINTER_QUERY)` PER EVENT (the shared constant exported from `use-coarse-pointer.ts`, so the coarse-pointer query has one definition; per-event evaluation honors mid-session pointer-type changes and never strands the suppression on a setup-time snapshot):

- **`contextmenu` → `preventDefault()` + `stopPropagation()` — always-on, NOT scroll-lock-gated.** xterm 6's element-level `contextmenu` listener runs `rightClickHandler` → `moveTextAreaUnderMouseCursor`, which moves the helper textarea under the pointer and focuses it; WebKit's long-press recognizer can fire `contextmenu` during a slow scroll drag, bypassing the synthetic-click chain entirely. A long-press is never a deliberate focus request on touch (right-click has no touch meaning), so the suppression applies in every lock state. The container's React `onContextMenu` preventDefault cannot stop this (root-delegated bubble — runs after xterm's own listener has focused), so only the capture-phase stop works.
- **`touchend` → `preventDefault()` — gated on the scroll-lock preference** (see [compose-and-bottom-bar](/run-kit/ui/compose-and-bottom-bar.md) § Scroll-lock mode for the chip and the persisted state): suppresses the browser's synthetic mousedown → focusin → click chain after a tap (chosen over reactive focusin-blur as the primary mechanism because blurring mid-gesture disrupts active touch sequences and can corrupt xterm.js internal state).
- **`mousedown` → `preventDefault()` + `stopPropagation()` — scroll-lock-gated**: closes xterm's second focus path (its mousedown handler calls `terminal.focus()`) against any synthetic-mouse delivery the `touchend` preventDefault didn't cover — and stays lock-gated because `mousedown` IS the deliberate tap's focus path: a plain tap on an unlocked terminal focuses xterm and opens the soft keyboard.
- **`focusin` → blur `.xterm`-contained targets — scroll-lock-gated**: last-resort backstop turning any residual unknown focus path into a flicker instead of a stuck keyboard; scoped to locked state so it can never disrupt normal use.

While locked the soft keyboard stays down while the SGR swipe-scroll above keeps working (`touchstart`/`touchmove` still fire normally). Fine-pointer devices see zero behavior change in any lock state (the per-event coarse check passes everything through). Unit coverage lives in `terminal-client.test.tsx` (suppression before child listeners while locked, unlocked-`contextmenu` suppression on coarse pointers, fine-pointer pass-through, unlocked-`mousedown` pass-through — the tap path, backstop blurs only `.xterm` targets); e2e coverage in `app/frontend/tests/e2e/touch-focus-gate.spec.ts` (an unlocked long-press/`contextmenu` does not focus the textarea while a plain tap does). (260816-lkzv) (ngec)

## Design Decisions

### A hidden page holds no tmux attach client — release streams, don't tune sizing policy
**Decision**: When a page is hidden past `HIDDEN_RELEASE_GRACE_MS` (60 s, immediate on `pagehide`/`freeze`), `RelayMux` closes every `/ws/terminals` stream server-side and transparently re-opens them on the `visible` transition; `/ws/state` stays connected.
**Why**: Every relay stream is a sized `tmux attach-session` client, and tmux's default `window-size latest` counts hidden pages' clients in its arbitration — after connection churn, windows fall back to the smallest attached client, so one forgotten background surface (detached desktop-shell view, backgrounded tab, minimized window) snaps every visible view to its grid ("tmux constantly resizing", amplified on high-latency links). With only on-screen pages holding sized clients, `window-size latest` resolves correctly by construction, phone viewers included; hidden pages also stop paying for PTY output streamed into an invisible surface.
**Rejected**: `window-size largest`/`smallest`/`manual` — sizing-policy mitigation treats the symptom and is wrong for phone viewers (largest overflows them; manual freezes everyone). Server-side idle detach — the server cannot observe page visibility, and the per-stream self-heal re-attaches a detached client within seconds. Per-component visibility listeners — the mux is the per-tab singleton that already owns re-open-all-live-streams, so suspension is that same mechanism pointed at a different trigger.
*Introduced by*: 260903-xj0w-hidden-page-stream-release

### The suspension close's echo is shielded across a fast resume
**Decision**: A per-stream `closeEchoPending` mark — armed only when a suspension `close` op actually went out on an OPEN socket — swallows exactly one post-resume `closed` 1000; any `opened` clears it; a 4004 after resume always retires the stream.
**Why**: The server echoes `closed` 1000 for every client `close` op, and a fast `visible` transition (one RTT — realistic on the high-latency links this feature targets) clears the suspended flag and re-issues `open` before the echo lands. Unshielded, the echo retires the just-resumed stream client-side while the server processes the re-open — an orphaned server-side attach client that nothing ever closes, reintroducing the hidden-client bug class the suspension exists to kill, plus a spurious `TerminalClient` probe re-open.
**Rejected**: Swallowing only while the suspended flag is set (loses the race by one RTT); swallowing every post-resume `closed` 1000 unconditionally (would eat a genuine later PTY-EOF close — the mark is one-shot and `opened`-cleared precisely so a lost echo can't linger); a code-discriminating swallow while suspended only for 1000 (firing a racing 4004 into a hidden page just churns the redirect for nobody).
*Introduced by*: 260903-xj0w-hidden-page-stream-release

### Scroll-lock suppresses focus at the container capture phase, not inside xterm
**Decision**: Capture-phase suppressors on run-kit's own terminal container keep xterm's helper textarea from gaining focus through non-tap paths, split by gesture intent: the `contextmenu` suppressor (long-press → `moveTextAreaUnderMouseCursor`) is always-on for coarse pointers in every lock state, while `touchend`/`mousedown` suppression plus the `focusin`-blur backstop stay gated on the scroll-lock preference. (ngec)
**Why**: Ancestor capture-phase listeners provably run before xterm's element-level target/bubble listeners, so the focus never happens; the fix needs no xterm fork, no option, and no version coupling. The lock-state split matches intent: a long-press is never a deliberate focus request on touch (always-on), while the synthetic `mousedown` of a clean tap IS the tap's focus path (lock-gated), so an unlocked tap still focuses the terminal and opens the keyboard.
**Rejected**: Patching/configuring xterm (no public option disables its contextmenu handler; forking is maintenance debt); relying on the container's React `onContextMenu` preventDefault (root-delegated bubble — runs after xterm has already focused, demonstrated in production as the silent-keyboard-pop leak); reactive focusin-blur as the primary mechanism (disrupts active touch sequences — kept only as a rarely-firing backstop); gating the contextmenu suppressor on scroll-lock (leaves the unlocked long-press side-effect-focus path open in the terminal's normal state).
*Introduced by*: 260816-lkzv-mobile-scroll-lock-hardening

### Pending-switch identity is `{server, @N}`, never the session name
**Decision**: `PendingSwitchTarget` keys click-intent/URL-match on `{server, windowId}` — excluding the session name, including the server.
**Why**: excluding the session name lets the selection survive a session rename or a cross-session move where `@N` survives but the session name changed (a session-name match would flip false and release pending-click suppression early, bouncing the selection). Including the server is load-bearing because tmux `@N` ids are unique only per server and `AppShell` persists across `$server` route changes without remounting — window-id-alone matching false-positives on a cross-server id collision (serverA `@5` vs serverB `@5`), which would suppress serverB's alignment and let serverA's failure bounce yank the user cross-server with a false toast.
**Rejected**: `{session, windowId}` matching (bounced the selection on rename/move); window-id-alone matching (cross-server collision).
*Introduced by*: 260529-jad6-window-api-stability, 260715-38kg-window-switch-confirmed-motion

### Fresh-switch mask teardown is a bare `tearDownMask()` at the `beginPendingSwitch` seam
**Decision**: `beginPendingSwitch` proactively clears a leftover mask/grace timer with a bare `tearDownMask()` at the top of its callback — enforcing "a fresh switch owns ALL feedback" at the one seam every pending switch passes through.
**Why**: the animated path reaches `beginPendingSwitch` (via `beginWindowSwitchGate → startViewTransition → runSwitch`) with its OWN just-opened gate current; the bare primitive clears a leftover armed mask without settling that gate, so the earned slide survives. The one shared seam means a future gateless caller inherits the fix.
**Rejected**: `abandonSwitchFeedback()` here (settles the animated path's own current gate with the displaced reason → skips the earned slide — R8 (260715-38kg)); per-call-site `tearDownMask()` at the two gateless callers (spreads the invariant across callers — a future gateless caller re-introduces the leftover-mask bug).
*Introduced by*: 260719-h0x4-window-switch-stale-mask-teardown

### Terminal link-opening is the SPA's job, via the shared `window.open` idiom
**Decision**: `WebLinksAddon` carries an explicit activation handler calling `window.open(uri, "_blank", "noopener,noreferrer")`; the addon's default handler is not used.
**Why**: The default opens a URL-less blank window and then assigns `location.href`, so an embedding shell only ever sees `about:blank` — the URL is gone before any host-side policy can act on it. No amount of Electron-side work can recover it, which makes this a frontend fix by necessity rather than by preference. Routing through `window.open` also puts terminal links on the same three-arg external-open idiom as every other outbound link in the SPA, so the shell needs exactly one window-open policy rather than a per-affordance special case.
**Rejected**: Fixing it in the desktop shell (impossible — `about:blank` carries no URL); a custom `linkHandler` on the `Terminal` options instead of the addon handler (reimplements the addon's URL detection for the same outcome); a Playwright e2e for the click path (xterm renders links on a canvas, so link-region clicks are not reliably automatable).
*Introduced by*: 260730-e9lz-shell-terminal-links-external

### A `resolved → ""` session-identity transition bumps the epoch, it is not inert
**Decision**: the session-identity watcher records `""` AND bumps `connectionEpoch` on a resolved → `""` transition, forcing a probe reconnect by `windowIdRef.current`.
**Why**: that probe is the ONLY reachable recovery path in the loss-of-identity state — `computeKillRedirect` and the URL writeback are both gated on a non-empty `sessionName`, so nothing else can act on a window that was killed externally, pinned to a filtered `_rk-pin-*` session, or reached via a dead deep link. The probe either re-resolves the owning session server-side (one flicker-free reconnect) or the relay closes 4004 and `onSessionNotFound` redirects.
**Rejected**: treating `""` as inert in both directions — it wedges the UI on kill-while-viewing (no redirect, no reconnect, no recovery path at all).

### Window-switch feedback stays optimistic
**Decision**: the heading and URL flip at click time while the sidebar highlight stays SSE-derived; the pending state is a full LogoSpinner mask, and an unconfirmed switch bounces back with a toast.
**Why**: each visual state is an honest, distinct signal — the click flip acknowledges intent, the SSE-derived highlight is the only confirmation, and the slide plays only on confirmed-fast arrival so motion never carries unconfirmed content. A full mask hides the stale bytes outright, so a user cannot read the old window as the new one and type into it.
**Rejected**: pessimistic navigation (heading/URL wait on SSE — discards the acknowledged-intent signal); a dimmed overlay instead of a full mask (leaves stale bytes legible, so the surface still reads as arrived).
*Introduced by*: 260715-38kg-window-switch-confirmed-motion

### Global `macOptionIsMeta` over scoped Option+letter interception
**Decision**: Set `macOptionIsMeta: true` once on the xterm `Terminal()` constructor so every Option/Alt + key chord is Meta-encoded uniformly.
**Why**: xterm.js's own first-class option for this exact tradeoff — no fork, no version coupling, no reimplementation of xterm's keyboard encoder, and one reversible line. Meta is only useful as a modifier if arbitrary letters reach the program, which is precisely what a uniform flag gives.
**Rejected**: Enumerating specific Option+letter combos inside the existing `attachCustomKeyEventHandler` (where Cmd+C copy is already special-cased) and emitting `\x1b` + letter manually. It only helps chords the app knows about in advance, so the allowlist would need extending every time a CLI adds a Meta binding, while still leaving the general case broken.
*Introduced by*: 260819-c9i9-xterm-option-meta-key

### Search decoration colors derive from the active theme, buffer fills blended down
**Decision**: the tty find bar's `ISearchOptions.decorations` are computed per search from the active theme palette — amber matches (`ansi[3]`), accent-green active match (`ansi[2]`) — with the in-buffer fills blended toward the terminal background (`blendHex`, 0.35/0.5 ratios) and the overview-ruler ticks at full strength.
**Why**: the addon accepts only opaque `#RRGGBB` (no alpha channel), so a full-strength fill would drown the matched glyphs; deriving from the palette keeps find highlights in the label-color vocabulary under every theme, and the ruler ticks sit outside the text grid so they need no blend.
**Rejected**: hardcoded decoration constants (drift from the theme system that already derives xterm's colors from the palette); alpha-channel colors (the addon silently rejects non-`#RRGGBB` forms).
*Introduced by*: 260819-zqf9-terminal-tile-find

### Buffer-walk exports read the live `Terminal` through a `terminalRef` prop seam
**Decision**: `TerminalClient` exposes the live `Terminal` instance via one optional `terminalRef?: React.MutableRefObject<Terminal | null>` prop with the same fill-at-init/null-on-cleanup lifecycle as the addon ref seams; the export transcript/visible-copy rows walk `terminal.buffer` through it.
**Why**: The export arms need buffer access and no existing seam exposes it — SerializeAddon's public API is serialize-only with no buffer accessor; a small additive prop honors the scaffold's parallel-merge contract (the import/registration block stays untouched).
**Rejected**: Casting into the addon's private `_terminal` (private API, violates type-narrowing-over-assertions); deriving plain text by stripping escapes from `serialize()` output (loses wrapped-line semantics); the DEV-only `window.__rkTerminals` registry (not a production seam).
*Introduced by*: 260819-shqo-terminal-tile-export

### Scrollback is a prop with a device-split default, not a context preference
**Decision**: `TerminalClient` takes an optional `scrollback?: number` prop; absent → `isMobileViewport() ? SCROLLBACK_MOBILE : SCROLLBACK_DESKTOP` at Terminal construction.
**Why**: the terminal-route tile (and duplicate tty tiles) want the big buffer with zero plumbing; boards opt down explicitly; sizing came from measured sessions (19k–31k rendered lines for the heaviest; ~25–60MB worst-case filled desktop buffer is acceptable for one tile, not for N board panes).
**Rejected**: a ChromeContext preference (no user-facing knob asked for); a flat global (mobile memory); resizing live buffers on viewport change (xterm applies `options.scrollback` live, but the split is a mount-time device rule like `fontPx` — not worth a reactive effect).
*Introduced by*: 260820-4le0-export-honesty-scrollback

### Menu-time honesty over click-time failure (the alt-screen export gate)
**Decision**: the server-capture export arm is gated on the SSE `altScreen` field (menu row disabled + hint, palette action absent) rather than returning an error shape from the history endpoint.
**Why**: the artifact is not merely unavailable for alt-screen panes — it structurally cannot exist (tmux stores no scrollback for the alternate screen); advertising the row and failing on click would keep the lie one step longer. The field is one format-list token + one derived bool.
**Rejected**: endpoint 409/422 + toast (click-time failure); probing `history_size` as the gate (an alt-screen pane with stale pre-TUI history would re-enable a misleading row).
*Introduced by*: 260820-4le0-export-honesty-scrollback

### POST-200 cancels only the bounce timer, never the intent or the gate
**Decision**: Confirmation-on-200 disarms the failure detector (the 5s bounce timer) and nothing else: `pendingClickRef` stays set until SSE confirms, and `confirmSwitchArrived()` is NOT called at POST resolution.
**Why**: The pending intent is what suppresses the URL writeback while the SSE snapshot is stale — clearing it at POST time would let the very next writeback pass navigate back to the stale active window. And `confirmSwitchArrived()` settles the first-paint gate as `"first-write"`; calling it at POST resolution (which typically precedes the tmux redraw bytes) would slide/unmask into not-yet-repainted stale content, violating the "slide = confirmed content arrival" contract. Paint feedback stays byte-driven; the POST 200 is navigation-truth evidence only.
**Rejected**: Calling `confirmSwitchArrived()` on 200 (breaks the earned-slide semantics); clearing `pendingClickRef` on 200 (re-exposes the stale-writeback yank the intent exists to suppress).
*Introduced by*: 260823-ke9i-switch-confirm-post-freshness

### No-fresh-evidence policy: extend-until-evidence, no GET re-verify
**Decision**: On timer expiry with no post-click evidence (or a disconnected socket), the confirmation window re-arms indefinitely; no one-shot GET-of-sessions verdict path exists.
**Why**: A bounce without post-click evidence is exactly the false-failure class the freshness gate exists to kill — bounding the re-arm ("one extension, then bounce anyway") reintroduces the evidence-free bounce, just later. The failure asymmetry favors extension: staying on the window the user chose (usually already confirmed via the POST) is strictly better than a false yank + toast. The intent still clears through supersession, the three teardown effects, and the next SSE snapshot (reconnect resubscribes re-ack with a fresh snapshot, so evidence eventually arrives on every recovery path). A fetch-based verdict would add a client-polling path the code-quality anti-patterns rule out, for a case the POST confirmation already covers.
**Rejected**: Bounded re-arm then bounce (evidence-free verdict, deferred); one-shot GET re-verify (client-polling anti-pattern; redundant with POST confirmation).
*Introduced by*: 260823-ke9i-switch-confirm-post-freshness

### Pending-switch verdict logic is a pure helper in `window-transition.ts`
**Decision**: The expiry decision (`resolvePendingSwitchVerdict` → confirm | bounce | rearm) and the POST-settlement classifier (`resolvePendingSwitchPost`) are pure exported functions in `src/lib/window-transition.ts` with colocated Vitest coverage; `app.tsx` supplies the ambient facts.
**Why**: The pending-switch machinery's established pattern — `isSamePendingTarget`, `isRedundantSwitch`, the gate/mask state machine — keeps decision logic DOM-free and unit-testable, which is the only way to test the sleep/wake scenario (frozen pre-click snapshot + half-open socket) deterministically, with no real sockets or timers.
**Rejected**: Inline logic in `bouncePendingSwitch` (untestable without mounting AppShell — the exact class of drift the pure-helper pattern exists to prevent).
*Introduced by*: 260823-ke9i-switch-confirm-post-freshness

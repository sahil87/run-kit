## Why

**Problem**: C1–C4 shipped the cron substrate (entry files, the stateless evaluator, the daemon
ticker, delivery) and the operator-tick backstop, but there is still no way to *see* any of it. Three
concrete gaps this change closes:

1. **No HTTP surface for cron at all.** `rk cron list` (the CLI) deliberately never computes
   next-fire/rung/orphan status — its own doc comment says so explicitly: *"a tmux probe against a
   dead socket would resurrect the server, so next-fire/rung/orphan derivations stay out of the CLI
   and belong to the API wave"* (`app/backend/cmd/rk/cron_list.go:14-19`; the same call is recorded
   as a Design Decision in `docs/memory/run-kit/cron.md` § `cron list` never touches tmux: *"next-fire/rung
   need live facts, which the API wave derives behind the HTTP surface"*). Nothing today computes
   those live facts. Without it, C6/C7 have nothing to render.
2. **No mutation surface.** Entries can only be created/muted/removed via `rk cron` from inside a
   pane. A desktop/mobile UI needs POST endpoints.
3. **The watchlist requires reading a second file the UI can never touch directly.** The "what is the
   operator currently watching" fact lives in a **fab-owned** state file
   (`$XDG_STATE_HOME/fab/operator/<server-slug>.yaml`, written only by `fab operator` verbs — a
   different repo, a different binary). `internal/cron/guards.go` already reads this file tolerantly
   for the `suppress_while` guards, but only extracts a coarse count (`TrackedCount`) and
   `LastTickAt` — never the actual `monitored:` records (which change, which pane, what stage). If
   the frontend read this file itself it would violate Constitution X (hooks/UI carry only the
   underivable) and duplicate a fab-owned schema in two places. rk must derive the join once, server-side,
   and hand C6/C7 a flat, already-joined fact on the window it belongs to.

**Consequence of not fixing this**: C6 and C7 (the sidebar CLOCK section and the mobile Activity feed)
cannot be built — they have no data source. The plan explicitly sequences `C5 → (C6 ∥ C7)`.

**Why this approach**: the spec is unusually prescriptive here (this is a "derive it once, expose it
flat" change, not a design-open one) — reuse every existing primitive (`cron.LoadEntries`,
`cron.ReadLog`, `cron.GatherFacts`, `cron.JoinAnchor`/`Ladder`, `cron.FabOperatorStatePath`, the
`s.initSSEHub(); s.sseHub.wake(server)` mutation-wake pattern already used by
`handleSessionStringOption` in `app/backend/api/sessions.go:141-145`, and the native per-pane join
pattern already used for the fab tier in `internal/sessions/sessions.go` FetchSessions, documented at
`docs/memory/run-kit/tmux-sessions.md` § Fab-Tier Derivation (native, per pane)) rather than invent
new mechanisms. This keeps the change additive and low-risk: no existing endpoint's behavior changes,
only new fields/routes are added.

## What Changes

### 1. `GET /api/cron?server=<slug>` — entries + derived facts

New handler in a new `app/backend/api/cron.go` (no existing file by that name; the package already
follows one-file-per-resource, e.g. `boards.go`, `servers.go`), registered in
`app/backend/api/router.go` alongside the existing `/api/sessions*`/`/api/boards*` routes.

Unlike `rk cron list` (disk-only, zero tmux), this handler is a live-server endpoint — the frontend
only ever calls it for a server it already knows is live (the same posture `GET /api/sessions`
already has) — so it may call `cron.GatherFacts` (which does live tmux reads) to resolve each entry's
target and compute the facts the CLI explicitly punts:

- **`next_fire`** (unix seconds): for `backoff` entries, `cron.JoinAnchor(rawEpoch, log, min, max).NextFire(min, max)`
  using the resolved target's `TargetFacts.StateEpoch`; for `every` entries, `lastDelivery + interval`
  (or `created_by.at + interval` before any delivery — the same anchor rule `schedule.go`'s
  unexported `everyAnchor`/`everyDue` already encode); `cron`-kind entries report no next-fire (unevaluated
  this wave, per `docs/memory/run-kit/cron.md`).
- **`rung`** (int): `cron.JoinAnchor(...).Rung` for `backoff` entries; 0 for `every`/`cron`.
- **`orphaned`** (bool): `true` when the entry's target fails resolution this tick
  (`!TargetFacts.Resolved()`) — a **live snapshot**, not a persisted TTL state. TTL-based orphan
  expiry (7d, `pinned` exempt) is explicitly C8 (wave 4) scope; this change only surfaces the
  boolean the evaluator already computes per-tick, never adds expiry/GC logic.
- **`last_fired`** (unix seconds, 0 = never): `cron.LastDelivery(log, entry.ID)`, exactly as
  `cron_list.go` already does.

**Architecture call**: the next-fire/rung/orphaned math is *schedule derivation logic that belongs in
`internal/cron`*, not the `api` package — `internal/cron` already owns every piece of it
(`JoinAnchor`, `Ladder.NextFire`, `everyDue`/`everyAnchor`). This change adds one new exported function
in `internal/cron` (e.g. `DeriveEntry(e Entry, log []LogLine, facts TargetFacts, now time.Time) DerivedEntry`
returning `{NextFire time.Time, HasNextFire bool, Rung int, Orphaned bool, LastFired int64}`) that the
API handler calls per entry — the API package stays a thin JSON translation layer, matching the
existing package boundary (`api` never reimplements `internal/cron` math) and keeping "UI is a pure
projection" honest: the projection logic lives in one place, testable without HTTP.

**Response shape** (camelCase JSON, matching the existing API convention — `sessions.go`'s
`worktreePath`, `agentState`, etc. — NOT the on-disk YAML's snake_case):

```json
{
  "entries": [
    {
      "id": "a3f9",
      "name": "operator tick",
      "schedule": {"kind": "backoff", "anchor": "operator-idle", "min": "60s", "max": "30m"},
      "wakeOn": {"event": "agent-state-change", "scope": "server", "debounce": "10s"},
      "target": {"kind": "role", "role": "operator"},
      "payload": "operator tick",
      "deliver": "immediate",
      "ifAbsent": "respawn",
      "pinned": true,
      "muted": false,
      "lastFired": 1788254900,
      "nextFire": 1788255200,
      "rung": 2,
      "orphaned": false
    }
  ]
}
```

`server` resolves via the existing `serverFromRequest(r)` helper (query param, same as every other
endpoint). An absent/empty entry file yields `{"entries": []}`, 200 — never a 404 (mirrors
`handleSessionOrderGet`'s "unset ⇒ empty, never 404" posture). Corrupt-entry diagnostics from
`cron.LoadEntries` are logged server-side (`slog`), never surfaced to the client — the tolerant-load
posture the CLI already has.

### 2. `POST /api/cron/create`, `POST /api/cron/delete`, `POST /api/cron/mute`

Three new POST-only handlers (Constitution IX), same file. Each wakes the SSE hub explicitly on
success — mirroring `handleSessionStringOption`'s exact pattern (`sessions.go:141-145`):
```go
s.initSSEHub()
s.sseHub.wake(server)
```
(the spec's own words: *"Mutations wake the SSE hub explicitly (user-option and file writes emit no
tmux event — the safety-poll lesson)"*.)

- **`POST /api/cron/create`** ← body mirrors the `rk cron add` schema fields (name, schedule
  kind+params, target kind+params, payload, deliver, if_absent, pinned) → `cron.Add(dir, slug, entry)`.
  Validation reuses `Entry.validate()` (already exported behavior via `Add`'s own call) — a validation
  failure is a 400 with the underlying error text (mirrors `handleSessionCreate`'s
  `validate.ValidateNewName` 400 pattern). Returns the created entry (with its assigned 4-char id) at
  201.
- **`POST /api/cron/delete`** ← `{"id": "a3f9"}` → `cron.Remove(dir, slug, id)`; `false` (id not
  found) → 404; success → 200 `{"ok": true}`.
- **`POST /api/cron/mute`** ← `{"id": "a3f9", "muted": true}` → `cron.SetMuted(dir, slug, id, muted)`;
  same 404/200 contract as delete.

**Non-goal**: `pin` gets no HTTP endpoint in this wave — the operator's dispatch text enumerates
exactly `create|delete|mute`, and neither C6's row actions ("mute/delete on the row's flyout card")
nor C7's entry detail sheet ("mute toggle, pin, delete" — wait, C7 DOES list pin) lists pin for C6.
`cron.SetPinned` already exists (unused by any HTTP handler after this change) — a `POST
/api/cron/pin` follow-on is trivial to add when C7 needs it, but is out of scope here per the explicit
dispatch enumeration.

### 3. The fab-operator-state reader — the real `monitored:` schema

`internal/cron/guards.go`'s `ParseOperatorState`/`ReadOperatorState` already reads this file
tolerantly but only extracts `LastTickAt` and a coarse `TrackedCount` — it deliberately treats
`monitored`/`watches`/`autopilot` as opaque (`trackedLen` counts by shape, never decodes fields). This
change adds a **new**, richer tolerant reader for the `monitored:` map's actual per-entry fields,
because the watchlist join needs the pane ID, not just a count.

**Verified against the actual fab-kit source** (`/home/sahil/code/sahil87/fab-kit/src/go/fab/cmd/fab/operator_state.go`,
the byte-compatible schema fab's `operator_tick_start.go`/`operator_monitored.go` write) — this is
the real, current cross-repo contract, not a guess from the spec's prose summary:

```go
// fab-owned; rk reads it tolerantly, never writes it.
type monitoredEntry struct {
    Pane           string   `yaml:"pane"`             // "%458" — the join key
    Repo           string   `yaml:"repo"`
    Session        string   `yaml:"session"`
    Stage          string   `yaml:"stage,omitempty"`
    Agent          string   `yaml:"agent,omitempty"`  // last-known agent state
    Branch         string   `yaml:"branch"`
    // StopStage, SpawnedBy, DependsOn, EnrolledAt, LastTransition also exist
    // on the fab side; not needed for the watchlist join, ignored (tolerant
    // read — unknown/unused keys never fail the parse).
}
// top-level: monitored: map[string]monitoredEntry  (keyed by an opaque change
// id / label the map key alone provides — e.g. "gmcp", "pending-c5"; verified
// live at ~/.local/state/fab/operator/*.yaml)
```

Add a new exported reader in `internal/cron` (new file, e.g. `watchlist.go` — sibling to `guards.go`,
same external-contract comment block) reusing `FabOperatorStatePath` for path resolution:

```go
type WatchlistEntry struct {
    ChangeID string // the monitored map's key
    Pane     string // "%N" — the join key onto WindowInfo/PaneInfo
    Repo     string
    Session  string
    Stage    string
    Agent    string
    Branch   string
}

// ReadWatchlist tolerantly parses the monitored: map plus last_tick_at.
// Absent/corrupt file -> (nil, 0, false), never an error.
func ReadWatchlist(path string) (entries []WatchlistEntry, lastTickAt int64, present bool)
```

Tolerance posture matches `guards.go` exactly: unknown top-level keys ignored, an absent file or YAML
parse failure degrades to `(nil, 0, false)` — never an error, never a partial panic. A `monitoredEntry`
missing `Pane` is skipped (nothing to join against) rather than failing the whole file.

### 4. Joining the watchlist onto the sessions payload, by pane ID

Extends `internal/sessions.FetchSessions` (`app/backend/internal/sessions/sessions.go`) with one more
per-window enrichment step, in the same per-request loop that already computes the fab tier
(`sd.windows[j].FabChange = fab.change`, `sessions.go:813-814`) and is documented at
`docs/memory/run-kit/tmux-sessions.md` § Fab-Tier Derivation (native, per pane). Unlike the fab tier
(memoized per-cwd because many panes share a worktree), the watchlist read is **one file per server**,
so it needs exactly one `cron.ReadWatchlist` call per `FetchSessions` invocation (no per-pane memo
needed), then a map lookup per pane by `PaneID`.

New `tmux.WindowInfo` fields (camelCase JSON, `omitempty` — the `FabChange`/`FabStage` precedent
immediately above them in the struct):

```go
Monitored       bool   `json:"monitored,omitempty"`
MonitoredChange string `json:"monitoredChange,omitempty"` // the monitored map's key
MonitoredStage  string `json:"monitoredStage,omitempty"`
MonitoredRepo   string `json:"monitoredRepo,omitempty"`
MonitoredBranch string `json:"monitoredBranch,omitempty"`
MonitoredAgent  string `json:"monitoredAgent,omitempty"`
```

A window is `Monitored: true` when any of its panes' `PaneID` matches a `WatchlistEntry.Pane` (the
same window-level-rollup-over-panes shape `rollupAgentState`/`rollupAgentSession` already use). This
gives C6/C7 everything the spec's flyout-card detail line and row indicator need
(*"a row-level 'watched' indicator plus a detail line on the row's existing flyout card (beside
`@rk_win_note`)"*) without either UI reaching into the fab-owned file itself — satisfying Constitution
X and the standing "UI is a pure projection" rule.

**Staleness** (`last_tick_at` → the single staleness timestamp serving every consumer per the spec):
add to `sessions.ProjectSession` (not per-window — a per-server fact):

```go
OperatorLastTickAt int64 `json:"operatorLastTickAt,omitempty"`
OperatorStale      bool  `json:"operatorStale,omitempty"`
```

populated identically on every `ProjectSession` in one `FetchSessions` call (all sessions on a server
share the one operator-state file). This is simpler for a frontend consumer than requiring it to find
the one `Hidden` operator session first, at the cost of a few repeated bytes per extra session — a
deliberate, easily-revisited simplicity/normalization tradeoff (see Assumptions).
<!-- assumed: staleness attaches to every ProjectSession rather than only the Hidden operator session — simpler consumer contract, cheap to relocate later if payload size ever matters -->

`OperatorStale` uses a new named threshold constant in `internal/cron` (e.g.
`DefaultWatchlistStaleThreshold`), distinct from `guards.go`'s `DefaultOperatorLoopFreshThreshold`
(120s — that one gates the `operator-loop-fresh` suppress guard, a different, much shorter-fuse
question: "is the in-session loop still ticking"). The UI-facing "is the whole monitoring system dead"
threshold is a longer, product-level number the spec never pins down numerically. A default of
**15 minutes** is assumed here — comfortably above the operator tick's max backoff gap (30m... actually
note: 15m is BELOW the 30m max backoff cap, so a healthy backoff-only tick cadence could trip false-stale
near its own max gap; this is called out explicitly for `/fab-clarify` or plan-stage reconsideration,
not silently locked in).

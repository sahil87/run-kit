## Why

1. **Pain point**: settings are editable only where someone hand-built a control. The dialog's General/Appearance tabs cover 6 of the 12 registry keys with bespoke wiring (`settings-dialog.tsx:536-625`); `auto_name`, `tmux_conf`, and `log_level` — the three keys Phase 1 added — have **no UI at all** (no client function, no control, no palette action). Every new registry key would need a hand-built row, which is exactly the per-key growth the registry was built to end: Phase 1 made key *storage* one registry entry, Phase 2 made key *HTTP plumbing* zero-cost, but key *UI* still pays the old tax.
2. **Consequence of not doing it**: the registry's `ui`/`live`/`category`/`description` metadata (served by `GET /api/settings` since Phase 2) stays dead data — the whole point of the registry-driven API (Phase 2 intake §Why-2) was that a settings surface could render itself from one payload. And `auto_name` (shipped in PR #711 as opt-in) remains toggleable only by hand-editing config.yaml **plus a daemon restart** — the plan explicitly assigns making it live to this phase (also recorded in `docs/memory/run-kit/operator-actuation.md:200-210`).
3. **Why registry-generated over more hand-built rows**: rows generated from registry metadata cannot drift from the key inventory — a future key with `ui: true` appears in the pane with a typed control, description, category placement, default indicator, and live/restart badge, with zero frontend work. Hand-built rich controls are kept where they encode real UX (theme pair picker with preview, accent descriptor popover) — the list is generated; the control per row is resolved per kind with key-specific overrides (the plan's "typed controls from the registry").

## What Changes

### 1. Backend: `auto_name` flips to `live: true` + the hub rewire seam

The only backend work in this change, sanctioned by the invocation as "what's needed to make 'live' keys actually take live effect":

- **Registry flip**: `internal/settings/settings.go:301-320` — `auto_name`'s entry changes `live: false` → `live: true`. The stale doc comment on `Settings.AutoName` (`settings.go:66-71`, "read at hub construction, so a change applies on the next daemon restart") is rewritten. The pinned metadata row in `internal/settings/registry_test.go:33-44` (`{"auto_name", "bool", "false", "behavior", true, false}`) updates to `true`.
- **Hub rewire on POST**: today `auto_name` is read exactly once — `api/router.go:613` seeds `Server.autoNameEnabled` from `settings.Load()` in `NewRouterAndServer`, and `initSSEHub` (`api/router.go:268-274`) either nils the hub's tracker or wires its `deliver` closure, once, under `s.sseOnce`. Per-tick sites only nil-check (`api/sse.go:1437-1441` advance, `:1594-1596` retain); there is no setter. This change adds one: `handlePostSettings` (`api/settings.go:81`), after a successful save whose body contains `auto_name`, calls `s.initSSEHub()` and a new hub-level apply seam (e.g. `sseHub.setAutoName(enabled bool)`) that nils the tracker on disable and installs a freshly-constructed, `deliver`-wired tracker on enable — the same wiring `initSSEHub` performs at `router.go:268-274`, extracted so both call sites share it. **Synchronization is load-bearing**: the tick loop reads `h.autoName` without coordination today, so the seam must make the swap race-free (guard the field with the hub's existing locking discipline or an explicit mutex — plan decides the exact shape). Disable→enable drops in-memory cooldowns; that is already the documented daemon-restart semantics (Constitution II — process-memory only) and stays acceptable.
- **The stale-seed field**: `Server.autoNameEnabled` (`api/router.go:179-185`) remains as the construction-time seed consumed by `initSSEHub`; its doc comment ("a toggle applies on the next daemon restart") is rewritten to describe the POST-driven live path.
- **Precedent preserved**: the POST's existing `board_order` side effect (`api/settings.go:120-126` → `broadcastBoardOrder`) is untouched. `api/settings_test.go:415` (`TestPostSettings_withoutBoardOrderBroadcastsNothing`) is updated to account for the new `auto_name` side effect; a new handler test covers toggle-on/toggle-off rewiring. Tracker unit tests (`api/auto_name_test.go`) keep passing unchanged — the tracker itself does not change.
- **No generic `settings-changed` SSE broadcast is added.** The registry's `live` contract is "applies on next read without a daemon restart" (`settings.go` registryEntry doc) — and every other live key already honors it: `ssh_host`/`instance_name` are `settings.Load()`-per-request in `api/health.go:28`, `instance_color` per-request in `api/pwa.go:70`, `board_order` has its dedicated broadcast, and theme/colors/flairs are frontend-consumed (fetch-on-mount + optimistic in-tab update). Cross-tab push for frontend keys would be new backend surface the invocation forbids and today's `live: true` semantics never promised. `auto_name` is the only key whose consumption cadence (read-once-at-construction) actually violated the live contract — the rewire fixes exactly that.

### 2. Backend: enum kinds carry their legal values in the registry

`kind: "enum"` entries currently keep their options implicit — `theme`'s modes appear nowhere in Go as data, `log_level`'s `info|debug` pair is hardcoded inside its parse/apply closures (`settings.go:336-353`). A generated enum control needs options as data, and the registry is the single source of truth by design, so `registryEntry` gains an `options []string` field (set on `theme`: `system, dark, light`; `log_level`: `info, debug`), surfaced through `KeyInfo` (`settings.go:500`), `Registry()` (`:512`), and the `GET /api/settings` wire struct (`api/settings.go:15` `settingEntry`, omitted/empty for non-enum kinds). This is registry-metadata enrichment riding the existing endpoint — not a new endpoint and not new behavior; the apply validators keep owning enforcement. `registry_test.go` and `api/settings_test.go` GET-shape tests extend accordingly. (`theme_dark`/`theme_light` are `kind: "string"` — their value space is the frontend theme list and they are handled by the rich theme control, §4.)

### 4. Typed controls generated per kind, with key-specific rich overrides

Row control resolution is a kind→component map with named-key overrides — "generated from the registry" means the *list and row chrome* are generated; the control slot is typed:

| kind | Generated control |
|---|---|
| `bool` | toggle/checkbox (`auto_name` — the first consumer) |
| `enum` | select over the entry's `options` (§2) (`log_level`) |
| `string` / `path` | the existing `TextSetting` (Enter/blur commit, Escape cancel, inline `role="alert"` rejection — `settings-dialog.tsx:109`) (`ssh_host`, `instance_name`, `tmux_conf`) |
| `color` | the existing descriptor-model `SwatchPopover` control (`AccentColorControl` shape, `settings-dialog.tsx:240`) (`instance_color`) |
| `map` / `list` | **no generated editor** — see below |

- **Key-specific overrides**: the curated Appearance tab keeps `ThemePairControl` (`settings-dialog.tsx:192` — mode buttons + shared `ThemePickerList` with hover preview) as the rich theme surface. In the table, overrides apply where a naive control would accept invalid values: `theme_dark`/`theme_light` render as selects over the client theme registry (`themes.ts` list) rather than free text (their backend validation is only non-empty, so a typo would persist silently), and `instance_color` binds the same `SwatchPopover` descriptor control in both presentations (repainting the top-bar stripe optimistically as today, via the accent context). Generic kind controls are the fallback every *future* key gets for free.
- **`map`/`list` rows** (`server_colors`, `server_flairs`, `board_order`): rendered as read-only rows — description, current-value summary (entry count / ordered names), modified-from-default indicator — with a hint pointing at their dedicated surfaces (sidebar row color/flair pickers, board sidebar reorder) and at the config.yaml escape hatch. The plan's control list (`bool/enum/string/color`) deliberately omits these kinds; their editing UX already exists where the entities live.
- **Modified-from-default indicator**: each row compares `value` against the registry `default` per kind (`default` is the text form; `null`-equals-empty for unset scalars, `{}`/`[]` for nested) and renders a modified dot — the shortcuts panel's own-default-vs-override dot is the visual precedent (`resolveBindings` `isDefault` comparison). No reset-to-default action is added in this change (the escape hatch and `null`-unset POST exist; a per-row reset is a natural follow-up).
- **`requires restart` badge**: every `live: false` row (`tmux_conf`, `log_level` after the §1 flip) renders a small badge driven directly by the GET payload's `live` flag — no frontend key list.
- **`ui` flag honored**: rows render only for `ui: true` entries (all 12 today; the flag is served as data — Phase 2 intake assumption 6).

### 5. Writes: generic POST, routed through existing context setters where they exist

- `api/client.ts`: the private registry helpers are exported for the pane — `SettingsEntry` (`client.ts:1022`, gains `options?: string[]`), `getSettingsEntries()` (`:1034`, keeps `deduplicatedFetch`), and `postSettings(patch)` (`:1062`). The 13 per-key wrappers (`:1071-1163`) stay untouched — their consumers (theme/accent/name contexts, sidebar) keep working.
- Keys with an existing optimistic context/setter write through it, so in-tab consumers repaint exactly as today: theme via `setTheme` (`theme-context.tsx:167`), `instance_color` via `useInstanceAccent().setColor`, `instance_name` via `useInstanceName().setInstanceName`. Keys with no context (`auto_name`, `ssh_host`, `log_level`, `tmux_conf`) POST via `postSettings` and update the dialog-local list state; a backend 400 surfaces inline on the row (the `TextSetting` contract).
- Failed writes toast per the existing convention; the 400-propagation contract (`throwOnError` shape) holds.

### 6. 'Edit in config.yaml' escape hatch

A footer row on the All-settings tab: renders the constant path `~/.config/run-kit/config.yaml` (a displayable constant *by design* — the Phase-1 fixed-root decision means no API is needed to resolve it) with a copy-to-clipboard button (`lib/clipboard.ts` `copyToClipboard`, the palette version-action precedent at `use-global-palette-actions.ts:322`) and a one-line hint that map/list keys and comments are edited there. **No open-in-editor mechanism is added**: `POST /api/open` validates against the session-derived exact-match allowlist (`api/open.go:122-125` — config.yaml would 400), and building a bypass is new backend surface the invocation forbids. The editor-deeplink composition (`lib/open-in-app.ts:38-42`, needs a resolved SSH host) MAY be layered on where resolvable — plan decides; display+copy is the required baseline.

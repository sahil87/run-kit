**Decisions of record carried from the plan and the design study** (not re-opened here):

- The **one-input rule stands**: the compose seam in `lib/quake-terminal.ts` (`useOperatorCompose`, `setOperatorComposeText`, `sendOperatorMessage`, `attachOperatorFiles`) remains the single draft/send/error owner. Only *where its one view renders* moves: into the drawer while `open`.
- While the drawer is open the launcher **collapses to glyph + chord (state dot kept)**; it does not disappear. The page heading returns to the top-bar center cell.
- Chrome rows consolidate: segments and meta share **one header row**. Hiding the operator session's tmux status bar is **parked** (per-session `status off` would strip it from full tty views too).
- A **pin** (`⌖`) suspends only the outside-click collapse; ⌘J, Esc and ▼ still collapse. Pin is ephemeral component state (Constitution IV: no URL, tmux, or localStorage write).
- Glass default **0.90 → 0.95** (Study F: the bleed drops below the reply text's contrast floor while the glass still reads "overlay").
- Non-goals: mobile (the navigation arm and the operator route's own compose strip stay the mobile input); the tmux status bar; any change to the templated-vs-direct send fork.

## Why

**Problem.** Today the desktop quake terminal has its input at the top (the quake launcher in the top bar) and the reply at the bottom (the embedded operator terminal inside the drawer, whose own `>` prompt sits up to a drawer-height away). Study A of the design study annotates the consequence: two prompt-shaped things on screen, one live; the eye travels top-bar → drawer body → top-bar for every exchange; the TUI's cursor invites typing it cannot receive. On top of that the launcher morph steals the center cell from the page heading while the machine is engaged (md–lg), the drawer spends two chrome rows (title strip + segment strip) plus a conditional status row before any reply is visible, an outside click always collapses the drawer (right for a peek, wrong for the "read the operator while typing in the pane below" case the drawer is best at), and at α 0.90 busy pane output bleeds through under the reply text.

**If we don't.** Every operator exchange keeps paying the top-to-bottom eye line; the drawer keeps losing a row of reply to chrome; users who want to keep the reply on screen while working in a pane have no way to hold it; the glass stays marginally too transparent for reading. Change 3 (the operator page, where the same compose strip docks under the tty tile full-screen) is built on this change's docked strip, so the drawer and the page would otherwise diverge.

**Why this approach.** The docked strip is the exact idiom every terminal route already uses (`compose-strip.tsx`: prompt → compose → reply, all at the bottom), so the drawer becomes a peek of the same shape the operator page will wear (plan Change 3). Because draft, in-flight flags, error and the send fork are already module state in `lib/quake-terminal.ts`, relocating the view costs no second compose implementation: the launcher keeps its role as the standing affordance and re-focus target, the drawer gains the input. Rejected: keeping the compose in the top bar (the status quo); a second in-drawer compose with its own state (the original one-input rule's rejected fork: two drafts, two error surfaces); persisting pin (Constitution IV; a pin on a closed drawer is meaningless).

## What Changes

All changes are desktop-only. The drawer JSX lives below the `if (!rendered || isMobile) return null;` guard (`quake-terminal.tsx:723`), the launcher self-gates at `quake-launcher.tsx:183`, and the mobile arm of the seam listener (`quake-terminal.tsx:336–380`) navigates to the operator route and writes the route strip's draft store, never `useOperatorCompose` — so nothing below perturbs mobile.

### 1. Docked compose strip (in `components/quake-terminal.tsx`)

While `machine === "open"` the drawer renders, as its last flex child above the grips (the grips are absolutely positioned and straddle the border; the strip sits inside the border, so the bottom grip, its tongue tab, and both corners are unaffected), a **compose strip** with wrapper `data-testid="quake-terminal-compose"` and class `border-t border-border shrink-0`. Top to bottom:

1. **Status line** — rendered only while `compose.error || compose.sending || compose.uploading` (the same predicate as today's `quake-terminal.tsx:874`), directly above the header row. Error: `<span role="alert" data-testid="quake-terminal-error" className="text-signal-red">`; else `<span data-testid="quake-terminal-uploading">{sending ? "sending…" : "uploading…"}</span>`. **The top-edge status row (`quake-terminal.tsx:874–886`) is removed** — the status has one home, at the eye line above the input (Study B).
2. **Header row** — `◉ → operator` label (the `◉` is `OperatorStateGlyph` from the launcher, extracted to a shared export so it carries the same live-state dot: `OPERATOR_STATE_DOT` colors, `data-testid="quake-terminal-compose-state"`), then `<OperatorContextChip server={server} compact />` (the chat-lane chip, `data-testid="quake-terminal-context"`, unchanged component), then right-aligned key hints in `text-text-secondary text-[10px]`: `Enter sends · ⇧Enter newline · Esc back to terminal` (`kbd`-free plain text; the effective ⌘J chord keycap stays on the collapsed launcher, not here).
3. **Textarea** — `<textarea data-testid="quake-terminal-compose-input" aria-label="Ask the operator" rows={1} placeholder="Ask the operator…">` bound to the shared store: `value={compose.text}`, `onChange → setOperatorComposeText`. Key handling reuses the route strip's `classifyComposeEnter` (`lib/compose-keys.ts:69`): `submit` → `e.preventDefault()`; ignore an empty/whitespace draft; `void sendOperatorMessage(server, target, value)`; focus stays in the textarea (Enter sends, focus retained — the launcher's `quake-launcher.tsx:266–273` semantics); `insert-line` (⇧Enter) inserts a newline. Auto-grow follows the route strip's bounded idiom (`compose-strip.tsx:170,412–430`: height tracks `scrollHeight` up to `MAX_TEXTAREA_ROWS = 6`, then internal scroll) — lift the constant/measure helper into a shared place rather than duplicating it. File paste/drop inside the drawer keeps routing through `attachOperatorFiles` (unchanged; the strip is inside the `data-quake-terminal` root, so the route terminals' paste forward still skips it).

**Engaged chrome.** A single `engaged` flag says the compose owns input right now: true while the textarea has real focus; a blur whose `relatedTarget` lies inside the strip wrapper does NOT clear it (the launcher's carve-out at `quake-launcher.tsx:249–265`, for the same reason: the chip's ✕ click must land). While `engaged` the textarea carries `border-accent-green` (else `border-border`), and the collapsed launcher (§2) carries the same accent border. The flag must be readable from BOTH trees (the strip in the root-layout drawer, the launcher in the top bar) — publish it as a module slot in `lib/quake-terminal.ts` (`setQuakeComposeEngaged` / `useQuakeComposeEngaged`, the machine-state slot idiom at `:426–460`) or derive it in each consumer from `focusin`/`focusout`; apply picks, the contract is one flag, one truth. Pinned-and-unfocused, the strip drops its accent border: chrome never claims focus it lacks (Study E).

**Focus-on-open and the two invariants move here.** Today the launcher's machine-follower effect (`quake-launcher.tsx:152–181`) captures the restore origin at `rest → open`, focuses+selects the launcher input, and on `open → rest` restores focus only if the launcher input is still `document.activeElement`. After this change:

- Entering `open` **focuses the docked textarea** (and places the caret at the end of any existing draft — a draft typed into the standing box before the machine opened is already in the store, so it appears in the textarea; nothing is lost because both views write `setOperatorComposeText`). The textarea mounts with the drawer, so the focus call runs after mount (an effect keyed on `machine` inside the drawer, or a module-registered input ref the launcher's effect targets — apply picks).
- **Invariant (a), origin capture excludes the compose's own wrapper**: the origin is kept only when `document.activeElement` lies outside every quake-terminal-owned element — use `isQuakeTerminalTarget(origin)` (`lib/quake-terminal.ts:668`), which covers both the launcher wrapper (`boxRef`, `data-quake-terminal`) and the drawer root. A mouse entry focuses the launcher input BEFORE `onFocus` transitions the machine, so an unguarded capture would name the box.
- **Invariant (b), the return is ownership-gated**: on reaching `rest` the effect takes no focus action unless the docked textarea (or another quake-terminal-owned element) is still `document.activeElement`. **The check must observe ownership while the drawer is still mounted** — the drawer is mounted through the exit slide (`QUAKE_SLIDE_MS = 240`, `finishClose` at `:259`), so an effect that runs on the `rest` transition (before `finishClose` unmounts) sees the textarea; an effect that ran after unmount would see `document.body` and wrongly skip the restore. The restore origin ref (`restoreFocusRef`) therefore lives somewhere reachable by both the entry capture and the exit check — a module slot in `lib/quake-terminal.ts` beside the machine state, or kept in the always-mounted launcher with the drawer reporting ownership; apply picks.
- The launcher's own `onFocus → open` (`quake-launcher.tsx:243–248`) stays: clicking or tabbing into the standing box opens the drawer, and the focus-on-open then moves focus to the docked textarea (the box collapses under the pointer by design — Study B: "the glyph stays as a click target that re-focuses the docked compose").

Existing rule kept: focus movement alone never changes the machine (`onBlur` never steps it); a click into the embedded terminal keeps `open` and the keystrokes reach the tmux pane (the yield is the compose declining to act).

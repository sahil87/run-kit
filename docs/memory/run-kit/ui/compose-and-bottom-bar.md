# run-kit UI — Compose & Bottom Bar

## Bottom Bar (Shell-level, Shared Across Routes)

Single row of `<kbd>` styled buttons — a **coarse-pointer-only** surface (`260814-ldbs`). On **fine pointers `BottomBar` does not render at all**, at either site (the AppShell footer and the `board-page.tsx` twin — both arrive via Shell's `bottomBarChildren` slot; Shell renders the `<footer gridArea:"bottombar">` wrapper itself, so the empty footer collapses the `auto` row to zero height — the PR #598 no-reserved-height property: the render gate, the bar's own 3px-seam + min-48px frame, and every effect live behind ONE predicate, `if (!coarse || composeFocused) return null`). The gate is the shared coarse-pointer seam (`useCoarsePointer()` — pointer TYPE, deliberately not viewport width), and the device rule is **coarse = the mobile experience everywhere**: `useIsMobile()` is width-OR-coarse, so a coarse desktop-width device (an iPad) gets the mobile grid, this bar verbatim, the drawer PANE/HOST panels, and NO status bar — the status bar exists exactly where the desktop grids exist (`!isMobile`; § status-signals.md → Status Bar). On coarse pointers the bar renders its full form: at shell level via `<Shell>`'s `bottombar` grid area on every route that mounts `<Shell>` — single-terminal, board, and tmux Server (no-window) alike; width tracks the content column (page width minus sidebar); styled with `border-t-[3px] border-border` (the 3px structural seam — see § Border-Width System) and `px-1.5 min-h-[48px]` — min-h, never a fixed height: the frame content-grows past 48px where the coarse safe floor needs room (61px keyboard-collapsed, 51px kb-open; a fixed frame clips the floor against the app-shell's `overflow: hidden` — § Mobile Responsive → Safe-Area Insets). Layout: `Tab Ctrl Alt Fn▴ ArrowPad | ⌘K a▏ ⌨`. The hostname is shown in the sidebar Host panel, not the bottom bar; Escape lives in the Function key dropdown's extended-keys section. The `a▏` button (conditionally rendered when `onOpenCompose` is provided) is an `aria-pressed` accent toggle for the docked compose strip (§ Docked Compose Strip), not a modal trigger. On fine pointers the `⌘K` palette hint and the `a` compose hint live in the status bar's right cluster instead — the status bar's `a` is the desktop compose **opener**, and the expanded strip carries an `a|` **close** affordance beside the attach (📎) button so open and close live in one visual family (the `compose-toggle` chord and palette entry work everywhere). The key chips, Surfaces chip, and scroll-lock are touch-only and simply don't exist on fine pointers. (`260509-17m3`, `260702-6m46`, `260811-0f3d`, `260814-ldbs`)

`BottomBarProps` contains no `wsRef`. Input handlers read `focused?.wsRef` from `FocusedTerminalContext` and send ANSI escape sequences through it. The component is byte-identical across single-terminal and board routes (same JSX, same callbacks: `onOpenCompose`, `onFocusTerminal`, `onScrollLockChange`) — board panes are terminals, so the input toolbar applies identically. When `focused === null` (Dashboard route, no active terminal), input handlers natural-no-op via the existing `wsRef.current?.readyState !== OPEN` guard — no error, no toast.

**Compose-focus hide (coarse only).** While the compose strip's textarea has focus on a coarse pointer, `BottomBar` does not render — it early-returns `null` when `useCoarsePointer() &&` the compose-focus flag is set, and returns on blur or strip unmount (Escape blurs the textarea — the strip's focus contract — so the restore has a clean seam; tapping the terminal or dismissing the keyboard blurs likewise). The focus signal is a **module store in `lib/compose-strip-events.ts`** (`setComposeStripFocused` / `isComposeStripFocused` / `subscribeComposeStripFocus` — the file's module-slot pattern, alongside the attach queue, the focus-on-open flag, and the focus registry): the strip publishes from the textarea's `onFocus`/`onBlur` and clears on unmount (a strip toggled off while focused restores the bar), with the mount effect **syncing from `document.activeElement`** rather than relying on `onFocus` alone — under `<StrictMode>` the effect replay clears the flag after focus-on-open already focused the textarea, and no new focus event fires. `BottomBar` consumes the store via `useSyncExternalStore`, so both footer mounts (AppShell `app.tsx` and the `board-page.tsx` twin) inherit the behavior with zero footer wiring (§ Design Decisions → Compose-focus signal is a module store). Hiding is by **unmount, not display-level `hidden`**, so the armed-modifier capture-phase `keydown` listener is torn down while composing and cannot intercept keystrokes typed into the textarea (§ Design Decisions → Bottom bar hides by early-return). Fine pointers never render the bar at all (the pointer gate above), so this hide path is coarse-only by construction. The hide/show changes footer height, which the terminal container's existing `ResizeObserver` picks up → `fitAndSync` on every focus change — the same reflow class as toggling the strip itself. (`260814-ink6`)

**Modifier toggles** (Ctrl, Alt): Sticky armed state with visual indicator (`accent` bg). Click to arm, auto-clears after next key is sent. Click again while armed to disarm. Multiple modifiers can be armed simultaneously. No Cmd (`⌘`) toggle — on desktop users hold the real Cmd key; on mobile Cmd combos aren't used in terminal workflows.

**Armed modifier bridging**: When modifiers are armed, a capture-phase `keydown` listener intercepts physical keypresses and translates them to terminal escape sequences (Ctrl+letter → control characters, Alt → ESC prefix). Sends via WebSocket, preventing xterm from receiving the unmodified key. Ignores real Cmd/Ctrl/Alt held by the OS.

**ArrowPad** (`arrow-pad.tsx`): Combined directional pad replacing individual arrow buttons. Sends ANSI escape sequences (`[A/B/C/D`). With modifiers, use xterm parameter encoding (`[1;{mod}X`). Modifier parameter: 1 + (alt?2:0) + (ctrl?4:0).

**Function key dropdown** (F▴): Opens a combined popup above the button. Top section: F1-F12 in a 4-column grid. Divider (`border-t border-border`). Bottom section: Esc, PgUp, PgDn, Home, End, Ins, Del in a 3-column grid (3x3, 7 items). Escape uses `sendSpecial` (preserves Ctrl re-arm semantics); other extended keys use `sendWithMods`. Closes after each selection, on outside click, or on Escape.

**Special keys** (Tab in bottom bar, Esc in Fn menu): Direct send via `sendSpecial`. Ctrl is not consumed for Esc/Tab (Esc IS Ctrl+[, Tab IS Ctrl+I in terminal semantics) — Ctrl stays armed for the next key. Alt prefix with ESC (Meta convention).

**All buttons**: 33px min-height / 35px min-width on fine pointers (`min-h-[33px] min-w-[35px]` — reduced from 36×36 to give the row air), full 36×36 touch target on coarse pointers (`coarse:min-h-[36px] coarse:min-w-[36px]`). Row gap is `gap-1.5` (6px) on fine pointers, `coarse:gap-1` (4px) on touch — so the 375px single-row budget is byte-identical to before. `text-xs`, `<kbd>` element styling. The row's vertical padding is asymmetric — `pt-1.5` with the bottom arm reading `var(--bottom-bar-pad,0.375rem)`, a `globals.css`-owned property: `max(floor, env(safe-area-inset-bottom))` while the keyboard is collapsed (6px everywhere except coarse pointers, where the floor rises to 1rem to clear the phone's corner-arc/home-indicator zone), floor-only under `html.kb-open` so neither arm holds height above the keyboard (§ Mobile Responsive → Safe-Area Insets). The floor renders as real screen gap only because the surrounding frame is `min-h-[48px]` and grows with the row — the frame's height is derived from the row's own paddings, never fixed (`260816-4v2o`).

**Chip tooltip chords** (`260801-mqim`): the `a▏` Compose and `⌘K` palette chips carry **registry-resolved** `kbd` chips in their tips — `BottomBar` consumes `useKeybindings()` once and a local `chordFor(actionId)` helper applies the shared enabled-else-`undefined` derivation (§ Tier-1 `Tip`) for `compose-toggle` and `command-palette`. So the palette tip reads ⌘K on a mac and `Ctrl+K` on Windows/Linux, and both reflect overrides. **The ⌘K chip's own button FACE is the literal `⌘K` glyph on every platform** — the glyph is the chip's identity, not a chord claim; only the tooltip resolves. The remaining non-registry `kbd` strings in this area are the compose/chat submit (`composeSubmitKeycap()` → `⌘Enter` / `Ctrl+Enter`) and the per-surface Insert chips (`Enter` on the strip, `Alt+Enter` in chat), editing chords the registry does not own.

**Focus preservation**: All bottom bar buttons that send terminal input or toggle modifier state have `onMouseDown={(e) => e.preventDefault()}` via a shared `preventFocusSteal` handler. This prevents the browser from shifting focus away from xterm.js's hidden textarea when buttons are tapped, keeping the on-screen keyboard visible on iOS/touch devices. The CmdK button is excluded (it intentionally opens a dialog that takes focus). The ArrowPad handles focus preservation independently via its own `onMouseDown` handler.

### Docked Compose Strip

`ComposeStrip` (`components/compose-strip.tsx`) is a single **global**, sticky text-input surface mounted at exactly one of two docks — in-tile on the desktop terminal route, the shell footer otherwise (next paragraph). It is a plain `<div>` — no backdrop, no `role="dialog"`/`aria-modal`, no focus trap, no Escape-closes, no close-on-send, no terminal dimming. A real `<textarea>` gives IME/dictation (xterm is a `<canvas>`, so the OS has no text input to attach to) and a stable home for pasting large text blocks over a laggy relay. Autocorrect, autocapitalize, and spellcheck are explicitly OFF on it — the text goes to a shell, where rewriting a path or a flag is a bug.

**Two docks — one mount predicate in `app.tsx`.** The strip renders at exactly ONE of two docks, selected by `inTileDock = composeStripEnabled && !isMobile && !!windowParam && !selectionBroadcastKeys && layout.order.includes("tty")`. The **in-tile dock** hosts the desktop terminal route's single-send mode: `app.tsx` hands one shared `<ComposeStrip>` element to `SurfaceLayout` as the opaque `ttyDockContent?: React.ReactNode` prop, rendered as the last child of the FIRST tty tile's flex column (the slot holding `wsRef`/`focusRef` — the registered focused terminal; a duplicate-tty layout hosts it in the first tty tile only), below the terminal body and inside the tile frame, so the tile's zoom/hide/close carries the strip with it and containment makes the send target self-evident. The terminal body shrinks and its existing ResizeObserver-driven fit refits — the same growth-drives-refit mechanic the footer row has always used (260718-dhdj), no new resize plumbing. The **footer dock** (the shell footer's full-width row immediately **above** the bottom-bar keys; the `board-page.tsx` footer mount is independent) keeps everything a tile cannot host: **selection broadcast** (a shell-level, cross-window concern — the dock split IS the mode signal: in-tile = sends to this terminal, footer = broadcast), the **board route**, **mobile** (no tile chrome), and **no-tty layouts** (`single:code`) as the fallback preserving send-to-window. Exactly one dock renders at a time (the footer mount gates on `composeStripEnabled && !inTileDock`), and one component over the module-global draft store serves both, so a dock flip (broadcast on/off, layout gaining or losing its tty tile, window switch remounting the keyed `SurfaceLayout`) loses no draft text, attachment path lines, or sent history. (`260813-j3jb`)

**Layout forks on pointer type.** The input surface below the header row forks on `useCoarsePointer()`, both branches built from shared element descriptors (`textareaEl`, `attachChip`, `sendChip`, …) so each control's props live in one place and exactly one branch renders. **Fine pointers keep the two-row stack** — a `flex flex-col gap-1.5` with **row 1** the `<textarea>` alone at `w-full` and **row 2** a `flex items-center gap-1.5` button row holding 📎 at the left and an `ml-auto` group carrying Insert + Send at the right (the `ml-auto` container, not a spacer, leaves the Tip-wrapped Insert/Send buttons untouched). **Coarse pointers collapse to ONE bottom-aligned row** (`flex items-end gap-1.5`): 📎 · textarea (`flex-1 min-w-0`) · ⏎ · Send — the flanking chips bottom-align so a grown textarea rises above them; the **Insert button is dropped on coarse** (the mobile return key already performs insert-line — `enterKeyHint="send"` per `classifyComposeEnter` surface `"strip"`), and the `Uploading…` status (its header home folded away — next paragraph) relocates into this row immediately left of Send, mirroring the header's uploading-left-of-× grouping. The textarea's **`rows` attribute forks** — `1` on coarse, `2` on fine — and the bounded auto-grow (`MAX_TEXTAREA_ROWS = 6`, scrollHeight-based `resize()`) treats that box as its **floor** by construction (the `height = "auto"` measurement resolves to the `rows` attribute), so the strip opens at one line on touch, grows to six rows, and settles back to one when emptied; fine pointers keep the two-row floor. (`260724-2bmy`, `260814-ink6`)

**Coarse header fold + the ⏎ local-newline chip.** On coarse pointers in normal terminal-target mode the `→ {target}` header row does not render (`showHeader = !coarsePointer || isSelectionTarget || !hasTarget`) — with one visible pane it carries no unique signal: the target name folds into the textarea placeholder (`→ {name}…`), and the × close drops with it (closing stays lossless via the module draft store; the `a▏` chip, the `View: Text Input` palette action, and the ⇧⌘E chord remain). The header **must return** whenever it carries real signal — **selection-broadcast mode** (`→ N selected`, with its `Sending…`/uploading affordances and ×) and the **disabled no-target state** — and renders unconditionally on fine pointers. The **⏎ chip** (coarse only, between the textarea and Send; `aria-label="Insert newline"`, `data-testid="compose-strip-newline"`, `preventFocusSteal`, the strip's secondary-button vocabulary with both-axis coarse touch targets) is the Shift+Enter local-newline path mobile keyboards cannot produce — a local edit, never a send: `insertTextAtCaret(textarea, "\n")` rides the shared undo-safe helper in `lib/readline-keys.ts` (`document.execCommand("insertText", …)` with the prototype-value-setter + bubbled-`input` fallback), and the resulting `input` event reaches the textarea's `onChange`, which ends any recall walk and writes the store — the draft persists and auto-grows exactly as if typed, caret after the newline. The chip is **hidden (not disabled) in selection-broadcast mode**, where the chat Enter policy already makes plain Enter a local newline; elsewhere it is enabled whenever the textarea is usable (a bare newline on an empty composer is a legal local edit that transmits nothing). `classifyComposeEnter` and `enterKeyHint` are untouched. (`260814-ink6`)

**Two distinct send paths** (do not conflate): the compose strip rides the **relay WebSocket as raw bytes** — a submit sends `text + "\r"`, an insert-line sends `text + "\n"`, a raw insert sends bare `text` (no trailing byte), over the focused terminal's `wsRef` (the muxed RelayMux stream, same path as BottomBar keystrokes), no backend endpoint. The **chat-send** path is entirely separate — `POST /api/windows/{id}/chat/send` with named-buffer paste + NOVELTY echo probe + probe-and-submit-gated Enter + per-`(server,paneID)` lock (see [chat](/run-kit/chat.md) § send path). Compose does NOT use that machinery. The two surfaces DO share the keydown layer — one surface-parameterized `classifyComposeEnter` Enter policy plus one `handleReadlineKey` editing layer — but not the delivery mechanism, and not plain Enter's meaning (§ Send semantics).

**Toggle + persistence.** The strip's enablement is the `composeStripEnabled` chrome preference (ChromeContext, `localStorage["runkit-compose-strip"]`, `"true"` sentinel — the `terminalFontSize`/`fixedWidth` pattern; see § Terminal Font Size). Parity affordances flip it via the SAME `toggleComposeStrip()` action: the ⇧⌘E / Shift+Ctrl+E `compose-toggle` chord (§ Keyboard Shortcuts — `ignoreInputs`, so it also closes the strip from inside the strip's own textarea; mounted on both AppShell and the board twin), the bottom-bar `a▏` chip (coarse pointers only — the bar itself is pointer-gated, § Bottom Bar; `aria-pressed={composeStripEnabled}` + the ctrl/alt pressed-state vocabulary `bg-accent/20 border-accent text-accent` when on, `text-text-secondary` off; the face's `▏` bar blinks while on — `rk-compose-caret`, reusing the `rk-caret-blink` cadence, static-but-visible under `prefers-reduced-motion` because the bar is the chip's face, not a flourish (`260813-z84r`); `preventFocusSteal` preserved), the status bar's `a` hint (the desktop opener, `260814-ldbs` — § status-signals.md → Status Bar), the `View: Text Input` palette action, an **`a|` close affordance** beside the attach (📎) button in the expanded strip (`data-testid="compose-strip-a-close"`, `aria-label="Close compose strip (a|)"`, `rk-glint` bordered secondary-button vocabulary, `preventFocusSteal` — `260814-ldbs`; with the bottom bar gone on fine pointers, opener and closer live in one visual family), and an **on-strip × close button** in the strip's own header row (`data-testid="compose-strip-close"`, `aria-label="Close compose strip"`). The × is a **pointer convenience** only — the chip and palette already satisfy Constitution V, so it adds no new keyboard shortcut. It consumes `toggleComposeStrip` from `useChromeDispatch()` *inside* `ComposeStrip` (not threaded as a per-route prop), so every dock inherits the close affordance with zero per-route work. It sits at the **far right** of the `→ {target}` header row, grouped with the conditional "Uploading…" status in a single `ml-auto` flex container so the × stays right-aligned whether or not the upload status renders (uploading immediately left of it). It follows the strip's secondary-button vocabulary (`rk-glint`, bordered, `text-text-secondary`, hover `border-text-secondary`, compact `text-xs`/`px-1.5 py-0.5 leading-none`), carries `onMouseDown={preventFocusSteal}` like every other strip button, and takes the coarse-pointer touch treatment on **both** axes (`coarse:min-h-[36px] coarse:min-w-[36px]` — a bare × has no horizontal padding, so it needs `min-w` too, unlike the wider padded buttons that use only `min-h`; NOT the tiny 16px attachment-remove `×` pattern). Closing needs **no confirmation** — it is lossless because the draft (text + attachments) lives in the module store under its target's key and survives toggle-off/on (see **Drafts are per-target and survive refresh**). The caller gates the mount (`{composeStripEnabled && <ComposeStrip />}` in `app.tsx` and `board-page.tsx` footers). Toggling grows/shrinks the footer grid row by the strip's height, which the terminal container's existing `ResizeObserver` picks up → `fitAndSync` (FitAddon `fit()` + tmux resize) — the same reflow class as a font-size change; no dedicated refit effect.

**Live target.** The strip sends to the **currently-focused** pane's `wsRef` from `FocusedTerminalContext`, read live at send time — never a target snapshotted at open. A persistent surface that outlives many focus changes would, with a frozen target, silently send to a stale/closed pane. The wrong-pane risk is instead mitigated by an always-visible `→ {window}` target label, resolved in layers: window-store name by `server:windowId` (live — tracks renames) → the `windowName` the registrant carried into `FocusedTerminalContext` (board entries have a server-derived `windowName`; the store only covers servers whose sidebar group has delivered sessions, so board panes from other servers would otherwise label as `@N`) → raw windowId. With `focused === null` (e.g. the `/$server` tiles route) the strip renders **disabled** with a "no target" label and never sends; its placeholder reads `No focused terminal — click a pane to target it` (both pointer types — the clause names no chord, § Education micro-copy). The terminal-target placeholder is itself an education surface: `Compose text — Enter inserts · {submitKeycap} sends · ↑ history` on fine pointers (the sole surfacing of ↑ sent-history recall anywhere in the UI) and `→ {name}…` on coarse — the target name folded in from the header row the coarse presentation drops (§ Coarse header fold + the ⏎ local-newline chip). `{submitKeycap}` resolves via the shared `composeSubmitKeycap()` seam (the fixed Enter-policy chords are classifier-owned, not registry bindings).

**Selection-broadcast target — the one FROZEN mode.** The optional `selectionTarget?: {keys, onSend}` prop (`ComposeSelectionTarget`) puts the strip in a second, explicit target mode, fed by `Selection: Send prompt to N agents` (§ Selection palette commands). While `keys` is non-empty the strip labels itself `→ N selected` instead of the focused window, keys its draft to the frozen recipient set, and submits through `onSend(text)` rather than any `wsRef` — the only mode where the target is snapshotted rather than read live (§ Design Decisions → Broadcast recipients are frozen). It is **submit-only**: `send()` early-returns for every non-submit mode, so the Insert chip is disabled (`canInsert` is false in selection mode) and Alt+Enter's raw insert is left NATIVE rather than consumed into a silent no-op; the 📎 upload button and the drag-drop/paste attach path are disabled too (`canUpload` gates them separately from `hasTarget`, since cross-server recipients share neither a websocket nor a worktree). Enter policy follows suit: the keydown calls `classifyComposeEnter(…, "chat")` in selection mode, so **plain Enter is a local newline**, Cmd/Ctrl+Enter and the Send button are the only submits, and `enterKeyHint` reads `"enter"` — the surface parameter is what diverges, never a fork of the classifier's policy at this call site. Send is gated on non-empty text (`canSubmit`) and on a `selectionSending` in-flight flag that also relabels the chip `Sending…`, so a second Enter cannot double-broadcast. The `aria-label` becomes `Compose prompt to send to selection` and the placeholder `Compose prompt — {submitKeycap} sends to all selected` on fine pointers (the short `Compose prompt…` on coarse — § Education micro-copy; broadcast takes the chat Enter policy, so the placeholder names `{submitKeycap}` as the sole submit). Clearing is the one behavior that is **not** unconditional here: `onSend` resolves with the DELIVERED recipient count, and only a non-zero count pushes sent history and clears the draft — a `0` (nobody received it) keeps the composed prompt, and an unexpected rejection escaping the executor is caught and likewise preserves it (§ Design Decisions → A broadcast clears its draft on DELIVERY). (`260808-ebgs`)

**Send semantics — Enter transmits a line, Cmd/Ctrl+Enter submits.** The keydown routes through the shared pure `classifyComposeEnter(key, surface)` (`lib/compose-keys.ts`) — the SAME classifier the chat send form uses, called here with `surface: "strip"`. One classifier remains the single authority for both surfaces' Enter policy, but the two **deliberately diverge on plain Enter**, and the divergence is declared inside the classifier per surface, never forked at a call site (see § Design Decisions → Enter transmits a line in the strip, composes in chat, and [chat](/run-kit/chat.md) § Send-form input box). The classifier takes key state + surface alone — Enter policy is pointer-independent, so it reads no pointer hook — and stays text-agnostic (empty-text policy lives at the call sites). `send(mode)` takes `Exclude<ComposeEnterAction, "default">` and delivers over the focused terminal's `wsRef`, guarded on `draftKey !== null` and `wsRef.readyState === WebSocket.OPEN`:
- **Enter = insert line** — `ws.send(text + "\n")` and clear that target's draft. The strip overlays the VISIBLE terminal, so the transmitted line lands in the pane's own composer where the user can see it (Claude Code treats a raw `"\n"` as newline-insert), and consecutive Enters stage sentence-per-line exactly like typing into the pane. On an **empty or whitespace-only** textarea Enter is a **full no-op**: the keydown is consumed (no local newline appears) and nothing is sent.
- **Shift+Enter = newline** — the ONLY local multi-line compose in the strip.
- **Cmd/Ctrl+Enter = submit** — `ws.send(text + "\r")`; on an **empty or whitespace-only** textarea a bare `ws.send("\r")` ("press Enter in the pane"), which completes the stage-then-submit loop from the keyboard. Whitespace-only counts as empty: the whitespace is discarded, never transmitted, and the draft still clears.
- **Alt+Enter = raw insert** — chord-only. `ws.send(text)` with **NO trailing byte** (byte-exact, for completing a partial line already in the agent's input); empty/whitespace-only is a no-op.
- Precedence (first match wins): non-Enter/IME-composing → default; meta/ctrl → submit; alt → insert; shift → default; plain Enter → insert-line (strip) / default (chat).

Enter is guarded against IME composition (`e.nativeEvent.isComposing`). A `"default"` action falls through to the textarea; every other action gets `preventDefault()` + `stopPropagation()` and is handed to `send(action)` as-is. Clear-on-delivery is uniform across modes — a delivered send clears that target's text + attachments (and revokes its preview URLs) and the strip stays open, including a delivered whitespace-only submit. A **guard-blocked** send (no target / stream not open) early-returns WITHOUT clearing, so the draft is preserved. Terminal-conventional `"\n"` semantics are **accepted and documented in the send-path code comment, not guarded**: on a plain shell pane the transmitted `"\n"` EXECUTES the line — which is exactly what Enter does in a terminal — and an embedded `\n` inside a raw insert executes per line there too, so raw insert is only truly Enter-free for single-line text on non-TUI panes.

**Readline editing chords** (`lib/readline-keys.ts` — shared with the chat send form, the consistency mirror of the shared Enter classifier). The textarea keydown routes through `handleReadlineKey(e.nativeEvent, e.currentTarget)` **before** Enter classification (after the strip's Escape branch), intercepting exactly five chords that browsers/macOS leave unbound: **Ctrl+U** (kill from cursor to line start — readline unix-line-discard, not a whole-line wipe), **Ctrl+W** (delete word backward), **Alt+B / Alt+F** (move cursor word backward / forward), **Alt+D** (delete word forward). Matching is on `KeyboardEvent.code` (`KeyU`/`KeyW`/`KeyB`/`KeyF`/`KeyD`), never `key` — on macOS Alt+B/F/D compose `∫`/`ƒ`/`∂` into `key`, so key-based matching would miss exactly the chords the layer exists for. Modifier matching is exact (Meta or Shift anywhere → unhandled; Ctrl chords reject Alt and vice versa) and IME-composing keydowns are never intercepted, so the natively-bound Cocoa chords (Ctrl+A/E/B/F/P/N/D/H/K/T/O/Y, Opt+arrows, Opt+Delete) pass through untouched. Word boundaries are whitespace-delimited (the readline default), crossing newlines; `lineStart` keys on the previous `\n`. Motions use `setSelectionRange`; deletions go through `document.execCommand("delete")` after selecting the range so the native undo stack (Cmd+Z) survives, with a controlled-component-safe fallback (prototype value setter + a bubbled `input` event) when `execCommand` is missing or returns false (jsdom, future removals) — that fallback keeps React state in sync at the cost of undo for that edit. A handled chord calls `preventDefault()` + `stopPropagation()` (so it never reaches global chord listeners) and returns `true`; an **empty** edit range (Ctrl+U at line start, Ctrl+W at position 0) still consumes the chord but performs no edit, because a collapsed-selection `execCommand("delete")` would eat a character backward. Conflict safety: app chords are suppressed while a textarea has focus (`shouldSuppressChord`), the `ignoreInputs` punch-through set (⌘K, ⇧⌘E, ⇧⌘/, ⇧⌘,) does not collide, and Alt chords are excluded from every registry tier (§ Keyboard Shortcuts). The one near-miss is `KeyW`: `kill-window` claims it on the `cmd` (⌘W) and `shifted` (⇧Ctrl+W) tiers — never plain Ctrl+W — so the exact-modifier rule (Meta or Shift → unhandled) is what keeps the two from overlapping rather than luck. **Platform caveat**: on Windows/Linux *browsers* Ctrl+W is browser-reserved (closes the tab before the page sees it) — that binding works on macOS and in the desktop shell only; win/linux web users keep native Ctrl+Backspace. Ctrl+U (view-source) IS interceptable and works everywhere. The pure classification + cursor math (`classifyReadlineKey`, `wordLeft`/`wordRight`/`lineStart`, `readlineMotionTarget`, `readlineDeleteRange`) are exported for mount-free unit tests (the `palette-move.ts` extraction pattern).

**Buttons + truthful `enterkeyhint`.** The two chips share ONE enablement rule on the terminal arm — empty/whitespace-only composer disables BOTH (Send loses its primary fill via `disabled:opacity-40`), non-empty text enables both with Send keeping the primary fill. A secondary **Insert** house-chip (border-styled, `data-testid="compose-strip-insert"`, `aria-label="Insert line"`, `preventFocusSteal`, `coarse:min-h-[36px]`) renders left of Send on **fine pointers** (dropped on coarse — the mobile return key already performs insert-line there, § Layout forks on pointer type) and fires `send("insert-line")` — it follows Enter, so it is disabled when there is no target or the text is empty/whitespace-only (`canInsert`), matching Enter's empty no-op. **Send** fires `send("submit")`, gated `hasTarget && text.trim() !== ""` on the terminal arm (`canSubmit`). The buttons diverge from the Cmd/Ctrl+Enter chord on empty BY DESIGN: the button state answers "is there text to send", while the chord keeps its empty-composer bare `"\r"` send ("press Enter in the pane" — a power-user pane keystroke, and the strip's only path for it); see § Design Decisions → Button/chord divergence on empty is deliberate. Selection-broadcast mode keeps its own rule (text required, Insert always disabled there). Tips: Insert reads `label="Insert line (Alt+Enter: raw insert)"` with `kbd="Enter"` — the chord-only raw insert stays discoverable in the label text, with no native `title` (titles are retired for Tip chips); Send keeps the platform-formatted submit chord from the shared `composeSubmitKeycap()` (`⌘Enter` on mac, `Ctrl+Enter` elsewhere, via `formatCombo({code:"Enter",tier:"cmd"}, detectPlatform())`), so both surfaces render the identical chip. None of these chords are registered in the command palette (focused-textarea editing chords like the unregistered Shift+Enter; the palette steals focus from the textarea it would act on), and Constitution V's keyboard reach is met by the chords themselves. The textarea's `enterKeyHint` is **`"send"`** unconditionally — the truthful hint, since Enter transmits the text to the pane and clears the draft. The Enter policy is pointer-independent — the classifier reads no pointer hook; `compose-strip.tsx` consumes `useCoarsePointer()` for **presentation only** (the coarse placeholder/header fold, single-row collapse, `rows` floor, and ⏎ chip — § Layout forks on pointer type) (`260814-ink6`). (`260802-lj98`, `260813-kvk7`)

**Drafts are per-target and survive refresh.** Every draft belongs to its **addressee**, not to the user: the store (`lib/compose-draft-store.ts`) is a map keyed by the send target's `entryKey(server, windowId)` — the same key the strip's `focusedKey()` computes from the live focused target each render. Switching targets (route change or board pane-focus cycling) swaps the visible draft; each window keeps its own unsent text + attachments, and a delivered send clears only that target's draft. A **selection-broadcast** draft is the one exception to live keying: it keys on `selectionDraftKey(keys)` — `selection:` plus the JSON of the SORTED recipient set — which cannot collide with any `server:@N` window key, so composing a broadcast never overwrites the focused pane's draft. With no target the key is `null`, the store yields a single frozen empty draft, and the key-bound setters no-op (the strip is disabled anyway). The store lives at module scope — not component state — because the mount is conditional (toggle-off unmounts it) AND per-route (the in-tile dock, the AppShell footer, and the BoardPage footer are distinct React subtrees), so component-local `useState` would destroy unsent drafts on toggle-off and on terminal↔board route changes. It is exposed through the same module-slot + listener-set + stable-snapshot pattern as the window-switch pending mask (`window-transition.ts`), read as `useSyncExternalStore(subscribeComposeDraft, () => getComposeDraft(draftKey))`: one **global** listener set (any commit notifies — at most one strip is mounted) over **per-key** stable snapshots, so `useSyncExternalStore` sees an identical object reference while a key's draft is unchanged. Commits notify only on an actual change. (`260718-dhdj`, `260801-cyth`)

**Text persistence — one localStorage key, pruned on every write.** Draft **text** survives a page refresh via `localStorage["runkit-compose-drafts"]`, a JSON map `{[entryKey]: {text, updatedAt}}` written through **synchronously** on every commit and hydrated at module load by the exported `hydrateComposeDrafts()` (also the test-reset seam: `localStorage.clear()` + re-hydrate). The read is tolerant in the `parseOverrides` posture of `keybindings.ts` — malformed JSON, non-object/array roots, and wrong-typed entries degrade to empty/skipped via an `isStoredDraft` type guard rather than an `as` cast — and every localStorage access is `try`/`catch` best-effort, never throwing. One shared `pruneDraftEntries()` helper runs on **both** the write and the hydrate path (no duplicated pipeline): empty-text entries are never stored, entries outside the `MAX_DRAFT_AGE_MS` (7-day) window are dropped — the check is two-sided (`Math.abs`) so a future-dated `updatedAt` from clock skew or corrupted storage ages out instead of sorting first and squatting the cap forever — and only the `MAX_PERSISTED_DRAFTS` (30) newest by `updatedAt` are kept. `pruneDraftEntries` is itself a thin wrapper over the generic `pruneByAgeAndCap(entries, isEmpty, cap)` that both persisted maps share (the sibling sent-history map is the other caller); the wrapper stays because it pins the draft-specific `text === ""` emptiness predicate and the `MAX_PERSISTED_DRAFTS` cap so neither draft call site restates them. Pruning is not optional hygiene: tmux window IDs are **reused after a server restart**, so a stale draft can otherwise point at a stranger. An all-empty map removes the key rather than storing `{}`. Multi-tab is last-write-wins — no `storage`-event sync. (`260801-cyth`, `260806-kadm`)

**Sent history — every transmitted text is recorded per target, one keystroke from recall.** Delivery is unverifiable at all three hops (`ws.send()` only queues bytes and an OPEN socket can be half-dead; the backend's `ptmx.Write` discards its error; the receiving TUI can silently swallow the bytes at a permission prompt or an open autocomplete), so the strip does **not** gate its clear on confirmation — the clear stays unconditional and the send semantics are byte-untouched. Instead the same module (`lib/compose-draft-store.ts`) carries a **second, independent per-target map** under the same `entryKey(server, windowId)`, exposed as `pushComposeSentHistory(key, text)` / `getComposeSentHistory(key)` / `hydrateComposeSentHistory()` (the test seam mirroring `hydrateComposeDrafts()`). Recovery over verification. Newest-first, capped at `MAX_SENT_HISTORY_PER_TARGET` (10) with the oldest evicted. Two push guards: **whitespace-only text pushes nothing** (so the empty-submit's bare `\r` never enters history) and **text identical to the current newest entry pushes nothing** (adjacent-duplicate collapse — the natural retry after a swallowed send must not burn a slot). The **stored** value is the exact untrimmed text — recall must reproduce what was transmitted, so only the guard trims. `getComposeSentHistory` is a plain read returning the live internal array as `readonly string[]` (never a defensive copy — every mutation replaces the array rather than mutating in place, and recall reads at keydown time, so history is deliberately NOT part of the `useSyncExternalStore` seam and a push notifies no subscriber); null/absent keys yield one frozen empty-array identity. (`260806-kadm`)

**History persistence rides a SIBLING localStorage key.** `runkit-compose-sent-history` (`COMPOSE_SENT_HISTORY_STORAGE_KEY`), schema `{[entryKey]: {entries: string[], updatedAt: number}}` — never folded into `runkit-compose-drafts`, so the shipped draft schema, its `isStoredDraft` guard, and its prune pipeline stay byte-compatible and neither surface's corruption can take the other down. Same discipline as drafts otherwise: write-through on every push (best-effort `try`/`catch`, `removeItem` when nothing remains), tolerant-parse hydration at module load through an `isStoredSentHistory` type guard (malformed JSON, non-object/array roots, and wrong-typed entries degrade to empty/skipped — `entries` validated as an array of strings, `updatedAt` as a finite number; no `as` casts on parsed storage), and the **same `pruneByAgeAndCap` helper** on both write and hydrate — targets with empty `entries` dropped, targets outside the shared `MAX_DRAFT_AGE_MS` (7-day, two-sided) window dropped, and the newest `MAX_PERSISTED_SENT_HISTORIES` (30) targets by `updatedAt` kept. The cap is a **sibling constant** of `MAX_PERSISTED_DRAFTS` rather than a reuse, so the two surfaces can diverge later without a rename. Hydration also re-caps each restored target's entries to 10. Window IDs are reused after a tmux server restart, so stale history must not resurrect against a stranger window. Multi-tab is last-write-wins, matching drafts. (`260806-kadm`)

**↑/↓ recall walk — a keydown layer between readline and the Enter classifier.** In the textarea's `onKeyDown`, recall sits after the Escape branch and the `handleReadlineKey` call (which owns no arrow keys — Ctrl+U/W, Alt+B/F/D only — so the composition is clean) and before `classifyComposeEnter`. **Only a BARE, non-composing arrow can recall**: an `isComposing` ↑/↓ navigates the IME candidate list (intercepting it would break the very surface the strip exists to provide, since xterm.js has no IME) and a modified arrow is a native editing motion (Shift extends the selection, Alt/Opt and Cmd are macOS paragraph/document jumps, Ctrl is bound by desktop environments) — the same exact-modifier discipline `classifyComposeEnter` and `classifyReadlineKey` already declare. **↑ is intercepted only when it cannot mean cursor movement**: the textarea is **empty**, or a walk is already in progress (where the visible text is recalled, not composed). A non-empty textarea outside a walk keeps native ↑ untouched — hijacking it would destroy in-progress composition. With no history for the target, ↑ starts no walk and changes nothing. Repeated ↑ steps toward older entries and **pins at the oldest** (no wrap). **↓ is intercepted only during a walk**, stepping toward newer; stepping **past the newest** restores the stashed pre-walk text and ends the walk. **Mid-walk the arrows follow the REPL line-boundary discipline**: a recalled entry can be multi-line, so ↑ steps older only with a collapsed caret on the entry's **first line** and ↓ steps newer only with a collapsed caret on the **last line** — everywhere else (an inner line, or any non-collapsed selection, whose bare arrow is the native collapse motion) the arrow moves the caret natively *within* the recalled text and the walk stays alive, since caret motion is not an edit. A recall step lands the caret at the entry's end (native value-set behavior), so single-line entries — first line == last line — walk straight through on repeated ↑, and the boundary gate is only observable on multi-line entries. An intercepted arrow is consumed (`preventDefault` + `stopPropagation`, mirroring the Enter-action handling so it never reaches global chords); a non-intercepted one falls through untouched. Recalled text is written through `setComposeText(draftKey, …)` — the textarea is store-controlled, so recall persists as the draft and auto-grows exactly as if typed. Recall restores **text only**: the `File` objects were revoked at send and are unpersistable, but their path lines ride the recalled text. (`260806-kadm`)

**Walk state lives in refs; four exits.** The walk is a `recallIndexRef` (steps back from live — `-1` means no walk, `0` selects the newest entry) plus a `recallStashRef` holding the textarea text captured at walk start. Both are `useRef`s, not state: no render reads them (the visible text is store-owned), so an arrow press costs zero re-renders. The walk ends via a shared `endRecall()` on **four** events: stepping past newest via ↓; **any text mutation that is not a recall step** — a user keystroke (`onChange`), an upload's appended path lines (`handleUpload`), or an attachment removal's spliced-out path line (`removeFile`), each of which calls `endRecall()` because leaving the walk armed would orphan the attachment (the next arrow overwrites the text, dropping the path line, while the `File` and its preview chip stay mounted pointing at a path the agent can never resolve); **any send** (so the next ↑ starts fresh from the newest entry, which is the text just sent); and a **target switch**, which fires **eagerly from a `draftKey` effect** rather than lazily at the next keydown — index and stash are meaningless against a stranger target, so a keydown-lazy check would leave an A→B→A round-trip resuming A's stale walk and let B's edits tear down A's stash. Because the teardown is eager, `handleRecallKey` needs no stale-target check: an in-progress walk always belongs to the currently-focused target. Escape keeps its blur-only semantics (the focus contract is unchanged). (`260806-kadm`)

**Push wiring is one line in `send()`.** After the `wsRef.readyState === WebSocket.OPEN` guard passes and immediately **before** `clearComposeDraft(draftKey)`, `pushComposeSentHistory(draftKey, text)` runs for **all three modes** (`submit`, `insert`, `insert-line`), recording the **pre-trailing-byte** text — the transmitted bytes, the clearing behavior, the focus contract, and `classifyComposeEnter` are all unchanged. A **guard-blocked** send early-returns above the push, so nothing is recorded and nothing was cleared (the draft is already preserved). An empty/whitespace-only submit reaches the push but the store's own guard makes it a no-op. Coverage is the two colocated unit-test siblings (`compose-draft-store.test.ts` for the store surface, persistence round-trip, tolerant parse, and pruning; `compose-strip.test.tsx` for the walk, its exits, and the per-mode push) — no Playwright spec, matching how the Enter matrix is tested. (`260806-kadm`)

**Attachments are in-memory per key; blob URLs are per-mount.** `File` objects cannot reach localStorage, so pending attachments live only in the in-memory map under their target's key and a hydrated draft carries an empty attachments array. The loss is cosmetic: uploads are **eager** (already on the target worktree's disk at attach time) and their path lines live in the persisted **text**, so after a refresh the previews and × remove-chips are gone but the path lines and uploaded files remain and sending still works. Blob-URL previews stay component-local (a fresh per-mount `Map<File, string>` ref, recreated lazily via `getBlobUrl` from the retained `File` objects). They are reclaimed at three seams: on unmount, on a delivered send (scoped to the cleared draft's files only — other targets' previews recreate lazily when their draft is shown again), and by a `[files]` effect that revokes URLs for any file no longer in the **visible** draft, so a departed target's URLs cannot strand in the map while the strip stays mounted. (`260801-cyth`)

**Focus routing — focus on OPEN, never otherwise.** Opening the strip focuses its textarea; everything else leaves focus where the user put it. The seam is a module-level **focus-on-open flag** in `lib/compose-strip-events.ts` (`markComposeStripFocusOnOpen` / `consumeComposeStripFocusOnOpen`, the same module-slot shape as the attach queue and focus registry beside it): `toggleComposeStrip()` marks it on the **off→on transition only**, and ComposeStrip's mount effect consumes-and-clears it and focuses. Because every open path funnels through that one toggle — the `a▏` chip, the `View: Text Input` palette entry, the ⇧⌘E chord, the terminal's drag-drop/paste auto-enable, and the board twin — one seam covers them all with no per-affordance wiring. The consume **always clears**, even when the effect declines to focus (the disabled "no target" state), so a stale flag can never grab focus on a later remount. A plain route remount with the strip already enabled never calls the toggle, so it never sets the flag and never steals focus. The rest of the no-steal contract is intact: **after-send never focuses**, and Escape in the textarea blurs it back to the terminal (**never closes the strip** — the × close button does not alter this; only the explicit toggle affordances close it). On mobile, opening summons the IME — desired, matching the ⌨ chip. `preventFocusSteal` (`onMouseDown` preventDefault) is on the Send/📎/Insert/× buttons. On touch devices the ⌨ keyboard button focuses the strip's real textarea when the preference is on, via the **focus registry** in the same module (`registerComposeStripFocuser`/`focusComposeStrip` — a module registry, not a `document.querySelector('[data-testid]')`, since test ids are test-only here; the focuser returns `false` in the disabled "no target" case so `bottom-bar.tsx` falls back to `onFocusTerminal`). (`260801-sm6g`)

**The textarea's `onFocus` also writes per-window focus memory.** Beside the coarse-hide publish, focusing the textarea records `compose` for the window it targets (`recordFocus`, `lib/focus-memory.ts`) — terminal-target mode only (a selection broadcast has no window identity to record against; its draft key is `selection:…`), and gated on the `focusMemoryWindow` prop from `app.tsx` so the write fires only when the strip's live target IS the route window — the focused-terminal context lags a window switch by a commit, so a restore-driven focus in that gap would otherwise cross-write the previous window's key (the gate is a prop, not `useMatches`, because the strip's unit tests mount it without a router). The strip root carries the production `data-compose-strip` marker, which the tty tile's pointerdown focus-memory write reads to skip presses landing inside the docked strip (a re-click on the already-focused textarea fires no focus event, so the skip is what keeps `compose` from being clobbered by `tty`). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (`260815-ltz7`)

**Uploads — eager and worktree-scoped; an attachment never faces a foreign worktree.** The strip calls `useFileUpload(focused.session, focused.windowId, focused.server)` scoped to the **live** focused target, so uploads land in that window's worktree `.uploads/` (backend `upload.go` unchanged — see § File Upload). Because the draft — attachments included — is keyed by that same target, an attachment can only ever be shown alongside the worktree it was uploaded to: changing focus changes the whole draft, so there is **no re-upload, no path rewriting, and no error surface** on a target change (the strip carries no `role="alert"` error state at all). The retained `File` objects back previews only. Terminal drag-drop / clipboard-paste gestures (`terminal-client.tsx`) hand raw files to the strip via a document `CustomEvent` bridge (`COMPOSE_STRIP_ATTACH_EVENT` + a module hand-off queue in `compose-strip-events.ts`, drained on both the event and mount), enabling the preference first if off — no prop-drilling of upload results. The `File[]` overload on `uploadFiles` (`hooks/use-file-upload.ts`) exists for that queue. (`260801-cyth`)

**Board-pane focus cleanup.** `BoardPane` registers itself as the focused terminal while `isFocused`, and clears `FocusedTerminalContext` on **unmount** iff it is still the registered pane (`focusedRef.current?.wsRef === wsRef`, unmount-only `[]` deps, ref-guarded so a sibling's newer registration during a focus cycle is not clobbered). Without it, leaving a board for `/$server` would strand a stale non-null target — the enabled strip would render active with a stale label and upload into the stale worktree. With it, the strip reverts to the disabled "no target" state.

### File Upload

Entry points, all on the terminal page:
- **Clipboard paste** (`Cmd+V` / `Ctrl+V`) — document-level paste listener; files in `clipboardData.files` trigger upload, text-only paste passes through to xterm
- **Drag-and-drop** — drop files onto the terminal area; `ring-2 ring-accent` border highlight during drag-over; non-file drag content ignored
- **Compose strip upload button** (📎) — the left-most chip on the docked compose strip (§ Docked Compose Strip → Layout forks on pointer type); opens native file picker via hidden `<input type="file">`

The paste/drop gestures live in `terminal-client.tsx` and hand raw files to the docked compose strip (enabling the `composeStripEnabled` preference first if off) via the `COMPOSE_STRIP_ATTACH_EVENT` document bridge; the strip uploads them to the **focused** target's worktree and inserts one path per line in its textarea (see § Docked Compose Strip). Server writes to `.uploads/{YYMMDD-HHmmss}-{sanitized-name}` in the target window's worktree. 50MB size limit. `.uploads/` auto-added to `.gitignore` on first use.

### iOS Keyboard Support

`useVisualViewport` hook (`app/frontend/src/hooks/use-visual-viewport.ts`) manages all viewport-related CSS side effects: adds the `fullbleed` class to `<html>` on mount (removed on cleanup), and listens to both `resize` and `scroll` events on `window.visualViewport`, setting `--app-height` (and `--app-offset-top`) CSS custom properties from `visualViewport.height`. The `scroll` listener catches iOS Safari viewport panning that doesn't trigger `resize`. **The hook is called once in `RootWrapper`** so the `--app-height` var is maintained on EVERY route — including the Host page and edge pages that mount no `Shell` — and owning the single idempotent effect at the root avoids the double-mount cleanup race a second copy in `Shell` would create. (`260707-4vq2`)

**Keyboard-open signal — `html.kb-open`.** The same rAF-coalesced `apply()` pass also derives a boolean keyboard-open signal and publishes it as the `kb-open` class on `<html>` (`syncKeyboardSignal`, called from `apply()` and from the initial sync — the hook's only two call sites). It registers **no additional listeners**: the derivation rides the existing `resize`/`scroll` pair, and `width` joins `height`/`offsetTop` in the change guard so a rotation reaches it. Removal is paired with `fullbleed`/`--app-height` in the existing cleanup, and the whole machinery is skipped when `window.visualViewport` is absent (jsdom, old browsers) — no class, no throw. The signal's sole consumer today is the bottom bar's safe pad — it gates both the raised coarse-pointer floor and the `env()` arm of `--bottom-bar-pad` (§ Mobile Responsive → Safe-Area Insets); it is app-wide because the hook mounts at the root, so both bottom-bar render sites (app shell and the board twin) see it for free.

The heuristic: **baseline = the maximum `visualViewport.height` observed since the last `visualViewport.width` change**; the signal is on when `height < baseline − KEYBOARD_DELTA_PX`, with `KEYBOARD_DELTA_PX = 150` (exported constant, `use-visual-viewport.ts`). A keyboard shrinks height without touching width, whereas rotations and window resizes change width — so a width change is the baseline-reset trigger. 150px sits above iOS URL-bar chrome deltas (~50–114px) and below any real keyboard (~260px+). Two accepted limitations, both self-healing: **rotating or split-screen-resizing while the keyboard is open** re-baselines to the keyboarded height and clears `kb-open` until the next keyboard close/open cycle; **mounting with the keyboard already up** likewise reads as closed until the keyboard first closes (which grows the baseline). Both degrade to the 6px base floor, never to a wrong-direction pad. Unit coverage is `use-visual-viewport.test.ts` (mocked `visualViewport` + controllable rAF): baseline-off, keyboard-on, restore-off, sub-threshold chrome delta does not fire, rotation resets the baseline, cleanup removes the class, missing-`visualViewport` mount/unmount is safe, and the listener set stays exactly `resize` + `scroll`. (`260805-fi9m`)

In fullbleed mode, `globals.css` pins the **`.app-root` root layout container** (`position: fixed; inset: 0; height: var(--app-height, 100vh)`) to the visual viewport regardless of document scroll — the pin lives on `.app-root` (not the per-route `.app-shell` beneath it) because the persistent TopBar lives inside `.app-root` above the content region, so pinning that container keeps the header above the content. The per-route `.app-shell` is `position: relative; height: 100%` — it fills the root layout's `flex-1` region (its `overflow: hidden` contains xterm's canvas). (`260707-4vq2`) When the iOS keyboard appears, the bottom bar stays pinned above it, the terminal shrinks, and xterm refits via the existing `ResizeObserver`. The `fullbleed` class is also present in `index.html` as a static default (FOUC prevention); the hook takes over lifecycle management at runtime.

**Keyboard toggle** (`⌨` U+2328): Right-aligned button in the bottom bar, visible only on touch devices (`hidden coarse:inline-flex`). Bidirectional toggle: when terminal is focused (detected via `document.activeElement.closest(".xterm")`), tapping blurs to dismiss the keyboard; when not focused, tapping calls `onFocusTerminal` callback which chains through `app.tsx` → `TerminalClient.focusRef` → `xtermRef.current.focus()` to summon the keyboard. Dynamic `aria-label`: "Hide keyboard" / "Show keyboard". Uses `preventFocusSteal` to avoid stealing focus on the dismiss path.

**Scroll-lock mode**: Long-press (>= 500ms) on the keyboard toggle button activates scroll-lock — a mode that prevents the soft keyboard from appearing when the terminal area is tapped, allowing uninterrupted reading and scrolling. State is the persisted `scrollLocked` chrome preference (ChromeContext, localStorage `runkit-scroll-lock`, default `false`, `composeStripEnabled` idiom) — BottomBar reads and writes it via `useChromeState`/`useChromeDispatch`, and the page shells (app.tsx, board-page.tsx) thread the context value down to every `TerminalClient` as the `scrollLocked` prop. While locked, the terminal container suppresses every xterm focus path with capture-phase listeners — see [terminal](/run-kit/ui/terminal.md) § Scroll-lock focus suppression for the mechanism (touchend/contextmenu/mousedown suppressors + focusin backstop, coarse pointers only). Touch scroll gestures (SGR mouse sequences) are unaffected — only focus is prevented. Activating scroll-lock while the keyboard is visible auto-dismisses it (`document.activeElement?.blur()`). Optional haptic feedback via `navigator.vibrate?.(50)` on toggle (graceful no-op if unavailable).

- **Long-press detection**: `touchstart`/`touchend`/`touchmove` handlers with a 500ms timer (`LONG_PRESS_MS` constant). Touch move > 10px (`LONG_PRESS_MOVE_THRESHOLD`) cancels the long-press. On timer expiry, scroll-lock toggles and subsequent `touchend`/`click` are suppressed via a ref flag. Desktop click behavior is unaffected (touch events only).
- **Tap in locked mode**: Tapping the keyboard button (< 500ms) when `scrollLocked` is `true` unlocks ONLY — it never summons the keyboard (a tap on 🔒 means "stop being locked", not "type now"; the next tap of the now-⌨ chip shows the keyboard as usual).
- **Visual indicator**: When locked, the button shows `bg-accent/20 border-accent text-accent` (same armed-state pattern as Ctrl/Alt modifier toggles) and the icon changes from `⌨` (U+2328) to `🔒` (U+1F512). `aria-label` updates to "Scroll lock on — tap to unlock".
- **State lifecycle**: Persisted and global — the lock survives remounts, terminal ↔ board navigation, and mobile tab reloads, and single-terminal and board routes always agree. A lock rehydrated on a fine-pointer profile is inert (the suppression effect gates on coarse pointer; the chip doesn't render there). The docked compose strip is unaffected — it has its own input field outside the terminal container.

## Design Decisions

### Bottom-bar frame is min-height, never fixed-height
**Decision**: The bar's frame div is `min-h-[48px]` with its real height derived from the toolbar row's own paddings (`pt-1.5` + chips + the `--bottom-bar-floor` bottom arm).
**Why**: The coarse raised safe floor lives in the ROW's padding; any fixed frame height caps the row and the overflow is clipped by the app-shell's `overflow: hidden` — the padding then still computes (16px) while the rendered chip-to-screen-bottom gap collapses to ~3px, exactly the corner-arc clipping the floor exists to prevent. min-h pins the 48px minimum without duplicating the geometry.
**Rejected**: fixed `h-[48px]` (clips the floor — the shipped bug); `h-[calc(...)]` mirroring the padding expression (states the geometry in two places, drift-prone).
*Introduced by*: 260816-4v2o-unclip-bottom-bar-safe-floor

### Scroll-lock is a persisted ChromeContext preference, and tap-while-locked never summons the keyboard
**Decision**: `scrollLocked` lives in ChromeContext persisted to `runkit-scroll-lock` (the `composeStripEnabled` idiom), read by BottomBar and both page shells; a plain tap on the 🔒 chip unlocks WITHOUT calling the keyboard-summon path.
**Why**: The lock exists for long mobile reading sessions, and mobile tabs reload constantly — per-mount state silently reset the lock on every remount, route change, and reload, which read as "the lock leaks". ChromeContext already owns exactly this class of persisted chrome preference. Unlock-and-summon on tap put the keyboard up for users tapping to reinforce the lock — the two intents (stop locking / type now) get one tap each instead of being fused.
**Rejected**: Per-mount `useState` synced via `onScrollLockChange` props (the original triplication across BottomBar/app.tsx/board-page.tsx — the reset bug); a module-level store outside ChromeContext (a second state-ownership pattern for no benefit); keeping the unlock+summon tap (hostile to the reinforce-the-lock intent).
*Introduced by*: 260816-lkzv-mobile-scroll-lock-hardening

### Compose-focus signal is a module store in `compose-strip-events.ts`, consumed inside BottomBar

### Edge-docked padding keeps the `max()` shape, with BOTH arms gated by the JS keyboard signal
**Decision**: The bottom bar's pad is a single `globals.css`-owned property, `--bottom-bar-pad`: `max(var(--bottom-bar-floor), env(safe-area-inset-bottom))` at `:root`, overridden to floor-only under `html.kb-open`. The floor half stays `--bottom-bar-floor`, raised from 6px to 1rem under `@media (pointer: coarse)` on `html:not(.kb-open)` — where `kb-open` is toggled on `<html>` by `useVisualViewport` when the on-screen keyboard opens. The component consumes `var(--bottom-bar-pad)` only.
**Why**: `env(safe-area-inset-bottom)` resolves to **0** in in-browser iOS Safari for this `position: fixed`, non-scrollable app (device-confirmed 2026-08-05), so the `max()` arm alone leaves the chips under the corner arc — the clearance has to come from the floor. A floor is static, so keyboard-collapse behavior has to be observed explicitly: iOS support for `interactive-widget=resizes-content` is unreliable, and `env()` carries no keyboard signal here. The env arm must be keyboard-gated too: in standalone PWA mode `env()` reports the real 34pt inset and — being layout-viewport-based — keeps reporting it while the keyboard covers that zone (device-confirmed 2026-08-17), so an ungated `max()` holds the full pad above the keyboard. Owning the whole expression in one property keeps the gate covering both arms and the geometry in one place. The JS half stays minimal — one class toggle inside the hook's existing rAF-coalesced pass, no new listeners; all padding math stays in CSS.
**Rejected**: an inline `max()` in the component class (gates only the floor arm — the PWA inset holds the pad above the keyboard); a static coarse floor with no keyboard gate (wastes ~10px above the keyboard on an already-short viewport); treating `env()` collapse or the layout-viewport resize as the keyboard signal (untrue on device); JS-probing `env()` and substituting a measured value (more machinery, still needs a hardcoded magnitude when the probe reads 0); a fixed 34px pad (wrong on non-notched phones).
*Introduced by*: 260805-fi9m-bottom-bar-keyboard-aware-safe-floor (floor gate); 260816-4v2o-unclip-bottom-bar-safe-floor (env-arm gate, `--bottom-bar-pad`)

### Keyboard-open detection is a width-keyed max-height baseline, not an absolute reference height
**Decision**: `useVisualViewport` treats the un-keyboarded baseline as the maximum `visualViewport.height` observed since the last `visualViewport.width` change, and calls the keyboard open when `height < baseline − 150px` (`KEYBOARD_DELTA_PX`).
**Why**: An on-screen keyboard changes height but never width, while rotations and window/split-screen resizes change width — so a width change is a reliable baseline-reset trigger, and a max-height baseline self-heals after any transient shrink. 150px clears iOS URL-bar chrome deltas (~50–114px) and undercuts any real keyboard (~260px+). The two residual gaps are accepted because both fail toward the pre-change 6px floor rather than a wrong pad: rotating or resizing *while* the keyboard is open re-baselines to the keyboarded height (clearing `kb-open` until the next close/open cycle), and a mount with the keyboard already up reads as closed until it first closes.
**Rejected**: comparing against `window.innerHeight` (browsers honoring `interactive-widget=resizes-content` shrink the layout viewport too, erasing the delta); `screen.height` (orientation semantics differ per platform); a dedicated keyboard-detection hook or extra listener (the existing rAF-coalesced pass already sees every geometry change). A desktop height-only window resize can false-positive, which is harmless — the only consumer is `@media (pointer: coarse)`-scoped.
*Introduced by*: 260805-fi9m-bottom-bar-keyboard-aware-safe-floor

### Compose layout forks on pointer type — fine stacks at two rows, coarse collapses to one

**Why**: Sharing one row left the input ~52% of a 375px strip while typing space is the surface's entire purpose; a stack buys the full width at the cost of one button-row height, which the strip can afford as docked chrome. The 2-row default is the user's explicit call, and it also removes the desktop oddity where a 1-line textarea rendered 2px *shorter* than the buttons beside it. On a phone with the on-screen keyboard up, vertical space is the scarce resource instead — the stack's ~130px plus the bottom-bar key row eats most of the halved viewport, so the coarse presentation collapses to one row and folds the header into the placeholder to keep terminal rows visible.

### The compose strip focuses on open, and only on open
**Decision**: The strip focuses its textarea on the off→on transition, via a module-level focus-on-open flag marked by `toggleComposeStrip` and consumed-and-cleared by the mount effect. After-send, Escape, and route remounts keep the no-steal rule.
**Why**: In practice every open was followed by a manual click into the textarea — opening the strip *is* the intent to type, so the blanket no-steal rule cost a gesture on the one transition where focus was unambiguous. Routing the flag through the single `toggleComposeStrip` seam covers every open path (chip, palette, chord, drag-drop, board twin) without per-affordance wiring, and keys the behavior on the TRANSITION rather than the mount — which is exactly what keeps a route remount with the strip already enabled from stealing focus. Consuming unconditionally (even when the effect declines in the "no target" state) is what stops a stale flag surfacing as a surprise focus grab later.
**Rejected**: Focusing on every mount (steals focus on terminal↔board remounts); a `focusOnOpen` prop threaded to each dock (wiring sites for one module-level fact, and the drag-drop auto-enable path bypasses them); calling the existing `focusComposeStrip()` registry from the toggle (the strip is not mounted yet at toggle time — the flag exists precisely to bridge that gap).

### A compose draft belongs to its send target, not to the URL and not to the user
**Decision**: Drafts are keyed by `entryKey(server, windowId)` — the strip's live send target — so each window owns its unsent text and attachments, and focus changes swap the visible draft rather than carrying one draft along.
**Why**: The strip's target is already resolved live at send time (§ Live target), so binding the draft to that same identity is what makes the `→ {window}` label truthful: what you see aimed at a window is what that window will receive. It also makes a cross-worktree attachment structurally impossible — the attachment and the worktree it was uploaded to are two halves of one keyed entry — which is what allows the entire re-home path to be deleted rather than hardened. Keying survives window renames, since `windowId` is tmux-stable, and the same draft appears whether the window is reached via its terminal route or a board pane.
**Rejected**: A single global draft carried across navigation — showing a draft composed for A while B is targeted is a wrong-pane-send footgun that the target label only partially mitigates, and it is the sole reason attachment re-homing had to exist. Keying by URL — equivalent to target keying on terminal routes, but on a board it pins one draft on screen while pane focus cycles underneath, recreating exactly the wrong-pane risk it was meant to remove.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### Draft text is persisted synchronously; attachments are not persisted at all
**Decision**: Every commit writes the text map through to `localStorage` synchronously (no debounce), and `File` objects are never persisted — a hydrated draft carries text only.
**Why**: Drafts are a few kilobytes at most, so the I/O saved by a debounce is negligible next to what it costs — a flush-on-unload edge case and non-determinism in unit and e2e tests — and the synchronous write closes the lose-a-keystroke-on-instant-reload window that motivated persistence in the first place. Dropping attachments is not a compromise but the honest boundary of the storage: uploads are eager and their path lines live in the persisted text, so the only casualty of a refresh is the preview thumbnails, while the files themselves are already on the target worktree's disk and still send correctly.
**Rejected**: Debounced writes (see above). IndexedDB `File` persistence — real complexity and a second storage substrate to buy back thumbnails. `sessionStorage` — dies with the tab, which fails the browser-restart case the persistence exists for. A `storage`-event multi-tab sync — two tabs composing to the same window is rare enough that last-write-wins is the right trade.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### One global listener set over per-key snapshots, and one prune pipeline over both persistence paths
**Decision**: The keyed store keeps a single listener set (any commit notifies every subscriber) with per-key stable snapshot objects, and both the write path and the hydrate path call the same `pruneDraftEntries()` helper.
**Why**: At most one strip is mounted at a time, so per-key subscription channels would add bookkeeping for zero benefit; what `useSyncExternalStore` actually needs is snapshot **identity** stability per key, which the snapshot cache provides. Sharing the prune helper matters because the two paths must agree by construction — a divergence between what is written and what is accepted back would let an entry the writer rejects survive a reload, or an entry the reader drops be silently rewritten. The age check is deliberately two-sided so a future-dated `updatedAt` cannot sort to the front and hold a cap slot forever.
**Rejected**: Per-key listener channels (complexity for a single-subscriber store). Separate filter/sort/slice pipelines at each site (the duplication that a review caught — two copies of a policy that must never disagree). A `__resetForTest` private export for the test seam — exporting the real `hydrateComposeDrafts()` instead means the tests reset through the same code path production uses, so a reset can never drift from a real hydration.
*Introduced by*: 260801-cyth-per-target-persistent-compose-drafts

### Enter transmits a line in the strip, composes in chat — one classifier, deliberately divergent per surface
**Decision**: `classifyComposeEnter(key, surface)` takes a REQUIRED `surface: "strip" | "chat"` and returns the per-surface plain-Enter action: `"insert-line"` on the strip (transmit `text + "\n"`, clear the draft; `enterKeyHint="send"`) and `"default"` (local newline; `enterKeyHint="enter"`) in chat. Everything else is shared and identical on both surfaces — Shift+Enter = newline, Cmd/Ctrl+Enter = the only submit chord, Alt+Enter = byte-exact insert-without-submit, IME-composing Enter never intercepted. The strip additionally sends a bare `"\r"` on an empty/whitespace-only submit; chat's empty send stays a no-op. The classifier still reads no pointer input.
**Why**: The strip overlays the VISIBLE terminal, so a transmitted line lands in the pane's own composer where the user watches it appear — Claude Code treats a raw `"\n"` as newline-insert, so consecutive Enters stage sentence-per-line exactly like typing into the pane, and one Cmd/Ctrl+Enter (or an empty one, the bare `"\r"`) submits. That stage-then-submit loop is the terminal-faithful flow the surface exists to offer, and gating every staged line behind the obscure Alt+Enter chord — with no keyboard way to press Enter afterwards — made the strip a local drafting box instead. The chat lens cannot show the pane's input box, so the same Enter there would make typed text visibly vanish into an invisible target; its premature-send hazard is also the original one (a reflexive Enter firing a half-written prompt at a live agent). Divergence is therefore the correct answer, and putting it INSIDE the classifier — with `surface` required, no default — keeps one authority for both policies: a call site can choose which policy it gets but cannot invent a third, and a new surface must state its choice rather than silently inherit one. Pointer-independence survives because the divergence axis is surface visibility, not input hardware.
**Rejected**: Keeping one shared policy across both surfaces (sacrifices either the strip's terminal-faithfulness or chat's visibility safety — the two surfaces genuinely differ); a default value for `surface` (recreates exactly the silent drift the shared classifier exists to prevent); branching plain Enter at the call sites (the same drift, one layer down); a user preference toggle (a second policy path for a decision with one defensible default per surface); guarding the shell-pane case where the transmitted `"\n"` executes the line (that IS what Enter does in a terminal — terminal-conventional, documented in a code comment).
*Introduced by*: 260802-lj98-compose-enter-insert-line

### Intercept only the readline chords the platform leaves unbound
**Decision**: The shared readline layer claims exactly Ctrl+U, Ctrl+W, Alt+B, Alt+F, Alt+D — matched on `KeyboardEvent.code` with exact modifiers — and leaves every natively-bound Cocoa editing chord alone. Deletions route through `execCommand("delete")` with a controlled-component-safe fallback; an empty computed range consumes the chord without editing.
**Why**: macOS already implements Ctrl+A/E/B/F/P/N/D/H/K/T/O/Y correctly *and* wires them into the system kill buffer, so reimplementing any of them (Ctrl+K especially) would break its pairing with Ctrl+Y — the five claimed chords are precisely the muscle-memory gap. Matching on `code` is mandatory rather than stylistic: macOS composes `∫`/`ƒ`/`∂` into `key` for Alt+B/F/D, so a key-based matcher would miss the exact chords the layer exists for. `execCommand` is deprecated but the only programmatic edit path the browser records on the native undo stack, and Cmd+Z after a Ctrl+W is table stakes for an editing chord. The empty-range guard is a real corruption fix, not defensiveness — `execCommand("delete")` on a collapsed selection deletes a character backward, so Ctrl+U at line start would silently eat text.
**Rejected**: A full readline emulation incl. a kill ring (duplicates working native behavior and cannot feed the system yank buffer); React `setText(...)` for the deletions (breaks native undo); `key`-based matching (blind to macOS Alt composition); polyfilling Ctrl+W on Windows/Linux browsers (browser-reserved — uninterceptable by a page; recorded as a caveat, with macOS and the desktop shell covered).
*Introduced by*: 260801-hsxm-compose-enter-policy-readline-keys

### Recovery over verification — a sent history, not a confirmed clear
**Decision**: The strip records every transmitted text per target and puts it one ↑ away, while the draft-clear stays unconditional and the send semantics stay byte-identical. Delivery is never confirmed before clearing.
**Why**: There is no ack channel through a PTY, and all three hops can lose the text silently — `ws.send()` only queues bytes and an OPEN socket can be half-dead after a sleep or a network switch, the backend discards its `ptmx.Write` error, and the receiving TUI can swallow the bytes outright (Claude Code at a permission prompt, an open autocomplete treating Enter as accept, a shell simply executing the line). A history makes the text recoverable regardless of WHICH hop lost it, which no confirmation scheme can claim, and it buys that without touching the payload bytes, the clear, or the focus contract — so the failure mode of the recovery feature is "the history is empty", never "the send changed".
**Rejected**: Echo-confirmation before clearing (the chat send path's novelty-echo probe) — heuristic, adds latency, and still cannot prove the *application* accepted the bytes rather than the PTY merely echoing them; explicitly deferred by the user, not merely unbuilt. Keeping the draft until confirmed — leaves stale text sitting in an addressed surface, and the confirmation it waits on may never arrive.
*Introduced by*: 260806-kadm-compose-send-history-recall

### Sent history rides a sibling localStorage key, not a widened draft schema
**Decision**: History persists under its own `runkit-compose-sent-history` key with its own type guard and its own map, sharing only the generic `pruneByAgeAndCap` helper with drafts.
**Why**: The shipped draft schema, its `isStoredDraft` guard, and its prune pipeline stay byte-compatible, so an older tab reading `runkit-compose-drafts` is unaffected and corruption in one surface cannot take the other down. The two entries also have genuinely independent lifetimes — a draft dies at send, which is precisely when a history entry is born. Sharing the age/cap helper (rather than the schema) is the right seam: the policy that must not diverge is the pruning, not the shape.
**Rejected**: Folding `entries` into the existing draft entry — it would widen `isStoredDraft`, force the draft's `text !== ""` emptiness prune to reason about history-only entries, and couple two lifetimes that have no reason to move together. Reusing `MAX_PERSISTED_DRAFTS` for the target cap — a shared constant would force a rename the first time either surface wants a different depth.
*Introduced by*: 260806-kadm-compose-send-history-recall

### ↑ recalls only when it cannot mean cursor movement
**Decision**: ArrowUp starts a walk only on an empty textarea, and only when bare and non-composing; ArrowDown is intercepted only mid-walk under the same bare/non-composing rule. Mid-walk, both arrows additionally require the line boundary — ↑ steps only from a collapsed caret on the recalled entry's first line, ↓ only from its last line; off the boundary they move the caret natively within the recalled text without ending the walk.
**Why**: The strip exists to be a real composition surface with IME — hijacking ↑ inside a multi-line draft would destroy in-progress composition, and swallowing an IME-composing arrow would break candidate navigation on the one surface that offers it (xterm.js has no IME). The modifier exclusions follow the same exact-modifier discipline both neighbouring keydown layers already declare: Shift+↑/↓ extends a selection, Alt/Opt and Cmd are macOS paragraph/document jumps, Ctrl is claimed by desktop environments. An empty textarea is the one state where ↑ has no native meaning worth preserving, which is what makes it a safe start gate. Mid-walk, an unconditional intercept proved wrong in use: recalled entries are themselves multi-line, and swallowing every ↑/↓ made them un-navigable — the REPL boundary discipline resolves the same conflict there (native motion inside the entry, history steps at its edges), while caret motion deliberately keeps the walk alive because moving the caret is not an edit.
**Rejected**: First-line gating as the *start* gate (intercept a user-typed draft when the caret sits on line 1) — a cursor-movement trap in composition, where a line-1 ↑ legitimately means "stay put"; the boundary rule is safe only mid-walk, where the visible text is recalled rather than composed. Keying the intercept on `e.key` alone — swallows IME candidate navigation and every modified native motion. Unconditional mid-walk intercept (the initial shape) — made multi-line recalls un-navigable.
*Introduced by*: 260806-kadm-compose-send-history-recall

### The recall walk lives in refs and ends eagerly on a target switch
**Decision**: The walk index and pre-walk stash are `useRef`s (never state), and the target-switch exit fires from a `draftKey` effect rather than from a check at the next keydown.
**Why**: No render reads the index or stash — the visible text is written through `setComposeText` and rendered by the store-controlled textarea, so state would fork the source of truth and cost a re-render per arrow press for no visual benefit. The exit must be eager because the index and stash are meaningless against a stranger target: a keydown-lazy comparison only runs when an arrow is pressed, so an A→B→A round-trip with no arrow on B resumes A's abandoned walk, and an edit on B tears down A's stash. The feared per-focus-change cost is nil — `endRecall()` on a dead walk is two ref writes and no render — and the eagerness is what lets `handleRecallKey` skip a stale-target check entirely.
**Rejected**: `useState` for the index (renders on every arrow press and races the store write). A `recallKeyRef` compared lazily at keydown (it leaves the A→B→A stale walk armed, which is the bug the eager exit exists to prevent). Ending the walk only on user keystrokes — `handleUpload` and `removeFile` mutate the text through the same setter, and leaving the walk armed orphans the attachment: the next arrow drops the path line while the `File` and its preview chip stay mounted, pointing at a path the agent can never resolve.
*Introduced by*: 260806-kadm-compose-send-history-recall

# run-kit Architecture — PR Status Collector

## The `internal/prstatus` Package

In-memory, periodically-refreshed cache of the current user's recent PR statuses (OPEN + recently MERGED/CLOSED), modeled on `internal/metrics.Collector` (260610-596o-pr-status-sidebar). `Collector` holds `byURL map[string]PRStatus` — **keyed by canonical PR URL**, since PR numbers are unique only per repository while the batched query spans every repo the viewer touches, so a number-keyed map would let `repoA#18` clobber `repoB#18` — under a `sync.RWMutex` plus an `interval`, alongside a separate `refreshMu` that **single-flights whole refresh passes**. `NewCollector(interval)` (defaults `interval`, `ghExec`, `available` seams), `Start(ctx)` (runs `refresh` immediately to warm the cache, then ticks at `interval`; exits on `ctx.Done()`), `Snapshot()` (deep copy under `RLock` — callers read lock-free), `RefreshNow(ctx)` (on-demand, used by the POST endpoint; best-effort — errors swallowed), and the private `refresh(ctx)`.

**One batched fetch**: `refresh` makes a SINGLE `gh api graphql` call querying `viewer.pullRequests(first: 100, states: [OPEN, MERGED, CLOSED], orderBy: UPDATED_AT DESC)` returning `number/url/state/isDraft/reviewDecision/updatedAt/headRefName/headRepository { nameWithOwner }` + the latest commit's `statusCheckRollup.state`, plus `viewer { login }` on the node the query already selects — one cross-repo call, O(1) in PR count. `parseBatch` decodes login and nodes together as a `ghBatch`, so the login and the PRs always describe the same fetch; the login is what keys the disk cache and what detects an account switch (below), at no extra call. The head-identity + `updatedAt` fields serve the **branch→PR seed** below: they let this ONE call pre-populate the branch refresher's head-index, and `updatedAt` is what lets indexed candidates take the same most-recently-updated-within-a-state-class tiebreak the gh path applies.

**Why include MERGED/CLOSED, not just OPEN**: a just-merged/closed PR is by definition recently updated, so it sits near the top of the `UPDATED_AT DESC` window and stays in the snapshot — letting the dot/line show `merged` (purple) or `closed` instead of dropping to a bare PR number the moment a PR lands. The merged state IS reachable and is the most useful signal on a change-bound window. The `first: 100` recency cap IS the eviction mechanism (below). Runs through the injectable `ghExec func(ctx) ([]byte, error)` field (default `defaultGhExec`) via `exec.CommandContext` + explicit arg slice (`gh api graphql -f query=… -F limit=100`) + 10s `ghTimeout` (no shell string, no user input in argv — Constitution §I).

**gh-availability guard**: the injectable `available func(ctx) bool` field (default `ghAvailable`, which checks `exec.LookPath("gh")` then `gh auth status`) gates the fetch — gh absent OR unauthenticated is a silent no-op (last-good map kept), matching the `command -v rk` fail-silent posture.

**Wholesale REPLACE = cleanup**: a successful refresh builds a fresh `map[string]PRStatus` and replaces `byURL` wholesale under `Lock`; the recency cap is the eviction — a merged/closed PR shows its terminal state while it stays near the top of the `UPDATED_AT DESC` window, then ages past the `first: 100` cap and drops from the next wholesale rebuild. This IS the cleanup mechanism, so there is no eviction logic or window-lifecycle hook.

**Stale-while-revalidate**: a `gh` call error (network blip) or a JSON parse failure leaves the last-good map untouched (mirrors `metrics.Collector` / `fetchPaneMapCached` degradation).

**Viewer-PR seed sink**: `SetViewerPRSink(func([]ViewerPR))` installs a nil-safe hook `refresh` invokes **only after a successful parse** (so stale-while-revalidate covers the seed too), after the `byURL` swap and OUTSIDE `mu` — the sink reaches into the branch refresher's own mutex, so holding this one across the call would couple the two. `ViewerPR` is an exported projection (`Number`/`URL`/`State`/`HeadRepo`/`HeadRef`/`UpdatedAt`) so the raw `ghPR` JSON shape stays private while `api/router.go` can wire the seam.

**Collector-side seed seams**: `Seed(byURL, viewerPRs)` pre-fills each half ONLY while that half is still empty (a seed can never clobber fetched state), carrying each `PRStatus.FetchedAt` through verbatim; the batch's `login` and its projected node list are retained in the SAME critical section as the `byURL` swap (so one cache document always describes ONE batch) and read back via `Login()`/`ViewerPRs()`; `SetRefreshHook(func())` installs the nil-safe cache-write callback `refresh` calls at the tail of a successful pass — outside `mu`, still inside `refreshMu`. `refreshMu` — held for the whole pass INCLUDING the gh call, and distinct from `mu`, which guards the map for `Snapshot` readers and never spans a subprocess — serializes the interval tick against an on-demand `RefreshNow`, so one pass's `byURL` swap can never interleave with another's sink publication (the index the branch refresher joins against always agrees with the snapshot SSE serves). Blocking is safe because both callers are background goroutines: the tick's own, and the detached one behind `POST /api/status/refresh`.

**Enum collapse** (pure helpers): `mapState(state, isDraft)` → `open|merged|closed` (`MERGED`→merged, `CLOSED`→closed, else open — draft surfaced separately via `IsDraft`); `mapChecks(rollupState)` → `pass|fail|pending|none` (`SUCCESS`→pass, `FAILURE`/`ERROR`→fail, `PENDING`/`EXPECTED`→pending, ""/unknown→none — GitHub's `statusCheckRollup.state` is already a pre-collapsed enum, so no per-check iteration); `mapReview(decision)` → `approved|changes_requested|review_required|none`. `PRStatus` struct: `Number int`, `URL string`, `State string`, `IsDraft bool`, `Checks string`, `ReviewDecision string`, `FetchedAt time.Time`.

**Startup seed cache** (`prstatus_disk.go`) (260809-r4vk-pr-status-disk-seed): runtime state is in-memory and is ALSO mirrored to one droppable JSON file — `$XDG_STATE_HOME/run-kit/prstatus.json` (else `~/.local/state/run-kit/prstatus.json`, `DefaultCachePath`), schema-versioned private persistence DTOs, `0600` file / `0700` dir, every write through `internal/fsatomic.WriteFile`, coalesced by a content dedup that zeroes the freshness-only stamps. Read ONCE at startup, written only from the two background refresh goroutines, never authoritative; a corrupt/absent/version-mismatched file is a silent cold start. Constitution §II's `$XDG_STATE_HOME/run-kit/` carve-out (v1.7.0) covers exactly this class alongside the write-only layout snapshots — no tmux option, no database, and deleting the file changes nothing but cold-start latency. See § Branch→PR Derivation → Startup Disk Seed. Wired into the SSE hub in `api/router.go`; cadence const `prStatusPollInterval = 90 * time.Second` lives in `api/sse.go`.

**Branch→PR refresher** (`prstatus_branch.go`) (260705-dmex-generic-agent-state-tier): a SEPARATE capability alongside the viewer-wide collector — `BranchRefresher` resolves a per-`(repoDir, branch)` PR **index-first**: a join against the viewer head-index seeded from the collector's ONE batched call resolves most pairs with **zero subprocesses**, and `gh pr list --head <branch> --state all --json number,url,state,updatedAt,isDraft` (in the pane's repo via `cmd.Dir`; `exec.CommandContext` + `ghTimeout` + explicit argv, branch passed as a discrete arg — §I) is the **fallback for index misses only**. Either way the result is served from an in-memory snapshot.

**All states, not just open** (`--state all`) (260706-4h26-durable-merged-pr-register-keys): a merged PR keeps resolving positive on every pass so its done-square is durable **statelessly** (no grace clock to expire, no negative-stamp retention, restart-proof — an rk restart re-derives it fresh from gh). The sessions hot path only **registers** observed pairs (`Register` — a cheap lock-guarded set touch) and **joins** via `Snapshot`/`SnapshotBranchPR` (NO exec); all `gh`/`git` subprocesses run on the refresher's background goroutine (`Start(ctx)` → immediate warm + `branchPRRefreshInterval = 30s` tick, mirroring `Collector.Start`), so the SSE hot path stays network-free.

**Coalescing registration-wake seam**: `Register` signals a cap-1 `wake` channel on **first-sight** keys only — a re-observation of a known pair never signals, so the every-2.5s SSE re-registration of every observed pair cannot degenerate the refresher into a 2.5s poll — and `Start`'s select loop answers a wake by waiting out a FIXED `branchPRWakeDebounce = 1s` settle window (`settle`: drains further wakes so one SSE pass's burst yields ONE pass, honors `ctx` cancellation, and is never extended by a drained wake) before running exactly one `refresh`.
`StoreViewerIndex` signals the SAME channel after a non-empty store, so whichever of the two racing startup events lands second — the first SSE registrations, or the collector's first batched fetch — triggers the debounced pass.
The 30s ticker still drives steady state and the wake is purely additive; on an UNSEEDED start the wake is what makes the first useful pass land seconds after `rk serve` starts, because `Start`'s own immediate refresh has nothing registered to resolve.
When the disk seed ran first, that immediate pass already carries the seeded pairs — they sit in `entries` before their first `Register`, so they are never first-sight and fire no wake — while the wake still covers every pair the seed did not carry.

**Viewer head-index** (`StoreViewerIndex([]ViewerPR)`, wired to `Collector.SetViewerPRSink`): a `(host-qualified repo, headRef) → []BranchPR` map replaced **wholesale** under `mu`, mirroring the collector's `byURL` rebuild — a PR that ages out of the batch simply stops being a candidate, so there is no eviction logic. The live index is in-memory; a fresh process may pre-fill it from the startup seed (`SeedViewerIndex`, §II's `$XDG_STATE_HOME/run-kit/` carve-out), and the first successful fetch replaces it. `viewerIndexKey` **lowercases** the `host/owner/name` identity half (hostnames and GitHub repository identities are case-insensitive, and `nameWithOwner` returns canonical case while a local `origin` URL may be typed differently) and NUL-joins the ref, which stays case-sensitive (git refs are). The host comes from the node's PR **URL** (`prURLHost` — `net/url` + `Hostname()`, port dropped): the batched query takes no `--hostname`, so the URL is the only host authority a node carries. Nodes with no URL, no parseable URL host, no `headRefName`, or no `headRepository` (a deleted fork) carry no joinable identity and are skipped.

**Per-repo origin identity** (`originRepo` + the `branchOriginExec` package-var seam + `parseOriginRepo`, `branchOriginTTL = 5m`): `git remote get-url origin` run in `repoDir` (`exec.CommandContext` + `ghTimeout` + explicit argv, `cmd.Dir = repoDir` — §I; a local config read, never the network), normalized to `host/owner/name`.
Acceptance is decided by **form**, not by a dotted-segment heuristic — only an allowlisted scheme (`https`/`http`/`ssh`/`git`) or the scp-like `user@host:owner/name` qualifies, so `file://`, absolute/relative filesystem paths, and dotted-relative lookalikes (`cache.local/acme/tool`) fail open.
The path must also split into **exactly two** non-empty segments: a GitHub/GHE repository path is exactly `owner/name`, so a deeper path (a GitLab subgroup, a Bitbucket `/scm/` prefix, a proxy prefix such as `github.com/proxy/acme/tool`) or a shallower one yields no identity — keeping only its trailing two segments would join the index under a repo the pane is not, attaching a wrong PR AND suppressing the authoritative gh fallback.
BOTH outcomes are cached per `repoDir` with a taken-at timestamp and pruned alongside `defaultBranches` for repos no live pair observes, so each repo costs at most one `git remote get-url` per TTL window.

**Resolution order per pair**: default-branch exclusion (FIRST, authoritative negative, no gh call, outranks an index hit) → viewer-index join (`viewerIndexPR`, ranked by the SHARED `pickBranchCandidate` helper `pickBranchPR` also uses, so indexed and gh-derived winners cannot disagree; short-circuited BEFORE origin resolution when no index is seeded, so an unwired collector costs zero `git`) → the fresh-negative skip (a pair holding a fresh gh-confirmed negative skips the fallback for that pass — checked BEFORE the lazy availability probe, so a pass whose every remaining pair is fresh-negative issues zero gh subprocesses) → the per-pair `gh pr list` fallback, which alone (with the exclusion) may write a negative.

**On-demand seam** (260715-jykd-manual-status-refresh): the exported `RefreshNow(ctx)` delegates to the same private `refresh(ctx)` the tick runs (mirroring `Collector.RefreshNow`), re-resolving every registered pair on demand — best-effort per pair (a transient `gh` error keeps the last-good entry, exactly as the tick path behaves).
Kicked by `POST /api/status/refresh` (§ API Endpoints) alongside the collector's `RefreshNow`.
`refresh` is **single-flighted** by its own `refreshMu`, held across the whole pass INCLUDING every subprocess and distinct from `mu` (which guards the maps for the hot-path `Register`/`Snapshot` readers and never spans a subprocess) — the same split the collector carries — so a tick/wake pass blocked in a slow `gh pr list` can never return a stale parsed-empty result and clear an entry a concurrent on-demand pass just resolved positively.
Blocking is safe because both callers are background goroutines: the tick's own, and the detached one behind the POST.
It gates on **one LAZILY-resolved** availability check per pass — the `gh auth status` probe is itself a subprocess that can burn the full 10s `ghTimeout` on a hung network, so it runs only when a pair actually reaches the gh fallback and is then memoized for the rest of the pass, on top of `checkAvailable`'s cross-pass cache of the `ghAvailable` verdict (positive AND negative, `branchPRAvailabilityTTL = 60s`).
A pass in which every pair resolves via the exclusion or an index hit therefore issues **zero** gh subprocesses, probe included — a wake-driven cold-start pass must not stall behind an answer it never uses.
The exclusion is deliberately NOT gated on availability (it needs only a local `git symbolic-ref`), so a stale positive still clears while gh is down.
A transient exec/network error **keeps the last-good entry** (true stale-while-revalidate — never fail-to-negative); a parsed malformed-JSON result likewise keeps last-good (`pickBranchPR` surfaces the parse error); a **successfully parsed empty/no-PR result clears the entry to a true negative** (`nil pr`) and stamps `branchEntry.negativeAt` — the gh path is the ONLY writer of that stamp — which suppresses the pair's gh fallback while fresh (`branchPRNegativeTTL = 10m`, the worst-case delay for a PR created by other means to appear; viewer-authored PRs land sooner via the index join, which runs before the fallback and overrides a fresh negative immediately).
Every positive write (gh result or index hit) and the exclusion's authoritative negative zero the stamp; transient errors write none; a seeded or not-yet-resolved `nil pr` carries none, so it still reaches the fallback (rtwx).
`pickBranchPR` selects by **precedence — open > merged > closed** (`branchStateRank`, state compared case-insensitively via `strings.ToUpper`; unknown/empty state sorts last), breaking ties **within a class** by most-recently-updated; a URL-less node is skipped (it can never key the live-status join), and an empty/all-skipped array returns `nil` (valid negative).
Unobserved pairs age out in two windows: resolution stops at `branchPRObservedTTL = 5m`, but the entry is retained and served until `branchPRRetainTTL = 30m` (the presence hold — a re-registered pair serves its last-good PR immediately and re-resolves on the next pass), then deleted.

**Refresher-side seed seams**: `SeedEntries([]SeedBranchPR)` pre-fills POSITIVE derivations only, stamps each `observedAt` at load time, never overwrites a present pair, and signals no wake; `SeedViewerIndex` shares `storeViewerIndex`'s store/skip/key rules behind a `viewerIndexSeeded` flag and likewise signals nothing; `PositiveEntries()` renders the live positives back into the cache's explicit `repoDir`/`branch` shape (never the NUL-joined key); `DiscardSeeded()` clears the `pr` of every still-marked entry; `SetRefreshHook` fires at the tail of a pass that had pairs to resolve (an empty `todo` returns first).
`branchEntry.seeded` marks an entry whose PR came from the seed — directly, or resolved from a seed-originated index; `viewerIndexPR` returns that provenance flag beside the candidate, read in the SAME `mu` section that read the candidate, so a concurrent index replacement can never leave the previous account's data written unmarked.
Any freshly-derived write (gh result, fresh-index hit, default-branch exclusion) clears the mark.
Exposed via the process-wide `DefaultBranchRefresher` (Started in `router.go` next to the collector) and the package-level `Register`/`SnapshotBranchPR` façade, `BranchPR` carries `Number`/`URL`/`State`/`UpdatedAt`/`IsDraft` (`State` drives precedence — parsed from the branch query's `state` field, compared case-insensitively, not surfaced further (260706-4h26-durable-merged-pr-register-keys); `IsDraft` is parsed from the same fallback query (260807-n927-branch-channel-draft-flag), seeding `WindowInfo.PrIsDraft` via `enrichWindowPR` — this author-agnostic channel is the ONLY one that sees a draft opened by someone other than the authenticated user, since the collector's `viewer { pullRequests }` query cannot.
The **viewer head-index** path carries no draft flag, but it only ever resolves viewer-authored PRs, which the URL-keyed collector join then overrides with the authoritative `IsDraft` anyway — so the index path has no draft gap to close).
See § Branch→PR Derivation

## Design Decisions

### PR-status collector with wholesale-rebuild cleanup + network-isolated three-layer split
**Decision**: `internal/prstatus.Collector` (mirroring `internal/metrics.Collector`) makes ONE batched `gh api graphql viewer.pullRequests(states: [OPEN, MERGED, CLOSED], orderBy: UPDATED_AT DESC, first: 100)` call on a slow 90s background tick, REPLACES its URL-keyed `byURL` map wholesale each refresh, and serves a deep-copied `Snapshot()`. Three layers on separate cadences keep the 2.5s SSE hot path network-free: (1) `PrURL`/`PrNumber` are derived from the pane's branch via the `prstatus` background branch refresher (register + snapshot-join, off the hot path — see § Branch→PR Derivation and the next decision); (2) the collector fetches live status behind the 90s tick + on-demand POST; (3) the SSE hub joins status onto any window with a derived `PrURL` via a pure `Snapshot()` read, keyed on the canonical URL. gh absent/unauth is a silent no-op (matches `command -v rk`).
**Why**: *include MERGED/CLOSED, not just OPEN* — a just-merged PR is recently updated, so it sits near the top of the `UPDATED_AT DESC` window and shows its `merged` (purple) state instead of dropping to a bare PR number — the merged dot is reachable and is the most useful signal on a change-bound window.
*Wholesale rebuild* — the `first: 100` recency cap is the eviction — a merged/closed PR shows its terminal state while it stays in the top-100 window, then ages out and drops from the next wholesale rebuild (along with killed windows) — cleanup for free, no eviction logic or window-lifecycle hook (the deciding factor when "how does cleanup happen?" was raised in design).
*GraphQL not `gh search prs`* — the literal `gh search prs --author @me` argv ERRORS — that subcommand doesn't expose `statusCheckRollup`/`reviewDecision` JSON fields; `gh api graphql` is the standard cross-repo batched mechanism and serves the identical one-call/O(1)/full-status intent.
*In-memory, not a tmux option or a state store* — the map is re-derivable in one call (Constitution §II — no DB, no tmux option), and a tmux option would add a two-writer race plus manual pruning; the only disk it touches is the never-authoritative startup seed cache (below), which changes nothing but cold-start latency.
*Injectable `ghExec`/`available` seams* — matches the codebase's exec-seam test pattern, lets table tests stub `gh` output deterministically.
**Rejected**: per-PR `gh pr view` polling (doesn't scale — 10 tasks = 10 calls); a webhook receiver writing `.status.yaml` (overkill, contradicts fab-kit's poll-free design); `gh search prs` (missing fields).
*Introduced by*: 260610-596o-pr-status-sidebar

### Two-tier agent-state + branch-derived PR links (own-your-signals over consuming `fab pane map`)
**Decision**: run-kit derives its agent and PR signals itself rather than consuming Claude-only, fab-root-coupled signals through `fab pane map`: agent lifecycle state (Tier 2) reads the `@rk_agent_state` pane user option written by any harness's hooks (Tier 1 — change/stage — stays fab's), and PR links are derived server-side from the pane's branch.
*Reconciler at parse-time*: the shell-command reconciler runs in `internal/tmux.parsePanes` (which already has the pane command + option value on one line) — colocated + unit-testable, mirroring the pure-parse convention; rollup/duration live in `internal/sessions`.
*Branch→PR is a per-`(repoDir,branch)` resolver alongside the viewer-wide URL-keyed collector, not a replacement*: the `gh api graphql viewer.pullRequests` query has no branch/repo/cwd seam so it cannot express `gh pr list --head`; the two compose (derive URL → join live status by URL).
*Resolution runs off the hot path*: the resolver lives in a background `BranchRefresher` and the FetchSessions/SSE path only registers + joins a snapshot, because inline `gh` execution there breaks the zero-network-call invariant and the 5s API cap; a shared process-wide `DefaultBranchRefresher` + package-level `Register`/`SnapshotBranchPR` façade keeps `FetchSessions`' signature free of the dependency.
*Clean swap, no dual-source fallback*: agent columns read `—` until `rk agent setup` runs (single-operator rollout; fallback code contradicts §IV).
*Explicit installer, not silent sync*: `rk agent setup` shows a diff + confirm before mutating user-global config, idempotent marker-keyed merge, `--uninstall`, plus `--yes`/`-y` non-interactive consent, `--dry-run` preview, and a non-TTY refusal naming `--yes` (260717-c424-toolkit-standards-conformance); full consent flow in [agent-state](/run-kit/agent-state.md) § `rk agent-setup`.
Full design: [agent-state](/run-kit/agent-state.md), spec [`docs/specs/agent-state.md`](../../../specs/agent-state.md).
Unblocks fab-kit backlog `[ioku]` (fab pane send/map become convention readers).
**Why**: in a two-state `active|idle` model the most notification-worthy state (`waiting` — blocked on a human) is invisible, non-Claude agents show nothing, and PR visibility is limited to fab-change-bound windows; per constitution Principle X (amended by this change) hooks carry only the underivable, so PR links (derivable from the branch) must NOT ride a push pipeline.
**Rejected**: consuming `fab pane map` for agent state and PR links; reconciling in `internal/sessions` (duplicates the shell-name set); extending the single graphql query for branch→PR (no scoping seam, misses non-viewer PRs); silent hook sync (surprising for user-config mutation).
*Introduced by*: 260705-dmex-generic-agent-state-tier

### First-sight-only registration wake, debounced into one pass
**Decision**: `BranchRefresher.Register` signals a cap-1 `wake` channel only when the `(repoDir, branch)` key is NEWLY inserted into `entries`; `Start`'s loop answers a wake by draining further wakes for a fixed `branchPRWakeDebounce = 1s` window, then runs exactly one `refresh`.
**Why**: `Start`'s immediate first refresh is a no-op at process start (nothing is registered until the SSE enrichment loop has observed panes), so without a wake the first USEFUL pass waits out a whole 30s tick — the visible half of a multi-minute blank-status window after every `rk serve` start. A wake makes that pass event-driven, and the fixed settle window collapses one SSE pass's burst of dozens of registrations into ONE pass; refusing to extend the window on a drained wake means a steady trickle of new pairs can never postpone the pass indefinitely.
**Rejected**: waking on EVERY `Register` — the SSE pass re-registers every observed pair every 2.5s, which degenerates the refresher into a 2.5s poll of N `gh` subprocesses; waking from the sessions layer — pushes refresher knowledge onto the zero-subprocess hot path; shortening the 30s tick — multiplies gh volume without fixing the no-op first pass or the sequential-pass duration.
*Introduced by*: 260807-2ept-pr-status-cold-start

### The collector pushes a STORED head-index and wakes on store, rather than seeding entries once
**Decision**: `Collector.refresh` hands its parsed nodes to a nil-safe `SetViewerPRSink(func([]ViewerPR))` after a successful parse; `BranchRefresher.StoreViewerIndex` replaces a `(host/owner/name, headRef) → candidates` index wholesale and signals the same coalescing wake whenever the store is non-empty. Every pass then joins against the stored index before falling back to `gh pr list`.
**Why**: the batched GraphQL call already fetches each recent viewer PR's head repo and ref, so N sequential `gh pr list` calls would re-fetch data the process holds — storing the index fixes the cold-start latency AND the O(N)-subprocess steady state, where a one-shot seed of `entries` fixes neither and races the first registrations. Waking on store is what makes startup ordering safe without depending on wiring order: the collector's first fetch and the first SSE registrations race, and on the restart path the registrations win, so whichever lands second must trigger the pass. An EMPTY store signals nothing — there is no index to serve a pass from, so a wake would only burn one `gh pr list` per pair. Accepted cost: every non-empty store wakes the refresher, so steady state carries ~1 extra branch pass per 90s collector tick — near-zero-subprocess, since that pass is index-served.
**Rejected**: one-shot seeding of `entries` (racy at startup, no steady-state benefit); a pull from the refresher into the collector (inverts the existing wiring direction and adds a dependency edge); relying on wiring order alone (loses the restart-path race).
*Introduced by*: 260807-2ept-pr-status-cold-start

### An index miss is never an authoritative negative
**Decision**: only the per-pair gh fallback's successfully-parsed empty result, or the default-branch exclusion, may clear an entry; an index miss always falls THROUGH to gh, and the exclusion outranks an index hit.
**Why**: the batch covers only viewer-authored PRs inside the top-`prFetchLimit` recently-updated window, so an empty bucket cannot distinguish "no PR" from "not covered" — treating it as a negative would blank PR status for every non-viewer-authored, aged-out, fork-head, or cross-host pair. Failing open costs one subprocess; failing closed loses the signal the feature exists for. Accepted edge: a non-viewer-authored OPEN PR sharing a head ref with the viewer's MERGED PR shows merged until the viewer's PR ages out of the batch — same-repo same-head cross-author PRs are vanishingly rare and the case self-heals.
**Rejected**: treating an empty index bucket as a negative.
*Introduced by*: 260807-2ept-pr-status-cold-start

### Origin identity is HOST-QUALIFIED, and accepted by URL FORM rather than a dotted-segment heuristic
**Decision**: the index key is `host/owner/name` — the host parsed from the node's PR URL on the seed side (`prURLHost`; the batched query takes no `--hostname`, so the URL is a node's only host authority) and from `git remote get-url origin` on the pane side (`parseOriginRepo`, which accepts only an allowlisted scheme — `https`/`http`/`ssh`/`git` — or the scp-like `user@host:owner/name`). The identity half is case-folded; branch names are not.
**Why**: `owner/name` is not unique across forges — a pane whose origin is `gitlab.com/sahil87/tool` or a GHE mirror would otherwise join a `github.com/sahil87/tool` viewer PR, attach a wrong-host link, AND suppress the authoritative gh fallback that would have resolved it correctly. Deciding acceptance by form is what makes "not a filesystem path" decidable: a dot in the first segment is no evidence of a host (`cache.local/acme/tool` is a directory), and every rejection is fail-open, so strictness costs at most a subprocess. Folding case on the identity but not the ref matches GitHub's case-insensitive repository identities against a locally-typed origin URL while respecting case-sensitive git refs. Known fail-open classes: host aliases such as `ssh.github.com:443`, userless scp-like remotes, and paths that are not exactly `owner/name` never resolve an identity and always take the gh path.
**Rejected**: an `owner/name`-only key (cross-forge false hits); a dotted-first-segment host heuristic (accepts relative-path remotes as hosts).
*Introduced by*: 260807-2ept-pr-status-cold-start

### `parseOriginRepo` accepts EXACTLY two path segments
**Decision**: the (`.git`/trailing-slash-trimmed) origin path must split into exactly two non-empty segments; anything deeper or shallower reports `ok=false` and falls open to the per-pair `gh pr list`. The accepted two-segment forms are `https`, `ssh://` with a port, scp-like, and `git://`, with or without `.git`, with credentials, and with a trailing slash.
**Why**: GitHub/GHE repository paths are exactly `owner/name`, so keeping the trailing two segments of a deeper path — a proxy prefix like `github.com/proxy/acme/tool`, a GitLab subgroup, a Bitbucket `/scm/` prefix — manufactures an identity the pane does not have, attaching a wrong PR AND suppressing the authoritative fallback that would have resolved it correctly (the same defect class as the host-mismatch above, narrower trigger). Every rejection costs one subprocess; a wrong join costs a wrong link.
**Rejected**: keeping the last two segments of an arbitrarily deep path (the manufactured-identity bug); per-forge special cases (unbounded, and failing open already covers them).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### `BranchRefresher.refresh` is single-flighted, mirroring the collector
**Decision**: a `refreshMu` distinct from the map-guarding `mu` is held across the whole pass including its subprocesses, so the interval-tick/wake pass and an on-demand `RefreshNow` serialize.
**Why**: a tick pass blocked in `gh pr list` (up to the 10s `ghTimeout`) could return a stale parsed-empty result and clear an entry a concurrent wake/forced pass had just resolved positively, blanking the PR glyph until the next pass. Blocking is safe for the same reason it is on the collector: both callers are background goroutines — the tick's own, and the detached one behind `POST /api/status/refresh` — never a handler inline.
**Rejected**: widening `mu` to cover the pass (it would then span subprocesses and stall the hot-path `Register`/`Snapshot` readers); a try-lock skip (silently drops the on-demand refresh a user explicitly asked for).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### The PR-status seed cache pre-fills startup state and is never a source of truth
**Decision**: one droppable JSON file under `$XDG_STATE_HOME/run-kit/` holds the collector's last-good `byURL` + viewer list and the refresher's POSITIVE branch entries, written from explicit schema-versioned DTOs through `fsatomic.WriteFile` (0600/0700); it is read exactly once before either poller starts, and the first fresh derivation replaces every seeded value — authoritative negatives included. A corrupt, absent, or version-mismatched file is a silent cold start.
**Why**: the cold-start machinery above is network-gated, so a restart while gh is slow, offline, or rate-limited still starts blank, and restarts are routine (`rk serve` restarts on self-update).
Extending the package's existing stale-while-revalidate rule across the process boundary needs no new poller, no cadence change, and no authority change — which is what keeps it inside Constitution §II's `$XDG_STATE_HOME/run-kit/` carve-out (v1.7.0 — two bounded classes, write-only recovery backups and never-authoritative startup seed caches): deleting the file changes nothing but cold-start latency.
Explicit DTOs keep the disk format from tracking in-memory struct evolution, and the integer `schema` is the clean discard path for a future shape change.
Seeding the collector's viewer list as well as its map matters because writes fire from both pollers: a branch-triggered write before the first successful fetch must not persist an empty collector half over the very seed it was loaded from.
Accepted cost: the file is viewer-wide rather than per-server, so concurrent daemons on one host share it last-writer-wins — correctness-neutral since nothing on disk is authoritative (the e2e harness is excluded — its per-run temp `XDG_STATE_HOME` keeps the e2e backend's writes out of the developer's real cache).
**Rejected**: serving the cache without revalidation (that is a state store — §II); persisting negatives (a seed exists to fill blanks, and a negative re-derives cheaply); marshalling the in-memory structs directly (couples the persisted format to refactors, and `PRStatus` carries no JSON tags); having the writer fall back to the loaded document per half (two sources of truth, and "empty" is ambiguous between a genuinely empty result and "not fetched yet").
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Account-switch invalidation lands at the NEXT successful fetch, carried by a seed-provenance mark
**Decision**: the batched query selects `viewer { login }`, the cache records it, and the startup seed applies unconditionally; the first successful fetch reporting a different login clears the `pr` of every still-seed-originated branch entry — once — and rewrites the file under the new login. `branchEntry.seeded` plus the store-level `viewerIndexSeeded` flag carry the provenance, `viewerIndexPR` returns it beside the candidate it describes, and any freshly-derived write (gh result, fresh-index hit, default-branch exclusion) clears it. An empty login on either side is "unknown", never a mismatch.
**Why**: verifying the login at startup needs the network call or subprocess the seed exists to survive; deferring is safe precisely because a seeded value is never authoritative — wrong-account data is at worst stale display in the interim and can neither suppress a fetch nor write back as fresh. Branch entries are the only state a wholesale rebuild does not touch, so they are the only place account A's data can outlive a fetch as account B; marking the index closes the second path, since a pair resolved from the seeded index is still account A's data. Returning the flag with the candidate rather than re-reading it at the write point closes a TOCTOU where a concurrent index replacement plus discard would leave account A's data written unmarked and persisted under login B.
**Rejected**: `gh api user` / `gh auth status` at startup (blocks on the very network the seed exists to survive); parsing `~/.config/gh/hosts.yml` (a gh-internal format, not a public contract); deleting seeded entries rather than clearing them (drops the registration and its `observedAt`, forcing first-sight wake churn); a global seed epoch with no per-entry mark (cannot tell which entries a pass has already refreshed).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### The cache's dedup key zeroes every freshness-only stamp; the written document keeps them
**Decision**: `Store.Save` compares a copy with the document's `savedAt` AND every collector entry's `fetchedAt` zeroed, while the file it writes carries the real values; genuine content timestamps (a PR's `updatedAt`) stay in the key, and branch entries serialize sorted by `(repoDir, branch)` so equal state assembled from a Go map serializes equally.
**Why**: `Collector.refresh` re-stamps `FetchedAt` on every successful pass, so a key that compared it would always differ and the 90s tick would rewrite the file forever at idle — the same reason `snapshot.ContentEqual` zeroes `TakenAt`. The written file must still carry honest `fetchedAt` values because the flyout's "checked Xs ago" line reads them after a restart. Accepted cost: a coalesced file's `fetchedAt` describes the last pass that actually changed content — conservatively older, self-correcting at the next real change.
**Rejected**: zeroing the stamps in the written document too (the UI would have no staleness left to report); a dirty flag instead of content dedup (a second source of truth about what changed).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Seeded entries restamp `observedAt` and preserve `FetchedAt`
**Decision**: a seeded branch entry's `observedAt` is stamped at load time; a seeded `PRStatus` keeps its original `FetchedAt`.
**Why**: the two timestamps mean different things. `observedAt` is liveness driving the 5-minute age-out, so a preserved pre-restart value would let the first refresh pass evict every seeded entry before the ~2.5s SSE re-registration bumps the live ones — exactly the blank window the seed removes. `FetchedAt` is freshness, surfaced as the flyout's "checked Xs ago", where honesty is the point. Load-time stamping keeps each seeded entry serveable for one TTL window, and entries for windows that have gone away age out like any unobserved pair.
**Rejected**: preserving both (evicts the seed before it can be used); restamping both (the UI would claim just-fetched data it never fetched).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Branch→PR presence continuity: gitRoot keying + detached-HEAD grace + entry retention
**Decision**: the register/join key's repoDir is the branch-supplying pane's git root (`windowPRKey`, raw-cwd fallback); a detached HEAD serves the cwd's last-known branch for `gitBranchDetachedGraceTTL = 5m` on the 15s re-probe cadence; refresher entries survive unobserved from `branchPRObservedTTL = 5m` (resolution stops) to `branchPRRetainTTL = 30m` (deletion).
**Why**: without continuity the PR glyph's presence is a per-tick conjunction of volatile lookups — pane `cd`s mint blank first-sight keys, every rebase negative-caches the branch for 15s, and a reopened dashboard hits deleted entries — so the top status tier flickers constantly. All three fixes are in-memory identity/continuity, keeping the zero-exec hot path and clearing authoritative negatives (default-branch exclusion, parsed-empty `gh pr list`) immediately.
**Rejected**: frontend hysteresis (every surface would need its own copy; the backend is the one place all consumers share) and a ~30s window-level hold (duplicates the refresher's existing stale-while-revalidate without covering the deletion path).
*Introduced by*: 260823-8ocy-solidify-branch-pr-presence

### Merged-PR durability is derived statelessly from `gh --state all`, never from a grace clock
**Decision**: the per-branch query is `--state all` and `pickBranchPR` ranks candidates open > merged > closed, so a merged PR re-resolves positive on every pass; no timer, no negative-stamp retention, no `wentNegativeAt` field.
**Why**: an in-memory grace window (`--state open` + a 10-minute `branchPRMergedGrace` clock) decays the merged done-square into a green fab square minutes after merge, and any rk restart wipes it entirely — in-memory recovery state is exactly what Constitution II forbids leaning on. Deriving from gh on every pass makes the square restart-proof end to end, including on a cold process with no prior positive.
**Rejected**: `--state open` plus a grace clock on a `wentNegativeAt` field (decays, and does not survive restart).
*Introduced by*: 260706-4h26-durable-merged-pr-register-keys

Web Tile — a real browser behind the tile

Design study for replacing the web tile's sandboxed iframe with Electron's own Chromium renderer when run-kit is viewed through the desktop shell. Builds on window-views.md / surface-layout.md and the shipped IframeWindow. Written 2026-09-16 in a /fab-discuss session against b020adf9; the execution plan is fab/plans/sahil/26-09-16-web-tile-native-browser.md. Decisions in §14 were proposed in that session and closed on 2026-09-16 by the change-0 spike (branch spike/web-native-view, never merged); §10 carries the spike's measured numbers.

Recommendation in five lines
  1. It is a second engine, not a replacement. The SPA is served by rk to any browser, PWA and phone, so the iframe stays as the universal engine. The shell gets a native engine behind the same chrome — tab strip, address bar, find bar, error surface — and the chrome stops knowing which engine it drives.
  2. WebContentsView, Electron's recommended API, owned by the main process — the same class the shell already uses for hosts. The <webview> tag would sit in the DOM for free but Electron's docs tell you not to use it; BrowserView is deprecated. Web views hang under the host view as child views so a host switch hides them with their parent.
  3. The crux is layering, not capability. A native view is always painted above the SPA's DOM, so every fixed overlay — palette, dialogs, quake drawer, toasts, tips, flyouts — needs one "overlay open" signal that hides or clips the web views. That signal does not exist yet and is the first thing to build after the spike.
  4. Everything the iframe loses cross-origin comes back for every address kind: sites that refuse framing render, logins persist in a partition of their own, back/forward carry a real canGoBack, find has match ordinals, title/favicon/location are events, and the guest gets real DevTools.
  5. One spike decides the plan. Four questions — child-view hiding on host detach, the overlay hide flash, sash-drag lag, chord forwarding through before-input-event — are answerable in a day on a throwaway branch. If layering proves intolerable, <webview> is the escape hatch, and the spike measures it too.

1. The web tile today

app/frontend/src/components/iframe-window.tsx renders the window's web-tab family as one sandboxed <iframe> per tab (up to eight, hidden but never unmounted — P3). Every browser affordance it offers is built by reaching into the frame's document, so the tile's abilities split sharply on origin:

The backend carries the plumbing that makes same-origin possible: the /proxy/{port} reverse proxy with HTML rewriting of localhost references (api/proxy.go), the /present/ file server, and the frame-check route (api/framecheck.go). Twelve Web: palette entries and two webOnly chords (⌘F, ⌘L) bind to the tile. About 50 Playwright tests cover it across web-tabs, web-tile-chrome, web-tile-find, web-tile-zoom, web-view-lens and present-viewer.

What already points the right way. WebFrame inside the component reports a FrameChromeState (loading, crossOrigin, trackedLocation, title, favicon, tileError) upward and registers a FrameHandle (refresh, retry, navigate) — the chrome binds to the active frame's entry. That pair is half of an engine contract already; §3 finishes it.

2. What "a real browser" means in Electron

The desktop shell (app/desktop, Electron 43) is a viewer: one persistent WebContentsView per (window, host) over the full window bounds, hardened webPreferences (sandbox, contextIsolation, no nodeIntegration), a sandboxed preload exposing the additive runkitShell bridge, sender-frame-gated IPC, an all-external window-open policy and a navigation allowlist. Electron gives three ways to embed a second Chromium renderer:

Recommend WebContentsView. It is the path Electron maintains, it matches the shell's existing view model, and hanging web views under the host view makes host switching and window teardown free. The price is §5 — layering. <webview> would make §5 disappear, and that is exactly why the spike measures it alongside: if the layering rules turn out to be unworkable, the tag is the fallback despite the warning, taken knowingly.

3. Two engines, one chrome

The single structural fact: the iframe cannot go away. The SPA is served to Safari on a phone, to Chrome as a PWA, to a colleague's browser over a tunnel. So the tile grows an engine seam and the chrome becomes engine-blind.

4. Architecture of the native engine

SPA · WebFrameNative

  • measures the tile content rect (ResizeObserver + layout/ratio/zoom/sidebar changes)
  • sends web:create · web:bounds · web:visible · commands
  • subscribes to web:event, feeds FrameChromeState
  • hides views while overlayPresence.count > 0 (§5)
  • sends the reclaim chord table once per view (§7)

preload · runkitShell.web

  • thin invokers, one onEvent subscription
  • additive group — canShellWeb() narrows it like servers.addDirect
  • exposed everywhere, privileged only for registered-host senders (main-side gate)

main · web-views.ts + glue

  • pure registry keyed (windowId, hostId, tabKey) — the views.ts pattern, node --test
  • creates a WebContentsView in the persist:rk-web partition, adds it as a child of the host view
  • relays webContents events → web:event
  • destroys with the host view; hides on host detach

The bridge group

ChannelPayloadNote
web:create{tabKey, url}tabKey is scoped to the sender webContents — two windows showing one host never collide
web:destroy{tabKey}tile unmount / tab close
web:bounds{tabKey, x, y, w, h}DIP coordinates relative to the host view — Electron handles DPR
web:visible{tabKey, visible}inactive tabs, overlay presence, sash drag
web:load · reload · back · forward · zoom · find · stop-find · devtoolsper commandone handler each, validated payloads (the parse*Payload precedent)
web:chords[{code, ctrl, meta, shift, alt}]the reclaim table main matches in before-input-event
web:event ←{tabKey, kind: title|favicon|url|loading|failed|history|found|focus|chord|popup, …}one main→renderer channel; the SPA demuxes by tabKey

Lifecycle

  • Create lazily when a tab is first active (not on family load — eight renderers for eight stored tabs is the wrong default). Hidden tabs stay created once visited, mirroring P3.
  • Host detach (a host switch) removes the host view from the window; child web views go with it. Verify in the spike that a detached parent hides its children — if not, the registry hides them explicitly on the switch seam.
  • Host view navigates or reloads (an rk update, a route reload): the renderer that owned the tabKeys is gone. Main tears down that host view's web views on did-navigate of the host webContents; the fresh SPA re-creates what it mounts.
  • Window close / host removed: destroyed with the host view — nothing new to track.

5. Layering — the crux live mock

A WebContentsView is composited above the host page. Nothing the SPA draws can appear over it: not the ⌘K palette, not a dialog, not the quake drawer, not a toast, not a Tip, not a sidebar flyout card, not the screen-break egg. The SPA currently has 21 components using z-50 or z-[60] and no central notion of "an overlay is open" — dialog state is spread across useDialogState, useSettingsDialog, useServerDialogs, the palette, the quake terminal and the toast stack.

7. Keyboard and focus

With focus inside a native view the SPA's keybinding dispatcher sees nothing — no capture-phase listener can reach a separate renderer. The iframe engine's chord-reclaim seam (capture keydown in the frame → preventDefault → synthetic bubbling KeyboardEvent on the parent document) has an exact analog:

  1. The SPA resolves its reclaim predicate for the web kind into a static table of {code, ctrl, meta, shift, alt} and sends it once per view (web:chords). The table is small: the registry chords the web tile reclaims today plus ⌘K and Escape.
  2. Main listens on the guest's before-input-event; a keyDown matching the table is preventDefault()ed and relayed as web:event {kind:"chord"}.
  3. The engine's onChord re-dispatches a synthetic KeyboardEvent on document — byte-identical to today's reclaim, so the palette listener and the window-level dispatcher see the same event they see now.

Tile focus. The guest's focus event replaces the contentDocument pointerdown + window-blur fallback for onInteract; the focus-memory rules (focus-ownership.md) are untouched because the seam is the same callback. Escape from inside the guest returns focus to the SPA (hostView.webContents.focus()) — the same intent as the code tile's focus hop.

9. Addressing, proxy and remote hosts

Stored @rk_win_web_<n> values are what they are: /present/… and /proxy/{port}/… root-relative paths, other relative paths, and absolute external URLs. The simplest correct rule for the native engine is load exactly what the iframe loads, made absolute against the host origin: new URL(toProxySrc(url), hostOrigin).

  • Present pages and relative addresses keep resolving against the rk host — same as any viewer.
  • Proxied ports keep riding /proxy/{port} — which is required for SSH remote hosts, where the proxy is the tunnel. Loading localhost:3000 directly would hit the viewer's machine, not the host's.
  • External URLs load directly. No frame-check, no HTML rewriting, real cookies.
Optional later rung — direct localhost for local hosts. When the host origin is loopback (the shell already knows via isLoopbackOrigin), a proxy-kind address could load http://localhost:{port} directly and skip the HTML-rewriting proxy entirely, which fixes every site the regex rewrite mangles. Cheap once the engine exists; not v1.

10. Process and memory budget

Each native view is a renderer process. Eight tabs per window across several windows adds up in a way eight iframes in one renderer did not.

  • Lazy creation — a view exists only for a tab that has been active at least once (§4).
  • Hidden means throttled — setVisible(false) lets Chromium mark the contents hidden and throttle timers/rAF; no extra work.
  • No cap in v1 — the spike's numbers (below) put one GitHub guest at roughly three quarters of the SPA's own renderer; eight warm guests would be the shell's largest consumer but not a runaway. A warm cap with reload-on-reactivate stays the knob if real use disagrees.
  • Terminal relay streams are unaffected — they belong to the host view, whose visibility rules are unchanged.

Measured in the change-0 spike (2026-09-16). Rig: Electron 43.2.0 on Linux (GCP VM, Xtigervnc display, software GL — no GPU device), 1280×720 window, guests in persist:rk-web-spike with no preload. 12. Alternatives considered

Strip X-Frame-Options in a backend proxy for external URLs

A /proxy-external?url= route that fetches the site and deletes the refusal headers would make refusing sites render in the iframe with no Electron work.

  • Cookies land at the rk origin: no logins, and a cross-site cookie jar under rk's name.
  • CSP, relative URLs, service workers and WebSockets break; the HTML-rewrite regex becomes a general-purpose proxy rewriter.
  • An open proxy on the daemon — Constitution I would need an allowlist it cannot express.

rejected

Replace the iframe outright

Cut the iframe engine and require the shell for web tiles.

  • Breaks every browser, PWA and phone viewer — the product is served by rk to all of them.
  • Removes the tutorial companion page and presented files from non-shell viewers.

rejected

<webview> as the engine

DOM-resident, so §5 vanishes; the swap is one component.

  • Electron's docs recommend against it; it is disabled by default and needs webviewTag: true on the hardened host view.
  • Focus isolation quirks; no child-view lifecycle.

spike fallback — measured in change 0; adopted only if layering fails.

BrowserView

Deprecated in favor of WebContentsView; no child views.

rejected

Also parked: applying the same engine to the code lens (code-server in an iframe has the same shape — chord reclaim, focus grab — but a different problem set: the workbench wants same-origin for its service worker and the folder-follow seam reads the frame's URL). The engine seam should not assume the web kind, and that is all this plan commits to.

14. Decisions proposed 2026-09-16 · closed the same day by the change-0 spike — green = confirmed, red = amended, blue = still open

Spike rig: Electron 43.2.0, Linux/X11 (an Xtigervnc display, software GL), the shell against this worktree's just dev Vite server, a throwaway tmux server with one window carrying @rk_win_web_1 = https://github.com in a split-h:tty,web layout. Experiments were driven from a loopback control server in main (guest ops, host switch, JS in host or guest, process metrics) plus xdotool for real key and pointer input, and judged from root-window screenshots. macOS was not exercised: every layering finding below is Linux-observed and the plan must not depend on the opposite holding elsewhere.

Engine model — confirmed. Two engines behind one engine-blind chrome; the iframe engine is never removed. Native is the default in a shell that carries the web bridge group; a per-viewer palette toggle opts a viewer back to the iframe. The spike also showed why the seam has to be clean: the chrome's frame-check probe ran against the native engine's address and painted "github.com refuses embedding" over a working native view until the probe was gated — change 1 must move every probe into the iframe engine, not the chrome.
API — amended: WebContentsView as a sibling of the host view on win.contentView, never a child of it. A guest added with hostView.addChildView(guest) never painted: events flowed normally (title, did-navigate, did-stop-loading), the SPA's tile showed the view's background color at the right rect, but the guest document reported visibilityState === "hidden" and capturePage() threw UnknownVizError — Chromium never gave the child a compositor surface. Re-parenting the same view onto win.contentView (removeChildView + addChildView) made it paint at once, pixel-aligned with the tile. Consequence: "a host switch carries the guests along for free" is gone; the registry owns z-order and visibility explicitly (next card). <webview> is not adopted — the layering verdict below is positive.
Host switch — closed (was "child hiding on host detach"). With guests as siblings, attachHostView's win.contentView.addChildView(incoming) appends the incoming host above every guest: switching to host B covered host A's GitHub guest completely and its document flipped to hidden (occlusion). Switching back re-appended A above its own guest and buried it — the SPA painted the placeholder card while the live view sat underneath. Registry rule for change 3: on detach, setVisible(false) the outgoing host's guests; on attach, after adding the host view, re-add each of the incoming host's active guests (addChildView on an existing child moves it to the top) and re-show them. Window close and host removal close the guests with the host, unchanged.
Layering rule — confirmed, with two amendments. Modal-class overlays hide the guests; toasts move over chrome. Amendment 1 — never call setBounds on a hidden guest: park incoming bounds while hidden and apply them in the same turn as setVisible(true). In the first palette run a bounds update landing right after setVisible(false) left the guest painted over the palette's right half; parking removed it and a direct reproduction did not recur, so the rule is cheap insurance rather than a proven bug. Amendment 2 — the transient "clip" class works but reflows: shrinking the bounds by the Tip's overlap (30 px) revealed the Tip and shifted the page's viewport by 30 px. For the tile's own header verbs prefer flipping the Tip to open upward; clip only for overlays that genuinely straddle the content rect.
The hide flash — closed: acceptable. Physical Ctrl+K → palette open in the SPA 17–33 ms → setVisible(false) applied 4–10 ms after that (21–40 ms after the keypress, under one 60 Hz frame of the palette's own paint). A 70 ms screenshot burst never caught a frame with the palette drawn over a still-visible guest, nor a hole without the palette; the engine's placeholder paints the tile background, so the card stays and only the page content goes. setBorderRadius(6) renders anti-aliased rounded corners on all four corners — keep it.
Sash drag — amended: the mid-drag hide is not needed for lag. With the engine sending bounds on every animation frame during the drag, the guest's edge tracked the tile edge within 1–2 px in 60 ms-step captures, GitHub reflowing live. The hide variant works too (placeholder card during the drag, final bounds on release, 4–10 ms signal-to-hide). Recommendation: live resize is the default (content never disappears), the hide stays as an engine option for pages whose reflow is expensive; the SPA's mid-drag pointer-events: none rule is unaffected.
Chord forwarding — confirmed, one rule added. before-input-event matching type === "keyDown" + code + (control || meta) on the guest, preventDefault, relay, synthetic bubbling KeyboardEvent on the SPA's document: from inside GitHub's page Ctrl+K opened the palette, Ctrl+F the find bar (typing then landed in the find query), Ctrl+L focused the address bar, Escape closed the palette and returned focus; typing into GitHub's email field, spaces included, was untouched and never reached the SPA. Rule: main calls hostWebContents.focus() on every relayed chord, not only Escape — without it the SPA shows a focused palette input while OS focus stays in the guest (document.hasFocus() === false) and the next keystrokes go to the page. Bridge rule learned the hard way: onEvent must return an unsubscribe and the engine must demux by tabKey; a leaked listener re-dispatched each chord a dozen times and the palette toggled itself shut.
Zoom source of truth — closed: the SPA's buckets own it, re-applied on every did-navigate. Chromium's store in the partition is per host and persistent: setZoomFactor(1.25) on github.com survived same-host navigation and reload, dropped to 1.0 on example.com and on docs.github.com, came back to 1.25 on history-back to github.com, and leaked into the <webview> twin, which opened github.com at 1.25 unasked. So a per-tab bucket and the per-host store do fight across hosts, and the re-apply rule wins. Ctrl+wheel inside the guest emits zoom-changed but Electron applies nothing itself — main relays the direction, the SPA steps its bucket and sends the factor back, so the buckets stay the single writer.
<webview> twin — measured, kept as the fallback only. Layering is free (the palette drew over it with no hide). Focus: the embedder's activeElement is the WEBVIEW element while the guest holds OS focus, and the palette's own input.focus() pulled focus back without a main-side hop — a real advantage; hostWebContents.focus() did not move focus off the element for Escape (the SPA would blur() it). Events on the element all fired: did-navigate, did-navigate-in-page, page-title-updated, dom-ready, did-stop-loading, focus, blur; chords still need the before-input-event relay through contents.hostWebContents (DOM keydown does not cross the boundary). Sash drags are plain layout. Memory 194 MB for github.com, the same order as the view. Costs unchanged: webviewTag: true on the hardened host view and Electron's do-not-use recommendation. Not adopted.
Containment · addressing — confirmed where exercised. The guest ran in persist:rk-web-spike with no preload, sandbox + contextIsolation, a deny-all permission handler, and an http(s)-only branch in the app-level navigation guard keyed on the guest's webContents.id; GitHub, example.com and the dev SPA loaded and navigated freely. Addressing was not exercised beyond an absolute external URL.
Memory — closed: no cap in v1. Numbers in §10: 80 MB for a blank renderer, 220 MB for github.com, 183 MB for a Vite dev SPA; hidden saves 2–40 MB. Lazy creation stays; a warm cap is a later knob.

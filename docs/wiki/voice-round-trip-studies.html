Voice Round-Trip you ⇄ operator

The outbound leg is easy: hold to talk, transcript, deliver into the operator pane. The question this study answers is the return leg — the operator talks back by running rk say (one new verb, a sibling of rk notify). The daemon fans it out over the state socket every dashboard already holds open; the browser renders a reply card and speaks it aloud. No polling, no new store — the reply rides the same channel that already paints sidebar state.

THE WIRE — what actually moves

How the reply reaches you

Three return channels, layered by where you are. All three exist today except the first's final hop — the reply card and the spoken line — which is the one genuinely new surface.

In the tab · primary

rk say → state socket → card + voice

The operator ends its turn with rk say "<summary>". The daemon fans it out on /ws/state — the socket every open dashboard already holds for sidebar state — and the browser shows the reply card and speaks it via speechSynthesis. TTS is free, on-device, and works on plaintext LAN origins; only the mic needs a secure context.

pane → rk say → daemon → /ws/state → HUD card + speechSynthesis.speak()
Away · fallback

Web Push when no tab is listening

No connected dashboard (or tab hidden)? The same rk say degrades to the existing rk notify Web Push path — push-on-agent-waiting already ships. Tapping the notification opens the PWA on the operator window, mic one hold away.

Always · the record

The pane is the transcript

HUD cards are ephemeral by design — Constitution II, no new state store. The full conversation is already durable in the operator pane itself; the HUD is a summary you can hear, the pane is the record you can scroll. Replay derives from tmux, not from a voice log.

Design notes

One new verb, one new route

rk say and POST /api/voice/transcribe are the only additions. Delivery (rk mux send with paste probe + gated Enter), agent-state, the state socket, and Web Push are all existing machinery — voice is a modality bolted onto seams that already exist.

The confirm gate

Raw STT text never hits send-keys unreviewed: the transcript settles in the HUD with a 3 s auto-send you can tap to edit or cancel. Destructive verbs additionally get a spoken-back confirm from the operator itself (stage 6 is that pattern).

Barge-in on waiting

When agent-state flips to waiting, the mic arms itself (amber) — you answer a question by just talking, no click. The waiting state already carries the pending question text (Constitution X: hooks carry only the underivable), so the HUD and the push share one source.

Keyboard-first survives

Hold ⌥Space is the push-to-talk chord; Voice: hold to talk registers in the palette per Constitution V. Voice is additive — every action here remains reachable by keyboard, and the compose strip still types.

Where speech is computed

STT runs on the daemon box (whisper.cpp, or a hosted API if audio may leave the machine) — the browser only records opus. TTS runs in the browser (speechSynthesis) — zero infra, per-device voice choice.

The one hard prerequisite

getUserMedia needs a secure context. Over plaintext LAN the mic is silently absent — the desktop shell (Electron) sidesteps it, otherwise HTTPS on the daemon or a tunnel. Everything on the return leg works on plaintext today.

# run-kit UI — Status Signals

## PR Status

Live PR status is exposed two ways: a **full one-line detail** (the Pane panel `PR` L3 register) and a **single status dot** (the unified `StatusDot`, see § Status Dot below). The detail surface is:

1. **Pane panel `PR` (L3) register** (the per-*selected*-window detail view; see § Pane Panel / `status-panel.tsx`). This is the full-line PR surface — mirrored in compact form by the status bar's left-cluster `pr` segment (§ Status Bar), which resolves the same `getPrSegments` colors. The `SessionTiles` window tile carries the `StatusDot` plus the rest-state PR glyph (§ Rest-state PR glyph); there is no `PrStatusLine` component; its module `pr-status-model.ts` is the single source of the shared PR color vocabulary + the StatusDot's exported model (§ Shared PR vocabulary). (`260701-70a0`, `260715-jykd`, `aqo6`)

The *dot* (a single colored dot, not the full line) reaches the remaining surfaces: the sidebar window-tree row and the `SessionTiles` window tile. The dense tree shows a single `StatusDot`, never the multi-part line. That single dot is the unified `StatusDot` driven by the compositional **two-family ladder** (cool fab blue-building → green-PR-ready, warm ad-hoc agent yellow, gray floor; core hue = phase, shape = status, additive yellow halo = `waiting`), reused on all its surfaces (sidebar row, SessionTiles window tile, pane-panel header). The dot tells the **local** story only — the branch's PR (the remote story) rides the separate rest-state glyph beside it. See § Status Dot. (`260610-obky`, `aqo6`)

### `PR` (L3) register — colored segments + open-first (`status-panel.tsx`)

> `WindowContent` renders the pyramid's **four orthogonal signal registers** (spec § Row Minimalism). See § Pane panel four-register view for the full L0/L1/L2/L3 model; this subsection covers the L3 `PR` register. (`260706-y1ar`)

The **`PR` (L3) register** shares the `tmx/cwd/git/fab` icon + value idiom but with an **open-first** interaction — it is the exception to the panel's "click row = copy" default. `getPrSegments(win)` returns `null` unless `win.prNumber` — the gate is **ungated from `fabChange`**: the L3 register shows the PR for ANY pane on a branch with a derived PR (universal derivation, Principle X; the dot renders no PR state — the row/tile glyph is the PR channel, see § Status Dot). Otherwise it returns an array of colored `{text, color}` segments — `#<n>` (`text-text-primary`), `<state>[ (draft)]` (via `PR_STATE_COLORS`), and, for an `open` PR only, `checks <prChecks>` (`PR_CHECKS_COLORS`) and `review: <prReview→spaces>` (`PR_REVIEW_COLORS`). `state` can be `open`/`merged`/`closed` — the collector queries `states: [OPEN, MERGED, CLOSED]`, so a recently-merged PR shows `merged` (checks/review suppressed for non-`open`), see `architecture.md` § `internal/prstatus`. The three color maps are imported from `pr-status-model.ts` (single source shared with the sidebar dot — the shared vocabulary home, § Shared PR vocabulary), so segment coloring follows GitHub state per-segment (no whole-value red swap) — the color story lives in § PR Status (draft-follows-health) above. The PR icon (``) is the Nerd Font git-pull-request glyph, matching the other rows' accent icons.

**Open-first split** — the row body's interaction is open-first (`↗`), not copy. The segment JSX is single-sourced via a shared `segmentSpans` const in `WindowContent` (consumed by both branches below, so the two can't drift), and the row branches on `win.prUrl`: (`260703-41ks`)

- **URL present** → the row body is a file-private `PrLinkRow` — a real `<a href={win.prUrl} target="_blank" rel="noopener noreferrer" title={win.prUrl} aria-label="Open PR #<n> in a new tab">` (NOT a `<button>` + `window.open`, so native middle-click / Ctrl-Cmd+click / right-click → "Copy link address" all work — the anchor-not-button PR-link idiom). The anchor is a flex row: a `shrink-0` prefix span + PR icon span, then a `min-w-0 truncate` segment-text child, then an **always-visible** (not hover-gated) `shrink-0` inline `↗` sibling immediately after it — so the `↗` hugs the (possibly truncated) text end, is never eaten by truncation, and never floats to the far right of a wide row. The `↗` is the affordance that signals this row **opens** rather than copies; the row hover treatment (`hover:bg-bg-inset`, segment `group-hover:text-accent`) is the row-level cue. Because the anchor is a flex container (whitespace-only `{" "}` text nodes between flex items are dropped and a trailing collapsible space trimmed), the inter-column gaps live as NBSPs INSIDE the prefix/icon spans — the at-rest prefix is `"pr"`+2×NBSP (4 monospace advances) matching `CopyableRow`'s `${prefix} ` (3 + gap = 4), and the `copied ✓`+NBSP feedback is 9 advances matching `CopyableRow`'s `copied ✓ ` — keeping the icon/content column-aligned with `tmx/cwd/git/fab` and the no-URL branch. **Copy is role-swapped, not dropped**: a sibling hover-revealed copy `<button aria-label="Copy PR URL">` (the `` clipboard glyph) sits in an absolutely-positioned right-side container reusing the **sidebar window-row icon-cluster gating** — the container is `pointer-events-none` at rest with `group-hover/pr:pointer-events-auto coarse:pointer-events-auto has-[:focus-visible]:pointer-events-auto`, and the button is `opacity-0 group-hover/pr:opacity-100 coarse:opacity-100 focus-visible:opacity-100` (revealed on hover / coarse pointers / keyboard focus; the anchor reserves `pr-6` so the icon doesn't overlap the inline `↗`/text). Its `onClick` does `e.preventDefault(); e.stopPropagation(); handleCopy("pr", win.prUrl)` — the button is a SIBLING of the anchor (not enclosed, so `<a>`-in-`<a>`/`<button>`-in-`<a>` nesting is avoided; `preventDefault` is belt-and-suspenders). Its color follows the window-row cluster precedent (`text-text-secondary hover:text-text-primary`), NOT `ICON_CLASS` (whose `text-accent-bright` would fight at equal specificity). The `copied ✓` feedback keeps the `copiedRow === "pr"` + `COPY_FEEDBACK_MS` mechanism, and because the row body is not a `CopyableRow`, `PrLinkRow` replicates the prefix swap (`pr` → `copied ✓`) inline. Both the anchor and the copy button are natively keyboard-focusable (Constitution V).
- **URL absent** (`prNumber` set, `prUrl` missing) → nothing to open, so the row stays a plain `CopyableRow` (prefix `"pr "`) copying the segment text (`prText`) on click — the row body IS the copy action, no anchor, no inline `↗`, no hover copy icon.

`CopyableRow` has no `className` prop; its `title` prop is live (the `cwd` row uses it).

**Draft state-color follows health, not readiness.** `getPrSegments(win)` (the colored-segment variant used in the panel) does NOT force a draft PR's state-color to `text-text-secondary` — a draft's state segment follows `PR_STATE_COLORS[win.prState]` like any other (open → `text-accent-green`/green), under the "green = HEALTH, not merge-readiness" semantic. Checks/review are suppressed for `!open` (merged/closed) PRs, and `merged` is `text-signal-purple`. The color story is one system across the rest-state glyph and these status-panel segments (green = health, red = fail, yellow = checks running, purple = merged) driven by the shared `isFailish` predicate. The sidebar `StatusDot` renders no PR state at all — it keys off the lifecycle `PHASE_HUE`/shape model (§ Status Dot); the row's PR color channel is the glyph (`prGlyphColor`). (`260615-2olv`, `aqo6`)

The rest-state PR glyph (window row + session tile) is the **one** surface that colors draft differently — gray, below fail, open-gated (§ Rest-state PR glyph). Draft-follows-health governs these segments; the glyph carries the orthogonal *whose turn is it* read, and the `" (draft)"` state-segment suffix here stays the accessible signal either way. (`e30p`)

### Pane panel four-register view (`status-panel.tsx` `WindowContent`)

The pane panel's `WindowContent` renders the pyramid's **register view** — one line per signal layer, **orthogonal, never collapsed**, so the sidebar `StatusDot` is a pure function of what the panel shows and can be **mentally derived** from it. The four registers each render as absent when their layer is absent (a plain shell pane shows only `out`). All prefixes are the **fixed-width 3-char vocabulary** `out`/`agt`/`fab` (+ `tmx`/`cwd`/`git` identity rows), each followed by a single-space advance; only `PR` is 2-char + NBSP-padded to the same 4-advance column. (`260706-4h26`)

```
out  active · <command>   /   <command> — idle Xm since last output   (L0: activity + activityTimestamp)
agt  waiting 3m           /   active   /   idle 12m                    (L1: agentState + epoch duration)
fab  <id> <slug> · <stage>[ · <displayState>]                         (L2: fabChange · fabStage · fabDisplayState)
PR   #<n> · <state>[ · checks <c> · review: <r>]                      (L3: prNumber/state/checks/review, ungated)
```

- **L0 `out`** (`getOutputLine`) — ALWAYS rendered (the floor layer's precondition is "always"). Speaks about bytes, not intent. Its elapsed is **never muted** here — the register view is uncontested for space, so the **waiting-pierce rule is automatic** (the duration-mute rule that hides elapsed when output flows applies only to the tip's one-line summary, spec § Duration-Text Ladder). Icon: `BrailleSnake`.
- **L1 `agt`** (`getAgentLine`) — `null` when no `agentState`, else `${agentState} ${agentIdleDuration}` (or bare state when no duration). The rk-computed `agentIdleDuration` is present for `waiting`/`idle`, empty for `active`. Icon: `StarTwinkle`. This is where a waiting duration is always visible regardless of flowing output (the pierce rule).
- **L2 `fab`** (`fabLine`) — `<id> <slug> · <stage>[ · <displayState>]`; the `displayState` segment is appended when present (`fab pane map` may omit it on older binaries). Rendered as a `CopyableRow` (copies the change id). Icon: `ClockSpinner`.
- **L3 `PR`** (`getPrSegments`) — see § `PR` (L3) register above. **Ungated from `fabChange`** — shows for ANY pane with a derived `prNumber` (universal derivation, Principle X). The open-first `PrLinkRow` / `CopyableRow` branch on `win.prUrl` folds in here.

The identity rows (`tmx`/`cwd`/`git`) are pane metadata, orthogonal to these four signal registers, and render above them. The per-second `useNow()` tick lives in this leaf (`WindowContent`) — the bottom panel is a single instance, so its tick is negligible and never touches the memoized sidebar tree (§ Render Performance).

**The register view has THREE surfaces**: this PANE panel, the sidebar row-hover flyout card (§ Row-hover register flyout card), and the status bar's left window cluster (§ Status Bar). All resolve their lines from the shared `sidebar/registers.ts` module (§ Register resolvers), so they cannot drift. The panel keeps the icon column (`BrailleSnake`/`StarTwinkle`/`ClockSpinner`), the identity rows, and the copy/open-first row interactions; the card is read-only glance content with only its PR + docs links interactive; the status bar renders the compact segment form of the `agt`/`fab`/`pr` registers plus the `tmx`/`cwd`/`git` identity rows — it carries **no `out` register** (and therefore no per-second clock) — clickable where the segment carries an action. The PANE panel surface is **opt-in**: it mounts only while its sidebar section-visibility toggle is on ([sidebar](/run-kit/ui/sidebar.md) § Section-Visibility Rail — default OFF on every viewport, so the board-route focused-tile fallback is likewise opt-in); on mobile the coarse status rail + three-tier cards are the default register-detail surface, with the panel reachable via the rail or the `Panel: Toggle Pane` palette entry. (`93dy`, `260814-ldbs`, `499u`, `260817-iha5`)

### Register resolvers — `sidebar/registers.ts`

The four register lines are resolved by pure functions over the streamed `WindowInfo` in `sidebar/registers.ts` — **one source for all three register surfaces** (the PANE panel's `WindowContent`, the row flyout card, and the status bar's window cluster), no React, no duplication:

- `getOutputLine(win, nowSeconds)` → the L0 `out` string. Takes `nowSeconds` as a parameter rather than reading a clock, so each consuming surface supplies its own leaf-scoped `useNow()` (§ Render Performance). Consumed by the PANE panel and the flyout card only — the status bar renders no `out` register (`499u`).
- `getAgentLine(win)` → the L1 `agt` string; `null` when no `agentState`.
- `getFabLine(win)` → the L2 `fab` string `<id> <slug> · <stage>[ · <displayState>]`; `null` without a parseable `fabChange` or without a stage.
- `getPrSegments(win)` → the L3 `PR` colored segments (+ the `PrSegment` type); `null` without `prNumber`. See § `PR` (L3) register for the segment vocabulary and gating.

Consumers own their own PRESENTATION — prefixes, icons, truncation, copy/open interactions — and share only the strings and segments. Covered by `registers.test.ts`; `status-panel.test.tsx` covers the panel's rendered register lines. (`93dy`)

### Shared PR vocabulary — `pr-status-model.ts`

The module `pr-status-model.ts` carries no `PrStatusLine` component — it is the single source of the shared PR **color vocabulary** AND the lifecycle **status-dot model** (below), imported by `status-dot.tsx`, `status-dot-label.ts`, `sidebar/registers.ts` (the shared register resolvers), `sidebar/window-row.tsx` and `session-tiles/session-tiles.tsx` (the rest-state PR glyph's gate + color on both surfaces), and `sidebar/row-flyout-card.tsx`, plus its own unit test (`pr-status-model.test.ts`). The PR text detail lives in the register resolvers, rendered by both the PANE panel's L3 `PR` register and the row flyout card (`getPrSegments`, § `PR` (L3) register). (`260715-jykd`, `93dy`)

**Module surface** (colocated in `pr-status-model.ts` — all `export`ed except the file-private `hasFreshAgent`, an internal helper to `statusDotState`):

- **PR color vocabulary**: `PR_STATE_COLORS`/`PR_CHECKS_COLORS`/`PR_REVIEW_COLORS` (the per-segment GitHub-state color maps, consumed by the L3 register resolver in `sidebar/registers.ts`) and `isFailish(win)` (`prChecks === "fail" || prReview === "changes_requested"` — the single fail predicate).
- **Row PR-glyph helpers**: `prOwnsGlyph(win)` (`!!prNumber && (prState === "open" || prState === "merged" || prState === "closed")` — a positive allowlist: an unknown/absent `prState`, the branch channel's unconfident `""` fallback, never owns) is **exported** — the gate for the rest-state PR glyph on the sidebar window row AND the session-tile window row (§ Window rows, § Session Tiles); it gates only the glyph, never any dot tier. `prGlyphColor(win)` returns the glyph's color token from the same vocabulary as a **six-way** first-match-wins chain: `text-text-secondary` for **closed** (a dead PR reads muted — its stale checks/review are historical noise, so closed sits above fail), then `text-signal-purple` for **merged** (a landed PR — the same historical-noise rationale puts merged above fail too), then `text-signal-red` when `isFailish(win)`, then `text-text-secondary` for an **open draft** (`win.prState === "open" && win.prIsDraft`), then **`text-signal-yellow` for open with `prChecks === "pending"` (checks running)**, then `text-accent-green` for open otherwise (checks pass or no decisive signal). **Fail sits above draft**: a draft with failing checks or changes requested reads red — `isFailish` dominates every open case. **Draft sits above pending**: drafts stay muted even while their checks run — pending would un-mute them. The draft branch is **gated on `prState === "open"`**, which keeps the closed path untouched *by construction* rather than incidentally (a closed draft reads closed, since the closed branch matches first; merged is already returned above it). Closed and open-draft share the inert gray token — the ✕ icon shape is what separates a closed PR from a draft (§ Rest-state PR glyph). No new color system, no new hex: `text-text-secondary` is the established inert/no-journey token (`PHASE_HUE.none`), and the pending yellow reuses `PR_CHECKS_COLORS.pending`'s token choice. **Draft, checks-pending, merged, and closed are glyph-only distinctions** — the dot renders no PR state at all (the local/remote split, § Status Dot). (`93dy`, `e30p`, `aqo6`, `xuej`)
- **Status-dot model**: the compositional dot model (`aqo6`): `DotShape` (`"ring" | "solid" | "failed"`), `DotPhase` (`"building" | "prReady" | "agent" | "none"`), `StatusDotState = { phase: DotPhase; shape: DotShape; waiting?: boolean }`, `fabPhase(stage)` (the stage-based two-stop split), `fabShape(displayState)`, `hasFreshAgent(win)` (file-private), `PHASE_HUE` (phase→hue token map), and the two-family `statusDotState(win)` — no PR branch (see § Status Dot for the ladder + the local/remote split).

The `StatusDot` component (`status-dot.tsx`, see § Status Dot) imports `statusDotState`/`PHASE_HUE`; `status-dot-label.ts` imports `DotPhase`/`DotShape`/`StatusDotState`; `dotLabel` lives in its own `status-dot-label.ts` module so both the dot and the row flyout card (which reuses the label as its header) import it without an import cycle (`260706-y1ar`). There are no `PR_DOT_COLOR`/`PR_DOT_LABEL` maps (`260615-0hsz`) and no `prDotState`/`PrDotState` five-state enum (`gyt1`) — `isFailish(win)` (`prChecks === "fail" || prReview === "changes_requested"`) is the single source of the fail definition, read by `prGlyphColor`'s fail branch and the Pane-panel segments.

### Status Dot (`status-dot.tsx`) — compositional two-family ladder + waiting halo

> Spec: `docs/site/status-dot.md` (+ `docs/img/status-dot-reference.svg`) is the canonical reference — four small legend strips (hue / shape / glyph / halo), one per channel, replace precedence prose + a per-cell matrix. Design authority: `docs/specs/status-pyramid.md`.

> Detail surface: the dot is a **pure decoration** — no native HTML `title`, no `tabIndex`, no per-dot hover-card of its own. The hover/focus detail surface is the sidebar row's flyout card (§ Row-hover register flyout card). (`93dy`)

`StatusDot({ win }: { win: WindowInfo })` (`app/frontend/src/components/status-dot.tsx`) is the **one** dot reused on all three surfaces — the sidebar window row (leading position, the row's primary status signal beside the owned-PR rest glyph — see § Window rows / Row Minimalism), the `SessionTiles` window tile, and the pane-panel header. It is a **first-class consumer of `agentState`**, using **TWO orthogonal visual channels PLUS an additive attention overlay**: **core hue = phase** (which journey + position in it), **shape = status** (health — the SAME meaning in every hue, fully compositional), and **`waiting` → a ladder-exempt additive yellow halo** (see § Waiting halo below). (`260615-0hsz`, `260706-y1ar`, `aqo6`)

**The local/remote split** — the ownership rule the vocabulary rests on: the **dot tells the LOCAL story** (what runs in this pane: which journey, is it healthy, does it need me); the **glyph tells the REMOTE story** (the branch's PR on GitHub — § Rest-state PR glyph). The dot renders no PR state in any family — no purple, no orange, no PR shapes; `statusDotState` consults no PR field. A window's PR still shows everywhere derivation reaches — the rest-state glyph on the row and the session tile, the PANE panel's L3 register, and the flyout card's "Open PR" link (Principle X: derivation is universal) — just never on the dot. (`aqo6`)

**Ladder — two families joined at the top** (`statusDotState(win)` in `pr-status-model.ts`). First precondition wins for the core hue + shape; `waiting = win.agentState === "waiting"` is computed independently and attached as `state.waiting` on every branch:

- **`fabChange` present (and `fabDisplayState !== "skipped"`) → cool family (fab pipeline):** `{ phase: fabPhase(win.fabStage), shape: fabShape(win.fabDisplayState) }` — blue `building` for intake·apply·review, green `prReady` for everything else.
- **no fab ownership but a fresh `agentState` → warm family (ad-hoc agent):** `{ phase: "agent", shape: agentState === "idle" ? "ring" : "solid" }` (yellow — a `waiting`/`active` agent is mid-turn → solid, only a resting `idle` agent is a ring).
- **neither → the gray L0 floor:** `{ phase: "none", shape: win.activity === "active" ? "solid" : "ring" }`.

A **`skipped`** `fabDisplayState` makes the window NOT fab-owned — the change has left its journey, so the ladder falls through (fresh agent → yellow, else the gray floor) rather than rendering any fab hue (§ Design Decisions → Skipped display-state falls through the whole ladder).

The result type is `StatusDotState = { phase: DotPhase; shape: DotShape; waiting?: boolean }`. `hasFreshAgent(win)` is `agentState ∈ {active, waiting, idle}` — #314 already clears stale/shell-reconciled values server-side (the reconciler + rollup omit a plain-shell pane), so a non-empty rolled-up `agentState` on the window IS fresh; no client-side staleness heuristic (R4).

**Waiting halo — additive attention overlay, ladder-exempt** (R2): when `state.waiting`, `StatusDot` appends the `rk-waiting-halo` class to the dot element — a **pulsing yellow box-shadow ring** layered around it (the `rk-waiting-halo` keyframe in `globals.css`, driven by `var(--color-signal-yellow)` — the semantic is constant (yellow = "needs you now" in every theme) while the value re-themes: dark `#facc15`, light `#b07d02` gold, `ui/visual-design.md` § Design Decisions → Signal hues are per-theme tokens). It is **ADDITIVE** — the core hue AND shape are untouched (a blue building dot keeps its blue core; a failed dot keeps its failed shape). NEVER a hue-flip — family identity must survive attention. The class rides the dot element itself (box-shadow renders outside the border-box, disturbing neither size nor hue). Under `prefers-reduced-motion` the halo is a **static yellow ring** (no pulse). The glance rule: **blue = still cooking, green = out the door, yellow core = my ad-hoc agents, gray = just a terminal, yellow HALO = needs me now.**

**Hue = phase** — four hues (spec § The Channel Model). `fabPhase(stage)` is the **two-stop split**: `intake`/`apply`/`review` → `building` (local work in progress); everything else — `ship`/`review-pr`/`done`, plus unknown/absent (`hydrate` lands here via the default arm) → `prReady` (local work complete, "PR is ready"). The split is **stage-based, never `prNumber`-based** — the dot must not consult PR fields; alignment with PR existence stays emergent, since `/git-pr` creates the PR mid-ship. `DotPhase = "building" | "prReady" | "agent" | "none"`. `PHASE_HUE: Record<DotPhase, string>` maps phase→core-hue token:

| Phase (`DotPhase`) | Family / source | Hue token |
|--------------------|-------------------|-----------|
| `building` | cool fab — intake · apply · review | `text-signal-blue` |
| `prReady` | cool fab — ship · review-pr · done (+ unknown/absent stage) | `text-accent-green` |
| `agent` | warm ad-hoc agent | `text-signal-yellow` |
| `none` | gray L0 floor (no journey) | `text-text-secondary` |

> **Why exactly two fab hues**: blue vs green answers "still cooking vs out the door" at a glance — the one pipeline distinction worth a hue on a 7px dot (the exact stage lives in the `fab` register on both register surfaces). Purple and orange are not dot hues — purple stays in the glyph/segment vocabularies. The maximal one-fab-hue reduction was rejected: it loses the building/PR-ready glance. (`aqo6`)

**Shape = status** — ONE vocabulary, three shapes, the same meaning in every hue, rendered by `StatusDot` from `{phase, shape}` with `color = PHASE_HUE[state.phase]` always (no per-shape color forcing); the halo is layered on top when `state.waiting`:

| Shape (`DotShape`) | Meaning | fab `fabDisplayState` | Rendering |
|--------------------|---------|------------------------|-----------|
| `solid` | running / live | `active` / `ready` / unknown (+ mid-turn agent, flowing floor) | filled circle (`backgroundColor: currentColor`, `border: none`) in phase hue |
| `ring` | at rest | `pending`, **`done` (parked)** (+ idle agent, quiet shell) | hollow circle, `1.8px solid currentColor` border in phase hue, transparent fill |
| `failed` | needs rescue | `failed` | **dotted ring** (`1.2px dotted currentColor`, transparent) in phase hue + a centered small **red** `bg-signal-red` dot (`w-[3px] h-[3px]`) |

Every shape EXCEPT `failed` renders at one uniform 7px footprint (`DOT_SIZE = "w-[7px] h-[7px]"`). The **`failed` dot is the lone size exception** — a slightly larger 9px footprint (`w-[9px] h-[9px]`): a CSS `dashed` border can't control its dash count and at 7px fits only ~4 dashes that read as flower petals, so it uses a `1.2px dotted` border at 9px, which renders as a delicate bead ring, with the `3px` red center sitting inside the 9px ring's ~6.6px hole.

**Shape mapping** — `fabShape(displayState)`: `pending`→`ring`; `failed`→`failed`; **`done`→`ring`** (a parked-done change is RESTING — journey complete; its green hue says "done", the merged glyph says how it ended); `active`/`ready`/unknown/absent→`solid` (a live fab window with a future/unrecognized state still reads as a live dot, not gone). `skipped` never reaches `fabShape` — the ladder fall-through handles it.

**Red — the honest split**: DOT-red appears in exactly one way — the small center dot of a `failed` dotted ring (a failure reads as a dotted ring **in its phase hue** with only the red center; no whole-dot red tint). The row GLYPH separately uses red for a failing PR — that is the glyph channel's vocabulary, not the dot's.

**Gray L0 floor** (`phase: "none"`, lowest precedence, no fab ownership + no fresh agent) is **monochrome gray** — color is reserved for the two journeys: `activity === "active"`→gray `solid` filled circle, else gray `ring`. No phase hue is ever applied here.

**Composed examples** (rows = phase/hue, cols = status/shape). The **waiting halo overlays ANY cell** — it is an overlay applicable to every tier, not a matrix row:

| Phase (hue) | ring (at rest) | solid (live) | failed |
|-------------|----------------|--------------|--------|
| building (blue) | blue ring (stage pending) | blue solid (intake/apply/review active·ready) | blue dotted-ring + red center (review failed) |
| PR-ready (green) | green ring (stage pending / **parked done**) | green solid (ship/review-pr active·ready) | green dotted-ring + red center (review-pr failed) |
| agent (yellow) | yellow ring (idle) | yellow solid (active/waiting mid-turn) | — |
| plain (gray floor) | gray ring (idle) | gray solid (active) | — |

**Accessibility** — every dot carries `role="img"` + `aria-label` composed from journey + status + **additive attention suffix**, never color alone (colorblind a11y + Constitution V). `role="img"`/`aria-label` are the accessible name and the dot's ONLY a11y surface: it carries **no `tabIndex`** — the row treeitem is the focus target, and focusing it opens the flyout card, which reuses the same `dotLabel` text as its header (§ Row-hover register flyout card). `dotLabel(win, state)` lives in its OWN module `status-dot-label.ts` (so both `status-dot.tsx` and the flyout card import it without an import cycle; `status-dot.tsx` re-exports it, keeping its public surface stable). It composes a **core label + additive `— agent waiting {dur}` suffix** (`coreLabel` + the `state.waiting` suffix): (`260706-y1ar`, `aqo6`)
- **fab tiers** (keyed on `phase ∈ {building, prReady}`, so a fab window whose `skipped` display-state fell through the ladder reads its floor/agent word — matching the dot it actually renders): the hue word (`FAB_PHASE_LABEL`: `building`→"building", `prReady`→"PR-ready") + a status word derived from `fabDisplayState` via `fabStatusWord` — NOT from the shape (`done` and `pending` both render the resting ring, but a parked-done change reads "parked", never "pending"): `pending`→"pending", `failed`→"failed", `done`→"parked", `ready`→"ready", `active`/unknown→"active" — e.g. `"building — active"`, `"PR-ready — parked"`, `"building — failed"`. NO PR words and no raw stage word — PR facts live in the glyph + register surfaces, the exact stage in the `fab` register.
- **warm agent tier** (`phase === "agent"`): agent-native words via `AGENT_SHAPE_LABEL` — the idle `ring` reads **"idle"** (NOT the fab-stage "pending") and `solid` reads "active" — e.g. `"agent — active"`, `"agent — idle"`. (`AGENT_SHAPE_LABEL.failed` is unreachable from the agent tier — retained only for `Record<DotShape, …>` totality, documented as such in the code comment.)
- **L0 floor**: the bare tmux activity word (`"active"`/`"idle"`).
- **Waiting suffix**: when `state.waiting`, append `" — agent waiting {dur}"` (duration from the rk-computed `agentIdleDuration`, present for `waiting`/`idle`) — so a review-failed waiting window reads `"building — failed — agent waiting 3m"` (R3).

**Impl symbols** — in `pr-status-model.ts` (colocated, see § PR Status exports): `DotShape` (`"ring" | "solid" | "failed"`), `DotPhase` (`"building" | "prReady" | "agent" | "none"`), `StatusDotState = {phase, shape, waiting?}`, `fabPhase`, `fabShape`, `hasFreshAgent` (file-private), `prOwnsGlyph`, `prGlyphColor`, `PHASE_HUE`, and the two-family `statusDotState`. In `status-dot-label.ts`: `dotLabel` + the file-private `coreLabel`/`fabStatusWord` + the `FAB_PHASE_LABEL`/`AGENT_SHAPE_LABEL` maps. In `status-dot.tsx`: `DOT_SIZE`, the three shape renderers returned directly by `StatusDot` (incl. the `rk-waiting-halo` class append), and a re-export of `dotLabel`; it imports `statusDotState`/`PHASE_HUE` from `pr-status-model.ts` and `dotLabel` from `status-dot-label.ts`. The component takes `{ win }` and returns one `<span>` per shape — no render-prop callback, no wrapper.

> **No PR maps on the dot.** The dot renders from `PHASE_HUE` + the label maps only. `isFailish`/`PR_STATE_COLORS`/`PR_CHECKS_COLORS`/`PR_REVIEW_COLORS` serve the glyph color chain and the Pane-panel L3 `PR` register segments (see § Shared PR vocabulary); none of them is consulted by `statusDotState`.

**Why this shape** (design decisions): (1) two families let a glance separate "my fab pipeline" (cool blue→green) from "my ad-hoc agents" (warm yellow) from "just a terminal" (gray) — the user's own two-journey framing; the blue/green two-stop encodes the one pipeline distinction worth a hue (still cooking vs out the door). (2) shape meaning is uniform across every hue — fully compositional, so the doc needs four small legend strips instead of a per-cell matrix; a parked-done change is simply "green + at rest" (the resting ring), no dedicated square shape. (3) the additive yellow halo keeps family identity intact when attention is highest (§ Design Decisions → Waiting attention is an additive halo, never a hue-flip). (4) keeping PR off the dot avoids double-encoding with the row glyph (one fact, one channel — a merged PR reads purple once, on the glyph) and keeps new PR-adjacent states (draft, checks-pending) from pressuring the dot — see § Design Decisions → PR is evicted from the dot. (`260706-y1ar`, `aqo6`)

**Call sites** — the three surfaces are bare `<StatusDot win={win} />`: (1) sidebar `WindowRow` — ONE leading dot, wrapped in a `data-testid="status-dot-tap"` span that on COARSE pointers is a leading tap zone (≥32×36px, dot centered, `touch-action: none`) wired to the row flyout gesture — the SECONDARY coarse target, sharing the row's scrub handlers with the 56px status rail at the row's right edge, which is the PRIMARY tap/scrub home (`pointerdown` opens the card and captures the pointer, a held slide scrubs the single-open card across rows, release keeps the last card open — § Row-hover register flyout card; the rail itself is sidebar.md § Sidebar Row Icon System / § Rest-state PR glyph); on fine pointers the wrapper is inert and a dot click selects the row; (2) the `SessionTiles` window tile — leading dot before the window name (dot + name + fab-stage badge + rest-state PR glyph + text preview); (3) pane panel `WindowPanel` `headerRight` — `<StatusDot win={win} />` before `{win.name}`. Surfaces (2) and (3) carry the dot alone with no hover-card of their own — the PANE panel itself and the sidebar row flyout are the register-detail surfaces. The dot's inputs (`agentState`, `fabChange`/`fabStage`/`fabDisplayState`, tmux `activity`) all ride `WindowInfo` via SSE — no PR field among them; the halo keyframe is the only bespoke CSS (`globals.css` `rk-waiting-halo`). Tests: `status-dot.test.tsx` (the ladder across floor/agent/fab families × shapes — incl. the parked-done green ring, the skipped fall-through, and a merged-PR fab window rendering the fab arm's state with no purple/orange/square — plus the additive halo and `dotLabel` composition incl. the waiting suffix, and asserts the dot carries no native `title`); `pr-status-model.test.ts` covers the ladder, `prOwnsGlyph`, and `prGlyphColor` (the checks-pending yellow + draft-outranks-pending cases); the reduced-motion static-ring form is asserted via the `agent-next-waiting.spec.ts` e2e (jsdom can't evaluate `globals.css` media queries).

### Row-hover register flyout card (`sidebar/row-flyout-card.tsx`)

The sidebar's **tier-2 hover-card** system — the app's status-detail hover surface: ONE shared card shell, the `useRowFlyout` hook (placement arms, the `size()` containment cap, the held-state key, portal/focus wiring, the notch) parameterized by a per-tier `content` render prop, consumed by all THREE row tiers — window, session, and server-group header (§ Design Decisions → One card shell, three tiers). The WINDOW tier's card is built on `@floating-ui/react` with **pointer-conditional placement** — on FINE pointers it opens on **whole-ROW hover** at a **fixed x** (the sidebar's right edge, `placement: "right"`); on COARSE pointers it anchors **below the row** (`bottom-start`, `top-start` fallback) with its width capped short of the row's 56px status rail so the finger's column stays visible and touchable mid-scrub. It is the single surface for all three triggers — fine-pointer row hover, keyboard row focus (the roving-tabindex treeitem, Constitution V), and coarse-pointer touch (the rail is the PRIMARY tap/scrub target, the leading dot tap zone the SECONDARY on the same handlers — press opens; a held slide scrubs the card across rows) — so status detail stays reachable by pointer, keyboard, and touch alike. The SESSION and SERVER-GROUP tiers' cards are **coarse-only** surfaces (`coarseOnly`) — their one trigger is the rail's tap/scrub `openNow`, the hover/focus triggers stay disabled, and placement is always the coarse arm, because fine pointers keep the identity tips + hover clusters as those tiers' surfaces. The row is a large forgiving target where the 7px dot was a precise one, and on fine pointers the fixed x means the card never jitters under the pointer. (`93dy`, `ys3q`, `b8eu`, `260817-ve5m`)

**Wiring** — `useRowFlyout({ suppressed, coarseOnly, content })` returns `{ setReference, referenceProps, card, open, openNow, close }`; each consuming row attaches `setReference` + spreads `referenceProps` on the **row root** (the floating reference is the ROW, not the mouse and not the dot — the session row merges the setter/props with its identity tip's, since the root references both popups) and renders `{flyout.card}` as its last child. The card's body is the **`content({ close })` render prop**, built ONLY while the card is open (the mount-only-while-open perf contract) — `close` lets action rows run the close-then-open popover handoff; the window tier passes `<WindowFlyoutContent …>` (registers + links + action rows), the session/server tiers pass their own title/facts/action content (below). `useFloating` reads `useCoarsePointer()` itself and branches (the coarse-only tiers force the coarse arm via `coarseOnly`): FINE — `placement: "right"`, middleware `offset(6)` / `flip()` / `shift({ padding: 8 })` / `size()` (a symmetric inline-max-width reset) / `arrow()`; COARSE — `placement: "bottom-start"`, middleware `offset(6)` / `flip({ fallbackPlacements: ["top-start"] })` (near the drawer bottom) / `shift({ padding: 8 })` / **`size()`** / `arrow()`, where `size()` caps the card's max-width at reference-width − `STATUS_RAIL_WIDTH_PX` (56, exported from this module) − 8px gap, floored at 120px — the containment invariant: the card's right edge stops BEFORE the rail column and never renders off-screen. Shared: `strategy: "fixed"`, `whileElementsMounted: autoUpdate`, `FloatingPortal` to `document.body` (escaping the sidebar's `overflow:hidden` clip). Interactions: `useHover` (`mouseOnly: true` so touch never hover-opens, `move: false`, function-form `delay`, `handleClose: safePolygon()` — the bridge letting the pointer travel row → card to click a link), `useFocus`, `useDismiss` (Escape / outside press / blur) — hover/focus gated `enabled: !suppressed && !coarseOnly`. Deliberately **no** `useRole({ role: "tooltip" })` — the card holds real links (§ Design Decisions → No `role="tooltip"` on the status detail hover-card). Surface tokens are the shared ones (`bg-bg-primary border border-border rounded-md shadow-lg`, monospace, `w-max`) — no new color tokens; the `max-w-xs` cap is fine-pointer-only (on coarse the `size()` middleware owns the width).

**Delay + warm window + single-open** — `FLYOUT_OPEN_DELAY_MS = 350` cold; **0 while the cluster is warm**, where warm = another card is open right now OR one closed under `FLYOUT_WARM_WINDOW_MS = 500` ago. So sweeping the pointer down the tree retargets instantly instead of strobing. The cluster state is **module-scoped** (`activeFlyout` + `lastClosedAt`, plus a `resetFlyoutWarmState()` test seam), NOT React context — see § Design Decisions → Flyout warm window is module state, not a nested `FloatingDelayGroup`. `flyoutOpenDelay()` is handed to `useHover` in **function form**, evaluated at event time, so warmth set by another row is seen without a re-render. `activeFlyout` also enforces **single-open**: opening closes any other open card. `lastClosedAt` is stamped only when the closing flyout was the active one, so a no-op close (a drag-start before the delay elapsed, or a close racing another row's open) never falsely arms the warm window; an unmount-while-open releases the coordinator the same way.

**Suppression** — `suppressed` (the window row passes `ghost || showPinPopover || showLabelPicker`; the session row `ghost || showColorPicker`; the server group `showColorPicker`) closes an open card and disables the hover/focus triggers, so the card never fights the row's other layers. The imperative `openNow()` honors the same gate with an early return. A drag start calls `flyout.close()` from the row's `onDragStart`.

**Slide-to-scrub (coarse pointers)** — the touch translation of the hover sweep, with every tier's rail sharing the ONE `useRailScrub` handler trio (spread onto the target element): the 56px status rail (primary — the visible, learnable home) and the window row's leading dot tap zone (secondary, on the same handlers). The target's `pointerdown` stops propagation, calls `flyout.openNow()`, and captures the pointer (`setPointerCapture(e.pointerId)`); while captured, `pointermove` hit-tests the finger position via the exported `scrubTargetAt(clientX, clientY)` — `document.elementFromPoint` + `closest(RAIL_ROW_SELECTOR)` + a lookup in the **scrub registry** (`flyoutScrubTargets`, a module-scoped `Map<HTMLElement, () => void>` from row root element to that row's imperative `openNow`, spanning ALL three tiers — window, session, and server-group rows register alike — living beside the `activeFlyout`/`lastClosedAt` coordinator, populated/unpopulated by an effect inside `useRowFlyout` keyed on the reference element, and cleared by the same `resetFlyoutWarmState()` test seam). Both ends of the gesture resolve the row root with the IDENTICAL shared selector (`RAIL_ROW_SELECTOR = "[data-rail-row]"`, exported from this module — every tier's `useRailScrub` start-handler `closest` and `scrubTargetAt` alike): every non-ghost rail-bearing row root carries the `data-rail-row` attribute, the one shape covering all three tier DOM shapes (window treeitems with `data-window-id`, session treeitems with `data-session-row`, non-treeitem server-group headers — § Design Decisions → Shared `data-rail-row` hit-test attribute). Over a DIFFERENT registered row the move retargets the single-open card across rows AND tiers by invoking that row's `openNow` (the coordinator closes the previous card); over non-row elements (gaps, the open card itself) or rows without a registered flyout it returns null and the current card stays open — no flicker-close. Suppressed rows are skipped by `openNow()`'s existing `suppressed` early-return (the registry effect re-registers when the gate flips, so a scrub never invokes a stale gate; unmount unregisters, so an SSE-removed row can't be retargeted). `pointerup`/`pointercancel` releases the capture and the last card STAYS open — dismissal is the existing `useDismiss` outside-press. The scrub NEVER selects or navigates a row (`onSelectWindow` never fires; the trailing click handler only stops propagation), and the row's `onDragStart` early-returns while a scrub is active so the gesture can't escalate into an HTML5 row drag — belt to the targets' `touch-action: none`, which keeps a rail/zone-started drag from scrolling the drawer while drags starting elsewhere on the row scroll normally. (`ys3q`, `b8eu`, `260817-ve5m`)

**Held-rail highlight (all tiers)** — while a row's card is open (tap-held or mid-scrub) that row's rail lightens: the band steps up one shade via `railHeldBand` (a deeper `color-mix` share of the tier's step-up shade — the hover tint, or the selected tint on an already-selected row) and the seam brightens to `RAIL_HELD_SEAM` (`var(--color-text-secondary)` — an existing token, brighter than `--color-border`); no highlight at rest. Rest bands derive per tier via `railRestBand` (the inset base mixed with the tier's rest tint — session `tint.base`, server header base/selected, the selected window row's selected shade; untinted window rails keep the plain `bg-bg-inset` class). The key is the row-local `flyout.open` state — the same key the window row's held hover-shade uses — so the highlight travels row-to-row with the single-open card during a scrub (retargeting closes one row's card and opens the next's). No new color tokens anywhere in the rail system. (`260817-ve5m`)

**Focus management** — the card is wrapped in `FloatingFocusManager` with `modal={false}` and `order={["reference", "content"]}`, which is what makes `FloatingPortal` render its tab-order guards so **Tab walks row → card links** in tree order. Two non-default settings are load-bearing: `initialFocus={-1}` (the manager's default would move focus to `order[0]` on open — a hover-open must never steal focus from the terminal) and `returnFocus` gated on a `focusInsideCard` flag set by an `onFocusCapture` on the card (the default returns focus even when nothing inside was focused, which on a hover-sweep close yanks focus to the just-left row's button and breaks the warm retarget). The flag resets on each fresh open via an effect keyed on the real `open` state — not inside `onOpenChange`, because `useFocus` re-fires `onOpenChange(true)` for every `focusin` bubbling from the portalled card through the React tree, and a reset there would batch with the capture-phase set and negate it. Escape-dismiss and the tree's arrow-key nav are unaffected: focus stays on the row until the user tabs in.

**Content** — the full **four-register view** (`out` / `agt` / `fab` / `pr`) — the same register view the PANE panel renders, resolved by the SHARED helpers in `sidebar/registers.ts` (§ Register resolvers), so the two surfaces cannot drift. Absent layers render as absent (a plain shell pane shows only `out`). Around them:

- **Title bar** — the card's first element is an **identity title bar** rendered through the shared `PopupTitleBar` (`sidebar/popup-title-bar.tsx` — the one chrome carrier of the popup grammar "title bar = identity, body = facts", § Tooltips — Two-Tier Taxonomy): a full-bleed `bg-bg-inset` strip (negative margins cancel the card's `px-2 py-1.5` padding), `border-b border-border`, top corners rounded into the card radius. The title is `Window @N · pane %N · N panes` (`WindowFlyoutTitle`) — the tmux window id and the ACTIVE pane's id in primary text, the literal words in secondary (`PopupTitleBarSecondary`); static text derived from the already-passed `win`, degrading by omission (no `panes` → `Window @N` alone; `1 pane` singular). The bar's `right` slot carries ONE affordance: the quiet circled-(i) **docs link** (`STATUS_DOT_DOCS_URL` → the `docs/site/status-dot.md` GitHub blob; `docs/site` is not served locally, matching the `NOTIFICATIONS_HELP_URL` convention) — actions live in the sectioned action rows at the card's bottom (one affordance, one home). The status label `dotLabel(win, state)` — the same text as the dot's `aria-label` (single source, imported from `status-dot-label.ts`) — is the first body line below the bar. All card affordances `stopPropagation` on click. The `FloatingArrow` notch fill is axis-dependent (`notchFill` against `POPUP_TITLE_BAR_HEIGHT_PX`, both exported from `popup-title-bar.tsx`): on a SIDE placement (fine pointers) the arrow middleware's resolved `y` decides — `bg-inset` while it sits inside the title-bar band, the card-surface fill below it; on the coarse BOTTOM placement the arrow sits on the card's TOP edge, always inside the full-width title band (inset fill); flipped to TOP it sits on the bottom edge in the action area (card-surface fill) — notch + bar read as one shape either way. (`xb77`, `b8eu`)
- **Register lines** — `RegisterLine` renders a fixed-width prefix + read-only content, prefixes `"out "`/`"agt "`/`"fab "` and `"pr  "` (2-char key + 2 NBSPs = the same 4-advance column, written as escapes so a careless re-encoding can't mojibake them; codepoints pinned by a unit test). Each line carries `min-w-0 truncate`, matching the PANE panel rows, so long `fab`/`pr` text ellipsizes inside the card's width cap (`max-w-xs` on fine pointers, the `size()` rail cap on coarse) instead of painting outside the card. The `pr` line renders `getPrSegments` as `·`-joined colored segments. There is no separate `agent:` line — the `agt` register carries it.
- **Freshness line** — `checked Xs ago` via the `FreshnessLine` leaf (below).
- **PR link** — an `"Open PR #N ↗"` anchor whenever `prUrl` exists (`prNumber` is independently optional → `"Open PR ↗"` rather than `#undefined`), `target="_blank" rel="noopener noreferrer"`, `stopPropagation` so opening the PR never selects the underlying row. It is an anchor, not a button, so native middle/Ctrl-click work. **This is the PR click path** — the row's rest glyph is informational and swaps away under the pointer.
- **Action rows (Change color / Fork / Pin / Kill)** — the card's last block (below the freshness line), rendered for ALL pointer types: the color/pin/kill home on coarse (the in-row cluster is fine-pointer-only — sidebar.md § Rest-state PR glyph) and additive + Tab-reachable on desktop via the existing `FloatingFocusManager` `order={["reference", "content"]}`. It is a **sectioned list** (`CardActionList`) — a `-mx-2` counter-inset (the title bar's idiom) so the top border off the registers/freshness block and the inter-row hairlines (`divide-y`) span the card edge to edge — with ONE row per action (`CardActionRow`) in a fixed **change-color → fork → pin → kill** order, each row carrying an icon + label left and a muted sub-hint right (the sub-hint is the row's flexible `min-w-0 truncate` part; the label never truncates) at `min-h-[28px]` on fine pointers / `coarse:min-h-[36px]` on touch (`ACTION_ROW_CLASS`, the row-cluster touch-target convention). **Optional-handler gated** — the handlers thread through `WindowFlyoutContent` props (`onChangeColorAction?` / `onFork?` / `onPinAction?` / `onKillAction?`), and a consumer wiring no handler renders no row (fork additionally requires `canForkWindow(win)` — the double gate, § Fork affordance below). The rows: (1) **Change color…** (exact wording — the FIRST action row of every tier's card, on BOTH pointer worlds on the window card; `PaletteIcon`, `data-testid="row-flyout-color-action"`), running the Pin-row close-then-open idiom — close the card, THEN open that tier's existing picker (window: the combined Label picker via `setShowLabelPicker(true)`; session: the header palette's `SwatchPopover`; server: the group's portalled `SwatchPopover`, header-anchored on coarse) — with each tier's `suppressed` gate including its picker-open state, so popover-over-card precedence holds everywhere and re-opening is inhibited while the popover is open; (2) **Fork conversation** (`ForkActionRow`, `data-testid="row-flyout-fork-action"`, sub-hint "new window, same directory", the busy guard below); (3) **Pin to board…** (`PinIcon filled={pinned}`, `data-testid="row-flyout-pin-action"`, sub-hint the pin state — "not pinned", the board name via the `pinnedBoard` option threaded from the existing `WindowRow` prop, or a bare "pinned" when pinned without a known board) wired only when `showPinIcon`, closing the card BEFORE opening the row's existing `PinPopover` (ordering independent of the consumer's state-update timing; the `suppressed` gate already includes `showPinPopover`, so popover-over-flyout precedence holds); (4) **Kill window** (red `hover:text-signal-red` treatment, sub-hint "confirms first", `data-testid="row-flyout-kill-action"`, non-ghost rows only) → the existing `onKillClick(srv, session, windowId, false)` → `KillDialog` confirm path — never a force-kill (there is no modifier on touch). Registers are read-only text; the card's interactive elements are the PR link, the title bar's ⓘ docs link, and the action rows. The card carries no icon column and no copy interactions — those are PANE-panel idiom (§ Pane panel four-register view).

**Session and server cards (coarse-only surfaces)** — the same shared shell with `coarseOnly: true`, so hover/focus never open them, placement is always the coarse arm, and the rail's tap/scrub is the one trigger; each tier's content is built via the `content({ close })` render prop only while open. The SESSION card (`session-row.tsx`): a `PopupTitleBar` title `Session <name>` (secondary literal + primary name — the identity-tip grammar); one facts line `$id · N windows · ~path` — the identity tip's content verbatim, omission-degrading (`sessionId`/`sessionPath` ride the session payload; the path is `~`-abbreviated via `abbreviateHomePath`); action rows in order — `Change color…` (close-then-open into the row's color `SwatchPopover`; rendered only when `onColorChange` is wired), `Spawn agent…` (rendered ONLY when the consumer wires the optional `onSpawnAgent` — the board-route sidebar wires none, so no row there), `New window` (the existing `onCreateWindow` path), `Kill session` (red, sub-hint `confirms first` — the existing kill-dialog path via `onKillClick(server, name, windowCount, false)`; never a force-kill on touch). The SERVER card (`index.tsx` `ServerGroup` header): title `Server <name>`; facts `tmux -L <name> · N sessions` (server names ARE socket names — the ServerPanel tile identity-tip wording; the count derives from the group's own data, no new fetch); action rows — `Change color…` (close-then-open into the group's portalled `SwatchPopover`, anchored at the header element on coarse where the palette button is gated off), `New session` (the existing `onCreateSession(server)` instant create), `Kill server` (red, `confirms first` — `onKillServer(server)` → `requestKillServer` → the existing `killServerTarget` dialog, rk-daemon warning included). Each tier's `suppressed` gate includes its color-popover-open state, so popover-over-card precedence holds at every tier. The desktop session/server surfaces (identity tips + hover clusters) are unchanged. (`260817-ve5m`)

**Fork affordance (`ForkActionRow`)** — the card's SECOND sectioned action row (after Change color…, § Action rows above), branching this window's agent conversation into a new window in the **same session and directory**. It is **double-gated**: `canForkWindow(win)` (an equality guard on `win.chatProvider === FORKABLE_CHAT_PROVIDER`, the module constant `"claude"` — the same `WindowInfo` field the chat lens gates on, so no new data plumbing; a `codex` window and a plain shell pane both fall through) **AND** a supplied optional `onFork` callback. A consumer wiring no handler — the board-route sidebar — renders no row and throws nothing, the optional-prop idiom `onSpawnAgent`/`onColorChange` already use. Tooltip and `aria-label` share one `FORK_TOOLTIP` constant naming the same-directory semantics explicitly (`"Fork conversation — new window, same directory"`), and the row's muted sub-hint carries the "new window, same directory" half — that is what keeps a fork (branch this conversation *here*) legible against the spawn dialog (a fresh agent, usually in a new worktree), since nothing else guards the shared working tree. `stopPropagation` on click so forking never also selects the underlying row (the PR/docs links' idiom). The glyph is a hand-built inline SVG (`ForkIcon`, a git-fork shape) per the card's stated convention (inline SVG renders without a patched terminal font and themes via `currentColor`). (`260806-s4av`, `b8eu`)

**Fork in-flight guard** — `ForkActionRow` owns its own `busy` state, so the flag is **leaf-scoped**: only the row re-renders while a fork is in flight, honoring the card's render-performance discipline. The guard is load-bearing rather than cosmetic — `onFork` POSTs a mutating endpoint that CREATES a tmux window, so N clicks would create N fork windows. `disabled={busy}` (the spawn dialog's idiom) plus an early `if (busy) return` in the click handler is the belt-and-braces; the flag clears on settle for **both** outcomes, so a failed fork stays retryable. A `mountedRef` guards the settle `setState`, because the card unmounts when the flyout closes and a *successful* fork navigates away — settle-after-unmount is the normal case here, not an edge one. The handler chain (`app.tsx` `handleForkWindow` → `Sidebar` → `WindowRow` → `useRowFlyout`'s options) returns the **already-error-handled** settle promise, never rejecting, which is what lets the row simply await it.

**Fork navigation on success** — `handleForkWindow` (`app.tsx`) calls `forkWindow(server, windowId)` and on success routes through the **shared `navigateToSpawnedWindow(srv, windowId)`**: same-server → `navigateToWindow` (inheriting the window-switch slide transition), cross-server → `navigate({ to: "/$server/$window" })` + close the mobile sidebar. That helper is **shared** with the spawn dialog's `onSpawned` path, so the fork and the spawn cannot drift on the routing rule (§ Spawn-Agent Dialog → Cross-server nav on success). A **falsy `windowId`** skips navigation entirely — the backend's id resolve is best-effort, and routing with an empty id would land on a junk `/$server/@` URL, so the SSE stream surfaces the new row instead. A rejected fork raises an **error toast** carrying the server's message (`404` no forkable claude chat, `400` a non-repo directory) rather than failing silently; there is no bespoke fork dialog (constitution §IV).

**Freshness line — "checked Xs ago"**: `prFetchedAtEpoch(win)` parses `prFetchedAt` (the collector-join `PrFetchedAt` timestamp, architecture.md § PR-Status SSE Join) to **epoch SECONDS**, returning `null` when absent OR unparseable (`Date.parse` → `NaN`) so the card omits the line rather than rendering "checked NaNs ago". `FreshnessLine` is its own leaf component (`data-testid="row-flyout-checked"`) owning a live `useNow()` clock and rendering `checked ${formatDuration(nowSeconds - fetchedAtEpoch)} ago` — reusing `formatDuration` (`lib/format.ts`) rather than adding a relative-time formatter. After a manual refresh the timestamp visibly resets — the ambient version of the trust signal the PANE refresh button's checkmark gives. (`260715-nwla`)

**Perf** — every hard constraint from § Render Performance holds at all three tiers: open/hover state is **row-local** (inside `useRowFlyout`, never lifted to `Sidebar`), the card body **mounts only while open** (the `content` render prop builds it per open), and both live clocks (`WindowFlyoutContent`'s `useNow` feeding the `out` register plus `FreshnessLine`'s own) are **leaf-scoped inside that open card** — the row itself never ticks and no `nowSeconds` prop is threaded into a memoized component. `WindowRow`, `SessionRow`, and `ServerGroup` all stay `memo`'d; the session/server cards bind only existing stable identity-arg seams, so no new props churn the memo tree. The scrub registry honors the same discipline: element-keyed module state with a mount/keyed-effect registration spanning all tiers — no context provider, no lifted state, no new props through `ServerGroup` (its one `setReferenceEl` state set is a mount-time one-off that bails out on an identical node). The two clocks are two `setInterval`s while one card is open; collapsing them onto a single hoisted clock is an available optimization, not a contract fix.

## Tooltips — Two-Tier Taxonomy

Tooltips are a two-tier system with a **hard boundary and no middle species** (§ Design Decisions → Two-tier tooltip boundary):

- **Tier-1 — `Tip`** (`components/tip.tsx`): **names a control**. One-line plain-text label + optional keycap chip (`kbd`) + optional dim modifier note. Carries the W3C tooltip pattern — `role="tooltip"` on the floating element, `aria-describedby` on the anchor while open. NEVER interactive content. This is the app-wide replacement for native `title=` on interactive chrome controls.
- **Tier-2 — hover-cards** (the sidebar row flyout card, § Row-hover register flyout card; the session/server **identity tips**, `sidebar/identity-tip.tsx`): hold a second line of **state** and/or **interactive content** (real `<a>` links). Deliberately role-less (§ Design Decisions → No `role="tooltip"` on the status detail hover-card). The identity tips land tier-2 by the promotion rule — they carry a second line of state (ids, counts, paths) — but stay non-interactive (`pointer-events-none`, no links/registers): slim `IdentityTipCard`s pairing a `PopupTitleBar` (identity) with ONE plain-text body line (facts), on a plain 300ms open delay (`IDENTITY_TIP_OPEN_DELAY_MS`) with no `TipGroup`/warm-window coupling, hover/focus-only (`mouseOnly`, suppressed under coarse pointers). (`xb77`)

**Shared title-bar grammar** — all three row popups render their header through `PopupTitleBar` (`sidebar/popup-title-bar.tsx`), the single chrome carrier of the grammar "title bar = identity, body = facts": a full-bleed `bg-bg-inset` strip (negative margins escape the host card's `px-2 py-1.5` padding), `border-b`, rounded top corners, secondary-literal/primary-handle text slots (`PopupTitleBarSecondary`), and an optional right-edge cluster (only the window card uses it — fork + docs). The tier weight distinction lives in the BODY, not the chrome: the window card's body is registers + links, the identity tips' body is one plain-text line. The notch-fill seam is shared too: `notchFill(arrowY)` (vs `POPUP_TITLE_BAR_HEIGHT_PX`) gives every popup's `FloatingArrow` the inset fill while it lands on the title band. (`xb77`)

**Promotion rule**: a tooltip that needs a second line of state or anything clickable is tier-2, not a fatter tier-1. Consequence at the `title=` migration boundary: native titles whose value is *state or a content reveal* rather than a control name stay native `title=` — they are neither converted to `Tip` nor promoted to new hover-cards. Left native by this rule: the PR-URL reveal and cwd reveal (`sidebar/status-panel.tsx`). (`260722-73al`, `xb77`)

### Tier-1 `Tip` (`components/tip.tsx`)

`Tip` wraps a **single child element** and clones it with the floating reference props/ref merged (`useMergeRefs`) — **no wrapper DOM node** is added, so layouts and the top-bar overflow fit's hidden width-measurement probe are unaffected (§ Design Decisions → Clone-child reference API). Built on `@floating-ui/react` (already a dependency — the tier-2 hover-card uses it too). A falsy `label` renders the child untouched (the conditional-tooltip idiom, e.g. "Copy version", "Create a server first").

**Visual shell — "quiet card"**: `bg-bg-card`, 1px `border-border`, 5px radius, soft shadow, 11px mono, `text-text-primary` label. The floating element is `pointer-events-none` (tier-1 holds nothing interactive, so it can never intercept a click) and `max-w-[40ch]` + `whitespace-nowrap` + truncate backstop the one-line ≤40ch cap. Optional slots: a `note` (dim `text-text-secondary` modifier, e.g. "⇧click: force") and a `kbd` keycap chip (`bg-bg-inset`, 1px border with a 2px bottom edge for the "key" read, 3px radius, 10px type). The `kbd` value is a plain string prop, but **for a registry-bound action the call site resolves the HOST-EFFECTIVE chord** rather than hard-coding a chord: `useKeybindings()` → `byAction.get(actionId)` → `formatCombo({ code, tier }, host.platform)` when the binding is `enabled`, else `undefined` so **no chip renders** — a tip advertising a dead chord would lie (§ Keyboard Shortcuts → Palette hints applies the same rule to palette hints). This makes every such chip reflect overrides and per-platform tiers. Five `Tip`-chip call sites resolve a chord this way: the top bar's Settings gear (§ Right cluster → Settings gear), the bottom bar's Compose `a▏` and palette `⌘K` chips (§ Bottom Bar), and the Open and Split split-buttons' primary segments (§ Open split-button, § Split control); the chevron menu's Settings and Keyboard shortcuts rows apply the same derive-and-omit rule to their trailing `MENU_ROW_KBD_CLASS` keycaps (§ Right cluster → overflow chevron menu). The same derive-and-omit rule governs chord clauses in prose copy — placeholders and empty states (§ Education micro-copy). A **computed, non-registry** `kbd` string is correct only for a chord with **no registry binding** — the compose/chat submit + insert editing chords, which are focused-textarea keys the registry does not own. Those are still platform-correct without the registry: Send resolves through the shared `composeSubmitKeycap()` (`formatCombo({code:"Enter",tier:"cmd"}, detectPlatform())` → `⌘Enter` / `Ctrl+Enter`), while the Insert chips carry literals that differ per surface — the strip's reads `Enter` (its Insert follows Enter; the Alt+Enter raw-insert chord lives in the tip's label text), chat's reads `Alt+Enter`. The `tip.tsx` prop doc states this contract. (`260801-mqim`, `260802-lj98`)

**Behavior contract** (user-approved design session):

- **Open delay** — 300ms on hover (`TIP_OPEN_DELAY_MS`); **0ms while the cluster is "warm"** (a sibling tip in the same group closed <500ms ago, `TIP_WARM_WINDOW_MS`) — macOS-menu sweep behavior. Delays ride `useDelayGroup`; outside any group the group context is `delay: 0`, so `Tip` falls back to its standalone 300ms open.
- **Warm clusters** — `TipGroup` (exported; a `FloatingDelayGroup` preset with `delay={{open: 300, close: 0}}`, `timeoutMs={500}`) wraps one chrome region: the top-bar's three regions (left breadcrumb cluster, center heading cluster, right control cluster — the latter contains the overflow menu and every registry control's popover), the sidebar root, the iframe URL bar, and the chat/compose button rows. A single-tip region needs no provider.
- **Keyboard** — opens immediately on `:focus-visible` (`useFocus` `visibleOnly` default), never on mouse-down focus (Constitution V).
- **Dismiss** — pointer-leave, Escape (`useDismiss`), and activating the control (`referencePress: true` — the tip never sits over the click's result).
- **Touch** — suppressed under `pointer: coarse` (via `useCoarsePointer`). The child renders unchanged with no reference props, portal, or ARIA wiring — the control's `aria-label` carries the name (§ Design Decisions → Suppress-by-early-return on coarse pointers).
- **Placement** — per-site `placement` prop, default `bottom` (top-bar convention); bottom-of-screen strips pass `top`, sidebar rows pass `right`. `offset(6)` / `flip()` / `shift({padding: 8})` / `autoUpdate` — the shared hover-card middleware set — flip and shift at viewport edges.
- **Reduced motion** — trivially satisfied: no fade, instant show/hide.

Named constants carry every magic value: `TIP_OPEN_DELAY_MS`, `TIP_WARM_WINDOW_MS`, `TIP_OFFSET_PX`, `TIP_SHIFT_PADDING_PX`.

**Migration — no native `title=` on chrome controls**: native `title=` is **REMOVED wherever `Tip` lands** (never both — the OS bubble would double the styled tip); `aria-label`s stay untouched. `Tip` covers the interactive chrome controls across ~15 component files: `top-bar.tsx`, `top-bar-overflow-menu.tsx`, `breadcrumb-dropdown.tsx` (the `title` prop — a component prop like `Dialog title=`, so kept under that name — renders as an internal `Tip` around the trigger), `open-button.tsx`, `waiting-badge.tsx`, `sidebar/index.tsx` (scope chip, copy capped at ≤40ch action labels), `sidebar/status-panel.tsx`, `iframe-window.tsx`, `chat-view.tsx` + `compose-strip.tsx` (the natural `kbd`-slot users — Send + the submit keycap, Insert + `Alt+Enter` in chat / `Enter` on the strip), `host-overview-page.tsx`, `swatch-popover.tsx`, and the board-route twin `board/board-header.tsx` (the `/board/$name` route re-implements chrome and does not render AppShell — see [tmux-sessions](/run-kit/tmux-sessions.md); its one real native tooltip — the unpin button — uses `Tip`; its three other `title=` matches are `Dialog` props, which stay native). **Seams that stay native `title=`**: `Dialog title=` component props everywhere; `title="Proxied content"` on the proxied iframe (its accessible name, asserted by `top-bar-overflow.spec.ts` and `web-view-lens.spec.ts`); `CollapsiblePanel`-style heading `title` props; and the tier-2 hover-card (untouched by the tier-1 migration). (`260722-73al`)

**Tests** — `tip.test.tsx` covers label/note/kbd render, `role="tooltip"` + `aria-describedby` wiring on open, focus-open, no render / no `aria-describedby` under a mocked coarse pointer, and label-less pass-through (7 tests). E2e `tests/e2e/tooltips.spec.ts` (+ sibling `tooltips.spec.md`) proves keyboard-focus open, hover open, and coarse-pointer absence, plus the palette chip's **resolved** keycap reading `Ctrl+K` — Playwright's `devices["Desktop Chrome"]` pins a **Windows** UA, so `detectPlatform()` returns `other` regardless of the runner's own OS. ## Attention Surfacing (`waiting` rollups + nav)

The per-window `waiting` overlay (agent blocked on a human) propagates UP the hierarchy as **count badges** and drives a **keyboard-first navigation** action and a **board-pane seam**. This is the UI half of #314's three-state `agentState` — see [agent-state](agent-state.md). All counts derive from the existing SSE session data already in the client — **no new endpoint, no `setInterval`/fetch** (Constitution II / code-quality anti-patterns).

**Shared rollup helpers** (`lib/waiting.ts`) — the single source of truth so every surface counts identically: `isWaiting(win)` (= `win.agentState === "waiting"`, keyed on the server-side window-level rollup that already applies `waiting > active > idle` across panes), `countWaitingWindows(windows)`, `countWaitingInSessions(sessions)`, and the instance-wide `countWaitingAcrossServers(sessionsByServer)` (which composes `countWaitingInSessions` over the streamed map). Pure functions over the streamed `WindowInfo`/`ProjectSession` shape.

**`WaitingBadge`** (`components/waiting-badge.tsx`) — a small count chip mounted unconditionally; **renders `null` when `count <= 0`** (attention badges are present only when they mean "something needs you"). Styling follows the existing count-chip vocabulary but in the **signal yellow** of the waiting overlay (`bg-signal-yellow/15 text-signal-yellow` — the *semantic* is constant: "yellow = an agent needs you now", the same glance language as the status-dot halo, in every theme; the *value* re-themes via `--color-signal-yellow`, `ui/visual-design.md` § Design Decisions → Signal hues are per-theme tokens), plus a `⚠` glyph. It is TEXT, not motion (the pulse lives on the per-window dot/seam) — legible via color + count + `aria-label`, never color-only. Mounted on four surfaces:

- **Session row** (`sidebar/session-row.tsx`) — count of the session's waiting windows (`countWaitingWindows(session.windows)`), rendered after the session name button (R8).
- **Host-page TMUX SERVERS server tile** (`host-overview-page.tsx`) — per-server count summed over the server's sessions (`countWaitingInSessions(sessionsByServer.get(name) ?? [])`), absolutely positioned top-right on the tile. One glance at `/` answers "does anything need me" (R9). Only attached servers stream windows, so an unattached server's count is 0 (badge absent) — never a wrong count.
- **Board header** (top-bar `BoardModeInfo`, `top-bar.tsx`) — count of the board's waiting panes (`waitingPaneCount` prop), rendered in the board-mode left info between the pane/server counts and the `⌘[⌘] cycle` hint (R10).
- **Sidebar SERVER-panel server tile** (`sidebar/server-panel.tsx`) — the fourth server-level surface, per-server count over the server's sessions. Placement **differs** from the Host-page tile: it rides the **same flex row as the tile's "N sess" count, right-aligned** (`flex items-center justify-between`) rather than absolute top-right, because the sidebar tile already occupies its top-right with a hover-revealed palette/kill action cluster (`top-1 right-1 z-10`) — the Host-page tile's `absolute right-2 top-2` would collide. `ServerTile` takes a plain `waitingCount: number`; `ServerPanel` takes the optional `waitingCounts?: Map<string, number>` and forwards `waitingCounts?.get(name) ?? 0` per tile, keeping the presentational panel decoupled from session data. The Sidebar computes the map in `sidebar/index.tsx` via `useMemo(() => …, [sessionsByServer])` over the already-consumed `sessionsByServer` (same `countWaitingInSessions` helper). Attached-server-only by construction (an unattached server is absent from `sessionsByServer` → count 0 → badge absent), the same accepted caveat as the Host-page tile — no eager attach-all: lazy-attach is deliberate, so an unattached server shows no badge. (`260708-4li7`)

**Board-pane waiting seam** (`board/board-pane.tsx` + `board-page.tsx`) — a waiting board pane gets a **3px pulsing yellow seam** (border-width system; the `rk-waiting-seam` class + `border-[3px]`), the board-pane form of the status-dot halo. Border precedence: a `waiting` pane always shows the seam (attention is the highest-priority signal); a focused-AND-waiting pane layers the accent focus shadow on top so it reads both. Under `prefers-reduced-motion` the seam is static yellow (`globals.css`). `BoardEntry` is a thin shape with no `agentState`, so `BoardPageContent` **joins each pinned pane back to its live `WindowInfo`** via `(server, windowId)` against the streamed `sessionsByServer` (use-boards attaches every board server, so window data incl. `agentState` is flowing) — a `waitingWindowIds` set (`${server}:${windowId}` keys) drives both the per-pane seam and the header count; a pane whose window is not yet in the snapshot is simply not waiting (no wrong signal).

**OS-level escape hatch** — inside the Electron desktop shell a fifth consumer, the `ShellBadgeReporter`, mirrors `countWaitingAcrossServers(sessionsByServer)` to the dock/taskbar badge, so the attention tier is visible when the window is not (§ Desktop-Shell Waiting Badge Reporter). Waiting only, like every surface above; a browser tab physically cannot do this, which is what the badge buys over the in-page badges.

**`Agent: Next waiting` palette action** (`app.tsx` `agentActions`, R11 — keyboard-first, Constitution V): cycles focus through windows whose rolled-up `agentState` is `waiting`, **current server first** (in sidebar order, from `flatWindows`) then other **attached** servers (from a live `sessionsByServerRef.current` read — unattached servers' window data isn't streamed, a known constraint). No-op with a `"No agents waiting"` toast when none. The cycle arithmetic is the pure `nextWaitingTarget(ordered, currentServer, currentWindowId)` helper (`lib/palette-agent-nav.ts`, unit-tested): empty → `null`; current window not in the list → first target (jump in); current IS a target → the next one **with wraparound** (`(idx+1) % len`). This is a deliberate contrast with `palette-move.ts` (reorder arithmetic, which does NOT wrap) — do NOT extend that module. Same-server targets navigate via `navigateToWindow`; cross-server targets `navigate({ to: "/$server/$window" })` (and close the mobile drawer). The action is appended to `paletteActions` as `agentActions`.

## Design Decisions

### No bounded-fallback timer on the waiting state
**Decision**: the create-server waiting state persists until the refreshed `servers` list contains the server — cleared by an event-driven effect on the list changing, with no timer and no polling.
**Why**: synchronous near-instant backend create makes a timer speculative; a polling loop would violate the no-client-polling anti-pattern.
**Rejected**: a ~5s bounded-fallback timeout for v1. If ever added it MUST be a single `setTimeout`, never a polling loop.
*Introduced by*: 260602-3i5d-fix-create-server-not-found-race

### No `role="tooltip"` on the status detail hover-card
**Decision**: the tier-2 status hover-card (today the sidebar row flyout card) advertises no `useRole({ role: "tooltip" })`.
**Why**: the W3C tooltip pattern requires a tooltip to contain NO interactive content, but this card holds real `<a>` links (PR + docs). Advertising `role="tooltip"` would lie to AT and wire a misleading `aria-describedby`.
**Rejected**: `role="tooltip"` (present in the plan, removed in review).
*Introduced by*: 260616-37ub-status-dot-tooltip, 260805-93dy-window-row-pr-glyph-register-flyout

### Two-tier tooltip boundary
**Decision**: tooltips are exactly two species with a hard boundary — tier-1 `Tip` (names a control: plain text + optional kbd/note, `role="tooltip"` + `aria-describedby`, never interactive) and tier-2 hover-cards (the sidebar row flyout card: state and/or real links, role-less). A tooltip needing a second line of state or anything clickable is tier-2; there is no fatter tier-1. Native `title=` values that are state or a content reveal (not a control name) stay native `title=` — neither converted to tier-1 nor promoted to new hover-cards.
**Why**: the two shells already had incompatible ARIA needs (§ No `role="tooltip"` on the status detail hover-card) — one visual language across both tiers, one clear rule for which to reach for, and no accidental middle species that lies to AT. Promoting state/content titles to new tier-2 cards is scope beyond naming a control, and two e2e specs assert those exact `title=` seams.
**Rejected**: a single configurable tooltip spanning both roles (re-introduces the role/interactivity conflict); promoting every native `title=` to a styled surface (builds hover-cards nobody asked for and breaks the asserted state-title seams).
*Introduced by*: 260722-73al-tip-tooltip-system

### Session/server identity tips are slim tier-2 hover-cards, not fattened Tips
**Decision**: the session/server identity tips are small role-less hover-cards on `@floating-ui/react` sharing the `PopupTitleBar` header (`sidebar/identity-tip.tsx`), not extensions of tier-1 `Tip`.
**Why**: the two-tier taxonomy's promotion rule is explicit — a tooltip that needs a second line of state is tier-2, not a fatter tier-1 — and the identity tips carry a second line of state (counts, paths, socket). Extending `Tip` would break its one-line `role="tooltip"` contract and its `pointer-events-none`/40ch invariants.
**Rejected**: extending `Tip` with a title-bar mode (dilutes the tier boundary every future tooltip decision leans on); reusing the full `useRowFlyout` machinery (it carries fork/focus-manager/warm-window weight these non-interactive cards don't need).
*Introduced by*: 260815-xb77-row-popup-identity-titlebars

### One status-detail surface, three triggers — the ROW, not the dot
**Decision**: window-row status detail is served by a single row-anchored flyout card serving fine-pointer row hover, keyboard row focus, and coarse-pointer touch (the status rail is the primary tap/scrub target, the dot tap zone secondary on the same handlers — press opens; a held slide scrubs the card across rows). There is no per-dot hover-card, and the `StatusDot` carries neither a `tabIndex` nor a native `title` on any of its three surfaces.
**Why**: the 7px dot was a precise pointer target and a second tab stop ahead of the row treeitem; the whole row is a large forgiving target and is already the focusable treeitem, so one surface covers every input modality with less markup, no jitter, and one fewer tab stop. Keeping a dot tip *and* a row card would mean two surfaces racing on the same hover. On coarse the rail gives the gesture a visible affordance and the card anchors below the row, capped short of the rail column (§ Row-hover register flyout card).
**Rejected**: keeping the dot tip for focus/touch alongside the row card (two overlapping surfaces, the dot tab stop retained); a mouse-following card (jitters and covers the row it describes); a hover preview inside the bottom PANE panel (detail lands far from the pointer); a `placement: "right"` card on coarse (no free space beside the mobile drawer — the card clipped off-screen).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout, 260816-b8eu-status-rail-card-actions

### Flyout warm window is module state, not a nested `FloatingDelayGroup`
**Decision**: the flyout's shared delay-group scope is module-scoped state (`activeFlyout` + `lastClosedAt`) consumed through floating-ui's function-form `delay`, not a second `FloatingDelayGroup` provider around the sessions tree.
**Why**: `useDelayGroup` binds to the NEAREST `FloatingDelayGroup`, and the session rows render tier-1 `Tip`s inside the same subtree — a nested provider would capture those tips, changing their delay and mixing tier-1/tier-2 warmth (the sidebar-is-one-warm-tip-cluster contract). Module state gives the flyout an independent warm cluster spanning every row, and the function-form `delay` is evaluated at event time so warmth set by another row is seen without a re-render.
**Rejected**: a nested `FloatingDelayGroup` (captures the session-row Tips); a flat per-row delay with no warmth (strobes on a row sweep).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout

### Element-keyed scrub registry beside the warm/single-open coordinator
**Decision**: the slide-to-scrub retarget uses a module-scoped `Map<HTMLElement, () => void>` (row root element → that row's imperative `openNow`) beside the `activeFlyout`/`lastClosedAt` coordinator, populated by an effect inside `useRowFlyout`; the gesture hit-tests with `elementFromPoint` + `closest()` to a row root and looks the handle up. Every rail-bearing tier registers in the SAME map, so a held slide retargets the single-open card across window, session, and server-group rows alike.
**Why**: module state is the established coordinator pattern in this file, costs no re-renders, and honors the memo tree — no context provider, no lifted state, no new props through `ServerGroup`. The element itself is the only always-present key: `rowKey` is optional, while the reference element is already known to the hook and needs no naming contract. Keying the registration effect on `openNow`'s closure means a flipped `suppressed` gate re-registers, so a scrub never invokes a stale gate.
**Rejected**: a React context of row handles (re-render churn through the memo tree); a `data-row-key`-keyed map (imposes a naming contract on an optional prop).
*Introduced by*: 260816-ys3q-mobile-pr-glyph-flyout-scrub

### Pointer-conditional placement inside one `useRowFlyout`
**Decision**: `useRowFlyout` reads `useCoarsePointer()` itself and branches placement/middleware/width-cap on it — fine: `placement: "right"` with the `offset(6)`/`flip()`/`shift({ padding: 8 })`/`size()` (inline-cap reset)/`arrow()` chain; coarse: `bottom-start` + `flip({ fallbackPlacements: ["top-start"] })` + `shift` + a `size()` cap (reference width − 56px rail − 8px gap, floored at 120px) + `arrow()`. One hook, two placement arms — plus a `coarseOnly` flag that forces the coarse arm (and disables hover/focus) for the session/server tiers, whose only trigger is the rail.
**Why**: the hook already owns all positioning; forking the hook or threading placement as a prop would spread the decision across consumers and risk drift. The `size()` arm is what enforces the containment invariant — the card's right edge stops before the rail column, so the finger's column stays visible and touchable mid-scrub.
**Rejected**: a separate mobile card component (duplicates the card body — the one-card-three-triggers principle); a CSS-only `max-w` calc (cannot know the reference row's width — `size()` measures it).
*Introduced by*: 260816-b8eu-status-rail-card-actions

### One card shell, three tiers
**Decision**: the flyout machinery is ONE shared shell — the `useRowFlyout` hook (placement arms, containment cap, held-state key, portal/focus wiring, notch) parameterized by a per-tier `content({ close })` render prop — consumed by the window (registers + links + action rows), session, and server-group rows (title + facts line + action rows each).
**Why**: all tiers are bound to one placement/containment/held-state implementation; duplicating the floating-ui wiring per tier creates three drift surfaces for the same behavior.
**Rejected**: per-tier card components with copied positioning (three drift surfaces); forcing session/server content through the window card's register renderer (registers are a window-only concept).
*Introduced by*: 260817-ve5m-three-tier-status-rail-cards

### Shared `data-rail-row` hit-test attribute
**Decision**: every rail-bearing row root carries a shared `data-rail-row` attribute, and BOTH scrub gesture ends (each tier's `useRailScrub` start-handler `closest` and the exported `scrubTargetAt`) select on it exclusively via the exported `RAIL_ROW_SELECTOR` constant.
**Why**: the three tiers have three DOM shapes (window rows are `treeitem` + `data-window-id`, session rows `treeitem` + `data-session-row`, server-group headers not treeitems at all) — a role-based selector cannot cover them; one attribute makes the selector identical at both gesture ends by construction.
**Rejected**: a union selector (three shapes to keep in sync at two call sites).
*Introduced by*: 260817-ve5m-three-tier-status-rail-cards

### No warmth coupling between the three row popups
**Decision**: the session/server identity tips use a plain open delay (`IDENTITY_TIP_OPEN_DELAY_MS = 300`) and join neither the sidebar `TipGroup` nor the window flyout's module-scoped warm window.
**Why**: the flyout deliberately keeps its warmth OUT of `TipGroup` because mixing tier-1/tier-2 warmth strobes; adding a third pool to either group re-creates the problem. Isolation is the shipped pattern.
**Rejected**: a unified cross-popup delay group — a real option later, but it changes tuned behavior for existing surfaces.
*Introduced by*: 260815-xb77-row-popup-identity-titlebars

### Fork affordance is double-gated: provider AND an optional handler
**Decision**: the flyout's fork action row renders only when `win.chatProvider === "claude"` **and** the consumer supplied an `onFork` callback; a consumer wiring no handler renders no row and throws nothing.
**Why**: the provider half is a data gate (the fork mechanism is Claude Code's `--resume <id> --fork-session`, so a codex window has nothing forkable) and reuses the exact `WindowInfo` field the chat lens already gates on — no new data plumbing. The handler half is a *capability* gate: `useRowFlyout` has no server or navigation access of its own, and the board-route sidebar has no business forking, so the optional-prop idiom (`onSpawnAgent`, `onColorChange`) gates the affordance per call site without the hook growing a dependency it cannot satisfy.
**Rejected**: a provider-only gate with a required handler (forces every consumer, including the board sidebar, to supply one); threading server/navigate into the flyout hook (widens a leaf hook's surface for one button).
*Introduced by*: 260806-s4av-row-flyout-session-fork

### Fork in-flight state is leaf-scoped in the fork row, and the guard is correctness not polish
**Decision**: `ForkActionRow` owns its own `busy` state with `disabled={busy}`, a redundant early `if (busy) return`, a `mountedRef`-guarded settle, and a clear on **both** outcomes — the guard lives inside the fork affordance wherever that affordance's home is.
**Why**: `onFork` POSTs a mutating endpoint that CREATES a tmux window, so N clicks create N fork windows — the guard is the only thing preventing that, not a loading-spinner nicety. Keeping the flag inside the row (rather than lifting it to the card or the window row) means only the row re-renders during a fork, honoring the card's render-performance contract. The `mountedRef` is required rather than defensive: a *successful* fork navigates away and the card unmounts, so settle-after-unmount is the common path.
**Rejected**: lifting `busy` to `RowFlyoutContent` or `WindowRow` (re-renders the whole card / breaks the row's `memo` discipline); relying on `disabled` alone (leaves a click-during-settle window); clearing only on success (a failed fork would be permanently unretryable); a shared "busy action row" abstraction (one consumer, premature).
*Introduced by*: 260806-s4av-row-flyout-session-fork, 260816-b8eu-status-rail-card-actions

### Rest glyph as an absolute overlay on the last slot, not a third flex slot
**Decision**: on FINE pointers the row's rest-state PR glyph is absolutely positioned at the icon cluster's right edge, over the kill button's 24px slot, and hidden by a display swap; the pin/kill buttons keep their opacity gating. On coarse pointers the glyph renders in the status rail's fixed 16px slot instead — the overlay is fine-pointer-only (sidebar.md § Design Decisions → The status rail is the coarse trailing zone).
**Why**: the action buttons are opacity-gated precisely so they occupy their slots at rest and stay keyboard-focusable. A display swap of the buttons themselves would make them unfocusable at rest (a keyboard regression), while overlaying the glyph delivers the approved "PR sits exactly where ✕ sits, only the last slot swaps" geometry with zero layout shift and no focus changes. Coarse has no hover cluster to overlay, so the rail slot is the glyph's home there — one PR channel per pointer world.
**Rejected**: a `hidden`/`flex` swap on the buttons (breaks Tab reachability at rest); a third flex slot (the glyph would sit left of the ✕ rather than in its place); an opacity fade over reserved space (the user rejected coexistence — the rest state must go away entirely); rendering BOTH the overlay and the rail slot on coarse (double-paints the same fact inside the rail's 56px).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout, 260816-b8eu-status-rail-card-actions

### Draft is a glyph-only gray, not a dot state and not a second icon
**Decision**: draft lives on the row glyph's existing color axis as `text-text-secondary`, and only there — the dot carries no PR state at all, so a draft is invisible to the dot while the glyph reads gray. Draft keeps the shared `GitPullRequestIcon`, varied only by color (the icon axis belongs to closed's ✕ variant, not draft).
**Why**: the glyph's color axis is a single pure function returning a Tailwind token, whereas the dot's hue axis is owned by the two-family channel model (cool = fab pipeline, warm = ad-hoc agent) — a draft hue there would break the family-identity glance rule the whole palette rests on, and a draft *shape* would need new geometry in `status-dot.tsx` plus label-map entries. Gray is the mapping already in the user's head (GitHub renders drafts gray) and `text-text-secondary` is the established inert/no-journey token in this exact model (`PHASE_HUE.none`), at ~4.8:1 in the light theme against the 3:1 WCAG floor for graphical objects. The two channels then answer different questions rather than duplicating one: the glyph says *whose turn is it*, the dot says *what runs here, is it healthy*.
**Rejected**: a new muted token or raw hex (contradicts the glyph's no-new-color-system rule); importing `PHASE_HUE.none` instead of the literal (couples the glyph's color axis to the dot's phase map — precisely the coupling being avoided); GitHub's distinct dashed draft glyph (a second SVG is more maintained surface for one bit color already carries, and the Sidebar Row Icon System pins one icon system per surface).
*Introduced by*: 260807-e30p-draft-pr-row-glyph-color

### The draft glyph branch sits below fail and is gated on `prState === "open"`
**Decision**: `prGlyphColor`'s chain is closed-muted → fail-ish → open-and-draft → open-checks-pending-yellow → open-green → merged-purple, with the draft branch conjoined on `win.prState === "open"`.
**Why**: a draft whose checks fail (or that has changes requested) is a problem first and a draft second, so `isFailish` keeps first position among the open cases; draft-first would hide a red signal behind a gray one on exactly the rows still owing work. The open-gate keeps the closed path untouched *by construction* (merged already returns above the fail branch) rather than defended only by GitHub's server-side un-draft-on-merge, and confines draft to displacing the open cases below it — the checks-pending yellow included (drafts stay muted while their checks run).
**Rejected**: draft above fail (buries the red signal); an ungated `if (win.prIsDraft)` (behaviorally identical today, but leaves the merged path defended by remote behavior instead of local structure).
*Introduced by*: 260807-e30p-draft-pr-row-glyph-color

### Closed PR earns a muted ✕ glyph, ranked above fail
**Decision**: `prOwnsGlyph`'s allowlist is `open`/`merged`/`closed` (an absent/unknown `prState` still never owns), `prGlyphColor` returns `text-text-secondary` for closed from a branch above the fail branch, and both glyph surfaces (window row, session tile) render the ✕ `GitPullRequestClosedIcon` when `prState === "closed"`. A closed draft reads closed — the draft branch is `open`-gated, so this falls out by construction.
**Why**: a closed-unmerged PR is an outcome worth a glance-level signal ("this branch's PR was rejected/abandoned — the window needs a decision: rework, re-open, or kill"); rendering no glyph made a closed PR indistinguishable from never having had one, which actively misleads during triage. Muted gray keeps a dead PR from drawing rest-state attention, and the ✕ shape is what separates closed from draft at the same inert token (GitHub disambiguates closed by shape, not color). Closed sits above fail because a closed PR's checks/review are historical noise — the same first-match rationale that puts `merged` above `fail` in the chain.
**Rejected**: GitHub-exact red + ✕ (collides visually with fail-ish red and lights up dead PRs — rejected by the user after mock review); red on the same `GitPullRequestIcon` (indistinguishable from failing; GitHub never colors the plain PR icon red); leaving closed glyph-less (the misleading gap); a new color outside the popular PR vocabulary (learning curve).
*Introduced by*: 260810-xuej-closed-pr-row-glyph

### PR is evicted from the dot — dot = local story, glyph = remote story
**Decision**: the status dot renders only the local story (fab journey / ad-hoc agent / floor) with four hues (blue building → green PR-ready, yellow agent, gray floor) and three shapes (ring / solid / failed); PR state — draft, checks-pending, open, merged, failing, closed — lives exclusively on the rest-state row/tile glyph via the six-way `prGlyphColor`. The blue/green split is stage-based (`fabPhase`), never `prNumber`-based.
**Why**: the row glyph made the dot's PR tier redundant (a merged fab PR rendered purple twice, two pixels apart), and the PR tier displaced live pipeline state (a fab window with a PR never showed its stage on the dot). Splitting by story makes shape meaning uniform across every hue — fully compositional, four legend strips replace a 6×5 matrix — and gives every new PR-adjacent state a home on the glyph instead of pressuring the dot. Stage-based hue keeps the dot free of PR fields; alignment with PR existence stays emergent (`/git-pr` creates the PR mid-ship).
**Rejected**: square-only removal (keeps the double-encoding; merged becomes indistinguishable from open on the dot); the maximal one-fab-hue reduction (loses the "still cooking vs out the door" glance); a `prNumber`-based blue/green split (couples the dot to PR fields).
*Introduced by*: 260810-aqo6-statusdot-compositional-vocabulary

### Skipped display-state falls through the whole ladder
**Decision**: `statusDotState` treats `fabDisplayState === "skipped"` as "not a fab-owned dot" and continues down the ladder (fresh agent → yellow, else gray floor), rather than forcing gray inside the fab arm.
**Why**: a skipped change has left its journey; ladder continuation is the least machinery and lands on the gray floor in the common agent-less case, without hiding a live agent on a skipped change's pane.
**Rejected**: a dedicated skipped→gray short-circuit (extra machinery that would also hide a live agent on a skipped change's pane); a fab resting ring for skipped (it is not a resting fab change — it left the journey).
*Introduced by*: 260810-aqo6-statusdot-compositional-vocabulary

### Waiting attention is an additive halo, never a hue-flip
**Decision**: `waiting` renders as a pulsing yellow `rk-waiting-halo` box-shadow ring layered around the dot, leaving the core hue and shape untouched (a blue building dot keeps its blue core; a failed dot keeps its failed shape); under `prefers-reduced-motion` it degrades to a static yellow ring.
**Why**: family identity must survive attention — the halo is the signal the user scans for, and it rides outside the border-box so it disturbs neither the dot's size nor its hue.
**Rejected**: a hue-flip on attention (destroys exactly the family signal the user is scanning for); a self-colored halo (vanishes in the reduced-motion static form).
*Introduced by*: 260706-y1ar, 260810-aqo6-statusdot-compositional-vocabulary

### Fab dot labels compose hue-word + displayState-derived status word
**Decision**: `dotLabel` fab labels are `building`/`PR-ready` (the phase word) + a status word derived from `fabDisplayState` (`done` → "parked", `ready` → "ready", `active`/unknown → "active"), never the raw stage word and never a PR word.
**Why**: the shape alone can't distinguish parked from pending (both render the resting ring), so the status word derives from the display-state; the label stays a pure function of what the dot shows while keeping the parked/pending split legible. The exact stage lives in the `fab` register on both register surfaces.
**Rejected**: the raw stage word (`review — active`) — re-encodes per-stage detail the dot no longer renders; a shape-derived status word (`done` would read "pending"); PR-native labels (`PR — merged`) — PR facts belong to the glyph and register surfaces, not the dot's label space.
*Introduced by*: 260810-aqo6-statusdot-compositional-vocabulary

### Clone-child reference API
**Decision**: `Tip` clones its single child element and merges the floating reference props/ref onto it (`useMergeRefs`), rather than rendering a wrapper element or a render-prop API.
**Why**: ~40 migrated call sites demand minimal churn; the top-bar's overflow fit measures `barRender()` widths in a hidden probe, so any wrapper element would distort measured widths; the codebase already uses the floating-ui reference-props idiom.
**Rejected**: a wrapper `<span>` (distorts probe widths and flex layouts); a render-prop shape handing each call site the reference setter (far noisier across 40 call sites).
*Introduced by*: 260722-73al-tip-tooltip-system

### Suppress-by-early-return on coarse pointers
**Decision**: under `pointer: coarse` (live via `useCoarsePointer`), `Tip` returns its child unchanged — no reference props, no portal, no ARIA wiring. Hooks still run unconditionally (parameterized on an `enabled` flag); only the render return is short-circuited.
**Why**: the approved spec gives touch no tooltip layer at all; not attaching the machinery is the cheapest correct implementation and makes the "no render under coarse pointer" assertion direct. The control's `aria-label` carries the name on touch.
**Rejected**: `enabled: false` on the hover/focus hooks only (still wires the `aria-describedby` machinery and keeps dead listeners).
*Introduced by*: 260722-73al-tip-tooltip-system

### Status-bar left cluster is branch-first descending relevance
**Decision**: the status bar's left window cluster renders `⑂ git → pr → fab → agt → tmx → cwd` — the git branch anchors the left edge, the volatile per-window signal segments follow, the identity rows trail — with the drop breakpoints unchanged, so display order equals survival order and the ladder reduces to one rule: rightmost dies first.
**Why**: the previous status-pyramid-ascending order put the most-consulted segments (PR, branch) at the far end of the cluster behind four low-value identity rows. Branch-first (over PR-first) keeps the left edge stable: the branch is always present in a worktree pane, while pr/fab/agt appear and vanish per window.
**Rejected**: PR-first pure-relevance ordering — leading with volatile segments makes the bar's left edge jump on every window switch to a PR-less window.
*Introduced by*: 260816-499u-status-bar-reorder-drop-out

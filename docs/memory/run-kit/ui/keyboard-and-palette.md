# run-kit UI — Keyboard & Palette

## Keyboard Shortcuts

Every app chord is **data in one declarative registry** — `app/frontend/src/lib/keybindings.ts` (pure, DOM-light, colocated `keybindings.test.ts`, the `window-view.ts`/`palette-*.ts` convention). The module owns the tier definitions, `DEFAULT_BINDINGS` with its per-platform default refinements, the tier-stamped claimed-key map, the per-device override layer, chord matching (incl. scope precedence and the terminal-seam refusal predicate), conflict detection, capture, per-platform formatting, the shared suppression predicate, and the palette-hint decorator. React integration is two hooks: `hooks/use-keybindings.ts` (the reactive effective map) and `hooks/use-keybinding-dispatch.ts` (ONE window-level `keydown` listener per route shell). (`260730-g40a`)

### Tiers and the `e.code` rule

Three tiers, each a modifier predicate in `matchesCombo` — **Alt is excluded from every tier** (macOS composes characters with it):

| Tier | Chord | Used by |
|------|-------|---------|
| `shifted` | `Shift + (Meta or Ctrl)` — ⇧⌘ on macOS, ⇧Ctrl on Windows/Linux | the Windows/Linux action tier in full, and the mac actions that stay shifted there (A, the ⇧⌘H hosts chord, the ⇧⌘↑/⇧⌘↓ session-jump pair, plus the shifted halves of the mac tier-split pairs — ⇧⌘T session, ⇧⌘D stacked split, ⇧⌘W close app window) |
| `cmd` | `(Meta or Ctrl)` without Shift | the legacy punctuation chords ⌘K ⌘., the board ⌘[/⌘] pair, and the macOS-demoted action defaults (§ Per-platform default tiers) |
| `ctrl` | plain `Ctrl` without Meta/Shift | `focus-hop` is the first shipped default — mac-only ⌃` via `macTier` (plain Ctrl belongs to the pane on Win/Linux, so its base tier is shifted); a mac chord capture reading plain Ctrl otherwise lands in this tier, kept distinct from ⌘ (macOS window/system territory the page must not claim) |

Matching is on **`KeyboardEvent.code`, never `e.key`** — layout-independent (`"KeyN"`, `"BracketLeft"`), and it sidesteps the shifted-accelerator character-resolution flakiness the shell docs flag ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam). **The letters are constant across platforms; only the modifier varies.** The shifted tier is what makes N/T/W/H/A coexist on Windows/Linux at all: **plain Ctrl must always reach the pane** there (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+N/P history), and legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so claiming the shifted tier costs terminal apps nothing (the same tier every cross-platform terminal — Windows Terminal, GNOME Terminal, Konsole, kitty — uses for app actions). That pane-ownership constraint is **Windows/Linux-only**, and browser key reservation is **host-specific** — so macOS defaults demote to the unshifted ⌘ tier wherever nothing immovable blocks them (§ Per-platform default tiers).

**The arrow pairs encode the sidebar's vertical stacking spatially** (`260822-ju2p`) — arrows walk the sidebar; on mac, hold Shift to leap a session. The **window pair** (`window-prev`/`window-next`) steps ONE row over the **flattened all-sessions window list in sidebar order** (the `useMergedSessions` array order IS that order), wrapping at the ends, so crossing a session boundary lands on the adjacent session's edge window — last window of the previous session going up, first of the next going down. The **session pair** (`session-prev`/`session-next`) hops the adjacent session in sidebar order (wraparound), landing on that session's tmux-active window (`isActiveWindow`); a target session whose snapshot carries no active window (the stale-SSE edge) falls back to its first window in sidebar order — never skipped — and sessions with no windows contribute nothing to the jump ring. Target resolution for both lives in the pure, DOM-light `lib/window-cycle.ts` (`cycleWindowTarget` / `sessionJumpTarget`, colocated tests — the `tile-chord.ts`/`zen-mode.ts` convention): both resolvers are total, resolving `null` on every degenerate shape (no windows, a stale `windowParam`, no other windowed session), and the caller treats `null` as "no action", never a throw. `app.tsx`'s `windowCycleActions`/`sessionJumpActions` memos are thin wrappers navigating through the existing rich `navigateToWindow` path (tmux align + transition + writeback suppression), and the palette entries (`Tab: Previous`/`Tab: Next`, `Session: Previous`/`Session: Next`, ids = the actionIds) are omitted when no window is current, so the gating gates the chords for free. Both pairs are `scope: "global"`. Tier split: the window pair demotes to **⌘↑/⌘↓ on macOS in both hosts** (`macTier: "cmd"` — mac-browser ⌘↑/⌘↓ is the page-interceptable scroll-to-top/bottom, the ⌘D/⌘[ accelerator class, so NO shell gate and no `browser`-owner claim row), while the session pair rides `macCode: "ArrowUp"`/`"ArrowDown"` with **NO `macTier`** (stays shifted — ⇧⌘↑/⇧⌘↓, tier-disjoint from the window pair on the same codes, the split-pair/`create-session` precedent). On Win/Linux both pairs live on the shifted tier (plain Ctrl belongs to the pane there — Ctrl+arrows are readline word movement), so the split is by AXIS instead: vertical ⇧Ctrl+↑/↓ = the fine-grained window step, horizontal ⇧Ctrl+←/→ = the coarse session hop. The terminal seam's existing refusal rules bubble both pairs out from under xterm focus with no `attachCustomKeyEventHandler` change (rule 1 shifted everywhere, rule 2 mac cmd-tier with `metaKey`) — the accepted Win/Linux cost is the same one every shifted-tier binding makes: Ctrl+Shift+arrow CSI sequences are refused to the pane. All four `mapLabel`s (`prev tab`/`next tab`/`prev session`/`next session`) are carried for parity but unrendered — arrow codes have no keycap cell in the panel's `KEY_ROWS` grids (the `Comma`/`Backquote` no-cell precedent).

**B and the surface digits demote on macOS in both hosts** — ⌘B is the VS Code primary-sidebar keycap, and ⌘1/⌘2/⌘3 toggle the tty/code/web tiles in tile order (the JetBrains tool-window model — § Stateful surface chords). All four are `preventDefault`-interceptable in a mac browser (the same accelerator class as the shipped ⌘D/⌘[/⌘]/⌘/ interceptions, not reserved like N/T/W), so none carries a shell gate, and all four carry rendered `mapLabel`s (`sidebar` / `tty` / `code` / `web`) — `KeyB` and `Digit1`–`Digit3` have keycap cells in the panel's tier-map grids. The digits' browser case is handled by **claims data, not a shell gate**: the mac-browser cmd-tier tab-digit claims (`MAC_BROWSER_CMD_CLAIMS`) resolve ⌘1/⌘2/⌘3 `reserved` outside the shell, so the chords are palette-only in a mac browser and live in the mac shell. On Win/Linux the rows sit on the shifted tier (⇧Ctrl+1/2/3) — the shell's Hosts switcher binds Alt+digit accelerators outside every tier there ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam) — and plain Ctrl+digit stays with the pane.

**`focus-hop` is the first shipped `ctrl`-tier default** (`260816-sm66`) — ⌃` on macOS in both hosts (`macTier: "ctrl"`), ⇧Ctrl+` on Win/Linux (plain Ctrl belongs to the pane there, so the base tier is shifted and `macTier` does the demotion). It hops focus between the tty and code tiles ([focus-ownership](/run-kit/ui/focus-ownership.md) § Recording Seams), and the terminal seam's third refusal rule is what lets ⌃` fire under terminal focus on mac (§ Dispatch seams). `Backquote` has no keycap cell in the panel's tier-map grids (the `Period`/`Comma` no-cell precedent), so the row ships no `mapLabel`; `formatCombo` renders the ctrl tier with the `` Ctrl+` `` spelling.

**`web-find` is the first `webOnly` binding and the first unshifted-Ctrl chord the SPA ships on Win/Linux** (`260819-ie2i`, `260821-zqlq`) — ⌘F in both mac hosts, Ctrl+F on Win/Linux: the `cmd` tier natively yields the browser's own find chord on every platform, so no `macTier`/`macCode` refinement. It opens the web tile's find-in-page bar ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Iframe Window → Find bar) and is meaningful only while the web tile owns focus — the `webOnly` data flag makes its dispatcher handler absent everywhere else (§ the `ttyOnly`/`webOnly` flags below), so the chord falls through untouched: native browser find elsewhere in the app, and the pane's Ctrl+F (readline forward-char) under Win/Linux terminal focus, where the cmd-tier seam rule is mac-only (§ Dispatch seams → Terminal seam). `scope: "terminal"` plus the palette body's own gate (registered only while the rendered layout includes an open `web` tile AND the window has web CONTENT — `hasWebUrl`; an onboarding tile has nothing to search, so the `Web: Find in page` entry is ABSENT there rather than disabled, and the tile's own `web-find:open` listener double-guards — the chord no-ops on an onboarding tile: nothing opens, nothing throws) keeps it inert off window routes; `ignoreInputs: true` makes it a chrome-level opener that fires from the URL bar and the find input itself (the ⌘K/`settings-open` class). `mapLabel: "find"` annotates its `KeyF` keycap cell. Inside the code-server iframe ⌘F is NOT reclaimed — code-server keeps its own find (§ the `ttyOnly`/`webOnly` flags).

**`terminal-find` is the tty mirror of `web-find`** (`260819-zqf9`) — ⌘F in both mac hosts (`macTier: "cmd"`), ⇧Ctrl+F on Win/Linux: the base tier is `shifted` because plain Ctrl+F is the pane's readline forward-char there and the terminal seam deliberately never refuses unmatched plain-Ctrl chords — the GNOME Terminal/Konsole/Windows Terminal find convention (§ Design Decisions → `terminal-find`'s base tier). It opens the tty tile's find bar ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Tile renderer → tty find bar) and is meaningful only while a tty tile owns focus — the `ttyOnly` flag makes its handler (`ttyGated("terminal-find")`, beside `webGated("web-find")` in `app.tsx`'s handler map) absent everywhere else, so the chord falls through untouched: the browser's native find, or `web-find` under web-tile focus. The terminal seam's existing refusal rules bubble the chord out from under xterm focus with NO `attachCustomKeyEventHandler` change: rule 1 refuses shifted-tier matches on every platform, rule 2 refuses cmd-tier matches with `metaKey` on mac (§ Dispatch seams → Terminal seam). `scope: "terminal"` plus the palette body's own gate (registered only while the rendered layout includes a tty tile) keeps it inert off window routes; `ignoreInputs: true` makes it a chrome-level opener that fires from the find input itself; `mapLabel: "find"` shares `web-find`'s `KeyF` keycap annotation. On mac the resolved ⌘F combo collides with `web-find`'s — coexistence, not a conflict: the surface gates are disjoint, so `findConflicts` skips the pair (§ `findConflicts` below). The chord handler and the `Terminal: Find` palette body both dispatch the `terminal-find:open` document CustomEvent (`TERMINAL_FIND_OPEN_EVENT` in `lib/terminal-find.ts`), which the mounted `SurfaceLayout` listens for — the `web-find:open` precedent, one open seam for all three entry points (chord, palette, the locally-toggling ⌕ button).

**`web-address` (⌘L/Ctrl+L) focuses the web tile's address bar** (`260819-v6y4`) — the browser's own address-bar chord, `cmd`-tier `KeyL` in both mac hosts and Ctrl+L on Win/Linux, with no `macTier`/`macCode` refinement. It focuses the web tile's address input with the raw value select-all'd, entering edit mode ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Iframe Window → Address input), through the same seam shape as `web-find`: the `webGated("web-address")` handler (absent unless the focused tile kind is `web`, so the chord falls through untouched everywhere else — the browser's own address bar elsewhere in the app, readline clear-screen under Win/Linux terminal focus) dispatches the `web-address:focus` document CustomEvent (`WEB_ADDRESS_FOCUS_EVENT` in `lib/web-url.ts`), which the mounted web tile listens for. `ignoreInputs: true` makes it a chrome-level opener that fires from inside the address input itself; `mapLabel: "address"` annotates its `KeyL` keycap cell. **The mac-browser `cmd`-tier `KeyL` claimed-keys row is DELIBERATELY ABSENT** — ⌘L is `preventDefault`-interceptable in mac browsers (the ⌘D/⌘J class — vscode.dev intercepts it), and the `webOnly` gate preserves the browser's own address-bar behavior everywhere except web-tile focus, which is exactly what the claim protected (§ Design Decisions → ⌘L rides the page-interceptable class). **mac-browser ⌘L interception is a pre-ship manual verification gate** (the ⌘J precedent — not automatable on the Linux e2e rig): if a mac browser refuses interception, the recorded fallback is restoring the `browser`-owner claim row plus palette-only access.

**`host-menu-open` (⇧⌘H/⇧Ctrl+H) opens the desktop-shell titlebar strip's hosts menu, with plain digits selecting a host while it is open** (`260820-nv0o`) — the easy two-stroke replacement for the awkward ⌥⌘1–9 stretch (`⇧⌘H, 3` mirrors ⌥⌘3; the direct accelerators are untouched). Shifted `KeyH` on every platform with **no mac refinement**: the cmd-tier ⌘H is the mac shell's hide accelerator and the mac-browser system hide claim (tier-disjoint), while shifted KeyH is free in every claim set — H matching the menu's `hosts` mapLabel. The handler is component-local to `ShellTitlebarStrip` (§ Dispatch seams — the fourth own-listener chord), a stateful toggle: closed → open with focus on the active row; open → close + refocus the trigger; a non-interactive switcher (older shell, empty list) never `preventDefault`s, and in a browser the strip never mounts, so the chord resolves to no handler anywhere else. The terminal seam's rule 1 (refuse every enabled shifted-tier match) bubbles it out from under xterm focus with no seam change. While the menu is open, plain `Digit1`–`Digit9` (strict no-modifier guard) select the Nth rendered host through the click/Enter switch path — rendered order IS the accelerator order; a digit past the live count releases the key, and the open-menu dialogs suspend it ([top-bar](/run-kit/ui/top-bar.md) § Desktop-Shell Titlebar Strip). The palette's `Host: Switcher` entry (id `host-menu-open`, so the chord hint renders) is layout-global in `useGlobalPaletteActions`, gated on a non-empty `useShellServers()` list, and opens the same menu through the `HOST_MENU_OPEN_EVENT` document seam in `lib/shell-strip.ts` (the `terminal-find:open` shape; open-only — statefulness lives in the chord handler, § Design Decisions). `mapLabel: "hosts"` annotates the `KeyH` keycap cell. The desktop shell's welcome page keeps its own local mirror of this chord (`welcome.ts` — shell-owned, no IPC; [desktop-shell](/run-kit/desktop-shell.md) § Welcome "Your Hosts" Section).

**⇧⌘P is deliberately unbound on every tier** — `KeyP` is reserved for a future create/open-PR action (the Conductor convention), recorded as a `DEFAULT_BINDINGS`-adjacent comment so a later change does not spend the keycap. The **⇧⌘digit layer** is reserved the same way — a comment beside `DEFAULT_BINDINGS` holds it for possible future positional tile jumps; the reservation is partial on mac, where ⇧⌘3/4/5 remain macOS system screenshot claims (`MAC_SCREENSHOT_CLAIMS`). Shifted `KeyL` and shifted `KeyM` are also deliberately unbound on every platform — free keycap real estate left unspent; the cmd-tier ⌘L (`web-address`) and the ⌘H/⌘M hide/minimize claims are untouched.

**`settings-open` is the one comma chord** (`260801-mqim`): a chrome-level *opener*, not a toggle — a re-fire while the dialog is open is a React state bailout, matching the macOS ⌘, convention where Preferences never closes itself. Its mac default is the OS-conventional ⌘, on every mac host (`macTier: "cmd"` — the same one-canonical-chord rule as the N/T/W family); in a mac browser ⌘, is the **browser's own Preferences accelerator** (claimed data, § Claimed keys), so the chord resolves `reserved` there and settings is palette-only in a mac browser. `ignoreInputs: true` mirrors `shortcuts-overlay`/`compose-toggle`, the other chrome-level chords. `mapLabel: "settings"` is carried for parity but unrendered: `Comma` has no keycap cell in the panel's tier-map grids, the `Period`/`Backquote` precedent.

**The app-window pair is two keyless-base SPA bindings over the shell's `windows` bridge group** (`260820-lfla`): `new-app-window` (⌘N on mac hosts — `code: ""`, base tier `shifted`, `macCode: "KeyN"`, `macTier: "cmd"`, label "New app window", `mapLabel: "new app"`) and `close-app-window` (⇧⌘W on mac hosts — `code: ""`, base tier `shifted`, `macCode: "KeyW"`, NO `macTier` so it stays shifted, label "Close app window", `mapLabel: "close app"`). Keyless base is the macro precedent: both resolve unbound on Win/Linux (the shell's New Window menu item stays menu-only there — plain Ctrl belongs to the pane); on mac hosts the `macCode` refinement spends the canonical ⌘N/⇧⌘W, which resolves browser-reserved in a mac browser (⌘N/⌘W claim data — and the handlers are bridge-gated absent everywhere outside the shell anyway). The bridge seam is the `windows` group in `lib/shell.ts` — `canNewShellWindow()` / `canCloseShellWindow()` / `newShellWindow()` / `closeShellWindow()`, all boolean-resolving and never throwing, with `close` additive on top of `newWindow` (narrowed separately, so an older shell exposes only the new-window path). The palette entries `App: New Window` / `App: Close Window` are layout-global in `use-global-palette-actions.ts`, each gated on its own `can*ShellWindow()` capability, with ids equal to the registry actionIds so the effective-chord hints attach and the chords resolve through the bodies via `fromPalette` in `app.tsx`'s `keybindingHandlers` (the board twin in `board-page.tsx` resolves them from `usePaletteGlobals()`). Main-side, `shell:new-window` duplicates the SENDER's window (same host, same route, fresh view) and `shell:close-window` closes the SENDER's window — not the focused one: the menu's Close Window seam closes the focused window, which is wrong for a chord handled in a non-focused view — both gated exactly like `servers:*` (`isHostsSender`). Both shell menu items stay accelerator-less (the unshifted-⌘ fall-through rule is inviolable), so `MAC_SHELL_CMD_CLAIMS` mirrors no new accelerators.

**O stays shifted on every platform; E is the win/linux compose keycap, with mac refined to ⌘I.** `compose-toggle`'s base row (`KeyE`, shifted) stands on Win/Linux — C is the win/linux terminal copy/paste claim, T is `create-window`, and ⇧Ctrl+I is the win/linux DevTools shell claim — while mac refines code AND tier together (`macCode: "KeyI"` + `macTier: "cmd"`, the split-pair precedent under the one host gate in `defaultComboFor`), giving the Cursor/VS Code inline-chat ⌘I habit. Unshifted ⌘E itself is macOS browser "use selection for find" territory, which is why the mac demotion rides a different letter rather than the base code. In a mac *browser* ⌘I is an interception **attempt** (the view-source accelerator class — shell-first posture: `preventDefault` is attempted and a blocked chord simply stays palette-reachable; no claim row and no verification gate). `compose-toggle` carries `ignoreInputs: true` so the chord also fires from *inside* the strip's own textarea (the one place the strip is most likely to be closed from) — the same field ⌘K and the shortcuts toggle use. `open-last-used` names the **behavior**, not an app, which is why it can carry a static chord at all while the per-target `Open:` palette entries cannot (§ Open-in-App palette actions). (`260801-sm6g`)

**The split pair is the first per-platform-CODE default** (`260807-rbx5`): `split-horizontal`/`split-vertical` bind the existing `Tab: Split Horizontal` / `Tab: Split Vertical` palette bodies, direction semantics inherited from the top-bar chip (horizontal = side-by-side = tmux `-h`; § Horizontal is the default split direction). Both are `scope: "terminal"` — the `view-cycle`/`open-last-used` precedent, since the palette bodies exist only on window routes, so `fromPalette` yields no handler elsewhere and the chord falls through untouched. The base (Win/Linux) codes are keycap-as-divider mnemonics: ⇧Ctrl+\ side-by-side (shift+\ types `|`, the divider the split creates — the VS Code split-editor keycap) and ⇧Ctrl+- stacked. macOS refines both to the D keycap (`macCode: "KeyD"`) for the iTerm2/Warp/Ghostty pair: `macTier: "cmd"` also demotes horizontal to ⌘D in **both** mac hosts (⌘D is the mac-browser bookmark accelerator, page-interceptable like ⌘[/⌘]/⌘/ — no shell gate, and no `browser`-owner claim entry), while vertical keeps the shifted tier as ⇧⌘D — tier-disjoint on the one code, so the mac pair is conflict-free. The mac pair cannot ship with constant codes: plain Ctrl+D is EOF and belongs to the pane on Win/Linux, and two rows cannot share ⇧Ctrl+D because equal-scope same-combo defaults would break the conflict-free invariant (§ Per-platform default tiers). Horizontal takes the plain ⌘D because it is the primary/default split. `mapLabel`s `split h` / `split v` annotate whichever keycap each is bound to on its map layer.

Both split rows also carry **`ttyOnly: true`** (`260812-wfic`) — an optional `KeyBinding` data flag meaning "this chord targets the tmux pane; only meaningful when the tty tile owns focus", set on the split pair and `terminal-find` (the tty ⌘F claim, `260819-zqf9`) and consulted by gate sites rather than hardcoded actionId lists: `app.tsx`'s handler map drops a `ttyOnly` handler when the focused tile kind is not `tty` (§ Dispatch seams), and the lens-iframe reclaim predicate never reclaims a keydown whose only matches are `ttyOnly` (§ Code Surface → Chord reclaim).

Its mirror **`webOnly?: boolean`** (`260819-ie2i`) means "only meaningful when the web tile owns focus" — set on exactly `web-find` and `web-address` and consumed by the same two gate-site shapes, as data: `app.tsx`'s handler map treats a `webOnly` handler as ABSENT unless the focused tile kind is `web` (the exact `ttyOnly` gate pattern, beside it in the handler map), and the reclaim predicate reclaims a `webOnly` match only inside a `web`-kind iframe. That predicate — `hasReclaimableMatch(e, bindings, kind)` — is focused-KIND-aware: `kind` is the kind of the iframe the keydown arrived in; a `ttyOnly` match is never reclaimable in any iframe, a `webOnly` match only under `"web"`, and `.some` semantics mean a chord matching BOTH a gated and an ungated binding still reclaims (the ungated match has a global meaning). For the code iframe the result is byte-identical to the pre-kind-aware predicate on every earlier binding. `app.tsx` builds one curried factory over it (`reclaimChordForKind`), and `SurfaceLayout` binds the kind per iframe mount — `"code"` to `CodeSurface`, `"web"` to `IframeWindow` ([lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Design Decisions → Chord-reclaim).

Five further bindings cover the remaining punctuation chords — same registry, so they are per-device rebindable like everything else: `command-palette` ⌘K (`cmd`, global, `ignoreInputs`), `view-cycle` ⌘. (`cmd`, terminal), `layout-cycle` ⌘; (`cmd`, terminal — the next same-arity layout preset, order kept; § Surface Layout), and the board pane-cycle pair `board-cycle-prev`/`board-cycle-next` ⌘[/⌘] (`cmd`, board). `scope` (`global | terminal | board | sidebar`) is descriptive — it drives the panel's grouping and conflict scoping; actual applicability is handler presence at each dispatcher mount. `sidebar` is schema-reserved with no binding. `kind` is `"builtin" | "macro"` — the builtins are the shipped registry actions above; `macro` bindings are user-defined and enter resolution from the macro store (see § Macro bindings). (`260730-hbyh`)

`Cmd+C`/`Ctrl+C` in a focused terminal is **not** a registry binding — it is a special case at the head of `attachCustomKeyEventHandler` (copy selection when one exists, else fall through to xterm's SIGINT), using `navigator.clipboard.writeText()` with a `document.execCommand('copy')` fallback for non-secure contexts and clearing the selection via `.finally()`.

No single-key shortcuts (`j`/`k`/`c`/`r`) or `Esc Esc` — these conflicted with xterm.js terminal input. Every action is also reachable via `Cmd+K` or top-bar buttons.

### Stateful surface chords

The surface family — `sidebar-toggle` (⌘B), `tty-toggle`/`code-toggle`/`web-toggle` (⌘1/⌘2/⌘3), and `compose-toggle` (⌘I) — follows the **JetBrains tool-window model**: ONE chord per surface with a three-state rule instead of separate toggle/focus layers. Hidden → show + focus; visible but unfocused → focus; focused → hide. `zen-toggle` (⇧⌘⏎) sits beside them as the section's plain two-state member — a chrome override with no focus arm. The whole family carries `ignoreInputs: true`: chrome toggles are modifier combos that never insert text, so they stay live inside real text inputs — the compose strip's textarea in particular, which is where a user drafting a prompt reaches for them. The semantics live in the **chord handlers**, not the palette bodies — the palette's `Tile: Show/Hide/Focus <Surface>`, `Sidebar: Toggle`/`Sidebar: Focus`, and `Compose: Focus` entries keep explicit single-verb semantics (§ Design Decisions → Statefulness lives in chord handlers, not palette bodies).

- **Tile chords (⌘1/⌘2/⌘3)** run the state machine in `lib/tile-chord.ts` (`tileChordHandler`, pure + Vitest-covered), wired in `app.tsx` against the CURRENT render layout (`renderLayout.order`) and `focusedTileKind`: hidden → `togglePanel(kind)` plus the **per-kind landing flag** (`focusOnLandingRef`, consumed by the layout-keyed effect) so the tile focuses once it lands; visible-unfocused → the `layoutFocusTileRef` focus-by-kind seam (the same path `Tile: Focus <Surface>` uses, so ⌘1 records `tty` through the seam's `recordTtySlot` and ⌘2/⌘3 record NOTHING — the steal-guard recording asymmetry, [focus-ownership](/run-kit/ui/focus-ownership.md)); focused → `togglePanel(kind)` then `restoreFocus(key, kind)` so focus never strands in a dead slot. Gating mounts NO handler — the chord falls through untouched (dispatcher rule 3, no `preventDefault`) — off a window route, on mobile, for a surface the window cannot tile (`tty` and `web` are tileable on EVERY window, so ⌘1/⌘3 mount on every desktop window route — only ⌘2 can sit this gate out), and for the arity-1 hide (the palette's `Tile: Hide` omission on `single` layouts). (`260821-zqlq`)
- **⌘B (sidebar)** keeps its component-local listener (`useSidebarKeyboardToggle` in `shell.tsx`, one of the three chords outside the dispatcher): hidden → open + focus the current window's row; visible-unfocused → focus the row; focus inside the sidebar → hide + return focus. The row focus and the focus return cross the shell→sidebar/route boundary through the module registries in `lib/sidebar-events.ts` (the `compose-strip-events` module-slot shape) — no DOM reach-around. Escape inside the sidebar returns focus WITHOUT hiding. Full contract: [sidebar](/run-kit/ui/sidebar.md) § Keyboard Navigation & Tree ARIA. Mobile keeps the plain visibility toggle (the stateful arms are desktop-only; the drawer's focus trap owns Escape there).
- **⌘I (compose)** runs `runComposeToggleChord` (`lib/compose-strip-events.ts`, shared verbatim by the AppShell and BoardPage dispatchers): strip off → toggle on (the off→on focus-on-open flag focuses the textarea — one press shows AND focuses); on + unfocused → `focusComposeStrip()`, a focuser decline falling back to the plain toggle so the chord never dead-presses; on + focused → toggle off (lossless via the draft store; `ignoreInputs` lets this arm fire from inside the textarea). Details: [compose-and-bottom-bar](/run-kit/ui/compose-and-bottom-bar.md) § Docked Compose Strip.
- **⇧⌘⏎ (zen)** toggles ZEN MODE — the desktop terminal route's transient distraction-free override (state in `contexts/zen-context.tsx` — `zenActive` plus the `zenZoomed` tracking boolean — NEVER persisted: no URL param, no localStorage write). Entering zen hides the root-layout top bar and the Shell sidebar as render-time overrides (the persisted `runkit-sidebar-open` preference and the layout state are never written) and, at arity > 1, zooms the focused tile through the app-level zoom ref seam when not already zoomed; the compose strip and the status bar stay visible. Exit — the same chord, the palette's `View: Exit Zen Mode`, or the status bar's exit-zen button — restores the chrome and unzooms ONLY a zen-initiated zoom still in effect (a pre-existing user zoom survives; a manual unzoom mid-zen is not toggled back). The handler mounts at ANY arity on `windowParam && !isMobile` (at arity 1 the chrome hide applies with no zoom attempted), survives window switches within the terminal route, and deactivates off it. The enter/exit decision is the pure `resolveZenToggle` (`lib/zen-mode.ts`, colocated tests). Esc is deliberately NOT a zen exit — it must keep flowing to the terminal pane. Shifted tier on BOTH platforms (no `macTier`): exact-modifier matching keeps the chord disjoint from the classifier-owned ⌘Enter/Ctrl+Enter compose-submit chords, which never carry Shift — a disjointness `classifyComposeEnter` enforces (a shift-carrying meta/ctrl Enter returns `default` and is left un-consumed, 260820-ecl4). Details: [lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § Surface Layout. (`260820-o8cr`)

Every family member is desktop-only — all stateful arms no-op under `isMobileViewport()` (the restore-router precedent: auto-focus pops the mobile IME).

### Per-platform default tiers (`macTier` / `macCode` / `defaultComboFor`)

The per-key table above is **data on the binding**, not a resolver branch. `KeyBinding` carries the base (Windows/Linux) `tier` plus two optional refinements — all of which touch the SHIPPED DEFAULT only, never the stored override:

- **`macTier?: BindingTier`** — the tier this binding's default combo uses on mac hosts. Shipped on `go-back`/`go-forward`/`shortcuts-overlay`/`split-horizontal`/`sidebar-toggle`/`tty-toggle`/`code-toggle`/`web-toggle`/`compose-toggle`/`window-prev`/`window-next` (all demoting to the `cmd` tier) and `focus-hop` (the one `ctrl`-tier demotion — ⌃`).
- **`macCode?: string`** — the KEY CODE the default combo uses on mac hosts, replacing `code`. A deliberate exception to 260730-n789's letters-constant rule, for chords whose mac convention has no legal cross-platform letter. Shipped on both split rows (`macCode: "KeyD"`: mac gets the iTerm2/Warp/Ghostty ⌘D/⇧⌘D pair while Win/Linux keeps the divider-mnemonic `\`/`−` base codes — `260807-rbx5`), on `compose-toggle` (`macCode: "KeyI"`: mac gets the Cursor/VS Code inline-chat ⌘I while Win/Linux keeps ⇧Ctrl+E, ⇧Ctrl+I being the DevTools shell claim there), and on `create-session` (`macCode: "KeyT"`: every mac host rides ⇧⌘T — the split-pair precedent, tier-disjoint from `create-window`'s ⌘T on the one code — while Win/Linux keeps ⇧Ctrl+N), and on `session-prev`/`session-next` (`macCode: "ArrowUp"`/`"ArrowDown"` with NO `macTier`: mac keeps the shifted tier as ⇧⌘↑/⇧⌘↓ — tier-disjoint from the window pair's ⌘↑/⌘↓ demotion on the same codes — while Win/Linux keeps the ⇧Ctrl+←/→ base codes). The keyless-base app-window pair carries `macCode` too (`new-app-window` `"KeyN"`, `close-app-window` `"KeyW"`): with `code: ""` the refinement is the ONLY code, so the chord exists solely where the refinement applies (every mac host — browser-reserved in a mac browser). Composes with `macTier` under the one mac gate.

Every other binding (including the legacy chords and macro projections) carries neither refinement and resolves identically everywhere.

`defaultComboFor(def, host)` is the **single seam** where platform is consulted for defaults — it returns `{ code: macCode ?? code, tier: macTier ?? tier }` when `host.platform === "mac"` and either mac refinement is set, else `{ code, tier }`: one canonical chord per action on every mac host, with browser-reserved chords handled downstream by claims data (§ Claimed keys), never by the default seam. Both `resolveBindings` (the no-override fallback *and* the `isDefault` comparison) and `applyCapture` (own-default detection, which therefore takes a required `host`) read defaults through it, so an effective map is always host-coherent: on a mac host ⌘[ *is* `go-back`'s default and shows no modified dot (and ⇧⌘D *is* `split-vertical`'s default, so re-capturing it is a diff-dropping no-op), while the same combos on Win/Linux are user overrides.

The **stored override shape is untouched** — `{ [actionId]: { code, tier } | null }`, byte-identical. Overrides are per-device by construction (localStorage), so per-platform storage is inherent and no migration exists. Win/Linux resolution is byte-identical to the pre-demotion map.

Which keys demote is constrained by what the environment refuses to give up:

- **⌘[ / ⌘] / ⌘/ demote on macOS in both hosts** — all three are interceptable in a mac browser (the board pane-cycle already ran on the cmd tier), and ⌘[/⌘] match native browser back/forward convention.
- **⌘B, the ⌘1/⌘2/⌘3 surface digits, and ⌘I demote on macOS in both hosts** — the VS Code primary-sidebar keycap, the positional tile chords, and the compose chord (via `macCode: "KeyI"`), page-interceptable in a mac browser like the set above (no shell gate anywhere). The digits carry no *shell-gate* — instead the mac browser's own cmd-tier tab-digit claims resolve them `reserved` there (palette-only), while ⌘B and ⌘I stay live in both mac hosts (⌘I as an interception attempt that degrades to palette when the browser refuses).
- **⌘↑ / ⌘↓ demote on macOS in both hosts** — the window-cycle pair (`window-prev`/`window-next`, `macTier: "cmd"`). Mac-browser ⌘↑/⌘↓ is the scroll-to-top/bottom accelerator, page-interceptable like the ⌘D/⌘[/⌘]/⌘/ set rather than reserved like N/T/W, so no shell gate and no `browser` claim row. The session pair on the same arrow codes instead keeps the shifted tier via `macCode` alone (⇧⌘↑/⇧⌘↓ — tier-disjoint from the window pair, the split-pair precedent).
- **⌃` demotes to the `ctrl` tier on macOS in both hosts** — `focus-hop`'s `macTier: "ctrl"`, the registry's first shipped ctrl-tier default. The only mac claim on `Backquote` is the cmd-tier ⌘` "cycle app windows" system row (§ Claimed keys), tier-disjoint from the ctrl-tier chord. Win/Linux keeps ⇧Ctrl+`: plain Ctrl is the pane's there, so the base tier is shifted.
- **The split pair refines to the D keycap on macOS in both hosts (`macCode`)** — `split-horizontal` also demotes to ⌘D (mac-browser ⌘D is the bookmark accelerator, `preventDefault`-interceptable like the ⌘[/⌘]/⌘/ set rather than reserved like N/T/W, so no shell gate and no `browser` claim row) while `split-vertical` keeps the shifted tier as ⇧⌘D — tier-disjoint on the one code, so the mac pair is conflict-free. Win/Linux never sees the D codes: the pair lives there on its divider-mnemonic base codes ⇧Ctrl+\ and ⇧Ctrl+- (§ The default binding set), because plain Ctrl+D is the pane's EOF and two rows cannot share ⇧Ctrl+D (equal scope → `findConflicts`).
- **The mac N/T/W map follows the universal tab-model convention** (Chrome/Safari/iTerm2/JetBrains: ⌘T tab, ⇧⌘T the bigger variant): unshifted ⌘ = the tab/tmux level, shifted = the level above. ⌘T is new tab (`create-window`, `macTier: "cmd"`), ⇧⌘T is new session (`create-session`'s `macCode: "KeyT"` — the tier stays shifted, tier-disjoint from `create-window`'s ⌘T on the one code, the split-pair precedent), ⌘W is close tab (`kill-window`, `macTier: "cmd"`), and the app-window pair sits beside them (⌘N `new-app-window`, ⇧⌘W `close-app-window` — the keyless-base bridge actions, § The default binding set). The refinements apply on EVERY mac host; a mac browser reserves N/T/W on both tiers (the `MAC_BROWSER_CMD_CLAIMS` ⌘N/⌘T/⌘W rows plus the shifted incognito / reopen-tab / close-window claims), so there the canonical combos resolve `reserved` and all five actions stay palette-only — the palette is the browser path by guarantee (Constitution V). The shell deliberately leaves the whole unshifted ⌘ tier unbound, which is exactly what these spend ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam; the menu's New Window / Close Window items stay accelerator-less for this).
- **⌘, demotes on every mac host** — `settings-open`'s `macTier: "cmd"` rides the OS-conventional Preferences chord everywhere on mac; a mac browser claims the unshifted ⌘, (Preferences), so the chord resolves `reserved` there and settings is palette-only in a mac browser, exactly like the N/T/W family.
- **H / A / O stay shifted on every platform** — ⌘H is macOS Hide (OS/app-menu level, dead in both hosts; the shell's App menu binds `role: hide`), so the hosts chord takes the shifted tier on `KeyH`; ⌘A is browser select-all plus the shell's Edit-menu `selectAll` role; ⌘O has no mac convention worth a demotion. (E's base also stays shifted — but only as the Win/Linux keycap; mac refines `compose-toggle` to ⌘I via `macCode`, the bullet above.)

### Claimed keys

Claimed keys are registry data (`claimedKeys(platform, shell)`), each carrying a **`tier`** (a claim occupies one chord tier — the mac ⌘ page tier has its own claimed set alongside the shifted tier) and an `owner` that drives presentation and effect:

- **`shell`** — menu accelerators. Shifted tier: ⇧CmdOrCtrl+R (force reload, everywhere) plus ⇧Ctrl+I (DevTools) on **win/linux only**. Both Hosts switchers — mac ⌥⌘1–9 and win/linux Alt+1–9 — sit on Alt-carrying accelerators no tier can express (Alt is excluded from every tier), so the shell owns no shifted digits on ANY platform; that unrepresentability is the point of both accelerator choices, not a gap in the mirror, and the freed win/linux ⇧Ctrl+1/2/3 are exactly what the surface tile chords spend ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam; § Design Decisions → Switcher claims are removed, not replaced). Mac `cmd` tier, present only inside the shell (`MAC_SHELL_CMD_CLAIMS`, mirroring the exhaustive mac bound set in `app/desktop/src/menu.ts`): ⌘Q quit, ⌘H hide, ⌘M minimize, ⌘R reload, the Edit roles ⌘Z/X/C/V/A, and zoom ⌘0/⌘+/⌘− (`Digit0`/`Equal`/`Minus`). The menu's New Window and Close Window items stay accelerator-less — the unshifted-⌘ fall-through rule never spends a menu accelerator on that tier — so the mirror carries no rows for them. Display + capture-warning data; the menu accelerator consumes the key before the page sees it anyway.
- **`system`** — shifted ⇧⌘Q (macOS logout), the mac ⇧⌘3/4/5 screenshot trio (`MAC_SCREENSHOT_CLAIMS`), and ⇧Ctrl+C/V (the win/linux terminal copy/paste convention), plus mac-browser `cmd`-tier ⌘Q/⌘H/⌘M (OS-level) and the mac `cmd`-tier ⌘` "cycle app windows" row (`Backquote`, macOS "Move focus to next window"). Display-only. The mac rows carry `platform: "mac"` with no `shell` restriction — like logout, screenshots and window cycling are system-wide, so they claim in both hosts (the `MAC_SCREENSHOT_CLAIMS` precedent). No binding occupies ⌘` — `focus-hop`'s ⌃` is the `ctrl` tier, disjoint — and the row is what makes rebind capture warn "claimed by system (cycle app windows)". Mac ⇧⌘1/2/6–9 carry **no** claim: unclaimed page real estate.
- **`browser`** — the one owner that changes resolution. Shifted N/T/W (incognito / reopen-tab / close-window) outside the shell on every platform; on a mac browser also the `cmd` tier's ⌘N/⌘T/⌘W (new window / new tab / close tab), ⌘, (Preferences — the reason `settings-open` is palette-only in a mac browser), and tab digits ⌘1–9. **⌘L (address bar) is deliberately NOT claimed** — it is page-interceptable (the ⌘D/⌘J class), and the `web-address` binding ships on it (§ The default binding set; § Design Decisions → ⌘L rides the page-interceptable class). Reservation is **tier-aware** — `resolveBindings` keys its reserved set on `` `${tier}:${code}` `` — so a combo resolves `enabled: false` with `disabledReason: "reserved"` only when a browser claim matches *both* its tier and its code. In a mac browser the N/T/W/`,` family's canonical combos are therefore inert chords whose actions stay palette-reachable (reserved-resolution is the sole browser story for them — no replacement chord — and the palette is the guaranteed path, Constitution V), and an override onto ⌘, is dead on a mac browser but live in the mac shell (⌘, being `settings-open`'s canonical mac default). Inside the shell every action is live.

Win/Linux claim sets are unchanged: the unshifted Ctrl tier there belongs to the pane, so it carries no claims data.

### Override layer

`localStorage["runkit-keybindings"]` stores **diffs only** — `{ [actionId]: { code, tier } | null }`, `null` meaning unbound/disabled (the same persistence shape as `runkit-terminal-font-size`; no backend, no config file, Constitution II). `resolveBindings(defaults, overrides, host)` merges them into the effective map — defaults resolved host-aware through `defaultComboFor` (§ Per-platform default tiers) — marking each binding `enabled` / `isDefault` / `disabledReason`. `parseOverrides` is tolerant — malformed JSON, a non-object root, or garbage entries degrade to "no override" — and both storage wrappers are try/catch, so an unavailable localStorage falls back to defaults without throwing.

This is also the **only** combo store: a macro's key lives here as an ordinary diff entry keyed by its actionId, never inside the macro definition. Macros therefore enter resolution as **keyless defaults** — `resolveBindings` resolves an effective combo whose `code` is `""` to `enabled: false, isDefault: false, disabledReason: "user"`, the same state a steal victim lands in, so the panel's `unbound` affordance covers both. Builtins always carry a code and are unaffected. (`260730-hbyh`)

Rebinding is **steal-with-warning** in a single capture press: `applyCapture(bindings, overrides, actionId, combo, host, defaults?)` gives the combo to the new owner, sets the previous owner's override to `null`, and reports it as `stolenFrom` so the panel flags it until it is rebound or reset. Re-capturing an action's own **host** default (`defaultComboFor(def, host)` — so ⌘[ counts for `go-back` on a mac) is a **no-op that short-circuits before the victim search**: it deletes the diff entry, keeping the blob diffs-only, and steals from nobody. The ordering is load-bearing — the mac defaults ship global↔board shadow pairs on ⌘[/⌘], so a victim search running first would let a no-op re-capture of either partner unbind the other. The optional `defaults` parameter is what the own-default check reads, so callers holding a **macro-extended** default set (`use-keybindings.ts`, which also passes its `host`) get the same detection as the `DEFAULT_BINDINGS` fallback. Stealing is kind-blind: a builtin capture can unbind a macro and a macro capture can unbind a builtin, one mechanism in both directions. Reactivity is an in-module pub/sub in `use-keybindings.ts` (the `use-local-storage-enum.ts` pattern — the native `storage` event fires only across tabs, which covers cross-tab for free); every write funnels through one `persist()`, and `setBinding` recomputes against freshly-read storage — **both** stores, so a macro-owned combo is steal-detected — meaning rapid successive captures compose.

`useKeybindings` composes `useMacros` and resolves over `DEFAULT_BINDINGS ∪ macros.map(macroToBinding)`. Because macros ride that one effective map, the dispatcher, the terminal seam (`attachCustomKeyEventHandler`), palette hints (`withShortcutHints`), and the panel key map (`custom` keycap state) pick them up with **zero** consumer changes. A macro-store change also re-reads override storage, since `removeMacro` drops the deleted macro's diff without a keybinding-store notification and the two stores must not drift in-memory. `reset all` writes `{}`, which unbinds every macro combo while leaving the definitions intact — rows return to `unbound`. (`260730-hbyh`)

### Macro bindings

A **macro** is a user-named keyboard route to an action that already exists — never a shell string. `app/frontend/src/lib/macros.ts` (pure, DOM-light, colocated `macros.test.ts`) owns the model; `hooks/use-macros.ts` is its React integration. (`260730-hbyh`)

```ts
type MacroTarget =
  | { type: "riff"; preset: string }              // → POST /api/riff
  | { type: "palette"; paletteActionId: string }; // → the palette action body
type MacroAction = { actionId: string; kind: "macro"; label: string; target: MacroTarget };
```

- **Two target kinds only.** A riff target carries the preset **NAME** alone; the pane commands and arguments live in the preset definition inside `fab/project/config.yaml` — the committed-config trust boundary ([rk-riff](/run-kit/rk-riff.md) § Security / Trust Boundary). Riff targets carry **no `args` passthrough**: `POST /api/riff` has no args field and its `task` REPLACES preset panes (`composePanes`), so per-macro dynamic args would need a backend extension. `isMacroTarget` narrows structurally, so a `{type:"shell",cmd}` blob planted in localStorage is dropped on parse.
- **Definitions in `localStorage["runkit-macros"]`** — a JSON array with the tolerant-parse posture of `parseOverrides` (malformed JSON, a non-array root, and invalid entries degrade to dropped/empty; valid entries are re-projected so unknown keys are stripped and `kind` is pinned) and try/catch storage wrappers. An empty list removes the key. The combo lives in `runkit-keybindings` (§ Override layer).
- **`actionId` is `"macro:<label-slug>"`** — lowercase, non-alphanumeric runs collapse to `-`, `-2`/`-3`… suffixes on collision (the riff `resolveWindowName` convention), empty slug falls back to `macro`. It doubles as the palette action id, so the `withShortcutHints` join is free. `isMacroActionId` is the guard that keeps macros out of target lists and out of palette-target resolution — no macro→macro recursion.
- **`macroToBinding(macro)`** projects a macro into a `KeyBinding`: `kind: "macro"`, `scope: "global"`, `tier: "shifted"`, `code: ""` (keyless — the unbound resolution in § Override layer), `description`/`mapLabel` from `macroCommandPreview(target)`, which renders `rk riff --preset discuss` / `palette: {actionId}`.
- **`useMacros()`** returns `{ macros, addMacro(label, target) → actionId, removeMacro(actionId) }` with the same in-module pub/sub + native `storage` reactivity as `use-keybindings.ts`; `addMacro` uniquifies against freshly-read storage so rapid adds compose. `removeMacro` also drops the actionId's `runkit-keybindings` entry, so a later same-slug macro can never inherit a ghost combo.

**Execution** is `executeMacro` in `app.tsx`, mounted on AppShell only. A `palette` target resolves its action body by id through the stable `getAllActions()` API channel **at call time** (the merged route + layout-globals list — the § Design Decisions "Chord handlers are the palette action bodies" convention; § Single palette mount + palette-actions slot) and invokes it in place; an absent action means no handler, so the chord falls through untouched. A `riff` target is **session-gated** (the `Agent: Spawn` precedent) and calls the existing `spawnRiff(server, session, { preset })` client: success surfaces an info toast and navigates via `navigateToWindow` when `windowId` is truthy (the spawn dialog's falsy-id guard preserved); failure — including a 400 for a preset gone from fabconfig — surfaces the error text as a toast. No new endpoint, no new exec surface, no fire-and-forget. `keybindingHandlers` spreads the macro handlers **first** so a theoretical id collision resolves builtin-first. The board route mounts no macro handlers, so macro chords fall through there.

Macros are also palette-reachable without their key: one `Macro: {label}` entry per macro (id = the macro's actionId) folded into `paletteActions`, riff macros filtered out with no session. `withShortcutHints` decorates them automatically; an unbound macro renders no hint.

`findConflicts` is a pure function over the effective map — two **enabled** bindings conflict when their codes match, their tiers collide (`tiersCollide`: equal, or the overlapping `cmd`/`ctrl` pair), their scopes are **EQUAL**, and their surface gates are not disjoint: a `ttyOnly`/`webOnly` pair never conflicts, because each gate renders its handler absent off its surface, so the two handlers are never simultaneously present — the mac ⌘F that `terminal-find` and `web-find` both claim is coexistence, not a conflict (`260819-zqf9`). A same-combo global↔scoped pair is a **shadow, not a conflict** (§ Scope precedence). It is the **test-only invariant guard** asserting the shipped defaults are conflict-free in every host — including the mac hosts, whose defaults ship exactly one such shadow shape; the capture UI takes its steal warning from `applyCapture`'s `stolenFrom` instead, and that search stays `scopesOverlap`-wide (`global` overlaps everything, equal scopes overlap, `terminal`/`board` are disjoint since those routes never co-mount).

### Dispatch seams

- **`useKeybindingDispatch(handlers)`** — one window-level bubble-phase `keydown` per route shell, keyed by `actionId`. Rules in order: skip `defaultPrevented` events (the shortcuts panel's capture-phase rebind listener claims its own); walk the **enabled** matches in `findMatches` order (§ Scope precedence) and fire the **first one that has a handler at this mount**; when **no** match has a handler the chord falls through untouched (no `preventDefault`), so a route without context for an action leaves browser/pane behavior alone; then `shouldSuppressChord` gates real text inputs unless the binding sets `ignoreInputs`. Bindings and handlers live in refs so the listener registers once per mount and SSE ticks never churn it.
- **`shouldSuppressChord(target)`** — the single shared input-gating predicate (`lib/keybindings.ts`): suppress only when a real text input owns focus, with two carve-outs — anything inside `.xterm` (the hidden helper textarea is the terminal's normal focus state) and `.rk-chat-input` (the chat lens's analog). jsdom-safe (`contentEditable` attribute fallback for the missing `isContentEditable` getter). Bindings carrying `ignoreInputs` skip it entirely — ⌘K, the shortcuts toggle, `settings-open`, the find/address openers, and the whole surface-toggle family (`compose-toggle`, `zen-toggle`, `sidebar-toggle`, the three tile digits).
- **Four chords keep their own component-local listeners** rather than joining the dispatcher, because their enablement is local state: ⌘K in `command-palette.tsx` (palette open-state), the `sidebar-toggle` chord (⌘B/⇧Ctrl+B) in `shell.tsx`'s `useSidebarKeyboardToggle`, ⌘. in `app.tsx`'s view-cycle effect (lens availability), and the `host-menu-open` chord (⇧⌘H/⇧Ctrl+H) in `shell-titlebar-strip.tsx` (switcher interactivity + menu open state; the strip's shell-only mount doubles as the handler-presence gate). Each reads its binding through `byAction` and matches with `matchesCombo` + `shouldSuppressChord` (honoring the binding's `ignoreInputs`, mirroring dispatcher rule 4 — `sidebar-toggle` relies on this to fire from the compose textarea) — definition and suppression are the registry's, enablement is the seam's.
- **Terminal seam** — `terminal-client.tsx`'s `attachCustomKeyEventHandler` keeps the ⌘C copy case first, then delegates the refusal decision to the pure predicate `shouldRefuseTerminalChord(e, bindings, platform)`, reading both the bindings and the host platform through render-updated refs (the handler attaches once at terminal init, but overrides can change any time). Returning `false` means xterm neither handles nor transmits the key, and xterm does not `preventDefault` a refused key, so the event bubbles to the window dispatcher and the action fires while the terminal owns focus. Three refusal rules:
  - **Any enabled shifted-tier match, on every platform** — legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so xterm would emit the Ctrl-char; refusing costs the pane nothing.
  - **On macOS only, an enabled `cmd`-tier match pressed with `metaKey`** — ⌘ chords never reach the pane as control bytes, so refusal is loss-free and the demoted ⌘[/⌘]/⌘/, ⌘B, ⌘1/⌘2/⌘3, ⌘I, and ⌘↑/⌘↓ (plus shell-host ⌘N/T/W) fire under terminal focus. The `metaKey` gate is load-bearing: `matchesCombo`'s cmd tier also accepts plain Ctrl, and mac Ctrl+[ is ESC.
  - **On macOS only, an enabled `ctrl`-tier match pressed with `ctrlKey` and WITHOUT `metaKey`** — lets ⌃` (`focus-hop`) bubble to the dispatcher under terminal focus, at the cost of stealing NUL (the byte Ctrl+` encodes to) from the pane: near-zero cost, the same trade VS Code makes for its own ⌃`. The `!metaKey` gate is rule 2's inverse — a ⌘+Ctrl combined press must not double-match.
  **Plain-Ctrl chords matching no enabled ctrl-tier binding are never refused on any platform** (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+[ ESC). On Win/Linux the cmd and ctrl rules never apply at all — cmd-tier combos *are* plain-Ctrl chords there, and no ctrl-tier default resolves there (`focus-hop`'s base tier is shifted) — so the seam is byte-identical to its pre-demotion behavior.

The chords are SPA-renderer bindings, **not Electron menu accelerators** — the shell's documented seam is accelerator *avoidance*, so the letters work identically in shell and browser hosts; only which modifier is bound varies (§ Per-platform default tiers).

### Scope precedence — scoped beats global

`findMatches(e, bindings)` returns **every** enabled matching binding, ordered non-`global` scopes first (registry order within each class). This exists because the mac demotion makes two shipped defaults share a combo by design: the board pane-cycle pair `board-cycle-prev`/`board-cycle-next` (`scope: "board"`) and the global `go-back`/`go-forward` both sit on ⌘[/⌘] on mac hosts.

Resolution is **precedence, not conflict**: the board route keeps pane-cycle on ⌘[/⌘] (back/forward stays palette-reachable there), every other route gets history navigation, and a *paneless* board — where the cycle handlers are absent — falls through to the global back/forward at the same mount, because the dispatcher's walk skips matches with no handler. `findConflicts` therefore flags only **equal**-scope pairs, while `applyCapture`'s steal search deliberately stays `scopesOverlap`-wide (§ Override layer, § Design Decisions).

### Shortcuts panel — the settings dialog's Shortcuts tab (`components/settings-shortcuts-panel.tsx`)

The cheatsheet is **THE single shortcuts surface** — app chords, user macros, and tmux keybindings in one sheet — living as the **Shortcuts tab of the settings dialog** ([dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Settings Dialog), `data-testid="settings-shortcuts-panel"`. It is **dialog-hosted, not a route** (Constitution IV fixes the route set), reached by three affordances: the `shortcuts-overlay` chord (⌘/ on mac hosts, ⇧Ctrl+/ on Win/Linux) and the `Help: Keyboard Shortcuts` palette action — ONE layout-global entry whose body the chord resolves through the merged palette list (§ Single palette mount + palette-actions slot), carrying **three-state toggle** semantics: closed → open on Shortcuts; open on Shortcuts → close; open on another tab → switch to Shortcuts without closing — plus the chevron menu's "Keyboard shortcuts" App-section row, a pure deep-link calling `useSettingsDialog().openSettings("shortcuts")` directly (the row renders under `AppLayout`, so the context is reachable; § Right cluster → overflow chevron menu). The host dialog owns the title, close (Escape/backdrop), and focus trap; the panel uses the bracket-heading vocabulary, `rk-glint` buttons, accent-green states, and theme tokens. Rows, keycap states, and capture all read the **host-effective** map, so the per-platform tiers surface without per-consumer branching.

**One scroll, one filter — no sub-tabs.** The core query is "what's the key for X?", and the user should not have to know which system owns X before asking. So a single filter input spans app rows + macro rows + tmux rows, and everything lives in one scroll container (the tab panel's internal scroll). Navigation is a **sticky jump-nav chip row** under the header instead (`<nav aria-label="Shortcut sections">`, `data-testid="shortcuts-jump-nav"`): `key map · global · terminal · board · custom · tmux`, each chip a `scrollIntoView` anchor onto a section ref. While a filter is active each chip additionally renders its **live match count** and dims (`opacity-40`) at zero hits, so matches below the fold stay discoverable. The `custom` chip renders only when that section does; the `key map` chip carries no count and dims while filtering (the map hides then). Contents in document order:

- **ONE keycap grid with a modifier picker**, **foldable** via a `▾ collapse map` / `▸ expand map` toggle and **auto-hidden entirely while a filter is active** (a keycap grid cannot answer a text query, and the reclaimed vertical space keeps row hits above the fold on short viewports). The **tables are the authority** for effective chords; the map is a **discovery + rebind tool** — which is why one grid answers "what does my keyboard do while I hold these modifiers" rather than two grids re-answering per-action chords the rows already carry. The grid is three rows of keycaps where a key renders `bound` (accent-green, host default combo), `custom` (accent, overridden), `claimed` (amber, dimmed — claimed wins over bound so a browser-reserved N reads claimed) or `free`, annotated with the binding's `mapLabel`, all via one shared `keyCell(states, code, idx)` over a per-layer state map. The map stays **app-layers-only**: tmux prefix chords are sequences, not combos, and do not fit the model. The digit run collapses into a **decorative `…` ellipsis cell** standing for Digit3–Digit8, which takes its claimed styling from **`Digit3`** — the mid-run representative whose shifted-tier mac claim (the ⇧⌘3 screenshot row) keeps the run's claims visible on the mac display, where `Digit1`/`Digit2`/`Digit9` have their own unclaimed cells. On the win/linux display `Digit3` is bound (the `web-toggle` chord), so the ellipsis renders plain there.
  - **The picker IS the map label**: the header's left slot reads **"Holding"** followed by a segmented control (`role="group"`, `aria-label="Keyboard map modifier"`, `aria-pressed` per segment, the platform-toggle visual idiom) whose selected segment supplies the modifier caps — `⌘` | `⇧ ⌘`. Selecting a segment swaps which layer the single grid renders, feeding `tierKeyStates(activeMapTier)`.
  - **The `⌘` option is a macOS-display affordance only** — the Win/Linux unshifted layer is plain Ctrl and belongs to the pane, so that display renders a static **"Holding Shift Ctrl"** label instead (a one-option segmented control is dead chrome). Default selection is `⌘`. The active layer is **derived** (`displayPlatform === "mac" ? mapTier : "shifted"`), so switching the display away from macOS falls back to the shifted layer while the `⌘` selection survives and reapplies on return.
  - **Session-scoped view state**, like the fold: `mapTier`, `mapFolded`, and the platform-display toggle are reading preferences, not transient state — they live in a module-scope `viewPrefs` object (with a `resetShortcutsPanelViewPrefs()` test seam) so they survive the panel's unmount on tab switch or dialog close, unlike the transient filter/capture state that resets with the panel.
  - The map header also carries the **"plain Ctrl always reaches the pane"** note (it explains why there is no Ctrl layer to pick) and the fold toggle, all on one row.
  - **Legend** (four states): `bound` · `custom` · `claimed — taken by the OS / browser / app menu (the desktop app frees the browser ones)` · `free`. The claimed entry is where the browser-vs-desktop story lives in the map — one line, no per-map captions.
- **Platform display toggle** (macOS ↔ Win·Linux) — a **view** control initialized from the detected host: it restyles keycaps and gates the `⌘` picker option, never what this host must actually press. Capture and the header chord always read the physical `host.platform`; claim lookups combine the *display* platform with the *physical* host's `shell` flag.
- **Header chord hint** — `{chord} toggles this sheet` derives from the effective map (`byAction.get("shortcuts-overlay")`) formatted for the physical host, so it reads ⌘/ on a mac and reflects overrides; it is **hidden entirely** when that binding is unbound or disabled rather than advertising a dead chord.
- **Filter input** over label + description, and a per-scope **grouped row list** (GLOBAL / TERMINAL / BOARD) with `ScopeBadge` pills on non-global rows.
- **Shell-owned locked rows are a subgroup at the END of GLOBAL** (a `SubHead` reading "Shell-owned — accelerators live in the desktop shell menu"), not a top-level section — three flavors of locked top-level section was one too many once tmux arrived. Same 🔒 non-interactive idiom (accelerators are edited in the shell menu; the DevTools row is win/linux only), and the rows still count toward the `global` jump chip. Locked rows are **free-form caps arrays**, not tier-constrained, which is what lets the `Switch to server 1–9` row render `⌥ ⌘ 1…9` on the mac display and `Alt 1…9` on the win/linux one — diverging from the shared `tierCaps` helper that still gives `Force reload` ⇧⌘R — because the switcher accelerator lives outside every tier on BOTH platforms (on win/linux the SPA's surface tile chords own ⇧Ctrl+1–3, and Alt is no tier).
- **Click-to-rebind capture** — arming a row installs a capture-phase window listener that `preventDefault`+`stopPropagation`s (keeping the chord away from the dialog's focus trap, the dispatcher, and the legacy listeners — so an armed capture's Escape cancels the capture WITHOUT closing the dialog); a modifier-only or tier-less press keeps capturing. After a successful capture the row shows a steal warning naming the victim, or a claimed-key warning when the combo is spoken for — the claim lookup is **tier-aware** (`c.tier === combo.tier && c.code === combo.code`), so capturing ⌘R inside the mac shell warns that the shell owns it while ⇧⌘R warns separately.
- **Browser-reserved rows carry a per-chord `desktop` tag in browser hosts** — a builtin row whose EFFECTIVE combo resolves `disabledReason: "reserved"` outside the shell renders its canonical keycaps plus a `desktop` pill (the ScopeBadge/pill idiom, `border-accent/60 text-accent-bright`; title "reserved by the browser — works in the desktop app; use the command palette here") — one pill per row, gated `b.disabledReason === "reserved" && !host.shell`, so ANY browser-host reserved row qualifies (the win/linux browser ⇧Ctrl+N/T/W rows included) and shell rows render plain (chord live, no tag): the tag is a browser-host presentation of a per-chord fact, not a blanket per-action label. Rows stay VISIBLE in the browser panel — a user who hits ⌘W out of habit must be able to learn why it did the browser thing. The keyless-base app-window pair renders ⌘N/⇧⌘W keycaps + the tag in a mac browser (their canonical mac combos resolving reserved) rather than an "unbound" button. The CUSTOM macro rows keep the amber `browser` pill instead (title "browser-reserved — rebind; the desktop shell frees this key") — a macro's reserved combo is a user capture, so rebind is the right advice there. Most of the ⌘ layer (⌘K, ⌘., ⌘[/⌘], ⌘/) works in a browser tab too, so the layer as a whole is **not** labelled desktop-only.
- **Per-row modified dot + ↺ reset**, an `unbound` button on user-disabled rows, the per-chord `desktop` tag on browser-host reserved rows (above), and a footer with the localStorage note + **reset all**.
- **`[ CUSTOM ]` section** (`data-testid="macro-section"`) — the editable macro tier (§ Macro bindings). One row per macro: the label, a monospace `macroCommandPreview` chip, the same click-to-rebind combo button as a builtin row (an unbound macro shows the amber `unbound` button; a browser-reserved combo shows the `browser` badge), and a `✕` delete that drops the definition **and** its combo diff. A riff macro whose preset is absent from the fetched preset list renders a red `missing preset` badge — no silent fallback. The grouped GLOBAL/TERMINAL/BOARD lists filter macros out (`b.kind !== "macro"`), so each macro renders exactly once; the filter input searches macro labels and previews too.
- **`+ bind a key to a palette action or riff preset…`** — an inline add flow: a searchable target list (riff presets + the mount's palette actions, macros excluded), a name input pre-filled from the picked target's label, and `add + capture key`, which creates the macro and immediately arms capture on the fresh row — naming and binding in one gesture. Target data arrives via optional props `paletteTargets` / `riffPresetNames`, fed by the settings dialog's Shortcuts-tab wrapper (`ShortcutsTabPanel` in `settings-dialog.tsx`, mounted only while the tab is active): `paletteTargets` is the merged palette list minus the macro entries themselves (no macro→macro chains), and **`paletteTargets == null` gates the whole add flow off** — the wrapper passes none unless the route has a server, so on board/host routes the CUSTOM rows render read/rebind/delete-only. `riffPresetNames == null` means "preset list unknown" — no badges, no riff targets offered.

- **`[ TMUX ]` section** (last, `data-testid="tmux-section"`) — the pane's own keybindings, **read-only**. tmux keys are pressed inside the pane and configured in `configs/tmux/default.conf`; run-kit only documents them, so every row is the same 🔒 locked, non-interactive idiom as the shell-owned subgroup (no capture, no reset, no rebind). Data is the existing curated `getKeybindings(currentServer)` client API (`app/backend/api/keybindings.go`'s whitelist — a read-only dependency, unchanged). Two `SubHead` groups: **Direct** for root-table rows (F2/F3/F4 new/prev/next window, Shift+F3/F4 prev/next pane, Shift+F7 copy mode) and **Prefix — Ctrl+S, then key** for prefix-table rows, rendered as a keycap **sequence** (`Ctrl` `S` *then* `\`) rather than a simultaneous combo. Both subheads hide while filtering (the group labels are navigation, not matches). Key-name formatting is `S-` → `Shift+`, `C-` → `Ctrl+`.

  The server comes from `useSessionContext().currentServer` read **inside** the panel, and the fetch runs only while the panel is visible (its tab active — the panel unmounts otherwise), cancel-flagged on unmount/server change. `null` bindings means loading; `[]` means no current server (board/host routes), an empty response, or a failed fetch — all three collapse to the one-line **"No tmux server running"** empty state, so there is no spinner deadlock and no crash path.

`riffPresetNames` comes from a best-effort `getRiffPresets(server, session)` fetch inside the settings dialog's `ShortcutsTabPanel` (`settings-dialog.tsx`) that runs only **while the Shortcuts tab is visible on a route with a session**, mapped to names; a failed fetch leaves it `null`. Detection is therefore advisory — `POST /api/riff` validates authoritatively at execution time either way (§ Macro bindings), so a macro is never silently inert.

Export/import of overrides is not offered.

### Palette hints

`withShortcutHints(actions, byAction, platform)` (pure, in `lib/keybindings.ts`) decorates a palette action array with each action's **effective** combo as its `shortcut` hint — `actionId` doubles as the palette id, so the join is free. Each route applies it to the list it registers into the slot (AppShell's `paletteActions`, the board's `boardRouteActions`), and the layout applies it to the global groups inside `use-global-palette-actions.ts` (§ Single palette mount + palette-actions slot). Formatting is per platform via `formatCombo`/`comboParts`: mac symbol tiers join bare (`⇧⌘N`, `⌘.`), other platforms join with `+` (`Shift+Ctrl+N`), and the `ctrl` tier keeps the `` Ctrl+` `` spelling on both. Hints reflect overrides. A **disabled** binding (user-disabled or browser-reserved) contributes NO hint — advertising a dead chord would lie — while the palette entry itself stays reachable. Actions with no registered binding pass through untouched, so hand-set hints survive; `buildViewActions` (`lib/palette-view.ts`) takes the effective cycle hint string as a parameter rather than hardcoding it.

The **page tier** — the unshifted `⌘<key>` tier on macOS, unshifted `Ctrl+<key>` on Windows/Linux — is left entirely unbound by the Electron desktop shell on every platform it packages for ([desktop-shell](/run-kit/desktop-shell.md) § Keyboard-Tier Menu Seam). The SPA spends part of that budget on **macOS**: ⌘[/⌘]/⌘/, ⌘B, and ⌘↑/⌘↓ in both mac hosts, the ⌘1/⌘2/⌘3 surface digits and ⌘I effectively inside the mac shell (a mac browser's tab-digit claims reserve ⌘1–9 as data, and ⌘I is an interception attempt that degrades to palette when blocked), and ⌘N/⌘T/⌘W/⌘, on every mac host — browser-reserved in a mac browser, so live only inside the shell (§ Per-platform default tiers) — alongside the legacy ⌘K/⌘. chords that always lived there. The demotion seam is the single mac branch of `defaultComboFor`; host shape never gates a default. Whatever the SPA does not take stays the browser's or the OS's: mac-browser ⌘N/T/W/L and ⌘1–9 are claimed data, and on **Windows/Linux the page tier remains untouched by the SPA** — plain Ctrl is the pane's.

### Education micro-copy (placeholders, empty states, in-situ hints)

Discoverability copy lives **at the point of use**, never in a dedicated surface — placeholders, empty states, and existing Tips teach the hidden feature they sit on, each string computed where the mode is known so it cannot lie about it (§ Design Decisions → Placeholder over inline legend; → Hints render from current state alone). No new routes, dialogs, or persistent state — the whole apparatus is copy plus existing Tip `kbd` slots and menu-row keycap chips. (`260811-ke2s`)

- **Mode-aware placeholders.** The compose strip's textarea is the exemplar (§ Docked Compose Strip): terminal target `Compose text — Enter inserts · {submitKeycap} sends · ↑ history` (the sole surfacing of ↑ sent-history recall anywhere in the UI), selection broadcast `Compose prompt — {submitKeycap} sends to all selected`, no target `No focused terminal — click a pane to target it`. The chat send box reads `Message the agent — Enter for newline · {submitKeycap} sends` — chat's plain Enter deliberately diverges from the strip (newline, not insert-line), and the placeholder is where the divergence stops surprising ([chat](/run-kit/chat.md) § Send-form input box). The command-palette input reads `Type a command — try Board: Pin: View: Tab:` and its no-results row `No results — try a prefix: Board:, Pin:, View:, Window:` — typed-namespace education, not a chord, so neither branches on pointer type (the confirming step's `Confirm action...` is untouched).
- **Empty states name their fill action.** No bare labels: the board page and host BOARDS zone name the sidebar row 📌 + `Pin:` palette route; SERVICES reads `No services — listening TCP ports appear here automatically`; HOST HEALTH `No metrics — waiting for the host's first report`; a session-less server group reads `(no sessions — a session groups tabs; + new, or {chord})`; every `{chord}` here is fine-pointer-only (see the coarse-pointer bullet below); the shortcuts panel's no-match line scopes its own filter (`… · the filter spans app, custom & tmux keys`).
- **Platform-aware keycaps, never hardcoded lies.** Fixed Enter-policy chords (owned by `classifyComposeEnter`, not the registry) use the `composeSubmitKeycap()` seam. Chords for **rebindable** actions (`create-session`, `command-palette`, `open-last-used`) are read from `useKeybindings().byAction` + `formatCombo(…, host.platform)` and the clause is **omitted when the binding is unbound/disabled** — the `sheetChord`/palette-hints rule (§ Palette hints, § Tier-1 `Tip`) extended to prose copy. The derivation stays inline at each call site (no shared helper — readability over cleverness).
- **Menu-row keycaps.** A menu row whose action has a registry binding carries a trailing right-aligned `kbd` chip (the shared `MENU_ROW_KBD_CLASS`, palette-row visual weight, `ml-auto`, `aria-hidden` so the chord stays out of the accessible name), derived inline by the same `byAction` + `formatCombo` enabled-else-`undefined` rule — the SplitControl direction popover rows, the overflow chevron menu's split rows (§ Split control), and the App-section Settings / Keyboard shortcuts rows. A menu is itself a discovery surface, so every open doubles as a shortcut lesson; rows without a matching binding stay keycap-free. (`260811-0f3d`)
- **Coarse pointers keep the short copy.** Keyboard-chord hints never render on touch — the Tip suppression rule (§ Design Decisions → Suppress-by-early-return on coarse pointers) applied to strings via `useCoarsePointer()`. It binds **every** chord clause, not just the placeholders: placeholders fall back to their short forms (`Compose prompt…` / `Message the agent…`; the compose strip's terminal-target coarse placeholder instead folds the target name in — `→ {name}…`, § Docked Compose Strip → Header fold + the coarse ⏎ local-newline chip); the SelectionIndicator drops both its `⇧click extends` clause and its `{chord} → Selection:` clause; and the empty states drop their chord tail, leaving the pointer path alone (`(no sessions — a session groups tabs; + new)`, `… click its 📌` on the board page and the host BOARDS zone). Each site folds the pointer test into the same expression that derives the chord (`!coarse && binding?.enabled ? formatCombo(…) : undefined`), so an unbound binding and a touch pointer collapse to one `undefined` and the copy has a single fallback branch.
- **Stateless.** Every hint renders from current state alone (selection active, binding bound, pointer type) — no first-run tours, dismissal flags, or rotating tip carousels.

Persisted via the EXISTING `setSessionOrder(server, order)` — the same primitive the sidebar session drag uses; no new backend.
- **`Tab: Move up` / `Tab: Move down`** (`window-move-up`/`-down`, `windowActions`) — move the current window ±1 index via `moveWindow(server, windowId, targetIndex)`, then navigate to the same stable window ID with `search: (prev) => prev` (view-preserving). The sole window-move pair. See § Window move actions above.

**`Board: Move up` / `Board: Move down`** (`board-move-up`/`-down`) — the same boundary-hidden / no-wraparound keyboard+touch path for the board list, registered in `board-page.tsx`'s `boardRouteActions` (NOT `app.tsx`), because "current board" only has meaning on a `/board/$name` route (the board registers its own route-scoped list — § Single palette mount + palette-actions slot). Each acts on the CURRENT board (the `/board/$name` param), computes the full new order via `computeMoveOrder(boardNames, currentBoardIdx, delta)` over the backend-sorted `boards`, and POSTs it via `setBoardOrder` (server-global `event: board-order` echo re-sorts every client — see § Board-list drag reorder). Hidden when the current board is first (`currentBoardIdx === 0` → only Move down) or last (only Move up); a `null` from `computeMoveOrder` is a defensive no-op. `onError` surfaces `useToast().addToast`. (`260708-a2qd`)

**Pure order-computation helpers** — the boundary gating, effective-order derivation, and swap arithmetic are extracted into `app/frontend/src/lib/palette-move.ts` (Vitest-covered `palette-move.test.ts`) so they are testable without mounting the shell; the palette action bodies are thin wrappers that call these then invoke the client mutation. Exports: `deriveEffectiveSessionOrder(liveNames, sseOrder)` (SSE-order-∪-natural), `computeMoveOrder(order, currentIdx, delta)` (insert-before splice, `null` on boundary/out-of-range — shared by Server, Session, AND Board Move), and `computeWindowMoveTarget(index, delta, minIndex, maxIndex)` (target index, `null` on boundary — used by the `Tab: Move` up/down pair). `MoveDelta = -1 | 1`.

**Selection palette commands (`Selection:` prefix)** — the action surface for the sidebar's window-row multi-select (§ Window-Row Multi-Select). Composed by the pure builders in `lib/palette-selection.ts` (+ colocated `palette-selection.test.ts`, the `palette-pin.ts`/`palette-move.ts` convention) with thin `onSelectAll(keys)` / `onClose(keys)` / `onCompose(keys)` / `onMove(targetSession)` bodies wired in `app.tsx`'s `selectionActions` memo. Four entry kinds, every one **omitted rather than disabled** when ineligible (the family's convention) — close and send need only a non-empty selection, so they are the two that stay eligible across a **cross-server** one (§ Design Decisions → Close and send are cross-server): (`260807-nf9f`, `260808-ebgs`)

- **`Selection: Select all merged (N)`** (id `selection-select-all-merged`) — replaces the selection with exactly the current server's merged-PR windows via `selectOnly`. Merged comes from the PR knowledge the frontend already has: `win.prState === "merged"` read directly (`mergedWindowKeys`), the same field `prGlyphColor` reads for its merged branch (§ Shared PR vocabulary). Scoped to the current server — a cross-server selection would dead-end the single-server bulk move below. Omitted with no current-server context or no merged windows. **It also carries the feature's discovery surface**: `SELECTION_GESTURE_HINT` (`x · ⌘-click · ⇧-click`) rides its `shortcut` badge, which the palette renders as a `<kbd>`. That is deliberate — `x` is a bare key handled inside the tree's own keydown and is NOT in `DEFAULT_BINDINGS` (§ Design Decisions → The `x` toggle is documented at the palette registration), so it appears on no chord map and in no shortcuts panel.
- **`Selection: Close N tab(s)`** (id `selection-close`, `buildSelectionCloseAction`) — the destructive one, and the only palette entry in the app that **confirms in the palette itself**. It carries a `confirmLabel` (`Close N tab(s) — Enter to confirm`), an optional field on `PaletteAction` that `CommandPalette` interprets as a **one-row confirmation sub-step**: selecting the entry does NOT run `onSelect` — it stashes the action in `confirming` state, replaces the whole result list with the single derived `${id}-confirm` row, resets query + index, and makes the search input `readOnly` with a `Confirm action…` placeholder (so typing cannot escape the step). Enter on that row runs the action once and closes; Escape (the shared `useFocusTrap` document handler), a backdrop click, and the ⌘K toggle all cancel through the same `closePalette` / `setConfirming(null)` seam, leaving the windows live and the selection intact. The mechanism is generic — any action can opt in by setting `confirmLabel`; the confirmed row itself carries `confirmLabel: undefined`, so a step can never recurse.
- **`Selection: Send prompt to N agent(s)`** (id `selection-send-prompt`, `buildSelectionSendPromptAction`) — hands a **snapshot** of the selected keys to `app.tsx`, which stores it as `selectionBroadcastKeys` and routes text entry to the docked compose strip in its selection-broadcast target mode (§ Docked Compose Strip → Selection-broadcast target). The action does not send: it opens the strip if the `composeStripEnabled` preference is off (`toggleComposeStrip()`, whose off→on focus-on-open flag then focuses the textarea) or, when it is already mounted, focuses it via `queueMicrotask(() => focusComposeStrip())` — one microtask later, so React has swapped the disabled focused-terminal target for the selection target first. Toggling the strip off cancels the target (an effect clearing `selectionBroadcastKeys`); per-window drafts in the module store are untouched.
- **`Selection: Move N tab(s) to <session>`** (ids `selection-move-to-<session>`) — one entry per eligible existing session, with the live count and correct singular/plural. **The palette's fuzzy filter IS the session picker**: no dialog, no create-if-missing, no new backend surface. A target that would be a COMPLETE no-op (every selected window already lives in it) is excluded; a selection with unresolved keys excludes nothing, since the move is still meaningful.

**The move family's server is the SELECTION's, never the route's.** With sessions scope `all` the sidebar paints every server's groups, so a user can select rows on server A while routed to server B — and tmux `@N` ids are unique per server only, so feeding the route server's sessions would list the wrong targets AND move the wrong windows. `app.tsx` derives `selectionServer = singleSelectedServer(selectedWindows)` and passes THAT server's sessions (the merged `useMergedSessions` list when it is the route server — it carries the ghost/rename overlays the sidebar paints — else the raw `ctx.sessionsByServer.get(srv)`), omitting the entries entirely when that server's sessions are `undefined` (not loaded yet, which is not the same answer as "no eligible targets"). `buildSelectionMoveActions` additionally takes an explicit `sessionsServer` first parameter and returns `[]` on a mismatch, so the contract is enforceable at the builder seam rather than trusted at the call site. `singleSelectedServer` returning `null` for an empty or cross-server selection omits the whole family (§ Design Decisions → The move builder owns the server-match guard).

The entries are folded into `paletteActions` in AppShell only. The **board route registers board-scoped actions only** (§ Design Decisions → One palette mount in AppLayout, routes register via the slot) and does not include them, while `BoardPage` mounts the sidebar with `currentServer={null}`. So a board-route user can still build a selection, but the indicator **suppresses its `→ Selection:` hint** there — `SelectionIndicator` takes `hasSelectionActions={currentServer !== null}`, keyed on the same non-null-server condition the `Selection:` family itself is scoped to — rather than advertising a palette route to entries that route cannot reach.

**Cross-session move actions**: Dynamically generated "Tab: Move to {sessionName}" actions (id `move-window-to-session-{sessionName}`) — one per session other than the current one. Only shown when `currentWindow` exists AND there are at least 2 sessions. On select, calls `moveWindowToSession(server, currentWindow.windowId, targetSession)` then navigates to `/$server` (server dashboard) because tmux auto-assigns the window index in the destination session and no `/$server/$session` route exists. Flat action list (not a sub-picker) — works well for typical session counts (2-5) and requires zero changes to the command palette component.

### Tmux Commands Dialog

`app/frontend/src/components/tmux-commands-dialog.tsx` — opened via command palette "Copy: tmux Commands" action (id `copy-tmux-attach`). Only available on terminal pages when `currentWindow` exists. Opens a `Dialog` with title "tmux commands" showing two copyable tmux command rows plus one non-copyable hint row:

| Label | Command |
|-------|---------|
| Attach | `tmux [-L {server}] attach-session -t {session} \; select-window -t {windowId}` |
| Send keys | `tmux [-L {server}] send-keys -t {windowId} "..." Enter` |
| Detach (while attached) | `prefix, d (Ctrl+S, d)` — hint text, no copy button |

A tmux window ID (`@N`) is a server-global, self-contained target, so the commands address `{windowId}` directly rather than a positional `{session}:{index}`.

**Server-aware command generation**: Commands include the `-L {server}` flag only when the server is not `"default"`. When the server is `"default"`, the flag is omitted. This matches the `tmuxExecServer` convention in the backend (see `tmux-sessions.md`).

Each copyable row has a label (`text-text-secondary text-[11px]`), a monospace code block (`bg-bg-inset border border-border rounded px-2 py-1.5 font-mono text-[11px] select-all`), and a copy button. Clicking the copy button writes the command to the clipboard via `navigator.clipboard.writeText` and swaps the copy icon to a checkmark for 1.5 seconds before reverting. Clipboard failure is silently caught.

Dialog state is a `showTmuxCommands` boolean in `app.tsx` (a route-local dialog state, unlike the layout-mounted server dialogs). Props: `server`, `session`, `windowId`, `onClose`.

### Command Palette Mobile Trigger

The `CommandPalette` component listens for a `palette:open` CustomEvent on `document` (in addition to `⌘K`). The `⋯` button in Line 1 dispatches this event on mobile. This is the mobile equivalent of `⌘K` — physical keyboards aren't available on phones.

### Keyboard-Navigable List Scroll Pattern

Both `CommandPalette` and `ThemeSelector` use the same scroll-into-view pattern for arrow key navigation: a `listRef` on the listbox container plus a `useEffect` on `[selectedIndex, open]` that queries `[aria-selected="true"]` and calls `scrollIntoView({ block: "nearest" })`. This ensures the selected item stays visible when navigating past the `max-h-64` scroll boundary. New keyboard-navigable list components SHOULD follow this pattern.

The sidebar session/window tree is a **third consumer** (see § Sidebar → Keyboard Navigation & Tree ARIA): a `treeRef` on the `role="tree"` container plus a `useEffect` on `[rovingKey]` that resolves the roving row (`[data-window-id]`/`[data-session-row]`) and calls `scrollIntoView({ block: "nearest" })` + `focus()`. It reuses the scroll-into-view half but deliberately diverges from the `selectedIndex` numeric-state model — the roving cursor is a row-key STRING (robust to the variable-length tree's expand/collapse and SSE row churn, where a numeric index can desync); the focus call is gated by `focusMovedRef` so passive SSE re-renders never scroll/steal focus.

## Design Decisions

### Statefulness lives in chord handlers, not palette bodies
**Decision**: The surface family's three-state show+focus / focus / hide rule (§ Stateful surface chords) is implemented in the chord handler layer (`lib/tile-chord.ts`, `runComposeToggleChord`, `useSidebarKeyboardToggle`); the palette `Tile:`/`Sidebar:`/`Compose:` entries keep explicit single-verb bodies.
**Why**: Palette entries are self-describing verbs a user picks by name — a stateful palette row would do different things on identical clicks; chords are positional muscle memory where statefulness is the point (the JetBrains tool-window model).
**Rejected**: Making `togglePanel` itself stateful — it backs the top-bar toggles and menu checkboxes, whose checkbox semantics must stay pure toggle.
*Introduced by*: 260819-qwr7-surface-focus-chords

### Zen is a transient render-time override, bound as a shifted-tier Enter chord
**Decision**: `zen-toggle` ships bound on `Enter` at the shifted tier on BOTH platforms (no `macTier`), with `ignoreInputs: true`, toggling the full zen state at ANY arity on the desktop terminal route: entering hides the top bar and the sidebar as render-time overrides and, at arity > 1, zooms the focused tile through the app-level zoom ref seam when not already zoomed. Zen state lives in `ZenContext` (deliberately NOT ChromeContext, whose shape is persisted chrome) and is never written to a URL param or localStorage — the sidebar hide composes `sidebarOpen && !zenActive` in Shell, and `setSidebarOpen` is never called on a zen path. Zen keeps the compose strip and the status bar visible, survives window switches within the terminal route, and deactivates off it.
**Why**: ⇧⌘⏎ is the iTerm2 maximize-pane habit; exact-modifier matching keeps the chord disjoint from the classifier-owned ⌘Enter/Ctrl+Enter compose-submit chords, which never carry Shift (enforced in `classifyComposeEnter`: a shift-carrying meta/ctrl Enter returns `default` and is never consumed by either compose surface, 260820-ecl4); Enter is free in every claim set; `ignoreInputs` lets the chord fire from the compose textarea. The transient-override design is what makes a compound zen possible WITHOUT coupling transient zoom state to persisted sidebar state: no zen path writes a persisted preference, so a reload — or exit — restores exactly what persisted state says.
**Rejected**: ⇧⌘M (one shift from ⌘M minimize, opposite meaning); writing zen into ChromeContext (its fields are persisted chrome — the shape itself would suggest persistence); suppressing the sidebar via `setSidebarOpen(false)` (persists `runkit-sidebar-open`); a default-unbound binding row (`KeyBinding.code` is a required field — default-unbound needs a type change rippling through combo matching for one action).
*Introduced by*: 260820-o8cr-true-zen-mode

### Exit unzooms only a zen-initiated zoom
**Decision**: one `zenZoomed` boolean beside `zenActive` records whether zen initiated the tile zoom; exit unzooms only when it is true and the zoom is still in effect (a manual unzoom mid-zen is not toggled back into a zoom).
**Why**: a zoom the user made before entering zen is their arrangement choice and survives exit; tracking is one boolean.
**Rejected**: always-unzoom on exit (materially simpler but destroys a pre-existing user zoom).
*Introduced by*: 260820-o8cr-true-zen-mode

### Esc is not a zen exit binding
**Decision**: zen exit affordances are ⇧⌘⏎ (toggle) and the status-bar exit-zen button (rendered only while zen is active) only.
**Why**: Esc must keep flowing to the terminal pane — vim/menus/readline consume it; a global Esc binding would break terminal use.
**Rejected**: a global Esc exit binding.
*Introduced by*: 260820-o8cr-true-zen-mode

### Shell servers reach the palette by empty-list gating, not an `isShell()` branch
**Decision**: `useShellServers()` resolves `[]` outside the desktop shell (the bridge wrappers swallow every absent/malformed/denied case), so `buildShellServerActions` yields no entries and `app.tsx` registers the group unconditionally — no `isShell()` conditional at the registration site. The list is a mount-time snapshot with no refresh seam, quoted labels distinguish shell servers from tmux servers, and v1 is switch-only.
**Why**: One code path for both environments — an `isShell()` branch would gate on a *second* signal that can disagree with whether the `servers` group actually answers (an older shell has `version`/`platform` but no bridge group), so the list's own emptiness is the more truthful gate. A snapshot suffices because every list mutation the shell offers (switch, add) loads a different server URL, which remounts the SPA anyway; only removing a non-active server leaves a stale entry until reload.
**Rejected**: An explicit `isShell()` conditional around the registration (a second, less accurate signal); a live refresh subscription or poll (a new seam for a list that changes only via flows that already remount the SPA); unquoted labels matching the tmux entries (two different kinds of "server" reading identically in one palette); including Add/Remove Server (Constitution IV — the native menu + welcome flow already own those, and Remove needs a confirm dialog the palette has no home for).
*Introduced by*: 260730-9lez-shell-keyboard-tier-symmetry

### One palette mount in AppLayout, routes register via the slot
**Decision**: The single (lazy) `CommandPalette` mounts in `AppLayout` and renders `[...routeActions, ...globalActions]` — routes publish route-scoped, shortcut-decorated lists through `useRegisterPaletteActions` (`palette-actions-context`, the `top-bar-slot-context` pattern), and the global groups (nav, font, refresh, help, shortcuts, settings, update/check/maintenance/version) build once at the layout in `use-global-palette-actions.ts`. The server create/kill dialogs follow the same shape: one mount in `AppLayout` (`server-dialogs-context` + `components/server-dialogs.tsx`, the `settings-dialog-context` pattern), triggered from any route.
**Why**: The board route does not render AppShell, so per-route mounts forced every globally-meaningful action and the server dialogs to be re-implemented inside `BoardPage` — and the twins had drifted in user-visible ways (the board's kill confirm lacked the daemon warning; its create input skipped the safe-name sanitization). A layout mount plus a register channel makes a global unreachable-by-omission impossible and gives every route the same dialog behavior.
**Rejected**: Per-route palette/dialog mounts with duplicated global groups (drift is inevitable — each global tweak must be written twice); rendering AppShell on the board route (AppShell is deliberately server-scoped); shared JSX with per-route state (removes JSX drift but keeps the state twins).
*Introduced by*: 260811-239r-board-twin-dialogs-palette

### The palette slot splits state from a stable API channel
**Decision**: `palette-actions-context` exposes three channels — a reactive state channel (`usePaletteActions`, the merged list, for the layout-level leaves that render it), a referentially-stable API channel (`setRouteActions` / `getAllActions`, identity never changes), and a globals-only channel (`usePaletteGlobals`) that routes may safely subscribe to. Routes resolve ids over `[...localRouteActions, ...globalActions]` at memo-build time, or imperatively via `getAllActions()` at chord/macro-invocation time.
**Why**: A route that both publishes its actions and subscribes to the merged state closes a render loop (publish → state change → re-render → fresh action identities → re-publish → "Maximum update depth exceeded"); and resolving through the slot state would lag one commit (the registration effect lands after the route's memo builds) with no way to trigger a rebuild, so a chord could stay dead. The globals-only prop identity never changes in response to a route registration, so subscribing to it is loop-safe.
**Rejected**: One reactive context for everything (render loop); routing all id resolution through the slot state (one-commit lag, unreachable rebuild).
*Introduced by*: 260811-239r-board-twin-dialogs-palette

### The action tier's LETTERS are uniform; its modifier is per platform
**Decision**: The canonical letters (N/T/W/A + [/]//, plus H on the hosts chord) are the same on every platform except where a `macCode` refinement deliberately moves one (the split pair, `compose-toggle`, `create-session`, the session-jump pair), but the modifier is not: Windows/Linux uses `Shift+Ctrl` throughout, while macOS demotes to the unshifted ⌘ tier wherever nothing immovable blocks it — [/]//, the ⌘↑/⌘↓ window-cycle pair, and the N/T/W family (⌘T tab / ⇧⌘T session, ⌘W tab / ⇧⌘W app window, ⌘N new app window) on every mac host (browser-reserved in a mac browser, so palette-only there), with A and the hosts H staying shifted everywhere. The refinement is declarative data on each binding (`macTier`/`macCode`) resolved once in `defaultComboFor`.
**Why**: Letter consistency is what must not fragment; chord weight is negotiable per environment, and the constraints that force Shift were never symmetric. Plain Ctrl must stay with the pane on Windows/Linux (Ctrl+W delete-word, Ctrl+L clear, Ctrl+T fzf, Ctrl+N/P history) — a macOS-only constraint-free tier gets taxed for nothing by uniformity, and the desktop shell exists precisely to hand the SPA the unshifted ⌘ tier, so a uniformly-shifted tier left that premise unspent. What blocks a demotion is genuinely immovable, not aesthetic: ⌘H is macOS Hide and ⌘A is select-all / the shell's Edit role. Because the resolver already funnels every consumer through one effective map, expressing the tier as per-key data costs no architecture.
**Rejected**: A uniform shifted tier on every platform (taxes mac users a three-key chord the environment would give them in two, and leaves the shell's whole reason for existing unused); demoting A or the hosts H too (⌘A/⌘H are dead in both mac hosts — the chord would silently do nothing); per-platform `DEFAULT_BINDINGS` arrays or a resolver-level actionId→tier table (duplicates every binding, or splits the per-key truth across two structures).
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts

### The mac N/T/W chords follow the two-level tab convention — unshifted ⌘ is the tab level, ⇧⌘ the level above
**Decision**: On mac hosts the unshifted ⌘ chord is the tab/tmux level and the shifted chord is the bigger variant of the same letter: ⌘T new tab / ⇧⌘T new session, ⌘W close tab / ⇧⌘W close app window, with ⌘N on the new app window. `create-session` keeps its shifted tier and carries `macCode: "KeyT"` (tier-disjoint from `create-window`'s ⌘T on the one code — the split-pair precedent); the app-window pair ships keyless base (`code: ""`) with `macCode` spending ⌘N/⇧⌘W on every mac host. In a mac browser these canonical combos are browser-reserved, so all five actions are palette-only there.
**Why**: It matches the universal macOS convention (Chrome/Safari/iTerm2/JetBrains: ⌘N window, ⌘T tab) and is frequency-correct — sessions are created far less often than tabs, so the cheaper chord goes to the tab level.
**Rejected**: Keeping ⌘N on `create-session` — inverts platform muscle memory and spends ⌘N on something that is not an OS-level window.
*Introduced by*: 260820-lfla-ntw-keymap-tab-rename

### "Tab" is the user-facing word for a tmux window; "window" is reserved for app windows and internals
**Decision**: User-facing copy says "tab" for tmux windows on every platform — shortcut overlay labels (New tab / Close tab / Previous tab / Next tab), mapLabels (new tab / close tab / prev tab / next tab), the palette's `Tab:` prefix for tmux-window-tied entries (`Tab: Create`, `Tab: Rename`, `Tab: Kill`, `Tab: Split …`, `Tab: Move …`), kill-confirm copy, sidebar aria-labels (`Rename tab`, `Set tab label`, `New tab in <session>`), toasts, hints, and the top-bar center heading prefix `Tab: <name>` (rename aria "Tab name"). "Window" is reserved for app windows (the `App: New Window` / `App: Close Window` palette entries, the shell menu's New Window / Close Window items) and for internals — actionIds (`create-window`, `kill-window`, `window-prev`, `window-next`), the API, and the tmux layer keep "window", as do the browser-owned claim labels ("new window", "close window" — they describe browser chrome).
**Why**: With the app-window pair sitting beside the tmux level in the same keymap and palette, "window" would otherwise mean two unrelated things (tmux window, app window) in labels and menus with no way for copy to disambiguate them.
**Rejected**: Per-platform copy forks (the vocabulary collision is platform-independent); renaming the internals/tmux layer (needless churn, no user-facing benefit).
*Introduced by*: 260820-lfla-ntw-keymap-tab-rename

### Win/Linux keeps ⇧Ctrl+N/T/W and a menu-only New Window — plain Ctrl belongs to the pane
**Decision**: The N/T/W realignment is mac-only: Win/Linux keeps ⇧Ctrl+N/T/W unchanged, and the shell's New Window item stays menu-only there (the app-window pair's keyless base resolves unbound off mac).
**Why**: Plain Ctrl belongs to the terminal pane on Win/Linux (readline Ctrl+N next-history, Ctrl+T transpose-chars), so the unshifted tier the mac shell hands the SPA has no analog there.
**Rejected**: Mirroring the mac ⌘-tier scheme on Ctrl — would shadow readline chords in every pane.
*Introduced by*: 260820-lfla-ntw-keymap-tab-rename

### The tables are the chord authority; the key map is a discovery and rebind tool
**Decision**: The panel renders ONE keycap grid with a "Holding ⌘ | ⇧⌘" modifier picker, and a browser-reserved chord carries its own per-chord `desktop` tag on the affected table ROWS rather than in a second grid or a per-map caption.
**Why**: Two stacked grids named the registry's internal tier taxonomy in user-facing chrome and re-answered per-action chords the rows already carry, at double the vertical mass — which pushed the authoritative tables and the TMUX section below the fold on short viewports. Giving each surface one job removes the duplication instead of restyling it: the map answers the physical question ("hold this — here's what my keyboard does", the model Karabiner-style keyboard viewers use), and the rows carry the per-action truth including where a chord cannot fire. The reserved state is genuinely per-chord, so a row is where the fact belongs.
**Rejected**: Keeping both grids with de-jargonized headers (still double the vertical mass, still duplicates the tables); labelling the whole ⌘ layer desktop-only (factually wrong — ⌘K/⌘./⌘[/⌘]//⌘/ all work in a browser tab); hiding browser-reserved rows in the browser panel (a user who hits ⌘W out of habit must be able to learn why it did the browser thing).
*Introduced by*: 260801-r8j2-shortcuts-map-modifier-picker

### One canonical chord per action; the `desktop` tag is the browser-host presentation of a reserved chord
**Decision**: Every action ships exactly one default chord per platform (the mac refinement applies on ALL mac hosts — no shell-gated alternates); a chord the browser reserves has no replacement browser chord and resolves `disabledReason: "reserved"` through claims data, staying palette-reachable (Constitution V's complete-registry guarantee). In the shortcuts panel, a browser-host reserved builtin row renders its canonical keycaps plus a single `desktop` pill ("reserved by the browser — works in the desktop app; use the command palette here"); rows stay visible, and shell rows render plain.
**Why**: A per-surface chord pair is two shortcuts nobody memorizes and doubles the panel's clutter — worse, the browser alternates for the N/T/W family were themselves browser-reserved dead chords. One canonical chord plus the palette fallback gives one thing to learn; the visible `desktop` tag answers "where does this chord work?" and preserves the learn-why-⌘W-did-the-browser-thing moment.
**Rejected**: Keeping distinct browser chord remaps (memorization tax, and the advertised second mapping was largely a dead chord); adding a second chord for any browser-blocked action (the palette is the browser path); hiding desktop-only rows in the browser panel (the user learns nothing); two pills on one row (the `desktop` tag and the old amber `browser` pill mark the same underlying reserved state — one affordance per fact).
*Introduced by*: 260823-c5yq-single-chord-palette-registry-session-copy

### The picker IS the map label, and the inactive layer falls back by derivation
**Decision**: The map header's left slot is "Holding" plus the segmented control itself (the selected segment supplies the modifier caps), with a static "Holding **Shift Ctrl**" on the Win·Linux display; the rendered layer is derived (`displayPlatform === "mac" ? mapTier : "shifted"`) rather than reset when the display toggles.
**Why**: The picker and the layer label are the same header element — rendering them separately would duplicate the modifier caps and widen the header row, and a one-option segmented control on Win·Linux is dead chrome. Deriving the fallback matches "the option disappears" rather than "the selection is destroyed": a user flipping the display to Win·Linux and back gets their ⌘ selection returned, consistent with the session-scoped view state the fold already establishes.
**Rejected**: A separate "Holding ⇧⌘" title plus a detached picker (duplicates the caps); resetting `mapTier` on display change (loses the selection on a round-trip for no benefit); persisting the selection to localStorage (a reading preference within one sheet, not a device setting).
*Introduced by*: 260801-r8j2-shortcuts-map-modifier-picker

### Chord handlers are the palette action bodies, looked up by id
**Decision**: The AppShell dispatcher resolves `create-session`, `create-window`, `kill-window`, `agent-next-waiting`, `go-back`, `go-forward`, and `settings-open` by finding the palette action with the matching id — over the MERGED route+globals list (`fromPalette` over `[...routeActions, ...usePaletteGlobals()]`, § The palette slot splits state from a stable API channel) — and reusing its `onSelect`.
**Why**: `actionId` doubles as the palette id by design, so the lookup is free — and reuse makes chord/palette drift impossible, including gating: a palette entry that does not exist (e.g. `kill-window` with no active session) yields no handler, and the dispatcher's no-handler fall-through is exactly the desired no-op. Resolving over the merged list keeps chords working when an id's ownership moves between a route group and the layout-level globals.
**Rejected**: A parallel handler implementation per chord — duplicates every gate and drifts from the palette behavior it must mirror.
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### Enablement-bearing chords keep their own listeners; the registry owns definition and suppression
**Decision**: `command-palette`, `sidebar-toggle`, and `view-cycle` dispatch from component/hook-local listeners that read their combo from the effective map and gate on the shared suppression predicate; the other chords (including the board pane-cycle) run through `useKeybindingDispatch`.
**Why**: Centralizing *definition* and *suppression* is the registry's charter; centralizing *enablement* is not — palette open-state and lens availability are local state, and routing them through one dispatcher would need context plumbing for zero user-visible gain.
**Rejected**: One dispatcher for every chord (high regression risk, new context plumbing); leaving these chords out of the registry entirely (they would be unrebindable and invisible to the shortcuts panel).
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### The terminal seam refuses shifted chords everywhere, cmd chords only on mac (metaKey-gated), and ctrl-tier chords only on mac (ctrlKey-gated)
**Decision**: `shouldRefuseTerminalChord` returns `true` for an enabled shifted-tier match on any platform, an enabled cmd-tier match on macOS **only when `event.metaKey` is set**, and an enabled ctrl-tier match on macOS **only when `event.ctrlKey` is set without `metaKey`**; everything else returns `true` from the handler (reaches the pane), after the ⌘C copy case.
**Why**: Refusal must be exactly as wide as the set of chords the pane cannot use. Legacy TTY encoding cannot distinguish Ctrl+Shift+letter from Ctrl+letter, so the shifted tier costs the pane nothing anywhere; ⌘ chords never reach a pane as control bytes, so refusing them on mac is loss-free and is what lets the demoted ⌘[/⌘]/⌘/, ⌘B, ⌘1/⌘2/⌘3, and ⌘I fire under terminal focus. The `metaKey` gate is the load-bearing half: `matchesCombo`'s cmd tier accepts Meta **or** Ctrl, so an ungated refusal would steal Ctrl+[ (ESC) from mac panes — the same hazard that forbids cmd refusal on Windows/Linux, where CmdOrCtrl *is* the pane's own Ctrl. The ctrl-tier rule is what lets ⌃` (`focus-hop`) fire under terminal focus on mac; it steals NUL (the byte Ctrl+` encodes to) from the pane — near-zero cost, the same trade VS Code makes for its own ⌃` — and its `!metaKey` gate is rule 2's inverse, so a ⌘+Ctrl combined press cannot double-match. Gating both mac rules on platform + modifier therefore keeps the Win/Linux seam byte-identical rather than making it a special case (no ctrl-tier default resolves there — `focus-hop`'s base tier is shifted).
**Rejected**: Refusing every registry match (breaks plain-Ctrl pane chords everywhere); refusing all cmd-tier matches on mac ungated (breaks Ctrl+[ = ESC); refusing every plain-Ctrl chord on mac to keep the predicate simple (steals the pane's whole control-byte vocabulary for one shipped ctrl-tier chord); narrowing `matchesCombo`'s cmd tier to Meta-only on mac (would change the legacy ⌘K/⌘. predicates project-wide); adding a `preventDefault` in the handler (xterm's non-preventing refusal is what lets the event bubble to the window dispatcher). Residual: on Windows/Linux an action deliberately rebound *into* the cmd/ctrl tier is not refused and reaches the pane while the terminal has focus.
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts; ctrl-tier rule: 260816-sm66-vscode-shortcut-realignment

### `terminal-find`'s base tier is shifted with a mac cmd demotion
**Decision**: `terminal-find` ships as ⇧Ctrl+F on Win/Linux (`tier: "shifted"`) and ⌘F on mac (`macTier: "cmd"`), reusing the established demotion data (the `go-back`/`sidebar-toggle` pattern).
**Why**: plain Ctrl+F belongs to the pane on Win/Linux (readline forward-char) and the terminal seam deliberately never refuses unmatched plain-Ctrl chords; the shifted tier is what every cross-platform terminal uses for find (GNOME Terminal/Konsole/Windows Terminal), and the seam's existing rules 1–2 make both chords bubble under terminal focus with zero xterm-handler changes.
**Rejected**: cmd-tier Ctrl+F everywhere (mirroring `web-find`) — it could never fire under terminal focus on Win/Linux without a new seam rule that steals readline's Ctrl+F from the pane.
*Introduced by*: 260819-zqf9-terminal-tile-find

### Overrides are localStorage diffs with single-press steal-and-warn
**Decision**: Only differences from the defaults are persisted (`{ [actionId]: {code,tier} | null }`), and one capture press hands the combo over, unbinding the previous owner and flagging it.
**Why**: A diff blob keeps the shipped defaults authoritative — adding or renaming a default binding needs no migration, and re-capturing an action's own **host** default drops its entry rather than freezing a redundant one. Single-press steal keeps rebinding to one gesture and is honest about the consequence, since the victim's `unbound` state is visible in the panel until it is rebound or reset. Storing only diffs also makes the per-platform tiers free: overrides are per-device by construction, so a device's platform is implicit and no per-platform storage key or migration exists. localStorage matches Constitution II (no database) and the `runkit-terminal-font-size` precedent.
**Rejected**: Persisting the full effective map (defaults freeze into user storage, and the per-platform default would be baked in); a press-again-to-confirm steal (two gestures for one intent, and the warning already carries the information); a backend-stored per-user map (a new persistence surface for a per-device preference); a per-platform override shape (per-device storage already makes per-platform inherent).
*Introduced by*: 260730-g40a-keyboard-shortcut-registry-overlay

### A same-combo global↔scoped pair is precedence for conflicts but still a steal target for capture
**Decision**: `findMatches` orders matches non-global-first and the dispatcher fires the first one with a handler; `findConflicts` flags only **equal**-scope pairs; `applyCapture`'s victim search stays `scopesOverlap`-wide, and its own-host-default check short-circuits **before** that search.
**Why**: Once dispatch is scoped-beats-global, a global↔scoped shadow leaves both bindings fully functional (the scoped one wins on its route, the global one everywhere else), so reporting it as a defaults-integrity conflict would make the shipped mac map permanently "dirty" — the board ⌘[/⌘] pair shadowing back/forward is intended, not a defect. Capture stealing cannot be narrowed the same way: four chords dispatch through component-local listeners that never see `findMatches` precedence, so a cross-scope rebind onto their combos would genuinely double-fire, and steal-with-warning is the visible, reversible guard. The short-circuit ordering follows from the same shape — the mac defaults ship shadow pairs, so a victim search running first would let a *no-op* re-capture of one partner unbind the other.
**Rejected**: Treating the shadow as a conflict (would flag the shipped mac defaults); narrowing `applyCapture` to equal scopes too (silently allows double-fire on the locally-listened chords); a schema flag marking locally-listened bindings (scope creep for one edge); resolving the shared combo by moving the board pane-cycle off ⌘[/⌘] (breaks an established board chord to accommodate a global default).
*Introduced by*: 260730-n789-macos-cmd-tier-shortcuts

### Macro targets are riff presets and palette action ids, never shell strings
**Decision**: `MacroTarget` is a two-arm union — a riff **preset name** or a **palette action id**. Execution reaches process spawn only through the existing `POST /api/riff`, which resolves the name as a map-key lookup against `fab/project/config.yaml`-defined presets; an unknown name is a `ValidationErr` → 400.
**Why**: A shortcut executing user-typed shell text would make a web-reachable endpoint run arbitrary commands — precisely what Constitution I exists to prevent. Both motivating flows ("spawn a worktree with a fab-discuss agent", "spawn a codex loop") are already expressible as riff presets, so the macro tier adds **zero** new process-execution surface: it is a keyboard route to an already-validated spawn, and a localStorage-planted preset name can never reach argv. Arguments belong in the preset definition, inside the committed-config trust boundary.
**Rejected**: An arbitrary command string on the macro (Constitution I); an `args?: string[]` passthrough on the riff target (`POST /api/riff` has no args seam and its `task` replaces preset panes, so it needs a backend extension the "no new exec surface" premise rules out — additive to the union later if that seam appears); a preset-authoring UI in the web app (Constitution IV — presets already have a home and an authoring path in fabconfig).
*Introduced by*: 260730-hbyh-shortcut-macro-riff-bindings

### Macro combos live in the keybindings diff map, not the macro definition
**Decision**: A macro definition carries no combo; its binding is an ordinary `runkit-keybindings` override entry keyed by the macro's actionId, and a macro without an entry resolves unbound (`disabledReason: "user"`).
**Why**: One binding store and one resolution path means steal-with-warning, per-row reset, reset-all, browser-reserved disabling, palette hints, the panel key map, and the terminal seam all work on macros with the existing machinery — no parallel plumbing, and reusing the steal-victim state gives the panel's `unbound` affordance for free.
**Rejected**: Storing the combo inside the MacroAction — a second combo store that `applyCapture`/steal/reset could not see without duplicated wiring.

**Decision**: `resolveBindings` carries one extra rule — an effective combo with an empty `code` resolves unbound — and macros enter resolution as ordinary defaults via `macroToBinding`.
**Why**: One resolver keeps every consumer (dispatch, hints, the panel, terminal seam, capture) macro-agnostic; builtins always carry a code, so they are untouched by the rule.
**Rejected**: A parallel `resolveMacroBindings` merged after the fact — duplicates the override/reserved/steal logic and forks the effective-map contract.

### The mac split pair rides a `macCode` default refinement rather than a platform-gated unbound vertical
**Decision**: `macCode?: string` refines a binding's SHIPPED DEFAULT key code on mac hosts, composing with `macTier` inside the one existing mac branch of `defaultComboFor` (`{ code: macCode ?? code, tier: macTier ?? tier }`). The split rows ship divider-mnemonic base codes — ⇧Ctrl+\ side-by-side (shift+\ types `|`, the divider the split creates), ⇧Ctrl+- stacked — with `macCode: "KeyD"` refining both to the iTerm2/Warp/Ghostty ⌘D/⇧⌘D pair on mac. ### An unrepresentable shell claim is recorded as absence plus the system claim that replaces it

### A tooltip keycap chip is resolved from the registry, never hard-coded
**Decision**: A `Tip`'s `kbd` slot for a registry-bound action is derived at the call site from the effective map (`useKeybindings()` → `byAction.get(id)` → `formatCombo(…, host.platform)` when `enabled`, else `undefined`), and the chip is **omitted** when the binding is unbound, disabled, or browser-reserved.

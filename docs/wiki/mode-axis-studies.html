Mode Axis — Semantic Shapes

Third study. Keeps the spring-loaded pad and the width = stage axis; asks what the vertical axis should mean and which shapes carry those meanings. Also fixes the dashed ≈ block collision (8/12 vs 9/12 duty cycle — indistinguishable at any width).

1 · First the tension: who writes the mode?

The memory records a hard split: markers and colors are user preferences (what you think about a task); the status dot is derived (activity / PR / agent signals); "the two axes never mix, by design." Your examples — in conversation, auto mode, blocked, waiting — sit right on that seam, so the write model has to be decided before the shapes.

W-A · declared human sets it, nothing else touches it
Today's model. Mode = "how I'm running this task". Zero plumbing, zero flicker, never lies about tooling. Cost: it goes stale — you forget to flip auto back to hands-on when the run ends, and the stripe silently drifts from reality.
W-B · derived per turn agent-state drives the shape
rk knows only active | waiting | idle (per turn, seconds apart), fab stage, and PR state. Mapping those onto the stripe (1) duplicates the dot's channel in a second place, (2) re-textures the stripe every turn — a marker that also carries your manual stage can't shimmer, (3) can't produce auto or blocked at all — neither is derivable anywhere today. Rejected.
W-C · lifecycle-stamped same option, two writers, boundary events only
The @rk_pane_agent_state precedent: a user-owned option that tooling may stamp at lifecycle boundaries, never per turn. fab fff stamps auto when it starts and clears it when it exits; fab ship/wait-for-review stamps waiting; the operator's annotate step may stamp conversing; a human stamps blocked (nobody else can know). Rule: tooling writes only the mode it owns and only on enter/exit, and never overwrites a human-set blocked. The dot keeps the fast signal; the stripe gets the slow one. This is the "modes a process takes during its lifetime" reading — coarse phases, not turns.

2 · Two candidate vocabularies

Five modes, each a distinct way of working. "Needs me right now" is deliberately absent — that's the agent-state waiting halo on the dot, fast and derived. Stage stays orthogonal: an auto row at stage 4 is "autopilot, nearly done".
V2 · whose turn is it
ModeMeans
minethe next move is mine

A turn-taking model answers the one question you ask when scanning a tree: "who is this waiting on?". It's crisper than V1 but loses conversing (the turn alternates every minute — exactly the flicker W-B was rejected for) and auto collapses into agent's. Worth keeping as the framing for the glosses in the pad: V1 words, V2 sub-text ("auto · agent's turn").

3 · Shape catalog — what each texture says on its own

Every candidate at stage 2 / 3 / 5 (6 / 11 / 22px), plus three rows stacked to check welding. The reading column is what the shape says before anyone tells you the legend — the test for "the shape reflects the meaning".

Collisions: dashed ≈ block at every width (drop one). hollow ≈ solid at stage 1 (2px) — fine, stage 1 = barely started. chevron vs hatch are distinct from 6px up (V's vs one-direction diagonals). wave needs ≥ 6px to read; below that it's a wobbly solid. crosshatch at 22px is very loud — reserve for the one state that deserves loud.

4 · Mapping options

Recommendation: M1. The shapes were chosen so each one is iconic for its mode without a legend: dots = the "…" typing indicator (conversing); chevrons = ⏩ fast-forward (auto — and fab fff is literally fast-forward); hollow = an empty channel with nothing flowing (waiting on others); hatch = barrier tape (blocked — keeps the shipped hazard-wedge pairing); solid = the plain default (hands-on). M2 swaps in the more literal but weaker-at-small-width textures (wave for speech, crosshatch for barred); it wins only at stage ≥ 3.

# run-kit UI — Lenses & Surface Layout

## Iframe Window (the `web` lens renderer)

`app/frontend/src/components/iframe-window.tsx` — the renderer for the **`web` surface/lens** (§ Window Views (Lens Model)), mounted as a tile by `SurfaceLayout` whenever the resolved layout's order includes `web` (§ Surface Layout). The `web` surface is ALWAYS available (§ Window Views (Lens Model)) — an empty/whitespace `rkUrl` selects the tile's ONBOARDING content state (§ Onboarding state below) in place of the iframe; a non-empty `rkUrl` renders the live iframe, and the existing `rkUrl` sync effect flips between the two in both directions (§ SSE Sync below). Bottom bar is NOT rendered for a web tile (no terminal to send keys to). The component is **presentational** — it takes `windowId`, `rkUrl`, and three optional interaction seams — an `onInteract: () => void` tile-focus seam, a `shouldReclaimChord` chord-reclaim predicate, and an `onPageMeta: (meta: { title: string | null }) => void` page-meta seam (all below) — and owns NO view/URL/localStorage logic (that lives in `surface-layout.ts` + `app.tsx`); it mutates no `@rk_type` (§ Window Views → decoupling). View switching is owned by the top-bar surface toggles / mobile switch group and the palette — the tile itself carries no switch-to-terminal affordance. (`260714-t97o`, `260812-ab5v`, `260819-v6y4`, `260821-zqlq`)

**Layout**: Outer wrapper `flex flex-col flex-1 min-h-0` with up to five children: URL bar (`shrink-0`), the find bar (`shrink-0`, rendered only while open — § Find bar below), the load progress line (rendered only while the frame loads — § Load progress line below), an in-tile error state (rendered in place of the iframe's VISIBLE area while active — § Error states below), and the content-zoom wrapper (`flex-1 min-h-0 overflow-hidden`) holding the iframe (§ Content zoom below). In the ONBOARDING state (empty/whitespace `rkUrl`) the wrapper holds only the reduced URL bar and the onboarding panel — the iframe, find bar, progress line, and error/probe machinery do not mount (§ Onboarding state below).

**URL Bar**: Thin toolbar above the iframe (`border-b border-border bg-bg-primary`), one warm-tip `TipGroup` cluster, button order per the approved design study (`fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html`):
- **Back / Forward buttons** (`WebBackGlyph`/`WebForwardGlyph` — `data-icon="web-back"`/`"web-forward"`, register arrow SVGs) — drive `contentWindow.history.back()/forward()` on same-origin frames; both are HIDDEN when the frame is cross-origin (cross-origin history is unreachable to a parent by design). The navigation is per-viewer view state and never touches `@rk_url` (spec window-views R7). The buttons render enabled whenever same-origin — a parent has no reliable canGoBack signal, and a boundary click is a harmless no-op. (`260819-v6y4`)
- **Refresh button** (`RefreshGlyph` — `data-icon="refresh"`, the same register export the top-bar RefreshButton renders) — a REAL reload on same-origin frames: `contentWindow.location.reload()` preserves the frame's CURRENT location and in-page state (no reset to the stored `@rk_url`); the `about:blank` bounce (clear `src`, re-set via `setTimeout(0)`) remains ONLY as the cross-origin fallback. Styled: `w-7 h-7 rounded hover:bg-bg-card text-text-secondary hover:text-text-primary` — every URL-bar button carries the tile-verb hover brighten. (`260819-v6y4`, 76uz)
- **Address input (display/edit split)** — at rest it SHOWS the kind-specific DISPLAY form (`displayForm(rawAddress)`, § Address model below — a proxied `/proxy/3000/…` reads `localhost:3000/…`, a presented file reads its basename with the `server`/`v` plumbing params hidden, an external URL reads host+path with the scheme omitted). Focusing it reveals the RAW editable value (the tracked frame location when known, else the stored `@rk_url`) with select-all; Escape (or blur) reverts to the display form with no POST. On Enter the input is normalized (`normalizeAddressInput` — bare `localhost:{port}`/`127.0.0.1:{port}` → `/proxy/{port}/…`, bare domain → `https://…`, already-valid values pass through) and scheme-checked (`isAllowedUrl`, the frontend mirror of the backend `@rk_url` allowlist — an invalid scheme surfaces an inline `role="alert"` error and fires NO POST), then calls `updateWindowUrl(server, windowId, url)` which delegates to the unified `setWindowOptions(server, windowId, { "@rk_url": url })` → `POST /api/windows/{windowId}/options` (partial-merge — only `@rk_url` is touched). On API failure, reverts input to the SSE-confirmed `rkUrl`. Styled: `bg-bg-card text-text-primary text-sm px-2 py-1 rounded border border-border`. **This is the one POST the web lens fires** — editing the content ADDRESS is *substrate* state (shared, POSTed, everyone sees it — spec R7), distinct from switching which lens you look through (per-viewer, no POST). (`260529-jad6`, `260819-v6y4`)
- **Find button** (`FindGlyph` — `data-icon="find"`, the same register export as the tty tile's find toggle: one find identity across surfaces; `aria-label="Find in page"`, `aria-pressed` while open — lit `text-accent-green` when the bar is open) — the pointer/touch entry point to the find bar; toggles it locally (the chord and palette entries share one open seam instead, § Find bar)
- **Open-in-browser button** (`OpenExternalGlyph` — `data-icon="open-external"`, register arrow-up-right; `aria-label="Open in browser"`, rightmost) — opens the CURRENT address (the tracked frame location when known, else the stored `@rk_url`) in a new tab via `window.open(…, "_blank", "noopener")`; relative addresses resolve naturally against the viewer's origin (the stored `@rk_url` stays relative per the display contract `docs/site/skill/display.md`). The universal escape hatch for anything the tile can't render; the `Web: Open in browser` palette action mirrors it (§ Address model below — the document-CustomEvent seams). (`260819-v6y4`)

**SSE Sync**: A `useEffect` on `rkUrl` syncs the URL bar text, the tracked-location display state, and the iframe `src`. Uses a `currentSrcRef` to avoid re-setting iframe `src` when the URL hasn't actually changed (prevents unnecessary reloads on identical SSE ticks); a genuine change also re-arms the load progress line. When `rkUrl` changes externally (Claude or another process runs `tmux set-option`), the URL bar updates and iframe navigates automatically.

**Interaction + reclaim seam (`onInteract`, `shouldReclaimChord`)**: in-frame clicks and keydowns stay in the frame's own document, and focus entering a frame fires NO focusin in the parent — parent-document listeners are blind to them. The component attaches capture-phase `pointerdown`/`keydown` listeners to the same-origin `contentDocument` after every iframe `load` (each navigation replaces the document; cross-origin access throws and is skipped silently — the `CodeSurface` attach pattern) plus a parent-window `blur` fallback that reports when `document.activeElement` is the iframe, covering cross-origin embeds. Every in-frame keydown reports `onInteract` FIRST, then — when a `shouldReclaimChord` predicate prop is injected — a keydown matching it is `preventDefault` + `stopImmediatePropagation`ed inside the frame and re-dispatched as a synthetic bubbling `KeyboardEvent` on the parent **document** (the CodeSurface `onKey` mechanism, byte-for-byte — § Code Surface → Chord reclaim): run-kit's registry chords (⌘K, ⌘., ⌘F, …) keep working with focus inside the frame while every non-claimed key reaches the framed page untouched (typing into an in-frame form is unchanged). `SurfaceLayout` injects the predicate bound to the `web` kind (`shouldReclaimChord("web")`, the kind-aware factory in `app.tsx` — § Surface Layout → Tile renderer), so `ttyOnly` chords pass through to the framed page and `webOnly` chords (⌘F, ⌘L) reclaim only here (§ Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags). Cross-origin frames get no reclaim — the `blur` fallback stays the only interaction signal, and once a cross-origin frame holds focus, later in-frame clicks report nothing — accepted, the tile is already focused by then. `SurfaceLayout` wires the seam to tile focus (§ Surface Layout → Focused tile); both props are optional and other mount contexts omit them unchanged. (`260815-41t9`, `260819-ie2i`)

**Find bar (⌘F find-in-page)**: the web tile ships in-frame page search for same-origin content — a `shrink-0` row rendered between the URL bar and the iframe while open (`data-testid="web-find-bar"`, the URL bar's border/background vocabulary; layout per the approved design study `fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html` state 03). The row is the shared presentational **`FindBar`** component (`components/find-bar.tsx`, colocated `find-bar.test.tsx`) — props-driven (`query`/`matchIndex`/`matchCount`/`onQueryChange`/`onNext`/`onPrev`/`onClose`, plus optional `toggles`, `disabled`, `statusText` (replaces the counter), and `scopeNote`), the consumer owning the search mechanism — also mounted by the tty tile (§ Tile renderer → tty find bar); `IframeWindow` owns the in-frame engine and passes no toggles. Row contents in order: an autofocused text input, the `n/N` match counter with the active ordinal in accent green (`0/0` when the query matches nothing), ∧/∨ previous/next buttons, a ✕ close button, and a right-aligned key hint `Enter next · ⇧Enter prev · Esc close` suppressed on coarse pointers (`useCoarsePointer()` — keyboard-chord copy never renders on touch). Enter advances to the next match, Shift+Enter to the previous (both wrap), Escape closes the bar and clears all highlights. Three entry points share ONE open seam: the ⌘F/Ctrl+F `web-find` chord (reclaimed inside the frame or handled at tile level while the web tile owns focus — § Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags) and the `Web: Find in page` palette action both dispatch the `web-find:open` document CustomEvent (`WEB_FIND_OPEN_EVENT`), which the mounted web tile listens for (the `window-heading:rename` / `theme-selector:open` precedent — at most one web tile per layout, so the receiver is unambiguous); the ⌕ URL-bar button (the pointer/touch entry) toggles the bar locally. A cross-origin frame renders the bar DISABLED — input and navigation buttons disabled, the inline hint `page is cross-origin — find unavailable` in place of the counter — and no search is attempted (⌘F pressed while a cross-origin frame holds focus never reaches the parent at all, so the ⌕ button and the palette are the bar's entry points there). Every iframe `load` resets the find state — matches, highlights, and the query die with the document they were collected from (no term persistence across navigations); the bar's open/closed state itself survives navigation. (`260819-ie2i`, `260819-zqf9`)

**Find engine (`lib/find-in-page.ts`)**: a pure module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract), parent-driven over the same-origin `contentDocument` — no script injected into the framed page. `collectMatches` walks the frame document's text nodes with a case-insensitive TreeWalker into DOM `Range`s (skipping non-rendered containers like `script`/`style`); `stepMatch` is the wrap-around active-index transition; `applyHighlights` registers two CSS Custom Highlights (`rk-find` all matches, `rk-find-active` the active match with its accent-green outline) on the FRAME window's `CSS.highlights` and installs one `<style>` element of `::highlight()` rules into the frame's `<head>` (inert DOM — `clearHighlights` removes both on reset); the active match scrolls into view (`block: "nearest"`). Where the Highlight API is unavailable, `contentWindow.find()` is the best-effort fallback — navigation works, the counter may read the zero form. All frame-DOM access carries the attach seam's try/catch posture (pre-load and cross-origin frames no-op silently). Unit-provable in jsdom without the Highlight API. e2e: `web-tile-find.spec.ts` (+ `.spec.md`) on the real-tmux port-3020 rig (the `web-view-lens.spec.ts` `_tmux.ts` pattern) proves ⌘K opening the palette with focus inside a same-origin web-tile frame, the ⌘F open → match count → Enter navigation → Escape close flow on a presented HTML file, and the cross-origin disabled bar + hint via the ⌕ button. (`260819-ie2i`)

**Address model (`lib/web-url.ts`)**: a pure, DOM-free module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract) owning every derivation over a stored `@rk_url` or an address-bar keystroke. `classifyAddress(url)` returns one of four kinds — `present` (root-relative `/present/…`, an `rk present` file), `proxy` (root-relative `/proxy/{port}/…` OR an absolute loopback `http(s)://localhost|127.0.0.1|[::1]:{port}…`), `external` (any other absolute http(s) URL), `relative` (any other root-relative path) — driving the header badge and the error-state posture; unrecognized input (incl. non-allowlist schemes, which the backend rejects anyway) degrades to `relative`, never throws. `displayForm(url)` is the kind-specific pretty REST form — present → the file's basename with the plumbing query params (`server`, `v`) hidden; proxy → `localhost:{port}{path}` (the `/proxy/` plumbing never shows at rest); external → `host{path}{?query}` with the scheme omitted; relative → the raw path; unparseable input degrades to the raw string. `normalizeAddressInput(input)` is the submit-time normalization — bare loopback `host:port[{path}]` (no scheme) → `/proxy/{port}{path or /}` (ride the same-origin proxy, matching the Host page's port addressing), bare domain `example.com[/path]` → `https://…`, already-valid values pass through, anything else passes through unchanged so `isAllowedUrl` can reject it with inline feedback. `isAllowedUrl(input)` is the frontend mirror of the backend scheme allowlist (http/https absolute with a host, root-relative — § tmux-sessions `@rk_url`). `proxyPortOf(url)` returns the proxy-kind target port. `toProxySrc(url)` is the iframe-src mapping (below). The module also exports the web tile's two document-CustomEvent constants — `WEB_ADDRESS_FOCUS_EVENT` (`web-address:focus`, the ⌘L/palette seam) and `WEB_OPEN_EXTERNAL_EVENT` (`web-open-external`, the palette seam) — the `WEB_FIND_OPEN_EVENT` precedent: at most one web tile per layout, so the receiver is unambiguous. The STORED `@rk_url` is never rewritten by display work — the display contract keeps relative addresses relative. (`260819-v6y4`)

**Current-path tracking + page meta**: as the user navigates inside a same-origin frame, the address bar's display value tracks the frame's location — read on the frame's `load` events (the attach seam's try/catch posture), stored root-relative (the viewer origin stripped) so `displayForm` sees the same shape as a stored relative `@rk_url`; `about:blank` (the cross-origin reload bounce's midpoint) reports nothing. Display-only, NEVER POSTed (spec window-views R7) — only an explicit Enter in the address bar writes `@rk_url`; in-frame navigation and back/forward are view-local. The same load pass clears the progress line and reports the same-origin `contentDocument.title` through the optional `onPageMeta` seam (`null` when cross-origin or empty) — `SurfaceLayout` holds it as state for the header (§ Surface Layout → Tile renderer). (`260819-v6y4`)

**Onboarding state (empty/whitespace `rkUrl`)**: with no address to render, the tile mounts the ONBOARDING state in place of the iframe and its probe machinery — the branch is `onboarding = !hasWebUrl({ rkUrl })` (the trim rule is the single source), and NO frame-check/dead-port probing runs (the probes key off an address; § Error states below). The **reduced URL bar** keeps only the REFRESH button and the ADDRESS INPUT — back/forward, the find ⌕ button, and the ↗ open-in-browser button are hidden (nothing to navigate, search, or open) — and the input is FULLY LIVE with placeholder `localhost:3000 · /present/… · https://…`: typing an address + Enter runs the existing submit pipeline (`normalizeAddressInput` → `isAllowedUrl` → `updateWindowUrl` → `POST /options` partial-merge on `@rk_url`, § URL Bar above) and boots the tile for real — the bar is itself an init path. The **body panel** (replacing the iframe; centered, monospace, on `bg-bg-primary`) carries a large dimmed `://` glyph, the heading **"Nothing to show yet"**, the subhead *"this tile follows the window's web address (@rk_url) — three ways to fill it:"*, three instruction rows (accent-green lead glyph, bold lead-in, `bg-bg-inset` bordered code chips): `❯` **Ask your agent to show something** — "Present this as a page" — the agent runs `rk present ./report.html` and it appears here (HTML files, diagrams, mocks, directories); `⇄` **Preview a dev server** — type `localhost:3000` in the address bar above (proxied through run-kit, works from any device), or have the agent run `rk present :3000`; `↗` **Open any URL** — external sites embed when they allow it, and find-in-page (⌘F) + back/forward work on same-origin pages. A dimmed footer reads *"the tile goes live automatically when an address lands ● no reload needed"*. The tile header renders the plain `://  Web` label — no kind badge, no page title, no meta chip (§ Surface Layout → Tile chrome). The flip is automatic in BOTH directions via the existing `rkUrl` sync effect (§ SSE Sync — `onboarding` derives from `rkUrl`, so an empty→set transition swaps the panel for the live iframe with no user action, and set→empty returns to onboarding); `present-auto-expand` is untouched — an already-open onboarding tile flips in place via the `withAutoWeb` identity arm (§ Surface Layout → Present auto-expand). The find entry points no-op here: the `Web: Find in page` palette entry is content-gated on `hasWebUrl` and the tile's own `web-find:open` listener double-guards ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § `web-find`). (`260821-zqlq`)

**Error states (fail loudly)**: a silent blank iframe is not a reachable state for a probed-blocked external URL or a dead proxied port — the tile renders an explicit error surface (`data-testid="web-tile-error"`) IN PLACE of the iframe's visible area, copy per the design study (states 05/06). Three kinds: **frame refusal** — for `external`-kind addresses the frontend calls `GET /api/frame-check` (`checkFrame`, [architecture](/run-kit/architecture.md) § API Layer) on address change; `embeddable: false` renders "`{host}` refuses embedding" + the reason line + an Open in browser ↗ button; **unreachable external** — `reachable: false` renders "`{host}` can't be reached" + the probe reason + the same hatch; **dead proxied port** — for `proxy`-kind addresses a same-origin `fetch` of the proxied path reads the reverse proxy's 502 (nothing listening) and renders "nothing listening on :{port}" + "connection refused — the dev server may have stopped" + a ↻ Retry button that re-runs detection and reloads (a nonce re-fires the probe effect). Present/relative kinds never probe; a same-origin fetch FAILURE (the app server itself down) is not a dead upstream and leaves the iframe alone. The error state clears on the next address change/retry. The iframe stays MOUNTED but `hidden` beneath the error surface (§ Design Decisions → Error states render over a hidden, still-mounted iframe). (`260819-v6y4`)

**Load progress line**: a 2px indeterminate accent-green sweep (`.rk-web-progress` in `globals.css`, `data-testid="web-load-progress"`) rendered at the content's top edge while the iframe loads — set on src change/reload/history navigation, cleared on the frame's `load` event (the element's presence IS the state). Under `prefers-reduced-motion` the sweep zeroes to a static dim line — load feedback is never motion-only. (`260819-v6y4`)

**Content zoom**: the web tile magnifies its guest content by a per-viewer zoom level `s` applied as a SCALE WRAPPER — the iframe renders inside the `overflow-hidden` wrapper (`data-testid="web-zoom-frame-wrapper"`) at `width/height: 100%/s` with `transform: scale(s); transform-origin: 0 0`, so zooming in shrinks the frame's CSS viewport and responsive guest layouts adapt exactly as under real browser zoom; at `s = 1` no transform is applied and the layout is identical to an unzoomed tile. The mechanism never reaches into the guest document, so it covers all four address kinds including cross-origin `external` (§ Design Decisions → Scale wrapper over guest-document CSS zoom). The pure, DOM-free `lib/web-zoom.ts` (colocated tests, the `web-url.ts` module contract) owns the derivations: the browser-standard ladder `WEB_ZOOM_LEVELS` (50%–300%, default/reset 1) + `stepWebZoom` (clamps at the ends, snaps an off-ladder value to the nearest level first); `webZoomKeyFor(rkUrl)` — the persistence bucket derived via `classifyAddress`: `external` → the URL's origin, `proxy`/loopback → `proxy:{port}`, `present`/`relative` → the single viewer-origin bucket `self` (presented files rotate paths, so per-path buckets would fragment state); and try/catch-noop `readWebZoom`/`writeWebZoom` over ONE localStorage key `runkit-web-zoom` holding a `{[bucket]: level}` map — a level of 1 removes the entry (100% is the absent state), per-viewer state only, never POSTed (Constitution IV; spec window-views R7). `IframeWindow` seeds its zoom state from the current `rkUrl`'s bucket, re-seeds when the bucket changes, and persists on every change. **Triggers**: (1) a compact control in the URL-bar cluster between the find ⌕ and open-external ↗ buttons (`data-testid="web-zoom-control"`; text-glyph `−`/`+` steppers with the percent readout between them doubling as the reset affordance — disabled at 100% — in the `w-7 h-7 rounded hover:bg-bg-card` + `Tip` URL-bar button vocabulary) — the universal floor trigger, and the only one that works over an `external` frame; NOT rendered in the onboarding state (the reduced URL bar keeps only refresh + address input). (2) The palette's `Web: Zoom in`/`Web: Zoom out`/`Web: Reset zoom` actions ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) dispatch the `web-zoom` document CustomEvent (`WEB_ZOOM_EVENT` in `lib/web-zoom.ts`, `detail.direction: "in" | "out" | "reset"` — the `web-find:open` precedent: the mounted tile is the single receiver, double-guarded to no-op on a contentless tile). (3) Ctrl/Cmd+wheel and touchpad-pinch gestures, reduced by the shared `lib/zoom-gesture.ts` accumulator ([terminal](/run-kit/ui/terminal.md) § Terminal Font Size → Gesture triggers) through TWO non-passive capture arms — one on the tile's own wrapper (covering the URL bar, find bar, and error surface, all parent-document DOM) and one attached to the same-origin frame's document on every `load` (the chord-reclaim attach posture: try/catch, cross-origin/pre-load skips silently, re-attaches per navigation) — a wheel event over an iframe never reaches the parent document, so both arms are needed. Over a cross-origin (`external`) frame gestures are unreachable — accepted platform limit, no fallback attach; the chrome control and palette remain the triggers. Only ctrl/meta-modified wheel and Safari `gesture*` events are intercepted (`preventDefault` — the gesture never becomes browser page zoom); everything else passes through untouched. e2e: `web-tile-zoom.spec.ts` (+ `.spec.md`) on the real-tmux rig (the `web-view-lens` pattern) proves control stepping, reset to 100%, persistence across reload, onboarding absence, and palette stepping on a same-origin page. (`260823-cwvv`)

**Proxy URL conversion**: `toProxySrc(url)` (`lib/web-url.ts`, § Address model above) maps an absolute loopback URL to its same-origin proxy path: `http://localhost:8080/docs` → `/proxy/8080/docs`. Portless loopback and every other address pass through unchanged (relative addresses are already same-origin).

**Iframe attributes**: `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"` (without `allow-downloads`, VS Code file downloads break — the same sandbox `CodeSurface` reuses, § Code Surface), `title="Proxied content"`, `border-0`.

**Window creation**: "Tab: New Iframe Tab" command palette action (id `create-iframe-window`) opens a `Dialog` with two inputs: window name (autofocused, Enter focuses URL input) and URL (Enter creates window). Create button disabled until both fields non-empty. Calls `createWindow(server, session, name, undefined, "iframe", url)` — the extended API client function passes `rkType` and `rkUrl` in the POST body. Backend uses `CreateWindowWithOptions` for atomic `\;`-chained tmux command. Only shown when a session is active. Synthetic iframe windows are created this way; `@rk_type=iframe` means "**default view = web**" (a creation-time hint, § Window Views → `defaultView`), not a locked identity. (`260714-t97o`, `260820-lfla`)

## Code Surface (the `code` lens renderer)

`app/frontend/src/components/code-surface.tsx` — the renderer for the **`code` surface/lens** (§ Window Views (Lens Model)) — mounted as a tile by `SurfaceLayout` whenever the resolved layout includes `code` (§ Surface Layout): via the top-bar surface toggles, the `Tile: Show Code` palette entry, a `?layout=…code…` deep link, or the switcher's `View: Code` row (which applies `single:code` through the shim). It embeds **code-server** at the window's git root — a full editor (tabs, syntax highlighting, SCM view, side-by-side diffs) beside the live agent terminal with no editor functionality built in run-kit. It is a lean component, NOT an `IframeWindow` reuse: the code-server URL is fully DERIVED, so the URL bar (`@rk_url` substrate chrome) is meaningless here — the component is exactly an iframe plus the not-running empty state (§ Design Decisions → The code surface is a lean `CodeSurface`). (`260811-k3vp`)

- **src** — `codeServerSrc(folder)` returns the RELATIVE path `/code/?folder=<folder>` (folder value `encodeURIComponent`d), never a composed absolute origin and never a port — the same relative-path discipline `toProxySrc` follows, so the embed rides the same origin through any reverse proxy. The path is STABLE: code-server keys browser-side workspace state by the proxy pathname, and `/code/` is fixed by the backend route (the port behind it is a private implementation detail, resolved server-side). code-server restores per-folder state from the `?folder=` param. The folder is the window's LATCHED code folder (the `gitRoot` prop arrives already substituted — § The code folder is a per-window latch), and the computed `src` is held in a **ref keyed to the iframe's MOUNT GENERATION** (the `reachable` gate): a latch update never rewrites a live frame's `src`, while a genuine remount (a reachability `false→true` flip, a window switch) boots the CURRENT latch.
- **Availability vs reachability** (spec right-panel.md § Surface Registry): AVAILABILITY = the window's code folder is LATCHED, or a `gitRoot` derives non-empty — the STABLE capability signal, computed upstream in `hasCode` over the latch-substituted effective window, so the surface toggle / switcher segment never strobe when the active pane leaves the repo (the port is always resolvable by convention, so the "configured" leg is always true). REACHABILITY (the host's TTL-cached probe, the state socket's `code-server` event) selects the surface's CONTENT only: reachable renders the iframe; unreachable renders the terse monospace empty state `code-server not running — check rk doctor` (`data-testid="code-surface-empty"`) instead of a dead iframe.
- **Sandbox** — the same token set as `IframeWindow`, including `allow-downloads` (without it VS Code file downloads break).
- **Chord reclaim** — focus inside the iframe swallows run-kit's chords (`⌘K` collides with VS Code's own), and same-origin makes an escape hatch possible: a capture-phase `keydown` listener attached to the iframe's `contentDocument` after every load intercepts events matching the INJECTED `shouldReclaimChord` predicate (built in `app.tsx` from the keybinding registry's pure, kind-aware `hasReclaimableMatch(e, bindings, kind)` — `findMatches(...).some(...)` over the surface-restriction flags, here bound to the `"code"` kind), `preventDefault` + `stopImmediatePropagation`s them before the embedded app's keybinding service, and re-dispatches a synthetic bubbling `KeyboardEvent` on the parent **document** (reaching both document-level listeners — the palette chord — and window-level ones — the dispatcher, the ⌘. view cycle). The reclaim carve-outs: a keydown whose ONLY registry matches are `ttyOnly` bindings (the tmux split pair — a keydown arriving inside the iframe means the code tile owns focus) is NOT reclaimed, so ⌘D reaches code-server's own keybinding service, and a `webOnly` match (⌘F web find) is NOT reclaimed in the code iframe either — code-server keeps its own find — while unrestricted registry chords (⌘K, ⌘., ⌘2, ⌃`, …) are reclaimed (`260812-wfic`, `260819-ie2i`) — ⌃` deliberately preempts code-server's own integrated-terminal toggle, the hop back to tty winning over the embedded app's binding. The effect is keyed on `reachable` (the iframe only mounts when reachable, so a reachability flip re-runs it against the fresh iframe), re-attaches on `load` (each navigation replaces the document), guards `contentDocument` access in try/catch (a cross-origin or pre-load frame silently skips the attach — click-out remains the escape), and removes the listener from the attached document on cleanup. Proven by the `code-surface.spec.ts` e2e "keyboard spike: a registry chord pressed INSIDE the iframe reaches the parent" (§ Design Decisions → Chord-reclaim via a capture-phase iframe listener).
- **Load-time focus grab — guarded** — the code-server workbench grabs DOM focus once per iframe load (a script `focus()` at editor-restore time that no VS Code / code-server setting suppresses), which would otherwise win every window switch and flip `focusedTileKind` to `code`, killing all `ttyOnly` keybindings. Per-window focus memory plus a steal guard answer it: `CodeSurface` reports the grab through the `onProgrammaticFocus?: () => boolean` prop, fed by a capture-phase `focusin` listener on the frame's contentDocument attached by the same load/attach effect as chord reclaim (the ONLY observable — a script `focus()` re-points the focus chain but fires no parent-side iframe event); `app.tsx` reverts an armed grab whose remembered kind is not `code`. The tile wrapper's `onFocus` consults the guard before `focusSlot`, so a grab never settles the focused kind on `code` (§ Surface Layout → Tile renderer). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (`260815-ltz7`)

### The code folder is a per-window latch

The folder the editor opens is per-window LATCHED state, never the live SSE derivation. `gitRoot` is re-derived per tick from the ACTIVE pane's cwd (backend `deriveGitRoot`, which the latch leaves untouched — it only picks the seed), so a pane switch or a `cd` would otherwise retarget the embedded editor to another workspace — or null the tile entirely when the pane leaves every repo — taking in-flight editor state with it (open tabs, dirty buffers, undo stacks). Derivation's only job is to SEED. (`260813-if5d`)

- **Storage** — `lib/code-folder-latch.ts`: value-bearing key `runkit-code-folder:{server}:{windowId}` (the `windowViewStorageKey` convention) holding the absolute folder path, with `readLatchedCodeFolder` / `writeLatchedCodeFolder` as try/catch-noop wrappers — pure and DOM-free apart from those, with colocated tests (the `window-view.ts` / `right-panel.ts` module contract). Absent, empty, and storage-unavailable all read alike as "not latched"; an empty folder is never written, so `""` cannot be stored. The latch is per-browser, like code-server's own tabs/layout state, and a tmux window id remapped by a snapshot restore orphans its key — a missing latch simply re-seeds on the next open.
- **Seed rule — derivation runs exactly once** — the latch is written the first time the code surface actually RENDERS for a window, keyed on `layout.order.includes("code")`, the choke point every entry path resolves through (the surface toggles, `View: Code`, `?view=code` / `?layout=` deep links, the mobile switch group's persisting switch-to-tile arm). Availability alone seeds nothing: an offered-but-never-opened code lens is not an open editor. An empty derivation seeds nothing either, so a window that has never been inside a repo simply offers no code surface. After seeding, derivation never moves the editor — not on a pane switch, not on tile close/reopen, not on reload.
- **Follow rule — only the editor's own navigation moves it** — `CodeSurface`'s `load`-event seam (the same one the chord reclaim re-attaches on) also reads the same-origin `contentWindow.location`, parses `folder`, and reports it via `onFolderNavigated` when present, non-empty, and different (decoded comparison) from the current folder; `SurfaceLayout` passes it through as `onCodeFolderNavigated` and `app.tsx` writes the latch. So File > Open Folder inside code-server re-latches and a later remount renders where the editor actually is, while the terminal never moves the editor. The location read carries the attach's try/catch posture — a cross-origin or pre-load frame skips silently.
- **The `app.tsx` substitution seam** — the latch is read AT RENDER (a `useMemo` over server + window id + a write-epoch counter, beside the `storedLayout` read that does the same), never mirrored through an effect (§ Design Decisions → The latch is read at render, never mirrored through an effect). The exported pure `withLatchedCodeFolder(win, latch)` substitutes `gitRoot: latch ?? live` into ONE effective window, which feeds `availableViews`, `resolveLayout` (render path AND the URL-mirror effect), `availableSurfaces`, `SurfaceLayout`'s `window` prop, and the window-switch transition classification — so the tile render guard, `tileMeta`, and `codeServerSrc` all follow the latch with the pure lib modules untouched (§ Design Decisions → Effective-window substitution). Unlatched windows pass through by identity.
- **Stale latches are accepted** — a latch pointing at a deleted worktree renders code-server's own "folder does not exist" state; the escape is File > Open Folder, which re-latches. No liveness probe, no reset verb, no palette entry. A cross-viewer tmux window option (`@rk_code_folder`) is a deliberately deferred upgrade path, not shipped behavior.
- **e2e — `code-folder-latch.spec.ts` (+ `.spec.md`)** — real tmux on the port-3020 rig with the `code-surface.spec.ts` code-server stub: a window with one pane inside a repo and one outside proves the code tile survives the active pane leaving the repo and reopens at the latched folder, and that a reload with the active pane still outside renders the latched folder. Live File > Open Folder navigation is unit-tested only (no live code-server in the harness).

## Window Views (Lens Model)

The model (`docs/specs/window-views.md`, rules R1–R7; arrangement generalized by `docs/specs/surface-layout.md`): **a window ROW is a substrate** (a supervised tmux pane); **a VIEW is a lens** over one derivable output of that pane (the tty is a lens; an iframe of the pane's HTTP service is a lens; the parsed agent transcript is a lens; later: desktop). **Which lenses a window offers is a derived capability set; what YOU look at is per-viewer client state** — the surface layout (§ Surface Layout) carried in the URL + localStorage, never a server-side `@rk_type` mutation, never part of the window's identity. A single-tile layout IS the exclusive-lens view: `single:chat` is "the chat lens", `single:tty` the default terminal. Lens state is frontend-only — no Go/API surface participates: the `@rk_type`/`@rk_url`/`@rk_chat` plumbing and `POST /options` carry no lens state, and the SSE payload already carries `rkType`/`rkUrl`/`chatProvider`. (`260714-t97o`, `260714-r7rq`)

Four lenses are implemented: `tty` (always available, `TerminalClient`), `web` (ALWAYS available, like `tty` — `hasWebUrl` selects its CONTENT: the onboarding state when `rkUrl` is empty/whitespace, the live iframe when set; `IframeWindow`, § Iframe Window → Onboarding state), `code` (available when the window's code folder is latched OR a `gitRoot` derives non-empty — the stable capability signal; `CodeSurface`, § Code Surface), and `chat` (available when `chatProvider` is non-empty, `ChatView` — the read-only transcript renderer, § Chat View). Capabilities are orthogonal and STACK (spec R5): one window can offer `tty`+`web`+`code`+`chat` at once, and the layout can tile up to three of them at once (§ Surface Layout). The lens set IS the layout's tileable surface set (`SurfaceKind = ViewName`). The registry is open-ended — `desktop` adds a `ViewName` member, an availability clause, a `defaultView` hint, and surfaces on the existing affordances (the top-bar toggle group, the palette `View:` action), NOT a new component/route/window-type.

### Pure view-model helper — `lib/window-view.ts`

The single source of lens CAPABILITY logic — pure, DOM-free, colocated `window-view.test.ts` (the same pattern as `window-transition.ts`/`navigation.ts`). `surface-layout.ts` builds its availability set on these predicates, so the toggles, the layout, and the palette share one capability source (no drift). Helpers take a minimal structural `{ rkType?, rkUrl?, chatProvider?, gitRoot? }` shape (assignable from `WindowInfo`):

- **`ViewName = "tty" | "web" | "chat" | "code"`** — the lens union; aliased as the layout's `SurfaceKind`.
- **`hasWebUrl(win)` / `hasChat(win)` / `hasCode(win)`** — the capability predicates (`hasChat`/`hasCode`) plus web's CONTENT selector: `hasWebUrl` is `rkUrl` non-empty after `.trim()` and gates NOTHING about availability — web is always available (below); it selects the web tile's content (onboarding vs live iframe — a whitespace-only `@rk_url` renders onboarding, never a blank-src iframe) and drives the web toggle's corner dot (§ Surface Toggles); `chatProvider` non-empty (mirrors the backend `resolveWindowChat` gate); for `code`, the window's `gitRoot` non-empty — evaluated over the LATCH-SUBSTITUTED effective window (`withLatchedCodeFolder`, § Code Surface → per-window latch), so the shipped predicate reads "latched OR derivable" while the module itself stays storage-free and DOM-free (the port is always resolvable by convention, so there is no configured-port leg); code-server REACHABILITY is deliberately NOT in this gate (it fluctuates and would strobe the toggles/palette; it selects the surface's content instead, § Code Surface).
- **`availableViews(win): ViewName[]`** (spec R1/R3) — `["tty"]`, plus `"web"` UNCONDITIONALLY (always available; `hasWebUrl` selects content, never availability), plus `"code"` when `hasCode`, plus `"chat"` when `hasChat`. **Availability is decoupled from `@rk_type`**: an iframe-typed window with no URL offers `tty` + `web` (the web tile renders its onboarding state; `defaultView` still hints `web` only for an iframe-typed window WITH a URL — below). Returned in the registry's fixed order via a `HINT_ORDER` (`[chat, code, web, tty]`) filter — so a fully-stacked window yields `["chat","code","web","tty"]`. The layout module's `availableTiles` re-derives the same set tty-first (§ Surface Layout).
- **`defaultView(win): ViewName`** (spec R5) — the window's default lens, applied ONLY as the layout ladder's hint rung (`hintLayout` wraps it as `single:<view>`): `"web"` when `rkType === "iframe"` AND `rkUrl` is set, else `"tty"`. `@rk_type=iframe` is a **creation-time default-view hint, never an identity**. Structured as spec R5's ordered hint precedence `desktop > chat > code > web > tty` (module const `HINT_ORDER`, only `web`/`tty` wired) so later lenses add a hint clause, not a branch. **`chat` and `code` sit in `HINT_ORDER` for capability ORDERING only — they contribute NO default hint**: a chat- or code-capable window still defaults to `tty` unless the viewer chose otherwise (preserves `260714-r7rq`'s terminal-default).
- **`nextView(available, current): ViewName | null`** — the cycle successor (wraps); `null` when < 2 views or `current` is absent. Powers the `Cmd/Ctrl+.` chord, which applies `single:<next>` (pure so the order is unit-testable).
- Input gating for the lens chord is **not** a `window-view.ts` concern: the shared `shouldSuppressChord` predicate in `lib/keybindings.ts` gates every app chord (§ Keyboard Shortcuts → Dispatch seams).
- **localStorage helpers** — **value-bearing** key `runkit-window-view:{server}:{windowId}` storing the view NAME, including `"chat"` (absent = default). `windowViewStorageKey`/`readStoredView` (READ-only — nothing writes this key anymore), try/catch-noop per `chrome-context.tsx`. The key is a LEGACY seed source: the layout mutation path writes `rk-layout:` keys, and `runkit-window-view` is read only by the translation shim's seeding (§ Surface Layout) and by the switch-transition classification. `resolveLayout` owns the resolution chain — the module carries no resolver of its own. (`260814-6b0j`)

### `?layout=` search param + the translation shim — `lib/router-url.ts`

`layout` is the terminal route's one layout search param (spec surface-layout.md L1, Constitution IV: no new route); the legacy `view`/`panel` params remain ACCEPTED so old deep links never break. The exported pure `validateTerminalSearch(search): { view?: "web" | "chat" | "code"; panel?: "web" | "code"; layout?: string }` passes `view` ∈ {`web`, `chat`, `code`} and `panel` ∈ {`web`, `code`} through, forwards any non-empty string `layout` (shape/arity validation happens in `parseLayout`, § Surface Layout), and **drops any other/unknown/non-string value** (treated as absent, NEVER errored). It is wired as the route's `validateSearch` and unit-tested directly in `router-url.test.ts`. The `declare module "@tanstack/react-router"` `Register` block types the params, so `useSearch({ strict: false })` in `app.tsx` reads them **with no `as` cast** (code-quality type-narrowing — `tsc --noEmit` clean). At resolution, `translateLegacyParams(view, panel)` maps `?view=X` → `single:X` and `?view=X&panel=Y` → `split-h:X,Y` (X in slot A), and the route mirrors the resolved layout back as `?layout=` ONLY.

### `app.tsx` integration — resolution, `switchView`, the layout render

`app.tsx` (terminal route) owns ONE layout-state block (§ Surface Layout → `app.tsx` integration for the full ladder/mirror/mutation machinery): `searchLayout = search.layout ?? translateLegacyParams(search.view, search.panel)`, `storedLayout = readStoredLayout(server, windowParam)`, `layout = resolveLayout(searchLayout, storedLayout, effectiveWindow)` (memoized; `effectiveWindow` is the current window with its latched code folder substituted in — § Code Surface → per-window latch). The lens model's consumers key off **slot A** — `resolvedView: ViewName = layout.order[0]` (spec R12's shim: a multi-tile layout reads as its slot-A surface to the `view-cycle` chord and the palette `View:` actions). One stable `switchView(view)` callback collapses to a single-tile layout: `applyLayout({ shape: "single", order: [view] })` — `applyLayout` persists per-window localStorage AND mirrors the URL via `replace: true` navigation, so a lens pick is a full user mutation (never an `@rk_type` mutation, spec R7). The **render** is `<SurfaceLayout layout={renderLayout} …/>` keyed `` `${server}:${windowId}` `` (a window switch remounts it) — `renderLayout` is the ladder-resolved layout plus the transient present auto-expand override (§ Surface Layout → Present auto-expand) — one tile per surface in the rendered order (§ Surface Layout → tile renderer). There is no `@rk_type`-mutating "switch" path anywhere: switching lenses/surfaces is the surface toggles' and the palette's job, neither of which mutates `@rk_type` (spec R7; the API client has no dedicated `@rk_type` helper — the generic `setWindowOptions` could set it, but no view-switch call site does).

### Lens-switch surfaces — palette, `view-cycle`, top-bar toggles

There is no lens-switcher component: the lens-switch surfaces are the command palette's `View: …` actions (§ Palette parity below — DESKTOP-only; on mobile they are superseded by the top-bar switch group and its `Tile: Switch to <Surface>` palette twin, § Surface Layout → Mobile slot-A + the top-bar switch group), the `view-cycle` chord, and the top bar's open-tile toggles for non-hidden surfaces (§ Surface Toggles — switch mode on mobile). The top-bar chevron menu carries no lens rows — its VIEW section holds the ▦ layout chip's shape rows plus the `menuOnly` Fixed width and Terminal font rows (§ Chrome (Top Bar) → Right cluster). (`260812-0c6o`, `260816-ox16-mobile-tile-switch-vocab`)

### Palette parity + keyboard shortcuts (Constitution V)

- **`View: Terminal` / `View: Web` / `View: Code` / `View: Chat` palette actions** (AppShell `viewActions` in `app.tsx` — DESKTOP-only; on mobile they are superseded by the `Tile: Switch to <Surface>` entries, § Surface Layout → Mobile slot-A + the top-bar switch group), each visible only when its view is **available AND not the current** (slot-A) view — each applies `single:<view>` through `applyLayout` via `switchView` (§ app.tsx integration). The gating + label + shortcut-hint composition live in a pure builder `buildViewActions(available, resolved, onSwitch, hints)` in `lib/palette-view.ts` (mirrors `lib/palette-move.ts`/`palette-update.ts`, unit-tested in `palette-view.test.ts`). The per-entry `shortcut` hint tracks the binding that reaches it: every switch shows the lens cycle's combo except `View: Chat`, which renders NO hint (chat carries no dedicated chord and is deliberately left unadvertised). `buildViewActions` takes the hint as a `ViewShortcutHints = { cycle: string }` parameter, and `app.tsx` passes the **effective** formatted `view-cycle` combo from the keybinding registry, so an override moves the hint (an empty string means "no working chord" and renders no hint); the module default (`⌘.`) matches the registry default for legacy callers and tests. One `buildViewActions` call feeds them; there is no `@rk_type`-mutating `toggle-iframe-terminal` action. The multi-tile affordances (add/close/promote/swap/zoom/shape) carry their own `Layout:` palette entries (§ Surface Layout → palette + chords).
- **The lens cycle chord** (`view-cycle`, default `⌘.` / `Ctrl+.`) is a registry binding on the `cmd` tier with `scope: "terminal"` (§ Keyboard Shortcuts), read through `bindingByAction` by a window-level `keydown` effect in `app.tsx` that `preventDefault()`s (so xterm doesn't also receive it), gates on the shared `shouldSuppressChord`, and calls `switchView(nextView(views, active))` — i.e. it cycles through **single-tile** lens layouts. No-op when < 2 views. The live view/window values and the effective binding are read via refs (`viewCycleRef`, `viewCycleBindingRef`) so the listener is stable across SSE ticks. It keeps its own listener rather than folding into the registry dispatcher because its enablement is lens-local state. `⌘.` is a free binding in the `⌘<punctuation>` family and `Ctrl+.` is inert in readline (unlike `Ctrl+/`→undo); per-device rebinding goes through the override layer.

### Heading is a static `Tab:` in every lens

The top-bar center `PageType: name` heading on the terminal route reads a **static `Tab: <name>` in every lens** (tty / web / code / chat) — it does NOT follow the active view (§ Window Heading). A single `WINDOW_PREFIX = "Tab:"` constant (`top-bar.tsx`) is passed as a constant `prefix` into `WindowHeading` at the terminal-mode center cell; there is no lens-following `terminalHeadingPrefix()` helper and no `WEB_PREFIX`/`CHAT_PREFIX` constants. The heading identifies the WINDOW (the substrate); which lens you look through is carried by the view content itself (chat bubbles vs. terminal) and the top bar's lit tile toggles, not the heading (§ Design Decisions → Heading identifies the window, not the lens). The name's anchor does not jump on a lens switch, since the prefix width does not change with the lens (§ Center-heading stable anchor + nav affordances). The click-to-rename affordance and boot-sweep treatment apply. (`260714-uco1`, `260717-6anu`, `260820-lfla`)

### Internal navigation targets the bare route (spec R6 / surface-layout L4)

Navigating to a DIFFERENT window carries NO layout/view/panel param — each destination window resolves its own layout via the ladder (§ Surface Layout → resolution ladder). Client-side navigations (sidebar/palette/breadcrumb via `navigateToWindow`, plus the window-death redirect and SSE-writeback switch) omit/clear `search`, and TanStack Router's `final` search middleware returns `{}` when `dest.search` is absent, so an outgoing `?layout=` does not leak onto the target. (Per-window localStorage covers the intent; the web-view-lens e2e persistence case exercises this through a real sidebar-click navigation to guard against a future `retainSearchParams`/router-upgrade regression.) History gets "what you saw": layout tweaks `replaceState` (no entry per tweak) while window switches push entries, so back/forward restores the historical arrangement each entry carried (spec L4). The one exception is the `Agent: Next waiting` / WaitingBadge deep-link, which INTENTIONALLY sets `?view=chat` for a chat-capable target — the shim translates it to `single:chat` (§ Chat View → WaitingBadge).

### Window-switch transition classification (one rule)

The window-switch slide transition's `switchTransitionRef` carries a SINGLE `ungatedIds` set: window ids whose EFFECTIVE resolved layout is **not tty-led** — i.e. slot A of `resolveLayout(stored ?? legacy-seed, win)` is a non-`tty` surface, which renders `<IframeWindow>` (web), `<CodeSurface>` (code), or `<ChatView>` (chat), none of which has the terminal's xterm first-write receipt seam, so they use the transition's **ungated capture** (a first-write gate would never release for a non-xterm surface → stuck transition / blank pane). Computed at render time from `resolveLayout(readStoredLayout(server, id) ?? translateLegacyParams(readStoredView(…), readStoredPanel(…)), undefined, withLatchedCodeFolder(win, readLatchedCodeFolder(server, id))).order[0] !== "tty"` — the target window is latch-substituted exactly like the current window's own resolution, so a code-latched window still classifies code-led after its active pane leaves the repo (URL is unknown for a not-yet-navigated target, so only localStorage — the new `rk-layout:` key AND its legacy predecessors via the shim — plus the default hint decide) — the same "keyed on the resolved layout, not `@rk_type`" invariant as the render path (§ Window-Switch Slide Transition).

## Surface Layout (the center is a layout of tiles)

The terminal route's center is a **layout manager** (`docs/specs/surface-layout.md`): a resolved **layout** `(shape, order, ratios)` renders as 1–3 **tiles**, each mounting an existing surface renderer unchanged. `docs/specs/right-panel.md`'s P6 slot mechanics do not apply to the layout manager; its availability derivation and P4 attention do (§ Surface Toggles). A **surface** is a (substrate, lens) pair of the ROUTE window; the tileable set is `tty | web | chat | code` (`SurfaceKind = ViewName` — § Window Views (Lens Model)); `tty` is `(current window, tty)`, always available, listed first. (`260812-ab5v`) Tiles are content-area state; the toggles that open and close them live in the top bar (§ Surface Toggles).

### The model — preset shapes × ordered surfaces × ratios

- **Shapes** (exact URL strings, `SHAPE_ARITY`): `single` (1), `split-h` / `split-v` (2), `row` / `col` / `main-left` / `main-right` / `main-top` (3). Slot A (first in `order`) is the main slot in `main-*` shapes. A layout carries exactly its shape's arity. Max 3 tiles (Constitution IV); presets, never free split trees.
- **Order** — 1–3 surface kinds; kinds MUST NOT repeat within a layout **except `tty`** (the muxed `/ws/terminals` relay supports N clients per pane, so duplicate tty tiles of one window are legal; only the FIRST tty tile receives the shared `wsRef`/`focusRef`).
- **Ratios** — divider positions, per-viewer localStorage ONLY, keyed `rk-layout-ratios:{server}:{windowId}:{shape}` (a ratio is meaningless across shapes), written on drag RELEASE; never in the URL. Clamped by `clampRatio` (`lib/right-panel.ts`, the `MIN_PANEL_WIDTH_PX` 280px floor bounding both sides).

### Pure layout model — `lib/surface-layout.ts`

New pure, DOM-free module with colocated tests (the `window-view.ts` pattern — § Design Decisions → Layout helpers live in a new pure module). Untrusted URL/localStorage strings are validated by guards on the parse path (no `as` casts):

- **`parseLayout` / `serializeLayout`** — `<shape>:<a>,<b>[,<c>]` round-trips byte-identically; rejects unknown shape/kind, arity mismatch, repeated non-tty kind (returns `null`). `ALL_SHAPES`, `shapesForArity(arity)` (the same-arity ring), `SURFACE_LABEL` / `SHAPE_LABEL` / `SURFACE_GLYPH` — shared copy for tile headers, the surface toggles' tooltips/aria, palette `Tile:`/`Layout:` entries, and the mobile switch group so none drift.
- **`resolveLayout(searchLayout, storedLayout, win)`** — the ladder: (1) valid URL `?layout=` → (2) localStorage `rk-layout:{server}:{@N windowId}` → (3) default-view hint (`hintLayout` wraps `defaultView(win)` as `single:<view>` — a legacy `@rk_type=iframe` window hints `single:web`) → (4) `single:tty`.
- **Availability degradation (`degradeLayout`)** — an unavailable surface drops out TILE-BY-TILE: the remaining order renders in the matching smaller-arity shape (3→2 `split-h`, 2→1 `single`, slot A kept); an unknown shape or fully-invalid value falls through to the ladder's next rung. No broken iframe ever mounts. `tty` and `web` never degrade — both are always available, so a `?layout=…web…` deep link on a URL-less window keeps its web tile (rendering the onboarding state, § Iframe Window → Onboarding state).
- **`SURFACE_RAIL_HIDDEN: ReadonlySet<SurfaceKind>`** — a per-surface demotion flag (currently `chat` only): a surface in the set renders NO button in the top-bar `surface-toggles` group in either mode (the desktop toggle group and its overflow Tiles rows; the mobile switch group) and no `Tile: Switch to Chat` palette entry — the consumers filter by the flag AT RENDER, never at availability, so `availableTiles` is untouched and the palette's `Tile: Show Chat` / `Tile: Hide Chat` entries keep working as chat's entry points (§ Surface Toggles). An already-open chat tile still renders and closes normally (the tile's ✕, `Tile: Hide Chat`, layout verbs) — the flag hides the toggle, never the tile. Un-hiding when chat ships is deleting the entry from the set. (`260812-0c6o`, `260816-ox16-mobile-tile-switch-vocab`)
- **The permanent translation shim** — `translateLegacyParams(view, panel)`: `?view=X` → `single:X`; `?view=X&panel=Y` → `split-h:X,Y`; bare `?panel=Y` → `split-h:tty,Y`. `seedLayoutFromLegacy(server, windowId)` migrates the localStorage predecessors: when no `rk-layout:` key exists, a stored `runkit-window-view` / `runkit-window-panel` value seeds the equivalent layout (legacy keys left in place — other tabs may be older).
- **Mutations** (all pure): `promote` (surface → slot A; order permutes, shape unchanged), `swapWithNext`, `closeSurface` (arity collapse, slot A kept; `null` when closing the last tile — disallowed), `addSurface` (1→2 `split-h`, 2→3 `main-left`; `null` at 3), `cycleShape` (next same-arity preset, order kept — tmux `next-layout` muscle memory), `setShape`.
- **Storage** — `rk-layout:{server}:{windowId}` (value-bearing, written on USER MUTATION only — spec L3) + the ratios key above; all reads/writes try/catch-noop.

### `app.tsx` integration — ladder, mirroring, write discipline

One layout-state block (§ Window Views → app.tsx integration): resolve via the ladder, then an effect MIRRORS the applied layout into the URL with `replace: true` navigation (`replaceState` — never `pushState` for a layout tweak; the window's DEFAULT layout — `hintLayout`, usually `single:tty` — mirrors as a CLEAN URL with the param DROPPED, and `applyLayout` applies the same rule on a mutation back to the default; window switches push entries as today, so back/forward restores the historical arrangement each entry carried, spec L4). **`applyLayout(next)` is the ONE mutation path** — `writeStoredLayout` + `replaceState` mirror; tile verbs, the surface toggles, the ▦ chip, the `view-cycle` chord, and the palette `View:` actions all funnel through it (L3: localStorage is written on user mutation only, never on merely arriving via a carried `?layout=`). Internal navigation (sidebar, ▾ switcher, palette) targets the bare route (§ Window Views → Internal navigation targets the bare route); layout consumers read resolved state, never parse `location.search` pre-ladder. `togglePanel(surface)` is the toggle behind the top-bar group, the overflow Tiles rows, and the palette `Tile: Show/Hide` entries: open surface → `closeSurface`, closed → `addSurface`, then `applyLayout` (a `null` mutation — closing the last tile — is a no-op).

### Present auto-expand (the `rk present` transient reaction)

A viewer MOUNTED on a window's terminal route that observes the window's `rkUrl` **transition** on the state stream — empty→set, or value→different-value — transiently auto-opens the `web` tile (spec surface-layout.md R7/L3 carve-out: a fresh `rk present` is an implicit request for attention). The reaction is view state of the zoom/`mobileActiveTile` class: it never calls `applyLayout`, so nothing is persisted (`rk-layout:` localStorage) and nothing is mirrored into the URL (`?layout=`). (`260815-wkcw`)

- **Trigger semantics (transition-observed)** — the pure reducer `observeRkUrl(state, rkUrl)` folds each observed value into per-window state: initialization (cold entry, first snapshot) NEVER triggers; a same-value SSE tick is a no-op (transition, not presence); a transition to empty clears `active` without latching (availability degradation owns the cleared case); a transition to a new non-empty value triggers UNLESS it exactly matches the dismissal latch. The observation state (`AutoExpandState { lastUrl, active, dismissedUrl }`) lives in an `app.tsx` ref `Map` keyed `` `${server}:${windowId}` `` and survives window switches: a change that happened while the viewer was away updates `lastUrl` silently on remount (not an observed transition), the override deactivates on remount (leaving+returning resolves via the normal ladder), and the latch survives. The observation effect skips frames where the window record is unresolved (a snapshot race must not fake a transition), and the `active` flag reaches render through a `{key, active}` state mirror that `renderLayout` gates on the CURRENT route key — a window switch away from an active auto-open never flashes a phantom web tile on the destination route.
- **Render-time override, never a mutation** — `renderLayout = withAutoWeb(layout, active)`: when active and the resolved layout lacks `web`, render as if `web` were appended through the existing growth conventions (`addSurface` — 1→2 `split-h`, 2→3 `main-left`; arity 3 without `web` is `null` → identity, a visual no-op). Identity when `web` is already open (`IframeWindow`'s SSE sync already navigates the frame on `rkUrl` change — no layout action, no focus move). `renderLayout` feeds `<SurfaceLayout layout>` and EVERY mutation seam — the tile verbs, `togglePanel`, the palette `buildLayoutActions`, the top-bar surface toggles' `open` set (a transiently auto-opened web tile reads lit), and the ▦ chip's `layout` prop — while the ladder-resolved `layout` keeps feeding the URL-mirror effect, localStorage, `resolvedView`, and the window-switch `ungatedIds` classification.
- **Take-ownership (L3)** — any user `applyLayout` while the override is active deactivates it: `dismissAutoExpand` (records the latch) when the applied layout lacks `web`, else `deactivateAutoExpand`. The mutation persists from the RENDERED state — touching it makes it yours.
- **Dismissal latch** — closing the auto-opened web tile (any mutation whose result lacks `web` while active) latches the window's current `rkUrl` value: a later observed transition TO that exact value does not re-open (so an agent's unset/re-set loop cannot fight a dismissal), while a different value re-triggers — timestamped present URLs (`target.URL(..., presentNowFn)`) change on every re-present and intentionally pass the latch. The latch is in-memory only (resets on reload; no sessionStorage/localStorage).
- **Mobile (R13)** — the same render path applies below `isMobileViewport()`: the auto-added `web` surface reads as an unpressed top-bar switch-group button carrying its corner dot (`hasWebUrl` is true — a transition trigger implies a non-empty `rkUrl`; the group's dots are the shared per-surface `showDot` predicate — web = "has content", § Surface Toggles — and the `mobileActiveTile` fallback derivation reads `renderLayout.order`, so tapping it takes switch-to-tile's transient open arm), but `mobileActiveTile` is never SET by the reaction — the visible tile is never auto-swapped on a phone. (`260816-ox16-mobile-tile-switch-vocab`)
- **Module** — `lib/present-auto-expand.ts` (`observeRkUrl` / `dismissAutoExpand` / `deactivateAutoExpand` / `withAutoWeb`), pure and DOM-free with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract).
- **e2e — `present-auto-expand.spec.ts` (+ `.spec.md`)** — real tmux on the port-3020 rig (the `web-view-lens.spec.ts` `_tmux.ts` pattern; `tmux set-option -w @rk_url` is the present-default-arm write path), gated on the status bar's Connected readiness signal: rkUrl set while viewing → the web tile appears with no `?layout=` change and no `rk-layout:` write; ✕-close → unset + re-set the same value stays closed, a different value re-opens; cold arrival with rkUrl already set → no auto-open.

## Chat View

A **read-only HTML chat view over the SAME agent pane** — a second view over the tmux pane, never a substrate (the pane stays the agent's parent, Constitution VI; the view only renders the streamed transcript). It is the **`chat` lens** of the window-view model (§ Window Views (Lens Model)) — a `chat` TILE in the surface layout on the existing `/$server/$window` terminal route (Constitution IV, no new route; a legacy `?view=chat` deep link still works — the shim translates it to `single:chat`, § Surface Layout). **All view-state plumbing — the `?layout=` param + shim, availability gate, `rk-layout:` localStorage persistence, palette parity, and the switch-transition classification — is the UNIFIED machinery** described in § Window Views (Lens Model) and § Surface Layout; this section owns only what is chat-SPECIFIC: the `chatProvider` gate, the connection-dot semantics, the renderer/stream, and the WaitingBadge deep-link. (The heading is a static `Tab:` in every lens, § Heading is a static `Tab:`.) The renderer + data layer live in `architecture.md`/[chat](/run-kit/chat.md) § Chat View Frontend. The chat stream is a `kind:"chat"` subscription on the shared state socket (NOT an `EventSource`) — the owner hook is `use-chat-subscription.ts`, and the connection dot below derives from socket-connected AND chat-acked, not `EventSource` health. (`260714-uco1`, `260717-vhvz`)

**The `chatProvider` gate.** `WindowInfo` carries `chatProvider?: string` + `chatSessionRef?: string` (`types.ts`) — the window-level `@rk_chat` rollup the backend emits (typed, not newly parsed). **A non-empty `chatProvider` is the SOLE availability gate** for the chat lens (`hasChat(win)` in `window-view.ts`) — mirroring the backend's own `resolveWindowChat` gating — so it transitively gates every chat affordance: the `View: Chat` palette action, the `Tile: Show Chat` / `Tile: Hide Chat` palette entries (chat's entry points — the surface-toggles group renders no chat button in either mode and no `Tile: Switch to Chat` entry is ever emitted, `SURFACE_RAIL_HIDDEN`, § Surface Layout), the chat tile's `<ChatView>` renderer, and the deep-link append. (The heading is NOT among them — it is a static `Tab:` in every lens, § Heading is a static `Tab:`.) There is NO separate `chatAvailable` variable — `resolveLayout`/`availableViews` fold the gate in (an unavailable `chat` in a layout degrades tile-by-tile, § Surface Layout).

### View state = the unified lens machinery (NOT a chat-specific mechanism)

The chat lens runs entirely on the unified lens + layout machinery (§ Window Views (Lens Model), § Surface Layout), with no chat-specific view-state module:
- Resolution is `resolveLayout` (URL `?layout=` → `rk-layout:` localStorage → default hint → `single:tty`); `lib/router-url.ts`'s single `validateTerminalSearch` still accepts `?view=chat`, which the shim translates to `single:chat`. There is no `lib/chat-view-resolve.ts`.
- Persistence is the value-bearing `rk-layout:{server}:{windowId}` key (the legacy `runkit-window-view:` key is only a shim seeding source). There is no `runkit:chat-view:` key-presence pref hook.
- Lens switching is palette-only: the `View: Chat` / `View: Terminal` palette actions call `switchView("chat")`/`switchView("tty")` — i.e. applying `single:chat`/`single:tty` (desktop; on mobile the `View:` entries are superseded, so chat's entry points there are its `Tile: Show/Hide Chat` entries — chat is `SURFACE_RAIL_HIDDEN`, so the switch group renders no chat button and no `Tile: Switch to Chat` exists). There is no switcher component and no dedicated chat chord.
- `chatViewActive = layout.order.includes("chat")` is the render + stream gate (`resolveLayout` already gated on `chatProvider`) — true whenever a chat TILE is open, slot A or not.

### Center heading `Tab: <name>` (static in the chat lens too)

The `chat` lens does NOT change the heading prefix — the top-bar heading is a static `Tab: <name>` in every lens (§ Heading is a static `Tab:`; § Window Heading for the boot-sweep/rename mechanics). ## Design Decisions

### Progress line is an absolute overlay, not an in-flow strip
**Decision**: The tty tile's 2px progress line renders inside a zero-height `relative` wrapper with an `absolute`, `pointer-events: none` 2px bar overlaying the content's top edge.
**Why**: The tile layout must not shift when progress appears, and — stronger — an in-flow strip would change the terminal container's height, firing `ResizeObserver → fit → PTY resize` churn on every task start/stop, which the window-switch machinery treats as a hard constraint (transform-only, no layout change).
**Rejected**: The web tile's in-flow `.rk-web-progress` form (fine over an iframe whose element's presence IS the loading state, resize-churn over xterm); reserving a permanent 2px row (burns 2px on every idle tile).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### One shared progress slot per window, wired on every tty mount
**Decision**: Progress is a single `SurfaceLayout` state slot (the `webPageTitle` precedent) fed by `onProgressChange` on every tty `TerminalClient` mount, primary and duplicates alike.
**Why**: All tty tiles show the same window, so per-tile state would duplicate identical values; wiring every mount keeps the signal alive when the primary tile is hidden (hide-never-unmount keeps its stream open), and duplicate firings fold idempotently under the rAF coalescing.
**Rejected**: Primary-tty-only wiring (loses updates in hidden-primary arrangements for no savings); per-tile state (duplication with no benefit).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### Heading identifies the window, not the lens
**Decision**: the terminal-route center heading is a static `Tab: <name>` in every lens (tty/web/code/chat) (`260820-lfla`); lens identity is carried by the tile content and the top bar's lit tile toggles, not the heading.
**Why**: the heading identifies the WINDOW (the substrate), per window-views.md "rows are substrates, views are lenses". Keeping the prefix constant also stops the name's anchor from jumping on a lens switch (the prefix width no longer changes with the lens).
**Rejected**: "the center page heading follows the lens" (window-views.md R4's original sentence — reversed in-spec within the change).
*Introduced by*: 260714-uco1-topbar-heading-anchor-nav

### Two verb families on tile headers
**Decision**: Tile-header verbs split into layout verbs (generic, arity-gated, unchanged) and content verbs (per-kind, any-arity, zoom-visible) — the tty tile carries a bordered pane segment holding Split H / Split V / Close Pane.
**Why**: Pane operations act on the tmux pane inside the tty tile; proximity is the disambiguation. The tile header is already per-kind on its left side (StatusDot, meta chips), so per-kind verbs on the right are an evolution, not a break.
**Rejected**: Keeping pane verbs in the top bar (target invisible on multi-tile layouts); moving only the splits; a confirm-on-close variant — the glyph+grouping distinction below was chosen.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### Page title crosses the component seam via a callback, kind stays derived
**Decision**: `IframeWindow` reports `{ title }` through an optional `onPageMeta` prop on frame `load`; `SurfaceLayout` holds it as state for the header. The kind badge is derived purely from `rkUrl` via `lib/web-url.ts` with no seam.
**Why**: the header is SurfaceLayout's render but only the mounted iframe can read `contentDocument.title`; a narrow optional callback matches the existing `onInteract`/`onFolderNavigated` seam shapes, and deriving the badge purely keeps it testable and SSE-consistent.
**Rejected**: rendering a second header inside `IframeWindow` (duplicates the tile-header contract) or lifting the whole iframe ref up (breaks the presentational-component boundary).
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Dead-port detection is a frontend same-origin fetch, not a proxy ErrorHandler
**Decision**: a dead proxied port is detected by `fetch`ing the proxied path from the frontend and reading the reverse proxy's 502, rendering the error state client-side.
**Why**: the proxy already answers 502 on connect failure (the default `ReverseProxy` error path); a same-origin fetch reads it with zero backend change and keeps `frame-check` scoped to absolute external URLs only.
**Rejected**: a custom `ErrorHandler` serving a styled error page from `proxy.go` — touches the proxy layer and couples error UI to the Go layer.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Error states render over a hidden, still-mounted iframe
**Decision**: the tile's error surfaces render in place of the iframe's VISIBLE area while the iframe stays mounted under the `hidden` class.
**Why**: unmounting would strand the attach seam's mount-once listeners, forcing a remount dance on Retry; `hidden` satisfies "replace the iframe render" visually with zero seam churn.
**Rejected**: conditional unmount of the iframe — breaks the mount-once attach effect and complicates Retry.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### `SurfaceLayout` owns zoom/drag/mount-once; `app.tsx` owns layout state
**Decision**: the tile renderer receives the resolved layout as a prop and owns only transient interaction state (zoom, the in-flight ratio drag, the ever-opened mount bookkeeping); layout resolution (the ladder), persistence, and URL mirroring live in `app.tsx` behind the single `applyLayout` mutation path.
**Why**: layout state is route-integrated (search params, history semantics, navigation seams) and belongs beside the lens machinery; zoom and drag are self-contained interaction state with no URL/localStorage footprint. Prop-in/callback-out composition keeps the renderer free of the router/storage import graph — tile chrome, verbs, and hide-never-unmount are unit-testable in jsdom — and new surface kinds slot in without touching the shell.
**Rejected**: the renderer importing storage/router helpers and owning layout resolution — two sources of truth for the layout (component + route) and untestable without mocking the router.
*Introduced by*: 260811-2r1w-right-panel-shell-web-surface (as the panel shell's contract); generalized to the tile renderer: 260812-ab5v-surface-layout-core

### Present auto-expand composes via `addSurface` at render time
**Decision**: `app.tsx` computes `renderLayout = withAutoWeb(layout, autoWebOpen)` — `addSurface(layout, "web") ?? layout` when the auto-open is active and the resolved layout lacks `web` — and feeds `renderLayout` to `SurfaceLayout`, the tile verbs, the top-bar surface toggles' open set, and the ▦ chip; `resolveLayout`'s output keeps feeding the URL-mirror effect, localStorage, and the window-switch transition classification.
**Why**: reuses the exact growth shapes every other web-open path produces (the surface toggles, the palette), so the auto-open looks identical to a manual open; verbs acting on the rendered layout make "touching it makes it yours" (L3) fall out for free — a mutation persists from what the user sees. And because nothing is written, R7's substrate-vs-view-state split and L3 ("write on user mutation only") stay intact.
**Rejected**: slot-A swap (steals the terminal from an actively-typing user); a zoom-like overlay (new interaction surface, not reachable by the existing verbs; closing semantics would need bespoke chrome).
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Value-exact dismissal latch; timestamped re-presents pass it
**Decision**: the dismissal latch matches the exact `rkUrl` string. A re-present of the same file carries a fresh timestamp and re-opens.
**Why**: a re-present is by definition a fresh request for attention; suppressing it would make the verb unreliable. The latch's job is narrower — the same value re-observed (unset/re-set, state replays) must not fight a dismissal.
**Rejected**: normalizing away the timestamp param or a time-window cooldown — heuristic, and it would suppress genuine re-presents.
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Auto-expand observation state lives in a per-window in-memory map
**Decision**: the auto-expand state (`lastUrl`, `active`, `dismissedUrl`) is held in an `app.tsx` ref `Map` keyed `` `${server}:${windowId}` `` and updated by the pure reducer in `lib/present-auto-expand.ts`; it is not cleared on window switch.
**Why**: surviving the map across switches means a value change that happened while the viewer was away updates `lastUrl` silently on remount (no spurious trigger), and a brief unresolved-window frame (snapshot races) cannot fake a transition. Matches the transition-observed rule without extra bookkeeping.
**Rejected**: `useState` reset on `[server, windowParam]` (the `mobileSlotA` pattern) — a reset makes the first post-switch observation indistinguishable from cold entry only if handled carefully, and loses the latch on every switch.
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Code-surface availability gates on stable signals; reachability gates content
**Decision**: `hasCode` — the availability gate for the `code` lens/tile — is stable signals only: the window's code folder is LATCHED, or a `gitRoot` derives non-empty (the code-server port is always resolvable by convention — preset `RK_CODE_SERVER_PORT` else `RK_PORT+2` — so a configured-port leg would be vacuous). The TTL-cached reachability probe never gates availability; it selects the surface's CONTENT (live iframe when up, the `code-server not running — check rk doctor` empty state when down).
**Why**: reachability fluctuates with code-server restarts — gating the surface toggle / switcher segment on it would strobe the affordances, and the not-running state could never render (the affordance would vanish exactly when its message is needed). The live derivation fluctuates too, with the ACTIVE PANE's cwd: a window whose editor is open would lose its surface toggle, switcher segment, and deep-link validity the moment an agent `cd`s out of the repo. The latch is what makes the signal genuinely stable per window; content states may fluctuate.
**Rejected**: availability = configured ∧ reachable (the spec's original wording — internally contradictory with the not-running state); availability = gitRoot ∧ port-configured (vacuous once the port resolves by convention); derivation-only availability (strobes with the terminal's cwd).
*Introduced by*: 260811-k3vp-right-panel-code-lens; gitRoot-only gate: 260811-a2bo-daemon-code-server-stable-route; latch-or-derivable: 260813-if5d-latch-code-surface-folder

### Web availability is unconditional; `hasWebUrl` selects the content
**Decision**: the `web` lens/tile is ALWAYS available (like `tty`) on every window; `hasWebUrl` selects the tile's CONTENT — an empty/whitespace `rkUrl` renders the onboarding state (reduced live URL bar + the fill-path panel), a non-empty `rkUrl` renders the live iframe — exactly as code splits availability from reachability.
**Why**: a single `hasWebUrl` availability predicate gated six consumer surfaces (the ⌘3 chord, the top-bar toggle, palette `View:`/`Tile:` entries, the mobile switch group, deep-link degradation), making the tile undiscoverable before initialization; the availability-vs-content split is the codebase's named model for "the lens exists but has nothing to show", and the onboarding state doubles as the discoverability surface (its live address bar is itself an init path).
**Rejected**: a ⌘3-only carve-out (a chord opening a tile the availability model says doesn't exist — the layout resolver would drop the tile anyway, so the resolver, toggles, and palette would each need contradictory special-cases); a modal/tooltip explainer (no live address bar, no automatic flip).
*Introduced by*: 260821-zqlq-web-tile-always-tileable-onboarding

### The web toggle dot means "has content"
**Decision**: the web toggle button always renders (the surface is always available); its corner dot is driven by a per-surface `showDot` predicate (`app.tsx`: `surface !== "web" || hasWebUrl(win)`) — web's dot means "has content"; every other surface's dot stays always-on; the overflow Tiles rows carry no dot.
**Why**: the button's constant presence is the discoverability affordance; the dot preserves the at-a-glance "something to see" signal the button's old appearance/disappearance carried.
**Rejected**: a dotless always-on web button (loses the content signal); hiding the button until content exists (recreates the discoverability hole).

### The code surface is a lean `CodeSurface`, not an `IframeWindow` reuse
**Decision**: the `code` lens/surface renders a new minimal component — an iframe of `/code/?folder=<gitRoot>` plus the not-running empty state — while `web` keeps `IframeWindow` with its URL bar and refresh chrome.
**Why**: the code-server URL is fully derived (the stable `/code/` path plus the git root — no port, no editable address), so the URL bar (`@rk_url` substrate state — a shared, POSTed content address) is meaningless; reusing `IframeWindow` would drag inapplicable chrome and substrate semantics into a surface whose content address nobody edits. The relative-path discipline (`toProxySrc`'s convention — never compose an absolute origin) is the one piece reused.
**Rejected**: `IframeWindow` with a hidden URL bar (dead chrome, plus `@rk_url` semantics that do not apply to a derived URL).
*Introduced by*: 260811-k3vp-right-panel-code-lens; stable `/code/` src: 260811-a2bo-daemon-code-server-stable-route

### Chord-reclaim via a capture-phase iframe `contentDocument` listener
**Decision**: Both iframe renderers (`CodeSurface`, `IframeWindow`) attach a capture-phase `keydown` listener to the same-origin iframe's `contentDocument` after every load (re-attached on each navigation, removed on cleanup, `contentDocument` access try/catch-guarded), reclaim exactly the events matching an injected `shouldReclaimChord` predicate — one curried factory in `app.tsx` (`reclaimChordForKind`) binds the registry's pure, kind-aware `hasReclaimableMatch` per surface kind; it carves out keydowns whose only matches are `ttyOnly` bindings and gates `webOnly` matches to the web kind — and re-dispatch a synthetic bubbling `KeyboardEvent` on the parent DOCUMENT.
**Why**: the `/proxy/` embed is same-origin by design, so a focused iframe's key events are reachable before the embedded app's keybinding service sees them; dispatching on the parent document reaches both document-level listeners (the palette's chord) and window-level ones (the keybinding dispatcher, the ⌘. view cycle) in one event. Injecting the predicate keeps both components free of the registry import graph, one factory keeps the two kinds reading one registry, and reclaiming only REGISTRY chords leaves the embedded/framed app's own Ctrl/⌘ bindings working.
**Rejected**: dispatching on `window` (misses document-level listeners); reclaiming every chord (breaks VS Code's own bindings); shipping without reclaim (click-out-only escape leaves ⌘K dead whenever the editor has focus).
*Introduced by*: 260811-k3vp-right-panel-code-lens; shared with the web tile + kind-aware predicate: 260819-ie2i-web-tile-keyboard-find

### The find-bar open seam is a document CustomEvent
**Decision**: each find consumer's chord handler and palette body dispatch ONE document CustomEvent — `web-find:open` (`WEB_FIND_OPEN_EVENT`), received by the mounted `IframeWindow`, and `terminal-find:open` (`TERMINAL_FIND_OPEN_EVENT`, `lib/terminal-find.ts`), received by the mounted `SurfaceLayout` (the `window-heading:rename` / `theme-selector:open` precedent). The ⌕ buttons toggle locally.
**Why**: `IframeWindow` is presentational and the web find bar's state belongs inside it, and the tty bar's state belongs to the tile layer — a CustomEvent avoids threading an imperative ref through `SurfaceLayout` (or deeper) for one action; only one web tile can exist per layout (kinds don't repeat except tty) and at most one terminal route's `SurfaceLayout` is mounted, so neither receiver is ambiguous.
**Rejected**: a `findBarRef`/`openFindRef` threaded app.tsx → SurfaceLayout → consumer (touched signatures for one opener); lifting find state into app.tsx (drags search state into the shell for no consumer).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find; tty seam: 260819-zqf9-terminal-tile-find

### Highlight styling enters the frame as a `<style>` element, not injected script
**Decision**: the engine registers Highlight objects on the frame window's `CSS.highlights` and appends one `<style>` with `::highlight(rk-find)` / `::highlight(rk-find-active)` rules to the frame's head, removed/replaced on reset.
**Why**: `::highlight()` pseudo-elements must be styled in the document that owns the ranges; a style element is inert DOM (no execution), which honors the no-script-injection constraint while keeping the search fully parent-driven.
**Rejected**: `window.find()` as the primary (no match count, engine-inconsistent); wrapping matches in `<mark>` elements (mutates the framed page's DOM structure — breaks pages that read their own DOM, and unwinding on reset is error-prone).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find

### Stateful digit chords toggle the surface tiles; `` ⌃` `` hops tty↔code focus
**Decision**: the tile chords are stateful three-state handlers (show+focus / focus / hide+restore) keyed on the CURRENT render layout and focused kind — one positional digit per surface kind (⌘1 tty / ⌘2 code / ⌘3 web, ⇧Ctrl+digit on Win/Linux) riding `togglePanel`, the per-kind landing flag, the `focusTileRef` seam, and the restore router, with the hide arm a no-op at arity 1; the code surface's `Tile: Show/Hide Code` palette entry carries the chord's hint (the `toggleTarget: "code"` / `toggleShortcut` seam) so it stays discoverable. The sibling `focus-hop` chord hops focus between the tty and code tiles through the `Tile: Focus <Surface>` focus-by-kind seam, opening a closed-but-available code tile first (open-then-focus — VS Code's ⌃`-opens-the-hidden-panel analog).
**Why**: the JetBrains tool-window model gives every surface both verbs on ONE chord — a pure toggle cannot express "put my cursor there", and a kind-fixed positional digit gives each surface a stable identity (toggling needs a stable target). Statefulness lives in the chord handlers only — the palette entries keep explicit single-verb semantics ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Design Decisions → Statefulness lives in chord handlers, not palette bodies).
**Rejected**: a generic first-non-tty toggle (a surface picker with no stable target across capability sets, and no chord for the hop); separate toggle and focus chord layers (double the keycap spend); making `togglePanel` itself stateful (it backs the top-bar toggles and menu checkboxes, whose semantics must stay pure toggle); no-op when the code tile is closed (deads the hop in the shipped `single:tty` default layout — VS Code's ⌃` opens the hidden panel, so the borrowed gesture includes the open half).
*Introduced by*: 260811-k3vp-right-panel-code-lens; retargeted to tiles: 260812-ab5v-surface-layout-core; stateful digit family: 260819-qwr7-surface-focus-chords

### Surface toggles are one ordered-registry group in the top bar

Click routing runs through the caller's `togglePanel` semantics unchanged.

**Rejected**: A dedicated collapsible rail column in the stage grid (a whole grid track, a persisted collapse pref, and a top-bar toggle chip to serve four small buttons); `menuOnly` toggles (the primary add/close affordance hidden behind the overflow menu at every width).

**Why**: At 0c6o's drafting the terminal route had no tile-focus concept; `260812-wfic` (landed alongside) then introduced the focused-slot state and `Tile: Focus <Surface>` palette entries, removing that blocker — but a cycling chord still doesn't ship, because a terminal-scoped ⌘[/⌘] pair shadows macOS history navigation and the usage need is unproven. ### Derivation seeds the code folder once; only the editor moves it
**Decision**: The code surface's folder is a per-window localStorage latch (`runkit-code-folder:{server}:{windowId}`). The backend's live `gitRoot` derivation seeds it exactly once — at the code surface's first actual render for that window — and the only writer afterward is the editor's own navigation, reported back from the iframe's `load` event. The terminal never moves the editor.
**Why**: `gitRoot` follows the ACTIVE pane's cwd and agents `cd` constantly, so a live folder makes the terminal's movement move the editor: a pane leaving every repo unmounts the tile, and two panes in two repos swap the workbench between them — either way the editor's in-flight state (open tabs, dirty buffers, undo stacks) is expensive or impossible to recover. That defeats hide-never-unmount (P3), which exists precisely so the iframes keep their in-memory state. A latch makes the folder the viewer's choice rather than the terminal's, and localStorage matches code-server's own per-browser tabs/layout state.
**Rejected**: Stabilizing the backend derivation (first-pane-with-a-root wins) — still moves the editor whenever panes `cd`, so it is a mitigation, not a guarantee; re-deriving on tile close/reopen (latch only while open) — reopening after a `cd` is exactly when the editor must come back where it was; a tmux window option (`@rk_code_folder`) for cross-viewer sharing — deferred, not rejected on merit; liveness probing a stale latch — code-server's own "folder does not exist" state plus File > Open Folder is the escape.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### Effective-window substitution over signature widening
**Decision**: Compute the latch once at the `app.tsx` seam and substitute `gitRoot: latch ?? live` into an effective `ViewWindow` (`withLatchedCodeFolder`) passed to all availability/render consumers.
**Why**: One substitution point makes `hasCode`, `availableTiles`, `degradeLayout`, the tile guard, `tileMeta`, and `codeServerSrc` all follow the latch with zero changes to the pure modules — they stay DOM-free and their existing tests stay valid. The seam is also where the storage identity (server, window id) already lives, and the helper is exported so the substitution is unit-testable without rendering the shell.
**Rejected**: Widening `ViewWindow` with a separate `latchedCodeFolder` field or threading a parallel parameter through `hasCode`/`availableViews`/`resolveLayout`/`availableSurfaces` — more touched signatures, drift risk between consumers, no behavioral gain.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### Iframe src fixed per mount generation
**Decision**: `CodeSurface` computes its iframe `src` once per iframe mount generation — a ref keyed to the `reachable` gate that mounts the iframe — not reactively from the folder prop.
**Why**: P3 (hide, never unmount): React re-rendering a changed `src` attribute re-navigates a live frame, even to a URL the frame is already at, which would reload the editor on the very latch update the follow rule just wrote. Keying the computation to mount generation means a reachability `false→true` flip or a window-switch remount picks up the CURRENT latch (fresh workbench, correct folder) while a mounted frame is never parent-navigated. A ref rather than `useMemo` because a memo cache is a documented performance hint React may discard, and a dropped cache here would re-navigate the live frame — the exact hazard the decision prevents.
**Rejected**: A `src` state set only at first render — goes stale across reachability flips (a remounting iframe would boot into the seed-time folder instead of where the editor last was).
*Introduced by*: 260813-if5d-latch-code-surface-folder

### The latch is read at render, never mirrored through an effect
**Decision**: `app.tsx` reads the code-folder latch during render (a `useMemo` over server + window id + a write-epoch counter, beside the `storedLayout` read that does the same), never mirroring it into state through an effect.
**Why**: an effect lands a frame late, so a window switch would render the PREVIOUS window's latch once — and a code iframe mounting in that frame would fix its `src` for its whole mount generation (§ Iframe src fixed per mount generation), stranding the editor at the previous window's folder.
**Rejected**: an effect that syncs the latch into component state — one stale frame is enough to fix a live iframe's `src` at the wrong folder.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### The waiting-badge click advances, never restarts
**Decision**: `handleWaitingBadgeClick` resolves its destination through `nextWaitingTarget(ordered, server, windowParam)` (`lib/palette-agent-nav.ts`) — the same helper the `Agent: Next waiting` palette action uses — rather than scanning the session's windows itself.
**Why**: the badge means "the next waiting window", relative to where the viewer already is. Picking the session's FIRST waiting window makes the badge a silent no-op whenever the viewer is already on that window, instead of advancing to the next one.
**Rejected**: a local `windows.find(isWaiting)` scan — re-implements the palette's ordering (drift risk) and dead-ends on the first waiting window.
*Introduced by*: 260717-vhvz

### Switch-to-tile's not-open arm routes through `switchView`, never a transient swap
**Decision**: `switchToTile(surface)` (`app.tsx`) forks on whether the target is already in `renderLayout.order`: open → a transient `setMobileSlotA` swap (no `applyLayout`, no URL/localStorage write); available-but-not-open → `switchView(surface)` → `applyLayout(single:<surface>)`.
**Why**: the two arms need opposite write discipline — a transient swap of an open tile keeps a shared multi-tile arrangement arriving via `?layout=` intact (spec surface-layout.md L3: write on user mutation only), while the not-open arm MUST persist: `switchView` carries per-window localStorage, the URL mirror, and code-folder latch seeding, which keys on `layout.order.includes("code")` — a transient-only mechanism would silently break latch seeding.
**Rejected**: a transient swap for both arms (breaks latch seeding and drops persistence the user expects from an explicit pick); always persisting (a tap on a shared 3-tile deep link would destroy the carried arrangement).
*Introduced by*: 260816-ox16-mobile-tile-switch-vocab

### Scale wrapper over guest-document CSS zoom
**Decision**: web-tile content zoom is a transform-scale wrapper on the iframe with compensated width/height (rendered at `100%/s`, scaled back by `s`, origin 0 0).
**Why**: works for all four address kinds including cross-origin `external`; reproduces browser-zoom semantics (zooming in shrinks the frame's CSS viewport, so responsive guest layouts adapt); zero reach into guest documents.
**Rejected**: injecting CSS `zoom` into the guest document — same-origin only, and touching proxied content re-opens the proxy-rewrite class of bugs (the stale Content-Length scar).

**Decision**: "Zoom" names content magnification everywhere (the web tile's URL-bar control, the `Web: Zoom *` palette actions); the tile-maximize verb's user-facing strings are Expand/Restore (`Layout: Expand`/`Layout: Restore`, the tile-header Tip/aria-labels, the `zen-toggle` binding description) while its ids (`layout-zoom`/`layout-unzoom`), the `ZoomGlyph`/`data-icon="zoom"` seam, and the `zoomed`/`zoomToggleRef` internals keep the zoom vocabulary.
**Why**: two different "Zoom"s in one tile header/palette is a vocabulary collision, and the browser muscle-memory meaning of zoom is content magnification; ids persist in user macros/overrides, so only labels may move.
**Rejected**: per-surface content-zoom names with the tile-maximize verb keeping "Zoom" — leaves "zoom" meaning maximize, fighting every browser's meaning of the word.

Two-tier URL model (`/$server/$window`) with server always in path (no `$session` middle segment). URLs are fully shareable — copying a URL and opening it elsewhere on the same host opens the same server and window (the session is re-derived from the snapshot). TanStack Router uses nested routes: `/$server` is a layout route (`serverLayoutRoute`) whose component (`ServerShell`) wraps `SessionProvider` + `AppShell`; the terminal child route is `path: "/$window"` and uses the paired `params: { parse, stringify }` API to serialize the single `window` param (no `session`) as its numeric part in the URL. The two directions are the exported pure helpers `windowIdToUrlSegment` (stringify — strips the leading `@`) and `urlSegmentToWindowId` (parse — idempotently prepends `@`) in `router.tsx`; parse restores the `@N` form so every `params.window` consumer keeps receiving `@N`. Child routes (server index and terminal) are matched by the router but rendered conditionally by `AppShell` based on whether the `window` param exists. (`260529-jad6`, `260703-8mpy`)

**Canonical page names** — the spoken/documentation vocabulary for referring to each route. Use these names in conversation, PRs, and docs instead of the raw path patterns. A mirror of this glossary is a comment beside the `routeTree` definition in `app/frontend/src/router.tsx`. (`260702-nuup`, `260715-zs1y`)

| Route path | Canonical name | Component |
|------------|----------------|-----------|
| `/` | **Host** | `HostOverviewPage` (global home / server list; also the host-console HOST HEALTH zone, PR #290) |
| `/$server` | **tmux Server** | `ServerShell` (a single server's view; the `resolveServerView` route guard runs here) |
| `/$server/$window` | **Terminal** | *(inherited layout — no dedicated component)* (a specific window `@N`) |
| `/board/$name` | **Board** | `BoardPage` (lazy) (cross-server pane board) |
| not-found fallback | **Not Found** | `NotFoundPage` (root `notFoundComponent` catch-all — not a registered path) |

The `$server` / `$window` / `$name` segments are **route params** (actual server names, window ids, board names), not literal path segments.

**Vocabulary split** — **every** route surfaces a `PageType: name` identity heading in the top-bar CENTER cell (`Window: <window>` — static in every lens, `Board: <board>`, `tmux Server: <server>`, solo `Host`) — the canonical page type is the two-tone prefix, the instance name is the subject (§ Chrome (Top Bar) center cell). Page identity lives in the chrome, not the page body. The split reads: **the left breadcrumb ends at the PARENT** (server / session — *the trail to here*), **the centered heading is the current-page leaf** naming both the page type and the instance (*what & where you are*), so a name never appears twice in one bar (move-don't-copy — § Chrome (Top Bar), § Section Heading). The bracket idiom names the in-page **section** labels (the tmux Server page's `Sessions`, the Host-page zones) via the shared `SectionHeading` (§ Section Heading). (`260702-6m46`, `260704-pr0p`, `260714-uco1`, `260715-zs1y`)

**Window identity is the tmux window ID (`@N`), not the index**, and **`@N` is the *only* window identity carried by the URL** — the URL *segment* carries only `@N`'s numeric part (`@N` sans `@`), restored to `@N` by the route's idempotent parse (see the `/$server/$window` route-table row above). The `$window` route param holds a stable `@N` string; all URL/API/relay/tmux layers address a specific window by this ID, while the window *index* is retained only for positional reorder/move. The owning **session name is derived from the active window's SSE snapshot** (locating `@N` within `sessions[].windows[]`), not read from the URL — `app.tsx` computes `currentSession = sessions.find(s => s.windows.some(w => w.windowId === windowParam))` and `sessionName = currentSession?.name`. Index-based bookmarked URLs (`/$server/$session/3`) AND session-bearing URLs (`/$server/$session/@N`) are a **hard break** — they do not resolve (no redirect shim; constitution §II — ephemeral URLs, no persistent state). See `architecture.md` § API Layer and `tmux-sessions.md` § Window addressing identity for the cross-layer contract. (`260529-chgz`, `260529-jad6`, `260703-8mpy`)

Server not found: if the `$server` segment doesn't match any known tmux server, a "Server not found" page renders with a link to `/`. A 3-segment URL does not match the 2-segment terminal route and falls through to the `NotFoundPage` / server-dashboard fallback.

**Three-way route guard (view / waiting / not-found)** — the `$server` segment is resolved by a pure exported helper `resolveServerView(server, servers, pendingServer, serversLoaded)` in `app.tsx` returning `"view" | "waiting" | "not-found"`. The branches: (a) `server` IN `servers` → `"view"` (render the server view); (b) NOT in list AND `server === pendingServer` → `"waiting"` (render `ServerWaiting`, a sibling of `ServerNotFound`); (c) NOT in list AND `server !== pendingServer` AND `serversLoaded` → `"not-found"` (render `ServerNotFound` immediately, so a typo'd URL still fails fast); (d) otherwise (e.g. before the first fetch resolves) → `"view"`, falling through to the server view / loading rather than flashing not-found. The guard keys on the explicit `serversLoaded` flag, **NOT** the `servers.length > 0` proxy (§ Design Decisions → Route guard keys on `serversLoaded`). The `pendingServer` waiting state applies only to the one server the user just created. `ServerWaiting` reuses `ServerNotFound`'s centered idiom (`flex flex-col items-center justify-center h-full gap-4 bg-bg-primary` — `h-full`, so these edge pages fit the content region below the persistent TopBar without overflow) + the shared `LogoSpinner`, showing a brief "Creating server… / Waiting for `<name>`" message. (260602-3i5d)

**Create-server → pending-marker → waiting-then-view lifecycle** — `SessionContext` (`app/frontend/src/contexts/session-context.tsx`) carries the transient state for this: `pendingServer: string \| null`, `markServerPending(name)` (an empty-string argument is the clear sentinel → sets `null`), and `serversLoaded: boolean` (set `true` in `fetchServers()`'s `finally`, so it counts as loaded even on an empty list or a caught fetch error — a permanently-false flag would hang the not-found branch forever). All three are threaded through the context type, the live provider value, and the `StandaloneSessionContextProvider` test fallback as safe no-ops/defaults. **BOTH server-create entry points drive this identical flow** — the waiting state is entry-point-agnostic: (1) the in-app **AppShell** "Server: Create" dialog (`handleCreateServer` in `app.tsx`), and (2) the `/` home-page **`HostOverviewPage`** "+ New Server" (`handleCreate` in `host-overview-page.tsx`). Each: calls `markServerPending(trimmed)` then navigates to `/$server`; its create `useOptimisticAction` fires `refreshServers()` from `onAlwaysSettled` (unmount-safe — the create dialog unmounts on navigation but the hook-owning component's root-level `SessionContext` stays mounted; the refresh touches only that) and clears the pending marker via `onAlwaysRollback` (`markServerPending("")`) so a failed create never strands the UI on the waiting state. `HostOverviewPage`'s displayed list reads SessionContext's `servers`/`serversLoaded` (the same source the guard reads, so page-display and guard-check cannot diverge) while keeping its local `ghostServers` optimistic tiles and the Host-page HOST HEALTH zone (§ HOST HEALTH Zone). `pendingServer` is auto-cleared by an effect **in SessionContext** (not in `app.tsx`) once the refreshed `servers` list contains it — event-driven on the list changing, with **no timer and no polling** (§ Design Decisions → No bounded-fallback timer on the waiting state). (`260602-3i5d`, `260701-f4e5`)

**Server-list fetch lifecycle**: the server list (`servers`, from `listServers()` → `GET /api/servers`) is a **one-time fetch on `SessionProvider` mount + explicit `refreshServers()`** — it is **NOT** part of the per-server SSE stream (SSE streams per-server *sessions*/order/metrics/board-changed only, never the list of servers). So a newly-created server does not appear until `refreshServers()` is called; the create flow above is what triggers that refresh. The `server-gone` event (below) is the symmetric *removal* trigger — it likewise drives a `refreshServers()` re-query rather than carrying the list inline.

Kill/not-found redirects go to `/$server` (server dashboard), not `/` (server list). The user stays in their server context.

### RECOVERY Zone

A conditional zone on the Host page `/`, extracted as `components/recovery-section.tsx` and slotted between TMUX SERVERS and SERVICES via the shared `SectionHeading` (label `Recovery`). It renders ONLY when restorable snapshot offers exist — zero footprint otherwise: no heading, no empty state, no reserved space. Offers are reboot-orphaned servers: a lingering live-latest layout snapshot whose server has no live tmux socket ([layout-snapshots](/run-kit/layout-snapshots.md) § Restorable offers). Dead servers never appear in the live server list or hierarchy. (260820-4psk)

- **Shared state hook** — `useRecoveryOffers()` is lifted to `HostOverviewPage` and handed to both the `RecoverySection` (rendering) and the palette registration, so every surface drives the SAME mutations over one offer list. Data flow: one `getRecoveryOffers()` GET on mount + a refetch after the hook's own restore/dismiss mutations — never `setInterval`+fetch polling, no new SSE kind; a fetch failure resolves to zero offers (an old or unreachable daemon simply has no recovery surface, so the section stays hidden).
- **Row anatomy** — one row per offer: a chevron expander, a hollow (non-live) dot (the ring shape of the status-dot ladder's at-rest tier — a dead server never reads as solid/live), the server name, and a meta line `N sessions · M windows · last seen X ago · system restart` ("last seen" from the snapshot's `takenAt` through the existing `formatDuration`, computed at render — on quiet servers it reads as the age of the last layout change, accepted; no ticking clock). Actions: a **Restore** button and an **×** dismiss button, replaced by an indeterminate per-row "restoring…" state while the synchronous restore POST is in flight. A **Restore all (N)** / **Dismiss all** pair rides the `SectionHeading` `side` slot when more than one offer exists — both are client-driven sequential per-server POSTs over `offersRef.current` (no bulk endpoint — dismiss-all loops the hook's own `dismiss`, mirroring restore-all's composition), continuing past per-server failures (each toasts), and neither confirms (consistent with the per-row controls; a dismissal is not data loss — the rolling history files survive, only the offer path closes via audited tombstone).
- **Expanded tree** — the chevron opens a read-only session tree straight from the offer payload: sessions with their stored `@rk_ses_color` swatches (`colorValueToHex`), windows with index/name/pane count and the recorded former commands, agent (`claude`) windows tagged `resumable` (display-only; the per-window resume affordance is a later phase the tree design accommodates).
- **Flows** — Restore POSTs `/api/recovery/restore`; on success the row is removed, the offers refetch, and `refreshServers()` runs so the restored server's live tile appears in TMUX SERVERS without waiting for SSE (the server list is fetch-on-demand — the create-server flow's `onAlwaysSettled` precedent); on failure the row returns to rest and the error surfaces via the toast idiom. Dismiss POSTs `/api/recovery/dismiss` and removes the row on success.

### Server-Gone Reap → not-found flip (in-band `gone` event + connection-loss fallback)

The backend signals a server whose tmux socket is gone right before reaping it from the poll set — see `tmux-sessions.md` § SSE Poll-Set Lifecycle. This rides the state socket as an in-band `gone` frame (`{"op":"gone","kind":"server","key":"<server>","reason":"server-exited"}`; the `key` names the server since one socket carries every server). There is **no new HTTP endpoint or component** (Constitution IX) — it reuses the one state socket and the existing `not-found` route guard. (`260603-gs2t`, `260716-qf3j`)

`SessionProvider` (`app/frontend/src/contexts/session-context.tsx`) routes it through the `StateSocket`'s `onGone(key)` callback. The handler: drop the server from `ackedServersRef` (its dot goes disconnected) and from `subscribedServersRef`, call `socketRef.current.unsubscribeServer(key)` to **release the StateSocket ref-count** (so the diff effect can re-subscribe cleanly if the server is later restored while still attached — see `architecture.md` § State Socket → `onGone`), delete the server's slice from `slicesByServer`, then call `fetchServers()` (the `useCallback` that `refreshServers` aliases). The now-dead server is already absent from `GET /api/servers` (enumeration is socket-file-based and self-healing), so the refreshed list **shrinks**, and if the user is currently viewing that server `resolveServerView(server, servers, pendingServer, serversLoaded)` flips to `"not-found"` (`serversLoaded` is already `true` post-mount), rendering the existing `ServerNotFound` view. This extends the three-way route guard (§ above): the same `not-found` branch that catches a typo'd URL also catches a reaped server.

**Connection-loss fallback** (belt-and-suspenders): a catastrophic socket death the backend can't signal (no poll tick lands, or the daemon is mid-restart) is covered by the socket-level disconnect debounce — the state socket's `onConnectionChange(false)` clears each acked server's `isConnected` after the 3s debounce, and the provider's server-list refresh path (a `fetchServers()` on reconnect / list change) still shrinks the list, so the guard-flip path fires even with no `gone` frame. The two paths are idempotent and **first-to-fire wins**: the `gone` frame is the fast path (sub-second), the connection-loss refresh is the guaranteed-eventual path. If the server is in fact still alive, the refreshed list still contains it and no flip occurs.

### URL as Resumable Bookmark

**tmux is the sole source of truth for "current window" per server.** The URL is a **resumable bookmark** — consulted on initial mount (and reload), then treated as derived state that follows tmux. Three contracts:

1. **Mount-time alignment (one-shot)**. On the first SSE payload after a route mounts, `app.tsx` compares the URL's `$window` window ID (`windowParam`, a `@N` string) to `currentSession.windows.find(w => w.isActiveWindow)?.windowId`. If they differ, it fires exactly one `selectWindow(server, urlWindowId)` to align tmux to the URL — `selectWindow` takes `(server, windowId)`, no session, since a window ID is a self-contained tmux target (and the backend `/select` handler derives the owning session for group disambiguation; see `architecture.md` § API Layer). Guarded by `hasAlignedToUrlRef: useRef(false)` keyed on the `${server}|${windowParam}` key (window-id-only — `$session` is not in the URL, so it is not part of the alignment key). Subsequent route changes to the same window never re-fire alignment. This supports reload (URL=active is a no-op) and deep-link (URL≠active aligns tmux, then yanks any other tabs on the same server per multi-client convergence). Since the compared identifier is the stable `@N`, a reorder/kill that shifts indices never spuriously triggers re-alignment.

2. **URL writeback (continuous)**. A separate effect watches the SSE-derived `activeWindow` and calls `navigate({ replace: true, to: "/$server/$window", params: { server, window: activeWindow.windowId } })` whenever `activeWindow.windowId !== windowParam`. The writeback writes the **window id only** — there is no `session` param to write. No debounce — tmux truth wins always. The effect skips when `dialogOpenRef.current === true` to avoid focus-stealing re-renders mid-dialog (this gates the URL writeback only, not the underlying SSE-derived selection). Comparing `windowId` (not `String(index)`) means an index shift from reorder produces no phantom writeback navigation to a different window. (`260529-chgz`, `260529-jad6`)

3. **Server-switch window resolution**. A per-server client-side memory records the window the user last viewed: an effect in `app.tsx` keyed on `[server, windowParam]` writes `runkit-last-window:{server}` (the value is the canonical `@N` window id — the URL-segment `N` form stays a `lib/router-url.ts` codec concern; reads/writes are try/catch-noop like every `runkit-*` preference key) on EVERY arrival path to a window — sidebar click, palette, deep link, board hop, and the contract-2 writeback itself. Recording is write-only: it navigates nothing and touches neither `hasAlignedToUrlRef` nor `pendingClickRef`; nothing is written on bare `/$server`, leaving any stored value intact. The three server-switch entry points — the sidebar server tile (`sidebar/index.tsx` `handleSwitchServer`), the palette `Server: Switch to {name}` entry (`app.tsx` `handleSwitchServer`), and the Host-page TMUX SERVERS tile (`host-overview-page.tsx`) — resolve a landing window through the shared pure `resolveServerLandingWindow` (`lib/last-window-per-server.ts`) and navigate to `/$server/$window` with a history PUSH (a user-initiated switch, retraced by the top-bar ◀ ▶ arrows), clearing any carried-over layout `search` param so the target window renders its own shared `@rk_win_layout`. Resolution order: the remembered window, validated against the target server's live snapshot — accepted OPTIMISTICALLY when that snapshot is empty (only attached servers stream windows, so empty means "not yet known", not "no windows"; a stale id self-heals via `SurfaceLayout`'s `onSessionNotFound` bounce to `/$server`) — then the derived fallback (the first session in the effective session order from `deriveEffectiveSessionOrder`, that session's `isActiveWindow` window, else its `windows[0]`), then bare `/$server` when nothing resolves. Bare `/$server` stays the session-tiles overview for every NON-switch path — the breadcrumb server crumb (a plain `<a href="/$server">`), the palette `Go: tmux Server`, every kill/not-found redirect, and server creation — none of them consult the resolver. The switch itself fires no `selectWindow`: landing on `/$server/$window` re-arms `hasAlignedToUrlRef` (it re-arms on every `windowParam` change), so tmux realignment rides contract 1 exactly as history Back/Forward already does. (260818-54lp-restore-window-on-server-switch)

**Sidebar clicks navigate optimistically AND mutate.** `navigateToWindow(windowId)` in `app.tsx` runs a `runSwitch()` body that fires an optimistic `navigate({ to: "/$server/$window", params: { server, window: windowId }, search: {} })` *and then* calls `selectWindow(server, windowId)` to bring tmux into agreement. This navigate **pushes** — a user-initiated window switch IS a navigation, so every switch routed through `navigateToWindow` (sidebar click, window-switcher ▾, command palette, keyboard shortcut, spawn-agent same-server branch) creates a distinct browser-history entry the top-bar ◀ ▶ arrows can retrace (see § Chrome → Browser-history arrows). **No dedup on distinct hops** — `w1→w5→w1` pushes three entries and Back retraces every hop (explicit no-dedup requirement). One early-return guard is NOT a history dedup: `navigateToWindow` early-outs when the target is a **redundant no-op** — BOTH the URL window AND tmux's active window (`isRedundantSwitch(windowId, windowParamRef.current, activeWindowRef.current?.windowId)` — a mobile-drawer dismissal tap, the palette's `"(current)"` entry). Such a click can change nothing (tmux emits no bytes, the event-driven SSE snapshot never re-confirms), so arming the pending-switch machinery would guarantee a spurious spinner mask at 300ms plus a false failure toast at 5s over the very terminal the user is on; the early-out keeps only the ergonomic drawer close. A genuine `w1→w5→w1` still pushes duplicates (each hop IS a real switch); only the degenerate self-click is inert. The two tmux/preference-driven navigates that MUST stay `replace: true` are the SSE URL-writeback effect (contract 2 above — tmux corrections aren't user intent, pushing would fight the Back button) and `switchView` (§ Window-View Lens — per-viewer lens toggles must not step through Back); `runSwitch` alone pushes. The optimistic navigate is what makes the terminal render immediately (including the first click from the `SessionTiles` density view and cross-session clicks the SSE writeback alone can't express); `pendingClickRef` suppresses the writeback's bounce-back until the SSE snapshot confirms the switch (typically sub-500ms with the tmuxctl control-mode subscription; see `architecture.md` § tmux Control-Mode Subscription). **SSE confirm is the PRIMARY, event-driven clear** — the resolved `selectWindow` POST is a parallel confirmation source that disarms ONLY the failure detector: a 200 whose `activeWindow` matches the pending target (or is absent — older daemon) cancels the switch's bounce timer while the intent itself clears via SSE (260823-ke9i). A single per-switch `CONFIRMATION_WINDOW_MS` (5s) failure-bounce timer BACKSTOPS the SSE clear, freshness-gated on the per-server receipt tick (`getServerReceiptTick` in session-context — a monotonic, ref-backed counter bumped on every server event + ack snapshot; see `architecture.md` § `session-context.tsx` transport): on expiry with no post-click evidence or a disconnected socket the timer re-arms (extend-until-evidence — a frozen pre-click snapshot can never render a failure), and only fresh post-click evidence showing a DIFFERENT window active — or an explicit POST rejection, fresh contradiction evidence that bounces immediately (while disconnected, re-arm still wins) — clears the intent, bounces the URL/heading to tmux truth, and shows a failure toast (§ Window-Switch Slide Transition → Confirmation-gated motion). This timer fires ONLY on fresh-evidence non-confirmation to un-stick a silent-failure limbo — never to prefer the click over an external event. Server-side overrides during a click (another agent or hook calling `tmux select-window` concurrently) resolve to whichever mutation tmux processed last — the confirmation timer does not contest a genuine external switch (SSE confirming ANY active window clears the intent). On mobile, `runSwitch` additionally closes the overlay sidebar after a destination tap. **Timing caveat:** on an *instant/fallback* switch — no View Transitions support, reduced motion, no outgoing window, or an unresolvable direction — `runSwitch` executes synchronously at click time. On an *animated* same-server switch the body runs INSIDE `document.startViewTransition`'s async callback, i.e. **≥1 frame after the click** (the browser first captures the outgoing snapshot, then invokes the callback); "navigate at click time" is precise only on the instant path; see § Window-Switch Slide Transition. (`260703-l4nf`, `260715-m4xy`, `260715-38kg`, `260823-ke9i`)

**Keyboard switch path via the command palette.** The window-switch path is also surfaced as `Window: Switch to <session> › <name>` palette entries — the `windowSwitchActions` useMemo in `app.tsx`, one entry per window across **every** session (built from `flatWindows`, the current server's merged sessions — not cross-server). Each entry reuses `navigateToWindow(fw.window.windowId)`, so it inherits the same `selectWindow` + URL-writeback + mobile-close + `pendingClickRef` suppression as a sidebar click — no separate `selectWindow` plumbing. The URL-active window (`fw.window.windowId === windowParam`) gets a `" (current)"` suffix, mirroring `Server: Switch to <name> (current)`. The `›` separator is U+203A (single right-pointing angle quote) for `<session> › <name>` palette labels. The block composes last in `paletteActions` (see § Boards Command Palette). (260613-o20f)

**Click-intent and URL-match key on `{server, @N}` — never the session name.** `pendingClickRef` is a `PendingSwitchTarget = { server: string; windowId: string }` (`src/lib/window-transition.ts`). Every consumer compares BOTH fields via the pure exported `isSamePendingTarget(pending, server, windowId)`: the writeback's `urlMatchesPending` is `isSamePendingTarget(pending, server, windowParam)` and `sseConfirmed` is `isSamePendingTarget(pending, server, activeWindow.windowId)`; the mount-alignment skip and `bouncePendingSwitch`'s guards use it too. See § Design Decisions → Pending-switch identity is `{server, @N}` for why the key excludes the session name and includes the server. (`260529-jad6`, `260715-38kg`)

**Sidebar selection follows the URL window ID, falling back to `isActiveWindow`.** `WindowRow.isSelected` derives from `currentSessionName === session.name && (hasUrlWindow ? currentWindowId === win.windowId : (!ghost && win.isActiveWindow))` in `app/frontend/src/components/sidebar/index.tsx`, where `hasUrlWindow = currentWindowId != null` and `currentWindowId` is the URL's `@N` window ID. When the route carries a window ID (the normal terminal-route case), selection is the stable `currentWindowId === win.windowId` comparison. The `isActiveWindow` term (set by the backend `WindowInfo.IsActiveWindow` from tmux's `#{window_active}`) drives selection only when no URL window is present — e.g., the dashboard route, or before the first navigation resolves. Because the URL window ID is written back from `isActiveWindow` (see contract 2 above), the two stay in lockstep with `tmux select-window` (external switches, `rk riff` window creation) without an index↔ID seam. Ghost windows (mid-creation, before the SSE snapshot includes them) match only via the `!ghost && win.isActiveWindow` fallback path when no URL window applies.

### Multi-Client Convergence

All clients viewing the same server's window route converge on the same window — the per-server invariant. When the SSE `event: sessions` payload changes which window is `isActiveWindow` for the currently-viewed session, every browser tab on `?server=<same>` and viewing `/$server/$window` navigates to the new window's `windowId` via `navigate({ replace: true })` (the URL writeback effect above).

Clients viewing `/board/$name` SHALL NOT navigate — the board route does not subscribe its URL to `isActiveWindow`. The SSE payload still arrives and `BoardPane` rendering still receives the updated `isActiveWindow` data; the route stays put.

Clients viewing different `?server=` values are independent — each server's SSE stream drives its own clients. Cross-server tabs never yank each other.

**Stale-URL tab yanks other tabs on mount**: when a new tab opens at `/$server/@7` while existing tabs are on `/$server/@2` (tmux active is window `@2`), the new tab's mount-time alignment fires `selectWindow(server, "@7")`. The resulting SSE snapshot then yanks every existing tab on that server to window `@7` via the writeback effect. This is intentional — the new tab represents user intent to view that window, and existing tabs collectively reflect "what tmux is now doing." A URL whose `@N` no longer exists on the server simply fails to resolve a current window (no nearest-index arithmetic) — see § Kill-redirect.

## Live Safe-Name Conversion

Every naming entry point converts a user-typed name to its safe/canonical form **live, in the input's `onChange`** — the user watches "My problem" become "My_problem" as they type (WYSIWYG), so the optimistic-update name is identical to the committed name. The conversion is **per name kind**, sourced from the shared pure module `app/frontend/src/lib/names.ts` (the established `src/lib/*.ts` + colocated `*.test.ts` home for shared pure logic), which exports one transform per kind plus a commit finisher:

| Export | Rule |
|--------|------|
| `toSafeSessionName(raw)` | spaces, **hyphens**, colons, periods, and the backend forbidden set (`; & | ` backtick ` $ ( ) { } [ ] < > ! # * ?` + control chars) → `_`; collapse `_` runs; strip leading `_`; **preserve case**; cap 128 (`MaxNameLength`). Hyphen→`_` is session-specific (session-group collision avoidance). |
| `toSafeWindowName(raw)` | same as session but **keeps hyphens** — `riff-*` windows use them legitimately and the group-collision rationale does not apply. |
| `toSafeServerName(raw)` | anything outside `[a-zA-Z0-9_-]` → `_`; collapse; strip leading `_`; cap 64 (`MaxServerNameLength`). Matches backend `ValidateServerName`. |
| `toSafeWorktreeName(raw)` | the window rule plus `/`→`_` and a leading `-` dropped (matching `ValidateWorktreeName`). |
| `finalizeSafeName(name)` | commit-time finisher — strips leading **and trailing** `_` runs. |
| `deriveNameFromPath(p)` | path-derived session-name suggestion — extracts the last path segment, composes the session transform + `finalizeSafeName` (both ends trimmed). |

Case is preserved ("My problem" → "My_problem", never lowercased). Chars outside a kind's unsafe set (e.g. `@`, `%`, `+` for session/window names) pass through unchanged — this is conversion, not stripping.

**Live-typing edges** (§ Design Decisions → Live transform + commit finalizer split): the live `onChange` transform strips **leading** unsafe chars as typed (a space pressed in an empty field produces nothing) and collapses `_` runs live, but a **trailing** `_` stays visible while typing — trimming it live would delete the separator the user just typed ("My " + "p" would become "Myp"). Commit/submit sites run `finalizeSafeName` to trim the trailing `_`. An input that is empty after conversion falls through to the existing empty-name submit guards — no new error surface. There is no caret-position management beyond React-controlled-input defaults; a mid-string length-changing edit may move the caret to the end (an accepted edge).

**Wired entry points** (each applies the kind's transform in `onChange` and `finalizeSafeName` at commit):

|---------|------|------|

| Session rename dialog input | `app.tsx` (state in `use-dialog-state.ts`) | session |
| Sidebar inline session rename | `sidebar/session-row.tsx` | session |

| "New iframe window" name field | `app.tsx` (`handleCreateIframeWindow`) | window |

## Session Creation Pattern

### Instant Creation (sidebar + tiles)

The pointer-driven `+` entry points create a session immediately without any prompt. Implemented by `executeCreateSessionInstant` in `app.tsx`.

**Algorithm**:
1. Derive a name from the active window's `worktreePath` using `deriveNameFromPath(worktreePath)` (from the shared `@/lib/names` module — § Live Safe-Name Conversion). If the result is empty (CWD is `/`, `~`, or `worktreePath` is undefined), the name is `session`.
2. Deduplicate against `sessions`: if the name is taken, try `{name}-2`, `{name}-3`, … up to `{name}-10`. If all are taken, use `{name}-11` (best-effort).
3. Call `createSession(server, derivedName, worktreePath)`. If no active window exists, call `createSession(server, "session")` (no `cwd` — tmux defaults to server CWD).
4. The session appears in the sidebar via the existing optimistic/ghost mechanism.

**Entry points** (all call `onCreateSession` → `executeCreateSessionInstant`):
- Sidebar `+` button (session level)
- Sidebar empty-state `+ New Session` button
- `SessionTiles` "+ New Session" dashed-border tile (the density view on `/$server`)
- Sidebar server-group-header `+` ("New session on {server}")

### Prompted Creation (`Session: Create` — chord + palette)

The `create-session` chord and the palette `Session: Create` action (one flow, two entry points — the chord resolves through the palette body via `fromPalette`) open `SessionNamePrompt` (`components/session-name-prompt.tsx`, lazy + Suspense on the shared `Dialog` shell): a single name input **pre-filled with the exact name instant creation would use** (the § Instant Creation algorithm, computed at open time from the freshest-value refs) and select-all'd — Enter accepts the default (instant creation plus one keystroke, the Cmd-S/save-as model), typing replaces it (live `toSafeSessionName` conversion, `finalizeSafeName` at submit), Escape/backdrop cancels. An empty or colliding name blocks submit (inline collision hint, the `CreateSessionDialog` pattern). Submit calls the same `executeCreateSessionInstant(server, name, cwd)` optimistic path (ghost, rollback, toast) with the same `currentWindow?.worktreePath || undefined` cwd, guarded by `isSessionCreatePending`; the prompt's open state folds into `dialogOpenRef`. The board route registers no `create-session` handler, so the chord falls through there. (260823-qe3n)

**Name derivation utilities**: `deriveNameFromPath` and the per-kind safe-name transforms live in the shared `app/frontend/src/lib/names.ts` module (§ Live Safe-Name Conversion), imported by `app.tsx` and every naming surface. Name conversion is split per kind (`toSafeSessionName`/`toSafeWindowName`/`toSafeServerName`/`toSafeWorktreeName`) — there is no single `toTmuxSafeName`.

### Folder-Prompted Creation (window-only, via Cmd+K)

One entry point opens `CreateSessionDialog` for a user who wants to specify a starting directory — **"Tab: Create at Folder"** (`create-window-at-folder`), which opens the dialog with `session={currentSession}` and the path input pre-filled with `currentWindow.worktreePath` (`defaultPath?: string`). Confirming calls `createWindow(server, session, undefined, cwd)` — **no name**, so tmux auto-names the window to the chosen folder's basename via `automatic-rename-format` (see [tmux-sessions](/run-kit/tmux-sessions.md) § Managed Window Creation). This flow sets no optimistic ghost, so there is no ghost label to derive. There is no session-level at-folder action: a session rooted elsewhere is created by prompt/instant create plus a `cd` in the pane. Dialog surface: [dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Window At-Folder Dialog. (260823-fe74)

### Unnamed `+ New Window` — Folder Auto-Naming

The `+ New Window` action does **not** pin the window name to `"zsh"` — it calls `createWindow` with **no name**, so tmux auto-names the window to its folder basename and live-updates it (the tmux-layer convention lives in [tmux-sessions](/run-kit/tmux-sessions.md) § Managed Window Creation). A hardcoded name would leave a sidebar full of windows as indistinguishable "zsh" rows. (260707-j66b)

**All three unnamed-window call sites:**

1. **Sidebar `+ New Window`** (`app.tsx`, the `create-window` "Window: Create" palette action) — `createWindow(srv, session, undefined, activeWin?.worktreePath)`. Its optimistic-ghost label becomes the **raw** (unsanitized) basename of the creation cwd via the local `rawBasename(cwd)` helper (falls back to `"window"` when no cwd). This is deliberately **NOT** `deriveNameFromPath` — that runs the session safe-name transform (`.`→`_` etc.), but tmux's `#{b:pane_current_path}` uses the unsanitized basename, so the ghost must match the raw form tmux will actually display.
2. **Palette "Tab: Create at Folder"** (`create-session-dialog.tsx`) — `createWindow(server, session, undefined, cwd)`; this flow sets **no** optimistic ghost, so no label is derived.
3. **Board-route `+ New Window`** (`board-page.tsx`) — `createWindowApi(srv, sess)` (no name, no cwd — the backend resolves a default; this action registers no ghost). Identical behavior to the same button on `/$server`.

**Client contract**: `createWindow(server, session, name?, cwd?, rkType?, rkUrl?)` in `api/client.ts` makes `name` optional and **omits it from the JSON body when absent/empty** (matching the existing omit-when-absent handling for `cwd`/`rkType`/`rkUrl`). Explicit names are still sent — the deliberate-name paths are unchanged: **iframe/service windows** (`Window: New Iframe Window`, `createWindow(..., name, undefined, "iframe", url)`), the `port-N` "Open in window" service windows (`server-list-page.tsx`), and `rk riff`.

**E2E** (`app/frontend/tests/e2e/new-window-unnamed.spec.ts`): asserts, via route interception on `POST /api/sessions/*/windows`, that the `+ New Window` request body carries **no `name` key** — a deterministic frontend→API seam. (The visual auto-rename is NOT asserted: the e2e tmux server is created with a bare `new-session` and `CreateWindow` never sources the config there, so `automatic-rename-format` isn't reliably applied on that server; the tmux-native naming is covered by the config + Go arg-builder tests instead.) (260707-j66b)

**Ghost TTL backstop** (`GHOST_WINDOW_TTL_MS = 15_000`, exported from `src/store/window-store.ts`): an optimistic ghost row is **claimed** only when a NEW windowId (one not in the ghost's `snapshotWindowIds`) arrives for its `(server, session)` via SSE (`setWindowsForSession`, oldest-ghost-first). Ordinary creates confirm within one SSE tick (~1-2s), and a *failed* create's caller rollback calls `removeGhost`. But if a create **succeeds somewhere else** — e.g. a tmux target ambiguity routes the window into a different session (exact-match session targets prevent this at the backend, see [tmux-sessions](/run-kit/tmux-sessions.md) § Exact-Match Session Targets) — no rollback fires and no claim ever arrives, stranding a permanently greyed, pulsing, unclickable row. `addGhostWindow` therefore arms a `setTimeout(() => get().removeGhost(optimisticId), GHOST_WINDOW_TTL_MS)`: the unclaimed ghost self-clears after 15s (comfortably past any legitimate claim). `removeGhost` is **idempotent** (filters by `optimisticId`), so a timer firing after the ghost was already claimed or rolled back is a no-op. This is a generic frontend backstop for the "no rollback, no claim" strand, independent of the backend root-cause fix. Two fake-timer unit tests cover TTL expiry and the claimed-ghost no-op. (260717-hikh)

## Instance Display Name

An optional per-instance display-name override lets a user label a run-kit instance ("dev mini") instead of showing its raw hostname. Stored host-side (`~/.config/run-kit/config.yaml` `instance_name`, see architecture/backend-packages § `internal/settings` and § `/api/settings`); empty means "derive from the hostname". Delivered frontend-side by **`InstanceNameProvider` / `useInstanceName()`** (`contexts/instance-name-context.tsx`), mounted once in `RootWrapper` beside `InstanceAccentProvider`.

The provider fetches `getHealth()` once on mount (StrictMode-guarded via a `didFetchRef`; `deduplicatedFetch` coalesces it with other same-tick `/api/health` consumers), owns the `{hostname, instanceName}` pair plus the optimistic `setInstanceName` write seam, and exposes `{ hostname, instanceName, displayName, setInstanceName }` where `displayName = instanceName ?? hostname`. `setInstanceName(name | null)` updates state optimistically then POSTs via `setInstanceName` client, toasting on write failure — so the settings-dialog edit repaints every consumer live and clearing the field reverts them to the hostname. This mirrors `InstanceAccentProvider` (fetch once, optimistic set, toast on failure).

**Three display surfaces prefer the display name** over the health-reported hostname: the browser tab title (`use-browser-title.ts` — `AppShell` consumes `useInstanceName().displayName` rather than fetching the hostname itself), the HOST panel hostname line (`sidebar/host-panel.tsx` — `instanceName ?? metrics.hostname`), and the host-overview HOST HEALTH hostname line (`host-overview-page.tsx` — `instanceName ?? hostMetrics.hostname`).

**Two surfaces deliberately keep the REAL hostname**, NOT the display name, and are NOT consumers of this provider: the instance-accent hash fallback (`instance-accent.ts` — renaming the instance must not silently change its color) and the SSH deeplink derivation (`open-in-app.ts` `resolveDeeplinkHost` — deeplinks need the reachable hostname, not a vanity label).

Every tmux session is a project — derived from tmux, no config file needed. Project root derived from window 0's `pane_current_path`.

Windows are `"active"` (last tmux activity within 10 seconds) or `"idle"`. No "exited" state.

## Chrome Architecture

**Lazy-loaded components**: `CommandPalette`, `ThemeSelector`, `CreateSessionDialog`, and `GuiSurface` are loaded via `React.lazy()` with dynamic `import()` (not static imports). Each uses `.then(m => ({ default: m.X }))` to re-wrap named exports for `React.lazy()` compatibility — except `GuiSurface`, which carries an `export default` so the lazy import needs no re-wrap. Render sites wrapped in per-component `<Suspense fallback={null}>` boundaries (the gui tile's fallback is the `code-surface-pending`-styled `opening…` state). These components are overlays/dialogs or heavy renderers that render conditionally — lazy loading keeps them out of the initial bundle for faster first paint; `GuiSurface` pulls in `@novnc/novnc@^1.7` (MPL-2.0 — file-level copyleft, compatible with bundling; the app's only MPL dependency), whose ~150 KB core is paid only by tabs that open a gui tile. noVNC ships no bundled `.d.ts`, so `app/frontend/src/types/novnc.d.ts` declares the `@novnc/novnc` module locally with exactly the RFB members the tile consumes — geometry comes from the gui state payload, never from noVNC internals; when the package upgrades, the typings file is re-derived against it (the local-typings rule for typeless deps).

**Shell wrapper (CSS Grid topology)** — `<Shell>` (`app/frontend/src/components/shell/shell.tsx`) is the shared chrome wrapper used by both `AppShell` and `BoardPage`. The shell is a single CSS Grid root carrying `height: 100%` — it fills the root layout's `flex-1` content region. The TopBar is NOT part of the Shell grid (260707-4vq2-lift-topbar-root-layout): it mounts once as `RootTopBar` in the persistent root layout, full-width above this Shell. The `--app-height` var (iOS keyboard handling) is maintained by `useVisualViewport()` in `RootWrapper` on the root layout div; Shell neither calls the hook nor reads the var. Desktop topology (`>= 640px`):

```
grid-template-areas:
  "sidebar content"
  "sidebar bottombar"
grid-template-rows:    1fr auto
grid-template-columns: ${sidebarWidth}px 1fr   (when sidebarOpen)
grid-template-columns: 0 1fr                   (when !sidebarOpen)
transition: grid-template-columns 150ms ease-out
```

Sidebar is full-height — it spans both rows and owns the entire left column. Content/bottombar stack in the right column. Sidebar collapse zeroes the first grid column (no 48px rail) — the content/bottombar cells extend their left edge to page.left automatically; no JS-side conditional rendering or component mutation.

The `sidebar` grid area is **Shell-owned**: on desktop `Shell` renders the `<aside style={{ gridArea: "sidebar" }} aria-label="Sidebar">` itself from its `sidebarChildren` prop, gated `!isMobile && sidebarOpen && !!sidebarChildren` (fully unmounts on collapse — no zero-width rail). Consumers place ONLY the `content` and `bottombar` grid areas; they never grid-area-place `sidebar`. The aside wraps `sidebarChildren` in a `flex-1 min-w-0 overflow-hidden` content wrapper and accepts an optional `sidebarResizeHandle?: ReactNode` slot rendered at its right edge — the desktop drag-resize handle. AppShell passes its handle through this slot; BoardPage passes none (drag-resize is intentionally absent on the board route). The aside carries `border-r border-border` ONLY when no handle is passed (BoardPage): with a handle the 3px handle bar is the visual seam, so a border would double it. Drag-resize wiring stays AppShell-only — all drag state/handlers (`handleDragHandlePointerDown`, width persistence, aria-value bounds) live in AppShell; the handle rides through the slot as an opaque node, so `Shell` stays dumb about drag logic. The mobile overlay never renders the handle. The handle is hidden when `sidebarOpen === false` (the only re-open affordance is the hamburger).

Mobile topology (`< 640px`): single column, `grid-template-areas: "content" / "bottombar"`. Sidebar renders as an overlay child of the Shell positioned via `gridRow: "1 / 3"` (spans content + bottombar, leaves the root-layout topbar above the Shell visible). Backdrop and `<aside>` use `position: absolute` (NOT `fixed inset-0`) so the overlay starts below the topbar — matches the existing project convention recorded in `fab/project/context.md`. The aside carries `role="dialog" aria-modal="true"`. Sidebar overlay open/close is driven by the same `sidebarOpen` state; `ChromeContext` carries no `drawerOpen`.

**Hamburger placement** — the hamburger icon is statically rendered at `TopBar.left` in both `sidebarOpen` states. Visual "relocation" on collapse is a side effect of the grid column collapsing; there is no component-level relocation logic. When `sidebarOpen === true`, the hamburger sits at the sidebar.right / topbar.left seam (pixel-identical to "attached to sidebar"). When `sidebarOpen === false`, it sits at page.left because the topbar grid cell has extended to page.left.

**Keyboard toggle** — `Cmd+\` (macOS) / `Ctrl+\` (Linux/Windows) toggles `sidebarOpen` from any route that mounts `<Shell>`. The chord is a `sidebar-toggle` builtin in the keybinding registry, so it is documented by the shortcuts overlay and per-device rebindable per Constitution V (Keyboard-First) — see [ui/keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Keyboard Shortcuts. The chord is suppressed when focus is inside a real text input/textarea/contenteditable, but NOT when focus is on xterm.js's helper textarea (recognized by `target.closest('.xterm') != null`) — without the xterm exception, the most common focus state would silently swallow the toggle.

**Sidebar width persistence** — width state lives in `ChromeContext` (`sidebarWidth`). The dispatch surface is split: `setSidebarWidth(width)` updates in-memory state only (called per-pointermove during drag), and `persistSidebarWidth(width)` writes `localStorage["runkit-sidebar-width"]` (called once at drag-end). This explicit split avoids localStorage thrash on every pointer event. Callers like the AppShell drag handler track the last-seen width in a ref (`dragLastWidthRef`) and call `persistSidebarWidth` once in `handleEnd`.

**Routing branches inside the `content` grid area**:
- AppShell (`/$server/$window`): `<SurfaceLayout>` — the resolved layout's 1–3 tiles, each mounting `<TerminalClient>` (tty) | `<IframeWindow>` (web) | `<CodeSurface>` (the lean code-server embed, code) — or `<SessionTiles>` when there is no window param. Tile selection follows the **resolved layout** (`resolveLayout`: URL `?layout=` > `rk-layout:` localStorage > default hint > `single:tty`, with tile-by-tile availability degradation), NOT `@rk_win_lens` identity; legacy `?view=`/`?panel=` deep links land through the translation shim; see `ui/lenses-and-layout.md` § Surface Layout and § Window Views (Lens Model). (260714-t97o-web-view-lens) (260811-k3vp-right-panel-code-lens) (260812-ab5v-surface-layout-core)
- BoardPage (`/board/$name`): `DesktopRow` / `MobileCarousel` body (the existing horizontal-scroll panes), flush with `sidebar.right` (no left gutter).

No `max-w-4xl` constraint — all zones span full width.

**ThemeProvider** (`app/frontend/src/contexts/theme-context.tsx`) — outermost provider. Split into ThemeStateContext (preference + resolved theme) and ThemeActionsContext (setTheme). Three modes: system, light, dark. Preference persisted to `localStorage` key `runkit-theme`. System mode listens to `matchMedia("(prefers-color-scheme: dark)")` change events. Theme applied via `data-theme` attribute on `<html>`. Blocking inline script in `index.html` `<head>` reads localStorage and sets `data-theme` before first paint (no-flicker initialization).

**ChromeProvider** (`app/frontend/src/contexts/chrome-context.tsx`) — split into two React contexts: `ChromeStateContext` (read-only state: `currentSession`, `currentWindow`, `sidebarOpen`, `sidebarWidth`, `isConnected`, `fixedWidth`) and `ChromeDispatchContext` (stable setter functions: `setCurrentSession`, `setCurrentWindow`, `setSidebarOpen` — persists to `localStorage["runkit-sidebar-open"]`, `setSidebarWidth` — in-memory only, `persistSidebarWidth(width)` — writes localStorage on drag-end, `setIsConnected`, `toggleFixedWidth`). There is no `drawerOpen`/`setDrawerOpen`: one `sidebarOpen` boolean covers both breakpoints, because the rendering form differs per breakpoint but the state does not (§ Design Decisions → Single `sidebarOpen` boolean). Chrome derives its content from the current selection — no slot injection, and no `setLine2Left`/`setLine2Right`/`setBottomBar`; top bar and bottom bar read the selection directly. `Breadcrumb` type includes optional `dropdownItems` for session/window switching.

**FocusedTerminalContext** (`app/frontend/src/contexts/focused-terminal-context.tsx`) — tracks the currently-focused terminal across the app so the shell-level `BottomBar` can target the right WebSocket regardless of route. Mounted in `RootWrapper` between `SessionProvider` and `OptimisticProvider`; provider tree order is `ThemeProvider > ChromeProvider > RootWrapper(SessionProvider > OptimisticProvider > FocusedTerminalProvider > Outlet)`. Shape:

```ts
type FocusedTerminal = {
  wsRef: React.RefObject<WebSocket | null>;
  server: string;
  session: string;
  windowIndex: string;
} | null;

type FocusedTerminalContextValue = {
  focused: FocusedTerminal;
  setFocused: (t: FocusedTerminal) => void;
};
```

Producers: `TerminalClient` registers on mount when its `registerFocus` prop is `true` (single-terminal route default) and clears on unmount. `BoardPane` registers when its `isFocused` prop becomes true (and on initial pane mount); it manages the registration itself and passes `registerFocus={false}` to its inner `TerminalClient` to avoid producer contention. `BoardPane` clears the focused terminal on **unmount** iff it is still the registered pane (ref-guarded still-mine check) so leaving a board for `/$server` does not strand a stale target; a pane-focus SWITCH does not unmount the losing pane, so the next pane to gain focus overwrites.

Consumers: the shell-level `BottomBar` reads `focused?.wsRef` (it takes no `wsRef` prop); the docked compose strip (`ComposeStrip`, § ui/compose-and-bottom-bar.md § Docked Compose Strip) reads `focused` live and sends to `focused.wsRef` at send time (the live-target model — no target frozen at open). When `focused === null` (e.g. the `/$server` tiles route), the strip renders disabled and BottomBar input handlers natural-no-op via the existing `wsRef.current?.readyState !== OPEN` guard. The docked-strip enablement is the persisted `composeStripEnabled` chrome preference (`ChromeContext`), not context state here.

**SessionProvider** (`app/frontend/src/contexts/session-context.tsx`) — root-mounted multi-server React Context. One `SessionProvider` instance lives above `<Outlet />` in `RootWrapper` and is shared by every route (`/`, `/$server/...`, `/board/$name`); it does NOT remount on server-route switches. State is keyed per server: `sessionsByServer: Map<string, ProjectSession[]>`, `sessionOrderByServer: Map<string, string[]>`, `isConnectedByServer: Map<string, boolean>`, `metricsByServer: Map<string, MetricsSnapshot | null>`. The `/` page component is `HostOverviewPage` (`host-overview-page.tsx`); the `top-bar` page-mode strings are `"host"` (`/`) and `"server"` (`/$server`). (260715-zs1y-host-tmux-server-rename) `currentServer: string | null` is dispatched from the matched route via `useMatches()` — `params.server` for `/$server/...`, `null` for `/board/$name` and `/`. Consumers read the per-server slice they need via `ctx.sessionsByServer.get(name)`. Provider tree order: `ThemeProvider > ChromeProvider > RootWrapper(SessionProvider > OptimisticProvider > Outlet)`. The provider also mirrors `currentServer`'s slice `isConnected` into `ChromeProvider`'s `isConnected` (an effect calling `setChromeConnected`); the sidebar footer dot reads its `isConnected` **prop** (§ ui/sidebar.md § Sidebar footer status row), so the mirror has no live reader. Persists most-recently active server to `localStorage` key `runkit-server` (single value, not split per server).

**State-socket transport** — the provider owns ONE `StateSocket` per tab (`src/lib/state-socket.ts`, § State Socket above) held in `socketRef`. The current server is auto-attached; non-current servers attach lazily via the `attachServer(name)` API exposed on context. The `attachedSet` drives a diff effect that `subscribeServer`/`unsubscribeServer`s (ref-counted on the socket); each subscribe `ack` updates only that server's slice. When a server disappears from `/api/servers` it is unsubscribed and its entries removed from every per-server map. A 3-second disconnect debounce runs per server, driven by socket-level connection-state changes — an `onerror` doesn't flip a still-acked server's `isConnectedByServer` until the debounce fires. `useBoards` and `useWindowPins` call `attachServer` for every known server when the sidebar mounts, costing nothing on the pool budget (one shared WS). (260716-qf3j-state-socket)

**`subscribeBoardChange`** (`session-context.tsx`) — context API that lets any consumer register a `(server: string) => void` handler and receive cross-server `board-changed` events through the one shared socket. `useBoards` and `useWindowPins` use it to react to per-server board mutations without opening their own connections — the state socket already streams `board-changed` (as `kind:"server"`), so multiplexing through one subscriber API keeps the wire-subscription count bounded.

**Server-independent host-metrics subscription + `useHostMetrics()`** (`session-context.tsx`; transport is the state socket's `metrics` subscription) (260701-vshd-cockpit-host-console-home) (260716-qf3j-state-socket) — a `subscribeMetrics()` on the shared socket (the in-band `kind:"metrics"` op, internally the retained `metricsOnlyServer` sentinel) that receives ONLY the server-independent `metrics`/`services` global events, so host health is available where there is no `currentServer` and no per-server subscription to carry it (the Host-page host-console home `/`; see ui/sidebar.md § HOST HEALTH Zone). It is **opened only when `attachedSet.size === 0`** (`hostMetricsWanted`) and dropped once any server attaches — the per-server subscription's `metrics` event already fans the same server-global payload into the shared `hostMetrics` state. The dedicated-stream mutual-exclusion holds, though not for pool-budget reasons: the one WebSocket holds no HTTP/1.1 pool slot at all (see § State Socket / ui/boards.md § Desktop Relay-Connection Suspension). A `metricsSubscribedRef` guard drives the subscribe/unsubscribe; the socket effect's cleanup resets it (+ `subscribedServersRef`/`ackedServersRef`) so a StrictMode remount re-subscribes on the fresh socket (§ State Socket → StrictMode safety). The parsed snapshot lands in provider state `hostMetrics` (`MetricsSnapshot | null`, `null` pre-tick) exposed via `HostMetricsContext` + the `useHostMetrics(): MetricsSnapshot | null` hook. **`useHostMetrics()` is NOT `currentServer`-gated** — unlike `useMetrics()` (which returns `currentServer ? metricsByServer.get(currentServer) : null`, hence `null` on `/`); both hooks use the same undefined-sentinel throw-outside-provider idiom. `useMetrics()` stays current-server-scoped, for `HostPanel`'s sidebar call site. Backend contract for the `metrics` subscription / `metricsOnlyServer` sentinel: see § State Socket + § API Layer `/ws/state`.

**Host-metrics health is not a context field.** The `metrics` subscription carries only the DATA (`hostMetrics`, via `useHostMetrics()`); there is no scalar health field for it on `SessionContextType`. Connection health reaches the UI per server via `isConnectedByServer` — the sidebar footer's dot derives its value at the caller (§ ui/sidebar.md § Sidebar footer status row) and routes without a mounted sidebar (Host `/`, a collapsed desktop sidebar, a closed mobile drawer) show no dot at all, which is the accepted tradeoff (§ ui/sidebar.md § Design Decisions → App-global actions live in the top bar). (260724-6j1v-sidebar-footer-chrome-settings)

**Kill-redirect gate (`currentWindowEverSeen`)** — The "session/window gone" redirect in `app/frontend/src/app.tsx` (around the `useEffect` that calls `computeKillRedirect` from `app/frontend/src/lib/navigation.ts`) MUST NOT fire for a freshly-navigated URL whose (session, window) pair has not yet been observed as valid in the SSE `sessions` stream. `computeKillRedirect` accepts a `currentWindowEverSeen?: boolean` param (defaults to `true` for legacy callers and unit tests) and short-circuits to `null` when false — bypassing both the "session gone → dashboard" and "window gone → nearest sibling" branches. The caller maintains two refs: `currentWindowEverSeenRef` (boolean, flipped `true` whenever the memoized `currentWindow` is non-null) and `lastObservedUrlKeyRef` (string, `${server}|${session}|${window}`). Any URL-key change resets the seen flag to `false`. This gates two transient SSE states that are not proof the URL is unreachable: (a) a stale cached first payload that replays an older server snapshot before delivering current data, and (b) a session whose `windows` array is briefly empty while tmux enumeration propagates into the next poll tick. Without the gate, either state makes `currentSession` or `currentWindow` null on the first SSE event after navigation, the redirect fires, and `TerminalClient` unmounts mid-initialization — surfacing as an e2e flake where `.xterm-screen` briefly appears then disappears. Genuine kills from another client still redirect normally, because the URL key only resets on navigation, not on SSE payload changes: once the seen flag is `true`, a subsequent payload that drops the window triggers the redirect as before.

**Window state (Zustand)** — window optimistic state is managed by a Zustand store at `app/frontend/src/store/window-store.ts`, keyed by the immutable tmux `windowId` (`@N`). `zustand` is a production dependency in `app/frontend/package.json`. ## Design Decisions

### A written note outranks the capture preview as the tile body
**Decision**: on the session-tiles density view, a window carrying a non-empty `@rk_win_note` renders the note (+ relative age, 24h stale dimming) as its tile body in place of the `capture-pane` preview; un-noted windows keep the preview unchanged, and the whole branch is render-only over payload fields that already ride SSE.
**Why**: the tile body answers "why is this tab here / what is it blocked on" — a written note answers exactly that where a raw terminal capture cannot; making notes visible on the monitoring-density view is what makes them worth writing. Degrade-to-absent keeps un-noted windows at zero behavior change, and render-only means no backend or preview-scope change.
**Rejected**: note as a second box below the preview (doubles tile height on a density view, and the capture is the weaker signal when a curated note exists); hiding the preview unconditionally (un-noted windows lose their only body).
*Introduced by*: 260827-8n6k-update-annotations-tile-note

### Live safe-name transform + commit finalizer split
**Decision**: The live `onChange` transform strips leading separators but keeps a trailing `_` visible; a separate `finalizeSafeName` trims leading+trailing `_` at commit. Name conversion happens live in the input (not silently at submit), per name kind, in one shared `src/lib/names.ts` module.
**Why**: Converting live gives WYSIWYG — the user sees exactly the name that will exist, so the optimistic-update name equals the committed name. Keeping the trailing `_` visible while typing is required so "My " + "p" does not collapse to "Myp" (trimming the trailing separator live would delete the separator the user just typed and break mid-word entry); commit-trim is the one minimal WYSIWYG deviation. One transform per kind in `src/lib/` (the shared-pure-logic home) keeps every entry point on one canonical rule with colocated Vitest coverage.
**Rejected**: (a) backend-side conversion — breaks WYSIWYG and optimistic-update parity (the backend stays reject-only, constitution §I); (b) submit-time silent conversion — the user commits a name they never saw; (c) keeping reject-only frontend errors (the old server-name UX) — explicitly the experience this moves away from; (d) strict-WYSIWYG commit (trailing `_` included) — leaves awkward trailing separators for no benefit.
*Introduced by*: 260722-ln4n-auto-safe-name-conversion

### Route guard keys on `serversLoaded`, not `servers.length > 0`
**Decision**: `resolveServerView`'s not-found branch gates on the explicit `serversLoaded` flag, never the `servers.length > 0` proxy.
**Why**: with pre-existing servers the length proxy is already truthy while the list is stale, so the guard fired not-found immediately for a just-created server before the post-create refresh landed. The explicit flag distinguishes "list has loaded" from "list is non-empty".
**Rejected**: `servers.length > 0` as a loaded-proxy — the root-cause bug of the create-server not-found race.
*Introduced by*: 260602-3i5d-fix-create-server-not-found-race

### Pointer creates are instant; `Session: Create` is a prefilled prompt, never a bare form
**Decision**: The sidebar/tiles `+` buttons create instantly via `executeCreateSessionInstant`; the `Session: Create` chord/palette flow opens `SessionNamePrompt` pre-filled with the exact derived name, select-all'd, so Enter reproduces the instant outcome and typing names the session at creation (§ Prompted Creation). `use-dialog-state.ts` still exposes no create-dialog API, and `CreateSessionDialog` is window-only, reachable solely from the "Tab: Create at Folder" palette action.
**Why**: The keyboard flow is where an explicit name is wanted — a prefilled prompt makes naming first-class at the cost of one Enter on the default path, without spending a second chord on a named-session variant (the Cmd-S/save-as model). The pointer `+` buttons stay zero-friction because the active window's `worktreePath` already implies name and cwd, and the optimistic ghost gives immediate feedback.
**Rejected**: A separate "Create session with name…" binding (a scarce keycap on a variant of an existing action); an empty-field dialog on the primary path (prompts for what the app can derive — the prefill keeps the derivation as the default).
*Introduced by*: 260823-qe3n-new-session-inline-name-prompt

### Universal stage is a nested grid; the status bar stays outside it
**Decision**: Shell's desktop grid is outer rows `"stage" / "statusbar"` with the stage a nested grid (`bg-bg-inset p-[6px]` + 6px column-gap, NO row-gap — the bottombar footer owns a content-gated `has-[>*]:mt-[6px]` seam instead (260815-g08a); columns `${sidebarWidth}px 1fr` / `0 1fr`, areas `"sidebar content" / "sidebar bottombar"`) holding the sidebar card, content, and bottombar; the statusbar row stays a direct outer-grid child.
**Why**: grid padding/gap apply to the whole grid — padding on the outer grid would inset the status bar from the viewport edges and gap would open seams around it, but the status bar must stay full-width flush attached chrome; nesting scopes the inset ground to exactly the region that floats cards, and the sidebar column keeps its width-collapse transition inside the stage.
**Rejected**: padding/gap on the outer grid (insets the status bar — breaks the attached-frame contract); a content-column-only stage wrapper with the sidebar attached outside it (the sidebar card would sit on the default background, not the shared ground).
*Introduced by*: 260815-19me-composed-frame-unification

### Server-switch landing uses a remembered position, not a tmux-derived pick
**Decision**: The primary landing signal for a server switch is the client-side per-server record of the window the user last viewed (`runkit-last-window:{server}`), with a session-order-derived pick only as fallback.
**Why**: A tmux server holds many sessions and `isActiveWindow` is scoped per session (at most one per session), so tmux can answer "the active window of session X" but not "the session the user was last in" — the signals that would (`session_activity`, `session_last_attached`) are not in the sessions format string and are absent from `SessionInfo` / `ProjectSession` / `types.ts`. Remembering client-side answers the user's actual complaint ("the window I was on"), needs no backend surface, and degrades to a derived pick when nothing is stored.
**Rejected**: Extending the backend to fetch `session_last_attached` — three type definitions, a format string, and a positional parse changed to serve a client-side navigation preference, and it still answers "last attached by any client on the host", not "where this browser was".
*Introduced by*: 260818-54lp-restore-window-on-server-switch

### Switch window resolution is scoped to the switch entry points, not the `/$server` route
**Decision**: The three switch call sites resolve a landing window; `/$server` renders the session-tiles overview for every other path.
**Why**: The overview is the multi-agent monitoring density view — a deliberate surface with its own purpose. A route-level redirect would delete it. Scoping to the switch action fixes the reported friction while leaving the URL as an explicit way to ask for the overview, so nothing becomes unreachable.
**Rejected**: A `beforeLoad` redirect or an `AppShell` effect on `serverIndexRoute` — a smaller diff, but it removes the overview entirely and would also hijack the kill/not-found redirects, which must keep landing on `/$server`.
*Introduced by*: 260818-54lp-restore-window-on-server-switch

### Optimistic navigation when the target server's stream has not attached
**Decision**: When a remembered window exists but the target server's session snapshot is empty, the switch navigates to it without validation.
**Why**: Only attached servers have their windows streamed, so an empty snapshot means "not yet known", not "no windows". Refusing to navigate would make the feature fail exactly on the first switch to a server — its most common case. A stale id is already self-healing: `SurfaceLayout`'s `onSessionNotFound` bounces to `/$server`.
**Rejected**: Blocking on a loaded snapshot (the feature silently does nothing on the common path), and pre-fetching the target server's sessions before navigating (a fetch on the critical path of every switch, for a preference).
*Introduced by*: 260818-54lp-restore-window-on-server-switch

### The dashboard rides SessionTiles' scroll container via a footer slot
**Decision**: `SessionTiles` takes `footer?: ReactNode` rendered after the grid inside its `overflow-y-auto` div; `app.tsx` passes the clock dashboard there.
**Why**: the page's layout rule is "only the tile area scrolls"; a sibling below `SessionTiles` would either create a second scroll region or shrink the grid's scroll box. A slot keeps one scroll container and one owner of the padding.
**Rejected**: rendering the dashboard inside `SessionTiles` directly (couples the tiles component to cron props); a sibling column below the tiles (two scroll regions).
*Introduced by*: 260910-1rx0-server-page-clock-dashboard

### One `useCronData` call, owned by app.tsx
**Decision**: the dashboard receives `cronData` as a prop from app.tsx's existing `useCronData(server)` call rather than calling the hook itself.
**Why**: app.tsx already holds the response for the palette's `cronActions`; a second hook instance would double every fetch on the sessions cadence for the same server.
**Rejected**: a second `useCronData` at the dashboard root (duplicates network work with no benefit).
*Introduced by*: 260910-1rx0-server-page-clock-dashboard

### Shared cron mutation handlers between palette and dashboard
**Decision**: app.tsx builds one memoized `cronHandlers = { onCreate, onMute, onPin, onDelete }` consumed by both `buildCronActions` and the dashboard.
**Why**: the delete-confirm dialog and the toast-on-error posture already exist for the palette; sharing the object keeps one delete-confirm path and one error surface.
**Rejected**: the dashboard calling `muteCron`/`pinCron`/`deleteCron` itself (a second delete-confirm or an unconfirmed delete).
*Introduced by*: 260910-1rx0-server-page-clock-dashboard

### Held state is client-resolved from shipped facts
**Decision**: `held (busy)` derives from `deliver: when-idle` + past-due `nextFire` + the client-resolved target window's `agentState ∈ {active, waiting}`.
**Why**: the `when-idle` busy predicate is documented as `active | waiting` and every input already rides the payloads; no backend field is needed for the common role/session/pane targets.
**Rejected**: a `heldReason` backend field (out of scope by intake); omitting the held state entirely (the registry's most useful state-column arm would stay empty).
*Introduced by*: 260910-1rx0-server-page-clock-dashboard

### Derived chrome (not slot injection)
**Decision**: top bar and bottom bar derive content from the current session:window selection. No `setLine2Left`/`setLine2Right`/`setBottomBar` setters. Split React Context preserved for performance (state vs dispatch).
**Why**: the single-view model means only one chrome state (terminal-focused).

### Single-view layout (sidebar + terminal/dashboard)
**Decision**: the terminal is the main content on `/:session/:window`; the Dashboard renders on `/`. No page transitions. Dashboard and Project page functionality is subsumed by the sidebar + Dashboard view.
**Rejected**: three separate pages (Dashboard, Project, Terminal).

### Dashboard as inline component in app.tsx (not separate route layout)
**Decision**: the Dashboard renders in the terminal area via a conditional branch (`sessionName && windowIndex ? <TerminalClient/> : <Dashboard/>`).
**Why**: reuses the existing chrome skeleton (top bar, sidebar) and avoids duplicating the app shell layout.
**Rejected**: a separate route with dedicated layout — would require lifting sidebar/chrome into a shared layout component and restructuring the route tree.

### Sidebar + drawer pattern on mobile
**Decision**: the desktop sidebar is drag-resizable (default 220px, min 160, max 400, localStorage persist), collapsible. Mobile (< 768px) uses a left-side drawer overlay triggered by `☰`.
**Why**: preserves the session/window tree layout across breakpoints.

### Active window sync — tmux truth, URL as bookmark
**Decision**: tmux is the sole source of truth for "current window" per server. The URL is a resumable bookmark used only on mount (and reload); after mount it is derived state, rewritten by an SSE-driven `navigate({ replace: true })` whenever the server-reported `isActiveWindow` differs from the URL. Mount-time alignment fires exactly one `selectWindow` to align tmux to a deep-linked URL (gated by `hasAlignedToUrlRef`). All clients on the same server converge ("yank" semantics) — cross-server tabs stay independent. Sidebar clicks are pure mutations (`selectWindow` only); no client-side timer or debounce. Push channel is tmux control mode (`tmux -CC`) via the `internal/tmuxctl/` package; primary latency target sub-500ms, with a 12-second safety-net poll as backstop. Board cleanup tracks control-mode latency.
**Why**: there is no client-owned selection state to protect, so a debounce (such as a 3-second `userNavTimestampRef`) must not be added.
**Rejected**: per-tab current window (reintroduces a second writer, doesn't match the dashboard model); hooks + `rk notify` + lockfile (incompatible with PR #197's Constitution §II Non-Goal); a client-side navigation debounce.
*Introduced by*: 260528-nvlp-active-window-sync

### `isActiveWindow` is event-derived per session group
**Decision**: the `isActiveWindow` that drives the URL writeback is derived two-tier per session group — event-tracked `@wid` authoritative, base `#{window_active}` as cold-start/reconnect fallback — not read from the base session pointer alone. The derivation lives entirely in the read path — neither a creator nor the ephemeral model is involved, and the frontend writeback is unchanged. See § Active-Window Event Derivation.
**Why**: the base pointer goes stale when an `rk-relay-*` ephemeral / `rk riff` / external `new-window` moves the active window (group members keep independent pointers), so reading it alone lags the highlight.
*Introduced by*: 260530-v6hm-active-window-event-derivation

### `currentWindowEverSeen` gate on kill-redirect over unconditional "gone → redirect"
**Decision**: the redirect in `app.tsx` that fires when `currentSession` or `currentWindow` is null is gated by a ref keyed on `${server}|${session}|${window}`, flipped true the first time `currentWindow` resolves non-null, reset on URL change — deferring the redirect until the URL target has been observed as valid at least once.
**Why**: the first SSE payload after a navigation is not authoritative: the SSE hub can replay a cached snapshot before delivering fresh data, and tmux window-list enumeration can lag by one poll tick when a session was just created. Unconditionally redirecting on either transient state tears down `TerminalClient` mid-mount. The gate preserves fast-redirect behavior for genuine kills (the seen flag stays true after the first valid observation) while eliminating the startup race.
**Rejected**: inspecting SSE payload identity or delaying `isConnected` (both push complexity into the hub layer and would not distinguish real kills from stale catch-up); a fixed startup debounce (arbitrary delay, races with fast tests).
*Introduced by*: 260417-g9uo-mobile-tap-focus-regression

### CSS Grid topology for the rotated shell over nested flex
**Decision**: Grid encodes the topology directly via `grid-template-areas: "sidebar topbar" "sidebar content" "sidebar bottombar"`; collapse is a one-line column-width change (`${sidebarWidth}px 1fr` ↔ `0 1fr`) animatable as a single `grid-template-columns` transition.
**Why**: the shell rotation makes the sidebar a column that spans all three rows (topbar, content, bottombar). Expressing "sidebar full-height; right column is a 3-row stack" with nested flex requires either a sibling sidebar with explicit height management plus a flex-col right column, or a 2-row layout with sidebar nested inside row 1 — neither matches the visual model and both diverge as future cells are added. Modern browsers (Safari 14+, Chrome 100+) animate `grid-template-columns` reliably.
**Rejected**: nested flex.
*Introduced by*: 260509-17m3-rotated-shell-layout

### Sidebar collapses to 0px, not a 48px rail
**Decision**: collapse zeroes the sidebar column, giving maximum content width when collapsed and accepting a small visual layout shift on toggle (the hamburger appears to "move" from sidebar-adjacent to page-adjacent, though structurally it always lives at TopBar.left — see the next decision).
**Rejected**: a 48px icon rail (VS Code/Linear/Slack convention) — avoids the visual relocation but consumes content width for a usability gain that diverges from the user's stated preference for max content width.
*Introduced by*: 260509-17m3-rotated-shell-layout

### Single `sidebarOpen` boolean over `sidebarOpen + drawerOpen`
**Decision**: the user's intent ("show me the sidebar") is one boolean; the renderer picks the form (grid column vs absolute overlay) by viewport width.
**Why**: the distinction between "sidebar open on desktop" and "drawer open on mobile" is a rendering-form difference, not a state difference. One boolean simplifies persistence (one localStorage key, `runkit-sidebar-open`), removes a class of "they're out of sync" bugs, and makes the keyboard chord a single state mutation.
**Rejected**: two booleans — preserves a historical artifact at the cost of doubled persistence/reset logic and a confusing surface for new contributors.
*Introduced by*: 260509-17m3-rotated-shell-layout

### `<Shell>` as a shared wrapper over per-route shell components
**Decision**: a single `<Shell>` (`src/components/shell/shell.tsx`) lets both AppShell and BoardPage consume a uniform topology; collapse animation, mobile overlay, and the topbar/content/bottombar geometry stay in one place. `Shell` renders the desktop `sidebar` grid area itself (from `sidebarChildren` + optional `sidebarResizeHandle`); consumers place only the `content`/`bottombar` grid areas via `style={{ gridArea: "content" | "bottombar" }}` elements. Pattern note: future routes that need the same chrome should adopt `<Shell>` rather than reimplementing the grid.
**Why**: both routes need the identical 3-row × 2-column grid, sidebar collapse, mobile overlay, and visual-viewport handling.
**Rejected**: per-route shell components — guaranteed to diverge over time (different collapse timings, drift in mobile overlay handling), defeats the rotation's "one topology, many routes" goal.
*Introduced by*: 260509-17m3-rotated-shell-layout

### `Shell` owns the desktop sidebar aside; the resize handle rides an opaque node slot
**Decision**: `Shell` renders the desktop `<aside style={{ gridArea: "sidebar" }} aria-label="Sidebar">` (gated `!isMobile && sidebarOpen && !!sidebarChildren`) and exposes an optional `sidebarResizeHandle?: ReactNode` rendered at the aside's right edge; `border-r border-border` is applied only when no handle is passed. The one per-caller divergence — AppShell's drag handle — rides through the opaque slot, so all drag state/handlers stay in AppShell and Shell stays dumb about drag logic.
**Why**: per-consumer copies of the aside scaffolding, the grid-area placement, and the `!isMobile && sidebarOpen` gate drift (an AppShell flex-row + drag handle vs a BoardPage border-r + a different `aria-label="board sidebar"`). Shell already reads `sidebarOpen`/`isMobile`, so the branch lives there with zero new data dependencies, and the uniform `aria-label="Sidebar"` gives AppShell's aside an accessible name.
**Rejected**: a render-prop (`sidebar={(ctx) => …}`) — no caller needs Shell-provided context, so a plain node prop is simpler; Shell owning the drag handle — it would pull `handleDragStart`/width persistence into Shell and couple it to AppShell-only state.
*Introduced by*: 260719-rwqf-shell-sidebar-slot

### `FocusedTerminalContext` as a separate, dedicated context (not a slice of ChromeContext)
**Decision**: a small dedicated context with its own provider (`FocusedTerminalProvider` mounted in `RootWrapper`) carries only `focused`/`setFocused`; only the shell-level BottomBar and the docked `ComposeStrip` read `focused` from it. The compose surface's enablement is a persisted `composeStripEnabled` chrome preference, and the strip reads `focused.wsRef` LIVE at send time (a live target following pane focus, mitigated by an always-visible `→ {window}` label). Pattern note: future multi-input UIs that need a single shared input target should follow this "lift focused-input target to context" pattern rather than prop-drilling.
**Why**: the shell-level BottomBar needs a way to target the focused terminal regardless of route. Folding the focused-terminal target into ChromeContext would mix UI state (sidebar open, fixed-width) with terminal-WS state and force every Chrome consumer to re-render whenever focus changes; the dedicated context keeps the dependency narrow.
**Rejected**: a compose target frozen at open (the modal model's snapshot) (260718-dhdj-docked-compose-strip).
*Introduced by*: 260509-17m3-rotated-shell-layout

### Read-only setter pair for in-memory + persisted state (`setSidebarWidth` + `persistSidebarWidth`)
**Decision**: the dispatch is split into `setSidebarWidth(width)` (in-memory state) and `persistSidebarWidth(width)` (localStorage write), so the drag handler calls the cheap one in the loop and the expensive one once at drag-end. Convention note: future state with the same shape (live in-memory updates + final commit to persistence) should follow this two-setter pattern.
**Why**: drag-resize fires per-pointermove (potentially 60+ events per second); persisting on every event would write localStorage 60 times per second per drag — unnecessary I/O and cache thrash.
**Rejected**: debouncing inside the dispatch (couples state lifecycle to a timing heuristic).
*Introduced by*: 260509-17m3-rotated-shell-layout

### Mobile sidebar overlay positioned via grid (`gridRow: "2/4"`), not `fixed inset-0`
**Decision**: the mobile overlay is a grid-row-spanning child with `position: absolute` (not `fixed`) so it anchors below the topbar inside the Shell; it has a backdrop and carries `role="dialog" aria-modal="true"`. The spec wording "fixed-position overlay with backdrop" is satisfied — the overlay is fixed-position-style (absolute inside the Shell that itself is full-viewport).
**Why**: the project convention recorded in `fab/project/context.md` and the `mobile-layout.spec.ts` assertion (`sidebarBox.y > 0`) require the mobile overlay to leave the topbar visible — the topbar has the hamburger which closes the overlay, so covering it would be a usability regression.
**Rejected**: the spec's literal `fixed inset-y-0 left-0 z-50` (covers the topbar).
*Introduced by*: 260509-17m3-rotated-shell-layout

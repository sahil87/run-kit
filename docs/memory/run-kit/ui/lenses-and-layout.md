# run-kit UI — Lenses & Surface Layout

## Iframe Window (the `web` lens renderer)

`app/frontend/src/components/iframe-window.tsx` — the renderer for the **`web` surface/lens** (§ Window Views (Lens Model)), mounted as a tile by `SurfaceLayout` whenever the layout's order includes `web` (§ Surface Layout). The `web` surface is ALWAYS available (§ Window Views (Lens Model)) — the tile renders the window's **web-tab family**: `SurfaceLayout` feeds `tabs={webTabs ?? []}` and `active={webActive}` (overlaid by the store's optimistic web override while select/remove/move is in flight — § Optimistic select/remove/move below), and the component derives the active address itself (`webTabs[(webActive || 1) - 1] ?? ""`, clamped — the same value `activeWebUrl(win)` yields). Stored `@rk_win_web_<n>` values may be site-relative paths beyond `/present/` and `/proxy/`; the hash-addressed tutorial companion page (`/tutorial/tutorial.html#chN`) is the first shipped consumer, and each viewer resolves it against its own run-kit origin. A family with declared tabs mounts one iframe PER TAB; the strip ALWAYS renders with the tile — at 0 tabs/0 drafts it is just the trailing `+`, keeping the draft entry points reachable from the empty state; an empty family selects the tile's ONBOARDING content state below the strip (§ Onboarding state below); and an out-of-range active pointer clamps to the family, never to onboarding. Bottom bar is NOT rendered for a web tile (no terminal to send keys to). The component takes `tabs`/`active`, an optional `onWriteUrl: (url: string) => Promise<unknown>` address-bar write seam (the caller owns the slot index — `SurfaceLayout` binds it to the active `@rk_win_web_<n>` option write, n = `webActive` or 1 while the pointer is unset), optional strip verb callbacks (`onSelectTab(n)` / `onCloseTab(n)` / `onAddTab(target) → {index, existed}` / `onMoveTab(n, to)` — the caller owns the POSTs; the component re-renders declared state from the next `tabs`/`active` props and never renumbers it locally), and three optional interaction seams — an `onInteract: () => void` tile-focus seam, a `shouldReclaimChord` chord-reclaim predicate, and an `onPageMeta: (meta: { title: string | null }) => void` page-meta seam (all below). It owns ephemeral draft and per-frame chrome state but no persisted view/URL/localStorage state; it mutates no `@rk_win_lens` (§ Window Views → decoupling). View switching is owned by the top-bar surface toggles / mobile switch group and the palette — the tile itself carries no switch-to-terminal affordance. (260714-t97o, 260812-ab5v, 260819-v6y4, 260821-zqlq, iip5, 9kip, s36e, 6uu0)

**Layout**: Outer wrapper `flex flex-col flex-1 min-h-0` with up to six children: the web tab strip (`shrink-0`, always rendered — § Web tab strip below), the URL bar (`shrink-0`), the find bar (`shrink-0`, rendered only while open — § Find bar below), the load progress line (rendered only while the ACTIVE frame loads — § Load progress line below), an in-tile error state (rendered in place of the ACTIVE iframe's VISIBLE area while active — § Error states below), and the content-zoom wrapper (`flex-1 min-h-0 overflow-hidden`) holding one `<iframe>` PER DECLARED TAB — each `key`ed by its URL, every non-active frame `hidden` but never unmounted (P3; § Web tab strip below). In the ONBOARDING state (empty family) the wrapper holds the strip (bare `+` plus any open drafts), the reduced URL bar, and the onboarding panel — the frames, find bar, progress line, and error/probe machinery do not mount (§ Onboarding state below).

**Web tab strip**: a `role="tablist"` strip (`data-testid="web-tab-strip"`, `shrink-0`, horizontally scrollable, 11px monospace, the tile-header `bg-bg-card border-b border-border` idiom) always renders above the URL bar — at 0 tabs/0 drafts it holds only the trailing `+` (a tablist with zero `role="tab"` children is the accepted resting shape), so the empty family keeps its draft entry points. Each declared tab (`role="tab"`, `aria-selected`, `data-testid="web-tab"`, `data-index={n}`, `title={displayForm(url)}`) labels itself with its URL-keyed tracked document title and falls back to `webTabTitle(url)`/`#n`. Its icon slot shows a per-frame loading spinner, static under `prefers-reduced-motion`; after load it shows the same-origin document's icon link or frame-origin `/favicon.ico`, an external host's `https://{host}/favicon.ico`, or the `classifyAddress` kind dot (green present / amber proxy / blue external) when no icon applies or an image errors. A cross-origin navigation clears the tracked title, location and icon derived from the prior readable document so the stored URL drives the fallbacks. The close `×` is always rendered on the active tab and on coarse pointers, hover/focus-within-revealed otherwise; `auxclick` button 1 closes through the same `onCloseTab` path. The strip is a ROVING-FOCUS tablist: only the selected entry is in the tab order; ←/→/Home/End move focus without writing; Enter/Space select; Delete/Backspace close; component-local ⌥⇧←/⌥⇧→ moves the active declared tab one slot through `onMoveTab`, with boundary presses as silent no-ops. Pointer drag crosses a 6px threshold before becoming reorder, paints a green drop-side indicator on the hovered tab edge, and commits one `onMoveTab(from, to)` on release; drafts are neither drag sources nor targets. The trailing `+`, a double-click on empty strip space, and the palette's `Web: New tab` event append a dashed viewer-local draft after every declared tab and focus the address bar. Multiple drafts may coexist. Enter materializes the selected draft through `onAddTab`, selects the returned server-assigned slot through `onSelectTab(index)`, and removes the draft after add resolves; add idempotence may return an existing slot. Escape or the draft's `×` discards only that draft without a POST. Drafts live for one mounted window tile and disappear on window switch/unmount. The `+` disables at the declared-family cap (`tabs.length >= 8`) with a `web tabs full (8)` Tip; add errors surface inline in the address bar's `role="alert"` submit-error slot. **Frames**: the zoom wrapper mounts one `<iframe key={url}>` per declared tab — every non-active frame `hidden` (`display:none`), never unmounted by selection or reorder and never re-`src`d, so in-page state survives tab switches; URL keys keep close and move renumbering from remounting frames. Frame-scoped state (ref, loading, cross-origin, tracked location, title, favicon, probe/error) lives in the extracted per-tab `WebFrame` and reports into the parent's URL-keyed chrome-state map; the URL bar, back/forward, refresh, find bar, progress line, error surface, `onPageMeta`, and zoom bind to the ACTIVE frame, while every same-origin frame contributes its title/icon to its own tab. All frames mount EAGERLY (the family cap of 8 bounds the count; no lazy mount, no LRU) and inactive frames run no dead-port probe timer — a frame probes on first mount and on activation. The document CustomEvents (`web-find:open`, `web-address:focus`, `web-tab:open-draft`, `web-open-external`, `web-zoom`) keep their single listeners on the ONE `IframeWindow` per layout. e2e: `web-tabs.spec.ts` seeds real tmux families and covers the one-tab strip, drafts and materialization/discard, drag/keyboard/palette reorder, middle-click close, shared-state convergence, and URL-keyed mounted frames. (9kip, s36e)

**Optimistic select/remove/move**: the strip verbs are wired in `SurfaceLayout` (`components/surface-layout.tsx`) through `useOptimisticAction` over the window store's per-entry `webOverride { webTabs?, webActive? }` (display only). Select sets `{ webActive: n }`; remove derives the local family with `webFamilyAfterRemove(tabs, active, n)`; move derives it with `webFamilyAfterMove(tabs, active, n, to)`, including the active-pointer repoint. Synchronous override refs make consecutive gestures compound on the family already displayed instead of stale SSE payload. Move POSTs are serialized in gesture order. A rejected move rolls back to the SSE-confirmed family, cancels every queued dependent move whose indices came from the rejected optimistic family, fires no dependent POST, and emits one error toast; dependents are dropped rather than reinterpreted against different indices. Successful verb POSTs wake the SSE hub, and a reconcile effect clears the override once the payload matches; a window switch drops any in-flight override (the override cleanup effect re-runs on its `[server, sessionName, windowId]` dep change — the grid is keyed by server, not remounted). Add is not optimistic because the slot index is server-assigned; `addWebTab` receives `toWebAddTarget(target)` so a root-relative `/proxy/…` draft reaches the backend's `rk present`-shaped target resolver. The component types verbs as promise-returning; optimistic executors are fire-and-forget, so the `SurfaceLayout` wrappers resolve at once. (9kip, s36e)

**URL Bar**: Thin toolbar above the iframe (`border-b border-border bg-bg-primary`), one warm-tip `TipGroup` cluster, button order per the approved design study (`fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html`):
- **Back / Forward buttons** (`WebBackGlyph`/`WebForwardGlyph` — `data-icon="web-back"`/`"web-forward"`, register arrow SVGs) — drive `contentWindow.history.back()/forward()` on same-origin frames; both are HIDDEN when the frame is cross-origin (cross-origin history is unreachable to a parent by design). The navigation is per-viewer view state and never touches the stored web tab (spec window-views R7). The buttons render enabled whenever same-origin — a parent has no reliable canGoBack signal, and a boundary click is a harmless no-op. (260819-v6y4)
- **Refresh button** (`RefreshGlyph` — `data-icon="refresh"`, the same register export the top-bar RefreshButton renders) — a REAL reload on same-origin frames: `contentWindow.location.reload()` preserves the frame's CURRENT location and in-page state (no reset to the stored tab address); the `about:blank` bounce (clear `src`, re-set via `setTimeout(0)`) remains ONLY as the cross-origin fallback. Styled: `w-7 h-7 rounded hover:bg-bg-card text-text-secondary hover:text-text-primary` — every URL-bar button carries the tile-verb hover brighten. (260819-v6y4, 76uz)
- **Address input (display/edit split)** — at rest it SHOWS the kind-specific DISPLAY form (`displayForm(rawAddress)`, § Address model below — a proxied `/proxy/3000/…` reads `localhost:3000/…`, a presented file reads its basename with the `server`/`v`/`raw` plumbing params hidden, an external URL reads host+path with the scheme omitted). Focusing it reveals the RAW editable value (the tracked frame location when known, else the active tab's address) with select-all. On Enter the input routes through the five-lane submit ladder (`routeAddressSubmit`, § Address model below). URL-shaped input (absolute http(s), root-relative, bare loopback `host:port` → `/proxy/{port}/…`) takes the WRITE lane: with a selected draft Enter calls `onAddTab(url)`, selects the returned index, and removes that draft after success; otherwise it calls `onWriteUrl(url)` and a same-URL submit is a no-op. PATH/PORT-shaped input — a relative path (`docs/foo.html`, `./x`), bare `:NNNN`, or a dotted single name — takes the ADD lane regardless of draft state: submitted raw to the add verb, the backend stats it under the window's first-pane worktree cwd, and the add's target-identity match makes the paste APPEND-OR-FOCUS (an existing tab for the target focuses, a new target appends; the current tab is never navigated in place). A dotted single name (`README.md`, `example.com`) is stat-decided: it exists → present tab; `ApiError` status 400 → one silent retry as `https://{name}` through the write lane (so a pasted `README.md` never lands on Moldova's TLD). Bare words and explicit non-http(s) schemes — with or without `//` (`ftp://x`, `file:/etc/passwd`, `mailto:a/b`); only the dotted `host.tld:port[/path]` bare-domain shape is exempt from the scheme reject — surface an inline `role="alert"` error and fire NO POST; an add-lane 400 without a fallback surfaces the backend body text (`target "…" does not exist`) in the same slot with the input kept editable; blank Enter is a silent no-op. `SurfaceLayout` binds the write seam to `setWindowOptions(server, windowId, { "@rk_win_web_<n>": url })` → `POST /api/windows/{windowId}/options` (partial-merge — n = `webActive`, or slot 1 while the pointer is unset). Escape reverts a declared tab's edit without a POST or discards the selected draft; an ordinary blur restores the rest display. The address bar REPLACES the active declared slot for URL-shaped input and APPENDS-OR-FOCUSES through add for path/port-shaped input; the strip `+`, empty-space double-click, and palette `Web: New tab` open drafts that materialize through add — § Design Decisions → Address bar replaces, `+` adds. On a replace failure the input reverts to the SSE-confirmed address; on a draft-add failure the draft remains selected with its submitted value and inline error for retry. Styled: `bg-bg-card text-text-primary text-sm px-2 py-1 rounded border border-border`. Editing a declared content address is *substrate* state (shared, POSTed, every viewer sees it); editing an unmaterialized draft is viewer-local and never POSTed. (260529-jad6, 260819-v6y4, iip5, 9kip, s36e)
- **Find button** (`FindGlyph` — `data-icon="find"`, the same register export as the tty tile's find toggle: one find identity across surfaces; `aria-label="Find in page"`, `aria-pressed` while open — lit `text-accent-green` when the bar is open) — the pointer/touch entry point to the find bar; toggles it locally (the chord and palette entries share one open seam instead, § Find bar)
- **Open-in-browser button** (`OpenExternalGlyph` — `data-icon="open-external"`, register arrow-up-right; `aria-label="Open in browser"`, rightmost) — opens the CURRENT address (the tracked frame location when known, else the stored tab address) in a new tab via `window.open(…, "_blank", "noopener")`; relative addresses resolve naturally against the viewer's origin (the stored address stays relative per the display contract `docs/site/skill/display.md`). The universal escape hatch for anything the tile can't render; the `Web: Open in browser` palette action mirrors it (§ Address model below — the document-CustomEvent seams). (260819-v6y4)

**SSE Sync**: a `useEffect` on the derived active address syncs the URL bar text (`setInputUrl(url)`) and clears the submit error on every active-address change — an SSE push, a tab select, or a same-slot replace. The iframe side needs NO sync effect: a changed tab URL re-keys (remounts) exactly that frame, and a selection change only flips `hidden` — no frame's `src` is ever rewritten by the parent, so identical SSE ticks and tab switches reload nothing. When the active web tab changes externally (an agent or another viewer runs `tmux set-option -w @rk_win_web_<n>` or a web verb), the next payload repaint flips the visible frame and the URL bar follows automatically. (9kip)

**Interaction + reclaim seam (`onInteract`, `shouldReclaimChord`)**: in-frame clicks and keydowns stay in the frame's own document, and focus entering a frame fires NO focusin in the parent — parent-document listeners are blind to them. The component attaches capture-phase `pointerdown`/`keydown` listeners to the same-origin `contentDocument` after every iframe `load` (each navigation replaces the document; cross-origin access throws and is skipped silently — the `CodeSurface` attach pattern) plus a parent-window `blur` fallback that reports when `document.activeElement` is the iframe, covering cross-origin embeds. Every in-frame keydown reports `onInteract` FIRST, then — when a `shouldReclaimChord` predicate prop is injected — a keydown matching it is `preventDefault` + `stopImmediatePropagation`ed inside the frame and re-dispatched as a synthetic bubbling `KeyboardEvent` on the parent **document** (the CodeSurface `onKey` mechanism, byte-for-byte — § Code Surface → Chord reclaim): run-kit's registry chords (⌘K, ⌘;, ⌘F, …) keep working with focus inside the frame while every non-claimed key reaches the framed page untouched (typing into an in-frame form is unchanged). `SurfaceLayout` injects the predicate bound to the `web` kind (`shouldReclaimChord("web")`, the kind-aware factory in `app.tsx` — § Surface Layout → Tile renderer), so `ttyOnly` chords pass through to the framed page and `webOnly` chords (⌘F, ⌘L) reclaim only here (§ Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags). Cross-origin frames get no reclaim — the `blur` fallback stays the only interaction signal, and once a cross-origin frame holds focus, later in-frame clicks report nothing — accepted, the tile is already focused by then. `SurfaceLayout` wires the seam to tile focus (§ Surface Layout → Focused tile); both props are optional and other mount contexts omit them unchanged. (260815-41t9, 260819-ie2i)

**Find bar (⌘F find-in-page)**: the web tile ships in-frame page search for same-origin content — a `shrink-0` row rendered between the URL bar and the iframe while open (`data-testid="web-find-bar"`, the URL bar's border/background vocabulary; layout per the approved design study `fab/changes/260819-v6y4-web-tile-browser-chrome/web-tile-chrome-design-study.html` state 03). The row is the shared presentational **`FindBar`** component (`components/find-bar.tsx`, colocated `find-bar.test.tsx`) — props-driven (`query`/`matchIndex`/`matchCount`/`onQueryChange`/`onNext`/`onPrev`/`onClose`, plus optional `toggles`, `disabled`, `statusText` (replaces the counter), and `scopeNote`), the consumer owning the search mechanism — also mounted by the tty tile (§ Tile renderer → tty find bar); `IframeWindow` owns the in-frame engine and passes no toggles. Row contents in order: an autofocused text input, the `n/N` match counter with the active ordinal in accent green (`0/0` when the query matches nothing), ∧/∨ previous/next buttons, a ✕ close button, and a right-aligned key hint `Enter next · ⇧Enter prev · Esc close` suppressed on coarse pointers (`useCoarsePointer()` — keyboard-chord copy never renders on touch). Enter advances to the next match, Shift+Enter to the previous (both wrap), Escape closes the bar and clears all highlights. Three entry points share ONE open seam: the ⌘F/Ctrl+F `web-find` chord (reclaimed inside the frame or handled at tile level while the web tile owns focus — § Keyboard Shortcuts → the `ttyOnly`/`webOnly` flags) and the `Web: Find in page` palette action both dispatch the `web-find:open` document CustomEvent (`WEB_FIND_OPEN_EVENT`), which the mounted web tile listens for (the `window-heading:rename` / `theme-selector:open` precedent — one `IframeWindow` per layout hosting N frames, so the receiver is unambiguous; the listener acts on the ACTIVE frame); the ⌕ URL-bar button (the pointer/touch entry) toggles the bar locally. A cross-origin frame renders the bar DISABLED — input and navigation buttons disabled, the inline hint `page is cross-origin — find unavailable` in place of the counter — and no search is attempted (⌘F pressed while a cross-origin frame holds focus never reaches the parent at all, so the ⌕ button and the palette are the bar's entry points there). Every ACTIVE frame `load` resets the find state — matches, highlights, and the query die with the document they were collected from (no term persistence across navigations); the bar's open/closed state itself survives navigation. (260819-ie2i, 260819-zqf9)

**Find engine (`lib/find-in-page.ts`)**: a pure module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract), parent-driven over the same-origin `contentDocument` — no script injected into the framed page. `collectMatches` walks the frame document's text nodes with a case-insensitive TreeWalker into DOM `Range`s (skipping non-rendered containers like `script`/`style`); `stepMatch` is the wrap-around active-index transition; `applyHighlights` registers two CSS Custom Highlights (`rk-find` all matches, `rk-find-active` the active match with its accent-green outline) on the FRAME window's `CSS.highlights` and installs one `<style>` element of `::highlight()` rules into the frame's `<head>` (inert DOM — `clearHighlights` removes both on reset); the active match scrolls into view (`block: "nearest"`). Where the Highlight API is unavailable, `contentWindow.find()` is the best-effort fallback — navigation works, the counter may read the zero form. All frame-DOM access carries the attach seam's try/catch posture (pre-load and cross-origin frames no-op silently). Unit-provable in jsdom without the Highlight API. e2e: `web-tile-find.spec.ts` on the real-tmux port-3020 rig (the `web-view-lens.spec.ts` `_tmux.ts` pattern) proves ⌘K opening the palette with focus inside a same-origin web-tile frame, the ⌘F open → match count → Enter navigation → Escape close flow on a presented HTML file, and the cross-origin disabled bar + hint via the ⌕ button. (260819-ie2i)

**Address model (`lib/web-url.ts`)**: a pure, DOM-free module with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract) owning every derivation over a stored `@rk_win_web_<n>` address or an address-bar keystroke. `classifyAddress(url)` returns one of four kinds — `present` (any root-relative `/present/…`, covering both `/present/{server}/{roothash}/{path}` and the legacy `/present/{windowId}/{n}/{path}?server=` arm), `proxy` (root-relative `/proxy/{port}/…` OR an absolute loopback `http(s)://localhost|127.0.0.1|[::1]:{port}…`), `external` (any other absolute http(s) URL), `relative` (any other root-relative path) — driving the header badge and error posture; unrecognized input degrades to `relative`, never throws. `displayForm(url)` is the kind-specific resting form: a presented file shows its basename, with content-keyed `server`/`roothash` path segments and the query plumbing excluded (the legacy `server` identity param, the shared `v` cache-buster, and the viewer shell's `raw` escape hatch — `PRESENT_PLUMBING_PARAMS`); a presented directory or degraded shape retains the raw-address fallback; proxy shows `localhost:{port}{path}`; external shows `host{path}{?query}` with the scheme omitted; relative stays raw. `normalizeAddressInput(input)` maps bare loopback `host:port[{path}]` to `/proxy/{port}{path or /}`, maps a bare domain to `https://…`, and otherwise passes through for `isAllowedUrl` to validate. `isAllowedUrl(input)` mirrors the backend allowlist (absolute http/https with a host or root-relative). `routeAddressSubmit(input)` is the address bar's submit router (`AddressSubmitRoute`, a three-arm union): `write` — URL-shaped input, the slot-write/draft lanes, composing `normalizeAddressInput`; `add` — path/port-shaped input handed raw to the backend add verb, with a `fallback` `https://{input}` form carried for dotted single segments (the caller retries it on `ApiError` 400); `reject` — bare words and explicit non-http(s) schemes. Lane order: absolute http(s) + root-relative pass-through → bare loopback rewrite + bare `:NNNN` as a port target → scheme reject (exempting only the full dotted `host.tld:port[/path]` bare-domain shape) → slash-bearing/`./`-leading paths → dotted single segments with fallback → reject. (ewud) `proxyPortOf(url)` returns the proxy-kind port; `toProxySrc(url)` owns iframe-src mapping. `webTabTitle(url)` is the shorter tab label: presented files show the basename with both address shapes' plumbing excluded, proxy shows `localhost:{port}{path}`, external shows the host, and relative stays raw; directory/degraded present shapes retain the raw-address fallback, and empty input returns `""` for the caller's `#n` fallback. `toWebAddTarget(url)` passes both present shapes through unchanged and re-expresses only a root-relative `/proxy/{port}…` address as `http://localhost:{port}…` for the backend's `rk present`-shaped add parser. The module exports `WEB_ADDRESS_FOCUS_EVENT` (`web-address:focus`, the plain ⌘L/palette focus seam), `WEB_TAB_DRAFT_EVENT` (`web-tab:open-draft`, the palette's draft-opening seam), and `WEB_OPEN_EXTERNAL_EVENT` (`web-open-external`, the palette seam). Each follows the `WEB_FIND_OPEN_EVENT` single-receiver pattern: one `IframeWindow` per layout hosts N frames, so one listener can act on the active frame or tile-local draft state. Display derivation never rewrites the stored relative address. (260819-v6y4, 9kip, 260901-ei4t-present-url-server-root-hash, s36e)

**What a present tab renders**: a present-kind address for a gated extension (`.md`/`.markdown`/`.excalidraw`) loads the backend-served viewer shell inside the frame — rendered markdown (mermaid diagrams on fenced blocks) or a static excalidraw SVG — at the document's own URL, so the frame content is the rendered document, not raw source; the raw form stays one `?raw=1` away. The shell's contract (extension gate, `X-Present-Format`, dev-proxy sourcing) lives in [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer → `/present/{server}/{roothash}/*`; its build shape in [build-and-release](/run-kit/build-and-release.md) § Build Pipeline. (260908-krov-present-viewer-shell) **Diagrams are zoomable figures** (`app/frontend/src/viewer/zoomable-figure.ts` over the pure `viewer/pan-zoom.ts`): every excalidraw scene (`.viewer-scene`) and every mermaid diagram (`.viewer-diagram`) is wrapped as a `.viewer-figure` (`role="group"`, `tabindex=0`, `data-testid="viewer-figure"`, `data-mode`, `data-zoomed`) holding a clipping `.viewer-figure-viewport` and a hover/focus-revealed toolbar (Zoom out · percent readout · Zoom in · Fit to view · Expand on inline figures). The SVG keeps its NATURAL layout box (explicit px `width`/`height` from its `viewBox`, `max-width: none`) and the only magnification is `transform: translate() scale()` with origin `0 0` — vector text stays crisp, nothing re-renders. Rest = the fit state (`fitScale`: `"contain"` for an excalidraw canvas, `"width"` for an inline diagram, never upscaled past natural); bounds `[fit, 8×]` (`FIGURE_ZOOM_MAX`); ctrl/⌘-wheel zooms continuously about the cursor (the tile's `applyWheelZoom` mapping from `lib/zoom-gesture.ts`), two-pointer pinch about the midpoint, Safari `gesture*` likewise; button/plain-key zoom steps a local extended ladder (`FIGURE_ZOOM_LEVELS`, 0.1…8) to the next level strictly beyond the current scale (no snap-then-step); drag pans with pointer capture once `isPannable`; plain keys `+`/`=` `-`/`_` `0` and arrows (`PAN_STEP_PX`, ×5 with Shift) act while focus is inside the figure — never ⌘/Ctrl variants. `touch-action` is `pan-x pan-y` at fit (page scroll survives a finger over an inline diagram) and `none` once zoomed. A `ResizeObserver` refits at fit and only re-clamps when zoomed. Layouts: `body[data-format="excalidraw"]` drops the reading column and the canvas figure is `100vh`; an inline mermaid figure keeps its fitted height and its **Expand** toggle (`aria-pressed`) grows the box to `calc(100vh − 2rem)` and back. **Current-path tracking + page meta**: every `WebFrame` handles its own `load` events through the attach seam's try/catch posture. A same-origin frame stores its location root-relative (viewer origin stripped), document title, and favicon link or frame-origin `/favicon.ico` in the parent's URL-keyed chrome map; every tab can therefore show metadata from its own frame. An unreadable cross-origin load clears that frame's tracked location/title/favicon so stored-URL fallbacks apply. The address bar, navigation controls and optional `onPageMeta` header seam bind only to the ACTIVE map entry; `SurfaceLayout` holds the active title for the tile header. All metadata and in-frame navigation are display-only and never POSTed; only explicit Enter on a declared tab's address writes its slot. (260819-v6y4, 9kip, s36e)

**Onboarding state (empty web-tab family)**: with no tab to render (`tabs.length === 0`), the tile mounts the ONBOARDING state in place of the frames and their probe machinery — the branch is `onboarding = tabs.length === 0`, and NO frame-check/dead-port probing runs (the probes key off an address; § Error states below). With ≥1 tab every frame mounts regardless of the active pointer's value (an out-of-range pointer clamps, never shows onboarding). The **reduced URL bar** keeps only the REFRESH button and the ADDRESS INPUT — back/forward, the find ⌕ button, and the ↗ open-in-browser button are hidden (nothing to navigate, search, or open) — and the input is FULLY LIVE with placeholder `localhost:3000 · /present/… · https://…`: typing an address + Enter runs the existing submit pipeline (`normalizeAddressInput` → `isAllowedUrl` → `onWriteUrl` → the slot-1 `@rk_win_web_1` POST, § URL Bar above) and boots the tile for real — the bar is itself an init path. The **body panel** (replacing the frames; centered, monospace, on `bg-bg-primary`) carries a large dimmed `://` glyph, the heading **"Nothing to show yet"**, the subhead *"this tile follows the window's active web tab (@rk_win_web_N) — three ways to fill it:"*, three instruction rows (accent-green lead glyph, bold lead-in, `bg-bg-inset` bordered code chips): `❯` **Ask your agent to show something** — "Present this as a page" — the agent runs `rk present ./report.html` and it appears here (HTML files, diagrams, mocks, directories); `⇄` **Preview a dev server** — type `localhost:3000` in the address bar above (proxied through run-kit, works from any device), or have the agent run `rk present :3000`; `↗` **Open any URL** — external sites embed when they allow it, and find-in-page (⌘F) + back/forward work on same-origin pages. A dimmed footer reads *"the tile goes live automatically when an address lands ● no reload needed"*. The tile header renders the plain `://  Web` label — no kind badge, no page title, no meta chip (§ Surface Layout → Tile chrome). The flip is automatic in BOTH directions — `onboarding` derives from the tab family's emptiness (§ SSE Sync), so an empty→non-empty transition swaps the panel for the live frames with no user action, and non-empty→empty returns to onboarding; `present-auto-expand` is untouched — an already-open onboarding tile flips in place via the `withAutoWeb` identity arm (§ Surface Layout → Present auto-expand). The find entry points no-op here: the `Web: Find in page` palette entry is content-gated on `hasWebUrl` and the tile's own `web-find:open` listener double-guards ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § `web-find`). (260821-zqlq, 9kip)

**Error states (fail loudly)**: a silent blank iframe is not a reachable state for a probed-blocked external URL or a dead proxied port — the tile renders an explicit error surface (`data-testid="web-tile-error"`) IN PLACE of the ACTIVE iframe's visible area, copy per the design study (states 05/06). Three kinds: **frame refusal** — for `external`-kind addresses the frontend calls `GET /api/frame-check` (`checkFrame`, [api-and-sockets](/run-kit/api-and-sockets.md) § API Layer) on address change; `embeddable: false` renders "`{host}` refuses embedding" + the reason line + an Open in browser ↗ button; **unreachable external** — `reachable: false` renders "`{host}` can't be reached" + the probe reason + the same hatch; **dead proxied port** — for `proxy`-kind addresses a same-origin `fetch` of the proxied path reads the reverse proxy's 502 (nothing listening) and renders "nothing listening on :{port}" + "connection refused — the dev server may have stopped" + a ↻ Retry button that re-runs detection and reloads (a nonce re-fires the probe effect). Present/relative kinds never probe; a same-origin fetch FAILURE (the app server itself down) is not a dead upstream and leaves the iframe alone. The probes live in the per-tab `WebFrame` and run on first mount and on ACTIVATION only — an inactive frame runs no probe timer and renders no error surface; only the active frame's entry feeds the tile's error render. The error state clears on the next address change/retry. The errored iframe stays MOUNTED but `hidden` beneath the error surface (§ Design Decisions → Error states render over a hidden, still-mounted iframe). (260819-v6y4, 9kip)

**Load progress line**: a 2px indeterminate accent-green sweep (`.rk-web-progress` in `globals.css`, `data-testid="web-load-progress"`) rendered at the content's top edge while the ACTIVE frame loads — set on the active frame's src change/reload/history navigation, cleared on that frame's `load` event (the element's presence IS the state; inactive frames carry no progress line). Under `prefers-reduced-motion` the sweep zeroes to a static dim line — load feedback is never motion-only. (260819-v6y4, 9kip)

**Content zoom**: the web tile magnifies its guest content by a per-viewer zoom level `s` applied as a SCALE WRAPPER on the ACTIVE frame — that iframe renders inside the `overflow-hidden` wrapper (`data-testid="web-zoom-frame-wrapper"`) at `width/height: 100%/s` with `transform: scale(s); transform-origin: 0 0`, so zooming in shrinks the frame's CSS viewport and responsive guest layouts adapt exactly as under real browser zoom; at `s = 1` no transform is applied and the layout is identical to an unzoomed tile. The mechanism never reaches into the guest document, so it covers all four address kinds including cross-origin `external` (§ Design Decisions → Scale wrapper over guest-document CSS zoom). Zoom has TWO trigger families with different quantization (the Chrome/macOS convention): CLICK/SHORTCUT zoom steps the discrete ladder; GESTURES are CONTINUOUS — the factor tracks the fingers through arbitrary values, clamped to `[WEB_ZOOM_MIN, WEB_ZOOM_MAX]` (0.5–3, the ladder's ends). The pure, DOM-free `lib/web-zoom.ts` (colocated tests, the `web-url.ts` module contract) owns the derivations: the browser-standard ladder `WEB_ZOOM_LEVELS` (50%–300%, default/reset 1) + `stepWebZoom` (clamps at the ends, snaps an off-ladder value to the nearest level FIRST — the load-bearing bridge from a gesture-set float to the button/palette ladder: a `+` click from 137% snaps to 125% and lands on 150%); `webZoomKeyFor(url)` — the persistence bucket derived via `classifyAddress`: `external` → the URL's origin, `proxy`/loopback → `proxy:{port}`, `present`/`relative` → the single viewer-origin bucket `self` (presented files rotate paths, so per-path buckets would fragment state); and try/catch-noop `readWebZoom`/`writeWebZoom` over ONE localStorage key `runkit-web-zoom` holding a `{[bucket]: level}` map — `readWebZoom` returns the stored FLOAT clamped to the bounds, never snapped (a gesture-set 1.37 reloads as 1.37; the ladder snap lives solely in `stepWebZoom`), `writeWebZoom` rounds to 2 decimals and a round-to-1 value removes the entry (100% is the absent state, robust to gesture float noise), per-viewer state only, never POSTed (Constitution IV; spec window-views R7). `IframeWindow` seeds its zoom state from the ACTIVE address's bucket and re-seeds when the bucket changes — an active-tab change switches buckets (per-viewer, per-bucket — not per tab). Persistence timing differs by family: click-path writes are immediate; gesture writes ride a trailing debounce (`ZOOM_PERSIST_DEBOUNCE_MS = 250` — a pinch emits dozens of events) whose pending write FLUSHES, never drops, on unmount and on bucket change (the flush targets the OLD bucket before re-seeding). **Triggers**: (1) a compact control in the URL-bar cluster between the find ⌕ and open-external ↗ buttons (`data-testid="web-zoom-control"`; text-glyph `−`/`+` steppers with the percent readout between them doubling as the reset affordance — disabled at 100% — in the `w-7 h-7 rounded hover:bg-bg-card` + `Tip` URL-bar button vocabulary) — the universal floor trigger, and the only one that works over an `external` frame; NOT rendered in the onboarding state (the reduced URL bar keeps only refresh + address input). (2) The palette's `Web: Zoom in`/`Web: Zoom out`/`Web: Reset zoom` actions ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) dispatch the `web-zoom` document CustomEvent (`WEB_ZOOM_EVENT` in `lib/web-zoom.ts`, `detail.direction: "in" | "out" | "reset"` — the `web-find:open` precedent: the mounted tile is the single receiver, double-guarded to no-op on a contentless tile). (3) Ctrl/Cmd+wheel and touchpad-pinch gestures — CONTINUOUS, applied per event: each ctrl/meta wheel event maps `s → clamp(s * exp(-deltaY * WHEEL_ZOOM_SENSITIVITY))` (`applyWheelZoom` in the shared `lib/zoom-gesture.ts` — exponential, so equal deltas multiply equally and a reversed gesture returns to its start), and Safari's `gesturechange` sets `clamp(base * scale)` from a base captured at `gesturestart` (its scale is cumulative — no accumulator state); the stepped accumulator family in the same module remains the TERMINAL's ([terminal](/run-kit/ui/terminal.md) § Terminal Font Size → Gesture triggers — integer font steps are inherently discrete). Both families arrive through TWO non-passive capture arms — one on the tile's own wrapper (covering the URL bar, find bar, and error surface, all parent-document DOM) and one attached to each same-origin frame's document on every `load` (the chord-reclaim attach posture: try/catch, cross-origin/pre-load skips silently, re-attaches per navigation) — a wheel event over an iframe never reaches the parent document, so both arms are needed. Over a cross-origin (`external`) frame gestures are unreachable — accepted platform limit, no fallback attach; the chrome control and palette remain the triggers. Only ctrl/meta-modified wheel and Safari `gesture*` events are intercepted (`preventDefault` — the gesture never becomes browser page zoom); everything else passes through untouched. e2e: `web-tile-zoom.spec.ts` on the real-tmux rig (the `web-view-lens` pattern) proves control stepping, reset to 100%, persistence across reload, onboarding absence, palette stepping, and the continuous gesture semantics (an in-frame ctrl-wheel lands on the off-ladder `182%`, a small tick compounds with no threshold, and a `+` click snaps back onto the ladder) on a same-origin page. (260823-cwvv, 260824-iafo, 9kip)

**Proxy URL conversion**: `toProxySrc(url)` (`lib/web-url.ts`, § Address model above) maps an absolute loopback URL to its same-origin proxy path: `http://localhost:8080/docs` → `/proxy/8080/docs`. Portless loopback and every other address pass through unchanged (relative addresses are already same-origin).

**Iframe attributes**: `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"` (without `allow-downloads`, VS Code file downloads break — the same sandbox `CodeSurface` reuses, § Code Surface), `title="Proxied content"`, `border-0`.

**Window creation**: "Tab: New Iframe Tab" command palette action (id `create-iframe-window`) opens a `Dialog` with two inputs: window name (autofocused, Enter focuses URL input) and URL (Enter creates window). Create button disabled until both fields non-empty. Calls `createWindow(server, session, name, undefined, url)` — the API client maps a given URL onto the `{ rkType: "iframe", rkUrl: <url> }` POST body (the backend keeps those body field names this release — Change 1 R10 — and stamps `@rk_win_layout=single:web` + `@rk_win_web_1` + `@rk_win_web_active=1`). Backend uses `CreateWindowWithOptions` for atomic `\;`-chained tmux command. Only shown when a session is active. Synthetic iframe windows are created this way. (260714-t97o, 260820-lfla, iip5)

## Code Surface (the `code` lens renderer)

`app/frontend/src/components/code-surface.tsx` — the renderer for the **`code` surface/lens** (§ Window Views (Lens Model)) — mounted as a tile by `SurfaceLayout` whenever the layout includes `code` (§ Surface Layout): via the top-bar surface toggles, the `Tile: Show Code` palette entry, or the switcher's `View: Code` row (which applies `single:code` through `switchView`). It embeds **code-server** at the window's code root — a full editor (tabs, syntax highlighting, SCM view, side-by-side diffs) beside the live agent terminal with no editor functionality built in run-kit. It is a lean component, NOT an `IframeWindow` reuse: the code-server URL is fully DERIVED, so the URL bar (`@rk_win_web_<n>` substrate chrome) is meaningless here — the component is exactly an iframe plus the not-running empty state and the `code-surface-pending` state (§ Design Decisions → The code surface is a lean `CodeSurface`). (260811-k3vp)

- **src** — the primary form is `codeServerWorkspaceSrc(workspacePath)` = `/code/?workspace=<encoded path>` (relative, never a composed origin or port — the `toProxySrc` discipline, riding the same origin through any reverse proxy), where `<path>` is the derived per-tab workspace file whose `settings` block carries `rk.tab`/`rk.server` — the identity the bridge extension reads ([code-bridge](/run-kit/code-bridge.md) § Tab identity). The path is STABLE: code-server keys browser-side workspace state by the proxy pathname and the workspace identity, and `/code/` is fixed by the backend route (the port behind it is a private implementation detail, resolved server-side). The sibling `codeServerSrc(folder)` = `/code/?folder=<folder>` survives only as the DEGRADE form (a failed workspace GET, or a refused code-root seed — each degrades with exactly one console warning so the editor still opens, folder-keyed, the run-kit menu items hidden) and as the editor's own File > Open Folder navigation form, which the follow rule re-derives (§ The code root → Follow rule). The computed `src` is held in a **ref keyed to the iframe's MOUNT GENERATION** (the `reachable` gate): a code-root update never rewrites a live frame's `src`, while a genuine remount (a reachability `false→true` flip, a window switch) boots the CURRENT workspace URL — with exactly two sanctioned parent re-navigations of a live frame, the nonce-keyed `followSrc` re-navigation after an editor-initiated folder move and the marker-gated first-boot rescue `reload()` (§ Design Decisions → Two sanctioned parent re-navigations).
- **Mount gating** — the iframe mounts only once the workspace path is known. `app.tsx` runs `useCodeWorkspace(server, windowId, win, codeTileOpen, seedRejected)` (`hooks/use-code-workspace.ts`), which fetches `GET /api/windows/{windowId}/code-workspace` (via `fetchCodeWorkspace` in `api/client.ts` over `deduplicatedFetch`; a `409` maps to a typed `{status:"no-root"}` result, never a throw) when the payload's substrate `win.codeRoot` is non-empty and the code tile is open, and passes the derived `codeSrc` through `SurfaceLayout` to `CodeSurface`'s `workspaceSrc` prop. Until the path resolves, a reachable tile renders the pending state `opening…` (`data-testid="code-surface-pending"`, the `code-surface-empty` styling — an unreachable host keeps the not-running state, never pending); a `409` keeps pending and re-fetches on the next payload change (the first-ever open costs one SSE tick while the seed POST lands). A refused seed POST (e.g. a root outside `$HOME`) is recorded per (server, window, seed) so a deterministic `400` never becomes per-tick POST spam, and the hook's `seed-rejected:` key degrades the tile to `?folder=` instead of pending forever — a later successful seed re-arms the `?workspace=` path.
- **Availability vs reachability** (spec right-panel.md § Surface Registry): AVAILABILITY = `codeRootFor(win)` is non-empty — the shared `@rk_win_code_root` OR a `gitRoot` derives non-empty — the STABLE capability signal (`hasCode`, computed over the payload), so the surface toggle / switcher segment never strobe when the active pane leaves the repo (the port is always resolvable by convention, so the "configured" leg is always true). REACHABILITY (the host's TTL-cached probe, the state socket's `code-server` event) selects the surface's CONTENT only: reachable renders the iframe once the workspace path resolves (the `code-surface-pending` state until then); unreachable renders the terse monospace empty state `code-server not running — check rk doctor` (`data-testid="code-surface-empty"`) instead of a dead iframe.
- **Sandbox** — the same token set as `IframeWindow`, including `allow-downloads` (without it VS Code file downloads break).
- **Chord reclaim** — focus inside the iframe swallows run-kit's chords (`⌘K` collides with VS Code's own), and same-origin makes an escape hatch possible: a capture-phase `keydown` listener attached to the iframe's `contentDocument` after every load intercepts events matching the INJECTED `shouldReclaimChord` predicate (built in `app.tsx` from the keybinding registry's pure, kind-aware `hasReclaimableMatch(e, bindings, kind)` — `findMatches(...).some(...)` over the surface-restriction flags, here bound to the `"code"` kind), `preventDefault` + `stopImmediatePropagation`s them before the embedded app's keybinding service, and re-dispatches a synthetic bubbling `KeyboardEvent` on the parent **document** (reaching both document-level listeners — the palette chord — and window-level ones — the dispatcher). The reclaim carve-outs: a keydown whose ONLY registry matches are `ttyOnly` bindings (the tmux split pair — a keydown arriving inside the iframe means the code tile owns focus) is NOT reclaimed, so ⌘D reaches code-server's own keybinding service, and a `webOnly` match (⌘F web find) is NOT reclaimed in the code iframe either — code-server keeps its own find — while unrestricted registry chords (⌘K, ⌘;, ⌘2, ⌃`, …) are reclaimed — ⌃` deliberately preempts code-server's own integrated-terminal toggle, the hop back to tty winning over the embedded app's binding (260812-wfic, 260819-ie2i). The effect is keyed on `reachable` (the iframe only mounts when reachable, so a reachability flip re-runs it against the fresh iframe), re-attaches on `load` (each navigation replaces the document), guards `contentDocument` access in try/catch (a cross-origin or pre-load frame silently skips the attach — click-out remains the escape), and removes the listener from the attached document on cleanup. Proven by the `code-surface.spec.ts` e2e "keyboard spike: a registry chord pressed INSIDE the iframe reaches the parent" (§ Design Decisions → Chord-reclaim via a capture-phase iframe listener).
- **Load-time focus grab — guarded** — the code-server workbench grabs DOM focus once per iframe load (a script `focus()` at editor-restore time that no VS Code / code-server setting suppresses), which would otherwise win every window switch and flip `focusedTileKind` to `code`, killing all `ttyOnly` keybindings. Per-window focus memory plus a steal guard answer it: `CodeSurface` reports the grab through the `onProgrammaticFocus?: () => boolean` prop, fed by a capture-phase `focusin` listener on the frame's contentDocument attached by the same load/attach effect as chord reclaim (the ONLY observable — a script `focus()` re-points the focus chain but fires no parent-side iframe event); `app.tsx` reverts an armed grab whose remembered kind is not `code`. The tile wrapper's `onFocus` consults the guard before `focusSlot`, so a grab never settles the focused kind on `code` (§ Surface Layout → Tile renderer). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (260815-ltz7)
- **First-boot rescue (positive empty-boot signal, one-shot reload)** — a never-cached `?workspace=` boot can load zero folders and never recover in place: VS Code web boots a `vscode-remote` `.code-workspace` from its server-side cached configuration first (`~/.rk/code-server-profile/User/caches/CachedConfigurations/workspaces/<id>/workspace.json`), so a never-cached workspace renders `NO FOLDER OPENED`, the late workspace-file load does not repopulate the live workbench, but it DOES write the cache — the next boot works. The oracle is the bridge extension's OWN empty-boot marker, never the absence of a host record: a good boot's record lands only after the remote extension host activates, which under load outlasts any fixed window (7 s measured with three concurrent workbenches), so absence cannot tell a slow boot from a broken one — while the extension provably runs `activate()` on the broken boot and reports it by writing `cb/boots/<hostId>.json`, whose stamp the status GET reports as `emptyBootAt` ([code-bridge](/run-kit/code-bridge.md) § Socket and registry contract, § Host resolution and liveness). The rule lives in the pure, DOM-free `lib/code-boot-rescue.ts` module (colocated `code-boot-rescue.test.ts`, the `code-folder-latch.ts` contract); `CodeSurface` only feeds it events and executes its one verb, driven by the optional injected **`fetchBridgeStatus` prop** (built in `app.tsx` as `() => fetchCodeBridge(server, windowId)` and threaded through `SurfaceLayout` like the other code-surface seams — absent ⇒ the generation is inert: no fetches, no timer). Per `?workspace=` mount generation (the effect's `[reachable, src]` keying re-runs on every generation boundary — a reachability flip, a window-switch remount, or a `followSrc` nonce adoption — resetting baselines, timers, and budget): the status GET is issued ONCE at src adoption, capturing BOTH baselines (`startedAt` and `emptyBootAt`; an `unavailable` result leaves both `null`, and a `null` baseline is never confirmable — `newerThanBaseline` fails closed on it); the iframe's first `load` arms a `CODE_BOOT_RESCUE_WAIT_MS` (10 s) timer; at expiry a SECOND GET is the first verdict — `installed !== true` (false, or null when the verdict GET is unavailable — an old backend's 404 included) ⇒ `skip-not-installed`: no reload, exactly one `console.warn` per generation naming `rk code-server install`; a host record strictly newer than ITS baseline is the good-boot confirmation and settles the generation EARLY (no re-check, no reload — and it outranks a newer marker at the same read: a live tab-keyed record proves the folder loaded); a marker strictly newer than ITS baseline ⇒ `"reload"` fires ONE `iframe.contentWindow.location.reload()` inside the component's try/catch posture — never a `src` write, so the `?workspace=` URL and tab identity survive; NEITHER stamp newer ⇒ exactly ONE re-check timer arms for `CODE_BOOT_RESCUE_RECHECK_MS` (10 s) later, whose read applies the same decision and then settles regardless. `newerThanBaseline(baseline, current)` — the one stamp-compare helper both stamps ride, replacing the retired `bridgeConfirmed` — is true iff `current` is a parseable non-empty stamp AND (`baseline === ""` OR `Date.parse(current) > Date.parse(baseline)`): the `""` baseline (read OK, nothing existed at adoption) accepts any parseable marker, a `null` baseline never confirms, and the browser clock is never consulted. At most THREE reads and ONE reload per generation, no interval loop; a settled generation ignores later `load` events (`settled` is set before each verdict fetch); unmount or a generation change clears pending timers and discards in-flight reads. `?folder=` mounts are never rescued (a folder-opened host writes no tab identity, so neither signal can exist). Until the updated extension is installed (`rk code-server update` / `rk update`) the backend reports `emptyBootAt: ""` and the rescue never fires — fail-closed. The host-record stamp can never produce `"reload"`. Unit coverage: `code-boot-rescue.test.ts` (the `newerThanBaseline` baseline/parse table and the full `decideRescue` decision table) and `code-surface.test.tsx` fake-timer scenarios over a mocked fetcher (newer marker at the re-check ⇒ three reads, one reload; newer record at the first verdict ⇒ two reads, no re-check, no reload; nothing newer at either verdict ⇒ three reads, no reload, a later `load` re-arms nothing; newer marker at the first verdict ⇒ one reload, no re-check; unavailable ⇒ no reload + one warn; remount ⇒ fresh baselines; `?folder=` / prop absent ⇒ inert). e2e `code-surface.spec.ts` carries both arms against the per-run `XDG_STATE_HOME` the harness forwards to the spec and the backend alike: the NEGATIVE arm ("a confirming bridge host record suppresses the rescue reload (exactly one iframe load)") writes a fake pid-alive host record after the baseline read and asserts exactly one `load`; the POSITIVE arm ("a newer empty-boot marker reloads the frame exactly once (positive rescue arm)") writes a fake pid-alive marker under `${XDG_STATE_HOME}/run-kit/cb/boots/` after the baseline read and asserts exactly two `load`s across the verdict + re-check window. `scripts/test-e2e.sh` makes the backend's `installed` answer deterministic: it plants a fixture bridge-extension manifest (`run-kit.rk-code-bridge-0.0.0-e2e/package.json`) under a per-run `XDG_DATA_HOME` and forwards that variable ONLY to the dev-server launch line, never to the Playwright run — the rig's only `XDG_DATA_HOME` reader is the backend's `codeserver.ExtensionsDir` derivation (260910-74q0-code-tile-first-boot-rescue-reload, 260910-oa3c-code-rescue-positive-signal-record-ownership).

### The code root — `@rk_win_code_root` seed + follow

The folder the editor opens is the shared, per-window tmux option **`@rk_win_code_root`** (surfaced on the payload as `codeRoot`), never the live SSE derivation. `gitRoot` is re-derived per tick from the ACTIVE pane's cwd (backend `deriveGitRoot` — the git toplevel when found, else the pane's raw cwd), so a pane switch or a `cd` would otherwise retarget the embedded editor to another workspace, taking in-flight editor state with it (open tabs, dirty buffers, undo stacks). Derivation's only job is to SEED. Because the state is a window option, every viewer of the tab renders the same folder and a snapshot restore carries it with the window. (260813-if5d, iip5)

- **Module** — `lib/code-folder-latch.ts` is pure and DOM-free with colocated tests (the `window-view.ts` / `right-panel.ts` module contract): `codeRootFor(win)` = `win?.codeRoot || win?.gitRoot || ""` — the folder the code surface opens and the availability predicate's input — and `codeRootSeed(win, layout)` = `layout.order.includes("code") && !win?.codeRoot && win?.gitRoot ? win.gitRoot : null` — the seed decision.
- **Seed rule — derivation runs exactly once** — the seed POSTs `setWindowOptions({ "@rk_win_code_root": gitRoot })` the first time the code surface actually RENDERS for a window whose `codeRoot` is empty, keyed on `layout.order.includes("code")`, the choke point every entry path resolves through (the surface toggles, `View: Code`, the mobile switch group). Availability alone seeds nothing: an offered-but-never-opened code lens is not an open editor. An empty derivation seeds nothing either — but the derivation is empty only when no cwd is resolvable at all (a window with no panes and no worktree path); a window outside every repo derives its pane's raw cwd and offers the code surface on that folder. A per-window in-flight ref suppresses a second POST while the payload still reads empty (the SSE tick arrives after the POST); after seeding, derivation never moves the editor — not on a pane switch, not on tile close/reopen, not on reload.
- **Follow rule — the editor's own navigation and the shell move it** — `CodeSurface`'s `load`-event seam (the same one the chord reclaim re-attaches on) also reads the same-origin `contentWindow.location`, parses `folder`, and reports it via `onFolderNavigated` when present, non-empty, and different (decoded comparison) from the current folder — a frame at `?workspace=…` carries no `folder` param, so the seam stays silent on the primary form; `SurfaceLayout` passes it through as `onCodeFolderNavigated` and `app.tsx`'s handler (a no-op when the folder equals the current root): (1) POSTs `setWindowOptions({ "@rk_win_code_root": folder })` as before, (2) re-fetches the workspace path for the new root, and (3) re-navigates the LIVE frame to the new `?workspace=` URL via the nonce-keyed `followSrc` prop — one of the two sanctioned parent re-navigations (§ Design Decisions → Two sanctioned parent re-navigations); a failed follow fetch leaves the editor at its own working `?folder=` navigation. So File > Open Folder inside code-server moves the shared code root AND restores the workspace identity the bare navigation dropped, while the terminal never moves the editor. The shell twin is `rk tab code set <folder>` — the same option write (`SetWindowOptions`; it never writes the workspace file — the GET is the single writer), so a CLI-set root repaints every viewer on the next option tick. The location read carries the attach's try/catch posture — a cross-origin or pre-load frame skips silently.
- **The render feed** — the payload record carries `codeRoot` directly, so `hasCode`, `availableTiles`, `degradeLayout`, the tile render guard, `tileMeta`, and the seed/fetch gating all read it with no substitution layer: `SurfaceLayout` computes `gitRoot={codeRootFor(win)}` for `CodeSurface` (the latch comparison baseline) and passes the hook-derived `codeSrc` down as `workspaceSrc`. A tab whose active pane left the repo keeps offering `code` (`hasCode` reads `codeRoot` as availability) and the editor stays on the shared root.
- **Stale roots are accepted** — a code root pointing at a deleted worktree renders code-server's own "folder does not exist" state; the escape is File > Open Folder, which moves the option via the follow write. No liveness probe, no reset verb, no palette entry.

(iip5)
- **e2e — `code-folder-latch.spec.ts`** — real tmux on the port-3020 rig with the `code-surface.spec.ts` code-server stub: a window with one pane inside a repo and one outside proves the first code-tile render seeds `@rk_win_code_root` (asserted via `_tmux.ts` `windowOption`), that the code tile survives the active pane leaving the repo and reopens at the seeded root across a reload (persistence is tmux's), and that the option is substrate state shared across viewers. ## GUI Surface (the `gui` lens renderer)

`app/frontend/src/components/gui-surface.tsx` — the renderer for the **`gui` surface/lens** (§ Window Views (Lens Model); spec `docs/specs/gui.md`), mounted as a tile by `SurfaceLayout`'s `case "gui"` and **lazy-loaded** (`export default` + `React.lazy` with a `Suspense` fallback styled like `code-surface-pending`) so tabs that never open a gui tile never pay for noVNC's ~150 KB core. The component embeds the host desktop through **noVNC's `RFB` class on a bare host `<div>`** (no `vnc.html` iframe — the library gives rk the focus/chord seams without a cross-document boundary), connecting to the **absolute** `ws(s)://<location.host>/ws/gui/host` URL built from `location` (never a relative path — the embed must work behind any proxy). The backend contract (the switch, supervisor, relay, payload) lives in [gui](/run-kit/gui.md). (o2sp)

**The `gui` signal — `useGui()`**: `contexts/session-context.tsx` handles the host-global `event: gui` socket slot in its own context (the `CodeServerContext` precedent): the payload is a LIST (`[]gui.StreamEntry`), narrowed to the `id === "host"` entry (fallback `[0]`) field-by-field with type guards (`enabled`/`reachable` booleans, `backend`/`display`/`wm`/`geometry` strings, `width`/`height`/`viewers` numbers — a malformed payload narrows to safe `false`/`""`/`0` defaults, never throws; a missing or non-string `geometry` reads `""`, the `wm` narrowing's shape (zuci)), deduped on the raw payload string so the every-tick broadcast does not re-render consumers. `useGui(): GuiSignal | null` returns `null` before the first event, which reads as **not available** — the opposite of `useCodeServer`'s null semantics, because the gui surface is never on by default and a late replay must not flash a button (D3).

**Availability — the 4-kind registry**: `lib/window-view.ts` exports `GuiHost = { enabled: boolean } | null | undefined` and `hasGui(host)` (`host?.enabled === true`); `availableViews(win, host?)` pushes `gui` when it holds, and `HINT_ORDER` is `[code, gui, web, tty]`. `lib/surface-layout.ts`'s `availableTiles(win, host?)` pushes `gui` **last** (the ⌘4 position) iff `hasGui(host)`; `degradeLayout`/`effectiveLayout(win, host?)` and `lib/right-panel.ts`'s `availableSurfaces(win, host?)` thread the same optional arg. Only `enabled` gates availability — `reachable`, `backend`, and `viewers` select the tile's CONTENT, never its existence (the code split). The host signal arrives as an **argument, not a store read**, so the pure modules stay DOM-free and colocated-testable (§ Design Decisions → Host signal is an argument, not a store read). `SURFACE_LABEL.gui = "GUI"`; `SURFACE_GLYPH.gui = "[]"` (the 2-char ASCII window frame, matching the `>_` / `://` / `{}` grammar); `SURFACE_KINDS` gains `"gui"`, so `parseLayout("split-h:tty,gui")` parses and the backend `layoutspec` registry accepts gui-bearing `@rk_win_layout` writes ([backend-packages](/run-kit/architecture/backend-packages.md) § Backend Libraries). **Off degrades, on restores, the option is never written**: with the switch off, `split-h:tty,gui` degrades to `single:tty` through the existing collapse while `@rk_win_layout` stays as written; when the payload flips `enabled: true` the same option renders the gui tile again — no `/options` write on either transition. Every toggle/palette/chord path keys off the same `availableTiles` result, so the 4th top-bar button, the overflow Tiles row, and the mobile switch group appear and disappear on the stream alone, with no gui-specific branch in `SurfaceToggleGroup`.

## Window Views (Lens Model)

The model (`docs/specs/window-views.md`, rules R1–R7; arrangement generalized by `docs/specs/surface-layout.md`): **a window ROW is a substrate** (a supervised tmux pane); **a VIEW is a lens** over one derivable output of that pane (the tty is a lens; an iframe of the pane's HTTP service is a lens; later: `gui`, the host desktop — `docs/specs/gui.md`). **Which lenses a window offers is a derived capability set; which surfaces the tab shows is shared tab state** — the surface layout (§ Surface Layout) carried in the `@rk_win_layout` window option, never part of the window's identity; only a viewer's zoom/single-tile choice is per-viewer client state. A single-tile layout IS the exclusive-lens view: `single:web` is "the web lens", `single:tty` the default terminal. The frontend is a renderer of the payload — the `@rk_win_layout`/`@rk_win_web_<n>`/`@rk_win_code_root` options and `POST /options` carry the layout and content addresses; the SSE payload carries `layout`/`webTabs`/`webActive`/`codeRoot`/`agentProvider`. (260714-t97o, 260714-r7rq, iip5, 260904-bf1l-agent-session-identity-rename)

Four lenses are implemented: `tty` (always available, `TerminalClient`), `web` (ALWAYS available, like `tty` — `hasWebUrl` selects its CONTENT: the onboarding state when the web-tab family is empty, the live iframe when the active tab carries an address; `IframeWindow`, § Iframe Window → Onboarding state), `code` (available when `codeRootFor(win)` is non-empty — the shared `@rk_win_code_root` or a derived `gitRoot`; the stable capability signal; `CodeSurface`, § Code Surface), and `gui` (available exactly when the host-global `event: gui` signal's `enabled` is true — a per-HOST capability threaded into the helpers as an optional arg; `GuiSurface`, § GUI Surface). Capabilities are orthogonal and STACK (spec R5): one window can offer `tty`+`web`+`code`+`gui` at once, and the layout can tile up to three of them at once (§ Surface Layout). The lens set IS the layout's tileable surface set (`SurfaceKind = ViewName`). There is no default-view hint: a web-first window carries an explicit `single:web` `@rk_win_layout` value (stamped at creation by the `rkType:"iframe"` arm, or by the retired-`@rk_win_lens` migration/dual-read). (iip5)

### Pure view-model helper — `lib/window-view.ts`

The single source of lens CAPABILITY logic — pure, DOM-free, colocated `window-view.test.ts` (the same pattern as `window-transition.ts`/`navigation.ts`). `surface-layout.ts` builds its availability set on these predicates, so the toggles, the layout, and the palette share one capability source (no drift). Helpers take a minimal structural `{ layout?, webTabs?, webActive?, codeRoot?, gitRoot? }` shape (`ViewWindow`, assignable from `WindowInfo`):

- **`ViewName = "tty" | "web" | "code" | "gui"`** — the lens union; aliased as the layout's `SurfaceKind`.
- **`GuiHost` / `hasGui(host)`** — the host-global gui signal the availability helpers consult (`{ enabled: boolean } | null | undefined`): absent/null reads as NOT available (never on by default — D3). Only `enabled` gates; `reachable`/`backend`/`viewers` select content, never presence.
- **`hasWebUrl(win)` / `hasCode(win)`** — web's CONTENT selector plus the code capability predicate: `hasWebUrl` is `(win?.webTabs?.length ?? 0) > 0` and gates NOTHING about availability — web is always available (below); it selects the web tile's content (onboarding vs live iframe — an empty web-tab family renders onboarding, never a blank-src iframe) and drives the web toggle's corner dot (§ Surface Toggles); for `code`, `(win?.codeRoot || win?.gitRoot)` non-empty — the shared `@rk_win_code_root` OR the live derivation, so a window whose code root is seeded keeps offering `code` after its active pane leaves the repo (the port is always resolvable by convention, so there is no configured-port leg); code-server REACHABILITY is deliberately NOT in this gate (it fluctuates and would strobe the toggles/palette; it selects the surface's content instead, § Code Surface).
- **`activeWebUrl(win): string`** — `webTabs[(webActive >= 1 ? webActive : 1) - 1] ?? ""`: the address the single web tile shows as its ACTIVE tab (empty family or out-of-range pointer → slot 1 / `""`). The tile header's display form reads it; `IframeWindow` derives the same value internally from its `tabs`/`active` props. (iip5, 9kip)
- **`availableViews(win, host?): ViewName[]`** (spec R1/R3) — `["tty"]`, plus `"web"` UNCONDITIONALLY (always available; `hasWebUrl` selects content, never availability), plus `"code"` when `hasCode`, plus `"gui"` when `hasGui(host)`. **Availability is decoupled from `@rk_win_lens`**: an iframe-created window with no URL offers `tty` + `web` (the web tile renders its onboarding state). Returned in the registry's fixed order via a `HINT_ORDER` (`[code, gui, web, tty]`) filter — so a fully-stacked window yields `["code","gui","web","tty"]` (`HINT_ORDER` is purely the capability ordering; there is no default-view hint). The layout module's `availableTiles` re-derives the same set tty-first (§ Surface Layout).
- Input gating for the lens chord is **not** a `window-view.ts` concern: the shared `shouldSuppressChord` predicate in `lib/keybindings.ts` gates every app chord (§ Keyboard Shortcuts → Dispatch seams).

## Surface Layout (the center is a layout of tiles)

The terminal route's center is a **layout manager** (`docs/specs/surface-layout.md`): a resolved **layout** `(shape, order, ratios)` renders as 1–3 **tiles**, each mounting an existing surface renderer unchanged. `docs/specs/right-panel.md`'s P6 slot mechanics do not apply to the layout manager; its availability derivation and P4 attention do (§ Surface Toggles). A **surface** is a (substrate, lens) pair of the ROUTE window; the tileable set is `tty | web | code | gui` (`SurfaceKind = ViewName` — § Window Views (Lens Model)); `tty` is `(current window, tty)`, always available, listed first. (260812-ab5v) Tiles are content-area state; the toggles that open and close them live in the top bar (§ Surface Toggles).

### The model — preset shapes × ordered surfaces × ratios

- **Shapes** (`SHAPE_ARITY`): `single` (1), `split-h` / `split-v` (2), `row` / `col` / `main-left` / `main-right` / `main-top` (3). Slot A (first in `order`) is the main slot in `main-*` shapes. A layout carries exactly its shape's arity. Max 3 tiles (Constitution IV); presets, never free split trees.
- **Order** — 1–3 surface kinds; kinds MUST NOT repeat within a layout **except `tty`** (the muxed `/ws/terminals` relay supports N clients per pane, so duplicate tty tiles of one window are legal; only the FIRST tty tile receives the shared `wsRef`/`focusRef`).
- **Ratios** — divider positions, per-viewer localStorage ONLY, keyed `rk-layout-ratios:{server}:{windowId}:{shape}` (a ratio is meaningless across shapes), written on drag RELEASE; never in the URL. Clamped by the shape-aware `clampBoundary` (`lib/right-panel.ts` § layout-divider clamp, composing `clampRatio`'s `MIN_PANEL_WIDTH_PX` 280px floor on the boundary's OWN axis): sibling-boundary chaining — a divider may never cross or strand its neighbor, degenerating to `prev + floor` when the band inverts — applies to `row`/`col` only, the shapes whose two ratios share an axis; a `main-*` shape's two ratios live on DIFFERENT axes (main-left/right: ratio 0 = x column boundary, ratio 1 = y row boundary; main-top swaps them) and clamp independently to `[floor, 100 − floor]`, as does `split-*`'s single ratio — the other ratio never bounds them. (ek6j)
- **Zoom** — the one zoomed tile, per-viewer localStorage ONLY, keyed `rk-layout-zoom:{server}:{windowId}` storing a surface KIND (`readStoredZoom`/`writeStoredZoom`, try/catch-noop like ratios; a stored kind the layout no longer hosts reads/clears as unset). Desktop zoom resolves the kind to its first slot in the layout; the mobile single-tile switch reads the same key (§ Mobile slot-A + the top-bar switch group). Zen-initiated zoom rides the same seam (zen is a viewer posture). (iip5)

### Pure layout model — `lib/surface-layout.ts`

Pure, DOM-free module with colocated tests (the `window-view.ts` pattern — § Design Decisions → Layout helpers live in a pure module). Untrusted URL/localStorage strings are validated by guards on the parse path (no `as` casts):

- **`parseLayout` / `serializeLayout`** — `<shape>:<a>,<b>[,<c>]` round-trips byte-identically; rejects unknown shape/kind, arity mismatch, repeated non-tty kind (returns `null`). `ALL_SHAPES`, `shapesForArity(arity)` (the same-arity ring), `SURFACE_LABEL` / `SHAPE_LABEL` / `SURFACE_GLYPH` — shared copy for tile headers, the surface toggles' tooltips/aria, palette `Tile:`/`Layout:` entries, and the mobile switch group so none drift.
- **`effectiveLayout(win, host?)`** — THE resolution: `degradeLayout(parseLayout(win?.layout), win, host) ?? { shape: "single", order: ["tty"] }`. The payload's raw `@rk_win_layout` string is the single source; an unset, malformed, or fully-unavailable value renders `single:tty`, and the option itself is NEVER rewritten by degradation (the author sees their mistake with `show-options`). Because kind validation is parse-time, a stored value carrying a kind that has left the registry fails `parseLayout` wholesale (a multi-tile layout degrades whole, not member-by-member) and heals to `single:tty` — the stale option value is overwritten on the next layout write; no option migration sweep exists. (iip5)
- **Availability degradation (`degradeLayout`)** — an unavailable surface drops out TILE-BY-TILE: the remaining order renders in the matching smaller-arity shape (3→2 `split-h`, 2→1 `single`, slot A kept). No broken iframe ever mounts. `tty` and `web` never degrade — both are always available, so a `…web…` layout on a URL-less window keeps its web tile (rendering the onboarding state, § Iframe Window → Onboarding state). `gui` degrades with the threaded host signal's `enabled` — off ⇒ the gui tile drops out of the rendered layout while `@rk_win_layout` keeps its value, on ⇒ the same option renders the tile again, with no write on either transition (§ GUI Surface).
- **`availableTiles(win, host?)`** — the shared registry rail in shortcut order (`tty`, `code`, `web`, then `gui` iff `hasGui(host)`); `SURFACE_LABEL`/`SURFACE_GLYPH` carry the gui rows (`GUI` / `[]`).
- **The inbound translation mapper** — `translateLegacyParams(view, panel)`: `?view=X` → `single:X`; `?view=X&panel=Y` → `split-h:X,Y`; bare `?panel=Y` → `split-h:tty,Y`. A pure param→layout-string mapper whose only consumer is the one-shot route-entry translation (§ `app.tsx` integration) — inbound-only for one release, removed by the follow-up cleanup change. Beside it, the pure `legacyTranslationDecision({carried, storedLayout, storedLegacy, winLayout})` folds the four candidate sources into `{ write?: string; dropParams: boolean }` — the translation's decision table, unit-tested without React. (iip5)
- **Mutations** (all pure): `promote` (surface → slot A; order permutes, shape unchanged), `swapWithNext`, `closeSurface` (arity collapse, slot A kept; `null` when closing the last tile — disallowed), `addSurface` (1→2 `split-h`, 2→3 `main-left`; `null` at 3), `cycleShape` (next same-arity preset, order kept — tmux `next-layout` muscle memory), `setShape`. The `rk tab layout` CLI verbs are the shell twins of these mutations: `internal/layoutspec` ports them case-for-case to Go (named sentinel errors where the TS returns `null`), so the frontend's `applyLayout` POST path and the shell verbs share one growth/collapse table (260829-c143).
- **Storage** — per-viewer only: the ratios key above + `rk-layout-zoom:{server}:{windowId}` (the zoomed surface KIND — `zoomStorageKey`/`readStoredZoom`/`writeStoredZoom`, kind-validated reads, `null` clears; § The model → Zoom). All reads/writes try/catch-noop. There is NO layout persistence in localStorage — the layout itself is `@rk_win_layout`. (iip5)

### `app.tsx` integration — derivation, optimistic write, one-shot translation

One layout-state block (§ Window Views → app.tsx integration): `baseLayout = useMemo(() => effectiveLayout(effectiveWindow, gui), [effectiveWindow, gui])` — the layout is DERIVED from the payload plus the host-global `useGui()` signal, never a `useState` copy and never a localStorage/URL read. **`applyLayout(next)` is the ONE mutation path** — `setWindowOptions(server, windowParam, { "@rk_win_layout": serializeLayout(next) })` through the unified `/options` seam, with no navigation and no localStorage write; tile verbs, the surface toggles, the ▦ chip, and the palette `View:` actions all funnel through it. The render is OPTIMISTIC: a `pendingLayout { key, value }` state (key = `` `${server}:${windowId}` ``) is set before the POST, and the rendered layout is `effectiveLayout({ ...effectiveWindow, layout: pendingLayout.value }, gui)` while the key matches — cleared when the SSE payload's `layout` equals the pending value, on POST rejection (revert to the payload value; the mutation-feedback path surfaces the failure), or on a route change. Degradation still applies to the pending value, so the tiles reorder immediately and never flicker back when the tick confirms. Internal navigation (sidebar, ▾ switcher, palette) targets the bare route (§ Window Views → Internal navigation targets the bare route); layout consumers read the derived layout, never parse `location.search`. `togglePanel(surface)` is the toggle behind the top-bar group, the overflow Tiles rows, and the palette `Tile: Show/Hide` entries: open surface → `closeSurface`, closed → `addSurface`, then `applyLayout` (a `null` mutation — closing the last tile — is a no-op).

**One-shot legacy translation (one release)** — a single effect per `(server, windowParam)` arrival, gated on `effectiveWindow !== null`, folds every retired layout carrier into the option: compute `carried = search.layout ?? translateLegacyParams(search.view, search.panel)`, the retired `rk-layout:{server}:{@N}` localStorage value, and `translateLegacyParams(readStoredView(…), readStoredPanel(…))`; when `win.layout` is empty, `legacyTranslationDecision` picks the winner (URL params > `rk-layout:` key > legacy view/panel keys) and exactly one POST writes it (a per-key in-flight ref suppresses a second fire while the payload still reads empty); when `win.layout` is set, nothing is written — the shared layout wins over any carried param. Both arms then navigate `replace: true` to the bare route when the URL carried any of the three params and delete exactly the four matching keys (`rk-layout:`, `runkit-window-view:`, `runkit-window-panel:`, `runkit-code-folder:` for this window only — never a prefix sweep); the code-folder arm POSTs `@rk_win_code_root` from a surviving `runkit-code-folder:` value when `win.codeRoot` is empty (§ Code Surface → The code root). Nothing in the frontend writes `?layout=` anymore; history entries are bare routes. (iip5)

### Present expansion — the layout write is the expand

`rk present` has NO client-side reaction: it is sugar over `rk tab web add <target> --show` — the CLI writes the web-tab slot AND the shared layout itself (the `webAddShow` helper: `WebAdd`, then `@rk_win_layout` gaining `web` when absent — grown through the ordinary table, a full 3-tile layout yielding its last slot — then `WebSelect(n)`). An agent or any external writer can equally expand by hand — `tmux set-option -w @rk_win_layout …`, `rk tab layout --add web`, or `rk tab web select <n>`. Every mounted viewer of the window repaints on the next option tick with no client-side state machine — the frontend renders `@rk_win_layout`, so any writer's expansion IS the render. Closing the revealed web tile POSTs the layout without it, which every viewer renders too. The frontend's own open-a-URL-in-tile sequence is the help-topic path (§ Help-topic open path below): it issues the same tab-add, layout, and select writes through the HTTP API, and every viewer repaints from the options exactly as after a CLI present. (iip5, 260829-c143)

### Help-topic open path — the frontend counterpart of `rk present`

The chevron menu's `Help topics` rows ([top-bar](/run-kit/ui/top-bar.md) § Help topics disclosure) and the six `Help: <topic>` palette actions ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) open a curated `https://shll.ai/…` documentation page in the CURRENT window's web tile through `openHelpTopic(topic)` in `lib/help-topics.ts` — a pure, React-free module with colocated tests that owns the `HELP_TOPICS` registry, the `helpTopicActionId`/`helpTopicPaletteLabel` derivations, the `HELP_TOPIC_EVENT` name (`rk:help-topic`), and the `isHelpTopic` detail guard. Every registered URL is framable (shll.ai is served by GitHub Pages and sends neither `X-Frame-Options` nor a frame-ancestors CSP), which is what lets the web tile's iframe render it.

`openHelpTopic` dispatches a cancelable `rk:help-topic` CustomEvent on `window` with the topic as `detail`. When `dispatchEvent` returns `false` (a listener cancelled it) the topic was taken in-tile and the dispatcher does nothing more; otherwise it falls back to `window.open(topic.url, "_blank", "noopener,noreferrer")` — the same call the `Help: Documentation` entry makes, so external navigation never unloads the live dashboard. `AppShell` (`app.tsx`) is the sole listener, registered only while `windowParam` is set (a terminal route with a current window) and removed on unmount or when the window clears, so on board, server, and host routes nobody cancels and the dispatcher opens a browser tab itself. The handler is `webAddShow` re-expressed client-side over existing pieces: it calls `event.preventDefault()` SYNCHRONOUSLY (the dispatcher decides on the return value, so an async cancel would arrive too late) and, still synchronously, decides the full-layout case — when `web` is absent from the layout and `addSurface(layout, "web")` is `null` (three tiles already) it opens `topic.url` through the same `window.open` fallback BEFORE any request is awaited, because `window.open` rides the click's transient user activation, which browsers revoke once the handler yields (a post-request open is what popup blockers return `null` for). Then (1) `addWebTab(server, windowParam, topic.url)` — `POST /api/windows/{id}/web`; the server dedupes an identical stored address and answers with the existing index and `existed: true`, so a re-open never grows the family — after which the full-layout case stops: the tab stays added for later, and NO layout write and no select happen (§ Design Decisions → The help-topic path does not yield a slot on a full layout); otherwise (2) ensures a web surface: on mobile (`isMobile`) it calls `switchToTile("web")` (the same add mutation plus the per-viewer zoom key, so the phone shows the tile) and on desktop `applyLayout(addSurface(layout, "web"))` when `web` was absent — and (3) `selectWebTab(server, windowParam, index)` — `POST /api/windows/{id}/web/{n}/select` — so the topic is the active tab even when it already existed. Any rejection (the family-cap 409's `error` text included) surfaces via `useToast()` as `addToast(err.message || "Failed to open help topic", "error")` and leaves the layout unchanged. The writes land in the same tmux options `rk present` writes (`@rk_win_web_<n>`, `@rk_win_layout`, `@rk_win_web_active`), so every mounted viewer of the window repaints on the option tick with no client-side state machine (§ Present expansion above). (260910-58al)

### Tile renderer — `components/surface-layout.tsx`

Presentational by contract: (shape, order) state lives in `app.tsx` and arrives as the `layout` prop; the component owns only transient interaction state — zoom, the focused slot, the in-flight ratio drag, the mount-once bookkeeping. `app.tsx` keys it by `server` (a same-server window switch keeps the grid mounted and re-renders it with a new `windowId` prop; only a server change remounts). Per-window transient state resets in ONE effect keyed on `[server, windowId]`, guarded against first mount (the `useState` initializers already seed the first window's values): the hide-never-unmount set (re-seeded from the new window's `layout.order`), zoom (re-derived from the new window's stored zoom key), the focused slot (back to slot A, the kind re-reported through `onFocusedKindChange`), the web page title, tty progress (idle, pending rAF commit cancelled), and the find state (closed and cleared, decorations dropped, no focus grab); ratios and the web-tab override keep their own keyed effects. Non-tty tiles (web, code, gui) carry `windowId` in their React key and remount per window; the tty tile's key is window-independent so its `TerminalClient` (xterm instance + relay stream) survives a same-session switch — [terminal](/run-kit/ui/terminal.md) § Terminal Relay. (260910-0awz)

Buttons are LIT (`aria-pressed`, accent-green border/text/10% bg) for every OPEN tile (`layout.order`), and every button's corner dot is PER-SURFACE via the caller's `showDot` predicate (`app.tsx`: web's dot means "has content" and renders only when the web-tab family is non-empty; gui's dot is VNC health — the live RFB connection state reported by the tile via `onGuiConnection`, falling back to the signal's `reachable` when no tile is open (R6); every other surface's dot is always-on; the overflow Tiles rows carry no dot) (260821-zqlq). Clicking an unlit button ADDS the surface (`addSurface` — 1→2 `split-h`, 2→3 `main-left`); clicking a lit one CLOSES its tile (`closeSurface` — the arity collapse). The caller (`app.tsx`'s `togglePanel`) runs the pure mutation + the `applyLayout` option POST; a disallowed mutation (closing the last tile) is a `null` no-op there. At 3 open tiles the remaining unlit buttons render DISABLED with a "Close a tile first" tooltip (the max-3 constraint must be visible, never a silent no-op); the `Tip` wraps a span so the disabled button's tooltip still fires (disabled buttons swallow pointer events).
- **Switch group (SWITCH mode, mobile)** — the same component and button grammar forked by the slot prop's `mode` discriminant: lit = the VISIBLE tile (exactly one — radio semantics), tapping an unlit button runs the switch-to-tile verb (§ Mobile slot-A + the top-bar switch group), tapping the lit one is a no-op, and the disabled-at-3 state never applies (switching never adds a tile). The group renders only when ≥2 surfaces survive the hidden filter and is `pinned` in-bar (never overflows; no Tiles menu rows on mobile). (260816-ox16-mobile-tile-switch-vocab)
- **Icon glyphs, labels in tooltips** — `>_` tty, `://` web, `{}` code, `[]` gui (the shared `SURFACE_GLYPH` map in `surface-layout.ts`); the text labels live in the `Tip` tooltips and the `<Label> tile` aria-labels (e2e hooks).
- **Availability + attention dots** (right-panel P4): a collapsed or absent tile may hide content, never state that wants a human.
- **`tty` toggle** — the tty surface's button, present on every window (tty is always available).
- **`lib/right-panel.ts`** keeps the SHARED surface registry — `type SurfaceName = SurfaceKind` and `availableSurfaces(win, host?)` (`tty` first, then `code`/`web`, then `gui` when the threaded host signal's `enabled` holds, per the `window-view.ts` capability predicates) — so the toggles, the layout, and the palette read one availability source, plus the shape-aware `clampBoundary` (composing `clampRatio`/`MIN_PANEL_WIDTH_PX`) for the tile dividers and `readStoredPanel`/`panelStorageKey` — the READ-only legacy `runkit-window-panel` input to the one-shot route-entry translation (nothing writes that key; absent simply means no legacy state; removed by the follow-up cleanup change). (260814-6b0j, iip5)
- **⌘1/⌘2/⌘3/⌘4 / ⇧Ctrl+1/2/3/4 (`tty-toggle` / `code-toggle` / `web-toggle` / `gui-toggle`)** — the stateful tile chords, one per surface kind in tile order ([keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Stateful surface chords): hidden → open via `togglePanel(kind)` + focus once the tile lands (the per-kind landing flag); visible-unfocused → focus via the `focusTileRef` seam; focused → hide via `togglePanel(kind)` + `restoreFocus` (a no-op at arity 1, mirroring the palette's `Tile: Hide` omission on `single` layouts). Gated on a desktop window route with the surface available — for `web` that is ALWAYS (the surface is always tileable, § Window Views), so ⌘3 mounts on every desktop window route; for the other surfaces a window without the surface mounts no handler and the chord falls through untouched (with the gui switch off, ⌘4 is inert — § Design Decisions → Stateful digit chords toggle the surface tiles; `` ⌃` `` hops tty↔code focus).
- **``⌃` `` / ``⇧Ctrl+` `` (`focus-hop`)** — hops focus between the tty and code tiles through the same focus-by-kind seam as `Tile: Focus <Surface>`, gated on a desktop window route with the code surface available; a closed-but-available code tile opens first (open-then-focus — [focus-ownership](/run-kit/ui/focus-ownership.md)).

## Design Decisions

### Host signal is an argument, not a store read
**Decision**: `availableTiles(win, host?)` / `effectiveLayout(win, host?)` / `availableViews(win, host?)` / `availableSurfaces(win, host?)` take the gui host signal as an optional second argument; `app.tsx` reads `useGui()` once and threads it down.
**Why**: keeps `lib/window-view.ts` / `lib/surface-layout.ts` pure and DOM-free so the colocated unit tests stay drift-free; `ViewWindow` stays per-window because gui availability is per-host.
**Rejected**: a module-level store or context read inside the pure helpers (untestable without React); a synthetic `gui` field on `ViewWindow` (lies about ownership).
*Introduced by*: 260909-o2sp-gui-surface-tile

### Visibility, not focus, gates the RFB connection
**Decision**: the gui tile disconnects after 15 s of not-visible (zoomed away or document hidden) and reconnects on the next visible; focus loss alone never disconnects.
**Why**: noVNC has no pause API; disconnecting when hidden stops framebuffer traffic and releases the relay `viewers` count so the backend probe resumes; focus loss is constant in a multi-tile layout and must not flap the connection.
**Rejected**: disconnect on blur (flaps); keep connected while hidden (wastes bandwidth on phones, keeps the probe suppressed).
*Introduced by*: 260909-o2sp-gui-surface-tile

### The gui chord gate is same-document capture, no steal guard
**Decision**: a capture-phase keydown on the canvas wrapper stops rk chords before noVNC's canvas handler and re-dispatches them on the parent document; no `onProgrammaticFocus` seam is wired.
**Why**: the canvas is in rk's own document, so the iframe re-dispatch dance's cross-document half is unnecessary (the re-dispatch still matters — the dispatcher listens in the bubble phase); noVNC only takes focus on click (`focusOnClick`), so there is no load-time grab to guard.
**Rejected**: reusing the iframe contentDocument reclaim verbatim (no frame here); disabling noVNC's keyboard entirely (breaks the guest).
*Introduced by*: 260909-o2sp-gui-surface-tile

### The bare-WM strip and launch rows hide on the screen-sharing backend
**Decision**: the gui tile's bare-WM strip and the palette's `GUI: Open …` rows require `backend !== "screen-sharing"` in addition to `enabled && reachable` (and `wm === ""` for the strip).
**Why**: the macOS mirror backend stamps no window manager, so `wm` is `""` there by construction and every macOS viewer would otherwise see a false "no window manager" strip; the mirror is view-only with no X display, so a launch can only miss.
**Rejected**: keying on `wm_hint` presence alone (the backend also fills it on darwin, so it does not discriminate); a backend change to stamp a sentinel (the backend's macOS branch stays untouched).
*Introduced by*: 260910-vu4p-gui-desktop-tile-strip-and-palette

### The strip's install line rides the status document, fetched once per bare transition
**Decision**: the tile fetches `GET /api/gui/host` once when the bare condition becomes true and reads `wm_hint`; the strip renders without the line (and without Copy) while it is unknown.
**Why**: the stream entry carries `wm` but not the hint; the hint is package-manager-aware wording built server-side, so the frontend must not hardcode `sudo apt …`; the once-per-transition never-poll rule is the tile's existing grammar for the unreachable reason.
**Rejected**: adding `wm_hint` to the stream entry (a backend change, and per-tick repetition of a static string); hardcoding the apt line in the frontend (wrong on dnf/pacman hosts).
*Introduced by*: 260910-vu4p-gui-desktop-tile-strip-and-palette

### The bare-WM strip is a flex sibling above the noVNC host, never an overlay
**Decision**: the strip renders as a flex-row child before the `flex-1 min-h-0` host div inside the existing `flex-col` canvas wrapper.
**Why**: noVNC observes the host div for `scaleViewport`/`resizeSession`, so the flex layout subtracts the strip from the fit and SetDesktopSize sees the reduced height without any measurement code; an overlay would hide desktop pixels behind text.
**Rejected**: an absolute-positioned banner (covers the taskbar area of the desktop); measuring the strip and passing an offset to noVNC (unnecessary — the layout already does it).
*Introduced by*: 260910-vu4p-gui-desktop-tile-strip-and-palette

### Sibling-boundary chaining is a row/col property, decided in the clamp
**Decision**: `clampBoundary(shape, …)` in `lib/right-panel.ts` owns the whole boundary band: it chains neighbor ratios as bounds only for `row`/`col` (same-axis dividers) and clamps every other shape's ratio to `clampRatio`'s own-axis `[floor, 100 − floor]` band, with all three drag call sites (single-axis divider, intersection x, intersection y) passing the live `layout.shape`.
**Why**: A `main-*` shape's two ratios live on different axes, so an index-neighbor is not a spatial neighbor there — treating it as one couples the axes (a column ratio inflates the row seam's floor, pinning it outright on short viewports and letting horizontal intersection motion drive vertical size). Deciding chaining inside the exported pure helper keeps the invariant in one directly unit-testable place beside its floor math.
**Rejected**: A neighbors-only helper feeding a shape-blind clamp (splits one invariant across files, leaves the composed band untested); homing the helper in `lib/surface-layout.ts` (needs runtime imports from `right-panel.ts`, which already runtime-imports `availableTiles` back — a module cycle).
*Introduced by*: 260908-ek6j-fix-main-divider-cross-axis-clamp

### Draft tabs are viewer-local, not a stored sentinel
**Decision**: The empty-tab flow is client-side draft state that materializes into a real slot on first Enter; nothing lands in tmux until an address exists.
**Why**: A stored blank fights three spec decisions at once — identity-is-the-URL (two blanks collide with idempotent add), "absent and empty read alike as unset" (an empty option value cannot exist), and "declared only". The One Rule classes drafts as viewer preferences (the compose-draft class).
**Rejected**: An `about:blank`/`/newtab` sentinel URL — needs an idempotence exemption and makes blanks shared state with no shared content.
*Introduced by*: 260901-s36e-web-tab-strip-drafts-reorder

### Progress line is an absolute overlay, not an in-flow strip
**Decision**: The tty tile's 2px progress line renders inside a zero-height `relative` wrapper with an `absolute`, `pointer-events: none` 2px bar overlaying the content's top edge.
**Why**: The tile layout must not shift when progress appears, and — stronger — an in-flow strip would change the terminal container's height, firing `ResizeObserver → fit → PTY resize` churn on every task start/stop, which the window-switch machinery treats as a hard constraint (transform-only, no layout change).
**Rejected**: The web tile's in-flow `.rk-web-progress` form (fine over an iframe whose element's presence IS the loading state, resize-churn over xterm); reserving a permanent 2px row (burns 2px on every idle tile).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### One shared progress slot per window, wired on every tty mount
**Decision**: Progress is a single `SurfaceLayout` state slot (the `webPageTitle` precedent) fed by `onProgressChange` on every tty `TerminalClient` mount, primary and duplicates alike.
**Why**: All tty tiles show the same window, so per-tile state would duplicate identical values; wiring every mount keeps the signal alive when the primary tile is hidden (hide-never-unmount keeps its stream open), and duplicate firings fold idempotently under the rAF coalescing.
**Rejected**: Primary-tty-only wiring (loses updates in hidden-primary arrangements for no savings); per-tile state (duplication with no benefit).
*Introduced by*: 260819-1vxq-terminal-tile-progress

### Heading identifies the window, not the lens
**Decision**: the terminal-route center heading is a static `Tab: <name>` in every lens (tty/web/code/gui); lens identity is carried by the tile content and the top bar's lit tile toggles, not the heading.
**Why**: the heading identifies the WINDOW (the substrate), per window-views.md "rows are substrates, views are lenses". Keeping the prefix constant also stops the name's anchor from jumping on a lens switch (the prefix width does not change with the lens).
**Rejected**: a lens-following heading ("the center page heading follows the lens") — the prefix would flip on every lens switch and misidentify what the heading names.
*Introduced by*: 260714-uco1-topbar-heading-anchor-nav; static `Tab:` in every lens: 260820-lfla

### Two verb families on tile headers
**Decision**: Tile-header verbs split into layout verbs (generic, arity-gated) and content verbs (per-kind, any-arity, zoom-visible) — the tty tile carries a bordered pane segment holding Split H / Split V / Close Pane.
**Why**: Pane operations act on the tmux pane inside the tty tile; proximity is the disambiguation. The tile header is already per-kind on its left side (StatusDot, meta chips), so per-kind verbs on the right are an evolution, not a break.
**Rejected**: Keeping pane verbs in the top bar (target invisible on multi-tile layouts); moving only the splits; a confirm-on-close variant — the glyph+grouping distinction below was chosen.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### Page title crosses the component seam via a callback, kind stays derived
**Decision**: `IframeWindow` reports `{ title }` through an optional `onPageMeta` prop on the ACTIVE frame's `load`; `SurfaceLayout` holds it as state for the header. The kind badge is derived purely from the active web tab's address via `lib/web-url.ts` with no seam.
**Why**: the header is SurfaceLayout's render but only the mounted iframe can read `contentDocument.title`; a narrow optional callback matches the existing `onInteract`/`onFolderNavigated` seam shapes, and deriving the badge purely keeps it testable and SSE-consistent.
**Rejected**: rendering a second header inside `IframeWindow` (duplicates the tile-header contract) or lifting the whole iframe ref up (breaks the presentational-component boundary).
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Dead-port detection is a frontend same-origin fetch, not a proxy ErrorHandler
**Decision**: a dead proxied port is detected by `fetch`ing the proxied path from the frontend and reading the reverse proxy's 502, rendering the error state client-side.
**Why**: the proxy already answers 502 on connect failure (the default `ReverseProxy` error path); a same-origin fetch reads it with zero backend change and keeps `frame-check` scoped to absolute external URLs only.
**Rejected**: a custom `ErrorHandler` serving a styled error page from `proxy.go` — touches the proxy layer and couples error UI to the Go layer.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### Error states render over a hidden, still-mounted iframe
**Decision**: the tile's error surfaces render in place of the iframe's VISIBLE area while the iframe stays mounted under the `hidden` class.
**Why**: unmounting would strand the attach seam's mount-once listeners, forcing a remount dance on Retry; `hidden` satisfies "replace the iframe render" visually with zero seam churn.
**Rejected**: conditional unmount of the iframe — breaks the mount-once attach effect and complicates Retry.
*Introduced by*: 260819-v6y4-web-tile-browser-chrome

### `SurfaceLayout` owns zoom/drag/mount-once; `app.tsx` owns layout state
**Decision**: the tile renderer receives the derived layout as a prop and owns only per-viewer interaction state (zoom — persisted via the `rk-layout-zoom:` key, the in-flight ratio drag, the ever-opened mount bookkeeping); layout derivation from the payload, the optimistic `pendingLayout` overlay, and the `@rk_win_layout` write live in `app.tsx` behind the single `applyLayout` mutation path.
**Why**: layout state is route-integrated (the payload feed, the one-shot translation effect, navigation seams) and belongs beside the lens machinery; zoom and drag are self-contained viewer postures with no tmux footprint. Prop-in/callback-out composition keeps the renderer free of the router/storage import graph — tile chrome, verbs, and hide-never-unmount are unit-testable in jsdom — and new surface kinds slot in without touching the shell.
**Rejected**: the renderer importing storage/router helpers and owning layout derivation — two sources of truth for the layout (component + route) and untestable without mocking the router.
*Introduced by*: 260811-2r1w-right-panel-shell-web-surface (as the panel shell's contract); generalized to the tile renderer: 260812-ab5v-surface-layout-core; option-driven derivation: 260828-iip5-ui-state-frontend-layout-code-root

### Zoom key stores a surface kind
**Decision**: `rk-layout-zoom:{server}:{@N}` holds a `SurfaceKind`; desktop zoom resolves it to the first slot of that kind, and the mobile single-tile switch reads the same key as its visible-tile choice.
**Why**: one key serves desktop zoom and the kind-addressed mobile switch group; the spec phrases the clear rule as "the zoomed *surface* leaves the layout", which is kind-shaped. A phone's tile choice and a desktop's zoom are the same viewer posture at different widths.
**Rejected**: slot index — breaks the mobile switch group's kind addressing and survives a reorder pointing at the wrong tile. Duplicate-tty zoom independence (hand-written layouts only) is not persisted.
*Introduced by*: 260828-iip5-ui-state-frontend-layout-code-root

### Mobile switch to a not-open surface grows the shared layout
**Decision**: `switchToTile(kind)` for a kind not in the layout runs `addSurface` through `applyLayout` (one `@rk_win_layout` POST) and sets the local zoom key; `null` growth (arity 3 without the kind) is a disabled no-op. Switching to an already-open surface writes only the zoom key.
**Why**: the spec names the shared `--add` mutation for this case, and the one-rule demands a phone posture never destroy shared tab state — a not-open switch must grow the arrangement, not collapse it.
**Rejected**: the `single:<kind>` collapse — it rewrote every desktop viewer's arrangement from a phone; a transient swap for the not-open arm — it breaks code-root seeding (keyed on `layout.order.includes("code")`) and drops the persistence an explicit pick implies.
*Introduced by*: 260828-iip5-ui-state-frontend-layout-code-root

### Code-surface availability gates on stable signals; reachability gates content
**Decision**: `hasCode` — the availability gate for the `code` lens/tile — is stable signals only: `(win?.codeRoot || win?.gitRoot)` non-empty — the shared `@rk_win_code_root` OR a non-empty live derivation (the git toplevel when found, else the pane's raw cwd) (the code-server port is always resolvable by convention — preset `RK_CODE_SERVER_PORT` else `RK_PORT+2` — so a configured-port leg would be vacuous). The TTL-cached reachability probe never gates availability; it selects the surface's CONTENT (live iframe when up, the `code-server not running — check rk doctor` empty state when down).
**Why**: reachability fluctuates with code-server restarts — gating the surface toggle / switcher segment on it would strobe the affordances, and the not-running state could never render (the affordance would vanish exactly when its message is needed). The live derivation fluctuates too, with the ACTIVE PANE's cwd: a window whose editor is open would lose its surface toggle, switcher segment, and deep-link validity the moment an agent `cd`s out of the repo. The seeded `@rk_win_code_root` is what makes the signal genuinely stable per window; content states may fluctuate.
**Rejected**: availability = configured ∧ reachable (internally contradictory with the not-running state); availability = gitRoot ∧ port-configured (vacuous once the port resolves by convention); derivation-only availability (strobes with the terminal's cwd).
*Introduced by*: 260811-k3vp-right-panel-code-lens; gitRoot-only gate: 260811-a2bo-daemon-code-server-stable-route; seeded code root: 260828-iip5-ui-state-frontend-layout-code-root

### Web availability is unconditional; `hasWebUrl` selects the content
**Decision**: the `web` lens/tile is ALWAYS available (like `tty`) on every window; `hasWebUrl` selects the tile's CONTENT — an empty web-tab family renders the onboarding state (reduced live URL bar + the fill-path panel), a non-empty active tab renders the live iframe — exactly as code splits availability from reachability.
**Why**: a single `hasWebUrl` availability predicate gated six consumer surfaces (the ⌘3 chord, the top-bar toggle, palette `View:`/`Tile:` entries, the mobile switch group, deep-link degradation), making the tile undiscoverable before initialization; the availability-vs-content split is the codebase's named model for "the lens exists but has nothing to show", and the onboarding state doubles as the discoverability surface (its live address bar is itself an init path).
**Rejected**: a ⌘3-only carve-out (a chord opening a tile the availability model says doesn't exist — the layout resolver would drop the tile anyway, so the resolver, toggles, and palette would each need contradictory special-cases); a modal/tooltip explainer (no live address bar, no automatic flip).
*Introduced by*: 260821-zqlq-web-tile-always-tileable-onboarding

### The web toggle dot means "has content"
**Decision**: the web toggle button always renders (the surface is always available); its corner dot is driven by a per-surface `showDot` predicate (`app.tsx`: `surface !== "web" || hasWebUrl(win)`) — web's dot means "has content"; every other surface's dot stays always-on; the overflow Tiles rows carry no dot.
**Why**: the button's constant presence is the discoverability affordance; the dot carries the at-a-glance "something to see" signal that a conditionally-present button would otherwise convey.
**Rejected**: a dotless always-on web button (loses the content signal); hiding the button until content exists (recreates the discoverability hole).
*Introduced by*: 260821-zqlq-web-tile-always-tileable-onboarding

### The code surface is a lean `CodeSurface`, not an `IframeWindow` reuse
**Decision**: the `code` lens/surface renders a minimal component — an iframe of the derived `/code/?workspace=<path>` URL (the `?folder=` form survives only as the degrade path and the editor's own File > Open Folder navigation) plus the not-running empty and pending states — while `web` uses `IframeWindow` with its URL bar and refresh chrome.
**Why**: the code-server URL is fully derived (the stable `/code/` path plus the code root — no port, no editable address), so the URL bar (the web tab's substrate state — a shared, POSTed content address) is meaningless; reusing `IframeWindow` would drag inapplicable chrome and substrate semantics into a surface whose content address nobody edits. The relative-path discipline (`toProxySrc`'s convention — never compose an absolute origin) is the one piece reused.
**Rejected**: `IframeWindow` with a hidden URL bar (dead chrome, plus web-tab-address semantics that do not apply to a derived URL).
*Introduced by*: 260811-k3vp-right-panel-code-lens; stable `/code/` src: 260811-a2bo-daemon-code-server-stable-route

### Chord-reclaim via a capture-phase iframe `contentDocument` listener
**Decision**: Both iframe renderers (`CodeSurface`, `IframeWindow`) attach a capture-phase `keydown` listener to the same-origin iframe's `contentDocument` after every load (re-attached on each navigation, removed on cleanup, `contentDocument` access try/catch-guarded), reclaim exactly the events matching an injected `shouldReclaimChord` predicate — one curried factory in `app.tsx` (`reclaimChordForKind`) binds the registry's pure, kind-aware `hasReclaimableMatch` per surface kind; it carves out keydowns whose only matches are `ttyOnly` bindings and gates `webOnly` matches to the web kind — and re-dispatch a synthetic bubbling `KeyboardEvent` on the parent DOCUMENT.
**Why**: the `/proxy/` embed is same-origin by design, so a focused iframe's key events are reachable before the embedded app's keybinding service sees them; dispatching on the parent document reaches both document-level listeners (the palette's chord) and window-level ones (the keybinding dispatcher) in one event. Injecting the predicate keeps both components free of the registry import graph, one factory keeps the two kinds reading one registry, and reclaiming only REGISTRY chords leaves the embedded/framed app's own Ctrl/⌘ bindings working.
**Rejected**: dispatching on `window` (misses document-level listeners); reclaiming every chord (breaks VS Code's own bindings); shipping without reclaim (click-out-only escape leaves ⌘K dead whenever the editor has focus).
*Introduced by*: 260811-k3vp-right-panel-code-lens; shared with the web tile + kind-aware predicate: 260819-ie2i-web-tile-keyboard-find

### The find-bar open seam is a document CustomEvent
**Decision**: each find consumer's chord handler and palette body dispatch ONE document CustomEvent — `web-find:open` (`WEB_FIND_OPEN_EVENT`), received by the mounted `IframeWindow`, and `terminal-find:open` (`TERMINAL_FIND_OPEN_EVENT`, `lib/terminal-find.ts`), received by the mounted `SurfaceLayout` (the `window-heading:rename` / `theme-selector:open` precedent). The ⌕ buttons toggle locally.
**Why**: `IframeWindow` is presentational and the web find bar's state belongs inside it, and the tty bar's state belongs to the tile layer — a CustomEvent avoids threading an imperative ref through `SurfaceLayout` (or deeper) for one action; only one web tile exists per layout (kinds don't repeat except tty) and at most one terminal route's `SurfaceLayout` is mounted, so neither receiver is ambiguous — the ONE `IframeWindow` stays the single receiver however many tab frames it hosts, acting on the ACTIVE frame.
**Rejected**: a `findBarRef`/`openFindRef` threaded app.tsx → SurfaceLayout → consumer (touched signatures for one opener); lifting find state into app.tsx (drags search state into the shell for no consumer).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find; tty seam: 260819-zqf9-terminal-tile-find

### Highlight styling enters the frame as a `<style>` element, not injected script
**Decision**: the engine registers Highlight objects on the frame window's `CSS.highlights` and appends one `<style>` with `::highlight(rk-find)` / `::highlight(rk-find-active)` rules to the frame's head, removed/replaced on reset.
**Why**: `::highlight()` pseudo-elements must be styled in the document that owns the ranges; a style element is inert DOM (no execution), which honors the no-script-injection constraint while keeping the search fully parent-driven.
**Rejected**: `window.find()` as the primary (no match count, engine-inconsistent); wrapping matches in `<mark>` elements (mutates the framed page's DOM structure — breaks pages that read their own DOM, and unwinding on reset is error-prone).
*Introduced by*: 260819-ie2i-web-tile-keyboard-find

### Stateful digit chords toggle the surface tiles; `` ⌃` `` hops tty↔code focus

### Derivation seeds the code root once; only the editor moves it
**Decision**: The code surface's folder is the shared per-window tmux option `@rk_win_code_root`. The backend's live `gitRoot` derivation seeds it exactly once — at the code surface's first actual render for that window — and the only writer afterward is the editor's own navigation, reported back from the iframe's `load` event. The terminal never moves the editor.
**Why**: `gitRoot` follows the ACTIVE pane's cwd and agents `cd` constantly, so a live folder makes the terminal's movement move the editor: a pane leaving every repo unmounts the tile, and two panes in two repos swap the workbench between them — either way the editor's in-flight state (open tabs, dirty buffers, undo stacks) is expensive or impossible to recover. That defeats hide-never-unmount (P3), which exists precisely so the iframes keep their in-memory state. A window option makes the folder the tab's choice rather than the terminal's — and every viewer of the tab sees the same folder, a snapshot restore carries it, and no viewer-local store needs migrating (the one-shot route-entry effect folds any surviving per-browser latch into the option once).
**Rejected**: Stabilizing the backend derivation (first-pane-with-a-root wins) — still moves the editor whenever panes `cd`, so it is a mitigation, not a guarantee; re-deriving on tile close/reopen (seed only while open) — reopening after a `cd` is exactly when the editor must come back where it was; liveness probing a stale root — code-server's own "folder does not exist" state plus File > Open Folder is the escape.
*Introduced by*: 260813-if5d-latch-code-surface-folder; shared `@rk_win_code_root`: 260828-iip5-ui-state-frontend-layout-code-root

### Iframe src fixed per mount generation, never a parent `src` rewrite
**Decision**: `CodeSurface` computes its iframe `src` once per iframe mount generation — a ref keyed to the `reachable` gate that mounts the iframe — not reactively from the folder prop; a mounted frame is parent-navigated only through the two sanctioned re-navigations (the nonce-keyed `followSrc` and the first-boot rescue `reload()` — § Design Decisions → Two sanctioned parent re-navigations), neither of which rewrites the `src` ref of a live frame.
**Why**: P3 (hide, never unmount): React re-rendering a changed `src` attribute re-navigates a live frame, even to a URL the frame is already at, which would reload the editor on the very code-root follow write the editor just caused. Keying the computation to mount generation means a reachability `false→true` flip or a window-switch remount picks up the CURRENT workspace URL (fresh workbench, correct folder) while a mounted frame is never parent-navigated outside the sanctioned re-navigations. A ref rather than `useMemo` because a memo cache is a documented performance hint React may discard, and a dropped cache here would re-navigate the live frame — the exact hazard the decision prevents.
**Rejected**: A `src` state set only at first render — goes stale across reachability flips (a remounting iframe would boot into the seed-time folder instead of where the editor last was).
*Introduced by*: 260813-if5d-latch-code-surface-folder; the `followSrc` exception: 260909-kji8-tab-keyed-code-workspace-actions; the rescue `reload()`: 260910-74q0-code-tile-first-boot-rescue-reload

### Two sanctioned parent re-navigations: the folder-follow and the first-boot rescue
**Decision**: `CodeSurface` may parent-navigate a live frame in exactly two cases. (1) The folder-follow: after an editor-initiated File > Open Folder (the frame navigates itself to a bare `/code/?folder=<new>`, dropping the workspace identity), `app.tsx` POSTs the `@rk_win_code_root` latch, re-fetches the workspace path for the new root, and re-navigates the live frame to the new `?workspace=` URL via the nonce-keyed `followSrc` prop; a `?folder=` load equal to the current root is not re-navigated. (2) The first-boot rescue: when a `?workspace=` mount generation's rescue verdict finds an empty-boot MARKER strictly newer than its baseline — the bridge extension positively reporting that THIS boot activated with zero folders — `CodeSurface` runs one `contentWindow.location.reload()` per generation (§ Code Surface → First-boot rescue). Both keep the frame's URL and tab identity — neither is a `src` write.
**Why**: in both cases the frame provably has no editor state to lose — the folder-follow targets a frame that already navigated itself (and must regain the workspace identity — its `rk.tab`/`rk.server` settings — that the bare `?folder=` form dropped, or the bridge host registers tab-less and the run-kit actions hide), and the rescue targets a frame whose boot loaded zero folders (the bridge extension's marker says nothing was ever edited). A `reload()` keeps the `?workspace=` URL and tab identity; a `src` write would re-navigate and lose the mount-generation ref discipline.
**Rejected**: leaving a followed frame on `?folder=` (a tab-less host, hidden actions); a `src` rewrite on every code-root change (re-navigates live frames on ordinary latch writes — the mount-generation rule's hazard); a blind rescue reload on every first open (double-boots good boots); inferring the broken boot from the ABSENCE of a new host record (a good boot's record can land later than any fixed window under load — 7 s measured with three concurrent workbenches — so the absence rule false-reloads exactly the boots the rescue exists to spare); degrading a rescued frame to `?folder=` (drops the tab identity the workspace file carries).
*Introduced by*: 260909-kji8-tab-keyed-code-workspace-actions; the rescue leg: 260910-74q0-code-tile-first-boot-rescue-reload; marker-gated: 260910-oa3c-code-rescue-positive-signal-record-ownership

### At most three point-in-time GETs per mount generation, not a payload field or a watcher
**Decision**: the first-boot rescue's signals are read by point-in-time `GET /api/windows/{windowId}/code-bridge` calls only — a two-stamp baseline at src adoption, a first verdict at the wait's expiry, and exactly one bounded re-check when neither stamp moved: at most three reads per mount generation.
**Why**: the state socket's idle cadence (12 s `safetyPollInterval` + 5 s TTL) cannot observe a record or marker written inside the wait window, so a per-tick payload field would misfire; three requests with no interval and no loop are not polling, and the derivation stays request-time (Constitution II, IX).
**Rejected**: an `fsnotify` watcher on `cb/` waking the hub (machinery for a once-per-workspace event); widening the wait to ≥ 20 s with a single read (a 20 s empty-editor dwell on every broken boot, and the good-boot confirmation latency doubles for nothing); inferring the verdict from record absence (§ The rescue fires only on a positive empty-boot signal).
*Introduced by*: 260910-74q0-code-tile-first-boot-rescue-reload; the three-read bound: 260910-oa3c-code-rescue-positive-signal-record-ownership

### The rescue fires only on a positive empty-boot signal
**Decision**: the code tile reloads only when the bridge extension itself reports that THIS boot activated with zero folders (an empty-boot marker newer than the mount baseline); the absence of a host record is never a trigger.
**Why**: a good boot's record lands only after the remote extension host activates, which under load takes longer than any fixed window (7 s measured with three concurrent workbenches), so absence cannot distinguish "slow" from "broken" — and a false reload is exactly the blind reload the rescue exists to avoid. The extension provably runs `activate()` on the broken boot, so it can name the failure directly.
**Rejected**: widening the fixed window (every extra second is a longer broken-boot dwell and still no guarantee); polling until a record appears (an interval loop on a UI path); keeping the absence rule with a re-check only (still infers from silence).
*Introduced by*: 260910-oa3c-code-rescue-positive-signal-record-ownership

### One bounded re-check, not a fixed single read
**Decision**: the verdict reads at 10 s and, when neither stamp has moved, once more at 20 s, then settles — at most three reads per mount generation.
**Why**: the marker is written by the same slow extension-host activation as the record, so a single read at 10 s would miss the broken boot under load; one re-check covers the measured latency with margin while keeping the per-generation cost bounded and interval-free.
**Rejected**: an interval until a signal appears (open-ended client polling); a single read at 20 s (doubles the good-boot confirmation latency for nothing).
*Introduced by*: 260910-oa3c-code-rescue-positive-signal-record-ownership

### The waiting-badge click advances, never restarts

### Gestures zoom continuously; only click/shortcut zoom steps the ladder
**Decision**: web-tile gesture zoom is continuous — `s *= exp(-deltaY * 0.01)` per ctrl/meta wheel event (`applyWheelZoom`), `s = base * e.scale` per Safari `gesturechange` — while buttons and palette actions keep the discrete ladder.
**Why**: a pinch that clicks between ladder stops reads as broken next to Chrome/macOS, where pinch tracks the fingers and only Cmd+± steps; the exponential mapping multiplies equal deltas equally, so in/out feel symmetric and a reversed gesture returns to its start.
**Rejected**: shrinking the step ladder (finer quantization) — still visibly clicks; linear `s += k*deltaY` — asymmetric feel, zoom-out crawls near the low bound.

**Why**: a reload must restore a gesture-set value exactly; snapping belongs to the one path that needs a ladder index.

### Viewer-owned figure zoom, independent of tile zoom
**Decision**: Diagram magnification in the present viewer lives inside the viewer shell as a CSS transform on the SVG within a fitted, clipping, pannable figure; the tile's content zoom is untouched and composes on top.
**Why**: The tile zoom shrinks the frame viewport and scales it back, so a fit-to-width SVG re-fits and never magnifies — at the 300% cap a wide scene is still fully visible, only sharper. A viewer-owned transform gives arbitrary crisp magnification with no re-render, no dependency, no route, no setting.
**Rejected**: Raising `WEB_ZOOM_MAX` (no effect on re-fitting content and changes every page's tile zoom); dropping the SVG `max-width: 100%` (wide scenes overflow at rest and lose the at-a-glance fit); the interactive `@excalidraw/excalidraw` viewer (React plus a large chunk in a deliberately plain-TypeScript shell — held until selection/editing is wanted); tile-injected guest zoom (cross-origin-unsafe).

### The viewer claims ctrl-wheel over figures at window capture; the tile keeps the rest

**Why**: DOM capture order is window → document → target and the tile attaches its arm at the frame's `document` on every load, so window capture is the one pre-emption point needing no change in `iframe-window.tsx`. **Rejected**: A yield hook in `iframe-window.tsx` (couples the tile to guest markup); letting both arms zoom (the tile would zoom on every figure gesture); `⌘`/`Ctrl` key variants (collide with shell and browser zoom).

### One `IframeWindow` chrome, N URL-keyed frames
**Decision**: the web tile stays a single `IframeWindow` component that mounts one `<iframe key={url}>` per tab — hidden when inactive, never unmounted by a selection change — with per-frame state held in the extracted `WebFrame` child and the chrome bound to the ACTIVE frame's entry.
**Why**: P3 (hide, never unmount): dev-server pages, HMR sessions, and half-filled forms keep their in-page state across tab switches, which a single re-`src`d iframe loses on every switch. One component keeps exactly one receiver for the `web-find:open` / `web-address:focus` / `web-open-external` / `web-zoom` document CustomEvents, one URL bar / find bar / zoom control DOM set, and one `sandbox` attribute set. Keying by URL means a middle close's slot renumber remounts nothing (identity is the URL); index keys would remount every surviving frame on a `WebRemove` shift, and stable client-side ids would be a second identity the spec deliberately avoids.
**Rejected**: N stacked `IframeWindow` instances (duplicated chrome, N receivers for every document CustomEvent — each would need listener gating — and zoom buckets re-seeding per instance); index keys (remount storm on a middle close); lazy frame mount or LRU eviction (P3 defers eviction; the family cap of 8 bounds the eager-mount cost).

### The help-topic path does not yield a slot on a full layout
**Decision**: when the current layout already holds three tiles and no `web`, the frontend help-topic handler still adds the web tab but performs NO layout write and opens the page in a browser tab (`window.open`, `noopener,noreferrer`). This DIVERGES from the CLI: `webAddShow` behind `rk tab web add --show` / `rk present` replaces the last slot with `web` (§ `--show` on a full 3-tile layout replaces the last slot).
**Why**: the frontend's full-layout signal is `addSurface(layout, "web") === null` — the same predicate that disables the surface toggles and `View:` switch targets — and the path reuses it rather than adding a client-side replace-last-slot mutation; the intake requires falling through to the browser-tab fallback rather than silently no-oping; adding the tab first keeps the page one strip-click away once the layout has room. The CLI's yield exists so an agent's `present` never fails to show; a person clicking a docs link has the browser tab as an acceptable answer.
**Rejected**: a silent no-op after adding the tab (the user clicked and nothing visibly happened); mirroring the CLI's last-slot replacement in the frontend (a new layout mutation that evicts a tile the viewer arranged, for a documentation page).
*Introduced by*: 260910-58al-help-topics-submenu

### Grid key is server-only; per-window state resets by effect
**Decision**: `SurfaceLayout` is keyed by `server`; transient per-window state (hide-never-unmount set, zoom, focused slot, web page title, tty progress, find state) resets in one `[server, windowId]` effect guarded against first mount.
**Why**: the tty tile must survive a same-session switch so the relay's same-session ride and the deferred-reset/clear designs apply ([terminal](/run-kit/ui/terminal.md) § Terminal Write Batching); the ratios reset already follows the effect pattern.
**Rejected**: hoisting `TerminalClient` above the keyed boundary (more prop plumbing, two ownership seams for the same tile) — recorded as the fallback if the reset effect proves too entangled.
*Introduced by*: 260910-0awz-tab-switch-persistent-terminal

### Non-tty tiles keep a per-window remount via their key
**Decision**: web/code/gui tile wrappers carry `windowId` in their React key; the tty tile wrapper's key is window-independent.
**Why**: their content identity changes with the window and each has mount-once bookkeeping (code first-boot rescue, per-url iframes, RFB session); limiting persistence to the tty tile keeps the review surface small.
**Rejected**: persisting all tiles and re-deriving their content by prop — a much larger change for no user-visible gain.
*Introduced by*: 260910-0awz-tab-switch-persistent-terminal

### The code lens keys on the derived folder — git toplevel when found, else the pane's raw cwd
**Decision**: the per-window availability half is `gitRoot`, derived in `FetchSessions` from the active pane's cwd (else first pane's, else the worktree path) via `config.FindGitRoot` — a filesystem stat-walk, no subprocess — falling back to that resolved cwd itself when no `.git` ancestor is found; the field is empty only when no cwd is resolvable at all.
**Why**: code-server keys browser workspace state on the `?folder=` value, so editor state follows the code — agents `cd` constantly, and two windows on one worktree deliberately share one editor state. Outside any repo there is no shared toplevel to key on, so each window keys on its own raw cwd (two non-git windows on different cwds get distinct editor state; two on the same cwd share) — the same "toplevel, else cwd" resolution the CLI's `rk code` applies per invocation.
**Rejected**: keying by window id (editor state would reset on every window recreation); keying by raw cwd everywhere (state would fragment across subdirectories of one repo — raw cwd is the fallback only where no git toplevel exists); a synthetic shared root for all non-git windows (would conflate unrelated directories' editor state).
*Introduced by*: 260811-k3vp-right-panel-code-lens; cwd fallback: 260907-a482-code-server-outside-git-root

### The code lens widens `deriveGitRoot`'s derivation rather than changing `config.FindGitRoot` or adding a field
**Decision**: the non-git case is a fallback branch inside `deriveGitRoot` — return the resolved cwd when `FindGitRoot` finds no `.git` ancestor — with the `GitRoot`/`gitRoot` field name and JSON key unchanged; `config.FindGitRoot`'s `""`-means-not-in-a-repo semantics are untouched.
**Why**: the frontend-facing `Window.GitRoot` has exactly one consumer (the code lens), so widening its derivation carries no cross-feature risk, while `FindGitRoot` is a shared primitive whose empty return gates unrelated features (`api/fork.go`, `api/closed.go`, `cmd/rk/operator.go`, `cmd/rk/riff.go`, `cmd/rk/tutorial.go`); the CLI's `codeTargetFolder` already ships the same "toplevel, else cwd" pattern, so the fallback mirrors an accepted precedent.
**Rejected**: changing `FindGitRoot`'s return semantics (silently changes every other call site's behavior); introducing a separate `workspaceRoot` field or renaming `gitRoot` (single-consumer field — a rename would ripple across the e2e/unit fixtures that reference the key for no behavioral benefit).
*Introduced by*: 260907-a482-code-server-outside-git-root

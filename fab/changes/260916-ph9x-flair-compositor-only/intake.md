## Why

**The problem.** The desktop app idles at 20–30% CPU while agents run. The plan's measurement (2026-09-16, headless Chromium, software GPU) attributes most of it to *continuous painting*, not JavaScript: the five flair overlays visible on the server page alone cost ~10 points of one core (`/runKit` 14.8–18.6% vs 4.3% with every flair off), and `RecalcStyleCount` stayed at 60/s until the last flair was disabled — **no flair type composites today, transforms included**. The sheet flairs animate `background-position` on pseudo-elements, which Blink can only run on the main thread (style recalc + paint + raster every frame); and even the transform-driven treatments (`nemo`) keep the main thread busy for reasons R1 pinned down below.

**Consequence of not fixing it.** Every flaired row anywhere on screen — sidebar rows, server tiles, picker previews — burns a fixed ~2 points of a core per overlay for as long as it is mounted, multiplied across every warm Electron `WebContentsView`. Flair is the project's most visible decorative channel and is per-row opt-in by design, so the cost scales with exactly the users who like the feature most.

**Why this approach.** Removing flairs or defaulting them off is ruled out by the plan's decisions of record. Reduced-motion already exists as the global escape hatch and stays as is. The measured path is to make every flair animation *compositor-only* — the compositor (cc, in the renderer process) ticks composited transform/opacity animations without waking the main thread — and R1 proved that every mechanism a flair needs (traversal, frame stepping, articulation, ambient tiles) has a composited encoding whose visual output can be made identical to today's, including the pixel-snapped hop of the pixel-art sprites. The plan's fallback path (pause-when-hidden) was measured too and dropped: once the animations composite, off-screen overlays cost nothing measurable, and neither `content-visibility: auto` nor an `IntersectionObserver` pause reduced cost on the still-main-thread flairs.

**Why nemo's parts tick (the new finding, not in the plan's hypothesis list).** Isolation runs (12 s): one tail class alone → 194 recalcs; the same tail at 4 s duration without `alternate` → 66 (floor); translate instead of rotate → same 195; `transform-origin: 50% 50%` → same; parent `opacity: 1` → same; no SVG background → same. So the rotations *are* composited, but **every iteration boundary of a composited animation costs one main-thread frame** (a style recalc + property-tree commit — no paint). Fourteen parts at 2.5–5 boundaries per second is ~55 main frames/s, i.e. almost the full 60/s. Keyframe *steps* inside an iteration are free: a 5-keyframe `step-end` sheet stepper and a 2-keyframe `steps(4)` stepper on 5 sprites both read ~2 recalcs/s per sprite = exactly their iteration rate; 16-, 32-, 48- and 64-keyframe step-end lists and a 64-keyframe linear list all composited (58–81 recalcs / 12 s). One 64-keyframe run out of ~45 read 60/s and did not reproduce on re-run — a spurious run is environmental (the page had ~2× the usual node count; likely a transient popover/reload), so a failing acceptance measurement is re-run once before it counts.

**The fix, measured end to end on nemo (30 s):** swims unchanged + tail/fin/blade re-encoded as 8 s iterations holding 10 (0.4 s cadence) or 20 (0.2 s cadence) full wags as explicit keyframes with per-segment `ease-in-out` (visually identical to `alternate`) + bubbles moved from the `::before` onto a child span translated by one tile per loop → **5.0% renderer, 213 recalcs (7/s), 22 animations still running** vs 11.2% before. Within the 3-point noise band of the floor.

**Pixel-art crispness (the "look unchanged" risk the plan did not list).** Today `background-position` is pixel-snapped: a sprite at 10.5px renders exactly like 11px (7 colors in the 200×22 row). A composited `translateX(10.5px)` renders the same nyan sheet through bilinear filtering: 18–19 colors, ~120 soft-edge pixels — visibly blurry pixel art at 1×, and `image-rendering: pixelated` does **not** change it. At 2× a .5 offset is a whole device pixel and stays crisp, but arbitrary fractional offsets blur there too. The composited cure is to quantize the traversal with `steps()` so the layer only ever sits on whole device pixels: `animation-timing-function: steps(calc(var(--rk-flair-w) + 40))` (jump-end; the step count equals the traversal distance in px) is accepted by Chromium (computes to `steps(240)`), lands on integer positions (`-4` where linear gave `-3.09`), renders 7 colors like the snapped background, and stays composited (1 recalc in 6 s with three sprites running). This is exactly today's motion: a background-position animation snaps to a new integer every frame the position crosses one, and `steps(distance)` emits the same integer sequence.

## What Changes

### 1. The compositing rule — `app/frontend/src/globals.css` § Flair overlays

The section's animation discipline flips from "background-position only, never transform" to **compositor-only**. Rules the rewritten block MUST satisfy for all sixteen flairs (`rain`, `scan`, `nyan`, `naruto`, `onepiece`, `pacman`, `matrix`, `aquarium`, `nemo`, `roadrunner`, `invaders`, `cube`, `warp`, `spidey`, `ironman`, `noon`):

1. **Every `@keyframes rk-flair-*` animates only `transform` and/or `opacity`.** No `background-position`, `background-position-x/-y`, `left/top/inset`, `border-*`, `color`, or `filter` in any flair keyframe. Container-query units, `var()` and `calc()` inside transform keyframes are allowed (measured compositable).
2. **No animated pseudo-elements.** `::before`/`::after` may still exist as *static* paint (none are needed once layers are spans — prefer removing them). Every moving layer is a real child `<span>` emitted by `FlairOverlay` (§ 2).
3. **No animation iteration shorter than 1 s.** Iteration boundaries cost a main-thread frame each (measured ~0.045 renderer points per boundary/s). Fast cadences are encoded *inside* a long iteration:
   - **Articulation** (nemo tail ±22°, fin ±18°, blades ±7°): one 8 s iteration whose keyframes list every half-wag — 10 full wags for the 0.4 s cadence (keyframes every 5%), 20 for the 0.2 s cadence (every 2.5%) — with `ease-in-out` as the animation timing function so each segment eases exactly like today's `alternate` half-cycle; `animation-delay` offsets (−0.1 s / −0.05 s / −0.13 s / −0.27 s) are kept verbatim; the counter-phase blade uses the inverted list.
   - **Frame stepping** of a sheet: the inner sheet span translates by whole frame heights with `steps(n)` (or a `step-end` keyframe list) inside an iteration ≥ 1 s. Where the sheet has `f` frames and the cadence is `c` s per frame, either use a `step-end` list of `⌈1 s / c⌉`-plus frames per iteration (repeat the frame cycle within the list — lists up to 64 keyframes measured compositable) or set `background-repeat: repeat-y` on a taller inner span and step through `k × f` frames with a 2-keyframe `steps(k×f)` translateY. `ironman`'s 22-frame narrative (80 beats over 16 s, A/B flicker pairs, hero holds around the turn) stays one 16 s `step-end` keyframe list on the inner sheet — frame index per percent exactly as today's `rk-flair-ironman-y`, values converted from `background-position-y: -30n px` to `transform: translateY(-30n px)`.
4. **Pixel-art layers move in whole device pixels.** Every layer whose art is pixel art (all sheet sprites, glued trails/dots/ghost, rain dashes, scan lines, matrix glyphs, stars, streaks, dust, cities, bubbles — everything except nemo's bezier fish/blades, cube's wireframe, warp's star planes) is translated with a `steps()` timing function whose count equals the traversal distance in CSS px, so positions are the same integer sequence `background-position` snaps to today:
   - **Width-dependent traversals** (a sprite crossing the box): `steps(calc(var(--rk-flair-w) + K))` where `--rk-flair-w` is the overlay's rounded integer width (§ 2) and `K` is the flair's balanced traversal constant. Conversion from today's keyframes: a layer of width `w` with `background-position-x: from A px to calc(100% + E px)` becomes a frame box `left: 0; width: w` translated `from translateX(A px) to translateX(calc(var(--rk-flair-w) * 1px + E px - w))` — `100%` on a no-repeat background resolves to `(W − w)`, so the end offset subtracts the layer width (the same arithmetic nemo already documents for its swims). Distance = `W + E − A − w`; for a fully-off-both-ends traversal this is `W + K` with `K = E − A − w` (nyan cat: `−36 → 100% + 40` on a 36 px sheet ⇒ `K = 40`; the glued trail `−176 → 100% + 4` on 140 px ⇒ `K = 40` too — glued layers share a distance by construction, so one `steps()` count per flair). `100cqw` is **not** used for these (a non-integer container width would make the step size fractional); smooth vector layers keep `100cqw`/`100cqh`.
   - **Fixed-period tiles** (repeat-x/-y ambience drifting exactly one or more periods per loop): a span covering the box plus one period (`width: calc(100% + P px)` anchored so the extra period is on the side the tile arrives from; `height: calc(100% + T px)` for vertical drift), `background-repeat` as today, translated by exactly `P` (or the multi-period displacement, e.g. rain 72/56, matrix 88/132/176) per iteration with `steps(P)` — an integer literal, no JS needed. Layers with different speeds get their own spans (rain's two lanes, onepiece's two waves, matrix's three tiles, ironman's two cities).
   - **At device pixel ratio ≥ 2** the hop should stay one *device* pixel like today's snapping: multiply the step count by 2 under `@media (min-resolution: 2dppx)` (a `--rk-flair-dpr` custom property of `1`/`2` folded into the `calc()`), so 2× displays keep today's hop rate. `<!-- assumed: 2× keeps device-pixel hops via a resolution media query; 1-CSS-px hops would halve the hop rate on retina -->`
5. **Every overlay is a size query container** (`container-type: size` moves from the cube/nemo rules to the shared overlay rule) so any flair may use `100cqw`/`100cqh` in transform keyframes.
6. **Layer order = DOM order**: what was on `::before` (ambience, behind) renders as the first child spans, what was on `::after` (the character, in front) as the later spans; explicit `z-index` only where today's rules set it (nemo bubbles z-1 under fish/weed z-2).
7. **Geometry and timing are otherwise byte-for-byte today's**: same sheets (data URIs unchanged, byte-identical), same durations, same `step-end`/`steps(26, jump-none)` shapes, same from/to constants, same strip anchoring (centered 22 px strips, spidey's `bottom: -8px` 30 px strip, ironman's 30 px centered strip, onepiece/noon bottom-anchored), same opacities (`0.92`/`0.9`), same `--rk-flair-color` tinting for rain/scan (the tinted gradients move to the lane spans' `background-image`). The blue fish's 50%/50.01% teleport and aquarium's mid-loop keyframes convert 1:1; invaders' wander becomes `translateX(0 → calc(var(--rk-flair-w) * 1px − 44px))` with today's `steps(26, jump-none)` `alternate` 13 s (a 44 px box on a 44 px sheet — the percentage wander mapped image-edge to box-edge, and so does this).
8. **Reduced motion**: the gate block's per-pseudo list collapses to hiding the sixteen overlay spans themselves (`display: none`) — the same visible result (nothing) and no per-layer list to keep in sync. The `.rk-flair-onepiece` wave baseline note stays true (it hides with the overlay).
9. **The header comment** rewrites the "Constraints the rules below rely on" list to the compositing rule above, keeps the drag-ghost explanation (why transforms live on children under a hidden-while-dragging overlay, now for every flair), keeps the WebGL rejection, and states the measured reason in one line (60/s main-thread ticking; iteration-boundary cost) — no change IDs.

### 2. `FlairOverlay` — `app/frontend/src/components/flair-overlay.tsx`

- **Every flair gets child layer markup**, not just cube/warp/nemo. A per-flair layer table in the component (a `const FLAIR_LAYERS: Record<FlairState, ...>` or equivalent) drives the spans; class names are flair-scoped and stable so the CSS can address them (e.g. `rk-nyan-stars`, `rk-nyan-cat`, `rk-nyan-trail`, each frame box holding one `rk-sheet` inner span — naming is the worker's call, the contract is: one span per moving layer, DOM order = paint order, a frame box + inner sheet pair for every stepped sprite). The existing cube/warp/nemo child markup is unchanged.
- **Integer width variable.** For flairs with width-dependent quantized traversals, the overlay span carries an inline `--rk-flair-w: <integer>` custom property kept current by a `ResizeObserver` on the overlay element — `Math.round(contentRect.width)`, written straight to `element.style` (no React state, no re-render), observer created on mount and disconnected on unmount. One observer per mounted overlay is acceptable (a handful to a few dozen overlays); a module-level shared observer is preferable if trivial. Picker preview cells (18 px / 28 px) and the composite preview mount the same overlay and get the same variable. Until the first observation lands, the CSS falls back to `var(--rk-flair-w, 240)` so the first frame is not degenerate.
- **Drag guard unchanged** (`hidden` returns `null` for every flair — now every flair carries transform-driven children, which is exactly the case the guard exists for). **Color prop unchanged** (`--rk-flair-color` is read by the rain/scan lane spans).
- The file header comment is rewritten for the new contract (single mount, per-flair layer table, the width variable and why it exists, drag guard).

Marker Axis — Two-Axis Studies

Follow-up to the window-row studies. Premise: the Label picker splits — color + flair stay together (card / palette), and the marker becomes two axes: how far (an ordinal stage, drawn as amount of ink) × what kind (a categorical pattern). Every stripe below is drawn with the shipped tile math from themes.ts markerStripeStyle, just parameterised by width.

The shipped conventions already imply a ladder — parked → in-progress → review → completed → archived — but the ink runs 1 → 6 → 6 → 6 → 6, so the ladder is not readable from the stripe. The two-axis model makes it readable and keeps the pattern classes as the categorical channel. It revisits a recorded decision ("new states are pattern classes, never a new weight between existing ones", sidebar.md § Marker vocabulary) — deliberately: width becomes a separate axis rather than more markers, which is what that rule was protecting against.

2 · Three encodings of stage × pattern

Each grid cell is a real 24px row fragment (stripe · dot · name). Columns = stage 1→5, rows = pattern. Judge two things: does stage read at a glance down a column, and does pattern survive at low stage?

A · width one stripe, ink width = stage
Widths 2 · 6 · 11 · 16 · 22. Stage reads instantly (a bar chart down the column). Pattern survives from stage 2 up; at stage 1 dotted/dashed collapse to a broken hairline and hatch is unreadable — acceptable if stage 1 means "parked" (pattern barely matters). Full-width hatch (stage 5) is loud; in practice hatch = hazard rarely reaches 5.
B · line count N × 2px lines, pattern per line
Lines 2px, gap 2px → max 18px. Countable (3 lines = stage 3) and it subsumes the shipped double. Dotted/dashed lines stay legible at every stage because line width never shrinks. Hatch does not decompose into lines — shown as a 45° tile per line, which just reads as noise; hatch would need to become a fill (see C) or stay a full-strip texture.
C · filled stops 5 fixed stops, filled count = stage, pattern = stop ink
Stops 3×14px on a 22% track. The empty track shows the total (…of 5), which A and B don't. Pattern reads only as texture of the filled stops — dotted vs solid is visible, hatch/block barely. Stacked rows don't weld (stops are 14px tall, rows 24px), so the sidebar stays airy — but it also stops looking like the stripe people know.

3 · Interaction: one-step, two-step, or both

All three demos are live. The row's left 26px is the target on desktop. The pad is the same component in every case — the only question is what opens it and whether a drag can skip it.

I1 · one-step drag = stage, click = next pattern, wheel = ±stage

buffed-pika

try: drag horizontally in the strip (travel is 18px per step, pointer-captured, so the drag can leave the 22px strip); click without moving to cycle the pattern.

Pros: fastest for the common edit (bump the stage). No surface appears. Cons: the second axis rides an undiscoverable click-cycles gesture, so users will learn one axis and forget the other; a click that jitters 3px becomes a stage change; there is no mobile analogue (a 10px strip is below any touch floor) — coarse pointers need a different control anyway, so I1 forces two UIs.
I2 · two-step click opens the pad; pick a cell
▾ fab-kit
swift-mink
buffed-pika

try: click the strip; hover cells to preview on the row; click a cell to commit (Esc / outside closes).

Pros: both axes visible at once — the pad is the vocabulary, so it teaches itself; same pad on mobile (from the card). Cons: two clicks for a one-step bump; the pad anchors at the row bottom-left like today's picker and can cover the rows below (or flips above near the bottom).
I3 · spring-loaded press opens the pad under the pointer; drag 2D; release commits — a plain click leaves it open
▾ fab-kit
swift-mink
buffed-pika

try: press in the strip and drag right (stage) or down (pattern) without releasing — the pad opens with the current cell under your pointer, so "press, drag right two cells, release" is the one-step bump; release without moving and it stays open as a click menu.

Why this one: it's I1's speed for the power user (press-drag-release, ~same motion) with I2's discoverability (the vocabulary appears every time), and no click-cycles hidden gesture. The pad wants the current cell under the pointer; when there's no room (the pointer is in the left 26px and the sidebar is flush with the screen edge) it clamps inside the sidebar and the drag becomes relative — the highlighted cell follows your displacement, so a straight horizontal drag still changes only the stage and a no-move release changes nothing. Same pad, click mode, on mobile from the card. Precedent: macOS spring-loaded menus / Sketch's colour scrubbers. Cost: a pad flashes for every edit, even a bump (mitigation: fade-in after ~80ms so a quick press-drag-release barely paints it).

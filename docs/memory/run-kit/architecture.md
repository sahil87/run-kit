# run-kit Architecture

## System Overview

run-kit is a web-based agent orchestration dashboard. In production, a single Go binary runs as a daemon in a dedicated tmux session:

1. **Go backend** (`app/backend/`, default port 3000) — single binary serving REST API, SSE, WebSocket terminal relay, and SPA static files on one port. Cobra CLI with subcommands: `serve` (default; foreground-only — daemon lifecycle is the `daemon start|stop|restart|status` tree), `update` (alias: `upgrade`), `doctor`, `status`, `url`, `skill`, `riff`, `tutorial` (guided-tour entry — a session-scoped singleton `tutorial` window running the `--tier`-resolved launcher (default `fast`) bare, with the kickoff prompt typed into the booted agent and verified; tmux-required, exit 1 outside), `desktop` (macOS-only install/update/status for the Electron shell), `remote` (SSH-only remote hosts — bootstrap, tunnel, connect), `code-server` (the rk-owned editor install — install/start/update), `tab` (tab-state family — layout/web-tab/code-root verbs over the `@rk_win_*` options, works with `rk serve` down), `present` (one-verb "show this to the user" — sugar over `rk tab web add --show`: attach a file/dir/port/URL target and open the web tile), `mux` (tmux-substrate family — the `send`/`await` agent-to-agent messaging verbs, the `capture`/`kill`/`process` substrate twins (pane capture/kill/process-tree, agent-state-aware), the `panes` whole-server enumeration query, plus the operator members `reap`, `snapshot list|show|restore`, `init-conf`, `guard`). Hidden from help: `shell-init` (sourced from shell rc — functional, excluded from `rk -h` and help-dump) and the deprecation aliases `reaper`/`snapshot`/`init-conf` at the root (hidden, each prints cobra's `Deprecated` pointer and runs byte-identically; removable in a future release — unlike the permanent `agent-hook` alias). Version info via `--version`/`-v` global flag (Cobra built-in)

In development, `just dev` runs two concurrent processes:
- Vite dev server (`:RK_PORT`, default 3000) — HMR, proxies `/api/*`, `/relay/*`, `/proxy/*`, and `/code/*` to Go backend
- Go backend (`:RK_PORT+1`, default 3001) — API, WebSocket relay, SPA static serving

Configuration via env vars: `.env` (committed) defines `RK_PORT` and `RK_HOST`, `.env.local` (gitignored) for overrides. Go backend and Vite both read `RK_PORT`/`RK_HOST` directly — no intermediate `BACKEND_*` vars. In dev mode, `dev.sh` is the translation layer: it passes `RK_PORT+1` to the Go backend and `RK_PORT` to Vite. `dev.sh` accepts `--port` for ad-hoc overrides. `RK_CODE_SERVER_PORT` (read into `Config.CodeServerPort` by `internal/config`; unset/empty/invalid ⇒ unset) is an OVERRIDE for the code lens's code-server port — set it only to point rk at an externally managed code-server; by default the daemon runs code-server itself (§ Daemon Lifecycle → the `rk-code-server` sibling session) and the effective port resolves via `Config.ResolvedCodeServerPort()` (a valid preset wins, else the `RK_PORT+2` convention; 0 only on a degenerate `RK_PORT` whose +2 falls outside 1–65535 — the one case the feature is off). The frontend never sees the port: the embed rides the stable same-origin `/code/` route (a full URL would bypass the proxy and break same-origin). **The pathname is state identity**: code-server keys browser-side workspace state (tabs, layout, IndexedDB) by the proxy pathname, and `/code/` never changes — the port behind it is a private implementation detail. Tmux config defaults to `~/.config/run-kit/tmux.conf` — an rk-managed file whose first line is a hash-stamped ownership header (`# rk-managed sha256:<hex> — DO NOT EDIT; overrides go in ~/.config/run-kit/tmux.d/`, the hex being the SHA-256 of the body), scaffolded by `rk mux init-conf` and refreshed three-state at daemon start (§ `rk serve` Wiring; full ownership contract in [configuration](/run-kit/configuration.md) § Managed tmux.conf). The `tmux_conf` settings key or the `RK_TMUX_CONF` env escape redirects the path and flips the file to user-owned (rk performs no ensure/refresh/doctor on it). The config is embedded in the binary via `go:embed`; every rk write rides the shared managed write path (`writeManagedConfig`). All consumers use `tmux.ConfigPath()` getter — no direct env var reads elsewhere. User extensions go in `~/.config/run-kit/tmux.d/*.conf` — a drop-in directory sourced via `source-file -q` at the end of the managed config; `tmux.d/user.conf` is scaffolded as a commented starter by every scaffold path and never overwritten. Files load in lexicographic order (numeric prefixes control precedence). The `-q` flag silences errors when the directory is empty or missing.

run-kit connects to **one tmux server at a time**, determined by the URL path segment. The URL hierarchy is `/$server/$window` (260529-jad6-window-api-stability) — the server name is always in the URL, making URLs fully shareable and self-contained. The window segment is the **bare numeric part** of the stable tmux **window ID** (`@N` sans `@`, e.g. `/$server/0`) (260703-8mpy-numeric-window-url) — NOT the mutable window index (260529-chgz-window-id-routing): the number in the URL is the ID's digits, restored to `@N` by the route's parse, never the positional index. The API/relay layers still address a window by the `@N` form (e.g. `/api/windows/%40N`, `/relay/%40N` — unchanged); only the page URL segment drops the `@`. The route shape carries **no `$session`** (260529-jad6-window-api-stability) — `@N` is server-global so the session is redundant in the URL; it is derived server-side / from the active window's SSE snapshot wherever a session name is needed for display. 3-segment `/$server/$session/$window` URLs are not served (no redirect shim). The active server is sent as a `?server=` query parameter on every API request (SSE, REST, WebSocket) by the frontend's `withServer()` helper. The backend is stateless — it defaults to the `default` tmux server when the parameter is absent. Server discovery scans `/tmp/tmux-{uid}/` for socket files. The frontend persists the last-used server in localStorage (`runkit-server`) as a convenience for the server list page, but the URL is always the source of truth. Server lifecycle: create (via server list page or command palette), kill (`tmux kill-server`), switch (navigate to `/$newserver`).

The pane-boards view (`/board/$name`) is a deliberate exception: it is a root-level peer to `/$server` (NOT under `/$server/...`) because boards aggregate windows across multiple tmux servers. It does not render the server-scoped AppShell — see `## Boards Feature` below.

## Data Model

**No database.** State derived at request time from:
- **tmux server** — `tmux list-sessions`, `tmux list-windows` via `internal/tmux/tmux.go`. Project roots derived from window 0's `pane_current_path`. Read-path functions (`ListSessions`, `ListWindows`, `ListServers`) accept `context.Context` from HTTP handlers for request cancellation propagation. Mutation functions (Create/Kill/Rename) use `context.Background()` — user-initiated actions complete regardless of client disconnect
- **`config.FindGitRoot()`** (`internal/config/gitroot.go`) — walk-up helper from `pane_current_path` looking for `.git`; live callers (`internal/sessions`, `ProjectRoot`). Session color lives in the tmux `@rk_ses_color` option (below)
- **tmux `@rk_win_color` / `@rk_ses_color` user options (color storage)** (260615-6rnr-expand-swatch-palette-blends) — per-window color in the `@rk_win_color` user option (`#{@rk_win_color}` is field 8 of the `ListWindows()` format string); per-session color in the `@rk_ses_color` option (field 5 of `ListSessions()`'s format string — a distinct name from window `@rk_win_color` so hierarchical format lookup never leaks one scope's value into the other). Both are ephemeral (survive session lifetime, not tmux-server restarts). The stored value is a **string color-value descriptor** in one of four forms: a legacy numeric/blend form `"4"` (single ANSI index) or `"1+3"` (two-hue blend, NOT a bare integer, though a legacy bare int is still accepted on read); a plain owned-family name `"blue"`; or a `-dark`-/`-light`-suffixed shade (`"blue-dark"` / `"blue-light"`). All forms round-trip; the numeric forms remain valid forever (see § validate closed sets). Window color set via `SetWindowColor`/`UnsetWindowColor` (`set-option -w -t {windowID} @rk_win_color {value}` / `-wu`); session color set via `SetSessionColor(session, value, server)` / `UnsetSessionColor` (`set-option -t {session} @rk_ses_color {value}` / `-u`). Both parse the raw option through `validate.NormalizeColorValue` (accepts legacy int OR descriptor, normalizes to the canonical string, drops on malformed) into `WindowInfo.Color *string` / `SessionInfo.Color *string` (nil when unset/malformed); `SessionInfo.Color` surfaces to the SSE snapshot as `ProjectSession.SessionColor` in `internal/sessions`. Pre-namespaced color keys migrate through `MigrateLegacyOptions` — see [tmux-sessions](/run-kit/tmux-sessions.md) § Legacy Option Migration. Both `-t` targets are self-contained (window ID; session name) — no `session:index` string
- **tmux `@rk_win_marker` window user option (marker well, window-scoped)** — the window's display-only marker state, stored per-window in `@rk_win_marker` (`#{@rk_win_marker}` is field 11 / index 10 of the `ListWindows()` format string). Ephemeral (survives session lifetime, not tmux-server restarts). Its closed-set schema is `<mode>[:<stage>]`, where mode is `manual`/`auto`/`blocked`, stage is `1`/`2`/`3`, and a bare mode means stage 1: the twelve accepted write tokens are `manual`, `manual:1..3`, `auto`, `auto:1..3`, `blocked`, `blocked:1..3`. `tmux.NormalizeMarker` maps stored flat tokens (`pipe`/`dotted`/`dashed`/`solid` → `manual:1`, `double` → `manual:2`, `thick` → `manual:3`, `hatch` → `blocked:2`, `block` → `blocked:3`) at the live `parseWindows` read boundary, layout-snapshot capture, and snapshot restore. Unknown values collapse to `""`; current tokens pass through unchanged. `WindowInfo.Marker string` (JSON `marker,omitempty`) drives the sidebar's fixed-ink marker well; markers are user label conventions with no behavioral wiring. Writes use the unified `POST /api/windows/{windowId}/options` allowlist. Scope is windows only — session rows and server tiles have no marker.
- **tmux `@rk_win_flair` user options (per-row flair, decorative)** — the row flair channel (`""`/`rain`/`scan`/`nyan`/`naruto`/`onepiece`/`pacman`/`matrix`/`aquarium`/`roadrunner`/`invaders`/`cube`/`warp`/`spidey`/`ironman` — an opt-in character-animation overlay, decoration only with no semantic wiring; see ui/sidebar.md § Row Flair). Window flair lives in the `@rk_win_flair` **window** option (`#{@rk_win_flair}` is field 13 / index 12 of the `ListWindows()` format string) and session flair in the **scope-split** `@rk_ses_flair` **session** option (field 7 of `ListSessions()`'s format string — a shared name would leak across scopes in format expansion, so the same-scope pair uses distinct names exactly like `@rk_win_color`/`@rk_ses_color`), both ephemeral. Values are a **closed-set token** validated by `validate.FlairValues` / `validate.ValidateFlairValue`; `parseWindows`/`parseSessions` drop any out-of-set value to empty (the `Marker` closed-set idiom), landing in `WindowInfo.Flair string` / `SessionInfo.Flair string` (JSON `flair,omitempty`). Window flair is written through the unified `POST /api/windows/{windowId}/options` allowlist; session flair through `POST /api/sessions/{session}/flair` via `tmux.SetSessionFlair`/`UnsetSessionFlair`. `#{@rk_win_flair}` is also in the layout-snapshot capture set (`layout.go`). Flair stops at the session tier — server rows carry none (they mirror the flair-free SERVER-pane tiles) (260814-2esh-sidebar-character-row-animations)
- **tmux `@rk_win_role` window user option (orchestration role, window-scoped)** — the window's orchestration role, stored per-window in the `@rk_win_role` user option (`#{@rk_win_role}` is field 12 / index 11 of the `ListWindows()` format string; the `RoleOption` constant sits in `internal/tmux/tmux.go` alongside `SessionOrderOption`/`ServerRankOption`). The value is a **closed-set token** — `""` (unset) | `"operator"` — validated by `validate.RoleValues` / `validate.ValidateRoleValue` (mirroring the marker rule). `parseWindows` drops any value outside `RoleValues` to `""`, landing it in `WindowInfo.Role string` (JSON `role,omitempty`) — the Marker parse idiom. `"operator"` is a **server-scoped radio**: at most one window per tmux server carries it, enforced in rk's write paths (never trusted to clients) by `tmux.ClearWindowRoleExcept` / `ClearWindowRoleExceptOnServer` — one `list-windows -a -F '#{window_id}\t#{@rk_win_role}'` read plus a single `\;`-chained `set-option -wu` batch unsets the option on every other carrier (zero carriers ⇒ no write call); the pure `roleCarriersToClear` parser makes the rule unit-testable without a live server. The sidebar pins the carrier's row below the SESSIONS header (see ui/sidebar.md § Operator Pinned Row). Written through the unified `POST /api/windows/{windowId}/options` allowlist or the `rk role` CLI — both apply the radio clear. No liveness reconciliation: the marking persists until explicitly cleared or the window is killed (a dead operator staying pinned is desired signal, unlike `@rk_agent_state`).
- **tmux `@rk_win_note` window user option (one-line status note, window-scoped)** — the window's free-text one-line status note (the "why" behind the derived signals; user/agent-authored annotation in the marker/flair user-preference class, NOT derived state), stored per-window in the `@rk_win_note` user option (`#{@rk_win_note}` is field 14 / index 13 — always the LAST field — of the `ListWindows()` format string; const `tmux.NoteOption`). The value schema is `<unix-epoch>:<text>` (the `@rk_agent_state` staleness precedent — the epoch lets the UI age notes honestly). Unlike the closed-set channels there is NO value validation on read: the parse is tolerant (`parseNoteValue` — a missing colon or a non-numeric/negative prefix keeps the whole value as text with epoch 0, never dropped), and `parseWindows` rejoins the tab-delimited tail (`strings.Join(parts[13:], "\t")`) so tabs inside the text cannot truncate sibling fields; the result lands in `WindowInfo.Note string` / `WindowInfo.NoteEpoch int64` (JSON `note,omitempty` / `noteEpoch,omitempty`). Written through the unified `POST /api/windows/{windowId}/options` allowlist with the epoch prefix stamped server-side (below), or by agents/operator templates via raw `set-option -wt` with their own `$(date +%s)` stamp. Also in the layout-snapshot capture set (trailing optional field, restored verbatim so the note's age survives a restore). Dies with the window.
- **tmux `@rk_srv_session_order` server-scoped user option** — sidebar session render order stored as a JSON-encoded array of session names on the tmux *server* (not per-window). Survives the same lifetime as the tmux server (lost on tmux server death, NOT on rk-go restart per Constitution VI). Read by `tmux.GetSessionOrder(ctx, server)` — treats unset / no-server / `failed to connect` as empty slice; surfaces other errors (including JSON decode) as wrapped Go errors. Written by `tmux.SetSessionOrder(ctx, server, order)` — `nil` slice normalized to `[]` so round-trips are lossless. Both functions go through `tmuxExecRawServer` with `context.WithTimeout(ctx, TmuxTimeout)` (10s). The constant `tmux.SessionOrderOption = "@rk_srv_session_order"` is the canonical option name
- **fab tier (native per-pane derivation)** — `internal/sessions/fabstate.go` derives the **fab tier proper** — change name, pipeline stage, display-state — from the filesystem inside every `FetchSessions`, with no `fab` subprocess on the sessions/SSE hot path (Constitution II: fab state comes from `.status.yaml`, derived at request time; status-pyramid.md documents the L2 register source as `cwd → .fab-status.yaml → .status.yaml`). Per pane: a bounded walk-up from the pane's cwd finds the nearest `.fab-status.yaml` symlink (Lstat, so a dangling symlink still counts and degrades at read time); the change name is the symlink target's parent-directory basename (`fab/changes/{name}/.status.yaml`, relative targets resolved against the symlink's own directory); the target's ordered `progress:` map (`yaml.v3` node parse — order is load-bearing) yields `(stage, displayState)` via fab's five-tier display-stage rule (first `active` → first `failed` → first `ready` → last `done`/`skipped` → first stage `pending`), mirrored from fab-kit `internal/status/status.go` `DisplayStage` — a **cross-repo schema coupling**: fab-side drift degrades fail-open to empty fields, never an error. Derivation runs fresh per fetch with a per-call memo (cwd → located link, resolved link → derived state) and nothing persisted across requests, so a stage transition shows on the next SSE tick; the failure modes (no symlink ancestor, dangling symlink = archived change, unreadable/unparsable YAML, empty `progress:`) degrade per-pane to empty fab fields. The window rollup (`fabStateMemo.windowState`) walks the window's panes in pane order — a change-bound pane's derivation wins, else the first pane with any derivation — landing in `WindowInfo.FabChange`/`FabStage`/`FabDisplayState` with the frontend JSON contract unchanged. Agent lifecycle state comes from the `@rk_agent_state` pane option (Tier 2, read natively by `internal/tmux`, see [agent-state](agent-state.md)); PR links are derived server-side from the pane's branch (see § Branch→PR Derivation). (260820-hol4-mux-panes-native-pane-map)

### Performance Caching

One in-memory cache reduces subprocess spawning on the SSE hot path (justified per code-quality.md performance carve-out — not general-purpose caching):

| Cache | Location | TTL | Key | Purpose |
|-------|----------|-----|-----|---------|
| SSE session cache | `sseHub.cache` (`api/sse.go`) | 500ms | server name | Skip `FetchSessions()` subprocess calls when data is fresh |

The cache uses `sync.RWMutex` for thread safety. The fab tier carries no cache — it is derived natively from the filesystem on every fetch (§ Data Model), so there is no subprocess to throttle. The SSE hub's existing JSON diff-check (`previousJSON`) remains as a separate concern — the session cache prevents redundant subprocess spawning, while the diff prevents redundant SSE broadcasts

## Backend Libraries (Go Modules)

Packages in `app/backend/internal/`:

| Package | Responsibility |

### tmux Runner Core

`internal/tmux/run.go` owns the **single** tmux subprocess-runner implementation, exported so the other backend packages delegate to it rather than carry their own copy (code-quality anti-pattern *"Inline tmux command construction — all tmux interaction goes through `internal/tmux/`"*):

```go
type RunOpts struct {
    Env []string // nil inherits the process environment without tmux client context (TMUX/TMUX_PANE scrubbed)
    Dir string   // "" inherits the process CWD
}
func Run(ctx context.Context, args []string, opts RunOpts) error
func RunOutput(ctx context.Context, args []string, opts RunOpts) ([]byte, error)
```

The fixed contract: `exec.CommandContext(ctx, "tmux", args...)` with an explicit argv slice, never a shell string (Constitution §I). `Run` uses `cmd.Run()`; `RunOutput` uses `cmd.Output()` (stdout returned, excluded from the error text). Both capture stderr separately and, on non-zero exit, wrap it as `fmt.Errorf("%w: %s", err, strings.TrimSpace(stderr))` — the stderr-in-error convention callers pattern-match on — falling back to the **bare** error when trimmed stderr is empty (so no dangling `": "`). The `%w` wrap keeps `errors.As` working with a `*exec.ExitError` target (`var exitErr *exec.ExitError; errors.As(err, &exitErr)`).

**Child-env scrub (inherit path)**: when `RunOpts.Env` is nil, the child environment is `os.Environ()` minus `TMUX` and `TMUX_PANE` — tmux client-context variables that, inherited, attribute daemon commands to the wrong pane on the target server (§ Design Decisions → The runner core scrubs tmux client context from the child env). An explicit `RunOpts.Env` passes through verbatim — the caller owns it (`CreateSession`'s `CleanEnvForServer()` is unaffected).

Two things are **deliberately not** in the core:

- **Timeouts** — the ctx is caller-owned; every call site keeps its own budget (`withTimeout()` 10s in `internal/tmux`, daemon `cmdTimeout`, riff `TmuxTimeout`, `agentHookCmdTimeout`). Centralizing them would flatten deliberately-divergent budgets and move timeout ownership away from the call site Constitution §I puts it at.
- **Socket targeting** — each caller builds its own argv prefix, because the four flavors are documented per-site semantics: `internal/tmux`'s `serverArgs(server)`, `internal/daemon`'s const `-L rk-daemon` prepend (via the thin `runTmux`/`runTmuxInDir`/`runTmuxOutput` argv-prefix wrappers), `internal/riff`'s `tmuxArgv(spec, …)` (`-L spec.Server` on the daemon path / bare + `$TMUX`-restoring `childEnv(spec)` on the CLI path), and `cmd/rk/agent_hook.go`'s `tmuxSocketArgs(tmux.OriginalTMUX)` (`-S`).

Consumers: in-package `CreateSession` (`RunOpts{Env: CleanEnvForServer(), Dir: ServerBirthDir()}`) plus `tmuxExecServer`/`tmuxExecRawServer` (which keep their line-splitting / raw-string wrapper roles over `RunOutput`); `internal/daemon`'s three wrappers; `internal/riff`'s four spawn-engine sites (`resolveWindowIDFromPane` discards the error per its best-effort contract; the other three wrap the core's error into `SubprocessErr` at the call site); and `cmd/rk/agent_hook.go`'s `writeAgentStateImpl`/`writeChatImpl` (`_ = tmux.Run(…)`, preserving the never-fail contract). `internal/tmuxctl` is unaffected — it owns the long-running `-CC` control-mode dial, the sanctioned bypass of this boundary. Out of scope by contract: sites wanting materially different semantics, e.g. `probeServerAlive`'s boolean liveness probe (no stderr capture wanted).

## SPA Static Serving

Dual-mode SPA serving in `app/backend/api/spa.go`. `hasEmbeddedAssets()` checks if the `embed.FS` contains real build output (more than `.gitkeep`):

- **Production** (`mountEmbeddedSPA`): serves from `embed.FS` through the `embeddedSPASub` package-var seam (`fs.Sub(build.Frontend, "frontend")` in production; overridden by tests to inject an `fstest.MapFS`, since the test-build embed.FS holds only `.gitkeep`) + `http.FS`. SPA fallback rewrites to `index.html`.
- **Development** (`mountFilesystemSPA`): serves from `app/frontend/dist/` on the local filesystem. Path traversal prevented (resolved path must stay within SPA directory).

Both modes: any request not matching `/api/*`, `/relay/*`, `/proxy/*`, or `/present/*` serves `index.html` for client-side routing. In development, Vite handles SPA fallback natively.

### Two-tier cache policy

Both mounts apply one shared policy via `setSPACacheControl(w, urlPath)`, keyed on the path of the file **actually being served** (not the raw request URL — the SPA fallback serves `index.html` even when the request URL looks like a stale hashed asset, and that response must never inherit the immutable policy):

| Path | `Cache-Control` | Validator |
|------|-----------------|-----------|
| under `/assets/` | `public, max-age=31536000, immutable` (`spaAssetsCacheControl`) | none needed — Vite content-hashes the filename, so a rebuild changes the URL |
| everything else — `index.html`, every SPA-fallback route, root-level files (favicons, manifests) | `no-cache` (`spaHTMLCacheControl`) | embedded: content ETag; filesystem: mtime `Last-Modified` |

Both values are named constants, so no header literal is repeated across the two mounts.

**Embedded-mode ETag**: embedded files carry a **zero modtime**, so `net/http` emits no `Last-Modified` and generates no `ETag` on its own — and a response carrying neither a validator nor a freshness lifetime is uncacheable, forcing a full ~700KB bundle transfer on every navigation. The validator is therefore content-derived: a quoted truncated SHA-256 (first 8 bytes, hex) of the served bytes, computed lazily per path and memoized in a per-mount `map[string]string` guarded by a `sync.Mutex`. The header is set **before** delegating to `http.FileServer`, so `net/http`'s `serveContent` answers `If-None-Match` with `304` itself — no hand-rolled conditional-request handling. Memoization is safe because the embedded FS is immutable for the process lifetime (same rationale as `pwa.go`'s `tintCached`); it is a pure function of fixed bytes, not persistent state, so Constitution §II is unaffected.

**Filesystem mode** applies the same two-tier `Cache-Control` but computes no ETag — `http.ServeFile` already supplies mtime-based `Last-Modified`/`If-Modified-Since` 304s. The contract is behavior parity (assets cached, HTML revalidated cheaply), not implementation symmetry.

The PWA identity routes (`api/pwa.go`) are registered before the SPA catch-all and set their own `Cache-Control: no-cache` plus a `?c=` cache-buster (§ PWA Identity Assets) — they never reach this handler and are unaffected by the policy.

## Chrome Architecture

**Lazy-loaded components**: `CommandPalette`, `ThemeSelector`, and `CreateSessionDialog` are loaded via `React.lazy()` with dynamic `import()` (not static imports). Each uses `.then(m => ({ default: m.X }))` to re-wrap named exports for `React.lazy()` compatibility. Render sites wrapped in per-component `<Suspense fallback={null}>` boundaries. These components are overlays/dialogs that render conditionally — lazy loading keeps them out of the initial bundle for faster first paint.

**Shell wrapper (CSS Grid topology)** — `<Shell>` (`app/frontend/src/components/shell/shell.tsx`) is the shared chrome wrapper used by both `AppShell` and `BoardPage`. The shell is a single CSS Grid root carrying `height: 100%` — it fills the root layout's `flex-1` content region. The TopBar is NOT part of the Shell grid (260707-4vq2-lift-topbar-root-layout): it mounts once as `RootTopBar` in the persistent root layout, full-width above this Shell. The `--app-height` var (iOS keyboard handling) is maintained by `useVisualViewport()` in `RootWrapper` on the root layout div; Shell neither calls the hook nor reads the var. Desktop topology (`>= 640px`):

```
grid-template-areas:
  "sidebar content"
  "sidebar bottombar"
grid-template-rows:    1fr auto
grid-template-columns: ${sidebarWidth}px 1fr   (when sidebarOpen)
grid-template-columns: 0 1fr                   (when !sidebarOpen)
transition: grid-template-columns 150ms ease-out
```

Sidebar is full-height — it spans both rows and owns the entire left column. Content/bottombar stack in the right column. Sidebar collapse zeroes the first grid column (no 48px rail) — the content/bottombar cells extend their left edge to page.left automatically; no JS-side conditional rendering or component mutation.

The `sidebar` grid area is **Shell-owned**: on desktop `Shell` renders the `<aside style={{ gridArea: "sidebar" }} aria-label="Sidebar">` itself from its `sidebarChildren` prop, gated `!isMobile && sidebarOpen && !!sidebarChildren` (fully unmounts on collapse — no zero-width rail). Consumers place ONLY the `content` and `bottombar` grid areas; they never grid-area-place `sidebar`. The aside wraps `sidebarChildren` in a `flex-1 min-w-0 overflow-hidden` content wrapper and accepts an optional `sidebarResizeHandle?: ReactNode` slot rendered at its right edge — the desktop drag-resize handle. AppShell passes its handle through this slot; BoardPage passes none (drag-resize is intentionally absent on the board route). The aside carries `border-r border-border` ONLY when no handle is passed (BoardPage): with a handle the 3px handle bar is the visual seam, so a border would double it. Drag-resize wiring stays AppShell-only — all drag state/handlers (`handleDragHandlePointerDown`, width persistence, aria-value bounds) live in AppShell; the handle rides through the slot as an opaque node, so `Shell` stays dumb about drag logic. The mobile overlay never renders the handle. The handle is hidden when `sidebarOpen === false` (the only re-open affordance is the hamburger).

Mobile topology (`< 640px`): single column, `grid-template-areas: "content" / "bottombar"`. Sidebar renders as an overlay child of the Shell positioned via `gridRow: "1 / 3"` (spans content + bottombar, leaves the root-layout topbar above the Shell visible). Backdrop and `<aside>` use `position: absolute` (NOT `fixed inset-0`) so the overlay starts below the topbar — matches the existing project convention recorded in `fab/project/context.md`. The aside carries `role="dialog" aria-modal="true"`. Sidebar overlay open/close is driven by the same `sidebarOpen` state; `ChromeContext` carries no `drawerOpen`.

**Hamburger placement** — the hamburger icon is statically rendered at `TopBar.left` in both `sidebarOpen` states. Visual "relocation" on collapse is a side effect of the grid column collapsing; there is no component-level relocation logic. When `sidebarOpen === true`, the hamburger sits at the sidebar.right / topbar.left seam (pixel-identical to "attached to sidebar"). When `sidebarOpen === false`, it sits at page.left because the topbar grid cell has extended to page.left.

**Keyboard toggle** — `Cmd+\` (macOS) / `Ctrl+\` (Linux/Windows) toggles `sidebarOpen` from any route that mounts `<Shell>`. **Sidebar width persistence** — width state lives in `ChromeContext` (`sidebarWidth`). **FocusedTerminalContext** (`app/frontend/src/contexts/focused-terminal-context.tsx`) — tracks the currently-focused terminal across the app so the shell-level `BottomBar` can target the right WebSocket regardless of route. Mounted in `RootWrapper` between `SessionProvider` and `OptimisticProvider`; provider tree order is `ThemeProvider > ChromeProvider > RootWrapper(SessionProvider > OptimisticProvider > FocusedTerminalProvider > Outlet)`. Shape:

```ts
type FocusedTerminal = {
  wsRef: React.RefObject<WebSocket | null>;
  server: string;
  session: string;
  windowIndex: string;
} | null;

type FocusedTerminalContextValue = {
  focused: FocusedTerminal;
  setFocused: (t: FocusedTerminal) => void;
};
```

Producers: `TerminalClient` registers on mount when its `registerFocus` prop is `true` (single-terminal route default) and clears on unmount. `BoardPane` registers when its `isFocused` prop becomes true (and on initial pane mount); it manages the registration itself and passes `registerFocus={false}` to its inner `TerminalClient` to avoid producer contention. `BoardPane` clears the focused terminal on **unmount** iff it is still the registered pane (ref-guarded still-mine check) so leaving a board for `/$server` does not strand a stale target; a pane-focus SWITCH does not unmount the losing pane, so the next pane to gain focus overwrites.

Consumers: the shell-level `BottomBar` reads `focused?.wsRef` (it takes no `wsRef` prop); the docked compose strip (`ComposeStrip`, § ui/compose-and-bottom-bar.md § Docked Compose Strip) reads `focused` live and sends to `focused.wsRef` at send time (the live-target model — no target frozen at open). When `focused === null` (e.g. the `/$server` tiles route), the strip renders disabled and BottomBar input handlers natural-no-op via the existing `wsRef.current?.readyState !== OPEN` guard. The docked-strip enablement is the persisted `composeStripEnabled` chrome preference (`ChromeContext`), not context state here.

**Kill-redirect gate (`currentWindowEverSeen`)** — The "session/window gone" redirect in `app/frontend/src/app.tsx` (around the `useEffect` that calls `computeKillRedirect` from `app/frontend/src/lib/navigation.ts`) MUST NOT fire for a freshly-navigated URL whose (session, window) pair has not yet been observed as valid in the SSE `sessions` stream. `computeKillRedirect` accepts a `currentWindowEverSeen?: boolean` param (defaults to `true` for legacy callers and unit tests) and short-circuits to `null` when false — bypassing both the "session gone → dashboard" and "window gone → nearest sibling" branches. The caller maintains two refs: `currentWindowEverSeenRef` (boolean, flipped `true` whenever the memoized `currentWindow` is non-null) and `lastObservedUrlKeyRef` (string, `${server}|${session}|${window}`). Any URL-key change resets the seen flag to `false`. This gates two transient SSE states that are not proof the URL is unreachable: (a) a stale cached first payload that replays an older server snapshot before delivering current data, and (b) a session whose `windows` array is briefly empty while tmux enumeration propagates into the next poll tick. Without the gate, either state makes `currentSession` or `currentWindow` null on the first SSE event after navigation, the redirect fires, and `TerminalClient` unmounts mid-initialization — surfacing as an e2e flake where `.xterm-screen` briefly appears then disappears. Genuine kills from another client still redirect normally, because the URL key only resets on navigation, not on SSE payload changes: once the seen flag is `true`, a subsequent payload that drops the window triggers the redirect as before.

## CLI Subcommands (Cobra)

`app/backend/cmd/rk/` uses `spf13/cobra` for CLI management. `root.go` declares `var version = "dev"` (overridden by ldflags) and registers all subcommands. `main.go` just calls `execute()`. Version info via `--version`/`-v` global flag (Cobra built-in, not a subcommand).

**Shared output convention — persistent `--quiet` + `outputSink`** (toolkit Principle 9) (260717-f8yv-cli-output-volume-controls). A single **persistent `--quiet` bool** is registered on `rootCmd` (`root.go`, bound to package-level `quiet`), so every present and future subcommand accepts it uniformly and inherits it with zero registration work; it is a deliberate no-op on any command not yet routed through the sink (incremental adoption). The convention, decided once, lives in `cmd/rk/output.go` (package `main`, no `internal/` package for a CLI-only concern): **`outputSink{data, chatter io.Writer}`** with `Dataf` (data channel) / `Notef` (chatter channel). **stdout carries data** — machine-consumable results (outcome lines, `--json` documents, requested previews/lists) — never gated by `--quiet`; **stderr carries chatter** — progress/decoration — routed to `io.Discard` under `--quiet`. **Errors always survive** (they flow through `RunE` returns and ungated stderr writes); `--quiet` never changes exit codes; a successful run with nothing to report is silent under `--quiet`. Built on `cmd.OutOrStdout()`/`cmd.ErrOrStderr()` (never bare `os.Stdout`/`os.Stderr`) so gating is unit-testable — the idiom `doctor.go`/`agent_setup.go` already used; `newSink(cmd)` reads `--quiet` off the invoked command (falling back to the package var for a bare test command), `newSinkWriters(data, chatter)` builds a test sink from explicit writers. **Adopted by `update`/`doctor`/`agent setup`** (the audit-named chatter carriers — see their rows); `mux reap` takes a display cap instead of a quiet conversion (its output is all data — see its row). This satisfies toolkit Principle 9 — see [toolkit-standards](toolkit-standards.md) § Requirement: Bounded, high-signal output (Principle 9).

## Embedded Frontend Assets

`app/backend/build/embed.go` exposes `//go:embed all:frontend` as `build.Frontend` (`embed.FS`) and `//go:embed all:codebridge` as `build.CodeBridge` (`embed.FS` — the packaged rk-code-bridge VSIX + `VERSION` sidecar; see [code-bridge](/run-kit/code-bridge.md) § Distribution). During development, both directories contain only `.gitkeep` (empty FS). Production builds copy `app/frontend/dist/` into `app/backend/build/frontend/` and the packaged VSIX into `app/backend/build/codebridge/` before `go build`.

Files read out of the `embed.FS` carry a **zero modtime** — `embed` records no timestamps — so `net/http` emits no `Last-Modified` for them and HTTP caching in embedded mode has to supply its own validator (§ SPA Static Serving → Two-tier cache policy).

`api/spa.go` uses dual-mode serving:
- **Production**: `hasEmbeddedAssets()` detects real build output (more than `.gitkeep`), serves from `embed.FS` via `mountEmbeddedSPA()`
- **Development**: Falls back to filesystem-based serving from `app/frontend/dist/` via `mountFilesystemSPA()` (Vite dev server handles frontend)

Both modes include SPA fallback (serve `index.html` for non-matching paths), API/relay route guards, and the two-tier cache policy.

## Boards Feature

Pane boards are named collections of pinned tmux windows rendered as a horizontal pane dashboard at `/board/$name`. The model is **link-based and server-scoped** (260718-co9z-link-based-board-pinning): a pinned window is `link-window`'d into its own single-window session `_rk-pin-<id>` while staying a member of its home session (dual presence — visible in SESSIONS AND on the board), and a board is the **set of pin-sessions sharing an `@rk_ses_pin_board` SESSION var** (not a tmux session itself, and not a `@rk_ses_pin_board` server-option encoding). Boards are server-scoped because `link-window`/`move-window` can't cross tmux servers — the board *list* is summarized across reachable servers, but there is no cross-server window union. A board exists only while ≥1 pin carries its name (no empty boards, no registry). Unpin is a `kill-session` on the pin-session (the window survives via its home link) with a last-link recovery path when the pin link is the window's only link. See `tmux-sessions.md` § Pin Sessions and § `@rk_ses_pin_board` for the full pin/unpin/reorder contract, the three session vars (`@rk_ses_pin_board`/`@rk_ses_pin_home`/`@rk_ses_pin_order`), order keys, and the pin-session-first direct-attach relay.

### Constitution Alignment

- **II (No Database)** — pin state lives only in tmux: the `_rk-pin-*` session structure + its `@rk_ses_pin_board`/`@rk_ses_pin_home`/`@rk_ses_pin_order` session vars (tmux session structure IS the record — not a derived server-option value) (260602-qn62-move-based-board-pin-sessions). Browser `localStorage` holds only view-local pane widths
- **IV (Minimal Surface Area)** — adds exactly one route (`/board/$name`) with one rendering path (`TerminalClient`/`/relay/{windowId}`); no relay ephemeral subsystem, no `@rk_ses_pin_board` encoding, no startup sweep, no SSE board-cleanup/bootstrap (260602-qn62-move-based-board-pin-sessions)
- **V (Keyboard-First)** — pin/unpin/switch/cycle reachable via Cmd+K palette; pane focus cycle via Cmd+[/]
- **VI (Tmux Sessions Survive Server Restarts)** — pin state persists with the tmux server across rk-go restarts, so there is NO restore-sweep (260602-qn62-move-based-board-pin-sessions); `tmux kill-server` loses the boards on that server (expected and acceptable). An emptied home session (its only window pinned away) persists via the `exit-empty off` backstop (260602-a1wo-prevent-exit-empty-server-death) so unpin can restore the window to it
- **VII (Convention Over Configuration)** — no new env vars, no new config files; reuses the established `@rk_*` user-option pattern

## Design Decisions

### `rk tutorial` types its kickoff into the booted agent, never a positional argument
**Decision**: the window runs the resolved launcher BARE (`riff.SkillPaneCommand(launcher, "")`); the kickoff prompt is then typed into the pane (`send-keys -l`) and submitted, with each step verified from the pane's own text — boot settle (non-blank, unchanged across two polls), echo check (alphanumerics-only compare, so input-box borders/wrapping are noise), and a one-retry Enter guard against the swallowed-Enter trap. An unverifiable delivery degrades to a stderr paste-it-yourself note carrying the exact kickoff text, exit 0.
**Why**: the launcher string is provider-opaque and only claude's CLI accepts a positional prompt — `kimi --auto '<prompt>'` parses the prompt as a subcommand and exits (`unknown command … See 'kimi --help'`), which is fatal on the tier the command defaults to. Typed keys are the only provider-agnostic delivery; the verification loop is what makes them safe.
**Rejected**: the launcher positional argument (riff's task-injection seam) — shipped first, broke immediately on the fast tier's kimi launcher; a per-provider prompt-flag table — rk would have to own provider CLI schemas it deliberately delegates to fab (constitution §III).
*Introduced by*: 260903-7ajq-rk-tutorial-entry

### `rk tutorial`'s singleton is session-scoped
**Decision**: an exact-name `tutorial` window in the current session is selected (by `@N` id) instead of creating a duplicate; a same-named window in another session does not match.
**Why**: re-running the entry command should return to the tour, and a tour belongs to the project session it started in.
**Rejected**: the operator launcher's server-wide singleton (a tour is not a per-server coordinator); riff-style collision suffixing (stacks abandoned `tutorial-2` windows).
*Introduced by*: 260903-7ajq-rk-tutorial-entry

### `rk tutorial` defaults to the `fast` tier
**Decision**: `--tier` defaults to `fast`, forwarded verbatim as the fab role selector.
**Why**: tour turns are short narration beats gated on the user saying "next"; the fast tier keeps them snappy, and the default is a one-line flip (to `""`, fab's default tier) if the fast provider ever breaks the tour's pacing contract.
**Rejected**: defaulting to fab's default tier with `fast` as opt-in — inverts the stated intent for the common case.
*Introduced by*: 260903-7ajq-rk-tutorial-entry

### Same-origin present targets use site-relative slot URLs
**Decision**: `present` and web-add targets whose scheme and host equal the
run-kit server origin resolve to their path and query as a leading-slash
`KindSiteRelative` value before localhost proxy classification.
**Why**: `rk url` is the origin agents can derive, and a site-relative slot lets
every remote viewer load the same run-kit-hosted resource from its own origin.
**Rejected**: A bare `/path` CLI target, which collides with absolute filesystem
paths; a `--relative` flag that adds surface for one caller.
*Introduced by*: 260902-6uu0-rk-skill-tutorial-topic

### The e2e palette opener defocuses only on retry, never on the first attempt
**Decision**: `_ready.ts`'s `openPalette` presses the chord with focus untouched on attempt 1; only a failed attempt blurs the active element before re-pressing, and the last attempt asserts rather than probes so exhaustion costs the same three waits as success and names the palette.
**Why**: focus state is itself observable behavior that several specs assert on, so a first attempt identical to a bare press means the helper cannot change what any passing focus-sensitive spec proves. The blur is the backstop for a chord lost some other way — the chord the helper presses is the shifted alias, which terminal focus does not consume.
**Rejected**: an unconditional pre-press blur (silently mutates focus at every call site, and would let a broken iframe-reclaim seam pass in the tests that prove it); a bare bounded retry with no focus handling (a no-op when focus is stably in the terminal, which is the failure being fixed); a Playwright `test.extend` fixture (heavier than the plain-module precedent).
*Introduced by*: 260830-my49-harden-e2e-palette-opener

### Doctor's ephemeral-servers row is always present and always OK-shaped
**Decision**: the `ephemeral servers` check appends unconditionally with `OK: true` in every branch; the count + `rk mux reap --ephemeral` hint, `none`, or an enumeration-skip message ride the Note.
**Why**: a stable check set keeps `--json` consumers schema-stable (the existing checks append unconditionally), and scratch servers are a hygiene fact, not a dependency failure — the row must never flip the overall verdict (the code-server and drift precedents).
**Rejected**: omitting the row at zero (unstable check set for JSON consumers); FAIL-shaping nonzero counts (ephemeral marks are deliberate creator opt-in, not a fault).
*Introduced by*: 260821-l1qe-ephemeral-server-surfacing

### Legacy marker values are normalized at every boundary, never migrated in place

**Decision**: Flat tokens are mapped forward by `NormalizeMarker` at three seams — the live read (`parseWindows`), the snapshot read (`layout.go` field 27), and the restore write (`restore.go`) — rather than by a one-shot rewrite of `@rk_win_marker` across running servers.

**Why**: Constitution II derives state from tmux at request time; a migration pass would need a writable sweep over every reachable server and would still miss servers started later from an old snapshot. Normalizing at the boundaries makes every path idempotent and leaves no window in a state its own validator rejects.

**Rejected**: A `MigrateLegacyOptions` row (that table remaps option names, and this is a value remap); a startup sweep (a write pass over user state at boot, with no way to reach detached servers).

*Introduced by*: 260830-srec-marker-migrate-well-ink-retirements

### Flair settings normalize is a membership check, not a canonicalizer
**Decision**: the `server_flairs` `mapSection` normalize func accepts a value iff it is non-empty AND `validate.FlairValues[value]` — a small closure in `internal/settings`, not a new exported validator.
**Why**: the settings parser is a `nestedSection` registry requiring a `func(string) (string, bool)` normalize, and the universal flair set is consumed generically — no flair names enumerated in new code.
**Rejected**: a `validate.NormalizeServerFlairValue` mirroring `NormalizeColorValue` — colors need canonicalization (legacy ints), flairs are exact tokens; a pass/fail membership check needs no canonical form.
*Introduced by*: 260820-arqw-server-flair-application

### Tmux-option-derived serving for `rk present`
**Decision**: file/dir targets of `rk present` are served by the `/present/{windowId}/{n}/*` GET route (the n-less form maps to slot 1 for one release), which resolves the window's `@rk_win_web_<n>_root` option from tmux at request time; the CLI only sets window options.
**Why**: Constitution II/X native — the serve root is an ephemeral fact about what the pane is presenting; it lives in tmux, dies with the window, and needs no registration state, no GC, and no new disk store; live edits are visible on a plain reload. Containment is symlink-resolved (`EvalSymlinks` + `filepath.Rel`), never a lexical prefix check — real trees carry legitimate intra-tree symlinks, so a prefix ban is both too weak and too strict (the code-server tarball lesson); the tmux socket is already the trust boundary (anyone who can set window options can run code in panes), so no new principal is introduced — but path traversal through the web server must be impossible.
**Rejected**: wrapping `python3 -m http.server` (port-picking, python dependency, orphan-process lifecycle); a spool-copy under `$XDG_STATE_HOME/run-kit/present/` (GC + size-cap problems, kills live iteration, strains Constitution II's carve-outs).
*Introduced by*: 260813-becu-rk-present-attach-verb

### `rk present` keeps the URL as stdout data while `rk tab web add` prints the address
**Decision**: `rk present` prints the resolved URL; `rk tab web add` prints `@N/web/<n>` and echoes the URL on stderr.
**Why**: the URL is `present`'s documented, parsed contract (`rk skill display`, callers); the spec assigns the address to `web add`. Two verbs, one code path (`webAddShow`), two data outputs.
**Rejected**: printing both lines from both verbs (stdout stops being one datum); making `present` print the address (unrequested break).
*Introduced by*: 260829-c143-rk-tab-cli-present-sugar

### `--show` on a full 3-tile layout replaces the last slot
**Decision**: when `web` is absent and the layout already holds 3 tiles, `--show` writes `web` into `Order[2]` instead of exiting 1.
**Why**: `rk present` must keep succeeding on every layout; the last slot is the least valuable tile in every 3-tile shape and slot A stays dominant.
**Rejected**: exit 1 (regresses `present`); replacing slot A (steals the user's main tile).
*Introduced by*: 260829-c143-rk-tab-cli-present-sugar

### The layout verb port lives in the existing `internal/layoutspec`
**Decision**: `internal/layoutspec` holds the pure mutations (`Default`, `Promote`, `SwapWithNext`, `Close`, `Add`, `Cycle`, `SetShape` with named sentinel errors) as a case-for-case port of the frontend's `surface-layout.ts` table, beside the grammar (`Parse`/`String`/`Has`) the `/options` validator uses.
**Why**: one Go table for shapes/surfaces/arity serves both the API validator and the `rk tab layout` verbs; a sibling package would duplicate the grammar and could drift — agent and human go through one growth/collapse table.
**Rejected**: a new `internal/layoutverbs` package.
*Introduced by*: 260829-c143-rk-tab-cli-present-sugar

### Go backend + Vite SPA over a Next.js monolith
**Decision**: a Go backend and a Vite SPA, decoupled for independent iteration.
**Why**: the Go backend is a stable, long-lived API that outlives any individual frontend; multi-client API support (web, mobile, CLI) without a split API surface.
**Rejected**: a Next.js monolith.

### Single port architecture
**Decision**: Go serves API, WebSocket relay, and SPA static files on one port, in one binary.
**Rejected**: a two-port split (Next.js :3000, relay :3001) — a Node.js artifact: separate processes required separate ports.

### chi over stdlib ServeMux
**Decision**: chi for middleware chaining (CORS, logging, recovery).
**Rejected**: Go 1.22+ ServeMux — it has pattern matching but lacks ergonomic middleware composition.

### TanStack Router over React Router
**Decision**: TanStack Router — type-safe params and search params, built-in loader pattern. Single route `/:session/:window` in the frontend.

### Vite proxy in dev (not CORS)
**Decision**: the Vite dev server proxies to the Go backend — single browser URL, no CORS config needed; WebSocket upgrade works transparently. Go includes chi CORS middleware for production/non-browser clients.

### SPA fallback in Go
**Decision**: Go serves the SPA standalone; TLS termination is handled externally via Tailscale Serve when needed.

### Every tmux session is a project
**Decision**: no config, no "Other" bucket. Project root derived from window 0's `pane_current_path`.

### Config via env vars (not YAML) for deployment binding
**Decision**: `.env` committed with defaults (`RK_PORT`, `RK_HOST`), `.env.local` for overrides, loaded via `.envrc` (direnv). Go and Vite read `RK_PORT`/`RK_HOST` directly. `dev.sh` translates `RK_PORT+1` for the backend subprocess. No relay port — single port serves everything.

### Dedicated tmux server (`-L runkit`)
**Decision**: run-kit sessions live on a named tmux server `runkit` with its own config (`internal/tmux/tmux.conf` loaded via `-f`). The default tmux server is also queried for session discovery (read-only display of external sessions). `CreateSession()` uses plain `tmux new-session` on the runkit server (no byobu dependency). `SessionInfo` carries a `Name` field; `ProjectSession` has `Name` and `Windows` fields. The caller passes the target server name to each tmux operation.

### One exported tmux runner core, per-site socket targeting
**Decision**: `internal/tmux` exports `Run`/`RunOutput`/`RunOpts` (§ tmux Runner Core) as the only implementation of the `exec.CommandContext("tmux", argv)` + capture-stderr + wrap-trimmed-stderr idiom; `internal/daemon`, `internal/riff`, and `cmd/rk` delegate to it.
**Why**: a hand-copied runner drifts — copies diverge on capture strategy (`CombinedOutput` vs stderr-only) and buffer type, and every fix to the idiom must then be applied N times or silently miss a copy. One implementation is what makes the code-quality rule "all tmux interaction goes through `internal/tmux/`" enforceable. `internal/tmux` holds the superset implementation (env + dir options), so exporting it is the minimal consolidation: no new package, no behavior change.
**Rejected**: unifying socket targeting along with the runner — the four flavors (`-L` const daemon socket / `-L spec.Server` / bare + restored `$TMUX` / `-S` from `tmux.OriginalTMUX`) are deliberate per-site semantics, so each caller keeps its own argv-prefix builder; centralizing timeouts in the core — Constitution §I keeps them caller-owned and the sites run deliberately different budgets; a "quiet" core variant for best-effort callers — error-discard stays at the call site (`riff.resolveWindowIDFromPane`, both `agent_hook` never-fail sites), keeping the core's contract single-shaped.
*Introduced by*: 260731-zeiy-consolidate-tmux-runner-core

### The runner core scrubs tmux client context from the child env
**Decision**: `newRunCmd` builds the child env as `os.Environ()` minus `TMUX`/`TMUX_PANE` on the inherit path (`RunOpts.Env == nil`); an explicit `Env` passes through verbatim. There is no process-global `os.Unsetenv("TMUX_PANE")` (the existing global `os.Unsetenv("TMUX")` stays as belt-and-braces).
**Why**: tmux attributes a CLI command to the pane named by `TMUX_PANE` resolved against the TARGET server, and pane ids are unique only per server — a daemon running inside a tmux pane leaks its own server's pane id into commands aimed at other servers, and when the colliding pane's session has only the dashboard's read-only `-CC` relay client attached, tmux refuses the mutating commands (`send-keys`) while permitting the read-only-listed ones (`set-buffer`/`paste-buffer`): the paste lands, Enter fails. The runner is the single shared seam, so the daemon's HTTP sends and the `rk mux send` CLI verb are both covered. rk CLI verbs legitimately read `$TMUX_PANE` to self-identify (`rk role`, `rk tab`, `rk owntab`, the guard shim), so only spawned tmux children may lose it.
**Rejected**: Global unset (breaks `rk role`/`rk tab`/`rk owntab` self-identification); per-call-site scrubbing (34+ call sites, one missed site reintroduces the bug).
*Introduced by*: 260902-8jco-tmux-pane-env-scrub-send-failures

### Two-tier SPA cache policy keyed on the `/assets/` prefix, with a content-derived embedded ETag
**Decision**: hashed assets get `public, max-age=31536000, immutable`; `index.html`, every SPA-fallback route, and other non-asset paths get `no-cache` plus a validator (§ SPA Static Serving).
**Why**: *the prefix split* — Vite content-hashes exactly the filenames under `/assets/`, so the URL changes whenever the content does and infinite caching is safe **by construction** — while the HTML entry point must revalidate every load so a new deploy reaches clients immediately, which `no-cache` + a cheap conditional fetch buys at ~3KB instead of the full bundle. *A content-derived ETag rather than mtime or version* — `embed.FS` records no timestamps, so embedded responses carry a zero modtime and `net/http` emits no `Last-Modified` and no `ETag` of its own — with neither validator nor freshness lifetime the browser could cache nothing, so every navigation would re-download ~700KB as a fresh 200 (dev/filesystem mode caches *better* without the ETag, because `http.ServeFile` sees a real mtime). A hash of the served bytes is the only honest validator available, and setting it before delegating to `http.FileServer` lets `serveContent` handle `If-None-Match` → 304 without hand-rolled conditional logic. *Memoized* — the embedded FS is immutable for the process lifetime, so the per-path hash is a pure function of fixed bytes — the same Constitution-§II-compatible shape as `pwa.go`'s `tintCached`, not persistent state.
**Rejected**: an rk-version-derived ETag — it aliases distinct dev builds that share a version string; computing ETags in filesystem mode too — `http.ServeFile`'s mtime validators already 304 correctly there, and the contract is behavior parity, not implementation symmetry; bundling the SPA into the Electron desktop shell to avoid the transfer entirely — it breaks version-match-by-construction between a host's UI and its API, and the shell never auto-updates.
*Introduced by*: 260801-ujuk-spa-asset-cache-headers

### Active window sync — tmux truth, URL as bookmark
**Decision**: tmux is the sole source of truth for "current window" per server. The URL is a resumable bookmark used only on mount (and reload); after mount it is derived state, rewritten by an SSE-driven `navigate({ replace: true })` whenever the server-reported `isActiveWindow` differs from the URL. **Why**: there is no client-owned selection state to protect, so a debounce (such as a 3-second `userNavTimestampRef`) must not be added.
**Rejected**: per-tab current window (reintroduces a second writer, doesn't match the dashboard model); hooks + `rk notify` + lockfile (incompatible with PR #197's Constitution §II Non-Goal); a client-side navigation debounce.
*Introduced by*: 260528-nvlp-active-window-sync

### The rk-owned profile lives in `~/.rk/code-server-profile`, seeded write-once, with extensions pinned to the default location
**Decision**: `--user-data-dir {home}/.rk/code-server-profile` (resolved via the `codeServerUserHomeDir` seam), `User/settings.json` seeded with `{"chat.disableAIFeatures": true, "workbench.startupEditor": "none"}` only when the file is absent, and `--extensions-dir` pinned to `$XDG_DATA_HOME/code-server/extensions` (else `~/.local/share/...`) — code-server's own default. A one-shot `os.Rename` migration (`migrateCodeServerProfile`, run before the seed) moves a legacy `~/.rk/code-server` profile dir across when the old exists and the new does not (both-exist ⇒ the new wins, both untouched; fresh host ⇒ no-op), preserving settings and hot-exit state.
**Why**: the two settings have no CLI flags, so a profile rk owns is the only reproducible-baseline mechanism that never touches the user's personal profile; write-once means user edits win forever (a baseline, not enforcement); `~/.rk/` is rk's user-config namespace and the seeded settings.json is the user-editable artifact; the extensions pin exists because code-server derives its default extensions dir from the user-data-dir, so the override alone would hide installed extensions. **Rejected**: `$XDG_DATA_HOME/rk/code-server` (mirrors code-server's placement but hides the editable settings.json in a data dir); `$XDG_STATE_HOME/run-kit/code-server` (those carve-outs are rk-written state — this dir is code-server-owned and user-edited); aborting the spawn on profile failures (an editor must never block the dashboard).

**Rejected**: keeping the port in the client contract (`/proxy/{port}/?folder=…`) — a port drift silently blanks every user's workspace; seeding the resolved port onto the server at startup and reading a field (per-request `config.Load()` is four getenvs and keeps tests on `t.Setenv` instead of a server-field seam).

### `@rk_win_url` dual-reads instead of a migration-sweep row
**Decision**: `@rk_win_url` has NO `legacyOptions` sweep row. It is dual-READ in both hot read paths (`parseWindows`, `ReadWebTabFamily`): with an empty `web_1` it surfaces as the dense family's first tab with the active pointer defaulted, and `WebRemove` on the last tab also clears the retired name. **Why**: a sweep row breaks the shipped frontend two ways: (1) the migration sweep is once-per-server, so a mid-session `tmux set-option -w @rk_win_url` (the present-auto-expand / web-view-lens live-flip path the frontend polls via the derived `rkUrl`) is never migrated and goes unread; (2) the read path cannot converge `@rk_url → @rk_win_url → @rk_win_web_1`, so the sweep row unsets the intermediate `@rk_win_url` that the legacy-scope-sweep e2e asserts holds the value. ### PR-status collector with wholesale-rebuild cleanup + network-isolated three-layer split
**Decision**: `internal/prstatus.Collector` (mirroring `internal/metrics.Collector`) makes ONE batched `gh api graphql viewer.pullRequests(states: [OPEN, MERGED, CLOSED], orderBy: UPDATED_AT DESC, first: 100)` call on a slow 90s background tick, REPLACES its URL-keyed `byURL` map wholesale each refresh, and serves a deep-copied `Snapshot()`. Three layers on separate cadences keep the 2.5s SSE hot path network-free: (1) `PrURL`/`PrNumber` are derived from the pane's branch via the `prstatus` background branch refresher (register + snapshot-join, off the hot path — see § Branch→PR Derivation and the next decision); (2) the collector fetches live status behind the 90s tick + on-demand POST; (3) the SSE hub joins status onto any window with a derived `PrURL` via a pure `Snapshot()` read, keyed on the canonical URL. gh absent/unauth is a silent no-op (matches `command -v rk`).
**Why**: *include MERGED/CLOSED, not just OPEN* — a just-merged PR is recently updated, so it sits near the top of the `UPDATED_AT DESC` window and shows its `merged` (purple) state instead of dropping to a bare PR number — the merged dot is reachable and is the most useful signal on a change-bound window. *Wholesale rebuild* — the `first: 100` recency cap is the eviction — a merged/closed PR shows its terminal state while it stays in the top-100 window, then ages out and drops from the next wholesale rebuild (along with killed windows) — cleanup for free, no eviction logic or window-lifecycle hook (the deciding factor when "how does cleanup happen?" was raised in design). *GraphQL not `gh search prs`* — the literal `gh search prs --author @me` argv ERRORS — that subcommand doesn't expose `statusCheckRollup`/`reviewDecision` JSON fields; `gh api graphql` is the standard cross-repo batched mechanism and serves the identical one-call/O(1)/full-status intent. *In-memory, not a tmux option or a state store* — the map is re-derivable in one call (Constitution §II — no DB, no tmux option), and a tmux option would add a two-writer race plus manual pruning; the only disk it touches is the never-authoritative startup seed cache (below), which changes nothing but cold-start latency. *Injectable `ghExec`/`available` seams* — matches the codebase's exec-seam test pattern, lets table tests stub `gh` output deterministically.
**Rejected**: per-PR `gh pr view` polling (doesn't scale — 10 tasks = 10 calls); a webhook receiver writing `.status.yaml` (overkill, contradicts fab-kit's poll-free design); `gh search prs` (missing fields).
*Introduced by*: 260610-596o-pr-status-sidebar

### Two-tier agent-state + branch-derived PR links (own-your-signals over consuming `fab pane map`)
**Decision**: run-kit derives its agent and PR signals itself rather than consuming Claude-only, fab-root-coupled signals through `fab pane map`: agent lifecycle state (Tier 2) reads the `@rk_agent_state` pane user option written by any harness's hooks (Tier 1 — change/stage — stays fab's), and PR links are derived server-side from the pane's branch. *Reconciler at parse-time*: the shell-command reconciler runs in `internal/tmux.parsePanes` (which already has the pane command + option value on one line) — colocated + unit-testable, mirroring the pure-parse convention; rollup/duration live in `internal/sessions`. *Branch→PR is a per-`(repoDir,branch)` resolver alongside the viewer-wide URL-keyed collector, not a replacement*: the `gh api graphql viewer.pullRequests` query has no branch/repo/cwd seam so it cannot express `gh pr list --head`; the two compose (derive URL → join live status by URL). *Resolution runs off the hot path*: the resolver lives in a background `BranchRefresher` and the FetchSessions/SSE path only registers + joins a snapshot, because inline `gh` execution there breaks the zero-network-call invariant and the 5s API cap; a shared process-wide `DefaultBranchRefresher` + package-level `Register`/`SnapshotBranchPR` façade keeps `FetchSessions`' signature free of the dependency. *Clean swap, no dual-source fallback*: agent columns read `—` until `rk agent setup` runs (single-operator rollout; fallback code contradicts §IV). *Explicit installer, not silent sync*: `rk agent setup` shows a diff + confirm before mutating user-global config, idempotent marker-keyed merge, `--uninstall`, plus `--yes`/`-y` non-interactive consent, `--dry-run` preview, and a non-TTY refusal naming `--yes` (260717-c424-toolkit-standards-conformance); full consent flow in [agent-state](agent-state.md) § `rk agent-setup`. Full design: [agent-state](agent-state.md), spec [`docs/specs/agent-state.md`](../../specs/agent-state.md). Unblocks fab-kit backlog `[ioku]` (fab pane send/map become convention readers).
**Why**: in a two-state `active|idle` model the most notification-worthy state (`waiting` — blocked on a human) is invisible, non-Claude agents show nothing, and PR visibility is limited to fab-change-bound windows; per constitution Principle X (amended by this change) hooks carry only the underivable, so PR links (derivable from the branch) must NOT ride a push pipeline.
**Rejected**: consuming `fab pane map` for agent state and PR links; reconciling in `internal/sessions` (duplicates the shell-name set); extending the single graphql query for branch→PR (no scoping seam, misses non-viewer PRs); silent hook sync (surprising for user-config mutation).
*Introduced by*: 260705-dmex-generic-agent-state-tier

### First-sight-only registration wake, debounced into one pass
**Decision**: `BranchRefresher.Register` signals a cap-1 `wake` channel only when the `(repoDir, branch)` key is NEWLY inserted into `entries`; `Start`'s loop answers a wake by draining further wakes for a fixed `branchPRWakeDebounce = 1s` window, then runs exactly one `refresh`.
**Why**: `Start`'s immediate first refresh is a no-op at process start (nothing is registered until the SSE enrichment loop has observed panes), so without a wake the first USEFUL pass waits out a whole 30s tick — the visible half of a multi-minute blank-status window after every `rk serve` start. A wake makes that pass event-driven, and the fixed settle window collapses one SSE pass's burst of dozens of registrations into ONE pass; refusing to extend the window on a drained wake means a steady trickle of new pairs can never postpone the pass indefinitely.
**Rejected**: waking on EVERY `Register` — the SSE pass re-registers every observed pair every 2.5s, which degenerates the refresher into a 2.5s poll of N `gh` subprocesses; waking from the sessions layer — pushes refresher knowledge onto the zero-subprocess hot path; shortening the 30s tick — multiplies gh volume without fixing the no-op first pass or the sequential-pass duration.
*Introduced by*: 260807-2ept-pr-status-cold-start

### The collector pushes a STORED head-index and wakes on store, rather than seeding entries once
**Decision**: `Collector.refresh` hands its parsed nodes to a nil-safe `SetViewerPRSink(func([]ViewerPR))` after a successful parse; `BranchRefresher.StoreViewerIndex` replaces a `(host/owner/name, headRef) → candidates` index wholesale and signals the same coalescing wake whenever the store is non-empty. Every pass then joins against the stored index before falling back to `gh pr list`.
**Why**: the batched GraphQL call already fetches each recent viewer PR's head repo and ref, so N sequential `gh pr list` calls would re-fetch data the process holds — storing the index fixes the cold-start latency AND the O(N)-subprocess steady state, where a one-shot seed of `entries` fixes neither and races the first registrations. Waking on store is what makes startup ordering safe without depending on wiring order: the collector's first fetch and the first SSE registrations race, and on the restart path the registrations win, so whichever lands second must trigger the pass. An EMPTY store signals nothing — there is no index to serve a pass from, so a wake would only burn one `gh pr list` per pair. Accepted cost: every non-empty store wakes the refresher, so steady state carries ~1 extra branch pass per 90s collector tick — near-zero-subprocess, since that pass is index-served.
**Rejected**: one-shot seeding of `entries` (racy at startup, no steady-state benefit); a pull from the refresher into the collector (inverts the existing wiring direction and adds a dependency edge); relying on wiring order alone (loses the restart-path race).
*Introduced by*: 260807-2ept-pr-status-cold-start

### An index miss is never an authoritative negative
**Decision**: only the per-pair gh fallback's successfully-parsed empty result, or the default-branch exclusion, may clear an entry; an index miss always falls THROUGH to gh, and the exclusion outranks an index hit.
**Why**: the batch covers only viewer-authored PRs inside the top-`prFetchLimit` recently-updated window, so an empty bucket cannot distinguish "no PR" from "not covered" — treating it as a negative would blank PR status for every non-viewer-authored, aged-out, fork-head, or cross-host pair. Failing open costs one subprocess; failing closed loses the signal the feature exists for. Accepted edge: a non-viewer-authored OPEN PR sharing a head ref with the viewer's MERGED PR shows merged until the viewer's PR ages out of the batch — same-repo same-head cross-author PRs are vanishingly rare and the case self-heals.
**Rejected**: treating an empty index bucket as a negative.
*Introduced by*: 260807-2ept-pr-status-cold-start

### Origin identity is HOST-QUALIFIED, and accepted by URL FORM rather than a dotted-segment heuristic
**Decision**: the index key is `host/owner/name` — the host parsed from the node's PR URL on the seed side (`prURLHost`; the batched query takes no `--hostname`, so the URL is a node's only host authority) and from `git remote get-url origin` on the pane side (`parseOriginRepo`, which accepts only an allowlisted scheme — `https`/`http`/`ssh`/`git` — or the scp-like `user@host:owner/name`). The identity half is case-folded; branch names are not.
**Why**: `owner/name` is not unique across forges — a pane whose origin is `gitlab.com/sahil87/tool` or a GHE mirror would otherwise join a `github.com/sahil87/tool` viewer PR, attach a wrong-host link, AND suppress the authoritative gh fallback that would have resolved it correctly. Deciding acceptance by form is what makes "not a filesystem path" decidable: a dot in the first segment is no evidence of a host (`cache.local/acme/tool` is a directory), and every rejection is fail-open, so strictness costs at most a subprocess. Folding case on the identity but not the ref matches GitHub's case-insensitive repository identities against a locally-typed origin URL while respecting case-sensitive git refs. Known fail-open classes: host aliases such as `ssh.github.com:443`, userless scp-like remotes, and paths that are not exactly `owner/name` never resolve an identity and always take the gh path.
**Rejected**: an `owner/name`-only key (cross-forge false hits); a dotted-first-segment host heuristic (accepts relative-path remotes as hosts).
*Introduced by*: 260807-2ept-pr-status-cold-start

### `parseOriginRepo` accepts EXACTLY two path segments
**Decision**: the (`.git`/trailing-slash-trimmed) origin path must split into exactly two non-empty segments; anything deeper or shallower reports `ok=false` and falls open to the per-pair `gh pr list`. The accepted two-segment forms are `https`, `ssh://` with a port, scp-like, and `git://`, with or without `.git`, with credentials, and with a trailing slash.
**Why**: GitHub/GHE repository paths are exactly `owner/name`, so keeping the trailing two segments of a deeper path — a proxy prefix like `github.com/proxy/acme/tool`, a GitLab subgroup, a Bitbucket `/scm/` prefix — manufactures an identity the pane does not have, attaching a wrong PR AND suppressing the authoritative fallback that would have resolved it correctly (the same defect class as the host-mismatch above, narrower trigger). Every rejection costs one subprocess; a wrong join costs a wrong link.
**Rejected**: keeping the last two segments of an arbitrarily deep path (the manufactured-identity bug); per-forge special cases (unbounded, and failing open already covers them).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### `BranchRefresher.refresh` is single-flighted, mirroring the collector
**Decision**: a `refreshMu` distinct from the map-guarding `mu` is held across the whole pass including its subprocesses, so the interval-tick/wake pass and an on-demand `RefreshNow` serialize.
**Why**: a tick pass blocked in `gh pr list` (up to the 10s `ghTimeout`) could return a stale parsed-empty result and clear an entry a concurrent wake/forced pass had just resolved positively, blanking the PR glyph until the next pass. Blocking is safe for the same reason it is on the collector: both callers are background goroutines — the tick's own, and the detached one behind `POST /api/status/refresh` — never a handler inline.
**Rejected**: widening `mu` to cover the pass (it would then span subprocesses and stall the hot-path `Register`/`Snapshot` readers); a try-lock skip (silently drops the on-demand refresh a user explicitly asked for).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### The PR-status seed cache pre-fills startup state and is never a source of truth
**Decision**: one droppable JSON file under `$XDG_STATE_HOME/run-kit/` holds the collector's last-good `byURL` + viewer list and the refresher's POSITIVE branch entries, written from explicit schema-versioned DTOs through `fsatomic.WriteFile` (0600/0700); it is read exactly once before either poller starts, and the first fresh derivation replaces every seeded value — authoritative negatives included. A corrupt, absent, or version-mismatched file is a silent cold start.
**Why**: the cold-start machinery above is network-gated, so a restart while gh is slow, offline, or rate-limited still starts blank, and restarts are routine (`rk serve` restarts on self-update). Extending the package's existing stale-while-revalidate rule across the process boundary needs no new poller, no cadence change, and no authority change — which is what keeps it inside Constitution §II's `$XDG_STATE_HOME/run-kit/` carve-out (v1.7.0 — two bounded classes, write-only recovery backups and never-authoritative startup seed caches): deleting the file changes nothing but cold-start latency. Explicit DTOs keep the disk format from tracking in-memory struct evolution, and the integer `schema` is the clean discard path for a future shape change. Seeding the collector's viewer list as well as its map matters because writes fire from both pollers: a branch-triggered write before the first successful fetch must not persist an empty collector half over the very seed it was loaded from. Accepted cost: the file is viewer-wide rather than per-server, so concurrent daemons on one host share it last-writer-wins — correctness-neutral since nothing on disk is authoritative (the e2e harness is excluded — its per-run temp `XDG_STATE_HOME` keeps the e2e backend's writes out of the developer's real cache).
**Rejected**: serving the cache without revalidation (that is a state store — §II); persisting negatives (a seed exists to fill blanks, and a negative re-derives cheaply); marshalling the in-memory structs directly (couples the persisted format to refactors, and `PRStatus` carries no JSON tags); having the writer fall back to the loaded document per half (two sources of truth, and "empty" is ambiguous between a genuinely empty result and "not fetched yet").
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Account-switch invalidation lands at the NEXT successful fetch, carried by a seed-provenance mark
**Decision**: the batched query selects `viewer { login }`, the cache records it, and the startup seed applies unconditionally; the first successful fetch reporting a different login clears the `pr` of every still-seed-originated branch entry — once — and rewrites the file under the new login. `branchEntry.seeded` plus the store-level `viewerIndexSeeded` flag carry the provenance, `viewerIndexPR` returns it beside the candidate it describes, and any freshly-derived write (gh result, fresh-index hit, default-branch exclusion) clears it. An empty login on either side is "unknown", never a mismatch.
**Why**: verifying the login at startup needs the network call or subprocess the seed exists to survive; deferring is safe precisely because a seeded value is never authoritative — wrong-account data is at worst stale display in the interim and can neither suppress a fetch nor write back as fresh. Branch entries are the only state a wholesale rebuild does not touch, so they are the only place account A's data can outlive a fetch as account B; marking the index closes the second path, since a pair resolved from the seeded index is still account A's data. Returning the flag with the candidate rather than re-reading it at the write point closes a TOCTOU where a concurrent index replacement plus discard would leave account A's data written unmarked and persisted under login B.
**Rejected**: `gh api user` / `gh auth status` at startup (blocks on the very network the seed exists to survive); parsing `~/.config/gh/hosts.yml` (a gh-internal format, not a public contract); deleting seeded entries rather than clearing them (drops the registration and its `observedAt`, forcing first-sight wake churn); a global seed epoch with no per-entry mark (cannot tell which entries a pass has already refreshed).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### The cache's dedup key zeroes every freshness-only stamp; the written document keeps them
**Decision**: `Store.Save` compares a copy with the document's `savedAt` AND every collector entry's `fetchedAt` zeroed, while the file it writes carries the real values; genuine content timestamps (a PR's `updatedAt`) stay in the key, and branch entries serialize sorted by `(repoDir, branch)` so equal state assembled from a Go map serializes equally.
**Why**: `Collector.refresh` re-stamps `FetchedAt` on every successful pass, so a key that compared it would always differ and the 90s tick would rewrite the file forever at idle — the same reason `snapshot.ContentEqual` zeroes `TakenAt`. The written file must still carry honest `fetchedAt` values because the flyout's "checked Xs ago" line reads them after a restart. Accepted cost: a coalesced file's `fetchedAt` describes the last pass that actually changed content — conservatively older, self-correcting at the next real change.
**Rejected**: zeroing the stamps in the written document too (the UI would have no staleness left to report); a dirty flag instead of content dedup (a second source of truth about what changed).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Seeded entries restamp `observedAt` and preserve `FetchedAt`
**Decision**: a seeded branch entry's `observedAt` is stamped at load time; a seeded `PRStatus` keeps its original `FetchedAt`.
**Why**: the two timestamps mean different things. `observedAt` is liveness driving the 5-minute age-out, so a preserved pre-restart value would let the first refresh pass evict every seeded entry before the ~2.5s SSE re-registration bumps the live ones — exactly the blank window the seed removes. `FetchedAt` is freshness, surfaced as the flyout's "checked Xs ago", where honesty is the point. Load-time stamping keeps each seeded entry serveable for one TTL window, and entries for windows that have gone away age out like any unobserved pair.
**Rejected**: preserving both (evicts the seed before it can be used); restamping both (the UI would claim just-fetched data it never fetched).
*Introduced by*: 260809-r4vk-pr-status-disk-seed

### Branch→PR presence continuity: gitRoot keying + detached-HEAD grace + entry retention
**Decision**: the register/join key's repoDir is the branch-supplying pane's git root (`windowPRKey`, raw-cwd fallback); a detached HEAD serves the cwd's last-known branch for `gitBranchDetachedGraceTTL = 5m` on the 15s re-probe cadence; refresher entries survive unobserved from `branchPRObservedTTL = 5m` (resolution stops) to `branchPRRetainTTL = 30m` (deletion).
**Why**: without continuity the PR glyph's presence is a per-tick conjunction of volatile lookups — pane `cd`s mint blank first-sight keys, every rebase negative-caches the branch for 15s, and a reopened dashboard hits deleted entries — so the top status tier flickers constantly. All three fixes are in-memory identity/continuity, keeping the zero-exec hot path and clearing authoritative negatives (default-branch exclusion, parsed-empty `gh pr list`) immediately.
**Rejected**: frontend hysteresis (every surface would need its own copy; the backend is the one place all consumers share) and a ~30s window-level hold (duplicates the refresher's existing stale-while-revalidate without covering the deletion path).
*Introduced by*: 260823-8ocy-solidify-branch-pr-presence

### Toolkit update-notify + one-click upgrade: delegated `shll check-updates` detection + scoped `shll update`, no new deps/routes/DB
**Decision**: the daemon execs `shll check-updates --json` once per ~6h (`internal/updatecheck`), consumes the per-tool verdicts it returns, and broadcasts the notable-tool set + composite key over the server-global `event: update-available`; the running version rides a set-once `event: version` slot; a `POST /api/update` runs the scoped `shll update <matched…>` in the managed `update` job window of the `rk-jobs` sibling session (fallback `rk update` self when shll is absent); a `POST /api/updates/check` runs the same pass on demand and returns the fresh verdict synchronously. run-kit is the only toolkit tool with a daemon + UI, so it is the only place a passive reminder for the WHOLE toolkit (shll, wt, idea, tu, hop, fab-kit) can live. Cross-repo: `shll check-updates` is owned by shll — that repo owns the check logic + policy values; the JSON contract is vendored in rk as `testdata/check-updates.json` (260720-puxw-check-updates-command). Frontend: `useUpdateNotification()` hook + top-bar L3 UpdateChip (single/multi form) + palette parity (two check commands, `Update Now` as the single update action) — see [ui/updates-and-notifications](/run-kit/ui/updates-and-notifications.md) § Update Notification.
**Why**: *Delegate the check to `shll check-updates`* — an in-rk reimplementation of shll's canonical check logic (a manifest HTTP fetch of `https://shll.ai/versions.json`, a `brew list --versions` join, and a hand-rolled sibling threshold evaluation) is two places for the notify policy, roster, and manifest schema to drift as the toolkit evolves. One exec of `shll check-updates --json` replaces those three code paths with a single subprocess under rk's standard discipline (`exec.CommandContext`, argv slice, 30s bound — §I), so the check is defined ONCE, on the shll side (§III Wrap, Don't Reinvent). *Two backends, not one filtered verdict* — the ambient loop and the default `run-kit: Check for Updates` command use shll's `released` manifest source (flag-free — its default, keeping the invocation valid across shll's `--released`→`--source` consolidation); the `incl. patches` command uses the FRESH `--source github` release-tags source because the shll.ai manifest refreshes ~daily and can lag a just-cut release. A github check runs as a SIDE-CHANNEL query — `CheckNow(ctx, SourceGithub)`, no cache write, no `OnQualify` — so the chip, dismissal key, and scoped `shll update` argv stay bound to the notify-policy-bearing released source (the github contract carries no `notify`/`notable`; every row lands `notable=false`, so caching it would wipe a legit released chip and starve the scoped-update argv). The two commands are therefore not "same data, two filters" but TWO BACKENDS: the default can report all-up-to-date while incl.-patches lists updates, purely from manifest lag — deliberate. *The run-kit row is re-compared locally* — shll can only see the brew-VISIBLE version, but run-kit's restart-relevant truth is the RUNNING ldflags version (brew's on-disk version can legitimately be ahead between upgrade and daemon restart), so rk consumes shll's `latest`+`notify` for that one row but does the comparison locally (producing BOTH `update_available` and `notable`), and keeps its `selfBrew` gate (a go-install/dev rk can't self-update through brew, so its own row is omitted). Sibling verdicts are trusted VERBATIM. *The retained semver helpers* — `crossesThreshold`/`anyIncrease`/`parseMajorMinor` exist ONLY as the machinery for that one local run-kit comparison and `New`'s suppression parse — the sibling-wide evaluation lives behind `shll check-updates`. *Dual failure posture (ambient fail-silent, manual fail-loud)* — the ambient 6h loop skips a failed pass silently and retains the previous verdict (stale-while-revalidate) — a background reminder must never crash or nag on a transient shll hiccup; but a MANUAL `POST /api/updates/check` deserves an honest answer, so `CheckNow` surfaces the failure as a `502`/`409` the client turns into an error toast. *An on-demand check endpoint at all* — with only the ambient chip and a blind force-update a user could not ask "is anything updatable right now?"; the endpoint runs the SAME code path as the loop and converges on the SAME cached verdict (so a manual notable finding lights the chip immediately). *Scoped `shll update` not `rk update`* — updating run-kit alone can skew cross-repo contracts (run-kit ↔ fab-kit share `@rk_agent_state`); `shll update <matched…>` keeps the matched tools moving together and delegates to `rk update --skip-brew-update` for run-kit's daemon-restart side effect (§III). It CANNOT run in-process (the restart kills the serving process mid-request), so the job runs in a managed window of the `rk-jobs` sibling session via `daemon.RunJob` (260812-z1ya-update-daemon-tmux-window) — the window survives the daemon restart it triggers by placement (Constitution VI), every tmux call stays `exec.CommandContext`-bound (§I — no detached-child carve-out), the response carries the `watch` target so the UI can jump to the live job, and output tees to `~/.rk/update.log` via `pipe-pane`. *The post-remediation re-check (R17)* — a siblings-only `shll update` never restarts the daemon, so nothing would naturally clear the consumed match: the chip would stick on `updating…`, the cached SSE slot would replay a stale match to every new tab, and a later click would 409. Firing `OnQualify` on ANY key change (incl. →empty), broadcasting the cleared verdict into the slot, clearing frontend state on key change, and a ~2min post-spawn `RecheckAfter` close the loop end to end. *SSE cached slots not a `GET /api/version`* — the two events reuse the exact `server-order`/`board-order` fan-out + cached-on-connect machinery (all clients incl. `?metrics=1`), and the connect IS the moment the client needs the version (§IV). *Extract `internal/selfpath`* — the brew marker + self-path resolver would otherwise be duplicated byte-for-byte in `upgrade.go` and `update.go`; the shared package means brew-install detection cannot drift between the CLI and web entry points. Accepted: until a shll release carries `check-updates` the not-on-PATH path keeps the checker silent (fail-silent-retain leaves the verdict empty → the chip stays hidden); a failed brew upgrade leaves the chip on `updating…` until the verdict changes (escape hatches: the palette force path + a page reload; the `remain-on-exit on` job window + teed log carry the evidence).
**Rejected**: reimplementing the check in rk (drift risk — §III); a github check that WRITES the shared cached verdict (would wipe the released chip + 409 the scoped update — the side-channel posture is load-bearing); silently treating an unknown `source` as released (masks a client bug — 400 instead); an invented client-side boolean instead of echoing `report.Source` (the echo doubles as a defensive check); a shll-side change (the github contract already omits `notify`/`notable` and self-identifies `"source":"github"`); in-process upgrade (restart kills the server); `GET /api/version` (needless surface); a semver DEPENDENCY (the ~20-line hand-rolled compare backs only the one local run-kit row); a frontend-only `updating` timeout (leaves the stale verdict up to 6h); tracking the job's exit from the handler process (the job must outlive the daemon it restarts — the window state + teed log are the observation surface); Web Push for update notices (reserved for waiting agents — update notices must not buzz phones, user-decided).
*Introduced by*: 260713-4zap-update-notify-one-click-upgrade, 260718-d15e-toolkit-manifest-update-notifications, 260720-n2ai-shll-check-updates-delegation-palette-checks, 260720-wb3n-github-source-patches-check

### `currentWindowEverSeen` gate on kill-redirect over unconditional "gone → redirect"
**Decision**: the redirect in `app.tsx` that fires when `currentSession` or `currentWindow` is null is gated by a ref keyed on `${server}|${session}|${window}`, flipped true the first time `currentWindow` resolves non-null, reset on URL change — deferring the redirect until the URL target has been observed as valid at least once.
**Why**: the first SSE payload after a navigation is not authoritative: the SSE hub can replay a cached snapshot before delivering fresh data, and tmux window-list enumeration can lag by one poll tick when a session was just created. Unconditionally redirecting on either transient state tears down `TerminalClient` mid-mount. The gate preserves fast-redirect behavior for genuine kills (the seen flag stays true after the first valid observation) while eliminating the startup race.
**Rejected**: inspecting SSE payload identity or delaying `isConnected` (both push complexity into the hub layer and would not distinguish real kills from stale catch-up); a fixed startup debounce (arbitrary delay, races with fast tests).
*Introduced by*: 260417-g9uo-mobile-tap-focus-regression

### CSS Grid topology for the rotated shell over nested flex
**Decision**: Grid encodes the topology directly via `grid-template-areas: "sidebar topbar" "sidebar content" "sidebar bottombar"`; collapse is a one-line column-width change (`${sidebarWidth}px 1fr` ↔ `0 1fr`) animatable as a single `grid-template-columns` transition.
**Why**: the shell rotation makes the sidebar a column that spans all three rows (topbar, content, bottombar). Expressing "sidebar full-height; right column is a 3-row stack" with nested flex requires either a sibling sidebar with explicit height management plus a flex-col right column, or a 2-row layout with sidebar nested inside row 1 — neither matches the visual model and both diverge as future cells are added. Modern browsers (Safari 14+, Chrome 100+) animate `grid-template-columns` reliably.
**Rejected**: nested flex.

### Sidebar collapses to 0px, not a 48px rail
**Decision**: collapse zeroes the sidebar column, giving maximum content width when collapsed and accepting a small visual layout shift on toggle (the hamburger appears to "move" from sidebar-adjacent to page-adjacent, though structurally it always lives at TopBar.left — see the next decision).
**Rejected**: a 48px icon rail (VS Code/Linear/Slack convention) — avoids the visual relocation but consumes content width for a usability gain that diverges from the user's stated preference for max content width.

### Hamburger statically rendered at TopBar.left
**Decision**: the hamburger's home is always TopBar.left; the column is what changes.
**Why**: makes the visual relocation on collapse a free side effect of the grid column collapsing — no component-level relocation logic, no conditional mount/unmount, no animation orchestration.
**Rejected**: state-conditional placement (hamburger inside sidebar when open, inside topbar when closed) — adds a state-dependent component-tree mutation that complicates focus management and adds animation responsibility.
*Introduced by*: 260509-17m3-rotated-shell-layout

### Single `sidebarOpen` boolean over `sidebarOpen + drawerOpen`
**Decision**: the user's intent ("show me the sidebar") is one boolean; the renderer picks the form (grid column vs absolute overlay) by viewport width.
**Why**: the distinction between "sidebar open on desktop" and "drawer open on mobile" is a rendering-form difference, not a state difference. One boolean simplifies persistence (one localStorage key, `runkit-sidebar-open`), removes a class of "they're out of sync" bugs, and makes the keyboard chord a single state mutation.
**Rejected**: two booleans — preserves a historical artifact at the cost of doubled persistence/reset logic and a confusing surface for new contributors.

### `<Shell>` as a shared wrapper over per-route shell components
**Decision**: a single `<Shell>` (`src/components/shell/shell.tsx`) lets both AppShell and BoardPage consume a uniform topology; collapse animation, mobile overlay, and the topbar/content/bottombar geometry stay in one place. `Shell` renders the desktop `sidebar` grid area itself (from `sidebarChildren` + optional `sidebarResizeHandle`); consumers place only the `content`/`bottombar` grid areas via `style={{ gridArea: "content" | "bottombar" }}` elements. Pattern note: future routes that need the same chrome should adopt `<Shell>` rather than reimplementing the grid.
**Why**: both routes need the identical 3-row × 2-column grid, sidebar collapse, mobile overlay, and visual-viewport handling.
**Rejected**: per-route shell components — guaranteed to diverge over time (different collapse timings, drift in mobile overlay handling), defeats the rotation's "one topology, many routes" goal.

### `Shell` owns the desktop sidebar aside; the resize handle rides an opaque node slot
**Decision**: `Shell` renders the desktop `<aside style={{ gridArea: "sidebar" }} aria-label="Sidebar">` (gated `!isMobile && sidebarOpen && !!sidebarChildren`) and exposes an optional `sidebarResizeHandle?: ReactNode` rendered at the aside's right edge; `border-r border-border` is applied only when no handle is passed. The one per-caller divergence — AppShell's drag handle — rides through the opaque slot, so all drag state/handlers stay in AppShell and Shell stays dumb about drag logic.
**Why**: per-consumer copies of the aside scaffolding, the grid-area placement, and the `!isMobile && sidebarOpen` gate drift (an AppShell flex-row + drag handle vs a BoardPage border-r + a different `aria-label="board sidebar"`). Shell already reads `sidebarOpen`/`isMobile`, so the branch lives there with zero new data dependencies, and the uniform `aria-label="Sidebar"` gives AppShell's aside an accessible name.
**Rejected**: a render-prop (`sidebar={(ctx) => …}`) — no caller needs Shell-provided context, so a plain node prop is simpler; Shell owning the drag handle — it would pull `handleDragStart`/width persistence into Shell and couple it to AppShell-only state.

### `FocusedTerminalContext` as a separate, dedicated context (not a slice of ChromeContext)
**Decision**: a small dedicated context with its own provider (`FocusedTerminalProvider` mounted in `RootWrapper`) carries only `focused`/`setFocused`; only the shell-level BottomBar and the docked `ComposeStrip` read `focused` from it. The compose surface's enablement is a persisted `composeStripEnabled` chrome preference, and the strip reads `focused.wsRef` LIVE at send time (a live target following pane focus, mitigated by an always-visible `→ {window}` label). Pattern note: future multi-input UIs that need a single shared input target should follow this "lift focused-input target to context" pattern rather than prop-drilling.
**Why**: the shell-level BottomBar needs a way to target the focused terminal regardless of route. Folding the focused-terminal target into ChromeContext would mix UI state (sidebar open, fixed-width) with terminal-WS state and force every Chrome consumer to re-render whenever focus changes; the dedicated context keeps the dependency narrow.
**Rejected**: a compose target frozen at open (the modal model's snapshot) (260718-dhdj-docked-compose-strip).
*Introduced by*: 260509-17m3-rotated-shell-layout

### Read-only setter pair for in-memory + persisted state (`setSidebarWidth` + `persistSidebarWidth`)
**Decision**: the dispatch is split into `setSidebarWidth(width)` (in-memory state) and `persistSidebarWidth(width)` (localStorage write), so the drag handler calls the cheap one in the loop and the expensive one once at drag-end. Convention note: future state with the same shape (live in-memory updates + final commit to persistence) should follow this two-setter pattern.
**Why**: drag-resize fires per-pointermove (potentially 60+ events per second); persisting on every event would write localStorage 60 times per second per drag — unnecessary I/O and cache thrash.
**Rejected**: debouncing inside the dispatch (couples state lifecycle to a timing heuristic).

### Open-in-app: wrap `wt` for the host, keep deeplink templates frontend-only, degrade fail-silent
**Decision**: the top-bar Open control uses TWO mechanisms for two execution contexts. **Host launch + app detection go through `wt`** (never a parallel `open -a` implementation): `internal/wt` wraps `wt open --list --json` (registry, filtered to `locus:"gui"` rows at the wrapper's parse seam — see the `internal/wt` package row) + `wt open <path> -a <app>` (launch), surfaced as `GET /api/open-apps` + `POST /api/open`. Filtering at the wrapper (not in `handleOpenApps`) means both consumers of `ListApps` — the GET registry and the POST launch validation (`appInRegistry`) — see the same gui-only view, so a non-gui action id like `tmux_window` 400s at launch instead of reaching exec. wt ≥ v0.1.5 carries `wt open --list --json`, so the host registry is live (VS Code's registry id is `code`, snake_case ids like `ghostty_macos`); the fail-silent path covers older `wt` that predates the flag. **Deeplink templates live in run-kit's FRONTEND ONLY** — a static TS const (`DEEPLINK_APPS`, `{scheme}://vscode-remote/ssh-remote+${host}${path}` for vscode/cursor/windsurf), no API, no host-side detection. Host-section presentation is also frontend-owned: the API returns wt's registry order with the `default` marker passed through, and `buildOpenTargets` applies the default-first ordering — a server-side sort would bake a UI ordering into the API response. See [ui/top-bar](/run-kit/ui/top-bar.md) § Open split-button.
**Why**: *wrap* — `wt` is the toolkit's canonical launcher and already owns app detection + launch (Constitution III — wrap, don't reinvent); one registry stays shared across the toolkit. *Fail-silent* (`ListApps` error → `200 []`, hiding the host section) — mirrors the toolkit's `command -v` fail-silent discipline and keeps run-kit **buildable/shippable against any `wt`** — the parser is tolerant (require `id`+`label`, ignore unknowns) and the API maps every wrapper error to `[]`. *Frontend-only deeplinks* — URL-scheme deeplinks are the only power a web page has over a remote CLIENT machine, and **client installs are undetectable from the host** — a Windsurf installed on the laptop but not the server means host-side detection is a wrong/inverted signal, so `wt` carries zero URL-scheme knowledge and a dead scheme simply no-ops on click.
**Rejected**: a parallel host `open -a` path (§III); teaching `wt`/the backend the deeplink schemes (host detection can't see client installs); a host-detected editor list for the remote case (inverted signal).
*Introduced by*: 260722-6d0f-navbar-open-in-app

### Derived `${sshUser}@${location.hostname}` is the deeplink host; the section shows on any remote client
**Decision**: the deeplink SSH destination resolves (frontend `resolveDeeplinkHost`) as the `ssh_host` setting verbatim (alias — no `user@` prefix) when set, else a derived `${sshUser}@${location.hostname}` on remote clients (prefix omitted when `sshUser` empty), else empty for local; the deeplink section's visibility keys only on remote-ness, not on whether a host is configured. See [ui/top-bar](/run-kit/ui/top-bar.md) § Open split-button.
**Why**: on a tailnet `location.hostname` is the SSH-reachable name the browser already used, and `sshUser` is derivable server-side, so zero-config Tailscale users get the feature without configuring anything. The accepted trade is "shown ⇒ works on tailnets, errors on tunnels": behind an HTTP-only tunnel the derived host isn't SSH-reachable and the editor shows its own connect error.
**Rejected**: gating the section on an SSH host being configured (leaves the feature dark for the common Tailscale case); reachability-probing the derived host before showing (guessing; the connect-error trade is accepted); an explicit-disable sentinel in v1 (deferred — the remote-only gate makes disable rarely needed).
*Introduced by*: 260722-fc3b-ssh-host-fallback-open-logos, 260823-li54-config-root-registry-core

### Shared frontend test scaffolding is imported per-test, never auto-installed via `setupFiles`
**Decision**: `src/test-utils/` (fixture factories + `stubMatchMedia`) is a plain importable module; `setupFiles` stays `["./src/test-setup.ts"]`, which carries only unconditional environment polyfills. See § Frontend Unit Tests.

It is also the smallest blast radius: pure test-code movement, zero production edits.
**Rejected**: registering the stub in `test-setup.ts` (breaks the assert-absent suites and hides the environment mutation from the file under test); a required-overrides `makeWindow` variant for the two sites needing `windowId`+`index` (a second signature to maintain when an explicit per-call override reads fine).
*Introduced by*: 260731-5hm6-frontend-vitest-test-utils

### `stubMatchMedia` covers only the predicate family; controllable-MQL stubs stay bespoke
**Decision**: the shared helper owns the fire-and-forget shape (per-query `matches`, `vi.fn()` listener stubs); tests that fire change events or inspect listener bookkeeping keep building their own MQL object and stubbing via `mockReturnValue(mql)`.
**Why**: the two families differ in kind, not degree — a controllable MQL is the *subject* of those tests, so folding it behind a predicate argument would either leak a mock-plumbing parameter into every caller or force the helper to grow an event-emitting MQL implementation no predicate-family caller wants.

### Mobile sidebar overlay positioned via grid (`gridRow: "2/4"`), not `fixed inset-0`
**Decision**: the mobile overlay is a grid-row-spanning child with `position: absolute` (not `fixed`) so it anchors below the topbar inside the Shell; it has a backdrop and carries `role="dialog" aria-modal="true"`. The spec wording "fixed-position overlay with backdrop" is satisfied — the overlay is fixed-position-style (absolute inside the Shell that itself is full-viewport).

### Shared Go test scaffolding is one `internal/testutil` package with layered opt-in helpers, not per-package `testhelpers_test.go`
**Decision**: the stub-executable fixture and the deadline-poll wait loop live in a single importable `rk/internal/testutil`, with each behavioral divergence across call sites expressed as an **explicit API layer** rather than flattened away: PATH-prepend is a separate `StubOnPath` function over the base `WriteStub` (so PATH-*replacing* callers keep their own `t.Setenv`), and fail-on-expiry is a separate `MustWaitUntil` over the fall-through `WaitUntil`. Shapes that resist the `cond func() bool` contract stay bespoke by design — see § Testing / Go Unit Tests for the enumerated exclusions.
**Why**: a single package is discoverable — code-quality.md's "duplicating existing utilities" anti-pattern tells authors to check `internal/` first, and these two families span 5 and 13 call sites respectively — enough reach that any hand-rolled copy diverges on the axes the layers name (PATH replacement vs prepend, `t.Fatalf` vs fall-through-and-assert). Making each divergence a named layer means a call site's choice is visible at the call site rather than buried in a local helper's body, so the consolidation preserves every site's exact semantics — a hard requirement, since the constitution's Test Integrity rule forbids changing what tests prove to suit test infrastructure.
**Rejected**: leaving the duplication (copies drift on exactly the two axes the layers name); per-package `testhelpers_test.go` files (re-duplicates across packages — the same problem one directory down, and `_test.go` helpers are not importable across packages); one flattened helper per family with a behavior flag or an always-prepend PATH (silently changes the semantics of the sites that replace PATH); a dedicated `_test.go` for `testutil` itself (every migrated caller exercises it, and the package is not linked into the production binary).
*Introduced by*: 260731-4404-go-internal-testutil

### Board e2e pin cleanup is an opt-in registry layer over universal ok-asserted base helpers, and `finally`-block cleanup stays non-asserted
**Decision**: `_boards.ts` splits the pin surface in two: `pinWindow`/`unpinWindow` are ok-asserted and universal, while `trackPin`/`unpinAll` are adopted only by specs that own a per-file `pinnedEntries` + `afterAll` loop. `connection-budget.spec.ts`'s `finally`-block cleanup unpin is a deliberate carve-out from the ok-assert rule. See § Testing / Playwright E2E Tests.
**Why**: pin cleanup is correctness-critical but not universal — a pin moves a window into a `_rk-pin-<id>` session that outlives the source session on the worktree's shared e2e primary server, yet many specs reap their own pins through the unpin flow under test or `global-teardown.ts`, so auto-registering every pin would change those specs' cleanup semantics under a behavior-preserving consolidation. Keeping the registry opt-in also keeps the sweep obligation legible at the call site, which matters because the registry's real lifetime is the **worker process**, not the spec file: Playwright reuses workers across files and never clears the module cache, so an unswept file leaks its entries into the next file's sweep. In the `finally` block, a throw replaces the in-flight try-block exception, which would mask the socket-count diagnostic the test exists for.
**Rejected**: a `pinTracked` convenience combining pin + track (hides the layer boundary and the sweep obligation that comes with it — call sites compose the two explicitly); a Playwright fixture via `test.extend` (heavier than the `_tmux.ts`/`_ready.ts` plain-module precedent, and per-worker fixture scoping would not remove the sweep obligation); routing `afterAll` sweeps through the ok-asserted `unpinWindow` (an already-gone pin would fail teardown for a condition that is expected); homing the pin helpers in `_ready.ts`/`_tmux.ts` (boards are an HTTP-API concern, not readiness or tmux lifecycle).
*Introduced by*: 260731-2kio-board-e2e-helpers

### A dedicated `internal/codeserver` package owns the code-server install + layout
**Decision**: release resolution, download/verify/extract, layout paths, and installed-version reads live in `internal/codeserver`; `internal/daemon` (the resolution ladder + install-job spawn) and `cmd/rk` (the `rk code-server` family + the `rk update` leg) both consume it.
**Why**: the engine has two consumers and zero tmux coupling; `internal/daemon` is tmux-lifecycle code and `cmd/rk` must stay thin. Mirrors the desktop-installer precedent (install engine as a library, CLI as the caller).
**Rejected**: growing `internal/daemon/codeserver.go` (couples pure install logic to the daemon package's tmux seams); implementing in `cmd/rk` (unreachable from the daemon's job-spawn decision and untestable per the internal-package convention).
*Introduced by*: 260813-oid2-own-code-server-install

### The install job runs the literal shell chain, exe path quoted
**Decision**: the `code-server-install` job's argv is the shell chain `<quoted-rk-exe> code-server install && <quoted-rk-exe> code-server start`, with the daemon's own `selfpath.Resolve`d exe path quoted via the daemon package's existing `shellQuote`.
**Why**: the chain is the agreed install→start sequencing (daemon start is one-shot; no supervisor loop, Constitution VI), visible verbatim in the job window — a user watching the dashboard sees exactly what runs; `&&` gives success-gated start for free; quoting closes the space-in-path edge `RunJob`'s unquoted argv join documents.
**Rejected**: an `--and-start` flag on install (hides the sequencing inside one process; diverges from the agreed command shape); relying on unquoted paths (breaks on any exe path with a space).

### Staged extract + rename promotion, temp-symlink flip
**Decision**: download and extract into a staging dir under `code-server-bin/`, promote with `os.Rename` to `<version>/`, then flip `current` via temp symlink + `os.Rename`.
**Why**: both promotions are single-syscall renames on the same filesystem — a crash at any point leaves either the old world intact or a garbage staging dir, never a torn active install.
**Rejected**: extracting directly into `<version>/` (a crash leaves a plausible-looking broken install that the ladder would happily spawn); `Symlink`+`Remove` flips (an observable missing-`current` window).
*Introduced by*: 260813-oid2-own-code-server-install

### `rk code-server update` skips when nothing is managed
**Decision**: no `~/.rk/code-server-bin` ⇒ update prints a not-managed data line and exits 0.
**Why**: "only touch what rk owns" — a user-managed PATH install must never be shadowed as a side effect of an update verb; exit 0 keeps `rk update`'s composed leg and `shll update`'s summary truthful.
**Rejected**: installing on update when unmanaged (silently converts a user-managed setup to rk-managed); erroring (a skip is not a failure — the update standard's exit-code rule).
*Introduced by*: 260813-oid2-own-code-server-install

### Install is the migration verb; foreign-session detection is a path-string match, not a spawn-argv version marker
**Decision**: `rk code-server install` respawns a running session whose live `#{pane_start_command}` lacks the managed `current` binary path, behind the daemon gate; the ownership gate on `update` stays.
**Why**: an explicit install is unambiguous intent to move the editor onto the managed binary — it closes the brew-era gap (a PATH binary satisfies rung 2, the update leg gates on the managed dir, the session survives restarts by design, and a fresh install reads already-current to update: nothing else ever migrates) with zero new state and a state-free re-run convergence.
**Rejected**: embedding `RK_CODE_SERVER_VERSION=<ver>` in the spawn argv to also detect a flipped-underneath managed session (grows the spawn contract for a rare corner — update normally runs right after `rk update` restarted the daemon — that honest daemon-down messaging already covers); auto-respawning from the daemon's own start path (Constitution VI — an implicit editor teardown on daemon start is exactly what the sibling design forbids).
*Introduced by*: 260813-2s4u-respawn-aware-code-server-install

### No HTTP probe on enumerated ports
**Decision**: `internal/ports` is a purely observational enumerator — it connects to no port; there is no `probe.go` and no verdict machinery (`probeTTL`/`probeEntry`/`probeCache`/`probePort`/`probeVerdicts`), and `Service` carries no `http:` boolean.
**Why**: a `GET /` to every newly-seen port *consumes* one-shot local servers on first contact — `gcloud`/`gh`/`aws` OAuth callback listeners handle exactly one request, so probing breaks routine CLI auth; there is no safe cadence, because the FIRST probe is the killer. Probing also spams dev-server access logs and can defeat idle-shutdown timers. Constitution §II: state is derived, never interacted with.
**Rejected**: any probing cadence, however slow (the first contact is the damage); an HTTP verdict field on `Service` (nothing can produce it without probing).
*Introduced by*: 260715-vfcz-passive-ports-process-attribution

### Merged-PR durability is derived statelessly from `gh --state all`, never from a grace clock
**Decision**: the per-branch query is `--state all` and `pickBranchPR` ranks candidates open > merged > closed, so a merged PR re-resolves positive on every pass; no timer, no negative-stamp retention, no `wentNegativeAt` field.
**Why**: an in-memory grace window (`--state open` + a 10-minute `branchPRMergedGrace` clock) decays the merged done-square into a green fab square minutes after merge, and any rk restart wipes it entirely — in-memory recovery state is exactly what Constitution II forbids leaning on. Deriving from gh on every pass makes the square restart-proof end to end, including on a cold process with no prior positive.
**Rejected**: `--state open` plus a grace clock on a `wentNegativeAt` field (decays, and does not survive restart).
*Introduced by*: 260706-4h26-durable-merged-pr-register-keys

### `sanitizeEnv` restores the pre-direnv PATH; `cleanPATH` is a last-resort guard only
**Decision**: `CleanEnvForServer()` reverse-applies `DIRENV_DIFF` to recover the operator's true pre-direnv environment INCLUDING PATH, and injects the POSIX-default `cleanPATH` iff no `PATH=` entry survives the reversal — never over a PATH that is already present.
**Why**: the target semantics are "as if the operator had started tmux from `$HOME`", and the reversal already yields the operator's real PATH; unconditionally resetting it to the POSIX default would strip brew, asdf, and every user toolchain from every rk-born tmux server, which is strictly worse than the direnv pollution the sanitization exists to remove.
**Rejected**: an unconditional POSIX-PATH reset (destroys the operator's toolchain PATH); dropping `cleanPATH` entirely (a reversal that leaves no PATH at all would give the server none).
*Introduced by*: 260706-6mpm-direnv-diff-reversal-server-env

### Binary/server version drift is a doctor-only informational note, probed per live server
**Decision**: doctor's tmux row compares the on-disk binary (`CurrentVersion`) against each running server (`ServerVersion` over the `ListServers` live derivation) and appends a per-server restart sentence — socket named, cost stated ("kills its sessions; pick a quiet moment") — when the binary is strictly newer (`OlderThan`, major.minor only); rk never restarts a server itself.
**Why**: an upgrade replaces the binary but never the running servers (by design — Constitution VI), and that latency is invisible: a user who just upgraded to clear the floor warning keeps old-server behavior with no explanation; naming the socket matters because multi-server (default, rk-daemon, rk-test-*) is routine, and probing only ListServers-confirmed-live sockets avoids the dead-socket server-resurrection trap.
**Rejected**: surfacing drift at daemon start (warn fatigue — that channel is reserved for the floor warning); default-socket-only probing (simpler but misses the rk-daemon socket where drift matters most); any auto-restart affordance (Constitution VI is non-negotiable).
*Introduced by*: 260819-a8bf-doctor-tmux-drift-note

### Intent lives in a JSDoc block above each test
**Decision**: Per-`test()` `/** Proves: … Steps: … */` block plus one file-header comment for shared setup; there are no companion documentation files.
**Why**: The intent text moves in the same diff hunk as the test, so drift is visible in review; sibling companion files had no consumer (no CI step, script, or skill read them) and had drifted into a shadow memory layer carrying change-ID citations and history narration.
**Rejected**: A CI drift-check over the companion files (tooling to protect an unread artifact); companion files only for long specs (two conventions is worse than one).
*Introduced by*: 260828-0daa-retire-spec-md-companion-docs

## Testing

Tests whose lifetime is tied to a compatibility shim carry `// retire-with: {shim-name}` immediately above the test, or in the file header when the whole spec is shim-bound. Shim-removal sweeps use `grep -r "retire-with"` to locate the full cross-language set.

### Go Unit Tests

Go `testing` package with table-driven tests. Test files co-located with source using `_test.go` suffix. Test scripts: `go test ./...` from `app/backend/`.

**Shared test scaffolding lives in `app/backend/internal/testutil`** (import path `rk/internal/testutil`) — a regular (non-`_test`) package, so its helpers are importable from `_test.go` files in any backend package. It is the first place to look before hand-rolling test scaffolding. Two families:

- **Stub executables** (`stub.go`): `WriteStub(t, dir, name, script)` writes `script` as an 0o755 file into `dir` (`t.Fatalf` on write error). `StubOnPath(t, name, script)` layers on top — fresh `t.TempDir()` + `WriteStub` + a PATH **prepend** that preserves the original (restored by `t.Setenv` cleanup) — and returns the dir. The PATH layer is **opt-in**: callers wanting PATH *replacement* call `WriteStub` and do their own `t.Setenv("PATH", dir)` (`internal/riff`, `internal/wt`); `cmd/rk/upgrade_test.go` wants the prepend and uses `StubOnPath`. Fixed-name conveniences (`stubFab` in riff, `installFakeBrew` in `cmd/rk`) stay **local** thin delegates in their own test files, keeping `testutil` package-agnostic.
- **Deadline-poll waits** (`wait.go`): `WaitUntil(t, timeout, cond) bool` polls `cond` at a fixed 50ms cadence (`waitPollInterval`) until true or `timeout`, checking `cond` **before** the first sleep so an already-true condition returns immediately; `timeout` stays a per-call-site argument (2s/3s in practice). `MustWaitUntil(t, timeout, cond, msg, args...)` is the fail-on-expiry variant. Its `args` evaluate **eagerly at call time**, so a failure message embedding state computed during the wait must use `if !WaitUntil(...) { t.Fatalf(..., freshState) }` instead. Callers: `internal/tmuxctl` (supervisor/client/integration), `api/terminals_relay_test.go`, `api/terminals_ws_test.go`.

Two shapes are deliberately **not** expressible through these helpers and stay bespoke: loops returning a value from inside the body or needing a tighter poll (`internal/tmuxctl/client_test.go`'s `fakeSleep.triggerNext`, 2ms), and blocking frame-readers / fixed-duration drain loops that must not exit early (`api/terminals_relay_test.go` `conn.ReadMessage()` waits, `api/sse_subscriber_test.go` drains). `internal/desktop/installed_test.go`'s `writeFakeBundle` is likewise outside `testutil` — it builds a directory bundle (`MkdirAll` + an 0o644 plist), not a 0o755 executable. `testutil` carries no `_test.go` of its own; every migrated caller exercises it, and it is not linked into the production binary.

#### Shared test scaffolding — `src/test-utils/`

`app/frontend/src/test-utils/` holds the shared vitest scaffolding, **imported per-test and deliberately NOT registered in `vitest.config.ts` `setupFiles`** — the only auto-installed frontend test code is `src/test-setup.ts`, which carries unconditional environment polyfills (`ResizeObserver`, `document.fonts`) and nothing opt-in. Two modules:

- **`fixtures.ts`** — the canonical spread-override factories `makeWindow(overrides?: Partial<WindowInfo>)`, `makeSession(overrides?: Partial<ProjectSession>)`, and `makeWindowWithPanes(overrides?: Partial<WindowInfo>)` (composed on `makeWindow`), typed against `@/types`. One canonical default set (`windowId: "@0"`, `index: 0`, `name: "zsh"`, `worktreePath: "/home/user"`, `activity: "idle"`, `isActiveWindow: false`, `activityTimestamp: 0`); `makeWindowWithPanes` layers a `/home/user/code/run-kit` worktree plus one active `%5`/`main` pane. Every signature is all-optional — a test that cares about a field (including `windowId`/`index`) passes it as an explicit per-call override rather than getting a bespoke required-args variant.
- **`match-media.ts`** — `stubMatchMedia(predicate?: (query: string) => boolean)` installs the fire-and-forget matchMedia stub via `vi.stubGlobal`, holding the MQL-shaped object literal (`matches: predicate(query)`, `media`, `onchange`, and `vi.fn()` listener stubs) in one place and returning the installed mock for per-test customization. The default predicate is always-false. Because `vi.stubGlobal` defines a configurable property on the jsdom global (jsdom implements no `matchMedia`), a test may `delete window.matchMedia` to restore jsdom's `undefined` — `tip.test.tsx` depends on exactly that restore path in its `afterEach`.

**Two matchMedia families, only one shared.** `stubMatchMedia` serves the *predicate* family — fire-and-forget stubs whose only variable is the per-query `matches` verdict. Tests that drive real media-query behavior (change events, listener bookkeeping) instead build a controllable MQL object and stub via `vi.stubGlobal("matchMedia", vi.fn().mockReturnValue(mql))`; that family (`hooks/use-coarse-pointer.test.ts`, `contexts/theme-context.test.tsx`, `theme-selector.test.tsx`, `swatch-popover.test.tsx`, `terminal-client.test.tsx`, `sidebar/index.core.test.tsx`, `sidebar/index.test.tsx`'s `makeMatchMedia`) is a different shape and stays bespoke. Reach for `stubMatchMedia` only when the test never inspects or fires listeners. Thin per-file wrappers over it (`stubCoarsePointer()`, `stubPointer(coarse)`) are idiomatic — they encode a file's pointer semantics while the shared module owns the literal.

Config at `app/frontend/playwright.config.ts`. Describe titles tagged `@perf` form the on-demand performance-audit tier. The config-path `grepInvert` excludes this tier from `just test-e2e` and CI; `scripts/pw.sh` sets `RK_E2E_PERF=1`, so `just pw test <name>` includes it.

Every `test()` in this directory carries a `/** Proves: … Steps: … */` JSDoc block immediately above it — the user-visible behavior under test in one or two sentences plus a numbered step list mirroring the body, so a reviewer can reason about intent without reading Playwright APIs — and each spec file opens with a file-header comment covering shared setup (`beforeAll`/`beforeEach`, fixtures, viewport, `page.route` stubs, saved/restored host-global state). Intent comments state what the test proves and why the setup is shaped as it is; they narrate no history and cite no change IDs or PR numbers. A PR that adds or modifies a `test()` updates its intent comment in the same commit. Unit tests (`*.test.ts`/`*.test.tsx`, `*_test.go`) are exempt — the test name plus code is self-documenting at that scope (constitution § Test Intent Comments).

## Security

- All subprocess calls use `os/exec.CommandContext` with argument slices (never `sh -c` or shell strings)
- All `exec.CommandContext` calls include timeout via `context.WithTimeout` (10s tmux, 30s build). Terminal relay attach uses `context.WithCancel` (long-lived, cancelled on disconnect)
- User input validated via `internal/validate` before reaching any subprocess. For `rk remote`, validation runs on **both sides of the store**: at add-time and again in `remote.Load`, because `~/.config/rk/remotes.yaml` is user-editable and its stored names/targets flow into tmux and ssh argv (see [remote-hosts](/run-kit/remote-hosts.md) § Stored entries are validated on the read path)
- SSH remote hosts: the tunnel is the system `ssh` binary invoked with an argv slice and `BatchMode=yes`, `StrictHostKeyChecking` untouched; every remote command is a compile-time literal (nothing user-provided is interpolated), and the remote daemon binds loopback only with SSH as the sole auth layer
- Directory listing restricted to `$HOME` via `ExpandTilde()` — rejects `..` traversal, absolute paths outside home, and `~username` syntax. Symlinks under `$HOME` are not resolved (accepted risk for local dev tool)
- File uploads: filename sanitized via `SanitizeFilename()` (strips path separators, null bytes, leading dots, collapses dot sequences); 50MB size limit enforced server-side via `http.MaxBytesReader`; writes via `os.Create` (not subprocess)
- CORS: permissive by default (`*` origin) for multi-client API flexibility. TLS handled by Tailscale Serve in production
- Web Push: the VAPID private key (`~/.rk/vapid.json`) is written mode `0600` and is **never** returned to any client — only the public key is served via `GET /api/push/vapid-public-key`. The subscribe/notify endpoints validate JSON shape and bound the request body (64 KiB); no subprocess execution is introduced by the push path (260615-xd9r-web-push-notifications)

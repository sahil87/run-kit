# run-kit UI — Lenses & Surface Layout

## Iframe Window (the `web` lens renderer)

`app/frontend/src/components/iframe-window.tsx` — the renderer for the **`web` surface/lens** (§ Window Views (Lens Model)), mounted as a tile by `SurfaceLayout` whenever the resolved layout's order includes `web` (§ Surface Layout). The ladder's availability degradation bakes in the capability gate, so an iframe-typed window with no `rkUrl` never resolves a `web` tile. Bottom bar is NOT rendered for a web tile (no terminal to send keys to). The component is **presentational** — it takes `windowId`, `rkUrl`, an `onSwitchToTty: () => void` callback, and an optional `onInteract: () => void` tile-focus seam (below) and owns NO view/URL/localStorage logic (that lives in `surface-layout.ts` + `app.tsx`); it mutates no `@rk_type` (§ Window Views → decoupling). The web tile passes `onSwitchToTty` (applies `single:tty` through the shared mutation path), so the `>_` switch-to-terminal button renders. (`260714-t97o`, `260812-ab5v`)

**Layout**: Outer wrapper `flex flex-col flex-1 min-h-0` with two children: URL bar (`shrink-0`) and iframe (`flex-1`).

**URL Bar**: Thin toolbar above the iframe (`border-b border-border bg-bg-primary`). Four elements:
- **Refresh button** (↻ `&#x21bb;`) — forces iframe reload by clearing `src` to `"about:blank"` then re-setting it via `setTimeout(0)`. Styled: `w-7 h-7 rounded hover:bg-bg-card text-text-secondary`
- **URL input field** — shows current `rkUrl`, editable. On Enter, calls `updateWindowUrl(server, windowId, url)` which delegates to the unified `setWindowOptions(server, windowId, { "@rk_url": url })` → `POST /api/windows/{windowId}/options` (partial-merge — only `@rk_url` is touched). On API failure, reverts input to the SSE-confirmed `rkUrl`. Styled: `bg-bg-card text-text-primary text-sm px-2 py-1 rounded border border-border`. **This is the one POST the web lens fires** — editing the content ADDRESS is *substrate* state (shared, POSTed, everyone sees it — spec R7), distinct from switching which lens you look through (per-viewer, no POST). (`260529-jad6`)
- **Submit indicator** (⏎ `&#x23ce;`) — decorative visual affordance (`text-text-secondary text-xs`)
- **`>_` switch-to-terminal button** (`aria-label="Switch to terminal"`) — it calls the injected `onSwitchToTty()` prop (which runs `app.tsx`'s `switchView("tty")` → `applyLayout(single:tty)` — persist + URL mirror, § Surface Layout), **NOT** an `@rk_type` mutation. It is a per-viewer *layout switch*, so flipping to the terminal and back preserves the window (no `@rk_type` mutation, no global flip — the e2e asserts zero `/options` POSTs across a flip). (`260714-t97o`)

**SSE Sync**: A `useEffect` on `rkUrl` syncs both the URL bar text and iframe `src`. Uses a `currentSrcRef` to avoid re-setting iframe `src` when the URL hasn't actually changed (prevents unnecessary reloads on identical SSE ticks). When `rkUrl` changes externally (Claude or another process runs `tmux set-option`), the URL bar updates and iframe navigates automatically.

**Interaction seam (`onInteract`)**: in-frame clicks and keydowns stay in the frame's own document, and focus entering a frame fires NO focusin in the parent — parent-document listeners are blind to them. When `onInteract` is provided, the component attaches capture-phase `pointerdown`/`keydown` listeners to the same-origin `contentDocument` after every iframe `load` (each navigation replaces the document; cross-origin access throws and is skipped silently — the `CodeSurface` attach pattern) plus a parent-window `blur` fallback that reports when `document.activeElement` is the iframe, covering cross-origin embeds. Once a cross-origin frame holds focus, later in-frame clicks report nothing — accepted, the tile is already focused by then. `SurfaceLayout` wires the seam to tile focus (§ Surface Layout → Focused tile); the prop is optional and other mount contexts omit it unchanged. (`260815-41t9`)

**Proxy URL conversion**: `toProxySrc(url)` converts localhost URLs to proxy paths: `http://localhost:8080/docs` -> `/proxy/8080/docs`. Non-localhost URLs pass through unchanged. Pattern: `^https?:\/\/(?:localhost|127\.0\.0\.1):(\d+)(\/.*)?$`.

**Iframe attributes**: `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"` (without `allow-downloads`, VS Code file downloads break — the same sandbox `CodeSurface` reuses, § Code Surface), `title="Proxied content"`, `border-0`.

**Window creation**: "Window: New Iframe Window" command palette action (id `create-iframe-window`) opens a `Dialog` with two inputs: window name (autofocused, Enter focuses URL input) and URL (Enter creates window). Create button disabled until both fields non-empty. Calls `createWindow(server, session, name, undefined, "iframe", url)` — the extended API client function passes `rkType` and `rkUrl` in the POST body. Backend uses `CreateWindowWithOptions` for atomic `\;`-chained tmux command. Only shown when a session is active. Synthetic iframe windows are created this way; `@rk_type=iframe` means "**default view = web**" (a creation-time hint, § Window Views → `defaultView`), not a locked identity. (`260714-t97o`)

## Code Surface (the `code` lens renderer)

`app/frontend/src/components/code-surface.tsx` — the renderer for the **`code` surface/lens** (§ Window Views (Lens Model)) — mounted as a tile by `SurfaceLayout` whenever the resolved layout includes `code` (§ Surface Layout): via the top-bar surface toggles, the `Layout: Add Code` palette entry, a `?layout=…code…` deep link, or the switcher's `View: Code` row (which applies `single:code` through the shim). It embeds **code-server** at the window's git root — a full editor (tabs, syntax highlighting, SCM view, side-by-side diffs) beside the live agent terminal with no editor functionality built in run-kit. It is a lean component, NOT an `IframeWindow` reuse: the code-server URL is fully DERIVED, so the URL bar (`@rk_url` substrate chrome) is meaningless here — the component is exactly an iframe plus the not-running empty state (§ Design Decisions → The code surface is a lean `CodeSurface`). (`260811-k3vp`)

- **src** — `codeServerSrc(folder)` returns the RELATIVE path `/code/?folder=<folder>` (folder value `encodeURIComponent`d), never a composed absolute origin and never a port — the same relative-path discipline `toProxySrc` follows, so the embed rides the same origin through any reverse proxy. The path is STABLE: code-server keys browser-side workspace state by the proxy pathname, and `/code/` is fixed by the backend route (the port behind it is a private implementation detail, resolved server-side). code-server restores per-folder state from the `?folder=` param. The folder is the window's LATCHED code folder (the `gitRoot` prop arrives already substituted — § The code folder is a per-window latch), and the computed `src` is held in a **ref keyed to the iframe's MOUNT GENERATION** (the `reachable` gate): a latch update never rewrites a live frame's `src`, while a genuine remount (a reachability `false→true` flip, a window switch) boots the CURRENT latch.
- **Availability vs reachability** (spec right-panel.md § Surface Registry): AVAILABILITY = the window's code folder is LATCHED, or a `gitRoot` derives non-empty — the STABLE capability signal, computed upstream in `hasCode` over the latch-substituted effective window, so the surface toggle / switcher segment never strobe when the active pane leaves the repo (the port is always resolvable by convention, so the "configured" leg is always true). REACHABILITY (the host's TTL-cached probe, the state socket's `code-server` event) selects the surface's CONTENT only: reachable renders the iframe; unreachable renders the terse monospace empty state `code-server not running — check rk doctor` (`data-testid="code-surface-empty"`) instead of a dead iframe.
- **Sandbox** — the same token set as `IframeWindow`, including `allow-downloads` (without it VS Code file downloads break).
- **Chord reclaim** — focus inside the iframe swallows run-kit's chords (`⌘K` collides with VS Code's own), and same-origin makes an escape hatch possible: a capture-phase `keydown` listener attached to the iframe's `contentDocument` after every load intercepts events matching the INJECTED `shouldReclaimChord` predicate (built in `app.tsx` from the keybinding registry's pure `hasReclaimableMatch(e, bindings)` — `findMatches(...).some(b => !b.ttyOnly)`), `preventDefault` + `stopImmediatePropagation`s them before the embedded app's keybinding service, and re-dispatches a synthetic bubbling `KeyboardEvent` on the parent **document** (reaching both document-level listeners — the palette chord — and window-level ones — the dispatcher, the ⌘. view cycle). The reclaim carve-out: a keydown whose ONLY registry matches are `ttyOnly` bindings (the tmux split pair — a keydown arriving inside the iframe means the code tile owns focus) is NOT reclaimed, so ⌘D reaches code-server's own keybinding service while non-`ttyOnly` registry chords (⌘K, ⌘., ⌘J, ⌃`, …) are reclaimed (`260812-wfic`) — ⌃` deliberately preempts code-server's own integrated-terminal toggle, the hop back to tty winning over the embedded app's binding. The effect is keyed on `reachable` (the iframe only mounts when reachable, so a reachability flip re-runs it against the fresh iframe), re-attaches on `load` (each navigation replaces the document), guards `contentDocument` access in try/catch (a cross-origin or pre-load frame silently skips the attach — click-out remains the escape), and removes the listener from the attached document on cleanup. Proven by the `code-surface.spec.ts` e2e "keyboard spike: a registry chord pressed INSIDE the iframe reaches the parent" (§ Design Decisions → Chord-reclaim via a capture-phase iframe listener).
- **Load-time focus grab — guarded** — the code-server workbench grabs DOM focus once per iframe load (a script `focus()` at editor-restore time that no VS Code / code-server setting suppresses), which would otherwise win every window switch and flip `focusedTileKind` to `code`, killing all `ttyOnly` keybindings. Per-window focus memory plus a steal guard answer it: `CodeSurface` reports the grab through the `onProgrammaticFocus?: () => boolean` prop, fed by a capture-phase `focusin` listener on the frame's contentDocument attached by the same load/attach effect as chord reclaim (the ONLY observable — a script `focus()` re-points the focus chain but fires no parent-side iframe event); `app.tsx` reverts an armed grab whose remembered kind is not `code`. The tile wrapper's `onFocus` consults the guard before `focusSlot`, so a grab never settles the focused kind on `code` (§ Surface Layout → Tile renderer). Full model: [focus-ownership](/run-kit/ui/focus-ownership.md). (`260815-ltz7`)

### The code folder is a per-window latch

The folder the editor opens is per-window LATCHED state, never the live SSE derivation. `gitRoot` is re-derived per tick from the ACTIVE pane's cwd (backend `deriveGitRoot`, which the latch leaves untouched — it only picks the seed), so a pane switch or a `cd` would otherwise retarget the embedded editor to another workspace — or null the tile entirely when the pane leaves every repo — taking in-flight editor state with it (open tabs, dirty buffers, undo stacks). Derivation's only job is to SEED. (`260813-if5d`)

- **Storage** — `lib/code-folder-latch.ts`: value-bearing key `runkit-code-folder:{server}:{windowId}` (the `windowViewStorageKey` convention) holding the absolute folder path, with `readLatchedCodeFolder` / `writeLatchedCodeFolder` as try/catch-noop wrappers — pure and DOM-free apart from those, with colocated tests (the `window-view.ts` / `right-panel.ts` module contract). Absent, empty, and storage-unavailable all read alike as "not latched"; an empty folder is never written, so `""` cannot be stored. The latch is per-browser, like code-server's own tabs/layout state, and a tmux window id remapped by a snapshot restore orphans its key — a missing latch simply re-seeds on the next open.
- **Seed rule — derivation runs exactly once** — the latch is written the first time the code surface actually RENDERS for a window, keyed on `layout.order.includes("code")`, the choke point every entry path resolves through (the surface toggles, `View: Code`, `?view=code` / `?layout=` deep links, the mobile sheet). Availability alone seeds nothing: an offered-but-never-opened code lens is not an open editor. An empty derivation seeds nothing either, so a window that has never been inside a repo simply offers no code surface. After seeding, derivation never moves the editor — not on a pane switch, not on tile close/reopen, not on reload.
- **Follow rule — only the editor's own navigation moves it** — `CodeSurface`'s `load`-event seam (the same one the chord reclaim re-attaches on) also reads the same-origin `contentWindow.location`, parses `folder`, and reports it via `onFolderNavigated` when present, non-empty, and different (decoded comparison) from the current folder; `SurfaceLayout` passes it through as `onCodeFolderNavigated` and `app.tsx` writes the latch. So File > Open Folder inside code-server re-latches and a later remount renders where the editor actually is, while the terminal never moves the editor. The location read carries the attach's try/catch posture — a cross-origin or pre-load frame skips silently.
- **The `app.tsx` substitution seam** — the latch is read AT RENDER (a `useMemo` over server + window id + a write-epoch counter, beside the `storedLayout` read that does the same), never mirrored through an effect (§ Design Decisions → The latch is read at render, never mirrored through an effect). The exported pure `withLatchedCodeFolder(win, latch)` substitutes `gitRoot: latch ?? live` into ONE effective window, which feeds `availableViews`, `resolveLayout` (render path AND the URL-mirror effect), `availableSurfaces`, `SurfaceLayout`'s `window` prop, and the window-switch transition classification — so the tile render guard, `tileMeta`, and `codeServerSrc` all follow the latch with the pure lib modules untouched (§ Design Decisions → Effective-window substitution). Unlatched windows pass through by identity.
- **Stale latches are accepted** — a latch pointing at a deleted worktree renders code-server's own "folder does not exist" state; the escape is File > Open Folder, which re-latches. No liveness probe, no reset verb, no palette entry. A cross-viewer tmux window option (`@rk_code_folder`) is a deliberately deferred upgrade path, not shipped behavior.
- **e2e — `code-folder-latch.spec.ts` (+ `.spec.md`)** — real tmux on the port-3020 rig with the `code-surface.spec.ts` code-server stub: a window with one pane inside a repo and one outside proves the code tile survives the active pane leaving the repo and reopens at the latched folder, and that a reload with the active pane still outside renders the latched folder. Live File > Open Folder navigation is unit-tested only (no live code-server in the harness).

## Window Views (Lens Model)

The model (`docs/specs/window-views.md`, rules R1–R7; arrangement generalized by `docs/specs/surface-layout.md`): **a window ROW is a substrate** (a supervised tmux pane); **a VIEW is a lens** over one derivable output of that pane (the tty is a lens; an iframe of the pane's HTTP service is a lens; the parsed agent transcript is a lens; later: desktop). **Which lenses a window offers is a derived capability set; what YOU look at is per-viewer client state** — the surface layout (§ Surface Layout) carried in the URL + localStorage, never a server-side `@rk_type` mutation, never part of the window's identity. A single-tile layout IS the exclusive-lens view: `single:chat` is "the chat lens", `single:tty` the default terminal. Lens state is frontend-only — no Go/API surface participates: the `@rk_type`/`@rk_url`/`@rk_chat` plumbing and `POST /options` carry no lens state, and the SSE payload already carries `rkType`/`rkUrl`/`chatProvider`. (`260714-t97o`, `260714-r7rq`)

Four lenses are implemented: `tty` (always available, `TerminalClient`), `web` (available when `rkUrl` is non-empty, `IframeWindow`), `code` (available when the window's code folder is latched OR a `gitRoot` derives non-empty — the stable capability signal; `CodeSurface`, § Code Surface), and `chat` (available when `chatProvider` is non-empty, `ChatView` — the read-only transcript renderer, § Chat View). Capabilities are orthogonal and STACK (spec R5): one window can offer `tty`+`web`+`code`+`chat` at once, and the layout can tile up to three of them at once (§ Surface Layout). The lens set IS the layout's tileable surface set (`SurfaceKind = ViewName`). The registry is open-ended — `desktop` adds a `ViewName` member, an availability clause, a `defaultView` hint, and surfaces on the existing affordances (the top-bar toggle group, the palette `View:` action), NOT a new component/route/window-type.

### Pure view-model helper — `lib/window-view.ts`

The single source of lens CAPABILITY logic — pure, DOM-free, colocated `window-view.test.ts` (the same pattern as `window-transition.ts`/`navigation.ts`). `surface-layout.ts` builds its availability set on these predicates, so the toggles, the layout, and the palette share one capability source (no drift). Helpers take a minimal structural `{ rkType?, rkUrl?, chatProvider?, gitRoot? }` shape (assignable from `WindowInfo`):

- **`ViewName = "tty" | "web" | "chat" | "code"`** — the lens union; aliased as the layout's `SurfaceKind`.
- **`hasWebUrl(win)` / `hasChat(win)` / `hasCode(win)`** — the single-source availability predicates: `rkUrl` non-empty after `.trim()` (whitespace-only `@rk_url` is NOT web — no blank-src iframe); `chatProvider` non-empty (mirrors the backend `resolveWindowChat` gate); for `code`, the window's `gitRoot` non-empty — evaluated over the LATCH-SUBSTITUTED effective window (`withLatchedCodeFolder`, § Code Surface → per-window latch), so the shipped predicate reads "latched OR derivable" while the module itself stays storage-free and DOM-free (the port is always resolvable by convention, so there is no configured-port leg); code-server REACHABILITY is deliberately NOT in this gate (it fluctuates and would strobe the toggles/palette; it selects the surface's content instead, § Code Surface).
- **`availableViews(win): ViewName[]`** (spec R1/R3) — `["tty"]`, plus `"web"` when `hasWebUrl`, plus `"code"` when `hasCode`, plus `"chat"` when `hasChat`. **Availability is decoupled from `@rk_type`**: an iframe-typed window with no URL offers only `tty`. Returned in the registry's fixed order via a `HINT_ORDER` (`[chat, code, web, tty]`) filter — so a fully-stacked window yields `["chat","code","web","tty"]`. The layout module's `availableTiles` re-derives the same set tty-first (§ Surface Layout).
- **`defaultView(win): ViewName`** (spec R5) — the window's default lens, applied ONLY as the layout ladder's hint rung (`hintLayout` wraps it as `single:<view>`): `"web"` when `rkType === "iframe"` AND `rkUrl` is set, else `"tty"`. `@rk_type=iframe` is a **creation-time default-view hint, never an identity**. Structured as spec R5's ordered hint precedence `desktop > chat > code > web > tty` (module const `HINT_ORDER`, only `web`/`tty` wired) so later lenses add a hint clause, not a branch. **`chat` and `code` sit in `HINT_ORDER` for capability ORDERING only — they contribute NO default hint**: a chat- or code-capable window still defaults to `tty` unless the viewer chose otherwise (preserves `260714-r7rq`'s terminal-default).
- **`nextView(available, current): ViewName | null`** — the cycle successor (wraps); `null` when < 2 views or `current` is absent. Powers the `Cmd/Ctrl+.` chord, which applies `single:<next>` (pure so the order is unit-testable).
- Input gating for the lens chord is **not** a `window-view.ts` concern: the shared `shouldSuppressChord` predicate in `lib/keybindings.ts` gates every app chord (§ Keyboard Shortcuts → Dispatch seams).
- **localStorage helpers** — **value-bearing** key `runkit-window-view:{server}:{windowId}` storing the view NAME, including `"chat"` (absent = default). `windowViewStorageKey`/`readStoredView` (READ-only — nothing writes this key anymore), try/catch-noop per `chrome-context.tsx`. The key is a LEGACY seed source: the layout mutation path writes `rk-layout:` keys, and `runkit-window-view` is read only by the translation shim's seeding (§ Surface Layout) and by the switch-transition classification. `resolveLayout` owns the resolution chain — the module carries no resolver of its own. (`260814-6b0j`)

### `?layout=` search param + the translation shim — `lib/router-url.ts`

`layout` is the terminal route's one layout search param (spec surface-layout.md L1, Constitution IV: no new route); the legacy `view`/`panel` params remain ACCEPTED so old deep links never break. The exported pure `validateTerminalSearch(search): { view?: "web" | "chat" | "code"; panel?: "web" | "code"; layout?: string }` passes `view` ∈ {`web`, `chat`, `code`} and `panel` ∈ {`web`, `code`} through, forwards any non-empty string `layout` (shape/arity validation happens in `parseLayout`, § Surface Layout), and **drops any other/unknown/non-string value** (treated as absent, NEVER errored). It is wired as the route's `validateSearch` and unit-tested directly in `router-url.test.ts`. The `declare module "@tanstack/react-router"` `Register` block types the params, so `useSearch({ strict: false })` in `app.tsx` reads them **with no `as` cast** (code-quality type-narrowing — `tsc --noEmit` clean). At resolution, `translateLegacyParams(view, panel)` maps `?view=X` → `single:X` and `?view=X&panel=Y` → `split-h:X,Y` (X in slot A), and the route mirrors the resolved layout back as `?layout=` ONLY.

### `app.tsx` integration — resolution, `switchView`, the layout render

`app.tsx` (terminal route) owns ONE layout-state block (§ Surface Layout → `app.tsx` integration for the full ladder/mirror/mutation machinery): `searchLayout = search.layout ?? translateLegacyParams(search.view, search.panel)`, `storedLayout = readStoredLayout(server, windowParam)`, `layout = resolveLayout(searchLayout, storedLayout, effectiveWindow)` (memoized; `effectiveWindow` is the current window with its latched code folder substituted in — § Code Surface → per-window latch). The lens model's consumers key off **slot A** — `resolvedView: ViewName = layout.order[0]` (spec R12's shim: a multi-tile layout reads as its slot-A surface to the `view-cycle` chord and the palette `View:` actions). One stable `switchView(view)` callback collapses to a single-tile layout: `applyLayout({ shape: "single", order: [view] })` — `applyLayout` persists per-window localStorage AND mirrors the URL via `replace: true` navigation, so a lens pick is a full user mutation (never an `@rk_type` mutation, spec R7). The **render** is `<SurfaceLayout layout={renderLayout} …/>` keyed `` `${server}:${windowId}` `` (a window switch remounts it) — `renderLayout` is the ladder-resolved layout plus the transient present auto-expand override (§ Surface Layout → Present auto-expand) — one tile per surface in the rendered order (§ Surface Layout → tile renderer). There is no `@rk_type`-mutating "switch" path anywhere: switching lenses/surfaces is the surface toggles' and the palette's job, neither of which mutates `@rk_type` (spec R7; the API client has no dedicated `@rk_type` helper — the generic `setWindowOptions` could set it, but no view-switch call site does).

### Lens-switch surfaces — palette, `view-cycle`, top-bar toggles

There is no lens-switcher component: the lens-switch surfaces are the command palette's `View: …` actions (§ Palette parity below), the `view-cycle` chord, and the top bar's open-tile toggles for non-hidden surfaces (§ Surface Toggles). The top-bar chevron menu carries no lens rows — its VIEW section holds the ▦ layout chip's shape rows plus the `menuOnly` Fixed width and Terminal font rows (§ Chrome (Top Bar) → Right cluster). (`260812-0c6o`)

### Palette parity + keyboard shortcuts (Constitution V)

- **`View: Terminal` / `View: Web` / `View: Code` / `View: Chat` palette actions** (AppShell `viewActions` in `app.tsx`), each visible only when its view is **available AND not the current** (slot-A) view — each applies `single:<view>` through `applyLayout` via `switchView` (§ app.tsx integration). The gating + label + shortcut-hint composition live in a pure builder `buildViewActions(available, resolved, onSwitch, hints)` in `lib/palette-view.ts` (mirrors `lib/palette-move.ts`/`palette-update.ts`, unit-tested in `palette-view.test.ts`). The per-entry `shortcut` hint tracks the binding that reaches it: every switch shows the lens cycle's combo except `View: Chat`, which renders NO hint (chat carries no dedicated chord and is deliberately left unadvertised). `buildViewActions` takes the hint as a `ViewShortcutHints = { cycle: string }` parameter, and `app.tsx` passes the **effective** formatted `view-cycle` combo from the keybinding registry, so an override moves the hint (an empty string means "no working chord" and renders no hint); the module default (`⌘.`) matches the registry default for legacy callers and tests. One `buildViewActions` call feeds them; there is no `@rk_type`-mutating `toggle-iframe-terminal` action. The multi-tile affordances (add/close/promote/swap/zoom/shape) carry their own `Layout:` palette entries (§ Surface Layout → palette + chords).
- **The lens cycle chord** (`view-cycle`, default `⌘.` / `Ctrl+.`) is a registry binding on the `cmd` tier with `scope: "terminal"` (§ Keyboard Shortcuts), read through `bindingByAction` by a window-level `keydown` effect in `app.tsx` that `preventDefault()`s (so xterm doesn't also receive it), gates on the shared `shouldSuppressChord`, and calls `switchView(nextView(views, active))` — i.e. it cycles through **single-tile** lens layouts. No-op when < 2 views. The live view/window values and the effective binding are read via refs (`viewCycleRef`, `viewCycleBindingRef`) so the listener is stable across SSE ticks. It keeps its own listener rather than folding into the registry dispatcher because its enablement is lens-local state. `⌘.` is a free binding in the `⌘<punctuation>` family and `Ctrl+.` is inert in readline (unlike `Ctrl+/`→undo); per-device rebinding goes through the override layer.

### Heading is a static `Window:` in every lens

The top-bar center `PageType: name` heading on the terminal route reads a **static `Window: <window>` in every lens** (tty / web / code / chat) — it does NOT follow the active view (§ Window Heading). A single `WINDOW_PREFIX = "Window:"` constant (`top-bar.tsx`) is passed as a constant `prefix` into `WindowHeading` at the terminal-mode center cell; there is no lens-following `terminalHeadingPrefix()` helper and no `WEB_PREFIX`/`CHAT_PREFIX` constants. The heading identifies the WINDOW (the substrate); which lens you look through is carried by the view content itself (chat bubbles vs. terminal) and the top bar's lit tile toggles, not the heading (§ Design Decisions → Heading identifies the window, not the lens). The name's anchor does not jump on a lens switch, since the prefix width does not change with the lens (§ Center-heading stable anchor + nav affordances). The click-to-rename affordance and boot-sweep treatment apply. (`260714-uco1`, `260717-6anu`)

### Internal navigation targets the bare route (spec R6 / surface-layout L4)

Navigating to a DIFFERENT window carries NO layout/view/panel param — each destination window resolves its own layout via the ladder (§ Surface Layout → resolution ladder). Client-side navigations (sidebar/palette/breadcrumb via `navigateToWindow`, plus the window-death redirect and SSE-writeback switch) omit/clear `search`, and TanStack Router's `final` search middleware returns `{}` when `dest.search` is absent, so an outgoing `?layout=` does not leak onto the target. (Per-window localStorage covers the intent; the web-view-lens e2e persistence case exercises this through a real sidebar-click navigation to guard against a future `retainSearchParams`/router-upgrade regression.) History gets "what you saw": layout tweaks `replaceState` (no entry per tweak) while window switches push entries, so back/forward restores the historical arrangement each entry carried (spec L4). The one exception is the `Agent: Next waiting` / WaitingBadge deep-link, which INTENTIONALLY sets `?view=chat` for a chat-capable target — the shim translates it to `single:chat` (§ Chat View → WaitingBadge).

### Window-switch transition classification (one rule)

## Surface Layout (the center is a layout of tiles)

The terminal route's center is a **layout manager** (`docs/specs/surface-layout.md`): a resolved **layout** `(shape, order, ratios)` renders as 1–3 **tiles**, each mounting an existing surface renderer unchanged. `docs/specs/right-panel.md`'s P6 slot mechanics do not apply to the layout manager; its availability derivation and P4 attention do (§ Surface Toggles). A **surface** is a (substrate, lens) pair of the ROUTE window; the tileable set is `tty | web | chat | code` (`SurfaceKind = ViewName` — § Window Views (Lens Model)); `tty` is `(current window, tty)`, always available, listed first. (`260812-ab5v`) Tiles are content-area state; the toggles that open and close them live in the top bar (§ Surface Toggles).

### The model — preset shapes × ordered surfaces × ratios

- **Shapes** (exact URL strings, `SHAPE_ARITY`): `single` (1), `split-h` / `split-v` (2), `row` / `col` / `main-left` / `main-right` / `main-top` (3). Slot A (first in `order`) is the main slot in `main-*` shapes. A layout carries exactly its shape's arity. Max 3 tiles (Constitution IV); presets, never free split trees.
- **Order** — 1–3 surface kinds; kinds MUST NOT repeat within a layout **except `tty`** (the muxed `/ws/terminals` relay supports N clients per pane, so duplicate tty tiles of one window are legal; only the FIRST tty tile receives the shared `wsRef`/`focusRef`).
- **Ratios** — divider positions, per-viewer localStorage ONLY, keyed `rk-layout-ratios:{server}:{windowId}:{shape}` (a ratio is meaningless across shapes), written on drag RELEASE; never in the URL. Clamped by `clampRatio` (`lib/right-panel.ts`, the `MIN_PANEL_WIDTH_PX` 280px floor bounding both sides).

### Pure layout model — `lib/surface-layout.ts`

New pure, DOM-free module with colocated tests (the `window-view.ts` pattern — § Design Decisions → Layout helpers live in a new pure module). Untrusted URL/localStorage strings are validated by guards on the parse path (no `as` casts):

- **`parseLayout` / `serializeLayout`** — `<shape>:<a>,<b>[,<c>]` round-trips byte-identically; rejects unknown shape/kind, arity mismatch, repeated non-tty kind (returns `null`). `ALL_SHAPES`, `shapesForArity(arity)` (the same-arity ring), `SURFACE_LABEL` / `SHAPE_LABEL` / `SURFACE_GLYPH` — shared copy for tile headers, the surface toggles' tooltips/aria, palette `Layout:` entries, and the mobile sheet tabs so none drift.
- **`resolveLayout(searchLayout, storedLayout, win)`** — the ladder: (1) valid URL `?layout=` → (2) localStorage `rk-layout:{server}:{@N windowId}` → (3) default-view hint (`hintLayout` wraps `defaultView(win)` as `single:<view>` — a legacy `@rk_type=iframe` window hints `single:web`) → (4) `single:tty`.
- **Availability degradation (`degradeLayout`)** — an unavailable surface drops out TILE-BY-TILE: the remaining order renders in the matching smaller-arity shape (3→2 `split-h`, 2→1 `single`, slot A kept); an unknown shape or fully-invalid value falls through to the ladder's next rung. No broken iframe ever mounts.
- **`SURFACE_RAIL_HIDDEN: ReadonlySet<SurfaceKind>`** — a per-surface demotion flag (currently `chat` only): a surface in the set renders NO toggle in the top-bar `surface-toggles` group (bar group or overflow Tiles rows) or the mobile surface sheet — the consumers filter by the flag AT RENDER, never at availability, so `availableTiles` is untouched and the palette's `Layout: Add Chat` / `Layout: Close Chat` entries keep working as chat's entry points (§ Surface Toggles). An already-open chat tile still renders and closes normally (the tile's ✕, `Layout: Close Chat`, layout verbs) — the flag hides the toggle, never the tile. Un-hiding when chat ships is deleting the entry from the set. (`260812-0c6o`)
- **The permanent translation shim** — `translateLegacyParams(view, panel)`: `?view=X` → `single:X`; `?view=X&panel=Y` → `split-h:X,Y`; bare `?panel=Y` → `split-h:tty,Y`. `seedLayoutFromLegacy(server, windowId)` migrates the localStorage predecessors: when no `rk-layout:` key exists, a stored `runkit-window-view` / `runkit-window-panel` value seeds the equivalent layout (legacy keys left in place — other tabs may be older).
- **Mutations** (all pure): `promote` (surface → slot A; order permutes, shape unchanged), `swapWithNext`, `closeSurface` (arity collapse, slot A kept; `null` when closing the last tile — disallowed), `addSurface` (1→2 `split-h`, 2→3 `main-left`; `null` at 3), `cycleShape` (next same-arity preset, order kept — tmux `next-layout` muscle memory), `setShape`.
- **Storage** — `rk-layout:{server}:{windowId}` (value-bearing, written on USER MUTATION only — spec L3) + the ratios key above; all reads/writes try/catch-noop.

### `app.tsx` integration — ladder, mirroring, write discipline

One layout-state block (§ Window Views → app.tsx integration): resolve via the ladder, then an effect MIRRORS the applied layout into the URL with `replace: true` navigation (`replaceState` — never `pushState` for a layout tweak; the window's DEFAULT layout — `hintLayout`, usually `single:tty` — mirrors as a CLEAN URL with the param DROPPED, and `applyLayout` applies the same rule on a mutation back to the default; window switches push entries as today, so back/forward restores the historical arrangement each entry carried, spec L4). **`applyLayout(next)` is the ONE mutation path** — `writeStoredLayout` + `replaceState` mirror; tile verbs, the surface toggles, the ▦ chip, the `view-cycle` chord, and the palette `View:` actions all funnel through it (L3: localStorage is written on user mutation only, never on merely arriving via a carried `?layout=`). Internal navigation (sidebar, ▾ switcher, palette) targets the bare route (§ Window Views → Internal navigation targets the bare route); layout consumers read resolved state, never parse `location.search` pre-ladder. `togglePanel(surface)` is the toggle behind the top-bar group, the overflow Tiles rows, and the palette `Layout: Add/Close` entries: open surface → `closeSurface`, closed → `addSurface`, then `applyLayout` (a `null` mutation — closing the last tile — is a no-op).

### Present auto-expand (the `rk present` transient reaction)

A viewer MOUNTED on a window's terminal route that observes the window's `rkUrl` **transition** on the state stream — empty→set, or value→different-value — transiently auto-opens the `web` tile (spec surface-layout.md R7/L3 carve-out: a fresh `rk present` is an implicit request for attention). The reaction is view state of the zoom/`mobileActiveTile` class: it never calls `applyLayout`, so nothing is persisted (`rk-layout:` localStorage) and nothing is mirrored into the URL (`?layout=`). (`260815-wkcw`)

- **Trigger semantics (transition-observed)** — the pure reducer `observeRkUrl(state, rkUrl)` folds each observed value into per-window state: initialization (cold entry, first snapshot) NEVER triggers; a same-value SSE tick is a no-op (transition, not presence); a transition to empty clears `active` without latching (availability degradation owns the cleared case); a transition to a new non-empty value triggers UNLESS it exactly matches the dismissal latch. The observation state (`AutoExpandState { lastUrl, active, dismissedUrl }`) lives in an `app.tsx` ref `Map` keyed `` `${server}:${windowId}` `` and survives window switches: a change that happened while the viewer was away updates `lastUrl` silently on remount (not an observed transition), the override deactivates on remount (leaving+returning resolves via the normal ladder), and the latch survives. The observation effect skips frames where the window record is unresolved (a snapshot race must not fake a transition), and the `active` flag reaches render through a `{key, active}` state mirror that `renderLayout` gates on the CURRENT route key — a window switch away from an active auto-open never flashes a phantom web tile on the destination route.
- **Render-time override, never a mutation** — `renderLayout = withAutoWeb(layout, active)`: when active and the resolved layout lacks `web`, render as if `web` were appended through the existing growth conventions (`addSurface` — 1→2 `split-h`, 2→3 `main-left`; arity 3 without `web` is `null` → identity, a visual no-op). Identity when `web` is already open (`IframeWindow`'s SSE sync already navigates the frame on `rkUrl` change — no layout action, no focus move). `renderLayout` feeds `<SurfaceLayout layout>` and EVERY mutation seam — the tile verbs, `togglePanel`, the palette `buildLayoutActions`, the top-bar surface toggles' `open` set (a transiently auto-opened web tile reads lit), and the ▦ chip's `layout` prop — while the ladder-resolved `layout` keeps feeding the URL-mirror effect, localStorage, `resolvedView`, and the window-switch `ungatedIds` classification.
- **Take-ownership (L3)** — any user `applyLayout` while the override is active deactivates it: `dismissAutoExpand` (records the latch) when the applied layout lacks `web`, else `deactivateAutoExpand`. The mutation persists from the RENDERED state — touching it makes it yours.
- **Dismissal latch** — closing the auto-opened web tile (any mutation whose result lacks `web` while active) latches the window's current `rkUrl` value: a later observed transition TO that exact value does not re-open (so an agent's unset/re-set loop cannot fight a dismissal), while a different value re-triggers — timestamped present URLs (`target.URL(..., presentNowFn)`) change on every re-present and intentionally pass the latch. The latch is in-memory only (resets on reload; no sessionStorage/localStorage).
- **Mobile (R13)** — the same render path applies below `isMobileViewport()`: the auto-added `web` surface becomes reachable as a tab in the mobile surface sheet (the ▦ chip appears when `renderLayout` is multi-tile, and the sheet's tab list plus the `mobileActiveTile` fallback derivation read `renderLayout.order`), but `mobileActiveTile` is never SET by the reaction — the visible tile is never auto-swapped on a phone.
- **Module** — `lib/present-auto-expand.ts` (`observeRkUrl` / `dismissAutoExpand` / `deactivateAutoExpand` / `withAutoWeb`), pure and DOM-free with colocated tests (the `window-view.ts` / `surface-layout.ts` module contract).
- **e2e — `present-auto-expand.spec.ts` (+ `.spec.md`)** — real tmux on the port-3020 rig (the `web-view-lens.spec.ts` `_tmux.ts` pattern; `tmux set-option -w @rk_url` is the present-default-arm write path), gated on the status bar's Connected readiness signal: rkUrl set while viewing → the web tile appears with no `?layout=` change and no `rk-layout:` write; ✕-close → unset + re-set the same value stays closed, a different value re-opens; cold arrival with rkUrl already set → no auto-open.

## Chat View

A **read-only HTML chat view over the SAME agent pane** — a second view over the tmux pane, never a substrate (the pane stays the agent's parent, Constitution VI; the view only renders the streamed transcript). It is the **`chat` lens** of the window-view model (§ Window Views (Lens Model)) — a `chat` TILE in the surface layout on the existing `/$server/$window` terminal route (Constitution IV, no new route; a legacy `?view=chat` deep link still works — the shim translates it to `single:chat`, § Surface Layout). **All view-state plumbing — the `?layout=` param + shim, availability gate, `rk-layout:` localStorage persistence, palette parity, and the switch-transition classification — is the UNIFIED machinery** described in § Window Views (Lens Model) and § Surface Layout; this section owns only what is chat-SPECIFIC: the `chatProvider` gate, the connection-dot semantics, the renderer/stream, and the WaitingBadge deep-link. (The heading is a static `Window:` in every lens, § Heading is a static `Window:`.) The renderer + data layer live in `architecture.md`/[chat](/run-kit/chat.md) § Chat View Frontend. The chat stream is a `kind:"chat"` subscription on the shared state socket (NOT an `EventSource`) — the owner hook is `use-chat-subscription.ts`, and the connection dot below derives from socket-connected AND chat-acked, not `EventSource` health. (`260714-uco1`, `260717-vhvz`)

**The `chatProvider` gate.** `WindowInfo` carries `chatProvider?: string` + `chatSessionRef?: string` (`types.ts`) — the window-level `@rk_chat` rollup the backend emits (typed, not newly parsed). **A non-empty `chatProvider` is the SOLE availability gate** for the chat lens (`hasChat(win)` in `window-view.ts`) — mirroring the backend's own `resolveWindowChat` gating — so it transitively gates every chat affordance: the `View: Chat` palette action, the `Layout: Add Chat` / `Layout: Close Chat` palette entries (chat's entry points — the surface toggles and the mobile surface sheet render no chat toggle, `SURFACE_RAIL_HIDDEN`, § Surface Layout), the chat tile's `<ChatView>` renderer, and the deep-link append. (The heading is NOT among them — it is a static `Window:` in every lens, § Heading is a static `Window:`.) There is NO separate `chatAvailable` variable — `resolveLayout`/`availableViews` fold the gate in (an unavailable `chat` in a layout degrades tile-by-tile, § Surface Layout).

### View state = the unified lens machinery (NOT a chat-specific mechanism)

The chat lens runs entirely on the unified lens + layout machinery (§ Window Views (Lens Model), § Surface Layout), with no chat-specific view-state module:
- Resolution is `resolveLayout` (URL `?layout=` → `rk-layout:` localStorage → default hint → `single:tty`); `lib/router-url.ts`'s single `validateTerminalSearch` still accepts `?view=chat`, which the shim translates to `single:chat`. There is no `lib/chat-view-resolve.ts`.
- Persistence is the value-bearing `rk-layout:{server}:{windowId}` key (the legacy `runkit-window-view:` key is only a shim seeding source). There is no `runkit:chat-view:` key-presence pref hook.
- Lens switching is palette-only: the `View: Chat` / `View: Terminal` palette actions call `switchView("chat")`/`switchView("tty")` — i.e. applying `single:chat`/`single:tty`. There is no switcher component and no dedicated chat chord.
- `chatViewActive = layout.order.includes("chat")` is the render + stream gate (`resolveLayout` already gated on `chatProvider`) — true whenever a chat TILE is open, slot A or not.

### Center heading `Window: <window>` (static in the chat lens too)

The `chat` lens does NOT change the heading prefix — the top-bar heading is a static `Window: <window>` in every lens (§ Heading is a static `Window:`; § Window Heading for the boot-sweep/rename mechanics). The `<ChatView>` renderer preserves the inline-rename affordance (the heading IS the rename surface, especially on mobile) — the same parametrized `WindowHeading`, no fork. (`260714-uco1`)

### Renderer swap + chat stream (`app.tsx`)

In the `windowParam` render arm, `<ChatView>` mounts as the chat TILE inside `<SurfaceLayout>` (fed the AppShell-owned subscription bundle — the tile mount reads like the legacy lens branch, § Surface Layout → tile renderer). `AppShell` owns the single owner-hook call — **`useChatSubscription(server, windowId)`**, opened only when `chatViewActive` (else passed empty strings so the hook idles) — and passes `{events, pending, connected, error}` into the tile. ONE chat subscription on the shared state socket feeds both the renderer and the connection dot (below). The chat pane joins the switch-transition **ungated capture** through the unified `ungatedIds` classification (any non-`tty`-led resolved layout; § Window Views → Window-switch transition classification) — `<ChatView>` has NO xterm first-write seam, so a first-write gate would never release. (`260717-vhvz`)

### Connection dot = chat stream health in chat mode (R9)

"Dot = per-page live-data health" (§ Chrome (Top Bar) → connection dot). In chat view, the `isConnected` `AppShell` passes to `<Sidebar>` reflects the **chat subscription's** health instead of the per-server sessions slice: `dotConnected = chatViewActive ? chatStream.connected : isConnected`. `chatStream.connected` = (state socket connected) AND (this window's `kind:"chat"` subscription acked), with the established 3s disconnect debounce (from `use-chat-subscription`). (`260717-vhvz`) In every other lens the dot keeps its per-server sessions-slice value.

### WaitingBadge click + `Agent: Next waiting` deep-link into `?view=chat`

`WaitingBadge` (`components/waiting-badge.tsx`) takes an **optional** `onClick` prop: when passed, the badge renders as a `<button>` (rk-glint hover, `stopPropagation` so it doesn't bubble to the parent row) that navigates to the next waiting window in its scope; when absent, it renders a **display-only** `<span>` (the board-header / Host-page-tile / server-panel mount sites pass no onClick). It is currently wired ONLY at the **sidebar session row** (`session-row.tsx` → `sidebar/index.tsx` → `AppShell`'s `handleWaitingBadgeClick`) — the one surface with a navigable per-session scope.

`handleWaitingBadgeClick(srv, sess)` (`app.tsx`) builds the clicked session's ordered waiting windows and calls **`nextWaitingTarget(ordered, server, windowParam)`** (`lib/palette-agent-nav.ts` — REUSED, not re-implemented; § Design Decisions → The waiting-badge click advances, never restarts). It appends `?view=chat` via the pure `chatSearchForTarget(hasChat)` helper (`lib/palette-agent-nav.ts`, unit-tested) — `{ view: "chat" }` iff the target window has a `chatProvider`, else empty search (the target resolves its own pref; the shim translates the param to `single:chat`, § Surface Layout). This is the ONE intentional `?view=` carry across a window switch (§ Window Views → Internal navigation targets the bare route). The existing `Agent: Next waiting` palette action gets the **same** `chatSearchForTarget` append rule for any target it navigates to.

## Design Decisions

### Heading identifies the window, not the lens
**Decision**: the terminal-route center heading is a static `Window: <window>` in every lens (tty/web/code/chat); lens identity is carried by the tile content and the top bar's lit tile toggles, not the heading.
**Why**: the heading identifies the WINDOW (the substrate), per window-views.md "rows are substrates, views are lenses". Keeping the prefix constant also stops the name's anchor from jumping on a lens switch (the prefix width no longer changes with the lens).
**Rejected**: "the center page heading follows the lens" (window-views.md R4's original sentence — reversed in-spec within the change).
*Introduced by*: 260714-uco1-topbar-heading-anchor-nav

### Two verb families on tile headers
**Decision**: Tile-header verbs split into layout verbs (generic, arity-gated, unchanged) and content verbs (per-kind, any-arity, zoom-visible) — the tty tile carries a bordered pane segment holding Split H / Split V / Close Pane.
**Why**: Pane operations act on the tmux pane inside the tty tile; proximity is the disambiguation. The tile header is already per-kind on its left side (StatusDot, meta chips), so per-kind verbs on the right are an evolution, not a break.
**Rejected**: Keeping pane verbs in the top bar (target invisible on multi-tile layouts); moving only the splits; a confirm-on-close variant — the glyph+grouping distinction below was chosen.
*Introduced by*: 260813-w1lf-terminal-tile-content-verbs

### `IframeWindow`'s `onSwitchToTty` is a callback prop, never an `@rk_type` mutation
**Decision**: `IframeWindow.onSwitchToTty` renders the `>_` "Switch to terminal" button, and the callback applies a per-viewer layout switch (`single:tty` through `applyLayout`); the web tile passes it, so the button renders on every web tile.
**Why**: switching to the terminal is view state, not substrate state — a callback keeps `IframeWindow` presentational and free of the view/layout import graph, and the flip fires zero `/options` POSTs (e2e-asserted). Every mount passes the callback (tiles sit side by side, so a "suppress beside the tty" gate has no context to serve).
**Rejected**: a client-side `@rk_type` mutation from the renderer (the former `updateWindowType` helper, since deleted with zero call sites) — mutates the window's identity for every viewer to serve one viewer's arrangement.
*Introduced by*: 260811-2r1w-right-panel-shell-web-surface; tile-context semantics: 260812-ab5v-surface-layout-core

### `SurfaceLayout` owns zoom/drag/mount-once; `app.tsx` owns layout state
**Decision**: the tile renderer receives the resolved layout as a prop and owns only transient interaction state (zoom, the in-flight ratio drag, the ever-opened mount bookkeeping); layout resolution (the ladder), persistence, and URL mirroring live in `app.tsx` behind the single `applyLayout` mutation path.
**Why**: layout state is route-integrated (search params, history semantics, navigation seams) and belongs beside the lens machinery; zoom and drag are self-contained interaction state with no URL/localStorage footprint. Prop-in/callback-out composition keeps the renderer free of the router/storage import graph — tile chrome, verbs, and hide-never-unmount are unit-testable in jsdom — and new surface kinds slot in without touching the shell.
**Rejected**: the renderer importing storage/router helpers and owning layout resolution — two sources of truth for the layout (component + route) and untestable without mocking the router.
*Introduced by*: 260811-2r1w-right-panel-shell-web-surface (as the panel shell's contract); generalized to the tile renderer: 260812-ab5v-surface-layout-core

### Present auto-expand composes via `addSurface` at render time
**Decision**: `app.tsx` computes `renderLayout = withAutoWeb(layout, autoWebOpen)` — `addSurface(layout, "web") ?? layout` when the auto-open is active and the resolved layout lacks `web` — and feeds `renderLayout` to `SurfaceLayout`, the tile verbs, the top-bar surface toggles' open set, and the ▦ chip; `resolveLayout`'s output keeps feeding the URL-mirror effect, localStorage, and the window-switch transition classification.
**Why**: reuses the exact growth shapes every other web-open path produces (the surface toggles, the palette), so the auto-open looks identical to a manual open; verbs acting on the rendered layout make "touching it makes it yours" (L3) fall out for free — a mutation persists from what the user sees. And because nothing is written, R7's substrate-vs-view-state split and L3 ("write on user mutation only") stay intact.
**Rejected**: slot-A swap (steals the terminal from an actively-typing user); a zoom-like overlay (new interaction surface, not reachable by the existing verbs; closing semantics would need bespoke chrome).
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Value-exact dismissal latch; timestamped re-presents pass it
**Decision**: the dismissal latch matches the exact `rkUrl` string. A re-present of the same file carries a fresh timestamp and re-opens.
**Why**: a re-present is by definition a fresh request for attention; suppressing it would make the verb unreliable. The latch's job is narrower — the same value re-observed (unset/re-set, state replays) must not fight a dismissal.
**Rejected**: normalizing away the timestamp param or a time-window cooldown — heuristic, and it would suppress genuine re-presents.
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Auto-expand observation state lives in a per-window in-memory map
**Decision**: the auto-expand state (`lastUrl`, `active`, `dismissedUrl`) is held in an `app.tsx` ref `Map` keyed `` `${server}:${windowId}` `` and updated by the pure reducer in `lib/present-auto-expand.ts`; it is not cleared on window switch.
**Why**: surviving the map across switches means a value change that happened while the viewer was away updates `lastUrl` silently on remount (no spurious trigger), and a brief unresolved-window frame (snapshot races) cannot fake a transition. Matches the transition-observed rule without extra bookkeeping.
**Rejected**: `useState` reset on `[server, windowParam]` (the `mobileSlotA` pattern) — a reset makes the first post-switch observation indistinguishable from cold entry only if handled carefully, and loses the latch on every switch.
*Introduced by*: 260815-wkcw-present-auto-expand-web-tile

### Code-surface availability gates on stable signals; reachability gates content
**Decision**: `hasCode` — the availability gate for the `code` lens/tile — is stable signals only: the window's code folder is LATCHED, or a `gitRoot` derives non-empty (the code-server port is always resolvable by convention — preset `RK_CODE_SERVER_PORT` else `RK_PORT+2` — so a configured-port leg would be vacuous). The TTL-cached reachability probe never gates availability; it selects the surface's CONTENT (live iframe when up, the `code-server not running — check rk doctor` empty state when down).
**Why**: reachability fluctuates with code-server restarts — gating the surface toggle / switcher segment on it would strobe the affordances, and the not-running state could never render (the affordance would vanish exactly when its message is needed). The live derivation fluctuates too, with the ACTIVE PANE's cwd: a window whose editor is open would lose its surface toggle, switcher segment, and deep-link validity the moment an agent `cd`s out of the repo. The latch is what makes the signal genuinely stable per window; content states may fluctuate.
**Rejected**: availability = configured ∧ reachable (the spec's original wording — internally contradictory with the not-running state); availability = gitRoot ∧ port-configured (vacuous once the port resolves by convention); derivation-only availability (strobes with the terminal's cwd).
*Introduced by*: 260811-k3vp-right-panel-code-lens; gitRoot-only gate: 260811-a2bo-daemon-code-server-stable-route; latch-or-derivable: 260813-if5d-latch-code-surface-folder

### The code surface is a lean `CodeSurface`, not an `IframeWindow` reuse
**Decision**: the `code` lens/surface renders a new minimal component — an iframe of `/code/?folder=<gitRoot>` plus the not-running empty state — while `web` keeps `IframeWindow` with its URL bar and refresh chrome.
**Why**: the code-server URL is fully derived (the stable `/code/` path plus the git root — no port, no editable address), so the URL bar (`@rk_url` substrate state — a shared, POSTed content address) is meaningless; reusing `IframeWindow` would drag inapplicable chrome and substrate semantics into a surface whose content address nobody edits. The relative-path discipline (`toProxySrc`'s convention — never compose an absolute origin) is the one piece reused.
**Rejected**: `IframeWindow` with a hidden URL bar (dead chrome, plus `@rk_url` semantics that do not apply to a derived URL).
*Introduced by*: 260811-k3vp-right-panel-code-lens; stable `/code/` src: 260811-a2bo-daemon-code-server-stable-route

### Chord-reclaim via a capture-phase iframe `contentDocument` listener
**Decision**: `CodeSurface` attaches a capture-phase `keydown` listener to the same-origin iframe's `contentDocument` after every load (re-attached on each navigation, removed on cleanup, `contentDocument` access try/catch-guarded), reclaims exactly the events matching an injected `shouldReclaimChord` predicate (built in `app.tsx` over the registry's pure `hasReclaimableMatch`, which carves out keydowns whose only matches are `ttyOnly` bindings), and re-dispatches a synthetic bubbling `KeyboardEvent` on the parent DOCUMENT.
**Why**: the `/proxy/` embed is same-origin by design, so a focused iframe's key events are reachable before the embedded app's keybinding service sees them; dispatching on the parent document reaches both document-level listeners (the palette's chord) and window-level ones (the keybinding dispatcher, the ⌘. view cycle) in one event. Injecting the predicate keeps the component free of the registry import graph, and reclaiming only REGISTRY chords leaves the embedded app's own Ctrl/⌘ bindings working.
**Rejected**: dispatching on `window` (misses document-level listeners); reclaiming every chord (breaks VS Code's own bindings); shipping without reclaim (click-out-only escape leaves ⌘K dead whenever the editor has focus).
*Introduced by*: 260811-k3vp-right-panel-code-lens

### `⌘J` toggles the code surface's tile; `` ⌃` `` hops tty↔code focus
**Decision**: the `code-toggle` chord handler is `togglePanel("code")` — add the code tile, or close it when already open (through `addSurface`/`closeSurface` → `applyLayout`) — gated on a desktop window route with the code surface available; the code surface's `Layout: Add/Close Code` palette entry carries the chord's hint (the `toggleTarget: "code"` / `toggleShortcut` seam) so it stays discoverable. The sibling `focus-hop` chord hops focus between the tty and code tiles through the `Layout: Focus <Surface>` focus-by-kind seam, opening a closed-but-available code tile first (open-then-focus — VS Code's ⌃`-opens-the-hidden-panel analog).
**Why**: the code surface is the secondary panel, so it earns the dedicated VS Code keycaps (⌘J panel, ⌃` focus hop); a generic first-non-tty toggle spent the chord on a surface picker and left the actual secondary panel chordless. The dedicated pair keeps one deterministic target per chord across capability sets.
**Rejected**: one chord per surface (chord-space cost, no muscle-memory win); a generic first-non-tty toggle (no stable target across capability sets, and no chord for the hop); no-op when the code tile is closed (deads the hop in the shipped `single:tty` default layout — VS Code's ⌃` opens the hidden panel, so the borrowed gesture includes the open half).
*Introduced by*: 260811-k3vp-right-panel-code-lens; retargeted to tiles: 260812-ab5v-surface-layout-core; dedicated `code-toggle`/`focus-hop` pair: 260816-sm66-vscode-shortcut-realignment

### Surface toggles are one ordered-registry group in the top bar
**Decision**: The open-tile toggles live in the top bar's right cluster as the single `surface-toggles` ordered-registry entry (`menuGroup: "tiles"`, terminal-route only) — a bordered sub-group with a divider, left of the remaining terminal chips, registered at the head so it is the first fit candidate to drop into the overflow menu; the menu's Tiles section mirrors the group as one `menuitemcheckbox` row per shown surface. Click routing runs through the caller's `togglePanel` semantics unchanged.
**Why**: A dedicated side column forks the stage grid template for one route's worth of four small buttons; as a registry entry the toggles inherit the top bar's probe/fit/overflow machinery for free, and the Tiles section keeps every toggle reachable at narrow widths. Grouping them as ONE entry (not four independent chips) preserves their internal order and divider treatment through the fit pipeline.
**Rejected**: A dedicated collapsible rail column in the stage grid (a whole grid track, a persisted collapse pref, and a top-bar toggle chip to serve four small buttons); `menuOnly` toggles (the primary add/close affordance hidden behind the overflow menu at every width).
*Introduced by*: 260815-19me-composed-frame-unification

### Chat is a tileable surface kind
**Decision**: The layout's tileable set is `tty | web | chat | code` (`SurfaceKind = ViewName`) — chat tiles mount `ChatView` like any other surface.
**Why**: `chat` is a shipped lens in the `window-view.ts` registry; excluding it would leave the palette's `View: Chat` action able to reach a surface the layout cannot tile, breaking the R12 shim (lens switches set `single:<view>` through the same mutation path).
**Rejected**: tty/web/code only (the intake's shorthand) — would regress chat users.
*Introduced by*: 260812-ab5v-surface-layout-core

### Two-tile growth and the legacy shim both map to `split-h`
**Decision**: `?view=X&panel=Y` translates to `split-h:X,Y` (X in slot A); growth appends 1→2 as `split-h` and 2→3 as `main-left` (close collapses 3→2 `split-h`, 2→1 `single`, slot A kept).
**Why**: `split-h` is the visual continuation of the shipped main+panel split, so legacy deep links and stored prefs land on the arrangement their authors saw; `main-left` keeps the incumbent slot-A tile dominant on growth.
**Rejected**: mapping 2-tile to `main-left` — no third tile justifies the asymmetric shape.
*Introduced by*: 260812-ab5v-surface-layout-core

### Layout helpers live in a new pure module; the panel module is minimally consolidated
**Decision**: `lib/surface-layout.ts` owns parse/serialize, the resolution ladder, the legacy shim, and the mutation helpers as a pure DOM-free module with colocated tests; `lib/right-panel.ts` keeps the ratio clamps and the shared registry (gaining `tty`, first) rather than being rewritten.
**Why**: mirrors the shipped `window-view.ts` pure-helper pattern (unit-testable, drift-free single source) and minimizes churn in shipped, tested code; one registry (`SurfaceName = SurfaceKind`) keeps the toggles, the layout, and the palette availability from drifting.
**Rejected**: rewriting `right-panel.ts` wholesale into the new module — bigger diff, no behavioral gain this phase.
*Introduced by*: 260812-ab5v-surface-layout-core

### Layout verbs are palette-reachable; the shape cycle is the one direct chord
**Decision**: ⛶ zoom / ◧ promote / ⇄ swap / ✕ close ship as boxed, rest-visible tile-header buttons + `Layout:` palette entries with NO direct keybindings; the one direct-bound layout chord is `layout-cycle` ⌘; (next same-arity preset, order kept). Further per-verb direct bindings remain open to a later phase if palette latency proves irritating.
**Why**: a small chord set plus palette rows covers keyboard-first (Constitution V — every action is keyboard-reachable) with far less chord-surface to defend against collisions and to learn; the cycle chord earns its binding because it is the tmux `next-layout` muscle memory. Zoom stays chordless because `` Ctrl+` `` — its only muscle-memory candidate — is the `focus-hop` keycap (and collides with code-server's own integrated-terminal toggle inside the code tile).
**Rejected**: direct-binding all four verb families (the spec's original § Verbs text — per-verb + directional-swap chords) — a large chord-surface commitment before the verbs have proven their usage frequency.

### Focused slot owned by SurfaceLayout, kind mirrored to app.tsx
**Decision**: The focused **slot** index is `SurfaceLayout` component state; `app.tsx` receives only the focused **kind** via `onFocusedKindChange` and triggers focus via a registered ref (`focusTileRef`, the `zoomToggleRef` pattern).
**Why**: Per-window reset comes free from the existing `${server}:${windowId}` key (the same reason zoom lives there); the `ttyOnly` gate and the palette only need the kind; duplicate-tty highlight needs the slot, which only the component knows.
**Rejected**: Lifting the slot into `app.tsx` — it would need manual reset on window switches and layout mutations, re-deriving what the component key already guarantees.

**Why**: "Scope is descriptive; handler presence gates" is the established dispatcher contract — a match with no handler falls through without `preventDefault` for free, so the chord reaches the focused surface (e.g. code-server's own ⌘D).

### Derivation seeds the code folder once; only the editor moves it
**Decision**: The code surface's folder is a per-window localStorage latch (`runkit-code-folder:{server}:{windowId}`). The backend's live `gitRoot` derivation seeds it exactly once — at the code surface's first actual render for that window — and the only writer afterward is the editor's own navigation, reported back from the iframe's `load` event. The terminal never moves the editor.
**Why**: `gitRoot` follows the ACTIVE pane's cwd and agents `cd` constantly, so a live folder makes the terminal's movement move the editor: a pane leaving every repo unmounts the tile, and two panes in two repos swap the workbench between them — either way the editor's in-flight state (open tabs, dirty buffers, undo stacks) is expensive or impossible to recover. That defeats hide-never-unmount (P3), which exists precisely so the iframes keep their in-memory state. A latch makes the folder the viewer's choice rather than the terminal's, and localStorage matches code-server's own per-browser tabs/layout state.
**Rejected**: Stabilizing the backend derivation (first-pane-with-a-root wins) — still moves the editor whenever panes `cd`, so it is a mitigation, not a guarantee; re-deriving on tile close/reopen (latch only while open) — reopening after a `cd` is exactly when the editor must come back where it was; a tmux window option (`@rk_code_folder`) for cross-viewer sharing — deferred, not rejected on merit; liveness probing a stale latch — code-server's own "folder does not exist" state plus File > Open Folder is the escape.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### Effective-window substitution over signature widening
**Decision**: Compute the latch once at the `app.tsx` seam and substitute `gitRoot: latch ?? live` into an effective `ViewWindow` (`withLatchedCodeFolder`) passed to all availability/render consumers.
**Why**: One substitution point makes `hasCode`, `availableTiles`, `degradeLayout`, the tile guard, `tileMeta`, and `codeServerSrc` all follow the latch with zero changes to the pure modules — they stay DOM-free and their existing tests stay valid. The seam is also where the storage identity (server, window id) already lives, and the helper is exported so the substitution is unit-testable without rendering the shell.
**Rejected**: Widening `ViewWindow` with a separate `latchedCodeFolder` field or threading a parallel parameter through `hasCode`/`availableViews`/`resolveLayout`/`availableSurfaces` — more touched signatures, drift risk between consumers, no behavioral gain.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### Iframe src fixed per mount generation
**Decision**: `CodeSurface` computes its iframe `src` once per iframe mount generation — a ref keyed to the `reachable` gate that mounts the iframe — not reactively from the folder prop.
**Why**: P3 (hide, never unmount): React re-rendering a changed `src` attribute re-navigates a live frame, even to a URL the frame is already at, which would reload the editor on the very latch update the follow rule just wrote. Keying the computation to mount generation means a reachability `false→true` flip or a window-switch remount picks up the CURRENT latch (fresh workbench, correct folder) while a mounted frame is never parent-navigated. A ref rather than `useMemo` because a memo cache is a documented performance hint React may discard, and a dropped cache here would re-navigate the live frame — the exact hazard the decision prevents.
**Rejected**: A `src` state set only at first render — goes stale across reachability flips (a remounting iframe would boot into the seed-time folder instead of where the editor last was).
*Introduced by*: 260813-if5d-latch-code-surface-folder

### The latch is read at render, never mirrored through an effect
**Decision**: `app.tsx` reads the code-folder latch during render (a `useMemo` over server + window id + a write-epoch counter, beside the `storedLayout` read that does the same), never mirroring it into state through an effect.
**Why**: an effect lands a frame late, so a window switch would render the PREVIOUS window's latch once — and a code iframe mounting in that frame would fix its `src` for its whole mount generation (§ Iframe src fixed per mount generation), stranding the editor at the previous window's folder.
**Rejected**: an effect that syncs the latch into component state — one stale frame is enough to fix a live iframe's `src` at the wrong folder.
*Introduced by*: 260813-if5d-latch-code-surface-folder

### The waiting-badge click advances, never restarts
**Decision**: `handleWaitingBadgeClick` resolves its destination through `nextWaitingTarget(ordered, server, windowParam)` (`lib/palette-agent-nav.ts`) — the same helper the `Agent: Next waiting` palette action uses — rather than scanning the session's windows itself.
**Why**: the badge means "the next waiting window", relative to where the viewer already is. Picking the session's FIRST waiting window makes the badge a silent no-op whenever the viewer is already on that window, instead of advancing to the next one.
**Rejected**: a local `windows.find(isWaiting)` scan — re-implements the palette's ordering (drift risk) and dead-ends on the first waiting window.
*Introduced by*: 260717-vhvz

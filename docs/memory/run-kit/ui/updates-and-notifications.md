# run-kit UI — Updates & Notifications

## Notifications (Web Push opt-in)

Browser Web Push lets `rk notify` (and any process on the box) deliver an OS notification that reaches the user **even when the RunKit PWA tab is closed**. The end-to-end backend/delivery model lives in `architecture.md` § Web Push Notifications; this section covers the frontend opt-in surface. (`260615-xd9r`)

**Two surfaces, one hook, no bell.** The opt-in is a Cmd+K palette entry (the keyboard-first path, Constitution §V) plus the settings dialog's **Notifications** preference row (§ Settings Dialog); both read `state` and call the same `enable`/`sendTest` from one `usePushSubscription()`, so they cannot drift. There is **no bell chip in the top bar** — notifications are an app-global preference and live in the settings dialog (§ Chrome (Top Bar) → Right cluster; § Design Decisions → App-global actions live in the top bar). The palette label reflects subscription state and is **terminal-themed text**, never a bell icon:

| Palette label | When | Action |
|---------------|------|--------|
| `Notifications: Enable push` | Not yet subscribed | Runs the enable flow: `Notification.requestPermission()` → on `granted`, `getVapidPublicKey()` (`GET /api/push/vapid-public-key`) → `registration.pushManager.subscribe({userVisibleOnly: true, applicationServerKey})` → `subscribePush(sub)` (`POST /api/push/subscribe`) |
| `Notifications: Enabled ✓` | Already subscribed | Reflects state; the `✓` is a Unicode checkmark (terminal-themed glyph, not a bell) |

**Wiring**: `usePushSubscription()` (`app/frontend/src/hooks/use-push-subscription.ts`) returns `{ state, enable, sendTest, actions }` — the first three feed the settings-dialog row directly, and `actions` is the `pushActions: PaletteAction[]` block built from the same handlers; it is threaded into `app.tsx`'s `paletteActions` useMemo (spread just before `windowSwitchActions` — see § Boards Command Palette for the composition). The flow logic is the self-contained `app/frontend/src/lib/push.ts` module (`registerServiceWorker()`, `enablePushSubscription()`, `getPushState()`) plus the `getVapidPublicKey()`/`subscribePush()` client functions in `api/client.ts` — a separate module rather than inlining into the 1600-line, SSE-coupled `app.tsx`. The service worker (`public/sw.js`) is registered on app load from `main.tsx`.

**Fail-silent / secure-context**: every path is throw-free. `registerServiceWorker()` is guarded by `'serviceWorker' in navigator` and no-ops on unsupported / insecure-context environments. The enable flow aborts silently (a toast is acceptable) when permission is denied or push is unsupported / the context is insecure, sending no subscription. Web Push (service worker + `PushManager`) requires a **secure context — HTTPS or `localhost`**; the user typically hits run-kit on `localhost:3000` or behind a TLS proxy (both secure), but raw-IP plaintext access simply cannot subscribe (silently).

## Update Notification

Notifies the web-UI user when a newer release of ANY shll-toolkit tool (run-kit, shll, wt, idea, tu, hop, fab-kit) crosses its per-tool notify threshold, and offers a one-click upgrade that runs a SCOPED `shll update <matched…>` (fallback `rk update` self when shll is absent) in a managed `rk-jobs` job window — brew-upgrading the matched tools and restarting the daemon when run-kit is among them — with a `watch`-target affordance that jumps the user to the live job window (§ Top-bar L3 UpdateChip → click). **In-app ONLY — explicitly NO Web Push** (user-decided: Web Push is reserved for waiting agents; update notices must not buzz phones). Two surfaces — a top-bar L3 chip + command-palette actions — both self-contained consumers of one context hook, the same shape `usePushSubscription` uses for notifications (no props threaded through `RootTopBar`→`TopBar`). The backend origin (SSE `event: version`/`event: update-available`, `POST /api/update`, `internal/updatecheck`) is in [architecture.md](/run-kit/architecture.md) § SSE Hub / § API Layer; this section is the frontend surface.

**TWO FEEDS light those surfaces**, merged ambient-first inside `useUpdateNotification` (§ Context state → the merged two-feed derivation): the **ambient** feed — the durable, policy-driven, cross-tab SSE `update-available` verdict from the 6h released-manifest checker — and the **manual** feed, a tab-local, non-persisted hold of the latest on-demand ⟳ / palette check result (§ On-demand check commands). The manual feed exists because that check is a deliberate SIDE CHANNEL the daemon never caches (the github source carries no notify policy, and caching its verdict would wipe a legit released-manifest chip and starve the scoped `shll update` argv — `Snapshot().Matched`), so its finding has no server-side home: without the frontend hold, a check that reports "3 tools updatable" evaporates with its ~5s toast while the persistent surfaces stay dark. (`260807-s6zs`)

### Context state + `useUpdateNotification()` hook

`SessionContext` (`contexts/session-context.tsx`) owns the update state (it already owns the server-global SSE pool + `?metrics=1` stream, and `version`/`update-available` are server-global like `server-order`/`board-order`, so this reuses the exact fan-out — no second context). It exposes:

- `daemonVersion: string | null` — the running daemon version from `event: version` (no leading `v`), `null` until first seen.
- `updateAvailable: UpdateAvailable | null` — the current toolkit-update verdict from `event: update-available`, `null` when none. `UpdateAvailable = { tools: UpdateTool[], key: string, current: string, latest: string }` where `UpdateTool = { tool, current, latest, updateAvailable?, notable? }`: `tools` is the **FULL per-tool verdict list** — every tool with a pending update INCLUDING sub-threshold rows, each carrying the optional `updateAvailable?: boolean` (installed < latest) and `notable?: boolean` (crosses the notify threshold) flags parsed from the extended SSE payload; a MISSING flag is treated as `true` (an old-daemon payload listed only matched tools, so all its rows count as notable). Chip/palette consumers read the NOTABLE subset via `useUpdateNotification`'s filter. `key` = the composite dismissal key (sorted `tool@latest` pairs over the NOTABLE set, comma-joined); `current`/`latest` = the legacy run-kit-row fields, populated only when run-kit is in the notable set (transitional not-yet-reloaded-frontend compat).
- `manualCheck: ManualCheckResult | null` — the latest MANUAL check result held for this tab, `null` when none. `ManualCheckResult = { tools: UpdateTool[], source: string }`: `tools` is the **updatable subset** the check reported (reusing the context's own `UpdateTool` row type — `api/client.ts`'s `UpdateCheckTool` is structurally compatible), `source` the echoed report backend (`"released"`/`"github"`). Plain `useState` — **deliberately NOT persisted** to localStorage or anywhere else (§ Design Decisions → The manual check feed is tab-local). (`260807-s6zs`)
- `applyManualCheckResult(tools, source): void` — the setter `useUpdateCheck` calls after a check resolves (naming mirrors `applyVersion`/`applyUpdateAvailable`/`applyHostMetrics`). An **EMPTY `tools` array CLEARS** the held result — a fresh verdict supersedes a stale one, so a clean re-check must never leave a chip lit that the toast just contradicted. Referentially stable (`useCallback` with an empty dep list): it reads the current ambient key through a render-mirrored `ambientKeyRef` rather than taking `updateAvailable` as a dependency, because `use-update-check.ts` memoizes `runUpdateCheck` on it and `use-global-palette-actions.ts` memoizes the check-action array on THAT — an identity that churned with ambient state would churn the palette's global check group. (`260807-s6zs`)
- **Ambient-key-change clearing** — a `manualAmbientKeyRef` stamps the ambient composite key observed at manual-store time (`undefined` when nothing is held), and an effect keyed on `[ambientKey, manualCheck]` clears `manualCheck` when the current ambient key differs from that baseline — the update-consumed signal (including the cleared empty key, which surfaces as `null`). Baselining at store time rather than watching `updateAvailable.key` raw is load-bearing (§ Design Decisions → Ambient-key-change clearing baselines at store time). A daemon restart instead discards the state via the post-restart tab reload (§ Reload guard). (`260807-s6zs`)
- `updateDismissedKey: string | null` — the composite-key dismissal from localStorage `runkit-update-dismissed` (const `UPDATE_DISMISSED_KEY`), lazily read in a try/catch on mount. It is a **single slot serving BOTH feeds** — compared against whichever key is effectively displayed.
- `updateNow(): Promise<UpdateTriggerResult>` — thin wrapper over the `triggerUpdate()` client helper (`POST /api/update`; rejects on non-2xx). The resolved `UpdateTriggerResult` (`{status, watch?: UpdateWatchTarget}`) carries the job-window `watch` target the click handler turns into navigation (§ Top-bar L3 UpdateChip → click).
- `dismissUpdate(): void` — writes the **EFFECTIVE displayed key** to localStorage `runkit-update-dismissed` + sets `updateDismissedKey`; a no-op on an empty key. It re-derives the same ambient-first merge the display uses (calling the shared `deriveUpdateFeed` over the notable ambient set and the manual set, with `computeUpdateKey` for the manual side), so it writes the ambient key when the ambient feed is lit and the client-composed manual key when the manual feed is — which is what makes the chip `✕` and the palette `run-kit: Dismiss Update Notice` entry work unchanged against a manual-fed chip, with the same re-show semantics (a later manual check finding a different tool set composes a different key). **Known cross-feed interaction**: with one dismissal slot for two feeds, dismissing a manual-fed chip overwrites an already-dismissed ambient key and re-lights the ambient chip (accepted — a single slot is the pre-existing contract; no second key was added, per the no-new-localStorage-keys constraint). (`260807-s6zs`)
- **`brew: boolean`** — whether the daemon is a Homebrew install, from the `event: version` `brew` field. Tracked in React `useState` (`isBrew`, drives palette visibility → must re-render, unlike the reload-decision refs below), **default `false` until the first version event is observed** (so the brew-gated `run-kit: Update Now` palette entry stays hidden on the brief pre-connect window; mirrors the `qualifies` absent-data-hidden gating). Set inside `applyVersion`.
- **`forceUpdateNow(): Promise<UpdateTriggerResult>`** — thin wrapper over `triggerForceUpdate()` (`POST /api/update` body `{"force":true}`; rejects on non-2xx). Same shape as `updateNow`.
- **`restartNow(): Promise<UpdateTriggerResult>`** — thin wrapper over `triggerRestart()` (`POST /api/restart`; rejects on non-2xx).

The `version`/`update-available` listeners are added on **BOTH** stream kinds — the per-server pool AND the dedicated `?metrics=1` subscription — server-global, applied idempotently (no `data.server` filter), exactly like `server-order`/`board-order`. Both call the pure-ish `applyVersion` / `applyUpdateAvailable` callbacks; malformed events are skipped. **`applyVersion(version, boot, brew)`** parses the payload as `{ version?, boot?, brew? }` **tolerantly** — `boot` passed only when `typeof data.boot === "string"` (else `null`), `brew` as `data.brew === true` (defaults `false`) — so an older daemon's boot-less/brew-less payload never breaks parsing or flips brew true. The `update-available` parse maps each `tools[]` row's optional `updateAvailable`/`notable` booleans onto `UpdateTool` — carried ONLY when the daemon sends real booleans (an old daemon's flag-less payload leaves them `undefined`, which consumers treat as `true`). **`applyUpdateAvailable(next)`** stores `next` but **dedups by composite `key`** (a re-delivery of the same matched set does not churn consumers) — AND handles a **CLEARED payload** (empty `key`) by clearing the stored state so the chip hides. It MUST NOT early-return on an empty key: a siblings-only `shll update` never restarts the daemon, so the post-remediation re-check's cleared `update-available` is the ONLY signal that clears the consumed match; an early return would leave a consumed match advertised forever.

**Tolerant `useUpdateNotification()` hook** (exported from `session-context.tsx`) — reads the context via `useContext(SessionContext)` DIRECTLY (not `useSessionContext`, so it **never throws outside the provider**; every field falls back — `updateNow`/`forceUpdateNow`/`restartNow` → `() => Promise.resolve({ status: "" })`, `dismissUpdate` → `() => {}`, `brew` → `false`, `manualCheck` → `null`, so the manual fields degrade to the no-manual-feed defaults). It returns the DERIVED display shape the chip + palette consume, so the gating logic — and THE two-feed merge — lives in one place:

- `isDev = daemonVersion === DEV_VERSION` (`"dev"`).
- `ambientTools` = the **NOTABLE subset** of `updateAvailable?.tools`, computed in a `useMemo`: `all.filter((t) => t.notable !== false)` (a missing/undefined flag counts as notable — old-daemon compat), returning `all` unchanged (stable referential identity) when nothing filters out so a no-op filter never mints a fresh array. The payload's `tools` is the FULL verdict list (incl. sub-threshold rows the incl.-patches check surfaces), but the ambient chip/dismissal machinery reads only this notable subset — so the AMBIENT feed stays policy-driven (a patch-only ambient finding never lights the chip). The empty base is a **module-level frozen `EMPTY_TOOLS` constant** (`Object.freeze([])` cast through `unknown` to the mutable `UpdateTool[]` contract — frozen at runtime for a real no-mutation guarantee, typed mutable so the cast doesn't ripple through `updateChipToolSummary`/`buildUpdateActions` consumers) so `?? EMPTY_TOOLS` never mints a new array per render (a fresh `[]` would break referential memoization downstream).
- `ambientKey = updateAvailable?.key ?? null` — the server-computed composite key.
- `manualTools = manualCheck?.tools ?? EMPTY_TOOLS` (same frozen fallback, same referential-stability reason) and `manualKey` = `computeUpdateKey(manualTools)` in a `useMemo` over `manualTools`, `null` for an empty set — the manual feed has **no server-computed key**, so its key is composed client-side (§ Manual composite key).
- **The merge — `deriveUpdateFeed(ambientTools, ambientKey, manualTools, manualKey, isDev, dismissedKey): { tools, key, manualOnly }`** — a pure exported function, called once here and once by `dismissUpdate`, so the precedence rule exists in **exactly one place** and no surface can drift. **Ambient-first**: `ambientShows = !isDev && ambientTools.length > 0 && ambientKey !== dismissedKey`; when `ambientShows || manualTools.length === 0` it returns the ambient shape with `manualOnly: false` — so with no manual result held, or with the ambient chip live, every field is purely ambient-derived (the frozen `EMPTY_TOOLS` identity included) and the manual feed is inert. Only when the ambient feed does NOT show and a manual result holds tools does it return `{ tools: manualTools, key: manualKey, manualOnly: true }`. (`260807-s6zs`)
- `singleRunKit = tools.length === 1 && tools[0].tool === "run-kit"` (`RUN_KIT_TOOL`) — the one shape that keeps the historical single-version chip/palette wording. Computed over the EFFECTIVE `tools`, so a manual-fed single run-kit row gets the same `⬆ v{latest}` chip form as an ambient one.
- `latest = singleRunKit ? tools[0].latest : null` / `current = singleRunKit ? tools[0].current : null` — the run-kit-row versions, surfaced ONLY for the single-run-kit `⬆ v{latest}` chip label + its transition title. Null otherwise (a multi/non-run-kit chip uses the count form + per-tool detail). The palette carries no version-bearing entry — `run-kit: Update Now` is a static label.
- **`qualifies = !isDev && tools.length > 0`** — computed over the effective feed. The frontend trusts the server's `update-available` verdict for the per-tool threshold decision (the backend already applied it); it only additionally suppresses the `dev` daemon and requires a non-empty set. It does NOT re-run any semver compare. The `dev` sentinel suppresses a manual-fed chip exactly as it suppresses an ambient one.
- **`showChip = qualifies && key !== updateDismissedKey`** — the composite-key dismissal gate, over the effective `key`. A later verdict with a DIFFERENT key re-shows the chip: on the ambient side because the changed key re-broadcasts `update-available`, on the manual side because a check finding a different tool set composes a different `computeUpdateKey`.
- **`manualOnly: boolean`** — true exactly when the surfaced fields came from the manual feed (false when the ambient feed shows, and false when neither does). The feed indicator `use-update-click` branches on for click routing, so no consumer re-derives the merge. (`260807-s6zs`)
- Returns `{ qualifies, showChip, tools, key, manualOnly, singleRunKit, latest, current, updateNow, dismissUpdate, daemonVersion, brew, forceUpdateNow, restartNow }`. `daemonVersion` is surfaced raw because `buildMaintenanceActions` does its own `version === "dev"` gate.

**Manual composite key — `computeUpdateKey(tools)` (`lib/palette-update.ts`)**: a pure exported helper composing **sorted `tool@latest` pairs, comma-joined** (`""` for an empty set) — a verbatim client-side mirror of the backend's `computeKey` (`app/backend/internal/updatecheck/updatecheck.go`), which composes the `key` the ambient payload carries. It lives beside `updateChipToolSummary` in the context-free pure-helper module for this surface (colocated `palette-update.test.ts`), not inline in `session-context.tsx`, so the sort/join semantics are testable without mounting the provider. Composing the manual key in the backend's exact shape is what lets the ONE `runkit-update-dismissed` slot serve both feeds unchanged. (`260807-s6zs`)

### Reload guard — `shouldReloadOnVersion` (post-restart auto-reload, boot-aware)

After a one-click upgrade the daemon restarts, which drops the state socket; the reconnect replays a **different** `version` global event (a set-once cached slot delivered once after `hello` over `/ws/state` — see `architecture.md` § State Socket), and the open tab is stale (it embeds the old frontend assets baked into the old binary). The guard auto-reloads it exactly once. The `StateSocket`'s resubscribe-on-reconnect replays the global slots, so the `version` listener fires on every reconnect. The guard also fires on a same-version restart (a plain `POST /api/restart`, a config-change/wedge-recovery restart, or a restart initiated from SSH) via the per-process `boot` id — so a tab that reconnects to a **new process at the same version** is not left silently running stale in-memory state: (`260714-3law`, `260716-qf3j`)

- The pure exported predicate is **4-arg**: `shouldReloadOnVersion(firstVersion: string | null, firstBoot: string | null, nextVersion: string, nextBoot: string | null): boolean`. Logic, in order: (1) `firstVersion === null` → `false` (**never reload on first connect** — no reload loop); (2) `nextVersion !== firstVersion` → `true` (a version change means new assets); (3) **same version** → reload on a **boot change** UNLESS the version is `"dev"`: `nextVersion === DEV_VERSION` returns `false` (the **air-recompile storm guard** — under `just dev`, air recompiles the backend on every save, minting a fresh boot id each time; reloading every dev tab on every recompile would be a reload storm), else `nextBoot !== null && nextBoot !== firstBoot`. A **null `nextBoot`** (older daemon, mixed-version window) never triggers the boot branch. (`260713-4zap`, `260714-3law`)
- `applyVersion(version, boot, brew)` (the `version`-listener callback): sets `daemonVersion` + `isBrew`; if `shouldReloadOnVersion(firstVersionRef.current, firstBootRef.current, version, boot)` → `location.reload()` (and returns); else, **only on the first-ever version** (`firstVersionRef.current === null`), stamps BOTH `firstVersionRef.current = version` and `firstBootRef.current = boot`. Both `firstVersionRef` and `firstBootRef` (new in `3law`) are `useRef` (not state — the reload decision must not re-render) so `applyVersion` stays referentially stable.
- Coverage this buys: update (version change), plain restart (boot change, same version), every open tab (the version slot is replayed per SSE connect), and restarts initiated from SSH or crash-recovery (the signal is server-originated, not client-action-originated).

### Top-bar L3 UpdateChip (`UpdateChip` in `top-bar.tsx`)

A self-contained chip **leading the L3 right cluster** (the L3 order is UpdateChip → Refresh, with the exempt overflow chevron right-most). Reads `useUpdateNotification()`. It is a registry candidate: its bar/menu presence is 100% registry-driven (registry `hidden: !showChip` keeps it out of the candidate set when it wouldn't render, so it never reserves width or an empty slot). Below `sm` it does not vanish; under width pressure it overflows into the chevron menu, where its function merges into the fixed version row (§ Right cluster overflow / § Steady-state version surfaces → surface 5). The palette update surface provides keyboard-first parity; the menu also reaches the update surface on phones. (`260715-h1ck`) The chip IS the **promoted/single-action form** of the unified update button whose resting form is the overflow menu's version + ⟳ row; the split is verdict-derived — the chip renders in-bar when `showChip` and bar space allow, otherwise the update surface appears on the version row. It stays single-action (no ⟳ segment): checking is a resting-row affordance only, never on the promoted chip (`260720-ml7k`).

- **Hide gate**: `if (!showChip || tools.length === 0) return null` — the hide conditions (no qualifying update / dismissed-for-key / daemon is `dev`) are folded into `showChip` inside the hook.
- **Single/multi presentation** (R15): the visible label is `⬆ v{latest}` when the single matched tool is run-kit (`singleRunKit`), else a count form `⬆ updates (N)` for any other single tool OR multiple tools. The chip runs a SCOPED update of exactly the matched tools, so the `title`/`aria-label` must say WHICH tools move: `restLabel = singleRunKit && current ? `Update run-kit: v{current} → v{latest}` : `Update: ${updateChipToolSummary(tools)}``, where `updateChipToolSummary` composes the per-tool `tool v{a} → v{b}` transitions (a tool with no known current degrades to `tool → v{latest}`). Accent styling (`border-accent-green text-accent-green` + `rk-glint` CRT-glint hover — the button hover vocabulary, § Hover-Animation Vocabulary).
- **Click → one-click trigger** via the shared **`useUpdateClick()`** hook (`hooks/use-update-click.ts`), consumed by BOTH the chip and the overflow-menu version-row update surface so the updating-state + failure catch/toast is ONE implementation, never a mirrored copy. `triggerUpdate` early-returns if already `updating`, records the composite `key` at click time (`clickKeyRef`), sets `updating`, then `void run().then((result) => consumeUpdateWatchTarget(result, navigate, addToast)).catch(...)`. **The resolved result drives a watch affordance** (`consumeUpdateWatchTarget`, exported from the same file and shared with the palette's restart wrapper, `260812-z1ya-update-daemon-tmux-window`): `status: "already-running"` with a `watch` target → navigate STRAIGHT to the job window's terminal route `/$server/$window` (window param = the `@N` id verbatim — the route's `parse`/`stringify` already maps it; the second click IS the jump); a fresh spawn (`202`, `watch` present) → an info toast `<session>:<window> is running` whose **"Watch" action slot** navigates to the same route (auto-navigating on every click would be disruptive); `watch` absent (old daemon) → no-op (no toast action, no navigation). **The click routes by feed**: `run = manualOnly ? forceUpdateNow : updateNow` — a surface lit from the MANUAL feed fires the full-roster force update (`POST /api/update {"force":true}`), exactly what the check toast's own "Update Now" action slot already runs; the ambient feed keeps the SCOPED `updateNow()` path unchanged. The scoped path exists to move only the server's `Snapshot().Matched` set, which a side-channel manual verdict never populates — a scoped click on a manual-fed chip would find nothing to do (§ Design Decisions → Manual-fed clicks force). On a request FAILURE (409 daemon-down / not-brew / no-match / network) it clears `updating` + shows an error toast — unchanged in shape on both paths. (`260807-s6zs`) The busy state renders a `<LogoSpinner size={12}>` + `<span>{"updating…"}</span>` — the busy label is a JS string expression (a real `…` U+2026), NOT raw JSX text (JSX text does not process JS escape sequences, so a raw `…` would render six literal chars; `update-chip.test.tsx` asserts the exact visible text `updating…`).
- **Two `updating`-clearing paths** (R13): (1) run-kit IN the spawned scope → the daemon restarts, the state socket drops, and the reconnect's differing version reloads the tab (discarding this state); (2) SIBLINGS-ONLY scope → NO daemon restart, so no reload comes — the post-remediation re-check (R17, architecture § internal/updatecheck) broadcasts a cleared/changed `update-available` whose composite `key` differs from the click-time key, and a `useEffect` keyed on `key` clears `updating` when `key !== clickKeyRef.current` (including the cleared empty key). The effect keys on the hook's EFFECTIVE `key`, which for a manual-fed click is the manual composite key; the manual state itself clears on an ambient-key change, which flows through as an effective-key change. A FAILED brew upgrade leaves the key unchanged, so `updating` persists until a page reload / the palette force path — the accepted residual, and a manual-fed **siblings-only sub-threshold** update sits in the same envelope (no daemon restart, and the R17 re-check re-broadcasts an unchanged/empty ambient key, so `updating…` and the manual chip persist until reload; no completion machinery was added for it).
- **Dismiss `✕`**: a small sibling button (rendered only when `!updating`, `aria-label="Dismiss update notice"`) → `dismissUpdate()` (composite-key localStorage). Dismissal silences only the chip; the palette action remains (keyboard-first recoverability, §V).

### Palette parity — `run-kit:` actions via `buildUpdateActions` (`lib/palette-update.ts`)

Keyboard-first parity (§V): the pure helper `buildUpdateActions(qualifies, tools, onDismiss): UpdatePaletteAction[]` (in `lib/palette-update.ts`, unit-testable, mirroring `lib/palette-move.ts`) returns, when `qualifies && tools.length > 0`, the **single** entry:

- `{ id: "run-kit-dismiss-update", label: "run-kit: Dismiss Update Notice", onSelect: onDismiss }` — the keyboard mirror of the chip's `✕`; `onDismiss` writes the composite key.

and an empty array otherwise (signature: `(qualifies, tools, onDismiss)` — no update callback). There is **no version-bearing update entry here** — the update action is `run-kit: Update Now` in `buildMaintenanceActions` (§ Maintenance palette entries), THE single update action (see § Design Decisions → Single static `Update Now`). **Gated on `qualifies` ALONE — the palette deliberately IGNORES chip dismissal** (`qualifies`, NOT the chip's `showChip`): dismissal silences the ambient chip, but the palette is deliberate discovery. The per-tool `updateChipToolSummary` helper (consumed by the chip + overflow-menu aria) is the single exported source in this module, so the top bar and the menu can never drift (R15 / A-024).

**A layout-level global group** (§ Single palette mount + palette-actions slot): `buildUpdateActions` is folded into the global groups built once by `use-global-palette-actions.ts` (the `updateActions` memo over `useUpdateNotification()`'s `qualifies`/`tools`/`dismissUpdate`), so every route — boards and the Host page included — gets the entry from the single palette mount. Below `sm` the top-bar UpdateChip is hidden, so the palette is a phone user's only update surface. (`260714-3law`, `260720-n2ai`)

### On-demand check commands — `buildCheckActions` + `composeCheckToast` + `useUpdateCheck` (`260720-n2ai`; two-backend split `260720-wb3n`)

Two on-demand check commands make "is anything updatable right now?" reachable without waiting on the ambient 6h chip or firing a blind force-update — keyboard-first (§V), reporting via the existing toast system (§ Post-pin success feedback + toast optional action for the toast primitive). The pure builder `buildCheckActions(version, onCheck, onCheckIncludingPatches): UpdatePaletteAction[]` (`lib/palette-update.ts`, unit-tested) returns:

- `{ id: "run-kit-check-updates", label: "run-kit: Check for Updates", onSelect: onCheck }` — reports tools crossing their notify threshold (`notable`).
- `{ id: "run-kit-check-updates-patches", label: "run-kit: Check for Updates (incl. patches)", onSelect: onCheckIncludingPatches }` — reports every tool with any pending update, annotating sub-threshold rows.

Both POST the same `/api/updates/check` endpoint but select **TWO BACKENDS** (`260720-wb3n`): the default check runs shll's `released` manifest source (POST body `{}`), while incl.-patches requests the FRESH `github` release-tags source (`checkForUpdates("github")` → body `{"source":"github"}`) — a SIDE-CHANNEL query the daemon answers without touching the cached verdict/chip. The two commands thus become "two backends", not "same data, two filters": the default can report all-up-to-date while incl.-patches lists updates, purely from the shll.ai manifest's ~1-day lag behind a just-cut release (the github source is the workaround). **Hidden on the `dev` sentinel** (`version === "dev"` → `[]`, same gating pattern as `buildMaintenanceActions`; a `null` version — no version event yet — counts as non-dev). **No brew gate** — checking is harmless without a remediation path (unlike `Update Now`).

**`composeCheckToast(tools, includePatches, source = ""): { message, updatable }`** (pure, unit-tested) composes the result toast over the verdict list: the default view filters `notable`, the incl.-patches view filters `updateAvailable` with sub-threshold rows annotated `(patch — below notify threshold)` (e.g. `tu v0.9.1 → v0.9.2 (patch — below notify threshold)`), reusing `updateChipToolSummary`'s per-tool `tool v{a} → v{b}` shape; an empty filtered set composes `All tools up to date` (`updatable: false`). The `source` argument is the ECHOED report backend from the check response (`"released"`/`"github"`; optional, default `""` for old daemons — keeping today's behavior). **When `source === "github"` the sub-threshold annotation is SUPPRESSED**: that backend carries no notify policy, so every row lands `notable=false`, and a github minor bump (e.g. `run-kit 3.8.7 → 3.9.1`) would otherwise be mislabeled a sub-threshold patch. The `updateAvailable`/`notable` filtering is unchanged — only the annotation keys off the source.

**Shared `useUpdateCheck()` hook** (`hooks/use-update-check.ts`) wires the POST→toast flow ONCE for the palette's global check group AND the overflow-menu resting-row check affordance (the same anti-drift extraction as `use-update-click.ts`, § Design Decisions → Shared check-flow hook): it returns `{ runUpdateCheck, checking }`. `runUpdateCheck(includePatches)` maps `includePatches === true` → `checkForUpdates("github")` (the fresh github source) and the default check → `checkForUpdates()` (released), passing the response's echoed `result.source` into `composeCheckToast` so the sub-threshold annotation keys off what actually ran (`POST /api/updates/check`, tolerant parse, rejects on non-2xx with the server message), then shows ONE result toast (deliberately NO intermediate "checking…" toast — the endpoint responds synchronously ~1-2s). **`checking: boolean`** is the in-flight UI value (drives the overflow menu's ⟳ spinner/disabled form, § Steady-state version surfaces → surface 5). Single-flight is enforced by a **`useRef` flag checked synchronously** at the top of `runUpdateCheck` (early-return when set), with `checking` state purely driving the spinner — so a same-tick double-click can't slip past the not-yet-flushed state, and `runUpdateCheck` keeps a **stable referential identity** across the in-flight transition (`use-global-palette-actions.ts` memoizes the check-action array on it; adding `checking` to its deps would churn that array mid-check). Both the ref and the state clear in a `.finally` on success AND failure.

**The result is ALSO persisted onto the tab-local manual feed** so the finding survives the toast on the persistent update surfaces instead of evaporating after ~5s: in the same `.then`, `runUpdateCheck` calls `applyManualCheckResult(updatableSubset(result.tools, includePatches), result.source)`. The persisted subset is the SAME "updatable" filter `composeCheckToast` reports for that view (`includePatches` ⇒ rows with `updateAvailable`; default ⇒ rows with `updateAvailable && notable`) — a local `updatableSubset` helper mirroring `composeCheckToast`'s `relevant` predicate — so the chip and the toast can never disagree about what was found, and an all-up-to-date result persists an EMPTY set that clears any stale positive. The seam is read via `useContext(SessionContext)` DIRECTLY and called optionally (`applyManualCheckResult?.(…)`), the same provider-tolerant idiom `useUpdateNotification` uses, so the hook never throws in an isolated test mount without a `SessionProvider`. **The toast flow is untouched** — this is in addition to it, never a replacement. (`260807-s6zs`) The result toast:

- an **info** toast with the `composeCheckToast` summary;
- when something updatable was reported AND the daemon can actually update (**`brew && daemonVersion !== "dev"`** — the same gate as the `Update Now` palette entry), the toast's **action slot carries "Update Now"**, triggering the same `forceUpdateNow()` force-update flow (a `.catch` on it surfaces an `"error"` toast);
- on a failed check (502 shll-missing, 409 dev, network) an **error** toast surfaces the server's message — the manual check is fail-LOUD, unlike the fail-silent ambient loop.

The layout-level global builder consumes the hook: `use-global-palette-actions.ts` memoizes `checkActions = buildCheckActions(daemonVersion, () => runUpdateCheck(false), () => runUpdateCheck(true))`, folded into the global groups right after `updateActions`.

### Maintenance palette entries — `buildMaintenanceActions` (`lib/palette-update.ts`)

Two **palette-only** maintenance actions, independent of the qualifying-update gate that governs `buildUpdateActions` — they make **update** and **daemon restart** reachable from the web (remote/mobile over Tailscale, no SSH), per Constitution V (keyboard-first) and IV (no new chrome). There is **no chip, no confirmation dialog, and no dedicated toast** — both fire immediately on select, and the SSE drop followed by the boot/version-driven tab reload IS the success feedback (only a rejection surfaces a toast) — plus the shared watch affordance on the resolved result (`consumeUpdateWatchTarget`, below).

The pure builder `buildMaintenanceActions(brew: boolean, version: string | null, onForceUpdate, onRestart): UpdatePaletteAction[]` (co-located with `buildUpdateActions` in `lib/palette-update.ts`, same test surface) computes `isDev = version === "dev"` and returns:

- `{ id: "run-kit-force-update", label: "run-kit: Update Now", onSelect: onForceUpdate }` — **THE single update action** in the palette: a force update (POST `/api/update` `{"force":true}`, a full-roster `shll update`; idempotent, and it picks up patch-only bumps a scoped match set would skip). Included ONLY when **`brew && !isDev`**. NOT gated on a qualifying update, so it reaches patch releases and works before any check has run. Brew-gated because a non-brew install cannot self-upgrade (the backend brew 409 would reject it anyway).
- `{ id: "run-kit-restart", label: "run-kit: Restart Daemon", onSelect: onRestart }` — included whenever **`!isDev`** (**NO brew requirement** — restart works for any install method).

Neither appears on a `dev` daemon (both gated on `!isDev`). `Update Now` is the ONE update entry in the palette — a static label; version detail lives in the check-result toasts and the chip summary (see § Design Decisions → Single static `Update Now` for why there is no dynamic `Update to v{X}` entry).

**A layout-level global group** (§ Single palette mount + palette-actions slot) — palette-only is load-bearing here: below `sm` the top-bar chip cluster is hidden, and there is no chip surface for these two at all. `use-global-palette-actions.ts` memoizes `maintenanceActions` over `buildMaintenanceActions(brew, daemonVersion, …)` (reading `brew`/`daemonVersion`/`forceUpdateNow`/`restartNow` from `useUpdateNotification()`), folded into the global groups after `checkActions`. Each action wraps `forceUpdateNow`/`restartNow` in `.then((result) => consumeUpdateWatchTarget(result, navigate, addToast))` + a `.catch` toast-on-failure with **`"error"` severity** (messages `"Update failed"` / `"Restart failed"`) — the restart action shares the identical watch affordance with no special-casing (the post-restart reload discards its "Watch" toast harmlessly).

### Steady-state version surfaces

The `UpdateChip` above renders **only when a qualifying update is pending** and names only the TARGET version, so the running version is otherwise **invisible in the web UI** — a user filing a bug report or verifying a restart had to SSH in for `rk --version`. `260715-ifco` adds **four passive, chrome-level surfaces** that expose the *current* `daemonVersion` in steady state (frontend-only — the version already reaches every tab via `event: version`; no backend, no new routes/pages/buttons per Constitution IV, palette-first per V); `260715-h1ck` adds a **fifth**, the overflow menu's fixed version row (surface 5); `260724-6j1v` adds a **sixth**, the sidebar footer's resting version readout (surface 6). All **degrade gracefully on a null `daemonVersion`** (hide/omit, never a `vundefined` placeholder) and show the **`dev` sentinel as-is** (`run-kit dev`, not `vdev`) — pure display, unlike the dev-gated update/restart actions.

**Shared `displayVersion` helper + `lib/palette-version.ts`.** A new pure, dependency-free module `app/frontend/src/lib/palette-version.ts` (mirroring the `lib/palette-update.ts` pattern, colocated `palette-version.test.ts`) exports:

- **`displayVersion(version: string): string`** — the single frontend source of the v-prefix convention, mirroring the backend `displayVersion()` (`app/backend/cmd/rk/root.go:16-21`): prefixes `v` to a numeric version, leaves `dev` and any already-`v`-prefixed string bare (idempotent — never `vdev` / `vv0.6.2`). Reused by all three display surfaces below (avoids the magic-string conditional per-site). Chosen to live in the palette module rather than a standalone `lib/version.ts` — the palette builder already needs it and it is the new dependency-free home.
- **`buildVersionAction(version: string | null, onSelect: () => void): VersionPaletteAction[]`** — returns `[]` when `version` is null (omit, no placeholder), else a single `{ id: "run-kit-version", label: `run-kit: Version — ${displayVersion(version)}`, onSelect }`. The LABEL carries the version, so typing "version" in the palette answers "what am I on?" **without selecting anything**. `VersionPaletteAction` is a local type mirroring `palette-update.ts`'s shape.

**1. Command-palette version entry** (the primary discovery surface, §V). `buildVersionAction` is built once at the layout (`versionActions` in `use-global-palette-actions.ts`, folded into the global groups after `maintenanceActions` — § Single palette mount + palette-actions slot), for the same reach reason as the update actions: below `sm` the top-bar right cluster is hidden, so on a phone the palette is the ONLY version surface.
  - **Gated on non-null `daemonVersion` INCLUDING `dev`** — `buildVersionAction`'s only gate is the null check (pure display; the entry is present for a `dev` daemon).
  - **On select**: copies the **DISPLAYED form** (`v0.6.2` / `dev` — what-you-see-is-what-you-copy, matches the label; NOT the raw `daemonVersion`) via `lib/clipboard.ts` `copyToClipboard`, then toasts `addToast(ok ? "Version copied" : "Copy failed", ok ? "info" : "error")`.

**2. Connection-dot version title** — the sidebar-footer dot's hover Tip folds in `Connected — run-kit {displayVersion(daemonVersion)}`; full mechanics in § Sidebar footer status row.

**3. Host-page footer stamp** (`host-overview-page.tsx`) — a small passive BIOS/boot-style footer line `run-kit {displayVersion(daemonVersion)}` at the **bottom of the scroll container, after the SERVICES `</section>`** (out of the zone hierarchy — a POST-footer, on-brand with the CRT/terminal aesthetic). `text-xs text-text-secondary font-mono`, no border, no interaction, **no hover treatment** (passive means passive — the hover-animation vocabulary categories don't apply to inert text). Reads `daemonVersion` from `useSessionContext()` and renders **nothing when null** (`{daemonVersion && (…)}`, absence not a hidden placeholder). The Host page `/` is the only route with no top-bar version surface on phones, and its BIOS-footer aesthetic fits the stamp best.

**5. Overflow menu's fixed version row** (`260715-h1ck`, `top-bar-overflow-menu.tsx`) — the top-bar overflow chevron's menu **always** contains a fixed version row as its last item (so the chevron renders even when nothing overflows; full mechanics in § Right cluster → overflow chevron menu). Placement between this row and the in-bar `UpdateChip` (surface 4) is ALWAYS derivation — from `showChip` + overflow measurement — never imperatively moved (§ Design Decisions → Dismissed-pending shows the menu update surface).

## Design Decisions

### Single static `Update Now` — no dynamic version label
**Decision**: the palette has ONE update action, the static `run-kit: Update Now` (a full-roster force update in `buildMaintenanceActions`); the former qualifying-gated `run-kit: Update to v{X}` entry and its `updateActionLabel` label composition (the single-run-kit / single-sibling / N-tools label shapes) are deleted.
**Why**: the dynamic label was multi-tool ambiguous (the update is toolkit-scoped, not single-tool) and went stale between check passes. A static label always reads true; version detail lives where it is fresh — the check-result toasts (`composeCheckToast`) and the chip's `updateChipToolSummary`. `Update Now` reaching every tool (force = full-roster `shll update`) also picks up patch-only bumps a scoped match set would skip.
**Rejected**: keeping the dynamic `Update to v{X}` label (ambiguous + stale); a 2×2 check×update / minor×patch command matrix (the update axis has only one real action — brew installs the manifest latest regardless; the minor/patch distinction exists only on the check axis).
*Introduced by*: 260720-n2ai-shll-check-updates-delegation-palette-checks

### Notable-set is the single convergence key; sub-threshold verdicts ride alongside
**Decision**: the chip visibility, the composite dismissal `Key`, and the `/api/update` argv stay derived from the NOTABLE set only; the full per-tool verdict list (incl. sub-threshold `notable:false` rows) rides the `update-available` payload but never affects Key/qualification. `useUpdateNotification` filters `tools` to the notable subset (missing flag = notable) with stable referential identity.
**Why**: keeps the chip, dismissal semantics, `use-update-click` completion signal, and `/api/update` argv byte-compatible with the pre-delegation behavior — a patch-only finding is toast-only by design (it must never light or re-dirty the chip). The ambient/released payload still carries the full per-tool verdict list so a released incl.-patches view reads sub-threshold rows off one payload; the incl.-patches command itself queries the fresh github source as a side channel (`260720-wb3n`) that likewise never dirties the chip.
**Rejected**: keying the chip/dismissal on the full `update_available` set (would light + re-dirty the chip on patch bumps and churn dismissals).
*Introduced by*: 260720-n2ai-shll-check-updates-delegation-palette-checks

### Shared check-flow hook instead of per-consumer duplication
**Decision**: the on-demand check POST→toast flow (result composition, gated Update Now action slot, error mapping) lives in ONE `useUpdateCheck` hook consumed by the layout-level palette global builder (`use-global-palette-actions.ts`) and the overflow-menu check affordance.
**Why**: mirrors `use-update-click.ts`'s anti-drift extraction — inline copies of the toast composition + error mapping at each consumer would drift.
**Rejected**: duplicating the flow inline at each consumer (copies of toast/error logic drift).
*Introduced by*: 260720-n2ai-shll-check-updates-delegation-palette-checks

### Github-sourced toast suppresses the sub-threshold annotation
**Decision**: `composeCheckToast` takes the echoed report `source` (optional, default `""`) and drops the `(patch — below notify threshold)` annotation when `source === "github"`; the `updateAvailable`/`notable` filtering is untouched. The frontend keys off the ECHOED report source rather than an invented client boolean.
**Why**: the github backend has no notify policy, so every row decodes `notable=false` — annotating each as a sub-threshold patch would mislabel a real minor bump (`run-kit 3.8.7 → 3.9.1`). Echoing `report.Source` doubles as a defensive check (the client reacts to what actually ran); an old daemon that omits `source` defaults to `""` and keeps today's annotated behavior.
**Rejected**: a client-side `includePatches`-implies-github boolean (fragile — decouples the annotation from what the daemon actually queried); suppressing on `includePatches` alone (a released incl.-patches view SHOULD still annotate its genuine sub-threshold rows).
*Introduced by*: 260720-wb3n-github-source-patches-check

### Dismissed-pending shows the menu update surface, not the ⟳
**Decision**: the overflow menu version row's update-surface condition is `qualifies && (updateOverflowed || !showChip)` (via `asUpdateSurface = tools.length>0 && (updateOverflowed || (qualifies && !showChip))`) — so a dismissed pending update shows the update surface rather than the resting ⟳ check affordance — while the chevron **attention badge** keeps the narrower undismissed-overflowed condition (`updateOverflowed && tools.length>0`).
**Why**: the menu is deliberate discovery (like the palette, which already ignores chip dismissal via its `qualifies`-only gate), so surfacing a known pending verdict there does not violate "dismissal silences the ambient chip" — the badge, which IS ambient, stays silenced. When a verdict is already known the update surface is the stronger, truer affordance; offering "check again" over a known pending update is a blind-affordance smell.
**Rejected**: rendering the ⟳ when dismissed (offers a redundant re-check while a pending verdict already exists); lighting the badge for the dismissed case too (would re-introduce the ambient signal dismissal is meant to silence).
*Introduced by*: 260720-ml7k-unified-toolbar-update-button

### The manual check feed is tab-local frontend state, not a cached backend verdict
**Decision**: a manual ⟳ / palette check result is held in plain, non-persisted `SessionContext` React state (`manualCheck`) and merged into the update surfaces frontend-side. The backend is untouched: `handleUpdatesCheck` still never writes the github verdict into the cached checker slot, and no API/SSE surface grows.
**Why**: the side-channel contract is deliberate — the github source carries no notify policy, so caching its verdict would wipe a legitimate released-manifest chip and starve the scoped `shll update` argv (`Snapshot().Matched`), reopening the argv-scoping question that design closed. Frontend state gives the finding a persistent home without touching any of that. The accepted tradeoff is explicit: the result is **tab-local and a page reload before updating forgets it** — re-clicking ⟳ is one click, and the ambient feed remains the durable cross-tab channel.
**Rejected**: caching the github verdict in a separate backend slot and broadcasting it over SSE to all tabs (grows the API/SSE surface and reopens argv scoping); persisting the manual result to localStorage (would resurrect a stale verdict across reloads with no server signal to invalidate it).
*Introduced by*: 260807-s6zs-manual-check-update-surface

### The two-feed merge lives in `useUpdateNotification` alone, ambient-first
**Decision**: `deriveUpdateFeed` is called from exactly one derivation (plus `dismissUpdate`, which needs the same effective key); the in-bar `UpdateChip`, the overflow-menu version row, and the palette's layout-level global group consume the merged output with **no per-surface or per-mount branching**. Precedence is ambient-first: when the ambient feed shows, every returned field is purely ambient-derived and the manual feed changes nothing.
**Why**: the AppShell↔board palette non-drift constraint is structurally guaranteed only if the merge happens at the single shared derivation — `asUpdateSurface = tools.length > 0 && (updateOverflowed || (qualifies && !showChip))` already picks up the manual feed with zero component edits. Ambient-first because the ambient feed is the durable, policy-driven, cross-tab channel; a tab-local snapshot must never displace a live policy verdict.
**Rejected**: merging at each consumer (four copies of the precedence rule — the exact drift the shared-hook architecture exists to prevent); manual-first or newest-wins precedence (a manual snapshot would shadow the durable ambient verdict and its scoped-update click path).
*Introduced by*: 260807-s6zs-manual-check-update-surface

### Manual-fed clicks force; ambient-fed clicks stay scoped
**Decision**: `useUpdateClick` branches on `manualOnly` — a manual-fed surface triggers `forceUpdateNow()` (full-roster `POST /api/update {"force":true}`), an ambient-fed surface keeps the scoped `updateNow()`.
**Why**: the scoped endpoint moves only the server's `Snapshot().Matched` set, which a side-channel manual verdict never populates — a scoped click on a manual-fed chip would find nothing to do. Force is also exactly what the check toast's own "Update Now" action already runs, so the chip and the toast remediate identically.
**Rejected**: always forcing (would widen the ambient chip's deliberately scoped argv to the full roster); teaching the backend to accept a client-supplied tool list (a new API surface, and it would let a stale tab drive the update argv).
*Introduced by*: 260807-s6zs-manual-check-update-surface

### The watch affordance: already-running navigates, fresh spawn offers a toast action
**Decision**: update/restart triggers resolve `UpdateTriggerResult` (`{status, watch?}`) and one shared pure helper — `consumeUpdateWatchTarget(result, navigate, addToast)` in `hooks/use-update-click.ts`, consumed by both `useUpdateClick` and the palette's restart wrapper — turns the `watch` target into UI: `already-running` navigates straight to the job window's terminal route (`/$server/$window`, window param = the `@N` id), a fresh spawn shows an info toast with a "Watch" action slot, and a `watch`-less (old-daemon) result is a no-op.
**Why**: the job runs in a managed tmux window (architecture § Daemon Lifecycle → `rk-jobs`), so the terminal route already renders it with zero new UI plumbing — the second click on an in-flight update IS the jump to the live job, which is more useful than an error. One helper keeps the chip, the overflow-menu surface, and the palette actions from drifting. Auto-navigating on every fresh spawn would rip the user off their current window for a job they may not want to watch, so fresh spawns only OFFER the jump.
**Rejected**: navigating on every trigger (disruptive); a `409 already-running` (treats a truthful derived answer as an error); new components or SSE additions (the terminal route + relay suffice).
*Introduced by*: 260812-z1ya-update-daemon-tmux-window

### Ambient-key-change clearing baselines at store time, not a raw key watcher
**Decision**: the provider stamps the ambient composite key observed when the manual result is stored (`manualAmbientKeyRef`) and clears the manual state only when a **later** ambient key differs from that baseline.
**Why**: a naive effect on `updateAvailable.key` would clear the manual result on the first ambient render after storage even when the key never changed (or on an initial `null`→`null` render), destroying the feed immediately. Baselining at store time mirrors `use-update-click.ts`'s `clickKeyRef` completion signal (R13) exactly, and treats the ambient verdict moving on as the update-consumed signal — including the cleared empty key.
**Rejected**: clearing on any `updateAvailable` state write (churns the manual result away on idempotent SSE replays); a timeout-based expiry (invents a policy the ambient feed already supplies).
*Introduced by*: 260807-s6zs-manual-check-update-surface

### Check affordance is a non-menuitem control (menu stays open)
**Decision**: the resting version row's ⟳ "Check for updates" affordance is a plain button (no `role="menuitem"`, `tabIndex={-1}`) inside the row, so the container's role-keyed close handler does not fire on click.
**Why**: the in-flight spinner + single-flight state is only meaningful if the menu stays open across the ~1-2s check; the font-stepper precedent (`role="group"` row, plain buttons) established this pattern for non-terminal menu actions. Arrow-key nav still reaches it (the focusables selector matches `button:not([disabled])`).
**Rejected**: `role="menuitem"` with close-on-click (hides the busy state and makes single-flight moot); an intermediate "checking…" toast (already rejected in `260720-n2ai`).
*Introduced by*: 260720-ml7k-unified-toolbar-update-button

### The settings Notifications row explains an unsupported browser instead of hiding
**Decision**: on push `state === "unsupported"` the settings Notifications row stays present and renders a "Not supported in this browser" note with no action buttons.
**Why**: render-nothing is a bar-chip idiom (an inapplicable chip should not reserve space in a fixed cluster), but a settings pane is an inventory of what exists — a silently missing row reads as a bug, while a stated absence answers the question. Blast radius is one branch of one row.
**Rejected**: hiding the row (carries the chip idiom into a pane where it misleads); a disabled Enable button with no explanation (looks broken without saying why).

# API Layer & Sockets

**Domain**: run-kit

## API Layer

All endpoints served by the single Go binary on one port. POST-only mutations with path-based intent (no multiplexed action field). **Uniform HTTP verb (constitution §IX)**: every mutating endpoint uses `POST`; there are zero `PUT`/`PATCH`/`DELETE` route registrations and the CORS `AllowedMethods` allowlist is exactly `[GET, POST, OPTIONS]` (260529-jad6). Endpoint semantics that would conventionally map to other verbs (e.g. partial update on `/options`) are expressed via the path and a documented body contract.

The SPA catch-all's regular-file branch serves the shipped
`/tutorial/tutorial.html` companion page (five hash-addressed chapters,
`#ch1`–`#ch5`) from the production frontend bundle. It is an ordinary static
file under `app/frontend/public/tutorial/`; no API or chi route is registered
for it. (6uu0, 00zd)

**Name validation — new-name vs. existing-name split**: `internal/validate` exposes two name rules and the API layer picks by whether the value names a **to-be-created / rename-target** entity or an **existing** one (260722-ln4n-auto-safe-name-conversion). `ValidateNewName(name, label)` (permissive `ValidateName` + a "no spaces" rejection) guards exactly the four new-name call sites — session create + session rename-to (`api/sessions.go`), window create (non-empty name only) + window rename-to (`api/windows.go`) — so the safe charset is a real backend contract, not merely UI steering. Every existing-name lookup (session URL params, `TargetSession`, upload/riff session values, session-order entries) keeps the permissive `ValidateName`, so pre-existing spacey names created outside run-kit stay renamable/killable. The backend stays reject-only (no server-side name conversion — constitution §I) and keeps hyphens legal for both name kinds; the session hyphen→`_` steering is UI-only (see [tmux-sessions](tmux-sessions.md) § Name-Validation Charset Contract for the full contract and rationale, and [ui/routes-and-shell](/run-kit/ui/routes-and-shell.md) § Live Safe-Name Conversion for the frontend transforms).

**Window addressing**: routes that act on a *specific existing window* are keyed by the stable tmux **window ID** under `/api/windows/{windowId}/...` (kill, move, move-to-session, rename, options, keys, select, split, close-pane, history) (260529-chgz-window-id-routing). The `{windowId}` path param is validated via `validate.ValidateWindowID` (`^@[0-9]+$`) by the `parseWindowID(r) (string, bool)` helper in `api/windows.go`, which delegates to the shared `decodeWindowID(r) (string, bool)` helper (`url.PathUnescape` + `ValidateWindowID` in exactly one place) (260529-jad6). The `/ws/terminals` mux is the second entry point (260717-803u-relay-mux): it validates its `open` op's already-JSON-decoded `windowId` through the **same** `validate.ValidateWindowID` call (no percent-decode — the id rides a JSON control frame, not a URL segment), so the two entry points share one validator and cannot drift (the drift that caused bug #205). `400` on malformed ID before any tmux call. A window ID is a server-global, self-contained tmux target, so the session name drops out of these paths. Routes that *create* a window or enumerate a session's windows stay session-scoped (`POST /api/sessions/{session}/windows`, session enumeration) — there is no window ID at create time.

**`broadcastServerOrder` — server-global fan-out (vs. per-server `broadcastSessionOrder`)** (260705-bpnr-server-tiles-drag-reorder): the SSE hub exposes `broadcastServerOrder(order []string)` (`api/sse.go`) alongside `broadcastSessionOrder(server, order)`. The distinction is load-bearing and deliberate: **session** order is a per-server concern (which server's sidebar reorders), so `broadcastSessionOrder` fans only to that server's clients and caches per-server in `previousOrderJSON[server]`. **Server** rank order is a HOST-global concern — a client viewing one server, or NONE (the bare `/` Host page on the `?metrics=1` sentinel stream), still needs to re-sort its whole server list — so `broadcastServerOrder` fans to EVERY client across every `h.clients` key (exactly like the `metrics`/`services` broadcasts) and caches in a SINGLE `cachedServerOrderJSON` slot replayed to every new client in `addClient` (NOT gated on `c.server`). It normalizes a `nil` order to `[]` so the cached JSON is always `"[]"`, never `"null"`. This is why the design chose a fresh server-global event rather than reusing the per-server `session-order` shape — the latter would neither reach `?metrics=1` clients nor fit a host-global cache.

**`broadcastBoardOrder` — server-global fan-out (vs. per-server `broadcastBoardChanged`)** (260708-a2qd-board-list-reorder): the SSE hub exposes `broadcastBoardOrder(order []string)` (`api/sse.go`), a verbatim structural mirror of `broadcastServerOrder` — a board is an emergent cross-server aggregate of `_rk-pin-*` sessions with no owning tmux server, so board **display order** is a HOST-global concern (exactly like server rank order, and unlike the per-server `board-changed` pin/unpin/reorder event which fans only to one server's clients). It fans `event: board-order` to EVERY client across every `h.clients` key (incl. the `?metrics=1` sentinel) and caches in a SINGLE `cachedBoardOrderJSON` slot replayed to every new client in `addClient` (NOT gated on `c.server`), normalizing a `nil` order to `[]` so the cached JSON is always `"[]"`, never `"null"`. Payload `{"order":[...]}`. Fired synchronously by `handlePostSettings` after the `board_order` save (see the `POST /api/settings` row); it deliberately does NOT reuse the per-server `board-changed` event (which is scoped to a tmux server and uncached), since an order write is host-global.

**`broadcastStatusRefresh` — server-global, BROADCAST-ONLY (no cached slot, no replay)** (260715-nwla-status-refresh-feedback): the SSE hub exposes `broadcastStatusRefresh(completedAt time.Time)` (`api/sse.go`), fanning `event: status-refresh` with payload `{"completedAt":"<RFC3339 UTC>"}` (`completedAt.UTC().Format(time.RFC3339)`) to EVERY client across every `h.clients` key incl. the `?metrics=1` sentinel, under `h.mu.Lock()` with the same drop-on-full `slog.Warn` debounce as its siblings. A manual PR-status refresh is a HOST-global concern (both PR pollers are process-wide, not per-`?server=`), so it fans out like `broadcastServerOrder`/`broadcastUpdateAvailable`, NOT to one server's clients like `broadcastBoardChanged`. **Unlike server-order/board-order/version/update-available it is the sole broadcast fn with NO cached slot and NO `addClient` replay case** — a completion pulse is transient by design; a client connecting after a pass completes is NOT owed a replayed event because freshness for a late connector is surfaced independently by the row flyout card's "checked Xs ago" line (`PrFetchedAt`), so a missed pulse loses nothing. Emitted from `finishStatusRefresh()` (nil-guarded, once per completed pass — see the `POST /api/status/refresh` row above); the frontend routes it through `session-context.tsx`'s `subscribeStatusRefresh` fan-out to clear the PANE-header refresh button's spinner (ui/sidebar.md § WindowPanel refresh button).

**`event: version` (set-once cached slot) + `event: update-available` (broadcast + cached replay)** (260713-4zap-update-notify-one-click-upgrade): two more server-global cached slots on `sseHub`, both delivered to EVERY client across every `h.clients` key including the `?metrics=1` sentinel (fan-out identical to `server-order`/`board-order`), replayed on connect from `addClient` (after the server-order/board-order sends, both gated on a non-empty cached string; NOT gated on `c.server`). They differ in whether they broadcast:

- **`event: version`** — the RUNNING daemon version (ldflags `main.version`, sentinel `"dev"` for local builds), payload `{"version":"0.5.3","boot":"<per-process id>","brew":<bool>,"started":<epoch secs>,"port":<bound port>}`, cached in `cachedVersionJSON`. Seeded ONCE via `sseHub.setVersion(version, boot, brew, started, port)` (called from `Server.SetVersion` after `NewRouterAndServer` — see § API Server version/checker wiring); the running version cannot change for the process lifetime, so there is **NO broadcast path** — it is a **replay-on-connect-only** slot (an empty version is ignored, leaving the slot empty → no event; `boot`/`brew` ride the same set-once slot). **`boot`** is a per-process identity generated ONCE at startup (16 hex chars from `crypto/rand` via `cmd/rk`'s `newBootID`), in-memory only (Constitution II); a *fresh* boot on every daemon start is what lets a reconnecting tab detect a **same-version** restart and reload (the reconnect after a restart is exactly the signal the frontend reload guard keys on — see ui/updates-and-notifications.md § Update Notification → Reload guard). **`brew`** is `selfpath.IsBrewInstalled` computed ONCE at startup in `serve.go` (`resolveBrewInstalled`; a resolve failure reports `false` → the palette's brew-gated force-update entry safely stays hidden); it gates the client-side force-update palette entry. **`started`** is the daemon process start (epoch seconds, captured in `serve.go` before router construction so the whole boot sequence counts toward uptime) and **`port`** the resolved `cfg.Port` the daemon bound — both server-derived constants known at boot, feeding the host page's run-kit system card daemon line (uptime = `now − started`; see ui/sidebar.md § HOST HEALTH Zone). An older daemon's field-less payload degrades client-side to an omitted uptime/port readout (never NaN/0 — the `boot`-field mixed-version precedent). This is the sole version-exposure mechanism — deliberately no `GET /api/version` (minimal surface §IV); the SSE connect IS the moment the client needs it. (260714-3law-force-update-restart-palette) (260824-j2k6-daemon-system-presentation)
- **`event: update-available`** — the current toolkit-update verdict, payload `{"tools":[{"tool":"fab-kit","current":"2.16.0","latest":"2.17.0","updateAvailable":true,"notable":true},…],"key":"fab-kit@2.17.0,run-kit@3.9.0","current":"","latest":"","source":"released"}`, cached in `cachedUpdateAvailableJSON`. The `tools` array carries EVERY tool with a pending update — including sub-threshold `notable:false` rows — so the client can filter EITHER check view (default = `notable` only; incl.-patches = all `updateAvailable`); `key`/`current`/`latest` are NOTABLE-derived. **One shared builder** `buildUpdateAvailablePayload(verdict updatecheck.Result)` (`api/sse.go`) maps `verdict.Tools` onto `[]updateAvailableTool{Tool, Current, Latest string, UpdateAvailable, Notable bool}` (camelCase `updateAvailable`/`notable` per the rk payload convention) + `key`/`current`/`latest` + `source` (`verdict.Source`, appended LAST on `updateAvailablePayload` so existing byte-fragment assertions on `"current":…,"latest":…` adjacency stay valid) — serving BOTH `broadcastUpdateAvailable` and the `POST /api/updates/check` response so the two shapes can never drift. The ambient SSE slot therefore also carries `source:"released"`, which is harmless. `broadcastUpdateAvailable(verdict)` builds that payload, marshals it, sets the cache, and fans the frame to every client under `h.mu.Lock()` (drop-with-`slog.Warn` on a full channel). Empty until the first check changes the key. Invoked via the `Checker.OnQualify(Result)` callback wired in `serve.go`, which fires on ANY key change — so a newly-matching tool or newer latest re-broadcasts AND a **CLEARED verdict** (empty `tools`/`key`, fired when a match is consumed) is NOT skipped: it is broadcast and REPLACES the cached slot exactly like a populated one, so a tab connecting after a consumed-match clear replays the cleared state rather than a stale match. A late-connecting client gets the cached slot on connect (`replayGlobalSlots` special-cases nothing). (260718-d15e) (260720-n2ai)

### `event: code-server` (host-global signal, TTL-cached probe + cached replay slot)

The SSE hub's poll loop broadcasts `event: code-server` with payload `{"reachable":bool}` on every tick — the port is NOT carried: it is a private implementation detail behind the stable `/code/` route — fanning to EVERY client across every `h.clients` key exactly like `services`, and caches the latest payload in a `cachedCodeServerJSON` slot replayed to late joiners in `replayGlobalSlots` (right after the services slot) — so a client connecting mid-session sees the signal immediately. `reachable` comes from `codeServerTick()`: a **TTL-cached** (`codeServerProbeTTL` = 5s, piggybacking the poll cadence) bare TCP dial of `127.0.0.1:{port}` with a 500ms `codeServerDialTimeout`, executed OUTSIDE `h.mu` so a filtered/hung listener never stalls event delivery — **never a per-request dial**. ### Proxy Content-Length header sync

`makeModifyResponse(port)` (`app/backend/api/proxy.go`) is the `ModifyResponse` hook on every per-port `ReverseProxy`. `httputil.ReverseProxy` copies the upstream response's **header map** verbatim to the client, so the `resp.ContentLength` *field* alone does not govern the wire: the header and the field are two independent surfaces and **both** must describe the same bytes.

**The discipline**: every branch that assigns a rewritten body to `resp.Body` sets three things together — the body, `resp.ContentLength`, and `resp.Header.Set("Content-Length", strconv.Itoa(len(rewritten)))` — where `rewritten` holds the FINAL wire bytes for that branch. The three body-replacing branches:

| Branch | Final wire bytes | `Content-Length` |
|--------|------------------|------------------|
| Plain (non-gzip) | uncompressed rewritten HTML | `len(rewritten)` |
| Gzip re-encode success | `buf.Bytes()` (re-compressed) | the **compressed** length |
| Gzip-encode fallback (`gz.Write` error) | uncompressed rewritten HTML, next to the existing `resp.Header.Del("Content-Encoding")` | uncompressed `len(rewritten)` |

The header is set **unconditionally**, not only when the body shrank — `header == body length` is an unconditional invariant, and the unconditional `Set` also gives a chunked upstream (one that arrived with no `Content-Length` at all) an accurate header. The early pass-through returns — HEAD requests (see below), non-`text/html` content-type, `gzip.NewReader` failure, body-read failure — do not touch the body and therefore touch neither surface. `Set` is chosen over `Del` (which would fall back to chunked encoding): an explicit length is deterministic across HTTP versions and directly assertable in tests.

**Test coverage** (`app/backend/api/proxy_test.go`): a shared `assertContentLength` helper checks header and field against the fully-read final body. `TestModifyResponseStaleContentLengthHeader` starts from a response carrying the *original* (larger) upstream header to prove the rewrite overwrites it; `TestModifyResponseHTMLRewrite` and `TestModifyResponseGzipHTML` carry the same assertions (gzip against the re-compressed wire length). The gzip-fallback branch is verified by construction review only — `gzip.Writer.Write` into a `bytes.Buffer` cannot fail, so the branch is untriggerable without restructuring production code for testability.

**HEAD guard**: a HEAD response has a legitimately empty body while its `Content-Length` header advertises the GET entity length, so the unconditional `Set` would rewrite it to `0`. `makeModifyResponse` therefore returns early when `resp.Request.Method == http.MethodHead` — there is no body to rewrite, and the upstream entity headers pass through untouched (`TestModifyResponseHEADPassthrough`). Also: the two `return nil` pass-throughs after a partial read (`gzip.NewReader` / `io.ReadAll` failure) hand the client whatever bytes remain in the already-drained body.

### Riff Engine Injection + Repo-Root Derivation

The `POST /api/riff` + `GET /api/riff/presets` handlers surface the extracted `internal/riff` spawn engine (full engine in [rk-riff](rk-riff.md)) (260713-sbk1-web-spawn-agent); `POST /api/windows/{windowId}/fork` is a **third** consumer of the same injected engine (§ Conversation Fork Endpoint below). Two seams are load-bearing:

**`RiffEngine` interface — a DEDICATED dependency, NOT folded into `TmuxOps`** (`api/router.go`): `type RiffEngine interface { Spawn(ctx, riff.Options) (riff.Result, error) }`, injected onto the `Server` struct as a nil-safe `riff RiffEngine` field mirroring the `metrics`/`services`/`prStatus` collector-injection pattern. `riff.Options` carries `{Server, Session, RepoRoot, Task, Preset}` plus the dialog-v2 spawn-shaping fields `{Where, WorktreeName, Tier}` (260714-q9cg). Production wiring is `prodRiffEngine{}` (delegates to `riff.Spawn`); tests inject a focused mock via the new `NewTestRouterWithRiff(logger, sf, ops, engine, hostname)` constructor (its recorded-inputs mock also records `Where`/`WorktreeName`/`Tier`). **Why a separate field rather than a `TmuxOps` method**: `TmuxOps`/`mockTmuxOps` are shared by every handler test, so a spawn method there would force a mock method into dozens of unrelated tests; the dedicated field keeps the blast radius to the riff handler + its own mock. `NewTestRouter` leaves `riff` nil (riff-unrelated tests never reach it).

**New-field validation is at the handler, before repo-root derivation** (260714-q9cg): `handleRiffSpawn` runs the full v2 validation ladder — `where` enum, `worktreeName`+`checkout` rejection, `validate.ValidateWorktreeName`, `validate.ValidateTier` — **before** `deriveRepoRoot` or any subprocess, so a malformed request `400`s with nothing created (constitution §I). See the `/api/riff` endpoint row above and [rk-riff](rk-riff.md) § Security / Trust Boundary. `handleRiffPresets` additionally reads `fabconfig.ReadTiers(repoRoot)` into the response so the dialog's Agent dropdown rides the one preflight fetch — **gated on `fabconfig.IsFabProject(repoRoot)`** (260714-gsmu-spawn-dialog-tier-gate-sidebar-entry) (a non-fab repo, no `fab/project/config.yaml`, returns `tiers: []` so the dialog hides the Agent Tier field — see the `/api/riff/presets` endpoint row and [rk-riff](rk-riff.md) § `IsFabProject`).

**Repo-root derivation from the target session's active pane** (`deriveRepoRoot` in `api/riff.go`, shared by both handlers): `ListWindows(ctx, session, server)` → the active window (`IsActiveWindow`, else the first) → that window's active pane (`PaneInfo.IsActive`, else the first pane, else the window's `WorktreePath`) → `Cwd` → `config.FindGitRoot`. It returns `(root, cwd, err)` so a non-repo caller can name the offending cwd in its `400`. The three no-root outcomes are distinguished: a derived-but-non-repo cwd, a session with no window/pane to derive a cwd from (the practical nonexistent-session path — the real `ListWindows` swallows its tmux error into an empty result), and a tmux-read failure (surfaced as a `400` "does it exist?" message, since a named-session read failure is most likely a gone session, client-correctable). This uses the existing `ListWindows` surface — no new tmux primitive — and is session-scoped (not window-scoped) because the endpoint's spawn target is a session, not a window.

### Conversation Fork Endpoint

`POST /api/windows/{windowId}/fork?server=` (`api/fork.go`) branches a live agent's conversation into a new tmux window in the **same session and the same directory**, riding the injected `RiffEngine` with `Where: "checkout"` and a `ResumeSessionRef`. It is **window-keyed and body-less**: `{windowId}` + `server` are the only client inputs, and the handler reads no request body at all — the session name, the Claude session uuid, the working directory, and the new window's name are all derived server-side (constitution §X). The endpoint row above carries the full gate ladder and status mapping; three properties are load-bearing enough to state separately. (260806-s4av)

**One `FetchSessions` walk resolves all four inputs** (`resolveForkSource` → the `forkSource` struct). It deliberately does **not** compose the agent-session-identity rollup + `deriveRepoRoot`: the fork needs the *enclosing session name* (which the rollup discards) and the cwd of the *requested* window, whereas `deriveRepoRoot` is session-keyed and would take the cwd from the session's **active** window — the wrong pane whenever a background window is forked. One walk yields the session name, the window name, the reconciled `(provider, ref)` pair, and the cwd; two composed helpers would mean two tmux reads and the wrong pane. The pane-cwd picking itself is the **shared** pure `windowCwd(win)` (`api/riff.go`) — active pane's cwd, else the first pane's non-empty cwd, else the window's `WorktreePath` — used by both `deriveRepoRoot` (session-keyed) and `resolveForkSource` (window-keyed) so the two cannot drift.

**The fork roots at the pane's EXACT cwd; the git-root walk is a gate only.** The engine receives the resolved pane cwd itself as its window root — a repo *subdirectory* reaches the engine verbatim — and `config.FindGitRoot` answers only "is this inside a repo at all", the same question riff's non-repo `400` asks. This is not a stylistic choice: Claude keys its transcript store by the **exact cwd** (`~/.claude/projects/<encoded-cwd>/`) and its resume lookup covers the project directory and its git worktrees but **not** parent directories, so rooting the fork at the walked-up repo root silently breaks `--resume` for every agent working in a subdirectory. Verified empirically 2026-08-06: a session started in `<repo>/app/backend` resumes from `<repo>/app/backend` and fails with "Execution error" from `<repo>`. `api/fork_test.go`'s `TestForkRootsAtPaneCwdNotGitRoot` locks the contract in.

**Timeouts and the 5s-rule exception.** Both contexts are `context.Background()`-derived rather than `r.Context()`, so a client disconnect can never truncate a half-created window: `forkResolveTimeout = 5s` bounds the resolve (mirroring `riffRepoRootTimeout`), and the engine spawn reuses the shared `riffSpawnTimeout = 90s`. The spawn inherits `handleRiffSpawn`'s **documented exception** to the 5s tmux-blocking review rule — it is the same synchronous engine call minus `wt create` (checkout mode skips `wt` entirely), with each individual subprocess keeping its own bound. Engine errors go through the shared `riffStatusForError` unchanged, so the engine's own claude-launcher rejection ([rk-riff](rk-riff.md) § Resume-Fork Launcher Seam) surfaces as a client-correctable `400` with nothing created.

## State Socket (`/ws/state`)

**One WebSocket per tab multiplexes every session-state + host-metrics stream** (260716-qf3j-state-socket) — a single established WebSocket carries what per-server + `?metrics=1` EventSource connections would otherwise. There is no `GET /api/sessions/stream` / `handleSSE` (D2). **Why**: SSE holds an HTTP/1.1 pool slot in EVERY browser engine and the pool caps at 6 per origin (spike `docs/findings/socket-pool-accounting.md`); a multi-server host held all 6 slots from SSE alone on plaintext origins, and on Firefox/WebKit a saturated pool **blocks new WebSocket handshakes entirely** — so terminal relays could never connect. An **established WebSocket holds NO pool slot** in any engine, dropping steady-state pool usage to ~zero and immune to multi-tab aggregation. A muxed *SSE* was rejected: it still holds one slot and needs out-of-band subscribe POSTs, reintroducing the POST-races-the-stream race class (memory: `relay-connect-select-alignment`). In-band subscribe frames are totally ordered with the events they gate, which also structurally fixes the long-standing `attachServer`→SSE race (memory: `multi-server-group-expand-async-race`, the change's explicit acceptance test). Terminal relays ride a second WebSocket, `/ws/terminals` (see § Terminal Relay) (260717-803u-relay-mux), kept SEPARATE from this socket (D6 — bulk binary terminal output must not share a send buffer/scheduler with state events). Every route holds a fixed 2 WS + 0 SSE.

### Wire protocol (JSON text frames both directions)

`app/backend/api/state_ws.go` owns the envelope types + `handleStateWS`. Client → server ops: `hello` (once, first frame, carrying a client-generated `conn` id), `subscribe {kind, key?, server?, req}`, `unsubscribe {kind, key?, server?}`, `preview-scope {server, expanded[]}`, `ping` (the client liveness heartbeat — § Client heartbeat + wake probes below). Server → client frames:

- **`ack {req, snapshot?}`** — answers a subscribe. For `server`/`metrics` it carries the current `snapshot` (the same payload the SSE `event: sessions` / cached-metrics slot carried); `snapshot` is `json.RawMessage` (empty → `null`, tolerated).
- **`event {kind, key?, type, data}`** — a producer event. `data` is `json.RawMessage` embedded **verbatim** (**contract-preservation rule**, load-bearing: event names and payloads ride `type`/`data` unmodified, so every consumer above the `subscribe*` seams stays transport-agnostic). Per-server events carry `kind:"server"` + `key`; host-global events carry `kind:"global"`.
- **`gone {kind, key, reason}`** — the dead-server signal (§ dead-server reap below).
- **`pong {op}`** — answers a client `ping`. Marshalled from the shared `pongFrame` type and enqueued **non-blocking on the connection's send channel `sc.ch`** (drop on a full channel, mirroring the unknown-op error path) so ONLY the writer pump ever writes the socket — gorilla permits one concurrent writer. A dropped pong is harmless: a full channel means event frames are already flowing, and any inbound frame counts as liveness client-side. `ping` is a KNOWN op (no `error` frame); every other unknown op draws the `error` frame.
- **`error {req, message}`** — a malformed/unhonorable op; `req` echoes the offending op's `req` (0 when none). The socket stays live.

**Event catalogue** — the `type` strings are `sessions`, `session-order`, `preview`, `board-changed` (`kind:"server"`) and `metrics`, `services`, `server-order`, `board-order`, `version`, `update-available`, `status-refresh`, `notify` (`kind:"global"`). Their producers, cached slots, poll cadence, `metricsOnlyServer` sentinel semantics, PR-status join, previews, and every `broadcast*`/`setVersion`/`setPreviewScope` helper live in the § SSE Hub family below (Event-Driven SSE Loop, PR-Status Join, Session-Tile Previews, `broadcastServerOrder`/`broadcastBoardOrder`/`broadcastStatusRefresh`, version/update-available slots).

### Host-global `notify` event

`broadcastNotify(title, body, url)` (`api/sse.go`) emits a pre-rendered `event` envelope with `kind:"global"`, `type:"notify"`, and data `{id, title, body, url?}`. `id` is a fresh 16-character hexadecimal token from 8 bytes of `crypto/rand`; `url` is omitted when empty. The helper marshals once, takes the hub lock, and fans the frame to every connected state client through `broadcastGlobalLocked`.

The event is broadcast-only: it writes no cached global slot, and `replayGlobalSlots` has no notify branch. A client connected during the broadcast can receive the event; a client that connects or reconnects afterward receives no stale notification.

Both notification producers call the helper:

- `handleNotify` completes `push.Notify`, initializes the state hub, and broadcasts the same title/body with an empty URL. Its `{"sent": N, "pruned": M}` response continues to describe only Web Push delivery.
- `newSSEHub` injects one combined notifier into `waitingPushTracker`: it calls `push.Notify` and `broadcastNotify` with the same title, body, and waiting-window deep link. The tracker's `notify` function remains directly replaceable in tests.

### Hub edge (`api/sse.go`)

The hub edge is a per-connection **subscription set**: a `stateConn` holds `ch chan hubEvent`, `connID`, and `subs map[string]*sseClient` (one routing record per subscribed server key). **`hubEvent`** is the unit producers fan out — `{kind, typ, key, data}` plus a `gone bool` marker and a `raw []byte` bypass whose PRIMARY use is pre-rendered broadcast fan-out (below) and which also carries handler-composed frames (the subscribe `ack`, `error` frames, pongs) that must ride the SAME ordered channel as the subscription's events. Each connection's writer pump renders its queued events via `renderEnvelope()` into the JSON envelope — which returns `raw` verbatim when set — so ONLY the writer pump ever writes the socket; a parallel `hubEvent.String()` renders an SSE-frame shape used ONLY by tests.

**Fan-out events are pre-rendered ONCE at the broadcast site** (260811-sqe7-prerender-broadcast-envelopes): every fan-out producer — the global `broadcastGlobalLocked` sites (`server-order`, `board-order`, `update-available`, `status-refresh`, `notify`, the `metrics`/`services` ticks) and the per-server poll units (the `sessions` poll delta, `broadcastSessionOrder`, `broadcastBoardChanged`) — wraps its event in `preRendered(ev)` (`api/state_ws.go`, beside `renderEnvelope`), which returns `hubEvent{raw: ev.renderEnvelope(), typ: ev.typ}`; per-server unit sites render once BEFORE the per-client fan-out, not per recipient. A broadcast to C connections costs 1 marshal instead of C identical per-recipient ones, with byte-identical wire frames (the raw passthrough) and `renderEnvelope` itself untouched. `typ` stays populated on raw events so the channel-full drop logs (`sendLocked`/`sendConnLockedOK`) still name the event. Events whose payload differs per recipient — or that already render exactly once — stay structured: `preview` (per-subscriber filtered subsets), single-recipient sends (`replayGlobalSlots`, the subscribe-time cached replay), and `gone` reap markers (the dedicated `gone` render path).

- **Metrics subscription = the `metricsOnlyServer` sentinel as the internal registry key** (Design Decision 6). The wire protocol exposes `subscribe kind:"metrics"`, but `stateSubscribe` registers it internally under the reserved `metricsOnlyServer = "\x00metrics-only"` key. The sentinel therefore participates in `safetyIntervalEffective`'s coverage gate and all poll logic exactly as any other key, so `/` keeps its fast cadence.
- **Server-key validation on the WS edge** (Constitution §I barrier preserved). The WS edge validates the server name: `validate.ValidateServerName` guards `stateSubscribe`/`stateUnsubscribe`'s `kind:"server"` key (`api/sse.go`) and the in-band `preview-scope` op's `server` (`api/state_ws.go` calls `hub.emitError`). An invalid name / unknown kind gets an `error` frame carrying the offending `req` (routed through the send channel so ONLY the writer pump ever writes to the socket — gorilla forbids concurrent writes), never a silent drop.
- **Ack ordering** (the load-bearing correctness property). `stateSubscribe` reads the ack snapshot (`previousJSON[key]` for a server, `cachedMetricsJSON` for metrics) **inside the SAME `h.mu` critical section that enqueues the ack**, AFTER `addClient` registers the routing record. This guarantees the ack's snapshot is ≥ every `sessions`/`metrics` frame already on the channel: a concurrent poll tick either ran before this lock (the read sees its value) or after the ack (the client's newest-wins apply is correct). Reading under an EARLIER lock would let a poll tick enqueue a NEWER `sessions` event ahead of a stale-snapshot ack; the client applies the ack's snapshot last and `previousJSON` dedup then suppresses re-emission, stranding stale UI on a quiet server. Regression-tested by `TestStateWS_SubscribeAckNotStaleUnderPollInterleave` (proven to FAIL against the earlier-read shape, clean under `-race`).
- **Cold-subscribe freshness — the subscribe path wakes the poll loop**. A `kind:"server"` subscribe for a server with no cached snapshot gets its first `sessions` event promptly (one poll pass), never by waiting out the 12s safety poll, via two complementary triggers. (1) **In-set cold server** (`h.previousJSON[key]` absent — first fetch failed or hasn't completed; the ack carries `null`): the `stateSubscribe` ack critical section records the cold condition, then calls `h.wake(key)` AFTER `h.mu.Unlock()` — `wake()` takes `h.mu.RLock` and Go's `sync.RWMutex` is non-reentrant, so calling it under the held write lock deadlocks. `wake()`'s new-entry allocation gate (§ Design Decisions → Hub wakes gate new-entry allocation) passes because `addClient` registered the subscription before the ack section. (2) **Server new to the poll set entirely**: a per-server wake cannot unpark the loop — `waitForNext` builds wait cases only from the server list snapshot taken before parking, so a brand-new server's wake channel is watched by nobody — so `addClient` fires the hub-level **membership wake** (`wakeMembership()`, the same `wakeMu`-guarded close/consume-and-replace idiom as the per-server wakes) when it registers a key new to `h.clients` while the loop is polling (`h.polling`), and `waitForNext` always includes that channel as a wait case (tagged `waitCase.isMembership`, consumed via `membershipWakeChannel`/`consumeMembershipWake`). A membership win carries no per-server bookkeeping (no `eventDrivenServers` entry — a brand-new server has no cache to invalidate — and no generation touch); the next pass re-derives the server list, which then includes the new key. **Storm guard**: a warm resubscribe (snapshot present in `previousJSON`) fires no wake, and an already-registered key fires no membership wake — dedup and cadence are unchanged; `removeClientLocked` deletes an emptied key, so unsubscribe→resubscribe of a genuinely-left server re-fires membership and recovers freshness. The lock order is `h.mu → wakeMu` at every nesting site.
- **Writer-pump cleanup** (mirrors `relay.go`). The per-connection writer pump drains `sc.ch` to the socket. On a `WriteMessage` failure it `cancel()`s AND sets a short read deadline (`stateWSCleanupWait = 100ms`) on the connection, so the read loop's parked `conn.ReadMessage()` returns promptly and runs `dropStateConn` cleanup instead of leaking the goroutine + its hub subscriptions until TCP teardown. The connection's lifecycle context is rooted at `context.Background()` (NOT `r.Context()` — the request context may be cancelled at the WS upgrade / hijack).

### Poll loop — bounded per-server fan-out (`poll()`)

Each tick re-derives the work-list from `h.clients` keys and runs the shape **fold → sweeps/reap → global broadcasts → bounded dispatch → `waitForNext`**. Per-server fetch work never runs on the poll goroutine itself: each server's per-tick work (cache check → `FetchSessions` → `attachPRStatus` → waiting-push/auto-name/operator-queue advance → sessions marshal/dedup/emit → previews → order bootstrap) is a `pollServerUnit(server, invalidateCache)` executed on a worker goroutine bounded by `ssePollConcurrency = 6` (the `pollSem` semaphore, acquired non-blocking at dispatch — parallelism across servers, never within one; within a unit execution stays serial, `capturePreviews`' one exec per expanded window included). Each unit **emits its own server's events as it completes** (`sessions` dedup + fan-out — with the per-server ack-ordering invariant, `previousJSON[server]` updated before that server's fan-out — plus `preview` and `session-order` bootstrap), never batched at end of tick, so one slow server cannot delay another server's snapshot.

**Single-flight is hub-level** (`pollInFlight`): a server has at most one unit in flight — across ticks AND across poll-goroutine restarts (a fresh poll goroutine re-spawned by `addClient` sees a straggler's entry and does not double-dispatch; the straggler's late result folds harmlessly). A tick skips dispatching an in-flight server and leaves its pending cache-invalidation flag un-consumed for its next dispatch. The in-flight set, semaphore, and results channel live on the hub, not in `poll()`-local state; `perServerGen`/`eventDrivenServers` stay owned by the poll goroutine (the invalidation flag is consumed at dispatch and handed to the unit as an immutable value — workers never touch the two maps).

**Join-free results flow**: a completing unit delivers a `pollUnitResult` (server, `polled`/`dead` outcome, live waiting-push/auto-name keys) to the buffered `pollResults` channel (capacity = the bound, so delivery never blocks) and signals the coalescing **results wake** — the membership-wake close/replace idiom under `wakeMu`, via the `signalResultsWake`/`resultsWakeChannel`/`consumeResultsWake` trio. The poll goroutine folds every completed result at the top of the next tick (`foldPollResults`) and runs the end-of-tick consumers over the folded view: the `waitingPush`/`autoName`/`operatorQueue` retain sweeps keep their observed-server scoping exactly (a server counts as observed only when its unit's result folded — successfully polled, or confirmed gone; an in-flight or transiently-failed server is in neither set and its episodes survive), and the dead-server reap stays a single block under one write lock over folded dead results (§ Dead-server `gone` reap below; full contract in [tmux-sessions](/run-kit/tmux-sessions.md) § SSE Poll-Set Lifecycle). A tick whose wait ended SOLELY on unit completions (`waitForNext`'s `resultsOnly` return) folds without dispatching — dispatching on completion alone would self-perpetuate, so re-poll cadence comes from each server's own wakes and the safety timer. The host-global broadcasts (`metrics`, `services`, `code-server`) are emitted every tick AHEAD of per-server dispatch, unchanged in shape (pre-rendered once, cached-slot update + `broadcastGlobalLocked` under `h.mu`), so a hung server delays neither them nor the sweeps — unit completion's results wake unparks the loop for a prompt fold rather than waiting out the 12s safety timer.

### Dead-server `gone` reap

The poll-set reap on a dead-server fetch error (memory: `tmux-sessions` § SSE Poll-Set Lifecycle) also fans an in-band `gone` frame: when a server unit's fetch returns `tmux.IsServerGone`, the unit reports `dead` on its `pollUnitResult`, and the tick-top reap block (over folded results, under one write lock) sends `hubEvent{gone: true, key: server}` (rendered as `{"op":"gone","kind":"server","key":...,"reason":"server-exited"}`) to that server's subscribed connections before deleting it from every per-server map. A later re-subscribe re-registers the server cleanly. This is the `gone` frame's ONLY emit path. Full reap mechanics + concurrency contract: `tmux-sessions.md`.

### Frontend `StateSocket` client (`src/lib/state-socket.ts`)

One `StateSocket` per tab owns the `/ws/state` WebSocket. On open it sends `hello` (conn id via `crypto.randomUUID()`) then resubscribes every active subscription (each re-acks with a fresh snapshot — the reconnect recovery path); on drop it reconnects with **exponential backoff 1s → 15s cap**. Its client heartbeat + wake probes (§ Client heartbeat + wake probes below) detect a silently half-open socket so this reconnect machinery can run — `ws.onclose` never fires for a TCP connection dropped during machine sleep while `readyState` stays `OPEN`. It exposes `subscribeServer`/`unsubscribeServer`/`subscribeMetrics`/`unsubscribeMetrics` (idempotent, **ref-counted** by a stable id `"server:<name>"` | `"metrics"` so overlapping consumers — e.g. the current server plus an expanded sidebar group naming the same server — share one wire subscription), a `sendPreviewScope(server, expanded)` in-band twin, and `onEvent`/`onAck`/`onGone`/`onConnectionChange` callbacks that demux the envelope back into `(kind, type, key, data)`. It tracks a `reqToKey` map to route an `ack` back to its subscription's kind/key, and **drops the pending `reqToKey` entry on an `error` frame** so a rejected subscribe doesn't leak a row. Pure/testable (injectable conn id; the WS is the standard browser global). The **Vite dev proxy carries a `/ws` entry with `ws: true`** (`app/frontend/vite.config.ts`) so the upgrade is forwarded in dev.

### Client heartbeat + wake probes (both sockets)

Both per-tab sockets — `StateSocket` (`src/lib/state-socket.ts`) and `RelayMux` (`src/lib/relay-mux.ts`) — carry the SAME client-initiated liveness layer (260723-rma2), the minimal detection that converts a silently half-open socket ("deaf forever") into "reconnected within seconds of wake". Server-initiated protocol-level WS pings cannot substitute: browsers answer them in the network stack, invisibly to JS, so the client would still trust its dead socket. Everything below feeds the EXISTING reconnect machinery (backoff + blind resubscribe on state; re-issue `open` per live stream on the mux) — there is no separate recovery path.

Shared constants (named, no magic numbers): `HEARTBEAT_INTERVAL_MS = 30000`, `LIVENESS_TIMEOUT_MS = 2 * HEARTBEAT_INTERVAL_MS` (~60s), `WAKE_PROBE_TIMEOUT_MS = 3000`, `RECONNECT_BASE_MS = 1000`. Backoff caps differ per socket (state 15s, mux 30s).

- **Heartbeat**: while the socket is `OPEN`, send `{op:"ping"}` every `HEARTBEAT_INTERVAL_MS`. `lastInbound` liveness is tracked on **every** inbound frame in `onmessage` — events/acks/`gone`/`error`/`pong` on state, binary data AND text control frames on the mux (a busy terminal never needs a pong to prove liveness); pongs are not individually correlated.
- **Outstanding-ping liveness clock (hidden-tab guard)**: death is judged by `outstandingPingSince`, NOT plain `now - lastInbound`. The clock starts when a ping is actually sent with none outstanding; ANY inbound frame clears it (`= null`); the check at the top of each heartbeat tick force-closes when a ping has been outstanding ≥ `LIVENESS_TIMEOUT_MS`. This is immune to background-tab timer throttling by construction — the clock never starts without a real send, and a live server answers a sent ping regardless of when throttling let it out, so delayed self-pings can never force-close a healthy socket. One timer (no separate check timer).
- **Force-close, distinct from permanent `close()`**: a private `forceClose()` closes the raw WebSocket **without** setting `closed = true` and **without** nulling `ws.onclose`, so the normal `onclose` → `scheduleReconnect()` handler fires (a local `ws.close()` fires `onclose` client-side even when the TCP peer is gone) and drives cleanup + reconnect. Public `close()` additionally tears down heartbeat/deadline timers and wake-probe listeners.
- **Wake probes**: instance-owned, environment-guarded listeners for `document` `visibilitychange` (→visible only), `window` `online`, and `window` `pageshow`, registered on `connect()` and removed on `close()`. Guards check both `typeof window/document !== "undefined"` AND `typeof …addEventListener === "function"` so a stubbed `window` (unit tests) and non-browser contexts never throw. On a wake event: (a) a pending reconnect backoff timer → clear it, reset `backoff` to `RECONNECT_BASE_MS`, and `connect()` immediately (waking mid-backoff must not wait out a 15s/30s cap); else (b) socket `OPEN` → send a probe `{op:"ping"}` and arm a `WAKE_PROBE_TIMEOUT_MS` deadline that `forceClose()`s on expiry, cancelled by any inbound frame.
- **Mux gating (idle-stays-closed preserved)**: `RelayMux`'s heartbeat runs only while the socket is `OPEN` AND `streams.size > 0`, reconciled from a single idempotent `syncHeartbeat()` called at every entry/exit point (`onopen`/`openStream`/`closeStream`/stream-`closed`/`onclose`/`close()`); it stops when the last stream closes and never connects a closed socket. The mux wake probe no-ops when `streams.size === 0`, so an idle mux (the deliberate zero-stream, no-socket state) is never resurrected. `RelayMux.handleControl` swallows the id-less `{op:"pong"}` (liveness bookkeeping already ran on frame receipt) **before** its `typeof msg.id !== "number"` early-return.

### `session-context.tsx` transport (seams above the socket)

`session-context.tsx` holds one `StateSocket` in `socketRef` (survives effect re-runs / StrictMode remounts) — there is no EventSource pool and no dedicated host-metrics EventSource effect. `attachServer` and every `subscribe*` helper sit above the transport seam, so consumers are transport-agnostic. The `attachedSet` drives a diff effect that `subscribeServer`/`unsubscribeServer`s; a `metrics` subscription is opened when `attachedSet` is empty (the `/` Host case) and dropped when a server is attached (the host-global `metrics` event rides every server subscription). Acked snapshots + events route into the existing slice-update paths; version/update/order/preview/`setPreviewScope` behave identically, and `setPreviewScope` sends **in-band** over the socket (no POST-races-the-stream window). The provider also maintains a **per-server receipt tick** (`receiptTicksRef`, a ref-backed `Map<server, number>`) bumped on every server-scoped receipt — the `onEvent` kind-`server` branch and the `onAck` server-snapshot branch — and exposed as the stable, imperative `getServerReceiptTick(server)` context method (monotonic for the provider's lifetime, `0` for a never-seen server; the `StandaloneSessionContextProvider` no-ops to `0`): the freshness signal the window-switch bounce verdict reads to tell post-click evidence from a frozen pre-click snapshot ([ui/terminal](/run-kit/ui/terminal.md) § Window-Switch Slide Transition → Confirmation-gated motion). (260823-ke9i)

- **Connection dots = socket-connected AND subscription-acked** (with the existing 3s debounce). Per-server `isConnected` flips true on that server's subscription `ack`; `ackedServersRef` tracks acked subscriptions and an `applyServerConnected` pass publishes `isConnected` on every socket connection-state change. Reconnect nuance (nice-to-have): on socket re-open an already-acked server flips Connected before its fresh re-ack lands (ms-scale window). See ui/top-bar.md § Chrome (Top Bar) connection dot and ui/updates-and-notifications.md § Reload guard.
- **StrictMode safety**. `main.tsx` wraps in `<StrictMode>` (the real dev + e2e runtime), which double-mounts the provider. The socket-construction effect destroys+recreates the `StateSocket` across the remount, but the guard refs (`metricsSubscribedRef`, `subscribedServersRef`, `ackedServersRef`) survive in refs — so mount 2 would see its guards already true and never re-subscribe on the FRESH socket, permanently losing the metrics subscription on `/` (Host dot dead forever; when this tab is the hub's only client the poll loop never starts). Fix: the socket effect's **cleanup resets all three guard refs**, so the remount re-subscribes cleanly. StrictMode-wrapped unit tests cover metrics + server re-subscription.
- **`onGone` releases the subscription**. On a `gone` for a still-attached server, `onGone` deletes it from `ackedServersRef` + `subscribedServersRef` AND calls `socketRef.current.unsubscribeServer(key)`, releasing the StateSocket ref-count so the diff effect re-subscribes cleanly when `attachedSet` recomputes (via `onGone`'s `fetchServers`) and the server is still desired — no permanently-dead UI for a server the user restarts.


## Terminal Relay — `/ws/terminals` mux

**One `/ws/terminals` WebSocket per tab carries ALL pane relay streams.** There is no `GET /relay/{windowId}` and no `handleRelay` (decision D2 — the frontend is the sole consumer, so there is no API-compat contract to keep; constitution IV). A board with N panes holds ONE terminals socket, so there is one reconnect path and one upgrade handshake regardless of pane count. (260717-803u-relay-mux) Combined with the state socket the tab's steady-state connection budget is a **fixed 2 WebSockets** (`/ws/state` + `/ws/terminals`) and zero SSE. **Why**: this is connection hygiene (TCP count, handshake count, one backoff loop) — the HTTP/1.1-pool relief comes from the state socket (an established WS holds no pool slot, but every extra WS *handshake* can block behind a saturated pool on Firefox/WebKit — spike `docs/findings/socket-pool-accounting.md`). Same port as the API, no separate relay port; `gorilla/websocket` + `creack/pty`. Handler in `app/backend/api/terminals_ws.go` (sibling of `state_ws.go`); `relay.go` holds only the shared `upgrader` + `forceTERM`, both consumed by the mux.

### Wire protocol (binary data frames + JSON control ops)

**Binary data frames `[u32 BE streamId][payload]`** in both directions (server→client PTY output, client→server keystrokes). **JSON text frames for control**:

- Client → server: `{"op":"open","id":<u32>,"server":..,"windowId":"@N","cols":<u16>,"rows":<u16>}`, `{"op":"resize","id":<u32>,"cols":<u16>,"rows":<u16>}`, `{"op":"close","id":<u32>}`, `{"op":"ping"}` (the client liveness heartbeat — **carries NO `id`**, § Client heartbeat + wake probes) (260723-rma2).
- Server → client: `{"op":"opened","id":<u32>}`, `{"op":"closed","id":<u32>,"code":4004|4001|1000,"reason":..}`, `{"op":"pong"}` (answers a `ping` — **no `id`**; marshalled from the shared `pongFrame` and enqueued via `tc.enqueueControl` onto the reserved control pseudo-stream so the single writer performs the write with short-frame priority).

Stream IDs are **client-allocated u32s, unique within a socket connection** (the `open` op carries the client's chosen id). A malformed control frame is ignored (the socket stays live, forward-compat); an unknown op **other than `ping`** is ignored (forward-compat), so an old server silently ignoring a `ping` is benign. **Stream-level failures surface as per-stream `closed` control events carrying codes `4004`/`4001` — the SOCKET itself never closes for a stream-level failure** (`4004` = session pick (pin-session-first / ResolveWindowSession) or SelectWindowInSession failed / bad window ID; `4001` = `pty.StartWithSize` failed; `1000` = graceful client `close` op or PTY EOF).

### Per-stream lifecycle

Each stream runs resolve → session-scoped select → direct attach → PTY pump. `startStream` runs on the socket read loop but does only cheap synchronous work there — validate the (already JSON-decoded) `windowId` via **`validate.ValidateWindowID`** (the same validator `decodeWindowID` wraps, so the REST and mux entry points share one validator and cannot drift — bug #205; the mux path needs no percent-decode since its id arrives decoded in JSON, not a URL segment) and **register a PLACEHOLDER stream (queue + closed chan, nil ptmx) under the connection mutex** — then dispatches the blocking tmux work to a goroutine (`attachStream`), so a resolve (≤5s) + select + attach never serializes behind other panes' keystrokes/opens (rework S2). The placeholder-first registration makes duplicate-id checks and racing resize/close ops deterministic (a resize/close arriving mid-attach finds the placeholder). `attachStream`:

1. **Picks the attach session with a pin-session-first preference** (260718-co9z-link-based-board-pinning) — a board-pinned window is LINKED into BOTH its home session AND its single-window `_rk-pin-*` pin-session, so the stream probes `HasSession` on the derivable `PinSessionName(windowID)` FIRST and attaches the pin-session when it exists; otherwise `s.tmux.ResolveWindowSession(ctx, server, windowID)` (5s timeout) resolves the window's HOME (non-pin) session. Attaching the pin-session (whose sole window is permanently active) gives the stream an independent current-window pointer and leaves the home session's active-window pointer untouched — merely viewing a pinned window never moves the home pointer. A missing/unresolvable window → per-stream `closed` 4004, socket open. (`ResolveWindowSession` does not assume "exactly one session" — under dual membership it re-resolves a `_rk-pin-*` naive result to the non-pin home; see `tmux-sessions.md` § Impact on Other Operations → `ResolveWindowSession`.)
2. **Session-scoped select** via `s.tmux.SelectWindowInSession(session, windowID, server)` scoped to whichever session step 1 picked — a bare `select-window -t @N` is ambiguous inside a tmux session group, so select and attach must agree on the same session (for a pin-session the select is a no-op in effect, its sole window already active, but the path stays uniform). Failure → `closed` 4004.
3. **Initial size rides the `open` op** — `pty.StartWithSize` at the open frame's `cols`/`rows` (falls back to 80×24 on zeros) — no wait-for-first-`resize` round trip. The managed-conf reload (`reloadConfigForAttach` — true-color terminal-overrides on a server started before the daemon's conf refresh) is **off this path**: at most one attempt per server per daemon lifetime behind a synchronous per-server once-guard (`Server.attachReloaded`, a `sync.Map`), with the managed-only gate check, the reload, and the legacy-option sweep all in one goroutine — the attach goroutine pays zero tmux execs (the switch mask lifts on the first PTY byte, so any synchronous exec here sits directly under the waiting logo). A managed-check read failure fails closed AND releases the guard (a later attach retries); an external verdict consumes it (adopt sources the conf itself when a server is adopted); the seams (`attachIsManaged`/`attachReloadConfig`/`attachMigrateLegacy`) are captured before the spawn so a test restoring them never races an in-flight goroutine. The attach itself still carries `-f confPath`, so a server rk starts gets the conf at client birth regardless. Then `tmux [-L server] attach-session -t <session>` via `creack/pty` with `forceTERM` (TERM=xterm-256color). Attach failure → `closed` 4001. (260904-71yx)
4. **Publishes the attach into the placeholder under the lock** (if the stream was torn down mid-attach, the just-started attach is cleaned up rather than orphaned), then **enqueues `opened` onto the stream's OWN bounded queue BEFORE starting the PTY reader** (rework M2). Channel FIFO + the scheduler's short-frame priority then guarantees the client sees `opened` before the first data frame — the ordering the client's deferred-reset re-arm depends on (data-before-`opened` wiped the reset). A `closed` for a FAILED open rides a reserved control pseudo-stream (`controlStreamID = math.MaxUint32`), never a real pane id — a failed open produced no data, so its `closed` has no ordering concern.
5. **Per-stream cleanup** (client `close` op, PTY EOF, socket teardown): `sync.Once`-guarded cancel + ptmx close + attach-process **kill AND reap** (`killAndReapAttach` — kill then `cmd.Wait`, the `internal/tmuxctl` contract), remove from the registry — no orphaned attach processes, no `<defunct>` zombies, no parked `os/exec` watcher goroutines. Exactly one goroutine owns each `Cmd`'s `Wait`: teardown's `sync.Once` for a published cmd; the publish-race branch (stream torn down mid-attach, step 4's cleanup) reaps its own never-published cmd in place, since `st.cmd` is still nil there and teardown cannot see it. Socket teardown tears down every stream. (260904-71yx)

**The relay answers terminal identification on the browser terminal's behalf.** tmux feature-detects each attached client with Device Attributes queries (DA1/DA2) on its tty. The per-stream PTY pump answers them at the relay — a `daFilter` (`terminals_da.go`) writes the canned xterm.js-equivalent reply back to the ptmx and strips the query from the browser-bound frame, so xterm.js never sees or answers one and replies are exactly-once per attach. Full mechanics (query set, replies, bounded chunk-boundary carry-over) in [tmux-sessions](/run-kit/tmux-sessions.md) § Terminal Relay; the frontend complement in [ui/terminal](/run-kit/ui/terminal.md) § Terminal Write Batching. (260801-f715-relay-device-attributes-responder)

### Write path — per-stream bounded queues + fair scheduler (D3, a v1 protocol requirement)

**Per-stream bounded send queue (`streamQueueDepth = 8` × `streamFrameSize = 4096B`) drained by a SINGLE writer goroutine** that schedules control/short frames (`shortFrameMax = 256B`; a keystroke echo) ahead of bulk output and round-robins across ready streams — **never FIFO across streams** (gorilla forbids concurrent writes, so all output funnels through this one writer). **This is a protocol requirement, not an optimization** (decision D3): spike 2 measured a shared FIFO at **1.66s** interactive echo p50 under a co-stream 1 Mbps flood vs **32ms** with per-stream queues + this scheduler at identical goodput (`docs/findings/relay-mux-hol.md`). The per-stream PTY reader is the queue producer; a **full queue PAUSES that stream's PTY reader** (backpressure into tmux's per-client buffering) and **NEVER drops bytes** (dropping mid-stream corrupts VT state). The kernel TCP send buffer is the shared tail after the scheduler (default autotuning acceptable — the scheduler bounds everything above it). `writeFrame` is an **injectable seam** (production writes the socket; the HOL unit test substitutes a paced writer). `drainReady` is a single short/control-priority pass with a round-robin bulk handoff per stream; the exact RR variant (plain vs deficit) is unobservable to the pinned test bound (D8).

### Frontend — `RelayMux` singleton + `TerminalClient` port

Frontend consumes the mux via a `RelayMux` singleton (`app/frontend/src/lib/relay-mux.ts`) — see `ui/terminal.md` § Terminal Write Batching and § Terminal Relay (frontend). `terminal-client.tsx` creates no socket of its own; the stream handle is surfaced through the `wsRef` seam via a WebSocket-shaped adapter (`readyState`/`send`/`close`). Socket-level reconnect is owned by `RelayMux` (exponential backoff, one loop for the whole tab); a stream-level `closed` is handled per-pane (4004 → `onSessionNotFound` redirect; non-4004 → print `[reconnecting…]` + one probed re-open, else `[disconnected]`). RefreshButton is the manual full-page recovery affordance. `RelayMux` also carries the client heartbeat + wake probes (§ Client heartbeat + wake probes), stream-gated so an idle mux stays closed, which detect a half-open socket and drive this reconnect loop.

**No startup sweep, no ephemeral** (260602-qn62): the relay attaches directly to a durable session (the window's pin-session when pinned, else its home session) — there is no per-connection ephemeral relay session and no in-server session class to reap. See `tmux-sessions.md` § Terminal Relay.

### HOL scheduler Go unit test (`terminals_ws_test.go`)

`TestScheduler_EchoNotHeadOfLineBlocked` ports the spike harness with **no real network**: the scheduler is wired to a paced `writeFrame` (sleeps ∝ bytes written), stream A floods 4096B frames, a stream-B echo frame is enqueued, and the test asserts B is written within a small **bounded number of A frames** (pins the observable non-FIFO fairness bound, not the exact RR algorithm). Relay behaviors are asserted per-stream against `/ws/terminals`: `opened` precedes the first data frame (`TestTerminals_OpenedPrecedesData`, pinning M2), initial-size attach + TERM forcing (`_InitialSizeAndTERM`), `resize` sets the PTY size (`_ResizeSetsClientSize`), client `close` → `closed` 1000 (`_ClientCloseYields1000`), bad/missing window → `closed` 4004 with the socket still open (`_BadWindowIDClosed4004`/`_MissingWindowClosed4004`), and `-race`-clean across the terminals+scheduler suite. The reap contract is pinned by `TestStreamTeardownReapsAttachChild` (teardown on a live pty child leaves `ProcessState` populated — `Wait` returned, no zombie — and a second teardown is a safe no-op) and `TestKillAndReapAttach` (the shared helper both kill sites call: nil-safe on nil cmd / nil `Process`, kills-then-reaps a live child). The reload gate is pinned by `TestReloadConfigForAttach` (async proof via an unbuffered-channel stub — a synchronous reload would deadlock the attach path; external skip; managed-check-failure skip with guard release + retry; once-per-server; distinct servers each reload) and `TestReloadConfigForAttachLegacySweep` (sweep behind the same gate, at most once per server).


## Design Decisions

### Tutorial companions are SPA static files, not a route or extraction mode
**Decision**: Ship the tutorial companions in `app/frontend/public/tutorial/`
and serve them at `/tutorial/…` through the SPA regular-file branch.
**Why**: The pages remain version-locked to the binary and fit the fixed-route
constitution while using the same static-file path as other Vite public assets.
**Rejected**: A Go handler with a new route; an `rk skill tutorial --pages`
extraction mode; externally hosted pages; agent-generated companion pages.
*Introduced by*: 260902-6uu0-rk-skill-tutorial-topic

### Notify events are broadcast-only, never cached
**Decision**: `broadcastNotify` fans a pre-rendered host-global event to current state connections without writing a cached slot; `replayGlobalSlots` never emits notify events.
**Why**: a notification is a moment-in-time signal, and the state socket reconnects after daemon restarts and sleep/wake. Replaying the last event would surface a stale OS notification on every reconnect.
**Rejected**: a cached last-notify slot; a server-side notification ring paired with client seen-state.
*Introduced by*: 260902-ziki-shell-os-notifications

### Present addresses key content by server and root hash
**Decision**: Presented files use `/present/{server}/{roothash}/{path}`, where `roothash` is a 12-hex prefix of the sha256 of the absolute serve root; request hashes may be 8–64 lowercase hex characters and must match exactly one declared root.
**Why**: The serve root and relative path identify the content, while a window id and dense web-tab slot identify only a current presenter position. Content-keying keeps the stored URL valid across slot renumbering, window swaps, and removal of one of several presenters.
**Rejected**: Stable per-tab ids, which conflict with the dense indexed family; filesystem paths in URLs, which disclose host layout; content hashes, which make live-file refresh semantics awkward; window-scoped hashes, which expire when that window closes even if another window declares the root.
*Introduced by*: 260901-ei4t-present-url-server-root-hash

### Resolve presented roots from live tmux declarations
**Decision**: Each content-keyed request derives the candidate root set from all live `@rk_win_web_<n>_root` options on the named server in one `list-windows -a -F` call; there is no registry, cache, or disk-backed presented-root store.
**Why**: The declaration set is already authoritative in tmux. Request-time derivation makes a root serve exactly while at least one live window declares it and avoids garbage collection for windows removed outside rk.
**Rejected**: A maintained server-scoped array of presented roots, which duplicates derivable state and can retain stale roots after out-of-band window death.
*Introduced by*: 260901-ei4t-present-url-server-root-hash

### `@rk_win_note` write rides the unified options endpoint
**Decision**: `@rk_win_note` is an allowlisted key on `POST /api/windows/{windowId}/options` rather than a dedicated `/note` route.
**Why**: the endpoint already owns per-key validation, the validate-all-then-execute batch, and the SSE hub wake; Constitution IV resists new surface.
**Rejected**: a dedicated `POST /api/windows/{id}/note` — duplicate plumbing for one key.
*Introduced by*: 260824-bb5n-tab-status-note

### Options allowlist accepts only scope-prefixed key names
**Decision**: the `POST /api/windows/{windowId}/options` allowlist accepts only the `@rk_<scope>_<name>` key names; the pre-rename legacy keys are rejected 400.
**Why**: dual-read exists for tmux-substrate writes made outside rk's binary (agent/operator text, stale scripts); rk's own API is a writer, and writers use the new names only.
**Rejected**: accepting legacy keys on the API and rewriting them to the new names — extends the transition surface for no external writer.
*Introduced by*: 260828-3o5d-rk-option-scope-prefix-rename

### The server stamps the note's epoch prefix

### One module-level hub polls per server; clients are indexed by server key
**Decision**: a module-level hub deduplicates polling across tabs (one `FetchSessions()` per server per interval). ### Hub wakes gate new-entry allocation on a live subscription, never a tmux existence check
**Decision**: `sseHub.wake(server)` creates a NEW `h.wakes` entry only when `h.clients[server]` is non-empty; a name with neither clients nor an existing entry is dropped without allocating, while an existing entry (any ever-polled server) accepts the wake even client-less — the pending closed channel fires on resubscribe. The check nests `h.mu.RLock → wakeMu` (the reap loop's lock order), holding the RLock across the allocation so a concurrent last-client removal cannot slip between check and write. **Why**: only poll-set servers ever have wake entries consumed/reaped, so entries for arbitrary names would live forever — and `/api/servers/wake` accepts any syntactically valid name from any local process; but dropping ALL client-less wakes would lose a wake racing a brief state-socket reconnect, deferring the repaint to the 12s safety poll. **Rejected**: a tmux server-existence check (a subprocess per wake, still leaks for real-but-unwatched servers); dropping every client-less wake (loses reconnect-window wakes); bounding/aging the map (complexity for no gain). *Introduced by*: 260902-0ccm-tab-cli-sse-wake.

### Membership wake companion to the per-server wake
**Decision**: cold-subscribe freshness rides TWO triggers — `h.wake(key)` from the subscribe-ack path when the ack finds no `previousJSON[key]`, plus a hub-level membership wake fired by `addClient` for keys new to `h.clients` while polling, always waited on by `waitForNext`.
**Why**: `waitForNext` selects only over wake channels for servers in the list snapshot taken before parking, so a per-server wake alone cannot unpark the loop for a server absent from that list; the membership wake is the minimal mechanism that reaches that shape.
**Rejected**: rebuilding wait cases dynamically mid-wait (structural — deferred to the poll-loop rework); waking ALL existing keys on any subscribe (wake storm, defeats coalescing); shortening the safety interval (papers over the hole, keeps worst-case latency).
*Introduced by*: 260904-jjda-ssehub-races-cold-subscribe-wake

### Join-free poll tick: async per-server units + fold-at-tick-top + results wake
**Decision**: the poll goroutine dispatches per-server units and proceeds to `waitForNext` without joining; unit results arrive on the buffered hub-level `pollResults` channel, fold at the top of the next tick, and unit completion signals a coalescing results wake (the membership-wake close/replace idiom) so folding, the retain sweeps, and a dead server's `gone` frame run promptly. A wait ended solely by unit completions yields a results-only tick that folds without dispatching.
**Why**: a full `WaitGroup` join would re-introduce head-of-line blocking at the tick boundary — one slow unit (worst case tens of seconds of inner exec deadlines) would park the loop, so a woken fast server's next snapshot and the `gone` frames would wait on the straggler. Join-free, nothing ever waits on a slow server: fast servers re-poll on their own wakes while the straggler runs, and its skipped ticks are guarded by hub-level single-flight.
**Rejected**: full per-tick join (simplest, but the tick re-arm waits on the slowest unit — the exact server-storm incident shape); a budgeted join / per-tick time budget (bounds the wait but still delays sweeps and `gone` frames up to the budget every straggler tick, and adds a tuning knob the join-free shape does not need); per-server poll goroutines with per-server waits (strongest isolation, but a much larger rework of `waitForNext`/`selectFirst` and the safety-timer model — not needed for per-unit emission or broadcast independence).
*Introduced by*: 260904-8jux-poll-loop-bounded-concurrency

### Poll fan-out bound is a named constant (`ssePollConcurrency = 6`)
**Decision**: concurrent per-server poll units are bounded by the package constant `ssePollConcurrency = 6` (beside `safetyPollInterval`), enforced by the `pollSem` semaphore acquired non-blocking at dispatch; the bound is not settings-registry-exposed.
**Why**: bounds daemon fork pressure during server storms (a `go test` run spawning tmux test servers at >1/s); 6 covers realistic live-server counts while keeping worst-case concurrent tmux execs low; convention over configuration (Constitution VII) — no settings key without demonstrated need.
**Rejected**: settings-registry exposure (trivially tunable as a constant); a `GOMAXPROCS`-derived bound (the workload is subprocess-bound, not CPU-bound).
*Introduced by*: 260904-8jux-poll-loop-bounded-concurrency

### Consistent locking over cache-ownership move
**Decision**: every `h.cache` access — the poll-side invalidate/read/write, the `attachPRStatus` in-place mutation of the cached slice, and the handler-side reads (`sendCachedPreviewLocked`, dead-server reap) — runs under `h.mu`, keeping the cache map shared between the poll goroutine and handler goroutines. `h.mu` is never held across `FetchSessions` or `capturePreviews` (subprocess execs) — lock hold times stay bounded to in-memory operations.
**Why**: surgical fix for the concurrent-map-access crash class (a detected concurrent map read/write is a Go runtime throw, killing the daemon); keeps the follow-on structural poll rework's rebase clean.
**Rejected**: cache-ownership move into the poll goroutine with copy-out — a deep copy per tick or COW discipline is structural work with no incremental safety over consistent locking here.

### The proxy forwards `X-Forwarded-Host` and 308-redirects the bare `/proxy/{port}`
**Decision**: every per-port `ReverseProxy`'s `Rewrite` hook calls `r.SetXForwarded()` (upstreams see `X-Forwarded-{For,Host,Proto}` derived from the inbound request), and `handleProxy` 308-redirects `/proxy/{port}` → `/proxy/{port}/` (query preserved) before proxying.
**Why**: code-server's `authenticateOrigin` compares the browser's `Origin` host against `Forwarded` → `X-Forwarded-Host` → `Host`; without the forwarded host it 403s every WebSocket handshake and POST while same-origin GETs load — "editor loads, then sits disconnected forever". **Rejected**: trusting `Host` alone (it already carries the upstream's host after `r.Out.Host = target.Host`); code-server-specific handling in the proxy (the forwarded headers + redirect are correct for every `/proxy/` consumer).
*Introduced by*: 260811-k3vp-right-panel-code-lens

### The code-server signal is a dedicated host-global event carrying reachability only, fed by a TTL-cached probe

**Why**: env config is process-static, so the every-tick broadcast is dedup-stable client-side (raw-payload compare collapses it to real transitions), and the replay slot serves late joiners; localhost refused fails fast and the dial timeout bounds a filtered listener, so the poll loop never stalls.
**Rejected**: piggybacking the `metrics` frame (its snapshot type is owned by `internal/metrics` — a dedicated event mirrors the services precedent without touching either contract); exposing the signal on `GET /api/health` (two mechanisms for one fact); an HTTP reachability probe instead of the bare TCP dial (body/redirect handling for zero gating value).
*Introduced by*: 260811-k3vp-right-panel-code-lens, 260811-a2bo-daemon-code-server-stable-route

### `Content-Length` header and `resp.ContentLength` field are updated together, unconditionally, in every body-replacing `ModifyResponse` branch
**Decision**: every branch of `makeModifyResponse` that swaps in a rewritten body sets `resp.ContentLength` AND `resp.Header.Set("Content-Length", …)` to the final wire length, unconditionally (not gated on "body shrank"), with an explicit `Set` rather than `Del`. Header-sync lives in each branch next to its body swap rather than in a shared tail, mirroring the branch structure (the gzip-fallback branch already owns its `Content-Encoding` delete there). Mechanics in § Proxy Content-Length header sync.
**Why**: a rewritten body is a new entity, and `httputil.ReverseProxy` forwards the upstream **header map** verbatim, so setting only the struct field leaves the client reading a stale (larger) length against a shorter body: the browser aborts with `ERR_CONTENT_LENGTH_MISMATCH` and the iframe renders blank. Explicit `Set` over `Del`: deleting the header would delegate framing to chunked encoding, whose behavior varies across HTTP versions and is not directly assertable; an explicit length is deterministic and testable. Unconditional: `header == body length` is an unconditional invariant, and the blanket `Set` additionally gives a chunked upstream that arrived with no `Content-Length` an accurate one. The diagnostic lesson is recorded because it cost the discovery: `curl -w '%{http_code}'` returns `200` (headers are fine), so only a full-body read exposes the truncation — smoke checks pass while every browser shows a blank frame.
**Rejected**: disabling HTML rewriting, and forcing chunked-only responses — both change proxy semantics far beyond the defect.
*Introduced by*: 260730-op63-proxy-content-length-fix

### Web-tab verbs are POST-only routes
**Decision**: the web-tab family operations are `POST /api/windows/{id}/web`, `POST …/web/{n}/remove`, `POST …/web/{n}/move`, and `POST …/web/{n}/select` — mutations are expressed as path verbs, not HTTP `DELETE`/`PUT`/`PATCH`.
**Why**: Constitution IX forbids `DELETE`/`PUT`/`PATCH`; the CORS allowlist is `[GET, POST, OPTIONS]`, and operation intent belongs in the URL path.
**Rejected**: the ui-state plan's `DELETE /api/windows/{id}/web/{n}` (constitutional violation).
*Introduced by*: 260828-fykg-ui-state-backend-tmux-options

### Backend write-compat shim over the retired web options
**Decision**: the backend translates `@rk_win_url`/`@rk_win_lens` `/options` writes onto the web-tab family (`translateLegacyOptionKeys`), for one release. The Window JSON carries no derived `rkUrl`/`rkType` fields — the frontend reads `layout`/`webTabs`/`webActive`/`codeRoot` directly (iip5).
**Why**: external writers still stamp the retired keys mid-session; translating them at the write seam keeps every reader on one representation. The frontend has no remaining consumer of a derived read — its web tile reads the tab family and writes the active slot directly.
**Rejected**: keeping a derived `rkUrl`/`rkType` read shim after the frontend stopped consuming it (dead marshal-time surface); removing the write translation in the same step (external writers' compat belongs to the cleanup change).
*Introduced by*: 260828-fykg-ui-state-backend-tmux-options; read shim removed: 260828-iip5-ui-state-frontend-layout-code-root

### Terminal relay mux (`/ws/terminals`) with per-stream queues + a fair scheduler — one socket per tab, kept SEPARATE from `/ws/state`
**Decision**: ALL pane relay streams ride ONE `/ws/terminals` connection per tab (binary `[u32 BE streamId][payload]` data frames + JSON `open`/`opened`/`resize`/`close`/`closed` control ops; client-allocated u32 stream ids), so a board holds a fixed 2 WebSockets total (state + terminals); there is no per-pane `/relay/{windowId}` socket and no deprecation shim for one. Per-stream bounded queues feed a single writer running a non-FIFO fair scheduler; a full queue pauses that stream's PTY reader; stream-level failures become `closed` control events (4004/4001), never socket closes; the per-stream resolve+select+attach runs on a goroutine after a placeholder stream is registered under the lock (rework S2); `opened` rides the stream's own queue before data (rework M2); the mux reuses `validate.ValidateWindowID`. Frontend `RelayMux` singleton + `TerminalClient` port — see [ui/terminal](/run-kit/ui/terminal.md) § Terminal Relay (frontend).
**Why**: per-stream bounded queues + a non-FIFO fair scheduler are a v1 requirement, not an optimization: on a muxed socket a shared FIFO gives 1.66s interactive echo p50 under a co-stream flood, vs 32ms with per-stream queues + control/short-frame-priority round-robin at identical goodput (spike 2, `docs/findings/relay-mux-hol.md`) — head-of-line blocking is the mux's one real risk and this fully mitigates it. A full queue pauses the PTY reader (backpressure) rather than dropping bytes because dropping mid-stream corrupts VT state; the pause pushes the stall into tmux's per-client buffering, the same mechanism a stalled per-pane TCP socket exerts. Stream-level failures become `closed` control events because one bad window (4004) or attach failure (4001) must not tear down the other panes' streams — the socket outlives any single stream. No `/relay/{windowId}` shim because the frontend is the sole consumer (personal tool, no API-compat contract; constitution IV — minimal surface). Kept separate from `/ws/state` (D6) because bulk binary terminal output must not share a send buffer/scheduler with state events — the terminals scheduler is tuned for interactive-echo fairness under flood, a concern `/ws/state` does not have. The async attach with a placeholder-under-lock (S2) keeps the per-stream resolve (≤5s) + select + attach off the socket read loop so it never serializes behind other panes' keystrokes/opens, while keeping duplicate-id/racing-resize/close deterministic. `opened` rides the stream's own queue before data (M2) because the client arms its deferred per-stream reset on `opened`, so a data-before-`opened` ordering wiped the reset; channel FIFO + short-frame priority guarantees opened→data.
**Rejected**: shared FIFO across streams (the 1.66s regression); merging into `/ws/state` (D6); dropping bytes on a full queue (VT corruption); a bespoke window-ID validator (would reintroduce the #205 drift — the mux reuses `validate.ValidateWindowID`); a `/relay/{windowId}` deprecation shim.
*Introduced by*: 260717-803u-relay-mux

### Attach-child reap: kill→Wait inside teardown's Once, in-branch reap for the unpublished cmd
**Decision**: every `tmux attach-session` child the relay forks is killed AND reaped through one nil-safe helper (`killAndReapAttach`: `Process.Kill` then `cmd.Wait`, the `internal/tmuxctl` kill→reap contract) — called from `stream.teardown()`'s `sync.Once` for a published cmd and in-place by `attachStream`'s publish-race branch for a cmd that was never published into the stream.
**Why**: `Wait` is load-bearing — without it every closed stream leaves a `<defunct>` zombie PID plus a permanently parked `os/exec` watchCtx goroutine, and at the fork ceiling every exec in the daemon fails at once (the 2026-09-04 incident: ~71 zombies growing per minute of tab navigation). Exactly-one-Wait falls out structurally: teardown is already the single Once-guarded cleanup owner, and the publish-race cmd is invisible to teardown by construction (`st.cmd` still nil). Kill-first means `Wait` returns promptly — an attach client never exits on its own.
**Rejected**: a dedicated per-stream reaper goroutine deferring `Wait` (adds a goroutine per stream to fix a goroutine leak; split ownership invites double-Wait); reaping in `pumpPTY` (the publish race forks a cmd that never gets a pump).
*Introduced by*: 260904-71yx-terminal-relay-reap-gate-reload

### Pre-attach conf reload: fully async behind a per-Server once-guard with error release
**Decision**: `reloadConfigForAttach` takes a synchronous per-server once-guard on the `Server` struct (`attachReloaded`, a `sync.Map` — the `MarkLegacyMigrationAttempt` pattern) and runs the managed-check + reload + legacy-option sweep in one goroutine; the guard entry is deleted on a managed-check read failure so a transient wobble retries on a later attach, and the seams are captured before the spawn so a test restore never races the goroutine. The sweep's own once-guard moves inside the goroutine, taken after the managed gate exactly as before — safe because the per-server reload guard already serializes to at most one goroutine per server.
**Why**: combines the two candidate fixes — zero execs under the switch mask (the mask arms at 300ms and lifts on the first PTY byte, and the old synchronous managed-check + `source-file` pair, two execs with 10s budgets each, sat directly under it) AND no per-attach exec storm feeding the daemon's fork load (the daemon-start `RefreshSweep` already propagates a stale conf to live servers, so per-attach repetition bought nothing). Server-struct storage gives tests free isolation (a fresh `&Server{}` starts unguarded — no reset seam) and the guard's lifetime equals the daemon's by construction.
**Rejected**: hash-stamp comparison per attach (still one synchronous read exec under the logo, plus new stamp-tracking state); pure async with no guard (unblocks the mask but keeps two execs per attach); a package-global guard in `internal/tmux` (needs a `ResetForTest` sibling and shares state across `Server` instances in tests for no benefit).
*Introduced by*: 260904-71yx-terminal-relay-reap-gate-reload

### Client-initiated app-level heartbeat with an outstanding-ping liveness clock — the minimal half-open detection layer for both sockets
**Decision**: both `/ws/state` and `/ws/terminals` carry a client-sent `{op:"ping"}`→`{op:"pong"}` heartbeat plus `visibilitychange`/`online`/`pageshow` wake probes. Death is judged by an outstanding-ping clock (started only on a real ping send with none outstanding, cleared by ANY inbound frame, force-closing when a sent ping has gone unanswered ≥ `LIVENESS_TIMEOUT_MS`), one timer. Force-close is a private path distinct from public `close()`. Wake probes reset backoff to base. The mux heartbeat is stream-gated by a single `syncHeartbeat()` reconciler (runs iff OPEN ∧ `streams.size > 0`). Frontend detail: § Client heartbeat + wake probes.
**Why**: the ONLY missing piece for recovery was DETECTING a silently half-open TCP socket so the already-complete reconnect machinery could run (`ws.onclose` never fires for a connection dropped during machine sleep while `readyState` stays `OPEN`). Client-initiated app-level ping, not server protocol-level WS pings: browsers answer protocol pings in the network stack, invisibly to JS, so they detect death only server-side — the client keeps trusting its dead socket; a client-sent application-level ping/pong is the only thing that drives client-side death detection. An outstanding-ping clock, not `now - lastInbound > timeout`: background-tab timer throttling delays the client's OWN pings, so a plain silence check false-positives on a quiet-but-healthy socket; the clock is immune to throttling by construction (a live server answers regardless of when the ping went out). Force-close is distinct from `close()` because `close()` permanently suppresses reconnect (`closed = true`, nulls `ws.onclose`); the liveness path must instead close the raw WebSocket so the normal `onclose`→`scheduleReconnect` handler fires (a local `ws.close()` fires `onclose` even against a dead peer), driving the existing backoff + blind resubscribe / re-issue-open recovery with no new recovery code. Wake probes reset backoff because waking from a long sleep mid-backoff must not wait out a 15s/30s cap. The mux heartbeat is stream-gated because an idle mux deliberately lets its socket stay closed (zero-stream state), so heartbeat/wake probes must never resurrect it.
**Rejected**: server-initiated protocol-level WS pings alone (auto-answered invisibly to JS); deferring liveness enforcement while `document.hidden` (weaker — a hidden tab with a dead socket goes unreaped until visible, needs extra visibility state); plain `now - lastInbound` (throttling false-positives).
*Introduced by*: 260723-rma2-websocket-liveness-heartbeat-wake-probes

### Server pong rides each handler's existing single writer, best-effort
**Decision**: both `/ws/state` and `/ws/terminals` answer a client `ping` with a shared `pongFrame` (`{"op":"pong"}`) marshalled once and enqueued through the connection's EXISTING single-writer path — `/ws/state` non-blocking on `sc.ch` (drop on a full channel, mirroring the unknown-op error-frame path), `/ws/terminals` via `tc.enqueueControl` on the reserved control pseudo-stream with short-frame priority. One shared `pongFrame` type in package `api`.
**Why**: gorilla/websocket permits one concurrent writer — all frames must funnel through each connection's single writer goroutine; a direct write races the pump. A dropped pong under channel pressure is harmless: pressure means event/data frames are already flowing, and any inbound frame counts as liveness client-side. One shared type because the wire shape is identical on both endpoints, both files in one package (code-quality bans duplication).
**Rejected**: direct write from the read loop (violates the one-writer invariant).
*Introduced by*: 260723-rma2-websocket-liveness-heartbeat-wake-probes

### Pre-render fan-out envelopes once at the broadcast site via a shared `preRendered` helper
**Decision**: each state-socket fan-out producer wraps its event in `preRendered(ev)` (`api/state_ws.go`), which renders the envelope once and returns the raw-bypass form `hubEvent{raw, typ}`; per-server loops render once before the loop. New fan-out producers MUST follow the same idiom — a payload identical across recipients is rendered once, never per writer pump.
**Why**: a broadcast to C connections otherwise costs C identical marshals of the same `eventFrame` (one per recipient's writer pump); the existing `raw` passthrough in `renderEnvelope` already supports verbatim delivery, so the wire bytes stay byte-identical and no render path changes. Keeping `typ` populated on the raw event keeps the channel-full drop logs (`sendLocked`/`sendConnLockedOK`) informative. One named helper states the render-once-and-keep-`typ` idiom in a single place instead of repeating it at nine call sites.
**Rejected**: inline `hubEvent{raw: ev.renderEnvelope(), typ: ev.typ}` at each site (functionally identical, but nine copies of a subtle convention invite drift); caching rendered envelopes in the hub slots (the caches store payload strings; single-recipient replays already render exactly once, so converting them is churn with zero win); converting `preview`/`gone` sends (payloads differ per recipient or ride dedicated render paths).
*Introduced by*: 260811-sqe7-prerender-broadcast-envelopes

### `sshHost`/`sshUser`/`instanceName` ride `GET /api/health`, no new route
**Decision**: the SSH destination + username + display-name override all ride the existing `GET /api/health` response as optional fields (each omitted when empty), rather than a new `/api/config` route. `sshHost` resolves **settings-only, per request** — `settings.Load().SSHHost` (the `ssh_host` key in `~/.config/run-kit/config.yaml`) is the single source; no env form participates (a set-but-ignored `RK_SSH_HOST` is flagged by `rk doctor`). The daemon's username is derived server-side via `os/user.Current()` (once in `NewRouterAndServer`, empty on failure, `SetSSHUser` test seam) as `sshUser`, and `instanceName` reads `settings.Load().InstanceName` per request.
**Why**: the fields need the smallest existing bootstrap surface (Constitution IV / VII — no settings page/route); health already carries `hostname`, is fetched once at mount, and is the only config-shaped GET. `sshUser` is pure derivation (Constitution X — derived, not configured), the missing ingredient for the `${sshUser}@${location.hostname}` deeplink fallback. Settings-only sshHost is one setting surface with no shadowing — a dialog edit can never silently no-op behind an env var, and headless provisioning sets the same `ssh_host` key.
**Rejected**: a new `/api/config` route (new surface, §IV); embedding it in the SSE/state stream (config is static, the stream is live state); requiring the user to configure the SSH username (derivable — Constitution X); an env fallback for `sshHost` (two writers, two truths — the dialog's live-edit promise breaks under shadowing).
*Introduced by*: 260722-6d0f-navbar-open-in-app, 260722-fc3b-ssh-host-fallback-open-logos, 260723-o7q8-settings-dialog, 260823-li54-config-root-registry-core

### `POST /api/open` path validation is scoped to the request's `?server=` via `FetchSessions`
**Decision**: the launch handler validates `path` against the pane cwds + window worktree paths of the `?server=`-scoped `FetchSessions` snapshot (compared after `filepath.Clean`), and `app` against the live `ListApps` registry, before any exec.
**Why**: `FetchSessions` is the canonical server-side derivation (Constitution X — derive, never trust a client-pushed path) already used by every session read, the Open button always acts on the current server's current window, and `?server=` scoping matches every other handler.
**Rejected**: a cross-server sweep of all tmux servers (N× subprocess cost against the 5s route budget for no real caller); trusting the client-supplied path (§I/§X violation).
*Introduced by*: 260722-6d0f-navbar-open-in-app

### The state socket generalizes the client edge; producer signatures stay frozen
**Decision**: the transport touches only the send/route path — `sseClient` is a per-connection subscription set and `hubEvent`/`renderEnvelope` are the send unit — while every producer, collector, and `broadcast*` signature keeps its shape.
**Why**: the poll/dedup/cache machinery is proven in production; confining the transport to the edge keeps the blast radius off it and lets consumers above the `subscribe*` seams stay transport-agnostic.
**Rejected**: reshaping producers around the socket's kind/key envelope (rewrites proven code for no behavioral gain).
*Introduced by*: 260716-qf3j-state-socket

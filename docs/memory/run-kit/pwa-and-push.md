# PWA & Web Push

**Domain**: run-kit

## PWA Layer

**Manifest**: `app/frontend/public/manifest.json` is a static committed file, linked from `index.html` via `<link rel="manifest" href="/manifest.json">`. It specifies `name`/`short_name` "RunKit", `display: "standalone"`, `start_url: "/"`, dark theme colors (`background_color` and `theme_color` both `#0f1117`), and a three-entry icon array (192px, 512px, 512px maskable) pointing at `/generated-icons/*.png`. In production the Go backend serves it — dynamically, per the § PWA Identity Assets section below — but the on-disk file is the stock-byte source.

**Service worker**: the tree ships a single hand-written `app/frontend/public/sw.js` served at the origin root (whole-app scope) — there is no Workbox / `vite-plugin-pwa` generation step wired in. Its full contract (push handler, `notificationclick` deep-link navigation, same-origin normalization) is in § Web Push Notifications → Service worker. It is copied into `app/backend/build/frontend/` by `scripts/build.sh` and served by the existing SPA static serving — no backend changes required.

**Icons**: Canonical SVG mark at `app/frontend/public/icon.svg` (a **grayscale** hexagonal cube, transparent background, five gray fills `#b4b4b4`/`#2a2a2a`/`#888888`/`#737373`/`#545454`). Generated variants in `app/frontend/public/generated-icons/`: `favicon.svg` (copy of icon.svg), `icon-192.png`, `icon-512.png`, `icon-512-maskable.png` (PNGs have solid `#0f1117` dark background with 20% padding, maskable has 40%). Generated by `scripts/generate-icons.sh` (uses `sharp` Node library). Run via `just icons`. These committed files are the stock-byte source the PWA identity routes tint per request (§ PWA Identity Assets). The same script also writes the desktop shell's **committed** 1024px variant `app/desktop/build/icon.png` (dark bg, 20% padding, rounded-rect `dest-in` mask for the macOS squircle) — see [desktop-shell](/run-kit/desktop-shell.md) § Packaging.


## PWA Identity Assets

The PWA manifest, Dock/Cmd-Tab icons, and tab favicon are served **dynamically** by the Go backend so the per-instance accent color (`~/.config/run-kit/config.yaml` `instance_color`, read per request — Constitution §II) tints the installed PWA's OS-level identity, making multiple run-kit instances distinguishable in the Dock and Cmd-Tab (260722-eo8e-accent-dock-icon). Five explicit `GET` routes are registered in `buildRouter` (`api/router.go`) immediately **before** `s.mountSPA(r)` so they win over the SPA catch-all: `/manifest.json`, `/generated-icons/favicon.svg`, and the three `/generated-icons/icon-*.png` PNG paths. With no owned accent every route serves the stock bytes byte-identically — zero-config installs get the stock identity.

**Handlers** (`api/pwa.go`):
- `readSPAAsset(relPath)` — reads a stock frontend asset through the same seam `mountSPA` branches on: the embedded FS when `useEmbeddedSPA` (prod), else the local filesystem trying `spaDir` (built dist) then the fallback dirs `app/frontend/public` and `../frontend/public` — the latter is the `air` dev cwd (`app/backend`, per `scripts/dev.sh`), so `just dev` serves these routes without a built dist. A missing asset returns 404, never panics. *(Its inline `fs.Sub(build.Frontend, "frontend")` is a second copy of the embedded-sub-FS lookup that `spa.go`'s `embeddedSPASub` seam owns.)*
- `handleManifest` (`GET /manifest.json`, `Content-Type: application/manifest+json`) — unset/unowned accent serves the stock JSON verbatim; an owned accent rewrites each of the three icon `src` literals to carry a `?c=<descriptor>` cache-buster (`url.QueryEscape`d, so a blend `+` becomes `%2B`). Rewrite is `strings.ReplaceAll` of the quoted src literals, not a JSON round-trip, so everything but the three srcs stays byte-identical. The changed URLs are also what makes Chrome detect a manifest change and refresh the installed icon on its lazy re-check cycle.
- `handleGeneratedIcon` (the three PNG paths) — the icon name is validated against a fixed `tintableIcons` allowlist (404 otherwise). Without `?c=`, or with a malformed/unowned descriptor, the stock PNG bytes are served (treat-as-absent, 200 — never 400, since browsers/OS surfaces fetch these and a broken query must not break the install). With an owned `?c=`, the stock PNG is colorized via `icontint.TintPNG` and memoized.
- `handleFavicon` (`GET /generated-icons/favicon.svg`, `Content-Type: image/svg+xml`, `Cache-Control: no-cache`) — `index.html`'s `rel=icon` href is static (no `?c=`), so the tint resolves from current settings per request; `no-cache` makes the browser revalidate so an accent change reaches open tabs on their next load. Owned accent → `icontint.TintSVG`; otherwise stock.

**In-memory tint cache**: tinted outputs are memoized on the `Server` struct — `tintCache map[string][]byte` guarded by `tintCacheMu sync.Mutex`, lazily initialized, keyed `"asset|descriptor"` — via the `tintCached(asset, descriptor, tint)` helper. Each entry is a pure function of the fixed stock bytes + descriptor (not persistent state — Constitution §II-compatible), and the key space is bounded at 10 owned families × 4 assets.

**`internal/icontint`** package — the tint engine, Go stdlib only (`image`, `image/png`, `image/color`); no new dependencies, `sharp` stays build-time-only. Because the logo is grayscale, the tint is a pure luminance→accent ramp:
- `familyHexByValue` — a fixed 40-entry map from every canonical owned color value to its **default-dark** hex: the 10 legacy descriptors (`"1"`, `"1+3"`, … `"3+4"`), the 10 family names (`"red"` … `"slate"`, same hex as their legacy twin), and the 20 `-dark`/`-light` shade variants (`"red-dark"` `#bd4c48` / `"red-light"` `#feb8b2` … `"slate-dark"` `#6b7885` / `"slate-light"` `#c1cedd` — the shade variants have no legacy form and are stored as names verbatim). A Dock icon is theme-independent, so the hexes are frozen from the default-dark palette rather than derived per active theme — each value equals `colorValueToHex(value, DEFAULT_DARK_THEME.palette)` from `app/frontend/src/themes.ts` (dark shade = mean-L − 0.14, light shade = mean-L + 0.14, same hue/chroma, gamut-reduced). Descriptors that validate but own no family (e.g. `"7"`, `"2+5"`) resolve to nothing, mirroring the frontend's `resolveFamily`.
- `Resolve(descriptor) (hex, canonical, ok)` — normalizes via `validate.NormalizeColorValue` (so `"04"` and `" 1 + 3 "` resolve, and family names trim to their verbatim form), looks up the owned family/shade, and returns the hex plus the canonical descriptor (the stable cache/URL key); `ok=false` on malformed or unowned values. Reuses `internal/validate` — no reimplementation of color parsing.
- The colorize ramp: BT.601 luma per pixel; pixels at/below `backgroundLumaCeil = 24` (the `#0f1117` background, luma ≈ 17) pass through untouched, brighter pixels render as `accent × (luma / peakLuma)` per channel (`peakLuma = 180`, round-to-nearest, clamped to 255), so the brightest logo gray `#b4b4b4` maps to the accent hex itself and darker grays to proportionally darker accent.
- `TintPNG(stock, hex) ([]byte, error)` — decodes the PNG, applies the ramp per pixel via `NRGBA` conversion (alpha preserved), re-encodes.
- `TintSVG(stock, hex) ([]byte, error)` — `strings.ReplaceAll` of the SVG's five known grayscale fills with the ramp hexes the PNG treatment produces for the same luma values, so browser tabs match the Dock.

**Dev parity**: `app/frontend/vite.config.ts` proxies `/manifest.json` and `/generated-icons` to the backend port (`RK_PORT + 1`, same target shape as `/api`). Vite's `server.proxy` middleware runs before public-dir static serving, so these entries shadow the static copies in `public/` — no static fallback needed. E2E coverage is `app/frontend/tests/e2e/pwa-assets.spec.ts` (tint-agnostic: it pins the serving pipeline via the `application/manifest+json` content-type that distinguishes the Go handler from Vite's static `application/json`, PNG magic bytes, and the favicon's `no-cache` header).


## Web Push Notifications

`260615-xd9r-web-push-notifications` lets any process on the box — primarily the fab-kit operator agent via `rk notify` — deliver a real OS-level notification that reaches the user **even when the RunKit PWA tab is closed**. This is the only browser-native mechanism that delivers to a closed tab: the *browser's* push service wakes the registered service worker, which shows the notification. It is the intended eventual replacement for fab-kit's `ntfy.sh` default (one feed across all operators on the box, content stays on infra the user runs).

**End-to-end delivery model**: a shell process runs `rk notify "msg"` → POSTs `{title, body}` to the local server `POST /api/notify` → the server iterates stored `PushSubscription`s and sends each a Web Push via `webpush-go` signed with the server's VAPID **private** key → the browser's push service wakes the registered service worker → `sw.js`'s `push` handler calls `self.registration.showNotification(title, {body, icon, data})` → the user sees an OS notification with the tab closed.

**`Notify` signature carries an optional deep-link URL (260714-r7rq)**: `push.Notify(ctx, title, body, url string)` — the 4th `url` param is threaded into the `payload` JSON as `url,omitempty` (empty ⇒ omitted, and the SW falls back to the app root on click). The only URL producer today is the waiting-push watcher (§ Web Push on Sustained Waiting → deep-link URL, `/{server}/{N}?view=chat` for chat-capable waiting windows); the generic `/api/notify` path (`api/push.go`) and `rk notify` (`cmd/rk/notify.go`) pass `""`.

**Service worker** (`app/frontend/public/sw.js`): a hand-written service worker served at the origin root `/sw.js` (whole-app scope). Its `push` handler parses the JSON payload `{title, body, icon?, url?}` (default title `"RunKit"`, default icon `/generated-icons/icon-192.png`) and tolerates an empty / non-JSON payload by falling back to defaults; it stores the deep-link `url` on the notification via `showNotification(title, { body, icon, data: { url } })`. **Its `notificationclick` handler focuses an already-open RunKit tab and NAVIGATES it to the deep-link target** (or `openWindow`s a new tab at the target), falling back to the app root `/` when no `url` was carried (260714-r7rq). Two safety details: (a) the URL is normalized through `sameOriginPath(value)` — it must start with `/` but **NOT `//`** (a protocol-relative `//evil.example` resolves to an EXTERNAL origin), and the resolved `new URL(value, origin).origin` is belt-and-braces compared to the SW's own origin — so a malformed/hostile payload can never redirect off-origin; (b) `client.navigate()` REJECTS for uncontrolled clients (`matchAll` uses `includeUncontrolled: true`) and may be unavailable in some browsers, so the call is chained `.catch(() => client.focus())` — a rejection must never propagate into `waitUntil` (it would surface as an unhandled SW error). The frontend ships only this hand-written `public/sw.js` and a static `public/manifest.json` linked from `index.html`; no Workbox / `vite-plugin-pwa` generation step is wired in. Registered on app load via `navigator.serviceWorker.register('/sw.js')` from `app/frontend/src/main.tsx`, guarded by `'serviceWorker' in navigator` so unsupported / insecure-context environments silently skip registration.

**Secure-context constraint**: service workers and `PushManager` require a **secure context — HTTPS or `localhost`**. The user typically hits run-kit on `localhost:3000` (or behind a TLS reverse proxy such as Tailscale Serve), both secure contexts, so it is satisfied in practice — but raw-IP / plaintext non-localhost access cannot subscribe (registration is skipped silently, no error).

**State persistence** (Constitution §II — No Database): the `internal/push` package owns two JSON files under `~/.rk/` — `vapid.json` (the VAPID keypair, private key written mode **`0600`**, never served) and `push-subscriptions.json` (the subscription array, de-duped by `endpoint`). See § Backend Libraries. There is no `/api/push/unsubscribe` in v1; dead subscriptions are pruned server-side on `404`/`410` during send.

**Fail-silent discipline** (end-to-end, constitution-aligned): every layer fails silently on its own prerequisite being absent. `rk notify` exits 0 with no output on any failure (server unreachable / non-2xx / timeout) so a notify failure never stalls the operator loop; the send fan-out tolerates individual subscription failures and prunes dead endpoints; the frontend subscribe flow aborts silently when permission is denied or the context is insecure / unsupported. The opt-in is a Cmd+K palette action with a terminal-themed label (NOT a bell) — see `ui/updates-and-notifications.md` § Notifications (Web Push opt-in).

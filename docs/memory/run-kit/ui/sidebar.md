# run-kit UI — Sidebar

## Sidebar

`app/frontend/src/components/sidebar/` — session/window tree navigation. The sidebar is decomposed into an orchestrator and focused sub-components:

- `index.tsx` — `Sidebar` orchestrator; owns all state (`collapsed`, `killTarget`, `editingWindow`, `editingSession`, `dragSource`, `dropTarget`, `sessionDropTarget`) and all `useOptimisticAction` hooks. Accepts a required `isConnected: boolean` (per-page live-data health, rendered by the footer dot in the mobile drawer — § Sidebar footer status row; on desktop the connection dot lives in the full-width status bar) and holds the file-private `SidebarFooter` + `BottomPanels` sub-components
- `section-rail.tsx` — `SectionRail`; the section-visibility micro-rail — four icon-only `aria-pressed` toggle buttons (Boards · Server · Pane · Host) rendered as the FIRST child of the `<nav>`, gating the optional sections below; see § Section-Visibility Rail
- `session-row.tsx` — `SessionRow` (exported as `memo(SessionRowInner)`); renders the session header row (chevron, name) plus a **trailing hover-revealed icon cluster** in fixed order `[🎨 palette/color] [🤖 bot spawn] [+ create window] [✕ kill]` — the bot button (`gsmu`) sits immediately **LEFT of `+`** so `+`/`✕` keep their muscle-memory edge positions; handles cross-session drag-over styling; all event handlers passed as props (stable identity-arg `useCallback`s — see § Render Performance). **Session-row icon cluster** (the spawn-agent trigger): each icon button shares the same affordance classes as its palette sibling (`text-text-secondary hover:text-text-primary opacity-0 group-hover:opacity-100`) plus the cluster's **uniform geometry** — `px-0.5 min-w-[24px] min-h-[24px]` on all four buttons (§ Sidebar row icon system). The whole cluster is **fine-pointer-only** — render-gated `!coarse` (the window-row relocation precedent; on coarse its actions live in the rail-triggered session card and the rail owns the right edge). The **bot button** (`onSpawnAgent && (…)`) renders **only when an `onSpawnAgent?: (server, session) => void` handler is present** (mirroring the optional `onColorChange` pattern), carries `aria-label={`Spawn agent in ${session.name}`}`, and on click does `e.stopPropagation()` then `onSpawnAgent(server, name)` — passing the ROW's explicit `{server, session}` (the spawn target). Its glyph is `BotIcon` from `sidebar/icons.tsx` — a lucide-style `bot` (robot head: antenna + rounded head with two eye dots + side ports) stroke SVG matching the `PaletteIcon` idiom (`stroke="currentColor"`, `strokeWidth={2}`, `aria-hidden`, 24-unit viewBox + 13px default size). **Prop threading** (`gsmu`): `onSpawnAgent` is optional on `SidebarProps` → threaded through `ServerGroupProps`/`ServerGroupInner` → `SessionRow` (mirroring `onColorChange`); the board-route sidebar passes NO handler, so the bot button is hidden there (Non-Goal — later wiring is cheap via the optional prop). See § Spawn-Agent Dialog for the dialog it opens. The row root also hosts a row-level **identity tip** (`xb77`): a slim non-interactive hover-card (`sidebar/identity-tip.tsx`'s `useIdentityTip` + `IdentityTipCard`, tier-2 by the tooltip promotion rule — see [status-signals](/run-kit/ui/status-signals.md) § Tooltips — Two-Tier Taxonomy) whose shared `PopupTitleBar` reads `Session <full untruncated name>` over a one-line body `$N · N windows · ~/{path}` (the tmux session id + root path ride `sessionId`/`sessionPath` on the session payload — underivable segments are omitted; the path is `~`-abbreviated via `lib/format.ts` `abbreviateHomePath`). Hover/focus open at the sidebar's right edge on a plain 300ms delay, `mouseOnly` + coarse-pointer suppression, no `TipGroup`/warm-window coupling, suppressed while the color popover is open, closed on drag start; the card renders `null` while closed (§ Render Performance). On COARSE pointers the row's right edge carries the 56px status rail — the same recessed inset band the window rail ships, tinted from the session's family tint, with an always-empty 16px glyph slot and the 12px `›` chevron — whose tap/scrub opens the coarse-only **session card** (status-signals.md § Row-hover register flyout card)
- `window-row.tsx` — `WindowRow` (exported as `memo(WindowRowInner)`); renders a single window row (a leading unified `<StatusDot>` + name) plus the absolutely-positioned trailing cluster (`PinIcon` pin / `CloseIcon` kill on the shared uniform geometry — § Sidebar Row Icon System — with the rest-state PR glyph overlaying the kill slot, § Rest-state PR glyph); handles drag-and-drop and inline rename display; hosts the row-hover flyout card (the row root is the card's floating reference, § Row-hover register flyout card); all event handlers passed as props. **Row Minimalism**: no trailing status TEXT cluster (no fab stage word, no `WindowDuration`/`TickingDuration` duration leaves or their per-second `useNow()` tick) — status is the leading `<StatusDot>` plus the owned-PR rest glyph (§ Window rows / Row Minimalism). Its only local state is the hover-icon/popover state plus the row-local flyout state. The icon cluster's pin/kill buttons are fine-pointer-only (render-gated `!coarse` — the container does not mount on coarse at all; the PR glyph's coarse home is the status rail's fixed 16px slot, and pin/kill live on the flyout card's action rows, § Rest-state PR glyph) and inert at rest (`pointer-events-none` + hover/focus restore). Renders no full PR line — the register detail lives in the flyout card and the PANE panel. (`260706-y1ar`, `260715-jykd`, `93dy`)
- `collapsible-panel.tsx` — `CollapsiblePanel`; reusable collapsible container with header (title + chevron) and localStorage open/closed state persistence via `storageKey` prop. Two modes: (a) legacy `max-height` CSS transition when `resizable` is absent/false (preserves existing Window/Host panel behaviour); (b) resizable mode (opt-in via `resizable` prop) — renders a 6px `ns-resize` drag handle at the bottom, persists user-set height to `localStorage[${storageKey}-height]`, and supports `defaultHeight`/`minHeight`/`maxHeight` props. The resizable content area is a clipping scroll surface, so it wires `useScrollEdgeFade` and toggles the `rk-scroll-fade-bottom` mask (§ Collapsible Panels) while scrollable-and-not-at-end — gated `!legacyMode && isOpen && !transitioning` (legacy mode keeps `overflow: visible` and gets no fade; mid-transition `overflow: hidden` would fade content that isn't actually clipped). `maxHeight` accepts a number or a `calc(100vh - Npx)` string form (parsed at drag time using `window.innerHeight`). On mobile (`useIsMobile()` — narrow-width OR coarse pointer, § Hooks (Frontend)) the drag handle is hidden and the content area is pinned to the `mobileHeight` prop (default 56px). All localStorage access wrapped in try/catch. **Header tint**: `tint` prop (`RowTint | null`) paints the header background. By default (legacy mode) the header uses `tint.base` with a `tint.base` ↔ `tint.hover` swap on hover. When `tintOnlyWhenCollapsed` is set, the tint is applied only while the panel is collapsed — and the shade switches to `tint.selected` with the hover swap disabled (stays flat), because in that mode the header is standing in for the selected item inside and a less-saturated hover would read as an inverted effect. `ServerPanel` is the only current consumer of `tintOnlyWhenCollapsed`; the legacy `base`/`hover` behavior is preserved for forward compatibility
- `status-panel.tsx` — `WindowPanel` (exported as both `WindowPanel` and deprecated `StatusPanel`); wraps the identity rows (`tmx`, `cwd`, `git`) plus the **four orthogonal signal registers** (`out`/`agt`/`fab`/`PR` — L0/L1/L2/L3, 3-char prefix vocabulary) in a `CollapsiblePanel` with copyable row interactions (via the file-private `CopyableRow`); see § Pane panel four-register view. The `PR` (L3) register is **ungated from `fabChange`** — shows for ANY pane with a derived `prNumber` (universal derivation); its interaction is **open-first** (the one row that isn't click-to-copy) — with a PR URL the row body is a real anchor (file-private `PrLinkRow`) opening the PR in a new tab (always-visible inline `↗`), and copy is role-swapped to a hover-revealed right-side icon (reusing the window-row icon-cluster gating); without a URL it stays a plain `CopyableRow` copying the segment text. See § PR Status. The panel's `headerRight` leads with a unified `<StatusDot win={win} />` before `{win.name}` — an at-a-glance status summary that survives panel collapse; the dot here is decoration only (the panel below IS the detail view) — see § Status Dot (`260703-41ks`, `260706-y1ar`)
- `host-panel.tsx` — `HostPanel`; hostname header + SSE dot inside a `CollapsiblePanel`, delegating the metric rows to the shared `HostMetrics` component (see § HostPanel). Keeps the `!metrics` "No metrics" branch
- `host-metrics.tsx` — `HostMetrics`; the shared layout-agnostic presentational component rendering the CPU sparkline / memory gauge / disk+uptime / load rows for a `MetricsSnapshot` via `lib/sparkline.ts` + `lib/gauge.ts`. Consumed by both `HostPanel` (sidebar) and the `/` HOST HEALTH zone (`260701-vshd`; see § HostPanel)
- `server-panel.tsx` — `ServerPanel`; swatch-style grid of server tiles (Mock A) inside a `CollapsiblePanel` with `title="Server"`, `storageKey="runkit-panel-server"`, `defaultOpen={true}`, `resizable={true}`, `defaultHeight={50}`, `minHeight={50}`, `mobileHeight={50}` — the panel is sized to one row of tightened tiles so the reclaimed height goes to the SESSIONS tree below. Its expansion state is purely the tile grid's own visibility — `runkit-panel-server` is `CollapsiblePanel`'s private persistence and no sidebar code path outside it reads that key; the sessions-pane scope is a separate, explicit state (§ Sessions-pane scope). The `headerRight` slot carries **only** the `LogoSpinner` when `refreshing` is true — no server name (the highlighted tile and the top-bar page heading already show it). The panel also passes `tint={activeTint}` + `tintOnlyWhenCollapsed` so the collapsed header background matches the selected server's `rowTints.get(activeColor).selected` shade (same body tint used by the active tile inside the panel) — collapsed and expanded readings agree, and the header hover stays flat at the selected shade. Desktop grid: `repeat(auto-fill, minmax(72px, 1fr))`, 6px gap — tiles expand to fill the sidebar width, multi-row, scrolls internally when overflowing the user-set height; partially-clipped tile rows at the bottom cut edge fade out via the `rk-scroll-fade-bottom` mask while more content exists below (§ Collapsible Panels). **Tile anatomy** — each tile is a focusable `<button role="option">` (no sibling action wrapper) with a two-line body tightened to ≈38px total: a 2px top color stripe (`h-0.5`, ANSI tint via `rowTints.get(color).base`, neutral `--color-border` for tiles without an assigned color) — the top edge is the server signature/active marker (**top border = server, left border = window rows**; no left-border marker) — then a body div (`px-1.5 pt-0.5 pb-1.5`) holding an 11px truncated name line and a count row. **Count row** (`flex h-3.5 items-center justify-between mt-0.5`): a **bare window-count number** (10px `text-text-secondary`, `{windowCount}`, from the `windowCount` field on `ServerInfo`) at the left with the `WaitingBadge` numeric pill right-aligned on the same flex row. The `h-3.5` (14px) reserve is a **fixed height held unconditionally** whether or not a badge renders — the pill is taller than the count text, so without the reserve the tile (and its whole grid row) would jump every time an agent starts/stops waiting. The tile carries NO native `title` tooltip (never both — the double-tooltip rule); a hover/focus **identity tip** (`xb77` — the shared slim hover-card, `sidebar/identity-tip.tsx`; see [status-signals](/run-kit/ui/status-signals.md) § Tooltips — Two-Tier Taxonomy) reads `Server <name>` in the title bar over a one-line body `tmux -L <name> · N sessions` — server names ARE socket names, so the socket flag composes frontend-side and shows uniformly for every server including `default`, and the session count rides the tile's existing `sessionCount`. Active tile: `aria-current="true"` + inset accent ring + `rowTints.get(color).selected` body tint (accent-subtle fallback for untinted active server). **No hover-revealed action cluster on server tiles** — server color and server kill live exclusively in the SESSIONS-pane server-group headers (§ Server-group header action cluster) and the command palette (`Server: Kill {name}`, § below); this makes the desktop tile consistent with mobile, which never carried the cluster. Mobile layout (`useIsMobile()` — narrow-width OR coarse pointer, § Hooks (Frontend)): single-row grid via `grid-auto-flow: column`, `grid-auto-columns: 72px`, `overflow-x: auto; overflow-y: hidden`, `scroll-snap-type: x mandatory` — swipe horizontally, tap to select. **Active-tile autoscroll (all layouts)**: a `useEffect` keyed on `[server]` calls `activeTileRef.current.scrollIntoView({ block: 'nearest', inline: 'nearest' })` on mount and whenever the active `server` changes — the ONE call serves both layouts (`block: 'nearest'` for the vertical desktop tile grid that scrolls internally inside the resizable `CollapsiblePanel`, `inline: 'nearest'` for the horizontal mobile single-row strip). It is un-gated by viewport (no `isMobile` read; deps are `[server]` only) and guarded by `typeof el.scrollIntoView === 'function'` for jsdom. `ServerInfo` shape (`{name, sessionCount, windowCount?, rank?}`) flows through from `/api/servers` — the tile renders `windowCount ?? 0`. **Drag-reorder** (`260705-bpnr`): regular server tiles are draggable via the shared `useServerReorder` hook (see § Server-tile drag reorder) — infra tiles are excluded (not draggable, not drop targets); the dragged tile dims via `opacity-50`. **Infra-server name de-emphasis** (`260705-uh8f-deemphasize-infra-servers`): the tile name span carries `text-text-secondary` (not the usual `text-text-primary`) when `isInfraServer(name)` (from `@/api/client`) — greyed, not disabled. Hover/click/active-selection are unchanged, so the infra tile stays fully attachable (useful for reading daemon logs) and never reads as dead/disconnected. See § Infra-server de-emphasis
- `server-selector.tsx` — `ServerSelector` (legacy); owns its own dropdown state (`serverDropdownOpen`, `refreshingServers`, `serverDropdownRef`); pinned-bottom server dropdown with outside-click dismiss. Retained for backwards compat — `ServerPanel` is the primary server-switcher in the current UI
- `kill-dialog.tsx` — `KillDialog`; stateless; renders the kill confirmation dialog for sessions and windows using `<Dialog>`

Consumers import `@/components/sidebar` — Vite resolves directory imports to `sidebar/index.tsx` automatically.

The tree's bulk multi-select state lives outside this directory, in `store/selection-store.ts` with its pure logic in `lib/selection.ts` and its palette family in `lib/palette-selection.ts` — see § Window-Row Multi-Select.

### Section-Visibility Rail (`section-rail.tsx`)

A horizontal micro-rail of four icon-only toggle buttons — **Boards · Server · Pane · Host**, fixed order — rendered as the FIRST child of the sidebar's `<nav>` (above `BoardsSection`), on every route that mounts `<Sidebar>`. The rail always renders (not self-hideable), and **Sessions is deliberately not in the set** — the session tree is the always-on core nav surface and is never hideable. The rail is the designated home for future sidebar-level controls. (`260817-iha5`)

- **Geometry + states**: 24×24px buttons with 13px stroke glyphs on fine pointers (the row-icon-system geometry, § Sidebar Row Icon System), 30×30 on coarse pointers (the shared 30px coarse axis); ~4px gap, ~8px side padding. Glyphs are four `sidebar/icons.tsx` stroke-SVG members in the file's fixed idiom — `BoardsSectionIcon`, `ServerSectionIcon`, `PaneSectionIcon`, `HostSectionIcon`. Each button is an `aria-pressed` toggle with a state-stable `aria-label` (`Toggle {Section} section`); pressed = the app's active-toggle treatment (`bg-accent-green/10` wash + inset `ring-accent-green` + `text-accent-green` — the top-bar segment active idiom), unpressed = `text-text-secondary` at rest / `text-text-primary` on hover. Fine pointers get a tier-1 `Tip` with a state-flipping action label (`Show/Hide {Section} section` — the scope-chip pattern, no native `title`; status-signals.md § Tooltips — Two-Tier Taxonomy); coarse pointers get no hover label — tapping the toggle is self-revealing.
- **State — four shared booleans**: `hooks/use-sidebar-sections.ts` owns the vocabulary — the `SidebarSection` type (`"boards" | "server" | "pane" | "host"`), the ordered `SIDEBAR_SECTIONS` tuple, and `useSidebarSectionVisible(section)` over the existing `useLocalStorageBoolean` pub/sub hook (§ Sessions-pane scope → Sessions-scope hooks), so the rail, the sidebar render, and the palette entries stay in sync within a tab (cross-tab rides the native `storage` event). One shared key per section — `runkit-sidebar-section-{boards|server|pane|host}` — across viewports AND routes (no per-viewport fork, no per-route state). Defaults: **Boards on, Server on, Pane off, Host off** on both viewports — on desktop the full-width status bar owns the Pane/Host readouts unless a user opts in, and the mobile drawer is nav + footer by default (the coarse status rail + tier cards carry the register detail — status-signals.md § Row-hover register flyout card).
- **Gating — one visibility gate per optional section**: `Sidebar` reads the four booleans locally (nothing threads through the memoized `ServerGroup`/`SessionRow`/`WindowRow` tree — § Render Performance invariants untouched) and conditionally renders each optional section at its existing mount site: `BoardsSection`, `ServerPanel`, and the `BottomPanels` pair — `WindowPanel` and `HostPanel` mount independently under their own booleans on EVERY viewport (`BottomPanels` takes `showPane`/`showHost`). Toggle-off fully UNMOUNTS the section — header gone, height reclaimed, effects/subscriptions stopped. Visibility is **orthogonal to collapse**: the `CollapsiblePanel` chevron and its persisted keys (`runkit-panel-*` + `-height`) are untouched by toggling, so re-toggling a section on restores it exactly as left (the VSCode Explorer precedent — collapse chevrons and view-visibility coexist).
- **Keyboard path**: one palette entry per section — `Panel: Toggle Boards|Server|Pane|Host` (ids `panel-toggle-*`, registered in `useGlobalPaletteActions`; [keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md) § Command Palette Actions) — also the recovery path when toggled-off sections hide content the user wants back.

### Sidebar Row Icon System

**Every action icon in a session or window row's trailing cluster is a stroke SVG from `sidebar/icons.tsx` — ONE icon system, no text glyphs.** The file's icon idiom is fixed: `stroke="currentColor"`, `strokeWidth={2}`, `fill="none"`, round caps/joins, a 24-unit `viewBox`, a `size = 13` default, and `aria-hidden` (the accessible name lives on the wrapping button's `aria-label`). Members: `PaletteIcon` (color), `BotIcon` (spawn agent), `PlusIcon` (create window), `CloseIcon` (kill), `GearIcon` (the top-bar Settings gear), `GitPullRequestIcon` (the window row's rest-state PR glyph — § Rest-state PR glyph; a lucide `git-pull-request` silhouette: source circle + rail, an arc into the merge rail, target circle), `GitPullRequestClosedIcon` (the rest-state glyph for a **closed** PR — a lucide `git-pull-request-closed` silhouette in the same idiom: source circle + rail, an ✕ where the merge arc was, truncated target rail + target circle) — plus the shared 16-unit `PinIcon` (`components/pin-icon.tsx`, rendered at 12px), whose 1.5/16 stroke resolves to ≈1.125px against the 24-unit family's 2/24×13 ≈ 1.08px, so the cluster reads at one weight. The two PR glyphs are the members that are **not** action icons — they are `aria-hidden` decoration inside a non-interactive span — but share the cluster's idiom because they sit in the same slot row and must read at the same ink weight; deliberately NOT the Nerd Font `` (U+F407) glyph the PANE panel's L3 register uses (one icon system per row cluster). **Equal ink metrics is the whole point**: mixed systems (a 16px text `+` beside a 13px stroke SVG) read as *unevenly spaced* even when the measured center-to-center gaps are exactly equal, because glyph ink width and weight differ. Uniform gaps are a consequence of uniform ink, not of nudging positions. (`260724-2bmy`, `xuej`)

**Uniform button geometry.** Every cluster button carries the same box: `px-0.5 min-w-[24px] min-h-[24px]` — a 24px square. The clusters are FINE-POINTER-ONLY surfaces at every tier (render-gated `!coarse` — on coarse the status rail + the tier's card own those actions and the rail's 56px column is the touch target), so cluster buttons carry no coarse touch-target axis. (`260724-2bmy`, `ys3q`, `260817-ve5m`)

**Optical centering over nominal centering.** `BotIcon`'s `viewBox` is `0 1.5 24 24` — a y-shift, not a wrapper transform, so the rendered box stays exactly 13px. The bot's antenna is top weight, which puts the *perceived* body (the head, spanning y=8..20) below the geometric center; the shifted view lifts the drawing ~0.8px so the head's center lands on the palette circle's center. The antenna dot keeps ~0.27px top clearance and is not clipped. (`260724-2bmy`)

**Scope**: the session row's four-button cluster, the window row's trailing zone, AND the server-group header's palette/plus/close cluster (`sidebar/index.tsx`) — every header tier shares the one icon system, and the fine-pointer clusters share the uniform slot geometry (`px-0.5 min-w-[24px] min-h-[24px]`, wrapper right padding `pr-2`), so the `+` and `×` icons align vertically down the sidebar (§ Server-group header action cluster). The trailing edge is pointer-split at every tier: on FINE pointers the hover-revealed clusters own it (the window row's is the pin + kill pair — render-gated `!coarse`, the whole `group/icons` container fine-pointer-only — plus the rest-state PR glyph sharing the kill button's slot as an absolute overlay, § Rest-state PR glyph); on COARSE pointers the trailing 56px of EVERY non-ghost row of all three tiers is the **status rail** — one recessed inset band (`bg-bg-inset`, `border-l border-border` seam) forming ONE continuous strip down the tree, carrying two FIXED slots that column-align down the sidebar: a 16px glyph slot (the window row's PR-glyph coarse home — an empty span when the row owns no PR; ALWAYS an empty span on session/server rows, which own no PR glyph) and a 12px `›` chevron hint at ~55% opacity, `aria-hidden`, on EVERY rail (a consistent rail is a learnable rail; the no-text-glyph rule governs ACTION icons — the chevron is static decoration). Per-tier band tints derive from the existing tint systems via the shared `railRestBand` `color-mix` idiom — window rails keep the neutral/selected treatment (the selected row mixes `tint.selected` or the gray sentinel into the inset base), session/server rails mix their header's family tint — never a new token; a held rail (its card open) steps up one shade with a brightened seam (`railHeldBand` / `RAIL_HELD_SEAM`). Every rail-bearing row reserves `coarse:pr-[56px]` so names truncate before the rail column (the literal matches `STATUS_RAIL_WIDTH_PX` — Tailwind scans literal classes only; the window row's fine-pointer `pr-[68px]`/`pr-11` is untouched). The rail is also the flyout gesture's primary tap/scrub target at every tier (status-signals.md § Row-hover register flyout card). (`260813-kvk7`, `ys3q`, `b8eu`, `260817-ve5m`)

### Rest-state PR glyph (`window-row.tsx`)

A window row whose window has an **owned PR** shows a rest-state PR glyph whose home is pointer-split: on FINE pointers an absolute overlay at the trailing cluster's LAST slot, right-edge-aligned with the hover ✕; on COARSE pointers inside the status rail's fixed 16px slot (§ Sidebar Row Icon System — the rail IS the coarse home; the `group/icons` overlay container does not mount on coarse). The icon is picked by state: `GitPullRequestIcon` for open/merged, the ✕ `GitPullRequestClosedIcon` for closed. It makes "which of my windows have PRs, and how are they doing" answerable by scanning the sidebar rather than by decoding a 7px dot's hue — the one status signal Row Minimalism admits beside the dot, and a glyph only (no status TEXT returns to the row). (`93dy`, `xuej`, `b8eu`) The glyph is the row's ONLY PR channel — the dot renders no PR state (the local/remote split, § Status Dot) — and the `SessionTiles` window tile carries the same rest-state glyph on its header line (same `prOwnsGlyph` gate, same `prGlyphColor`, same state-picked icon, `aria-hidden`, `data-testid="tile-pr-glyph"`, never on ghosts); the pane panel deliberately carries none — its L3 register is the detail surface. (`aqo6`, `xuej`)

**Gate + color** — `prOwnsGlyph(win)` (`!!prNumber && (prState === "open" || prState === "merged" || prState === "closed")`: open, failing, merged, and closed all earn the glyph; an unknown/absent state never does — the backend's unconfident `""` branch fallback, MapBranchState), deliberately un-family-gated: any pane with an owned PR shows the glyph — even a plain floor pane whose dot stays gray (derivation is universal, Principle X; the dot never renders PR state, § Status Dot). Color is `prGlyphColor(win)` from the shared PR vocabulary — a **six-way** mapping: gray (`text-text-secondary`) for **closed** (a dead PR reads muted; its stale checks/review are historical noise, so the closed branch sits **above fail**), purple for **merged** (the same landed-PR historical-noise rationale — merged also sits above fail), red for a fail-ish PR (`isFailish`), gray (`text-text-secondary`) for an open **draft**, **yellow (`text-signal-yellow`) for an open PR with checks pending (checks running)**, green for open otherwise. The draft branch sits **below fail** (a failing draft reads red — a problem first, a draft second), **above pending** (drafts stay muted even while their checks run), and is **gated on `prState === "open"`**, so the closed path stays untouched by construction (a closed draft reads closed — the closed branch matches first; merged already returned above). Closed and open-draft share the inert gray token; the ✕ `GitPullRequestClosedIcon` shape is what separates a closed PR from a draft. Draft, checks-pending, merged, and closed are **glyph-only** distinctions: the dot carries no PR state, so the two channels answer different questions — the glyph *whose turn is it / how is the PR doing*, the dot *what runs here, is it healthy*. No JSX carries the token: the row already interpolates `${prGlyphColor(win)}` into the glyph span's `className`. Ghost rows render no glyph. (`93dy`, `e30p`, `aqo6`, `xuej`)

**Draft fidelity is dual-sourced — the branch channel is what covers a teammate's draft.** `prIsDraft` reaches the frontend from **two** backend channels: the author-agnostic branch refresher seeds it (`BranchPR.IsDraft` from `branchPRExec`'s `--json` field list → `enrichWindowPR`, `app/backend/internal/prstatus/prstatus_branch.go`), and the URL-keyed viewer-wide collector join overrides it on a hit. The branch seed is the load-bearing half for **any PR you did not open**: the collector's query is `viewer { pullRequests }` — the authenticated user's own PRs — so a teammate's draft never keys that join **at any `$limit`** (a categorical blind spot, not a top-`$limit` aging edge), and `api/sse.go`'s collector-only reset therefore leaves `PrIsDraft` intact, so a join miss preserves the branch-derived flag rather than falling back to `false`. The flag is dual-sourced in exactly the shape `prState` already is (`MapBranchState` seed + collector override), so a teammate's open draft renders gray on the same code path as your own. (`e30p`, `n927`)

The residual fidelity limit is **staleness, not absence**: the two channels tick at different cadences (branch refresher 30s, collector 90s) and on a URL hit the **staler collector wins**, so a draft just marked ready-for-review — or a PR just converted *to* draft — can read one generation behind for up to ~90s. Collector-wins-on-hit is deliberate: on the PRs the collector *can* see it stays the single authority for the whole PR row, and it mirrors `prState`'s precedence. The degradation stays graceful (it lands on exactly the other legitimate rendering, never on something wrong) and the glyph is `aria-hidden` decoration. The accessible draft signal — `getPrSegments`' `" (draft)"` state-segment suffix in the flyout card and the PANE panel's L3 register — reads the same field, so every draft surface moves together rather than disagreeing. (`e30p`, `n927`)

### Infra-server de-emphasis

**Infrastructure** tmux servers — the `rk-daemon` socket (hosting the run-kit daemon itself, backend `ServerSocket`, `app/backend/internal/daemon/daemon.go`) and any `rk-test-*` socket (the isolated test-socket umbrella, backend `IsTestServerName`, `app/backend/internal/tmux/tmux.go:1342`) — are de-emphasized (greyed + sorted-last) but NOT hidden (§ Design Decisions → Infra servers are greyed, not hidden). (`260705-uh8f`)

**Identification lives in one frontend home** (`app/frontend/src/api/client.ts`, near the `ServerInfo` type): an exported `DAEMON_SERVER = "rk-daemon"` constant, a module-private `TEST_SERVER_PREFIX = "rk-test-"` (the one frontend home of that literal, mirroring the backend `IsTestServerName`), an exported `isInfraServer(name)` (true for the exact daemon socket or any `rk-test-` prefix), and an exported `compareServers(a, b)`. Identification is name-based, not a backend `isDaemon` flag (§ Design Decisions → Infra servers are greyed, not hidden). Consumers import these; magic strings are never re-derived at call sites.

**`compareServers` ordering**: regular servers first (alphabetical), then infra servers (alphabetical within their class). Comparison is plain byte-order lexicographic (`a.name < b.name`), NOT `localeCompare` — this mirrors the backend's `sort.Strings` byte order. `rk-test-*` sockets sort within the infra class.

**Single sort choke point** — `app/frontend/src/contexts/session-context.tsx` `fetchServers`: the fetched array is sorted once at the sole `setServers` ingestion point (`setServers(Array.isArray(data) ? [...data].sort(compareServersRanked) : [])` — note the `[...data]` copy: the sort is non-mutating, and the fresh reference each fetch matches production behavior, where `listServers` already returns a fresh array). Every consumer of `ctx.servers` inherits the effective ordering from this one place: the Sidebar Server-panel tile grid (`server-panel.tsx`), the Sessions-tree per-server `ServerGroup`s (`sidebar/index.tsx`), the Host-page TMUX SERVERS zone (`host-overview-page.tsx`), and the command-palette `Server: Switch to {name}` entries (`app.tsx`). **The backend does not sort** — `/api/servers` stays alphabetical (an asserted API contract, `servers_test.go:143`); display order is a frontend concern. `servers[0]` (the Host page's "Open in window" target, `host-overview-page.tsx`) prefers a real workspace over `rk-daemon` (see § SERVICES Zone on `/`). (`260705-bpnr`)

**Rank-aware comparator composition**: the choke-point sort key is **(infra-class, rank, name)** via `compareServersRanked(a, b)` (exported from `client.ts` beside `compareServers`), which **wraps** `compareServers` — the infra-last class pin and the byte-order intra-class ordering are preserved; rank is a secondary key inserted ONLY inside the regular class. Its logic: for a cross-class pair OR two infra servers it defers ENTIRELY to `compareServers` (infra ignore rank — their intra-class order stays byte-alphabetical); for two regular servers rank is primary — a ranked server sorts before any unranked one, two ranked sort by `rank` ascending, two unranked fall back to byte-order name. An **all-regular-unranked** list is byte-alphabetical, identical to `compareServers`. The rank on each `ServerInfo` comes from the `/api/servers` `rank` field (`@rk_server_rank`, see `architecture.md` / `tmux-sessions.md`). `session-context.tsx` imports `compareServersRanked`. (`260705-bpnr`)

**Live re-sort without refetch** — SessionContext listens for the server-global `event: server-order` on BOTH the per-server pool streams and the dedicated `?metrics=1` stream (identical payload on every stream, since the event is host-global). The `applyServerOrder(order)` handler stamps each named server's `rank` from its index in `order`, drops the rank of any server not listed (so it falls to the unranked tail), then re-sorts the held `servers` array with the same `compareServersRanked` — a state update, NO `/api/servers` refetch. Churn is bounded to explicit reorder events (not per-tick SSE), so no dedup guard is needed. See § Server-tile drag reorder below for the write path.

**Grey (de-emphasized, not disabled) treatment**: the tile **name** text renders `text-text-secondary` instead of `text-text-primary` when `isInfraServer(name)`, on two surfaces — the Sidebar Server tile (`ServerTile`, `server-panel.tsx`) and the Host-page TMUX SERVERS tile (`host-overview-page.tsx`). Applied **uniformly** to all infra servers (`rk-daemon` and `rk-test-*`). Hover, click, and active-selection are all unchanged — the tile stays fully attachable (reading daemon logs is legitimate) and MUST NOT read as dead/disconnected. The infra de-emphasis is a SERVER-tile treatment only — it does not touch the Sessions-tree `ServerGroup` header, which carries its own per-server tint treatment (§ Per-server `ServerGroup`s → Server-group header tint); an infra server's group header tints from its color (or the gray sentinel) like any other.

### Render Performance (memo tree + leaf-scoped `useNow`)

The sidebar tree does not re-render on every SSE session tick. The session SSE stream fires several times/sec; each tick produces a fresh `slicesByServer` Map in `session-context.tsx`, which churns the derived `sessionsByServer`/`sessionOrderByServer`/`isConnectedByServer` Maps (intentional fresh refs, documented in that file). Three coupled parts keep the whole tree (every `ServerGroup`/`SessionRow`/`WindowRow`) from re-rendering on each tick; **all three are load-bearing — undoing any one silently re-breaks the perf win with no test catching it.** (`260613-ect6`)

**1. Row components are `React.memo`'d.** `WindowRow` (`memo(WindowRowInner)`, `window-row.tsx:955`), `SessionRow` (`memo(SessionRowInner)`, `session-row.tsx:514`), and `ServerGroup` (`memo(ServerGroupInner)`, `index.tsx:2870`) are each wrapped in `memo` (bare named import from `react`). **These are the first — and currently only — `React.memo` usages in the frontend.**

**2. The per-second `now` tick lives in a leaf `useNow()` hook (`hooks/use-now.ts`), NOT a threaded prop.** `useNow()` returns `Math.floor(Date.now()/1000)` and self-ticks every 1s. Its consumers are leaves that are each a single live instance: `WindowContent` in `status-panel.tsx` (feeds the L0 `out` register's elapsed via `getOutputLine`), and inside the row flyout card `RowFlyoutContent` + `FreshnessLine` — both **mounted only while one card is open** (§ Row-hover register flyout card). The sidebar tree itself does not tick per-second — there is no `WindowDuration` leaf inside `WindowRow` and no `nowSeconds` prop threaded through `ServerGroup`→`WindowRow`/`WindowPanel` (a value that changes every render threaded into a memoized child defeats the memo). **Do NOT reintroduce a `nowSeconds` prop on these components, and do NOT re-add a per-second tick to `WindowRow`.** A clock inside a hover surface is acceptable only while that surface is open and mounted. The bottom panel (`WindowContent`) is a single instance, so its per-second re-render is negligible and does not touch the memoized `ServerGroup`/`SessionRow`/`WindowRow` tree. (`260706-y1ar`) The row popups hold the same line: the window flyout's identity title bar is static text composed from the already-passed `win` prop (no new clock, subscription, or lifted state), and the session/server identity-tip cards render `null` while closed — nothing popup-related re-renders while no popup is open, and the memo tree is untouched. (`xb77`) The flyout's slide-to-scrub registry holds it too: an element-keyed module-scope `Map` beside the single-open coordinator, populated by a registration effect inside the row-local `useRowFlyout` — no context, no lifted state, no new props through `ServerGroup`, no re-renders (status-signals.md § Row-hover register flyout card). (`ys3q`) The coarse status rail and the three card tiers hold the same line: the rail is static per-render row content at all three tiers (its inputs — `coarse`, `ghost`, `prOwnsGlyph(win)`, `isSelected`, tint — are already row props/derivations), and every tier's card state is row-local `useRowFlyout` state with the card body built only while open via the `content` render prop — the session/server cards bind the EXISTING stable identity-arg seams (`onServerColorChange`/`onCreateSession`/`onKillServer`/`onSpawnAgent` — no new props), so the R6a memo contract is untouched. (`b8eu`, `260817-ve5m`)

**3. Handler/array props are referentially stable, so the memos actually skip.** Per-row/per-group handlers are identity-arg `useCallback`s in `Sidebar` (taking `server`/`session`/`windowId` as arguments, following the existing `toggleSession` pattern — `handleSessionRowKill`/`handleWindowRowKill`/`handleSessionColorChange`/`handleWindowColorChange`/the drag handlers, `index.tsx:723-749` and the rename/drag block above), so a leaf calls a stable callback with its own identity rather than receiving a fresh closure. The Map/array context props (`rowTints`, `ansiPalette`, `allBoards`, `pinnedSet`, `pinnedToBoard`, `isPinnedToActiveBoardFor`) are verified stable across session ticks (sourced from `useMemo`/`useWindowPins`, changing only on theme/board events).

**THE SUBTLE INVARIANT (R6a — most regression-prone):** the three handler props `Sidebar` *receives from its parents* — `onSelectWindow`, `onCreateWindow`, `onCreateSession` — MUST be `useCallback`s **at their source in the parents**, because both parents (`AppShell` in `app.tsx`, `BoardPage` in `board-page.tsx`) consume `useSessionContext()` and therefore re-render on **every** SSE tick. An inline arrow re-added at either parent recreates these references each tick and silently defeats `ServerGroup`'s memo for **every** group (including the currently-viewed one), with **no test catching it**. The stable callbacks are `handleSidebarSelectWindow`/`handleSidebarCreateWindow`/`handleSidebarCreateSession` (`app.tsx:1116-1154`) and `handleSelectWindow` (`board-page.tsx:363`). **Root-cause fix:** `handleCreateSessionInstant` (`app.tsx:583`) and board-page's `handleCreateSession` (`board-page.tsx:145`) read churning values (`currentWindow`, `isSessionCreatePending`, `ctx.sessionsByServer`) via **render-time-mutated refs** (`currentWindowRef`/`isSessionCreatePendingRef`/`sessionsByServerRef`, set `ref.current = value` on each render) — the same `dialogOpenRef`/`orderOverrideRef` idiom used elsewhere — so the callbacks stay referentially stable across ticks instead of taking those churning values as `useCallback` deps.

**Why the memo skip is cross-server, not full per-row:** `updateSlice` (`session-context.tsx:216-227`) builds a `new Map(prev)` and replaces only the **changed** server's slice via `next.set(server, ...)`; every other server's slice object — and its `slice.sessions` array ref — carries over unchanged. So a tick on server B leaves server A's `sessions` prop referentially identical, and `ServerGroup`'s memo skips A's whole subtree. The currently-ticking server's own rows DO still re-render on its own data tick (correct — its `sessions` ref changed); the `useNow` leaf is what additionally isolates the pure clock tick from even that server's row bodies.

**Shared modal focus trap** (`useFocusTrap`): `useFocusTrap(containerRef, active, onEscape)` (`app/frontend/src/hooks/use-focus-trap.ts`) is the single focus-cycle contract, consumed by **three** surfaces — the Shell mobile drawer, `Dialog` (`components/dialog.tsx`), and `CommandPalette` (`components/command-palette.tsx`). **Nested-modal deference** (R10): while a nested **modal** dialog — a `[role="dialog"][aria-modal="true"]` **descendant** of the trap container — is open, `hasNestedDialog(container)` detects it and the trap stands down entirely: its `handleKeyDown` early-returns before both Escape and Tab. So a single Escape dismisses only the topmost modal, and the container-wide Tab wrap can't pull focus out of the nested dialog into the elements behind it. This applies to every `useFocusTrap` consumer; the live case is the drawer — `KillDialog`→non-portaled `Dialog` renders inside the Sidebar tree, hence inside the `<aside>` — while `Dialog` and `CommandPalette` are leaf modals today, so their stand-down is dormant (correct semantics if one ever nests). The container itself carries `role="dialog"` but is correctly excluded: `querySelector` returns descendants only, backed by an explicit `!== container` guard. **The `aria-modal="true"` part of the selector is load-bearing** (`260613-o20f` PR review): `PinPopover` carries `role="dialog"` but is NON-modal (no `aria-modal`, no internal Tab-trap) — matching it would have made the trap stand down for a layer that doesn't contain focus itself, letting Tab escape the container and regressing the `aria-modal` contract; restricting to modal dialogs keeps the trap live for `PinPopover`/`SwatchPopover`. (Those two popovers attach capture-phase `document` keydown listeners with `stopPropagation`, which independently suppress the trap's bubble-phase Escape listener — so there's no Escape collision with them even though they are not caught by `hasNestedDialog`.)

**Scope behaviors**:

- **`all`** (default): the Sessions Pane iterates the full `servers` array; every server renders as a `ServerGroup` with per-server collapse state (`runkit-panel-sessions-{server}` via `readServerOpen`) applied as usual.
- **`current`** (resolvable): when scope is `current` AND `currentServer !== null` AND `currentServer` is present in the `servers` list, the pane renders exactly one `ServerGroup` (the entry whose `name === currentServer`), omitting all other groups from the DOM (absent, not CSS-hidden), and **force-opens** it (`isOpen={true}` passed regardless of `localStorage["runkit-panel-sessions-{currentServer}"]`) so the filtered view always shows content rather than a degenerate collapsed header. The force-open is **render-time only** — the persisted per-server key is never written by it, and chevron clicks still flow through `toggleServerSection(currentServer)` so the persisted state advances (taking visible effect when scope returns to `all`). Other servers' persisted collapse states sit dormant while filtered out — never cleared or overwritten.
- **`current` fallback-to-all**: when scope is `current` but no current server resolves — a board route (`currentServer === null`) OR a stale/deleted route param not in the `servers` list — the pane **falls back to rendering all servers**. There is no dead-end hint in this case — the `current` scope is never a dead-end or an empty pane.

The `currentOnly` gate in `index.tsx` is exactly `sessionsScope === "current" && currentServer !== null && servers.some((s) => s.name === currentServer)`; when true, `visibleServers` filters to the current server and each group's `isOpen` is forced true, otherwise `visibleServers` is the full list and `isOpen` reads `readServerOpen`. The transition between the all-servers tree and the current-only tree snaps in the next React commit — no group-list-level animation (only the per-group `CollapsiblePanel` body transitions remain). Empty `servers` still renders the "No servers" empty state regardless of scope.

**Session collapse persistence**: the per-session window-list collapse map (`collapsed` in `sidebar/index.tsx`, keyed `` `${server}:${session.name}` ``) survives a refresh, a fresh tab, and a dev-server reload. It persists in a SINGLE localStorage key `runkit-session-collapsed` (the exported `SESSION_COLLAPSED_STORAGE_KEY`) holding a JSON object of collapsed **exceptions** — `{"default:utils2": true, "fabKit1:relay-spike": true}`. Only `true` entries are stored: expanding a session **deletes** its key, and an emptied map removes the storage key outright rather than persisting `{}`, so "no exceptions" and "never used" are one state on the next read. A session with no entry renders expanded — the read sites keep their `collapsed[sessionRowKey] ?? false` default, so a new session and a cleared browser behave exactly as an untouched one. The state is seeded lazily at mount (`useState(readCollapsedSessions)`), so a collapsed session paints collapsed on the first frame with no post-hydration flip. This map key sits **alongside**, not in place of, the per-server section scalars `runkit-panel-sessions-{server}` (§ Default collapse + persistence) — a server's open/closed bit is one boolean per server; the per-session exceptions are one map for all servers, because per-session scalar keys would sprawl unboundedly across killed sessions and could not be enumerated for cleanup. (`260807-kddk`)

**Collapse read/write posture**: `readCollapsedSessions()` is tolerant — a throwing `localStorage` (privacy mode, sandboxed iframe), malformed JSON, a non-object root (an array included), and non-`true` entry values each degrade to `{}` (everything expanded); never a throw, never a blank sidebar. Normalizing to `true`-only entries on read is what keeps the map exceptions-only: a stored `false` is dropped, not honored. `writeCollapsedSessions()` is best-effort under the same try/catch silence (the file-wide localStorage convention). `toggleSession` derives `next` from a `collapsedRef` synchronous mirror, advances the ref, calls the writer, then commits the already-computed value via `setCollapsed(next)` — **the write stays OUTSIDE the state updater**, the same StrictMode purity constraint `toggleServerSection` carries (§ Default collapse + persistence): React 19 double-invokes updaters, so a `setItem` inside one is observed by the second pass and a single click nets to a no-op. The ref mirror covers the second hazard the snapshot alone does not — two toggles batched into one render would both derive from the same stale closure-captured state and persist a map disagreeing with what is committed.

**Two accepted gaps in the collapse map** (§ Design Decisions → Collapse exceptions are a single map key): (1) **no stale-entry pruning** — entries outlive the sessions they name, across kill and rename alike, so a recreated session that reuses a previously-collapsed name **inherits** that collapsed entry. Pruning would require the full session set across *non-attached* servers, which the client deliberately does not have; the orphans are single booleans and cost nothing but that surprise. (2) **no cross-tab sync** — there is no `storage` listener, and each tab snapshots the map at mount. Because a write replaces the **whole** map (the per-server scalars are independent keys, so a collision there is confined to one server), two tabs are last-write-wins across every server's exceptions: the later writer's snapshot wins and the other tab's collapses are dropped. A refresh picks up whatever was written last.

**Desktop selection-keyed autoscroll (scroll-only)**: a SEPARATE `useEffect` on `Sidebar` — alongside, NOT replacing, the mobile drawer-open effect above — brings the selected window row into view when the **selection identity** `selectionKey = ${currentServer}:${currentWindowId}` changes (a sidebar click, palette switch, or deep link). **Session rename**: calls `renameSession(server, oldName, newName)` via `useOptimisticAction`. Toast error on failure. The dialog-based session rename in `app.tsx` is an alternate path — inline editing is an additional one.

**Cross-cancellation**: Only one inline edit (window or session) may be active at a time. Starting any new inline edit cancels the currently active one without committing it. `handleStartEditing` (window edit) sets `sessionCancelledRef.current = true` and clears `editingSession` before activating the window input; `handleStartSessionEditing` sets `cancelledRef.current = true` and clears `editingWindow` before activating the session input. This ensures blur on the cancelled input is a no-op.

**Window drag-and-drop reorder**: Window items in the sidebar are `draggable={true}` (ghost windows excluded). Uses native HTML5 drag-and-drop — no external library (constitution IV). Drag state managed via `dragSource` and `dropTarget` state in `Sidebar`. On `dragStart`, sets `dataTransfer` with JSON `{ server, session, index, windowId, name }`, a dedicated marker MIME `application/x-window-drag` (`WINDOW_DRAG_MIME`, value: the `windowId`) so foreign drop targets — the sidebar board rows, § Sidebar Boards Section — can gate on `dataTransfer.types` during `dragover`, and `effectAllowed: "copyMove"` so board rows can offer the copy (link) cursor while `"move"` stays permitted for the reorder/move targets (`260811-g0t1`). The `windowId` and `name` fields serve cross-session optimistic operations; within-session drops use only `session` and `index`. Within-session drops: drop indicator is a 2px accent-colored top border (`borderTop: 2px solid var(--color-accent)`) on the hovered window item when source and target differ. On `drop`, uses `useOptimisticAction` to immediately swap window indices in the Zustand store via `swapWindowOrder(session, srcIndex, dstIndex)`, then fires `moveWindow(server, srcWindowId, dstIndex)` API call in the background (server captured at drop-handler time; the move targets the source by its stable `windowId` and the destination by position). The optimistic action's arg tuple is `(server, session, srcWindowId, srcIndex, dstIndex)` — `session`/`srcIndex` retained for the store-side swap/rollback, while the API call uses only `srcWindowId` + `dstIndex`. `onSelectWindow` is called immediately (not deferred to API success). On API failure, `onAlwaysRollback` reverses the swap via `swapWindowOrder(session, dstIndex, srcIndex)` and shows a toast error. SSE reconciliation naturally clears the optimistic state when `setWindowsForSession` replaces all entries with server-confirmed data. Same-position drops are no-ops (source === target check). All drag visual state (drop indicators) cleared on `dragEnd` and `drop` — handles both successful drops and cancelled drags (Escape, drag outside sidebar).

**Cross-session drag-and-drop**: Dropping a window onto a different session's header moves it to that session. `handleDragOver` accepts drag events on session headers when the dragged window is from a different session. Visual feedback: the session header shows an accent border (`border-accent`) when a valid cross-session drop is hovering. The drag data payload includes `{ session, index, windowId, name }` — `windowId` and `name` serve optimistic store operations (within-session drop ignores the extra fields). On drop, `handleSessionDrop` calls `executeMoveToSession` (a `useOptimisticAction` instance) with all six arguments `(server, srcSession, srcIndex, windowId, windowName, dstSession)`. The optimistic lifecycle:

- **`onOptimistic`**: calls `killWindow(srcSession, windowId)` to hide the window from the source session, `addGhostWindow(dstSession, windowName)` to show it in the target (using the source window's display name, not a placeholder), and navigates to `/$server` immediately. The `optimisticId` is stored in a ref for rollback.
- **`action`**: calls `moveWindowToSession(server, srcSession, srcIndex, dstSession)` — the API client function with `server` as the first positional argument.
- **`onAlwaysRollback`** (API failure): calls `restoreWindow(srcSession, windowId)` to un-hide in source + `removeGhost(optimisticId)` to remove from target. Toast: "Failed to move window to session".
- **`onAlwaysSettled`** (success): clears the ref. SSE reconciliation handles final state — `setWindowsForSession` removes the entry from the source (not in incoming list), adds it to the target (new incoming entry), and reconciles the ghost (new `windowId` not in ghost's `snapshotWindowIds`).

Same-session header drops are ignored (not a valid cross-session target). Within-session window-to-window drag-and-drop is unchanged. The sidebar handles the move internally — no `onMoveWindowToSession` prop or `handleMoveWindowToSession` callback in `app.tsx` (the sidebar imports `moveWindowToSession` directly from `@/api/client`, matching the pattern of other sidebar API calls).

**Session drag-and-drop reorder**: Session header rows are themselves draggable (the row root, not the chevron / name button) — except optimistic ghost sessions, which set `draggable={false}` because they have no canonical name to persist yet. The reorder feature shares the SAME `<SessionRow>` `onDragOver` handler used by cross-session window drops; the two are disambiguated by `dataTransfer.types`: window drags use the default JSON payload, session reorder drags use a custom MIME `application/x-session-reorder` (so a window-drag never accidentally triggers a session reorder, and vice versa). Native HTML5 drag-and-drop, no external library (Constitution IV).

The persisted order lives server-side in tmux user-option `@rk_session_order` (see `tmux-sessions.md` § "Server-Scoped User Options"), broadcast to all connected clients via SSE event `session-order`. Frontend pipeline:

- **Source of truth**: `SessionContext.sessionOrder: string[]` populated from the SSE `session-order` event handler in `session-context.tsx` (`es.addEventListener("session-order", ...)`). The handler ignores events whose `server` field doesn't match the current `server` prop — defense-in-depth alongside the backend's per-server filtering.
- **Render-time order computation**: `Sidebar` derives `orderedSessions` via `useMemo` over `sessions` and an effective order. Sessions absent from the saved order render at the bottom in their natural sequence (`Number.POSITIVE_INFINITY` rank) so newly created sessions never disappear from the sidebar.
- **Snappy drag (derive-over-store)**: The transient drag override is held in a server-keyed `orderOverrideRef = useRef<Record<string, string[]>>({})` (NOT React state), and the displayed order is *derived at render* as `orderOverrideRef.current[server] ?? (sessionOrderByServer.get(server) ?? [])` — `handleSessionReorderStart`/`handleSessionReorderOver` compute the new order via `splice` and write it into the ref for instant visual feedback. Because writing a ref does not re-render, the handlers call a minimal `forceRender` nudge (`useReducer((x) => x + 1, 0)`). The override clears via a **per-server, render-time SSE-equality reconcile**: while computing each visible server's props, if `arraysEqual(orderOverrideRef.current[server], sseOrder)` the override is deleted and `localOrder` rendered as `null` in the same pass (no nudge needed — the displayed output is unchanged). The per-server equality check (NOT a whole-`sessionOrderByServer`-Map watcher `useEffect`, which would re-run on every unrelated SSE slice tick — sessions/metrics/connection fire a fresh Map reference several times a second) fires only on the relevant server's echo, so unrelated churn triggers no reconcile work; **do not reintroduce a whole-Map watcher.** No **data** snap-back: the override outlives the debounced PUT until that server's SSE order echoes the new arrangement, so the *order* never reverts. (`260609-ebks`)
- **`dragover` MUST accept the drop even on the self-target row**: `handleSessionReorderOver` MUST call `e.preventDefault()` + `dropEffect = "move"` for a valid same-server session-reorder drag *even when hovering the dragged row itself* (`sessionDragSource.name === targetName`), then bail with no reorder math. HTML5 DnD registers a release as an accepted drop only when the LAST `dragover` before mouse-up was `preventDefault()`ed; insert-before splicing lands the dragged row under the cursor, so the dragged row's OWN element is the **common terminal hover state** at release. Bailing early there (folding the self-name check into the leading guard) leaves the final `dragover` uncancelled → no `drop` fires → `dragend` sees `dropEffect: "none"` → the browser plays its native **cancelled-drag snap-back ghost** flying back to the drag origin, contradicting the visibly-succeeded reorder (the data stuck via the debounce). **Guard order (invariant across both this handler and `useServerReorder.onDragOver` — see § Server-tile drag reorder)**: source/scope guard (`!sessionDragSource || sessionDragSource.server !== server`, confines the drag to one server's group) + MIME guard (`application/x-session-reorder`) come BEFORE acceptance; the self-target no-op (`if (sessionDragSource.name === targetName) return;`) comes AFTER `preventDefault()`. Do NOT re-fold the self-name check back into the leading guard — that is exactly the snap-back regression. Session-reorder keeps **debounce-only persistence** — even though `drop` also fires on session rows, there is no session drop-flush (the row's own `onDrop={handleSessionDrop}` is the window-move handler and no-ops safely on a reorder payload: empty `application/json` → `JSON.parse` throws → `catch` → return). (`260705-i41e`)
- **Debounced PUT**: 250ms trailing debounce via `orderPutTimerRef` + `setTimeout`. Drag events fire on every cursor frame; coalescing avoids one HTTP call per frame. `handleSessionReorderEnd` (dragend) does NOT cancel the pending timer — a fast drag-and-release within 250ms still flushes via the timer, otherwise the user's edit is lost.
- **Drag visual**: Source row gets `opacity-50` while it is the drag source (driven by the `isDragSource` prop on `<SessionRow>`).

`<SessionRow>` exposes optional drag props (`draggable`, `isDragSource`, `onDragStart`, `onDragEnd`) — present for the new feature, absent for any future caller that doesn't want session reorder. The row root passes them straight through to the underlying `<div>`.

**Server-tile drag reorder**: the two server-tile grids — the Sidebar `ServerPanel` (`server-panel.tsx`) and the Host-page TMUX SERVERS grid (`host-overview-page.tsx`) — are drag-reorderable, sharing ONE lifted hook `useServerReorder(servers, onError)` (`app/frontend/src/hooks/use-server-reorder.ts`) so neither grid copy-pastes the handler logic. (`260705-bpnr`) It mirrors the § Session drag-and-drop reorder pattern verbatim: native HTML5 DnD (no external library, Constitution IV), a custom MIME `application/x-server-reorder` (`SERVER_REORDER_MIME` — so a server drag never collides with the `application/x-session-reorder` session drag or the default-JSON window drag), insert-before splice semantics on `dragOver`, and the derive-over-store optimistic override.

- **Effective-order input**: the hook takes the already-`compareServersRanked`-sorted `ctx.servers` and returns `{ orderedServers, getTileProps(name), isDragging, draggingName }`. Consumers render `orderedServers` (the transient optimistic order during a drag, else the authoritative list) and spread `getTileProps(name)` onto each tile.
- **Infra excluded**: only REGULAR servers participate. `getTileProps` returns `{ draggable: false }` (no drop handlers) for `isInfraServer(name)` tiles — they are neither draggable nor valid drop targets, and the reorder POST carries only the regular-class order (rank `i` → i-th regular server; infra ignore rank server-side, so omitting them is correct and keeps them pinned last).
- **Derive-over-store optimistic override**: the transient dragged order lives in `overrideRef = useRef<string[] | null>` (of regular server NAMES), NOT React state — so writing it doesn't re-render; a minimal `forceRender` (`useReducer((x)=>x+1,0)`) drives the optimistic repaint (the same idiom as the sidebar session reorder). `onDragStart` seeds the override with the current regular order; `onDragOver` splices the dragged name to the target position. The override clears via a **render-time equality reconcile**: once the authoritative regular order element-wise equals the stored override (via `namesEqual`), the round-trip has landed and the ref is dropped (mutating a ref during render is safe — output unchanged, no nudge). **No data snap-back on drag-end** — the override outlives the debounced POST until the SSE `server-order` echo re-sorts `ctx.servers` to match, which triggers the reconcile, so the *order* never reverts.
- **`onDragOver` MUST accept the drop even on the self-target tile**: `onDragOver` MUST call `e.preventDefault()` + `dropEffect = "move"` for a valid same-hook server-reorder drag *even when hovering the dragged tile itself* (`dragName === targetName`), then bail with no reorder math. HTML5 DnD registers a release as an accepted drop only when the LAST `dragover` before mouse-up was `preventDefault()`ed; insert-before splicing lands the dragged tile under the cursor, so the dragged tile's OWN element is the **common terminal hover state** at release. Folding the self-target check into the leading guard leaves the release-over-self `dragover` uncancelled → no `drop` fires → `dragend` sees `dropEffect: "none"` → the browser plays its native **cancelled-drag snap-back ghost** flying the tile back to the drag origin, reading as failure even though the reorder visibly succeeded and persisted (the data stuck via the debounce). **Guard order (invariant, shared verbatim with the sidebar `handleSessionReorderOver` — see § Session drag-and-drop reorder)**: originating-instance guard (`!dragName` — the hook is instantiated by BOTH `ServerPanel` and the Host-page grid; a null-`dragNameRef` instance did not start the drag and must not accept it) → infra guard (`isInfraServer(targetName)`, infra tiles are non-targets) → MIME guard (`SERVER_REORDER_MIME`) — all BEFORE acceptance; then `preventDefault()` + `dropEffect = "move"`; then the self-target no-op (`if (dragName === targetName) return;`) AFTER acceptance. Do NOT re-fold the self-target check back into the leading `!dragName` guard — that is exactly the snap-back regression. (`260705-i41e`)
- **Debounce + drop-flush**: reorder writes go through a `SERVER_ORDER_DEBOUNCE_MS = 250` trailing debounce (`putTimerRef`), coalescing a rapid drag-over sweep into one `setServerOrder(order)` POST — mirroring the sidebar's `SESSION_ORDER_DEBOUNCE_MS`. `onDrop` flushes any pending debounced POST immediately so the write isn't lost if the SSE echo races the timer. The self-target drop acceptance (above) is what lets releasing over the source tile fire `onDrop`, which flushes and clears the timer (single POST, no double-post). A **mount-scoped unmount cleanup effect** (`useEffect(() => () => clearTimeout(putTimerRef.current), [])`) clears a pending timer so a drag ending right before the grid unmounts never fires a stray post-unmount write (mirrors `sidebar/index.tsx:258-262`). (`260705-i41e`)
- **Drag-source feedback**: both grids dim the dragged tile via `opacity-50`, driven by `isDragging && draggingName === name` (the session-reorder `isDragSource` treatment). Do NOT delete the `isDragging`/`draggingName` fields — they are the drag-affordance seam wired into both grids.
- **Non-drag paths**: the Sessions-tree per-server `ServerGroup`s and the palette `Server: Switch to {name}` entries FOLLOW the order (via the `compareServersRanked` choke point) but expose no server drag affordance. Touch devices get no drag (HTML5 DnD doesn't fire on touch — the palette `Server: Move up/down` are the touch/keyboard path; see § Command Palette Move up/down). Coverage: the hook's logic (MIME discrimination, insert-before splice, infra exclusion, override seed/reconcile, debounce/drop-flush, **self-target drop acceptance + drop-on-source flush**) is Vitest-covered in `use-server-reorder.test.ts`; the API+SSE slice is the `server-reorder.spec.ts` e2e (a live-drag e2e is infeasible under the single-infra-server e2e harness `RK_SERVER_ALLOWLIST=rk-test-e2e`, so it is descoped to Vitest, mirroring the `fixme`'d session-drag e2e). **The native snap-back ghost animation is browser-chrome-level and NOT observable via Playwright synthetic DnD** — the drop-acceptance (`preventDefault`/`dropEffect`) is the only testable seam, so it has unit coverage only, no e2e. (`260705-i41e`)

### Operator Pinned Row (`role === "operator"`)

A window carrying the `@rk_role=operator` window option (the server-scoped operator radio — see [architecture](/run-kit/architecture.md) § Data Model) renders its sidebar row **pinned at the top of its `ServerGroup`'s session area** — directly below the SESSIONS header on the single-server route, at the top of the server group's content on multi-server (board-route) sidebars — **above all session groups**. Placement is the ONLY visual treatment: no badge, frame, label, divider, or any new chrome, and no empty-state placeholder — with no operator marked the sidebar renders exactly as if the feature did not exist. (`260813-ifya-operator-role-pinned-row`)

The mechanics (`sidebar/index.tsx`, `ServerGroupInner`):

- **Move, don't copy** — the row is the ordinary `WindowRow` component (same styling, status dot, hover icons, flyout, kill, label zone, pin popover) EXCLUDED from its home session's window rows (a `renderedWindows` filter drops the carrier from its session group, and `ariaSetSize` follows the filtered list); the session's displayed window count stays tmux-derived and unchanged.
- **Carrier resolution** — an `operatorEntry` memo walks `orderedSessions` and returns the first non-ghost window with `role === "operator"` (`null` otherwise ⇒ nothing renders). Ghost rows are never carriers; the backend's server-scoped radio (at most one carrier per server) makes "first wins" a defensive tie-break, not the rule.
- **Not draggable** — `draggable={false}`; the pinned row does not participate in window drag-reorder (§ Window drag-and-drop reorder).
- **Roving tabindex** — the pinned row still joins the tree's keyboard navigation; its key LEADS the group's visible-row slice regardless of its home session's collapse state, since it is painted above the session groups (§ Keyboard Navigation & Tree ARIA).
- **Collapsed group** — the row renders inside the group's `{isOpen && …}` body, so a collapsed server group hides it like every other row; no floating orphan row ever renders.
- **Name only** — the pinned row shows just the window name (no session prefix); the row flyout carries the rest of the context.

### Keyboard Navigation & Tree ARIA

The session/window tree is a **W3C-APG two-level disclosure tree** with roving-tabindex arrow navigation, scoped entirely to the Sessions tree DOM (never `document`, never the terminal — no xterm.js key conflict). Builds on the Wave-2 memo tree (§ Render Performance) and preserves its SSE-tick invariant. Frontend-only — no backend/API/route/tmux changes.

**Tree ARIA roles** (two levels — decided; the server group stays structural, NOT a treeitem):
- The scrollable Sessions region (`<div role="tree" aria-label="Session tree">`, `index.tsx:1070`) carries `role="tree"`; the outer `<nav aria-label="Sessions">` stays the separate landmark, so the landmark and the tree widget don't collide on one element.
- **Session rows** (`SessionRow`, `session-row.tsx:113-128`) are `role="treeitem"` `aria-level={1}` with `aria-expanded={!isCollapsed}` (lifted onto the treeitem from the chevron), `aria-setsize`/`aria-posinset` (position among `orderedSessions`), and `data-session-row="${server}:${name}"` as the stable focus handle. `aria-controls={windowGroupId}` is emitted **ONLY while expanded** — the `role="group"` window list is mounted only when `!isCollapsed`, so a collapsed row pointing `aria-controls` at an unmounted id would be invalid ARIA (SF-5, enforced via `aria-controls={isCollapsed ? undefined : windowGroupId}`).
- **Window rows** (`WindowRow`, `window-row.tsx:204-217`) are `role="treeitem"` `aria-level={2}` LEAF nodes (no `aria-expanded`) with `aria-setsize`/`aria-posinset` (position among `session.windows`), reusing their existing `data-window-id` handle.
- The **window-list container** (`<div role="group" id={windowGroupId}>`, `index.tsx:1597`) is `role="group"`; that id — `windowGroupId` = `windows-${server}-${session.name}` (`index.tsx:1549`) — is threaded down for the parent session's `aria-controls`. The wrapper carries no left margin — window rows are full-bleed, and the 12px hierarchy indent lives inside each row's left padding (§ Left-Edge Label Zone). Server-group `<section>` headers stay structural wrappers — server collapse/expand remains mouse/Tab-button only for v1.

**Roving-tabindex arrow nav**: exactly one tree row carries `tabIndex={0}` (the roving row), the rest `-1` (`tabIndex={rovingKey === key ? 0 : -1}`, threaded as a single primitive into the memo'd rows so an arrow press flips `tabIndex` on only the two affected rows — the Wave-2 memo skip is preserved). The keydown handler is on the `role="tree"` container (`handleTreeKeyDown`) and early-returns when the target is an `<input>`/`<textarea>`/`isContentEditable` (so a row's rename input keeps Enter=commit / Escape=cancel and arrows move the caret). Bindings (APG-standard, each `preventDefault()`s):
- **ArrowDown/ArrowUp** — next/prev visible row; **stop at the ends (no wrap)**; flow **continuously across all open server groups** as one flat list.
- **ArrowRight** — collapsed session → expand (focus stays, via `toggleSession`); expanded session → first window child; window → no-op (leaf).
- **ArrowLeft** — expanded session → collapse; window → parent session row (scans upward for the nearest `aria-level="1"`); collapsed session → no-op (no parent treeitem — the server header is a wrapper).
- **Enter AND Space** — activate. Derives the target from a typed `RowIdentity` discriminated union (`identityForKey`) and calls `onSelectWindow(server, session, windowId)` / `onSelectWindow(server, session, firstWindowId)` **DIRECTLY** — NOT a synthesized `.click()` or a magic-string `aria-label` match (SF-2). Ghost/optimistic rows (`ghost` flag or empty `windowId`) are a no-op (SF-3), mirroring the drag-path `isGhostWindow` guard; an empty session (no first window) is likewise a no-op.
- **Home/End** — first/last visible row.

**THE LOAD-BEARING INVARIANT (most regression-prone)**: the roving cursor is a `rovingKey` STRING (the row's `data-window-id` / `data-session-row`), NOT a numeric index — so it survives expand/collapse and SSE add/remove without ever pointing at a stale or wrong row, and the "session, then descend into its windows, across groups" order falls out of DOM order for free (`getVisibleRows` reads `[role="treeitem"]` straight from the tree at keypress time). The key-normalization effect (resets `rovingKey` to the first visible row when it matches no rendered treeitem) is gated on `[rovingKey, rowsVersion]`, where `rowsVersion` (a `useReducer` counter) is bumped by `registerGroupRows` **ONLY when a server group's visible-row-SET signature changes** (the `|`-joined ordered row-key string — window add/remove, collapse/expand, rename), NOT on the several-per-second passive SSE activity ticks. This preserves the Wave-2 #262 invariant: **an SSE tick must NOT change roving state or steal focus.** A tick recomputes `rowSlice`/`rowSignature` but the signature STRING is unchanged → no bump → the normalize effect doesn't run (no full-tree `querySelectorAll`, no `setRovingKey`). The only `row.focus()` is gated by `focusMovedRef`, set `true` only on an actual keypress-driven move, so a passive re-render never pulls focus into the sidebar. DOM focus + `scrollIntoView({ block: "nearest" })` on a roving change reuse the CommandPalette/ThemeSelector "Keyboard-Navigable List Scroll Pattern" (§ Keyboard-Navigable List Scroll Pattern). Roving focus is INDEPENDENT of the URL-based `isSelected`/`aria-current="page"` selection (§ URL as Resumable Bookmark) — do not conflate them. The mobile-drawer focus effect (§ Window rows → Current-row focus on mobile drawer open) likewise `setRovingKey`s the row it focuses so its DOM focus and the tab-stop stay in sync (SF-4).

**APG caveats**: the inner per-row buttons (chevron, name, +, ✕, pin, swatch, kill) remain natively `Tab`-focusable rather than being subsumed under the single tree tab stop — a deliberate keyboard-first choice (every control stays reachable) over strict APG purity. The window row's status dot is NOT among them — it carries no `tabIndex`; focusing the row itself opens the flyout card, whose links are Tab-reachable from there (§ Row-hover register flyout card). `role="tree"` wraps the per-server `<section role="presentation">` wrappers — semantically transparent, so the accessibility tree reads tree → treeitem(level 1) → group → treeitem(level 2) with no interposed landmark. The wrappers carry no `aria-labelledby` (a global ARIA property would void the presentation role per WAI-ARIA presentational-conflict-resolution), and the header toggle button carries no `server-header-*` id — `aria-labelledby` would be its only consumer (exsp). The implementation reuses the scroll half of the named list-scroll pattern but deliberately diverges from its `selectedIndex` numeric-state model in favor of the `rovingKey` string + DOM enumeration (see § Keyboard-Navigable List Scroll Pattern's third-consumer note).

### Window-Row Multi-Select (APG multiselectable tree)

The tree is `aria-multiselectable="true"` and carries a **window-rows-only** bulk selection layered onto the roving-tabindex model above. Selection is orthogonal to both the roving cursor and the URL-based `aria-current="page"` selection — three independent notions of "current row" coexist on the same tree. Session and server rows are never selectable: each window is a worktree/change and PR status is per-window (§ PR Status). Its reason for existing is the cleanup chore — windows whose PRs merged accumulate in working sessions — served end-to-end by the two-command flow **`Selection: Select all merged` → `Selection: Close N windows`** (confirmed in the palette; moving the set to a parking session is the non-destructive variant of the same flow). **Three bulk actions** act on the set — move, close, and prompt broadcast — and all three are frontend-only: N sequential calls over per-window endpoints that already shipped for the single-window paths (`moveWindowToSession`, `killWindow`, `sendChatMessage`), no backend surface, no new endpoint, no new client fn. (`260807-nf9f`, `260808-ebgs`)

**Selection state — a dedicated zustand store** (`store/selection-store.ts`, following the `window-store.ts` shape): `selected: ReadonlySet<string>` keyed by the composite `${server}:${windowId}` handle (the same key `entryKey()` and the sidebar's roving `data-row-key` use — tmux `@N` ids are unique per server only), plus a nullable `anchor` for shift-range extension. Actions: `toggle` (flip one key, move the anchor onto it), `select` (add, anchor untouched), `selectOnly` (wholesale replace), `settleBatch(batchKeys, retainKeys)` (§ below), `clear`, and `prune(liveKeys)`. There is deliberately no standalone `setAnchor` (nor a `deselect`): every action that should move the anchor moves it as part of its own write, so no consumer ever needed one. A store rather than sidebar-local state because the two consumers are in different subtrees — the tree that paints and mutates the selection is `sidebar/index.tsx`, the palette that ACTS on it is composed in `app.tsx` (§ Design Decisions → Selection state lives in a dedicated store).

**Pure logic** lives dependency-free in `lib/selection.ts` (the `lib/palette-move.ts` discipline — unit-testable without mounting the tree): `selectionKey(server, windowId)`, `splitSelectionKey(key)` (splits at the FIRST `:`, so a windowId containing `:` round-trips), `rangeBetween(orderedKeys, anchorKey, targetKey)` (inclusive, direction-independent, `[]` when either endpoint is absent — the caller degrades to a plain toggle), `singleSelectedServer(selectedKeys)` (`null` when empty or cross-server — the bulk-move gate), and `pruneSelection(selected, liveKeys)` (returns the SAME set instance when nothing changed, so a caller no-ops without a state write).

**Gestures** (window rows only; ghost/optimistic rows — `ghost` flag or empty `windowId` — are never selectable, mirroring the SF-3 activation guard):
- **Cmd/Ctrl-click** toggles the row and does NOT navigate. **Shift-click** extends the inclusive range from the anchor in VISIBLE-row order (`getVisibleWindowKeys()`, the same `[role="treeitem"]` DOM walk roving nav uses) without navigating; with no anchor — or a stale one whose row has left the tree — it degrades to a plain toggle. The anchor stays put across a shift-click so a second one re-extends from the same fixed end. **Plain click** is unchanged: it navigates, and additionally clears a live selection. The seam is one stable identity-arg `onRowClick(server, session, windowId, {meta, ctrl, shift})` prop on `WindowRow` returning `true` when it CONSUMED the click (the row then `preventDefault()`s instead of navigating) — one reference for every row, so the memo contract holds (§ Render Performance).
- **`x` on the focused row** toggles its selection (`preventDefault()`), a case in the bubble-phase `handleTreeKeyDown`. Chorded `x` (⌘X/Ctrl+X/Alt+X — cut & friends) is explicitly passed through, session rows are a no-op, and the handler's existing `<input>`/`<textarea>`/`contentEditable` early-return keeps `x` typed into a rename input from being hijacked. `x` rather than Space, which is already bound to activation (§ Design Decisions → Keyboard selection-toggle key is `x`).
- **Escape clears** a non-empty selection — a **separate `onKeyDownCapture` handler** on the `role="tree"` container, not a case in the bubble-phase handler (§ Design Decisions → Escape-to-clear is a CAPTURE-phase handler). It consumes the event only when there is a selection AND the target is not editable, so the rename input's Escape-cancels and the flyout card's own Escape-dismiss both keep working.

**Row treatment**: a selected window row's `role="treeitem"` carries `aria-selected="true"` plus a **2px inset accent ring** (`boxShadow: inset 0 0 0 2px var(--color-accent)` — the session-row drop-target idiom), which reads as "member of a set" without competing with the URL selection's tint-depth + bold treatment and costs no layout (rows never shift when selected). The transient `isDragOver` indicator WINS over it while a drag is in flight. `aria-selected` is emitted ONLY when the row is wired for multi-select (`onRowClick` present) — the board-route and unit-test mounts otherwise announce a selection model they don't have.

**Selection-count indicator** (`SelectionIndicator`, file-private in `sidebar/index.tsx`): a non-interactive `role="status"` strip directly under the scrollable tree reading `N selected · ⇧click extends · x to toggle · <palette chord> → Selection: · Esc to clear` (`data-testid="selection-indicator"`). The `⇧click extends` clause renders on fine pointers only — keyboard-chord hints never render on coarse pointers (§ Education micro-copy). The chord is **derived, never literal** — the HOST-effective `command-palette` binding via `useKeybindings()` + `formatCombo` (the same derivation the top-bar Settings gear uses), so it tracks platform (⌘K vs Ctrl+K) and user rebinds; the whole `→ Selection:` clause is dropped when that binding is unbound/disabled or the mount has no `Selection:` actions (§ Selection palette commands). No buttons, no action strip — the palette is the sole action surface (Constitution IV + V). It renders nothing while the selection is empty, so it costs no vertical space at rest, and its hint text is half the `x` gesture's discovery surface (the other half is the palette entry's `shortcut` badge, § Selection palette commands).

**Prune — liveness is DATA-derived, and collapse is not departure.** Each `ServerGroup` registers TWO independent things with the sidebar: its VISIBLE-row identity slice + signature (`registerGroupRows` → `rowsVersion`, gating roving-key normalization) and its DATA window-key set + signature (`registerGroupDataKeys` → `dataKeysVersion`, gating the selection prune). The data set is composed from `orderedSessions` **ignoring `collapsed`/`isOpen`** (real windows only, ghosts excluded), so it holds every window the SSE snapshot knows for that server; its signature is a **sorted** `|`-joined key string, so a pure session/window reorder — which moves nothing in or out of the snapshot — does not bump the counter. The prune effect is gated on `dataKeysVersion` alone and prunes against `getLiveWindowKeys()` (the union over every rendered group's data keys), dropping a stale anchor with its key. **Collapsing or expanding a session changes no data key, so it bumps nothing and touches neither selection nor anchor** — and both signatures being strings over key sets means neither counter bumps on the several-per-second passive SSE activity ticks, preserving the load-bearing "an SSE tick must not change tree state" invariant on both paths. `unregisterGroupRows(server)` is the unmount counterpart to BOTH registrations (drops both slices, bumps both counters), wired from a `ServerGroup` cleanup effect keyed on `[server]` alone — a cleanup on either registration effect would fire on every signature change and double-bump. It covers the case no surviving group's signature does: a whole group leaving the tree (the sessions-scope ALL→CURRENT switch, a server dropping out of the SSE snapshot).

**Bulk execution — three executors over ONE sequential batch helper.** `executeSelectionBatch(keys, operation)` (`lib/palette-selection.ts`) is the shared control flow: it walks the composite keys **in order**, resolves each through `splitSelectionKey` (a malformed key fails locally as that batch item with the first error `malformed window key`, never a thrown exception), awaits `operation({server, windowId})` one at a time, and continues past a rejection, returning `{failedKeys, firstError}`. Its sibling `batchToast(copy, total, result)` composes the ONE aggregate report every batch emits — `<verb> N <noun><qualifier>` on full success, `<verb> X of N <noun><qualifier> — F failed: <first error>` on partial or total failure — so only the operation-specific verb/noun/qualifier copy lives at the call sites. The three `app.tsx` executors are thin over that pair and each ends with `settleBatch(keys, failedKeys)`:

- **`executeBulkMove(srv, keys, targetSession)`** — `moveWindowToSession(srv, windowId, targetSession)` per key. Move is **single-server by gate** (`singleSelectedServer` omits its entries otherwise), so it deliberately IGNORES each key's own server and moves every window on `srv`; only the control flow is shared. Toast `Moved N windows to <session>`.
- **`executeBulkClose(keys)`** — `killWindow(server, windowId)` per key, each against the key's OWN server. Toast `Closed N windows`.
- **`executeBulkSend(keys, text)`** — `sendChatMessage(server, windowId, text)` per key on the key's own server, at the endpoint's default `submit:true` ([chat](/run-kit/chat.md) § Send Path). A per-window structured `409` (novelty-probe failure — text pasted, Enter withheld) is that recipient's failure and does not stop the later ones. Toast `Sent prompt to N agents` / `Sent to X of N agents — F failed: <first error>`. It alone also **resolves the delivered count** (`keys.length - failedKeys.length`), which the compose strip consumes for draft retention (§ Design Decisions → A broadcast clears its draft on DELIVERY).

No bulk optimistic/ghost machinery on any of the three — rows repaint from the SSE stream; the single-window drag-and-drop optimistic `executeMoveToSession` path is untouched (§ Cross-Session Move: Compound Optimistic Update). The terminal `settleBatch(keys, failedKeys)` **subtracts only the keys this batch owned and gave up** from whatever the store now holds, dropping the anchor only when it pointed at one of those (§ Design Decisions → An async batch settles by RECONCILING). In the uncontended case that leaves exactly the failed windows selected as the retry affordance; in the contended one — the palette closes before the batch runs, so a slow batch races the user — a selection the user starts mid-batch survives.

**Tests**: `lib/selection.test.ts` + `store/selection-store.test.ts` + `lib/palette-selection.test.ts` (colocated Vitest units — builder eligibility/counts plus the batch helper's sequencing, malformed-key handling, first-error retention, and toast composition), `sidebar/index.test.tsx` (group-unmount pruning, collapse/expand survival), `command-palette.test.tsx` (the confirm sub-step's Enter/Escape paths), `compose-strip.test.tsx` (the selection-broadcast target, its Enter policy, and both delivery outcomes), and the e2e `tests/e2e/sidebar-multiselect.spec.ts` + its sibling `.spec.md` (cmd/shift-click, `x`, Escape, the count indicator, collapse survival, the real two-POST bulk move, a confirmed bulk close that removes both windows from tmux — with an Escape-cancel that issues no kill — and a broadcast whose frozen target survives a live-selection change and records two ordered chat-send POSTs at `maxInFlight === 1`), all against the isolated e2e tmux server.

**Copyable rows**: The `tmx`, `cwd`, `git`, and `fab` rows are interactive `<button type="button">` elements that copy their underlying value to the clipboard on click or keyboard activation (Enter/Space). Copy values per row:

| Row | Copy value | Source |
|-----|------------|--------|
| `tmx` | Pane ID (e.g., `%5`) | `activePane.paneId` |
| `cwd` | Full unshortened path (e.g., `/home/sahil/code/run-kit`) | `activePane.cwd ?? win.worktreePath` |

**`cwd` deleted-directory marker**: when the active pane's `cwdMissing` flag is set (the backend `os.Stat` found the pane's cwd no longer exists — typically an archived change whose worktree was deleted out from under a still-live tmux window), the `cwd` row keeps the shortened stale path as a breadcrumb but recolors the whole value `text-signal-red` and appends a `(deleted)` tag (`data-testid="cwd-deleted"`); the row `title` reads `<full-path> (no longer exists)`. It uses **color over dimming** — a vanished cwd is more notable, not less, so it reuses the panel's failure-red token (the same `text-signal-red` the `pr` fail-ish row uses) rather than the dimmed `text-text-secondary` of a normal path. The row stays copyable (still copies the stale full path). The marker is **self-healing**: it only shows while tmux still reports the deleted path; once the shell's cwd recovers to a real directory the backend stat succeeds, `cwdMissing` clears, and the row reverts to its normal style. This is the minimal honest signal — run-kit does NOT close or rename the orphaned tmux window (Constitution §VI forbids tearing down tmux windows). ### SERVICES Zone on `/` (Host-page host-console home)

`HostOverviewPage` renders a **SERVICES** zone (`<section aria-label="Services">`) as the LAST zone, below the TMUX SERVERS tile grid, inside the same scroll container. It surfaces the host's listening TCP **ports** as tiles — a listening port is a HOST property (owned by no tmux window/session), so `/` (the box-level console) is its home, mirroring the HOST HEALTH rationale. The backend (`internal/ports`) passively enumerates and broadcasts **ALL** listening ports (procfs on Linux, lsof on darwin) with best-effort process attribution on BOTH platforms — no probing, no HTTP filter (see architecture.md § `internal/ports`). A tile is therefore **not guaranteed to speak HTTP**; the frontend does NO protocol guessing and applies no client-side denylist. Read-only awareness view; the only action opens a port's UI in a tmux window (Constitution IV — nothing mutates host state directly). (`260701-5d0z`, `260703-8y2a`, `260715-vfcz`)

- **Data source**: **`useHostServices()`** (its own `HostServicesContext`, separate from `HostMetricsContext` so the ~2.5s services stream doesn't cascade re-renders into metrics-only consumers). It rides the SAME server-independent broadcast as host metrics — the `event: services` frame arrives on every stream (the dedicated `?metrics=1` stream on a bare `/`, and each per-server stream's fan-out), deduped on the raw payload string (`applyHostServices`). Returns `[]` (never null) before the first tick, so consumers map over it unconditionally. See architecture.md § API Layer `/api/sessions/stream` (`event: services`) and § Server-independent host-metrics subscription.
- **Tiles**: each `Service` (from `@/types` — `{ port, process?, pid? }`) renders a row keyed by `svc.port` showing `:{port}` (mono) + the optional `process` name. **Process attribution is best-effort on BOTH platforms**: macOS populates `process`/`pid` from lsof; Linux joins lsof attribution onto its procfs port set and populates them where lsof can attribute the port, leaving them absent (bare tile) for ports lsof can't see (e.g. root-owned `sshd :22` under a non-root lsof) — see architecture.md § `internal/ports`. Empty state: `No services — listening TCP ports appear here automatically` when the list is empty (pre-first-tick, nothing listening, or an unsupported platform where the collector returns `[]` — Windows/BSD; macOS and Linux both enumerate) — the enumeration is passive and automatic, and the empty state says so (§ Education micro-copy). (`260715-vfcz`)
- **"Open in window" action** (`handleOpenInWindow`): opens the port's UI in an `@rk_type=iframe` tmux window via the existing `/proxy/{port}/` reverse proxy (`createWindow(server, session, "port-{port}", undefined, "iframe", "/proxy/{port}/")` — the `rkType`/`rkUrl` args become the `@rk_type`/`@rk_url` window options), then navigates to `/$server` (the new window surfaces via SSE). The window **name** is `port-{port}`, NOT `:{port}` — tmux rejects colons and periods in window names (`validate.ValidateName`); the tile still *displays* `:{port}`. Since `/` is server-less, it resolves a **target (server, session)**: `servers[0]` + that server's first session from the SSE cache (`sessionsByServer`), else an authoritative `getSessions()` fetch (the per-server stream is usually not attached yet on a fresh `/` load, so the cache can be empty even when sessions exist — fetching avoids a duplicate-name 500 on `new-session`), else an instant `"services"` session created on the fly (`createSession`). An `openingRef` guard debounces a double-click into a single create flow. `servers[0]` reflects the infra-last sort applied in `session-context.tsx` `fetchServers` (see § Infra-server de-emphasis), so a real workspace is preferred over `rk-daemon` as the "first-listed server" target. (`260705-uh8f`)
- **Button gated SOLELY on server existence**: the "Open in window" button is `disabled` with `title="Create a server first"` ONLY when `servers.length === 0` (there is no target to host the iframe window); otherwise it is enabled regardless of port number. The tile still renders in the disabled case.
- **Well-known-port de-emphasis**: with the SERVICES zone showing ALL listening ports, well-known/system ports (`port < 1024`, the reserved range — `sshd:22`, `smtp:25`, …) are visually de-emphasized, mirroring the `isInfraServer` server-tile treatment: their `:{port}` renders grey (`text-text-secondary` instead of `text-text-primary`) and they sort **last as a class**. `isWellKnownPort(port) = port < 1024`; the `orderedServices` `useMemo` partitions `hostServices` into regular vs. well-known, sorts each sub-group by port ascending, and concatenates (regular first) — so regular tiles keep their port-ascending order and well-known tiles trail. **Presentation-only, applied at render in `host-overview-page.tsx`**: the backend snapshot stays port-sorted; this is a frontend concern (parallel to the `session-context.tsx` infra-last server sort — see § Infra-server de-emphasis). Every tile, well-known or not, renders with its "Open in window" button. (`260715-vfcz`)
- **No HTTP gate anywhere**: there is no client-side HTTP-likely heuristic (no `NON_HTTP_PORTS` denylist, no `isLikelyHttpPort(port)`, no disabled branch, no `"Not a web service"` tooltip, no `handleOpenInWindow` guard) and no denylist or HTTP gate on the server; **do not re-add one**. The backend broadcasts ALL listening ports and does no probing, so a tile is not guaranteed to be a web service; **opening a non-HTTP port yields a user-initiated failed iframe — the iframe load IS the on-demand probe** (visible and harmless; there is no ambient probe). The empty state is `No services — listening TCP ports appear here automatically` (meaning "no listening ports"). `types.ts` `Service`/`ServicesSnapshot` carry no `http:` flag — there is no HTTP verdict. ### Row Anatomy — Selection & Board-Pin Cues (`window-row.tsx`)

The window row's visual channels are orthogonal: **hue = label** (family tint), **tint depth = selection**, **left-edge zone = the independent marker axis + the Label-picker trigger** (§ Left-Edge Label Zone — the trigger is fine-pointer-only; on coarse the display-only stripe remains and the card's `Change color…` row is the touch path). Selection and the board-pin cue are borderless — the sidebar window row carries no left accent border.

**Full-bleed row box**: the row `<button>` (`window-row.tsx:238`) spans the sidebar **edge-to-edge** — every box-anchored visual layer (family tint via `buttonStyle`, hover fill, 40% selection tint, the `isDragOver` box-shadow, and the `inset-0` scanline overlay) reaches the physical sidebar left edge with no gutter. The 12px hierarchy indent lives inside the button's left padding (`pl-[30px]` = 12px indent + 18px content padding), not as a group margin on the window-list wrapper — so the status dot and window name sit at a fixed 30px from the sidebar edge (dot leading edge) while the box itself extends to the seam. The wider scanline band on selected+double rows follows from the box reaching the edge and is intended. On COARSE pointers the content start is `coarse:pl-4` (≈16px = 4px stripe inset + 10px max stripe width + 2px clearance) — the interactive label zone does not render there (§ Left-Edge Label Zone); fine pointers keep `pl-[30px]` byte-identical.

**Selection = tint depth + typography, borderless**: a selected colored row deepens to the 40% family tint (`rowTints.get(color).selected`); an uncolored selected row uses the gray sentinel's deeper 0.5 tint. The name goes `font-medium` + `text-text-primary`. There is **no** left accent border on selection.

**Board-pin active-board cue on the pin glyph** (not a border): the persistent filled pin glyph — already `opacity-100` + filled whenever the window is pinned to any board (`isPinnedToAny`) — renders **accent-colored** when the row is pinned to the currently-viewed board (`isPinnedToActiveBoard`), and monochrome `text-text-secondary` otherwise. `isPinnedToActiveBoard` implies `isPinnedToAny`, so the accent branch is always the persistent (never hover-gated) glyph. This is load-bearing because link-based pinning keeps pinned rows visible in SESSIONS: the cue distinguishes "pinned to the board you're viewing" from "pinned to some board" with zero new elements, leaving the left-edge zone for the marker + Label picker. See § Active-Board Highlight in Sessions Tree, § Sidebar Pin Icon on Window Rows. (`260718-co9z`)

### Left-Edge Label Zone (`window-row.tsx` `LabelZone`)

The whole 26px to the left of the status dot on each window row is ONE interactive target that opens the combined **Label picker** (colors + marker). It consolidates both of the row's label axes on the left edge — hue and the independent 5-state marker — leaving the right hover cluster for actions (pin + kill). The interactive zone is **fine-pointer-only**: on coarse pointers the zone and its palette-icon reveal are render-gated off; the touch path to color/marker is the card's `Change color…` row (status-signals.md § Row-hover register flyout card), the display-only marker stripe stays rendered, and the content start reclaims the space (`coarse:pl-4`, ≈16px). The marker is an abstract label axis, orthogonal to hue and selection; its states are deliberately unnamed in the UI (todo/doing/done for one user, priority for another), though `dashed` = "working" and `thick` = "completed" are the suggested conventions — **label conventions only, with no functional wiring** to `@rk_agent_state` or the status pyramid.

**One 26px target, opens the picker — never cycles, never selects**: clicking anywhere in the zone opens the combined Label picker anchored at the row's bottom-left (an `absolute left-0 top-full z-50` wrapper; the row root stays overflow-free so the `top-full` popover is not clipped even on a selected+double row). The click `stopPropagation`s so it does not select the row, and coexists with drag-reorder. Cursor is `pointer` (menu-opener semantics). The zone is enabled on non-ghost rows wired with both the color and marker write seams plus a `server` (`labelZoneEnabled`).

**Zone geometry**: an absolute `z-20` sibling positioned `left-0` spanning `LABEL_ZONE_WIDTH = 26`px (full row height). Because the row box is full-bleed (§ Row Anatomy), `left-0` IS the physical sidebar edge — the zone needs no negative offset, so the coordinate expression is a plain `left-0` overlay. The zone's absolute span (sidebar x = 0…26) is 26px of the true sidebar edge. The palette-icon home is a 12px band (`ICON_ZONE_WIDTH = 12`) inset `ICON_EDGE_INSET = 12`px off the physical edge (sidebar x = 12…24) — past the widest (double, 4+6=10px) marker stripe, so the hover icon sits beside the stripe rather than over it. The button content is padded clear with `pl-[30px]` (12px hierarchy indent + 18px content padding) so the leading StatusDot + name start 4px past the zone's inner edge — the dot keeps its click-to-select (and its coarse-pointer flyout tap), and the dot + name keep their exact x-positions (no content shift). On coarse pointers the interactive zone does not render at all; only the display-only marker stripe remains at the left edge (and the row overlays — scanlines/hazard/data-rain/flair — stay).

**Hover affordance — palette icon + two-stage zone glow**: at rest the zone is transparent with no icon. On ROW hover (`group-hover`) the shipped `PaletteIcon` (~11px, in the 12px icon zone at `left: ICON_EDGE_INSET = 12`px, beside the edge-anchored stripe rather than over it) fades to ~65% and the whole zone glows ~12% family color; when the ZONE ITSELF is hovered the icon reaches full opacity and the glow deepens to ~24% (`color-mix`). **Marker vocabulary — 5 states, one display order**: `themes.ts` owns `MARKER_STATES = ["", "dotted", "dashed", "solid", "double", "thick"]` (empty first, then the display order dotted → dashed → solid → double → thick) and the `markerStripeStyle(state, color)` helper, shared by this stripe and the Label picker's marker cells so the stripe vocabulary lives in exactly one place. Rendering per state, all in the guarded family color (gray uncolored): `dotted` = 3px-wide column of 3px dashes / 3px gaps; `dashed` = 3px-wide column of 8px dashes / 4px gaps (12px period); `solid` = `border-left: 3px solid`; `double` = `border-left: 6px double`; `thick` = `border-left: 6px solid` (a continuous bar). Markers are available on all rows including uncolored ones.

**Marker semantics (user-owned, deliberately distinct from the status dot)**: markers and row colors are USER PREFERENCES — what the user thinks about a task — whereas status-dot states are DERIVED (activity/PR/agent signals, § Status Dot); the two axes never mix, by design. Three markers carry agreed meanings: `dashed` = **working** (an agent is actively working here — the data-rain pairing), `thick` = **completed** (done, taped off — the hazard-wedge pairing), `double` = **different** (this window IS different — what "different" means is the user's call; the scanline wash makes it the showcase mark). The remaining states — none, `dotted`, `solid` — are entirely free for per-user conventions (e.g. dotted = "still deciding whether to start an agent", solid = "made up my mind what to do"). None of this is wired to `@rk_agent_state` or any derived signal; the semantics are hand-set conventions only.

**Dashed data rain (always-on row overlay)**: a `dashed`-marked window row carries `.rk-dash-rain` — two sparse 1px dash tracks streaming LEFT→RIGHT across the row's full width in the guarded marker color: the ambient "agent is working" cue. Mounted on `isDashed` alone (`window-row.tsx`), in every state — "working" is inherently live, and the thinned two-lane rain is quiet enough to run ambiently (§ Design Decisions → Dashed data rain is always-on, not selection-gated); the gutter stripe itself stays STATIC in every state. Same overlay discipline as scanlines/hazard: a dedicated clipped inner element (`absolute inset-0 z-[5] overflow-hidden pointer-events-none`), never the row root, reading `--rk-marker-color` from the root (set for dashed rows too). Each track has its own rhythm (7px dash/36px period at y 8px; 5px dash/28px period at y 16px) so the lanes drift at different speeds and read as rain, not a marquee. **Seamless loop rule**: each layer's tile is ONE FIXED PERIOD wide (`background-size: 36px 1px, 28px 1px` — never `100%`, which makes the tile element-width-dependent and snaps at the loop boundary), and the keyframes displace each layer by an integer multiple of its own period (72/56px over 2.8s), so the cycle point is invisible. `background-position` only, never transform (the drag-ghost rule). Under `prefers-reduced-motion` the rain hides entirely; the static label cue is the dashed stripe itself. The picker's marker preview cells never carry it.

**Marker stripe is display-only**: the marker renders as a left-edge stripe via `markerStripeStyle`, hoisted to the ROW ROOT so it renders on every pointer (including coarse, where the interactive zone is gone) — anchored near-flush at the sidebar's physical left edge, `left: STRIPE_EDGE_INSET = 4`px with width `LABEL_ZONE_WIDTH - STRIPE_EDGE_INSET` (`window-row.tsx`). It is purely a display of current state — `pointer-events-none`, never a click target (the picker's openers are the zone on fine pointers and the card's `Change color…` row on coarse); it does not cycle.

**One-period fixed stripe tiles**: the gradient cases (`dotted`, `dashed`) use a plain `linear-gradient` of exactly one period with `backgroundRepeat: "repeat-y"` — dotted `backgroundSize: "3px 6px"` (`${color} 0 3px, transparent 3px 6px`), dashed `backgroundSize: "3px 12px"` (`${color} 0 8px, transparent 8px 12px`) — NOT `border-left: dotted` (a dotted border distributes dots per-element and restarts at every row, so stacked dotted rows would show seams while solid/double merge) and NOT an element-height-dependent `repeating-linear-gradient` + `3px 100%` + `no-repeat` tile. Because each tile is exactly one period, the rhythm is correct at ANY element height (e.g. the 18px picker preview cells), not only at heights that happen to be period multiples; row rendering is pixel-identical because the 6px/12px periods divide the 24px (36px coarse) row heights exactly, so the rhythm carries across adjacent stacked rows.

**Marker/color plumbing**: `WindowInfo.marker?: string` (`src/types.ts`) carries the state from the `@rk_marker` window option (architecture.md § `@rk_marker`). `setWindowMarker(server, windowId, marker | null)` in `client.ts` delegates to `setWindowOptions({"@rk_marker": ...})` (empty/`null` clears). `sidebar/index.tsx` owns `onColorChange` + `onMarkerChange` handlers, prop-drilled through `ServerGroup` to `WindowRow`; the Label picker passes the **exact** picked color and marker state straight to these (no cycling — any state is one click). The `Window: Label` palette action opens this same picker via an imperative `label-popover:open` CustomEvent that the matching `WindowRow` listens for (`{ detail: { server, windowId } }`, mirroring the `pin-popover:open` pattern); the row registers both listeners in one `useEffect`. **Scope: window rows only** — session rows and server tiles get the owned-palette color affordance but no marker and no left-edge label zone.

### Row Flair — Character Animations (all three row types)

A row can carry at most one **flair** — `""` (unset) / `nyan` / `naruto` / `onepiece` — an opt-in, purely decorative character-animation overlay channel, orthogonal to color tint and (window-only) markers: a row can have all three at once. Flair carries no semantic meaning and has no wiring to `@rk_agent_state` or the status pyramid. `themes.ts` owns the single vocabulary `FLAIR_STATES = ["", "nyan", "naruto", "onepiece"]` + the `FlairState` type, shared by the picker and all gating. (`260814-2esh`)

**Overlay mount — same slot on every row type**: a flaired row mounts a dedicated `<span aria-hidden="true" class="absolute inset-0 z-[5] overflow-hidden pointer-events-none rk-flair-{value}">` — clipping on the overlay, never the row root (the `.rk-scanlines` discipline). Window rows (`window-row.tsx`, sibling of the scanlines/hazard/dash-rain overlay slot, gated on `win.flair`) and session rows (`session-row.tsx`, on the already-`relative` row root); server group headers carry NO flair — they mirror the SERVER-pane tiles, whose visual identity stays flair-free. Flair is a stable string on the existing row data objects, so the `SessionRow`/`WindowRow` memoization is untouched; the animation itself is CSS-only — no JS timers, no per-render props. The treatments themselves (`.rk-flair-nyan`/`-naruto`/`-onepiece`, always-on ambient, hidden entirely under `prefers-reduced-motion`) are documented in [visual-design](/run-kit/ui/visual-design.md) § Character Flair Overlays.

**Flair plumbing**: window flair rides the `@rk_flair` window option onto `WindowInfo.flair?: string`; session flair rides the scope-split `@rk_session_flair` session option onto the session payload's `flair` (a shared name leaks across scopes in tmux format expansion — see tmux-sessions.md § user-option registry). `sidebar/index.tsx` owns `handleWindowFlairChange` / `handleSessionFlairChange` (beside `handleWindowMarkerChange`), calling `setWindowFlair` / `setSessionFlair` with toast-on-error; `""` clears, mirroring the marker contract.

**Picker entry points — one flair section, two surfaces**: `SwatchPopover` renders a **flair section** whenever an `onSelectFlair` callback is supplied (with `selectedFlair`): four cells — ∅ / nyan / naruto / onepiece in `FLAIR_STATES` order (`data-flair-value` per cell) — following the marker column's pattern, except the non-∅ cells ARE live previews carrying their always-on animated `.rk-flair-*` overlay (marker preview cells never animate; flair previews do). Selection calls `onSelectFlair` directly with the exact state (no cycling; `""` clears), the current cell carries `aria-selected` + selection ring, and keyboard nav reaches the flair cells. The section is wired at the two flair-capable entry points: the window-row **Label picker** (color + marker + flair) and the session-row **color picker** (color + flair, still NO marker column — markers stay window-only). The server-group color picker stays color-only.

### Sidebar Kill Controls

- **Session row ✕**: the session-row cluster's ✕ button (fine-pointer-only — render-gated `!coarse` with the whole cluster; on touch the kill path is the session card's Kill session row, which always confirms) with red hover. Normal click opens confirmation dialog: "Kill session **{name}** and all {N} windows?" **Ctrl+Click / Cmd+Click** bypasses the confirmation dialog and kills immediately (best-effort `.catch(() => {})`).
- **Window row ✕**: Hover-reveal ✕ button on window rows, fine-pointer-only (the buttons render-gate on `!coarse`; on touch the kill path is the flyout card's Kill action row — status-signals.md § Row-hover register flyout card). Normal click opens confirmation dialog: "Kill window in **{session}**?" **Ctrl+Click / Cmd+Click** bypasses the confirmation dialog and kills immediately (best-effort `.catch(() => {})`); the card's Kill row always passes `ctrl: false`, so kill on touch always confirms (there is no modifier on touch).

The Ctrl+Click force-kill pattern follows the "modifier = power action" convention. Modifier detection uses `e.ctrlKey || e.metaKey` (Ctrl on Linux/Windows, Cmd on macOS).

### Command-palette per-server kill listing

The command palette's `serverActions` block (AppShell's route list) lists **one `Server: Kill {name}` entry per server**, the current server suffixed ` (current)` — following the `Server: Switch to {name}` enumeration pattern. Entry composition is a pure builder, `buildServerKillActions(serverNames, currentServer, onKill)` in `app/frontend/src/lib/palette-server-kill.ts` (mirroring `palette-pin.ts` / `palette-move.ts`, colocated unit test), each action id `kill-server-{name}` with a thin `onKill(name)` body; `app.tsx` wires `onKill` to the `server-dialogs-context` `requestKillServer` trigger, funneling every entry through the single layout-mounted kill-server confirm (`components/server-dialogs.tsx`, incl. the `DAEMON_SERVER` warning — § Kill guard for `rk-daemon`; § Server create/kill dialogs). This is the keyboard escape hatch (Constitution V) that keeps **every** server killable — including non-current servers, which have no SESSIONS-pane group header under the pane's `current` scope mode (§ Sessions-pane scope) and no hover kill affordance on the SERVER-panel tile (§ Sidebar `server-panel.tsx` — the tile carries no action cluster). Kill stays the existing POST flow (Constitution IX); the board route registers no server entries (its sidebar kill affordances reach the same dialog through the context).

### Server create/kill dialogs — single AppLayout mount

The create-server and kill-server confirm dialogs render **exactly once**, mounted in `AppLayout` alongside the one `SettingsDialog` mount (§ Design Decisions → One palette mount in AppLayout, routes register via the slot): `components/server-dialogs.tsx` owns the create-input local state and the submit/kill handlers (`useOptimisticAction` wrappers around `createServer`/`killServer` with `markServerPending`/`markKilled` + ghost add/remove), and `contexts/server-dialogs-context.tsx` (the `settings-dialog-context` pattern — small state + referentially-stable triggers) is the trigger channel: any route calls `openCreateServer()` / `requestKillServer(name)` and reads the open-state (`createServerOpen`, `killServerTarget`) for its modal-gating predicate (AppShell's `dialogOpenRef` gates chord handling on it). Both `Sidebar` mounts (AppShell and BoardPage) wire `onCreateServer`/`onKillServer` straight to the context triggers — the memoized server-group header cluster depends on their referential stability.

**Unified behavior is one superset on ALL routes** — there is no route-specific dialog variant:

- **Create**: `toSafeServerName` applies live on input change and `finalizeSafeName` on submit (§ Live Safe-Name Conversion); on submit the flow runs `markServerPending(name)` and navigates to `/$server` (route-agnostic — a board-route create lands on the new server), with `refreshServers()` on settle so the waiting state swaps to the view.
- **Kill**: the `DAEMON_SERVER` warning renders on every route when the target is the daemon server (§ Kill guard for `rk-daemon`). After a confirmed kill the app navigates to `/` **only when the killed server is `SessionContext`'s `currentServer`** (the deepest-first route-param walk) — `null` on board routes, so a board kill never navigates away.

## Design Decisions

### Rail button labels are tier-1 Tips, not identity-tip cards
**Decision**: Rail button hover labels use the shared tier-1 `Tip` component with a state-flipping action label, like the SESSIONS scope chip.
**Why**: The tooltip promotion rule (status-signals.md § Tooltips — Two-Tier Taxonomy) is explicit: a tooltip that names a control is tier-1; tier-2 identity tips carry a second line of identity/state. A rail toggle's label is a control name with zero state payload.
**Rejected**: `IdentityTipCard` per button — a title-bar-plus-body card for a 24px toggle violates the two-tier boundary and duplicates chrome for no added information.
*Introduced by*: 260817-iha5-sidebar-section-visibility-rail

### Section-visibility gate lives in the Sidebar orchestrator
**Decision**: Section booleans are read in `Sidebar` (and `SectionRail`) via `useSidebarSectionVisible`; gated sections are conditionally rendered at their existing mount sites.
**Why**: `Sidebar` already re-renders on its own state; reading four pub/sub booleans there adds no churn to the memoized row tree (R6a untouched — no new props through `ServerGroup`).
**Rejected**: A context provider for section visibility — needless indirection for four booleans already synchronized by the `useLocalStorageBoolean` pub/sub.
*Introduced by*: 260817-iha5-sidebar-section-visibility-rail

### Server tree wrappers are presentational sections, not groups
**Decision**: The per-server `<section>` wrapper inside the sidebar `role="tree"` carries `role="presentation"` and no `aria-labelledby`; the element stays `<section>` (no swap to `<div>`), and the header toggle button keeps its own `aria-expanded` + `aria-label` naming.
**Why**: A `<section>` with an accessible name maps to the implicit `region` landmark role, which is not a valid intervening node between a tree and its treeitems; `role="presentation"` makes the wrapper semantically transparent, so the accessibility tree reads tree → treeitem(level 1) → group → treeitem(level 2). The `aria-labelledby` removal is spec-required, not optional: WAI-ARIA presentational-conflict-resolution voids the presentation role when the element carries a global ARIA property, so keeping it would silently leave the section exposed as a named `region` and make the fix a no-op.
**Rejected**: (a) `role="group"` per server — the server header row's non-treeitem buttons live inside the same wrapper, so a group would still interpose non-treeitem interactive content between the tree and its level-1 treeitems (backlog exsp also prescribes `presentation`); (b) swapping `<section>` for `<div>` — implicit semantics are neutralized either way, so the swap is pure churn; (c) keeping `aria-labelledby` alongside `role="presentation"` — spec-voided, change becomes a no-op.
*Introduced by*: 260811-exsp-sidebar-tree-aria-presentation

### Sessions-pane scope is explicit state, not the SERVER panel's expansion
**Decision**: The sessions-pane scope (`all | current`) is its own persisted state (`runkit-panel-sessions-scope`), read via `useSessionsScope`, with no migration from the old `runkit-panel-server` coupling; the SERVER panel defaults open and its expansion no longer affects the session list.
**Why**: "do I want to see server tiles?" and "which servers' sessions do I want listed?" are unrelated concerns that previously shared one bit — so the SERVER panel couldn't default open without permanently filtering the list, and users couldn't filter the list without paying the tile grid's vertical cost. `runkit-panel-server` encodes panel visibility, not scope intent, so carrying it over would guess wrong as often as right.
**Rejected**: Migrating the old key (encodes the wrong intent); keeping the "Select a server above…" hint with reworded text for the no-current-server case (chose fallback-to-all instead — never a dead-end).
*Introduced by*: 260720-rzg7-sessions-scope-toggle-delink

### Scope state uses a generic enum-typed localStorage hook
**Decision**: Add `useLocalStorageEnum<T extends string>` as a generic sibling of `useLocalStorageBoolean` (same pub/sub + `storage`-event mechanics, unrecognized values → default), plus a thin `useSessionsScope()` wrapper exporting the `SessionsScope` type and key constant.
**Why**: The chip, session list, and palette entry are cross-component siblings needing one reactive source; a generic hook mirrors the established boolean sibling and keeps the scope vocabulary in one importable home.
**Rejected**: Encoding scope as a boolean in the existing hook (values are semantically `all|current`, not true/false); duplicating the pub/sub logic in a scope-specific hook (needless divergence from the boolean sibling).
*Introduced by*: 260720-rzg7-sessions-scope-toggle-delink

### Infra servers are greyed, not hidden; identified frontend-side by name
**Decision**: infrastructure tmux servers (`rk-daemon`, `rk-test-*`) are de-emphasized (greyed + sorted-last) but never hidden; they are identified frontend-side by name (`isInfraServer`), not by a backend flag.
**Why**: the backend deliberately surfaces every server so the operator sees exactly what `rk reaper` would reap (the contract at `tmux.go:1332-1341`); greying + sorting-last preserves that visibility while making the infra/workspace distinction legible. A name-based check keeps a pure display concern out of the API, and the socket name is effectively frozen (renaming it orphans deployed daemons).
**Rejected**: hiding infra servers (loses the reaper-visibility contract); a backend `isDaemon` flag on `/api/servers` (API surface for a display concern).
*Introduced by*: 260705-uh8f-deemphasize-infra-servers

### HostMetrics is a shared component
**Decision**: the host metric-row rendering lives in one layout-agnostic `HostMetrics` presentational component consumed by both the sidebar `HostPanel` and the `/` HOST HEALTH zone.
**Why**: the two host surfaces must stay visually consistent; a shared component avoids drift.
**Rejected**: duplicating the ~120 lines across the two surfaces (drift risk).
*Introduced by*: 260701-vshd-cockpit-host-console-home

### Focused-pane context carries thin board-entry data, not just identity
**Decision**: the focused-pane context value is `{ server, windowId, windowName, panes }` (tile identity + the board entry's thin pane data), not the bare `{ server, windowId, cwd }` triple the top-bar slot's `focusedPane` carries. The board route's board-entry enrichment reaches the sidebar PANE fallback through this one channel.
**Why**: the pin-only thin render (a window whose home session died while pinned, so the `windowId` lookup in `sessionsByServer` misses) needs `windowName` + `panes` at the consumer; publishing them with the identity keeps `BottomPanels` free of any board-API knowledge and avoids a second data channel. Server-side enrichment of `GET /api/boards/{name}` was rejected upstream (staleness between `board-changed` refetches + duplicates the live SSE enrichment the home-session copy already delivers), so the fill is a pure client-side join.
**Rejected**: publishing only `{server, windowId}` and having the sidebar fetch/join board entries (reintroduces board-data plumbing into the sidebar plus a fetch the board page already holds); a dedicated thin-render branch inside `WindowPanel` (would duplicate row markup and couple the pure panel to board types — instead the fallback synthesizes a partial `WindowInfo` with `activityTimestamp: 0` and renders through the unchanged `WindowPanel`).
*Introduced by*: 260720-zx4i-board-route-pane-host-panels

### App-global actions live in the top bar; the sidebar footer is a passive status row
**Decision**: Settings is a persistent top-bar right-cluster chip (the L3-tail fit candidate, immediately before the exempt chevron); Help, Keyboard shortcuts, and Theme… are `menuOnly` App-section rows in the chevron menu, above the fixed version row; notifications live in the settings dialog. The sidebar footer (mobile drawer only) keeps only passive readouts — the connection dot and the resting version line — plus a right-aligned, truncating, non-interactive status slot whose only content so far is the accent-green update-available hint. Theme switching has no click-to-cycle surface: the "Theme…" row opens the theme selector. On desktop the connection dot lives in the full-width status bar — mounted on every desktop route, with the Host page mounting its own `StatusBar` — so sidebar-less desktop states (the Host route `/`, a collapsed desktop sidebar via `Cmd+\`) keep the indicator; a closed mobile drawer shows no connection dot, with no mode-gated fallback.
**Why**: the top bar is the one chrome surface mounted on EVERY route, so app-global actions parked there stay reachable on the Host page, on mobile, and with the sidebar collapsed — the footer's action cluster vanished exactly when the sidebar did. One home (not split across rail + menu) avoids "where did settings go?" hunting; Settings, the highest-frequency of the four, keeps a one-click chip while the other three tolerate a second click, and all four stay palette-reachable via their existing entries (Constitution V). The freed footer row gains room for one-line status (the update hint), and the dot's absence on a closed mobile drawer remains cheap and reversible — the drawer is one tap away.
**Rejected**: keeping the four actions in the footer — whether as borderless glyphs (the pre-`260811-cj4b` treatment) or as bordered footer-scale chips (`260811-cj4b`), both spent the sidebar's only always-visible bottom row on low-frequency actions that hid with the sidebar; parking Settings/Keyboard at the bottom of the right rail mixes app-global scope into page chrome and drops the actions on Host/server/board routes and mobile; a settings *page* (constitution §IV — no settings pages).
*Introduced by*: 260812-d1at-relocate-footer-actions-top-bar

### Connection state reaches the Sidebar as a prop, not through the top-bar slot
**Decision**: `isConnected` is a required `SidebarProps` field — AppShell passes its chat-aware `dotConnected`, BoardPage its `boardConnected`. Neither `TopBarSlot` nor `TopBarProps` carries an `isConnected` field, and the Host page registers no slot at all (connection state was its only payload).
**Why**: explicit dataflow, unit-testable without mounting a slot provider and registering a fake slot, and it leaves no dead slot plumbing behind. The footer dot gets exactly the same per-page values (chat-aware on terminal routes, AND-over-servers on boards).
**Rejected**: the Sidebar reading `useTopBarSlot()` (keeps a dead-ish field alive, couples the sidebar to top-bar plumbing, and forces every sidebar test into a slot-provider harness).
*Introduced by*: 260724-6j1v-sidebar-footer-chrome-settings

### Footer version is a readout; the overflow menu's version row stays the update surface
**Decision**: the footer's `v…` line is a passive readout with click-to-copy only, rendering nothing when `daemonVersion` is null. The overflow menu's fixed version row keeps both its copy form and its update/⟳-check forms.
**Why**: the footer's job is resting identity ("what am I running") at a glance; the menu row is the *unified update button's* resting form and owns the check affordance and the update flip (§ Steady-state version surfaces → surface 5). Duplicating the update surface would mean two places to keep the updating-state and toast behavior in sync. Rendering nothing on a null version avoids a dead copy target and a `vundefined` placeholder — the same degrade-or-omit rule every version surface follows.
**Rejected**: a `RunKit` text fallback in the footer when the version is unknown (surface 5's form, but here it would be a live-looking button with nothing to copy); moving the update surface into the footer (loses the menu's ⟳ + attention-badge wiring for no gain).
*Introduced by*: 260724-6j1v-sidebar-footer-chrome-settings

### The sidebar keeps unmount-on-collapse
**Decision**: joining the card family did not change the sidebar aside's mount gating — it still fully unmounts when `sidebarOpen` is false.
**Why**: the right rail's never-unmount contract existed for iframe in-memory state (web/code surfaces); the sidebar holds no iframes, and its unmount-on-collapse is long-established behavior with the 150ms column transition.
**Rejected**: display-hiding the sidebar like the rail (a mounted-but-hidden subtree with zero benefit).
*Introduced by*: 260815-19me-composed-frame-unification

### One stroke-SVG icon system in sidebar rows, sized by ink not by position
**Decision**: Sidebar row action glyphs are all `sidebar/icons.tsx` stroke SVGs on one idiom (24-unit viewBox, `strokeWidth={2}`, 13px) — `PlusIcon` and `CloseIcon` replace the former text `+`/`✕` — and `BotIcon` is optically centered by a `viewBox` y-shift rather than a wrapper transform.
**Why**: The reported "icons aren't equidistant" was optical, not geometric: measured center-to-center gaps were already even to within 0.7px, but a 16px text glyph beside a 13px stroke SVG differs in ink width and weight, which reads as uneven whitespace. Equalizing the ink is the root-cause fix; nudging positions would have chased the symptom. Shifting `BotIcon`'s viewBox keeps the rendered box exactly 13px, which a `translate-y` wrapper class would not guarantee across the cluster's flex centering.
**Rejected**: nudging gaps/padding per button (treats the symptom); resizing the text glyphs down to 13px (still two ink systems); a `translate-y-[0.5px]` wrapper on the bot button (changes the box, not the drawing).
*Introduced by*: 260724-2bmy-mobile-chrome-polish

### Render-gate the coarse window-row cluster
**Decision**: On coarse pointers the window row's entire trailing `group/icons` cluster — pin/kill buttons AND the container — is render-gated (`!coarse && …`) rather than CSS-hidden; the coarse trailing zone is the 56px status rail instead (§ Sidebar Row Icon System). The session-row and server-group-header clusters follow the identical gate (their actions live in their tiers' rail-triggered cards).
**Why**: Render-gating removes the buttons from the accessibility tree and tab order on touch (an `opacity-0 pointer-events-none` button would still be focusable), and the row already reads `useCoarsePointer()`. The container has no reason to survive on coarse once the rest-state PR glyph's home is the rail's fixed 16px slot — an empty container would only risk swallowing rail touches when a sticky `:hover` restores its pointer-events. Pin/kill stay reachable on coarse through the flyout card's action rows — and removing an always-visible ✕ per row also removes a fat-finger kill hazard on a phone.
**Rejected**: pure CSS class removal (`coarse:opacity-100` → nothing) — leaves invisible focusable buttons in the DOM on touch and makes the "not hittable" contract depend on class subtleties instead of structure; keeping the container mounted as the glyph's overlay anchor (dead DOM on coarse, touch-swallow risk).
*Introduced by*: 260816-ys3q-mobile-pr-glyph-flyout-scrub, 260816-b8eu-status-rail-card-actions

### Cluster gating mirrors the window precedent
**Decision**: the session-row and server-group-header clusters are render-gated `!coarse`, not CSS-hidden — the same structural gate the window row's cluster carries.
**Why**: render-gating removes the buttons from the accessibility tree and tab order on touch and makes "not hittable" structural; an always-visible coarse fallback cluster is the cramped touch affordance the rail + card system exists to avoid (the actions live in each tier's card; palette/desktop paths are untouched).
**Rejected**: class removal (invisible focusable buttons in the DOM on touch).
*Introduced by*: 260817-ve5m-three-tier-status-rail-cards

### The status rail is the coarse trailing zone — gesture home AND glyph slot
**Decision**: On coarse pointers the trailing 56px of every non-ghost row of ALL THREE tiers (window, session, server-group header) is a visually-treated status rail (inset band, seam, fixed 16px glyph slot + 12px `›` slots — the glyph slot always empty on session/server rows) forming ONE continuous strip down the tree, serving as the flyout gesture's PRIMARY tap/scrub target at every tier AND the PR glyph's coarse home on window rows; the fine-pointer absolute last-slot glyph overlay renders only on fine pointers. While a row's card is open its rail carries the held treatment (band a shade up, brightened seam).
**Why**: The flyout's coarse open gesture needed a visible, learnable home (a 7px dot has no affordance), one PR channel per pointer world avoids double-painting two glyph renderings inside the rail's width — the rail slot IS the coarse home — and extending the ONE rail to every tier (instead of per-tier surfaces) reuses the one placement/containment/held-state implementation while making the strip continuous. The rail lives inside the existing row (no new surface, Constitution IV) and is static per-render content, adding no subscriptions.
**Rejected**: rail treatments with grip dots (read as drag-to-reorder) or an accent edge glow (green is a status hue — mixed signal on failing rows, no affordance on PR-less rows); keeping the overlay and hiding it under the rail band (dead DOM, z-index fights); a left-edge rail (the left edge belongs to the marker/label axis); per-tier coarse affordances instead of the one rail (three right-edge idioms in one tree).
*Introduced by*: 260816-b8eu-status-rail-card-actions; three-tier extension + 56px: 260817-ve5m-three-tier-status-rail-cards

### Keyboard selection-toggle key is `x`, not Space
**Decision**: The focused-row multi-select toggle in the sidebar tree is `x` (chorded `⌘X`/`Ctrl+X`/`Alt+X` explicitly passed through).
**Why**: `Enter` and `Space` are both already bound to row activation in the tree keydown switch, so repurposing Space would be a behavior regression for every existing keyboard user rather than an addition. `x` is unbound in the tree handler and is the well-precedented list-multiselect key (Gmail-style).
**Rejected**: Space — it already activates the row.
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### The `x` toggle is documented at the palette registration, not in `DEFAULT_BINDINGS`
**Decision**: `x` (with cmd/shift-click) is surfaced through `SELECTION_GESTURE_HINT` on the `Selection: Select all merged` entry's `shortcut` badge plus the count indicator's hint text, and is deliberately absent from `DEFAULT_BINDINGS`.
**Why**: The project review rule asks that a new shortcut be documented at the palette registration, and `PaletteAction.shortcut` is the seam the palette already renders as a `<kbd>`. `DEFAULT_BINDINGS` is a modifier-chord registry driving a window-level dispatcher (§ Keyboard Shortcuts) — registering a bare `x` there would hijack the key app-wide instead of inside the focused tree, which is a behavior change rather than documentation.
**Rejected**: A `DEFAULT_BINDINGS` entry (app-wide hijack of a bare letter); leaving the gesture undocumented (it appears on no chord map and in no shortcuts overlay, so nothing else would surface it).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### Selection state lives in a dedicated store, not sidebar-local state
**Decision**: A small dedicated zustand store (`store/selection-store.ts`) owns the window-row selection.
**Why**: The command palette is composed in `app.tsx` while the tree lives in `components/sidebar/index.tsx`; both must read and write the selection, and a shared store is the project's established seam for exactly that (`window-store.ts`).
**Rejected**: Sidebar-local `useState` plus prop threading — the palette is not a descendant of the sidebar, so it would mean lifting the state into `app.tsx` and threading a setter down through `Sidebar` → `ServerGroup` → `WindowRow`, churning the very memo contract those identity-arg props exist to protect (§ Render Performance).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### Escape-to-clear is a CAPTURE-phase handler on the tree
**Decision**: Escape-to-clear lives in a separate `onKeyDownCapture` on the `role="tree"` container, not as a case in the bubble-phase `handleTreeKeyDown`.
**Why**: Each window row spreads the row-flyout card's floating-ui `referenceProps`, whose `useDismiss` contributes an `onKeyDown` that `stopPropagation()`s Escape while the card is open — and the card OPENS on keyboard row focus (`useFocus`), which is exactly the state a keyboard user clearing a selection is in, so a bubble-phase handler never sees the key. Capture gives the tree first refusal. First refusal is not seizure: the handler consumes the event only when there is a selection to clear and only outside an editable target, so the rename input's Escape-cancels and the card's own Escape-dismiss both still work.
**Rejected**: Disabling the flyout's `escapeKey` dismiss, or setting `escapeKeyBubbles` — either degrades the card's own documented Escape-dismiss contract for an unrelated feature.
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### Selection liveness comes from a DATA key registry, parallel to the visible-row one
**Decision**: Each `ServerGroup` registers two independent things: its visible-row identity slice + signature (`registerGroupRows` → `rowsVersion`, gating roving-key normalization) and its DATA window-key set + signature (`registerGroupDataKeys` → `dataKeysVersion`, gating the selection prune), with `unregisterGroupRows` dropping both on unmount.
**Why**: The two consumers need different notions of "present". Roving navigation is inherently about rendered rows; selection is not — a window folded out of view is still a live tmux window the user meant to select, and `Select all merged` deliberately selects windows inside collapsed sessions. Keying the prune on visibility makes every collapse a silent selection wipe. Both signatures are strings over key sets, so neither counter bumps on the several-per-second passive SSE ticks — the "an SSE tick must not change tree state" invariant holds on both paths — and the data signature is sorted so a pure reorder does not bump it either.
**Rejected**: Reusing `rowsVersion` for both (it bumps on collapse/expand by design, because roving normalization needs it — any consumer riding it inherits that semantics); a `useEffect` watching `sessionsByServer` in the sidebar (re-runs every tick and reintroduces the whole-Map watcher churn the derive-over-store pattern removed); deriving live keys from the raw `sessionsByServer` prop at prune time (it lacks the optimistic ghost/rename overlays the groups actually paint, so it would disagree with the rendered tree).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### Bulk move is N sequential calls with continue-on-error, not a new bulk endpoint
**Decision**: The bulk action awaits one existing `move-to-session` POST per selected window in sequence and collects failures rather than aborting.
**Why**: tmux window moves mutate session state serially and the endpoint is already serial-safe, so reusing it adds zero backend surface (Constitution IV). Each window's move is independent, so aborting on the first error would strand the remaining windows for a likely-unrelated failure.
**Rejected**: A batch endpoint (new backend surface for no behavioral gain); parallel `Promise.all` (concurrent tmux session mutation, and a rejected promise loses the per-window outcome detail the aggregate toast reports).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### An async batch settles by RECONCILING against its own keys, not by clobbering the store
**Decision**: `executeBulkMove` ends with `settleBatch(batchKeys, retainKeys)` — a subtract-only store action that removes only the keys the batch owned and gave up, leaving every other key (and an anchor the user moved elsewhere) untouched.
**Why**: The palette closes before the batch runs and the batch is fire-and-forget, so a slow move races the user. `clear()` and `selectOnly()` act on whatever the store holds at settle time, so a selection the user started mid-batch is silently destroyed by an operation that had nothing to do with it. Scoping the write to the batch's own keys makes the outcome identical in the uncontended case and correct in the contended one. Subtract-only rather than re-adding the retained keys, so a user who deliberately cleared mid-batch does not have the failures resurrected over their intent.
**Rejected**: An in-flight flag refusing a second batch — it treats a legitimate concurrent action as an error and does not fix the actual race (the user's new SELECTION, not a second batch, is what gets clobbered); reconciling handles both and lets two disjoint batches settle independently.
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### The move builder owns the server-match guard
**Decision**: `buildSelectionMoveActions` takes the server its `sessions` argument belongs to as an explicit first parameter and returns `[]` on a mismatch against the selection's own `singleSelectedServer`.
**Why**: tmux window ids (`@N`) are unique per server only, so a caller handing over the wrong server's session list would silently produce plausible-looking targets keyed on colliding ids — which is exactly the shape of defect the parameter closes. Fixing only the call site would leave the builder willing to re-key ANY caller's sessions under the selection's server. A cheap equality guard makes the contract enforceable at the seam and directly unit-testable, at the cost of one extra argument at the single call site.
**Rejected**: Trusting `app.tsx` to feed the right list (the contract stays unenforceable, and the failure mode is silent wrong targets rather than an error).
*Introduced by*: 260807-nf9f-sidebar-multiselect-move-windows

### The destructive bulk action confirms INSIDE the palette, not in a dialog
**Decision**: `PaletteAction` carries an optional `confirmLabel`; `CommandPalette` turns a selection of such an action into a one-row confirmation sub-step (results replaced by the single `${id}-confirm` row, search input `readOnly`, Enter runs it once, Escape / backdrop / the toggle chord cancel), and bulk close is its only user.
**Why**: Closing N windows is irreversible and the `Selection:` family had no confirm affordance, but the palette is the family's sole action surface (Constitution IV + V) and already owns a two-step shape — the move entries' fuzzy-filter session picker. Keeping the second step inside the palette means the confirm is reachable with the same keystrokes that opened it, adds no component, and leaves the guard swappable later. Deriving the confirm row (rather than storing a second action list) makes recursion impossible: the derived row carries `confirmLabel: undefined`.
**Rejected**: A `<Dialog>` confirm (a new modal surface for one action, and it breaks the keyboard flow the palette establishes); no confirmation at all (the first destructive bulk action deserves one); a typed-name confirmation (disproportionate to a window close, whose contents survive in git/worktrees anyway).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### Close and send are cross-server; only move keeps its single-server gate
**Decision**: `buildSelectionCloseAction` and `buildSelectionSendPromptAction` gate on a non-empty selection alone, and their executors derive each request's server from the composite key via `splitSelectionKey`. Move keeps `singleSelectedServer` as its eligibility gate.
**Why**: Move's gate encodes a real tmux constraint — a window cannot move between tmux servers — not a family convention. Close and send are per-window requests that each carry their own `?server=`, so a cross-server selection is fully executable; refusing it would be a self-imposed restriction on exactly the cleanup case the feature exists for (merged windows scattered across servers under sessions scope `all`).
**Rejected**: Applying the single-server gate uniformly for consistency (it makes the family's most common selection ineligible for its most useful actions); splitting a cross-server batch into per-server sub-batches (the sequential per-key loop already handles it with no grouping).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### Broadcast recipients are FROZEN when the palette action is chosen
**Decision**: `Selection: Send prompt…` snapshots the selected composite keys into `selectionBroadcastKeys`; the compose target's label, draft key, requests, and `settleBatch` reconciliation all read that snapshot, not the live store.
**Why**: Composing a prompt takes seconds to minutes, and the tree stays interactive throughout — a live read would let the set the user confirmed in the palette (`Send prompt to 5 agents`) silently differ from the set that receives it. The snapshot keeps the visible `→ N selected` label honest end-to-end and keeps the batch's settle keys aligned with what it actually attempted. It is the deliberate exception to the strip's live-target rule (§ Live target), which exists to avoid sending to a stale pane — a frozen SET of windows has no equivalent staleness, since each request re-resolves its pane server-side.
**Rejected**: Reading the live selection at Send time (delivers to recipients the user never confirmed); disabling selection gestures while a broadcast is composing (freezes the tree for a surface the user may abandon).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### Selection broadcast is submit-only and takes the CHAT half of the Enter classifier
**Decision**: In selection mode the strip enables only its submitted-text path — insert-line, raw insert, and upload are unavailable — and classifies Enter with `surface: "chat"` rather than `"strip"`, so plain Enter inserts a local newline and Cmd/Ctrl+Enter is the sole submit.
**Why**: Both halves follow from the transport. The strip's terminal modes ride the focused pane's `wsRef` and uploads scope to that pane's worktree; a frozen cross-server recipient set has neither, so those affordances would target the wrong window or an invalid path. And the classifier's own stated reason for `insert-line` is VISIBILITY — the strip overlays the pane a staged line lands in — which is exactly what a broadcast lacks, making chat's newline-Enter the correct half (§ Enter transmits a line in the strip, composes in chat). The divergence stays inside the classifier's surface parameter; only the argument changes here.
**Rejected**: Keeping `surface: "strip"` and returning early on the non-submit actions (the keydown is already consumed at that point, so plain Enter becomes a dead key under an `enterKeyHint="send"` that promises otherwise); broadcasting raw bytes over the focused pane's socket (wrong window, and no socket at all for other servers).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### A broadcast clears its draft on DELIVERY, not on resolve
**Decision**: `ComposeSelectionTarget.onSend` resolves with the delivered recipient count; the strip pushes sent history and clears the draft only when that count is non-zero, and `app.tsx` likewise keeps the frozen target when it is zero.
**Why**: The executor absorbs every per-recipient failure into one aggregate toast and always resolves, so a resolve-means-sent rule would destroy the prompt at 0-of-N delivery — the exact case where the user needs the text most, and where the failed recipients are still selected as the retry affordance. A partial delivery clears like any other send: the text did reach agents, and `↑` recalls it from sent history. Keeping the count in the resolution (rather than rejecting on total failure) leaves one return channel for a spectrum of outcomes.
**Rejected**: Unconditional clear (matches the terminal modes but loses an undeliverable prompt); rejecting on zero delivery (turns an ordinary outcome into an exception the caller must distinguish from a real crash — the strip catches those separately and preserves the draft too).
*Introduced by*: 260808-ebgs-selection-bulk-close-send-prompt

### Collapse exceptions are a single map key, not per-session scalars
**Decision**: The per-session window-list collapse state persists as ONE localStorage key `runkit-session-collapsed` holding a JSON object of `true`-only exceptions keyed `` `${server}:${session}` ``, sitting beside (never replacing) the per-server section scalars `runkit-panel-sessions-{server}`. Expanding deletes the entry and an emptied map removes the key. Neither stale-entry pruning nor cross-tab sync is implemented.
**Why**: A keyed boolean set is the natural shape for a map — one key reads, parses, and rewrites atomically, and the whole surface stays enumerable for a future cleanup. Exceptions-only means the expanded default keeps applying to every session the user never touched, so the map never has to be reconciled against the live session set. The two omissions are priced deliberately: orphan entries are single booleans (the cost is that a recreated session reusing a collapsed name inherits the collapse), and the existing per-server persistence already sets the no-`storage`-listener precedent (the cost, sharper here than for the scalars, is that a whole-map write makes concurrent tabs last-write-wins across every server's exceptions).
**Rejected**: One key per session (`runkit-session-collapsed-{server}:{session}`) — sprawls unboundedly across killed sessions and cannot be enumerated for pruning; the per-server pattern gets away with scalars only because its value is a single boolean per server. Also rejected: storing `false` for an expanded session (turns the default into data that must be migrated if it ever changes), and pruning on load against the visible session set (the client has no session list for non-attached servers, so it would delete live entries).
*Introduced by*: 260807-kddk-persist-sidebar-session-collapse

### The collapse write is a ref-derived value committed outside the updater
**Decision**: `toggleSession` reads a `collapsedRef` synchronous mirror, computes `next`, advances the ref, writes localStorage, then commits `setCollapsed(next)` — a plain value, not a functional updater, with no side effect and no derivation inside one.
**Why**: React 19 StrictMode (active via `main.tsx` in dev and e2e) double-invokes state updaters, so a `localStorage.setItem` inside one runs twice and the second pass observes the first pass's write, making a single click a net no-op — the same failure `toggleServerSection` documents. The ref covers the second hazard a plain snapshot does not: back-to-back toggles batched into one render would both read the same stale closure-captured `collapsed`, persisting a map that disagrees with committed state.
**Rejected**: A `useEffect` keyed on `collapsed` — inherently StrictMode-safe, but it re-serializes the hydrated map on every mount, silently rewrites a malformed stored value, and moves the write off the user action that caused it.
*Introduced by*: 260807-kddk-persist-sidebar-session-collapse

### Operator marking is placement-only — move, don't copy, no new chrome
**Decision**: `@rk_role=operator`'s entire UI treatment is the placement of its row — the ordinary `WindowRow` pinned at the top of the server's session area (below the SESSIONS header), moved out of its home session group (rendered exactly once), with no badge, frame, micro-label, divider, or accent, and no empty-state placeholder when nothing is marked.
**Why**: The operator window needs findability (it is the control plane for a server's worker windows), not ornamentation; the user explicitly declined every chrome variant, and an unchanged sidebar in the unmarked state keeps the feature invisible until used. Move-don't-copy keeps each window's row count and group membership truthful.
**Rejected**: Framed slot / badge / divider / left-edge accent mockups (explicit user rejection); rendering the row in both positions (a copy lies about session membership and row counts); a flyout action row as the manual marking path (dropped with the chrome — the palette pair is the keyboard-first fallback).
*Introduced by*: 260813-ifya-operator-role-pinned-row

### Scroll-edge fade is a conditional mask, not a permanent veil
**Decision**: The sidebar scroll-edge fade is a shared hook (`useScrollEdgeFade` — scrollable-and-not-at-end detection) plus a `mask-image` utility class (`rk-scroll-fade-bottom`) applied conditionally to the two clipping viewports (sessions tree, SERVER panel resizable area).
**Why**: Rows/tiles carry per-item color tints; a mask fades whatever is there. Rendering only while more content exists below preserves the "reads as more below" semantic — a permanent veil would dim the final row of a short or fully-scrolled list.
**Rejected**: Row-quantized viewport heights; opaque background-colored overlay (mismatches tinted content).

### Server-group color is a header-bar surface only

**Why**: The left gutter belongs to the window-marker vocabulary (§ Left-Edge Label Zone, `markerStripeStyle`) and must stay untouched.
**Rejected**: A full-height group stripe (claims the left gutter the marker axis owns).

### Dashed data rain is always-on, not selection-gated
**Decision**: `.rk-dash-rain` mounts on `isDashed` alone — a dashed-marked window row streams its two dash tracks in every state, not only while selected. The gutter stripe itself stays static in every state.
**Why**: "working" is inherently live, and the thinned two-lane rain is quiet enough to run ambiently (a deliberate user call).
**Rejected**: Gating the rain on row selection.

### Flair is an independent per-row channel, orthogonal to color and marker
**Decision**: Row character animations live on a dedicated flair channel (the `@rk_flair` window option and scope-split `@rk_session_flair` session option) with at most one value per row — never as new marker states. Server group headers carry no flair: they mirror the SERVER-pane tiles, whose visual identity must stay flair-free.
**Why**: Markers are a semantic border-style vocabulary with a picker-grid invariant (`GRID_ROWS === MARKER_CELLS.length`) and exist on window rows only; flair must reach session rows and compose freely with color + marker. User-confirmed in the change's clarification session.
**Rejected**: New marker states — would break the 6-cell picker-grid invariant and force markers onto row types that don't have them.

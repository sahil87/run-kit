# run-kit UI — Operator Console

**Domain**: run-kit/ui

## Overview

The operator chat console is the talk-to-the-operator surface: a global overlay that slides down from under the top bar on every route (Host, tmux Server, Terminal, Board) carrying a live embedded view of the server operator's window, so a message is written and its reply read without leaving the current route. On desktop the INPUT lives in the top bar — the operator omnibox (`components/operator-omnibox.tsx`) is the console's compose relocated into the bar's center cell, and the drawer is output-only (the one-input rule), driving ONE shared compose seam. On mobile the console has no surface of its own: every open request resolves the operator window and NAVIGATES to its ordinary terminal route, whose own chrome — the top-bar heading, the compose strip, the bottom-bar key chips, the `--bottom-bar-pad` safe-area handling — IS the mobile console. It is frontend-only — no new backend route, no transcript read path: delivery forks between the templated chat lane (the window-scoped operator-request `user-message` template, carrying a server-derived context envelope naming what the user was looking at) and the existing `POST /api/windows/{id}/send` agent-target lane, and reading rides the existing `/ws/terminals` relay mux. The desktop drawer also carries a `Terminal | Activity` segment header — Activity swaps the embedded terminal for the cron Activity feed ([cron-activity](/run-kit/ui/cron-activity.md)) — and its title strip carries the operator loop's tick-age stamp. The implementation is `app/frontend/src/components/operator-console.tsx` (the overlay plus the mobile tongue), `app/frontend/src/components/operator-omnibox.tsx` (the desktop input), `app/frontend/src/components/operator-context-chip.tsx` (the chat-lane chip the compose surfaces mount), and pure helpers, per-viewer stores, the ⌘J two-state machine, the shared compose seam, and the chat-subject store in `app/frontend/src/lib/operator-console.ts` (colocated tests throughout).

## Requirements

### Requirement: Root-layout mount; overlay, not a route
The console SHALL mount exactly once at the persistent root layout in `app/frontend/src/app.tsx` (lazy-imported beside the single `CommandPalette` mount), as an `absolute` overlay inside the main area (the `relative flex-1 min-h-0` region under the top bar), so pages below keep their layout. On desktop, opening/closing never navigates and never writes URL or tmux state — open/closed is ephemeral per-viewer component state (Constitution IV; the geometry/opacity localStorage stores below are the carve-out preferences), so a reload always starts closed; on mobile a console request IS navigation (the mobile-navigation requirement below) — open/closed has no mobile form, though the component still mounts there (the seam listener lives in it) while rendering nothing. On desktop the drawer's rendered flag FOLLOWS the ⌘J two-state machine (below): entering `open` runs the enter slide, and entering `rest` runs the exit slide. Esc releases the machine to `rest` via a bubble-phase document keydown listener that honors `defaultPrevented` (a nested modal's Escape wins — the console is a non-modal drawer, not a focus trap) and stands down when a nested `role="dialog"` renders inside the drawer root (the inline cron entry-detail panel owns that Escape — the segments requirement below). Every collapse path (Esc, the chord, the header collapse button, and an outside click while `open` — the outside-click requirement below) funnels through the exit slide below — the unmount, which closes the terminal stream, fires only after the slide completes. Focus ownership on desktop is the omnibox's machine-follower effect (entering `open` from `rest` focuses the omnibox with any draft selected; returning to `rest` blurs it and restores the previously focused element — under the two invariants the machine requirement below states: an origin inside the box is never recorded, and the restore runs only while the box still owns focus). (02jx)

### Requirement: True quake slide, mounted through exit (desktop drawer)
The desktop drawer SHALL slide in both directions: it mounts raised fully above the top-bar seam (the `.rk-console-closed` class on `.rk-console-slide` — `transform: translateY(-102%)`, transform-only so the motion composes with the centering `translate` property — with the raised portion hidden by a dedicated `pointer-events-none absolute inset-0 overflow-clip` wrapper around the console only, not the shared main area) and transitions to rest over 240ms (`cubic-bezier(0.2, 0.9, 0.25, 1)` in `globals.css`), the raised class dropping two animation frames after mount so the transition animates. A close request drives an internal `closing` state that re-applies the raised class and holds the unmount until the root's `transform` `transitionend` fires (with a slide-duration-plus-margin timeout fallback), so the terminal stream tears down AFTER the slide, not mid-animation; a re-open mid-exit cancels the close and the drawer transitions back down from wherever the slide had reached. `prefers-reduced-motion` zeroes the transition in CSS AND skips the mounted-through-exit delay in JS (immediate unmount).

#### Scenario: Toggle from any route
- **GIVEN** a closed console on desktop
- **WHEN** the chord fires
- **THEN** the drawer slides down from fully above the top-bar seam in ~240ms
- **AND WHEN** Esc is pressed, **THEN** it slides back up and unmounts only after the transition ends
- **AND GIVEN** reduced motion, **THEN** open/close are instant

### Requirement: One document-event seam for every entry point
All quick-terminal entry points SHALL reach the layout-mounted console by dispatching the `rk:operator-console` document CustomEvent (`OPERATOR_CONSOLE_EVENT`) via `requestOperatorConsole(req)` in `lib/operator-console.ts` — never by prop threading or direct state access, because the entry points live in route shells the layout does not compose directly (the `palette:open` / `HOST_MENU_OPEN_EVENT` seam idiom). The request shape is `{ action: "toggle" | "open", server?, send?, segment? }`: on DESKTOP, `toggle` steps the ⌘J machine between `rest` and `open`, while `open` lands at `open`; entering `open` focuses the omnibox through its machine-follower effect. On MOBILE both actions collapse into one navigation (the mobile-navigation requirement below). `send` carries the palette Ask-operator fallback row's query — delivered immediately once open on desktop (dropped unsent when the resolved server has no operator window, the hint line being the answer there), seeded into the operator route's compose-strip draft on mobile. An optional `segment?: "terminal" | "activity"` selects the drawer's body segment on open: the desktop listener applies it to the segment state after the machine transition (a `segment: "activity"` request also bypasses the operator-route no-op gate — the operator-route-gate requirement below), while the mobile arm maps `activity` to the operator route's `?tab=activity` search param (merged with the `?from=` origin carrier on a cross-route navigation, an in-place `replace` search update when already on the route); requests without `segment` see no behavior change. The event-seam entry points are the registry chord (⌘J/⇧Ctrl+J — [keyboard-and-palette](/run-kit/ui/keyboard-and-palette.md)), the palette actions `Operator: Open console` and `Operator: Show clock activity` (the latter always carrying `segment: "activity"`), the palette's Ask-operator fallback row, the status-bar `◷` clock chip ([status-signals](/run-kit/ui/status-signals.md) § Status Bar), the desktop `?tab=activity` deep-link handoff (the mobile-navigation requirement below), the mobile tongue (the affordance-pair requirement below), and the top-bar overflow-menu row ([top-bar](/run-kit/ui/top-bar.md)). The sidebar pinned operator row is ordinary `onSelectWindow` navigation ([sidebar](/run-kit/ui/sidebar.md) § Operator Pinned Row), outside this event seam. The omnibox itself is also not an event-seam entry point — it drives the shared compose seam and the machine slot directly. (02jx)

### Requirement: Desktop openers are inert on the resolved operator route
The desktop `onRequest` listener in `components/operator-console.tsx` SHALL treat every valid `toggle` and `open` request as a no-op while the current route is the resolved operator window's own terminal route. The component derives that fact once as `onOperatorRoute` from the route server/window and its resolved console server/target, mirrors it into `onOperatorRouteRef` for the once-registered listener, and checks the ref immediately after the mobile early return. A matching desktop request returns before reading or changing the machine and before mutating `pinnedServer` or `pendingSend`. The chord, overflow-menu row, palette action, and palette Ask-operator fallback remain visible and actionable; activation shows the informational toast `already viewing the operator — nothing to open`, throttled by `alreadyOnOperatorHintAtRef` and `NO_OPERATOR_HINT_THROTTLE_MS` to at most once per four-second toast lifetime. Requests on every other desktop route retain their action, server-pin, and pending-send semantics. The one bypass: a request carrying `segment: "activity"` skips the gate entirely — the Activity view is not visible on the desktop route itself, so the drawer must open to show it. Mobile is unaffected: its listener branch runs first, navigation remains idempotent on the target route, and the tongue renders its return state there. (02jx)

#### Scenario: Activate a quick-terminal opener on the operator route
- **GIVEN** desktop is showing the resolved operator window's terminal route
- **WHEN** the chord, overflow-menu row, palette action, or palette fallback dispatches a console request
- **THEN** the machine, `pinnedServer`, and `pendingSend` remain unchanged
- **AND** one informational toast is shown during each four-second throttle window
- **AND GIVEN** the same request on another desktop route, **THEN** its ordinary open/toggle and payload behavior applies

### Requirement: The ⌘J two-state machine (desktop)
The desktop console SHALL use the `ConsoleMachineState = "rest" | "open"` module slot in `lib/operator-console.ts` (`getConsoleMachineState` / `setConsoleMachineState` / `useConsoleMachineState`). The omnibox (top bar) and drawer (root-layout overlay) mount in different trees and share this state owner. `cycleConsoleMachine` implements the complete chord table: `rest → open` and `open → rest`. In `rest` the drawer is closed and the omnibox is outside the machine engagement; entering `open` drops the drawer and the omnibox's follower effect focuses and selects its draft. The drawer remains open if focus moves into its terminal; focus movement alone does not change the machine.

**Focus return obeys two invariants**, both of which make the omnibox incapable of overriding a genuine user focus choice ([focus-ownership](/run-kit/ui/focus-ownership.md) § The Operator Console's Own Focus Return). (a) **Origin capture excludes the box**: entering `open` records `document.activeElement` as the restore origin ONLY when it lies outside the omnibox wrapper (`boxRef`), else `null` — a mouse entry focuses the input BEFORE `onFocus` transitions the machine, so an unguarded capture names the box's own input. (b) **The return is ownership-gated**: on reaching `rest` the effect takes no focus action at all unless the omnibox input is still `document.activeElement` — the release either came from the box giving focus up (Esc, the chord, the header collapse button), or from the user focusing something else, and the second case already has its owner. Together they mean a click into an xterm pane leaves focus in the terminal and the keystrokes reach the tmux pane; without them the two rules compose into a self-sustaining loop (the restore re-focuses the box, whose `onFocus` re-enters the machine) that no input, not even Esc, can escape. (260906-f4s6) The machine is the drawer's controlling state — entering `open` runs the enter slide, and entering `rest` runs the exit. Enter with a non-empty draft sends through the compose seam and sets `open`. Esc releases `open` directly to `rest`, owned by the console's document listener so a single Esc never double-handles. The header collapse button (`▼`, `aria-label="Collapse operator console"`) maps to `rest`. **A click outside the console's own DOM while `open` also maps to `rest`** — a capture-phase `document` `click` listener gated on `isOperatorConsoleTarget(e.target)` (the same containment check the file-paste forward uses, § Console file paste/drop below), attached only while `machine === "open"`. The listener does not act inline: it snapshots `getConsoleMachineActivity()` (a counter bumped on every `setConsoleMachineState` call, including a same-value no-op) at capture time, then defers the actual collapse to a `setTimeout(…, 0)` settle check that (a) bails if the activity counter moved because a click-driven event-seam entry point already claimed the interaction and (b) bails if any `role="dialog"` OTHER than the console's own drawer is open at settle time (the settings dialog, the command palette) — a modal owns the interaction while open, so the console holding still behind it is correct regardless of where inside (or outside) the dialog the click landed; this is also what lets the settings dialog's opacity control live-apply to a console that stays open beneath it. The settle deferral is a macrotask, not a microtask: a microtask can run before React commits the same click's own state update (mounting the settings dialog, or re-rendering after a trigger's own state change), which the settle check depends on having already happened. Mobile has no machine: no omnibox exists there and console requests navigate instead of opening anything (the mobile-navigation requirement below). (02jx)

#### Scenario: Chord toggle and Escape release
- **GIVEN** rest on desktop
- **WHEN** ⌘J fires once
- **THEN** the machine enters `open`, the drawer opens, and the omnibox receives focus without sending
- **AND WHEN** ⌘J fires again, **THEN** the machine returns to `rest`
- **AND WHEN** Esc fires at `open`, **THEN** one key press returns directly to `rest`

#### Scenario: Click outside collapses the open drawer
- **GIVEN** the console `open` on desktop
- **WHEN** a click lands outside the drawer and the omnibox
- **THEN** the machine transitions to `rest` and the drawer unmounts through the exit slide
- **AND GIVEN** a click inside the drawer or the omnibox, **THEN** nothing collapses
- **AND GIVEN** a click-driven event-seam entry point outside the console's own DOM, **THEN** that trigger's machine decision wins over the outside-collapse
- **AND GIVEN** a click that opens the settings dialog (or any other `role="dialog"` overlay), **THEN** the console stays open — a modal owns the interaction while it's up

### Requirement: The omnibox — the console's compose relocated into the top bar (desktop)
On desktop the console's ONLY input and standing pointer affordance SHALL be the operator omnibox (`components/operator-omnibox.tsx`) in the top bar's center cell ([top-bar](/run-kit/ui/top-bar.md) § Chrome (Top Bar) center cell), rendered on every route and resolving its server exactly as the console does (`resolveOperatorConsoleTarget` with an ephemeral last-viewed ref, the route server arriving as a prop; tolerant of a missing `SessionProvider` — degrades to "no operator"). One component has two visible rungs: at ≥ `lg` a STANDING bordered input (`◉` glyph, the effective chord keycap; slim at rest — `w-[12ch]` with the short "Ask…" placeholder (the standing `◉` glyph names the operator; the placeholder does not repeat it), widening to `2xl:w-[20ch]` with the full "Ask the operator…" placeholder only at ≥ `2xl` — the placeholder gate is width-only, never the engaged state — so the standing box never eats the crumbs' min-useful-width at `lg`/`xl`; `max-w-[40vw]` throughout) beside the compact heading; at md–lg a dim `· ◉ ask` ghost whose click (or the chord engaging the machine) MORPHS the center into the same box in place, while Esc or the next chord restores the heading; below `md` the ghost stays hidden (the 640px no-overlap budget) but the chord/palette still morph the box; on mobile the component renders null. The ◉ glyph carries the resolved operator's live-state dot in BOTH visible rungs, positioned at bottom-right with a background-colored cutout ring: `active` is green, `waiting` is amber, every other resolved state is grey, and no operator means no dot. `OPERATOR_STATE_DOT` in `lib/operator-console.ts` owns the mapped state colors. Clicking into the standing box engages the machine at `open`; Enter with a non-empty draft sends and keeps `open` with focus retained for follow-ups. (02jx)

The box renders from TWO derived flags, deliberately not one. **`morphed`** (`machine !== "rest"` — the same value the top bar computes as `omniboxMorphed` to hide its heading, [top-bar](/run-kit/ui/top-bar.md) § Chrome (Top Bar) center cell) says the box is RENDERED in place of the heading and gates the ghost. **`engaged`** (`morphed && (boxFocused || !wide)`) says the box LOOKS like it owns input, and gates the accent border, the `w-[34ch]` compose width, and the `OperatorContextChip` mount. They diverge at `open`, where a blur deliberately does not release the machine (the drawer is a peek that outlives the box's focus) — a machine-derived chrome would claim focus the box no longer has while the user types in a terminal. The `!wide` term is the md–lg morph-hold carve-out: below `lg` the box stands where the heading was and a live draft holds it there after a blur, so standing the chrome down would read as discarding an unsent message. `boxFocused` tracks the input's real focus/blur, and a blur whose `relatedTarget` lies within the wrapper does NOT clear it — the same carve-out that keeps the machine engaged there, for the same reason: the context chip must survive long enough for its ✕ click to land. (260906-f4s6)

The omnibox wrapper carries the console-root attribute (`data-operator-console`) so the route terminals' document-level file-paste forward skips omnibox-origin pastes, and the box owns its own file path — pasting an image uploads to the operator window's session and insert-stages the returned path (the file-paste requirement below). Escape is deliberately NOT handled in the component (the console's document listener owns the release to `rest`).

#### Scenario: Enter from the standing omnibox
- **GIVEN** a ≥ lg viewport with the omnibox standing
- **WHEN** text is typed and Enter pressed
- **THEN** exactly one agent-target send fires at the operator window, the draft clears, the drawer slides open, and focus stays in the omnibox

### Requirement: Anatomy — title strip, segment header, status line, body
The console SHALL render, top to bottom: (a) a title strip with `◉ OPERATOR`, the resolved server name (or a server picker when the route carries no server param and more than one server exists), the operator window's live agent state from the sessions payload (`agentState` + idle duration), the operator loop's tick-age stamp, and a collapse affordance; (b) the `Terminal | Activity` segment header (the segments requirement below); (c) the status line at the drawer's top edge, directly under the omnibox: the inline send/upload error (`role="alert"`) or the minimal sending…/uploading… indicator, rendered only while one is live; (d) the body — on Terminal an embedded live terminal (the drawer is output-only: the compose IS the top-bar omnibox, the one-input rule), on Activity the cron feed. The **tick-age stamp** (`data-testid="operator-console-tick"`) appends `· tick {formatDuration age} ago` after the agent-state span, read render-time-only (no ticking timer — the feed's SSE-cadence contract) from the FIRST session on the resolved server carrying `operatorLastTickAt > 0`; when that session's `operatorStale` is true the stamp renders `⚠`-prefixed in `text-signal-yellow` with a `Tip` reading `Operator last ticked {age} ago`, and when no session carries the field nothing renders. Desktop geometry is a centered drawer sized from the persisted per-viewer geometry (defaults 55vh × 760px — the resize requirement below), with the body filling the remaining space and a glass background (the glass requirement below). The console's collapse button renders `▼` (matching `CollapsiblePanel`'s collapse-indicator glyph, not a destructive close glyph — the button only hides the drawer, it never terminates the underlying operator session) and carries the compose strip's button idiom: `coarse:` ≥36px touch targets and the `rk-glint` hover treatment.

#### Scenario: Open console on an operator-bearing server
- **GIVEN** an open console on a server with an operator window
- **WHEN** it renders
- **THEN** the title strip shows the server and live operator state and the terminal shows the operator window's live frame — input focus living in the omnibox (the machine)

### Requirement: Desktop Terminal | Activity segments
The desktop drawer SHALL render a two-segment header (Terminal, Activity) between the title strip and the status line — the shared presentational `ConsoleSegments` strip from `components/terminal-activity-tabs.tsx` (a controlled `{ value, onChange }` component carrying the `role="tablist"`/`role="tab"`/`aria-selected` markup, the `controlClass({ variant: "segment" })` classes, and the `terminal-activity-tabs` test id), the same render the mobile operator route's `TerminalActivityTabs` drives through the router `tab` search param. The selected segment is console-local ephemeral component state (`useState`, default `terminal`, written to no URL, tmux, or localStorage — the drawer's open/closed posture, Constitution IV), reset to `terminal` on every close path (`finishClose`), and set on open when a seam request carries `segment`. On Activity the body mounts `<CronActivityFeed server={server} inline />` ([cron-activity](/run-kit/ui/cron-activity.md) — the `inline` variant makes the entry-detail sheet render in-container) and the `TerminalClient` is UNMOUNTED — the drawer holds at most one relay stream (the keyed remount on switching back is cheap); an unresolved server renders the feed's own hint line. Esc inside the inline entry-detail panel returns to the feed only, never collapses the drawer: the panel's focus trap claims the key with `preventDefault` and the drawer's document Esc listener additionally stands down via a DOM check for a nested `[role="dialog"]` inside the drawer root (registered at open, it runs before the nested layer's trap).

#### Scenario: Switch segments
- **GIVEN** the open drawer on the Terminal segment with the embedded terminal mounted
- **WHEN** the user selects Activity
- **THEN** the cron feed renders and the embedded terminal is unmounted
- **AND WHEN** the drawer is closed and re-opened by a plain toggle/open request, **THEN** the Terminal segment is selected
- **AND GIVEN** an open request carrying `segment: "activity"`, **THEN** the drawer opens on the Activity segment

### Requirement: Embedded terminal over the shared relay mux
The embedded terminal MUST be the existing `TerminalClient` (`components/terminal-client.tsx`) over the shared `/ws/terminals` `RelayMux` — the same mechanism a board pane uses to render a cross-server window — pointed at the operator window's `(server, windowId)` with `registerFocus={false}` so the BottomBar keeps its own focus target (the BoardPane precedent). No new backend endpoint, no transcript read path, no new WS subscription kind. The stream opens at the console viewport's cols/rows under the existing multi-client attach semantics (identical to a second browser tab on the same window) and closes on console unmount; the mount is keyed `${server}:${windowId}` so a server switch re-attaches cleanly. The console instance sets `transparent` — TerminalClient's opt-in per-instance prop (xterm `allowTransparency` + a transparent theme background) — so the drawer's glass shows through the cells; route and board terminals never set it and keep the opaque theme background with no renderer cost.

### Requirement: One shared compose seam — the send forks between templated chat and direct
ONE compose implementation SHALL drive the console's input — the desktop omnibox: the shared compose seam in `lib/operator-console.ts` (`useOperatorCompose` + `setOperatorComposeText` + `sendOperatorMessage` + `attachOperatorFiles`), whose draft, in-flight flags, and inline error are MODULE state (the module-store idiom) so the send/upload logic exists exactly once. Message delivery fires on Enter and FORKS inside `sendOperatorMessage` on the chat-subject store, read AT SEND TIME (never a captured closure — a pendingSend delivered in the same commit as a chip reset must see the reset): with a subject attached for the resolved server, the message rides the templated lane — `sendOperatorRequest(server, subjectWindowId, "user-message", text)` (`api/client.ts` — the `withServer` + `throwOnError` + `OperatorRequestResult` shape, `text` carried in the body only when non-empty) posting `{template: "user-message", text}` to the window-scoped operator-request route AT THE SUBJECT window id (a different window id than the direct lane's operator-window target), where the server composes a source envelope from the subject's facts ([operator-actuation](/run-kit/operator-actuation.md) § the `chatDelivery` chat lane); otherwise — chip dismissed, or no subject — the direct lane `sendToWindow(server, operatorWindowId, text, "submit", "agent")` byte-identically: the agent-target lane that resolves the operator window's agent pane server-side and runs the full injection engine (sanitize → paste → novelty probe → probe-gated Enter → observation/recovery; [agent-send](/run-kit/agent-send.md) § Send Path). The console STAMPS the subject: its route walk reads the `window` param, and the subject is set only when the console's resolved server IS the route's server (window ids are server-scoped — a pinned/picked cross-server retarget attaches nothing); on the operator window's OWN route the subject is instead the validated `?from=` origin window (the mobile navigation's context carrier — an unknown, cross-server, or self id attaches nothing: a subject must never be the send's own target). The palette Ask-operator fallback's desktop `pendingSend` flows through the same `sendOperatorMessage`, so it rides the same fork. On mobile the operator input is the terminal route's OWN compose strip — not the shared seam — whose PLAIN text submit keys on the same chat-subject store: when the stamped subject is a DIFFERENT window than the strip's target (the `?from=` case on the operator window's route), the submit rides the templated lane; chip dismissed or no/invalid subject ⇒ the strip's ordinary `sendToWindow` path. Special-key and mode-carrying sends (bottom-bar keys, enter, raw) ALWAYS go direct to the pane — driving the TUI is the point of the route. BOTH lanes are chat-send allow + probe: no client-side busy gate, no `operatorQueueTracker` interaction — the templated lane declares `chatDelivery`, so a console send can never resolve `202 queued` and no queued-outcome handling exists on this path. A whitespace-only or in-flight send is a guarded no-op. The console is a HUMAN surface driving a pane through the one gated injection engine — distinct from the agent-messaging spec's Conversation row (multi-turn cross-provider agent dialogue ⇒ MCP bridge), which governs agent-to-agent tool-mediated dialogue, not humans.

#### Scenario: Enter forks on subject + chip
- **GIVEN** a terminal route (`/$server/$window`) with the chip attached and text in the compose input (the omnibox, or the operator route's compose strip under `?from=`)
- **WHEN** Enter is pressed
- **THEN** exactly one POST to `/api/windows/{routeWindowId}/operator-request` fires with `{template: "user-message", text}` and no `sendToWindow` call is made
- **AND GIVEN** the chip dismissed OR a board/host/server route (no subject), **THEN** the send is exactly `sendToWindow(server, operatorWindowId, text, "submit", "agent")`, and a busy operator still receives the attempt on either lane (the probe remains the fail-closed floor)

### Requirement: Context chip — visible, dismissable, default on, ephemeral
When a subject window resolves, the active compose surface SHALL show the attached context as a chip (`components/operator-context-chip.tsx`) naming the source (subject `@N` and window name, e.g. `from: @5 "zesty-fjord"`) with a ✕ dismiss affordance floored at a 24px fine / 40px coarse hit area (`min-w-[24px] min-h-[24px] coarse:min-w-[40px] coarse:min-h-[40px]`) — the IDE-chat attach pattern (Cursor/Copilot attach the active file the same way): implicit context the user cannot see erodes trust in what the operator was told. The desktop omnibox renders it while the machine is engaged (composing — the resting box stays slim); the operator terminal route's compose strip renders it when a `?from=` subject is attached — a subject on a DIFFERENT window than the strip's own target (on an ordinary terminal route the stamped subject IS the route window, the omnibox's chip, and the strip must not reroute its own send). At the operator-route compose-strip mount the chip's LABEL is itself a control — the component's opt-in `onNavigate` prop, passed only there — whose tap navigates back to the subject window's terminal route (the chip names exactly where the user came from, so it doubles as the secondary return affordance beside the tongue's return state); the omnibox mount passes nothing and keeps an inert label. The ✕ stays dismiss-only on both mounts. The chip defaults to ATTACHED whenever a subject resolves; dismissing it drops the envelope for subsequent sends (the direct lane) until it resets. Chip state lives in the chat-subject store beside the compose seam (module state so the surfaces stay in lockstep — Constitution IV ephemeral: no URL/tmux/localStorage write) and resets to attached when the console re-engages (the desktop machine leaves rest) or the subject identity changes (the store resets dismissal on a subject change itself — which is what re-attaches the chip on mobile route arrivals). On routes with no subject, no chip renders.

#### Scenario: Chip lifecycle
- **GIVEN** the chip dismissed on a terminal route
- **WHEN** the console is closed and re-opened (or the route's window changes)
- **THEN** the chip is attached again
- **AND GIVEN** a board route, **THEN** no chip renders and sends are direct

### Requirement: Send errors surface inline, text preserved
Structured send failures (probe failure, `staged_send_failure`, submit-unverified — the thrown `ApiError` messages from either lane's `throwOnError` shape) SHALL render as an inline status line (`role="alert"`), never as toasts — the user is looking at this surface. The line sits at the drawer's top edge, directly under the omnibox (the compose relocated); a send from the operator route's compose strip rides that strip's own error surface. The draft survives a failure in the shared compose state for retry/edit; the line clears on the next successful send or on any edit (`setOperatorComposeText`).

#### Scenario: A structured 409 surfaces inline
- **GIVEN** a send that fails with a structured 409
- **WHEN** the error resolves
- **THEN** the server's message renders inline in the console and the draft still holds the text

### Requirement: Mouse resize with per-viewer geometry persistence (desktop drawer)
The desktop drawer SHALL be mouse-resizable. The bottom tongue-grip (a 64×12px pull tab hanging from the drawer's bottom edge, `cursor-ns-resize`) drags HEIGHT, clamped 25–85% of the viewport height; side grips on both edges (`cursor-ew-resize`) drag WIDTH symmetrically about the center line — an edge delta moves both sides (the width changes by twice the pointer delta, sign flipped on the left grip), clamped 420px–96vw, so the drawer stays centered. Grips use pointer capture and suspend the slide transition during a drag (the `.rk-console-dragging` class — no animated fighting); the live drag drives an in-component override and the store write lands on pointer-up. Geometry persists per-viewer in one localStorage JSON key `runkit-operator-console-geometry` (`{heightVh, widthPx}`) via the geometry store in `lib/operator-console.ts` (the `use-local-storage-enum.ts` pub/sub idiom: same-tab subscriber notify plus the cross-tab `storage` event, with numeric clamping in place of the enum hook's allowed-list validation), read on mount with try/catch and defaults (55vh / 760px) on absent, corrupt, or out-of-clamp values — no tmux, URL, or server state (Constitution IV). The width ceiling rides a `maxWidth: 96vw` style so it keeps tracking live viewport resizes.

#### Scenario: Resize persists across reload
- **GIVEN** a viewer who resized the drawer to 70vh × 900px
- **WHEN** the page reloads and the console reopens
- **THEN** it opens at 70vh × 900px
- **AND GIVEN** a corrupted stored value, **THEN** the defaults apply without error

### Requirement: Affordance pair — omnibox (desktop) / tongue (mobile)
Two pointer affordances SHALL stand beside the chord/palette entry points — exactly one standing affordance per form factor, both gating on the shared narrow-width-OR-coarse-pointer `useIsMobile()` rule so they never overlap or gap. On DESKTOP the standing affordance is the top-bar operator omnibox ([top-bar](/run-kit/ui/top-bar.md) § Chrome (Top Bar) center cell), expressed as the ≥lg standing box or the md–lg ghost and carrying the live-state dot on its ◉ glyph; no tongue renders at rest. On MOBILE the tongue (`OperatorConsoleTongue`, mounted beside the console in the root layout) is the STANDING affordance: a centered pull tab always visible under the top bar on every route — a 64×12px visual tab whose button box is the ≥36px coarse hit area — whose tap dispatches `toggle` through the same document seam (navigation on mobile — the mobile-navigation requirement below), carrying an amber dot when the resolved server's operator is `waiting`; it hides when no operator window resolves on the resolved server (omitted, not disabled — the availability requirement). The tongue is a TOGGLE: while the current route IS the resolved operator window's terminal route (server AND window id both compared — window ids are server-scoped) it renders in a RETURN state (`data-tongue-state="return"` vs `"operator"`, a small ⌃ mark in the tab, the waiting dot suppressed — the user is already looking at the operator) whose tap navigates BACK with priority: the validated `?from=` origin window (the shared `resolveFromOrigin` in `lib/operator-console.ts` — the same validation class the chat-subject stamping applies, so an unknown, cross-server, or self id falls through), else `router.history.back()` when `window.history.length > 1` (a cold deep-link has no back entry — a dead tap is worse than the fallback), else the server route `/$server`. No bottom-bar chip exists anywhere (the 375px single-row budget is untouched and the bottom bar is tty-route-only); the overflow-menu row stays as the labeled backup on every route. On desktop the tongue exists only attached to the drawer's bottom edge while the console is OPEN, where it IS the height drag grip (it slides with the drawer). Both affordances read the console's resolved server + operator window through the shared `useOperatorConsoleContext()` in `lib/operator-console.ts` (the console's own server rule plus `findOperatorWindow`, with last-viewed tracked ephemerally per consumer), tolerant of a missing `SessionProvider` — chrome degrades to "no operator", never crashes. (02jx)

#### Scenario: Mobile tongue toggles
- **GIVEN** a mobile viewport on a route that is not the operator window's route, with an operator present
- **WHEN** any route renders
- **THEN** the tongue is visible under the top bar and a tap navigates to the operator window's terminal route
- **AND GIVEN** the operator route itself, **THEN** the tongue renders the return state (dot suppressed) and a tap returns to the `?from=` origin window (else history back, else the server route)
- **AND GIVEN** desktop at rest, **THEN** no tongue renders (the omnibox is the standing affordance)

### Requirement: Glass background with a per-viewer opacity setting (desktop drawer)
The desktop drawer's background SHALL be glass: `color-mix(in srgb, var(--color-bg-primary) {α}%, transparent)` over a FIXED `backdrop-filter: blur(6px)` (+ the `-webkit-` prefix; the bottom tongue-grip shares the same background). α is a per-viewer preference stored in localStorage (`runkit-operator-console-opacity`, the same pub/sub store idiom as the geometry store), default 0.90, clamped 0.5–1.0, applied live to an open console via the store's same-tab notify; α = 1.0 disables the backdrop-filter entirely (the zero-cost opaque path). Blur is a constant — not configurable. The settings dialog surfaces α as a This-device row ([dialogs-and-state](/run-kit/ui/dialogs-and-state.md) § Settings Dialog) — a client-side resident of the one settings surface, NOT an `internal/settings` registry key.

#### Scenario: Glass over busy output
- **GIVEN** default settings
- **WHEN** the drawer opens over busy terminal output
- **THEN** the background shows through at α 0.90 with 6px blur and the xterm cells are transparent
- **AND GIVEN** α set to 1.0, **THEN** no backdrop-filter is applied

### Requirement: Console file paste/drop — upload to the operator's worktree, stage as insert
The console SHALL bind its own file handlers on its root (marked `data-operator-console`): `onPasteCapture` — CAPTURE phase, because xterm's own textarea paste handler stops propagation, so a bubble-phase handler would never see file pastes targeted at the embedded terminal — and `onDrop` (with a `dragover` preventDefault for file drags); the omnibox binds its own `onPaste`, its wrapper carrying the same root attribute. Clipboard/dropped files ride `attachOperatorFiles` in the shared compose seam: upload via the existing `uploadFile` client (`POST /api/sessions/{session}/upload`) scoped to the OPERATOR window's session, and each returned path is delivered to the operator pane through the send lane as an INSERT — `sendToWindow(server, windowId, path + " ", "raw", "agent")`, the trailing space keeping consecutive inserts from concatenating — staged into the TUI composer where the `[Image #N]` chip renders, NEVER submitted; the user's typed message then submits normally and carries the staged image. Text paste falls through untouched (native input behavior in the omnibox; xterm bracketed paste in the terminal). In-flight state shows the minimal "uploading…" indicator in the status line (the drawer's top edge); failures ride the inline error line and deliver nothing. With no operator window resolved, file paste is a no-op (the hint line is the answer). Route terminals' document-level strip forward MUST skip console-origin pastes and drops ([compose-and-bottom-bar](/run-kit/ui/compose-and-bottom-bar.md) § File Upload — the `isOperatorConsoleTarget` containment guard).

#### Scenario: ⌘V of an image lands in the operator composer
- **GIVEN** an open console with a resolvable operator and an image on the clipboard
- **WHEN** ⌘V fires in the console
- **THEN** exactly one upload posts to the operator window's session and one insert-mode send delivers the returned path — and nothing lands on the tab below
- **AND** no submit fires until the user sends their message
- **AND GIVEN** an upload failure, **THEN** the inline error line shows it and nothing is delivered

### Requirement: Server-context resolution
The console SHALL resolve its server context via `resolveConsoleServer(routeServer, servers, lastViewed)`: the current route's server param always wins — read through the shared exported `useCurrentServerFromRoute()` hook (`contexts/session-context.tsx`), the single implementation of the deepest-first route-param walk, consumed by the console, `LayoutCommandPalette`'s Ask-operator gate, and the console-context resolution below (the console additionally walks the `window` param the same deepest-first way, feeding the compose lane fork's subject); on param-less routes (Host, Board) the sole server is preselected when exactly one exists, else a title-strip picker defaults to the most recently viewed server still listed (tracked ephemerally in a component ref — no persistence), then the first listed server; `null` only when the server list is empty. The operator window is discovered client-side from the sessions payload by `findOperatorWindow` (`role === "operator"` with a non-empty `windowId` — the server-scoped radio makes the first hit the only hit). The non-drawer surfaces (the mobile tongue and the omnibox) share the same resolution through `resolveOperatorConsoleTarget` / `useOperatorConsoleContext` in `lib/operator-console.ts`. A pinned or picked server is scoped to the route it was requested from: navigation clears both, retargeting the console to the new route's server. (02jx)

### Requirement: Availability degrades to absent
When the resolved server has no operator window, the desktop console body SHALL render a single hint line (`no operator on this server — run rk operator`) instead of the terminal — no stream opens and no send is possible. On mobile the tongue is omitted (never disabled) and the remaining openers (chord, palette action, palette fallback row per its existing gate, overflow-menu row) surface the same message as a brief toast — throttled so repeats within one toast lifetime never stack — and stay put: no navigation fires when `findOperatorWindow` resolves nothing. The palette Ask-operator fallback row is omitted when its availability check can establish that no operator exists; the console openers themselves (chord, palette action, menu row) stay available — the hint is the answer.

#### Scenario: Operator-less server
- **GIVEN** a server with no `role === "operator"` window
- **WHEN** the console opens on desktop
- **THEN** the hint line renders, no terminal stream opens, and no send is possible
- **AND GIVEN** a mobile viewport, **WHEN** the chord or the overflow-menu row fires, **THEN** no navigation occurs and the toast hint renders once

### Requirement: Mobile open is navigation to the operator terminal route
On mobile (the shared narrow-width-OR-coarse-pointer `useIsMobile()` rule) a console request SHALL NOT open any console surface: the layout-mounted seam listener resolves `{server, target}` (the `detail.server` pin wins, else `resolveConsoleServer(routeServer, servers, lastViewed)`; the operator window via `findOperatorWindow`) and navigates to the operator window's ordinary terminal route (`/$server/$window`) — the route's own chrome (the top-bar heading, the compose strip, the bottom-bar key chips, the `--bottom-bar-pad` safe-area handling) IS the mobile console. All three actions collapse to this navigation, idempotently: re-activating while already on the target operator route (server AND window id match) skips the navigate entirely, so an existing `?from=` (and the chip it feeds) survives. A navigation FROM a terminal route on the same server appends `?from=<originWindowId>` (never the operator window itself); the param passes the terminal route's `validateTerminalSearch` as an opaque non-empty string (`lib/router-url.ts`) and is validated against the same-server session windows at stamp time (the compose-seam requirement) — unknown, cross-server, or self ids render no chip and send direct. A `send` payload (the palette Ask-operator fallback row) seeds the operator route's compose-strip draft via the compose-draft store (`server:windowId`-keyed, `setComposeText`) instead of auto-sending — the user reviews in the strip and sends. The component still MOUNTS on mobile (the seam listener lives in it) but renders nothing; a desktop→mobile viewport flip resets the machine to `rest` and tears down any in-flight slide state so no effect or frame survives the gate (the self-gating-component rule: the gate owns the frames AND the effects). The operator-less case never navigates (the availability requirement's hide-plus-hint).

The operator terminal route ITSELF carries a second mobile surface: a `Terminal | Activity` segmented header (`components/terminal-activity-tabs.tsx`, mounted by AppShell inside `<main>` above the surface-layout column) rendered exactly when the shared `useIsMobile()` rule holds AND the resolved window's role is `operator` — every non-operator route and every desktop viewport renders the header-less tree byte-identically. The segments drive the terminal route's `tab` search param (`"terminal" | "activity"` on `TerminalSearch`, validated by a guarded block in `lib/router-url.ts`'s `validateTerminalSearch` following the `view`/`panel` pattern — unknown values drop to absent, which reads as `terminal`) through the router's search-param setter with `replace: true` — a client-side search update, never a full navigation or a history-stack entry. `tab=activity` swaps the content slot to the cron Activity feed ([cron-activity](/run-kit/ui/cron-activity.md)) while the terminal column stays MOUNTED-but-hidden (the `hidden` class — the same hide-never-unmount posture SurfaceLayout applies to its own hidden tiles), so switching back to `Terminal` needs no reconnect; cron notify pushes deep-link directly onto `?tab=activity` ([cron](/run-kit/cron.md) § Notify Deep-Links). The role is known only once the sessions payload resolves the window, so a cold `?tab=activity` deep link swaps in a beat after mount. The mobile seam arm maps a request carrying `segment: "activity"` onto that same param — merged with `?from=` on a cross-route navigation, an in-place `replace` search update when already on the route — so the deep-link, the palette's `Operator: Show clock activity`, and any other segment-carrying caller agree. On DESKTOP the param is inert on the route (the tabs are mobile-only and the route has no Activity view), so `app.tsx` hands it off once per arrival: on a desktop operator terminal route carrying `?tab=activity`, an effect dispatches `requestOperatorConsole({ action: "open", segment: "activity" })` and immediately strips the param (`navigate` with `tab: undefined`, `replace: true`) so a reload does not re-open — one deep-link landing correctly on both form factors.

#### Scenario: Tongue tap on mobile
- **GIVEN** a mobile viewport on any route with an operator window on the resolved server
- **WHEN** any entry point fires
- **THEN** the app navigates to `/$server/$window` for the operator window — no console overlay mounts
- **AND GIVEN** a re-activation while already on the operator route, **THEN** no navigation fires and the current `?from=` survives
- **AND GIVEN** a navigation from a terminal route `/$srv/@5`, **THEN** the target URL carries `?from=@5` and the operator route's compose strip renders the context chip naming `@5`

## Design Decisions

### Reply channel is the live TUI embed, not transcript rendering
**Decision**: the console reads replies by embedding a live terminal view of the operator window over the existing `/ws/terminals` mux.
**Why**: Constitution X (derive over push) and the surviving tty + compose pair are the read path; the embed adds zero backend surface — no transcript endpoint, no new WS subscription kind.
**Rejected**: a transcript-rendered chat panel (rebuilds a deliberately deleted wing — backfill endpoint, live transcript stream, message rendering); an `rk say`-style push card channel (pushes state derivable from the transcript).
*Introduced by*: 260904-qa85-operator-chat-console

### Console sends are chat steers — two lanes, one allow+probe posture
**Decision**: compose delivery forks between a templated chat lane (`user-message`, carrying a server-derived source envelope, when a route-window subject resolves and the context chip is attached) and the direct chat lane (`send target:"agent"` verbatim); both deliver with allow+probe busy semantics and bypass the operator-request queue entirely.
**Why**: a template request is work handed over (busy ⇒ enqueue); a typed console message is a human steer from a user watching the pane — it must land now, whose novelty probe is the fail-closed floor. The templated lane carries the context the server derives better than the user can hand-type it (Constitution X); the registry's `chatDelivery` property gives that template the chat posture, so the fork adds context without adding queue semantics.
**Rejected**: a client-side busy gate (strands hookless operators; the probe is the floor); delivering the templated send through request semantics (busy ⇒ 202 — silently parks a live chat message while the user watches the pane); client-side context-prefix composition (spoofable and drifty — inverts Constitution X).
*Introduced by*: 260904-qa85-operator-chat-console; lane fork (260905-4xu7-operator-templated-chat-lane)

### Entry points reach the console through a document-event seam
**Decision**: the chord, palette action, palette fallback row, mobile tongue, and overflow-menu row all dispatch the `rk:operator-console` CustomEvent rather than threading callbacks to the layout-mounted console; the omnibox owns the machine slot and shared compose seam directly.
**Why**: the entry points live in route shells the root layout does not compose directly; the document-event seam is the codebase's established idiom for crossing that boundary (`palette:open`, `HOST_MENU_OPEN_EVENT`, `WEB_FIND_OPEN_EVENT`).
**Rejected**: lifting open state into a new context provider with prop-threaded callbacks (a provider is easy to add later if threading deepens; the seam keeps every caller to one line).
*Introduced by*: 260904-qa85-operator-chat-console; omnibox boundary (260908-02jx-flush-surface-toggles-drop-operator-button)

### `segment` rides the existing event seam
**Decision**: the segment request is an optional field on `OperatorConsoleRequest`, applied by both form-factor arms (desktop segment state, mobile `?tab=activity`).
**Why**: every entry point already funnels through the one document event; a second event or a module slot would split the seam.
**Rejected**: a dedicated `rk:operator-console-segment` event; a URL param on desktop (the drawer is an overlay, not a route — Constitution IV).
*Introduced by*: 260910-6ehs-console-activity-segment-status-chip

### Operator-route openers stay visible and answer with a toast
**Decision**: the desktop operator-route gate lives in `operator-console.tsx`'s single document-event listener. Every quick-terminal entry point remains visible and clickable while the resolved operator route is current, and activation returns without state mutation after showing a throttled informational toast — except a request carrying `segment: "activity"`, which bypasses the gate because the Activity view exists only inside the drawer on desktop.
**Why**: one listener gives the chord, menu row, palette action, and palette fallback the same behavior, preserves the palette's always-listed availability idiom, and gives explicit feedback that the activation registered.
**Rejected**: hiding the overflow row while separately gating palette entry points, which distributes one route rule across multiple callers; a silent visible no-op, which provides no explanation for the inert action.
*Introduced by*: 260908-aumn-operator-direct-open-quake-gate

### Esc is a bubble-phase listener honoring `defaultPrevented`, not a focus trap
**Decision**: the console's Esc handling is a document keydown listener that skips `defaultPrevented` Escapes and releases the ⌘J machine to `rest` (desktop — the console has no mobile surface to close), with no focus trap.
**Why**: the console is a non-modal overlay the page stays live under; a nested modal's Escape must win, and cheap-close is the only stated requirement.
**Rejected**: the palette's modal focus-trap contract (wrong for a drawer; would capture keys the live page below still owns).
*Introduced by*: 260904-qa85-operator-chat-console

### The tongue is a toggle, mirroring desktop ⌘J
**Decision**: on the operator route the tongue renders a return state (tap = back: `?from=` origin → history back → server route) instead of hiding.
**Why**: mobile entry to the operator is one tap but exit had no standing affordance; one tab that goes in and out matches the desktop ⌘J model and uses the `?from=` fact the URL already carries.
**Rejected**: keeping the tongue hidden (one-way door); a top-bar back button (the history arrows are hidden below `lg` by the degradation ladder and a second affordance splits the model).
*Introduced by*: 260905-h7tx-operator-tongue-return-chip-glyphs

### The tongue serves mobile instead of a bottom-bar chip
**Decision**: on mobile the tongue under the top bar is the standing affordance for the console; no bottom-bar button exists.
**Why**: the bottom bar exists only on terminal tty views and its 375px single-row budget is fixed; the tongue hangs under the top bar, so it costs no bar space and works on every route.
**Rejected**: a bottom-bar chip (budget + route-scope); a hover-reveal affordance (invisible — contradicts the visual-indication goal).
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste

### Opacity is a localStorage-backed settings-dialog row
**Decision**: the console's glass α is a per-viewer localStorage key surfaced as a This-device row in the settings dialog; the blur is fixed at 6px and not exposed.
**Why**: Constitution IV layering puts per-viewer state in localStorage while "exposed in settings" is honored by the dialog being the one settings surface, which already hosts client-side residents (the terminal-font stepper); α=1 disables the filter for a zero-cost opaque path.
**Rejected**: an `internal/settings` registry key (per-instance daemon config — the wrong layer for a per-eye preference); a console-strip-only control (the user asked for settings).
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste

### Attachments deliver as insert, not submit
**Decision**: console file paste/drop uploads and then delivers each returned path as a send-lane insert (staged into the TUI composer as its `[Image #N]` chip); the user's own Enter submits.
**Why**: it mirrors the TUI-composer staging behavior the injection engine's echo probe already recognizes; auto-submitting an image without its message would be wrong.
**Rejected**: appending the path to the console textarea (the path would ride the submit as plain text — the user sees raw paths and can mangle them); auto-submit per file.
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste

### One input per form factor — the desktop drawer is output-only
**Decision**: on desktop the console's only input is the top-bar omnibox; the drawer renders no compose strip (the embedded operator terminal plus the status/error line at its top edge). On mobile the console has no input surface of its own — open requests navigate to the operator window's terminal route and its own compose strip is the input.
**Why**: with the omnibox standing (or morphable) at every desktop width, a second in-drawer compose would fork the draft, the error surface, and the send path; on mobile the operator is a TUI whose prompts need the route's compose strip + bottom-bar key chips, so navigation is the input story, not a parallel compose (see the mobile-navigation decision).
**Rejected**: keeping the drawer compose on desktop (two inputs, two drafts, ambiguous error lines); a mobile console compose of its own (the TUI-input gap — no arrows/Esc/Ctrl-C reach the pane — and the safe-area defects it carried).
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste; mobile navigation (260905-a9mn-operator-console-mobile-navigation)

### The omnibox is the console's compose relocated, driven by one shared seam
**Decision**: draft, in-flight flags, and the inline error live as module state in `lib/operator-console.ts` (`useOperatorCompose` + `setOperatorComposeText` + `sendOperatorMessage` + `attachOperatorFiles`); the desktop omnibox is the seam's one view. Mobile operator input is the operator terminal route's own compose strip, which keys its chat-lane fork on the same chat-subject store.
**Why**: the omnibox mounts in a different tree (top bar) than the console overlay (root layout) and the two must stay in lockstep; the send/upload logic exists exactly once.
**Rejected**: a second compose implementation in the omnibox (guaranteed drift); prop-threading between the bar and the overlay (the entry-point seam idiom already rejects this).
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste; mobile strip fork (260905-a9mn-operator-console-mobile-navigation)

### Desktop standing affordance is the omnibox
**Decision**: The omnibox's standing box and md–lg ghost are the desktop standing affordance for the operator console, and both ◉ glyphs carry the resolved operator's live-state dot; mobile retains the tongue.
**Why**: The omnibox is the console's only desktop input, presents the same operator glyph, and opens the same two-state machine, so it carries both action and status without consuming another right-cluster slot.
**Rejected**: A separate right-cluster ◉ control — duplicate action and fit-budget cost; omitting the dot — loses the amber `waiting` attention signal.
*Introduced by*: 260908-02jx-flush-surface-toggles-drop-operator-button

### The short placeholder does not repeat the operator glyph
**Decision**: Below `2xl` the omnibox placeholder is `Ask…`; the standing `◉` glyph beside the input is the operator's name in the box. The placeholder is selected by the `2xl` media query alone — engaging the box never switches it to the long form.
**Why**: A placeholder that carries its own `◉` renders the box as `◉ Ask ◉…` — two operator glyphs and a dangling ellipsis that reads as a truncated label, especially beside the context chip's own truncation `…`. `Ask…` is 4ch, well inside the 12ch resting budget, and follows the codebase's trailing-ellipsis placeholder convention. The gate stays width-only because the mounted chip leaves the engaged input ~12ch inside `w-[34ch]`, where `Ask the operator…` (18ch) clips mid-word.
**Rejected**: `Ask the operator…` whenever engaged (clips against the chip); `Ask` with no ellipsis (reads as a button label, breaks the placeholder convention); a wider resting box (trades away the breadcrumbs' `lg`/`xl` width budget for a placeholder).
*Introduced by*: 260909-ae2w-omnibox-placeholder-clarity

### The ghost/morph rung is md–lg-only
**Decision**: the dim `· ◉ ask` ghost renders only in the md–lg band; below `md` the chord and palette still morph the box in place with no ghost rendered, and at ≥ `lg` the standing box replaces the ghost entirely.
**Why**: the 640px no-overlap budget (the nav floor plus the hamburger against the anchored center heading) has no room for a standing affordance below `md`; the standing box and the morph share one component and one state, so the design is one thing at two widths.
**Rejected**: showing the ghost below `md` (paints over the anchored heading — the forbidden overlap class); a standing box at every width (no room).
*Introduced by*: 260905-sh7y-console-slide-resize-glass-paste

### Mobile console = navigation, not a parallel input surface
**Decision**: on mobile, opening the operator navigates to the operator window's ordinary terminal route; the console's mobile surface is deleted.
**Why**: the operator is a TUI — prompts need arrows/Enter/Esc/Ctrl-C, which only the terminal route's compose strip + bottom bar deliver on mobile; the route chrome also carries the top-bar heading and the `--bottom-bar-pad` safe-area handling, dissolving both reported defects with zero new code (Constitution IV).
**Rejected**: mounting ComposeStrip + BottomBar inside a mobile console surface (more parallel surface); patching the safe-area pad only (leaves the TUI-input gap).
*Introduced by*: 260905-a9mn-operator-console-mobile-navigation

### Origin context rides a `?from=` search param
**Decision**: the mobile navigation appends `?from=<originWindowId>` when navigating from a terminal route; the operator route stamps the chat subject from it and the compose strip's plain submit rides the templated chat lane behind the dismissable chip.
**Why**: preserves the chat-lane parity (server-derived envelope, Constitution X) without new persistence; the param is a route fact, visible and shareable.
**Rejected**: dropping origin context on mobile (loses the envelope the user confirmed they want); a module-store handoff without the param (invisible state, dies on reload).
*Introduced by*: 260905-a9mn-operator-console-mobile-navigation

### Operator-less mobile fallback is hide-plus-hint
**Decision**: the tongue hides when no operator resolves; the other openers toast the existing hint instead of navigating.
**Why**: omitted-not-disabled is the established availability pattern; the openers that remain reachable (chord, palette, menu) must answer with something — the toast is the lightest existing surface.
**Rejected**: always-visible tongue with hint-on-tap (a standing affordance that cannot act); silent no-op (indistinguishable from breakage).
*Introduced by*: 260905-a9mn-operator-console-mobile-navigation

### Outside-click collapse defers its decision past a settle timeout
**Decision**: the outside-click-collapse listener registers on `document` in the **capture** phase (so its activity snapshot precedes any same-click handler), but does not act inline — it defers the actual collapse to a `setTimeout(…, 0)` that re-checks `getConsoleMachineActivity()` against the value captured at click time, and separately bails if an unrelated `role="dialog"` is open.
**Why**: a same-click event-seam trigger outside the console's DOM reads and re-writes the machine in response to the SAME click, and a click that opens an unrelated modal (the settings dialog) needs the console to stay open underneath it. Neither can be resolved by phase ordering alone: capture-then-bubble happens fully synchronously (so acting inline in capture would race the trigger's own bubble-phase handler and the not-yet-mounted dialog), and a microtask deferral is not late enough either — React's own commit of the SAME click's state update (mounting the dialog, or the button's re-render) is not guaranteed to land before a same-tick microtask. A macrotask settle is what reliably runs after that commit.
**Rejected**: acting synchronously in the capture handler (races a click-driven event-seam trigger's own handler, and an unrelated dialog is not yet mounted to check against); a microtask-based settle (same race, one tier later — insufficiently deferred relative to React's commit); a bubble-phase (or `pointerdown`) listener with no deferral at all (`pointerdown`'s mousedown→mouseup→click gap gives React enough time to flush the machine change before the trigger's own handler reads it, flipping the toggle direction).
*Introduced by*: 260907-jp91-operator-console-collapse-icon

### Outside-click containment reuses the existing console-DOM marker; unrelated-dialog bail-out is global
**Decision**: the outside-click check excludes the console's own DOM via `isOperatorConsoleTarget`/`OPERATOR_CONSOLE_ROOT_ATTR` (already applied to both the drawer and the top-bar omnibox for recognizing console-owned paste/drop events) rather than a new containment mechanism or tagging every entry-point trigger element; separately, the settle check bails whenever ANY `role="dialog"` other than the console's own drawer exists in the document, rather than checking the clicked target's ancestry.
**Why**: the marker already spans exactly the console's own interactive DOM, so reusing it avoids touching unrelated trigger components such as menu and palette rows — the settle-timeout deferral (above) is what protects them, not tagging. The dialog bail-out is checked globally rather than by the click target's ancestry because the trigger that OPENS a dialog (e.g. the settings gear button) is not itself inside a dialog at click time — only a global "is a dialog open right now" check, evaluated after the settle delay, catches both the opening click and every subsequent click inside the open dialog.
**Rejected**: adding the console marker to every entry-point trigger (unnecessary — the settle-timeout activity check already resolves that race, and would have required touching shared components like the sidebar row used by many non-operator rows); checking the clicked target's `role="dialog"` ancestry instead of a global existence check (misses the trigger click that opens the dialog, since the dialog doesn't exist in the DOM yet at that click).
*Introduced by*: 260907-jp91-operator-console-collapse-icon

### The mobile cron Activity view mounts on the operator terminal route
**Decision**: the `Terminal | Activity` segmented header mounts on the existing operator-window terminal route (gated on mobile + `role === "operator"`), not on a new overlay/sheet component.
**Why**: no mobile drawer/sheet exists — every console-open request already navigates to the operator window's ordinary terminal route, whose own chrome IS the mobile console (the mobile-navigation decision above); a parallel overlay would duplicate that chrome.
**Rejected**: a new mobile overlay/sheet component hosting the segments (duplicates the route chrome, contradicts the navigation design); an always-on header on every terminal route (visual noise on non-operator windows — the role gate keeps every other route byte-identical).
*Introduced by*: 260907-yxen-mobile-cron-activity-feed

### Tab switch swaps content in place, keeping the terminal mounted
**Decision**: `tab=activity` swaps the content slot to the Activity feed but does not unmount the terminal — the surface-layout column takes the `hidden` class and keeps its stream.
**Why**: matches the hide-never-unmount posture SurfaceLayout already applies to its own hidden tiles and the console's toggle-not-teardown behavior; switching back needs no reconnect and loses no scrollback.
**Rejected**: unmounting the terminal on tab-away (simpler, but regresses the guarantee that hidden terminals stay connected).
*Introduced by*: 260907-yxen-mobile-cron-activity-feed

## Why

**The problem.** After Change 1 every PANE row *fits* the 220 px default sidebar for typical values, but two rows still carry expendable tails that truncate first when values run long: the `pr` row (`#386 · open · checks fail · review: changes requested` — 52 characters) and the `fab` row when the pane is *off* its change branch (`y1ar status-pyramid-ui-surfacing · review · failed` — the slug is the off-branch signal, and it is exactly the part the ellipsis eats). Meanwhile, when a desktop viewer opts the PANE section back in (rail toggle or `Panel: Toggle Pane`), the same six registers render **twice on screen at once** — in the sidebar panel and in the status bar's left window cluster — 30 px apart. The study (§ A, annotated screenshot) counted the change slug ×4 and the window name ×4 on one desktop frame; the bar's window cluster is the redundant copy whenever the panel is visible, and it is also the cluster that pushes the bar's host segments into truncation (the `⑂`/`fab` values are the 30–48-character strings that overflow the bar).

**If we don't fix it.** The register view has two desktop homes competing for the same 1512 px, so Change 2's measured fold has to fit six volatile window segments *plus* the host cluster even when the panel is already showing them; and the panel — the surface the user explicitly opted into — keeps truncating the one value on each of two rows that the user most needs to read whole (the PR health, the off-branch slug).

**Why this approach.**
- *Yield the whole cluster, not `pr`-only.* The study kept `pr` in the bar while yielding; the plan drops the whole cluster. Keeping `pr` needs a new `StatusBar` prop and a `WindowCluster` branch — that puts this change on the same file Change 2 rewrites and forces the two changes serial. The panel shows the `pr` row with its open-first `↗` directly in the sidebar, so the bar's copy is redundant there. If the `pr`-keep is wanted after all it is a follow-up on top of Change 2.
- *Gate at the mount, not inside `StatusBar`.* `window={null}` is already the board mount's contract (`board-page.tsx` passes it), so the terminal-route mount can express "no window cluster" with zero component change — the reason 2 ∥ 3 is file-disjoint.
- *Continuation lines rather than truncation* is the flyout card's recorded decision (status-signals § Design Decisions → *Continuation lines rather than truncation*): truncation is unavoidable somewhere, so the layout chooses what gets cut — decisive tokens first, expendable text on its own dim line where cutting is harmless. The panel adopts the same rule for the two rows that have an expendable tail.
- *Rejected* (recorded in the study § F and the plan): yielding the bar whenever the sidebar is open (the default desktop has the sidebar open and the panel OFF — the bar would vanish for everyone); a settings surface for which bar segments show (Constitution IV); dropping the `git` row when it equals the change; continuation for `out`/`agt`/`opr` (they fit after Change 1; `opr`'s facets stay inline in the panel).

## What Changes

### 1. Mount gate — `app/frontend/src/app.tsx` (terminal-route `StatusBar` mount, ~line 5306)

The terminal-route `<StatusBar window={currentWindow ?? null} …/>` mount inside `AppShell` gains a gate: the window cluster yields when the PANE section is visible **and** the sidebar is actually on screen.

```tsx
// beside the other hooks in AppShell
const [paneSectionVisible] = useSidebarSectionVisible("pane");
const { sidebarOpen } = useChromeState();   // or read from the already-destructured chrome state in AppShell
// The panel is on screen only when its section is on AND the sidebar is
// rendered — Shell composes `sidebarOpen && !zenActive`, so zen hides the
// panel without touching the persisted preference and the bar must come back.
const paneRegistersVisible = paneSectionVisible && sidebarOpen && !zenOn;

<StatusBar
  window={paneRegistersVisible ? null : currentWindow ?? null}
  server={server}
  isConnected={dotConnected}
  onOpenCompose={toggleComposeStrip}
  zenActive={zenOn}
  onExitZen={zenOn ? toggleZen : undefined}
/>
```

- `useSidebarSectionVisible("pane")` (`hooks/use-sidebar-sections.ts`) is the `useLocalStorageBoolean` pub/sub over `runkit-sidebar-section-pane` — the same subscription `Sidebar`, `SectionRail`, and the `Panel: Toggle Pane` palette entry (`use-global-palette-actions.ts:215`) already share, so the bar flips **live** when the rail toggle or the palette entry fires, with no new state and no new prop threading. `sidebarOpen` is `ChromeState.sidebarOpen` (`contexts/chrome-context.tsx`, persisted at `runkit-sidebar-open`) — the value `Shell` already composes with `!zenActive` to decide whether the sidebar renders. `zenOn` is the existing `zenApplies(zenActive, windowParam, isMobile)` value in `AppShell` (`app.tsx:1370`) already passed to `Shell` and `StatusBar`.
- **Three inputs, one rule**: the bar's window cluster renders iff the panel is *not* on screen. Section off ⇒ bar shows the cluster (today's default desktop). Section on + sidebar open ⇒ bar passes `window={null}` and keeps only the host cluster (`status-bar-host`). Section on + sidebar collapsed (`Cmd+\` / the top-bar sidebar toggle) ⇒ the panel is unmounted (the sidebar keeps unmount-on-collapse — sidebar.md § Design Decisions), so the bar shows the cluster again. Section on + sidebar open + **zen active** ⇒ `Shell` hides the sidebar, so the bar shows the cluster again (zen keeps the bar visible by design — 260820-o8cr R5/R8 — and it must not become the one desktop state with *no* register view).
- **No change** to `StatusBar`, `WindowCluster`, `StatusBarProps`, the board mount (`board/board-page.tsx` — `window={null}` already), the Host mount (`host-overview-page.tsx`), or mobile (no bar — `!isMobile` gate untouched). The right/host cluster (`status-bar-host`) is unaffected in every state.
- The `CollapsiblePanel`'s own collapsed state (`runkit-panel-window`) is **not** a gate input: a collapsed PANE panel still shows its header (StatusDot + window name) and the user collapsed a panel they explicitly opted into; re-expanding is one click. Gating on it would need a fourth subscription for a state the user created deliberately.

### 2. Continuation lines — `app/frontend/src/components/sidebar/status-panel.tsx`

Two rows split into a **key line** (decisive tokens, `text-text-primary`, the existing interactions) and a **continuation line** (the expendable tail, `text-text-secondary`, indented under the value column, `min-w-0 truncate`). A row never exceeds two lines. The continuation line is rendered only when it has content — no empty second line, ever.

**Indentation.** The continuation line is indented to sit under the row's *value* column. In the panel that column starts after the 4-advance key (`fab ` / `pr` + 2 NBSP) **and** the 2-advance icon cell (`ClockSpinner`/`` glyph + its NBSP/space) — i.e. `pl-[6ch]`. The flyout card's `pl-[4ch]` is the same rule applied to a card with no icon column (its value column *is* the 4-advance column); the panel mirrors the rule, not the number. The continuation line is a block-level sibling under the key line (the row wrapper becomes `flex flex-col`), never a wrapping inline.

**`pr` row.** Key line: `#<n> · <state>` + the always-visible `↗` (URL branch) — the `getPrSegments` *identity* segments (`#n`, then the state segment incl. `(draft)` when present). Continuation: the *health* segments — `checks <c> · review: <r>` — coloured per segment via the existing `PR_CHECKS_COLORS` / `PR_REVIEW_COLORS` (the segment `color`), with `text-text-secondary` ` · ` separators; `data-testid="pr-line-cont"`. Merged/closed PRs already have no health segments (`getPrSegments` suppresses them for `!open`), so they render one line, no continuation. Both the URL branch (`PrLinkRow`) and the no-URL branch (`CopyableRow`) render the same split — the identity/health JSX is built once (the existing single-sourced `segmentSpans` idiom, now two arrays) so the two branches cannot drift.

- **The anchor wraps both lines** in the URL branch: the `<a>` in `PrLinkRow` becomes a `flex flex-col` block containing the key line (prefix + icon + `pr-line` span + `↗`) and the continuation line, so open-first (click, middle/Ctrl+click, right-click → copy link) covers the whole two-line block and the `hover:bg-bg-inset` tint paints the block. The `↗` stays on the key line, immediately after the (possibly truncated) identity span, `shrink-0`. The hover-revealed copy icon (the `absolute` sibling `<button aria-label="Copy PR URL">`) stays vertically centred on the **key line**, not the block — anchor it to the top row (`top-0` with the key line's height, or wrap the key line in its own `relative` row) rather than `top-1/2` of a two-line block. The `title={prUrl}` and `aria-label` are unchanged. `data-testid="pr-line"` stays on the key-line identity span (the e2e `pane-register-panel.spec.ts` asserts `pr-line` contains `#386` / `#999` — still true; `status-panel.test.tsx` asserts full strings like `#241 · open · checks fail` on `pr-line` — those move to `pr-line` + `pr-line-cont` assertions).
- The no-URL branch: `CopyableRow` gets the same two-line body (its `<button>` is already `text-left w-full`; drop `truncate` from the button for this row and let the two child lines truncate individually — the `flex` prop's flex-row form does not fit a two-line body, so either a new `block`/`stack` prop or a local two-line wrapper). Copy value stays `prText` (the joined full text).
- Resolver seam: split at the resolver so the rule is shared — add `getPrParts(win): { identity: PrSegment[]; health: PrSegment[] } | null` to `sidebar/registers.ts` (identity = `#n` + the state segment when present; health = checks + review, empty for `!open`), and make `getPrSegments` the pure formatter `[...identity, ...health]` so its output stays byte-identical (`registers.test.ts` pins it). The panel composes from `getPrParts`; the flyout card and the status bar keep consuming `getPrSegments` unchanged. (status-signals § Register resolvers *already documents* a `getPrParts` `{ identity, health }` resolver that the code does not have — see Affected Memory.)

**`fab` row.** Key line: `<id> · <stage>[ · <displayState>]` — the `FAB_STATE_COLORS` hue on the state token, `CopyableRow` copying the 4-char id, `ClockSpinner` icon, all as today minus the slug. Continuation: `<slug>` **only when `getFabParts(win, gitBranch)` returns a slug** (the pane's branch does not carry the change — `main`, a hand-named branch); `data-testid="fab-line-cont"`, `text-text-secondary`, `pl-[6ch]`, `truncate`. When the branch carries the change (the fab-pane norm) the row is one line, exactly as after Change 1. The key line no longer contains the slug in any case (today it renders `{id}{slug ? ` ${slug}` : ""} · {stage}` — the slug moves down). The copy value stays `fabParts.id`. The whole two-line block stays inside the `CopyableRow` button so a click anywhere on the row copies (same as the `pr` no-URL branch above).

- The flyout card's fab composition (`RegisterLine` + `ContinuationLine` in `row-flyout-card.tsx`) is **not** lifted into a shared component: both surfaces already compose from the one `getFabParts` resolver, and the panel's key line carries interactions and hover classes (`group-hover:text-accent`, the copy row) the card's read-only line deliberately lacks — a shared JSX piece would need props for exactly those differences. The shared *rule* (slug only when the branch does not carry it) lives in the resolver, which is what keeps the surfaces from disagreeing.

**Unchanged rows**: `tmx`, `cwd` (its own two-span head-truncation from Change 1), `git`, `out`, `agt`, `opr` (facets stay inline — they fit). The header comment block in `status-panel.tsx` above `WindowContent` documents the continuation rule (constraints, not history — no change-ID citations).

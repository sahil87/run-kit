# run-kit UI — Status Signals

## PR Status

Live PR status is exposed two ways: a **full detail** (the Pane panel `PR` L3 register — identity on a key line, health facts on a continuation line) and a **single status dot** (the unified `StatusDot`, see § Status Dot below). The detail surface is:

1. **Pane panel `PR` (L3) register** (the per-*selected*-window detail view; see § Pane Panel / `status-panel.tsx`). This is the full-line PR surface — mirrored in compact form by the status bar's left-cluster `pr` segment (§ Status Bar), which resolves the same `getPrSegments` colors. The `SessionTiles` window tile carries the `StatusDot` plus the rest-state PR glyph (§ Rest-state PR glyph); there is no `PrStatusLine` component; its module `pr-status-model.ts` is the single source of the shared PR color vocabulary + the StatusDot's exported model (§ Shared PR vocabulary). (260701-70a0) (260715-jykd) (aqo6)

The *dot* (a single colored dot, not the full line) reaches the remaining surfaces: the sidebar window-tree row and the `SessionTiles` window tile. The dense tree shows a single `StatusDot`, never the multi-part line. That single dot is the unified `StatusDot` driven by the compositional **two-family ladder** (cool fab blue-building → green-PR-ready, warm ad-hoc agent yellow, gray floor; core hue = phase, shape = liveness, additive overlays = the `waiting` yellow halo + the `failed` red center + the `watched` neutral underbar), reused on all its surfaces (sidebar row, SessionTiles window tile, pane-panel header). The dot tells the **local** story only — the branch's PR (the remote story) rides the separate rest-state glyph beside it. See § Status Dot. (260610-obky) (aqo6) (18ot)

**PR-field presence is backend-continuous**: the streamed `prNumber`/`prUrl`/`prState` these surfaces gate on carry server-side continuity — the branch→PR join is keyed on the pane's git root (cd-churn and same-worktree pane flips hit one stable entry), a detached HEAD (rebase) serves the last-known branch for a 5-minute grace, and unobserved refresher entries are retained for 30 minutes past their 5-minute resolution window — so the glyph and the L3 register hold steady through rebases, pane movement, and a reopened dashboard. Glyph semantics themselves are unchanged (`prOwnsGlyph`'s positive allowlist and `prGlyphColor`'s six-way chain below); the mechanism lives in [pr-status](/run-kit/architecture/pr-status.md) § Branch→PR Derivation. (260823-8ocy)

The viewed window's `prState` also feeds the **Smash Easter egg**: an observed `open`/`closed` → `merged` flip on the window the user is viewing (first observation never fires — merged is a terminal state visible forever on old windows) fires the one-shot green-fist screen-break once per PR number via `runkit-egg-smash` — see [screen-break-eggs](/run-kit/ui/screen-break-eggs.md). (kp2l)

### `PR` (L3) register — colored segments + open-first (`status-panel.tsx`)

> `WindowContent` renders the pyramid's **five orthogonal signal registers** (spec § Row Minimalism). See § Pane panel five-register view for the full L0–L4 model; this subsection covers the L3 `PR` register. (260706-y1ar)

The **`PR` (L3) register** shares the `tmx/cwd/git/fab` icon + value idiom but with an **open-first** interaction — it is the exception to the panel's "click row = copy" default. `getPrParts(win)` returns `null` unless `win.prNumber` — the gate is **ungated from `fabChange`**: the L3 register shows the PR for ANY pane on a branch with a derived PR (universal derivation, Principle X; the dot renders no PR state — the row/tile glyph is the PR channel, see § Status Dot). Otherwise it returns two groups of colored `{text, color}` segments — **identity**: `#<n>` (`text-text-primary`) and `<state>[ (draft)]` (via `PR_STATE_COLORS`); **health**: for an `open` PR only, `checks <prChecks>` (`PR_CHECKS_COLORS`) and `review: <prReview→spaces>` (`PR_REVIEW_COLORS`) — the panel renders identity on the row's **key line** (`data-testid="pr-line"`) and health on a dim **continuation line** (`data-testid="pr-line-cont"`, rendered only when health is non-empty, so a merged/closed PR is one line). `getPrSegments(win)` is the joined one-line form `[...identity, ...health]` the flyout card and the status bar render. `state` can be `open`/`merged`/`closed` — the collector queries `states: [OPEN, MERGED, CLOSED]`, so a recently-merged PR shows `merged` (checks/review suppressed for non-`open`), see `architecture.md` § `internal/prstatus`. The three color maps are imported from `pr-status-model.ts` (single source shared with the sidebar dot — the shared vocabulary home, § Shared PR vocabulary), so segment coloring follows GitHub state per-segment (no whole-value red swap) — the color story lives in § PR Status (draft-follows-health) above. The PR icon (``) is the Nerd Font git-pull-request glyph, matching the other rows' accent icons.

**Open-first split** — the row body's interaction is open-first (`↗`), not copy. The segment JSX is single-sourced via one `toSegmentSpans` builder in `WindowContent` (both lines of both branches below, so the two can't drift), and the row branches on `win.prUrl`: (260703-41ks)

- **URL present** → the row body is a file-private `PrLinkRow` — a real `<a href={win.prUrl} target="_blank" rel="noopener noreferrer" title={win.prUrl} aria-label="Open PR #<n> in a new tab">` (NOT a `<button>` + `window.open`, so native middle-click / Ctrl-Cmd+click / right-click → "Copy link address" all work — the anchor-not-button PR-link idiom). The anchor is a `flex flex-col` block of at most two lines, so open-first and the `hover:bg-bg-inset` tint cover the whole block: the **key line** is a flex row — a `shrink-0` prefix span + PR icon span, then the `min-w-0 truncate` identity span (`pr-line`), then an **always-visible** (not hover-gated) `shrink-0` inline `↗` sibling immediately after it — so the `↗` hugs the (possibly truncated) identity end, is never eaten by truncation, and never floats to the far right of a wide row; the **continuation line** (`pr-line-cont`, a `ContinuationLine`: `w-full min-w-0 truncate pl-[6ch] text-text-secondary`, each health segment keeping its own hue class) follows only when the PR has health facts. The `↗` is the affordance that signals this row **opens** rather than copies; the row hover treatment (`hover:bg-bg-inset`, segment `group-hover:text-accent`) is the row-level cue. Because the anchor is a flex container (whitespace-only `{" "}` text nodes between flex items are dropped and a trailing collapsible space trimmed), the key gap lives as NBSPs INSIDE the prefix span — the at-rest prefix is `"pr"`+2×NBSP (4 monospace advances) matching `CopyableRow`'s 4-advance key (`${prefix} ` inline; `${prefix}`+NBSP in its flex mode), and the `copied ✓`+NBSP feedback is 9 advances matching `CopyableRow`'s — while the icon→value gap is an NBSP **text node** between the icon span and `pr-line` (an NBSP-only node survives flex whitespace dropping) placed OUTSIDE the 14px `ICON_CLASS` span, so it measures one 12px advance like the inline rows' `{" "}` and the value column shares one x with `tmx/cwd/git/fab` (§ Design Decisions → Flex rows carry their gaps as NBSPs). **Copy is role-swapped, not dropped**: a sibling hover-revealed copy `<button aria-label="Copy PR URL">` (the `` clipboard glyph) sits in an absolutely-positioned right-side container — `top-0 h-[1lh]`, one text line tall, so the 24px button stays centred on the KEY line when the block is two lines (`top-1/2` would centre it between the lines) — reusing the **sidebar window-row icon-cluster gating** — the container is `pointer-events-none` at rest with `group-hover/pr:pointer-events-auto coarse:pointer-events-auto has-[:focus-visible]:pointer-events-auto`, and the button is `opacity-0 group-hover/pr:opacity-100 coarse:opacity-100 focus-visible:opacity-100` (revealed on hover / coarse pointers / keyboard focus; the anchor reserves `pr-6` so the icon doesn't overlap the inline `↗`/text). Its `onClick` does `e.preventDefault(); e.stopPropagation(); handleCopy("pr", win.prUrl)` — the button is a SIBLING of the anchor (not enclosed, so `<a>`-in-`<a>`/`<button>`-in-`<a>` nesting is avoided; `preventDefault` is belt-and-suspenders). Its color follows the window-row cluster precedent (`text-text-secondary hover:text-text-primary`), NOT `ICON_CLASS` (whose `text-accent-bright` would fight at equal specificity). The `copied ✓` feedback keeps the `copiedRow === "pr"` + `COPY_FEEDBACK_MS` mechanism, and because the row body is not a `CopyableRow`, `PrLinkRow` replicates the prefix swap (`pr` → `copied ✓`) inline. Both the anchor and the copy button are natively keyboard-focusable (Constitution V).
- **URL absent** (`prNumber` set, `prUrl` missing) → nothing to open, so the row stays a plain `CopyableRow` (prefix `"pr "`) copying the joined full text (`prText`, identity then health) on click — the row body IS the copy action, no anchor, no inline `↗`, no hover copy icon. It splits the same way: identity on the key line, health on the `continuation` line, both inside the one button.

`CopyableRow` has no `className` prop; its `title` prop is live (the `cwd` row uses it); a `flex` prop switches the button from a truncating inline row to a flex row whose children own their own shrink rules (the `cwd` row's two-span value — the parent yields, the basename never truncates); and a `continuation` prop (a `ContinuationLine`) stacks the button `flex flex-col` — a `w-full truncate` key line above the continuation, each line truncating on its own, a click anywhere on the block still copying (the `pr` no-URL branch and the `fab` row).

**Draft state-color follows health, not readiness.** `getPrParts(win)` (the panel's L3 source — `getPrSegments` joins the same segments for the flyout card and the status bar) does NOT force a draft PR's state-color to `text-text-secondary` — a draft's state segment follows `PR_STATE_COLORS[win.prState]` like any other (open → `text-accent-green`/green), under the "green = HEALTH, not merge-readiness" semantic. Checks/review are suppressed for `!open` (merged/closed) PRs, and `merged` is `text-signal-purple`. The color story is one system across the rest-state glyph and these status-panel segments (green = health, red = fail, yellow = checks running, purple = merged) driven by the shared `isFailish` predicate. The sidebar `StatusDot` renders no PR state at all — it keys off the lifecycle `PHASE_HUE`/shape model (§ Status Dot); the row's PR color channel is the glyph (`prGlyphColor`). (260615-2olv) (aqo6)

The rest-state PR glyph (window row + session tile) is the **one** surface that colors draft differently — gray, below fail, open-gated — and the one surface that gives draft its own shape (the dotted-rail `GitPullRequestDraftIcon`, § Row PR-glyph helpers). Draft-follows-health governs these segments; the glyph carries the orthogonal *whose turn is it* read, and the `" (draft)"` state-segment suffix here stays the accessible signal either way. (e30p) (lvvw)

### Pane panel five-register view (`status-panel.tsx` `WindowContent`)

The pane panel's `WindowContent` renders the pyramid's **register view** — one line per signal layer, **orthogonal, never collapsed**, so the sidebar `StatusDot` is a pure function of what the panel shows and can be **mentally derived** from it. The five registers each render as absent when their layer is absent (a plain shell pane shows only `out`). All prefixes are the **fixed-width 3-char vocabulary** `out`/`agt`/`fab`/`opr` (+ `tmx`/`cwd`/`git` identity rows), each followed by a one-advance gap — a plain space on the inline rows, an NBSP on the flex rows (`CopyableRow`'s `flex` mode, the `cwd` row) because a flex container trims a trailing collapsible space; only `PR` is 2-char + NBSP-padded to the same 4-advance column. The icon cell is 2 advances — the 14px glyph plus a one-advance gap — and on the flex rows (`cwd`, `pr`) that gap is an NBSP text node OUTSIDE the icon span so it measures at the row's 12px size and the value column lines up across rows. (260706-4h26) (3k45)

```
out  <cmd> · flowing      /   <cmd> · idle Xm                          (L0: activity + activityTimestamp)
agt  waiting 3m           /   active   /   idle 12m                    (L1: agentState + epoch duration)
fab  <id> · <stage>[ · <displayState>]                                (L2: fabChange · fabStage · fabDisplayState)
       <slug>                                                          (continuation — only when the branch does not carry the change)
PR   #<n> · <state>                                                    (L3: prNumber/state/checks/review, ungated)
       checks <c> · review: <r>                                        (continuation — open PRs with health facts only)
opr  watched[ · <stage>][ · tick <age> ago][ · <repo> · <branch>]  /  done · operator-touched   (L4: monitored* + owner + operator watchdog facts)
```

- **L0 `out`** (`getOutputLine`) — ALWAYS rendered (the floor layer's precondition is "always"). Speaks about bytes, not intent: `<cmd> · flowing` while output flows (bare `flowing` with no command), else `<cmd> · idle <dur>` from `activityTimestamp` (bare `idle <dur>` with no command), else `<cmd>` / bare `idle` with no usable timestamp. `flowing` is the spec's own L0 word (spec § Duration-Text Ladder), keeping L0 lexically distinct from the L1 `active` agent state; the output-activity narration lives in the tier-1 `Output activity` tip, not on the register. Its elapsed is **never muted** here — the register view is uncontested for space, so the **waiting-pierce rule is automatic** (the duration-mute rule that hides elapsed when output flows applies only to the tip's one-line summary, spec § Duration-Text Ladder). Icon: `BrailleSnake`.
- **L1 `agt`** (`getAgentLine`) — `null` when no `agentState`, else `${agentState} ${agentIdleDuration}` gated on `waiting`/`idle` (or bare state otherwise). The rk-computed `agentIdleDuration` is populated for `active` too (the live-agent staleness signal), but rendered only for the two rest states. Icon: `StarTwinkle`. This is where a waiting duration is always visible regardless of flowing output (the pierce rule).
- **L2 `fab`** (`getFabParts`) — `<id>[ <slug>] · <stage>[ · <displayState>]`; the `displayState` segment is appended when present (derived natively alongside the stage — empty only when no change resolves) and renders in the fab hue vocabulary (`FAB_STATE_COLORS`, § Shared PR vocabulary). The slug is written once — the branch carries it: when the active pane's branch ends with `<id>-<slug>` (a fab pane's branch IS the change folder name, already shown by the `git` row) the slug is omitted; beside a `main` or hand-named branch it renders on the row's dim **continuation line** (`data-testid="fab-line-cont"`), itself the signal that the pane is off its change branch — the key line never carries it. Rendered as a `CopyableRow` with a `continuation` (copies the change id from anywhere on the block). Icon: `ClockSpinner`.
- **L3 `PR`** (`getPrParts`) — identity (`#<n> · <state>`) on the key line, the health facts on a continuation line; see § `PR` (L3) register above. **Ungated from `fabChange`** — shows for ANY pane with a derived `prNumber` (universal derivation, Principle X). The open-first `PrLinkRow` / `CopyableRow` branch on `win.prUrl` folds in here.
- **L4 `opr`** (`getOperatorParts`) — two branches, monitored-wins precedence (hzih): `win.monitored === true` yields the watched head `watched[ · <monitoredStage>][ · tick <formatDuration> ago]` (the stage segment omitted when absent, the tick segment when `operator`/`lastTickAt` is undefined or 0 — never ticked; a non-positive elapsed renders `tick 0s ago`) with facets `<monitoredRepo> · <monitoredBranch>` appended inline (empty segments omitted); otherwise `win.owner === "operator"` (an operator-owned window no longer on the watchlist — the `@rk_win_owner` trail) yields exactly `{ head: "done · operator-touched" }` — no facets, no tick age (there is no live loop relation), and the `operator` facts are ignored entirely; otherwise `null` (degrade-to-absent). Rendered after the `fab` row as a plain `div` (`data-testid="register-operator"`) with a `Tip label="Operator watchlist"` on the `opr ` prefix; no per-layer icon (the watchlist has no animated mark — the 4-advance key keeps the column). Stale (`operator.stale`, consumed verbatim from the server-derived `operatorStale` — never recomputed client-side) dims the value to `text-text-secondary` and marks the row `data-stale="true"` — **watched head only**: stale is the live loop's overdue tick and a done row has no loop, so the done head is never stale-dimmed (consumers gate the stale flag on `win.monitored === true`). The `operator?: OperatorLoopFacts` input is derived in `BottomPanels` from the owning session — see [sidebar](/run-kit/ui/sidebar.md) § WindowPanel. (0536)

The identity rows (`tmx`/`cwd`/`git`) are pane metadata, orthogonal to these five signal registers, and render above them: `tmx` shows the active pane's id — `%107` for a one-pane window, `%109 · 3/3` for multi-pane (the ordinal only disambiguates); `cwd` is a basename-first two-span value — the abbreviated parent (with its trailing `/`) dim in `text-text-secondary` and head-truncating (`dir="rtl"` with the text isolated in `<bdi dir="ltr">`), the basename primary and `shrink-0`, never the part that truncates; `git` dims a leading `^\d{6}-` date prefix to `text-text-secondary`. The per-second `useNow()` tick lives in this leaf (`WindowContent`) — the bottom panel is a single instance, so its tick is negligible and never touches the memoized sidebar tree (§ Render Performance).

**Continuation lines** — the `pr` and `fab` rows are the panel's two-line rows (§ Design Decisions → The panel adopts the card's continuation rule): the decisive tokens lead on the key line, the expendable tail (the PR health facts; the slug when the branch does not carry it) moves to a `ContinuationLine` — `w-full min-w-0 truncate pl-[6ch] text-text-secondary`, indented to the panel's VALUE column (the 4-advance key + the 2-advance icon cell; the flyout card's `pl-[4ch]` is the same rule on a surface with no icon column). A row never exceeds two lines and a continuation line renders only with content — a merged PR, a branch carrying the change, or `none` checks/review leave the row one line. `out`/`agt`/`opr` fit and stay one line (`opr`'s facets inline).

**The register view has THREE surfaces**: this PANE panel, the sidebar row-hover flyout card (§ Row-hover register flyout card), and the status bar's left window cluster (§ Status Bar). All resolve their lines from the shared `sidebar/registers.ts` module (§ Register resolvers), so they cannot drift. The panel keeps the icon column (`BrailleSnake`/`StarTwinkle`/`ClockSpinner`), the identity rows, and the copy/open-first row interactions; the card is read-only glance content with only its PR + docs links interactive; the status bar renders the compact segment form of the `agt`/`fab`/`pr` registers plus the `tmx`/`cwd`/`git` identity rows — it carries **no `out` register** (and therefore no per-second clock) — clickable where the segment carries an action. The PANE panel surface is **opt-in**: it mounts only while its sidebar section-visibility toggle is on ([sidebar](/run-kit/ui/sidebar.md) § Section-Visibility Rail — default OFF on every viewport, so the board-route focused-tile fallback is likewise opt-in); on desktop the register view has ONE home at a time — while the panel is on screen (section on, panel expanded, sidebar open, zen off) the status bar yields its window cluster (§ Status Bar); on mobile the coarse status rail + three-tier cards are the default register-detail surface, with the panel reachable via the rail or the `Panel: Toggle Pane` palette entry. (93dy) (260814-ldbs) (499u) (260817-iha5)

### Register resolvers — `sidebar/registers.ts`

The five register lines are resolved by pure functions over the streamed `WindowInfo` in `sidebar/registers.ts` — **one source for all three register surfaces** (the PANE panel's `WindowContent`, the row flyout card, and the status bar's window cluster), no React, no duplication:

- `getOutputLine(win, nowSeconds)` → the L0 `out` string: `<cmd> · flowing` while output flows, `<cmd> · idle <dur>` at rest, segments omitted as their inputs fall away (`flowing`, `idle <dur>`, `<cmd>`, or bare `idle`). Takes `nowSeconds` as a parameter rather than reading a clock, so each consuming surface supplies its own leaf-scoped `useNow()` (§ Render Performance). Consumed by the PANE panel only — the status bar renders no `out` register (499u), and neither does the flyout card.
- `getAgentLine(win)` → the L1 `agt` string; `null` when no `agentState`.
- `getFabParts(win, branch?)` / `getPrParts(win)` (+ the `FabParts` / `PrParts` types) → the L2 `fab` and L3 `PR` registers as structured parts — `{ id, slug?, stage, displayState? }` and `{ identity, health }` (both `PrSegment[]`: identity = `#<n>` + the state segment, health = the open-only `checks`/`review` segments, empty for merged/closed) — for surfaces that compose a register across lines or colour its tokens (all three surfaces compose the `fab` register from parts; the PANE panel composes `pr` from `getPrParts` — identity on the key line, health on the continuation line — while the flyout card and the status bar render the joined `getPrSegments`). The optional `branch` is the active pane's git branch: when `branch.endsWith(`${id}-${slug}`)` the branch already shows the slug and `FabParts.slug` is `undefined`; otherwise the slug stays — its presence beside a `main` or hand-named branch is the off-branch signal. `getPrParts` is `null` without `prNumber`.
- `getFabLine(win, branch?)` → the L2 `fab` string `<id>[ <slug>] · <stage>[ · <displayState>]`; `null` without a parseable `fabChange` or without a stage. A pure formatter over `getFabParts` — the plain-text form for copy/aria/`title`; every production surface composes from `getFabParts` instead, so its only consumer today is `registers.test.ts`.
- `getPrSegments(win)` → the L3 `PR` colored segments as ONE flat list (+ the `PrSegment` type); `null` without `prNumber`. A pure formatter over `getPrParts` — `[...identity, ...health]`. See § `PR` (L3) register for the segment vocabulary and gating.
- `getOperatorParts(win, operator, nowSeconds)` (+ the `OperatorLoopFacts = { stale: boolean; lastTickAt?: number }` and `OperatorParts = { head: string; facets?: string }` types) → the L4 `opr` register. Monitored wins: `win.monitored === true` yields `head` = `watched · <monitoredStage> · tick <age> ago` (stage omitted when absent, tick omitted when `operator` is undefined or `lastTickAt` is 0/absent) with `facets` = `<monitoredRepo> · <monitoredBranch>` (empty segments omitted, undefined when both absent); an unmonitored window with `win.owner === "operator"` yields exactly `{ head: "done · operator-touched" }` — no facets, no tick segment, the `operator` input ignored; anything else is `null`. The tick age uses the shared `formatDuration` from `@/lib/format`; `nowSeconds` is passed in like `getOutputLine` — the resolver holds no clock; `operator.stale` is consumed verbatim (and applies only to the watched branch — the done head is never stale). Consumed by the PANE panel (inline facets) and the row flyout card (facets on a continuation line). (0536) (hzih)

- `getTmxLabel(win)` → the `tmx` identity-row label — the active pane's id leads: `%107` for a one-pane window, `%109 · 3/3` for multi-pane, the ordinal only disambiguating. Not a register (pane metadata) but shared for the same reason: three consumers (the PANE panel's `WindowContent`, the status bar's left-cluster `tmx` segment, and the status bar's overflow `tmx` row) render one string. The ordinal is the active pane's 1-based position in `win.panes` (`findIndex(isActive) + 1`), never `paneIndex + 1` — `paneIndex` is tmux's `#{pane_index}`, which already honours `pane-base-index`, so re-offsetting it would read `2/1` for a single pane on a base-index-1 server. The id segment comes only from the active pane — consumers copy `activePane.paneId`, and the label never shows an id nothing copies — so with no pane marked active or an empty active `paneId` the id and its ` · ` separator are omitted and the ordinal falls back to 1 (`1/3`); a single (or zero) pane with no id yields the empty string, and both surfaces render the row passive in that case.
- `splitDatePrefix(branch)` → `{ prefix, rest }`, splitting a leading fab-style `^\d{6}-` date prefix from the branch (`prefix` empty when absent), so the PANE panel's `git` row and the status bar's `⑂` segment dim the least scannable part of the branch from one regex. Copy values always use the full branch, never the split.

Consumers own their own PRESENTATION — prefixes, icons, continuation lines, truncation, copy/open interactions — and share only the strings, segments and parts. Every surface composes the `fab` register from `getFabParts` (so the state token can carry its hue and the slug can drop when the branch carries it); the PANE panel composes `pr` from `getPrParts`, the other surfaces consume the joined `getPrSegments`; `opr` is consumed as parts on both the panel (facets inline) and the card (facets on a continuation line). Covered by `registers.test.ts`; `status-panel.test.tsx` covers the panel's rendered register lines. (93dy)

### Shared PR vocabulary — `pr-status-model.ts`

The module `pr-status-model.ts` carries no `PrStatusLine` component — it is the single source of the shared PR **color vocabulary** AND the lifecycle **status-dot model** (below), imported by `status-dot.tsx`, `status-dot-label.ts`, `sidebar/registers.ts` (the shared register resolvers), `sidebar/window-row.tsx` / `session-tiles/session-tiles.tsx` (the rest-state PR glyph's gate + color on both surfaces), and — for `FAB_STATE_COLORS`, the `fab` register's state-token hue — all three register surfaces (`sidebar/status-panel.tsx`, `sidebar/row-flyout-card.tsx`, `status-bar.tsx`), plus its own unit test (`pr-status-model.test.ts`). The PR text detail lives in the register resolvers, rendered by both the PANE panel's L3 `PR` register (`getPrParts`) and the row flyout card (`getPrSegments`, § Row-hover register flyout card). (260715-jykd) (93dy)

**Module surface** (colocated in `pr-status-model.ts` — all `export`ed except the file-private `hasFreshAgent`, an internal helper to `statusDotState`):

- **PR color vocabulary**: `PR_STATE_COLORS`/`PR_CHECKS_COLORS`/`PR_REVIEW_COLORS` (the per-segment GitHub-state color maps, consumed by the L3 register resolver in `sidebar/registers.ts`), `isFailish(win)` (`prChecks === "fail" || prReview === "changes_requested"` — the single fail predicate), and `FAB_STATE_COLORS` — the fab displayState → hue map, keyed by the backend display-state vocabulary (`active | ready | pending | done | failed`, `api/sortwindows.go`): `active`/`done` → `text-accent-green` (running or landed), `ready`/`pending` → `text-signal-yellow` (waiting on a gate), `failed` → `text-signal-red`; an unknown state renders the token with no extra class (`FAB_STATE_COLORS[state] ?? ""`). The `fab` register's state token renders through it on all three register surfaces.
- **Row PR-glyph helpers**: `prOwnsGlyph(win)` (`!!prNumber && (prState === "open" || prState === "merged" || prState === "closed")` — a positive allowlist: an unknown/absent `prState`, the branch channel's unconfident `""` fallback, never owns) is **exported** — the gate for the rest-state PR glyph on the sidebar window row AND the session-tile window row (§ Window rows, § Session Tiles); it gates only the glyph, never any dot tier. `prGlyphColor(win)` returns the glyph's color token from the same vocabulary as a **six-way** first-match-wins chain: `text-signal-red` for **closed** (GitHub's closed red — the same token `PR_STATE_COLORS.closed` paints the register segment, so glyph and text agree; closed sits above fail because a closed PR's checks/review are historical noise and a closed PR with passing checks must not fall through to green), then `text-signal-purple` for **merged** (a landed PR — the same historical-noise rationale puts merged above fail too), then `text-signal-red` when `isFailish(win)`, then `text-text-secondary` for an **open draft** (`win.prState === "open" && win.prIsDraft`), then **`text-signal-yellow` for open with `prChecks === "pending"` (checks running)**, then `text-accent-green` for open otherwise (checks pass or no decisive signal). **Fail sits above draft**: a draft with failing checks or changes requested reads red — `isFailish` dominates every open case. **Draft sits above pending**: drafts stay muted even while their checks run — pending would un-mute them. The draft branch is **gated on `prState === "open"`**, which keeps the closed path untouched *by construction* rather than incidentally (a closed draft reads closed, since the closed branch matches first; merged is already returned above it). Draft is the only gray glyph state. **Shape carries what color cannot**: `prGlyphIcon(win)` (exported from `sidebar/icons.tsx`, the single state→icon selector consumed by the window row's fine overlay, its coarse rail slot, and the session-tile header) picks the ✕ `GitPullRequestClosedIcon` for closed FIRST, the dotted-rail `GitPullRequestDraftIcon` for `open && prIsDraft`, and the arc `GitPullRequestIcon` otherwise — so closed and failing (both red) separate by shape, closed and draft separate by color, and draft and open separate by shape as well as color. A closed draft reads closed in both channels. No new color system, no new hex: `text-text-secondary` is the established inert/no-journey token (`PHASE_HUE.none`), the closed red is `PR_STATE_COLORS.closed`, and the pending yellow reuses `PR_CHECKS_COLORS.pending`'s token choice. **Draft, checks-pending, merged, and closed are glyph-only distinctions** — the dot renders no PR state at all (the local/remote split, § Status Dot). (93dy) (e30p) (aqo6) (xuej) (lvvw)
- **Status-dot model**: the compositional dot model (aqo6; shape channel 18ot): `DotShape` (`"ring" | "solid"` — liveness only), `DotPhase` (`"building" | "prReady" | "agent" | "none"`), `StatusDotState = { phase: DotPhase; shape: DotShape; failed?: boolean; waiting?: boolean }` (two additive overlay flags), `fabPhase(stage)` (the stage-based two-stop split), `hasFreshAgent(win)` (file-private), `PHASE_HUE` (phase→hue token map), and the two-family `statusDotState(win)` — shape derived per family from liveness, no PR branch (see § Status Dot for the ladder + the local/remote split).

### Status Dot (`status-dot.tsx`) — compositional two-family ladder + additive overlays

> Spec: `docs/site/status-dot.md` (+ `docs/img/status-dot-reference.svg`) is the canonical reference — small legend strips (hue / shape / glyph / overlays), one per channel, replace precedence prose + a per-cell matrix. Design authority: `docs/specs/status-pyramid.md`; the watched-underbar placement study is `docs/wiki/watched-row-indicator-studies.html` (indexed in `docs/specs/index.md`).

> Detail surface: the dot is a **pure decoration** — no native HTML `title`, no `tabIndex`, no per-dot hover-card of its own. The hover/focus detail surface is the sidebar row's flyout card (§ Row-hover register flyout card). (93dy)

`StatusDot({ win, watched }: { win: WindowInfo; watched?: WatchedFlag })` (`app/frontend/src/components/status-dot.tsx`) is the **one** dot reused on all three surfaces — the sidebar window row (leading position, the row's primary status signal beside the owned-PR rest glyph — see § Window rows / Row Minimalism), the `SessionTiles` window tile, and the pane-panel header. It is a **first-class consumer of `agentState`**, using **TWO orthogonal visual channels PLUS THREE additive overlay flags**: **core hue = phase** (which journey + position in it), **shape = liveness** (work happening NOW vs at rest — the SAME meaning in every hue, fully compositional), **`failed` → an additive red-center overlay** (the only dot-red — see § Failed red-center overlay below), **`waiting` → a ladder-exempt additive yellow halo** (see § Waiting halo below), and **`watched` → an additive neutral underbar** (see § Watched underbar below). (260615-0hsz) (260706-y1ar) (aqo6) (18ot) (0536)

**The local/remote split** — the ownership rule the vocabulary rests on: the **dot tells the LOCAL story** (what runs in this pane: which journey, is it healthy, does it need me); the **glyph tells the REMOTE story** (the branch's PR on GitHub — § Rest-state PR glyph). The dot renders no PR state in any family — no purple, no orange, no PR shapes; `statusDotState` consults no PR field. A window's PR still shows everywhere derivation reaches — the rest-state glyph on the row and the session tile, the PANE panel's L3 register, and the flyout card's "Open PR" link (Principle X: derivation is universal) — just never on the dot. (aqo6)

**Ladder — two families joined at the top** (`statusDotState(win)` in `pr-status-model.ts`). First precondition wins for the core hue; shape is liveness, derived per family; `failed` (`fabDisplayState === "failed"` on a fab-owned window) and `waiting` (`win.agentState === "waiting"`) are additive overlay flags computed independently and attached on every branch:

- **`fabChange` present (and `fabDisplayState !== "skipped"`) → cool family (fab pipeline):** `{ phase: fabPhase(win.fabStage), shape: win.agentState === "active" ? "solid" : "ring", failed: win.fabDisplayState === "failed" }` — blue `building` for intake·apply·review, green `prReady` for everything else; `fabDisplayState` contributes only the `failed` flag and the `skipped` gate, never the shape. (18ot)
- **no fab ownership but a fresh `agentState` → warm family (ad-hoc agent):** `{ phase: "agent", shape: agentState === "active" ? "solid" : "ring" }` (yellow — only a mid-turn `active` agent is solid; `waiting` and `idle` are both at rest → ring). (18ot)
- **neither → the gray L0 floor:** `{ phase: "none", shape: win.activity === "active" ? "solid" : "ring" }`.

A **`skipped`** `fabDisplayState` makes the window NOT fab-owned — the change has left its journey, so the ladder falls through (fresh agent → yellow, else the gray floor) rather than rendering any fab hue (§ Design Decisions → Skipped display-state falls through the whole ladder).

The result type is `StatusDotState = { phase: DotPhase; shape: DotShape; failed?: boolean; waiting?: boolean }`. `hasFreshAgent(win)` is `agentState ∈ {active, waiting, idle}` — #314 already clears stale/shell-reconciled values server-side (the reconciler + rollup omit a plain-shell pane), so a non-empty rolled-up `agentState` on the window IS fresh; no client-side staleness heuristic (R4).

**Waiting halo — additive attention overlay, ladder-exempt** (R2): when `state.waiting`, `StatusDot` appends the `rk-waiting-halo` class to the dot element — a **pulsing yellow ring** layered around it, carried by a `::after` pseudo-element (`.rk-waiting-halo { position: relative }` hosts it; `.rk-waiting-halo::after` paints it: a 1.5px border in `var(--color-signal-yellow)` at its 85% peak, `inset: -2.5px` so the ring sits flush OUTSIDE the dot's 1.8px border — an absolutely positioned pseudo anchors to the padding box — `border-radius: inherit`, `pointer-events: none`), animated by the `@keyframes rk-waiting-halo` in `globals.css` over `transform: scale(1 → 1.3)` and `opacity 0.65 → 1` (1.4s ease-in-out infinite) so it runs on the compositor — the semantic is constant (yellow = "needs you now" in every theme) while the value re-themes: dark `#facc15`, light `#b07d02` gold, `ui/visual-design.md` § Design Decisions → Signal hues are per-theme tokens). It is **ADDITIVE** — the core hue AND shape are untouched (a blue building dot keeps its blue core; a failed dot keeps its red-center flag). NEVER a hue-flip — family identity must survive attention. The class rides the dot element itself (the absolutely positioned ring renders outside the dot's box, disturbing neither size nor hue). Under `prefers-reduced-motion` the halo is a **static 2px full-yellow ring** (`inset: -3px`, `animation: none`). A waiting agent renders the RING base under the halo — blocked is at rest by definition (§ Design Decisions → waiting = ring + halo). The glance rule: **blue = still cooking, green = out the door, yellow core = my ad-hoc agents, gray = just a terminal, yellow HALO = needs me now, red CENTER = the pipeline failed here.** (18ot)

**Watched underbar — additive relation overlay, sidebar-row-only**: when the mount passes the optional `watched?: WatchedFlag` prop (`WatchedFlag = { stale: boolean }`, exported from `status-dot-label.ts` and re-exported by `status-dot.tsx` for the same no-import-cycle reason as `dotLabel`) — today only the sidebar window row, for non-ghost windows with `win.monitored === true` — the dot element is wrapped in a `relative inline-flex items-center justify-center shrink-0` span with a sibling bar after it: `absolute left-0 right-0 h-px text-text-secondary` (dot-width — 7px under an unflagged dot, 9px under a flagged one), painted from `currentColor` via the `rk-watched-underbar` utility in `globals.css`, at `-bottom-[4px]` under the 7px dot and `-bottom-[3px]` under the 9px flagged dot (the watched footprint stays ~12px tall either way, clear of the waiting halo ring's ≈3px reach; the wrapper carries no overflow rule because the halo's pseudo ring paints outside the dot's box). The ink is **neutral in every state** — never `accent-green`, never the phase hue, selected rows included — so it can never be misread as journey; above/below the dot is the one free geometric slot (the halo owns the perimeter, the red center the middle). **Stale** (the operator loop's tick is overdue — `watched.stale` read verbatim from the server-derived `ProjectSession.operatorStale`, never recomputed client-side) adds `opacity-50` + the dashed `rk-watched-underbar-stale` utility (a `repeating-linear-gradient` 1px-on/2px-off pattern, so staleness is never encoded in opacity alone) + `data-stale="true"`; both utilities are static — no animation, nothing to zero under reduced motion (one audit-list line in the `prefers-reduced-motion` block). The bar is `aria-hidden` decoration with no hit target of its own (`data-testid="status-dot-watched-bar"`); the dot keeps `role="img"` + the `aria-label`, which grows a trailing `— watched` clause (§ Accessibility). When `watched` is undefined the component renders EXACTLY its base form (no wrapper, no bar) — every non-sidebar mount (the SessionTiles window tile, the pane-panel header, the status bar, the tty tile header) passes nothing and is byte-identical. (0536)

**Hue = phase** — four hues (spec § The Channel Model). `fabPhase(stage)` is the **two-stop split**: `intake`/`apply`/`review` → `building` (local work in progress); everything else — `ship`/`review-pr`/`done`, plus unknown/absent (`hydrate` lands here via the default arm) → `prReady` (local work complete, "PR is ready"). The split is **stage-based, never `prNumber`-based** — the dot must not consult PR fields; alignment with PR existence stays emergent, since `/git-pr` creates the PR mid-ship. `DotPhase = "building" | "prReady" | "agent" | "none"`. `PHASE_HUE: Record<DotPhase, string>` maps phase→core-hue token:

| Phase (`DotPhase`) | Family / source | Hue token |
|--------------------|-------------------|-----------|
| `building` | cool fab — intake · apply · review | `text-signal-blue` |
| `prReady` | cool fab — ship · review-pr · done (+ unknown/absent stage) | `text-accent-green` |
| `agent` | warm ad-hoc agent | `text-signal-yellow` |
| `none` | gray L0 floor (no journey) | `text-text-secondary` |

> **Why exactly two fab hues**: blue vs green answers "still cooking vs out the door" at a glance — the one pipeline distinction worth a hue on a 7px dot (the exact stage lives in the `fab` register on both register surfaces). Purple and orange are not dot hues — purple stays in the glyph/segment vocabularies. The maximal one-fab-hue reduction was rejected: it loses the building/PR-ready glance. (aqo6)

**Shape = liveness** — ONE vocabulary, two shapes, the same meaning in every hue, rendered by `StatusDot` from `{phase, shape}` with `color = PHASE_HUE[state.phase]` always (no per-shape color forcing); the overlay flags (`failed`, `waiting`) layer on top: (18ot)

| Shape (`DotShape`) | Meaning | Per-family source | Rendering |
|--------------------|---------|-------------------|-----------|
| `solid` | work happening NOW | journey hues (blue · green · yellow): the rolled-up `agentState === "active"` (mid-turn); floor: `activity === "active"` | filled circle (`backgroundColor: currentColor`, `border: none`) in phase hue |
| `ring` | at rest (no live worker · idle agent · waiting agent · parked done · quiet shell) | journey hues: `agentState` `waiting`/`idle`/absent-or-stale; floor: quiet | hollow circle, `1.8px solid currentColor` border in phase hue, transparent fill |

The shape source is **per-family**: journey hues read the window's rolled-up `agentState` ONLY — absent/stale ⇒ ring; the output-flowing L0 `activity` fallback is the gray floor's ALONE (a dev server flowing output in a fab worktree renders ring, never solid — § Design Decisions → Shape source is per-family). `agentState` is PID-reconciled server-side, so a solid cannot outlive its process — but solid is not proof of progress: a live-but-wedged agent stays solid until the reserved `stuck` overlay exists (accepted residual, documented not fixed). Both shapes render at one uniform 7px footprint (`DOT_SIZE = "w-[7px] h-[7px]"`). (18ot)

**Failed red-center overlay — additive failure flag, not a shape**: `StatusDotState.failed` is true iff the window is fab-owned and `fabDisplayState === "failed"`; it composes with EITHER shape (failure and liveness are orthogonal). Flagged dots render at a larger **9px footprint** (`FLAGGED_SIZE = "w-[9px] h-[9px]"`) with the ~3px `bg-signal-red` center (`RED_CENTER`) so failure salience never drops: over a **ring** — the standard hollow ring with the red center inside ("failed, nobody on it — act"); over a **solid** — the **bullseye**: 9px fill in the phase hue → 6px `bg-bg-primary` gap circle → 3px red center, cutting a dark gap ring between fill and center so failure changes the SILHOUETTE and is never color alone ("failed, rework live"; the gap circle uses the shell ground token so it re-themes with the mounting surfaces). (18ot)

**Red — the honest split**: DOT-red appears in exactly one way — the small red center of a flagged (`failed`) dot (no whole-dot red tint). The row GLYPH separately uses red for a failing PR — that is the glyph channel's vocabulary, not the dot's.

**Gray L0 floor** (`phase: "none"`, lowest precedence, no fab ownership + no fresh agent) is **monochrome gray** — color is reserved for the two journeys: `activity === "active"`→gray `solid` filled circle, else gray `ring`. No phase hue is ever applied here.

**Composed examples** (rows = phase/hue, cols = liveness/shape). The **waiting halo, the red-center flag, and the watched underbar overlay ANY cell** — they are additive overlays applicable to every tier, not matrix rows (the underbar mounts on the sidebar window row only). A parked-done change is "green + at rest" — the resting green ring (journey complete; its green hue says "done", the merged glyph says how it ended). (18ot)

| Phase (hue) | ring (at rest) | solid (live) | + failed overlay |
|-------------|----------------|--------------|------------------|
| building (blue) | blue ring (no live worker / idle / waiting) | blue solid (worker mid-turn) | blue ring + red center (review failed — act) / blue bullseye (rework live) |
| PR-ready (green) | green ring (idle / **parked done**) | green solid (worker mid-turn) | green ring + red center (review-pr failed — act) / green bullseye (rework live) |
| agent (yellow) | yellow ring (idle / waiting) | yellow solid (mid-turn) | — (the flag is fab-owned only) |
| plain (gray floor) | gray ring (quiet) | gray solid (output flowing) | — |

**Accessibility** — every dot carries `role="img"` + `aria-label` composed from journey + liveness + **additive flags**, never color alone (colorblind a11y + Constitution V). `role="img"`/`aria-label` are the accessible name and the dot's ONLY a11y surface: it carries **no `tabIndex`** — the row treeitem is the focus target, and focusing it opens the flyout card (§ Row-hover register flyout card). `dotLabel(win, state, watched?)` lives in its OWN module `status-dot-label.ts` (`status-dot.tsx` re-exports it, keeping its public surface stable). It composes a **core label + additive suffixes** in overlay precedence order (`coreLabel`, then the `state.waiting` attention suffix, then the `watched` relation suffix) — a pure function of what the dot shows (hue word + liveness word + flags): (260706-y1ar) (aqo6) (18ot)
- **fab tiers** (keyed on `phase ∈ {building, prReady}`, so a fab window whose `skipped` display-state fell through the ladder reads its floor/agent word — matching the dot it actually renders): the hue word (`FAB_PHASE_LABEL`: `building`→"building", `prReady`→"PR-ready") + a liveness word via `fabLivenessWord(state)` — derived from shape + the failed flag, NOT from `fabDisplayState`: `solid`→"worker live", `ring`→"at rest", flagged `solid`→"failed — rework live", flagged `ring`→"failed — at rest" — e.g. `"building — worker live"`, `"PR-ready — at rest"` (a parked-done change reads exactly this), `"building — failed — rework live"`. NO PR words, no raw stage word, no displayState words — PR facts live in the glyph + register surfaces, the exact stage in the `fab` register. (18ot)
- **warm agent tier** (`phase === "agent"`): agent-native words via `AGENT_SHAPE_LABEL` — the `ring` reads **"idle"** and `solid` reads "active" — e.g. `"agent — active"`, `"agent — idle"`. A waiting agent renders the ring and reads `"agent — idle"`; the additive waiting suffix carries the attention. (18ot)
- **L0 floor**: the bare tmux activity word (`"active"`/`"idle"`).
- **Waiting suffix**: when `state.waiting`, append `" — agent waiting {dur}"` (duration from the rk-computed `agentIdleDuration`, populated for `active` too but rendered only for the two rest states) — so a review-failed waiting window reads `"building — failed — at rest — agent waiting 3m"` (R3). (18ot)
- **Watched suffix**: when the `watched` flag is passed, append `" — watched"` (or `" — watched (operator stale)"` when `watched.stale`) AFTER the waiting suffix — a watched, waiting, stale-loop agent reads `"agent — idle — agent waiting 3m — watched (operator stale)"`. The exact monitored stage lives in the `opr` register, not the label (the same rule the fab stage word follows); no clause when `watched` is undefined, so unwatched mounts' labels are unchanged. (0536)

**Impl symbols** — in `pr-status-model.ts` (colocated, see § PR Status exports): `DotShape` (`"ring" | "solid"`), `DotPhase` (`"building" | "prReady" | "agent" | "none"`), `StatusDotState = {phase, shape, failed?, waiting?}`, `fabPhase`, `hasFreshAgent` (file-private), `prOwnsGlyph`, `prGlyphColor`, `PHASE_HUE`, and the two-family `statusDotState`. > **No PR maps on the dot.** The dot renders from `PHASE_HUE` + the label maps only. `isFailish`/`PR_STATE_COLORS`/`PR_CHECKS_COLORS`/`PR_REVIEW_COLORS` serve the glyph color chain and the Pane-panel L3 `PR` register segments (see § Shared PR vocabulary); none of them is consulted by `statusDotState`.

**Why this shape** (design decisions): (1) two families let a glance separate "my fab pipeline" (cool blue→green) from "my ad-hoc agents" (warm yellow) from "just a terminal" (gray) — the user's own two-journey framing; the blue/green two-stop encodes the one pipeline distinction worth a hue (still cooking vs out the door). (2) shape meaning is uniform across every hue — liveness, fully compositional, so the doc needs small legend strips instead of a per-cell matrix; a parked-done change is simply "green + at rest" (the resting ring), no dedicated square shape. (3) the three additive overlay flags keep family identity intact when it matters most — the yellow halo for attention (§ Design Decisions → Waiting attention is an additive halo, never a hue-flip), the red center for failure (§ Design Decisions → Failure is an additive red-center overlay, not a shape), and the neutral underbar for the operator-watchlist relation (§ Design Decisions → Watched is an additive overlay, never a hue or a shape), so "failed, rework live" (bullseye) and "failed, nobody on it — act" (ring + center) are distinct at a glance. (4) keeping PR off the dot avoids double-encoding with the row glyph (one fact, one channel — a merged PR reads purple once, on the glyph) and keeps new PR-adjacent states (draft, checks-pending) from pressuring the dot — see § Design Decisions → PR is evicted from the dot. (260706-y1ar) (aqo6) (18ot)

### Row-hover register flyout card (`sidebar/row-flyout-card.tsx`)

The sidebar's **tier-2 hover-card** system — the app's status-detail hover surface: ONE shared card shell, the `useRowFlyout` hook (placement arms, the `size()` containment cap, the held-state key, portal/focus wiring, the notch) parameterized by a per-mount `content` render prop, consumed by FOUR mounts — the window row, the session row, the server-group header, and the TMUX SERVERS panel tile (§ Design Decisions → One card shell, four mounts). The card is built on `@floating-ui/react` with **pointer-conditional placement** — on FINE pointers it opens on **whole-ROW hover** at a **fixed x** (the sidebar's right edge, `placement: "right"`); on COARSE pointers it anchors **below the row** (`bottom-start`, `top-start` fallback) with its width capped short of the row's 56px status rail so the finger's column stays visible and touchable mid-scrub. On the three rail-bearing tiers (window, session, server-group header) it is the single surface for all three triggers — fine-pointer row hover, keyboard row focus (the roving-tabindex treeitem, Constitution V), and coarse-pointer touch (the status rail is the sole tap/scrub target — press opens and a held slide scrubs the card across rows) — so status detail stays reachable by pointer, keyboard, and touch alike. The TILE mount is **fine-pointer-only** (`suppressed: coarse || showColorPicker`) — it has no rail and no coarse trigger; the coarse server surface stays the sessions-pane header card — and it is the one **edge-anchored** mount (`edgeAnchor: true`): tiles are multi-column grid cells, not full-bleed rows, so "right of the reference" would land mid-panel on top of sibling tiles; the opt-in positions the card against a virtual reference (the tile's y-band at the sidebar root's right x) so it opens at the sidebar's right edge exactly like the row cards, and blocks pointer events inside the hover-close polygon so a sibling tile crossed en route to the card cannot hover-steal the single-open card (a pointer that STOPS on the sibling still retargets — a stalled pointer collapses the polygon and its own hover-open fires, instantly while warm). The row is a large forgiving target where the 7px dot was a precise one, and on fine pointers the fixed x means the card never jitters under the pointer. (93dy) (ys3q) (b8eu) (260817-ve5m) (260903-1ldw)

**Wiring** — `useRowFlyout({ suppressed, content })` returns `{ setReference, referenceProps, card, open, openNow, close }`; each consuming row attaches `setReference` + spreads `referenceProps` on its **root element** (the floating reference is the ROW/tile, not the mouse and not the dot) and renders `{flyout.card}` as its last child. Under `edgeAnchor` the hook splits events from position: `setReference` keeps hover/focus/dismiss on the real node and installs `refs.setPositionReference` with the `edgeAnchorReference` virtual element — the node's y-band at a degenerate width-0 x on the sidebar root's right edge (`EDGE_ANCHOR_CONTAINER_SELECTOR` = `nav[aria-label="Sessions"]`, resolved per measuring pass via `closest()` inside `getBoundingClientRect`, never lifted state; no container ancestor ⇒ fall back to the node's own rect), with `contextElement` set so `autoUpdate` observes a real node. The card's body is the **`content({ close })` render prop**, built ONLY while the card is open (the mount-only-while-open perf contract) — `close` lets action rows run the close-then-open popover handoff; the window mount passes `<WindowFlyoutContent …>` (registers + links + action rows), the session mount passes its own title/facts/action content, and both server mounts pass the shared `ServerCardContent` (below). `useFloating` reads `useCoarsePointer()` itself and branches: FINE — `placement: "right"`, middleware `offset(6)` / `flip()` / `shift({ padding: 8 })` / `size()` (a symmetric inline-max-width reset) / `arrow()`; COARSE — `placement: "bottom-start"`, middleware `offset(6)` / `flip({ fallbackPlacements: ["top-start"] })` (near the drawer bottom) / `shift({ padding: 8 })` / **`size()`** / `arrow()`, where `size()` caps the card's max-width at reference-width − `STATUS_RAIL_WIDTH_PX` (56, exported from this module) − 8px gap, floored at 120px — the containment invariant: the card's right edge stops BEFORE the rail column and never renders off-screen. Shared: `strategy: "fixed"`, `whileElementsMounted: autoUpdate`, `FloatingPortal` to `document.body` (escaping the sidebar's `overflow:hidden` clip). Interactions: `useHover` (`mouseOnly: true` so touch never hover-opens, `move: false`, function-form `delay`, `handleClose: safePolygon()` — the bridge letting the pointer travel row → card to click a link; the edge-anchored tile mount passes `safePolygon({ blockPointerEvents: true })` instead), `useFocus`, `useDismiss` (Escape / outside press / blur) — hover/focus gated `enabled: !suppressed`. Deliberately **no** `useRole({ role: "tooltip" })` — the card holds real links (§ Design Decisions → No `role="tooltip"` on the status detail hover-card). Surface tokens are the shared ones (`bg-bg-card border border-border rounded-md rk-popup-elev`, monospace, `w-max`) — the shadow is the theme-aware `.rk-popup-elev` occlusion utility (two `--rk-popup-shadow-*` alphas with light overrides under `html[data-theme="light"]`; [visual-design](/run-kit/ui/visual-design.md) § Popup elevation shadow), not Tailwind's stock `shadow-lg`, and still no new color tokens; the `max-w-xs` cap is fine-pointer-only (on coarse the `size()` middleware owns the width). (nwz9)

**Delay + warm window + single-open** — `FLYOUT_OPEN_DELAY_MS = 500` cold; **0 while the cluster is warm**, where warm = another card is open right now OR one closed under `FLYOUT_WARM_WINDOW_MS = 500` ago. So sweeping the pointer down the tree retargets instantly instead of strobing. The cluster state is **module-scoped** (`activeFlyout` + `lastClosedAt`, plus a `resetFlyoutWarmState()` test seam), NOT React context — see § Design Decisions → Flyout warm window is module state, not a nested `FloatingDelayGroup`. `flyoutOpenDelay()` is handed to `useHover` in **function form**, evaluated at event time, so warmth set by another row is seen without a re-render. `activeFlyout` also enforces **single-open**: opening closes any other open card. `lastClosedAt` is stamped only when the closing flyout was the active one, so a no-op close (a drag-start before the delay elapsed, or a close racing another row's open) never falsely arms the warm window; an unmount-while-open releases the coordinator the same way.

**Suppression** — `suppressed` (the window row passes `ghost || showPinPopover || showLabelPicker`; the session row `ghost || showColorPicker`; the server group `showColorPicker`; the server tile `coarse || showColorPicker` — the coarse half makes the tile mount fine-pointer-only, keeping the sessions-pane header card as the coarse server surface) closes an open card and disables the hover/focus triggers, so the card never fights the row's other layers. The imperative `openNow()` honors the same gate with an early return. A drag start calls `flyout.close()` from the row's `onDragStart`.

**Slide-to-scrub (coarse pointers)** — every rail-bearing tier spreads the single `useRailScrub` handler trio onto its 56px status rail (the server tile has no rail and registers no scrub target). `pointerdown` stops propagation, opens the flyout, and captures the pointer; `pointermove` hit-tests `RAIL_ROW_SELECTOR = "[data-rail-row]"` through the module-scoped scrub registry and retargets the single-open card across registered window, session, and server rows. Gaps and unregistered rows leave the current card open. Release keeps the last card open; outside press dismisses it. The gesture never selects, navigates, or starts HTML5 row drag.

**Held-rail highlight (all rail-bearing tiers)** — while a row's card is open (tap-held or mid-scrub) that row's rail lightens: the band steps up one shade via `railHeldBand` (a deeper `color-mix` share of the tier's step-up shade — the hover tint, or the selected tint on an already-selected row) and the seam brightens to `RAIL_HELD_SEAM` (`var(--color-text-secondary)` — an existing token, brighter than `--color-border`); no highlight at rest. Rest bands derive per tier via `railRestBand` (the inset base mixed with the tier's rest tint — session `tint.base`, server header base/selected, the selected window row's selected shade; untinted window rails keep the plain `bg-bg-inset` class). The key is the row-local `flyout.open` state — the same key the window row's held hover-shade uses — so the highlight travels row-to-row with the single-open card during a scrub (retargeting closes one row's card and opens the next's). No new color tokens anywhere in the rail system. (260817-ve5m)

**Focus management** — the card is wrapped in `FloatingFocusManager` with `modal={false}` and `order={["reference", "content"]}`, which is what makes `FloatingPortal` render its tab-order guards so **Tab walks row → card links** in tree order. Two non-default settings are load-bearing: `initialFocus={-1}` (the manager's default would move focus to `order[0]` on open — a hover-open must never steal focus from the terminal) and `returnFocus` gated on a `focusInsideCard` flag set by an `onFocusCapture` on the card (the default returns focus even when nothing inside was focused, which on a hover-sweep close yanks focus to the just-left row's button and breaks the warm retarget). The flag resets on each fresh open via an effect keyed on the real `open` state — not inside `onOpenChange`, because `useFocus` re-fires `onOpenChange(true)` for every `focusin` bubbling from the portalled card through the React tree, and a reset there would batch with the capture-phase set and negate it. Escape-dismiss and the tree's arrow-key nav are unaffected: focus stays on the row until the user tabs in.

**Content** — the window card's body is the **`fab`, `pr`, and `opr` registers plus the `note` line**, composed from the SHARED `sidebar/registers.ts` module (`getFabParts` / `getOperatorParts` as parts, `getPrSegments` as the joined `pr` line) (§ Register resolvers), so the surfaces cannot drift. The `out`/`agt` registers and the dot-label line are not rendered — the row already carries the window name, the status dot, the PR glyph and the colour label, so those lines would restate it (§ Design Decisions → The card says only what the row cannot). When a window has no change, no PR, no note, no watchlist join, and no owner (`fabParts`, `prSegments`, `win.note`, `win.monitored` all empty and `win.owner` unset) the card renders **no body block at all** — a real absence guarded by `hasBody` (`fabParts || prSegments || win.note || win.monitored || win.owner === "operator"`), not an empty wrapper, because an empty flex container would still contribute the card's `gap` and leave a visible dead strip between title bar and action rows. A bare `prUrl` with no `prNumber` renders nothing and does not count as content. No group headings — with one register group left there is nothing to separate. Around the body:

- **Title bar** — the card's first element is an **identity title bar** rendered through the shared `PopupTitleBar` (`sidebar/popup-title-bar.tsx` — the one chrome carrier of the popup grammar "title bar = identity, body = facts", § Tooltips — Two-Tier Taxonomy): a full-bleed `bg-bg-inset` strip (negative margins cancel the card's `px-2 py-1.5` padding), `border-b border-border`, top corners rounded into the card radius. The title is `Window @N · pane %N · N panes` (`WindowFlyoutTitle`) — the tmux window id and the ACTIVE pane's id in primary text, the literal words in secondary (`PopupTitleBarSecondary`); static text derived from the already-passed `win`, degrading by omission (no `panes` → `Window @N` alone; `1 pane` singular). The bar's `right` slot carries ONE affordance: the quiet circled-(i) **docs link** (`STATUS_DOT_DOCS_URL` → the `docs/site/status-dot.md` GitHub blob; `docs/site` is not served locally, matching the `NOTIFICATIONS_HELP_URL` convention) — actions live in the sectioned action rows at the card's bottom (one affordance, one home). All card affordances `stopPropagation` on click. The `FloatingArrow` notch fill is axis-dependent (`notchFill` against `POPUP_TITLE_BAR_HEIGHT_PX`, both exported from `popup-title-bar.tsx`): on a SIDE placement (fine pointers) the arrow middleware's resolved `y` decides — `bg-inset` while it sits inside the title-bar band, `var(--color-bg-card)` (the card-surface fill) below it; on the coarse BOTTOM placement the arrow sits on the card's TOP edge, always inside the full-width title band (inset fill); flipped to TOP it sits on the bottom edge in the action area (the same `bg-card` fill) — notch + bar read as one shape either way. (xb77) (b8eu)
- **Register + continuation lines** — `RegisterLine` renders a fixed-width prefix + read-only content, prefixes `"fab "`, `"pr  "` (2-char key + 2 NBSPs = the same 4-advance column, written as escapes so a careless re-encoding can't mojibake them; codepoints pinned by a unit test), and `"opr "`. Each line carries `min-w-0 truncate`, matching the PANE panel rows, so long `fab`/`pr` text ellipsizes inside the card's width cap (`max-w-xs` on fine pointers, the `size()` rail cap on coarse) instead of painting outside the card. Critical tokens lead; long values continue on a `ContinuationLine` — `pl-[4ch]` (the same 4-advance prefix column) in `text-text-secondary`, truncating harmlessly because the register's decisive tokens already lead. The `fab` register leads with `id · stage[ · displayState]` in primary text, the displayState token coloured via `FAB_STATE_COLORS` (unknown state ⇒ no extra class); the slug follows on a continuation line only when `getFabParts(win, branch)` returns one — the card passes the active pane's `gitBranch`, so when the branch carries the change the slug is `undefined` and no continuation renders (the branch already shows it). The `pr` register renders as ONE line — every `getPrSegments` segment (`#N · state[ (draft)] · checks <c> · review: <r>`, `·`-joined, each with its vocabulary colour) inside the `min-w-0 truncate` span, the `↗` after it — so the anchor never spans two visual rows; only the `fab` slug and the `opr` facets ride continuation lines on the card (the PANE panel is the surface that splits `pr` across two lines — § `PR` (L3) register). The `opr` register is the LAST body register, after the `pr` block: a `RegisterLine` (`prefix="opr "`, `testid="row-flyout-opr"`) carries the head — `watched · <stage>[ · tick <age> ago]` for a monitored window, or `done · operator-touched` for an owner-only one — in `text-text-primary`, and a `ContinuationLine` (`testid="row-flyout-opr-facets"`) carries the `repo · branch` facets when present (watched head only). Stale (`operator.stale`, read verbatim — never recomputed) flips the watched head to `text-text-secondary` and marks the line `data-stale="true"` via `RegisterLine`'s `stale` prop (the NoteLine stale idiom — never opacity on the register); the done head is never stale — the card gates the flag on `win.monitored === true` (`oprStale`), so an owner-only window renders primary text with no `data-stale` even under `operator.stale`. Its input is the card's `operator?: OperatorLoopFacts` prop (`{ stale, lastTickAt? }` threaded from the row's session-facts props); the card reads `Math.floor(Date.now() / 1000)` once per render for the tick age — the card holds no clock, matching `NoteLine`. (0536)
- **Note line** — the body's first element is `NoteLine` (`data-testid="row-flyout-note"`): the window's `@rk_win_note` one-line status note plus its relative age — `note blocked on flaky e2e · 2h ago` (the `note ` prefix in secondary, the age via the shared `formatDuration`, `lib/format.ts`). **Staleness**: the age always renders next to the text, and a note older than `NOTE_STALE_SECONDS` (24h) renders **dimmed** (reduced-opacity secondary — faded, never hidden); notes never auto-expire or auto-delete client-side — only an overwrite or explicit clear removes one. An epoch-0 (tolerant-parse) note renders text-only, undimmed, no age. Degrade-to-absent: no `note` on the payload → no line, no reserved space. The card holds no clock — the age is as of the last SSE frame (the same render-performance contract as every other register line; the agent-side write itself rides the ~12s safety poll, while a UI write via `Window: Set note…` repaints immediately through the endpoint's hub wake). (260824-bb5n-tab-status-note)
- **Freshness line** — `checked Xs ago` via the `FreshnessLine` leaf (below), rendered as a continuation line inside the `pr` group and only when the `pr` register renders — a `prFetchedAt` with no `prNumber` renders nothing.
- **PR link** — the `pr` register's identity line is an anchor (`#N · state ↗`) whenever `prUrl` exists and `prNumber` is set (a bare `prUrl` with no number renders nothing — it is a link with no information attached), keeping its `href`, `target="_blank" rel="noopener noreferrer"`, `title`, `aria-label`, segment colours and `stopPropagation` (opening the PR never selects the underlying row). The anchor wraps the whole `pr` line; the freshness line continues as plain text outside it. **Fork affordance (`ForkActionRow`)** — the card's SECOND sectioned action row (after Change color…, § Action rows above), branching this window's agent conversation into a new window in the **same session and directory**. The glyph is a hand-built inline SVG (`ForkIcon`, a git-fork shape) per the card's stated convention (inline SVG renders without a patched terminal font and themes via `currentColor`). **Fix tab name affordance (`FixTabNameActionRow`)** — the card's THIRD sectioned action row (between fork and pin), asking the server's operator window to rename this tab from its transcript (the flyout arm of the operator actuation seam — [operator-actuation](/run-kit/operator-actuation.md), which owns the full contract). **Fork in-flight guard** — `ForkActionRow` owns its own `busy` state, so the flag is **leaf-scoped**: only the row re-renders while a fork is in flight, honoring the card's render-performance discipline. The guard is load-bearing rather than cosmetic — `onFork` POSTs a mutating endpoint that CREATES a tmux window, so N clicks would create N fork windows. `disabled={busy}` (the spawn dialog's idiom) plus an early `if (busy) return` in the click handler is the belt-and-braces; the flag clears on settle for **both** outcomes, so a failed fork stays retryable. A `mountedRef` guards the settle `setState`, because the card unmounts when the flyout closes and a *successful* fork navigates away — settle-after-unmount is the normal case here, not an edge one. The handler chain (`app.tsx` `handleForkWindow` → `Sidebar` → `WindowRow` → `useRowFlyout`'s options) returns the **already-error-handled** settle promise, never rejecting, which is what lets the row simply await it.

**Fork navigation on success** — `handleForkWindow` (`app.tsx`) calls `forkWindow(server, windowId)` and on success routes through the **shared `navigateToSpawnedWindow(srv, windowId)`**: same-server → `navigateToWindow` (inheriting the window-switch slide transition), cross-server → `navigate({ to: "/$server/$window" })` + close the mobile sidebar. A rejected fork raises an **error toast** carrying the server's message (`404` no forkable agent session, `400` a non-repo directory) rather than failing silently; there is no bespoke fork dialog (constitution §IV).

## Tooltips — Two-Tier Taxonomy

Tooltips are a two-tier system with a **hard boundary and no middle species** (§ Design Decisions → Two-tier tooltip boundary):

- **Tier-1 — `Tip`** (`components/tip.tsx`): **names a control**. One-line plain-text label + optional keycap chip (`kbd`) + optional dim modifier note. Carries the W3C tooltip pattern — `role="tooltip"` on the floating element, `aria-describedby` on the anchor while open. NEVER interactive content. This is the app-wide replacement for native `title=` on interactive chrome controls.
- **Tier-2 — hover-cards** (the sidebar row flyout card, § Row-hover register flyout card): hold a second line of **state** and/or **interactive content** (real `<a>` links). Deliberately role-less (§ Design Decisions → No `role="tooltip"` on the status detail hover-card). The flyout card is the single tier-2 surface per row on every pointer class: its `PopupTitleBar` + facts line carry the identity facts (ids, counts, paths, socket) and its body carries the registers, links, and action rows — one surface answers both the naming and the state question. (xb77) (260903-1ldw)

**Shared title-bar grammar** — every row flyout card renders its header through `PopupTitleBar` (`sidebar/popup-title-bar.tsx`), the single chrome carrier of the grammar "title bar = identity, body = facts": a full-bleed `bg-bg-inset` strip (negative margins escape the host card's `px-2 py-1.5` padding), `border-b`, rounded top corners, secondary-literal/primary-handle text slots (`PopupTitleBarSecondary`), and an optional right-edge cluster (only the window card uses it — the docs link). The tier weight distinction lives in the BODY, not the chrome: the window card's body is registers + links, the session/server cards' bodies are a facts line + action rows. The notch-fill seam is shared too: `notchFill(arrowY)` (vs `POPUP_TITLE_BAR_HEIGHT_PX`) gives every card's `FloatingArrow` the inset fill while it lands on the title band. The elevation shell is shared as well: the flyout card renders `bg-bg-card` + `rk-popup-elev` — the surface token the tier-1 `Tip` already uses, with one theme-aware occlusion shadow across the taxonomy ([visual-design](/run-kit/ui/visual-design.md) § Popup elevation shadow). (xb77) (nwz9)

**Promotion rule**: a tooltip that needs a second line of state or anything clickable is tier-2, not a fatter tier-1. Consequence at the `title=` migration boundary: native titles whose value is *state or a content reveal* rather than a control name stay native `title=` — they are neither converted to `Tip` nor promoted to new hover-cards. Left native by this rule: the PR-URL reveal and cwd reveal (`sidebar/status-panel.tsx`). (260722-73al) (xb77)

### Tier-1 `Tip` (`components/tip.tsx`)

`Tip` wraps a **single child element** and clones it with the floating reference props/ref merged (`useMergeRefs`) — **no wrapper DOM node** is added, so layouts and the top-bar overflow fit's hidden width-measurement probe are unaffected (§ Design Decisions → Clone-child reference API). Built on `@floating-ui/react` (already a dependency — the tier-2 hover-card uses it too). A falsy `label` renders the child untouched (the conditional-tooltip idiom, e.g. "Copy version", "Create a server first").

**Visual shell — "quiet card"**: `bg-bg-card`, 1px `border-border`, 5px radius, soft shadow, 11px mono, `text-text-primary` label. The floating element is `pointer-events-none` (tier-1 holds nothing interactive, so it can never intercept a click) and `max-w-[40ch]` + `whitespace-nowrap` + truncate backstop the one-line ≤40ch cap. Optional slots: a `note` (dim `text-text-secondary` modifier, e.g. "⇧click: force") and a `kbd` keycap chip (`bg-bg-inset`, 1px border with a 2px bottom edge for the "key" read, 3px radius, 10px type). The `kbd` value is a plain string prop, but **for a registry-bound action the call site resolves the HOST-EFFECTIVE chord** rather than hard-coding a chord: `useKeybindings()` → `byAction.get(actionId)` → `formatCombo({ code, tier }, host.platform)` when the binding is `enabled`, else `undefined` so **no chip renders** — a tip advertising a dead chord would lie (§ Keyboard Shortcuts → Palette hints applies the same rule to palette hints). This makes every such chip reflect overrides and per-platform tiers. Six `Tip`-chip call-site families resolve a chord this way: the top bar's Settings gear (§ Right cluster → Settings gear), the bottom bar's Compose `a▏` and palette `⌘K` chips (§ Bottom Bar), the Open and Split split-buttons' primary segments (§ Open split-button, § Split control), and the gui header fold's three zoom chips (the live `gui-zoom-in`/`-out`/`-fit` bindings — [lenses-and-layout](/run-kit/ui/lenses-and-layout.md) § GUI Surface → The header fold cluster); the chevron menu's Settings and Keyboard shortcuts rows apply the same derive-and-omit rule to their trailing `MENU_ROW_KBD_CLASS` keycaps (§ Right cluster → overflow chevron menu). The same derive-and-omit rule governs chord clauses in prose copy — placeholders and empty states (§ Education micro-copy). A **computed, non-registry** `kbd` string is correct only for a chord with **no registry binding** — the compose strip's submit + insert editing chords, which are focused-textarea keys the registry does not own. Those are still platform-correct without the registry: Send resolves through the shared `composeSubmitKeycap()` (`formatCombo({code:"Enter",tier:"cmd"}, detectPlatform())` → `⌘Enter` / `Ctrl+Enter`), while the strip's Insert chip carries the literal `Enter` (its Insert follows Enter; the Alt+Enter raw-insert chord lives in the tip's label text). The `tip.tsx` prop doc states this contract. (260801-mqim) (260802-lj98)

**Behavior contract** (user-approved design session):

- **Open delay** — 300ms on hover (`TIP_OPEN_DELAY_MS`); **0ms while the cluster is "warm"** (a sibling tip in the same group closed <500ms ago, `TIP_WARM_WINDOW_MS`) — macOS-menu sweep behavior. Delays ride `useDelayGroup`; outside any group the group context is `delay: 0`, so `Tip` falls back to its standalone 300ms open.
- **Warm clusters** — `TipGroup` (exported; a `FloatingDelayGroup` preset with `delay={{open: 300, close: 0}}`, `timeoutMs={500}`) wraps one chrome region: the top-bar's three regions (left breadcrumb cluster, center heading cluster, right control cluster — the latter contains the overflow menu and every registry control's popover), the sidebar root, the iframe URL bar, the gui tile header's fold cluster (sweeping the row opens each control's tip at 0 ms), and the compose button row. A single-tip region needs no provider.
- **Keyboard** — opens immediately on `:focus-visible` (`useFocus` `visibleOnly` default), never on mouse-down focus (Constitution V).
- **Dismiss** — pointer-leave, Escape (`useDismiss`), and activating the control (`referencePress: true` — the tip never sits over the click's result).
- **Touch** — suppressed under `pointer: coarse` (via `useCoarsePointer`). The child renders unchanged with no reference props, portal, or ARIA wiring — the control's `aria-label` carries the name (§ Design Decisions → Suppress-by-early-return on coarse pointers).
- **Placement** — per-site `placement` prop, default `bottom` (top-bar convention); bottom-of-screen strips pass `top`, sidebar rows pass `right`. `offset(6)` / `flip()` / `shift({padding: 8})` / `autoUpdate` — the shared hover-card middleware set — flip and shift at viewport edges.
- **Reduced motion** — trivially satisfied: no fade, instant show/hide.

Named constants carry every magic value: `TIP_OPEN_DELAY_MS`, `TIP_WARM_WINDOW_MS`, `TIP_OFFSET_PX`, `TIP_SHIFT_PADDING_PX`.

**Migration — no native `title=` on chrome controls**: native `title=` is **REMOVED wherever `Tip` lands** (never both — the OS bubble would double the styled tip); `aria-label`s stay untouched. `Tip` covers the interactive chrome controls across ~15 component files: `top-bar.tsx`, `top-bar-overflow-menu.tsx`, `breadcrumb-dropdown.tsx` (the `title` prop — a component prop like `Dialog title=`, so kept under that name — renders as an internal `Tip` around the trigger), `open-button.tsx`, `waiting-badge.tsx`, `sidebar/index.tsx` (scope chip, copy capped at ≤40ch action labels), `sidebar/status-panel.tsx`, `iframe-window.tsx`, `compose-strip.tsx` (the natural `kbd`-slot user — Send + the submit keycap, Insert + `Enter`), `host-overview-page.tsx`, `swatch-popover.tsx`, and the board-route twin `board/board-header.tsx` (the `/board/$name` route re-implements chrome and does not render AppShell — see [tmux-sessions](/run-kit/tmux-sessions.md); its one real native tooltip — the unpin button — uses `Tip`; its three other `title=` matches are `Dialog` props, which stay native). **Seams that stay native `title=`**: `Dialog title=` component props everywhere; `title="Proxied content"` on the proxied iframe (its accessible name, asserted by `top-bar-overflow.spec.ts` and `web-view-lens.spec.ts`); `CollapsiblePanel`-style heading `title` props; and the tier-2 hover-card (untouched by the tier-1 migration). (260722-73al)

**Tests** — `tip.test.tsx` covers label/note/kbd render, `role="tooltip"` + `aria-describedby` wiring on open, focus-open, no render / no `aria-describedby` under a mocked coarse pointer, and label-less pass-through (7 tests). E2e `app/frontend/tests/e2e/tooltips.spec.ts` proves keyboard-focus open, hover open, and coarse-pointer absence, plus the palette chip's **resolved** keycap reading `Ctrl+K` — Playwright's `devices["Desktop Chrome"]` pins a **Windows** UA, so `detectPlatform()` returns `other` regardless of the runner's own OS. Registry-resolved chips are covered per-site: `bottom-bar.test.tsx` (the palette chip's `Ctrl+K` tip beside the button face's `⌘K` glyph, the Compose chip's `Shift+Ctrl+E`, and the omit-when-disabled case seeded via a `{"compose-toggle": null}` override) and `sidebar/index.test.tsx` (the Settings gear's `Shift+Ctrl+,`). Per-site unit tests on migrated controls (`top-bar.test.tsx`, `top-bar-overflow-menu.test.tsx`, `top-bar.update-chip.test.tsx`, `board/board-header.test.tsx`, `host-overview-page.test.tsx`) assert the native `title` is gone and the `aria-label` preserved — deep tooltip behavior lives once in `tip.test.tsx`.

## Attention Surfacing (`waiting` rollups + nav)

The per-window `waiting` overlay (agent blocked on a human) propagates UP the hierarchy as **count badges** and drives a **keyboard-first navigation** action and a **board-pane seam**. This is the UI half of #314's three-state `agentState` — see [agent-state](/run-kit/agent-state.md). All counts derive from the existing SSE session data already in the client — **no new endpoint, no `setInterval`/fetch** (Constitution II / code-quality anti-patterns).

**Shared rollup helpers** (`lib/waiting.ts`) — the single source of truth so every surface counts identically: `isWaiting(win)` (= `win.agentState === "waiting"`, keyed on the server-side window-level rollup that already applies `waiting > active > idle` across panes), `countWaitingWindows(windows)`, `countWaitingInSessions(sessions)`, and the instance-wide `countWaitingAcrossServers(sessionsByServer)` (which composes `countWaitingInSessions` over the streamed map). Pure functions over the streamed `WindowInfo`/`ProjectSession` shape.

**`WaitingBadge`** (`components/waiting-badge.tsx`) — a small count chip mounted unconditionally; **renders `null` when `count <= 0`** (attention badges are present only when they mean "something needs you"). Styling follows the existing count-chip vocabulary but in the **signal yellow** of the waiting overlay (`bg-signal-yellow/15 text-signal-yellow` — the *semantic* is constant: "yellow = an agent needs you now", the same glance language as the status-dot halo, in every theme; the *value* re-themes via `--color-signal-yellow`, `ui/visual-design.md` § Design Decisions → Signal hues are per-theme tokens), plus a `⚠` glyph. It is TEXT, not motion (the pulse lives on the per-window dot/seam) — legible via color + count + `aria-label`, never color-only. Mounted on four surfaces:

- **Session row** (`sidebar/session-row.tsx`) — count of the session's waiting windows (`countWaitingWindows(session.windows)`), rendered after the session name button (R8).
- **Host-page TMUX SERVERS server tile** (`host-overview-page.tsx`) — per-server count summed over the server's sessions (`countWaitingInSessions(sessionsByServer.get(name) ?? [])`), absolutely positioned top-right on the tile. One glance at `/` answers "does anything need me" (R9). Only attached servers stream windows, so an unattached server's count is 0 (badge absent) — never a wrong count.
- **Board header** (top-bar `BoardModeInfo`, `top-bar.tsx`) — count of the board's waiting panes (`waitingPaneCount` prop), rendered in the board-mode left info between the pane/server counts and the `⌘[⌘] cycle` hint (R10).
- **Sidebar SERVER-panel server tile** (`sidebar/server-panel.tsx`) — the fourth server-level surface, per-server count over the server's sessions. Placement **differs** from the Host-page tile: it rides the **same flex row as the tile's "N sess" count, right-aligned** (`flex items-center justify-between`) — the count row is the badge's home, and a `h-3.5` reserve holds the badge's height when no badge renders so the grid row never jumps. `ServerTile` takes a plain `waitingCount: number`; `ServerPanel` takes the optional `waitingCounts?: Map<string, number>` and forwards `waitingCounts?.get(name) ?? 0` per tile, keeping the presentational panel decoupled from session data. The Sidebar computes the map in `sidebar/index.tsx` via `useMemo(() => …, [sessionsByServer])` over the already-consumed `sessionsByServer` (same `countWaitingInSessions` helper). Attached-server-only by construction (an unattached server is absent from `sessionsByServer` → count 0 → badge absent), the same accepted caveat as the Host-page tile — no eager attach-all: lazy-attach is deliberate, so an unattached server shows no badge. (260708-4li7)

**Informational sibling — the neutral count chip**: the session row's attached-viewer chip ([ui/sidebar](/run-kit/ui/sidebar.md) § `session-row.tsx`; backed by the payload's `viewers` field — [tmux-sessions](/run-kit/tmux-sessions.md) § Attached-Client Enumeration) reuses the count-chip GEOMETRY but none of the attention treatment: `text-text-secondary`, no signal yellow, no `⚠`, non-interactive, and gated at ≥2 (the 1-viewer norm stays chrome-free). "N viewers attached" is a FACT, not a request — yellow/motion stays reserved for "an agent needs you now"; the diagnostic detail (the per-viewer grids) lives in the row's flyout card, not on the chip. (260903-1eua-attached-viewer-count-indicator)

**Board-pane waiting seam** (`board/board-pane.tsx` + `board-page.tsx`) — a waiting board pane gets a **3px pulsing yellow seam** (border-width system; the `rk-waiting-seam` class + `border-[3px]`), the board-pane form of the status-dot halo: the pane's own 3px border is the static 55% yellow trough and a full-yellow `::after` ring at `inset: -3px` over the border fades with opacity only (composited). Border precedence: a `waiting` pane always shows the seam (attention is the highest-priority signal); a focused-AND-waiting pane layers the accent focus shadow on top so it reads both. Under `prefers-reduced-motion` the seam is the full-yellow border with the pseudo ring hidden (`globals.css`). `BoardEntry` is a thin shape with no `agentState`, so `BoardPageContent` **joins each pinned pane back to its live `WindowInfo`** via `(server, windowId)` against the streamed `sessionsByServer` (use-boards attaches every board server, so window data incl. `agentState` is flowing) — a `waitingWindowIds` set (`${server}:${windowId}` keys) drives both the per-pane seam and the header count; a pane whose window is not yet in the snapshot is simply not waiting (no wrong signal).

**OS-level escape hatch** — inside the Electron desktop shell a fifth consumer, the `ShellBadgeReporter`, mirrors `countWaitingAcrossServers(sessionsByServer)` to the dock/taskbar badge, so the attention tier is visible when the window is not (§ Desktop-Shell Waiting Badge Reporter). Waiting only, like every surface above; a browser tab physically cannot do this, which is what the badge buys over the in-page badges.

**`Agent: Next waiting` palette action** (`app.tsx` `agentActions`, R11 — keyboard-first, Constitution V): cycles focus through windows whose rolled-up `agentState` is `waiting`, **current server first** (in sidebar order, from `flatWindows`) then other **attached** servers (from a live `sessionsByServerRef.current` read — unattached servers' window data isn't streamed, a known constraint). No-op with a `"No agents waiting"` toast when none. The cycle arithmetic is the pure `nextWaitingTarget(ordered, currentServer, currentWindowId)` helper (`lib/palette/agent-nav.ts`, unit-tested): empty → `null`; current window not in the list → first target (jump in); current IS a target → the next one **with wraparound** (`(idx+1) % len`). This is a deliberate contrast with `palette/move.ts` (reorder arithmetic, which does NOT wrap) — do NOT extend that module. Same-server targets navigate via `navigateToWindow`; cross-server targets `navigate({ to: "/$server/$window" })` (and close the mobile drawer). The action is appended to `paletteActions` as `agentActions`.

## Design Decisions

### Provenance rides a system-owned glyph slot, never the style channel
**Decision**: external-server provenance is a leading glyph (↗, `ControlGlyph name="external"`) in the same slot as the protected shield — not a gutter marker, tile border, texture, or `EXT` text badge — and renders only on `managed === false`.
**Why**: the left-gutter marker/texture vocabulary is user-assigned label space (`""`/dotted/dashed/… plus hatch textures from the picker), so "dashed = external" would collide with a user label; the glyph slot is a closed system-owned set. Gating on present-and-false (never on absence) means an old backend mid-deploy paints no wrong treatment — degradation lands on the pre-feature rendering.
**Rejected**: provenance on the style channel (user-vocabulary collision); an `EXT` text badge (competes with the waiting badge's count-row slot); hatch-only (too quiet); `!managed` (treats absence as external).
*Introduced by*: 260826-lv87-external-server-provenance-adopt

### No bounded-fallback timer on the waiting state
**Decision**: the create-server waiting state persists until the refreshed `servers` list contains the server — cleared by an event-driven effect on the list changing, with no timer and no polling.
**Why**: synchronous near-instant backend create makes a timer speculative; a polling loop would violate the no-client-polling anti-pattern.
**Rejected**: a ~5s bounded-fallback timeout for v1. If ever added it MUST be a single `setTimeout`, never a polling loop.
*Introduced by*: 260602-3i5d-fix-create-server-not-found-race

### No `role="tooltip"` on the status detail hover-card
**Decision**: the tier-2 status hover-card (today the sidebar row flyout card) advertises no `useRole({ role: "tooltip" })`.
**Why**: the W3C tooltip pattern requires a tooltip to contain NO interactive content, but this card holds real `<a>` links (PR + docs). Advertising `role="tooltip"` would lie to AT and wire a misleading `aria-describedby`.
**Rejected**: `role="tooltip"` (present in the plan, removed in review).
*Introduced by*: 260616-37ub-status-dot-tooltip, 260805-93dy-window-row-pr-glyph-register-flyout

### Two-tier tooltip boundary
**Decision**: tooltips are exactly two species with a hard boundary — tier-1 `Tip` (names a control: plain text + optional kbd/note, `role="tooltip"` + `aria-describedby`, never interactive) and tier-2 hover-cards (the sidebar row flyout card: state and/or real links, role-less). A tooltip needing a second line of state or anything clickable is tier-2; there is no fatter tier-1. Native `title=` values that are state or a content reveal (not a control name) stay native `title=` — neither converted to tier-1 nor promoted to new hover-cards.
**Why**: the two shells already had incompatible ARIA needs (§ No `role="tooltip"` on the status detail hover-card) — one visual language across both tiers, one clear rule for which to reach for, and no accidental middle species that lies to AT. Promoting state/content titles to new tier-2 cards is scope beyond naming a control, and two e2e specs assert those exact `title=` seams.
**Rejected**: a single configurable tooltip spanning both roles (re-introduces the role/interactivity conflict); promoting every native `title=` to a styled surface (builds hover-cards nobody asked for and breaks the asserted state-title seams).
*Introduced by*: 260722-73al-tip-tooltip-system

### The flyout card is the single hover surface per row, on every pointer class
**Decision**: session and server rows are served by the same tier-2 flyout card on fine-pointer hover/focus as on the coarse rail; there is no separate slim hover-card species for identity facts — the card's `PopupTitleBar` + facts line carry them.
**Why**: one hover surface per row keeps the two pointer regimes convergent and the sidebar learnable, and labeled card rows are more discoverable than hover-revealed chrome. The promotion rule still holds for the card itself — it needs a second line of state and real links, so it is tier-2, not a fatter tier-1 `Tip`.
**Rejected**: a parallel non-interactive identity hover-card beside the card on fine pointers (two hover surfaces racing on the same row, duplicating the title/facts content); extending `Tip` with a title-bar mode (breaks its one-line `role="tooltip"` contract and its `pointer-events-none`/40ch invariants, diluting the tier boundary every future tooltip decision leans on).
*Introduced by*: 260815-xb77-row-popup-identity-titlebars, 260903-1ldw-standardize-color-entry-flyout-card

### One status-detail surface, three triggers — the ROW, not the dot
**Decision**: Window-row status detail is served by a single row-anchored flyout card for fine-pointer row hover, keyboard row focus, and coarse-pointer status-rail touch/scrub. The dot wrapper is inert, and `StatusDot` carries neither a `tabIndex` nor a native `title` on any surface.
**Why**: the 7px dot was a precise pointer target and a second tab stop ahead of the row treeitem; the whole row is a large forgiving target and is already the focusable treeitem, so one surface covers every input modality with less markup, no jitter, and one fewer tab stop. Keeping a dot tip *and* a row card would mean two surfaces racing on the same hover. On coarse the rail gives the gesture a visible affordance and the card anchors below the row, capped short of the rail column (§ Row-hover register flyout card).
**Rejected**: keeping the dot tip for focus/touch alongside the row card (two overlapping surfaces, the dot tab stop retained); a mouse-following card (jitters and covers the row it describes); a hover preview inside the bottom PANE panel (detail lands far from the pointer); a `placement: "right"` card on coarse (no free space beside the mobile drawer — the card clipped off-screen).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout, 260816-b8eu-status-rail-card-actions

### Flyout warm window is module state, not a nested `FloatingDelayGroup`
**Decision**: the flyout's shared delay-group scope is module-scoped state (`activeFlyout` + `lastClosedAt`) consumed through floating-ui's function-form `delay`, not a second `FloatingDelayGroup` provider around the sessions tree.
**Why**: `useDelayGroup` binds to the NEAREST `FloatingDelayGroup`, and the sidebar renders tier-1 `Tip`s under the shared `TipGroup` (the section rail, the pane panel, the footer) — a nested provider would capture any tips in its subtree, changing their delay and mixing tier-1/tier-2 warmth (the sidebar-is-one-warm-tip-cluster contract). Module state gives the flyout an independent warm cluster spanning every mount, and the function-form `delay` is evaluated at event time so warmth set by another row is seen without a re-render.
**Rejected**: a nested `FloatingDelayGroup` (captures any tier-1 Tips in its subtree); a flat per-row delay with no warmth (strobes on a row sweep).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout, 260903-1ldw-standardize-color-entry-flyout-card

### Element-keyed scrub registry beside the warm/single-open coordinator
**Decision**: the slide-to-scrub retarget uses a module-scoped `Map<HTMLElement, () => void>` (row root element → that row's imperative `openNow`) beside the `activeFlyout`/`lastClosedAt` coordinator, populated by an effect inside `useRowFlyout`; the gesture hit-tests with `elementFromPoint` + `closest()` to a row root and looks the handle up. Every rail-bearing tier registers in the SAME map, so a held slide retargets the single-open card across window, session, and server-group rows alike.
**Why**: module state is the established coordinator pattern in this file, costs no re-renders, and honors the memo tree — no context provider, no lifted state, no new props through `ServerGroup`. The element itself is the only always-present key: `rowKey` is optional, while the reference element is already known to the hook and needs no naming contract. Keying the registration effect on `openNow`'s closure means a flipped `suppressed` gate re-registers, so a scrub never invokes a stale gate.
**Rejected**: a React context of row handles (re-render churn through the memo tree); a `data-row-key`-keyed map (imposes a naming contract on an optional prop).
*Introduced by*: 260816-ys3q-mobile-pr-glyph-flyout-scrub

### Pointer-conditional placement inside one `useRowFlyout`
**Decision**: `useRowFlyout` reads `useCoarsePointer()` itself and branches placement/middleware/width-cap on it — fine: `placement: "right"` with the `offset(6)`/`flip()`/`shift({ padding: 8 })`/`size()` (inline-cap reset)/`arrow()` chain; coarse: `bottom-start` + `flip({ fallbackPlacements: ["top-start"] })` + `shift` + a `size()` cap (reference width − 56px rail − 8px gap, floored at 120px) + `arrow()`. One hook, two placement arms, on every mount.
**Why**: the hook already owns all positioning; forking the hook or threading placement as a prop would spread the decision across consumers and risk drift. The `size()` arm is what enforces the containment invariant — the card's right edge stops before the rail column, so the finger's column stays visible and touchable mid-scrub.
**Rejected**: a separate mobile card component (duplicates the card body — the one-card-three-triggers principle); a CSS-only `max-w` calc (cannot know the reference row's width — `size()` measures it).
*Introduced by*: 260816-b8eu-status-rail-card-actions, 260903-1ldw-standardize-color-entry-flyout-card

### One card shell, four mounts
**Decision**: the flyout machinery is ONE shared shell — the `useRowFlyout` hook (placement arms, containment cap, held-state key, portal/focus wiring, notch) parameterized by a per-mount `content({ close })` render prop — consumed by four mounts: the window row (registers + links + action rows), the session row, the server-group header (title + facts line + action rows each), and the TMUX SERVERS panel tile. The two server mounts share one content implementation, `ServerCardContent` (`sidebar/server-card.tsx`).
**Why**: all mounts are bound to one placement/containment/held-state implementation; duplicating the floating-ui wiring per mount creates drift surfaces for the same behavior, and two server surfaces rendering separate content would drift on the same card.
**Rejected**: per-mount card components with copied positioning (drift surfaces); forcing session/server content through the window card's register renderer (registers are a window-only concept); a second server-card implementation for the tile (two sources for one card).

### Fork affordance is double-gated: provider AND an optional handler
**Decision**: the flyout's fork action row renders only when `canForkWindow(win)` accepts the source provider (`"claude"` or `"codex"`) **and** the consumer supplied an `onFork` callback; a consumer wiring no handler renders no row and throws nothing.
**Why**: the provider half is a data gate (Claude uses `--resume <id> --fork-session` and Codex uses `fork <id>`) and reuses the `WindowInfo` agent-session-identity field the backend already rolls up for every window — no new data plumbing. The handler half is a *capability* gate: `useRowFlyout` has no server or navigation access of its own, and the board-route sidebar has no business forking, so the optional-prop idiom (`onSpawnAgent`, `onColorChange`) gates the affordance per call site without the hook growing a dependency it cannot satisfy.
**Rejected**: a provider-only gate with a required handler (forces every consumer, including the board sidebar, to supply one); threading server/navigate into the flyout hook (widens a leaf hook's surface for one button).
*Introduced by*: 260806-s4av-row-flyout-session-fork

### Fork in-flight state is leaf-scoped in the fork row, and the guard is correctness not polish
**Decision**: `ForkActionRow` owns its own `busy` state with `disabled={busy}`, a redundant early `if (busy) return`, a `mountedRef`-guarded settle, and a clear on **both** outcomes — the guard lives inside the fork affordance wherever that affordance's home is.
**Why**: `onFork` POSTs a mutating endpoint that CREATES a tmux window, so N clicks create N fork windows — the guard is the only thing preventing that, not a loading-spinner nicety. Keeping the flag inside the row (rather than lifting it to the card or the window row) means only the row re-renders during a fork, honoring the card's render-performance contract. The `mountedRef` is required rather than defensive: a *successful* fork navigates away and the card unmounts, so settle-after-unmount is the common path.
**Rejected**: lifting `busy` to `RowFlyoutContent` or `WindowRow` (re-renders the whole card / breaks the row's `memo` discipline); relying on `disabled` alone (leaves a click-during-settle window); clearing only on success (a failed fork would be permanently unretryable); a shared "busy action row" abstraction (one consumer, premature).
*Introduced by*: 260806-s4av-row-flyout-session-fork, 260816-b8eu-status-rail-card-actions

### Fix tab name availability is server-derived conversation capability, not identity presence
**Decision**: `canRequestWindowOperatorAction` gates the Fix tab name row (the flyout and the palette alike, through the one shared function) on three sessions-payload facts — the server has an operator window, the subject's server-derived `conversationAvailable` is true, and the subject is not the operator. The backend derives `conversationAvailable` once per identified window per fetch (the window rollup seam, never per-pane): providers with a cheap `ConversationChecker` probe answer through it, every other provider resolves via the bounded glob/index lookups, and every failure class — absent identity, unregistered provider, invalid ref, missing transcript — degrades to false. The derive tick never errors and never spawns a subprocess.
**Why**: keeps the flyout and palette honest for identity-only providers — Copilot advertises identity and lifecycle but has no transcript adapter, so an action gated on identity alone would predictably 404 — without per-pane unbounded scans or request-priced work on the derive tick.
**Rejected**: advertising on identity presence alone (predictably fails for Copilot); caching transcript resolutions (Constitution II — derive at request time).
*Introduced by*: 260908-nnqu-fix-agent-neutral-detection

### Rest glyph as an absolute overlay on the last slot, not a third flex slot
**Decision**: on FINE pointers the row's rest-state PR glyph is absolutely positioned at the icon cluster's right edge, over the kill button's 24px slot, and hidden by a display swap; the pin/kill buttons keep their opacity gating. On coarse pointers the glyph renders in the status rail's fixed 16px slot instead — the overlay is fine-pointer-only (sidebar.md § Design Decisions → The status rail is the coarse trailing zone).
**Why**: the action buttons are opacity-gated precisely so they occupy their slots at rest and stay keyboard-focusable. A display swap of the buttons themselves would make them unfocusable at rest (a keyboard regression), while overlaying the glyph delivers the approved "PR sits exactly where ✕ sits, only the last slot swaps" geometry with zero layout shift and no focus changes. Coarse has no hover cluster to overlay, so the rail slot is the glyph's home there — one PR channel per pointer world.
**Rejected**: a `hidden`/`flex` swap on the buttons (breaks Tab reachability at rest); a third flex slot (the glyph would sit left of the ✕ rather than in its place); an opacity fade over reserved space (the user rejected coexistence — the rest state must go away entirely); rendering BOTH the overlay and the rail slot on coarse (double-paints the same fact inside the rail's 56px).
*Introduced by*: 260805-93dy-window-row-pr-glyph-register-flyout, 260816-b8eu-status-rail-card-actions

### Draft is glyph-only — gray color plus its own dotted-rail shape, never a dot state
**Decision**: draft lives on the row glyph and only there — the dot carries no PR state at all. On the glyph, draft is `text-text-secondary` (the only gray glyph state) AND renders the lucide `git-pull-request-draft` silhouette (`GitPullRequestDraftIcon`: source circle + rail, a dotted merge rail where the arc sits, target circle) via the shared `prGlyphIcon` selector. A failing draft keeps the draft shape in red.
**Why**: the glyph's color axis is a single pure function returning a Tailwind token, whereas the dot's hue axis is owned by the two-family channel model (cool = fab pipeline, warm = ad-hoc agent) — a draft hue there would break the family-identity glance rule the whole palette rests on. Gray is the mapping already in the user's head (GitHub renders drafts gray) and `text-text-secondary` is the established inert/no-journey token in this exact model (`PHASE_HUE.none`), at ~4.8:1 in the light theme against the 3:1 WCAG floor for graphical objects. The shape is needed because gray-arc vs green-arc is a color-only distinction that fails for colorblind users and dim themes, and because at 13px the corner detail of a sibling icon does not read peripherally — the dotted rail is GitHub's own draft silhouette and empties the right half of the glyph, a silhouette-level difference. One more 13px SVG in the fixed icon idiom is cheaper than the confusion. The two channels then answer different questions rather than duplicating one: the glyph says *whose turn is it*, the dot says *what runs here, is it healthy*.
**Rejected**: a new muted token or raw hex (contradicts the glyph's no-new-color-system rule); importing `PHASE_HUE.none` instead of the literal (couples the glyph's color axis to the dot's phase map — precisely the coupling being avoided); draft on the shared arc icon varied only by color (a second SVG looked like extra surface for one bit, but color alone left draft indistinguishable from other gray states at row size).
*Introduced by*: 260807-e30p-draft-pr-row-glyph-color, 260829-lvvw-pr-glyph-draft-shape-closed-red

### The draft glyph branch sits below fail and is gated on `prState === "open"`
**Decision**: `prGlyphColor`'s chain is closed-red → merged-purple → fail-ish-red → open-and-draft-gray → open-checks-pending-yellow → open-green, with the draft branch conjoined on `win.prState === "open"`.
**Why**: a draft whose checks fail (or that has changes requested) is a problem first and a draft second, so `isFailish` keeps first position among the open cases; draft-first would hide a red signal behind a gray one on exactly the rows still owing work. The open-gate keeps the closed path untouched *by construction* (merged already returns above the fail branch) rather than defended only by GitHub's server-side un-draft-on-merge, and confines draft to displacing the open cases below it — the checks-pending yellow included (drafts stay muted while their checks run).
**Rejected**: draft above fail (buries the red signal); an ungated `if (win.prIsDraft)` (behaviorally identical today, but leaves the merged path defended by remote behavior instead of local structure).
*Introduced by*: 260807-e30p-draft-pr-row-glyph-color

### Closed PR earns a red ✕ glyph, ranked above fail
**Decision**: `prOwnsGlyph`'s allowlist is `open`/`merged`/`closed` (an absent/unknown `prState` still never owns), `prGlyphColor` returns `text-signal-red` for closed from a branch above the fail branch, and every glyph surface (window row fine overlay, coarse rail slot, session tile) renders the ✕ `GitPullRequestClosedIcon` when `prState === "closed"` via `prGlyphIcon`. A closed draft reads closed — closed is checked first in both the color chain and the icon selector.
**Why**: a closed-unmerged PR is an outcome worth a glance-level signal ("this branch's PR was rejected/abandoned — the window needs a decision: rework, re-open, or kill"); rendering no glyph made a closed PR indistinguishable from never having had one, which actively misleads during triage. Red is GitHub's closed coloring — the mapping already in the user's head — and `PR_STATE_COLORS.closed` already paints the register segment red, so the glyph now agrees with the text beside it. The accepted cost is that red on the sidebar no longer exclusively means "act now": closed and failing share the token and are separated by shape (✕ vs arc), which is the same shape distinction GitHub relies on. Closed sits above fail because a closed PR's checks/review are historical noise — the same first-match rationale that puts `merged` above `fail` — and so a closed PR with passing checks cannot fall through to green.
**Rejected**: muted gray + ✕ (at 13px the ✕ is a ~3px corner detail, leaving closed indistinguishable from a gray draft at a glance — the user could not triage without hovering); a bolder or dimmer gray ✕ (near-invisible on the dark theme); red on the same `GitPullRequestIcon` (indistinguishable from failing; GitHub never colors the plain PR icon red); leaving closed glyph-less (the misleading gap); a new color outside the popular PR vocabulary (learning curve).
*Introduced by*: 260810-xuej-closed-pr-row-glyph, 260829-lvvw-pr-glyph-draft-shape-closed-red

### PR is evicted from the dot — dot = local story, glyph = remote story
**Decision**: the status dot renders only the local story (fab journey / ad-hoc agent / floor) with four hues (blue building → green PR-ready, yellow agent, gray floor) and two liveness shapes (ring / solid) plus two additive overlay flags (the failed red center, the waiting halo); PR state — draft, checks-pending, open, merged, failing, closed — lives exclusively on the rest-state row/tile glyph via the six-way `prGlyphColor`. The blue/green split is stage-based (`fabPhase`), never `prNumber`-based.
**Why**: the row glyph made the dot's PR tier redundant (a merged fab PR rendered purple twice, two pixels apart), and the PR tier displaced live pipeline state (a fab window with a PR never showed its stage on the dot). Splitting by story makes shape meaning uniform across every hue — fully compositional, four legend strips replace a 6×5 matrix — and gives every new PR-adjacent state a home on the glyph instead of pressuring the dot. Stage-based hue keeps the dot free of PR fields; alignment with PR existence stays emergent (`/git-pr` creates the PR mid-ship).
**Rejected**: square-only removal (keeps the double-encoding; merged becomes indistinguishable from open on the dot); the maximal one-fab-hue reduction (loses the "still cooking vs out the door" glance); a `prNumber`-based blue/green split (couples the dot to PR fields).
*Introduced by*: 260810-aqo6-statusdot-compositional-vocabulary

### Skipped display-state falls through the whole ladder
**Decision**: `statusDotState` treats `fabDisplayState === "skipped"` as "not a fab-owned dot" and continues down the ladder (fresh agent → yellow, else gray floor), rather than forcing gray inside the fab arm.
**Why**: a skipped change has left its journey; ladder continuation is the least machinery and lands on the gray floor in the common agent-less case, without hiding a live agent on a skipped change's pane.
**Rejected**: a dedicated skipped→gray short-circuit (extra machinery that would also hide a live agent on a skipped change's pane); a fab resting ring for skipped (it is not a resting fab change — it left the journey).
*Introduced by*: 260810-aqo6-statusdot-compositional-vocabulary

### Waiting attention is an additive halo, never a hue-flip
**Decision**: `waiting` renders as a pulsing yellow `rk-waiting-halo` `::after` ring layered around the dot, leaving the core hue and shape untouched (a blue building dot keeps its blue core; a failed dot keeps its red-center flag); under `prefers-reduced-motion` it degrades to a static yellow ring.
**Why**: family identity must survive attention — the halo is the signal the user scans for, and its absolutely positioned pseudo ring paints outside the dot's box so it disturbs neither the dot's size nor its hue.
**Rejected**: a hue-flip on attention (destroys exactly the family signal the user is scanning for); a self-colored halo (vanishes in the reduced-motion static form).
*Introduced by*: 260706-y1ar, 260810-aqo6-statusdot-compositional-vocabulary

### Attention overlays run on the compositor
**Decision**: the waiting halo and the board-pane waiting seam pulse via pseudo-element rings animated with `transform`/`opacity` only; no attention animation touches a main-thread property.
**Why**: measured 2026-09-16 with `just perf-idle-cpu` ([testing](/run-kit/architecture/testing.md) § Performance probes): four animated box-shadow halos cost +3.6 points of a core and 1802 style recalcs per 30s on an otherwise idle `/`, scaling with waiting agents × render sites (≈4–5 dots per waiting window on a desktop tty route); eight composited pseudo-ring halos cost +0.5 points and 111 recalcs. Blink cannot composite `box-shadow` or `border-color`; it composites `transform` and `opacity` for free.
**Rejected**: `will-change` on the box-shadow rule (cannot composite a non-compositable property); a JS `requestAnimationFrame` pulse (moves the cost, does not remove it); removing or slowing the pulse (changes the signal — attention semantics and timing are a rendering-independent decision of record).
*Introduced by*: 260916-h7l1-waiting-halo-composited

### The seam's border is the trough; the overlay ring is the peak
**Decision**: `.rk-waiting-seam` paints the pane's own 3px border at 55% yellow and fades a full-yellow `::after` ring over it with `opacity`.
**Why**: a static trough plus an opacity-faded full ring reproduces the 55% → 100% pulse endpoints with a single composited property, and the reduced-motion form falls out as "border at full yellow, ring hidden".
**Rejected**: scaling a ring (a 3px seam has no room for lift-off); animating `border-color` with a compositing hint (never composited).
*Introduced by*: 260916-h7l1-waiting-halo-composited

### One scaled ring for the halo, two-ring opacity fallback
**Decision**: the halo is a single `::after` ring at `inset: -2.5px` scaled 1 → 1.3 with opacity 0.65 → 1 (ring colour at the 85% peak); if the ≈1px lift-off gap at the pulse peak is ever rejected by eye review, the fallback is a static 55% `::before` ring plus a 3px 85% `::after` ring fading with opacity only.
**Why**: scaling reproduces the growing-ring motion most faithfully, and the fallback keeps the ring flush at the cost of a two-step growth — either form is composited. An absolutely positioned pseudo anchors to the dot's PADDING box (not its border box), and Chromium snaps the dot's fractional 1.8px ring border when resolving that padding edge — `inset: -2.5px` clears the snapped 1px of border plus the 1.5px ring, landing the ring flush outside the border-box (verified by screenshot pair at 1× and 2×).
**Rejected**: a `z-index: -1` ring behind the dot (paints above the host's border within the host's stacking context, so it tints hollow rings); animating `inset`/`border-width` (main thread).
*Introduced by*: 260916-h7l1-waiting-halo-composited

### Fab dot labels compose hue-word + liveness word + overlay flags
**Decision**: `dotLabel` fab labels are `building`/`PR-ready` (the phase word) + a liveness word derived from shape and the failed flag via `fabLivenessWord` (`solid` → "worker live", `ring` → "at rest", flagged solid → "failed — rework live", flagged ring → "failed — at rest"), never the raw stage word, never a PR word, and never a `fabDisplayState` word — a parked-done change reads "PR-ready — at rest".
**Why**: the label is a pure function of what the dot shows, and the dot shows liveness — a displayState-derived word would state bookkeeping the shape does not encode (a stage-active window with an idle agent renders a ring, so "active" would lie). The exact stage lives in the `fab` register on both register surfaces.
**Rejected**: the raw stage word (`review — active`) — re-encodes per-stage detail the dot does not render; displayState-derived status words ("parked", "ready") — couple the label to bookkeeping the shape does not render; PR-native labels (`PR — merged`) — PR facts belong to the glyph and register surfaces, not the dot's label space.
*Introduced by*: 260903-18ot-statusdot-shape-liveness-overlays

### Shape source is per-family (agentState on journey hues; L0 only on the floor)
**Decision**: Journey hues (blue · green · yellow) derive shape from the rolled `agentState` only (absent ⇒ ring); the output-flowing L0 fallback applies to the gray floor alone.
**Why**: `@rk_pane_agent_state` is PID-reconciled — solid cannot outlive the process; a single global L0 fallback would let any byte source (dev server, log tail) make a fab dot lie solid.
**Rejected**: one uniform agentState-else-L0 rule (re-introduces the stale-solid lie via output); keeping shape on `fabDisplayState` (bookkeeping renders solid for hours-idle agents — the motivating bug).

### Failure is an additive red-center overlay, not a shape
**Decision**: `failed` leaves the shape set and becomes `StatusDotState.failed?: boolean`, rendered as a red center — inside the hollow ring at rest, as a bullseye (dark gap ring) over solid — with flagged dots keeping the 9px footprint.
**Why**: failure and liveness are orthogonal facts; the overlay makes "failed, nobody on it — act" vs "failed, rework live" distinct at a glance, and the silhouette change keeps failure legible without color (a11y).
**Rejected**: moving review-failure to the PR glyph (a `review`-stage failure is pre-PR and the glyph is owned-PR-gated — the failure would be invisible; and dot-red = my pipeline failed here vs glyph-red = the PR is failing/closed on GitHub is a load-bearing split); keeping the third shape (non-compositional, hides rework liveness).

### waiting = ring + halo

**Why**: the underbar's two states (live / stale) stay legible on a 1px bar; the trail's value is "which windows did the operator touch", a card-level fact; the row keeps mirroring the status pyramid's overlays only.

### Clone-child reference API
**Decision**: `Tip` clones its single child element and merges the floating reference props/ref onto it (`useMergeRefs`), rather than rendering a wrapper element or a render-prop API.
**Why**: ~40 migrated call sites demand minimal churn; the top-bar's overflow fit measures `barRender()` widths in a hidden probe, so any wrapper element would distort measured widths; the codebase already uses the floating-ui reference-props idiom.
**Rejected**: a wrapper `<span>` (distorts probe widths and flex layouts); a render-prop shape handing each call site the reference setter (far noisier across 40 call sites).
*Introduced by*: 260722-73al-tip-tooltip-system

### Suppress-by-early-return on coarse pointers
**Decision**: under `pointer: coarse` (live via `useCoarsePointer`), `Tip` returns its child unchanged — no reference props, no portal, no ARIA wiring. Hooks still run unconditionally (parameterized on an `enabled` flag); only the render return is short-circuited.
**Why**: the approved spec gives touch no tooltip layer at all; not attaching the machinery is the cheapest correct implementation and makes the "no render under coarse pointer" assertion direct. The control's `aria-label` carries the name on touch.
**Rejected**: `enabled: false` on the hover/focus hooks only (still wires the `aria-describedby` machinery and keeps dead listeners).
*Introduced by*: 260722-73al-tip-tooltip-system

### A measured priority fold replaces the breakpoint ladder
**Decision**: the status bar folds by measured priority — every segment renders at natural width or moves to the `…` menu, one ladder across both clusters, truncation reserved for the single rightmost truncatable never-fold survivor (`fab` before `pr`).
**Why**: overflow is caused by value length (30-char branches, 48-char fab lines), not viewport width; breakpoints answer the wrong question (at common laptop widths nothing had dropped yet and six segments truncated proportionally), and independent per-cluster ladders let a long left cluster squeeze the host name.
**Rejected**: CSS breakpoints (answer the wrong question); horizontal scroll or a two-row bar (a scrolling strip hides what it exists to show; two rows is a card, not a strip); a segment-visibility setting (Constitution IV — one registry-driven settings surface).
*Introduced by*: 260914-msu9-status-bar-priority-fold

### Sibling module, not a generalisation of `gui-toolbar-fold`
**Decision**: `lib/status-bar-fold.ts` is a fourth dependency-free pure module beside the three measured-overflow precedents (`top-bar-overflow.ts` `computeVisibleCount`, `crumb-collapse.ts`, `gui-toolbar-fold.ts`); the two-pass reserve and hysteresis rules are restated in it, not imported.
**Why**: a priority fold (any position may fold) and the gui module's suffix fold (the tail folds) share two constants and little else; every precedent deliberately keeps its own constant to stay dependency-free.
**Rejected**: extracting a shared fold-core (a larger diff touching a shipped gui module for two constants).
*Introduced by*: 260914-msu9-status-bar-priority-fold

### Last-survivor truncation targets the rightmost truncatable never-fold item
**Decision**: never-fold items share `prio: null`, so when the never-fold set alone overflows the truncation target is the rightmost `truncatable` item in display order — `fab` before `pr`; `zen ✕`, the stale `◷` chip, and the connection dot are never truncatable.
**Why**: display order is the only tiebreak available among never-fold items, and `fab` carries the longer value on an off-change branch.
**Rejected**: truncating `pr` first (the shorter value; its anchor is the most-clicked segment).
*Introduced by*: 260914-msu9-status-bar-priority-fold

### Status-bar left cluster is branch-first descending relevance
**Decision**: the status bar's left window cluster renders `⑂ git → pr → fab → agt → tmx → cwd` — the git branch anchors the left edge, the volatile per-window signal segments follow, the identity rows trail. Display order is fixed; SURVIVAL order is the fold's priority table (`tmx`/`cwd` fold early, `git` late, `pr`/`fab` never), not display order.
**Why**: a status-pyramid-ascending order puts the most-consulted segments (PR, branch) at the far end of the cluster behind four low-value identity rows. Branch-first (over PR-first) keeps the left edge stable: the branch is always present in a worktree pane, while pr/fab/agt appear and vanish per window.
**Rejected**: PR-first pure-relevance ordering — leading with volatile segments makes the bar's left edge jump on every window switch to a PR-less window.

### PANE-on yields the bar's window cluster
**Decision**: While the PANE panel is on screen — the `pane` section visible, the panel expanded (its own persisted `runkit-panel-window` open state, read through the exported `PANE_PANEL_OPEN_STORAGE_KEY`), the sidebar open, zen off — the terminal-route `StatusBar` receives `window={null}` and keeps only its host cluster; the gate lives at the `AppShell` mount, not inside `StatusBar`. (3k45)
**Why**: The register view has one desktop home at a time. The bar's window cluster exists because the desktop panel is opt-in; an opted-in panel makes it a redundant copy 30px away, and the 30–48-character `⑂`/`fab` values are what push the host segments into truncation. `window={null}` is already the board mount's contract, so no `StatusBar` or `WindowCluster` change is needed. Zen hides the sidebar without touching the preference, so the `!zenOn` term keeps a register view on screen in zen. A collapsed panel shows only its header and no registers, so without the expanded term the user would see neither surface — collapse must hand the cluster back exactly as hiding the section does.
**Rejected**: Keeping `pr` in the bar while yielding (needs a `StatusBar` prop plus a `WindowCluster` branch; the panel already shows `pr` open-first); yielding whenever the sidebar is open (the default desktop has the sidebar open and the panel off); a settings surface for which segments show (Constitution IV); lifting the panel's open state into `ChromeContext` or a prop chain (the boolean already rides `useLocalStorageBoolean`'s in-module pub/sub, so subscribing by key is the same mechanism `paneSectionVisible` uses).

### Flex rows carry their gaps as NBSPs
**Decision**: A flex-laid-out register row (`CopyableRow` in `flex` mode — the `cwd` row — and `PrLinkRow`) ends its key with an NBSP inside the prefix span (`{prefix}`+NBSP; `copied ✓`+NBSP) and carries its icon→value gap as an NBSP text node outside the 14px icon span; inline rows keep plain spaces and `{" "}` text nodes.
**Why**: A flex container trims a flex item's trailing collapsible space and drops whitespace-only text nodes, so a plain-space gap disappears and the icon column shifts one advance left. An NBSP is not collapsible, so it survives in both positions; keeping the value gap outside the icon span means it measures at the row's 12px size rather than the icon's 14px, which is what keeps the value column on one x across inline and flex rows.
**Rejected**: `whitespace-pre` on the prefix span (departs from the documented idiom and leaves a collapsible space other containers trim again); the gap inside the icon span (a 14px advance — the value column sat 2px right of the inline rows).
*Introduced by*: 260915-3k45-pane-icon-column-collapse-yield

### The panel adopts the card's continuation rule
**Decision**: The PANE panel's `pr` and `fab` rows split into a key line of decisive tokens and a dim `pl-[6ch]` continuation line for the expendable tail (the PR health facts; the slug when the branch does not carry it), two lines maximum, the continuation rendered only with content; the identity/health split is the shared `getPrParts` resolver, with `getPrSegments` as its joined formatter.
**Why**: Truncation is unavoidable at the 220px default, so the layout chooses what gets cut — the same reasoning as § Continuation lines rather than truncation. `6ch` is the panel's value column (the 4-advance key + the 2-advance icon cell); the card's `4ch` is the same rule on a surface with no icon column. A resolver-level split keeps the rule shared across surfaces (Constitution X). The `pr` anchor spans both lines so open-first covers the block; the copy icon's container is one text line tall (`h-[1lh]`) so it stays on the key line.
**Rejected**: Truncating the tail (cuts the health facts and the off-branch slug first); three-line rows; slicing `prSegments` inline in the panel (a per-surface rule); lifting the card's fab composition into a shared component (the panel's key line carries copy/hover interactions the read-only card line lacks — the shared rule already lives in the resolver).
*Introduced by*: 260914-msji-pane-panel-yield-continuation

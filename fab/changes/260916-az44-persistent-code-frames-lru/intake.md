Full Vitest (`just test-frontend`) is the unit gate. >
> **Explicitly out of scope:** the `web` tile (IframeWindow) — leave it; pre-warming the next likely window's code frame — leave it; any change to code-server spawn flags, the /code proxy, or extension activation — measured as not the lever.
>
> **Alternatives rejected:** reconnecting a new iframe document to the old code-server connection (impossible — the graceful disconnect on unload is unconditional and VS Code holds the reconnection token in memory only); one shared code frame that navigates between workspaces (a workspace switch is a full workbench reload — same cost as a remount); unbounded retention (each frame is a ~250–320 MB extension host on the server plus a browser renderer); tuning caching/proxy (warm network is already 3 KB).
>
> **Constraints:** Constitution IV (the LRU is in-memory viewer state, nothing new is persisted), V (no new user-facing action is needed; if a "Tile: Evict code frames"/"reload" verb is added it must be in the palette), code-quality "no in-memory caches unless justified by performance measurement" — the numbers above are that justification; the retained frames are hidden at display level (`hidden` class), never `visibility`/off-screen. The bridge: each retained workbench keeps its tab-keyed host record and socket alive under `$XDG_STATE_HOME/run-kit/cb/`, which is fine and makes `rk code exec` faster for those tabs. Reachability still gates content: an unreachable host renders the not-running state and drops every frame.
>
> **Risks to check during apply:** hidden iframes still run JS and hold WebSockets (accepted); VS Code layout on re-show (prototype: fine at display:none→block, 16 ms); the first-boot rescue's `[reachable, src]` effect must not re-arm on show/hide; the tile-focus `onInteract` seam of a hidden frame can't fire (it has no focus) — verify; window kill while its frame is hidden must evict without errors.

Key decisions carried from the conversation (all recorded as Certain/Confident rows in § Assumptions): one change, not split; the `code` tile key drops `windowId`; a per-server LRU inside `SurfaceLayout` keyed by workspace src; cap 3 desktop / 1 mobile; four eviction triggers; `useCodeWorkspace` becomes a per-window map; `web` tile, pre-warming, and code-server/proxy tuning are out of scope; the retained frames use the existing `hidden`-class mechanism.

## Why

**The pain.** The terminal route's center is a layout of tiles (`docs/specs/surface-layout.md`); since PR #914 the grid is keyed by `server`, so the `tty` tile's `TerminalClient` survives a same-server window switch — the switch is instant. The `code` tile does not: its React key carries `windowId`, so every switch unmounts the code-server iframe. An iframe unmount is a page unload; VS Code web sends its graceful disconnect, code-server disposes the connection and terminates that workbench's extension host. Switching back boots a brand-new workbench: 1.4 s to `.monaco-workbench`, ~2 s to explorer rows, ~2.9 s to the SCM status-bar item on a warm cache and an idle box (2.2 / 2.5 / 4.1 s cold); under load the extension host alone has taken 7 s. On top of the boot, the pending `opening…` state flashes for a render tick on every switch because `useCodeWorkspace` holds a single resolved entry and refetches for the newly active window. For an operator hopping between agent tabs with the editor open beside each, every hop costs seconds of blank editor, and the edit position, scroll, and undo stack are gone (the undo stack is in-memory; code-server's own hot-exit only saves dirty buffers).

**If we do nothing.** The code tile stays the one surface that penalizes tab switching, exactly when the tab-switch flicker fix made the terminal free. Users learn to keep the code tile closed or to avoid switching — the opposite of the "editor beside the live agent" posture the `code` lens exists for. The right-panel spec's P3 (Hide, never unmount) already promised this behavior within a window and explicitly deferred the cross-window LRU "until latency data exists"; the data now exists.

**Why this approach.** The prototype proves the mechanism: a live code-server iframe display-hidden for 6 s and shown again re-lays out in 16 ms with no reconnect, no page errors, and no reboot — the same `hidden`-class hide-never-unmount mechanism the tile renderer already uses within a window. Nothing on the request path is the lever (warm network is 3 KB; rk's GETs are ~2 ms; spawn flags do not affect boot), so the only way to skip the cost is to not pay it: keep the workbench alive. The retention must be bounded because each live workbench is one ~250–320 MB extension-host process on the server plus a browser renderer, and it must be bundled with the per-window workspace cache because the cap alone still flashes `opening…`. The three pieces (key change, LRU cap, workspace map) are one behavior and ship as one change. The rejected alternatives are dead ends by construction: a new iframe document cannot rejoin the old connection (the graceful disconnect on unload is unconditional and the reconnection token lives only in the dying renderer's memory), and one shared frame that navigates between workspaces pays a full workbench reload per switch — the same cost.

## What Changes

### 1. `surface-layout.tsx`: the `code` tile survives a same-server window switch; a per-server LRU of live `CodeSurface` instances

**Today.** `renderTile` keys the tile wrapper as `` key={kind === "tty" ? `${kind}${suffix}` : `${kind}${suffix}:${windowId}`} `` (line ~1793). The tile list is `visibleTiles` (from `layout.order`) plus `hiddenTiles` (kinds in `everOpened` not in `layout.order`, slot `-1`); `everOpened` is per-window and re-seeded from the new window's `layout.order` in the `[server, windowId, layout.order]` reset effect. The `case "code"` branch of `renderContent` mounts ONE `CodeSurface` with `workspaceSrc={codeWorkspaceSrc ?? null}` — the active window's src.

**After.**

- **Frame records.** `SurfaceLayout` keeps an ordered list (most-recently-shown last) of retained code frames — component state, the same tier as `everOpened`/zoom (§ Design Decisions "SurfaceLayout owns zoom/drag/mount-once"). Each record is `{ windowId: string; src: string; root: string }`: `src` is the window's resolved workspace src at the time the frame was created — the `/code/?workspace=<path>` URL the derivation GET produced, or the `?folder=` degrade src — and doubles as the frame's identity and React key (`code:${src}`); `root` is the window's `codeRootFor(win)` at creation, compared later for the root-change eviction. Lookup is by `windowId` (the workspace path is tab-keyed — it embeds the window id — so src and windowId identify the same frame; the record carries both so the lookup needs no string parsing). A record is created only when the window's src has resolved (non-null) and the code tile is open for that window: a pending tile has no frame and does not count toward the cap.
- **Rendering.** The active window's frame renders in its slot exactly as today (visible or `hidden` when the tile is closed/zoomed away — the existing P3 path). Every OTHER record renders as a hidden tile wrapper (`hidden` class, `slot: -1`) through the same `renderTile`/`allTiles` flat list (both desktop and mobile branches — "visible + hidden tiles render from ONE flat list" is load-bearing for reconciliation). Retained frames are hidden at display level only — never `visibility: hidden` or off-screen — matching the P3 mechanism the prototype measured (16 ms re-layout on `display:none → block`).
- **Per-instance seams unchanged.** Each retained `CodeSurface` keeps its own props: `gitRoot` (the record's `root`), `workspaceSrc` (the record's `src` — fixed; the mount-generation ref in `CodeSurface` already ignores later changes), `followSrc` (only the active window's follow reaches its frame — see § 3), `fetchBridgeStatus`, `reachable`, `shouldReclaimChord`, `onInteract`, `onProgrammaticFocus`, `onFolderNavigated`. `onInteract`/`onFolderNavigated` for a NON-active frame must be bound to that frame's `windowId` (not the active `windowId`/`focusKey`) or omitted: a hidden frame cannot receive focus or navigate, but a stale closure recording `code` focus against the wrong window's focus-memory key would be a latent bug. The first-boot rescue and chord-reclaim effects key on `[reachable, src]` inside `CodeSurface`; neither prop changes on show/hide, so neither re-arms — the apply MUST assert this (risk list).
- **The `[server, windowId]` reset effect** learns that `code` persists: `everOpened` is still re-seeded from the new window's `layout.order` (it governs which KINDS are mounted-hidden for the active window); the frame list is NOT reset — it is the cross-window state. The effect touches the LRU only to (a) bump the incoming window's record to most-recently-shown if one exists, and (b) run the overflow eviction after the incoming window's frame is created. `focusSlot(0)` / kind re-report, zoom, find, progress, web title, drag state behave exactly as today.
- **Header meta and chrome.** The visible code tile's header meta (root basename) reads from the active window as today. Hidden retained tiles render their wrapper `hidden`, so their chrome is invisible; no new chrome.

### 2. LRU cap and the four eviction triggers

- **Cap.** A named constant `CODE_FRAME_CAP_DESKTOP = 3` and `CODE_FRAME_CAP_MOBILE = 1`, selected by the existing `isMobile` prop `SurfaceLayout` already receives (app.tsx derives it from the shared narrow-or-coarse `isMobileViewport()` rule in `chrome-context.tsx`). The cap counts every live frame including the active window's — so desktop = active + up to 2 retained. A cap change at runtime (a viewport crossing the mobile threshold) evicts down to the new cap on the next reconciliation.
- **Eviction = unmount.** Evicting a frame removes its record; the tile wrapper leaves the flat list and React unmounts the `CodeSurface` (iframe unload → graceful disconnect → the extension host terminates, as today on every switch).
- **Trigger (a) — LRU overflow on switch.** When the incoming window needs a new frame and `records.length === cap`, evict the least-recently-SHOWN record (list head). "Shown" = became the active window's visible frame; a retained frame never bumps itself (it cannot be interacted with). The active window's own frame is never the eviction victim while it is active.
- **Trigger (b) — the frame's window killed/closed.** A window that leaves the server's live window set (killed via `Window: Kill`, closed by tmux, or gone from the SSE payload) has its record evicted. `SurfaceLayout` today receives only the active `window: ViewWindow | null`; app.tsx threads the set of live window ids for the current server (a `liveWindowIds: ReadonlySet<string>` or equivalent prop derived from the session context it already holds) and a reconciliation effect drops any record whose `windowId` is absent. Kill while hidden must evict without errors (risk list) — the hidden `CodeSurface` unmounts through the ordinary path.
- **Trigger (c) — the window's code root changed.** If a live window's `codeRootFor(win)` differs from its record's `root` AND the divergence is not the follow rule's own write (see § 3: a follow updates the record in place), the record is evicted so the next show mounts fresh at the new root's src. The active window's frame under an external root change (e.g. `rk tab` writing `@rk_win_code_root`) follows the same rule — today that case already remounts via the workspace re-derivation on the next mount generation; the change makes the eviction explicit.
- **Trigger (d) — reachability `true→false`.** When `codeReachable` flips to false every record is dropped (the frames are dead — the host is gone; `CodeSurface`'s own mount-generation rule already unmounts the iframe on this flip and renders the not-running state). A subsequent `false→true` starts with an empty LRU; the active window's frame mounts at its CURRENT map src (the existing mount-generation rule).
- **Closing the code tile** in a window keeps that window's frame retained (existing hide-never-unmount) and it keeps counting toward the cap. Opening it again shows the same instance.
- **No new user-facing action.** No palette verb is added (Constitution IV — resist creep; the description says none is needed). If apply finds a reload/evict verb necessary it MUST be palette-registered (Constitution V) — but the default is none.

### 3. `app/frontend/src/hooks/use-code-workspace.ts`: a per-window map of resolved workspace srcs

**Today.** `resolved` is a single `{ key, src } | null` keyed `${server}:${windowId}:${codeRoot}` (or the `seed-rejected:` namespace). A switch to another window means `resolved.key !== rootKey` → refetch → the tile renders `code-surface-pending` for a tick; switching back refetches again; a retained frame's src would be lost with the entry.

**After.**

- `resolved` becomes `Map<string, string>` (key → src) held in state (or a ref + version counter — apply picks; the map must survive across window switches for the lifetime of the hook). Keys keep today's shapes: `${server}:${windowId}:${root}` for the substrate (workspace) entry and `${server}:${windowId}:seed-rejected:${folder}` for the seed-refusal degrade. Nothing is persisted (Constitution IV: in-memory viewer state).
- The derivation effect fires only when the ACTIVE window's `rootKey` has no entry — an already-resolved window (a revisit) renders its src synchronously, so no `opening…` flash on a switch back. A `no-root` (409) result still leaves the entry absent (pending) and the next payload change re-drives the effect; a non-409 failure still writes the `?folder=` degrade src with exactly one console warning per key; the seed-rejected path still writes its own namespaced key and the substrate entry wins over it when both exist.
- **New return shape.** Besides today's `codeSrc` (the active window's src or null), the hook exposes the srcs of every resolved window for the renderer: e.g. `codeSrcFor(windowId: string): string | null` (a stable callback resolving through the map with the same substrate-over-fallback precedence, needing the window's root — so the hook takes or is handed a `windowsById` lookup) or a `codeSrcByWindow: ReadonlyMap<string, string>` keyed by windowId. Apply picks the shape that keeps `SurfaceLayout` prop-in/callback-out; the memory DD "SurfaceLayout owns zoom/drag/mount-once; app.tsx owns layout state" stays true.
- `followFolder(folder)` keeps its nonce-keyed `followSrc` (scoped to the active window as today) and updates THAT window's map entry (`${server}:${windowId}:${folder}` → the new workspace src). The renderer treats a follow as an in-place update of the window's frame record (`src` and `root` both move) — never as an eviction (§ 2 trigger c).
- Entries for killed windows are dropped alongside the frame eviction (the hook receives the same live-window signal, or app.tsx prunes on kill); otherwise the map is unbounded — its values are short strings and the window count per server is small.

### 4. `app.tsx`: threading

- `SurfaceLayout` stays keyed by `server` (`key={server}` at the render site) — a server change still remounts the grid and, with it, the LRU (per-server by construction).
- `codeWorkspaceSrc` becomes per-window: app.tsx passes the per-window lookup from § 3 (plus, for compatibility, the active window's `codeSrc` if the prop is kept). `codeFollowSrc` stays the active window's nonce-keyed follow.
- Thread the live-window-id set for the current server (trigger b) and keep passing `isMobile` (the cap) and `codeReachable` (trigger d).
- `useCodeWorkspace` is invoked with what it needs to resolve srcs for retained windows — at minimum the active window as today; for retained windows the map already holds their srcs from when they were active, so no additional fetches are needed for the retained set (a frame exists only for a window that was active with the tile open, which is exactly when its entry was written).

### 5. Tests
